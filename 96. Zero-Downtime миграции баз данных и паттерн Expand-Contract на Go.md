# Zero-Downtime миграции баз данных и паттерн Expand-Contract на Go

В этом файле собраны уникальные упражнения по теме **"Zero-Downtime миграции баз данных и паттерн Expand-Contract на Go"**, отсортированные по возрастанию сложности.

---

1. **Проблема даунтайма при миграциях схемы в HighLoad**: Изучите природу сбоев при обновлении базы данных под нагрузкой: эксклюзивная блокировка таблицы (ACCESS EXCLUSIVE LOCK), очередь ожидающих запросов, исчерпание пула соединений и каскадный отказ веб-серверов. Сформулируйте «золотое правило» Zero-Downtime: ни одна миграция схемы не должна блокировать операции чтения и записи более чем на несколько миллисекунд.

2. **Паттерн Expand-Contract (Parallel Run)**: Разберите фазы жизненного цикла эволюции схемы по паттерну Expand-Contract: 1) Expand (расширение схемы новым столбцом/таблицей без удаления старых); 2) Parallel Run / Dual Write (приложение пишет в обе структуры); 3) Backfill (фоновый перенос исторических данных); 4) Switch Read (переключение чтения на новую структуру); 5) Contract (удаление старых полей после полного обновления всех клиентов).

3. **Инструменты миграций на Go: golang-migrate vs goose**: Сравните популярные библиотеки миграций на Go: golang-migrate/migrate и pressly/goose. Изучите поддержку чистого SQL с транзакциями, возможность выполнения миграций в виде Go-функций (для сложной трансформации данных) и обработку ошибок блокировок.

4. **Транзакционные DDL-миграции в PostgreSQL**: Объясните, почему PostgreSQL превосходит MySQL в безопасности миграций: поддержка транзакционного DDL (BEGIN ... ALTER TABLE ... COMMIT). Покажите, что в случае ошибки в скрипте миграции изменения автоматически откатываются, исключая нахождение базы данных в промежуточном поврежденном состоянии.

5. **Обязательное правило: установка lock_timeout**: Напишите скрипт миграции, начинающийся с директивы SET lock_timeout = '2s'. Объясните механику: если миграция не может получить блокировку таблицы в течение 2 секунд из-за фоновых долгих транзакций, она аварийно прерывается, не выстраивая за собой очередь входящих пользовательских запросов.

6. **Безопасное добавление столбцов со значениями по умолчанию**: Изучите эволюцию PostgreSQL: в версиях до 11 команда ALTER TABLE ... ADD COLUMN ... DEFAULT 'val' приводила к полной перезаписи таблицы на диске с эксклюзивным локом на часы. Начиная с PG 11, добавление столбца со значением по умолчанию выполняется мгновенно как метаданные без перезаписи строк.

7. **Добавление ограничения NOT NULL без блокировки таблицы**: Прямое выполнение ALTER TABLE users ALTER COLUMN age SET NOT NULL сканирует всю таблицу под эксклюзивным локом. Реализуйте безопасный трехшаговый подход: 1) добавление проверочного ограничения CHECK (age IS NOT NULL) NOT VALID; 2) фоновая валидация без блокировки записи ALTER TABLE users VALIDATE CONSTRAINT users_age_not_null; 3) замена на нативный NOT NULL.

8. **Безопасное создание индексов: CREATE INDEX CONCURRENTLY**: Создание индекса на таблице с миллионами записей блокирует запись на минуты. Используйте директиву CREATE INDEX CONCURRENTLY. Объясните ее внутреннее устройство: два прохода по таблице без эксклюзивной блокировки. Обработайте статус INVALID индекса при сбое и напишите код автоматического повтора.

9. **Паттерн безопасного переименования столбца (Rename Column)**: Попытка переименовать колонку name в full_name одной командой ALTER TABLE RENAME COLUMN мгновенно ломает все работающие реплики старого сервиса. Спроектируйте 5-шаговый цикл Expand-Contract для безопасного переименования без единой секунды простоя.

10. **Шаг 1 Expand: добавление нового столбца**: Создайте миграцию, добавляющую новый столбец full_name TEXT NULL. Примените ее к боевой базе данных. Докажите, что текущая версия Go-приложения v1 продолжает работать, полностью игнорируя новый столбец.

11. **Шаг 2 Dual Write: двойная запись в Go-коде**: Выкатите версию приложения v2: слой репозитория при создании и обновлении пользователя записывает значение одновременно в name и full_name в одном SQL-запросе, но читает по-прежнему из name. Это гарантирует свежесть данных в обеих колонках.

12. **Шаг 3 Backfill: фоновый перенос исторических данных**: Напишите фоновый скрипт на Go для копирования данных из name в full_name для всех старых записей, созданных до внедрения версии v2. Настройте обработку записей порциями (batch processing).

13. **Потоковый бэкфилл порциями по первичному ключу (Chunking)**: Никогда не выполняйте UPDATE users SET full_name = name WHERE full_name IS NULL одним запросом (блокировка миллионов строк и раздувание WAL-лога!). Реализуйте пагинацию по первичному ключу: UPDATE users SET full_name = name WHERE id BETWEEN :start AND :end. Замерьте время одного чанка (не более 100 мс).

14. **Динамический троттлинг фонового бэкфилла**: Фоновый скрипт переноса данных не должен конкурировать с пользовательским трафиком. Реализуйте адаптивный троттлинг: перед каждым чанком скрипт запрашивает метрики базы данных (pg_stat_activity, задержку репликации WAL). При росте нагрузки скрипт увеличивает паузу time.Sleep.

15. **Шаг 4 Switch Read: переключение чтения на новую колонку**: После завершения бэкфилла и проверки 100% совпадения данных выкатите версию сервиса v3: чтение переключается на новую колонку full_name, а запись по-прежнему ведется в обе колонки для сохранения возможности мгновенного отката на v2.

16. **Шаг 5 Contract: удаление старой колонки**: Убедившись в стабильной работе v3 в течение нескольких дней, отключите запись в старую колонку (v4) и примените финальную миграцию сжатия: ALTER TABLE users DROP COLUMN name.

17. **Безопасное изменение типа данных столбца (int32 -> int64)**: Поле id в высоконагруженной таблице исчерпало диапазон 32-битного integer (2.1 млрд). Прямой ALTER TABLE ALTER COLUMN id TYPE BIGINT переписывает всю таблицу. Реализуйте миграцию типа по паттерну Expand-Contract: добавление колонки big_id, триггер синхронизации, бэкфилл и подмена первичного ключа.

18. **Паттерн View-based Abstraction для мгновенной подмены схемы**: Скройте структуру таблицы за представлением PostgreSQL: CREATE VIEW users_v1 AS SELECT id, name FROM users. Покажите, как перенаправление запросов приложения в View в сочетании с триггерами INSTEAD OF INSERT/UPDATE позволяет прозрачно трансформировать схему хранилища без изменения кода клиентов.

19. **Триггеры базы данных vs Двойная запись в Go: компромиссы**: Сравните два подхода к синхронизации старой и новой колонок: триггер PostgreSQL (BEFORE INSERT OR UPDATE) гарантирует 100% атомарность, но нагружает CPU базы данных; двойная запись в Go снижает нагрузку на СУБД, но требует аккуратной обработки сетевых сбоев.

20. **Миграции схемы в процессе Rolling Update в Kubernetes**: В процессе постепенного обновления подов (RollingUpdate) в кластере одновременно работают поды старой версии v1 и новой v2. Сформулируйте требование: база данных обязана быть совместима одновременно с обеими версиями кода в течение всего окна деплоя.

21. **Автоматическое тестирование совместимости схемы в CI/CD**: Напишите шаг CI/CD пайплайна: поднять базу данных с новой схемой, запустить тестовый набор старой версии приложения v1. Если старый код падает при обращении к новой схеме базы данных, билд прерывается, предотвращая аварийный релиз.

22. **Симуляция и поиск зависших блокировок в тестах**: Напишите тест с использованием pg_locks и pg_stat_activity: запустите долгую фоновую транзакцию чтения и попытайтесь применить миграцию DDL. Убедитесь, что настроенный lock_timeout корректно прерывает миграцию, а мониторинг генерирует алерт о конфликте блокировок.

23. **Секционирование больших таблиц (Partitioning) без даунтайма**: Таблица аудита выросла до сотен гигабайт. Реализуйте перевод таблицы на декларативное секционирование (Declarative Partitioning) без простоя: создание новой партиционированной таблицы audit_partitioned, настройка Dual-Write, поэтапный бэкфилл исторических партиций и подмена таблиц через ALTER TABLE RENAME.

24. **Безопасное добавление внешних ключей (Foreign Key Constraints)**: Команда ALTER TABLE orders ADD CONSTRAINT fk_user FOREIGN KEY (user_id) REFERENCES users(id) сканирует обе таблицы с блокировкой. Реализуйте безопасное добавление: добавление с опцией NOT VALID (валидируются только новые строки), а затем валидация существующих строк через ALTER TABLE orders VALIDATE CONSTRAINT fk_user.

25. **Стратегия отката миграций: почему Down-миграции опасны**: Проанализируйте, почему выполнение Down-миграций (удаление добавленных колонок) на проде при аварии может привести к безвозвратной потере новых пользовательских данных. Объясните приоритет стратегии Forward-Fix (исправление ошибки накатом новой миграции вперед).

26. **Мониторинг лага репликации во время миграций**: Массивные операции DDL и пакетные бэкфиллы генерируют гигабайты WAL-логов, вызывая отставание реплик PostgreSQL. Напишите код опроса pg_stat_replication: если replay_lag превышает 1 секунду, приостановите выполнение миграционных чанков.

27. **Shadow Writing и валидация целостности данных**: Перед полным переключением чтения на новую структуру данных напишите сервис теневой проверки: фоновая горутина асинхронно сверяет результаты выборки из старой и новой таблицы (diff(oldRow, newRow)). При обнаружении несовпадений генерируется алерт без влияния на пользователей.

28. **Zero-Downtime миграции в NoSQL (Ленивая миграция документов в MongoDB)**: В документо-ориентированных СУБД (MongoDB) нет жесткой схемы DDL. Реализуйте паттерн On-Read Migration: при чтении документа старого формата v1 Go-сервер на лету дополняет его полями по умолчанию до формата v2 и асинхронно сохраняет обновленную версию документа в базу.

29. **Безопасное удаление неиспользуемых таблиц**: Перед выполнением DROP TABLE old_orders переименуйте таблицу в _deprecated_old_orders, отзовите права на запись и выдержите паузу в 14 дней. Если ни один сервис не выдал ошибку отсутствия таблицы, выполните удаление.

30. **Полнофункциональная утилита Zero-Downtime миграций на Go**: Создайте законченный инструмент на Go: консольная утилита фонового переноса данных с поддержкой контроля размера чанков, мониторингом задержки репликации PostgreSQL, автоматической установкой lock_timeout, верификацией целостности данных и корректным прерыванием по SIGINT с сохранением прогресса.
