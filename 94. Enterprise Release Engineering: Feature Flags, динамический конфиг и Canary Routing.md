# Enterprise Release Engineering: Feature Flags, динамический конфиг и Canary Routing

В этом файле собраны уникальные упражнения по теме **"Enterprise Release Engineering: Feature Flags, динамический конфиг и Canary Routing"**, отсортированные по возрастанию сложности.

---

1. **Философия Feature Flags: разделение деплоя и релиза**: Изучите фундаментальный принцип современной Enterprise-разработки: Deploy $\neq$ Release. Объясните, как флаги функционала (Feature Flags / Toggles) позволяют непрерывно сливать код в ветку `main` без создания долгоживущих фиче-веток (Trunk-Based Development), снижая риски интеграционного ада (Merge Hell).

2. **Классификация флагов по Мартину Фаулеру**: Разберите 4 типа фиче-флагов: Release Toggles (временные флаги для скрытия незавершенного функционала), Experiment Toggles (флаги для A/B-тестирования), Ops Toggles (рубильники безопасности и защита от перегрузок) и Permission Toggles (управление доступом по ролям и тарифам). Опишите их жизненный цикл и динамичность.

3. **Базовый потокобезопасный менеджер флагов в памяти**: Создайте простейший менеджер флагов на Go: структура `FlagManager` со словарем `map[string]bool` и защитой через `sync.RWMutex`. Реализуйте методы `Set(name string, enabled bool)` и `IsEnabled(name string) bool`. Напишите тест на параллельное чтение и запись с флагом `-race`.

4. **Открытый стандарт OpenFeature и экосистема Go SDK**: Изучите открытый отраслевой стандарт OpenFeature (проект CNCF). Разберите ключевые концепции: `Provider` (источник данных о флагах), `Client` (интерфейс для разработчиков приложений), `EvaluationContext` (контекст вычисления) и `Hook` (перехватчики событий).

5. **Подключение официального Go SDK open-feature/go-sdk**: Установите `github.com/open-feature/go-sdk`. Настройте провайдер в памяти: `openfeature.SetProvider(inmemory.NewProvider(flagsMap))`. Создайте клиент: `client := openfeature.NewClient("order-service")`. Выполните вызов флага: `isNewCheckout, err := client.BooleanValue(ctx, "new_checkout_flow", false, evalCtx)`.

6. **Контекст вычисления (Evaluation Context) и таргетинг**: Реализуйте контекст пользователя `openfeature.NewEvaluationContext(targetingKey, attributes)`: передайте `userId`, `userGroup`, `country`, `appVersion`. Напишите правило: «Флаг включен, если пользователь является сотрудником компании (`userGroup == "beta-testers"`) ИЛИ находится в стране `RU`».

7. **Процентные раскатки (Percentage Rollouts) и детерминированное хэширование**: Реализуйте алгоритм плавной процентной раскатки функционала (например, включить фичу для 15% пользователей). Используйте функцию консистентного хэширования: `hash := crc32.ChecksumIEEE([]byte(flagName + ":" + userId)) % 100`. Докажите, что конкретный пользователь всегда попадает в одну и ту же группу при неизменном проценте.

8. **Сегментация пользователей (User Segmentation)**: Спроектируйте правила сегментации: выделение сегментов «VIP-клиенты», «Пользователи мобильного приложения iOS версии > 4.2», «Корпоративные клиенты с тарифом Enterprise». Напишите движок правил, сопоставляющий атрибуты контекста с критериями сегментов.

9. **Сложные логические правила таргетинга (Rule Engine)**: Разработайте интерпретатор логических выражений для флагов на Go: поддержка условий с операторами `AND`, `OR`, `NOT`, проверки вхождения в список (`IN`), сравнения чисел (`>`, `<`) и семантического сравнения версий (SemVer, например `version >= "2.4.0"`).

10. **Аварийные рубильники (Kill Switches) для высоконагруженных систем**: Реализуйте операционный флаг безопасности (Ops Toggle): при резком росте нагрузки или сбое стороннего сервиса рекомендаций дежурный инженер активирует флаг `disable_recommendations`. Сервис мгновенно отключает тяжелые вызовы рекомендаций, возвращая клиентам статическую заглушку и спасая сайт от падения.

11. **Интеграция с открытыми серверами управления флагами (Flipt)**: Подключите OpenFeature провайдер для открытого сервера управления флагами Flipt (`github.com/flipt-io/flipt-openfeature-provider-go`). Разверните Flipt в Docker, настройте получение правил флагов по gRPC и продемонстрируйте изменение флага через Flipt Web UI без перезапуска Go-сервиса.

12. **Хранение и распространение флагов через Redis Pub/Sub**: Для сверхбыстрого доступа флаги должны читаться из памяти (< 1 мкс), но синхронизироваться между десятками подов. Реализуйте провайдер с локальным кэшем L1: при изменении флага в Redis публикуется событие в Pub/Sub канал `flags:updates`, и все реплики сервиса мгновенно обновляют свои локальные мапы.

13. **Канареечные релизы (Canary Releases) с канареечной маршрутизацией**: Используйте фиче-флаги для канареечной маршрутизации: при вызове метода HTTP/gRPC сервис проверяет флаг `canary_v2_backend`. Если флаг активен для данного запроса, шлюз перенаправляет трафик на новый микросервис v2, а для остальных запросов — на стабильный v1.

14. **Канареечная маршрутизация на уровне HTTP Middleware**: Напишите HTTP-middleware для Canary Routing: извлечение сессионной куки или заголовка, вычисление флага раскатки, добавление заголовка `X-Upstream-Version: v2` и маршрутизация на соответствующий пул подов в Kubernetes Service Mesh.

15. **Организация A/B тестирования и сбор событий взаимодействия**: Реализуйте инфраструктуру A/B тестирования: функция вычисления флага `client.StringValue(ctx, "button_color", "blue", evalCtx)` возвращает один из вариантов (`"blue"`, `"green"`, `"red"`). Залогируйте факт показа варианта в Kafka/ClickHouse для последующего расчета статистической значимости конверсии.

16. **Хуки OpenFeature (Hooks) для аудита и телеметрии**: Реализуйте кастомный хук OpenFeature, реализующий методы `Before`, `After`, `Error`, `Finally`. Автоматически экспортируйте в Prometheus счетчик вычислений флагов: `feature_flag_evaluations_total{flag_name, variant, reason}` и логируйте неожиданные ошибки оценки.

17. **Аудит изменений и система одобрения флагов**: Спроектируйте аудит-лог изменения флагов: структура `FlagAuditEvent` с полями `Author`, `FlagKey`, `OldValue`, `NewValue`, `Timestamp`, `Reason`. Напишите вебхук-уведомление в корпоративный мессенджер (Slack / Mattermost / Telegram) при каждом переключении флага в проде.

18. **Управление техническим долгом: процесс вывода флагов из эксплуатации**: Флаги, оставшиеся в кодовой базе после завершения релиза (Stale Flags), загрязняют код условиями `if/else`. Разработайте стратегию жизненного цикла флага: добавление метаданных `createdAt`, `ownerEmail`, `expirationDate`. Реализуйте фоновый аудит, сигнализирующий о флагах, активных более 60 дней.

19. **Статический анализатор для поиска мертвых фиче-флагов**: Используя пакет `go/ast` (из Главы 55), напишите утилиту командной строки, которая сканирует кодовую базу, находит вызовы `client.BooleanValue` для закрытых флагов и указывает номера строк кода, готовые к удалению старых веток `if/else`.

20. **Динамическая перезагрузка конфигурации (Hot Reload) с fsnotify**: Перейдите к динамической конфигурации приложения: подключите библиотеку `fsnotify/fsnotify`. Напишите наблюдатель за файлом `config.yaml`: при изменении файла на диске сервис перечитывает YAML-конфигурацию на лету без перезапуска процесса и сброса активных соединений.

21. **Управление конфигурацией с помощью библиотеки Viper**: Изучите библиотеку `spf13/viper`: инициализация `viper.SetConfigName("config")`, вызов `viper.WatchConfig()` и регистрация коллбэка `viper.OnConfigChange(func(e fsnotify.Event) { ... })`. Покажите, как безопасно читать обновленные значения параметров.

22. **Валидация динамической конфигурации перед применением**: Что если администратор допустил синтаксическую ошибку в YAML или указал отрицательный таймаут? Процесс не должен падать! Реализуйте двухфазную перезагрузку: новая конфигурация парсится и проверяется функцией `Validate()`. Если конфиг невалиден, изменение отклоняется с записью в лог ошибок, а сервис продолжает работать на старом конфиге.

23. **Потокобезопасная атомарная подмена конфига через atomic.Pointer**: Чтение параметров конфигурации происходит в тысячах параллельных горутин. Использование мьютекса создает точку блокировки. Примените атомарный указатель из Go 1.19+: `type AppConfigHolder struct { cfg atomic.Pointer[AppConfig] }`. Докажите на бенчмарке нулевую задержку чтения `holder.cfg.Load()`.

24. **Многоуровневая иерархия конфигурации (Config Precedence)**: Реализуйте правильный порядок переопределения параметров в Enterprise-системе: 1) Флаги командной строки (наивысший приоритет) -> 2) Переменные окружения (`APP_*`) -> 3) Удаленный конфиг-сервер (Consul/etcd) -> 4) Локальный файл `config.yaml` -> 5) Зашитые значения по умолчанию (Default).

25. **Тестирование кода с фиче-флагами в Go юнит-тестах**: Напишите юнит-тесты бизнес-логики: покажите, как протестировать обе ветки функционала (`flag=true` и `flag=false`) с использованием `testify`. Создайте тестовый мок-провайдер, позволяющий динамически переключать флаги прямо внутри тела конкретного теста без влияния на соседние параллельные тесты.

26. **Корреляция метрик и флагов в Prometheus / Grafana**: Спроектируйте панель мониторинга Grafana: наложите вертикальные маркеры событий переключения фиче-флагов (Grafana Annotations) поверх графиков задержек ответов (p99 latency) и частоты ошибок (5xx rate). Это позволяет мгновенно понять, какая именно фича вызвала деградацию системы.

27. **Безопасный оффлайн-режим (Graceful Fallback) при сбое сервера флагов**: Что делать, если внешний сервер управления флагами (Flipt/LaunchDarkly) стал недоступен из-за сетевой аварии? Клиент не должен блокировать запросы! Реализуйте безопасный fallback: использование закешированных значений из локального файла или возврат безопасных дефолтных значений по умолчанию.

28. **Мультитенантные фиче-флаги в B2B SaaS**: В B2B системе разные клиенты (Tenant A, Tenant B) платят за разные тарифные планы. Реализуйте многоуровневый флаг: флаг включен глобально -> но активирован только для компаний на тарифе `Enterprise` -> с возможностью точечного включения фичи для конкретного пилотного пользователя внутри компании.

29. **Автоматический откат канареечных релизов (Auto-Rollback)**: Напишите фоновый супервизор канареечного релиза на Go: супервизор непрерывно опрашивает Prometheus API. Если в течение 3 минут после включения флага для 10% пользователей процент ошибок 5xx превышает 0.5%, супервизор автоматически переключает флаг в `false`, отправляет алерт и предотвращает масштабную аварию.

30. **Комплексная платформа Release Engineering и Dynamic Config на Go**: Разработайте законченную корпоративную систему: интеграция OpenFeature SDK с провайдером в памяти и синхронизацией через Redis, динамический конфиг на `atomic.Pointer` с валидацией и наблюдением через `fsnotify`, правила таргетинга пользователей, канареечные процентные раскатки, метрики вычислений и авто-откат при сбоях.
