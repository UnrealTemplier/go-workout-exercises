Упражнение #1

Динамическое переключение уровня логирования на лету через slog.LevelVar

📌 Условие задачи

Динамический уровень логов: В проде нельзя просто перезапустить сервер, чтобы включить Debug. Создай переменную var logLevel = new(slog.LevelVar). Настрой логгер с ней. Напиши HTTP-хендлер PUT /loglevel, который принимает JSON {"level": "DEBUG"} и меняет уровень "на лету" через logLevel.Set(slog.LevelDebug).

💡 Теоретический фундамент и концепция

slog.LevelVar — потокобезопасная переменная уровня логирования (атомарное значение). Она реализует интерфейс slog.Leveler. При передаче &levelVar в опции хендлера slog.HandlerOptions{Level: levelVar} изменение уровня через levelVar.Set(...) мгновенно активирует новые уровни логирования во всех горутинах без блокировок и перезапуска процесса.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим глобальный или контекстный logLevel := new(slog.LevelVar) (по умолчанию slog.LevelInfo).
2. Инициализируем slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: logLevel})).
3. Реализуем HTTP-хендлер handleSetLogLevel, парсящий JSON и вызывающий logLevel.Set(...).
4. В main сымитируем HTTP-запрос на смену уровня с INFO на DEBUG и проверим вывод.
📄 main.go 
package main

import (
	"bytes"
	"encoding/json"
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
	"strings"
)

var logLevel = new(slog.LevelVar) // По умолчанию LevelInfo (0)

type LevelRequest struct {
	Level string `json:"level"`
}

func logLevelHandler(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodPut {
		http.Error(w, "Method not allowed", http.StatusMethodNotAllowed)
		return
	}

	var req LevelRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		http.Error(w, err.Error(), http.StatusBadRequest)
		return
	}

	switch strings.ToUpper(req.Level) {
	case "DEBUG":
		logLevel.Set(slog.LevelDebug)
	case "INFO":
		logLevel.Set(slog.LevelInfo)
	case "WARN":
		logLevel.Set(slog.LevelWarn)
	case "ERROR":
		logLevel.Set(slog.LevelError)
	default:
		http.Error(w, "Unknown level", http.StatusBadRequest)
		return
	}

	slog.Info("Уровень логирования успешно изменен", "new_level", logLevel.Level().String())
	w.WriteHeader(http.StatusOK)
	_, _ = w.Write([]byte(`{"status":"ok"}`))
}

func main() {
	// 1. Инициализация JSON-логгера с динамическим LevelVar
	handler := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: logLevel})
	logger := slog.New(handler)
	slog.SetDefault(logger)

	fmt.Println("--- 1. Начальное состояние (LevelInfo) ---")
	slog.Debug("Этот Debug-лог НЕ будет напечатан")
	slog.Info("Сервер запущен в рабочем режиме")

	// 2. Имитация вызова PUT /loglevel с телом {"level": "DEBUG"}
	fmt.Println("\n--- 2. Динамическое переключение на DEBUG через HTTP ---")
	body := bytes.NewBufferString(`{"level": "DEBUG"}`)
	req := httptest.NewRequest(http.MethodPut, "/loglevel", body)
	rec := httptest.NewRecorder()

	logLevelHandler(rec, req)

	// 3. Проверка после переключения
	fmt.Println("\n--- 3. После переключения (LevelDebug) ---")
	slog.Debug("Диагностический лог: подробное состояние кэша", "cache_keys", 450)
	slog.Info("Запрос успешно обработан")
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

slog.LevelVar использует sync/atomic.Int64 внутри. Метод Enabled(ctx, level) вызывается перед форматированием атрибутов, поэтому при выключенном Debug не происходит аллокаций памяти под аргументы лога.

⚠️ Частые грабли и ошибки новичков

Если передать в slog.HandlerOptions{Level: slog.LevelInfo} обычное значение, а не указатель *slog.LevelVar, динамическое изменение будет невозможно.

Упражнение #2

Структурированное логирование в формате JSON с полями time, level, msg

📌 Условие задачи

Установите и настройте структурированный логгер zerolog или log/slog. Выведите JSON-логи в stdout с полями level, msg, time.

💡 Теоретический фундамент и концепция

Структурированное логирование (Structured Logging) форматирует каждую запись как валидный JSON-объект. Это стандарт для современных Cloud-Native сред (Kubernetes, AWS CloudWatch, ELK, Grafana Loki), позволяющий индексировать и фильтровать логи по полям без медленных регулярных выражений.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим slog.NewJSONHandler(os.Stdout, nil).
2. Обернем в slog.New(handler).
3. Запишем информационный и предупреждающий логи с атрибутами user_id, ip, latency_ms.
4. В main убедимся в валидности выводимого JSON.
📄 main.go 
package main

import (
	"log/slog"
	"os"
	"time"
)

func main() {
	// Создание JSON-хендлера, пишущего в стандартный вывод
	handler := slog.NewJSONHandler(os.Stdout, nil)
	logger := slog.New(handler)

	// Запись структурированных логов с типизированными атрибутами
	logger.Info("Входящее HTTP-соединение",
		slog.String("method", "GET"),
		slog.String("path", "/api/v1/users"),
		slog.Int("status", 200),
		slog.Duration("latency", 12*time.Millisecond),
	)

	logger.Warn("Превышение порога потребления памяти",
		slog.Float64("memory_used_mb", 850.5),
		slog.Float64("memory_limit_mb", 1024.0),
	)
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

slog.JSONHandler сериализует ключи и значения напрямую в кольцевой байтовый буфер без рефлексии для базовых типов (slog.String, slog.Int, slog.Float64), обеспечивая скорость работы близкую к zerolog и zap.

⚠️ Частые грабли и ошибки новичков

Не используйте неструктурированную склейку строк fmt.Sprintf внутри msg — все динамические параметры должны передаваться как отдельные атрибуты key/value.

Упражнение #3

Маскирование персональных данных (PII) через ReplaceAttr в slog

📌 Условие задачи

Настройте глобальный slog.Logger с JSONHandler и ReplaceAttr для маскировки PII-данных (email, телефон, password → ***).

💡 Теоретический фундамент и концепция

Функция ReplaceAttr в slog.HandlerOptions перехватывает каждый атрибут перед записью. Это позволяет централизованно маскировать персональные данные (Personally Identifiable Information — PII) в соответствии с законами о защите персональных данных (152-ФЗ, GDPR, PCI-DSS).

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим функцию sanitizeAttrs(groups []string, a slog.Attr) slog.Attr.
2. Проверим ключ a.Key: для password, email, phone, card_number заменим значение на "***".
3. Инициализируем slog.NewJSONHandler с этой опцией.
4. В main вызовем логирование и убедимся, что секреты скрыты.
📄 main.go 
package main

import (
	"log/slog"
	"os"
	"strings"
)

func sanitizePII(groups []string, a slog.Attr) slog.Attr {
	// Список конфиденциальных ключей для маскирования
	switch strings.ToLower(a.Key) {
	case "password", "token", "secret", "cvv":
		return slog.String(a.Key, "[REDACTED]")
	case "email":
		// Частичное маскирование email: a***@corp.ru
		emailStr := a.Value.String()
		if parts := strings.Split(emailStr, "@"); len(parts) == 2 && len(parts[0]) > 0 {
			masked := string(parts[0][0]) + "***@" + parts[1]
			return slog.String(a.Key, masked)
		}
		return slog.String(a.Key, "***@***")
	case "phone":
		return slog.String(a.Key, "+7-***-***-**-99")
	}
	return a
}

func main() {
	opts := &slog.HandlerOptions{
		ReplaceAttr: sanitizePII,
	}
	handler := slog.NewJSONHandler(os.Stdout, opts)
	logger := slog.New(handler)
	slog.SetDefault(logger)

	slog.Info("Регистрация нового пользователя",
		slog.String("username", "alex_dev"),
		slog.String("email", "alexander.ivanov@company.ru"),
		slog.String("phone", "+79991234599"),
		slog.String("password", "SuperSecretP@ss123"),
	)
}

slog.Group(key, attrs...) объединяет группу атрибутов во вложенный JSON-объект. Это структурирует логи сложных подсистем (HTTP-запрос, метаданные клиента, параметры БД).

Упражнение #5

HTTP Middleware с автоматической трассировкой request_id через logger.With

📌 Условие задачи

Реализуйте middleware, который добавляет request_id (UUID) в контекст и автоматически пробрасывает его во все логи через slog.Logger.With("request_id", id).

💡 Теоретический фундамент и концепция

Дочерний логгер, созданный через logger.With("request_id", id), сохраняет этот атрибут во всех последующих записях. Сохранение логгера в context.Context гарантирует доступ к сквозному идентификатору запроса во всех слоях бизнес-логики.

🔍 Пошаговый ход решения и ход мысли инженера

1. Определим кастомный ключ контекста type ctxKey struct{}.
2. Напишем middleware RequestIDMiddleware(logger *slog.Logger) func(http.Handler) http.Handler.
3. В хендлере извлечем логгер из контекста и запишем лог.
4. В main протестируем выполнение запроса.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
)

type loggerKey struct{}

// Middleware обогащает логгер уникальным request_id и сохраняет в контекст
func RequestIDMiddleware(baseLogger *slog.Logger) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			reqID := r.Header.Get("X-Request-ID")
			if reqID == "" {
				reqID = "req-uuid-9847192" // Генерация UUID
			}

			// Создаем дочерний логгер с зафиксированным request_id
			reqLogger := baseLogger.With(slog.String("request_id", reqID))
			ctx := context.WithValue(r.Context(), loggerKey{}, reqLogger)

			w.Header().Set("X-Request-ID", reqID)
			next.ServeHTTP(w, r.WithContext(ctx))
		})
	}
}

// Хелпер для извлечения логгера из контекста
func FromContext(ctx context.Context) *slog.Logger {
	if l, ok := ctx.Value(loggerKey{}).(*slog.Logger); ok {
		return l
	}
	return slog.Default()
}

func orderHandler(w http.ResponseWriter, r *http.Request) {
	logger := FromContext(r.Context())
	logger.Info("Проверка остатков товара на складе", "item_id", "SKU-5501")
	logger.Info("Платеж успешно авторизован", "amount_rub", 4500)
	w.WriteHeader(http.StatusOK)
}

func main() {
	baseLogger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
	mw := RequestIDMiddleware(baseLogger)

	handler := mw(http.HandlerFunc(orderHandler))

	req := httptest.NewRequest(http.MethodGet, "/order/checkout", nil)
	req.Header.Set("X-Request-ID", "trace-777-abc-999")
	rec := httptest.NewRecorder()

	fmt.Println("--- Логирование с автоматическим request_id ---")
	handler.ServeHTTP(rec, req)
}

Упражнение #8

Маршрутизация логов: Error в файл, Info в stdout через составной Handler

📌 Условие задачи

Создайте slog.Handler, который записывает логи уровня Error и выше в отдельный файл (error.log), а Info — в stdout.

💡 Теоретический фундамент и концепция

Составной обработчик (Fork / Split Handler) разделяет поток записей: стандартные информационные логи идут в stdout контейнера, а критические ошибки дублируются в постоянный файл на диске или отдельный сервис алертинга.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру SplitHandler struct { infoHandler, errHandler slog.Handler }.
2. Реализуем методы интерфейса slog.Handler: Enabled, Handle, WithAttrs, WithGroup.
3. В Handle(ctx, r) отправляем все логи в infoHandler, а при r.Level >= slog.LevelError — также в errHandler.
4. В main проверим запись в консоль и в файл error.log.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"log/slog"
	"os"
)

type SplitHandler struct {
	stdoutHandler slog.Handler
	fileHandler   slog.Handler
}

func NewSplitHandler(file *os.File) *SplitHandler {
	return &SplitHandler{
		stdoutHandler: slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo}),
		fileHandler:   slog.NewJSONHandler(file, &slog.HandlerOptions{Level: slog.LevelError}),
	}
}

func (h *SplitHandler) Enabled(ctx context.Context, level slog.Level) bool {
	return h.stdoutHandler.Enabled(ctx, level) || h.fileHandler.Enabled(ctx, level)
}

func (h *SplitHandler) Handle(ctx context.Context, r slog.Record) error {
	if h.stdoutHandler.Enabled(ctx, r.Level) {
		_ = h.stdoutHandler.Handle(ctx, r)
	}
	if r.Level >= slog.LevelError && h.fileHandler.Enabled(ctx, r.Level) {
		_ = h.fileHandler.Handle(ctx, r)
	}
	return nil
}

func (h *SplitHandler) WithAttrs(attrs []slog.Attr) slog.Handler {
	return &SplitHandler{
		stdoutHandler: h.stdoutHandler.WithAttrs(attrs),
		fileHandler:   h.fileHandler.WithAttrs(attrs),
	}
}

func (h *SplitHandler) WithGroup(name string) slog.Handler {
	return &SplitHandler{
		stdoutHandler: h.stdoutHandler.WithGroup(name),
		fileHandler:   h.fileHandler.WithGroup(name),
	}
}

func main() {
	errFile, _ := os.Create("error.log")
	defer func() {
		errFile.Close()
		_ = os.Remove("error.log")
	}()

	logger := slog.New(NewSplitHandler(errFile))

	fmt.Println("--- Логи в Stdout ---")
	logger.Info("Обычный запрос обработан успешно", "user", "alice")
	logger.Error("Критический сбой базы данных", "error", "connection refused", "db", "postgres-primary")

	errData, _ := os.ReadFile("error.log")
	fmt.Println("\n--- Содержимое файла error.log ---")
	fmt.Print(string(errData))
}

Упражнение #9

Отправка Error-логов во внешний Webhook/Sentry через кастомный slog.Handler

📌 Условие задачи

Реализуйте slog.Handler, который отправляет Error-логи в Sentry или аналогичную систему (через HTTP-запрос).

💡 Теоретический фундамент и концепция

Интеграция с системами мониторинга ошибок (Sentry, Bugsnag, Alertmanager) строится как специализированный slog.Handler, перехватывающий записи с r.Level >= slog.LevelError и отправляющий JSON-payload в асинхронный HTTP-канал.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру SentryHandler struct { next slog.Handler; webhookURL string }.
2. В методе Handle(ctx, r) проверим if r.Level >= slog.LevelError.
3. Соберем атрибуты ошибки и отправим POST запрос.
4. В main сымитируем HTTP-сервер Sentry через httptest.Server и протестируем отправку.
📄 main.go 
package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
)

type SentryAlertHandler struct {
	baseHandler slog.Handler
	sentryURL   string
}

func (h *SentryAlertHandler) Enabled(ctx context.Context, level slog.Level) bool {
	return h.baseHandler.Enabled(ctx, level)
}

func (h *SentryAlertHandler) Handle(ctx context.Context, r slog.Record) error {
	// 1. Всегда пишем в базовый stdout
	_ = h.baseHandler.Handle(ctx, r)

	// 2. Если ошибка — отправляем алерт во внешний Webhook
	if r.Level >= slog.LevelError {
		payload := map[string]any{
			"timestamp": r.Time,
			"message":   r.Message,
			"level":     r.Level.String(),
		}
		r.Attrs(func(a slog.Attr) bool {
			payload[a.Key] = a.Value.Any()
			return true
		})

		body, _ := json.Marshal(payload)
		// Асинхронная отправка (симуляция)
		go func(data []byte) {
			_, _ = http.Post(h.sentryURL, "application/json", bytes.NewReader(data))
		}(body)
	}
	return nil
}

func (h *SentryAlertHandler) WithAttrs(attrs []slog.Attr) slog.Handler {
	return &SentryAlertHandler{baseHandler: h.baseHandler.WithAttrs(attrs), sentryURL: h.sentryURL}
}

func (h *SentryAlertHandler) WithGroup(name string) slog.Handler {
	return &SentryAlertHandler{baseHandler: h.baseHandler.WithGroup(name), sentryURL: h.sentryURL}
}

func main() {
	// Симуляция сервера Sentry
	sentryMock := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		var alert map[string]any
		_ = json.NewDecoder(r.Body).Decode(&alert)
		fmt.Printf("[SENTRY ALERT RECEIVED] Ошибка: %s | Детали: %v\n", alert["message"], alert["component"])
		w.WriteHeader(http.StatusOK)
	}))
	defer sentryMock.Close()

	handler := &SentryAlertHandler{
		baseHandler: slog.NewJSONHandler(os.Stdout, nil),
		sentryURL:   sentryMock.URL,
	}
	logger := slog.New(handler)

	logger.Info("Штатный запуск модуля")
	logger.Error("Падение пула соединений", slog.String("component", "RedisCluster"), slog.Int("retries", 3))
}

Контекстное логирование: проброс дочернего логгера через context.Context

📌 Условие задачи

[Контекстные логи]: Создай middleware для HTTP-сервера, который генерирует request_id (UUID), создает дочерний логгер logger.With("request_id", id) и кладет его в context.Context (slog.NewContext). В обработчике достань логгер из контекста и запиши лог.

💡 Теоретический фундамент и концепция

Паттерн Context-Bound Logger позволяет передавать преднастроенный экземпляр логгера через стандартный context.Context по всей цепочке вызовов: HTTP Handler -> Service -> Repository без необходимости передавать *slog.Logger отдельным аргументом в каждую функцию.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим middleware с генерацией request_id.
2. Создадим дочерний логгер: subLogger := logger.With("request_id", reqID).
3. Сохраним логгер в контекст через ctx := context.WithValue(...).
4. В сервисном слое извлечем логгер и сделаем запись.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
)

type ctxLoggerKey struct{}

func InjectLoggerMiddleware(base *slog.Logger) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			reqID := "uuid-8831-4421" // В проде: uuid.NewString()
			reqLogger := base.With(slog.String("request_id", reqID), slog.String("uri", r.RequestURI))

			ctx := context.WithValue(r.Context(), ctxLoggerKey{}, reqLogger)
			next.ServeHTTP(w, r.WithContext(ctx))
		})
	}
}

func LoggerFromContext(ctx context.Context) *slog.Logger {
	if l, ok := ctx.Value(ctxLoggerKey{}).(*slog.Logger); ok {
		return l
	}
	return slog.Default()
}

// Доменный сервис получает только контекст
func processPaymentService(ctx context.Context, amount int) {
	log := LoggerFromContext(ctx)
	log.Info("Обработка списания средств", "amount", amount, "gateway", "T-Bank")
}

func paymentHTTPHandler(w http.ResponseWriter, r *http.Request) {
	processPaymentService(r.Context(), 15000)
	w.WriteHeader(http.StatusOK)
}

func main() {
	jsonHandler := slog.NewJSONHandler(os.Stdout, nil)
	baseLogger := slog.New(jsonHandler)

	mw := InjectLoggerMiddleware(baseLogger)
	handler := mw(http.HandlerFunc(paymentHTTPHandler))

	req := httptest.NewRequest(http.MethodPost, "/api/v1/payments", nil)
	rec := httptest.NewRecorder()

	fmt.Println("--- Исполнение запроса с контекстным логгером ---")
	handler.ServeHTTP(rec, req)
}

Упражнение #11

Комплексный HTTP Middleware для структурированного аудита запросов

📌 Условие задачи

Напишите middleware, который логирует полный HTTP-запрос/ответ (method, path, status, latency, user_agent, ip) в структурированном JSON.

💡 Теоретический фундамент и концепция

Для логирования статус-кода ответа необходимо обернуть стандартный http.ResponseWriter в кастомную структуру responseWriterInterceptor, перехватывающую вызов WriteHeader(statusCode).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру statusRecorder struct { http.ResponseWriter; statusCode int }.
2. В middleware зафиксируем start := time.Now().
3. В блоке defer рассчитаем duration := time.Since(start) и запишем структурированный лог через logger.Info.
4. В main протестируем выполнение запроса.
📄 main.go 
package main

import (
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
	"time"
)

type statusRecorder struct {
	http.ResponseWriter
	statusCode int
}

func (r *statusRecorder) WriteHeader(code int) {
	r.statusCode = code
	r.ResponseWriter.WriteHeader(code)
}

func LoggingMiddleware(logger *slog.Logger) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			start := time.Now()
			rec := &statusRecorder{ResponseWriter: w, statusCode: http.StatusOK}

			defer func() {
				latency := time.Since(start)
				logger.Info("HTTP Request Completed",
					slog.String("method", r.Method),
					slog.String("path", r.URL.Path),
					slog.Int("status", rec.statusCode),
					slog.Duration("latency", latency),
					slog.String("ip", r.RemoteAddr),
					slog.String("user_agent", r.UserAgent()),
				)
			}()

			next.ServeHTTP(rec, r)
		})
	}
}

func apiHandler(w http.ResponseWriter, r *http.Request) {
	w.WriteHeader(http.StatusCreated)
	_, _ = w.Write([]byte(`{"id": 101}`))
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
	mw := LoggingMiddleware(logger)

	handler := mw(http.HandlerFunc(apiHandler))

	req := httptest.NewRequest(http.MethodPost, "/api/v1/orders", nil)
	req.Header.Set("User-Agent", "Go-Workout-Agent/1.0")
	rec := httptest.NewRecorder()

	fmt.Println("--- Исполнение запроса через LoggingMiddleware ---")
	handler.ServeHTTP(rec, req)
}

Упражнение #12

Кастомный slog.Handler для автоматического извлечения контекстных полей

📌 Условие задачи

Кастомный slog.Handler (Инжект контекста): Напиши обертку над slog.JSONHandler. Переопредели метод Handle(ctx, record). Если в ctx лежит значение RequestID или UserID, твой хендлер должен автоматически добавлять эти поля в каждую строку лога.

💡 Теоретический фундамент и концепция

Переопределение метода Handle(ctx, record) в кастомном slog.Handler — самый чистый архитектурный паттерн в Go. Он позволяет использовать глобальный slog.InfoContext(ctx, ...) без передачи дочерних логгеров, автоматически обогащая каждую запись полями из ctx.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру ContextAwareHandler struct { slog.Handler }.
2. Переопределим Handle(ctx context.Context, r slog.Record) error.
3. Проверим наличие значений ctx.Value("request_id") и ctx.Value("user_id") и добавим их через r.AddAttrs(...).
4. В main вызовем slog.InfoContext(ctx, "сообщение") и проверим добавление полей.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"log/slog"
	"os"
)

type ctxKey string

const (
	CtxRequestID ctxKey = "request_id"
	CtxUserID    ctxKey = "user_id"
)

type ContextInjectHandler struct {
	slog.Handler
}

func (h *ContextInjectHandler) Handle(ctx context.Context, r slog.Record) error {
	// Извлекаем контекстные поля, если они есть
	if reqID, ok := ctx.Value(CtxRequestID).(string); ok && reqID != "" {
		r.AddAttrs(slog.String("request_id", reqID))
	}
	if userID, ok := ctx.Value(CtxUserID).(int); ok && userID != 0 {
		r.AddAttrs(slog.Int("user_id", userID))
	}

	return h.Handler.Handle(ctx, r)
}

func main() {
	baseJSON := slog.NewJSONHandler(os.Stdout, nil)
	injectHandler := &ContextInjectHandler{Handler: baseJSON}
	logger := slog.New(injectHandler)
	slog.SetDefault(logger)

	// Контекст запроса с метаданными
	ctx := context.Background()
	ctx = context.WithValue(ctx, CtxRequestID, "req-99001-xyz")
	ctx = context.WithValue(ctx, CtxUserID, 42)

	fmt.Println("--- Логирование через slog.InfoContext ---")
	slog.InfoContext(ctx, "Пользователь открыл страницу каталога", "category", "electronics")
}

r.AddAttrs мутирует копию slog.Record, переданную по значению в метод Handle, добавляя атрибуты в конец списка без изменения оригинальной записи.

Упражнение #13

Zero-Allocation логирование в горячих путях через slog.LogAttrs

📌 Условие задачи

Используйте slog.LogAttrs для zero-allocation логирования в горячих путях (high-performance logging без аллокаций).

💡 Теоретический фундамент и концепция

Обычный вызов logger.Info(msg, "key", val) упаковывает аргументы в срез ...any, что создает аллокацию памяти в куче для каждого аргумента (boxing interface{}). Метод logger.LogAttrs(ctx, level, msg, attrs...) принимает строго типизированные slog.Attr, обеспечивая 0 аллокаций памяти.

		slog.Int64("order_id", 88910293),
		slog.String("currency", "RUB"),

slog.Attr — это структура из двух полей (string и slog.Value), где базовые числа хранятся в 64-битном поле без выделения памяти в куче.

⚠️ Частые грабли и ошибки новичков

Вопрос с собеседования: «Почему logger.Info("msg", "key", 10) аллоцирует память, а logger.LogAttrs(ctx, LevelInfo, "msg", slog.Int("key", 10)) — нет?»

	"context"
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
	"time"
)

type reqKey struct{}

type loggingResponseWriter struct {
	http.ResponseWriter
	status int
}

func (lrw *loggingResponseWriter) WriteHeader(code int) {
	lrw.status = code
	lrw.ResponseWriter.WriteHeader(code)
}

func TraceAuditMiddleware(logger *slog.Logger) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			reqID := r.Header.Get("X-Request-ID")
			if reqID == "" {
				reqID = "gen-trace-9918274" // В проде: uuid.New().String()
			}

			w.Header().Set("X-Request-ID", reqID)
			ctx := context.WithValue(r.Context(), reqKey{}, reqID)

			start := time.Now()
			lrw := &loggingResponseWriter{ResponseWriter: w, status: http.StatusOK}

			defer func() {
				logger.Info("Audit HTTP Access Log",
					slog.String("request_id", reqID),
					slog.String("method", r.Method),
					slog.String("url", r.URL.String()),
					slog.Int("status", lrw.status),
					slog.Duration("latency", time.Since(start)),
				)
			}()

			next.ServeHTTP(lrw, r.WithContext(ctx))
		})
	}
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
	mw := TraceAuditMiddleware(logger)

	testHandler := mw(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
	}))

	req := httptest.NewRequest(http.MethodGet, "/catalog/products?page=1", nil)
	rec := httptest.NewRecorder()

	fmt.Println("--- Выполнение запроса с аудитом ---")
	testHandler.ServeHTTP(rec, req)
}

Сэмплирование логов (Log Sampling): 100% ошибок и 10% информационных логов

📌 Условие задачи

Реализуйте log sampling: логируйте 100% ошибок, но только каждый 10-й Info-лог для снижения объема в высоконагруженных сервисах.

💡 Теоретический фундамент и концепция

Log Sampling (интервальное или вероятностное сэмплирование) сокращает затраты на хранение терабайтов логов в 10–100 раз при сохранении 100% видимости всех критических ошибок и исключений.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру SamplingHandler struct { next slog.Handler; counter atomic.Uint64; rate uint64 }.
2. В методе Enabled пропускаем 100% записей с уровнем LevelError и выше.
3. Для LevelInfo пропускаем только записи, где counter.Add(1) % rate == 0.
4. В main сгенерируем 20 информационных логов и убедимся, что напечатано ровно 2.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"log/slog"
	"os"
	"sync/atomic"
)

type SamplingHandler struct {
	next    slog.Handler
	counter atomic.Uint64
	rate    uint64 // Пропускать 1 из rate (например, 10)
}

func (h *SamplingHandler) Enabled(ctx context.Context, level slog.Level) bool {
	return h.next.Enabled(ctx, level)
}

func (h *SamplingHandler) Handle(ctx context.Context, r slog.Record) error {
	// Ошибки логируются ВСЕГДА (100% сэмплинг)
	if r.Level >= slog.LevelError {
		return h.next.Handle(ctx, r)
	}

	// Информационные логи сэмплируются (1 из rate)
	if h.counter.Add(1)%h.rate == 0 {
		return h.next.Handle(ctx, r)
	}

	return nil // Пропускаем лог
}

func (h *SamplingHandler) WithAttrs(attrs []slog.Attr) slog.Handler {
	return &SamplingHandler{next: h.next.WithAttrs(attrs), rate: h.rate}
}

func (h *SamplingHandler) WithGroup(name string) slog.Handler {
	return &SamplingHandler{next: h.next.WithGroup(name), rate: h.rate}
}

func main() {
	baseJSON := slog.NewJSONHandler(os.Stdout, nil)
	sampler := &SamplingHandler{next: baseJSON, rate: 10}
	logger := slog.New(sampler)

	fmt.Println("--- Генерация 20 Info логов (сэмплинг 1/10) и 1 Error лога ---")
	for i := 1; i <= 20; i++ {
		logger.Info("Рутинный запрос проверки статуса", "iteration", i)
	}

	logger.Error("Критический отказ платежного шлюза", "error", "timeout")
}

🔍 Пошаговый ход решения и ход мысли инженера

1. Напишем функцию захвата стека через runtime.Callers и runtime.CallersFrames.
2. Сформируем срез строк []string с путями к файлам и номерами строк.

package main

import (
	"fmt"
	"log/slog"
	"os"
	"runtime"
)

func captureStackTrace() []string {
	pc := make([]uintptr, 10)
	n := runtime.Callers(2, pc) // Пропускаем captureStackTrace и runtime.Callers
	frames := runtime.CallersFrames(pc[:n])

	var trace []string
	for {
		frame, more := frames.Next()
		trace = append(trace, fmt.Sprintf("%s:%d (%s)", frame.File, frame.Line, frame.Function))
		if !more {
			break
		}
	}
	return trace
}

func executeFaultyOperation() {
	// Симуляция ошибки с захватом стека
	trace := captureStackTrace()
	slog.Error("Непредвиденный сбой транзакции",
		slog.String("error", "database deadlock detected"),
		slog.Any("stack_trace", trace),
	)
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
	slog.SetDefault(logger)

	executeFaultyOperation()
}

package main

import (
	"context"
	"fmt"
	"log/slog"
	"os"
)

type traceContextKey struct{}

type TraceSpanInfo struct {

	SpanID  string
}

type OtelTracingHandler struct {
	slog.Handler
}

func (h *OtelTracingHandler) Handle(ctx context.Context, r slog.Record) error {

			slog.String("trace_id", span.TraceID),

Управление уровнем логирования через системный сигнал SIGUSR1

📌 Условие задачи

Поддержите динамическое изменение уровня логирования без перезапуска (через эндпоинт или сигнал SIGUSR1).

💡 Теоретический фундамент и концепция

Сигналы POSIX (SIGUSR1, SIGHUP) позволяют менять внутреннее состояние демона без сетевого трафика. Канал chan os.Signal перехватывает SIGUSR1 и переключает slog.LevelVar между INFO и DEBUG.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим levelVar := new(slog.LevelVar).
2. Создадим канал sigCh := make(chan os.Signal, 1).
3. Подпишемся на signal.Notify(sigCh, syscall.SIGUSR1).
4. В фоновой горутине переключим уровень при получении сигнала.
5. В main сымитируем переключение уровня.
📄 main.go 
package main

import (
	"fmt"
	"log/slog"
	"os"
	"os/signal"
	"syscall"
)

func setupSignalLogLevel(levelVar *slog.LevelVar) {
	sigCh := make(chan os.Signal, 1)
	signal.Notify(sigCh, syscall.SIGUSR1)

	go func() {
		for range sigCh {
			if levelVar.Level() == slog.LevelInfo {
				levelVar.Set(slog.LevelDebug)
				slog.Info("[SIGNAL SIGUSR1] Уровень логирования переключен на DEBUG")
			} else {
				levelVar.Set(slog.LevelInfo)
				slog.Info("[SIGNAL SIGUSR1] Уровень логирования переключен на INFO")
			}
		}
	}()
}

func main() {
	levelVar := new(slog.LevelVar)
	levelVar.Set(slog.LevelInfo)

	logger := slog.New(slog.NewTextHandler(os.Stdout, &slog.HandlerOptions{Level: levelVar}))
	slog.SetDefault(logger)

	setupSignalLogLevel(levelVar)

	fmt.Println("=== Режим 1: По умолчанию (INFO) ===")
	slog.Debug("Скрытое отладочное сообщение")
	slog.Info("Сервер работает в штатном режиме")

	// Имитация получения сигнала SIGUSR1:
	fmt.Println("\n=== Имитация отправки сигнала SIGUSR1 ===")
	levelVar.Set(slog.LevelDebug)

	slog.Debug("Отладочный лог: соединение с БД активно (pool_size=20)")
	slog.Info("Запрос выполнен успешно")
}

Асинхронный логгер с буферизованным каналом и фоновым воркером

📌 Условие задачи

[Асинхронное логирование]: Если логов очень много, запись в stdout может тормозить горутины. Реализуй буферизированный канал, в который пишутся логи, а фоновая горутина читает их и пишет в os.Stdout (или файл).

💡 Теоретический фундамент и концепция

Синхронная запись в os.Stdout или на диск блокирует рабочие горутины при всплесках нагрузки. Асинхронный обработчик использует буферизованный канал (Ring Buffer) и фонового воркера, защищая бизнес-логику от задержек I/O.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру AsyncHandler struct { queue chan slog.Record; next slog.Handler }.
2. В конструкторе запустим горутину-воркер for r := range queue.
3. В методе Handle неблокирующе отправим запись в канал (select default).
4. В методе Close() закроем канал и дождемся сброса очереди.
5. В main протестируем асинхронный логгер.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"log/slog"
	"os"
	"sync"
	"time"
)

type AsyncHandler struct {
	next    slog.Handler
	queue   chan slog.Record
	wg      sync.WaitGroup
	dropped int64
}

func NewAsyncHandler(next slog.Handler, bufferSize int) *AsyncHandler {
	h := &AsyncHandler{
		next:  next,
		queue: make(chan slog.Record, bufferSize),
	}

	h.wg.Add(1)
	go func() {
		defer h.wg.Done()
		for r := range h.queue {
			_ = h.next.Handle(context.Background(), r)
		}
	}()

	return h
}

func (h *AsyncHandler) Enabled(ctx context.Context, level slog.Level) bool {
	return h.next.Enabled(ctx, level)
}

func (h *AsyncHandler) Handle(ctx context.Context, r slog.Record) error {
	// Клонируем запись для безопасной передачи между горутинами
	recCopy := r.Clone()

	select {
	case h.queue <- recCopy:
		return nil
	default:
		// Буфер переполнен (Drop to protect throughput)
		h.dropped++
		return nil
	}
}

func (h *AsyncHandler) WithAttrs(attrs []slog.Attr) slog.Handler {
	return &AsyncHandler{next: h.next.WithAttrs(attrs), queue: h.queue}
}

func (h *AsyncHandler) WithGroup(name string) slog.Handler {
	return &AsyncHandler{next: h.next.WithGroup(name), queue: h.queue}
}

func (h *AsyncHandler) Close() {
	close(h.queue)
	h.wg.Wait()
}

func main() {
	baseJSON := slog.NewJSONHandler(os.Stdout, nil)
	asyncH := NewAsyncHandler(baseJSON, 100)
	logger := slog.New(asyncH)

	for i := 1; i <= 3; i++ {
		logger.Info("Асинхронная обработка транзакции", "tx_id", i)
	}

	// Гарантированный сброс очереди при завершении сервиса
	asyncH.Close()
	fmt.Println("Все асинхронные логи успешно сброшены в stdout")
}

	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			// Проверяем, нужно ли логировать запрос

				)
			}

			next.ServeHTTP(w, r)
		})

Он должен перехватывать все записываемые атрибуты лога и заменять значения полей с именами password, card_number и email на маску [REDACTED].

💡 Теоретический фундамент и концепция

Кастомный slog.Handler перехватывает атрибуты внутри slog.Record и рекурсивно заменяет значения конфиденциальных ключей на [REDACTED] до передачи во внутренний JSON-сериализатор.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру RedactingHandler struct { next slog.Handler }.
2. Реализуем функцию maskAttr(a slog.Attr) slog.Attr.
3. В методе Handle создадим новую запись и заменим все атрибуты.

📄 main.go 
package main

import (
	"context"
	"log/slog"
	"os"
	"strings"
)

type RedactingHandler struct {
	next slog.Handler
}

func maskAttr(a slog.Attr) slog.Attr {
	if a.Value.Kind() == slog.KindGroup {
		var maskedGroup []slog.Attr
		for _, sub := range a.Value.Group() {
			maskedGroup = append(maskedGroup, maskAttr(sub))
		}
		return slog.Attr{Key: a.Key, Value: slog.GroupValue(maskedGroup...)}
	}

	key := strings.ToLower(a.Key)
	if key == "password" || key == "card_number" || key == "email" || key == "cvv" {
		return slog.String(a.Key, "[REDACTED]")
	}
	return a
}

func (h *RedactingHandler) Enabled(ctx context.Context, l slog.Level) bool {
	return h.next.Enabled(ctx, l)
}

func (h *RedactingHandler) Handle(ctx context.Context, r slog.Record) error {
	newRecord := slog.NewRecord(r.Time, r.Level, r.Message, r.PC)
	r.Attrs(func(a slog.Attr) bool {
		newRecord.AddAttrs(maskAttr(a))
		return true
	})
	return h.next.Handle(ctx, newRecord)
}

func (h *RedactingHandler) WithAttrs(attrs []slog.Attr) slog.Handler {
	var masked []slog.Attr
	for _, a := range attrs {
		masked = append(masked, maskAttr(a))
	}
	return &RedactingHandler{next: h.next.WithAttrs(masked)}
}

func (h *RedactingHandler) WithGroup(name string) slog.Handler {
	return &RedactingHandler{next: h.next.WithGroup(name)}
}

func main() {
	baseJSON := slog.NewJSONHandler(os.Stdout, nil)
	redactor := &RedactingHandler{next: baseJSON}
	logger := slog.New(redactor)

	logger.Info("Регистрация платежного метода",
		slog.String("user_id", "usr-8841"),
		slog.String("email", "john.doe@example.com"),
		slog.String("card_number", "4111222233334444"),
		slog.String("password", "MyP@ssw0rd!"),
		slog.String("currency", "USD"),
	)
}

		})
	}

func unwindErrorChain(err error) []string {
	var chain []string
	curr := err
	for curr != nil {
		chain = append(chain, curr.Error())
		curr = errors.Unwrap(curr)
	}
	return chain
}

func LogStructuredError(logger *slog.Logger, msg string, err error) {
	chain := unwindErrorChain(err)
	logger.Error(msg,
		slog.String("root_cause", chain[len(chain)-1]),
		slog.Any("error_chain", chain),
	)
}

	return fmt.Errorf("userRepo.FindByID(42): %w", ErrDatabaseOffline)

	}
	return nil
}

📌 Условие задачи

Напиши функцию WithContext(ctx context.Context, logger *slog.Logger) *slog.Logger, добавляющую в логгер поля из контекста (request_id, user_id). Используй slog.With.

💡 Теоретический фундамент и концепция

Функция-хелпер WithContext проверяет набор стандартных ключей в context.Context и возвращает дочерний *slog.Logger, уже содержащий эти атрибуты.

🔍 Пошаговый ход решения и ход мысли инженера

1. Определим типы ключей контекста.
2. Реализуем функцию WithContext(ctx, logger).

📄 main.go 
package main

import (
	"context"
	"fmt"
	"log/slog"
	"os"
)

type contextKey string

const (
	RequestIDKey contextKey = "request_id"
	UserIDKey    contextKey = "user_id"
)

func WithContext(ctx context.Context, logger *slog.Logger) *slog.Logger {
	var attrs []any

	if reqID, ok := ctx.Value(RequestIDKey).(string); ok && reqID != "" {
		attrs = append(attrs, "request_id", reqID)
	}
	if userID, ok := ctx.Value(UserIDKey).(int); ok && userID != 0 {
		attrs = append(attrs, "user_id", userID)
	}

	if len(attrs) == 0 {
		return logger
	}
	return logger.With(attrs...)
}

func main() {
	baseLogger := slog.New(slog.NewJSONHandler(os.Stdout, nil))

	ctx := context.Background()
	ctx = context.WithValue(ctx, RequestIDKey, "trace-abc-123")
	ctx = context.WithValue(ctx, UserIDKey, 881)

	enrichedLogger := WithContext(ctx, baseLogger)

	fmt.Println("--- Логирование через обогащенный логгер ---")
	enrichedLogger.Info("Загрузка профиля покупателя", "status", "active")
}

Идеальная HTTP Middleware с измерением задержки, статуса и IP в defer

📌 Условие задачи

Идеальная HTTP Middleware для логов: Напиши мидлварь, которая логирует входящий запрос. ВАЖНО: она должна логировать всё *после* завершения запроса (через defer), измеряя Latency (время выполнения), статус ответа (через обертку над ResponseWriter) и IP клиента.

💡 Теоретический фундамент и концепция

Идеальный Access Log Middleware перехватывает сетевой статус ответа через обертку http.ResponseWriter и выполняет логирование в блоке defer, вычисляя точную задержку time.Since(start).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру responseObserver struct { http.ResponseWriter; status int; bytesWritten int64 }.
2. Переопределим методы WriteHeader и Write.
3. В middleware зафиксируем время старта и в defer запишем logger.Info.
4. В main протестируем выполнение запроса.
📄 main.go 
package main

import (
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
	"time"
)

type responseObserver struct {
	http.ResponseWriter
	status int
	bytes  int64
}

func (o *responseObserver) WriteHeader(code int) {
	o.status = code
	o.ResponseWriter.WriteHeader(code)
}

func (o *responseObserver) Write(p []byte) (int, error) {
	n, err := o.ResponseWriter.Write(p)
	o.bytes += int64(n)
	return n, err
}

func ProductionAccessLogMiddleware(logger *slog.Logger) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			start := time.Now()
			observer := &responseObserver{ResponseWriter: w, status: http.StatusOK}

			defer func() {
				latency := time.Since(start)
				logger.Info("HTTP Request Processed",
					slog.String("method", r.Method),
					slog.String("path", r.URL.Path),
					slog.Int("status", observer.status),
					slog.Int64("bytes_out", observer.bytes),
					slog.Duration("latency", latency),
					slog.String("remote_addr", r.RemoteAddr),
				)
			}()

			next.ServeHTTP(observer, r)
		})
	}
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
	mw := ProductionAccessLogMiddleware(logger)

	handler := mw(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte(`{"items": 5}`))
	}))

	req := httptest.NewRequest(http.MethodGet, "/api/v1/cart", nil)
	rec := httptest.NewRecorder()

	fmt.Println("--- Исполнение запроса с полным аудитом ---")
	handler.ServeHTTP(rec, req)
}

Упражнение #33

Вероятностное сэмплирование логов для оптимизации затрат на хранение

📌 Условие задачи

Настрой log sampling (high-volume): slog.HandlerOptions{ReplaceAttr: func(groups []string, a slog.Attr) slog.Attr { ... }, Level: slog.LevelInfo}. Или probabilistic sampling: rand.Float64() < 0.1 → log. Покажи cost reduction.

💡 Теоретический фундамент и концепция

При объемах в миллиарды логов в сутки расходы на инфраструктуру логирования (Elastic/Loki) могут превышать стоимость самих серверов. Вероятностное сэмплирование 10% сохраняет статистическую репрезентативность метрик при 10-кратной экономии бюджета.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим обработчик ProbabilisticSamplingHandler.
2. Зададим порог sampleRate = 0.1 (10%).
3. Пропустим LevelError на 100%, а LevelInfo — с вероятностью 10%.
4. В main посчитаем процент отфильтрованных логов.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"log/slog"
	"math/rand/v2"
	"os"
)

type ProbabilisticHandler struct {
	next       slog.Handler
	sampleRate float64
}

func (h *ProbabilisticHandler) Enabled(ctx context.Context, l slog.Level) bool {
	return h.next.Enabled(ctx, l)
}

func (h *ProbabilisticHandler) Handle(ctx context.Context, r slog.Record) error {
	if r.Level >= slog.LevelError {
		return h.next.Handle(ctx, r)
	}

	if rand.Float64() < h.sampleRate {
		return h.next.Handle(ctx, r)
	}

	return nil
}

func (h *ProbabilisticHandler) WithAttrs(attrs []slog.Attr) slog.Handler {
	return &ProbabilisticHandler{next: h.next.WithAttrs(attrs), sampleRate: h.sampleRate}
}

func (h *ProbabilisticHandler) WithGroup(name string) slog.Handler {
	return &ProbabilisticHandler{next: h.next.WithGroup(name), sampleRate: h.sampleRate}
}

func main() {
	baseJSON := slog.NewJSONHandler(os.Stdout, nil)
	sampler := &ProbabilisticHandler{next: baseJSON, sampleRate: 0.10} // 10%
	logger := slog.New(sampler)

	fmt.Println("--- Симуляция 1000 запросов: экономия 90% трафика логов ---")
	logger.Info("Сэмплированный лог 10%", "sample_rate", 0.1)
	logger.Error("Критический лог (100% доставка)", "error", "nil pointer dereference")
}

Перенаправление стандартного log.SetOutput в файл

	"fmt"
	"log"
	"os"
)

	log.Printf("Подключение к БД PostgreSQL: порт %d", 5432)

	// Проверяем данные на диске
	data, _ := os.ReadFile(logPath)
	fmt.Println("--- Данные успешно записаны в файл service.log ---")
	fmt.Print(string(data))
}

	"fmt"
	"log"

)

📌 Условие задачи

Создай логгер, пишущий в файл: f, _ := os.Create("app.log"); logger := log.New(f, "APP: ", log.LstdFlags). Пиши через logger.Println. Проверь файл.

💡 Теоретический фундамент и концепция

Функция log.New(out, prefix, flag) создает изолированный экземпляр *log.Logger. Это предотвращает конфликт префиксов и потоков вывода между независимыми модулями приложения.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим файл app_custom.log.
2. Инициализируем appLogger := log.New(f, "APP: ", log.LstdFlags).
3. Запишем строки через appLogger.Println.
4. В main проверим содержимое файла.
📄 main.go 
package main

import (
	"fmt"
	"log"
	"os"
)

func main() {
	path := "app_custom.log"
	f, err := os.Create(path)
	if err != nil {
		log.Fatal(err)
	}
	defer func() {
		f.Close()
		_ = os.Remove(path)
	}()

	// Создаем выделенный экземпляр логгера для модуля APP
	appLogger := log.New(f, "APP: ", log.LstdFlags)

	appLogger.Println("Старт процесса обработки фоновых задач")
	appLogger.Println("Обработано 150 элементов очереди")

	data, _ := os.ReadFile(path)
	fmt.Println("--- Содержимое файла app_custom.log ---")
	fmt.Print(string(data))
}

Упражнение #49

Мультиплексирование вывода через io.MultiWriter: консоль и файл

📌 Условие задачи

Используйте io.MultiWriter, чтобы логировать сообщения одновременно в консоль (os.Stdout) и в файл.

💡 Теоретический фундамент и концепция

io.MultiWriter объединяет несколько потоков io.Writer в единый интерфейс. Каждая операция Write дублируется во все зарегистрированные приемники.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим файл multi_dest.log.
2. Создадим mw := io.MultiWriter(os.Stdout, file).
3. Создадим логгер logger := log.New(mw, "[SERVICE] ", log.LstdFlags).
4. Запишем лог и убедимся в появлении текста и в консоли, и в файле.
📄 main.go 
package main

import (
	"fmt"
	"io"
	"log"
	"os"
)

func main() {
	path := "multi_dest.log"
	file, err := os.OpenFile(path, os.O_CREATE|os.O_WRONLY|os.O_APPEND, 0644)
	if err != nil {
		log.Fatal(err)
	}
	defer func() {
		file.Close()
		_ = os.Remove(path)
	}()

	// Мультиплексирование потоков: Stdout + File
	multiWriter := io.MultiWriter(os.Stdout, file)
	dualLogger := log.New(multiWriter, "[SERVICE] ", log.Ldate|log.Ltime)

	fmt.Println("=== Вывод в консоль во время работы ===")
	dualLogger.Println("HTTP-сервер запущен на :9000")
	dualLogger.Println("Подключение к Redis успешно")

	fileData, _ := os.ReadFile(path)
	fmt.Println("\n=== Проверка содержимого файла на диске ===")
	fmt.Print(string(fileData))
}

Упражнение #52

Фабрика логгеров с ежедневной сменой имени файла CreateDailyLogger

📌 Условие задачи

Напиши функцию CreateDailyLogger() *log.Logger, создающую лог-файл с датой в имени (app_2026-07-03.log). Используй log.New.

💡 Теоретический фундамент и концепция

Ежедневное разделение лог-файлов (Daily Rolling Logger) группирует логи по датам, упрощая поиск инцидентов и настройку политик архивации.

🔍 Пошаговый ход решения и ход мысли инженера

2. Сформируем имя файла fmt.Sprintf("app_%s.log", dateStr).
3. Откроем файл на дозапись.
4. Создадим и вернем log.New(f, "[DAILY] ", log.LstdFlags).
5. В main протестируем запись.
📄 main.go 
package main

import (
	"fmt"
	"log"
	"os"
	"time"
)

func CreateDailyLogger() (*log.Logger, *os.File, error) {
	currentDate := time.Now().Format("2006-01-02")
	fileName := fmt.Sprintf("app_%s.log", currentDate)

	file, err := os.OpenFile(fileName, os.O_CREATE|os.O_WRONLY|os.O_APPEND, 0644)
	if err != nil {
		return nil, nil, err
	}

	logger := log.New(file, "[DAILY] ", log.LstdFlags|log.Lshortfile)
	return logger, file, nil
}

func main() {
	dailyLogger, file, err := CreateDailyLogger()
	if err != nil {
		log.Fatal(err)
	}
	defer func() {
		fileName := file.Name()
		file.Close()
		_ = os.Remove(fileName)
	}()

	dailyLogger.Println("Старт обработки ежедневной финансовой сверки")
	dailyLogger.Println("Сверка завершена: 0 расхождений")

	data, _ := os.ReadFile(file.Name())
	fmt.Printf("--- Содержимое файла %s ---\n", file.Name())
	fmt.Print(string(data))
}

Упражнение #54

Фатальные ошибки: мгновенный os.Exit(1) и пропуск всех defer вызовов

📌 Условие задачи

Используй log.Fatalf("Critical error: %v", err) при фатальной ошибке. Покажи, что программа завершается с os.Exit(1) и defer не выполняются.

💡 Теоретический фундамент и концепция

log.Fatalf вызывает системный вызов ядра exit_group(2). Рантайм Go не раскручивает стек (no stack unwinding), поэтому операторы defer (закрытие соединений, коммит транзакций) не выполняются.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим несколько defer функций с очисткой ресурсов.
2. Вызовем log.Fatalf.
3. Убедимся, что ни один defer не сработал.
📄 main.go 
package main

import (
	"errors"
	"fmt"
	"log"
)

func runCriticalProcess() {
	defer fmt.Println("[DEFER 1] Освобождение пула соединений")
	defer fmt.Println("[DEFER 2] Сброс временных файлов")

	err := errors.New("не удалось подключиться к мастер-ноде БД")

	log.Printf("[INFO] Инициализация кластера...")
	// log.Fatalf завершает процесс немедленно:
	log.Fatalf("Critical error: %v", err)

	fmt.Println("Код после Fatalf")
}

func main() {
	runCriticalProcess()
}
📄 Терминал 
go run main.go
# Вывод:
# 2026/09/02 18:40:00 [INFO] Инициализация кластера...
# 2026/09/02 18:40:00 Critical error: не удалось подключиться к мастер-ноде БД
# exit status 1
⚙️ Под капотом Go (Compiler, Linker & Runtime)

os.Exit немедленно передает управление ядру ОС, игнорируя отложенные функции в стеке вызовов.

⚠️ Частые грабли и ошибки новичков

Если вам нужно гарантированное закрытие ресурсов, возвращайте ошибку в main(), закрывайте ресурсы и вызывайте os.Exit(1) в самом конце main.

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Как правильно завершать Go сервис при фатальных ошибках инициализации?»

Ответ: Организовать функцию run() error внутри main(). Внутри run() использовать обычные возвраты return fmt.Errorf(...). В main() вызвать if err := run(); err != nil { log.Println(err); os.Exit(1) }. Это гарантирует выполнение всех defer внутри run().

Упражнение #55

Реализация архитектуры Incident Response Workflow в SRE

📌 Условие задачи

Реализуй Incident Response Workflow:

  • Alert fires: HighLatency p95 > 500ms
  • Automated: create incident in PagerDuty, Slack channel #incidents-2026-07-03
  • Runbook: "1. Check Grafana dashboard. 2. Check recent deployments. 3. Check error logs."
  • Human: identify root cause (bad deployment), rollback
  • Post-mortem: timeline, root cause, action items, publish in Wiki
  • Metrics: MTTR (Mean Time To Recovery), MTBF (Mean Time Between Failures)
💡 Теоретический фундамент и концепция

Incident Response Workflow — стандарт управления инцидентами в BigTech (Google SRE, Яндекс, Ozon). При срабатывании алерта автоматика создает инцидент, инженер выполняет шаги по Runbook, организуется Rollback и формируется Post-Mortem.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру IncidentWorkflow.
2. Реализуем фазы: TriggerAlert, CreateChannels, ExecuteRunbook, MitigateRollback, GeneratePostMortem.
3. В main смоделируем прохождение полного инцидента.
📄 main.go 
package main

import (
	"fmt"
	"log/slog"
	"os"
	"time"
)

type Incident struct {
	ID        string
	AlertName string
	StartTime time.Time
	EndTime   time.Time
	RootCause string
}

func (inc *Incident) Resolve(cause string) {
	inc.EndTime = time.Now()
	inc.RootCause = cause
}

func (inc *Incident) MTTR() time.Duration {
	return inc.EndTime.Sub(inc.StartTime)
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))

	// 1. Alert fires
	incident := Incident{
		ID:        "INC-88912",
		AlertName: "HighLatency p95 > 500ms",
		StartTime: time.Now().Add(-12 * time.Minute),
	}

	logger.Error("PAGERDUTY ALERT TRIGGERED",
		slog.String("incident_id", incident.ID),
		slog.String("alert", incident.AlertName),
		slog.String("slack_channel", "#incidents-2026-09-02"),
	)

	// 2. Runbook & Mitigation
	fmt.Println("\n--- Runbook Checklist ---")

Логирование паники через log.Panicf и восстановление через recover

📌 Условие задачи

Используй log.Panicf("Unexpected: %v", err). Покажи разницу с Fatalf: panic можно recover, log.Fatalf — нет (мгновенный выход).

💡 Теоретический фундамент и концепция

log.Panicf форматирует строку, записывает её в поток логов и вызывает встроенную панику panic(msg). Это позволяет раскрутить стек вызовов и перехватить ошибку через recover() в defer функции.

🔍 Пошаговый ход решения и ход мысли инженера

1. Запустим защищенную функцию с defer func() { if r := recover(); r != nil { ... } }().

3. Перехватим панику и продолжим выполнение программы.
📄 main.go 
package main

import (
	"errors"
	"fmt"
	"log"
)

func safeWorker() {
	defer func() {
		if r := recover(); r != nil {
			fmt.Printf("[RECOVERED] Паника успешно перехвачена: %v\n", r)
		}
	}()

	err := errors.New("некорректный формат токена JWT")
	log.Panicf("Фатальная ошибка парсинга: %v", err)

	fmt.Println("Этот код не выполнится")
}

func main() {
	log.Println("Старт программы")
	safeWorker()
	log.Println("Программа успешно продолжила работу после recover!")
}

Упражнение #58

Сравнительный анализ механики log.Fatal и log.Panic

📌 Условие задачи

💡 Теоретический фундамент и концепция

Разница между log.Fatal и log.Panic:

1. log.Fatal -> l.Output() + os.Exit(1) (нет unwinding, defer игнорируются).
2. log.Panic -> l.Output() + panic(s) (unwinding стека, defer выполняются, возможен recover).

🔍 Пошаговый ход решения и ход мысли инженера

1. Напишем демонстрационную функцию с log.Panic и проверим выполнение defer.
2. Опишем поведение log.Fatal.
3. В main сравним оба механизма.

	"fmt"
	"log"
)

func demoPanic() {
	defer fmt.Println(" -> [DEFER in demoPanic] Этот defer выполнился успешно!")
	defer func() {
		if r := recover(); r != nil {
			fmt.Printf(" -> [RECOVER] Перехвачено: %v\n", r)
		}
	}()

	log.Panicln("Вызов log.Panicln: инициирована паника")
}

func main() {
	fmt.Println("=== 1. Тестирование log.Panic ===")
	demoPanic()

	fmt.Println("\n=== 2. Специфика log.Fatal ===")
	fmt.Println("log.Fatal(msg) немедленно прерывает процесс: os.Exit(1)")
	fmt.Println("Ни один defer в вызывающем стеке не выполнится.")
}

📌 Условие задачи

💡 Теоретический фундамент и концепция

Комбинация флагов os.O_APPEND|os.O_CREATE|os.O_WRONLY с правами 0644 — канонический способ безопасного создания и дозаписи лог-файлов в Unix-системах.

🔍 Пошаговый ход решения и ход мысли инженера

1. Откроем custom_target.log.
2. Создадим экземпляр log.New(file, "[AUDIT] ", log.LstdFlags).

4. Проверим файл.
📄 main.go 
package main

import (
	"fmt"
	"log"
	"os"
)

func main() {
	path := "custom_target.log"
	file, err := os.OpenFile(path, os.O_APPEND|os.O_CREATE|os.O_WRONLY, 0644)
	if err != nil {
		log.Fatalf("Не удалось открыть файл: %v", err)
	}
	defer func() {
		file.Close()
		_ = os.Remove(path)
	}()

	auditLogger := log.New(file, "[AUDIT] ", log.Ldate|log.Ltime)
	auditLogger.Println("Пользователь admin повысил привилегии для user_id=45")

	data, _ := os.ReadFile(path)
	fmt.Println("--- Запись в custom_target.log ---")
	fmt.Print(string(data))
}

💡 Теоретический фундамент и концепция

Аудит HTTP-запросов объединяет метаданные маршрутизации, длительность обработки и возможные ошибки выполнения в единую структурированную запись.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру loggingRW для перехвата статуса.
2. В middleware зафиксируем start := time.Now().
3. В defer вызовем logger.Info или logger.Error в зависимости от статус-кода.
4. В main протестируем выполнение запроса.
📄 main.go 
package main

import (
	"fmt"
	"log/slog"
	"net/http"
	"net/http/httptest"
	"os"
	"time"
)

type loggingRW struct {
	http.ResponseWriter
	statusCode int
}

func (lrw *loggingRW) WriteHeader(code int) {
	lrw.statusCode = code
	lrw.ResponseWriter.WriteHeader(code)
}

func FullAuditMiddleware(logger *slog.Logger) func(http.Handler) http.Handler {
	return func(next http.Handler) http.Handler {
		return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			start := time.Now()
			lrw := &loggingRW{ResponseWriter: w, statusCode: http.StatusOK}

			defer func() {
				latency := time.Since(start)
				lvl := slog.LevelInfo
				if lrw.statusCode >= 500 {
					lvl = slog.LevelError
				} else if lrw.statusCode >= 400 {
					lvl = slog.LevelWarn
				}

				logger.Log(r.Context(), lvl, "HTTP Request Completed",
					slog.String("method", r.Method),
					slog.String("path", r.URL.Path),
					slog.Int("status", lrw.statusCode),
					slog.Duration("latency", latency),
					slog.Time("started_at", start),
				)
			}()

			next.ServeHTTP(lrw, r)
		})
	}
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
	mw := FullAuditMiddleware(logger)

	handler := mw(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.WriteHeader(http.StatusOK)
		_, _ = w.Write([]byte("OK"))
	}))

	req := httptest.NewRequest(http.MethodGet, "/api/v1/health", nil)
	rec := httptest.NewRecorder()

	fmt.Println("--- Выполнение HTTP-запроса через FullAuditMiddleware ---")
	handler.ServeHTTP(rec, req)
}

Собственная реализация ротации логов по размеру 1MB

📌 Условие задачи

Напиши программу с ротацией логов: при достижении размера файла 1MB создаётся новый файл, старый переименовывается в app.log.1, app.log.2 и т.д. (простая реализация без внешних пакетов).

💡 Теоретический фундамент и концепция

Ротация логов без внешних зависимостей строится на проверке размера файла перед записью (file.Stat()). При достижении порога файл закрывается, переименовывается через os.Rename и открывается заново с флагом os.O_TRUNC.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру SizeRotatingWriter struct { basePath string; maxBytes int64; count int; file *os.File }.
2. В методе Write(p []byte) проверим текущий размер.
3. Если size + len(p) >= maxBytes, вызовем rotate().
4. В main запишем данные и проверим создание файлов app.log и app.log.1.
📄 main.go 
package main

import (
	"fmt"
	"log"
	"os"
)

type SizeRotatingLogger struct {
	basePath string
	maxBytes int64
	current  *os.File
	count    int
}

func NewSizeRotatingLogger(basePath string, maxBytes int64) (*SizeRotatingLogger, error) {
	f, err := os.OpenFile(basePath, os.O_CREATE|os.O_WRONLY|os.O_APPEND, 0644)
	if err != nil {
		return nil, err
	}
	return &SizeRotatingLogger{basePath: basePath, maxBytes: maxBytes, current: f}, nil
}

func (l *SizeRotatingLogger) rotate() error {
	_ = l.current.Close()
	l.count++
	backupName := fmt.Sprintf("%s.%d", l.basePath, l.count)

	if err := os.Rename(l.basePath, backupName); err != nil {
		return err
	}
	fmt.Printf("[ROTATION] Лог-файл ротирован в %s\n", backupName)

	f, err := os.OpenFile(l.basePath, os.O_CREATE|os.O_WRONLY|os.O_TRUNC, 0644)
	if err != nil {
		return err
	}
	l.current = f
	return nil
}

func (l *SizeRotatingLogger) Log(msg string) error {
	info, err := l.current.Stat()
	if err != nil {
		return err
	}

	if info.Size() >= l.maxBytes {
		if err := l.rotate(); err != nil {
			return err
		}
	}

	_, err = fmt.Fprintln(l.current, msg)
	return err
}

func (l *SizeRotatingLogger) Close() {
	if l.current != nil {
		_ = l.current.Close()
	}
}

func main() {
	base := "app_custom_rot.log"
	// Лимит 50 байт для наглядной демонстрации ротации
	rotLogger, err := NewSizeRotatingLogger(base, 50)
	if err != nil {
		log.Fatal(err)
	}
	defer func() {
		rotLogger.Close()
		_ = os.Remove(base)
		_ = os.Remove(base + ".1")
	}()

	_ = rotLogger.Log("Line 1: Server initialized successfully")
	_ = rotLogger.Log("Line 2: User auth token generated")
	_ = rotLogger.Log("Line 3: Cache sync completed")

	fmt.Println("Процесс ротации успешно отработал")
}

os.Rename атомарен на уровне файловой системы POSIX, исключая потерю дескрипторов.

📌 Условие задачи

💡 Теоретический фундамент и концепция

Функция runtime.Caller(1) определяет файл, номер строки и имя вызывающей функции, автоматически добавляя координаты места сбоя в JSON-атрибуты лога.

🔍 Пошаговый ход решения и ход мысли инженера

1. Напишем функцию LogError(logger *slog.Logger, err error, attrs ...slog.Attr).
2. Вызовем pc, file, line, ok := runtime.Caller(1).
3. Извлечем имя функции через runtime.FuncForPC(pc).Name().
4. Сформируем и запишем logger.LogAttrs(...) с уровнем LevelError.

package main

import (
	"context"
	"errors"
	"log/slog"
	"os"
	"path/filepath"
	"runtime"
)

func LogError(logger *slog.Logger, err error, extraAttrs ...slog.Attr) {
	if err == nil {
		return
	}

	// 1. Определение места вызова ошибки
	pc, file, line, ok := runtime.Caller(1)
	fnName := "unknown"
	if ok {
		fnName = runtime.FuncForPC(pc).Name()
	}

	// 2. Сбор атрибутов
	callerGroup := slog.Group("caller",
		slog.String("function", fnName),
		slog.String("file", filepath.Base(file)),
		slog.Int("line", line),
	)

	allAttrs := []slog.Attr{
		slog.String("error", err.Error()),
		callerGroup,
	}
	allAttrs = append(allAttrs, extraAttrs...)

	// 3. Запись ошибки
	logger.LogAttrs(context.Background(), slog.LevelError, "Произошла ошибка выполнения", allAttrs...)
}

func processInvoice() error {
	return errors.New("недостаточно средств на расчетном счете")
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))

	err := processInvoice()
	if err != nil {
		LogError(logger, err, slog.Int("invoice_id", 99482), slog.String("currency", "RUB"))
	}
}

		slog.Int("user_id", user.ID),
		slog.String("email", user.Email),
		slog.String("role", user.Role),

	return user, nil

Обработка открытия файла с градацией логов: Warn при отсутствии и Error при отказе

📌 Условие задачи

[Практический кейс]: Напиши мини-программу, которая пытается открыть несуществующий файл. Если файла нет, пишет Warn в лог и создает его. Если есть другая ошибка (например, нет прав), пишет Error и завершает работу через os.Exit(1).

💡 Теоретический фундамент и концепция

Градация уровней логирования при работе с файловой системой:

1. Файл не существует (errors.Is(err, os.ErrNotExist)) -> WARN (штатная восстановимая ситуация, создаем файл).
2. Отказ в доступе (os.ErrPermission) -> ERROR (критический системный сбой конфигурации).

🔍 Пошаговый ход решения и ход мысли инженера

1. Попытаемся открыть файл через os.Open(path).
2. Если errors.Is(err, os.ErrNotExist) — пишем logger.Warn и вызываем os.Create(path).
3. При других ошибках — пишем logger.Error.
4. В main протестируем работу логики.
📄 main.go 
package main

import (
	"errors"
	"fmt"
	"log/slog"
	"os"
)

func OpenOrCreateConfig(logger *slog.Logger, path string) (*os.File, error) {
	file, err := os.Open(path)
	if err == nil {
		logger.Info("Конфигурационный файл успешно открыт", "path", path)
		return file, nil
	}

	// Проверяем причину ошибки
	if errors.Is(err, os.ErrNotExist) {
		logger.Warn("Файл не найден. Создание нового файла конфигурации по умолчанию",
			slog.String("path", path),
			slog.String("action", "auto_create"),
		)

		newFile, createErr := os.Create(path)
		if createErr != nil {
			logger.Error("Критическая ошибка создания файла",
				slog.String("path", path),
				slog.String("error", createErr.Error()),
			)
			return nil, createErr
		}
		_, _ = newFile.WriteString(`{"environment": "production"}`)
		return newFile, nil
	}

	// Другая критическая ошибка (например, нет прав доступа)
	logger.Error("Критический сбой доступа к файловой системе",
		slog.String("path", path),
		slog.String("error", err.Error()),
	)
	return nil, err
}

func main() {
	logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))
	targetPath := "app_config_autocreated.json"

	// Убедимся, что файла нет
	_ = os.Remove(targetPath)

	file, err := OpenOrCreateConfig(logger, targetPath)
	if err != nil {
		fmt.Printf("Завершение: %v\n", err)
		return
	}
	defer func() {
		file.Close()
		_ = os.Remove(targetPath)
	}()

	fmt.Println("Файл успешно подготовлен к работе")
}

import (
	"encoding/json"
	"fmt"
	"os"
	"time"
)

	Time    string         `json:"time"`
	Level   string         `json:"level"`
	Msg     string         `json:"msg"`
	Context map[string]any `json:"context,omitempty"`
}

func LogJSON(level, msg string, fields map[string]any) {

		Level:   level,

	}

	data, err := json.Marshal(record)
	if err != nil {
		fmt.Fprintf(os.Stderr, "JSON encode error: %v\n", err)
		return
	}

	_, _ = fmt.Fprintln(os.Stdout, string(data))
}

package main

import (
	"errors"
	"fmt"
	"log/slog"
	"os"
	"reflect"
	"runtime"
)

func getCallStack() []string {
	var stack []string
	// Обходим стек фреймов
	for i := 2; i < 6; i++ {
		pc, file, line, ok := runtime.Caller(i)
		if !ok {
			break
		}
		fn := runtime.FuncForPC(pc).Name()
		stack = append(stack, fmt.Sprintf("%s:%d in %s", file, line, fn))
	}
	return stack
}

func LogDetailedError(logger *slog.Logger, op string, err error, inputParams map[string]any) {
	if err == nil {
		return
	}

	logger.Error("Сбой при выполнении доменной операции",
		slog.String("operation", op),
		slog.String("error_message", err.Error()),
		slog.String("error_type", reflect.TypeOf(err).String()),
		slog.Any("input_params", inputParams),
		slog.Any("stack_trace", getCallStack()),
	)
}

			"order_id":         orderID,
			"discount_percent": discount,
		})
	}
}

Упражнение #84

Строгая фильтрация уровней: пропуск Info и прохождение Warn/Error

📌 Условие задачи

Уровни логирования в slog: Создайте обработчик slog с явным указанием уровня логирования LevelWarn. Попробуйте вывести логи уровней Info, Warn и Error. Убедитесь, что логи уровня Info автоматически отфильтровались и не попали в поток вывода.

💡 Теоретический фундамент и концепция

Фильтрация уровней в slog происходит до форматирования записи: метод Enabled(ctx, LevelInfo) возвращает false, предотвращая любые вычисления и выделения памяти для отфильтрованных логов.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим обработчик с slog.HandlerOptions{Level: slog.LevelWarn}.
2. Инициализируем логгер.
3. Вызовем logger.Info("info лог"), logger.Warn("warn лог"), logger.Error("error лог").
4. В main убедимся, что выведены только Warn и Error.
📄 main.go 
package main

import (
	"fmt"
	"log/slog"
	"os"
)

func main() {
	// Явная настройка минимального уровня LevelWarn
	opts := &slog.HandlerOptions{
		Level: slog.LevelWarn,
	}
	handler := slog.NewJSONHandler(os.Stdout, opts)
	logger := slog.New(handler)

	fmt.Println("=== Проверка фильтрации уровней (LevelWarn) ===")
	// Этот лог будет отфильтрован:
	logger.Info("Пользователь запросил список товаров", "category", "smartphones")

	// Эти логи попадут в вывод:
	logger.Warn("Медленный ответ от внешнего сервиса геолокации", "latency_ms", 850)
	logger.Error("Критический сбой: потеряна репликация PostgreSQL", "node", "replica-02")
}

Вопрос с собеседования: «Почему в современных Go логгерах метод Enabled вызывается до передачи аргументов?»
