# Паттерны и каверзные случаи конкурентности (Race, Leaks, Worker Pool)

В этом файле собраны уникальные упражнения по теме **"Паттерны и каверзные случаи конкурентности (Race, Leaks, Worker Pool)"**, отсортированные по возрастанию сложности.

---

1. Fan-out/Fan-in: генератор чисел, несколько горутин умножают числа на 2, затем объединяют результаты в один канал.

2. **Pipeline (Конвейер)**: Создайте цепочку из трех горутин: первая генерирует числа, вторая возводит их в квадрат, третья фильтрует четные. Соедините их каналами.

3. **Fan-Out**: Запустите несколько (N) горутин-воркеров, которые одновременно читают из одного входного канала и обрабатывают задачи.

4. Pipeline: стадии `generate` → `square` → `print`. Используйте каналы для связи.

5. **Fan-In**: Напишите функцию, которая принимает множество каналов и сливает их данные в один выходной канал (Multiplexing).

6. «Graceful shutdown»: запустите воркер, который читает из канала. При получении SIGINT (или через контекст) завершите воркер, дождавшись окончания текущих задач.

7. **Worker Pool (Пул воркеров)**: Реализуйте систему, где создается фиксированное число горутин (например, 5), которые берут задачи из очереди (канала) и обрабатывают их. Это классика для ограничения нагрузки на CPU или БД.

8. Ограничьте количество одновременно выполняемых HTTP-запросов с помощью Worker Pool или семафора на основе буферизованного канала (`sem := make(chan struct{}, 10)`).

9. Семафор на основе канала (буферизированный канал ёмкостью N): ограничьте количество одновременно выполняющихся горутин, которые обращаются к внешнему ресурсу.

10. **Паттерн "Pub/Sub"**: Создайте структуру `Broker`, к которой могут подключаться клиенты (каналы), и которая рассылает сообщения всем подписчикам.

11. **Ping-Pong**: Напишите программу, где две горутины играют в "пинг-понг", передавая мяч (структуру с счетчиком) через два канала друг другу, пока счетчик не достигнет 10.

12. Барьерная синхронизация: используйте канал, чтобы заставить несколько горутин дождаться друг друга перед стартом следующей фазы.

13. Реализуй **Worker Pool**: фиксированное число воркеров (например, 3), канал задач (`chan func() error`), канал результатов. Воркеры читают задачи, выполняют, отправляют результат. `main` закрывает канал задач и ждёт `sync.WaitGroup`.

14. Реализуйте отмену долгой операции (например, скачивания файла) по сигналу из канала, используя `select` внутри цикла чтения.

15. **Генератор (Generator)**: Напишите функцию, которая возвращает канал и в скрытой горутине генерирует туда последовательность чисел (например, Фибоначчи).

16. Реализуй **Pipeline** из 3 стадий: `Generator` → `Square` → `Printer`. Каждая стадия — горутина + канал. Замерь throughput: сколько чисел обработано за 1 секунду.

17. Реализуй **Fan-Out / Fan-In**: один генератор, 4 воркера (fan-out), один мержер (fan-in). Воркеры обрабатывают задачи параллельно, результаты собираются в один канал. Используй `sync.WaitGroup` для fan-in.

18. **Паттерн "Конвейер" (Pipeline)**: Напишите конвейер обработки чисел из трех стадий (каждая стадия — это функция, принимающая канал и возвращающая новый канал):
    * Стадия 1: Генерация чисел от 1 до 100.
    * Стадия 2: Фильтрация (пропускает только нечетные числа).
    * Стадия 3: Возведение в квадрат.
    В функции `main` прочитайте финальные результаты из выходного канала.

19. Реализуй **Future / Promise**: функция `AsyncCompute(fn func() int) <-chan int` запускает `fn` в горутине и возвращает канал с результатом. Вызвающий читает из канала, когда результат нужен.

20. Реализуй **Semaphore** через канал: `type Semaphore chan struct{}`. Методы: `Acquire()`, `Release()`. Ограничь доступ к ресурсу (например, 2 одновременных запроса к "базе данных").

21. Реализуй **Rate Limiter** (token bucket): канал `tokens` с буфером N. Каждый запрос берёт токен (`<-tokens`). Пополняющая горутина добавляет токен каждые `interval`. Если токенов нет — запрос блокируется.

22. **Паттерн "Worker Pool" (Пул воркеров)**: Напишите классический пул воркеров. У вас есть канал задач `jobs` и канал результатов `results`. Запустите фиксированное количество горутин-воркеров (например, 3 воркера), которые разбирают задачи из канала `jobs`, имитируют работу и отправляют результаты в канал `results`.

23. Реализуй **Rate Limiter** (leaky bucket): запросы поступают в буферизованный канал. Обрабатывающая горутина читает из канала с фиксированной частотой (`time.Ticker`). Если буфер переполнен — запрос отклоняется.

24. Deadlock: создайте ситуацию взаимной блокировки (две горутины, два мьютекса, захватываемых в разном порядке). Обнаружьте с `-race`.

25. Реализуй **Pub/Sub** через каналы: `type PubSub struct { subscribers map[string][]chan string; mu sync.RWMutex }`. Методы: `Subscribe(topic string) <-chan string`, `Publish(topic, msg string)`. Подписчики получают сообщения.

26. **Паттерн "Fan-In" (Слияние каналов)**: Напишите функцию `FanIn(channels ...<-chan int) <-chan int`. Она должна принимать произвольное количество каналов, запускать горутины для чтения из каждого и сливать все полученные данные в один результирующий канал. Обеспечьте корректное закрытие результирующего канала только после того, как закроются ВСЕ входные каналы (используйте `sync.WaitGroup`).

27. Реализуй **Bounded Queue** через канал: `type Queue struct { ch chan int }`. Методы `Enqueue(v int) bool` (false если полон), `Dequeue() (int, bool)`. Используй канал как синхронизированную очередь.

28. **Генератор (Generator)**: Напиши функцию, которая внутри себя создает канал, запускает горутину (которая пишет туда числа 1..10 и закрывает его) и возвращает этот канал (`<-chan int`).

29. Избегайте deadlock с помощью упорядочивания захвата мьютексов или `sync.Map`.

30. Реализуй **Circuit Breaker** (упрощённый): три состояния — `Closed`, `Open`, `HalfOpen`. При N ошибок подряд — переход в `Open`. В `Open` — быстрый fail. Через таймаут — `HalfOpen`, где один запрос пробует пройти. Используй `sync/atomic` для состояния.

31. **Пул воркеров (Worker Pool)**: Создай канал `jobs` и канал `results`. Запусти 3 горутины-воркера, которые читают из `jobs`, умножают число на 2 и пишут в `results`. Из `main` отправь 10 задач в `jobs` и собери 10 ответов.

32. Реализуй **Retry with backoff**: функция пытается выполнить операцию 3 раза. Между попытками — экспоненциальная задержка (100ms, 200ms, 400ms). Если контекст отменён — прерывай сразу.

33. **Паттерн "Fan-Out" (Раздача задач)**: Напишите программу, которая берет поток данных из одного канала и распределяет его по нескольким разным каналам-слушателям (каждое сообщение должно дублироваться во все каналы-слушатели).

34. Реализуй **Parallel For** (аналог `Parallel.ForEach` в C#): `ParallelFor(items []int, fn func(int))`. Запускает обработку каждого элемента в горутине, но ограничивает concurrency через семафор.

35. Утечка горутин: горутина пишет в канал, который никто не читает. Найдите утечку с помощью профилировщика или счётчика горутин (`runtime.NumGoroutine`). Исправьте, закрыв канал или добавив буфер/select.

36. **Data Race с замыканием**: Запустите цикл `for`, в котором создаются горутины, использующие переменную цикла `i`. (Для Go < 1.22 все выведут последнее значение).

37. **Fan-out (Разветвление)**: Улучши упр. 308. Один "генератор" пишет задачи в канал, а 5 воркеров конкурируют за чтение из этого канала.

38. **Fan-Out**: Создай один канал с задачами (числами). Запусти 3 горутины-обработчика (воркера), которые читают из этого канала и выводят результат с своим ID.

39. Реализуй **Map-Reduce**: фаза Map — N горутин обрабатывают входные данные, фаза Reduce — одна горутина агрегирует результаты из канала. Используй `sync.WaitGroup` для барьера между фазами.

40. **Data Race со слайсом**: Несколько горутин одновременно делают `append` в один общий слайс. Программа упадет с `concurrent map read and map write` или повредит память. Защитите слайс мьютексом.

41. Реализуй **"errgroup"** вручную (или используй `golang.org/x/sync/errgroup`): запускаешь N горутин, если **любая** возвращает ошибку — отменяешь остальные через `context.WithCancel`. Собери первую ошибку.

42. **Fan-in (Слияние)**: Напиши функцию `Merge(ch1, ch2 <-chan int) <-chan int`. Внутри запусти горутину, которая читает из обоих каналов (через `select` или горутины с WaitGroup) и пишет данные в один общий выходной канал.

43. **Ограничение частоты запросов (Rate Limiting)**: Напишите программу, имитирующую отправку запросов к внешнему API. API разрешает обрабатывать не более 5 запросов в секунду. Используйте тикер `time.NewTicker`, чтобы ограничить частоту отправки запросов (ровно 1 запрос каждые 200 миллисекунд).

44. Закрытие закрытого канала: продемонстрируйте панику. Исправьте, используя флаг или `sync.Once` для безопасного закрытия.

45. Реализуй **"pipeline cancellation"**: pipeline из 3 стадий. Если стадия 2 получает ошибку — она закрывает свой выходной канал, стадия 3 завершает чтение, стадия 1 должна узнать об отмене через `select` на `done` канале.

46. **Goroutine Leak**: Напишите горутину, которая заблокирована на чтении из канала `<-ch`, но канал никогда не закрывается и туда никто не пишет. Используйте `runtime.NumGoroutine()`, чтобы доказать, что память утекает.

47. **Пайплайн (Pipeline)**: Создай конвейер: Генератор -> Сквер (возводит в квадрат) -> Принтер (выводит). Каждая стадия — это функция, принимающая входной канал и возвращающая выходной.

48. Реализуй **"streaming"** обработку: читаешь большой файл построчно, отправляешь строки в pipeline (стадия 1), фильтруешь (стадия 2), агрегируешь статистику (стадия 3). Всё — через каналы, без загрузки файла целиком в память.

49. **Pipeline**: Создай 3 стадии. Стадия 1 генерирует числа. Стадия 2 возводит их в квадрат (читает из канала 1, пишет в канал 2). Стадия 3 печатает результат (читает из канала 2).

50. Реализуй **"throttled parallel download"**: скачивай 10 URL параллельно, но не более 3 одновременных запросов. Используй семафор + `sync.WaitGroup`. Собери результаты (размер или статус) в канал.

51. Запустите вашу программу с флагом детектора гонок: `go run -race main.go`. Намеренно создайте Data Race и изучите подробный отчет, который выдает Go.

52. «Broadcast» через закрытие канала: несколько горутин ждут сигнала старта, читая из одного канала. Закрытие канала разблокирует всех.

53. **Rate Limiting с очередью (Bursting)**: Перепишите предыдущую задачу. Настройте ограничение частоты так, чтобы система могла обрабатывать всплески (bursts) до 3 запросов одновременно, но при этом средняя скорость не превышала 5 запросов в секунду (реализуйте это с помощью буферизованного канала емкостью 3 элемента, который постепенно наполняется по тикеру).

54. Реализуй **"timeout per task"** в worker pool: каждая задача имеет свой дедлайн. Если задача не уложилась — воркер отменяет её (через `context.WithDeadline`) и берёт следующую.

55. Напишите функцию, которая возвращает канал, но внутри не стартует горутину для записи в него, или стартует, но падает с паникой, не закрыв канал. Изучите, как это приводит к Deadlock в вызывающем коде.

56. **Worker Pool (Пул воркеров)**: Создай очередь заданий (канал на 100 элементов). Запусти фиксированное количество воркеров (например, 5), которые читают задания и "обрабатывают" (sleep random time). Дождись выполнения всех заданий через `WaitGroup`.

57. Реализуй **"priority queue"** с конкурентным доступом: `type PriorityQueue struct { items []Item; mu sync.Mutex; cond *sync.Cond }`. Воркеры забирают задачи с наивысшим приоритетом. Продюсеры добавляют задачи. Используй `heap.Interface` + `sync.Mutex`.

58. `nil`-канал в `select`: покажите, что `select` игнорирует case с `nil`-каналом, что можно использовать для динамического отключения веток.

59. **Tee-канал (Тройник)**: Напиши функцию, которая читает из одного канала и дублирует каждое значение в **два** исходящих канала.

60. Напиши программу с **"data race на слайсе"**: две горутины `append`ят в один слайс. Запусти с `-race`. Покажи, что `append` — не атомарная операция (чтение len/cap, выделение памяти, копирование, запись).

61. **WGC (WaitGroup Copy)**: Передайте `sync.WaitGroup` в анонимную функцию (горутину) по значению (без взятия адреса). Убедитесь, что `Wait()` в `main` никогда не дождется завершения.

62. **Семафор на каналах (Concurrency Limiter)**: Напишите функцию, которая должна параллельно скачать 100 файлов. Однако жесткий лимит операционной системы разрешает одновременно открывать не более 10 сетевых соединений. Реализуйте этот ограничитель конкурентности, используя буферизованный канал емкостью 10 в качестве семафора (запись в канал перед стартом задачи, чтение из канала при завершении задачи).

63. Напиши программу с **"channel deadlock"**: две горутины пытаются записать друг в друга (A пишет в ch1, читает из ch2; B пишет в ch2, читает из ch1). Никакой `select` — чистый deadlock. Покажи, как `select` с `default` или таймаутом решает это.

64. **Debouncer (Подавитель дребезга)**: Напиши функцию, которая принимает канал событий (кликов). Она должна передавать событие дальше, только если с момента прошлого события прошло более 500 мс. (Используй `time.Timer`).

65. Изучите проблему "Channel Deadlock" при использовании буферизованных каналов: горутина пишет в переполненный канал и блокируется, а читать некому.

66. Напиши программу с **"closing nil channel"**: `var ch chan int; close(ch)`. Получи панику. Напиши защиту: проверяй `if ch != nil` перед закрытием.

67. **Семафор (Semaphore)**: У тебя 100 задач. Используй буферизированный канал `sem := make(chan struct{}, 5)`, чтобы ограничить максимальное количество *одновременно* работающих горутин до 5. (Пиши в `sem` перед стартом, читай в конце).

68. Обработка ошибок в горутинах: канал для ошибок, main собирает ошибки от воркеров и агрегирует их.

69. **Rate Limiting (Ограничение скорости)**: Используй `time.Tick` (например, каждые 200ms) для ограничения частоты обработки запросов. Запросы поступают быстрее, но обрабатываются только по тику.

70. **Rate Limiter (Ограничитель)**: Используй `time.Ticker`, чтобы разрешать выполнение не более 3 задач в секунду (выполняй задачу только после получения тика из `ticker.C`).

71. Напиши программу с **"send on closed channel"**: закрой канал, затем отправь в него значение. Получи панику. Напиши `SafeSend(ch chan int, v int) bool`, которая возвращает `false` вместо паники (используй `recover` или `select` с `default` + проверка, но лучше — не закрывай канал, если есть писатели).

72. **Паттерн "Future/Promise"**: Напишите функцию `FetchData() <-chan string`, которая мгновенно возвращает канал (обещание результата), а внутри запускает фоновую горутину для тяжелого вычисления. Когда вычисление завершено, горутина пишет результат в канал и закрывает его. В основной горутине выполните другие полезные действия, а затем заберите результат из канала, когда он понадобится.

73. Реализуйте функцию, которая "форкает" выполнение (создает горутину), но гарантирует, что при панике внутри горутины программа не упадет молча, а залогирует ошибку (recover внутри горутины).

74. Напиши программу с **"multiple closers"**: две горутины могут закрыть канал. Получи панику. Решение: только **писатель** закрывает канал, или используй `sync.Once`.

75. **Or-Channel (Или-канал)**: Напиши функцию `Or(channels ...<-chan struct{}) <-chan struct{}`. Она должна вернуть канал, который закроется, как только закроется **хотя бы один** из переданных каналов.

76. **Done Channel Pattern (Устаревший, но важный)**: Реализуй отмену горутины через закрытие специального канала `done chan struct{}` (до эры `context`).

77. Напишите программу, где горутина удерживает `Mutex` и пытается сделать HTTP-запрос с таймаутом. Что будет, если таймаут сработает, а Mutex останется заблокированным?

78. Конкурентный доступ к слайсу: покажите, что конкурентное чтение безопасно, а запись — нет. Защитите мьютексом.

79. Напиши программу с **"goroutine leak in range"**: `for v := range ch` никогда не завершится, если кто-то не закроет `ch`. Покажи, что если писатель завис/упал — читатель тоже зависнет. Используй `select` с `ctx.Done()` для выхода.

80. **Паттерн "Publish-Subscribe" (Pub-Sub)**: Напишите простую шину сообщений на чистом Go. Должна быть структура `PubSub` с методами `Subscribe(topic string) <-chan string` и `Publish(topic string, msg string)`. Обеспечьте потокобезопасность шины (используйте мьютексы).

81. Напиши программу с **"select on send without default"**: `select { case ch <- v: }`. Если канал небуферизованный и нет читателя — это **блокировка**. Добавь `default` для non-blocking send.
