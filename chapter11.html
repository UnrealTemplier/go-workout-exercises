Упражнение #1

Сравнение встроенной функции new(T) и литерального взятия адреса &T{}

📌 Условие задачи

Сравните работу оператора new и взятия адреса от литерала &struct{} для создания указателей на структуры.

💡 Теоретический фундамент и концепция

Два способа создания указателей на структуры в Go:

1. new(User): выделяет память, заполняет все поля нулевыми значениями (Zero Values) и возвращает *User;
2. &User{Name: "Иван", Age: 30}: создает экземпляр с возможностью явной инициализации полей и возвращает *User.

Оба способа семантически эквивалентны при создании структуры с нулевыми полями (new(User) $\equiv$ &User{}). Однако в промышленной разработке &User{...} предпочтительнее благодаря гибкости инициализации.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем структуру type User struct { Name string; Age int }.
2. Создаем u1 := new(User).
3. Создаем u2 := &User{Name: "Алексей", Age: 28}.
4. Сравниваем типы и значения.
📄 main.go 
package main

import "fmt"

type User struct {
	Name string
	Age  int
}

func main() {
	// 1. Инициализация через new():
	u1 := new(User)
	u1.Name = "Нулевой профиль"
	u1.Age = 20

	// 2. Инициализация через литерал &User{}:
	u2 := &User{
		Name: "Алексей",
		Age:  28,
	}

	fmt.Printf("u1: %T -> %+v (адрес: %p)\n", u1, *u1, u1)
	fmt.Printf("u2: %T -> %+v (адрес: %p)\n", u2, *u2, u2)
}
📄 Терминал

# u1: *main.User -> {Name:Нулевой профиль Age:20} (адрес: 0xc000010060)
# u2: *main.User -> {Name:Алексей Age:28} (адрес: 0xc000010090)
⚙️ Под капотом Go (Compiler, Linker & Runtime)

В компиляторе Go new(T) и &T{} компилируются в идентичные AST-узлы ONIT и обрабатываются одинаково аллокатором памяти рантайма (runtime.newobject).

⚠️ Частые грабли и ошибки новичков
  • Попытка инициализировать поля структуры прямо внутри new(User{...}) — синтаксическая ошибка! new принимает только тип new(User).
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «В чем разница между new(T) и make(T)?»

Ответ: new(T) выделяет зануленную память для ЛЮБОГО типа T и возвращает указатель *T. make(T, ...) используется ТОЛЬКО для трех встроенных типов (слайсы, мапы, каналы) и возвращает готовое к работе инициализированное значение самого типа T (не указатель).

Упражнение #2

Мутация элементов среза vs append внутри функции: передача по значению []int vs указатель *[]int

📌 Условие задачи

Измените элементы среза внутри функции, затем выполните append внутри функции. Верните срез или используйте указатель на срез — разберите разницу в поведении.

💡 Теоретический фундамент и концепция

Механика передачи срезов в функции:

  • Срез передается по значению как 24-байтный дескриптор SliceHeader (Data, Len, Cap);
  • Изменение элементов s[0] = 999 видно вызывающему коду (так как Data ссылается на тот же массив);
  • Вызов append(s, ...) внутри функции изменяет только локальные Len и Cap (а при реаллокации и Data), поэтому исходный срез в main() не увидит добавленный элемент без возврата среза или передачи указателя *[]int.

🔍 Пошаговый ход решения и ход мысли инженера

1. Пишем функцию MutateSlice(s []int) — меняет s[0] и делает append.
2. Пишем функцию AppendByPointer(s *[]int, val int) — делает *s = append(*s, val).
3. Сравниваем результаты в main().
📄 main.go 
package main

import "fmt"

func MutateSlice(s []int) {
	s[0] = 999          // Мутация элемента базового массива (ВИДНА СНАРУЖИ!)
	s = append(s, 100)  // Изменение локального заголовка среза (НЕ ВИДНО СНАРУЖИ!)
	fmt.Printf("Внутри MutateSlice:     %v (len=%d, cap=%d)\n", s, len(s), cap(s))
}

func AppendByPointer(s *[]int, val int) {
	*s = append(*s, val) // Перезапись SliceHeader по указателю (ВИДНА СНАРУЖИ!)
}

func main() {
	data := []int{1, 2, 3}
	fmt.Printf("1. Исходный срез:          %v\n", data)

	MutateSlice(data)
	fmt.Printf("2. После MutateSlice:      %v (s[0] изменился, но 100 не добавилось!)\n\n", data)

	AppendByPointer(&data, 100)
	fmt.Printf("3. После AppendByPointer:  %v (100 УСПЕШНО ДОБАВЛЕНО!)\n", data)
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

При передаче &data функция получает адрес структуры SliceHeader на стеке вызывающей функции и обновляет поля Data, Len, Cap напрямую по адресу.

⚠️ Частые грабли и ошибки новичков
  • Использование *[]int везде подряд: идиоматичный стиль Go рекомендует возвращать новый срез func Append(s []int) []int вместо передачи указателей на срезы.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему в Go не принято передавать указатели на срезы *[]T, кроме редких случаев?»

Ответ: Потому что возврат среза s = append(s, val) более идиоматичен, потокобезопасен и согласуется со стандартной библиотекой (slices.Compact, sort.Slice).

Упражнение #3

Указатель на фиксированный массив *[N]int и прямая модификация элементов

📌 Условие задачи

Создайте массив, получите указатель на него и попробуйте изменить элементы через указатель.

💡 Теоретический фундамент и концепция

Указатель на массив *[N]T:

  • Позволяет передавать массивы без $O(N)$ копирования данных;
  • В Go доступен синтаксический сахар: ptr[0] = 100 эквивалентно явному разыменованию (*ptr)[0] = 100.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем массив arr := [3]int{10, 20, 30}.
2. Получаем указатель ptr := &arr.
3. Модифицируем элементы через ptr[0] и (*ptr)[1].
📄 main.go 
package main

import "fmt"

func ModifyArrayByPointer(p *[3]int) {
	p[0] = 777       // Неявное разыменование компилятором
	(*p)[1] = 888    // Явное разыменование
}

func main() {
	numbers := [3]int{10, 20, 30}
	fmt.Printf("До вызова:    %v\n", numbers)

	ModifyArrayByPointer(&numbers)

	fmt.Printf("После вызова: %v (ОРИГИНАЛЬНЫЙ МАССИВ ИЗМЕНЕН!)\n", numbers)
}
📄 Терминал

# После вызова: [777 888 30] (ОРИГИНАЛЬНЫЙ МАССИВ ИЗМЕНЕН!)
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Доступ к p[i] транслируется в смещение p + i * sizeof(T) в памяти.

⚠️ Частые грабли и ошибки новичков
  • Выход за границы p[5]: компилятор Go выполняет Bounds Checking и вызовет панику.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Каков размер указателя *[1000000]int?»

Ответ: Ровно 8 байт на 64-битной архитектуре (хранит только 64-битный адрес первого элемента).

Упражнение #4

Операторы адресации & и разыменования * в языке Go

📌 Условие задачи

Создайте переменную, получите её адрес с помощью &, сохраните его в указатель и выведите значение указателя и значение по адресу (*).

💡 Теоретический фундамент и концепция

Базовые операции с указателями:

  • &x: оператор взятия адреса памяти переменной x (возвращает *T);
  • *p: оператор разыменования (доступ к значению, хранящемуся по адресу p).

🔍 Пошаговый ход решения и ход мысли инженера

2. Сохраняем ptr := &x.
3. Печатаем адрес ptr и разыменованное значение *ptr.

package main

import "fmt"

func main() {
	score := 42
	ptr := &score // ptr имеет тип *int

	fmt.Printf("1. Значение score:            %d\n", score)
	fmt.Printf("2. Адрес в памяти (&score):   %p\n", &score)
	fmt.Printf("3. Значение указателя ptr:    %p\n", ptr)
	fmt.Printf("4. Разыменование (*ptr):      %d\n", *ptr)

	// Изменяем значение по адресу:
	*ptr = 100
	fmt.Printf("5. score после *ptr = 100:    %d\n", score)
}

Упражнение #8

Очистка среза ClearSlice(s *[]int) с сохранением емкости (*s = (*s)[:0])

📌 Условие задачи

Напиши функцию ClearSlice(s *[]int), которая принимает указатель на слайс и делает *s = (*s)[:0]. Покажи, что теперь оригинал изменился.

💡 Теоретический фундамент и концепция

Паттерн сброса длины среза (Zero-Allocation Slice Reset):

  • Синтаксис (*s)[:0] обнуляет длину (len = 0), но сохраняет выделенную емкость (cap);
  • Передача *[]int гарантирует, что вызывающий код увидит изменение len = 0 оригинального среза;
  • Позволяет повторно использовать буфер без аллокаций памяти.

🔍 Пошаговый ход решения и ход мысли инженера

1. Пишем ClearSlice(s *[]int).
2. Выполняем *s = (*s)[:0].
3. Демонстрируем сохранение емкости cap.
📄 main.go 
package main

import "fmt"

func ClearSlice(s *[]int) {
	if s == nil {
		return
	}
	*s = (*s)[:0] // Сброс длины до 0 с сохранением базового массива и cap!
}

func main() {
	buffer := make([]int, 5, 10)
	for i := range buffer {
		buffer[i] = i * 10
	}

	fmt.Printf("До очистки:    %v | len=%d, cap=%d\n", buffer, len(buffer), cap(buffer))

	ClearSlice(&buffer)

	fmt.Printf("После очистки: %v | len=%d, cap=%d (БУФЕР СОХРАНЕН!)\n",
		buffer, len(buffer), cap(buffer))
}
📄 Терминал 
go run main.go
# До очистки:    [0 10 20 30 40] | len=5, cap=10
# После очистки: [] | len=0, cap=10 (БУФЕР СОХРАНЕН!)
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Изменяется только поле Len в структуре SliceHeader, память кучи не освобождается и не переаллоцируется.

⚠️ Частые грабли и ошибки новичков
  • Утечка ссылок на старые объекты: если срез содержал указатели []*Object, перед [:0] их нужно занулить, чтобы сборщик мусора GC мог освободить память.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему встроенная функция clear(slice) в Go 1.21+ не обнуляет длину среза?»

Ответ: clear(slice) заполняет элементы нулевыми значениями (Zero Values), сохраняя len, а s = s[:0] сбрасывает len до 0.

💡 Теоретический фундамент и концепция

Nil Pointer Dereference:

  • Неинициализированный указатель имеет значение nil (адрес 0x0);
  • Попытка чтения или записи по nil-указателю вызывает исключение защиты памяти процессора (Page Fault), которое рантайм Go преобразует в панику.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем var u *User (nil).
2. Заворачиваем доступ к полю в defer + recover.
3. Ловим панику.
📄 main.go 
package main

import "fmt"

type User struct {
	Name string
}

func main() {
	var u *User // nil-указатель

	fmt.Printf("Состояние u: %v (isNil = %t)\n", u, u == nil)

	func() {
		defer func() {
			if r := recover(); r != nil {
				fmt.Printf("⚠️ Перехвачена паника: %v\n", r)
			}
		}()

		// Разыменование nil приводит к панике:
		fmt.Println(u.Name)
	}()
}

Доступ к адресу 0x0 блокируется механизмом виртуальной памяти ОС (MMU).

⚠️ Частые грабли и ошибки новичков
  • Вызов метода у nil-указателя: если метод читает поля u.Name, произойдет паника, но если метод не обращается к полям получателя, он выполнится успешно!

Различие идентичности (Identity) и равенства (Equality):

  • &a == &b: сравнивает физические адреса в оперативной памяти (два разных объекта в памяти всегда имеют разные адреса);
  • *p1 == *p2: сравнивает логические значения по этим адресам.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем a, b := 10, 10.
2. Сравниваем &a == &b (false).
3. Создаем p1 := &a, p2 := &a.
4. Сравниваем p1 == p2 (true).
📄 main.go 
package main

import "fmt"

func main() {
	a := 10
	b := 10

	// 1. Две разные переменные имеют РАЗНЫЕ адреса памяти:
	fmt.Printf("1. &a == &b: %t (адрес a: %p, адрес b: %p)\n", &a == &b, &a, &b)
	fmt.Printf("2. *(&a) == *(&b): %t (значения одинаковы: 10 == 10)\n", *(&a) == *(&b))

	// 2. Два указателя на одну и ту же переменную:
	p1 := &a
	p2 := &a
	fmt.Printf("3. p1 == p2: %t (указывают на один и тот же адрес: %p)\n", p1 == p2, p1)
}

Инициализация массива указателей [3]*int адресами трех независимых переменных

📌 Условие задачи

Массив указателей: Создай массив [3]*int. Проинициализируй его адресами трех разных переменных.

💡 Теоретический фундамент и концепция

Закрепление синтаксиса массива указателей.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем x, y, z := 1, 2, 3.
2. Создаем arr := [3]*int{&x, &y, &z}.

📄 main.go 
package main

import "fmt"

func main() {
	x, y, z := 100, 200, 300
	var ptrArr [3]*int

	ptrArr[0] = &x
	ptrArr[1] = &y
	ptrArr[2] = &z

	for i, ptr := range ptrArr {
		fmt.Printf("Элемент #%d -> Адрес: %p, Значение: %d\n", i, ptr, *ptr)
	}
}

Упражнение #49

Исследование размеров типов через unsafe.Sizeof: инвариант 8-байтных указателей

📌 Условие задачи

Размер типов: Импортируй unsafe. Узнай с помощью unsafe.Sizeof размер переменной int64 и размер указателя *int64. Убедись, что размер указателя не зависит от того, на какой тип он указывает.

💡 Теоретический фундамент и концепция

Инвариант размеров указателей в архитектуре компьютера:

  • На 64-битной архитектуре (amd64, arm64) ЛЮБОЙ указатель занимает ровно 8 байт;
  • Размер указателя не зависит от размера типа, на который он ссылается (*bool — 8 байт, *byte — 8 байт, *[1000000]int — 8 байт);
  • Функция unsafe.Sizeof вычисляет размер типа на этапе компиляции с нулевыми накладными расходами.

🔍 Пошаговый ход решения и ход мысли инженера

1. Импортируем unsafe.
2. Замеряем unsafe.Sizeof для различных типов и указателей на них.
3. Анализируем результаты.
📄 main.go 
package main

import (
	"fmt"
	"unsafe"
)

type BigStruct struct {
	Buffer [1024]byte
}

func main() {
	var (
		b   bool
		i64 int64
		big BigStruct

		pBool   *bool
		pInt64  *int64
		pBig    *BigStruct
	)

	fmt.Println("=== РАЗМЕРЫ ТИПОВ В ПАМЯТИ (unsafe.Sizeof) ===")
	fmt.Printf("1. bool:               %4d байт  | *bool:       %4d байт\n",
		unsafe.Sizeof(b), unsafe.Sizeof(pBool))
	fmt.Printf("2. int64:              %4d байт  | *int64:      %4d байт\n",
		unsafe.Sizeof(i64), unsafe.Sizeof(pInt64))
	fmt.Printf("3. BigStruct (1024B):  %4d байт  | *BigStruct:  %4d байт\n",
		unsafe.Sizeof(big), unsafe.Sizeof(pBig))
}

⚠️ Частые грабли и ошибки новичков
  • Передача *bool вместо bool для «экономии памяти»: указатель *bool занимает 8 байт против 1 байта у самого bool!
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему передача *bool или *byte в функцию неэффективна по памяти?»

Ответ: Потому что сам bool занимает 1 байт, а указатель на него — 8 байт (в 8 раз больше), плюс создает аллокацию в куче и дополнительное косвенное чтение из памяти.
