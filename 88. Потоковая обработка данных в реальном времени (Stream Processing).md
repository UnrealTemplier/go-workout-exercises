# Потоковая обработка данных в реальном времени (Stream Processing)

В этом файле собраны уникальные упражнения по теме **"Потоковая обработка данных в реальном времени (Stream Processing)"**, отсортированные по возрастанию сложности.

---

1. **Концепция потоковой обработки (Stream vs Batch Processing)**: Изучите фундаментальные различия между пакетной обработкой (Batch) и непрерывными бесконечными потоками данных (Unbounded Streams). Спроектируйте базовую модель потокового события на Go: структура `Event[T any]` с полями `ID string`, `Key string`, `Payload T`, `Timestamp time.Time`. Объясните, почему потоковая обработка требует работы в памяти с инкрементальным сохранением состояния.

2. **Потоковые конвейеры на Go-каналах (Pipelines, Fan-In, Fan-Out)**: Реализуйте конвейер обработки потока кликов в реальном времени: генератор событий -> стадия фильтрации (отсечение ботов) -> параллельная стадия обогащения данных (Fan-Out на 8 горутин-воркеров) -> слияние потоков в единый канал (Fan-In) -> агрегатор. Обеспечьте корректную передачу отмены через `context.Context` и закрытие каналов без паник.

3. **Проблема времени: Event Time vs Processing Time vs Ingestion Time**: Разберите три концепции времени в распределенных потоковых системах: Event Time (время генерации события на клиенте), Ingestion Time (время попадания в брокер Kafka) и Processing Time (время обработки горутиной на сервере). Напишите код, демонстрирующий, как задержки сети и рассинхронизация часов приводят к искажению аналитики при использовании Processing Time вместо Event Time.

4. **Механизм водяных знаков (Watermarks) и задержка данных**: Водяные знаки (Watermarks) сообщают обработчику, что события со временем события $T \le W$ гарантированно получены. Реализуйте генератор водяных знаков с допустимым отставанием (Bounded Out-Of-Orderness Watermark Generator): $W(t) = \max(EventTime) - \Delta t_{delay}$. Продемонстрируйте, как водяной знак позволяет закрывать временные окна для агрегации.

5. **Тумблинговые фиксированные окна (Tumbling Windows)**: Реализуйте неперекрывающиеся тумблинговые окна фиксированного размера (например, 1-минутные окна подсчета посещений). Напишите структуру `TumblingWindowAssigner`, распределяющую входящие события по временным корзинам (Buckets) по формуле `window_start = timestamp - (timestamp % window_size)`. При наступлении водяного знака окно сбрасывает результат и очищает память.

6. **Скользящие окна (Sliding / Hopping Windows)**: Реализуйте скользящие окна с перекрытием: размер окна 10 минут, шаг сдвига (slide) 1 минута. Покажите, что каждое событие должно быть добавлено одновременно в несколько активных окон. Реализуйте эффективное хранение и инкрементальное обновление суммы, исключающее полный пересчет всех элементов при каждом сдвиге.

7. **Сессионные окна (Session Windows) по интервалу неактивности**: В веб-аналитике действия пользователя объединяются в сессию, если пауза между событиями не превышает заданный порог (Inactivity Gap, например, 30 минут). Напишите алгоритм слияния сессионных окон (Session Window Merger): при поступлении события в промежуток между двумя окнами эти окна динамически объединяются в одну непрерывную сессию.

8. **Встроенное хранилище состояния (State Store) на Pebble / BadgerDB**: Потоковая обработка не может зависеть от сетевых походов в СУБД для каждого события. Подключите встраиваемый LSM-движок `cockroachdb/pebble` или `dgraph-io/badger` как локальный State Store. Реализуйте методы `PutState(key, state)`, `GetState(key)` и замерьте задержку чтения/записи (субмиллисекундный доступ).

9. **Инкрементальные агрегации в потоке (Streaming Aggregations)**: Вместо накопления всех событий окна в памяти напишите агрегатор с инкрементальным свертыванием: структуры `Count`, `Sum`, `MinMax` обновляются по формулам онлайн-статистики (алгоритм Велфорда для дисперсии и среднего). Докажите, что потребление памяти остается константным $O(1)$ независимо от миллиона событий внутри окна.

10. **Вероятностный подсчет уникальных пользователей (HyperLogLog)**: Подсчет уникальных посетителей (Unique Active Users) в окне требует сохранения множества `map[string]struct{}`, что приводит к исчерпанию RAM при миллионах ключей. Интегрируйте вероятностный алгоритм HyperLogLog (`clarkduvall/hyperloglog`). Покажите, как HLL оценивает кардинальность с точностью до 1–2% при потреблении всего 1.5 КБ памяти.

11. **Соединение потоков (Stream-Stream Join)**: Реализуйте потоковое соединение двух независимых потоков событий: поток кликов по баннерам (`AdClickEvent`) и поток покупок товаров (`OrderCreatedEvent`). Соединение выполняется по `user_id` в пределах 15-минутного временного окна. События буферизуются в локальном State Store до прихода пары или истечения окна.

12. **Обогащение потока данными таблицы (Stream-Table Join / Enrichment)**: Поток событий заказов содержит только `product_id`. Реализуйте обогащение потока метаданными товара (название, категория, вес) из таблицы PostgreSQL. Примените паттерн локального кэширования с периодическим обновлением (Cache Refresh) или подпиской на Change Data Capture (CDC), чтобы исключить сетевые задержки при обработке потока.

13. **Дедупликация событий в скользящем окне**: Из-за сбоев сети продюсеры могут присылать дублирующиеся события. Реализуйте потоковый дедупликатор: идентификаторы событий `event_id` сохраняются в кольцевой буфер или фильтр Блума со скользящим окном жизни (TTL 10 минут). Если событие уже встречалось в окне, оно отбрасывается без передачи вниз по конвейеру.

14. **Обработка запаздывающих событий (Late Arriving Data) и Side Outputs**: Что делать, если мобильное устройство вышло из метро и прислало событие с задержкой в 2 часа, когда соответствующее окно уже закрыто? Реализуйте обработку с порогом допустимого опоздания (Allowed Lateness): незначительно опоздавшие события обновляют результат окна, а безнадежно устаревшие события направляются в резервный поток (Dead Letter Stream / Side Output) для аудита.

15. **Семантика Exactly-Once Processing (EoS)**: Разберите различия между семантиками доставки: At-Most-Once, At-Least-Once и Exactly-Once. Покажите, как комбинация идемпотентного продюсера, транзакционной фиксации оффсетов Kafka и двухфазного коммита (Two-Phase Commit) в State Store обеспечивает гарантию Exactly-Once в распределенном конвейере.

16. **Снимки состояния и алгоритм Чанди-Лэмпорта (Chandy-Lamport Checkpointing)**: Реализуйте упрощенную версию алгоритма Чанди-Лэмпорта для распределенных снимков состояния (Checkpointing): координатор пускает специальное маркерное сообщение (Barrier) через граф потоковых операторов. При получении барьера каждый оператор фиксирует локальный снимок состояния в надежное хранилище (S3/диск) и передает барьер дальше.

17. **Фреймворк Goka для Kafka на Go**: Изучите и примените библиотеку `lovoo/goka`: разработайте потоковое приложение с эмиттерами (Emitters), процессорами (Processors) и групповыми таблицами (Group Tables). Покажите, как Goka абстрагирует подписку на партиции Kafka, локальный кэш на базе LevelDB и управление состоянием акторов.

18. **Партиционирование по ключу и строгий порядок обработки**: Спроектируйте распределение событий: события с одинаковым ключом (`user_id` или `sensor_id`) обязаны попадать в одну и ту же партицию и обрабатываться строго последовательно. Реализуйте роутинг событий по алгоритму консистентного хэширования (`fnv.New32a(key) % num_workers`) с защитой от изменения порядка.

19. **Адаптивное обратное давление (Backpressure)**: Если стадия агрегации не справляется со входящим потоком (100k событий/сек), буферы каналов переполняются, вызывая неконтролируемый рост памяти. Реализуйте механизм обратного давления: при заполнении входного канала воркера более чем на 80%, читатель Kafka уменьшает размер запрашиваемой порции (Batch Size) или временно приостанавливает вычитку партиции (`Pause/Resume`).

20. **Потоковое обнаружение аномалий (Z-Score / Moving StdDev)**: Напишите алгоритм детектирования аномалий во временных рядах телеметрии датчиков давления: поддерживайте скользящее среднее и стандартное отклонение (алгоритм Welford в окне из 100 точек). Если входящее значение отклоняется более чем на $3\sigma$ ($Z > 3$), немедленно генерируйте событие тревоги `AnomalyDetectedEvent`.

21. **Построение направленного ациклического графа (DAG) обработки**: Создайте DSL для описания потоковой топологии на Go: `topology.Source("kafka-orders").Filter(isPaid).Map(extractMetrics).Window(tumbling1m).Sink("clickhouse")`. Реализуйте валидацию графа на отсутствие циклов и генерацию горутин конвейера при запуске.

22. **Оконные триггеры (Window Triggers) и ранний сброс (Early Emission)**: В длительных окнах (например, суточное окно подсчета выручки) клиенты не хотят ждать конца суток для получения метрик. Реализуйте составной триггер: окно сбрасывает промежуточные результаты каждые 5 минут ИЛИ при накоплении каждых 10 000 новых событий, а финальный результат публикует по достижении водяного знака времени суток.

23. **Компактификация и вытеснение локального состояния**: Если сервис отслеживает действия миллиарда пользователей, локальный State Store на диске переполнится. Настройте политику устаревания (State TTL): горутина-сборщик периодически удаляет ключи пользователей, не проявлявших активности более 7 дней, и запускает ручную компактификацию Pebble/Badger (`CompactRange`).

24. **Replay потока и повторный расчет аналитики**: В аналитическую формулу закралась ошибка. Реализуйте процедуру безопасного повторного прогона (Stream Replay): новый экземпляр сервиса подключается к брокеру Kafka с оффсета за прошлую неделю, рассчитывает исправленные метрики в отдельную таблицу `metrics_recalculated`, после чего оператор переключает чтение без потери данных.

25. **Мониторинг задержки обработки (Processing Lag)**: Экспортируйте метрики Prometheus для потокового процессора: `stream_processing_lag_seconds` ($T_{current} - T_{event}$), `watermark_delay_seconds`, `events_in_flight` и `state_store_bytes`. Настройте алерт на рост лага обработки, сигнализирующий о нехватке вычислительных ресурсов воркеров.

26. **Тестирование потоковой топологии с виртуальным временем**: Напишите детерминированный тестовый стенд: вместо реального брокера Kafka используйте тестовый драйвер, который генерирует события с контролируемыми метками времени и водяными знаками. Докажите, что логика агрегации окон отрабатывает идентично независимо от задержек CPU тестовой машины.

27. **Высокопроизводительный кольцевой буфер (Disruptor Pattern) на Go**: Каналы Go имеют накладные расходы на блокировки мьютексов при высокой конкуренции. Изучите паттерн LMAX Disruptor: реализуйте lock-free кольцевой буфер на атомарных операциях (`sync/atomic`) для передачи событий между этапами конвейера. Покажите на бенчмарке снижение межпоточной задержки до десятков наносекунд.

28. **Потоковая пакетная запись в ClickHouse с фиксацией оффсетов**: ClickHouse требует вставки данных крупными пачками (от 10 000 до 100 000 строк). Напишите потоковый Sink, который накапливает события из Kafka в памяти, периодически сбрасывает их в ClickHouse через `clickhouse-go` пачками и коммитит оффсеты в Kafka ТОЛЬКО после успешного завершения транзакции вставки в ClickHouse.

29. **Graceful Drain потокового процессора при выкатке**: При обновлении версии пода в Kubernetes процессор должен корректно остановиться: прекратить прием новых сообщений из брокера, довести до конца обработку всех событий, находящихся в каналах конвейера (Drain in-flight), сбросить промежуточное состояние окон в локальный State Store, зафиксировать оффсеты и закрыть соединения.

30. **Реализация движка обнаружения мошенничества в реальном времени (Fraud Detection)**: Объедините все изученные техники в комплексный сервис финансового мониторинга: прием потока платежей из Kafka, фильтрация по скользящему окну (например, более 3 транзакций за 10 секунд с разных IP), обогащение данными профиля из кэша, детектирование аномалий сумм через Z-Score, сохранение состояния в Pebble, генерация алертов в Kafka и вывод метрик Prometheus.
