# Оркестрация распределенных процессов (Durable Execution) на Temporal.io

В этом файле собраны уникальные упражнения по теме **"Оркестрация распределенных процессов (Durable Execution) на Temporal.io"**, отсортированные по возрастанию сложности.

---

1. **Введение в парадигму Durable Execution (Temporal.io)**: Изучите концепцию долговечного исполнения (Durable Execution): состояние приложения, стек вызовов, локальные переменные и таймеры сохраняются даже при падении сервера, перезагрузке пода или сбое сети. Объясните, почему Temporal заменяет хрупкие самописные машины состояний, цепочки очередей и распределенные саги.

2. **Архитектура Temporal: Cluster, Workflows, Activities, Workers**: Разберите компоненты Temporal: Temporal Cluster (сохраняет историю событий в БД), Task Queues (виртуальные очереди задач), Workflow Definition (описание бизнес-процесса), Activity Definition (выполнение сайд-эффектов) и Temporal Worker (Go-бинарник, исполняющий код). Нарисуйте схему их взаимодействия.

3. **Подключение к Temporal Cluster на Go**: Используя официальный SDK `go.temporal.io/sdk`, напишите код инициализации клиента: `client.Dial(client.Options{HostPort: "localhost:7233"})`. Настройте подключение с поддержкой mTLS-сертификатов для защищенного корпоративного контура. Реализуйте проверку доступности кластера при старте.

4. **Создание и запуск первого Temporal Worker на Go**: Создайте рабочий процесс (Worker): инициализируйте `worker.New(client, "order-tasks", worker.Options{})`, зарегистрируйте функцию рабочего процесса `w.RegisterWorkflow(OrderWorkflow)` и функцию действия `w.RegisterActivity(ChargeCardActivity)`. Запустите воркер через `w.Run(worker.InterruptCh())` с обработкой системных сигналов.

5. **Золотое правило Workflow: Детерминированность**: Код Workflow исполняется через механизм Event Sourcing / Replay. Сформулируйте и продемонстрируйте «Золотое правило»: код рабочего процесса ОБЯЗАН быть строго детерминированным! Почему категорически запрещено использовать `time.Now()`, `rand.Int()`, стандартные горутины `go func()`, глобальные переменные и любые прямые сетевые/дисковые вызовы внутри Workflow?

6. **Workflow Context vs Стандартный Go context.Context**: Изучите интерфейс `workflow.Context`. В чем его отличие от стандартного `context.Context` из библиотеки Go? Покажите, как `workflow.Context` управляет детерминированным временем через `workflow.Now(ctx)`, логами через `workflow.GetLogger(ctx)` и генерацией UUID через `workflow.SideEffect`.

7. **Реализация первой Activity (Сетевые вызовы и сайд-эффекты)**: Напишите Activity-функцию `ProcessPaymentActivity(ctx context.Context, req PaymentRequest) (PaymentResponse, error)`. Поскольку Activity выполняется вне механизма детерминированного replay, в ней разрешены любые операции ввода-вывода (HTTP, gRPC, SQL). Продемонстрируйте использование стандартного `context.Context` для передачи таймаутов.

8. **Конфигурация таймаутов Activity**: Настройте параметры вызова Activity в `workflow.ActivityOptions`: `StartToCloseTimeout` (максимальное время одного выполнения), `ScheduleToStartTimeout` (время ожидания свободного воркера в очереди), `ScheduleToCloseTimeout` (общее время от постановки до финала) и `HeartbeatTimeout`. Объясните назначение каждого таймаута.

9. **Автоматические повторные попытки (RetryPolicy) в Temporal**: Сконфигурируйте политику повторов `temporal.RetryPolicy`: `InitialInterval: 1 * time.Second`, `BackoffCoefficient: 2.0`, `MaximumInterval: 100 * time.Second`, `MaximumAttempts: 5`. Продемонстрируйте, как Temporal автоматически повторяет временно сбоящую Activity без необходимости писать циклы ретраев в Go-коде.

10. **Неповторяемые ошибки (Non-Retryable Application Errors)**: Если платежная карта заблокирована или на счете недостаточно средств, повторять вызов бессмысленно. Реализуйте возврат неповторяемой ошибки: `temporal.NewNonRetryableApplicationError("insufficient funds", "INSUFFICIENT_FUNDS", nil)`. Убедитесь, что Temporal мгновенно прерывает ретраи и возвращает ошибку в Workflow.

11. **Activity Heartbeating для длительных операций**: При выполнении тяжелой задачи (например, транскодирование видео на 2 часа) воркер может зависнуть. Реализуйте отправку пульса `activity.RecordHeartbeat(ctx, progress)`. Установите `HeartbeatTimeout: 30 * time.Second`. Если воркер перестает слать heartbeat, Temporal считает его умершим и переназначает задачу другому воркеру с последнего сохраненного прогресса.

12. **Параллельное выполнение Activities через workflow.Go**: Вам необходимо одновременно забронировать отель, авиабилеты и аренду автомобиля. Используйте детерминированную конкурентность Temporal: запустите действия параллельно с помощью `workflow.Go(ctx, func(ctx workflow.Context) { ... })` или сохраните несколько `workflow.Future` и дождитесь их завершения через `workflow.Selector`.

13. **Сигналы (Signals): Асинхронное взаимодействие с Workflow**: Реализуйте прием внешних сигналов в работающий Workflow. Создайте канал сигналов: `signalChan := workflow.GetSignalChannel(ctx, "PaymentConfirmedSignal")`. Напишите внешний HTTP-хэндлер, который по эндпоинту `/webhooks/payment` отправляет сигнал в работающий экземпляр процесса через `client.SignalWorkflow(...)`.

14. **Запросы (Queries): Синхронное чтение состояния Workflow**: Как узнать текущий статус выполнения многодневного бизнес-процесса? Зарегистрируйте Query-хэндлер внутри Workflow: `workflow.SetQueryHandler(ctx, "getStatus", func() (OrderStatus, error) { return currentStatus, nil })`. Напишите клиентский код, вызывающий `client.QueryWorkflow(...)` для мгновенного синхронного получения статуса без изменения истории событий.

15. **Таймеры в Temporal: Сон на дни и месяцы без расхода ресурсов**: Реализуйте шаг бизнес-логики: «Если пользователь не подтвердил регистрацию в течение 7 дней, отправить напоминание; если не подтвердил за 30 дней — удалить аккаунт». Используйте `workflow.Sleep(ctx, 7 * 24 * time.Hour)`. Объясните, почему во время сна процесс не потребляет CPU или RAM сервера, так как состояние спит в базе данных кластера.

16. **Паттерн Human-in-the-Loop (Согласование человеком)**: Спроектируйте процесс выдачи кредита: автоматический скоринг -> если сумма > 1 000 000 руб, Workflow засыпает и ждет сигнал согласования от менеджера (`ManagerApprovalSignal`) в течение 3 дней. При получении сигнала кредит одобряется, при истечении 3 дней без ответа — автоматически отклоняется по таймауту.

17. **Дочерние рабочие процессы (Child Workflows)**: Разбейте сложный монолитный Workflow на композируемые дочерние процессы с помощью `workflow.ExecuteChildWorkflow(ctx, SubWorkflow, args)`. Настройте политику завершения родителя `ParentClosePolicy` (должен ли дочерний процесс прерываться при отмене родителя) и получите результат работы дочернего процесса.

18. **Реализация распределенной Саги на Temporal**: Реализуйте паттерн Saga для бронирования путешествия: последовательно бронируются рейс, отель и авто. Напишите стек компенсаций (срез замыканий `compensations = append(compensations, cancelFlightActivity)`). При возникновении ошибки на любом этапе Workflow в обратном порядке выполняет все накопленные компенсации, гарантируя консистентность.

19. **Версионирование рабочих процессов (Workflow Versioning)**: Вы обновили бизнес-логику в коде (заменили старую Activity на новую). Старые запущенные экземпляры процессов при выкатке упадут с ошибкой недетерминированности (`NonDeterministicWorkflowPolicy`)! Примените метод `workflow.GetVersion(ctx, "changeID", workflow.DefaultVersion, 1)` для безопасного разделения веток исполнения старого и нового кода.

20. **Тестирование на недетерминированность (Replay Testing)**: Перед деплоем новой версии Workflow в прод необходимо убедиться, что новый код совместим со всей историей завершенных и текущих процессов. Напишите тест с использованием `worker.NewWorkflowReplayer()`: выгрузите JSON-историю событий реального продакшен-процесса и прогоните ее через новый код. Убедитесь в отсутствии ошибок `DeterminismError`.

21. **Политики повторного использования Workflow ID**: Сконфигурируйте `WorkflowIdReusePolicy`: `ALLOW_DUPLICATE`, `ALLOW_DUPLICATE_FAILED_ONLY`, `REJECT_DUPLICATE`. Продемонстрируйте, как использование бизнес-идентификатора заказа в качестве `WorkflowID` защищает систему от случайного повторного запуска одного и того же заказа.

22. **Динамические очереди задач (Task Routing per Worker Pool)**: Некоторые задачи требуют специальных аппаратных ресурсов (например, наличие GPU или доступ к изолированной банковской сети). Покажите, как маршрутизировать конкретные Activities на специализированные пулы воркеров, передавая кастомное имя `TaskQueue` в `workflow.ActivityOptions`.

23. **Паттерн Continue-As-New для бесконечных процессов**: Если процесс работает годами (например, IoT-устройство шлет телеметрию раз в минуту), история событий Temporal Cluster превысит рекомендуемый лимит в 10 000 событий. Реализуйте метод `workflow.NewContinueAsNewError(ctx, ProcessDeviceWorkflow, updatedState)`: текущая история архивируется, а процесс перезапускается с чистого листа со свежим состоянием.

24. **Отмена процессов (Workflow Cancellation) и очистка ресурсов**: Реализуйте обработку сигнала отмены Workflow (`client.CancelWorkflow`). Внутри рабочего процесса перехватите отмену через `workflow.GetSignalChannel` или проверку `ctx.Err()`. Создайте новый отсоединенный контекст `workflow.NewDisconnectedContext(ctx)` для гарантированного выполнения завершающих очищающих Activities.

25. **Модульное тестирование Workflow с Time Skipping**: Напишите юнит-тесты на Temporal с использованием пакета `go.temporal.io/sdk/testsuite`. Протестируйте 30-дневный таймер: покажите, как тестовое окружение Temporal автоматически перематывает виртуальное время вперед (Time Skipping) без реального ожидания, позволяя выполнить тест за несколько миллисекунд.

26. **Мокирование Activities в тестах**: В тестовом наборе `testsuite.WorkflowTestSuite` замените реальные Activity-функции на моки с помощью `env.OnActivity(ProcessPaymentActivity, mock.Anything, mock.Anything).Return(expectedResp, nil)`. Проверьте корректность бизнес-логики Workflow при имитации ошибок платежного шлюза.

27. **Распределенная трассировка и логирование через Interceptors**: Подключите интерцепторы OpenTelemetry в Temporal: `opentelemetry.NewTracingInterceptor()`. Убедитесь, что W3C Trace Context прозрачно пробрасывается из клиентского запроса в Workflow, а затем во все дочерние Activities, обеспечивая сквозную визуализацию пути запроса в Jaeger / Grafana Tempo.

28. **Сквозное шифрование полезной нагрузки (Custom DataConverter)**: Политики безопасности запрещают хранить персональные данные (паспорт, номер карты) в открытом виде в базе данных кластера Temporal. Реализуйте кастомный `converter.DataConverter`, который прозрачно шифрует все аргументы и результаты функций алгоритмом AES-256-GCM на стороне воркера до отправки в кластер.

29. **Тюнинг производительности воркеров под HighLoad**: Оптимизируйте конфигурацию воркера под высокие нагрузки: настройка `MaxConcurrentActivityExecutionSize`, `MaxConcurrentWorkflowTaskExecutionSize`, тюнинг кэша рабочих процессов `worker.SetStickyWorkflowCacheSize(10000)` и пула горутин. Объясните влияние Sticky Execution на снижение задержки исполнения задач.

30. **Сквозной бизнес-процесс E-Commerce Order Fulfillment**: Спроектируйте законченный комплексный рабочий процесс интернет-магазина: резервация товаров на складе -> авторизация платежа -> ожидание ручного подтверждения службой безопасности при подозрительной транзакции (Signal) -> отправка курьерской службой -> трекинг статуса доставки с таймерами -> начисление бонусов. Включите полную обработку сбоев, компенсации Саги и версионирование.
