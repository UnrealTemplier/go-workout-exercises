# Облачные хранилища, Envelope Encryption и KMS

В этом файле собраны уникальные упражнения по теме **"Облачные хранилища, Envelope Encryption и KMS"**, отсортированные по возрастанию сложности.

---

1. **Шифрование конвертов (Envelope Encryption) с KMS**: * Объясните в комментариях концепцию шифрования конвертов: почему мы не отправляем файлы размером в гигабайты напрямую в Key Management Service (KMS) облачного провайдера для шифрования (ограничения сетевого трафика и лимиты размера данных KMS).
    * Напишите код интеграции с AWS KMS (или GCP KMS) с использованием официального AWS SDK для Go.
    * Вызовите метод `GenerateDataKey` [641]. Получите локальный ключ шифрования данных (DEK) в открытом и зашифрованном (KMS) виде [641].
    * Зашифруйте тестовую строку с помощью DEK (симметричный алгоритм AES-GCM) [641].
    * Удалите открытый DEK из памяти, сохранив зашифрованный DEK рядом с зашифрованными данными.

2. **Ручное Envelope Encryption.**: Реализуйте на Go: сгенерируйте случайный AES-256-GCM ключ (DEK) через `crypto/rand`, зашифруйте им файл, затем зашифруйте DEK мастер-ключом (KEK) через AES-GCM или RSA-OAEP. Сохраните вместе: `encrypted_dek + nonce + ciphertext`. Объясните, зачем шифровать данные DEK, а не KEK напрямую (perf + ротация).

3. **AWS SDK v2 (S3 Basics)**: Установи пакет `github.com/aws/aws-sdk-go-v2`. Настрой клиент через `config.LoadDefaultConfig`. Подними локально MinIO в Docker (совместим с S3 API). Напиши код для создания бакета и загрузки небольшого текстового файла.

4. **Envelope Encryption вручную.**: Сгенерируйте DEK (Data Encryption Key) AES-256, зашифруйте им файл. Затем зашифруйте DEK с помощью KEK (Key Encryption Key), хранящегося локально (эмуляция KMS). Сохраните зашифрованный DEK и зашифрованный файл вместе.

5. **[S3 Baseline]**: Используй AWS SDK v2 для Go (`github.com/aws/aws-sdk-go-v2`). Подними LocalStack или MinIO в Docker. Загрузи небольшой текстовый файл в бакет (`s3.PutObject`) и скачай его обратно.

6. **AWS KMS setup**: Создайте KMS key в AWS Console или через Terraform. Изучите key policies и IAM permissions.

7. **AWS KMS: GenerateDataKey.**: Используйте AWS SDK (`github.com/aws/aws-sdk-go-v2/service/kms`) для вызова `GenerateDataKey` (AES-256). Получите `Plaintext` (DEK) и `CiphertextBlob` (зашифрованный DEK). Зашифруйте файл, удалите `Plaintext` из памяти (`memzero`), сохраните `CiphertextBlob` рядом с данными. Объясните, почему DEK никогда не хранится в plaintext вне RAM.

8. **Presigned URLs (Прямая загрузка)**: Гонять гигабайты видео через свой Go-сервер — смерть для сети. Сгенерируй Presigned URL (подписанную ссылку) со сроком жизни 15 минут. Верни её клиенту (фронтенду), чтобы он загрузил файл *напрямую* в S3, минуя твой бэкенд.

9. **Encrypt data with DEK**: Используйте plaintext DEK для шифрования данных через AES-256-GCM:
    ```go
    block, _ := aes.NewCipher(dekPlaintext)
    gcm, _ := cipher.NewGCM(block)
    ciphertext := gcm.Seal(nil, nonce, plaintext, aad)
    ```

10. **Decrypt flow**: При чтении:
    * Извлеките encrypted DEK
    * Вызовите `kms.Decrypt()` для получения plaintext DEK
    * Используйте plaintext DEK для дешифрования данных
    * **Важно:** удаляйте plaintext DEK из памяти после использования

11. **Store encrypted DEK + data**: Сохраните encrypted DEK и encrypted data вместе (например, в S3 object metadata или в БД).

12. **[Multipart Upload]**: Напиши загрузчик больших файлов (> 100MB). Используй `s3.NewMultipartUploader`. Разбей файл на части по 5MB, загрузи их конкурентно (через горутины), затем вызови `CompleteMultipartUpload`.

13. **Расшифровка через Envelope Encryption.**: Прочитайте зашифрованный DEK, расшифруйте его KEK, затем расшифруйте файл. Реализуйте прозрачную обёртку `Encrypt(plain io.Reader, kek []byte) (io.Reader, error)` и `Decrypt(encrypted io.Reader, kek []byte) (io.Reader, error)`.

14. **Multipart Upload (Своими руками)**: Файл весит 5 ГБ. Загрузить его одним куском не выйдет (S3 отвалится по таймауту). Вызови `CreateMultipartUpload`. Нарежь файл на куски по 10 МБ. Используя `sync.WaitGroup`, запусти горутины, каждая из которых грузит свой кусок (`UploadPart`). Собери ETag каждого куска и вызови `CompleteMultipartUpload`.

15. **Key Rotation без перешифрования данных.**: Реализуйте схему: старый KEK расшифровывает DEK, новый KEK зашифровывает тот же DEK, обновляет `encrypted_dek` в метаданных. Данные не трогаются. Объясните, почему envelope encryption позволяет ротировать KEK за O(1) на объект.

16. **GCP Cloud KMS: аналог.**: Реализуйте тот же сценарий через `cloud.google.com/go/kms/apiv1`. Сравните API: AWS возвращает DEK в ответе, GCP требует `Encrypt`/`Decrypt` вызовов для DEK (или `GenerateRandomBytes` + `Encrypt`). Объясните разницу в trust model.

17. **KMS grants**: Используйте KMS grants для делегирования доступа к ключу другим AWS accounts или services.

18. **Потоковое шифрование (Streaming Envelope Encryption)**: При обработке терабайтных бэкапов мы не можем держать данные в оперативной памяти. Напишите Go-код, который принимает `io.Reader` исходного файла, читает его чанками, шифрует каждый чанк "на лету" с помощью DEK в режиме потокового шифра (например, AES-CFB или AES-GCM со смещением nonce) и записывает результат в выходной `io.Writer`.

19. **KMS key policies**: Настройте fine-grained key policies: кто может использовать ключ, с каких IP, в какое время.

20. **S3 Multipart Upload вручную.**: Используйте AWS SDK: `CreateMultipartUpload`, загрузите 5 частей по 100 MB через `UploadPart`, завершите `CompleteMultipartUpload`. Покажите, что ETag каждой части — MD5 (или контрольная сумма), и порядок parts важен. Объясните, зачем multipart: resume, parallel upload, большие файлы.

21. **CloudTrail для KMS**: Включите CloudTrail для аудита всех KMS API вызовов. Это критично для compliance (PCI DSS, HIPAA).

22. **[Каверзный кейс — Abort Multipart Upload]**: Если во время загрузки 5-й части пропало соединение, вызови `AbortMultipartUpload`. Если этого не сделать, "висящие" части останутся в S3 и будут тарифицироваться. Напиши cron-job, который вызывает `ListMultipartUploads` и удаляет загрузки старше 1 часа.

23. **S3 Uploader (High-Level)**: Забудь ручной код из 893. Используй `manager.NewUploader(client)` из пакета `feature/s3/manager`. Передай ему `io.Reader` большого файла. Убедись, что менеджер сам "под капотом" буферизирует данные и конкурентно грузит их через Multipart.

24. **Multipart + Envelope Encryption.**: Реализуйте: перед каждым `UploadPart` генерируйте уникальный DEK (или derived key через HKDF от общего DEK + part number). Шифруйте часть AES-GCM, загружайте. Сохраните метаданные шифрования (`x-amz-meta-x-dek`, `x-amz-meta-x-nonce`) в `CompleteMultipartUpload`. Объясните, почему нельзя использовать один nonce для всех частей.

25. **Azure Key Vault**: Используйте `github.com/Azure/azure-sdk-for-go/sdk/keyvault/azkeys` для Azure Key Vault.

26. **Интеграция с AWS KMS.**: Используя `aws-sdk-go-v2`, создайте ключ KMS (Customer Master Key). Зашифруйте небольшой секрет (например, пароль БД) напрямую через `Encrypt` API KMS, затем расшифруйте.

27. **HashiCorp Vault как KMS**: Используйте Vault Transit secrets engine как альтернативу cloud KMS. Это даёт control over keys и on-premise deployment.

28. **Знакомство с KMS**: Установи клиент KMS. Создай в AWS (или локально через LocalStack) Master Key (CMK). Напиши Go-код, который отправляет строку "my_secret" в KMS и получает зашифрованные байты (`Encrypt`), а затем расшифровывает их обратно.

29. **Streaming Encryption без полного чтения в RAM.**: Реализуйте `io.Reader`, который читает из `os.File`, шифрует chunk-by-chunk (AES-GCM с счётчиком), и передаёт в `UploadPart` через `io.Pipe`. Покажите, что пиковое потребление RAM — размер одного chunk (5 MB), а не всего файла. Объясните, почему AES-GCM streaming требует careful nonce management (counter-based).

30. **Envelope Encryption для S3**: Шифруйте S3 objects client-side через envelope encryption перед upload. Это даёт full control over keys (vs S3-managed encryption).

31. **[Envelope Encryption — Концепция]**: Изучи паттерн: данные шифруются локальным симметричным ключом (AES-GCM), а сам локальный ключ шифруется облачным асимметричным ключом (KMS). В БД сохраняется только зашифрованный локальный ключ (Ciphertext Blob) и зашифрованные данные.

32. **DEK caching**: Для производительности кэшируйте plaintext DEK в памяти (с TTL). Но помните: при compromise приложения все cached DEKs скомпрометированы.

33. **Проверка целостности после upload.**: После `CompleteMultipartUpload` вызовите `HeadObject`, получите `x-amz-meta-x-dek`. Расшифруйте DEK через KMS, скачайте файл, расшифруйте, сравните SHA-256 с оригиналом. Объясните, почему S3 ETag не гарантирует целостность при клиентском шифровании (ETag считается от ciphertext).

34. **Многокомпонентная загрузка с шифрованием (Multipart Upload в S3)**: Используя AWS SDK v2 для Go, реализуйте загрузку большого файла в бакет S3 по частям (Multipart Upload) [643]. Каждый чанк (минимальный размер 5 МБ по требованиям S3) должен шифроваться локальным DEK (из задачи №641) непосредственно перед отправкой в S3 [643]. Обеспечьте вызов `CompleteMultipartUpload` при успешной отправке всех зашифрованных частей [643].

35. **DEK per tenant**: Для multi-tenant SaaS используйте отдельный DEK per tenant. Это позволяет crypto-shredding (удаление данных через удаление DEK).

36. **Envelope Encryption (Концепция)**: *Нельзя отправлять 5 ГБ данных в KMS.* Архитектура конверта: сгенерируй случайный 32-байтный Data Encryption Key (DEK) прямо в Go. Зашифруй большой файл локально с помощью AES-GCM (из Блока 68), используя этот DEK.

37. **Envelope Encryption с AWS KMS.**: Сгенерируйте DEK через KMS (`GenerateDataKey`), который возвращает открытый и зашифрованный DEK. Зашифруйте файл открытым DEK, сохраните зашифрованный DEK. При расшифровке сначала расшифруйте DEK через KMS, затем файл.

38. **KMS latency optimization**: KMS вызовы имеют latency 50-200ms. Кэшируйте DEKs, используйте batch operations, минимизируйте KMS calls.

39. **SSE-KMS vs Client-Side Encryption.**: Сравните: (1) SSE-KMS (S3 шифрует данные, ключ в KMS, вы не управляете DEK), (2) CSE (вы шифруете, KMS только оборачивает DEK). Покажите, что при SSE-KMS провайдер видет plaintext (внутри инфраструктуры), при CSE — нет. Объясните compliance (GDPR, HIPAA) требования к CSE.

40. **KMS cost optimization**: KMS charges per API call. Для high-volume используйте DEK caching и batch encryption.

41. **[Интеграция KMS]**: Сгенерируй KMS Key в AWS (или эмулируй в LocalStack). Используй `kms.GenerateDataKey` (вернет открытый ключ и зашифрованный ключ).

42. **Шифрование Конвертом (Wrap)**: Отправь свой сгенерированный DEK в KMS, чтобы зашифровать его (Wrap). Сохрани в S3 два объекта: зашифрованный файл (данные) и зашифрованный DEK (ключ от данных). Теперь, даже если хакер украдет данные из S3, он не сможет их расшифровать без доступа к AWS KMS.

43. **KMS + HSM**: Для maximum security используйте CloudHSM (AWS) или Cloud HSM (GCP) — dedicated hardware security modules.

44. **Object Lock + Legal Hold.**: Настройте S3 Object Lock (WORM) на bucket. Загрузите зашифрованный объект с `Retention Mode: Compliance`, `RetainUntilDate: +7 years`. Покажите, что даже root-аккаунт не может удалить объект до даты. Объясните, как envelope encryption + WORM защищают от ransomware (зашифрованные данные не подменить).

45. **KMS key aliases**: Используйте aliases для key rotation без изменения application code.

46. **KMS cross-account**: Для multi-account AWS setup используйте cross-account KMS access через key policies.

47. **Пакетная ротация DEK.**: У вас 10 000 объектов в S3. Реализуйте worker pool, который: читает `encrypted_dek` из S3 metadata, вызывает KMS Decrypt, затем KMS Encrypt с новым KEK, обновляет S3 metadata через `CopyObject` (metadata replace). Объясните, почему `CopyObject` — единственный способ обновить metadata без re-upload.

49. **Расшифровка (Unwrap & Stream)**: Скачай зашифрованный DEK из S3. Отправь его в KMS для расшифровки. Получив чистый DEK, скачай зашифрованный файл из S3 потоком (`GetObject`). Используй `cipher.StreamReader`, чтобы расшифровывать гигабайтный файл на лету (in-memory) и сразу отдавать клиенту через HTTP, не сохраняя его на диск!

50. **Ротация ключей KMS.**: Настройте автоматическую ротацию ключа в AWS KMS (или эмуляцию через версионирование). Реализуйте механизм, при котором старые DEK расшифровываются старой версией ключа, но новые шифруются новой версией.

51. **Предотвращение утечек незавершенных загрузок (Abort Upload)**: Напишите код обработки ошибок для задачи №643. Если при загрузке одного из чанков в S3 произошел сбой, программа должна гарантированно вызвать метод `AbortMultipartUpload` [643]. Напишите подробный комментарий, объясняющий финансовые риски игнорирования этого шага (S3 продолжит бессрочно хранить недозагруженные части файла на дисках и тарифицировать их, так как они не видны в стандартном списке объектов бакета).

52. **[Шифрование и загрузка]**: Зашифруй 50MB файл с помощью открытого Data Key (AES-GCM). Загрузи файл в S3. В метаданные объекта (`Metadata`) положи зашифрованный Data Key.

68. **Part size optimization**: Оптимальный part size: 16-64MB. Меньше — overhead от API calls. Больше — wasted bandwidth при retry.

69. **Resume failed upload**: При failure сохраняйте upload ID и completed parts. Resume upload через `UploadPartCopy` или повторный `UploadPart` для failed parts.

70. **Envelope Encryption + S3 SSE**: Комбинируйте client-side envelope encryption с S3 server-side encryption (SSE-S3 или SSE-KMS) для defense in depth.

71. **Abort incomplete upload**: Используйте `AbortMultipartUpload` для cleanup incomplete uploads. Иначе они занимают место и incur storage costs.

72. **[Высокая сложность — Streaming Encryption]**: Перепиши предыдущее задание так, чтобы не загружать весь файл в память. Читай файл чанками по 64KB, шифруйте их через `cipher.NewGCMEncryptor` (обновляя nonce-счетчик) и стримьте напрямую в `s3.NewMultipartUploader` через `io.Pipe`.

73. **Lifecycle policy для cleanup**: Настройте S3 lifecycle policy для automatic abort incomplete uploads старше 7 дней.

74. **Параллельная загрузка частей с контролем конкурентности.**: Реализуйте загрузку 10 частей параллельно с ограничением на количество одновременных загрузок (семафор). Обработайте ошибки отдельных частей с возможностью повторной загрузки.

75. **Multipart upload progress tracking**: Отслеживайте progress: bytes uploaded / total bytes. Экспортируйте в Prometheus.

76. **Multipart upload rate limiting**: Ограничьте bandwidth для multipart uploads, чтобы не saturate network.

77. **Multipart upload + checksums**: Вычисляйте checksum (MD5, SHA256) для каждой part. S3 верифицирует checksums при CompleteMultipartUpload.

78. **Multipart upload + metadata**: Добавляйте custom metadata к multipart upload (например, `x-amz-meta-encrypted-dek`).

79. **Multipart upload + ACL**: Устанавливайте ACL для multipart upload (например, `private`, `public-read`).

80. **Resume Multipart Upload после сбоя.**: Эмулируйте обрыв сети, сохранив `UploadId`. Реализуйте функцию, которая возобновляет загрузку с незавершённых частей (запрос `ListParts`, проверка уже загруженных, догрузка остальных).

81. **Multipart upload + storage class**: Указывайте storage class (Standard, Infrequent Access, Glacier) для multipart upload.

82. **GCS multipart upload (composite objects)**: GCS использует composite objects вместо multipart upload:
    * Upload parts как отдельные objects
    * `Compose` для объединения в один object
    Изучите отличия от S3.

83. **GCS resumable upload**: Используйте resumable upload для больших файлов в GCS. Это позволяет resume при network failure.

84. **Multipart upload benchmarking**: Сравните производительность:
    * Single PUT vs multipart upload
    * Sequential vs parallel parts
    * Разные part sizes
    * Разные concurrency levels

85. **Multipart upload testing**: Напишите тесты, которые:
    * Загружают 1GB файл через multipart
    * Симулируют network failure mid-upload
    * Resume upload
    * Верифицируют integrity

86. **Генерация Pre-signed URL для S3.**: Создайте временную ссылку (на 1 час) для скачивания объекта из S3 без публичного доступа к бакету. Используйте `PresignClient`.

87. **KMS key rotation**: Настройте automatic key rotation в KMS (раз в год). Старые encrypted DEKs остаются валидными, новые данные шифруются новым KEK.

88. **Crypto-shredding для GDPR.**: Для "right to be forgotten" удаляйте DEK пользователя. Данные становятся нечитаемыми без физического удаления из БД.

89. **Envelope Encryption — это standard.**: Никогда не храните plaintext keys в приложении. Используйте KMS для KEK, DEK для data encryption. Это даёт key rotation без re-encryption данных.

90. **Multipart Upload для файлов >100MB.**: Single PUT имеет 5GB limit и не поддерживает resume. Multipart upload даёт parallel upload, resume при failure, и обходит size limits.

91. **Блок 32 (Envelope Encryption)**: — начните после Блока 10 (криптография), так как envelope encryption — прямое продолжение AES-GCM + RSA/Ed25519. Знание `crypto/rand` и `cipher` обязательно.

92. **Observability из коробки.**: Service mesh автоматически даёт:

    Используйте это, не изобретайте своё.

93. **Блок 34 (Tracing)**: — параллельно с Service Mesh, так как tracing — это cross-cutting concern. Требует понимания `context.Context` propagation (Блок 1, GMP — goroutine-local storage не существует, только context).

94. **S3 Lifecycle policies.**: Настройте automatic abort incomplete multipart uploads, transition to Infrequent Access/Glacier, expiration старых objects.
