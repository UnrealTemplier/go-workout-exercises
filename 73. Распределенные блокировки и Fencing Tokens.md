# Распределенные блокировки и Fencing Tokens

В этом файле собраны уникальные упражнения по теме **"Распределенные блокировки и Fencing Tokens"**, отсортированные по возрастанию сложности.

---

1. **Базовый Redis Lock**: Реализуй блокировку. Используй `SET resource_name my_random_value NX PX 10000`. `NX` (только если ключа нет) гарантирует эксклюзивность, `PX 10000` (TTL 10 сек) спасает от дедлока, если сервер умрет с блокировкой.

2. **Безопасное снятие блокировки (Lua-скрипт)**: Клиент должен удалять *только свою* блокировку. Если просто сделать `GET` и `DEL`, то между ними другой процесс может перехватить ключ (Race Condition). Напиши Lua-скрипт `if redis.call("get",KEYS[1]) == ARGV[1] then return redis.call("del",KEYS[1]) else return 0 end`. Выполни его через `client.Eval()`.

3. **Продление TTL (Watchdog Pattern)**: Бизнес-логика занимает больше 10 секунд, но ставить TTL = 1 час опасно (вдруг воркер упал). Напиши фоновую горутину ("сторожевой пес"). Пока основная горутина работает, "пес" каждые 3 секунды отправляет в Redis команду на продление TTL (`PEXPIRE`) текущего лока. При выходе из функции убивай "пса" через `context`.

4. **Уязвимость одиночного Redis (Redlock)**: Redis кластер асинхронен. Ты взял лок на мастере, мастер упал, данные не успели реплицироваться на слейв, слейв стал мастером. Другой сервис берет лок на те же данные! Изучи алгоритм **Redlock**. Установи библиотеку `github.com/go-redsync/redsync`. Подними 3 независимых Redis-сервера и настрой блокировку, требующую кворума (минимум 2 из 3 серверов должны подтвердить лок).

5. **Ужас Split-Brain (Пауза сборщика мусора)**: *Мысленный и практический тест.* Воркер А взял лок на 5 секунд. Внезапно Go ловит тяжелую GC-паузу (или гипервизор ОС фризит виртуалку) на 6 секунд. Лок в Redis истек. Воркер Б берет лок и пишет в БД. Тут Воркер А "отвисает" и ТОЖЕ пишет в БД (он же уверен, что лок его!). Осознай, почему *любые* TTL-локи уязвимы к рассинхронизации времени.

6. **Fencing Token (Защита от Split-Brain)**: Решение проблемы 835. Токен ограждения (Fencing) — это монотонно возрастающее число. В Redis/etcd при взятии блокировки получай инкрементный токен (например, `Token: 42`). Воркер передает этот токен в БД вместе с запросом на изменение данных.

7. **Валидация Fencing Token на ресурсе**: Модифицируй таблицу в PostgreSQL, добавив `last_token_id INT`. Когда Воркер А (отвисший) присылает запрос с `Token=42`, а БД уже обработала запрос от Воркера Б с `Token=43`, база должна отклонить запрос А (42 < 43). Напиши логику, где ресурс сам защищается от устаревших локов!

8. **Знакомство с etcd**: `etcd` (движок Kubernetes) — это консистентное хранилище на базе протокола Raft. Подключи клиент `go.etcd.io/etcd/client/v3`. Сделай базовые `Put`, `Get` и `Delete`. Убедись, что etcd требует передачи контекста в каждый вызов.

9. **etcd Distributed Lock**: etcd решает проблемы Redis-локов за счет строгого консенсуса. Используй встроенный пакет `go.etcd.io/etcd/client/v3/concurrency`. Создай сессию `concurrency.NewSession()` и мьютекс `concurrency.NewMutex()`. Вызови `Lock()` и `Unlock()`.

10. **Управление Lease (Аренда в etcd)**: Механизм локов в etcd построен на Арендах (Lease). Создай Lease на 5 секунд. Привяжи к нему ключ. Пока твоя Go-программа жива, клиент etcd автоматически шлет keep-alive (продлевая аренду). Принудительно убей программу. Убедись, что через 5 секунд ключ сам исчез из etcd.

11. **Redis SET NX EX.**: Реализуйте lock: `SET lock:resource <random_value> NX EX 30`. Unlock через Lua-скрипт: удалить только если `value` совпадает. Объясните, почему нужен уникальный `random_value` (UUID) и почему `DEL` без проверки — опасен (можно удалить чужой lock).

12. **Проблема без distributed locks**: Два инстанса одновременно обрабатывают один order. Результат: double payment, data corruption.

13. **etcd Mutex.**: Используйте `clientv3/concurrency.Mutex`. Захватите `Lock(ctx)`, выполните критическую секцию, `Unlock()`. Покажите, что при crash процесса lease истекает и lock автоматически освобождается. Объясните, почему это надёжнее Redis (lease bound to TTL, not client connection).

14. **Redis single-node lock**: Простейший distributed lock:
    ```
    SET lock_key "owner" NX EX 30
    ```
    Проблема: если Redis упадёт, lock потерян.

15. **Redlock algorithm**: Изучите Redlock от Salvatore Sanfilippo (antirez):
    * 5 независимых Redis instances
    * Lock acquired, если majority (3/5) согласились
    * Timeout + retry logic

16. **Redlock implementation**: Реализуйте Redlock через `github.com/go-redsync/redsync`:
    ```go
    rs := redsync.New(pools)
    mutex := rs.NewMutex("my-lock", redsync.WithExpiry(30*time.Second))
    mutex.Lock()
    defer mutex.Unlock()
    ```

17. **PostgreSQL Advisory Lock.**: Реализуйте `pg_advisory_lock(key)` и `pg_advisory_unlock(key)` через `database/sql`. Сравните с Redis/etcd: нет network partition между БД и приложением (если они в одном DC), но нет автоматического release при смерти приложения (требуется session termination).

18. **Redlock controversy**: Изучите критику Redlock от Martin Kleppmann. Redlock не даёт true distributed consensus, только best-effort locking.

19. **etcd distributed lock**: Используйте etcd для reliable distributed locks:
    ```go
    session, _ := concurrency.NewSession(client)
    mutex := concurrency.NewMutex(session, "/locks/my-lock")
    mutex.Lock(ctx)
    defer mutex.Unlock(ctx)
    ```

20. **etcd lock + lease**: etcd lock автоматически освобождается при session expiry (lease TTL).

21. **Redlock Algorithm (упрощённый).**: Реализуйте: 5 Redis-нод, acquire lock на majority (>=3) с одинаковым TTL, clock drift margin. Release — удаление на всех нодах. Объясните критику Martin Kleppmann: clock skew, delay между acquire и actual lock, феномен «временной дыры» (lock истекает до окончания работы).

22. **Простая распределенная блокировка на Redis (один экземпляр).**: Реализуйте блокировку с `SET NX PX`, используя `go-redis`. Захватите блокировку с уникальным токеном (UUID), выполните критическую секцию, освободите с проверкой токена (Lua-скрипт).

23. **[Redlock Basic]**: Установи `github.com/go-redsync/redsync/v2`. Реализуй захват блокировки на 3 независимых инстансах Redis. Убедись, что если 2 Redis упадут, блокировка не будет получена.

24. **Consul distributed lock**: Используйте Consul для locks:
    ```go
    lock, _ := consul.LockKey("my-lock")
    leaderCh, _ := lock.Lock(nil)
    defer lock.Unlock()
    ```

25. **Keepalive при длинной операции.**: Операция занимает 60 сек, lock TTL = 30 сек. Реализуйте горутину, которая каждые 10 сек продлевает lease (Redis `PEXPIRE` или etcd `KeepAlive`). При завершении операции — stop renew, release lock. Объясните, почему `max_extension_count` защищает от infinite loop при hung process.

26. **Lock timeout**: Всегда устанавливайте timeout на lock acquisition. Иначе deadlock при hung process.

27. **Lock retry with backoff**: Если lock не получен, retry с exponential backoff + jitter.

28. **Проблема Delay (GC Pause, Network Lag).**: Реализуйте симуляцию: узел захватил lock (TTL=5с), затем GC pause 10 сек (или `time.Sleep`). Lease истекает, другой узел захватывает lock. Первый узел просыпается и продолжает работу в критической секции. Покажите, что **два узла одновременно владеют lock**.

29. **Lock scope**: Минимизируйте critical section под lock. Не держите lock дольше необходимого.

30. **Redlock: блокировка через несколько Redis-узлов.**: Реализуйте алгоритм Redlock: попытайтесь захватить блокировку на N независимых Redis-серверах (минимум 3), используя одинаковый ключ и случайный токен. Блокировка считается успешной, если захвачено большинство за время таймаута.

31. **[Lock with Context]**: Используй `redsunc.LockContext`. Если контекст отменяется (таймаут), блокировка должна автоматически сниматься.

32. **Read-write locks**: Для read-heavy workloads используйте read-write locks (multiple readers, single writer).

33. **Fencing Token: Monotonic Counter.**: Реализуйте центральный сервис (etcd или PostgreSQL sequence), который выдаёт monotonic token при каждом захвате lock. Процесс получает token=42, выполняет `UPDATE accounts SET balance = 100, token = 42 WHERE token < 42`. Объясните, как storage отклоняет stale операции (token < current).

34. **Lock testing**: Напишите тесты, которые:

    * Каждая пытается захватить lock
    * Проверяют, что только одна goroutine в critical section одновременно

35. **Fencing tokens защищают от stale leaders/workers.**: При получении leadership/lock генерируйте монотонно возрастающий token. Используйте его для защиты от race conditions.

36. **Fencing с etcd Revision.**: Используйте `CreateRevision` из etcd как fencing token. При захвате lock через `clientv3.Txn` получите `CreateRevision`. Все последующие writes в БД включают `WHERE revision >= $createRevision`. Объясните, почему etcd revision — идеальный fencing token (strictly monotonic, persistent, replicated).

38. **[Каверзный кейс — The GC Pause Problem]**: Напиши симуляцию: Горутина A берет Redlock на 2 секунды. Локально она начинает выполнять работу. Но тут происходит Stop-The-World (GC) на 3 секунды (сэмулируй через `runtime.GC()` в цикле или `debug.SetGCPercent(-1)`). Lock в Redis истекает. Горутина B берет блокировку и начинает писать в файл/БД. Горутина A просыпается после GC и *продолжает* писать, думая, что держит лок. Происходит повреждение данных.

Усилите безопасность, добавив монотонно возрастающий fencing token (версию) из Redis, который проверяется на целевом сервисе перед модификацией данных.

59. **[Защита на стороне хранилища]**: Клиент A (токен 1) берет лок, получает GC паузу. Клиент B (токен 2) берет лок. Когда B пишет в хранилище (например, PostgreSQL), он передает токен 2. Хранилище запоминает `last_token = 2`. Когда просыпается A и пытается записать с токеном 1, PostgreSQL отклоняет операцию (через триггер или middleware), так как `1 < 2`.

66. **[Финальное испытание — HA Distributed Cache]**
