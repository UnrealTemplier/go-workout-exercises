1. **gRPC Keepalive на стороне клиента.**: Настройте `keepalive.ClientParameters`: `Time: 10s`, `Timeout: 3s`, `PermitWithoutStream: true`. Проверьте, что при обрыве сети клиент обнаруживает мёртвое соединение и переподключается.

2. **W3C Trace Context вручную.**: Реализуйте middleware, которое парсит заголовки `traceparent` (`00-<trace-id>-<span-id>-01`) и `tracestate` (vendor-specific). Генерирует новый `span-id` для входящего запроса. Пропагирует дальше в исходящие HTTP-запросы. Объясните формат traceparent и флаги `01` (sampled).

3. **B3 Propagation (Zipkin).**: Реализуйте аналог для B3: заголовки `X-B3-TraceId`, `X-B3-SpanId`, `X-B3-ParentSpanId`, `X-B3-Sampled`. Покажите, как B3 использует 64-bit IDs (vs 128-bit в W3C). Объясните, когда B3 нужен (legacy Zipkin), а когда W3C (OpenTelemetry, современный стандарт).

4. **gRPC Graceful Draining на сервере.**: При получении `SIGTERM` сервер вызывает `GracefulStop()`: перестаёт принимать новые запросы, но завершает текущие стримы. Клиенты должны корректно переключиться на другие экземпляры.

5. **Context propagation в gRPC.**: Используйте `metadata.MD` для передачи traceparent в gRPC. Реализуйте `UnaryClientInterceptor` и `UnaryServerInterceptor`, которые извлекают/вставляют traceparent из `metadata`. Объясните, почему gRPC требует ручного propagation (нет стандартных заголовков как в HTTP).

6. **Ручной Span.**: Используйте `go.opentelemetry.io/otel`: создайте `Tracer`, `Span`, добавьте `attributes` (`user_id`, `operation`), `events` («cache miss»), `status` (Error при 5xx). Завершите span через `defer span.End()`. Объясните, что span — это единица работы, а trace — дерево spans.

7. **gRPC Client-side Load Balancing с Draining.**: Настройте клиент с DNS-резолвером и round-robin балансировкой. При graceful draining сервер отправляет GOAWAY, и клиент исключает его из списка доступных адресов. Убедитесь в отсутствии ошибок на клиенте.

8. **Nested Spans и Parent-Child.**: Реализуйте функцию `ProcessOrder`, которая создаёт span, внутри вызывает `ValidatePayment` (child span) и `ReserveInventory` (child span). Покажите в Jaeger/Zipkin UI иерархию: `ProcessOrder` → `ValidatePayment` + `ReserveInventory`. Объясните, как `context.Context` передаёт parent span.

9. **Проблема SIGTERM в K8s**: Когда K8s гасит под, он шлет `SIGTERM` и *одновременно* дает команду iptables/Envoy убрать под из балансировки. Обновление роутинга занимает время (до 1-3 сек). Если твой Go-код сделает `srv.Shutdown()` мгновенно при получении SIGTERM, запросы, которые всё еще летят со стороны Envoy, упадут с 502 Bad Gateway. Осознай эту архитектурную боль!

34. **Антипаттерн Healthcheck (Liveness vs Readiness)**: Многие новички проверяют подключение к БД в `livenessProbe`. Если БД моргнула, K8s убьет и перезапустит твой Go-под. Это КАТАСТРОФА (поднимется под, БД лежит, он снова упадет — CrashLoopBackOff).
    Напиши правильные хендлеры:
    * `/live` (Liveness) — возвращает 200 OK всегда, пока сам процесс жив.
    * `/ready` (Readiness) — проверяет пинг до БД. Если БД лежит — возвращает 503 (под перестает получать HTTP трафик, но **не перезапускается**!).

51. **Service Mesh + gRPC Keepalive.**: Покажите, что Istio sidecar (Envoy) имеет свой `idle_timeout` (по умолчанию 1h для HTTP/2). gRPC keepalive PING сбрасывает Envoy idle timer. Объясните, как настроить `DestinationRule` с `tcpKeepalive` и `h2UpgradePolicy` для совместимости.

52. **Zero-Trust (SPIFFE/SPIRE)**: Использовать API-токены — прошлый век. Внедри SPIFFE. В кластере подними SPIRE. В Go-коде используй пакет `github.com/spiffe/go-spiffe/v2`. Получай короткоживущие X.509 сертификаты (SVID) напрямую из сокета оркестратора (без паролей!) и используй их для настройки двустороннего mTLS `tls.Config`.

53. **Защита сервера от частых пингов (Keepalive Enforcement)**: Чтобы клиенты не забивали сервер бесконечными пингами (DDoS-эффект), настройте на стороне gRPC-сервера политику `EnforcementPolicy` [653]:
    ```go
    keepalive.EnforcementPolicy{
        MinTime:             5 * time.Second, // минимальный интервал между пингами от клиента
        PermitWithoutStream: true,            // разрешить пинги без активных стримов
    }
    ```
    Объясните, почему при нарушении этого правила сервер принудительно разорвет соединение, отправив GOAWAY-фрейм с кодом ошибки `ENHANCE_YOUR_CALM` [653].

54. **Long-lived gRPC Streams (BiDi) и Draining.**: Реализуйте BiDi stream. При `GracefulStop` сервер должен отправить `io.EOF` (закрыть stream) клиентам, а не обрывать. Клиент должен обработать `EOF` и реконнектиться. Объясните, почему BiDi streams сложнее drain, чем unary RPC.

55. **Distributed Tracing Context обязателен.**: Без trace context propagation вы не сможете отладить request, который проходит через 5+ сервисов. W3C Trace Context — это standard.

56. **[Draining Long-lived Streams]**: У тебя есть bidirectional stream, который держит соединение часами. `GracefulStop()` будет висеть вечно, дожидаясь его закрытия. Реализуй механизм: при получении `SIGTERM` отправляй всем активным стримам специальное сообщение `ServerShuttingDownError`, заставляя клиентов инициировать разрыв соединения.

57. **Context propagation через все boundaries.**: HTTP headers, gRPC metadata, Kafka headers, NATS headers — везде пробрасывайте trace context. Иначе trace обрывается.

58. **gRPC Channelz.**: Включите `grpc.Channelz` сервис. Напишите клиент, который запрашивает `GetChannel`/`GetSubchannel` и выводит: состояние соединений (`READY`, `IDLE`, `TRANSIENT_FAILURE`), количество streams, last call started. Объясните, как это помогает debug «залипших» соединений.

59. **Cloud-Scale Rate Limiting (Redis Lua)**: В распределенной системе локальный счетчик не работает. Напиши алгоритм Token Bucket (Корзина токенов). Засунь всю логику (проверка, декремент, рефилл) в **один Lua-скрипт**. Вызывай его из Go через `redis.Eval`. Это гарантирует атомарность и убережет от Race Conditions при тысячах запросов с разных подов.

60. **Trace ID в логах и метриках.**: Каждый log entry и metric должен содержать trace_id. Это позволяет drill-down из Grafana в Jaeger в Kibana.

61. **Graceful Shutdown — это закон.**: При SIGTERM:
    * Stop accepting new requests
    * Wait for in-flight requests to complete (с timeout)
    * Close database connections
    * Flush buffers
    * Exit cleanly

62. **Connection Pool Tuning.**: Настройте gRPC клиент: `MaxRecvMsgSize`, `MaxSendMsgSize`, `InitialWindowSize`, `InitialConnWindowSize`. 74. **[Финальное испытание — Cloud-Native gRPC Service]**
    Разверни микросервис в локальном K8s (Minikube + Istio):

    - **Безопасность:** При чтении файлов из S3 используется Envelope Encryption (AWS KMS). Данные кэшируются в памяти, ключи в Redis.
    - **Сетевая стабильность:** Настроены gRPC Keepalive (клиент и сервер).
    - **Деплой:** При `kubectl delete pod` срабатывает `preStop: sleep 5`, затем Go-код ловит `SIGTERM`, рассылает `GOAWAY` стримам, вызывает `GracefulStop()`, закрывает пул Redis и завершается без единой 5xx ошибки в логах Istio.
