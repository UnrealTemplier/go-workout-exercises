# Альтернативные RPC-протоколы

В этом файле собраны уникальные упражнения по теме **"Альтернативные RPC-протоколы"**, отсортированные по возрастанию сложности.

---

1. **Базовый сервер.**: Реализуйте HTTP handler, парсящий JSON-RPC 2.0 Request: `{"jsonrpc":"2.0","method":"add","params":[1,2],"id":"uuid"}`. Dispatch по `method` через `map[string]func`. Возвращайте Response: `{"jsonrpc":"2.0","result":3,"id":"uuid"}`. Объясните, почему `jsonrpc: "2.0"` — обязательное поле.

2. **Method Registry.**: Реализуйте type-safe registry: `Register(name string, fn any)`, где `fn` — функция с сигнатурой `func(ctx, T) (R, error)`. Используйте `reflect` для вызова и валидации аргументов. Объясните компромисс: reflection vs code generation (как в `go-jsonrpc` от Filecoin).

3. **Notifications.**: Обработайте Request без поля `id`: это notification, не требует ответа (HTTP 204 или пустое тело). Реализуйте fire-and-forget метод `logEvent`. Объясните, почему notification не может иметь `error` в ответе — и как обрабатывать failures на стороне сервера (async logging).

4. **Реализация JSON-RPC 2.0 сервера**: Напишите HTTP-обработчик, соответствующий официальной спецификации протокола JSON-RPC 2.0. Сервер должен принимать только POST-запросы с телом в формате JSON, содержащим поля `jsonrpc` (строго `"2.0"`), `method`, `params` и `id`. Выполните указанный метод и верните ответ в формате `{"jsonrpc": "2.0", "result": ..., "id": ...}`. В случае ошибок возвращайте объект `error` со стандартными кодами ошибок (например, `-32601` для ненашедшегося метода).

5. **Batch Requests.**: Реализуйте обработку массива запросов: `[]Request`. Выполняйте параллельно (goroutine per request), сохраняйте порядок `id` в ответе. Обработайте partial failure: если один запрос падает, остальные возвращают результат. Объясните, почему пустой batch (`[]`) — ошибка `-32600`.

6. **Реализация JSON-RPC 2.0 сервера (HTTP).**: Создайте HTTP-обработчик, который принимает JSON-RPC запрос (`method`, `params`, `id`). Реализуйте метод `echo` (возвращает переданную строку). Обработайте `id` – запросы с `id` должны вернуть ответ, без `id` – это уведомление (не отвечать).

7. **Стандартные коды ошибок.**: Реализуйте иерархию ошибок: `ParseError` (-32700), `InvalidRequest` (-32600), `MethodNotFound` (-32601), `InvalidParams` (-32602), `InternalError` (-32603). Добавьте custom errors: `-32000` Application Error. Объясните, почему `error.data` — полезно для деталей, но опасно для утечки stack trace.

8. **Пакетные запросы (Batch Requests) в JSON-RPC**: Расширьте ваш JSON-RPC сервер из предыдущей задачи. Спецификация позволяет передавать массив запросов в одном HTTP-теле (пакетный запрос). Настройте парсинг: если пришел JSON-массив, обработайте все запросы параллельно с помощью горутин (используя `sync.WaitGroup`) и верните массив JSON-ответов.

9. **Базовый JSON-RPC server**: Реализуйте endpoint `/rpc`, который парсит request, диспатчит по method name, возвращает response.

10. **Клиент.**: Реализуйте JSON-RPC клиент: генерирует `id` (UUID), отправляет POST, парсит Response. Обрабатывайте: HTTP 200 с `error` в теле (это валидный JSON-RPC error, не HTTP error), timeout, HTTP 500. Объясните, почему `id` в ответе должен совпадать с запросом (out-of-order в HTTP/1.1 pipelining).

11. **Параметры по имени и по позиции.**: Поддержите оба варианта: `"params": ["hello"]` и `"params": {"text": "hello"}`. Используйте рефлексию для вызова обработчиков.

12. **Standard error codes**: Используйте standard codes: `-32700` Parse error, `-32600` Invalid Request, `-32601` Method not found, `-32602` Invalid params, `-32603` Internal error.

13. **Batch requests**: Поддерживайте batch: `[req1, req2, req3]` → `[resp1, resp2, resp3]`. Responses могут приходить в любом порядке (server может обрабатывать параллельно).

14. **Уведомления (Notifications) в JSON-RPC**: Согласно спецификации, если в JSON-RPC запросе отсутствует поле `id`, это считается уведомлением (событием), не требующим ответа. Настройте сервер: выполните логику метода, но верните пустой HTTP-ответ со статусом `204 No Content` без записи тела.

15. **Batch ordering guarantee**: Для use cases, где порядок важен, гарантируйте in-order responses или документируйте, что порядок не гарантирован.

16. **Middleware stack.**: Реализуйте onion-мiddleware для JSON-RPC: Logging (method, duration, id), Metrics (Prometheus counters), Recovery (panic → `-32603 InternalError`). Объясните, как middleware работает с batch (один лог на batch или per-request).

17. **Method registration через reflection**: Используйте reflect для автоматической регистрации Go-методов как JSON-RPC методов (с валидацией signatures).

18. **Code-generated dispatcher**: Альтернатива reflection — кодогенерация type-safe dispatcher из Go интерфейса (быстрее, type-safe).

19. **Named vs positional params**: Поддерживайте оба варианта: `{"params":{"a":1,"b":2}}` и `{"params":[1,2]}`. Spec разрешает оба.

20. **Batch-запросы JSON-RPC.**: Если приходит массив запросов, обработайте их параллельно и верните массив ответов. Обработайте пустой batch (должен вернуть пустой массив).

21. **Валидация параметров.**: Парсите `params` в struct через `json.Unmarshal` + `go-playground/validator`. Возвращайте `-32602 InvalidParams` с детализацией (какое поле невалидно). Объясните, почему `json.RawMessage` + delayed unmarshal — лучше, чем `map[string]any` для типобезопасности.

22. **Notifications (без response)**: Реализуйте обработку notifications (без `id` field). Сервер не должен отправлять response, даже при ошибке.

23. **Middleware chain**: Реализуйте middleware для JSON-RPC: logging, auth, rate limiting, request validation — по аналогии с HTTP middleware.

24. **gRPC-Web: концептуальный разбор**: Опишите в виде подробного комментария концепцию стандарта gRPC-Web:
    * Почему современные браузеры не могут напрямую общаться со стандартными gRPC-серверами (ограничения браузерных JS-интерфейсов `Fetch`/`XHR` по управлению низкоуровневыми фреймами HTTP/2 и трейлерами ответов) [592].
    * Какую роль играет промежуточный прокси-сервер (например, Envoy или Go-прокси), который транслирует запросы gRPC-Web (кодированные в Base64 или бинарные) в стандартный gRPC [592].

25. **Custom error types**: Расширьте error object полем `data` для machine-readable деталей: `{"code":-32000,"message":"validation failed","data":{"field":"email","reason":"invalid"}}`.

26. **JSON-RPC over WebSocket**: Используйте JSON-RPC поверх WebSocket для bidirectional RPC (client и server оба могут инициировать calls). Это основа LSP.

27. **Bidirectional JSON-RPC.**: Реализуйте duplex channel через WebSocket: клиент и сервер могут отправлять notifications друг другу. Используйте `jsonrpc2` поверх `gorilla/websocket`. Объясните, как `id` помогает коррелировать request-response в дуплексном потоке.

28. **JSON-RPC client library**: Напишите type-safe Go client с code-generated методами из JSON schema или OpenRPC spec.

29. **OpenRPC specification**: Изучите OpenRPC (аналог OpenAPI для JSON-RPC). Генерируйте documentation и clients из spec.

30. **Стандартные ошибки JSON-RPC.**: Реализуйте возврат ошибок в формате `{"code": -32601, "message": "Method not found"}` для неизвестных методов. При ошибке в обработчике возвращайте код `-32000` с деталями.

31. **JSON-RPC vs REST vs gRPC:**
    * JSON-RPC: simple, one endpoint, batch support
    * REST: resource-oriented, HTTP semantics, cacheable
    * gRPC: typed, streaming, high-performance
    JSON-RPC идеален, когда у вас много "действий", а не "ресурсов".

32. **HTTP/1.1 vs HTTP/2.**: Объясните проблемы JSON-RPC over HTTP/1.1: head-of-line blocking, нет multiplexing. Реализуйте клиент с connection pool (`http.Transport.MaxConnsPerHost`, `DisableKeepAlives: false`). Сравните latency batch-запросов через HTTP/1.1 и HTTP/2 (gRPC использует HTTP/2 именно поэтому). Объясните, почему JSON-RPC 2.0 спецификация транспорт-агностична.

59. REST (JSON/HTTP)

60. **Metadata.**: Передайте metadata из браузера: custom headers (`X-Request-ID`, `Authorization`). На сервере извлеките через `metadata.FromIncomingContext(ctx)`. Объясните, как CORS preflight обрабатывает custom headers, и почему `Access-Control-Allow-Headers` должен включать `X-Grpc-Web` и `X-User-Agent`.

61. **Error Handling.**: Реализуйте mapping gRPC status codes → HTTP-совместимый ответ. В JavaScript клиенте обработайте `grpc.web.Error` с `code` и `message`. Объясните, почему gRPC-Web не использует HTTP status codes напрямую (всё 200 OK, ошибка в body).

62. **Connect streaming**: Используйте `connect.StreamingHandlerFunc` для server/client/bidirectional streaming, который работает в браузерах через multiple HTTP requests.

63. **Connect vs gRPC-Web**: Connect не требует Envoy proxy, поддерживает JSON out-of-the-box, более идиоматичен для Go. Предпочитайте Connect для новых проектов.

64. **[JSON-RPC Уведомления]**: Если в запросе нет поля `id`, это уведомление (fire-and-forget). Сервер должен выполнить метод, но вернуть HTTP-статус `204 No Content` без тела.

65. **Пакетные запросы (Batching)**: Уникальная фича JSON-RPC. Если клиент присылает массив объектов-запросов, сервер должен выполнить их (можно конкурентно) и вернуть массив ответов в одном HTTP-ответе. Реализуй этот функционал.

66. **JSON-RPC поверх WebSockets**: Сделай WebSocket-соединение. Внутри соединения обменивайтесь сообщениями строго в формате JSON-RPC 2.0. Это идеальный вариант для игр или тяжелых SPA, где нужен двунаправленный RPC без сложной настройки gRPC.

70. **Проблема gRPC-Web (Теория)**: Стандартный gRPC использует HTTP/2 Trailers (заголовки в конце тела ответа) для передачи статуса (ошибок). Браузеры (Fetch API/XHR) не дают доступа к Trailers. Поэтому вызывать чистый gRPC из JS нельзя. Осознай эту архитектурную боль.

72. GraphQL

73. **Компрессия.**: Настройте gzip на gRPC-Web proxy (Envoy) или через `grpc.UseCompressor(gzip.Name)` на сервере. Объясните, что gRPC-Web не поддерживает per-message compression negotiation как нативный gRPC (HTTP/2 SETTINGS), поэтому compression обычно на уровне HTTP (Content-Encoding).

74. **Batch support — ключевая фича.**: Один HTTP request может нести 100 RPC calls. Это решает N+1 проблему и снижает latency.

75. **Notifications для fire-and-forget.**: Если response не нужен (telemetry, analytics), отправляйте без `id` field — сервер не будет тратить ресурсы на response.

80. WebSockets

81. **Protobuf-first подход.**: Определяйте API в `.proto` файлах, генерируйте type-safe clients для всех языков. Это single source of truth.

82. **[gRPC-Web — Прокси]**: Подними обычный gRPC-сервер. Используй `grpcweb` пакет (`github.com/improbable-eng/grpc-web/go/grpcweb`). Оберни gRPC-сервер в `grpcweb.WrapServer()`. Запуши HTTP-запрос через `curl` с заголовком `Content-Type: application/grpc-web+proto`.

83. **In-process gRPC-Web (Без Envoy)**: Использовать Envoy не всегда удобно (лишний компонент). Установи библиотеку `github.com/improbable-eng/grpc-web/go/grpcweb`. Оберни свой стандартный `grpc.Server` в `grpcweb.WrapServer`. Теперь твой Go-сервер сам может принимать gRPC-Web запросы прямо от браузера на стандартном HTTP порту!

84. **Обработка ошибок gRPC-Web.**: Сервер возвращает статус `NotFound`. Убедитесь, что gRPC-Web клиент корректно получает код и сообщение ошибки (с учетом CORS, если необходимо).

85. Server-Sent Events (SSE)

86. **Documentation auto-generation.**: OpenAPI для REST, GraphQL introspection, Protobuf reflection для Connect/gRPC. Hand-written docs устаревают мгновенно.

87. **SDK generation из единой schema.**: Один OpenAPI/Protobuf/GraphQL spec → auto-generated clients для TypeScript, Python, Go, Java, Swift, Kotlin. Это force multiplier для adoption.

88. **[Каверзный кейс — CORS и Preflight]**: Браузеры перед gRPC-Web запросом отправляют `OPTIONS` preflight-запрос. Напиши middleware, которое перехватывает `OPTIONS`, проверяет заголовок `Origin` и возвращает `Access-Control-Allow-Origin`, `Access-Control-Allow-Headers: content-type, x-grpc-web` и `Access-Control-Allow-Methods: POST`. Без этого gRPC-Web из браузера работать не будет.
89. **Bidirectional Streaming Fallback**: В gRPC-Web из браузера не работает двунаправленный (Bidirectional) стриминг, а клиентский стриминг поддерживается очень ограниченно. Перепиши свой `.proto` файл так, чтобы использовать только Unary (запрос-ответ) и Server Streaming. Сгенерируй TS/JS код через `protoc-gen-grpc-web` и сделай успешный вызов из браузера к твоему Go-серверу из упр. 799.
