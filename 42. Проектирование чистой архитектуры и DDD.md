# Проектирование чистой архитектуры и DDD

В этом файле собраны уникальные упражнения по теме **"Проектирование чистой архитектуры и DDD"**, отсортированные по возрастанию сложности.

---

1. **Плоская структура (Flat Layout) для микро-сервисов**: Напишите небольшую CLI-утилиту, структура которой состоит из одного пакета `main` и нескольких файлов в корне директории (например, `main.go`, `config.go`, `db.go`). Опишите в комментариях границы применимости такой структуры: в какой момент плоская структура становится хаосом и требует разделения на слои.

2. **Standard Project Layout**: Возьми свой старый проект, где всё лежало в корне. Отрефактори его по стандарту `golang-standards/project-layout`: создай папки `cmd/app` (точка входа `main.go`), `internal/` (приватный код проекта, недоступный для импорта снаружи) и `pkg/` (публичные библиотеки, если есть).

3. Спроектируй **CRUD-сервис на одном пакете**: `main.go`, `handlers.go`, `models.go`, `db.go`. Все в `package main`. Покажи, почему это работает для 100 строк, но ломается при росте.

4. **Слоистая архитектура «handler → service → repository»**. Реализуйте CRUD для сущности User с in-memory хранилищем, строго разделяя транспортный, бизнес-логический и storage слои.

5. **Трёхслойная архитектура (3-Tier)**: Создайте проект со слоями: Handler (HTTP) → Service (бизнес-логика) → Repository (БД). Изучите, почему это минимально жизнеспособная структура.

6. Раздели на **слои (layered architecture)**: `handlers/` (HTTP), `services/` (бизнес-логика), `repositories/` (данные), `models/` (сущности). Каждый слой зависит только от нижележащего. Покажи направление зависимостей (внутрь).

7. **Структура проекта**: Организуйте код по стандарту `golang-standards/project-layout`: `/cmd`, `/internal`, `/pkg`, `/api`, `/migrations`, `/scripts`.

8. Инвертируй зависимости через **интерфейсы**: `repository.UserRepository` — интерфейс, `repository.PostgresUserRepository` — реализация. `service.UserService` принимает `UserRepository`, не знает о PostgreSQL. Покажи DIP (Dependency Inversion Principle).

9. **Dependency Injection**: Реализуйте ручную инъекцию зависимостей через конструкторы (`NewService(repo Repository)`) без использования DI-фреймворков. Поймите, почему в Go не любят рефлексию.

10. Реализуй **Clean Architecture** (Uncle Bob): слои `entities` → `usecases` → `interface_adapters` → `frameworks_drivers`. В Go: `domain/` (entities, interfaces), `usecase/` (interactors), `delivery/http/` (handlers), `repository/postgres/` (DB). Покажи, что `domain` не зависит ни от чего.

11. **Configuration Management**: Используйте `github.com/spf13/viper` или `caarlos0/env` для загрузки конфигурации из переменных окружения, `.env` файлов и флагов CLI с приоритетами.

12. **Избавление от глобального состояния (Global State)**: Если у тебя есть глобальные переменные `var DB *sql.DB` или `var Log *slog.Logger`, избавься от них. Создай структуру `App` или `Dependencies`, проинициализируй всё в `main` и передавай явно в конструкторы сервисов и хендлеров.

13. **Dependency Injection (ручная)**. Передавайте зависимости (репозитории, логгер, конфиг) через конструкторы. Запретите глобальные переменные, добейтесь тестируемости.

14. Реализуй **Hexagonal Architecture (Ports & Adapters)**: `domain/` (business logic), `ports/` (interfaces: `ForStoringUsers`, `ForSendingEmails`), `adapters/` (реализации: `PostgresUserStore`, `SMTPEmailSender`, `MockEmailSender`). Покажи, что домен — центр, всё остальное — заменяемые адаптеры.

15. **Graceful Shutdown**: Реализуйте паттерн, где при SIGINT сервер перестаёт принимать новые запросы, дожидается завершения текущих (с таймаутом), закрывает соединения с БД/Redis/Kafka и только потом завершается.

16. Реализуй **Vertical Slice Architecture**: не разделяй по слоям, а по **фичам**: `features/user/create/`, `features/user/get/`, `features/order/create/`. Каждый slice содержит handler, service, repository, model. Покажи, что добавление фичи = добавление папки, не изменение 10 файлов.

17. **Чистая архитектура (Clean Architecture)**: Создайте структуру каталогов для стандартного веб-приложения:
    * `/domain` — описание бизнес-сущностей.
    * `/delivery` — уровень представления (HTTP-обработчики, gRPC).
    * `/usecase` — бизнес-сценарии (интеракторы).
    * `/repository` — уровень работы с инфраструктурой (SQL-запросы, файлы).
    Реализуйте простой сценарий регистрации пользователя, соблюдая жесткое правило зависимостей: внутренние слои никогда не должны импортировать внешние.

18. **Monolith First**: Создайте полноценный CRUD-монолит для e-commerce (Users, Products, Orders, Payments) с чёткими границами модулей внутри одного процесса.

19. Реализуй **Feature Modules с shared kernel**: `modules/user/`, `modules/order/`, `modules/payment/`, `shared/` (logger, config, middleware, errors). Каждый модуль — mini-clean-architecture. Покажи, как модули коммуницируют через **events**, не прямые вызовы.

20. **Modular Monolith**: Разделите монолит на независимые модули (`/internal/users`, `/internal/orders`), которые общаются только через публичные интерфейсы, а не импортируют внутренние структуры друг друга.

21. **Принцип инверсии зависимостей (DIP в Go)**: Интерфейсы в Go определяются там, где они *используются*, а не там, где реализуются! Перенеси интерфейс `UserRepository` из пакета базы данных в пакет бизнес-логики (`service`). Пакет `service` не должен ничего знать о пакете `postgres`.

22. **Конфигурация приложения**. Загружайте настройки из YAML/JSON-файла и переменных окружения с приоритетом env. Используйте библиотеку `envconfig` или `viper`.

23. Реализуй **Modular Monolith**: монолит, но с чёткими границами модулей. Каждый модуль имеет свой `internal/` (скрыт от других модулей). Коммуникация только через `pkg/events/` (event bus). Покажи путь к микросервисам: вырезай модуль, добавляй gRPC/HTTP API.

---

24. **API Versioning**: Реализуйте версионирование API через URL (`/v1/users`, `/v2/users`) или через заголовки (`Accept: application/vnd.myapi.v2+json`). Обсудите trade-offs.

25. Спроектируй **декомпозицию по DDD Bounded Contexts**: `User Context` (профиль, аутентификация), `Order Context` (заказы, корзина), `Payment Context` (списание, возврат), `Inventory Context` (склад, резервирование), `Shipping Context` (доставка, трекинг). Покажи, что каждый контекст — потенциальный микросервис.

26. **Feature Flags**: Интегрируйте систему feature flags (например, через Redis или LaunchDarkly) для постепенного rollout новых фич без redeploy.

27. Определи **Aggregate Roots**: `User` (root: `User`, entities: `Address`, `PaymentMethod`), `Order` (root: `Order`, entities: `OrderItem`, `OrderStatus`), `Product` (root: `Product`, entities: `ProductVariant`, `Inventory`). Покажи invariants: `Order.total = sum(OrderItem.subtotal)`.

28. **Background Jobs**: Реализуйте систему фоновых задач через Redis queue или PostgreSQL `SKIP LOCKED` (для простой job queue без внешних зависимостей).

29. Реализуй **Domain Events**: `OrderCreated`, `PaymentProcessed`, `InventoryReserved`, `ShipmentShipped`. Events — immutable facts, не команды. Публикуй внутри aggregate, когда state меняется. Покажи eventual consistency между контекстами.

30. **Циклические зависимости (Import Cycle)**: Намеренно создай ситуацию: пакет `user` импортирует `order`, а `order` импортирует `user`. Получи ошибку компилятора. Реши проблему двумя способами: 1) объединением в один пакет, 2) вынесением общих структур/интерфейсов в третий независимый пакет `domain` или `core`.

31. **Graceful Shutdown всей системы**. Реализуйте корректный порядок остановки: сначала прекращаем приём новых запросов, затем завершаем фоновые горутины, закрываем соединения с БД и брокерами.

32. **Порты и Адаптеры (Hexagonal Architecture)**: Перепишите простой сценарий регистрации пользователя в Clean Architecture в соответствии с концепцией гексагональной архитектуры. Опишите "порты" (входящие и исходящие интерфейсы, например, `UserRepository` и `UserService`) во внутреннем ядре. Реализуйте "адаптеры" (внешние элементы, такие как хранилище Postgres или HTTP-сервер) во внешнем слое. Продемонстрируйте инверсию зависимостей (Dependency Inversion Principle) в действии.

33. **Слои Clean Architecture**: Разделите код на 4 слоя: Entities (доменные объекты) → Use Cases (бизнес-логика) → Interfaces (adapters) → Frameworks (HTTP, DB). Зависимости направлены только внутрь.

34. Реализуй **Anti-Corruption Layer (ACL)**: `Order Service` интегрируется с legacy `Payment Gateway`. Создай `PaymentGatewayAdapter` (переводит наш `PaymentRequest` в их XML), `PaymentGatewayTranslator` (их callback → наши `PaymentProcessed` event). Legacy не "загрязняет" наш домен.

35. **Hexagonal Architecture (Ports & Adapters)**: Определите "порты" (интерфейсы) для внешних зависимостей (UserRepository, EmailSender) и реализуйте "адаптеры" (PostgresUserRepository, SendGridEmailSender).

36. Спроектируй **Saga Orchestration**: `OrderSaga` (orchestrator) координирует: `CreateOrder` → `ReserveInventory` → `ProcessPayment` → `ShipOrder`. Каждый шаг — gRPC/HTTP/event. Compensation: `PaymentFailed` → `ReleaseInventory`. Реализуй state machine в `OrderSaga`.

37. **Domain Entities**: Создайте богатые доменные объекты с поведением (методами), а не просто структуры с данными. Например, `Order.CanBeCancelled() bool`, `Order.ApplyDiscount(percent float64)`.

38. Спроектируй **Saga Choreography**: нет центрального orchestrator'а. `OrderService` публикует `OrderCreated`. `InventoryService` подписывается, резервирует, публикует `InventoryReserved`. `PaymentService` подписывается... Покажи децентрализацию, но сложность отслеживания.

39. **Модульный монолит (Modular Monolith)**: Раздели приложение на два независимых домена: `billing` (счета) и `inventory` (склад). Запрети пакету `billing` делать SQL-запросы в таблицы склада. `billing` должен общаться со складом **только** через публичные Go-интерфейсы пакета `inventory`.

40. **Структура проекта: `/cmd`, `/internal`, `/pkg`**. Создайте проект с пакетами `cmd/server`, `internal/app`, `internal/handler`, `internal/service`, `internal/repository`, `pkg/logger`. Опишите, что куда класть.

41. **Value Objects**: Реализуйте неизменяемые объекты для концепций без идентичности: `Money{amount, currency}`, `Email{address}`, `Address{street, city, zip}`.

42. Реализуй **CQRS в микросервисе**: `Order Command Service` (PostgreSQL, normalized schema, transactions) обрабатывает `CreateOrder`, `CancelOrder`. `Order Query Service` (Elasticsearch/ClickHouse, denormalized views) отвечает на `GetOrderHistory`, `SearchOrders`. Синхронизация через events.

43. **Domain Events**: Создайте систему событий (`OrderCreated`, `PaymentProcessed`), которые генерируются при изменении состояния агрегатов и публикуются в event bus.

44. Реализуй **Event Sourcing**: `OrderAggregate` хранит не текущее состояние, а последовательность `OrderCreated`, `OrderItemAdded`, `OrderPaymentApplied`, `OrderShipped`. `GetState()` = `fold(events, initialState)`. Покажи: replay, temporal queries, audit trail.

45. **Внедрение зависимостей (Dependency Injection)**: Напишите код инициализации вашего приложения в файле `main.go`. Настройте ручное внедрение зависимостей ("manual DI"): создайте экземпляр базы данных, передайте его в конструктор репозитория `NewSQLRepository(db)`, репозиторий передайте в юзкейс `NewUsecase(repo)`, а юзкейс — в HTTP-обработчик `NewHandler(usecase)`.

46. **Aggregates**: Определите границы агрегатов (например, `Order` как aggregate root, содержащий `OrderItems`). Транзакции не должны пересекать границы агрегатов.

47. Реализуй **Materialized View из Event Stream**: `OrderProjection` читает `OrderEvents` Kafka topic, строит `OrderSummary` в Redis/PostgreSQL. Пересоздай projection с нуля (replay с начала stream). Покажи, что view — disposable, source of truth — events.

48. **Repositories**: Реализуйте репозитории, которые скрывают детали хранения. Интерфейс `OrderRepository` не должен знать про SQL или PostgreSQL.

49. Спроектируй **Strangler Fig Pattern**: legacy монолит на Java. Новый сервис `UserService` на Go. API Gateway маршрутизирует: `/users/*` → новый сервис, остальное → legacy. Постепенно вырезаем функциональность. Покажи incremental migration.

---

50. **Feature Toggles (Флаги фичей)**: Спроектируй сервис, который проверяет флаги. Оберни новую (нестабильную) бизнес-логику в условие `if featureflags.IsEnabled("new_payment_gateway")`. Реализуй динамическое переключение флага в памяти (или через Redis) без перезапуска приложения.

51. **Модульный монолит с доменными пакетами**. Разделите внутренние пакеты по доменам: `internal/users`, `internal/orders`. Каждый домен имеет свой handler, service, repository. Избегайте циклических зависимостей.

52. **Application Services**: Создайте use case'ы как тонкие orchestration слои: `CreateOrderUseCase.Execute(dto CreateOrderDTO) (OrderID, error)`.

53. **Anti-Corruption Layer (ACL)**: При интеграции с legacy-системой создайте адаптер, который транслирует внешнюю модель в вашу доменную модель, защищая её от "загрязнения".

54. **Bounded Contexts**: Разделите большую систему на контексты (например, "Inventory", "Billing", "Shipping"), каждый со своей доменной моделью и БД.

55. **Конфигурация через Options Pattern**: Напиши сложный пакет (например, кастомный кэш), который требует десяток настроек (размер, TTL, алгоритм вытеснения). Реализуй его создание через `NewCache(opts ...Option)`, чтобы значения по умолчанию применялись автоматически, а переопределялись красиво через функциональные опции.

---

56. **Middleware pipeline**. Выстройте цепочку middleware (логирование, аутентификация, восстановление после паники, трассировка) с возможностью конфигурирования порядка без изменения кода.

57. **Тонкие сущности (Entities) и богатое поведение**: Напишите структуру `User` в слое `domain`. Перенесите бизнес-правила валидации состояния (например, метод `CanBeActivated() bool`, проверяющий наличие подтвержденного email и заполненного профиля) внутрь самой структуры `User` (Rich Domain Model), очистив слой `usecase` от дублирования этой проверки.

58. **Ubiquitous Language**: Убедитесь, что имена классов, методов и переменных отражают бизнес-терминологию (не `data1`, `process()`, а `Invoice.CalculateTax()`).

59. **Service Decomposition**: Разделите монолит на микросервисы по бизнес-возможностям: User Service, Product Service, Order Service, Payment Service.

60. **API Gateway**: Создайте единый entry point (через Kong, Envoy или собственный Go-сервис), который роутит запросы к нужным микросервисам, агрегирует ответы, занимается аутентификацией.

61. **Ядро домена (Entities & Use Cases)**: Создай пакет `domain`. Напиши там структуры (Entities) и чистую бизнес-логику (одобрение кредита по сложным правилам). В этом пакете **не должно быть** ни одного импорта, связанного с `net/http`, `sql`, `json` или внешними либами.

62. **Версионирование API**. Реализуйте `v1` и `v2` эндпоинтов на одном сервере. `v2` меняет формат ответа. Клиенты могут плавно мигрировать.

63. **BFF (Backend for Frontend)**: Создайте отдельные API для мобильного и веб-клиентов с разными контрактами и оптимизациями под каждый клиент.

64. **Inter-Service Communication (Sync)**: Используйте gRPC для синхронного общения между сервисами с retry, circuit breaker и timeout.

65. **Перевод инфраструктурных ошибок в доменные**: На уровне базы данных при отсутствии записи возникает ошибка `sql.ErrNoRows`. Если вы прокинете её до самого верхнего уровня HTTP-доставки, слой представления завяжется на конкретную СУБД. Напишите адаптер базы данных, который перехватывает `sql.ErrNoRows` и возвращает кастомную ошибку уровня домена `domain.ErrUserNotFound`. На уровне delivery обработайте именно её, возвращая клиенту `404 Not Found`.

---

66. **Inter-Service Communication (Async)**: Используйте Kafka/RabbitMQ для асинхронного общения (event-driven) для снижения coupling.

67. **Порты и Адаптеры**: В `domain` объяви "порт" — интерфейс `NotificationSender`. В пакете `infrastructure` напиши два "адаптера": `EmailSender` и `SMSSender`. В `main.go` собери приложение, подставив нужный адаптер в домен.

68. **Паттерн Repository (интерфейс)**. Опишите интерфейс `UserRepository`. Реализуйте две имплементации: `PostgresUserRepo` и `InMemoryUserRepo`. Переключайтесь между ними флагом конфигурации.

69. **Service Discovery**: В Kubernetes используйте DNS-based discovery. Для on-premise рассмотрите Consul или etcd.

70. **Distributed Transactions (Saga)**: Реализуйте Saga pattern через orchestration (центральный координатор) или choreography (сервисы реагируют на события друг друга).

71. **Saga Compensation**: Для каждого действия в Saga реализуйте компенсирующее действие (например, `ReserveInventory` → `ReleaseInventory` при ошибке платежа).

72. **Idempotency Keys**: Добавьте `Idempotency-Key` заголовок для всех POST/PUT/PATCH запросов, чтобы повторные вызовы не создавали дубликаты.

73. **Трансляция Ошибок**: Доменный слой возвращает кастомную маркерную ошибку `ErrInsufficientFunds`. Слой базы данных возвращает `sql.ErrNoRows`. Напиши HTTP-хендлер, который отлавливает эти ошибки через `errors.Is` и переводит первую в HTTP 402 Payment Required, а вторую в HTTP 404 Not Found. Не пускай SQL-ошибки в домен, а доменные — пользователю в сыром виде!

74. **Unit of Work (транзакционность)**. Создайте `UnitOfWork`, который управляет транзакцией БД. Сервис создаёт нескольких пользователей в одной транзакции через UoW.

75. **Объекты-значения (Value Objects)**: Создайте неизменяемую структуру `Money` с полями `Amount int64` (хранение в копейках/центах) и `Currency string`. Напишите методы `Add(other Money) (Money, error)` и `Equals(other Money) bool`. Объясните в комментариях, почему объекты-значения в DDD не имеют уникального идентификатора и должны быть абсолютно неизменяемыми.

76. **Strangler Fig Pattern**: Постепенно мигрируйте с монолита на микросервисы, перенаправляя трафик через API Gateway на новые сервисы по мере их готовности.

77. **Database per Service**: Каждый микросервис имеет свою БД. Используйте event sourcing или CDC для синхронизации данных между сервисами.

78. **Разделение DTO и Domain Models**: Напиши структуру `CreateUserRequest` (DTO) для парсинга JSON (с тегами `json` и `validate`) и структуру `User` (доменная сущность) для логики. Напиши маппер (функцию-преобразователь), который перекладывает данные из DTO в доменную модель после синтаксической валидации.

79. **Сервисный слой с доменными сервисами**. Выделите `UserService` и `OrderService`. При создании заказа сервис заказов вызывает сервис пользователей для проверки существования пользователя. Покажите инверсию зависимостей.
