Упражнение #1

Объявление переменных всех базовых типов через ключевое слово var

📌 Условие задачи

Объявите переменные всех базовых типов с помощью var (с указанием типа и без), выведите их значения и типы (%T).

💡 Теоретический фундамент и концепция

В языке Go переменные объявляются с помощью ключевого слова var.

Существует две формы объявления:

1. С явным указанием типа: var a int = 10 — компилятор строго фиксирует тип переменной;
2. С выводом типа (Type Inference): var b = 3.14 — компилятор автоматически выводит тип float64 на этапе статического анализа.

Базовые типы Go:

  • Числовые: int, int8-int64, uint, uint8-uint64, uintptr, float32, float64, complex64, complex128;
  • Булевы: bool (true/false);
  • Строковые: string;
  • Символьные: byte (алиас uint8), rune (алиас int32).

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем переменные с явным типом.
2. Объявляем переменные с выводом типа компилятором.
3. Выводим значение и тип каждой переменной через fmt.Printf("%v (%T)\n", v, v).
📄 main.go 
package main

import "fmt"

func main() {
	// Явное указание типа
	var count int = 42
	var rate float64 = 99.95
	var title string = "Golang Core"
	var isValid bool = true
	var char rune = '🚀'

	// Вывод типа компилятором (Type Inference)
	var inferredInt = 100
	var inferredFloat = 3.1415
	var inferredStr = "Auto type"

	fmt.Printf("count:         значение = %-12v | тип = %T\n", count, count)
	fmt.Printf("rate:          значение = %-12v | тип = %T\n", rate, rate)
	fmt.Printf("title:         значение = %-12v | тип = %T\n", title, title)
	fmt.Printf("isValid:       значение = %-12v | тип = %T\n", isValid, isValid)
	fmt.Printf("char:          значение = %-12c | тип = %T\n", char, char)
	fmt.Printf("inferredInt:   значение = %-12v | тип = %T\n", inferredInt, inferredInt)
	fmt.Printf("inferredFloat: значение = %-12v | тип = %T\n", inferredFloat, inferredFloat)
	fmt.Printf("inferredStr:   значение = %-12v | тип = %T\n", inferredStr, inferredStr)
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

При выводе типа для целочисленных литералов без точки (например 100) компилятор Go по умолчанию всегда назначает тип int (размер которого равен размеру машинного слова: 64 бита на x86-64 и 32 бита на ARM32). Для литералов с плавающей точкой (3.14) всегда назначается float64.

⚠️ Частые грабли и ошибки новичков
  • На 64-битной архитектуре int занимает 8 байт, но при этом тип int и тип int64 — это два разных типа в системе типов Go! Нельзя сложить var a int и var b int64 без явного преобразования int64(a) + b.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему в Go нет автоматического неявного приведения типов (Implicit Type Casting), как в C++ или Java?»

Ответ: Это фундаментальное архитектурное решение Кена Томпсона и Роба Пайка. Неявное приведение типов (например, int32 к int64 или int к float) является источником трудноуловимых багов переполнения, потери точности и скрытых накладных расходов. В Go любая конвертация обязана быть осознанной и явной.

Упражнение #2

Короткое объявление := и частичное переприсваивание (Short Declaration)

📌 Условие задачи

Используйте короткое объявление := внутри функции и посмотрите, что происходит при повторном объявлении (частичное переприсваивание).

💡 Теоретический фундамент и концепция

Оператор краткого объявления :=:

1. Доступен только внутри функций (на уровне пакета запрещен);
2. Создает новую переменную с автоматическим выводом типа;
3. Правило частичного переприсваивания (Redeclaration): оператор := можно повторно вызывать со списком переменных, если хотя бы одна переменная в списке является НОВОЙ в текущей области видимости. При этом старая переменная не создается заново, а просто перезаписывается.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем переменную name := "Gopher".
2. Вызываем функцию, возвращающую 2 значения, где первое — старая name, а второе — новая err.
3. Анализируем, как name обновилась, а err создалась.
4. Проверяем ошибку, если попытаться написать name := "New" без новых переменных.
📄 main.go 
package main

import (
	"fmt"
	"strconv"
)

func main() {
	// 1. Первичное короткое объявление
	id := 100
	fmt.Printf("1. Исходный id = %d (тип: %T)\n", id, id)

	// 2. Частичное переприсваивание: id уже существует, но num — новая переменная!
	id, num := 200, 42
	fmt.Printf("2. После := id = %d, num = %d\n", id, num)

	// 3. Типичный паттерн в продакшене с обработкой ошибок:
	val, err := strconv.Atoi("1024")
	if err != nil {
		return
	}
	fmt.Printf("3. val = %d\n", val)

	// Здесь err уже объявлена, но val2 — новая!
	val2, err := strconv.Atoi("2048")
	if err != nil {
		return
	}
	fmt.Printf("4. val2 = %d, err = %v\n", val2, err)
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Синтаксический парсер компилятора (cmd/compile/internal/syntax) при обработке узла AssignList проверяет таблицу символов (Scope Symbol Table). Для существующих идентификаторов генерируется SSA-инструкция OpCopy (присвоение), а для новых — OpVarDef (аллокация на стеке).

⚠️ Частые грабли и ошибки новичков
  • Попытка повторно объявить переменную без новых идентификаторов: x := 1; x := 2 вызовет ошибку компиляции no new variables on left side of :=.
  • Опасность случайного затенения (Shadowing) во вложенных блоках if/for.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему в блоке if err := do(); err != nil переменная err не перезаписывает внешнюю err, а затеняет её?»

Ответ: Потому что конструкция if создает новую дочернюю лексическую область видимости (Block Scope). Любой оператор := внутри новой области видимости создает локальную переменную, полностью изолированную от внешнего контекста.

Упражнение #4

Размеры целочисленных типов в байтах через unsafe.Sizeof

📌 Условие задачи

Объявите переменные всех базовых целочисленных типов (int8, int16, int32, int64, uint8 и т.д.) и выведите их размер в байтах с помощью unsafe.Sizeof.

💡 Теоретический фундамент и концепция

Разрядность целочисленных типов строго специфицирована:

  • int8, uint8 (byte) $ ightarrow$ 1 байт (8 бит);
  • int16, uint16 $ ightarrow$ 2 байта (16 бит);
  • int32, uint32 (rune) $ ightarrow$ 4 байта (32 бит);
  • int64, uint64 $ ightarrow$ 8 байт (64 бит);
  • int, uint, uintptr $ ightarrow$ размер машинного слова платформы (8 байт на 64-бит, 4 байта на 32-бит).

Функция unsafe.Sizeof(x) вычисляется на этапе компиляции (Compile-time constant) и возвращает размер типа в байтах.

🔍 Пошаговый ход решения и ход мысли инженера

1. Импортируем пакет unsafe.
2. Создаем переменные всех целочисленных типов.
3. Печатаем таблицу размеров.

	"fmt"
	"unsafe"

	var i16 int16
	var i32 int32
	var i64 int64
	var u8 uint8
	var u16 uint16
	var u32 uint32
	var u64 uint64
	var i int
	var u uint
	var ptr uintptr

	fmt.Printf("int32:   %d байта | uint32 (rune): %d байта\n", unsafe.Sizeof(i32), unsafe.Sizeof(u32))
	fmt.Printf("int64:   %d байт  | uint64:        %d байт\n", unsafe.Sizeof(i64), unsafe.Sizeof(u64))

Вопрос с собеседования: «Зачем нужен тип uintptr и чем он отличается от обычного указателя *T?»

Ответ: uintptr — это целое число без знака, достаточно большое для хранения адреса любого указателя. Главное отличие: Garbage Collector не считает uintptr активной ссылкой на объект. Если объект удерживается только через uintptr, сборщик мусора имеет право уничтожить его и освободить память.

💡 Теоретический фундамент и концепция

Упражнение #7

Нетипизированные константы (Untyped Constants):

Упражнение #9

Матрица явных преобразований типов (Type Casting)

📌 Условие задачи

Преобразуйте int в float64 и обратно, string в []byte и []rune, int в string (через strconv.Itoa и через string(rune)).

💡 Теоретический фундамент и концепция

Базовые трансформации типов в Go:

1. float64(intVal) / int(floatVal) (с отбрасыванием дробной части);
2. []byte(str) — срез сырых байт UTF-8;
3. []rune(str) — срез кодовых точек Unicode (символов);
4. strconv.Itoa(42) $ ightarrow$ строка "42";
5. string(rune(65)) $ ightarrow$ символ "A" (по коду ASCII/Unicode).

🔍 Пошаговый ход решения и ход мысли инженера

1. Проводим конвертацию чисел.
2. Проводим конвертацию строк в байты и руны.
3. Сравниваем strconv.Itoa и string(rune).
📄 main.go 
package main

import (
	"fmt"
	"strconv"
)

func main() {
	// 1. Числовые преобразования
	var i int = 42
	var f float64 = float64(i)
	var truncatedInt int = int(99.99) // Дробная часть отсекается -> 99

	fmt.Printf("1. Числа:  i=%d -> f=%.2f, float=99.99 -> int=%d\n", i, f, truncatedInt)

	// 2. Строка в байты и руны
	text := "Go 🚀"
	bytes := []byte(text)
	runes := []rune(text)
	fmt.Printf("2. Строка: %q\n", text)
	fmt.Printf("   []byte: %v (байт: %d)\n", bytes, len(bytes))
	fmt.Printf("   []rune: %v (руны: %d)\n", runes, len(runes))

	// 3. int -> string (Разница между strconv.Itoa и string(rune))
	numStr := strconv.Itoa(65)     // Строка "65"
	runeStr := string(rune(65))    // Символ с кодом 65 -> "A"

	fmt.Printf("   string(rune(65))   -> %q\n", runeStr)

Упражнение #10

Перекрытие и затенение переменных (Variable Shadowing)

📌 Условие задачи

Покажите перекрытие переменной (shadowing): объявите переменную на уровне пакета и внутри функции с тем же именем.

💡 Теоретический фундамент и концепция

Затенение (Shadowing):

Если во внутренней области видимости (внутри функции или блока {}) объявлена переменная с именем, совпадающим с внешней переменной:

1. Внутренняя переменная полностью перекрывает внешнюю;
2. Все обращения по этому имени внутри блока адресуются к локальной переменной;
3. Внешняя переменная остается нетронутой.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем глобальную переменную пакета var AppMode = "PRODUCTION".
2. В функции main объявляем локальную переменную AppMode := "DEVELOPMENT".
3. Сравниваем их значения через вызов отдельной функции.
📄 main.go 
package main

import "fmt"

// Глобальная переменная на уровне пакета
var AppMode = "PRODUCTION"

func printGlobal() {
	fmt.Println("Внутри printGlobal():", AppMode)
}

func main() {
	fmt.Println("1. До затенения:", AppMode)

	// Затенение: создаем локальную переменную с тем же именем
	AppMode := "DEVELOPMENT"

	fmt.Println("2. Внутри main() (затенено):", AppMode)

	// Внешняя функция по-прежнему видит глобальную переменную
	printGlobal()
}
ℹ️ Демонстрация Variable Shadowing
📄 Терминал 
go run main.go
# 1. До затенения: PRODUCTION
# 2. Внутри main() (затенено): DEVELOPMENT
# Внутри printGlobal(): PRODUCTION
ℹ️ Результат перекрытия
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Компилятор разрешает имена переменных по цепочке лексических областей видимости (Lexical Scopes) от текущего блока вверх до уровня пакета и universe scope.

⚠️ Частые грабли и ошибки новичков
  • Случайное затенение переменной err во внутреннем if блоке (if val, err := parse(); err != nil), из-за чего внешняя переменная err остается nil, и ошибка игнорируется. Для поиска таких багов используют линтер shadow (go vet -vettool=$(which shadow)).

Ответ: Потому что затенение err (Err Shadowing) — одна из самых частых причин тихих падений распределенных микросервисов в продакшене.

Пустой идентификатор _ в блоке констант:

1. Позволяет пропустить нежелательное значение iota (например, нулевое значение);

Упражнение #12

Глубокая анатомия строк: байты, руны, итерация и UTF-8 срезы

📌 Условие задачи

Поработайте со строкой: длина в байтах, итерация по байтам и по рунам, срезы по индексам (с учётом UTF-8).

💡 Теоретический фундамент и концепция

Строки в Go:

1. Строка — это иммутабельный срез байт (struct { Data *byte; Len int });
2. Функция len(s) возвращает количество байт, а не букв;
3. Цикл for i := 0; i < len(s); i++ итерируется по сырым байтам;
4. Цикл for idx, r := range s декодирует UTF-8 и итерируется по рунам;
5. Срез строки по индексам s[0:4] режет по байтам, что может разорвать кириллический символ пополам.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем строку "Go Да 🚀".
2. Показываем разницу между длиной в байтах и рунах.
3. Проводим итерацию обоими способами.
4. Демонстрируем безопасный срез через []rune.
📄 main.go 
package main

import (
	"fmt"
	"unicode/utf8"
)

func main() {
	s := "Go Да 🚀"

	fmt.Printf("Исходная строка:    %s\n", s)
	fmt.Printf("Длина в байтах len: %d\n", len(s))
	fmt.Printf("Количество рун:     %d\n\n", utf8.RuneCountInString(s))

	fmt.Println("--- 1. Итерация по рунам (for range): ---")
	for idx, r := range s {
		fmt.Printf("Байт смещения: %2d | Руна: %c (код %5d)\n", idx, r, r)
	}

	fmt.Println("\n--- 2. Безопасный срез первых 4 символов: ---")
	runes := []rune(s)
	safeSub := string(runes[:4])
	fmt.Printf("Срез по рунам [:4]: %q\n", safeSub)
}

package main

import "fmt"

type LogLevel int

const (
	LevelDebug LogLevel = iota
	LevelInfo
	LevelWarn
	LevelError
	LevelFatal
)

func (l LogLevel) String() string {
	names := [...]string{"DEBUG", "INFO", "WARN", "ERROR", "FATAL"}

	}
	return names[l]
}

	fmt.Printf("Текущий уровень: %s (%d)\n", currentLevel, currentLevel)
	fmt.Printf("LevelWarn:       %s (%d)\n", LevelWarn, LevelWarn)
	fmt.Printf("LevelError:      %s (%d)\n", LevelError, LevelError)
}

Упражнение #14

Арифметика с int8 и uint8 и механика переполнения (Integer Overflow)

📌 Условие задачи

Сделайте арифметические операции с int8 и uint8, проверьте переполнение (например, var a uint8 = 255; a++).

💡 Теоретический фундамент и концепция

Переполнение целых чисел в Go:

1. Для беззнаковых типов (uint8, 0..255): при 255 + 1 значение совершает циклический переход (wrap-around) в 0;
2. Для знаковых типов (int8, -128..127): при 127 + 1 значение переходит в -128 (из-за знакового бита в дополнительном коде);
3. Критично: в рантайме Go переполнение целых чисел НЕ вызывает паники и исключений!

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем var u uint8 = 255 и делаем u++.
2. Создаем var s int8 = 127 и делаем s++.
3. Анализируем результаты.
📄 main.go 
package main

import "fmt"

func main() {
	// 1. Беззнаковое переполнение (uint8: 0..255)
	var u uint8 = 255
	fmt.Printf("uint8 до инкремента:  %d\n", u)
	u++
	fmt.Printf("uint8 после u++:      %d (wrap around to 0)\n\n", u)

	// 2. Знаковое переполнение (int8: -128..127)
	var s int8 = 127
	fmt.Printf("int8 до инкремента:   %d\n", s)
	s++
	fmt.Printf("int8 после s++:      %d (wrap around to -128)\n", s)
}

📄 Терминал

# uint8 после u++:      0 (wrap around to 0)
# 
# int8 до инкремента:   127
# int8 после s++:      -128 (wrap around to -128)
ℹ️ Результаты переполнения
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Процессор выполняет обычные операции сложения ADD. Флаг переполнения регистра (Carry/Overflow flag) игнорируется рантаймом Go ради максимальной скорости вычислений.

⚠️ Частые грабли и ошибки новичков
  • Использование uint для счетчиков в циклах обратного отсчета: for i := uint(10); i >= 0; i-- — цикл станет бесконечным, так как 0 - 1 превратится в 18446744073709551615 ($\ge 0$).

Упражнение #16

Анализ переполнения uint8 и wrap-around эффекта

📌 Условие задачи

Изучите переполнение целочисленных типов (integer overflow) на примере uint8, добавив единицу к максимальному значению.

💡 Теоретический фундамент и концепция

Детальный бинарный разбор uint8:

import "fmt"

func main() {
	var val uint8 = 254

	for i := 0; i < 3; i++ {
		fmt.Printf("Значение: %3d | Битовый вид: %08b\n", val, val)
		val++
	}
}

Массивы ([N]T) в Go:

1. Массив является типом-значением (Value Type);

4. Проверяем, что в main массив остался неизменным.

}

func main() {
	original := [5]int{10, 20, 30, 40, 50}

	fmt.Println("1. До вызова:   ", original)

Упражнение #19

Механика срезов: append, len, cap и разделение памяти подсрезов

📌 Условие задачи

Создайте срез, добавьте элементы append, исследуйте len и cap. Создайте подсрез и измените элемент — проверьте эффект на исходный срез.

💡 Теоретический фундамент и концепция

Анатомия срезов (Slices):

Срез состоит из:

1. Data — указатель на базовый массив;
2. len — количество доступных элементов;
3. cap — общая вместимость базового массива до необходимости реаллокации.

Критическое свойство подсрезов:

Если создать подсрез sub := original[1:3], он указывает на тот же самый базовый массив. Изменение элемента в sub изменит его и в original!

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем срез с помощью make([]int, 3, 5).
2. Добавляем элементы через append.
3. Создаем подсрез sub := s[1:3] и меняем sub[0] = 777.
4. Анализируем изменение в исходном срезе.
📄 main.go 
package main

import "fmt"

func main() {
	// Срез: len = 3, cap = 5
	s := make([]int, 3, 5)
	s[0], s[1], s[2] = 10, 20, 30

	fmt.Printf("Исходный срез:  %v (len=%d, cap=%d)\n", s, len(s), cap(s))

	// Создаем подсрез
	sub := s[1:3] // [20, 30]
	fmt.Printf("Подсрез s[1:3]: %v (len=%d, cap=%d)\n", sub, len(sub), cap(sub))

	// Изменяем подсрез
	sub[0] = 777

	fmt.Println("\n--- После изменения sub[0] = 777: ---")
	fmt.Printf("Подсрез:        %v\n", sub)
	fmt.Printf("Исходный срез:  %v (ЭЛЕМЕНТ ТОЖЕ ИЗМЕНИЛСЯ!)\n", s)
}
ℹ️ Связь срезов через общий базовый массив
📄 Терминал

# Подсрез s[1:3]: [20 30] (len=2, cap=4)

# Подсрез:        [777 30]
# Исходный срез:  [10 777 30] (ЭЛЕМЕНТ ТОЖЕ ИЗМЕНИЛСЯ!)
ℹ️ Мутация разделяемого массива
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Если после создания подсреза вызвать append, который превысит cap, произойдет реаллокация (создание нового массива в куче), и связь между срезами разорвется.

⚠️ Частые грабли и ошибки новичков
  • Утечка памяти (Memory Leak): удерживание гигантского массива из-за маленького подсреза sub := hugeSlice[:2]. Решение: скопировать данные через copy().
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Как устроен алгоритм роста cap при append в Go 1.18+?»

Ответ: Для маленьких срезов ($< 256$ элементов) вместимость удваивается ($ imes 2$). Для больших срезов рост замедляется по плавной формуле $ ext{cap} += ( ext{cap} + 3 imes 256) / 4$, стремясь к коэффициенту $1.25$ для экономии оперативной памяти.

Упражнение #21

Хэш-таблицы (map): добавление, удаление, comma-ok и итерация

📌 Условие задачи

Создайте map string->int, добавьте, удалите, проверьте наличие ключа (запятая-ok), проитерируйтесь в цикле.

💡 Теоретический фундамент и концепция

Хэш-таблицы (map[K]V) в Go:

1. Инициализируются через make(map[K]V) или литерал map[K]V{...};
2. Удаление ключа: delete(m, key);
3. Проверка существования ключа (паттерн Comma-ok): val, ok := m[key] (если ok == false, ключа нет в мапе, а val равен нулевому значению типа);
4. Порядок итерации for k, v := range m в Go рандомизирован (намеренно меняется при каждом запуске для предотвращения зависимости от порядка).

🔍 Пошаговый ход решения и ход мысли инженера

1. Инициализируем мапу инвентаря товаров.
2. Добавляем товары, удаляем один через delete.
3. Проверяем наличие существующего и несуществующего ключа через comma-ok.
4. Обходим мапу в цикле.
📄 main.go 
package main

import "fmt"

func main() {
	// 1. Инициализация
	inventory := make(map[string]int)
	inventory["ноутбук"] = 10
	inventory["мышь"] = 50
	inventory["клавиатура"] = 25

	// 2. Удаление
	delete(inventory, "мышь")

	// 3. Проверка ключа (comma-ok idiom)
	if count, ok := inventory["ноутбук"]; ok {
		fmt.Printf("✔ Ноутбуки в наличии: %d шт.\n", count)
	}

	if _, ok := inventory["мышь"]; !ok {
		fmt.Println("❌ Товар 'мышь' отсутствует на складе.")
	}

	// 4. Итерация
	fmt.Println("\n--- Весь инвентарь: ---")
	for item, qty := range inventory {
		fmt.Printf("• %-12s: %d шт.\n", item, qty)
	}
}

  • Чтение из неинициализированной nil-мапы безопасно (вернет нулевое значение), но запись в nil-мапу вызывает неисправимую панику: panic: assignment to entry in nil map. Всегда используйте make(map[K]V).

Упражнение #23

Структуры (struct): способы инициализации и вложенные структуры

📌 Условие задачи

Объявите структуру Person с полями Name, Age. Инициализируйте разными способами (именованные поля, без имён), вложите структуру Address.

💡 Теоретический фундамент и концепция

Структуры (struct):

1. Пользовательский композитный тип данных;
2. Именованная инициализация (Field: Value): Person{Name: "Иван", Age: 30} — рекомендованный стандарт индустрии;
3. Позиционная инициализация: Person{"Иван", 30} — хрупкая (ломается при добавлении новых полей в структуру);
4. Композиция: вложение одной структуры в другую (Address внутри Person).

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем структуры Address и Person.
2. Инициализируем несколькими способами.
3. Печатаем через %+v.
📄 main.go 
package main

import "fmt"

type Address struct {
	City   string
	Street string
}

type Person struct {
	Name    string
	Age     int
	Address Address
}

func main() {
	// 1. Именованная инициализация (Best Practice)
	p1 := Person{
		Name: "Екатерина",
		Age:  28,
		Address: Address{
			City:   "Москва",
			Street: "Тверская",
		},
	}

	// 2. Позиционная инициализация
	addr := Address{"Казань", "Баумана"}
	p2 := Person{"Руслан", 31, addr}

	// 3. Частичная инициализация (неуказанные поля получают Zero Value)
	p3 := Person{Name: "Аноним"}

	fmt.Printf("p1: %+v\n", p1)
	fmt.Printf("p2: %+v\n", p2)
	fmt.Printf("p3: %+v\n", p3)
}

Упражнение #29

Побитовые операции над uint8 (&, |, ^, <<, >>)

📌 Условие задачи

Используйте побитовые операторы (&, |, ^, <<, >>) над переменными типа uint8.

💡 Теоретический фундамент и концепция

Побитовые операторы в Go:

  • & (AND) — побитовое И (маскирование);
  • | (OR) — побитовое ИЛИ (установка битов);
  • ^ (XOR / NOT) — исключающее ИЛИ (бинарная операция) или побитовая инверсия (унарная операция ^x);
  • &^ (AND NOT) — сброс битов (битовая очистка, Bit Clear);
  • << / >> — побитовый сдвиг влево/вправо.

	fmt.Printf("b:       %08b (%d)\n\n", b, b)

	fmt.Printf("a & b:   %08b (AND)\n", a&b)
	fmt.Printf("a | b:   %08b (OR)\n", a|b)
	fmt.Printf("a ^ b:   %08b (XOR)\n", a^b)
	fmt.Printf("a &^ b:  %08b (AND NOT - сброс битов b из a)\n", a&^b)
	fmt.Printf("a << 2:  %08b (Сдвиг влево на 2 -> * 4)\n", a<<2)
	fmt.Printf("a >> 2:  %08b (Сдвиг вправо на 2 -> / 4)\n", a>>2)
}

Фундаментальное отличие кавычек в Go:

		char, char, unsafe.Sizeof(char))
	fmt.Printf("str  (\"Z\"): значение = %-4s | тип = %-8T | размер заголовка = %d байт\n",
		str, str, unsafe.Sizeof(str))

Объявите несколько строковых констант и проведите их конкатенацию во время компиляции (без рантайм-затрат).

💡 Теоретический фундамент и концепция

Compile-Time Constant Folding:

Если операция сложения строк выполняется над const:

1. Компилятор склеивает строки во время компиляции;
2. В скомпилированном бинарнике сохраняется одна готовая итоговая строка;
3. В рантайме не тратится ни одного такта CPU и ни одного байта оперативной памяти на конкатенацию.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем константы Host, Port, Endpoint.
2. Склеиваем их в константу FullURL.
3. Выводим итоговую константу.
📄 main.go 
package main

import "fmt"

const (
	Protocol = "https://"
	Domain   = "api.cloud.yandex.net"
	Version  = "/v2"
	Resource = "/compute/instances"

	// Конкатенация происходит на этапе компиляции (Zero Cost):
	FullURL = Protocol + Domain + Version + Resource
)

func main() {
	fmt.Println("Сконкатенированный URL (Compile-Time):")
	fmt.Println(FullURL)
}
ℹ️ Конкатенация констант на этапе компиляции
📄 Терминал

# https://api.cloud.yandex.net/v2/compute/instances

⚠️ Частые грабли и ошибки новичков
  • Попытка использовать вызов функции внутри объявления const (const url = FullURL + strings.ToLower("PATH")): константы не могут зависеть от функций рантайма.

Упражнение #41

Строгое приведение типов при арифметических операциях

📌 Условие задачи

Приведение типов: Создайте переменную int32 и float64. Попробуйте сложить их напрямую. Исправьте ошибку компиляции с помощью явного приведения типов.

💡 Теоретический фундамент и концепция

В Go отсутствует неявное приведение типов:

  • Выражение var1 + var2 компилируется только если оба операнда имеют в точности один и тот же тип;
  • Для сложения int32 и float64 необходимо явно привести один из операндов: float64(a) + b (для точного вещественного результата) или a + int32(b) (с отсечением дроби).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем var a int32 = 40 и var b float64 = 2.5.
2. Показываем ошибку при попытке a + b.
3. Применяем явное приведение к float64.
📄 main.go 
package main

import "fmt"

func main() {
	var a int32 = 40
	var b float64 = 2.5

	// Не скомпилируется: sum := a + b // mismatched types int32 and float64

	// Явное приведение к float64:
	sumFloat := float64(a) + b

	// Явное приведение к int32 (отбрасывает дробную часть b):
	sumInt := a + int32(b)

	fmt.Printf("Результат float64: %.2f\n", sumFloat)
	fmt.Printf("Результат int32:   %d\n", sumInt)
}
ℹ️ Явное приведение типов
📄 Терминал 
go run main.go
# Результат float64: 42.50
# Результат int32:   42
ℹ️ Результат
⚙️ Под капотом Go (Compiler, Linker & Runtime)

При float64(a) компилятор генерирует инструкцию процессора CVTSI2SD (Convert Doubleword Integer to Scalar Double-Precision Floating-Point).

⚠️ Частые грабли и ошибки новичков
  • Приведение большого float64 (например 1e18) к int32 приведет к неопределенному значению из-за переполнения диапазона int32 ($\pm 2 \cdot 10^9$).
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему в Go даже int и int64 требуют явного приведения на 64-битной системе, хотя их размер в байтах одинаков?»

Ответ: Для кроссплатформенной переносимости. Если бы int неявно приводился к int64, код скомпилировался бы на x86-64, но упал с ошибкой на 32-битных микроконтроллерах или ARM32, где int равен int32.

💡 Теоретический фундамент и концепция

Пустой идентификатор _:

  • Принимает любое значение, не выделяя под него память;

	return 100, 200, nil
}

func main() {
	// Нам нужны только координаты X и Y, ошибку отбрасываем:
	x, y, _ := parseCoordinate()

	fmt.Printf("Координаты: X = %d, Y = %d\n", x, y)
}
ℹ️ Игнорирование значений через _
📄 Терминал

ℹ️ Вывод

⚠️ Частые грабли и ошибки новичков
  • Игнорирование критических ошибок в продакшене (f, _ := os.Open("file.txt")): если файл не существует, f будет nil, и последующий вызов f.Read() приведет к панике.
🏢 В продакшене BigTech и на собеседованиях

Ответ: 1) При записи в bytes.Buffer (метод Write буфера в памяти никогда не возвращает ошибку); 2) В defer file.Close() для файлов, открытых только на чтение; 3) При закрытии тела HTTP-ответа defer resp.Body.Close().

Атомарный обмен значениями переменных без временной переменной

📌 Условие задачи

Напишите программу, которая меняет местами значения двух переменных без использования третьей (через множественное присваивание a, b = b, a).

💡 Теоретический фундамент и концепция

Множественное присваивание a, b = b, a:

1. Идиоматичный способ обмена значениями (Swap) в Go;
2. Не требует временной переменной temp;
3. Правая часть вычисляется полностью до изменения левой части.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем a, b := 10, 20.
2. Выполняем a, b = b, a.
3. Проверяем значения.
📄 main.go

import "fmt"

func main() {
	a := "Первый"
	b := "Второй"

	fmt.Printf("До обмена:    a = %s, b = %s\n", a, b)

	// Элегантный обмен без temp переменной
	a, b = b, a

	fmt.Printf("После обмена: a = %s, b = %s\n", a, b)
}
ℹ️ Swap через множественное присваивание
📄 Терминал 
go run main.go
# До обмена:    a = Первый, b = Второй
# После обмена: a = Второй, b = Первый
ℹ️ Результат обмена
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Компилятор Go использует два свободных регистра процессора (например, RAX и RBX) для временного сохранения значений операндов перед записью.

⚠️ Частые грабли и ошибки новичков
  • В языках без множественного присваивания приходится использовать арифметические трюки с XOR (a ^= b; b ^= a; a ^= b), которые ухудшают читаемость. В Go всегда используют a, b = b, a.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Как реализовать переворот среза (Reverse Slice) на месте (in-place) в Go?»

Ответ: Двумя указателями в цикле: for i, j := 0, len(s)-1; i < j; i, j = i+1, j-1 { s[i], s[j] = s[j], s[i] }.

}

Безопасное сложение целых чисел SafeAdd с проверкой переполнения

📌 Условие задачи

💡 Теоретический фундамент и концепция

Математика проверки переполнения:

Для знакового $N$-битного целого числа:

  • Если $b > 0$ и $a > ext{MaxInt} - b$ $ ightarrow$ переполнение сверху (Overflow);
  • Если $b < 0$ и $a < ext{MinInt} - b$ $ ightarrow$ переполнение снизу (Underflow).

🔍 Пошаговый ход решения и ход мысли инженера

1. Импортируем math.
2. Реализуем функцию SafeAdd(a, b int) (int, error).
3. Тестируем на нормальных значениях и на граничных math.MaxInt.
📄 main.go 
package main

import (
	"errors"
	"fmt"
	"math"
)

var ErrOverflow = errors.New("целочисленное переполнение (integer overflow)")

func SafeAdd(a, b int) (int, error) {
	if b > 0 && a > math.MaxInt-b {
		return 0, ErrOverflow
	}
	if b < 0 && a < math.MinInt-b {
		return 0, ErrOverflow
	}
	return a + b, nil
}

func main() {
	// 1. Безопасное сложение
	res, err := SafeAdd(100, 200)
	fmt.Printf("100 + 200 = %d, ошибка: %v\n", res, err)

	// 2. Попытка переполнения
	_, err = SafeAdd(math.MaxInt, 1)
	if errors.Is(err, ErrOverflow) {
		fmt.Println("❌ Переполнение успешно перехвачено!")
	}
}
ℹ️ Безопасная арифметика SafeAdd
📄 Терминал

# ❌ Переполнение успешно перехвачено!
ℹ️ Успешная валидация границ
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Проверка выполняется до операции сложения, исключая UB процессора.

⚠️ Частые грабли и ошибки новичков
  • Попытка проверить if a + b < a: после того как переполнение уже произошло, оптимизатор компилятора может посчитать такое условие недостижимым и вырезать его. Всегда проверяйте границы ДО сложения (a > Max - b).

Упражнение #68

Сравнение точности float32 vs float64 и проблема 0.1 + 0.2 != 0.3

📌 Условие задачи

Напиши программу, которая демонстрирует разницу между float32 и float64 в точности: сложи 0.1 + 0.2, сравни результаты. Покажи проблему точности с плавающей точкой.

💡 Теоретический фундамент и концепция

Стандарт IEEE 754:

Двоичная система не может точно представить десятичные дроби $0.1$ и $0.2$:

  • float32 имеет 24 бита мантиссы ($pprox 7$ значащих десятичных цифр);
  • float64 имеет 53 бита мантиссы ($pprox 15-17$ значащих цифр);
  • 0.1 + 0.2 == 0.30000000000000004 (поэтому прямое 0.1 + 0.2 == 0.3 возвращает false).

🔍 Пошаговый ход решения и ход мысли инженера

1. Складываем 0.1 + 0.2 в float32 и float64.
2. Сравниваем с 0.3.
3. Пишем безопасное сравнение через эпсилон $ arepsilon$.
📄 main.go 
package main

import (
	"fmt"
	"math"
)

func main() {
	var a32, b32 float32 = 0.1, 0.2
	sum32 := a32 + b32

	var a64, b64 float64 = 0.1, 0.2
	sum64 := a64 + b64

	fmt.Printf("float32: 0.1 + 0.2 = %.10f (равно 0.3? %t)\n", sum32, sum32 == 0.3)
	fmt.Printf("float64: 0.1 + 0.2 = %.20f (равно 0.3? %t)\n", sum64, sum64 == 0.3)

	// Безопасное сравнение с погрешностью epsilon
	const eps = 1e-9
	isEqual := math.Abs(sum64-0.3) < eps
	fmt.Printf("Безопасное сравнение (|sum - 0.3| < 1e-9): %t\n", isEqual)
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

💡 Теоретический фундамент и концепция

Строгая типизация защищает от физических катастроф:

1. type Celsius float64 и type Fahrenheit float64 — это два изолированных типа;
2. Попытка сложить c + f вызывает ошибку компилятора mismatched types Celsius and Fahrenheit;
3. Сложение физически разнородных величин без явной конвертации запрещено на уровне языка!

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем типы Celsius и Fahrenheit.
2. Пишем функции CToF(c Celsius) Fahrenheit и FToC(f Fahrenheit) Celsius.
3. Демонстрируем ошибку и правильный расчет.
📄 main.go 
package main

import "fmt"

type Celsius float64
type Fahrenheit float64

func CToF(c Celsius) Fahrenheit {
	return Fahrenheit(c*9/5 + 32)
}

func FToC(f Fahrenheit) Celsius {
	return Celsius((f - 32) * 5 / 9)
}

func main() {
	var c Celsius = 100
	var f Fahrenheit = 212

	// Ошибка компиляции: invalid := c + f // mismatched types Celsius and Fahrenheit

	// Корректное сложение после конвертации:
	sumCelsius := c + FToC(f)

	fmt.Printf("100 °C в Фаренгейтах: %.1f °F\n", CToF(c))
	fmt.Printf("212 °F в Цельсиях:    %.1f °C\n", FToC(f))
	fmt.Printf("Сумма (в Цельсиях):   %.1f °C\n", sumCelsius)
}

Упражнение #79

Битовые флаги прав доступа (Bitmask) через iota и сдвиг 1 << iota

📌 Условие задачи

Используй iota для создания битовых флагов (например, Read = 1 << iota, Write, Execute).

💡 Теоретический фундамент и концепция

Битовые маски (Bitmasks):

  • Read = 1 << 0 ($001_2 = 1$)
  • Write = 1 << 1 ($010_2 = 2$)
  • Execute = 1 << 2 ($100_2 = 4$)
  • Комбинирование прав: Read | Write ($011_2 = 3$);
  • Проверка прав: (perms & Read) != 0.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем Permission = 1 << iota.
2. Создаем комбинированные права.
3. Проверяем наличие конкретных прав.
📄 main.go 
package main

import "fmt"

type Permission uint8

const (
	PermRead    Permission = 1 << iota // 1 (0001)
	PermWrite                          // 2 (0010)
	PermExecute                        // 4 (0100)
	PermAdmin                          // 8 (1000)
)

func main() {
	// Комбинируем права: Чтение + Запись
	userPerms := PermRead | PermWrite

	fmt.Printf("userPerms: %04b (%d)\n", userPerms, userPerms)

	// Проверка наличия прав
	canRead := (userPerms & PermRead) != 0
	canExec := (userPerms & PermExecute) != 0

	fmt.Printf("Право на чтение:     %t\n", canRead)
	fmt.Printf("Право на исполнение: %t\n", canExec)
}

📄 Терминал

# Право на чтение:     true
# Право на исполнение: false
ℹ️ Результат проверки прав
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Операция userPerms & PermRead выделяет 0-й бит, результат сравнивается с нулем за 1 машинный такт.

⚠️ Частые грабли и ошибки новичков
  • Использование оператора && (логическое И) вместо & (побитовое И).
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Как сбросить конкретный флаг (например PermWrite) из маски userPerms?»

Циклический сдвиг (Circular Shift):

Выражение a, b, c = b, c, a:

1. Временно фиксирует старые значения (b, c, a);
2. Одновременно записывает: в a попадает старый b, в b — старый c, в c — старый a;

	a, b, c = b, c, a
	fmt.Printf("Сдвиг 1:      a = %d, b = %d, c = %d\n", a, b, c)

	a, b, c = b, c, a
	fmt.Printf("Сдвиг 2:      a = %d, b = %d, c = %d\n", a, b, c)

Упражнение #99

Инициализация ссылочных типов через make() (slice, map, channel)

📌 Условие задачи

Используй make() для создания slice, map, channel. Объясни, почему make() нужен именно для этих типов, а для других — нет.

💡 Теоретический фундамент и концепция

Почему make() существует только для slice, map и channel?

Эти три типа являются сложными дескрипторами (ссылочными типами рантайма):

1. slice требует аллокации базового массива и настройки полей Data, Len, Cap;
2. map требует создания структуры hmap и массива бакетов;
3. channel требует создания структуры hchan, кольцевого буфера и очередей ожидания горутин sudog.

Обычные типы (int, struct) не имеют внутренних сложных структур и создаются через var или new().

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем срез через make([]int, len, cap).
2. Создаем мапу через make(map[string]int, hint).
3. Создаем буферизованный канал через make(chan int, buffer).
📄 main.go 
package main

import "fmt"

func main() {
	// 1. Slice: len = 3, cap = 10
	s := make([]int, 3, 10)

	// 2. Map с предварительным хинтом емкости 50
	m := make(map[string]int, 50)
	m["connections"] = 100

	// 3. Channel: буферизованный канал на 5 сообщений
	ch := make(chan int, 5)
	ch <- 42

	fmt.Printf("Slice:   len=%d, cap=%d\n", len(s), cap(s))
	fmt.Printf("Map:     len=%d, key[connections]=%d\n", len(m), m["connections"])
	fmt.Printf("Channel: len=%d, cap=%d, received=%d\n", len(ch), cap(ch), <-ch)
}
ℹ️ Инициализация через make()
📄 Терминал 
go run main.go
# Slice:   len=3, cap=10
# Map:     len=1, key[connections]=100
# Channel: len=1, cap=5, received=42
ℹ️ Результат
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Компилятор транслирует вызовы make в рантайм функции: runtime.makeslice, runtime.makemap_small / runtime.makemap и runtime.makechan.

⚠️ Частые грабли и ошибки новичков
  • Вызов make(int): компилятор выдаст ошибку cannot make type int. make применим только к слайсам, мапам и каналам.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Зачем указывать второй аргумент hint в make(map[string]int, 1000)?»

Ответ: Это заранее аллоцирует нужное количество бакетов памяти. При добавлении 1000 элементов мапе не придется многократно реаллоцироваться и перестраивать хэш-таблицу (Rehashing), что ускоряет заполнение в 3–5 раз.

Упражнение #100

Отложенные вызовы defer и порядок выполнения LIFO (стек)

📌 Условие задачи

Напиши программу с defer: отложи несколько вызовов функций. Покажи, что они выполняются в порядке LIFO (последний defer — первым).

💡 Теоретический фундамент и концепция

Ключевое слово defer:

1. Откладывает выполнение функции до момента выхода из текущей окружающей функции;
2. Аргументы функции вычисляются немедленно в точке вызова defer;
3. Вызовы накапливаются в стек горутины и исполняются в порядке LIFO (Last In, First Out) — последний добавленный defer сработает самым первым.

🔍 Пошаговый ход решения и ход мысли инженера

1. В цикле откладываем вызовы defer fmt.Println(i).
2. Наблюдаем обратный порядок вывода 3 -> 2 -> 1 -> 0.
📄 main.go 
package main

import "fmt"

func main() {
	fmt.Println("Старт функции main")

	defer fmt.Println("Defer #1 (первый зарегистрирован -> сработает третьим)")
	defer fmt.Println("Defer #2 (второй зарегистрирован -> сработает вторым)")
	defer fmt.Println("Defer #3 (третий зарегистрирован -> сработает ПЕРВЫМ)")

	for i := 1; i <= 3; i++ {
		defer fmt.Printf("Цикл defer i = %d\n", i)
	}

	fmt.Println("Конец тела функции main (сейчас начнут выполняться defer)")
}
ℹ️ Порядок LIFO в defer
📄 Терминал

# Цикл defer i = 1
# Defer #3 (третий зарегистрирован -> сработает ПЕРВЫМ)

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Начиная с Go 1.14 компилятор оптимизирует defer через Open-Coded Defers (встраивание вызовов прямо перед RET инструкцией функции), сводя накладные расходы на вызов defer почти к нулю ($pprox 1.5$ нс).

⚠️ Частые грабли и ошибки новичков
  • Вызов defer file.Close() внутри длинного цикла: файлы не закроются до завершения всей функции main, что приведет к исчерпанию файловых дескрипторов. В циклах используют замыкания или явное закрытие.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Когда вычисляются аргументы функции, переданной в defer?»

Ответ: Аргументы вычисляются немедленно в момент вызова строки defer, а не в момент фактического исполнения функции при выходе.

Упражнение #101

Самоссылающиеся структуры (Self-Referential Structs) и односвязный список

📌 Условие задачи

Создай "self-referential" структуру: type Node struct { Value int; Next *Node }. Создай связный список из 3 узлов вручную. Обойди список и выведи значения.

💡 Теоретический фундамент и концепция

Самоссылающиеся структуры (Связные списки, Деревья, Графы):

  • Структура не может содержать саму себя по значению (type Node struct { Next Node } — бесконечный размер);
  • Структура может содержать указатель на саму себя (Next *Node), так как указатель имеет фиксированный размер 8 байт;
  • Завершение списка обозначается Next == nil.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем type Node struct { Value int; Next *Node }.
2. Создаем 3 узла и связываем их: n1 -> n2 -> n3.
3. В цикле for curr != nil обходим список.
📄 main.go 
package main

import "fmt"

type Node struct {
	Value int
	Next  *Node
}

func main() {
	// Создаем 3 узла связного списка
	n3 := &Node{Value: 30, Next: nil}
	n2 := &Node{Value: 20, Next: n3}
	n1 := &Node{Value: 10, Next: n2}

	fmt.Println("Обход односвязного списка:")
	curr := n1
	for curr != nil {
		fmt.Printf("[%d] -> ", curr.Value)
		curr = curr.Next
	}
	fmt.Println("nil")
}

📄 Терминал

# [10] -> [20] -> [30] -> nil

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Каждый узел аллоцируется в куче, поле Next хранит 64-битный адрес следующего узла.

⚠️ Частые грабли и ошибки новичков
  • Создание кольцевой ссылки (n3.Next = n1): цикл for curr != nil станет бесконечным и зависнет.

Менеджер битовых флагов: функции HasFlag, AddFlag, RemoveFlag

📌 Условие задачи

Создай константы с iota для битовых флагов: FlagRead = 1 << iota, FlagWrite, FlagExecute. Напиши функции HasFlag(flags, flag int) bool, AddFlag, RemoveFlag.

💡 Теоретический фундамент и концепция

Паттерны битовых операций:

  • Проверка: (flags & flag) != 0
  • Добавление: flags | flag
  • Удаление: flags &^ flag (Bit Clear)
  • Переключение: flags ^ flag

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем флаги FlagRead, FlagWrite, FlagExecute.
2. Реализуем хелперы HasFlag, AddFlag, RemoveFlag.
3. Тестируем полный жизненный цикл прав.
📄 main.go 
package main

import "fmt"

const (
	FlagRead    = 1 << iota // 1 (001)
	FlagWrite               // 2 (010)
	FlagExecute             // 4 (100)
)

func HasFlag(flags, flag int) bool { return (flags & flag) != 0 }
func AddFlag(flags, flag int) int  { return flags | flag }
func RemoveFlag(flags, flag int) int { return flags &^ flag }

func main() {
	var perms int

	// Добавляем Read и Execute
	perms = AddFlag(perms, FlagRead)
	perms = AddFlag(perms, FlagExecute)

	fmt.Printf("Права: %03b\n", perms)
	fmt.Printf("Есть чтение?    %t\n", HasFlag(perms, FlagRead))
	fmt.Printf("Есть запись?    %t\n", HasFlag(perms, FlagWrite))
	fmt.Printf("Есть исполнение?%t\n\n", HasFlag(perms, FlagExecute))

	// Удаляем исполнение
	perms = RemoveFlag(perms, FlagExecute)
	fmt.Printf("После RemoveFlag(Execute): %03b\n", perms)
	fmt.Printf("Есть исполнение? %t\n", HasFlag(perms, FlagExecute))
}

package main

import (
	"errors"
	"fmt"
)

type Operation int

const (
	OpAdd Operation = iota
	OpSub
	OpMul
	OpDiv
)

func Calculate(op Operation, a, b float64) (float64, error) {
	switch op {
	case OpAdd:
		return a + b, nil
	case OpSub:
		return a - b, nil
	case OpMul:
		return a * b, nil
	case OpDiv:
		if b == 0 {
			return 0, errors.New("деление на ноль")
		}
		return a / b, nil
	default:
		return 0, errors.New("неизвестная операция")
	}
}

func main() {
	res1, _ := Calculate(OpAdd, 15, 5)
	res2, _ := Calculate(OpMul, 15, 5)
	res3, _ := Calculate(OpDiv, 15, 5)

	fmt.Printf("15 + 5 = %.1f\n", res1)
	fmt.Printf("15 * 5 = %.1f\n", res2)
	fmt.Printf("15 / 5 = %.1f\n", res3)
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Плотный switch по iota (0, 1, 2, 3) компилятор оптимизирует в Jump Table (таблицу прямых переходов), работающую за $O(1)$ без последовательных сравнений.

  • Забыть ветку default для обработки невалидных кодов операций.

Вопрос с собеседования: «При каких условиях компилятор Go превращает switch в Jump Table?»

Ответ: Когда значения case являются плотными целыми константами (например, 0, 1, 2, 3, 4 как в iota), а количество веток $\ge 4$.

Упражнение #111

Глубокий сравнительный анализ типизированных и нетипизированных констант

📌 Условие задачи

Напиши программу с "typed" и "untyped" константами. Покажи, что untyped константу можно присвоить любому совместимому типу, а typed — только своему типу.

💡 Теоретический фундамент и концепция

Финальное закрепление теории констант:

  • Typed (const Max int32 = 100): жестко привязана к int32. Попытка присвоить var y int64 = Max вызовет ошибку компиляции;
  • Untyped (const Limit = 100): может быть присвоена int, int8, int16, int32, int64, uint, float32, float64, complex128 без единой строки явного каста!

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем const UntypedVal = 50 и const TypedVal int32 = 50.
2. Демонстрируем присвоение в переменные int8, uint64, float64.
3. Анализируем разницу.
📄 main.go 
package main

import "fmt"

const UntypedVal = 50       // Нетипизированная
const TypedVal int32 = 50   // Типизированная (int32)

func main() {
	// UntypedVal свободно присваивается в любые совместимые типы:
	var vInt8 int8 = UntypedVal
	var vUint64 uint64 = UntypedVal
	var vFloat float64 = UntypedVal
	var vComplex complex128 = UntypedVal

	fmt.Printf("vInt8:    %d (%T)\n", vInt8, vInt8)
	fmt.Printf("vUint64:  %d (%T)\n", vUint64, vUint64)
	fmt.Printf("vFloat:   %.1f (%T)\n", vFloat, vFloat)
	fmt.Printf("vComplex: %v (%T)\n\n", vComplex, vComplex)

	// TypedVal жестко требует совпадения типа:
	var target32 int32 = TypedVal
	// var target64 int64 = TypedVal // ОШИБКА: cannot use TypedVal (type int32) as type int64

	fmt.Printf("target32: %d (%T)\n", target32, target32)
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Нетипизированные константы дают языку Go ту же гибкость и лаконичность, что и динамические языки, сохраняя при этом 100% строгую статическую безопасность типов во время компиляции.

⚠️ Частые грабли и ошибки новичков
  • Ограничение: нетипизированное число не может быть присвоено типу, если его значение выходит за границы этого типа (например const Huge = 300; var b int8 = Huge вызовет ошибку 300 overflows int8).

Вопрос с собеседования: «Почему в Go нетипизированные константы называют "секретным оружием системы типов"?»

Ответ: Потому что они избавляют разработчика от тысяч громоздких явных кастов float64(2) * r или time.Duration(10) * time.Second, сохраняя исходный код чистым, лаконичным и абсолютно типобезопасным.
