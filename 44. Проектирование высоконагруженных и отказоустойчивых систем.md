# Проектирование высоконагруженных и отказоустойчивых систем

В этом файле собраны уникальные упражнения по теме **"Проектирование высоконагруженных и отказоустойчивых систем"**, отсортированные по возрастанию сложности.

---

1. **CQRS (Command Query Responsibility Segregation)**: Разделите модели для записи (commands) и чтения (queries). Write model — нормализованная БД, Read model — денормализованные view в Redis/Elasticsearch.

2. **Event Sourcing**: Сохраняйте все изменения состояния как последовательность событий в Kafka/EventStoreDB. Восстанавливайте текущее состояние через replay событий.

3. **Materialized Views**: Создавайте read-оптимизированные проекции из event stream (например, `UserOrdersView` обновляется при каждом `OrderCreated` событии).

4. **Read Replicas**: Настройте master-slave репликацию в PostgreSQL. Write операции идут в master, read — в slaves (через separate DB connection pool).

5. **Database Sharding**: Горизонтальное шардирование по `user_id` (например, `user_id % 16` определяет шард). Реализуйте routing logic в приложении или через Vitess/Citus.

6. Спроектируй **Caching Strategy**: `Cache-Aside` (проверь кеш → miss → БД → кеш), `Read-Through` (кеш сам ходит в БД), `Write-Through` (писать в кеш и БД синхронно), `Write-Behind` (писать в кеш, async в БД). Покажи trade-offs по consistency и latency.

7. **Caching Strategies**: Реализуйте Cache-Aside (lazy loading), Write-Through, Write-Behind (async write). Используйте Redis для hot data, CDN для static assets.

8. Реализуй **Multi-Level Cache**: L1 (in-process, `sync.Map`, 1ms), L2 (Redis, 5ms), L3 (PostgreSQL, 50ms). `GetUser`: L1 → L2 → L3. `Invalidate`: publish event, все уровни обновляются. Покажи hit rate per level.

9. Реализуй **Cache Warming**: при деплое новой версии — preload hot data into cache. `CacheWarmer` читает `SELECT * FROM products WHERE active = true ORDER BY views DESC LIMIT 10000`, пишет в Redis. Покажи, что cold cache = DB overload.

10. **Cache Invalidation**: Реализуйте инвалидацию кэша через pub/sub (Redis Pub/Sub) при изменении данных в БД.

11. Реализуй **Rate Limiting (Token Bucket)**: `user_id` — 100 requests/minute. Redis: `INCR user:123:rate` + `EXPIRE 60`. Или `redis-cell` модуль. Distributed: все instances share Redis state. Покажи fairness.

12. **Rate Limiting**: Реализуйте distributed rate limiter через Redis Lua scripts (token bucket или sliding window) для защиты от DoS и fair usage.

13. Реализуй **Rate Limiting (Sliding Window Counter)**: Redis `ZADD` timestamp'ов, `ZREMRANGEBYSCORE` старых, `ZCARD` для подсчёта. Точнее, но дороже. Покажи precision vs performance trade-off.

14. **Load Shedding**: При перегрузке отбрасывайте "дешёвые" запросы (health checks, неважные метрики) или возвращайте cached/stale data.

15. Реализуй **Load Balancing (Layer 4)**: HAProxy/Nginx TCP passthrough. Round-robin, least-connections, IP-hash (sticky sessions). Покажи, что L4 не видит HTTP, работает с любым TCP.

16. **Backpressure**: Если consumer не успевает обрабатывать сообщения из Kafka, уменьшайте fetch size или приостанавливайте producer.

17. Реализуй **Load Balancing (Layer 7)**: Nginx/Envoy HTTP routing. Path-based: `/api/v1/users/*` → `user-service-v1`, `/api/v2/users/*` → `user-service-v2`. Header-based: `Canary: true` → `user-service-canary`. Cookie-based: `version=v2` → `user-service-v2`.

18. **Bulkhead Pattern**: Изолируйте ресурсы для разных клиентов/тенантов (separate thread pools, connection pools), чтобы падение одного не уронило всю систему.

19. Реализуй **Auto-Scaling (HPA)**: Kubernetes `HorizontalPodAutoscaler` по CPU (target 70%), memory, custom metrics (Kafka lag, request latency). `KEDA` для event-driven scaling: 0 replicas when no messages, scale to 100 when 10000 messages in queue.

20. **Circuit Breaker**: Реализуйте автоматическое "размыкание цепи" при N подряд ошибках к downstream сервису, с последующими попытками восстановления.

21. Реализуй **Database Connection Pooling**: `pgxpool` с `MaxConns=50`, `MinConns=10`, `MaxConnLifetime=1h`. Мониторинг: `pgxpool.Stat().TotalConns()`, `IdleConns()`, `WaitCount()`. Покажи, что pool exhaustion = cascading failure.

22. **Retry with Exponential Backoff**: При transient errors делайте retry с увеличивающейся задержкой (1s, 2s, 4s, 8s) и jitter для предотвращения thundering herd.

23. Реализуй **Async Processing (Worker Pool)**: HTTP API принимает `CreateReportRequest`, возвращает `job_id`. Job queue (Redis/RabbitMQ/Kafka). Workers (10 goroutines) обрабатывают. Client polls `GET /jobs/{id}/status`. Покажи decoupling от long-running tasks.

24. **Horizontal Scaling**: Спроектируйте сервисы как stateless, чтобы можно было запускать N инстансов за load balancer'ом. State храните в Redis/PostgreSQL/Kafka.

25. Реализуй **Backpressure**: `Order Service` получает 10000 RPS, `Payment Service` обрабатывает 1000 RPS. Queue (Kafka) буферизует. Если queue > 100000 messages — reject new requests (`503 Service Unavailable`), клиент retry. Покажи, что без backpressure — OOM, data loss.

26. **Vertical Partitioning (Functional Partitioning)**: Разделите данные по функциональности: "горячие" данные (последние заказы) в быстрой БД, "холодные" (архив) в дешёвом хранилище (S3 + Athena).

27. Реализуй **Graceful Degradation**: `Recommendation Service` недоступен. `Product Service` возвращает products без recommendations (default: popular items). `Search Service` returns results without personalization. Покажи partial functionality vs total failure.

---

28. **Singleflight (Шторм кэша / Thundering Herd)**: Кэш инвалидировался. Тысяча клиентов одновременно запрашивает один тяжелый SQL-запрос. База данных ложится. Используй пакет `golang.org/x/sync/singleflight`. Оберни вызов к БД. Убедись, что если 1000 горутин обращаются одновременно, реальный SQL-запрос выполнится ровно **один** раз, а результат раздастся всем тысяче ожидающих.

29. **Graceful Degradation (Мягкая деградация)**: Твой рекомендательный сервис (AI) упал. В HTTP-хендлере интернет-магазина оберни вызов к сервису в таймаут (200мс). Если рекомендаций нет, перехвати ошибку, не роняй страницу 500-й ошибкой, а верни статичный захардкоженный список "Самые популярные товары". Клиент не должен заметить поломки!

30. Спроектируй **System for 1M RPS**: horizontal scaling (1000 instances), stateless services, shared-nothing architecture. Load balancer (L4) distributes. Caching at every layer: CDN (static), edge cache (API responses), application cache (hot data), database cache (query results).

31. Реализуй **Connection Pooling at Scale**: 1000 instances × 50 DB connections = 50000 connections. PostgreSQL limit: ~10000. Solution: PgBouncer (connection pooler), `transaction` pooling mode. Or: RDS Proxy, read replicas, connection multiplexing.

32. **Circuit Breaker + Fallback**: (Развитие 569). Настрой полноценный `gobreaker` (из предыдущих блоков). Добавь в него Fallback-функцию (что возвращать, когда предохранитель разомкнут). Убедись, что при "отключении" зависимого сервиса твой код мгновенно возвращает кэш, не тратя время на таймауты.

33. **Проектирование отказоустойчивости**. Примените Bulkhead (отдельные пулы соединений для разных downstream), Retry с exponential backoff, Timeout для всех внешних вызовов.

34. Реализуй **Request Coalescing**: 1000 requests for same `product:123` simultaneously. Only 1 goes to DB, 999 wait for result. `singleflight.Group` (Go) or `cache stampede` protection. Reduces DB load 1000x for hot keys.

35. **Failure Mode Analysis**: Для каждого компонента (БД, Redis, Kafka, external API) проанализируйте: что произойдёт при его падении? Как система деградирует?

36. Реализуй **Request Deduplication**: same `CreateOrder` request retried by client (network timeout). `Idempotency-Key` + `singleflight` = process once, return cached response. Even across instances: Redis distributed lock.

37. **Graceful Degradation**: Если recommendation service недоступен, возвращайте popular items вместо персональных рекомендаций.

38. Реализуй **Prefetching + Predictive Caching**: ML model predicts "user likely to view product X next". Prefetch into cache before request. Warm CDN edge for geographic region. Reduce latency from 200ms to 20ms.

39. **Timeout Everywhere**: Установите таймауты на все network calls (HTTP, gRPC, DB, Redis). Нет таймаута = бесконечное ожидание = cascade failure.

40. Реализуй **Load Shedding**: system overloaded (CPU > 90%, latency p99 > 2s). Drop low-priority requests (analytics, non-critical reads). Accept high-priority (payments, critical writes). `503` with `Retry-After` header. Client backs off exponentially.

41. **Retry Budget**: Ограничьте общее количество retry в системе (например, не более 10% от общего трафика), чтобы retry storm не усугубил проблему.

42. **Application-Level Sharding**: Одна БД больше не справляется. Подними две PostgreSQL (`db_node_0` и `db_node_1`). В Go-коде напиши роутер подключений: при создании юзера бери остаток от деления `userID % 2`. Если 0 — пиши в первую базу, если 1 — во вторую. Реализуй абстракцию, чтобы бизнес-логика не замечала, что баз две.

43. **Горизонтальное масштабирование: stateless-сервисы**. Спроектируйте сервис так, чтобы любой экземпляр мог обработать любой запрос. Вынесите состояние в Redis (сессии) и БД. Покажите балансировку через Nginx или Kubernetes Service.

44. Реализуй **Admission Control**: `token bucket` for incoming requests. If bucket empty — reject immediately. Protects backend from overload. Separate buckets per priority, per tenant, per endpoint. Dynamic: reduce rate if latency grows.

45. **Chaos Testing (Pod Kill)**: Используйте `pumba` или `chaos-mesh` для случайного убийства подов и проверки, что система восстанавливается.

46. Реализуй **Parallel Processing**: `GetOrderDetails` needs data from 5 services. Sequential: 5 × 100ms = 500ms. Parallel: `errgroup.Group`, 5 concurrent requests, 100ms + overhead. Timeout: `context.WithTimeout(150ms)`, return partial if some fail.

47. **Chaos Testing (Network Latency)**: Эмулируйте сетевые задержки через `tc` (traffic control) и проверяйте, что таймауты и retry работают корректно.

48. Реализуй **Batching + Windowing**: 1000 `GetUser` requests/sec. Individual: 1000 DB queries. Batched: accumulate 50ms window, 1 query `SELECT * FROM users WHERE id IN (...)`. 1000 → 20 queries. Trade-off: latency + throughput.

49. **Chaos Testing (Database Failover)**: Остановите primary БД и проверьте, что приложение корректно переключается на replica.

50. **Consistent Hashing (Согласованное хеширование)**: У тебя 3 in-memory кэш-сервера. Если один упадет, обычный `userID % 3` сдвинет ВСЕ ключи (кэш инвалидируется на 100%). Реализуй (или возьми библиотеку `stathat.com/c/consistent`) кольцо консистентного хеширования, чтобы при падении одной ноды перераспределилось только 33% ключей, а остальные остались на своих местах.

51. Реализуй **Approximation Algorithms**: `HyperLogLog` for unique users (0.1% error, 1KB memory vs 1GB for exact). `Count-Min Sketch` for frequency (heavy hitters). `Bloom Filter` for "probably in set" (cache negative lookups). Acceptable for analytics, not billing.

52. **Disaster Recovery (DR)**: Настройте cross-region replication для БД и object storage. Тестируйте failover в DR регион.

53. **Backup and Restore**: Регулярные backups БД с тестированием restore procedure. RPO (Recovery Point Objective) и RTO (Recovery Time Objective).

54. **Runbooks**: Документируйте процедуры для incident response: "что делать при high CPU", "что делать при DB connection pool exhaustion".

55. **Shedding Load (Сброс нагрузки)**: Твой сервер захлебывается (CPU > 90%). Напиши HTTP-мидлварь, которая мониторит метрику CPU (или количество активных горутин). Если порог превышен, она начинает отклонять все *новые некритичные* запросы со статусом `503 Service Unavailable`, спасая сервер от полного краха (OOM).

56. **Load Testing**: Используйте `k6`, `vegeta` или `wrk` для нагрузочного тестирования. Определите max RPS, P99 latency, breaking point.

57. **Profiling in Production**: Используйте `pprof` для снятия CPU/memory profiles в production (на canary инстансах) для поиска bottlenecks.

58. **Database Query Optimization**: Используйте `EXPLAIN ANALYZE` для медленных запросов. Добавляйте индексы, оптимизируйте JOIN'ы, используйте materialized views.

59. **Worker Pool с динамическим масштабированием (Auto-scaling)**: Напиши Worker Pool, который по умолчанию держит 5 горутин. Если длина очереди задач превышает 100, пул должен временно породить еще 20 горутин (до лимита). Когда очередь пустеет — убивать "лишние" горутины для экономии памяти.

60. **Connection Pooling**: Настройте optimal pool size для PostgreSQL (`max_conns = (core_count * 2) + disk_spindles`). Используйте PgBouncer для connection multiplexing.

61. **Batch Processing**: Объединяйте множество мелких операций в batch (например, bulk INSERT вместо 1000 отдельных INSERT'ов).

62. **Async Processing**: Выносите "тяжёлые" операции (email sending, image processing) в background jobs через Kafka/RabbitMQ.

63. **Финальный босс (Global-scale SaaS Platform):**
    Спроектируйте multi-tenant SaaS платформу для project management (типа Jira/Asana):
    
    **Архитектура:**
    * Modular monolith для core functionality (projects, tasks, users).
    * Микросервисы для специфичных доменов: Notification Service, Analytics Service, Billing Service.
    * API Gateway (Kong) с rate limiting, authentication, request routing.
    * BFF для web и mobile клиентов.
    
    **Data Layer:**
    * PostgreSQL (с Citus для sharding) для transactional data.
    * Redis для caching, sessions, real-time presence.
    * Elasticsearch для full-text search по tasks.
    * Kafka для event streaming и async communication.
    * S3 для file attachments.
    
    **Multi-tenancy:**
    * Database-per-tenant для enterprise customers (изоляция, compliance).
    * Shared database с Row-Level Security для SMB customers.
    * Data residency: EU tenants в eu-west-1, US tenants в us-east-1.
    
    **Scalability:**
    * Horizontal scaling через Kubernetes HPA.
    * Read replicas для read-heavy operations.
    * CQRS для analytics dashboard (write model → Kafka → materialized views в ClickHouse).
    * CDN для static assets и media.
    
    **Resilience:**
    * Circuit breakers для external integrations.
    * Retry с exponential backoff и jitter.
    * Bulkhead isolation для tenant workloads.
    * Graceful degradation при partial failures.
    
    **Observability:**
    * OpenTelemetry для distributed tracing.
    * Prometheus + Grafana для metrics и SLO dashboards.
    * Loki для structured logs.
    * Jaeger для trace visualization.
    
    **Security & Compliance:**
    * OAuth2/OIDC для authentication.
    * RBAC + ABAC для authorization.
    * Encryption at rest (AES-256) и in transit (TLS 1.3).
    * Audit logging для compliance (SOC 2, GDPR).
    * Secrets management через HashiCorp Vault.
    
    **Deployment:**
    * GitOps через ArgoCD.
    * Blue-green deployments для zero-downtime releases.
    * Feature flags для gradual rollout.
    * Canary deployments с automated rollback при errors.

64. **Проблема C10k (Продвинутая сеть на epoll)**: У тебя 100 000 висящих TCP-подключений (умные часы шлют пинги раз в час). 100к горутин (`go handleConn()`) съедят 200-400 МБ оперативки просто на стеки. Изучи и напиши сырой TCP-сервер, используя пакет `golang.org/x/sys/unix` и системный вызов `epoll` (на Linux) или `kqueue` (на macOS/BSD). Ты поймешь, как работают Event Loops внутри Node.js или Nginx, и сможешь держать сотни тысяч коннектов всего на 1-2 горутинах!
