# Шаблоны проектирования распределенных и enterprise-систем

В этом файле собраны уникальные упражнения по теме **"Шаблоны проектирования распределенных и enterprise-систем"**, отсортированные по возрастанию сложности.

---

1. Реализуй **API Gateway** (Kong/Envoy/самописный): маршрутизация `/users/*` → `user-service:8080`, `/orders/*` → `order-service:8080`, `/payments/*` → `payment-service:8080`. Добавь: auth (JWT validation), rate limiting, request/response transformation.

2. Реализуй **Backend-for-Frontend (BFF)**: `Mobile BFF` (агрегирует данные для iOS/Android: мало полей, оптимизированные запросы), `Web BFF` (больше данных, SSR-ready), `Admin BFF` (все поля, фильтры, экспорт). Покажи, что generic API плох для всех клиентов.

3. Реализуй **GraphQL Gateway (Apollo Federation)**: `User Service` предоставляет `type User @key(fields: "id")`. `Order Service` extends `User` полем `orders: [Order]`. Gateway агрегирует schema'ы, маршрутизирует queries. Покажи federated graph.

4. Реализуй **gRPC-Gateway**: `order.proto` с HTTP annotations (`option (google.api.http) = { get: "/v1/orders/{id}" }`). `protoc-gen-grpc-gateway` генерирует HTTP REST API поверх gRPC. Один сервис — два протокола.

5. Реализуй **Sidecar Gateway (Istio/Linkerd)**: сервис не знает о TLS, mTLS, retry, circuit breaker, rate limit. Sidecar proxy (Envoy) добавляет это transparently. Покажи service mesh vs API gateway.

---

6. Спроектируй **Database-per-Service**: `User Service` → PostgreSQL (users, auth), `Order Service` → PostgreSQL (orders, items), `Inventory Service` → PostgreSQL (products, stock), `Analytics Service` → ClickHouse (events, aggregations). Покажи, что shared database — антипаттерн.

7. Реализуй **Saga с Outbox Pattern**: `Order Service` транзакция: `INSERT INTO orders ...` + `INSERT INTO outbox (topic, payload) ...`. Отдельный worker читает outbox, публикует в Kafka, удаляет. Покажи atomicity: БД commit = event published (eventually).

8. Реализуй **Change Data Capture (CDC)**: Debezium читает PostgreSQL WAL (`pgoutput`), публикует `dbserver1.public.orders` в Kafka. `Search Service` (Elasticsearch) и `Cache Service` (Redis) — consumers. Покажи zero-code data pipeline.

9. Спроектируй **Polyglot Persistence**: `User Service` — PostgreSQL (relational data), `Session Service` — Redis (TTL, fast access), `Search Service` — Elasticsearch (full-text), `Analytics` — ClickHouse (OLAP), `Logs` — Loki/Elasticsearch (time-series). Покажи правильный инструмент для задачи.

10. Реализуй **Read Replica Pattern**: `Order Service` пишет в PostgreSQL primary, читает из read replicas (load balancing). Replication lag: `SELECT pg_last_xact_replay_timestamp()` — покажи eventual consistency. Стратегия: "read own writes" (писатель читает primary).

11. Реализуй **Sharding**: `User Service` шардирует по `user_id % 16`. Router layer (pgBouncer/самописный) направляет запрос. Rebalancing: добавь шард, мигрируй диапазон (consistent hashing). Покажи горизонтальное масштабирование.

12. Реализуй **CQRS с Event Sourcing**: `Command Side` — Event Store (Kafka/NATS JetStream, append-only). `Query Side` — multiple projections: `OrderSummaryView` (Redis), `OrderAnalyticsView` (ClickHouse), `OrderSearchView` (Elasticsearch). Покажи, что projections независимы, replayable.

---

13. Реализуй **Synchronous Communication (gRPC)**: `Order Service` вызывает `Inventory Service.Reserve()` synchronously. Покажи coupling: latency stack, cascading failure, tight runtime dependency. Когда уместно: simple operations, strong consistency needed.

14. Реализуй **Asynchronous Messaging (Events)**: `Order Service` публикует `OrderCreated`. `Inventory Service` подписывается, обрабатывает. Покажи decoupling: services evolve independently, temporal decoupling (consumer offline OK). Когда уместно: eventual consistency acceptable.

15. Реализуй **Asynchronous Request-Response (Commands)**: `Order Service` отправляет `ReserveInventoryCommand` в queue, ждёт `InventoryReserved` или `InventoryReservationFailed` event. Timeout: если нет ответа за 5s → compensation. Покажи async saga.

16. Реализуй **Circuit Breaker + Fallback**: `Order Service` → `Payment Service`. CB: Closed (normal) → Open (5 errors, 30s timeout) → Half-Open (1 trial). Fallback: если Open, queue payment for later processing (async). Покажи graceful degradation.

17. Реализуй **Bulkhead Pattern**: `Order Service` имеет пулы: `Pool A` (10 goroutines) для `Inventory Service`, `Pool B` (10 goroutines) для `Payment Service`, `Pool C` (5 goroutines) для `Email Service`. Если `Payment Service` медленный — `Pool B` заполнен, но `Pool A` и `Pool C` работают.

18. Реализуй **Retry with Exponential Backoff + Jitter**: `Inventory Service` временно недоступен. Retry: 100ms, 200ms, 400ms, 800ms + random jitter (0-100ms). Jitter предотвращает thundering herd при восстановлении. Max retries: 3, then circuit breaker.

19. Реализуй **Idempotency Key**: клиент генерирует `Idempotency-Key: uuid` для `CreateOrder`. Сервер хранит обработанные ключи (Redis, TTL=24h). При повторе с тем же ключом — возвращает cached response, не создаёт дубликат. Покажи exactly-once обработка.

20. Реализуй **Transactional Outbox + Inbox**: `Outbox` (публикация events) + `Inbox` (идемпотентная обработка входящих events). `Inbox` таблица: `idempotent_key`, `processed_at`. При получении `OrderCreated` — `INSERT INTO inbox ... ON CONFLICT DO NOTHING`. Покажи exactly-once consumption.

---

21. **CQRS (разделение команд и запросов)**. Команды (create, update) идут через доменную модель. Запросы (получение списка) идут напрямую в БД через оптимизированные read-модели (денормализованные).

22. **Multi-tenancy (Shared DB, Shared Schema)**: Все тенанты в одной БД, каждая таблица имеет `tenant_id`. Используйте Row-Level Security (RLS) в PostgreSQL для изоляции.

23. Реализуй **Zero Trust Architecture**: нет "internal network" = trusted. Каждый сервис аутентифицирует caller (mTLS + JWT). Каждый request авторизуется. Network segmentation: `frontend` → `api-gateway` → `services`, но `services` не общаются напрямую без auth.

24. **Multi-tenancy (Shared DB, Separate Schemas)**: Каждый тенант имеет свою схему в одной БД. Более изолированно, но сложнее управлять миграциями.

25. Реализуй **mTLS everywhere**: сервисы имеют certificates issued by internal CA. `Order Service` verifies `Payment Service` certificate, `Payment Service` verifies `Order Service`. No service-to-service trust without mutual verification.

26. **CQRS (Command and Query Responsibility Segregation)**: Раздели сервис на две части. `CommandService` обрабатывает POST/PUT, реализует сложную логику и пишет в PostgreSQL. `QueryService` обрабатывает GET, читает данные из сверхбыстрого Redis (или ElasticSearch), куда данные асинхронно перекладываются после записи.

27. **Transactional Outbox для надёжной публикации событий**. Сервис сохраняет событие в таблицу `outbox` в той же транзакции, что и изменение агрегата. Отдельный процесс отправляет события в брокер с гарантией at-least-once.

28. **Multi-tenancy (Separate DB)**: Каждый тенант имеет свою БД. Максимальная изоляция, но дорого и сложно масштабировать.

29. Реализуй **OAuth2/OIDC**: `API Gateway` → `Authorization Server` (Keycloak/Auth0). Client получает `access_token` (JWT). Gateway validates token, extracts `sub` (user_id), `roles`, `scopes`. Передаёт `X-User-ID`, `X-Roles` downstream. Покажи token introspection vs local validation.

30. **Паттерн Outbox (Транзакционный Outbox)**: При отправке сообщений в Kafka сразу после записи в БД может возникнуть сбой: запись сохранилась, а сообщение не ушло (или наоборот). Решите проблему:
    * В рамках одной SQL-транзакции сохраните пользователя в таблицу `users` и событие `"UserCreated"` в служебную таблицу `outbox` в PostgreSQL.
    * Напишите фонового демона (CDC-воркер), который раз в секунду опрашивает таблицу `outbox`, публикует новые события в Kafka и удаляет (или помечает как отправленные) обработанные строки.

31. **Tenant-aware Routing**: В API Gateway извлекайте `tenant_id` из JWT/subdomain и роутите запрос к нужной БД или региону.

32. Реализуй **RBAC + ABAC**: `RBAC`: `role=admin` → all operations, `role=user` → own data only. `ABAC`: `order.owner_id == user.id` OR `user.hasPermission("orders:view:all")`. Policy engine (OPA/Rego) для сложных правил.

33. **Data Residency**: Храните данные EU-тенантов в EU-регионе, US-тенантов — в US. Реализуйте через geo-routing и separate deployments.

34. Реализуй **Data Encryption**: encryption at rest (PostgreSQL TDE, disk encryption), encryption in transit (TLS 1.3), field-level encryption (PII: `encrypt(credit_card)` в application layer, key in HSM/Vault). Покажи defense in depth.

35. **Saga Pattern (Распределенная транзакция)**: Пользователь покупает товар. Участвуют `OrderService` (создает заказ) и `BillingService` (списывает деньги). Напиши Сагу (через хореографию событий). Если `BillingService` отвечает "Денег нет", он шлет событие `PaymentFailed`. `OrderService` ловит его и запускает *компенсирующую транзакцию* — меняет статус заказа на "Отменен".

36. **Saga (Choreography) для распределённой транзакции**. Сервис заказов создаёт заказ, публикует событие. Сервис резервирования товара слушает событие, резервирует, публикует своё событие. Если резервирование не удалось, сервис заказов компенсирует, отменяя заказ.

37. **Audit Logging**: Логируйте все изменения критичных данных (кто, когда, что изменил, старое/новое значение) в append-only таблицу или Kafka topic.

38. Реализуй **Secret Management**: нет secrets in code/env. `HashiCorp Vault` / `AWS Secrets Manager` / `Kubernetes External Secrets`. Application requests secret at startup, caches in memory, rotates automatically. Audit: who accessed what secret when.

39. **Soft Delete**: Не удаляйте данные физически, помечайте как `deleted_at`. Это нужно для audit и восстановления.

40. Реализуй **Audit Logging**: immutable log of all sensitive operations. `who` (user/service), `what` (operation), `when` (timestamp), `on_whom` (target), `result` (success/failure), `before`/`after` (for changes). Append-only, signed, replicated. Retention: 7 years.

41. **PII Encryption**: Шифруйте персональные данные (email, phone) at rest через application-level encryption (например, `pgcrypto` или HashiCorp Vault).

42. Реализуй **GDPR/CCPA Compliance**: `right to access` — export all user data. `right to erasure` — delete/anonymize user data across all services. `data portability` — machine-readable export. `consent management` — track what user consented to, when, revoke.

43. **Паттерн Idempotency Key (Ключ идемпотентности)**: Реализуйте middleware на уровне API-шлюза. При получении POST-запроса на создание платежа шлюз проверяет HTTP-заголовок `Idempotency-Key`.
    * Если ключ новый — шлюз выполняет обработку, сохраняет результат (статус-код и тело ответа) в Redis по этому ключу с TTL 24 часа и возвращает ответ клиенту.
    * Если ключ уже существует в Redis — шлюз мгновенно возвращает закэшированный ответ, не запуская повторное списание.

44. **Secrets Management**: Используйте HashiCorp Vault или AWS Secrets Manager для хранения DB credentials, API keys. Никогда не храните секреты в коде или env vars в plain text.

45. Реализуй **Input Validation Defense**: `whitelist` approach (accept known-good), not `blacklist` (reject known-bad). Validate at edge (API Gateway), validate at service, validate at database (constraints). Sanitize: HTML escape, SQL parameterization, path traversal prevention.

46. **Inbox Pattern (Дедупликация)**: В продолжение паттерна Outbox (из прошлых блоков). Консьюмер ловит события из Kafka. Вдруг Kafka прислала одно и то же событие дважды. Реализуй таблицу `inbox_events` (или ключи в Redis). Прежде чем начать работу, проверяй, есть ли ID события в Inbox. Если есть — скипай. Записывай обработанный ID в одной транзакции с бизнес-результатом.

47. **API Gateway на Go**. Напишите обратный прокси, который маршрутизирует запросы к разным микросервисам по префиксам (`/users`, `/orders`). Добавьте агрегацию ответов: один endpoint собирает данные из двух сервисов и возвращает клиенту.

48. **RBAC (Role-Based Access Control)**: Реализуйте систему ролей (`admin`, `manager`, `user`) с permissions на уровне ресурсов (`orders:read`, `orders:write`).

49. Реализуй **Rate Limiting + DDoS Protection**: per-IP (1000 req/min), per-user (100 req/min), per-endpoint (`/login` — 5 req/min). CloudFlare/AWS Shield for L3/L4. Application-level for L7. Challenge (CAPTCHA) for suspicious patterns.

---

50. Реализуй **CI/CD Pipeline**: GitHub Actions/GitLab CI. Stages: `lint` (`golangci-lint`), `test` (`go test -race -cover`), `build` (`go build`, Docker build), `scan` (Trivy/Snyk for vulnerabilities), `deploy-staging` (auto), `deploy-production` (manual approval). Gates: coverage > 80%, no critical CVEs.

51. **ABAC (Attribute-Based Access Control)**: Более гибкая модель: "пользователь может редактировать заказ, если он его владелец И заказ в статусе draft".

52. Реализуй **GitOps (ArgoCD/Flux)**: Git repo = single source of truth for Kubernetes manifests. ArgoCD watches repo, syncs cluster. `Application` CRD defines sync policy (auto/manual), prune (delete resources not in git), self-heal. Rollback = `git revert` + sync.

53. **OAuth2/OIDC Provider**: Реализуйте собственный Identity Provider или интегрируйтесь с Keycloak/Auth0 для SSO.

54. **Idempotency Key (Идемпотентный API)**: Спроектируй HTTP-эндпоинт `POST /charge`. Клиент (мобилка) может случайно отправить запрос дважды из-за лагов сети. Требуй заголовок `Idempotency-Key`. Кэшируй результат первого успешного выполнения по этому ключу. При дубле — просто отдавай закешированный HTTP-ответ 200 OK (без повторного списания!).

55. Реализуй **Blue-Green Deployment**: two identical environments. Blue = current, Green = new. Test green, switch traffic (DNS/load balancer), blue stays for instant rollback. Zero downtime, but double resources.

56. **Compliance (GDPR, HIPAA, PCI DSS)**: Реализуйте "right to be forgotten" (удаление всех данных пользователя), data retention policies, encryption in transit and at rest.

57. **Паттерн Saga (Оркестрация)**: Реализуйте распределенную транзакцию покупки товара. Микросервис `OrderService` выступает оркестратором. Он поочередно отправляет gRPC-запросы в `PaymentService` (списание денег) и `InventoryService` (бронирование товара на складе). Если на этапе бронирования товара произошел сбой, оркестратор должен запустить компенсирующую транзакцию: отправить gRPC-запрос в `PaymentService` для возврата списанных денежных средств.

58. **Case Study: Twitter-clone (High Read, Medium Write):**
    * Timeline generation: fan-out on write (для обычных пользователей) vs fan-out on read (для знаменитостей).
    * Timeline storage: Redis sorted sets для быстрого получения последних tweets.
    * Media storage: S3 + CDN для изображений/видео.
    * Search: Elasticsearch для full-text search по tweets.
    * Real-time notifications: WebSocket + Redis Pub/Sub.

59. Реализуй **Feature Flags**: `LaunchDarkly`/`Unleash`/`custom`. `if feature.IsEnabled("new-checkout", userID) { newCheckout() } else { oldCheckout() }`. Gradual rollout: 1% users, 10%, 100%. Kill switch: disable feature in 1 second without deployment.

60. **Case Study: Uber-like (High Write, Geo-spatial):**
    * Location tracking: NATS/Redis для real-time updates местоположения водителей (100k updates/sec).
    * Matching algorithm: geo-spatial queries через PostGIS или Redis GEO.
    * Surge pricing: Kafka Streams для real-time подсчёта demand/supply ratio.
    * Trip lifecycle: Saga pattern через events (DriverAssigned → TripStarted → TripCompleted → PaymentProcessed).

61. Реализуй **Observability-Driven Deployment**: deploy → monitor SLO for 30 min → auto-promote or rollback. Metrics: error rate, latency p95, business metrics (orders/min). If any metric degrades → automatic rollback to previous version.

62. **Event Sourcing (База)**: Вместо таблицы `accounts` (где хранится текущий баланс), создай таблицу `account_events` (`id, account_id, type, amount, timestamp`). Типы: `DEPOSITED`, `WITHDRAWN`. Напиши функцию, которая берет все события аккаунта и последовательно применяет их (reduce/fold), чтобы вычислить текущий баланс "на лету" (или собрать проекцию в памяти).

63. Реализуй **Infrastructure as Code (Terraform/Pulumi)**: PostgreSQL cluster, Redis cluster, Kubernetes cluster, load balancer, DNS, TLS certificates. Version controlled, code-reviewed, tested (terratest). Drift detection: `terraform plan` shows differences.

64. **Case Study: E-commerce (Complex Business Logic):**
    * Inventory management: distributed locks через Redis для предотвращения overselling.
    * Pricing engine: правила скидок, промокоды, dynamic pricing.
    * Order processing: Saga с компенсирующими действиями.
    * Payment gateway integration: idempotency, webhook handling, reconciliation.

65. **Case Study: Fintech/Banking (ACID, Compliance):**
    * Double-entry bookkeeping: каждая транзакция — это debit и credit записи.
    * Fraud detection: real-time scoring через ML model ( TensorFlow Serving).
    * Audit trail: immutable log всех операций.
    * Regulatory reporting: batch jobs для генерации отчётов.

66. Реализуй **Chaos Engineering**: `LitmusChaos`/`ChaosMesh`. Kill random pod: service should auto-heal (Kubernetes restart), traffic should reroute (no 500s). Network partition: split-brain detection, quorum requirements. Latency injection: circuit breaker should open.

67. **Case Study: Video Streaming (High Bandwidth, CDN):**
    * Video transcoding: background jobs через Kafka + FFmpeg workers.
    * Adaptive bitrate streaming: HLS/DASH manifest generation.
    * CDN integration: CloudFront/Cloudflare для delivery.
    * Recommendation engine: collaborative filtering через Elasticsearch.

68. **Защита от перегрузок (Load Shedding)**: При резком всплеске трафика сервер может упасть из-за нехватки памяти или процессора. Напишите HTTP-middleware, которое отслеживает текущую нагрузку: если глубина очереди активных запросов сервера превышает 500 штук или загрузка процессора приближается к критической, middleware должно мгновенно возвращать статус `503 Service Unavailable`, сбрасывая избыточную нагрузку и защищая систему от падения.

69. Реализуй **Disaster Recovery**: RPO (Recovery Point Objective) = 5 min, RTO (Recovery Time Objective) = 15 min. Multi-AZ: synchronous replication (RPO=0). Multi-region: asynchronous replication (RPO=5min). Automated failover: Patroni/HAProxy for PostgreSQL. Regular DR drills.

70. **API Gateway / BFF (Backend For Frontend)**: У тебя 3 микросервиса (gRPC). Фронтенду для страницы профиля нужны данные из всех трех. Напиши Go-сервис (BFF), который принимает 1 HTTP запрос от фронтенда, асинхронно (через `errgroup`) делает 3 gRPC запроса, агрегирует данные в единый JSON и возвращает клиенту.

71. **Case Study: IoT Platform (Massive Scale, Time-series):**
    * Device connectivity: MQTT broker (например, EMQX) для миллионов устройств.
    * Time-series storage: TimescaleDB или InfluxDB для метрик.
    * Rule engine: CEP (Complex Event Processing) для триггеров на основе правил.
    * Device management: OTA updates, device twins.

72. Реализуй **Cost Optimization**: right-sizing (monitor CPU/memory usage, adjust requests/limits), spot instances for batch jobs, reserved instances for baseline, auto-scaling to zero (KEDA for dev environments). FinOps: team accountability for cloud spend.

---

73. **Case Study: Collaborative Editing (CRDT, Real-time):**
    * Operational Transformation (OT) или CRDT для conflict resolution.
    * WebSocket для real-time sync между клиентами.
    * Presence awareness: кто сейчас редактирует документ.
    * Version history: snapshot'ы каждые N операций для быстрого восстановления.

74. Спроектируй **Multi-Tenant SaaS**: `shared database, shared schema` (tenant_id column, row-level security), `shared database, separate schema` (schema per tenant), `separate database` (isolation, cost). Покажи trade-offs: isolation, cost, complexity, compliance.

75. **Case Study: Booking System (High Contention):**
    * Seat reservation: optimistic locking через `version` column или distributed locks.
    * Time-limited holds: временное резервирование с TTL (Redis).
    * Waitlist: очередь на освобождённые места.
    * Overbooking strategy: статистическая модель для компенсации no-shows.

76. Реализуй **Tenant Isolation**: `tenant_id` in every table, `WHERE tenant_id = current_tenant()` in every query (RLS policy in PostgreSQL). JWT contains `tenant_id`, service extracts and enforces. Cross-tenant queries forbidden. Resource quotas per tenant.

77. **Docker Multi-stage Builds**: Оптимизируйте Dockerfile для минимального размера образа (builder stage → runtime stage с `scratch` или `distroless`).

78. **Паттерн "Душитель" (Strangler Fig)**: Представь, что у тебя есть старый монолит на Python. Напиши Go-сервис (Reverse Proxy через `httputil.ReverseProxy`), который стоит перед монолитом. Настрой роутинг: запросы на `/api/v1/users` обрабатывай в новом Go-коде, а все остальные роуты прозрачно проксируй в монолит. Так переписывают огромные легаси системы без даунтайма.

---

79. Реализуй **Plugin Architecture**: core system + plugins (shared library, gRPC service, WebAssembly module). `PluginManager` loads plugins dynamically. Sandboxing: WebAssembly (WASI) for untrusted plugins, gRPC for trusted. Version compatibility: plugin API versioning.

80. **Kubernetes Deployments**: Создайте Deployment, Service, ConfigMap, Secret манифесты для вашего Go-сервиса.

81. **Cache Stampede & Singleflight**: При резком сбросе кэша популярного товара (например, во время распродажи) тысячи параллельных запросов могут одновременно ринуться в базу данных, обрушив её. 99. **Паттерн "Переборка" (Bulkhead)**: Если внешняя интеграция (например, API отправки SMS) начинает зависать и отвечать по 10 секунд, все ваши горутины могут заблокироваться в ожидании ответа, парализовав работу остального приложения. 111. **Минимизация влияния GC в High-Load системах**: На высоконагруженных проектах сборщик мусора (Garbage Collector) может создавать задержки (Stop-The-World). Перепишите критический путь обработки входящих пакетов данных, снизив аллокации в куче (heap allocations) до нуля:
    * Замените динамическое выделение памяти под буферы слайсов на переиспользование структур с помощью `sync.Pool` [455].
    * Замените использование интерфейсов `any` (которые всегда приводят к аллокации в куче при приведении типов) на строгую типизацию.
    * Запустите бенчмарк с флагом `-benchmem` и убедитесь, что количество аллокаций памяти упало до нуля.
