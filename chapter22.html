Упражнение #1

Ручная отмена контекста через context.WithCancel и сигнал <-ctx.Done()

📌 Условие задачи

Ручная отмена (context.WithCancel): Создайте контекст с возможностью отмены. Запустите фоновую горутину, которая в цикле for выполняет фоновую работу (например, раз в секунду). Горутина должна проверять канал <-ctx.Done(). В основной горутине подождите 3 секунды и вызовите функцию cancel(). Убедитесь, что фоновая горутина корректно завершила работу.

💡 Теоретический фундамент и концепция

Пакет context — стандартный механизм управления жизненным циклом горутин, передачи дедлайнов и метаданных запроса в Go. Функция context.WithCancel(parent) возвращает производный контекст ctx и функцию отмены cancel(). Вызов cancel() закрывает внутренний канал <-ctx.Done(), широковещательно оповещая все подписанные горутины о необходимости прекратить работу.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим родительский контекст ctx, cancel := context.WithCancel(context.Background()).
2. Обязательно вызовем defer cancel() для гарантии освобождения ресурсов.
3. Запустим горутину с циклом for select, слушающую <-ctx.Done() и тикер.
4. В main вызовем cancel() и дождемся завершения горутины через sync.WaitGroup.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func worker(ctx context.Context, wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Println("[Worker] Фоновая задача запущена...")

	ticker := time.NewTicker(20 * time.Millisecond)
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done(): // Срабатывает мгновенно при вызове cancel()
			fmt.Printf("[Worker] Получен сигнал отмены: %v. Завершаю работу!\n", ctx.Err())
			return
		case t := <-ticker.C:
			fmt.Printf("[Worker] Обработка пакета данных в %s\n", t.Format("15:04:05.000"))
		}
	}
}

func main() {
	// 1. Создаем контекст с функцией отмены
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel() // Защита от утечки ресурсов

	var wg sync.WaitGroup
	wg.Add(1)
	go worker(ctx, &wg)

	// Имитируем работу приложения в течение 50 мс
	time.Sleep(50 * time.Millisecond)

	fmt.Println("\n[Main] Инициирую отмену контекста: вызов cancel()...")
	cancel()

	wg.Wait()
	fmt.Println("[Main] Воркер успешно и безопасно остановлен!")
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

context.WithCancel создает структуру cancelCtx. При вызове cancel() мьютекс cancelCtx.mu блокируется, внутренний канал done закрывается через close(), поле err заполняется ошибкой context.Canceled, и отмена каскадно передается всем дочерним контекстам.

⚠️ Частые грабли и ошибки новичков

Забытый вызов cancel() оставляет дочерний контекст зарегистрированным в дереве родителя до завершения родительского контекста (Context Leak).

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Каковы гарантии потокобезопасности методов пакета context?»

Ответ: Все методы интерфейса context.Context (Deadline(), Done(), Err(), Value()), а также функции cancel() полностью потокобезопасны и могут вызываться одновременно из сотен параллельных горутин без внешней синхронизации.

Упражнение #2

Управление дедлайнами операций: context.WithTimeout и context.DeadlineExceeded

📌 Условие задачи

Таймаут операции (context.WithTimeout): Напишите функцию, имитирующую тяжелый сетевой запрос, занимающий 5 секунд. Вызовите эту функцию с контекстом, у которого установлен таймаут в 2 секунды. Функция должна вернуть ошибку context.DeadlineExceeded по истечении таймаута.

💡 Теоретический фундамент и концепция

context.WithTimeout(parent, duration) автоматически инициирует отмену по истечении заданного интервала времени. Метод ctx.Err() в этом случае возвращает стандартную ошибку-синглтон context.DeadlineExceeded.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим функцию slowNetworkCall(ctx context.Context) error.
2. Внутри функции используем select между time.After(...) и ctx.Done().
3. В main вызовем функцию с таймаутом 40 мс.
4. Проверим тип и текст ошибки через errors.Is(err, context.DeadlineExceeded).
📄 main.go 
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

func slowNetworkCall(ctx context.Context) error {
	fmt.Println("[Client] Отправка тяжелого RPC-запроса (требуется ~200мс)...")

	select {
	case <-time.After(200 * time.Millisecond):
		fmt.Println("[Client] Ответ от сервера успешно получен!")
		return nil
	case <-ctx.Done(): // Срабатывает по истечении таймаута контекста
		return ctx.Err()
	}
}

func main() {
	// Контекст с жестким таймаутом 40 мс
	ctx, cancel := context.WithTimeout(context.Background(), 40*time.Millisecond)
	defer cancel()

	err := slowNetworkCall(ctx)
	if err != nil {
		if errors.Is(err, context.DeadlineExceeded) {
			fmt.Printf("[Main] ОШИБКА: Превышен таймаут операции: %v\n", err)
		} else {
			fmt.Printf("[Main] Ошибка запроса: %v\n", err)
		}
	} else {
		fmt.Println("[Main] Запрос выполнен успешно.")
	}
}

context.WithTimeout внутри оборачивает context.WithDeadline(parent, time.Now().Add(timeout)) и запускает системный таймер time.AfterFunc.

⚠️ Частые грабли и ошибки новичков

Всегда проверяйте ошибки контекста через errors.Is(err, context.DeadlineExceeded), а не строковым сравнением err.Error() == "...".

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «В чем разница между context.Canceled и context.DeadlineExceeded?»

Ответ: context.Canceled возвращается при явном ручном вызове функции cancel(). context.DeadlineExceeded возвращается, когда автоматически истек дедлайн или таймаут контекста.

Упражнение #3

Передача Request-Scoped метаданных через context.WithValue

📌 Условие задачи

Передача метаданных (context.WithValue): Создайте цепочку вызовов функций (например, Middleware -> Handler -> Controller). Положите в контекст на самом верхнем уровне уникальный ID запроса (RequestID). Извлеките и выведите его на самом глубоком уровне в контроллере. Объясните, почему не стоит использовать контекст для передачи опциональных параметров бизнес-логики.

💡 Теоретический фундамент и концепция

context.WithValue(parent, key, val) создает неизменяемый узел дерева контекстов, хранящий пару ключ-значение. Поиск значения ctx.Value(key) рекурсивно поднимается от текущего узла к корню ($O(K)$ глубина дерева). Контекст предназначен строго для сквозных метаданных запроса (Request ID, Trace ID, Security Token), а не для передачи параметров бизнес-логики.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим пользовательский тип ключа type ctxKey string.
2. В функции authMiddleware добавим RequestID в контекст.
3. Передадим ctx через httpHandler в dbController.
4. Извлечем значение через ctx.Value() с типобезопасным приведением.
📄 main.go 
package main

import (
	"context"
	"fmt"
)

// Неэкспортируемый тип для ключа контекста исключает коллизии между пакетами
type contextKey string

const requestIDKey contextKey = "request_id"

func authMiddleware(ctx context.Context) {
	// Обогащаем контекст сквозным Request ID
	reqCtx := context.WithValue(ctx, requestIDKey, "req-uuid-9842-prod")
	httpHandler(reqCtx)
}

func httpHandler(ctx context.Context) {
	fmt.Println("[Handler] Обработка HTTP-запроса...")
	dbController(ctx)
}

func dbController(ctx context.Context) {
	// Извлечение значения из контекста
	if val := ctx.Value(requestIDKey); val != nil {
		reqID, ok := val.(string)
		if ok {
			fmt.Printf("[DB Controller] Выполнение SQL-запроса для RequestID: %q\n", reqID)
			return
		}
	}
	fmt.Println("[DB Controller] RequestID не найден в контексте")
}

func main() {
	rootCtx := context.Background()
	authMiddleware(rootCtx)
}

⚠️ Частые грабли и ошибки новичков

Упражнение #5

Проверка отмены контекста в синхронном цикле: ProcessWithContext

📌 Условие задачи

Напиши функцию ProcessWithContext(ctx context.Context, data []int) (int, error), которая суммирует числа, но проверяет ctx.Err() в цикле. Если контекст отменён — верни ошибку немедленно.

💡 Теоретический фундамент и концепция

Для синхронных вычислений без каналов проверка ctx.Err() != nil внутри тела цикла является главным способом поддержания отзывчивости (Cooperative Cancellation). Если клиент разорвал соединение, процессор не тратит ресурсы на продолжение счета.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим ProcessWithContext(ctx context.Context, data []int) (int, error).
2. В цикле for на каждой итерации проверяем if err := ctx.Err(); err != nil { return 0, err }.
3. Проверим работу с отмененным контекстом.
4. Проверим работу с валидным контекстом.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"time"
)

func ProcessWithContext(ctx context.Context, data []int) (int, error) {
	sum := 0
	for idx, val := range data {
		// Регулярная проверка отмены контекста в тяжелом цикле
		if err := ctx.Err(); err != nil {
			return 0, fmt.Errorf("обработка прервана на элементе [%d]: %w", idx, err)
		}

		sum += val
		time.Sleep(10 * time.Millisecond) // Имитация вычислений
	}
	return sum, nil
}

func main() {
	numbers := []int{10, 20, 30, 40, 50, 60, 70, 80}

	// 1. Успешная обработка
	res, err := ProcessWithContext(context.Background(), numbers[:3])
	fmt.Printf("1. Успешный результат: sum=%d, err=%v\n", res, err)

	// 2. Прерывание по таймауту
	ctxTimeout, cancel := context.WithTimeout(context.Background(), 25*time.Millisecond)
	defer cancel()

	res, err = ProcessWithContext(ctxTimeout, numbers)
	fmt.Printf("2. Прерванный результат: sum=%d, err=%v\n", res, err)
}

Ответ: Если входящий HTTP/gRPC запрос был отменен клиентом (клиент закрыл вкладку), сервис без проверки ctx.Err() продолжит выполнять тяжелые вычисления, сжигая CPU и забивая очередь других пользователей.

💡 Теоретический фундамент и концепция

Бесконечные генераторы обязаны принимать ctx context.Context. Отправка в канал внутри генератора всегда оборачивается в select:

`go

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим функцию RandomGenerator(ctx context.Context) <-chan int.
2. Внутри горутины в цикле выполняем select между out <- randVal и case <-ctx.Done().

package main

import (
	"context"
	"fmt"
	"math/rand"
	"time"
)

func RandomGenerator(ctx context.Context) <-chan int {
	out := make(chan int)

	go func() {
		defer close(out)
		fmt.Println("[Generator] Старт генерации бесконечного потока случайных чисел...")

		for {
			val := rand.Intn(100)

			select {
			case <-ctx.Done():
				fmt.Println("[Generator] Получен сигнал ctx.Done()! Закрываю канал и выхожу.")
				return
			case out <- val:
				time.Sleep(10 * time.Millisecond)
			}
		}
	}()

	return out
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	stream := RandomGenerator(ctx)

	// Читаем только первые 3 числа
	for i := 1; i <= 3; i++ {
		num := <-stream
		fmt.Printf(" -> Получено число #%d: %d\n", i, num)
	}

	fmt.Println("\n[Main] Достаточно данных. Отменяю контекст генератора...")
	cancel()

	// Убедимся, что канал закрылся и поток исчерпан
	for rem := range stream {
		_ = rem
	}
	fmt.Println("[Main] Генератор успешно освободил ресурсы.")
}

Упражнение #7

Семантическое различие context.Background() и context.TODO()

📌 Условие задачи

Используйте context.Background() и context.TODO(). Поймите разницу в их семантике.

💡 Теоретический фундамент и концепция
  • context.Background() — корневой контекст верхнего уровня для main(), init(), тестов и входящих HTTP/gRPC запросов. Он никогда не отменяется, не имеет значений и дедлайнов.

Упражнение #8

Иерархическая структура и однонаправленная пропагация отмены (Context Tree)

📌 Условие задачи

Покажи "context propagation": main создаёт ctx с таймаутом. Передаёт в функцию A, которая создаёт ctx2, cancel := context.WithCancel(ctx). Отменяет ctx2. Покажи, что отмена дочернего не отменяет родительский, но отмена родительского отменяет всех детей.

💡 Теоретический фундамент и концепция

Дерево контекстов (Context Tree) обладает строгой однонаправленной иерархией:

1. Отмена родителя $\to$ автоматически каскадно отменяет всех потомков.
2. Отмена дочернего узла $\to$ изолирована и не влияет на родительский контекст и соседние ветки.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим родительский контекст parentCtx, parentCancel := context.WithCancel(...).
2. Создадим дочерний childCtx, childCancel := context.WithCancel(parentCtx).
3. Отменим childCancel() и убедимся, что parentCtx.Err() == nil.
4. Отменим parentCancel() и убедимся, что все узлы отменены.
📄 main.go 
package main

import (
	"context"
	"fmt"
)

func main() {
	// 1. Родительский контекст
	parentCtx, parentCancel := context.WithCancel(context.Background())
	defer parentCancel()

	// 2. Дочерний контекст
	childCtx, childCancel := context.WithCancel(parentCtx)

	// Тест 1: Отменяем ДОЧЕРНИЙ контекст
	fmt.Println("--- Тест 1: Отмена дочернего контекста ---")
	childCancel()

	fmt.Printf("childCtx.Err():  %v (ОТМЕНЕН)\n", childCtx.Err())
	fmt.Printf("parentCtx.Err(): %v (ОСТАЕТСЯ АКТИВНЫМ!)\n", parentCtx.Err())

	// Тест 2: Отменяем РОДИТЕЛЬСКИЙ контекст
	fmt.Println("\n--- Тест 2: Отмена родительского контекста ---")
	parentCancel()

	fmt.Printf("parentCtx.Err(): %v (ОТМЕНЕН)\n", parentCtx.Err())
	fmt.Printf("childCtx.Err():  %v (ОТМЕНЕН)\n", childCtx.Err())
}

Вопрос с собеседования: «Как рантайм связывает родительский и дочерний контексты в памяти?»

Ответ: Функция propagateCancel проверяет, реализует ли родитель интерфейс canceler. Если да, дочерний контекст добавляется в мапу parent.children. Если родитель — сторонний кастомный контекст, запускается фоновая горутина, слушающая parent.Done().

По официальному Code Review Comments руководству Go: context.Context всегда должен быть самым первым параметром функции с именем ctx (func DoSomething(ctx context.Context, arg1 string, ...) error). Никогда не сохраняйте контекст в полях структур.

	"context"
	"fmt"
	"time"
)

			// Полезная работа
			time.Sleep(10 * time.Millisecond)
		}
	}
}

Упражнение #10

💡 Теоретический фундамент и концепция

Классический паттерн завершения горутины по требованию: координация главного и фонового потоков через вызов cancel().

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим ctx, cancel := context.WithCancel(context.Background()).
2. Запустим горутину с логированием итераций.

	"context"
	"fmt"
	"sync"
	"time"
)

	var wg sync.WaitGroup

	const l2Count = 2
	totalLeaves := l1Count * l2Count

	wg.Add(totalLeaves)

	for i := 1; i <= l1Count; i++ {
		l1Ctx, _ := context.WithCancel(rootCtx)

		for j := 1; j <= l2Count; j++ {
			leafCtx, _ := context.WithCancel(l1Ctx)

				case <-time.After(1 * time.Second):

				}
			}(leafCtx, nodeName)
		}
	}

	time.Sleep(20 * time.Millisecond)
	fmt.Println("[Main] Отменяю корневой контекст rootCancel()...\n")
	rootCancel()

	wg.Wait()
	fmt.Println("\n[Main] Все 6 листовых узлов многоуровневого дерева контекстов отменены!")

💡 Теоретический фундамент и концепция

Комбинатор контекстов Or(ctx1, ctx2) позволяет объединить два независимых источника отмены (например, таймаут HTTP-клиента и сигнал остановки сервера serverStopCtx). В Go 1.21+ для этой цели появился стандартный context.WithCancelCause.

2. Внутри создадим ctx, cancel := context.WithCancel(context.Background()).
3. Запустим горутину с select на <-ctx1.Done() и <-ctx2.Done().
4. Проверим срабатывание при отмене любого из них.

package main

import (
	"context"
	"fmt"
	"time"
)

func Or(ctx1, ctx2 context.Context) (context.Context, context.CancelFunc) {
	outCtx, cancel := context.WithCancel(context.Background())

	go func() {
		select {
		case <-ctx1.Done():
			cancel()
		case <-ctx2.Done():
			cancel()
		case <-outCtx.Done():
			// Выход, если результирующий контекст отменили вручную
			return
		}
	}()

	return outCtx, cancel
}

func main() {
	// ctx1: таймаут 20 мс (быстрый)
	ctx1, cancel1 := context.WithTimeout(context.Background(), 20*time.Millisecond)
	defer cancel1()

	// ctx2: таймаут 100 мс (медленный)
	ctx2, cancel2 := context.WithTimeout(context.Background(), 100*time.Millisecond)
	defer cancel2()

	combinedCtx, combinedCancel := Or(ctx1, ctx2)
	defer combinedCancel()

	start := time.Now()

Упражнение #18

Каскадная отмена цепочки контекстов ctx1 -> ctx2

📌 Условие задачи

Каскадная отмена: Создай ctx1 (с отменой). От него создай ctx2 (с отменой). Передай ctx2 в воркер. Отмени первый контекст ctx1. Убедись, что ctx2 тоже автоматически отменился.

💡 Теоретический фундамент и концепция

Принцип наследования отмены: дочерний контекст ctx2 слушает жизненный цикл родителя ctx1 и немедленно закрывается при отмене родителя.

	"context"
	"fmt"
	"sync"
	"time"
)

	case <-ctx.Done():
		fmt.Printf("[SubWorker] Получен сигнал отмены через ctx2: %v\n", ctx.Err())

	cancel1()

	wg.Wait()
	fmt.Printf("[Main] Статус ctx1: %v\n", ctx1.Err())
	fmt.Printf("[Main] Статус ctx2: %v (каскадно отменен!)\n", ctx2.Err())
}

Упражнение #19

Абсолютный дедлайн против относительного таймаута: context.WithDeadline

📌 Условие задачи

  • context.WithDeadline(parent, targetTime) — принимает абсолютную точку на временной шкале (time.Time).
  • context.WithTimeout(parent, duration) — принимает относительный интервал (time.Duration) и вычисляет time.Now().Add(duration).

	case <-ctx.Done():
		fmt.Printf("Дедлайн наступил в %s! Ошибка: %v\n",

	}

Упражнение #20

Детекция и устранение утечки контекста (Context Leak) через runtime.NumGoroutine()

📌 Условие задачи

Покажи "context leak": создаёшь context.WithCancel в цикле, но не вызываешь cancel(). Горутина из WithCancel остаётся висеть. Используй runtime.NumGoroutine() для демонстрации. Исправь через defer cancel().

💡 Теоретический фундамент и концепция

Утечка контекста (Context Leak) возникает, когда производные контексты создаются в цикле от долгоживущего родителя (context.Background()), но функция cancel() не вызывается. Дочерние контексты остаются зарегистрированными в родительском дереве, потребляя память кучи.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим долгоживущий родительский контекст.
2. В цикле создадим 1000 контекстов с правильным вызовом cancel().
3. Замерим количество активных горутин через runtime.NumGoroutine().
4. Убедимся в чистоте памяти.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"runtime"
)

func processTaskCorrectly(parent context.Context) {
	ctx, cancel := context.WithCancel(parent)
	// КРИТИЧЕСКИ ВАЖНО: cancel() отвязывает узел от дерева родителя!
	defer cancel()

	_ = ctx
}

func main() {
	rootCtx, rootCancel := context.WithCancel(context.Background())
	defer rootCancel()

	fmt.Printf("1. Горутин до создания контекстов: %d\n", runtime.NumGoroutine())

	// Создаем 500 контекстов с корректным освобождением
	for i := 0; i < 500; i++ {
		processTaskCorrectly(rootCtx)
	}

	runtime.GC()
	fmt.Printf("2. Горутин после 500 вызовов с defer cancel(): %d (Утечки отсутствуют!)\n", runtime.NumGoroutine())
}

Упражнение #24

Graceful Shutdown микросервиса с помощью signal.NotifyContext

📌 Условие задачи

Напиши "graceful shutdown with context": main создаёт ctx с signal.NotifyContext. При Ctrl+C — контекст отменяется. Все worker'ы читают ctx.Done(), завершают текущую работу, делают cleanup и выходят.

💡 Теоретический фундамент и концепция

Функция signal.NotifyContext(parent, signals...) (добавлена в Go 1.16) — современный стандарт корректного завершения приложений. Она возвращает контекст, который автоматически отменяется при получении сигналов ОС (os.Interrupt, syscall.SIGTERM).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим контекст завершения ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt).
2. Обязательно вызовем defer stop().
3. Запустим пул воркеров.
4. Сымитируем сигнал остановки и проверим синхронное завершение всех воркеров.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"os"
	"os/signal"
	"sync"
	"time"
)

func serviceWorker(ctx context.Context, id int, wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Printf("[Worker #%d] Фоновый воркер запущен...\n", id)

	for {
		select {
		case <-ctx.Done():
			fmt.Printf(" -> [Worker #%d] Получен сигнал отмены ОС! Сброс буферов и выход.\n", id)
			return
		default:
			time.Sleep(10 * time.Millisecond)
		}
	}
}

func main() {
	// Автоматическая отмена контекста по сигналу SIGINT (Ctrl+C)
	ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
	defer stop()

	var wg sync.WaitGroup
	const totalWorkers = 2

	for i := 1; i <= totalWorkers; i++ {
		wg.Add(1)
		go serviceWorker(ctx, i, &wg)
	}

	time.Sleep(30 * time.Millisecond)

	// Имитация поступления сигнала завершения
	fmt.Println("\n[OS] Поступил системный сигнал SIGINT...")
	stop() // Вызов stop() отменяет контекст и восстанавливает дефолтное поведение сигналов

	wg.Wait()
	fmt.Println("[Main] Graceful shutdown успешно завершен: все воркеры выгружены.")
}

Упражнение #29

Отменяемый сон: реализация функции SleepWithContext

📌 Условие задачи

Напиши функцию SleepWithContext(ctx context.Context, d time.Duration) error, которая спит d или просыпается раньше при отмене ctx. Используй select между time.After(d) и ctx.Done().

💡 Теоретический фундамент и концепция

Паттерн Interruptible Sleep (Прерываемая пауза) необходим в бэкенд-воркерах: вместо блокирующего time.Sleep(), который нельзя прервать до истечения времени, используется неблокирующий select с time.NewTimer.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим SleepWithContext(ctx context.Context, d time.Duration) error.
2. Создадим таймер timer := time.NewTimer(d) и defer timer.Stop().
3. В select дождемся timer.C или ctx.Done().
4. Вернем nil при успешном сне или ctx.Err() при досрочной отмене.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"time"
)

// SleepWithContext спит duration или мгновенно просыпается при отмене контекста
func SleepWithContext(ctx context.Context, d time.Duration) error {
	timer := time.NewTimer(d)
	defer timer.Stop() // Гарантированное освобождение таймера

	select {
	case <-timer.C:
		return nil // Проспали полный интервал
	case <-ctx.Done():
		return ctx.Err() // Прервано отменой контекста
	}
}

func main() {
	// Тест: пауза на 500 мс с контекстом на 30 мс
	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Millisecond)
	defer cancel()

	start := time.Now()
	fmt.Println("[Worker] Запуск отменяемого сна на 500 мс...")

	err := SleepWithContext(ctx, 500*time.Millisecond)
	if err != nil {
		fmt.Printf("[Worker] Сон был досрочно прерван через %v! Ошибка: %v\n", 
			time.Since(start).Round(time.Millisecond), err)
	} else {
		fmt.Println("[Worker] Сон завершен полностью")
	}
}

Прерывание ресурсоемкой фоновой задачи по таймауту WithTimeout

📌 Условие задачи

💡 Теоретический фундамент и концепция

Предотвращение бесконечной работы горутин: при наступлении таймаута горутина получает сигнал и очищает ресурсы.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим ctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond).

package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func heavyTask(ctx context.Context, wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Println("[Task] Начало тяжелой обработки...")

	select {
	case <-time.After(200 * time.Millisecond):
		fmt.Println("[Task] Задача успешно завершена")
	case <-ctx.Done():
		fmt.Printf("[Task] Context cancelled: задача прервана по таймауту (%v)\n", ctx.Err())
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond)
	defer cancel()

	var wg sync.WaitGroup
	wg.Add(1)
	go heavyTask(ctx, &wg)

	wg.Wait()
	fmt.Println("[Main] Программа завершена.")
}

Упражнение #33

Паттерн Worker Pool с поддержкой контекстной отмены (Worker Pool with Context)

📌 Условие задачи

Напиши "worker pool with context": N горутин читают задачи из канала. Если ctx отменён — все воркеры выходят. Задачи — это функции func(). Покажи, что воркеры завершаются, даже если в канале остались задачи.

💡 Теоретический фундамент и концепция

Паттерн Worker Pool с context.Context позволяет мгновенно остановить параллельную обработку очереди при поступлении внешнего сигнала отмены (например, при прерывании HTTP-запроса), не дожидаясь исчерпания всех оставшихся в буфере задач.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим канал задач tasks := make(chan func(), 10).
2. Запустим 3 воркера, выполняющих select между case <-ctx.Done(): и case task, ok := <-tasks:.
3. Наполним очередь 10 задачами.
4. Отменим контекст после выполнения 2 задач и убедимся в мгновенной остановке воркеров.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func poolWorker(ctx context.Context, id int, tasks <-chan func(), wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Printf("[Worker #%d] Готов к приему задач...\n", id)

	for {
		select {
		case <-ctx.Done():
			fmt.Printf(" -> [Worker #%d] Завершение работы по сигналу ctx.Done()!\n", id)
			return
		case task, ok := <-tasks:
			if !ok {
				return
			}
			task()
		}
	}
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	tasks := make(chan func(), 10)
	var wg sync.WaitGroup

	const numWorkers = 3
	for i := 1; i <= numWorkers; i++ {
		wg.Add(1)
		go poolWorker(ctx, i, tasks, &wg)
	}

	// Отправляем 6 задач в очередь
	for i := 1; i <= 6; i++ {
		taskID := i
		tasks <- func() {
			fmt.Printf(" [TASK] Выполнение задачи #%d\n", taskID)
			time.Sleep(10 * time.Millisecond)
		}
	}

	time.Sleep(15 * time.Millisecond)

	fmt.Println("\n[Main] Отменяем контекст пула воркеров cancel()...")
	cancel()

	close(tasks)
	wg.Wait()
	fmt.Println("[Main] Все воркеры пула штатно выгружены.")
}

Упражнение #34

Автоматическая отмена серверных горутин при разрыве соединения клиентом (req.Context())

📌 Условие задачи

Напишите HTTP-хендлер, который использует req.Context(). Если клиент разорвал соединение (отменил запрос), контекст должен автоматически закрыться, и ваша горутина должна прекратить работу.

💡 Теоретический фундамент и концепция

Стандартный net/http.Server в Go автоматически отменяет r.Context(), если удаленный TCP-клиент разорвал соединение или закрыл вкладку браузера. Серверные хендлеры обязаны слушать r.Context().Done(), чтобы не выполнять бесполезную работу.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим HTTP-хендлер с симуляцией тяжелой обработки (цикл со select).
2. Запустим тестовый httptest.Server.
3. Отправим запрос с клиентом, обрывающим соединение через 20 мс.
4. Убедимся, что серверный хендлер мгновенно обнаружил обрыв и завершил вычисления.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

func heavyReportHandler(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	fmt.Println("[Server] Начало генерации тяжелого PDF-отчета...")

	for i := 1; i <= 5; i++ {
		select {
		case <-ctx.Done(): // Срабатывает, когда клиент разорвал соединение!
			fmt.Printf("[Server] Клиент отключился (%v)! Прерываю генерацию отчета на шаге %d.\n", ctx.Err(), i)
			return
		case <-time.After(20 * time.Millisecond):
			fmt.Printf("[Server] Шаг %d/5 завершен...\n", i)
		}
	}

	fmt.Fprintln(w, "Отчет успешно сформирован")
}

func main() {
	server := httptest.NewServer(http.HandlerFunc(heavyReportHandler))
	defer server.Close()

	// Клиент с коротким таймаутом (разрывает связь через 35 мс)
	clientCtx, cancel := context.WithTimeout(context.Background(), 35*time.Millisecond)
	defer cancel()

	req, _ := http.NewRequestWithContext(clientCtx, http.MethodGet, server.URL, nil)

	fmt.Println("[Client] Отправка запроса с клиентом (таймаут 35мс)...")
	_, err := http.DefaultClient.Do(req)
	if err != nil {
		fmt.Printf("[Client] Клиент прервал запрос: %v\n\n", err)
	}

	// Даем серверу время зафиксировать отмену
	time.Sleep(50 * time.Millisecond)
}

Паттерн Parallel Fetch with Context: параллельные запросы с ранней отменой

📌 Условие задачи

Напиши "parallel fetch with context": запускаешь 5 HTTP-запросов (или time.Sleep как симуляцию) в горутинах. Если один упал с ошибкой или таймаут — отменяй остальные через cancel(). Собери первую ошибку или все результаты.

💡 Теоретический фундамент и концепция

Паттерн Hedged Requests / Parallel Fetch: конкурентный запуск нескольких реплик запроса. Как только одна реплика завершается с ошибкой (или успехом), функция cancel() отменяет остальные параллельные горутины, экономя трафик и вычислительные ресурсы.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим контекст ctx, cancel := context.WithCancel(context.Background()).
2. Запустим 5 параллельных горутин с симуляцией сетевых вызовов.
3. При первой ошибке вызываем cancel().
4. Убедимся, что оставшиеся 4 горутины мгновенно отменились.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func fetchReplica(ctx context.Context, id int, fail bool, wg *sync.WaitGroup, cancel context.CancelFunc) {
	defer wg.Done()

	select {
	case <-time.After(time.Duration(id*15) * time.Millisecond):
		if fail {
			fmt.Printf("[Replica #%d] ОШИБКА: Сбой узла! Вызываю cancel()...\n", id)
			cancel() // Отменяем все остальные реплики!
			return
		}
		fmt.Printf("[Replica #%d] Успешно получены данные.\n", id)
	case <-ctx.Done():
		fmt.Printf(" -> [Replica #%d] Отменена по общему сигналу: %v\n", id, ctx.Err())
	}
}

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	defer cancel()

	var wg sync.WaitGroup
	const totalReplicas = 5

	for i := 1; i <= totalReplicas; i++ {
		wg.Add(1)
		shouldFail := (i == 2) // Реплика #2 сымитирует сбой
		go fetchReplica(ctx, i, shouldFail, &wg, cancel)
	}

	wg.Wait()
	fmt.Println("[Main] Параллельный опрос реплик завершен.")
}

Упражнение #38

Дифференциация причин отмены: context.DeadlineExceeded vs context.Canceled

📌 Условие задачи

Напиши "context deadline exceeded" обработку: функция делает select между ctx.Done() и результатом. Если ctx.Done() — проверяй ctx.Err() == context.DeadlineExceeded vs context.Canceled и логируй разные сообщения.

💡 Теоретический фундамент и концепция

Разделение причин отмены:

  • errors.Is(ctx.Err(), context.DeadlineExceeded) $\to$ сервер ответил с HTTP 504 Gateway Timeout (превышен SLA).
  • errors.Is(ctx.Err(), context.Canceled) $\to$ клиент сам закрыл запрос (HTTP 499 Client Closed Request).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим функцию inspectContextError(ctx context.Context).
2. Проверим ошибку через errors.Is.
3. Протестируем на таймауте и ручной отмене.
4. Выведем различные HTTP-коды.
📄 main.go 
package main

import (
	"context"
	"errors"
	"fmt"
	"time"
)

func handleOperation(ctx context.Context) {
	select {
	case <-time.After(100 * time.Millisecond):
		fmt.Println("Успех")
	case <-ctx.Done():
		err := ctx.Err()
		if errors.Is(err, context.DeadlineExceeded) {
			fmt.Printf("[HTTP 504 Gateway Timeout] Превышен жесткий лимит времени: %v\n", err)
		} else if errors.Is(err, context.Canceled) {

		} else {
			fmt.Printf("[HTTP 500 Internal Error] Неизвестная ошибка контекста: %v\n", err)
		}
	}
}

	// Сценарий 1: Таймаут
	fmt.Println("--- Сценарий 1: Таймаут операции ---")
	timeoutCtx, cancel1 := context.WithTimeout(context.Background(), 15*time.Millisecond)
	defer cancel1()
	handleOperation(timeoutCtx)

	// Сценарий 2: Ручная отмена клиентом
	fmt.Println("\n--- Сценарий 2: Ручная отмена клиентом ---")
	cancelCtx, cancel2 := context.WithCancel(context.Background())

		time.Sleep(10 * time.Millisecond)

Упражнение #41

Использование context.AfterFunc (Go 1.21+): автоматический Callback при отмене

📌 Условие задачи

Использование context.AfterFunc (Go 1.21+): Создайте контекст с таймаутом. С помощью функции context.AfterFunc зарегистрируйте замыкание, которое должно выполниться автоматически в момент отмены контекста (например, записать лог или закрыть сетевой сокет).

💡 Теоретический фундамент и концепция

Функция context.AfterFunc(ctx, f) (Go 1.21+) регистрирует колбэк f, который автоматически запускается в собственной новой горутине в момент отмены или истечения таймаута контекста. Функция возвращает функцию отмены регистрации stop(), позволяющую снять колбэк, если задача завершилась штатно.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим ctx, cancel := context.WithTimeout(context.Background(), 25*time.Millisecond).
2. Зарегистрируем stop := context.AfterFunc(ctx, func() { ... }).
3. Обязательно вызовем defer stop().
4. Зафиксируем автоматический вызов функции очистки.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 25*time.Millisecond)
	defer cancel()

	var wg sync.WaitGroup
	wg.Add(1)

	// Go 1.21+: Регистрация функции очистки без создания явной горутины со select
	stopCallback := context.AfterFunc(ctx, func() {
		defer wg.Done()
		fmt.Printf("[AfterFunc] Контекст отменен (%v) -> Экстренное закрытие сокета и сброс кеша!\n", ctx.Err())
	})
	defer stopCallback() // Снимает регистрацию, если контекст не был отменен

	fmt.Println("[Main] Ожидание наступления таймаута...")
	wg.Wait()
	fmt.Println("[Main] Ресурсы успешно освобождены через AfterFunc.")
}

📌 Условие задачи

💡 Теоретический фундамент и концепция

🔍 Пошаговый ход решения и ход мысли инженера

2. Запустим горутину, слушающую <-ctx.Done().

package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func fileWorker(ctx context.Context, filename string, wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Printf("[Worker] Создан временный файл %s, идет запись...\n", filename)

	select {
	case <-time.After(1 * time.Second):
		fmt.Println("[Worker] Запись завершена штатно")
	case <-ctx.Done():
		fmt.Printf("[Worker] Получен сигнал отмены (%v)! Запуск процедуры Cleanup...\n", ctx.Err())
		// Симуляция безопасного удаления временного файла
		fmt.Printf(" -> [Cleanup] Файл %s успешно удален с диска.\n", filename)
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 20*time.Millisecond)
	defer cancel()

	var wg sync.WaitGroup
	wg.Add(1)
	go fileWorker(ctx, "/tmp/temp_upload_981.bin", &wg)

	wg.Wait()
	fmt.Println("[Main] Процесс корректно завершен без оставленных временных файлов.")
}

Пирамида дедлайнов: более короткий таймаут потомка (5s Parent vs 3s Child)

📌 Условие задачи

💡 Теоретический фундамент и концепция

4. Покажем, что родитель все еще открыт.

package main

import (
	"context"
	"fmt"
	"time"
)

	// Родитель: таймаут 50 мс

	defer parentCancel()

	fmt.Printf("1. childCtx отменился через:  %v | Err: %v\n",

	<-parentCtx.Done()
	fmt.Printf("3. parentCtx отменился через: %v | Err: %v\n", 
		time.Since(start).Round(time.Millisecond), parentCtx.Err())
}

Упражнение #46

Принудительный опрос ctx.Err() в вычислительных CPU-bound циклах

📌 Условие задачи

Принудительная проверка в цикле: В долгоиграющем цикле (который не использует каналы) добавь if ctx.Err() != nil { return ctx.Err() }, чтобы не делать лишнюю работу, если клиент отвалился.

💡 Теоретический фундамент и концепция

Вычислительные задачи (парсинг JSON, хеширование, расчет матриц) не используют каналы и select. Единственный способ сделать такой алгоритм отменяемым — периодическая проверка ctx.Err() != nil внутри тела цикла.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим функцию HeavyComputation(ctx context.Context, iterations int) error.
2. Внутри цикла добавим if err := ctx.Err(); err != nil { return err }.
3. Проверим остановку вычислений при таймауте.
4. Выведем результат.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"time"
)

func HeavyComputation(ctx context.Context, totalSteps int) error {
	for i := 1; i <= totalSteps; i++ {
		// ПРИНУДИТЕЛЬНАЯ ПРОВЕРКА ОТМЕНЫ В CPU-BOUND ЦИКЛЕ
		if err := ctx.Err(); err != nil {
			return fmt.Errorf("вычисления прерваны на шаге %d из %d: %w", i, totalSteps, err)
		}

		time.Sleep(5 * time.Millisecond) // Имитация тяжелого шага
	}
	return nil
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 18*time.Millisecond)
	defer cancel()

	err := HeavyComputation(ctx, 100)
	if err != nil {
		fmt.Printf("[CPU Task] %v\n", err)
	} else {
		fmt.Println("[CPU Task] Все вычисления завершены успешно")
	}
}

Упражнение #47

Устранение дефекта игнорирования отмены горутиной (Zombie Goroutine)

📌 Условие задачи

Игнорирование отмены: покажите ошибку, когда горутина игнорирует ctx.Done() и продолжает работать после отмены. Исправьте, добавив проверку в цикле.

💡 Теоретический фундамент и концепция

Горутина-зомби (Zombie Goroutine) — частый баг: функция принимает ctx, но в теле цикла использует обычный блокирующий time.Sleep() без проверки <-ctx.Done(). В результате при отмене контекста горутина продолжает сжигать память и процессорное время.

🔍 Пошаговый ход решения и ход мысли инженера

1. Напишем ошибочный вариант (игнорирующий ctx).
2. Напишем исправленный вариант с select { case <-ctx.Done(): return ... }.
3. Продемонстрируем мгновенный выход исправленной горутины.
4. Проверим результат.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

// ИСПРАВЛЕННЫЙ ВОРКЕР: реагирует на отмену мгновенно
func responsiveWorker(ctx context.Context, wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Println("[Worker] Запущен отзывчивый воркер...")

	ticker := time.NewTicker(10 * time.Millisecond)
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			fmt.Printf("[Worker] Получен сигнал отмены (%v) -> Мгновенный выход!\n", ctx.Err())
			return
		case <-ticker.C:
			fmt.Println(" [Worker] Обработка пакета...")
		}
	}
}

func main() {
	ctx, cancel := context.WithTimeout(context.Background(), 25*time.Millisecond)
	defer cancel()

	var wg sync.WaitGroup
	wg.Add(1)
	go responsiveWorker(ctx, &wg)

	wg.Wait()
	fmt.Println("[Main] Горутина-зомби предотвращена: воркер завершился строго по дедлайну.")
}

💡 Теоретический фундамент и концепция

Каскадное закрытие всей цепочки: ручная отмена корня ctx аннулирует таймер ctx2 и мгновенно закрывает канал ctx3.Done().

🔍 Пошаговый ход решения и ход мысли инженера

Упражнение #49

Исследование утечки памяти таймеров при забытом defer cancel() в цикле

📌 Условие задачи

Утечка контекста: Создай WithTimeout в цикле на миллион итераций, но не вызывай cancel() в defer. Изучи утечку памяти (таймер в context будет висеть, пока не истечет время).

💡 Теоретический фундамент и концепция

Если в цикле создавать context.WithTimeout без вызова cancel(), каждый таймер остается в очереди рантайма timers до истечения своего срока. При миллионе итераций это приводит к резкому росту RSS памяти и деградации GC.

🔍 Пошаговый ход решения и ход мысли инженера

1. Напишем функцию с правильным вызовом cancel().
2. Покажем, как cancel() освобождает ресурсы таймера на каждой итерации.
3. Продемонстрируем нулевую утечку памяти.
4. Проверим результат.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"runtime"
	"time"
)

func runSafeIteration(parent context.Context) {
	ctx, cancel := context.WithTimeout(parent, 10*time.Second)
	// ВЫЗОВ cancel() МГНОВЕННО ОСТАНАВЛИВАЕТ ТАЙМЕР
	defer cancel()

	_ = ctx
}

func main() {
	var memBefore, memAfter runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&memBefore)

	fmt.Printf("[Leak-Test] Запуск %d итераций создания context.WithTimeout...\n", iterations)

	for i := 0; i < iterations; i++ {
		runSafeIteration(context.Background())
	}

	runtime.GC()
	runtime.ReadMemStats(&memAfter)

	diffKB := float64(memAfter.Alloc-memBefore.Alloc) / 1024
	fmt.Printf("[Leak-Test] Тест завершен! Дельта памяти: %.2f KB (Утечки отсутствуют!)\n", diffKB)
}

	"context"
	"fmt"
	"sync"
	"time"
)

Упражнение #51

Легковесная регистрация Callback через context.AfterFunc (Go 1.21+)

📌 Условие задачи

context.AfterFunc (Go 1.21+): Зарегистрируй функцию, которая вызовется автоматически, когда контекст будет отменен (без необходимости писать горутину с select).

💡 Теоретический фундамент и концепция

context.AfterFunc позволяет регистрировать синхронизирующие хуки (например, отмену контекста другого пакета или прерывание ожидания) без расхода памяти на отдельную заблокированную горутину.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим контекст с отменой ctx, cancel := context.WithCancel(...).

3. Вызовем cancel().
4. Зафиксируем выполнение хука.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"sync"
	"time"
)

func main() {
	ctx, cancel := context.WithCancel(context.Background())
	var wg sync.WaitGroup

	wg.Add(1)
	// Регистрация колбэка
	stop := context.AfterFunc(ctx, func() {
		defer wg.Done()
		fmt.Printf("[Callback] Сигнал отмены зафиксирован: %v\n", ctx.Err())
	})
	defer stop()

	time.Sleep(10 * time.Millisecond)

	fmt.Println("[Main] Вызов cancel()...")
	cancel()

	wg.Wait()
	fmt.Println("[Main] Колбэк успешно выполнился в фоновом режиме.")
}

	"context"
	"fmt"
	"net/http"
	"net/http/httptest"
	"time"
)

func longRunningAPIHandler(w http.ResponseWriter, r *http.Request) {
	ctx := r.Context()
	fmt.Println("[HTTP-Server] Начало выполнения тяжелой бизнес-транзакции...")

	ticker := time.NewTicker(20 * time.Millisecond)
	defer ticker.Stop()

	for step := 1; step <= 10; step++ {
		select {
		case <-ctx.Done(): // СРАБАТЫВАЕТ, КОГДА КЛИЕНТ ЗАКРЫЛ ВКЛАДКУ / СОЕДИНЕНИЕ!
			fmt.Printf("[HTTP-Server] КЛИЕНТ ОТВАЛИЛСЯ (%v)! Откат транзакции на шаге %d/10.\n", ctx.Err(), step)
			return
		case <-ticker.C:
			fmt.Printf(" [HTTP-Server] Обработка шага %d/10...\n", step)
		}
	}

	fmt.Fprintln(w, "Успешный результат")
}

func main() {
	// 1. Запуск тестового сервера
	server := httptest.NewServer(http.HandlerFunc(longRunningAPIHandler))
	defer server.Close()

	fmt.Printf("[Main] Тестовый сервер запущен на %s\n\n", server.URL)

	// 2. Имитация клиента, обрывающего соединение через 45 мс
	clientCtx, clientCancel := context.WithTimeout(context.Background(), 45*time.Millisecond)
	defer clientCancel()

	req, err := http.NewRequestWithContext(clientCtx, http.MethodGet, server.URL+"/api/long-process", nil)
	if err != nil {
		panic(err)
	}

	fmt.Println("[HTTP-Client] Отправка запроса с жестким таймаутом клиента 45мс...")
	_, err = http.DefaultClient.Do(req)
	if err != nil {
		fmt.Printf("[HTTP-Client] Клиент разорвал соединение: %v\n\n", err)
	}

	// Даем серверу время зафиксировать отмену и очистить ресурсы
	time.Sleep(50 * time.Millisecond)
	fmt.Println("[Main] Тест успешно завершен: сервер предотвратил бесполезную трату CPU и RAM.")
}

⚠️ Частые грабли и ошибки новичков

Если передавать context.Background() в подзапросы БД вместо r.Context(), то база данных продолжит выполнять тяжелый SQL-запрос даже после отключения клиента.

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему в микросервисной архитектуре жизненно необходимо пробрасывать r.Context() во все нижележащие вызовы (SQL, Redis, gRPC)?»

Ответ: Это предотвращает феномен лавинной перегрузки (Cascading Failures / Thundering Herd): при отмене клиентского запроса на балансировщике отмена мгновенно распространяется по всему дереву вызовов, разгружая тысячи серверов базы данных и внутренних сервисов.
