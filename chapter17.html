Упражнение #1

Оборачивание ошибок через fmt.Errorf и спецификатор %w

📌 Условие задачи

Используйте fmt.Errorf("failed to process user %d: %w", id, err) для оборачивания (wrap) ошибки с сохранением контекста и цепочки вызовов.

💡 Теоретический фундамент и концепция

В Go 1.13+ спецификатор %w внутри fmt.Errorf создает обернутую ошибку (Wrapped Error), реализующую скрытый интерфейс Unwrap() error. Это позволяет добавлять контекст к ошибке на каждом уровне архитектуры без потери доступа к первопричине (Root Cause).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим базовую ошибку базы данных var ErrDatabaseUnavailable = errors.New("database connection refused").
2. Напишем функцию processUser(id int) error, которая вызывает запрос и оборачивает ошибку через fmt.Errorf("failed to process user %d: %w", id, err).
3. В main вызовем функцию и проверим, что errors.Is(err, ErrDatabaseUnavailable) возвращает true.
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

var ErrDatabaseUnavailable = errors.New("database connection refused")

func queryUser(id int) error {
	// Симуляция сбоя подключения к БД
	return ErrDatabaseUnavailable
}

func processUser(id int) error {
	if err := queryUser(id); err != nil {
		return fmt.Errorf("failed to process user %d: %w", id, err)
	}
	return nil
}

func main() {
	err := processUser(42)
	if err != nil {
		fmt.Println("Полный текст ошибки:", err)
		if errors.Is(err, ErrDatabaseUnavailable) {
			fmt.Println("Первопричина: сбой подключения к базе данных")
		}
	}
}

go run main.go

# Первопричина: сбой подключения к базе данных
⚙️ Под капотом Go (Compiler, Linker & Runtime)

fmt.Errorf со спецификатором %w оборачивает ошибку в структуру fmt.wrapError, у которой есть метод Unwrap() error, возвращающий исходную ошибку err.

⚠️ Частые грабли и ошибки новичков

Использование %v или %s вместо %w просто форматирует текст ошибки в строку, безвозвратно уничтожая цепочку Unwrap(), делая невозможным вызов errors.Is и errors.As.

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Когда следует использовать %w, а когда %v при форматировании ошибок?»

Ответ: %w используют, когда вызывающий код (клиент пакета) должен иметь возможность программно проверить тип или маркер ошибки через errors.Is/errors.As. %v используют, когда вы хотите скрыть детали реализации и не делать ошибку частью публичного API пакета.

Упражнение #2

Функция деления и возврат сигнатуры (float64, error)

📌 Условие задачи

Напишите функцию деления, которая возвращает (float64, error). При делении на ноль возвращайте errors.New("division by zero").

💡 Теоретический фундамент и концепция

Идиоматичный паттерн в Go для функций, способных завершиться сбоем — возвращать пару значений (T, error), где error всегда идет последним возвращаемым значением. При успешном выполнении возвращается (result, nil).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим функцию Divide(a, b float64) (float64, error).
2. Проверим if b == 0 и вернем 0, errors.New("division by zero").
3. При b != 0 вернем результат деления a / b, nil.
4. В main протестируем успешный вызов и деление на ноль.
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

func Divide(a, b float64) (float64, error) {
	if b == 0 {
		return 0, errors.New("division by zero")
	}
	return a / b, nil
}

func main() {
	res, err := Divide(10, 2)
	if err != nil {
		fmt.Println("Ошибка:", err)
	} else {
		fmt.Printf("10 / 2 = %.2f\n", res)
	}

	_, errZero := Divide(10, 0)
	if errZero != nil {
		fmt.Println("Ошибка деления на 0:", errZero)
	}
}
📄 Терминал 
go run main.go
# Вывод:
# 10 / 2 = 5.00
# Ошибка деления на 0: division by zero
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Интерфейс error в Go — это встроенный стандартный интерфейс с единственным методом Error() string. errors.New создает экземпляр структуры errors.errorString в памяти кучи.

⚠️ Частые грабли и ошибки новичков

Никогда не используйте возвращаемое полезное значение, если err != nil. По соглашению в Go, при ошибке полезное значение считается невалидным (zero value).

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему в Go ошибки возвращаются как значения, а не через исключения (try/catch)?»

Ответ: Возврат ошибок как обычных значений делает поток управления прозрачным, локальным и предсказуемым. Разработчик обязан явно обработать или пробросить ошибку на месте возникновения, что исключает скрытые прыжки по стеку вызовов.

Упражнение #3

Кастомный тип ошибки AppError с полями Code и Message

📌 Условие задачи

Кастомная ошибка: Создай структуру AppError с полями Code int и Message string. Реализуй для неё метод Error() string. Верни её из функции.

💡 Теоретический фундамент и концепция

Любая пользовательская структура данных в Go становится ошибкой, если она реализует интерфейс error, то есть определяет метод Error() string. Это позволяет прикреплять к ошибке любые метаданные (HTTP статус-код, внутренний код ошибки, таймстемп, трассировку).

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим структуру AppError с полями Code int и Message string.
2. Реализуем метод (e *AppError) Error() string.
3. Напишем функцию validateUser(age int) error, возвращающую *AppError.
4. В main вызовем функцию и обработаем ошибку.
📄 main.go 
package main

import "fmt"

type AppError struct {
	Code    int
	Message string
}

func (e *AppError) Error() string {
	return fmt.Sprintf("[Error %d] %s", e.Code, e.Message)
}

func validateUser(age int) error {
	if age < 18 {
		return &AppError{
			Code:    403,
			Message: "пользователь должен быть совершеннолетним",
		}
	}
	return nil
}

func main() {
	err := validateUser(16)
	if err != nil {
		fmt.Println("Получена ошибка:", err.Error())
	}
}
📄 Терминал 
go run main.go
# Вывод:
# Получена ошибка: [Error 403] пользователь должен быть совершеннолетним
⚙️ Под капотом Go (Compiler, Linker & Runtime)

При возврате &AppError в интерфейс error создается iface { tab: *itab(AppError), data: *AppError }. Метод Error() вызывается через таблицу методов itab.

⚠️ Частые грабли и ошибки новичков

Критическая ловушка типизированного nil: если функция возвращает *AppError равный nil, а сигнатура возврата объявлена как error, то err != nil вернет true! Всегда возвращайте литерал nil, если ошибки нет.

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему возврат var err *AppError = nil внутри функции с возвращаемым типом error приводит к багу?»

Ответ: Интерфейс error считается nil только когда оба его внутренних поля tab (тип) и data (указатель) равны nil. Если вернуть типизированный указатель (*AppError)(nil), поле типа tab будет заполнено дескриптором *AppError, поэтому проверка if err != nil ошибочно вернет true.

Упражнение #4

Базовые ошибки: errors.New против fmt.Errorf

📌 Условие задачи

Базовые ошибки: Используй errors.New("bad input") и fmt.Errorf("user %s not found", name) для создания простых ошибок.

💡 Теоретический фундамент и концепция
  • errors.New используется для статических текстовых сообщений, не требующих форматирования.
  • fmt.Errorf используется для динамических сообщений с интерполяцией переменных (ID, имена файлов, статусы).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим функцию checkInput(input string) error со статической ошибкой errors.New.
2. Создадим функцию findUser(name string) error с динамической ошибкой fmt.Errorf.
3. В main вызовем обе функции и распечатаем результат.
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

func checkInput(input string) error {
	if input == "" {
		return errors.New("bad input: empty payload")
	}
	return nil
}

func findUser(name string) error {
	// Симулируем отсутствие пользователя
	return fmt.Errorf("user %q not found in local cache", name)
}

func main() {
	if err := checkInput(""); err != nil {
		fmt.Println("checkInput err:", err)
	}

	if err := findUser("Алексей"); err != nil {
		fmt.Println("findUser err:  ", err)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

errors.New возвращает указатель &errorString{s}. Два вызова errors.New("err") == errors.New("err") вернут false, так как сравниваются адреса в куче.

⚠️ Частые грабли и ошибки новичков

По соглашению Go, текст ошибок должен начинаться со строчной буквы и не заканчиваться точкой (кроме имен собственных и аббревиатур), чтобы при оборачивании текст сливался в читаемую фразу.

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему в Go сообщения об ошибках пишут со строчной буквы?»

Ответ: Потому что ошибки в Go часто оборачиваются в цепочки через fmt.Errorf("failed to %s: %w", op, err). Если бы каждая ошибка начиналась с заглавной буквы, цепочка выглядела бы неаккуратно: Failed to open: File not found: Permission denied.

Упражнение #5

Sentinel-ошибки и проверка через errors.Is

📌 Условие задачи

Создайте Sentinel-ошибку var ErrNotFound = errors.New("not found"). Используйте errors.Is(err, ErrNotFound) для проверки, даже если ошибка была обернута несколько раз.

💡 Теоретический фундамент и концепция

Sentinel Error (маркерная ошибка) — это предопределенная переменная на уровне пакета. errors.Is рекурсивно разворачивает цепочку ошибок через Unwrap(), проверяя, есть ли среди них искомый маркер.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим var ErrNotFound = errors.New("not found").
2. Создадим цепочку из трех функций: repoFind -> serviceGet -> handlerGet.
3. Каждая промежуточная функция оборачивает ошибку через %w.
4. В main убедимся, что errors.Is(err, ErrNotFound) находит маркер на самом верху.

package main

import (
	"errors"
	"fmt"
)

var ErrNotFound = errors.New("not found")

func repoFind(id int) error {
	return ErrNotFound
}

func serviceGet(id int) error {
	if err := repoFind(id); err != nil {
		return fmt.Errorf("service error for id %d: %w", id, err)
	}
	return nil
}

func handlerGet(id int) error {
	if err := serviceGet(id); err != nil {
		return fmt.Errorf("handler GET failed: %w", err)
	}
	return nil
}

func main() {
	err := handlerGet(100)
	if err != nil {
		fmt.Println("Цепочка ошибок:", err)
		if errors.Is(err, ErrNotFound) {
			fmt.Println("-> Результат: запись успешно опознана как ErrNotFound (HTTP 404)")
		}
	}
}

errors.Is проверяет err == target, а если не совпало — вызывает метод Is(error) bool у структуры ошибки (если он есть) или метод Unwrap() error, повторяя поиск по цепочке.

Упражнение #7

💡 Теоретический фундамент и концепция

Прямое сравнение err == ErrNotFound работает только для прямых необернутых ошибок. Как только ошибка будет обернута через %w, прямое сравнение вернет false.

Упражнение #9

Множественные типы ошибок и диспетчеризация через errors.As

📌 Условие задачи

Напишите функцию, которая возвращает несколько разных типов ошибок, и корректно обработайте их в main с помощью switch и errors.As.

💡 Теоретический фундамент и концепция

errors.As находит в цепочке ошибку, соответствующую целевому типу структуры/указателя, и копирует значение в переданный указатель. Это безопасный аналог Type Assertion для цепочек ошибок.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим кастомные типы ошибок NetworkTimeoutError и InvalidFormatError.
2. Напишем функцию fetchData(url string) error.
3. В main обработаем ошибки через switch с errors.As.
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

type NetworkTimeoutError struct {
	URL string
}

func (e *NetworkTimeoutError) Error() string {
	return fmt.Sprintf("network timeout requesting %s", e.URL)
}

type InvalidFormatError struct {
	Line int
}

func (e *InvalidFormatError) Error() string {
	return fmt.Sprintf("invalid payload format at line %d", e.Line)
}

func fetchData(mode int) error {
	switch mode {
	case 1:
		return fmt.Errorf("api gateway: %w", &NetworkTimeoutError{URL: "https://api.internal/v1"})
	case 2:
		return fmt.Errorf("parser: %w", &InvalidFormatError{Line: 42})
	default:
		return nil
	}
}

func main() {
	for _, mode := range []int{1, 2} {
		err := fetchData(mode)
		var netErr *NetworkTimeoutError
		var fmtErr *InvalidFormatError

		switch {
		case errors.As(err, &netErr):
			fmt.Printf("[RETRY] Тайм-аут сети к URL: %s\n", netErr.URL)
		case errors.As(err, &fmtErr):
			fmt.Printf("[REJECT] Ошибка формата на строке: %d\n", fmtErr.Line)
		default:
			fmt.Println("Успех или неизвестная ошибка")
		}
	}
}

errors.As проверяет типы через рефлексию reflect.TypeOf и метод As(target any) bool, присваивая указатель на найденную структуру.

Упражнение #17

Паттерн повторных попыток (Retry) с экспоненциальной задержкой

📌 Условие задачи

Реализуйте паттерн повторных попыток (Retry): если функция вернула определенную ошибку (например, "timeout"), вызовите ее снова до 3 раз с экспоненциальной задержкой.

💡 Теоретический фундамент и концепция

Паттерн Retry с экспоненциальным backoff увеличивает задержку между попытками вдвое ($T, 2T, 4T$), снижая нагрузку на восстанавливающуюся систему.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим var ErrTimeout = errors.New("timeout").
2. Реализуем Retry(attempts int, initialDelay time.Duration, fn func() error) error.
3. В цикле вызываем функцию, при ErrTimeout удваиваем задержку.
4. В main протестируем успешное восстановление на 3-й попытке.
📄 main.go 
package main

import (
	"errors"
	"fmt"
	"time"
)

var ErrTimeout = errors.New("request timeout")

func Retry(attempts int, delay time.Duration, fn func() error) error {
	var lastErr error
	for i := 1; i <= attempts; i++ {
		err := fn()
		if err == nil {
			return nil
		}
		if !errors.Is(err, ErrTimeout) {
			return err // Non-retryable error
		}
		lastErr = err
		fmt.Printf("Попытка %d не удалась (%v). Ожидание %v...\n", i, err, delay)
		time.Sleep(delay)
		delay *= 2 // Экспоненциальный рост
	}
	return fmt.Errorf("все %d попыток исчерпаны: %w", attempts, lastErr)
}

func main() {
	count := 0
	unstableCall := func() error {
		count++
		if count < 3 {
			return ErrTimeout
		}
		return nil
	}

	err := Retry(3, 10*time.Millisecond, unstableCall)
	if err != nil {
		fmt.Println("Итоговый сбой:", err)
	} else {
		fmt.Println("Успешно выполнено на попытке:", count)
	}
}

⚠️ Частые грабли и ошибки новичков

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Зачем к экспоненциальному backoff добавляют Full Jitter (рандомизацию)?»

Ответ: Без Jitter все параллельные клиенты будут повторять запросы в одни и те же синхронные моменты времени, вызывая повторные волны перегрузки (Thundering Herd Problem). Jitter размывает запросы во времени.

3. Соберем ошибки в срез и вернем errors.Join(errs...).
4. В main убедимся, что errors.Is находит любую из ошибок в объединенном результате.

package main

import (
	"errors"
	"fmt"
	"strings"
)

var (
	ErrInvalidEmail    = errors.New("некорректный email")
	ErrPasswordTooWeak = errors.New("пароль должен быть не менее 8 символов")
	ErrUnderage        = errors.New("возраст должен быть не менее 18 лет")
)

type RegistrationForm struct {
	Email    string
	Password string
	Age      int
}

func ValidateForm(f RegistrationForm) error {
	var errs []error
	if !strings.Contains(f.Email, "@") {
		errs = append(errs, ErrInvalidEmail)
	}
	if len(f.Password) < 8 {
		errs = append(errs, ErrPasswordTooWeak)
	}
	if f.Age < 18 {
		errs = append(errs, ErrUnderage)
	}
	return errors.Join(errs...)
}

func main() {
	form := RegistrationForm{
		Email:    "bad-email",
		Password: "123",
		Age:      15,
	}

	err := ValidateForm(form)
	if err != nil {
		fmt.Println("Сводная ошибка валидации:")
		fmt.Println(err)

		// errors.Is находит каждую отдельную ошибку в Join:
		fmt.Println("-> Email с ошибкой:", errors.Is(err, ErrInvalidEmail))
		fmt.Println("-> Пароль слабый: ", errors.Is(err, ErrPasswordTooWeak))
	}
}

Диспетчеризация sentinel errors через switch и errors.Is

📌 Условие задачи

Напиши функцию, возвращающую разные sentinel errors: ErrInvalidInput, ErrNotFound, ErrPermissionDenied. В вызывающем коде используй switch с errors.Is для разной логики обработки.

💡 Теоретический фундамент и концепция

Конструкция switch с предикатами errors.Is позволяет элегантно маршрутизировать обработку различных бизнес-ошибок.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим три sentinel-ошибки: ErrInvalidInput, ErrNotFound, ErrPermissionDenied.
2. Создадим функцию executeAction(code int) error.
3. В main напишем блок switch с ветками case errors.Is(err, ...).
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

var (
	ErrInvalidInput      = errors.New("invalid input")
	ErrNotFound          = errors.New("not found")
	ErrPermissionDenied  = errors.New("permission denied")
)

func executeAction(scenario int) error {
	switch scenario {
	case 1:
		return fmt.Errorf("action: %w", ErrInvalidInput)
	case 2:
		return fmt.Errorf("action: %w", ErrNotFound)
	case 3:
		return fmt.Errorf("action: %w", ErrPermissionDenied)
	default:
		return nil
	}
}

func handle(scenario int) {
	err := executeAction(scenario)
	switch {
	case errors.Is(err, ErrInvalidInput):
		fmt.Println("[400 Bad Request] Некорректные параметры запроса")
	case errors.Is(err, ErrNotFound):
		fmt.Println("[404 Not Found] Запрошенный объект не существует")
	case errors.Is(err, ErrPermissionDenied):
		fmt.Println("[403 Forbidden] Недостаточно прав для операции")
	case err != nil:
		fmt.Printf("[500 Internal Error] Непредвиденный сбой: %v\n", err)
	default:
		fmt.Println("[200 OK] Успешное выполнение")
	}
}

func main() {
	handle(1)
	handle(2)
	handle(3)
	handle(0)
}

Упражнение #27

Паттерн Guard Clauses: ранний возврат и плоская структура кода

📌 Условие задачи

Напиши функцию с guard clauses: функция выполняет 3 проверки (валидация входных данных, проверка существования файла, проверка прав). Каждая проверка — if err != nil { return ..., err }. Избегай вложенных if/else.

💡 Теоретический фундамент и концепция

Паттерн Guard Clauses (защитные условия) устраняет "лесенку" вложенных блоков if-else, делая код плоским, линейным и простым для чтения.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим функцию ProcessDocument(user string, docID string, data []byte) error.
2. Реализуем 3 последовательных проверки с немедленным выходом при ошибке.
3. В main протестируем обработку.
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

func validateInput(user, docID string) error {
	if user == "" || docID == "" {
		return errors.New("пользователь и ID документа обязательны")
	}
	return nil
}

func checkPermissions(user string) error {
	if user == "guest" {
		return errors.New("гостевым пользователям запрещено редактирование")
	}
	return nil
}

func verifyPayload(data []byte) error {
	if len(data) == 0 {
		return errors.New("документ не может быть пустым")
	}
	return nil
}

func ProcessDocument(user, docID string, data []byte) error {
	// Guard 1: Проверка входных аргументов
	if err := validateInput(user, docID); err != nil {
		return fmt.Errorf("guard validate: %w", err)
	}

	// Guard 2: Проверка прав доступа
	if err := checkPermissions(user); err != nil {
		return fmt.Errorf("guard perms: %w", err)
	}

	// Guard 3: Проверка тела документа
	if err := verifyPayload(data); err != nil {
		return fmt.Errorf("guard payload: %w", err)
	}

	// Основная логика (Happy Path):
	fmt.Printf("Документ %s успешно обработан для %s (%d байт)\n", docID, user, len(data))
	return nil
}

func main() {
	if err := ProcessDocument("guest", "doc-1", []byte("data")); err != nil {
		fmt.Println("Сбой:", err)
	}

	if err := ProcessDocument("admin", "doc-2", []byte("Hello Go")); err != nil {
		fmt.Println("Сбой:", err)
	}
}

Guard clauses минимизируют цикломатическую сложность (Cyclomatic Complexity) функции.

⚠️ Частые грабли и ошибки новичков

Не оборачивайте успешную часть в else { ... }. После блока if err != nil { return err } код продолжается на основном уровне отступа.

🏢 В продакшене BigTech и на собеседованиях

Объединение ошибок цикла валидации через errors.Join

📌 Условие задачи

💡 Теоретический фундамент и концепция

Сбор нескольких независимых ошибок в цикле с последующим вызовом errors.Join(errs...) позволяет вернуть клиенту исчерпывающий список всех некорректных строк за один запрос.

package main

import (
	"errors"
	"fmt"
	"strconv"
)

func validateRows(rows []string) error {
	var errList []error
	for i, row := range rows {
		if _, err := strconv.Atoi(row); err != nil {
			errList = append(errList, fmt.Errorf("строка %d (%q): не является числом", i+1, row))
		}
	}
	return errors.Join(errList...)
}

func main() {
	batch := []string{"100", "invalid_num", "300", "another_bad_val", "500"}

	err := validateRows(batch)
	if err != nil {
		fmt.Println("Ошибки пакетной обработки:")
		fmt.Println(err)
	}
}

Перехват критической паники через defer и recover на верхнем уровне

💡 Теоретический фундамент и концепция

panic останавливает нормальное выполнение горутины, раскручивая стек и выполняя defer-функции. Функция recover() останавливает панику и возвращает значение, переданное в panic().

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим функцию riskyOperation(), вызывающую panic("непредвиденный сбой драйвера").
2. Создадим middleware safeHandler(), содержащий defer func() { if r := recover(); r != nil { ... } }().
3. В main вызовем safeHandler() и убедимся, что процесс не упал.
📄 main.go

	"fmt"
	"runtime/debug"
)

}

func safeHandler() {
	defer func() {
		if r := recover(); r != nil {

			fmt.Printf("[STACKTRACE]:\n%s\n", string(debug.Stack()))
		}
	}()

	fmt.Println("Старт обработки запроса...")
	riskyOperation()
	fmt.Println("Запрос обработан успешно (не будет напечатано)")
}

func main() {
	safeHandler()
	fmt.Println("Сервер продолжает стабильную работу после перехвата паники!")
}

📌 Условие задачи

💡 Теоретический фундамент и концепция

Именованные возвращаемые значения (result int, err error) доступны внутри defer-замыкания. Это позволяет выполнять откат ресурсов (Rollback / Cleanup) строго в случае возникновения ошибки.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим функцию ExecuteTransaction(amount int) (txID int, err error).
2. В defer проверим if err != nil и сымитируем Rollback.
3. При err == nil выполним Commit.
4. В main протестируем успешную и неуспешную транзакцию.
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

func ExecuteTransaction(amount int) (txID int, err error) {
	fmt.Println("[TX] Начало транзакции")
	txID = 1001

	defer func() {
		if err != nil {
			fmt.Printf("[TX #%d] Ошибка (%v) -> Выполнен ROLLBACK!\n", txID, err)
		} else {
			fmt.Printf("[TX #%d] Успех -> Выполнен COMMIT!\n", txID)
		}
	}()

	if amount <= 0 {
		err = errors.New("сумма перевода должна быть больше нуля")
		return 0, err
	}

	// Успешная бизнес-логика
	return txID, nil
}

func main() {
	_, _ = ExecuteTransaction(500)
	_, _ = ExecuteTransaction(-50)
}

💡 Теоретический фундамент и концепция

Кастомные структуры ошибок, обернутые через %w, сохраняют все свои поля и методы при извлечении через errors.As.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру QuotaExceededError struct { Limit, Used int }.
2. Обернем её: fmt.Errorf("storage service: %w", &QuotaExceededError{Limit: 100, Used: 120}).

📄 main.go 
package main

import (
	"errors"
	"fmt"
)

type QuotaExceededError struct {
	Limit int
	Used  int
}

func (e *QuotaExceededError) Error() string {
	return fmt.Sprintf("превышена квота: использовано %d из %d MB", e.Used, e.Limit)
}

func uploadFile(sizeMB int) error {
	limit := 100
	if sizeMB > limit {
		return fmt.Errorf("upload handler: %w", &QuotaExceededError{Limit: limit, Used: sizeMB})
	}
	return nil
}

func main() {
	err := uploadFile(150)
	if err != nil {
		var quotaErr *QuotaExceededError
		if errors.As(err, &quotaErr) {
			fmt.Printf("Перерасход квоты на %d MB!\n", quotaErr.Used-quotaErr.Limit)
		}
	}
}

	"errors"
	"fmt"
)

	Port int
}

💡 Теоретический фундамент и концепция

При параллельном или последовательном выполнении независимых задач (очистка временных файлов, сброс кэшей) важно выполнить *все* задачи и вернуть совокупную ошибку.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим функцию cleanupOldLogs(dirs []string) error.
2. Для каждой директории выполним удаление.

4. В main вызовем очистку.
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

func cleanDir(dir string) error {
	if dir == "/var/log/protected" {
		return errors.New("permission denied")
	}
	return nil
}

func cleanupOldLogs(dirs []string) error {
	var errs []error
	for _, d := range dirs {
		if err := cleanDir(d); err != nil {
			errs = append(errs, fmt.Errorf("cleanup %s: %w", d, err))
		}
	}

	if len(errs) > 0 {
		return fmt.Errorf("cleanup failed with %d errors:\n%w", len(errs), errors.Join(errs...))
	}
	return nil
}

func main() {
	dirs := []string{"/tmp/logs", "/var/log/protected", "/opt/logs"}
	if err := cleanupOldLogs(dirs); err != nil {
		fmt.Println(err)
	}
}

Упражнение #41

Универсальный исполнитель повторов Retry с логированием

📌 Условие задачи

Напиши функцию Retry(operation func() error, attempts int, delay time.Duration) error, которая повторяет операцию при ошибке с задержкой. Логируй каждую попытку.

💡 Теоретический фундамент и концепция

Универсальная функция Retry инкапсулирует цикл повторов произвольного замыкания func() error, логируя каждую неудачную попытку в консоль.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим Retry(operation func() error, attempts int, delay time.Duration) error.
2. В цикле вызовем operation(), логируя попытку i.
3. В main сымитируем операцию, успешную со второй попытки.
📄 main.go 
package main

import (
	"errors"
	"fmt"
	"time"
)

func Retry(operation func() error, attempts int, delay time.Duration) error {
	var lastErr error
	for i := 1; i <= attempts; i++ {
		err := operation()
		if err == nil {
			fmt.Printf("[RETRY] Попытка %d/%d: УСПЕХ!\n", i, attempts)
			return nil
		}
		lastErr = err
		fmt.Printf("[RETRY] Попытка %d/%d завершилась ошибкой: %v\n", i, attempts, err)
		if i < attempts {
			time.Sleep(delay)
		}
	}
	return fmt.Errorf("все %d попыток провалены: %w", attempts, lastErr)
}

func main() {
	calls := 0
	sendWebhook := func() error {
		calls++
		if calls < 2 {
			return errors.New("503 Service Unavailable")
		}
		return nil
	}

	err := Retry(sendWebhook, 3, 5*time.Millisecond)
	if err != nil {
		fmt.Println("Итог:", err)
	}
}

# [RETRY] Попытка 2/3: УСПЕХ!
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Замыкание sendWebhook сохраняет состояние счетчика вызовов calls между итерациями цикла.

⚠️ Частые грабли и ошибки новичков

Всегда проверяйте i < attempts перед time.Sleep, чтобы не спать впустую после последней неудачной попытки.

🏢 В продакшене BigTech и на собеседованиях

Ответ: Заменить time.Sleep(delay) на select { case <-ctx.Done(): return ctx.Err(); case <-time.After(delay): }.

	"fmt"
	"time"
)

func RunWithTimeout(timeout time.Duration, op func() error) error {
	ctx, cancel := context.WithTimeout(context.Background(), timeout)
	defer cancel()

	done := make(chan error, 1)
	go func() {
		done <- op()
	}()

	select {
	case err := <-done:
		return err
	case <-ctx.Done():
		return ctx.Err() // context.DeadlineExceeded
	}
}

func main() {
	slowOperation := func() error {
		time.Sleep(100 * time.Millisecond)
		return nil
	}

	err := RunWithTimeout(20*time.Millisecond, slowOperation)
	if errors.Is(err, context.DeadlineExceeded) {
		fmt.Println("Операция отменена по таймауту:", err)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Буферизованный канал make(chan error, 1) предотвращает утечку горутины, если та завершится после истечения таймаута.

⚠️ Частые грабли и ошибки новичков

Всегда создавайте канал завершения с буфером размера 1, иначе горутина зависнет на отправке done <- op(), вызвав утечку памяти (Goroutine Leak).

🏢 В продакшене BigTech и на собеседованиях

Ответ: Если канал небуферизован, а операция завершилась после того, как select вышел по ctx.Done(), горутина навечно заблокируется на done <- err, так как читателя больше нет. Буфер емкостью 1 позволяет горутине завершиться и быть собранной сборщиком мусора.

	}()

1. Создадим 3 шага конвейера: stepAuth, stepFetchData, stepRender.
2. Реализуем HandleRequest(action string) (string, int).
3. В main протестируем успешный запрос и обработку сбоя.
📄 main.go

	"errors"
	"fmt"
)

func stepAuth(token string) error {
	if token != "secret_token" {
		return errors.New("auth: invalid bearer token")

}

func stepFetchData() error {
	return errors.New("db: connection dropped by peer")
}

func stepRender() error {
	return nil
}

func HandleRequest(token string) (body string, statusCode int) {

	execute := func() error {
		if err := stepAuth(token); err != nil {
			return fmt.Errorf("step 1 failed: %w", err)

		if err := stepFetchData(); err != nil {

			return fmt.Errorf("step 3 failed: %w", err)
		}

		fmt.Printf("[SERVER ERROR LOG] Ошибка обработки запроса: %v\n", err)
		return `{"error": "Internal Server Error"}`, 500
	}

	return `{"status": "success"}`, 200
}

Упражнение #50

Сравнение стратегий обработки: Fail-Fast против Best-Effort

📌 Условие задачи

Напиши программу с двумя стратегиями: fail fast (при первой ошибке всё падает) и best effort (продолжается с логированием ошибок, собирает все). Сравни подходы.

💡 Теоретический фундамент и концепция
  • Fail-Fast: Прерывает выполнение при первом сбое. Подходит для транзакций, платежей, миграций БД.
  • Best-Effort: Продолжает выполнение, обрабатывая все возможные элементы и собирая ошибки. Подходит для фоновых рассылок, очистки мусора, импорта каталогов.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим список задач tasks.
2. Реализуем стратегию processFailFast(tasks []int) error.
3. Реализуем стратегию processBestEffort(tasks []int) error.
4. В main сравним поведение на одних и тех же данных.
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

func runTask(id int) error {
	if id == 2 || id == 4 {
		return fmt.Errorf("task #%d failed", id)
	}
	fmt.Printf(" -> Задача #%d успешно выполнена\n", id)
	return nil
}

// Fail-Fast: остановка на первом сбое
func processFailFast(tasks []int) error {
	fmt.Println("=== Стратегия FAIL-FAST ===")
	for _, id := range tasks {
		if err := runTask(id); err != nil {
			return fmt.Errorf("fail-fast abort: %w", err)
		}
	}
	return nil
}

// Best-Effort: сбор всех ошибок и продолжение
func processBestEffort(tasks []int) error {
	fmt.Println("\n=== Стратегия BEST-EFFORT ===")
	var errs []error
	for _, id := range tasks {
		if err := runTask(id); err != nil {
			errs = append(errs, err)
		}
	}
	return errors.Join(errs...)
}

func main() {
	tasks := []int{1, 2, 3, 4, 5}

	if err := processFailFast(tasks); err != nil {
		fmt.Println("Прервано:", err)
	}

	if err := processBestEffort(tasks); err != nil {
		fmt.Println("Сводные ошибки после выполнения:")
		fmt.Println(err)
	}
}

Вопрос с собеседования: «Когда применять Fail-Fast, а когда Best-Effort в распределенных системах?»

Ответ: Fail-Fast применяют для операций с жесткой согласованностью (ACID, двухфазный коммит 2PC). Best-Effort применяют для массовых асинхронных уведомлений (Push/Email рассылки), пакетной инвалидации кэшей и репликации с eventual consistency.

Опасность игнорирования ошибок через blank identifier _

📌 Условие задачи

Игнорирование ошибок: Напишите код, в котором вы умышленно игнорируете возвращаемую ошибку с помощью _. Напишите комментарий, почему в продакшн-кодовой базе это является критически опасной практикой.

💡 Теоретический фундамент и концепция

Игнорирование возвращаемой ошибки через _ скрывает сбои оборудования, сети или формата данных. Программа продолжает работу в поврежденном состоянии, порождая "тихие" баги (Silent Failures) и коррупцию данных.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим структуру UserSession.
2. Покажем опасный пример с _ = json.Unmarshal(...).
3. Покажем безопасный пример с явной обработкой ошибки.
📄 main.go 
package main

import (
	"encoding/json"
	"fmt"
)

type UserSession struct {
	UserID  int    `json:"user_id"`
	IsAdmin bool   `json:"is_admin"`
}

func dangerousHandler(rawJSON []byte) {
	var session UserSession
	// ОПАСНО: игнорирование ошибки! Если JSON битый, session останется пустой,
	// и дальнейшая логика может некорректно авторизовать или деавторизовать пользователя.
	_ = json.Unmarshal(rawJSON, &session)

	fmt.Printf("[Опасно] UserID=%d, IsAdmin=%v (тихая ошибка)\n", session.UserID, session.IsAdmin)
}

func safeHandler(rawJSON []byte) error {
	var session UserSession
	if err := json.Unmarshal(rawJSON, &session); err != nil {
		return fmt.Errorf("парсинг сессии: %w", err)
	}
	fmt.Printf("[Безопасно] UserID=%d, IsAdmin=%v\n", session.UserID, session.IsAdmin)
	return nil
}

func main() {
	badJSON := []byte(`{"user_id": "NOT_AN_INTEGER"}`)

	dangerousHandler(badJSON)

	if err := safeHandler(badJSON); err != nil {

import (
	"encoding/json"
	"errors"
	"fmt"
)

var (
	ErrInvalidValue = errors.New("недопустимое значение")
	ErrRequired     = errors.New("обязательное поле отсутствует")
)

type Config struct {
	Host string `json:"host"`
	Port int    `json:"port"`
}

func ParseConfig(data []byte) (*Config, error) {
	var cfg Config
	if err := json.Unmarshal(data, &cfg); err != nil {
		return nil, fmt.Errorf("invalid json syntax: %w", err)
	}

	if cfg.Host == "" {
		return nil, fmt.Errorf("field %q: %w", "host", ErrRequired)
	}
	if cfg.Port < 1 || cfg.Port > 65535 {
		return nil, fmt.Errorf("field %q (value %d): %w (expected 1..65535)", "port", cfg.Port, ErrInvalidValue)
	}

	return &cfg, nil
}

func main() {
	invalidJSON := []byte(`{"host": "localhost", "port": 99999}`)

	cfg, err := ParseConfig(invalidJSON)
	if err != nil {
		fmt.Println("Ошибка конфигурации:", err)
		if errors.Is(err, ErrInvalidValue) {
			fmt.Println("-> Ошибка связана с недопустимым значением поля")
		}
	} else {
		fmt.Printf("Конфиг валиден: %+v\n", cfg)
	}
}

Упражнение #55

Сравнение инструментов: errors.Is против errors.As

📌 Условие задачи

Напиши программу, демонстрирующую разницу между errors.Is (sentinel errors) и errors.As (custom types). Приведи примеры: когда что использовать.

💡 Теоретический фундамент и концепция
  • errors.Is: проверяет равенство *конкретного значения* ошибки (sentinel errors, например ErrNotFound, io.EOF).
  • errors.As: проверяет соответствие *типу ошибки* и извлекает экземпляр структуры для чтения ее полей (например *os.PathError, *ValidationError).

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявим sentinel ошибку ErrClosed.
2. Объявим структуру ошибки HTTPError struct { Status int }.
3. Создадим две функции, возвращающие эти ошибки.
4. В main покажем работу errors.Is и errors.As.
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

// 1. Sentinel Error (Маркер): проверяется через errors.Is
var ErrConnectionClosed = errors.New("connection closed")

// 2. Custom Type Error (Структура с данными): извлекается через errors.As
type HTTPError struct {
	StatusCode int
	Detail     string
}

func (e *HTTPError) Error() string {
	return fmt.Sprintf("HTTP %d: %s", e.StatusCode, e.Detail)
}

func doNetworkCall(mode int) error {
	if mode == 1 {
		return fmt.Errorf("network layer: %w", ErrConnectionClosed)
	}
	return fmt.Errorf("api layer: %w", &HTTPError{StatusCode: 503, Detail: "Service Overloaded"})
}

func main() {
	// Пример 1: Проверка через errors.Is
	err1 := doNetworkCall(1)
	if errors.Is(err1, ErrConnectionClosed) {
		fmt.Println("[errors.Is] Обнаружено закрытие соединения (Sentinel)")
	}

	// Пример 2: Извлечение через errors.As
	err2 := doNetworkCall(2)
	var httpErr *HTTPError
	if errors.As(err2, &httpErr) {
		fmt.Printf("[errors.As] Извлечен тип HTTPError: статус=%d, детали=%s\n",
			httpErr.StatusCode, httpErr.Detail)
	}
}

# Вывод:
# [errors.Is] Обнаружено закрытие соединения (Sentinel)
# [errors.As] Извлечен тип HTTPError: статус=503, детали=Service Overloaded
⚙️ Под капотом Go (Compiler, Linker & Runtime)

errors.Is сравнивает указатели/значения, а errors.As сравнивает reflect.TypeOf и копирует указатель на объект.

⚠️ Частые грабли и ошибки новичков

Не используйте errors.Is для структур HTTPError{}, если их поля могут отличаться при каждом вызове.

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Когда выбирать Sentinel Error, а когда Custom Struct Error?»

Ответ: Sentinel Error (errors.Is) выбирают, когда важен только сам факт конкретной ошибки (нет динамических данных). Custom Struct Error (errors.As) выбирают, когда ошибка несет динамические метаданные (таймаут, имя файла, HTTP-код, параметры валидации).

Упражнение #56

Устранение антипаттерна Log-and-Return: чистая обработка ошибок

📌 Условие задачи

Напиши функцию, которая логирует ошибку и возвращает её (log-and-return). Объясни, почему это антипаттерн (дублирование логов, нарушение единственной ответственности). Перепиши: возвращай ошибку с контекстом, а логируй в одном месте — в main.

💡 Теоретический фундамент и концепция

Антипаттерн Log-and-Return заключается в том, что функция пишет ошибку в лог И возвращает её наверх. В результате при глубине стека в 5 функций одна ошибка записывается в лог 5 раз с разным текстом.

Правило Go: *Ошибку нужно либо залогировать (обработать), либо вернуть (пробросить с контекстом), но никогда не делать и то, и другое одновременно!*

🔍 Пошаговый ход решения и ход мысли инженера

1. Напишем антипаттерн с дублирующим логированием.
2. Перепишем функцию идиоматично с оборачиванием через %w.
3. Залогируем ошибку ровно один раз на самом верхнем уровне (main).
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

var ErrRecordNotFound = errors.New("record not found")

// ПЛОХО: Log-and-Return (дублирует логирование на каждом слое)
func badFindUser(id int) error {
	err := ErrRecordNotFound
	// fmt.Printf("[ERROR in badFindUser] id=%d: %v\n", id, err) // АНТИПАТТЕРН!
	return err
}

// ХОРОШО: Только добавляем контекст и возвращаем
func goodFindUser(id int) error {
	err := ErrRecordNotFound
	if err != nil {
		return fmt.Errorf("findUser(id=%d): %w", id, err)
	}
	return nil
}

func goodService(id int) error {
	if err := goodFindUser(id); err != nil {
		return fmt.Errorf("userService: %w", err)
	}
	return nil
}

func main() {
	// ЕДИНСТВЕННОЕ место логирования — точка входа/выхода
	err := goodService(42)
	if err != nil {
		fmt.Printf("[FINAL LOG] Ошибка обработки запроса: %v\n", err)
	}
}

Упражнение #57

Паттерн Graceful Degradation: логирование и продолжение работы

📌 Условие задачи

Реализуйте функцию, которая в случае ошибки заносит её в лог, но продолжает выполнение цикла (graceful degradation).

💡 Теоретический фундамент и концепция

Graceful Degradation (плавная деградация) позволяет сервису продолжать обслуживание пользователей при отказе второстепенных компонентов (например, если сервис рекомендаций недоступен, возвращаем стандартный список товаров).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим список пользователей для отправки уведомлений.
2. Если отправка одному пользователю падает, залогируем ошибку и продолжим цикл (continue).
3. В main убедимся, что остальные пользователи успешно получили уведомления.
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

func sendPush(user string) error {
	if user == "banned_user" {
		return errors.New("push token revoked")
	}
	fmt.Printf("Push успешно доставлен пользователю: %s\n", user)
	return nil
}

func BroadcastNotifications(users []string) {
	for _, user := range users {
		err := sendPush(user)
		if err != nil {
			// Graceful degradation: логируем сбой и продолжаем обработку остальных
			fmt.Printf("[WARN] Не удалось отправить push пользователю %s: %v (продолжаем)\n", user, err)
			continue
		}
	}
}

func main() {
	users := []string{"alice", "banned_user", "carol", "dave"}
	BroadcastNotifications(users)
	fmt.Println("Рассылка завершена успешно для доступных пользователей!")
}

# Push успешно доставлен пользователю: dave

⚠️ Частые грабли и ошибки новичков

Вопрос с собеседования: «Что такое Circuit Breaker и как он связан с Graceful Degradation?»

Ответ: Circuit Breaker отслеживает частоту ошибок к внешнему сервису. При превышении порога он размыкает цепь (Open State) и мгновенно возвращает fallback-ответ без выполнения реальных сетевых запросов, защищая систему от зависаний.

Упражнение #58

Конкурентная обработка ошибок: сбор из горутин через канал и sync.WaitGroup

📌 Условие задачи

Напиши программу с ошибками в горутинах: запусти 5 горутин, каждая возвращает ошибку через канал chan error. Собери все ошибки в main после sync.WaitGroup.

💡 Теоретический фундамент и концепция

Горутины не могут возвращать значения через return. Стандартный паттерн сбора ошибок от параллельных воркеров — отправка ошибок в буферизованный канал chan error с последующим закрытием канала после завершения sync.WaitGroup.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создадим буферизованный канал errCh := make(chan error, 5).
2. Запустим 5 горутин с wg.Add(1) и отправкой ошибки в канал при сбое.
3. В отдельной горутине подождем wg.Wait() и закроем errCh.
4. В main вычитаем все ошибки из канала через for err := range errCh.
📄 main.go 
package main

import (
	"errors"
	"fmt"
	"sync"
)

func worker(id int, errCh chan<- error, wg *sync.WaitGroup) {
	defer wg.Done()

	// Симулируем сбои у четных воркеров
	if id%2 == 0 {
		errCh <- fmt.Errorf("воркер #%d: сбой обработки данных", id)
		return
	}

	fmt.Printf("Воркер #%d успешно завершил задачу\n", id)
}

func main() {
	const numWorkers = 5
	errCh := make(chan error, numWorkers)
	var wg sync.WaitGroup

	for i := 1; i <= numWorkers; i++ {
		wg.Add(1)
		go worker(i, errCh, &wg)
	}

	// Закрываем канал после завершения всех воркеров
	go func() {
		wg.Wait()
		close(errCh)
	}()

	// Сбор всех возникших ошибок
	var collectedErrs []error
	for err := range errCh {
		collectedErrs = append(collectedErrs, err)
	}

	aggErr := errors.Join(collectedErrs...)
	if aggErr != nil {
		fmt.Println("\nОбнаружены ошибки при параллельном выполнении:")
		fmt.Println(aggErr)
	}
}

Буферизованный канал make(chan error, numWorkers) гарантирует, что ни один воркер не заблокируется на отправке ошибки.

⚠️ Частые грабли и ошибки новичков

Если канал небуферизован, а main начинает читать только после wg.Wait(), возникнет дедлок (все воркеры заблокируются на отправке).

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Как работает пакет golang.org/x/sync/errgroup?»

Ответ: errgroup.Group запускает задачи в горутинах через g.Go(func() error). При первой ошибке он отменяет контекст всех остальных горутин и возвращает первую возникшую ошибку из метода g.Wait().
