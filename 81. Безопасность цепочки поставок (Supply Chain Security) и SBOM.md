# Безопасность цепочки поставок (Supply Chain Security) и SBOM

В этом файле собраны уникальные упражнения по теме **"Безопасность цепочки поставок (Supply Chain Security) и SBOM"**, отсортированные по возрастанию сложности.

---

1. **Анализ реальной эксплуатируемости уязвимостей с `govulncheck`**: * Установите официальную утилиту статического анализа уязвимостей Go: `go install golang.org/x/vuln/cmd/govulncheck@latest` [656].
    * Напишите подробный комментарий, объясняющий принципиальное архитектурное отличие `govulncheck` от обычных сканеров уязвимостей (он анализирует граф вызовов AST вашего приложения и проверяет, вызывается ли уязвимая функция *реально* в вашем коде, что сводит количество ложноположительных срабатываний к минимуму) [656].
    * Запустите сканирование вашего проекта командой `govulncheck ./...` [657].

2. **Анализ уязвимостей (`govulncheck`)**: Установи официальную утилиту `go install golang.org/x/vuln/cmd/govulncheck@latest`. Найди старый проект на Go (или намеренно скачай уязвимую версию библиотеки, например, старый `golang.org/x/crypto`). Запусти `govulncheck ./...`. Изучи отчет: утилита строит граф вызовов и показывает уязвимость **только если** твой код реально вызывает уязвимую функцию!

3. **Запуск `govulncheck`.**: Установите `golang.org/x/vuln/cmd/govulncheck`, запустите на реальном Go-проекте. Проанализируйте вывод: различите `Vulnerability #1: GO-2024-...` с `Found in` (пакет импортирован) и `Not found in` (пакет есть в графе, но уязвимый символ не вызывается). Объясните, почему call graph analysis снижает false positives.

4. **Запуск `govulncheck` локально.**: Установите `govulncheck`, просканируйте свой модуль на известные уязвимости. Проанализируйте вывод и исправьте найденные уязвимости (обновлением версий).

5. **govulncheck установка**: Установите `govulncheck` через `go install golang.org/x/vuln/cmd/govulncheck@latest`. Это официальный инструмент от Go team.

6. **Первое сканирование**: Запустите `govulncheck ./...` в вашем проекте. Изучите вывод: какие уязвимости найдены, их severity, affected packages.

7. **govulncheck modes**: Изучите разные modes:
    * `govulncheck ./...` — сканирует imports
    * `govulncheck -mode=binary ./myapp` — сканирует compiled binary
    * `govulncheck -mode=extract ./...` — detailed vulnerability info

8. **Understanding govulncheck output**: Разберите вывод:
    * OSV ID (Open Source Vulnerability ID)
    * Affected symbol (какая функция уязвима)
    * Call stack (использует ли ваш код уязвимую функцию)
    * Fixed version (в какой версии исправлено)

9. **Сравнение с ручным аудитом.**: Выполните `go list -m all | grep <vulnerable_pkg>` и `go mod graph`. Покажите, как `govulncheck` использует OSV (Open Source Vulnerabilities) database и `vulncheck.Binary` для бинарников. Объясните, почему `govulncheck ./...` анализирует исходники, а `govulncheck -mode binary ./app` — скомпилированный бинарник.

10. **Магия `go.sum` и Checksum Database**: Открой файл `go.sum`. Измени одну букву в хэше любой библиотеки. Попытайся сделать `go build`. Получи ошибку безопасности `checksum mismatch`. Узнай, как Go проверяет хэши через глобальную базу `sum.golang.org` (защита от того, что хакер перезапишет Git-тег в репозитории автора библиотеки).

11. **[Симуляция уязвимости]**: Подключи старую версию пакета с известной CVE (например, `github.com/golang-jwt/jwt/v4 v4.0.0`). Запусти `govulncheck`. Убедись, что утилита нашла уязвимость. Обнови пакет до последней версии и проверь, что отчет чист.

12. **govulncheck ignore**: Для false positives или accepted risks создайте `.govulncheck.ignore` файл с OSV IDs для игнорирования.

13. **go.sum verification**: Изучите `go.sum` файл. Каждая строка — это cryptographic hash модуля. Go автоматически верифицирует checksums при `go mod download`.

14. **Интеграция `govulncheck` в CI/CD.**: Добавьте шаг `govulncheck ./...` в GitHub Actions или GitLab CI. Настройте падение пайплайна при обнаружении уязвимостей высокого уровня.

15. **GOSUMDB environment variable**: Настройте `GOSUMDB=sum.golang.org` (default) или отключите через `GOSUMDB=off` для private modules.

16. **Изоляция с Vendoring**: В секретных корпоративных сетях (Air-gapped) нет интернета. Выполни `go mod vendor`. Убедись, что все зависимости скачались в папку `vendor`. Скомпилируй проект флагом `go build -mod=vendor`, отключив сеть. Это также гарантирует, что даже если автор удалит библиотеку из GitHub, твой бинарник соберется.

17. **Автоматический аудит уязвимостей в GitHub Actions**: Интегрируйте `govulncheck` в ваш пайплайн сборки CI (из раздела №39) [657]. Добавьте шаг автоматического запуска `govulncheck` перед этапом компиляции Docker-образа. Пайплайн должен завершаться ошибкой и блокировать слияние кода в ветку `main`, если в кодовой базе обнаружены транзитивные уязвимости с известными CVE.

18. **[Каверзный кейс — Transitive Dependency]**: Ты не используешь уязвимый пакет напрямую, но его использует одна из твоих зависимостей. Запусти `govulncheck`. Если уязвимая функция не вызывается в твоем графе вызовов, `govulncheck` выдаст предупреждение, но не ошибку. Объясни, почему это безопаснее, чем просто сканировать `go.sum`.

19. **go mod verify**: Запустите `go mod verify` для проверки, что все модули в cache match их checksums в `go.sum`.

20. **Уязвимость в indirect dependency.**: Создайте ситуацию: `go.mod` содержит `github.com/gin-gonic/gin v1.9.0`, которая тянет `github.com/chenzhuoyu/base64x` со старой косвенной зависимостью. Покажите `go mod why github.com/chenzhuoyu/base64x`. Исправьте через `go get -u` или `replace` директиву. Объясните, почему `go mod tidy` не всегда поднимает indirect до безопасной версии.

21. **Module proxy**: Используйте `GOPROXY=https://proxy.golang.org,direct` (default) для кэширования modules. Это защищает от disappearing modules.

22. **Direct vs proxy**: Поймите разницу:
    * `GOPROXY=direct` — качает напрямую из VCS (Git)
    * `GOPROXY=https://proxy.golang.org` — качает из Google's proxy
    * `GOPROXY=off` — только из local cache

23. **Свой GOPROXY**: Настрой переменную `GOPROXY=https://proxy.golang.org,direct`. Изучи инструмент `Athens` (или Nexus/Artifactory). Подними Athens в Docker, перенаправь `GOPROXY` на него. Теперь все зависимости кэшируются на твоем внутреннем сервере (защита от падения GitHub).

24. **Генерация SBOM (Software Bill of Materials).**: Используйте `syft` или встроенную поддержку Go (`go version -m <binary>` и `go.sum`) для создания списка зависимостей. Экспортируйте SBOM в формате SPDX/CycloneDX.

25. **SLSA Levels в теории и на практике.**: Напишите эссе с примерами для Go-проекта: **Level 1** — SBOM + provenance (who, what, when); **Level 2** — signed provenance + hosted build (GitHub Actions); **Level 3** — hardened build (hermetic, reproducible, no external network, readonly source); **Level 4** — two-person review + reproducible builds. Спроектируйте CI/CD для достижения Level 3.

26. **Vendor vs modules trade-offs:**
    * Vendor: reproducible, но увеличивает repo size
    * Modules: smaller repo, но требует network для builds
    Используйте vendor для production-critical applications.

27. **[CI/CD Integration]**: Добавь шаг `govulncheck ./...` в GitHub Actions. Настрой его так, чтобы пайплайн падал (non-zero exit code), если найдена уязвимость, которая реально используется в коде.

28. **go mod tidy**: Регулярно запускайте `go mod tidy` для удаления unused dependencies и добавления missing ones.

29. **Dependency pinning**: В `go.mod` используйте exact versions (`v1.2.3`) вместо ranges для critical dependencies.

30. **Приватные модули (GOPRIVATE)**: У тебя есть приватная библиотека на GitLab. По умолчанию `go get` попытается проверить её через публичный `sum.golang.org` и получит 404 (или сольет название твоей секретной либы в логи Google). Настрой `GOPRIVATE=gitlab.mycompany.com/*`, чтобы Go качал этот код напрямую (используя SSH/Git ключи), минуя публичные прокси и базы хэшей.

31. **Защита от подмены зависимостей (Dependency Confusion)**: * Объясните в комментариях концепцию атаки Dependency Confusion: как злоумышленник может опубликовать вредоносный пакет с тем же именем, что и ваш приватный внутренний модуль, в публичный реестр `proxy.golang.org`, вынудив компилятор скачать его.
    * Напишите конфигурацию переменной окружения `GOPRIVATE` (например, `GOPRIVATE=github.com/mycompany/*`), которая указывает Go-тулингу скачивать приватные модули напрямую из вашего репозитория, полностью минуя публичные прокси-серверы и серверы проверки контрольных сумм (`sumdb`).

32. **Minimum version selection**: Поймите Go's MVS (Minimum Version Selection) algorithm. Go выбирает минимальную версию, которая удовлетворяет все requirements.

33. **Cosign: подпись бинарника.**: Используйте `cosign sign-blob` для подписи Go-бинарника. Проверьте через `cosign verify-blob`. Объясните keyless signing: OIDC (GitHub Actions token) → Fulcio (CA) → ephemeral key pair → подпись → Rekor (transparency log). Покажите, что private key никогда не существует на диске.

34. **Replace directive**: Используйте `replace` для pinning specific versions или замены modules на forks:
    ```go
    replace github.com/vulnerable/pkg => github.com/mycompany/fork v1.2.4
    ```

35. **Go Checksum Database**: Изучите `sum.golang.org` — это transparency log для Go modules. Все checksums публично логируются для предотвращения tampering.

36. **Сканирование SBOM на уязвимости.**: Запустите `grype` на сгенерированном SBOM, проанализируйте результат. Настройте автоматическое сканирование SBOM при каждой сборке.

37. **Dependency audit script**: Напишите скрипт, который:
    * Запускает `govulncheck`
    * Проверяет `go mod verify`
    * Логирует результаты
    * Алертит при findings

38. **[Private Go Proxy]**: Если ты пишешь проприетарный код, по умолчанию Go может слать хеши твоих модулей на публичный `proxy.golang.org` для верификации. Настрой переменную окружения `GOPRIVATE=gitlab.mycompany.com/*`, чтобы Go не утекал информацию о внутренних пакетах.

39. **Cosign установка**: Установите `cosign` через `go install github.com/sigstore/cosign/v2/cmd/cosign@latest`.

40. **Воспроизводимые сборки (Reproducible Builds)**: Скомпилируй бинарник. Попроси друга скомпилировать этот же коммит на его макбуке. Сравните хэши `sha256sum`. Они будут **разными**! (В бинарник вшиваются локальные пути ОС: `/Users/name/...`). Добавь флаг `-trimpath`. Скомпилируйте снова — теперь хэши совпадут. Это криптографическая гарантия, что CI-сервер не подменил код при сборке.

41. **Rekor Transparency Log.**: После подписи найдите запись в Rekor через `rekor-cli get --uuid <...>` или `cosign verify` с `--rekor-url`. Объясните, как transparency log защищает от отката подписей (software supply chain transparency): злоумышленник не может тайно подписать вредоносный бинарник, не оставив публичной записи.

42. **Key generation**: Сгенерируйте key pair через `cosign generate-key-pair`. Это создаёт `cosign.key` (private) и `cosign.pub` (public).

43. **Keyless signing (Fulcio)**: Используйте keyless signing через Fulcio (Sigstore's CA):
    ```bash
    cosign sign --yes myregistry.io/myimage:tag
    ```
    Это использует OIDC identity (GitHub Actions, Google Cloud) вместо static keys.

44. **Sign Docker image**: Подпишите Docker image:
    ```bash
    cosign sign --key cosign.key myregistry.io/myimage:v1.2.3
    ```

45. **SLSA Provenance generation.**: Настройте `slsa-github-generator` (`.github/workflows/slsa3.yml`) для сборки Go-приложения. Получите `provenance.intoto.jsonl`. Проверьте аттестацию через `cosign verify-attestation --type slsaprovenance`. Объясните, что provenance связывает artifact с конкретным git commit, builder и build parameters.

46. **SBOM (Software Bill of Materials)**: По новым законам США и ЕС, ты обязан поставлять софт со списком всех его "деталей" (библиотек). Используй утилиту `go version -m myapp` для встроенного мини-SBOM. Затем установи `github.com/CycloneDX/cyclonedx-gomod` и сгенерируй полноценный XML/JSON отчет по стандарту CycloneDX.

47. **Verify binary**: Верифицируйте binary signature:
    ```bash
    cosign verify-blob --key cosign.pub --signature myapp.sig myapp
    ```

48. **[go mod verify]**: Запусти `go mod verify`. Объясни, что эта команда проверяет соответствие скачанных модулей в `$GOPATH/pkg/mod` хэшам из `go.sum` (защита от подмены файлов на диске).

49. **Подписание и верификация модулей.**: Изучите механизм Go Checksum Database (`sum.golang.org`). Настройте `GONOSUMCHECK` для приватных модулей. Подпишите свой модуль с помощью `cosign` и проверьте подпись при сборке.

50. **Валидация контрольных сумм с `go.sum`**: Напишите упражнение на понимание работы механизма защиты `go.sum`. Объясните, как Go использует SHA-256 хэши в файле `go.sum` для контроля целостности скачиваемого кода библиотек [659]. Напишите тест: вручную измените хэш-сумму одной из библиотек в файле `go.sum` и запустите сборку `go build` [659]. Проанализируйте ошибку безопасности, выдаваемую компилятором Go.

51. **Dependency Confusion Attack.**: Создайте приватный модуль `company.com/internal/api`. Покажите, что если `GOPRIVATE` не настроен, `go get` может обратиться к public proxy и скачать одноимённый публичный модуль (если злоумышленник его зарегистрирует). Исправьте: `GOPRIVATE=company.com`, `GONOSUMDB=company.com`, `GONOPROXY=company.com`. Объясните разницу между тремя переменными.

52. **Typosquatting (Опечатки)**: Хакеры создают пакеты вроде `github.com/sirupsen/logrus` (вместо `sirupsen`). Напиши CI-баш-скрипт, который парсит `go.mod` и ищет подозрительные домены или запрещает скачивание пакетов, не входящих во внутренний "белый список" компании.

53. **[Vendoring & Auditing]**: Выполни `go mod vendor`. Передай папку `vendor/` на проверку в SCA-сканер (например, Snyk или Trivy). Оцени плюсы подхода (воспроизводимость сборки, аудит исходников) и минусы (огромный PR, если обновить зависимость).

54. **Cosign в CI/CD**: Настройте GitHub Actions для автоматической подписи Docker images при push в main branch.

55. **Cosign + Kubernetes**: Используйте cosign policy controller в Kubernetes для блокировки неподписанных images:
    ```yaml
    apiVersion: policy.sigstore.dev/v1beta1
    kind: ClusterImagePolicy
    spec:
      images:
      - glob: "myregistry.io/*"
      authorities:
      - key:
          data: |
            -----BEGIN PUBLIC KEY-----
            ...
            -----END PUBLIC KEY-----
    ```

56. **Генерация SBOM.**: Используйте `syft` (или `cyclonedx-gomod`) для создания SBOM (CycloneDX/SPDX) из `go.mod`. Проверьте наличие `purl`, `license`, `hash`. Объясните NTIA minimum elements: supplier, component name, version, other unique identifiers, dependency relationship, author of SBOM data.

57. **Блокировка зависимостей с известными уязвимостями.**: Настройте инструмент (например, `osv-scanner` с фильтром) так, чтобы CI падал при наличии уязвимостей с CVSS выше 7.0 в зависимостях.

58. **Checksum Database (`sum.golang.org`).**: Покажите, как `go.sum` защищает от MITM: при `go mod tidy` Go сверяет hash модулей с `GOSUMDB`. Объясните, почему отключение `GOSUMDB=off` — антипаттерн. Покажите, как `go env GOSUMDB` работает с `sum.golang.org` (публичная аудиторская база).

59. **SLSA framework**: Изучите SLSA (Supply-chain Levels for Software Artifacts):
    * Level 0: No guarantees
    * Level 1: Build script defined
    * Level 2: Hosted build platform
    * Level 3: Isolated, hermetic builds
    * Level 4: Two-party review

60. **Безопасная очистка памяти (Memory Wiping)**: Сборщик мусора Go не очищает память сразу. Если твой процесс сдампят (Core Dump) хакеры, они найдут там пароли в виде строк. Строки в Go неизменяемы. Создай пароль как `[]byte`. После использования напиши функцию, которая в цикле перезаписывает этот срез нулями `b[i] = 0` (или используй библиотеку `awnumar/memguard`), уничтожая секрет в RAM.

61. **SLSA provenance generator**: Используйте `slsa-framework/slsa-github-generator` для автоматической генерации SLSA Level 3 provenance в GitHub Actions.

62. **Использование локального вендоринга (Vendoring)**: Напишите команду сохранения локальной копии всех зависимостей в папку проекта: `go mod vendor` [660]. Объясните преимущества вендоринга с точки зрения SecOps: полная независимость сборки в CI от работоспособности внешних серверов (защита от удаления пакетов авторами на GitHub) [660], а также возможность проводить изолированный аудит безопасности и аудит лицензий кода сторонних библиотек внутри папки `vendor/`.

63. **In-toto attestations**: Изучите in-toto framework для software supply chain security. Cosign использует in-toto format для attestations.

64. **[SBOM (Software Bill of Materials)]**: Сгенерируй SBOM для своего бинарника с помощью утилиты `syft`. Это JSON/XML файл со списком всех зависимостей и их версий. Изучи, зачем это нужно энтерпрайзу (для быстрого поиска уязвимостей по списку CVE, не разбирая исходники).

65. **Private Module Proxy (Athens/Artifactory).**: Настройте `GOPROXY=https://athens.company.com,https://proxy.golang.org,direct`. Покажите, что приватные модули кэшируются и проверяются внутри perimeter. Объясните air-gapped сценарий: `GOPROXY=https://athens.company.com` (без fallback) + `GONOSUMDB=*` + `GONOPROXY=*`.

66. **Multiple signatures**: Подпишите image несколькими keys (например, dev team + security team). Verifiers могут требовать все или subset signatures.

67. **Signature expiration**: Настройте expiration для signatures через certificate validity period (для keyless signing).

68. **Attestations**: Создайте attestation (SLSA provenance):
    ```bash
    cosign attest --predicate slsa-provenance.json --type slsaprovenance myimage:tag
    ```

69. **Отключение CGO для безопасности**: В 99% случаев CGO тебе не нужен. Переменная `CGO_ENABLED=1` тащит в твой бинарник сишный рантайм ОС (динамическую линковку). Это увеличивает площадь атаки (уязвимости libc). Всегда компилируй с `CGO_ENABLED=0`, получая статически слинкованный бинарник, который безопасен и работает в пустом `scratch` образе.
