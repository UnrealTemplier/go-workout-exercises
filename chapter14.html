Упражнение #1

Неявная реализация интерфейсов (Implicit Interface Satisfaction) без ключевого слова implements

📌 Условие задачи

Объяви интерфейс Greeter с методом Greet() string. Создай структуру Englishman, реализующую его. Покажи, что в Go нет ключевого слова implements — реализация неявная.

💡 Теоретический фундамент и концепция

Утиная типизация (Structural Typing / Implicit Satisfaction) в Go:

  • В Go отсутствует ключевое слово implements;
  • Тип автоматически удовлетворяет интерфейсу, если он реализует все методы, объявленные в интерфейсе с совпадающими сигнатурами;
  • Это исключает жесткую связь между поставщиком реализации и потребителем API (Loose Coupling).

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем интерфейс Greeter с методом Greet() string.
2. Создаем структуру Englishman{} и реализуем метод Greet() string.
3. Присваиваем структуру переменной интерфейса.
📄 main.go 
package main

import "fmt"

type Greeter interface {
	Greet() string
}

type Englishman struct {
	Name string
}

// Englishman автоматически реализует интерфейс Greeter:
func (e Englishman) Greet() string {
	return fmt.Sprintf("Hello, my name is %s!", e.Name)
}

func main() {
	var g Greeter = Englishman{Name: "Arthur"}
	fmt.Println(g.Greet())
}
📄 Терминал 
go run main.go
# Hello, my name is Arthur!
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Компилятор Go строит интерфейсную таблицу runtime.iface (состоящую из itab с таблицей указателей на функции и data с указателем на значение).

⚠️ Частые грабли и ошибки новичков
  • Попытка искать ключевое слово implements или забыть один из методов интерфейса (ошибка does not implement ... (missing method)).
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему создатели Go отказались от явного implements?»

Ответ: Неявные интерфейсы позволяют пакетам определять минимальные интерфейсы под свои нужды для типов из чужих библиотек без необходимости изменять исходный код этих библиотек.

Упражнение #2

Полиморфизм интерфейсов: динамическое переназначение структур Englishman и Spaniard

📌 Условие задачи

Создай переменную типа интерфейса var g Greeter. Присвой ей Englishman{}. Вызови метод. Затем присвой другую структуру Spaniard{} — покажи полиморфизм.

💡 Теоретический фундамент и концепция

Динамический полиморфизм (Runtime Polymorphism):

  • Переменная интерфейсного типа может в рантайме хранить значения любых конкретных типов, удовлетворяющих данному интерфейсу;
  • При каждом вызове метода вызывается реализация текущего активного типа.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем структуры Englishman и Spaniard.
2. Присваиваем поочередно интерфейсу var g Greeter.
3. Демонстрируем полиморфный вызов.
📄 main.go 
package main

import "fmt"

type Greeter interface {
	Greet() string
}

type Englishman struct{}

func (Englishman) Greet() string {
	return "Hello!"
}

type Spaniard struct{}

func (Spaniard) Greet() string {
	return "¡Hola!"
}

func main() {
	var g Greeter

	g = Englishman{}
	fmt.Printf("g (Englishman): %s\n", g.Greet())

	g = Spaniard{}
	fmt.Printf("g (Spaniard):   %s\n", g.Greet())
}
📄 Терминал 
go run main.go
# g (Englishman): Hello!
# g (Spaniard):   ¡Hola!
⚙️ Под капотом Go (Compiler, Linker & Runtime)

При переприсваивании g = Spaniard{} обновляется указатель itab внутри интерфейсной структуры на таблицу методов Spaniard.

⚠️ Частые грабли и ошибки новичков
  • Вызов метода на неинициализированном интерфейсе var g Greeter; g.Greet() (паника nil pointer dereference).
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Из каких двух указателей состоит интерфейс iface под капотом?»

Ответ: 1) *itab (тип данных, метаинформация и таблица адресов методов); 2) unsafe.Pointer (указатель на сами данные объекта в памяти).

Полиморфизм в коллекциях: гетерогенный срез []Speaker и вызов методов в цикле

📌 Условие задачи

Полиморфизм: Создай срез []Speaker. Положи туда собаку и кошку. В цикле пройдись по срезу и вызови Speak() для каждого. Заметь: структуры нигде не заявляют implements Speaker, они просто имеют нужный метод.

💡 Теоретический фундамент и концепция

Гетерогенные коллекции интерфейсов:

  • Срез интерфейсов []Speaker может объединять совершенно разнородные структуры в единую полиморфную последовательность.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем type Speaker interface { Speak() string }.
2. Создаем срез speakers := []Speaker{Dog{}, Cat{}}.
3. Итерируемся в цикле for range.
📄 main.go 
package main

import "fmt"

type Speaker interface {
	Speak() string
}

type Dog struct{ Breed string }

func (d Dog) Speak() string {
	return fmt.Sprintf("[%s] Гав!", d.Breed)
}

type Cat struct{ Color string }

func (c Cat) Speak() string {
	return fmt.Sprintf("[%s] Мяу!", c.Color)
}

func main() {
	speakers := []Speaker{
		Dog{Breed: "Овчарка"},
		Cat{Color: "Рыжий"},
		Dog{Breed: "Хаски"},

Конструкция Type Switch (v.(type)):

  • Специальная конструкция Go для инспекции динамического типа значения, упакованного в пустой интерфейс any / interface{};
  • Внутри каждого case T: переменная автоматически приводится к конкретному типу T.

package main

	X, Y int
}

	switch val := v.(type) {

		fmt.Printf("Строка: %q (длина: %d байт)\n", val, len(val))

	default:
		fmt.Printf("Неизвестный тип (%T): %v\n", val, val)
	}
}

import "fmt"

func AssertString(v any) (result string) {
	defer func() {
		if r := recover(); r != nil {

			result = "<ОШИБКА ТИПА>"

	return v.(string)
}

func main() {

	fmt.Printf("1. Успешный вызов: %s\n", res1)

	res2 := AssertString(12345) // Передаем int вместо string!
	fmt.Printf("2. Результат:      %s\n", res2)
}

Упражнение #11

Универсальный числовой конвертер ToInt(v any) (int, error) через Type Switch и strconv

📌 Условие задачи

Напиши функцию ToInt(v interface{}) (int, error), принимающую int, int8, int16, int32, int64, uint, string (через strconv) и возвращающую int. Используй type switch.

💡 Теоретический фундамент и концепция

Паттерн гибкого парсинга параметров (Flexible Type Coercion):

  • В микросервисах параметры конфигурации и JSON-поля могут приходить как числами, так и строками;
  • ToInt нормализует все числовые типы и строковые представления к базовому типу int.

🔍 Пошаговый ход решения и ход мысли инженера

1. Пишем ToInt(v any) (int, error).
2. Обрабатываем int, int8..int64, uint..uint64, float64, string, bool.
3. Тестируем все варианты.
📄 main.go 
package main

import (
	"fmt"
	"strconv"
)

func ToInt(v any) (int, error) {
	switch val := v.(type) {
	case int:
		return val, nil
	case int8:
		return int(val), nil
	case int16:
		return int(val), nil
	case int32:
		return int(val), nil
	case int64:
		return int(val), nil
	case uint:
		return int(val), nil
	case float64:
		return int(val), nil
	case string:
		n, err := strconv.Atoi(val)
		if err != nil {
			return 0, fmt.Errorf("не удалось преобразовать строку %q в int: %w", val, err)
		}
		return n, nil
	case bool:
		if val {
			return 1, nil
		}
		return 0, nil
	default:
		return 0, fmt.Errorf("неподдерживаемый тип для преобразования в int: %T", v)
	}
}

func main() {
	tests := []any{
		42,
		int32(100),
		"777",
		3.99,
		true,
		"не_число",
	}

	for _, item := range tests {
		val, err := ToInt(item)
		if err != nil {
			fmt.Printf("Вход: %-10v (%-7T) -> Ошибка: %v\n", item, item, err)
		} else {
			fmt.Printf("Вход: %-10v (%-7T) -> int: %d\n", item, item, val)
		}
	}
}

	"fmt"
	"io"
)

type MyBuffer struct {
	data   []byte
	offset int
}

func NewMyBuffer(text string) *MyBuffer {
	return &MyBuffer{data: []byte(text)}
}

func (b *MyBuffer) Read(p []byte) (n int, err error) {
	if b.offset >= len(b.data) {
		return 0, io.EOF
	}

	n = copy(p, b.data[b.offset:])
	b.offset += n
	return n, nil
}

func main() {
	buf := NewMyBuffer("Потоковые данные из MyBuffer!")

	allBytes, err := io.ReadAll(buf)
	if err != nil {
		panic(err)
	}

	fmt.Printf("Прочитано: %q (всего %d байт)\n", string(allBytes), len(allBytes))
}

	"fmt"
	"io"

	offset int

	if m.offset >= len(m.buf) {

package main

import (
	"fmt"
	"reflect"
)

func IsReallyNil(v any) bool {
	if v == nil {
		return true
	}

	val := reflect.ValueOf(v)
	switch val.Kind() {
	case reflect.Pointer, reflect.Slice, reflect.Map, reflect.Chan, reflect.Func, reflect.Interface:
		return val.IsNil()
	default:
		return false
	}
}

func main() {
	var cleanNil any = nil
	var nilPtr *int = nil
	var ifaceWithNil any = nilPtr
	var number int = 0

	fmt.Printf("1. cleanNil:       IsReallyNil = %t\n", IsReallyNil(cleanNil))
	fmt.Printf("2. ifaceWithNil:   IsReallyNil = %t\n", IsReallyNil(ifaceWithNil))
	fmt.Printf("3. number (0):     IsReallyNil = %t\n", IsReallyNil(number))
}

# 2. ifaceWithNil:   IsReallyNil = true

Упражнение #47

Различие типов: кастомный тип type MyInt int и паника при i.(int)

📌 Условие задачи

Создай тип MyInt int. Реализуй для него метод String() string. Присвой var i any = MyInt(5). Сделай type assertion i.(int) — получи панику. Объясни, почему MyInt и int — разные типы, хотя underlying type одинаковый.

💡 Теоретический фундамент и концепция

Строгая типизация Defined Types:

  • type MyInt int создает новый уникальный тип с базовым типом int;
  • В интерфейсе сохраняется дескриптор типа MyInt, а не int;
  • Поэтому Type Assertion i.(int) выбрасывает панику!

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем type MyInt int.
2. Реализуем (m MyInt) String() string.
3. Показываем панику при i.(int) и правильный i.(MyInt).
📄 main.go 
package main

import "fmt"

type MyInt int

func (m MyInt) String() string {
	return fmt.Sprintf("MyInt(%d)", int(m))
}

func main() {
	var i any = MyInt(5)

	// 1. Правильный Type Assertion к точному типу MyInt:
	if val, ok := i.(MyInt); ok {
		fmt.Printf("1. Успешное приведение к MyInt: %s\n", val)
	}

	// 2. Попытка приведения к базовому типу int (ok == false):
	if _, ok := i.(int); !ok {
		fmt.Println("2. Приведение i.(int) вернуло false, так как MyInt != int в системе типов Go!")
	}
}

⚠️ Частые грабли и ошибки новичков

package main

	"fmt"
	"reflect"
)

		fmt.Println("Объект равен nil")

		}
	}
}

Упражнение #75

Паттерн Стратегия (Strategy Pattern) на базе интерфейса Sorter

📌 Условие задачи

Создайте и используйте интерфейс Sorter с методом Sort(data []int), реализуйте его с разными алгоритмами (пузырёк, выбор) и выберите стратегию во время выполнения.

💡 Теоретический фундамент и концепция

Паттерн Strategy через интерфейсы:

  • Позволяет динамически подменять алгоритмы в рантайме без изменения клиентского кода.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем интерфейс Sorter с методом Sort(data []int).
2. Реализуем BubbleSorter и SelectionSorter.
3. Применяем стратегии.
📄 main.go 
package main

import "fmt"

type Sorter interface {
	Sort(data []int)
}

type BubbleSorter struct{}

func (BubbleSorter) Sort(data []int) {
	n := len(data)
	for i := 0; i < n-1; i++ {
		for j := 0; j < n-i-1; j++ {
			if data[j] > data[j+1] {
				data[j], data[j+1] = data[j+1], data[j]
			}
		}
	}
}

type SelectionSorter struct{}

func (SelectionSorter) Sort(data []int) {
	n := len(data)
	for i := 0; i < n-1; i++ {
		minIdx := i
		for j := i + 1; j < n; j++ {
			if data[j] < data[minIdx] {
				minIdx = j
			}
		}
		data[i], data[minIdx] = data[minIdx], data[i]
	}
}

func ExecuteSort(s Sorter, arr []int) {
	s.Sort(arr)
	fmt.Printf("Отсортировано (%T): %v\n", s, arr)
}

func main() {
	arr1 := []int{5, 2, 9, 1}
	arr2 := []int{8, 3, 7, 4}

	ExecuteSort(BubbleSorter{}, arr1)
	ExecuteSort(SelectionSorter{}, arr2)
}

# Отсортировано (main.BubbleSorter): [1 2 5 9]
# Отсортировано (main.SelectionSorter): [3 4 7 8]

Упражнение #76

Сравнение Generics Max[T cmp.Ordered] против пустых интерфейсов MaxInterface(a, b any)

📌 Условие задачи

Создай generic-функцию Max[T constraints.Ordered](a, b T) T и сравни с интерфейсным подходом MaxInterface(a, b interface{}) (interface{}, error). Покажи преимущества generics над пустыми интерфейсами.

💡 Теоретический фундамент и концепция

Преимущества Generics над any / interface{}:

1. Безопасность типов во время компиляции: исключает ошибки времени выполнения;
2. Нулевой оверхед (Zero Boxing Overhead): данные передаются в регистрах CPU без упаковки в eface и аллокаций в куче;
3. Прямой возврат точного типа T: не требует Type Assertion со стороны вызывающего кода.

🔍 Пошаговый ход решения и ход мысли инженера

1. Пишем MaxGeneric[T cmp.Ordered](a, b T) T.
2. Пишем MaxInterface(a, b any) (any, error).
3. Сравниваем удобство и производительность.
📄 main.go 
package main

import (
	"cmp"
	"fmt"
)

// 1. Современный generic-подход (Go 1.21+):
func MaxGeneric[T cmp.Ordered](a, b T) T {
	if a > b {
		return a
	}
	return b
}

// 2. Устаревший интерфейсный подход (до Go 1.18):
func MaxInterface(a, b any) (any, error) {
	switch va := a.(type) {
	case int:
		if vb, ok := b.(int); ok {
			if va > vb {
				return va, nil
			}
			return vb, nil
		}
	}
	return nil, fmt.Errorf("несовместимые типы")
}

func main() {
	// Generic: строгая типизация и возврат int без кастов:
	maxInt := MaxGeneric(10, 25)
	maxStr := MaxGeneric("apple", "banana")

	fmt.Printf("Generic Max Int: %d\n", maxInt)
	fmt.Printf("Generic Max Str: %s\n", maxStr)

	// Interface: требуется проверка ошибки и Type Assertion:
	res, _ := MaxInterface(10, 25)
	val := res.(int)
	fmt.Printf("Interface Max:   %d\n", val)
}
📄 Терминал 
go run main.go
# Generic Max Int: 25
# Generic Max Str: banana
# Interface Max:   25
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Generics используют механизм мономорфизации компилятора (GCShape Stenciling) для генерации быстрого кода.

⚠️ Частые грабли и ошибки новичков
  • Использование any для математических функций при наличии дженериков.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Когда следует использовать Generics, а когда интерфейсы?»

Ответ: Generics используют, когда алгоритм одинаков для разных типов и важна сохранность типа (контейнеры, слайсы, алгоритмы). Интерфейсы используют, когда у разных типов различается поведение (полиморфизм).
