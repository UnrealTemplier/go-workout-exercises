# Масштабируемые распределенные планировщики и очереди задач

В этом файле собраны уникальные упражнения по теме **"Масштабируемые распределенные планировщики и очереди задач"**, отсортированные по возрастанию сложности.

---

1. **Архитектура асинхронной обработки фоновых задач**: Спроектируйте архитектуру системы фоновых задач на Go. Выделите три ключевые роли: Producer (формирует задачу и ставит в очередь), Broker/Queue Storage (надежно сохраняет задачи) и Worker Pool (конкурентно исполняет задачи). Опишите различия между очередями общего назначения (RabbitMQ/Kafka) и специализированными менеджерами фоновых задач (Asynq/River).

2. **Потокобезопасная очередь задач в памяти (In-Memory Worker Pool)**: Напишите простой воркер-пул на Go с использованием каналов `chan Task` и пула из $N$ горутин. Реализуйте безопасную постановку задач, остановку пула с ожиданием завершения текущих задач (`sync.WaitGroup`) и отмену по таймауту через `context.Context`.

3. **Очереди задач на Redis Streams vs Sorted Sets**: Сравните две структуры Redis для очередей: Redis Streams (`XADD`, `XREADGROUP`, `XACK`) и Sorted Sets (`ZADD` с меткой времени для отложенных задач). Реализуйте прототип постановки и извлечения задач с использованием consumer groups в Streams, гарантирующих доставку только одному воркеру.

4. **Преимущества очередей на базе PostgreSQL (River / pg_cron)**: Изучите библиотеку `riverqueue/river` для Go. Объясните главное архитектурное преимущество очередей на базе PostgreSQL перед Redis: возможность постановки задачи в очередь в рамках той же транзакции базы данных, где изменяются бизнес-данные (отсутствие проблемы Dual-Write без внешнего Outbox).

5. **Конкурентное чтение задач: SELECT ... FOR UPDATE SKIP LOCKED**: Напишите SQL-запрос для безопасного извлечения задач из таблицы `jobs` несколькими параллельными воркерами: `SELECT id, payload FROM jobs WHERE status = 'pending' AND run_at <= NOW() ORDER BY run_at ASC LIMIT 1 FOR UPDATE SKIP LOCKED`. Объясните, как директива `SKIP LOCKED` позволяет воркерам не блокировать друг друга и работать с максимальной параллельностью.

6. **Детектирование зависших воркеров и Heartbeat**: Что произойдет, если воркер взял задачу, но процесс внезапно упал по SIGKILL или Out-Of-Memory? Задача останется в статусе `running` навсегда. Реализуйте механизм Heartbeat: воркер каждые 15 секунд обновляет поле `last_heartbeat = NOW()`. Отдельный процесс-рековерер находит задачи с `last_heartbeat < NOW() - INTERVAL '1 minute'` и возвращает их в статус `pending` для повторного исполнения.

7. **Очереди с приоритетами (Priority Queues)**: Спроектируйте систему приоритетов задач: `Critical`, `High`, `Default`, `Low`. Напишите диспетчер воркеров, который сначала опрашивает очередь `Critical`, и только при ее опустошении переходит к более низким приоритетам, либо использует взвешенное случайное распределение (Weighted Fair Queuing), чтобы низкоприоритетные задачи не голодали бесконечно (starvation).

8. **Отложенные задачи (Delayed / Scheduled Tasks)**: Реализуйте постановку задач с выполнением в будущем (`EnqueueIn(task, 2 * time.Hour)`). Напишите воркер, который с помощью планировщика выбирает задачи, у которых время `run_at <= time.Now()`. Продемонстрируйте корректность работы при изменении системного времени и смене часовых поясов.

9. **Периодические задачи (Cron-like Scheduling)**: Реализуйте распределенный планировщик периодических задач (например, генерация отчетов каждый день в 03:00 по cron-выражению `0 3 * * *`). Решите проблему дублирования: если запущено 10 реплик сервиса, задача должна выполниться ровно один раз. Используйте распределенный мьютекс в Redis или `pg_advisory_lock` в PostgreSQL.

10. **Политики повторных попыток (Retry Policies) и Full Jitter**: При сбое воркера (сетевая ошибка, недоступность внешнего API) задача должна быть повторена. Реализуйте алгоритм экспоненциального отката с добавлением полного джиттера (Full Jitter): `sleep = rand(0, min(max_backoff, base * 2^attempt))`. Докажите, что добавление случайности исключает резонансные волны повторных запросов к сбоящему сервису.

11. **Паттерн Dead Letter Queue (DLQ) для ядовитых сообщений**: Если задача падает с ошибкой после исчерпания максимального числа попыток (например, 5 ретраев), она не должна бесконечно забивать очередь. Реализуйте перенос задачи в таблицу или очередь `dead_letter_jobs` с сохранением стека ошибки, времени и параметров. Напишите API для просмотра и ручного перезапуска (Replay) задач из DLQ.

12. **Версионирование схемы полезной нагрузки задач**: Воркер старой версии приложения может попытаться обработать задачу, созданную новой версией сервиса с обновленной схемой JSON. Разработайте стратегию версионирования payload: добавление поля `schema_version int`, обработка неизвестных полей и валидация схемы перед передачей в бизнес-обработчик.

13. **Идемпотентность исполнения задач и дедупликация**: Из-за сбоев сети задача может быть выполнена повторно. Реализуйте дедупликацию задач: при постановке вычисляется уникальный ключ дедупликации `dedup_key` (например, хэш от типа задачи и идентификатора заказа). Если задача с таким ключом уже находится в очереди или была выполнена недавно, повторная постановка игнорируется.

14. **Прерывание задач через Context и Graceful Abortion**: Реализуйте механизм отмены выполняющейся задачи: пользователь нажимает кнопку «Отменить экспорт» в UI. Сервис отправляет сигнал отмены (в Redis или PostgreSQL), воркер периодически проверяет `ctx.Err()` или канал отмены и корректно прерывает длительную операцию, очищая созданные временные файлы на диске.

15. **Динамическое масштабирование пула воркеров по длине очереди (Queue Lag)**: Напишите автоскейлер воркеров: фоновый монитор замеряет глубину очереди (количество задач в статусе `pending`). Если глубина очереди превышает порог 1000 задач, пул динамически создает дополнительные горутины-воркеры до заданного максимума `max_workers`, а при снижении нагрузки плавно останавливает лишние горутины.

16. **Распределенный Rate Limiting выполнения задач**: Представьте, что 50 воркеров обрабатывают задачи отправки SMS через шлюз провайдера, имеющий жесткий лимит 100 запросов в секунду на весь аккаунт. Реализуйте распределенный Rate Limiter на базе алгоритма Token Bucket или Leaky Bucket в Redis с помощью Lua-скрипта. Если лимит исчерпан, воркер откладывает задачу на несколько миллисекунд назад в очередь.

17. **Справедливое планирование (Fair Scheduling) между тенантами**: В Multi-Tenant SaaS один крупный клиент может поставить в очередь 1 миллион задач, заблокировав обработку задач остальных 500 клиентов. Спроектируйте алгоритм честного распределения: задачи группируются по `tenant_id`, и воркер выбирает задачи в порядке Round-Robin между активными тенантами, не позволяя ни одному клиенту монополизировать пул.

18. **Пакетная обработка задач (Batching / Bulk Processing)**: Отправка 10 000 сообщений в аналитику по одному сообщению на задачу неэффективна. Реализуйте воркер пакетной обработки: он накапливает до 100 задач или ждет максимум 500 мс (что наступит раньше), после чего выполняет одну пакетную вставку в ClickHouse или отправку пачки запросов по HTTP.

19. **Graceful Shutdown очереди: безопасный слив задач**: Напишите корректное завершение работы воркера при получении сигналов `SIGINT` или `SIGTERM`: воркер прекращает забор новых задач из очереди, дожидается завершения текущих задач в пределах заданного таймаута (например, 30 секунд), сохраняет прогресс и освобождает блокировки в базе данных.

20. **Мониторинг и метрики: Prometheus гистограммы времени обработки**: Оснастите систему очередей метриками Prometheus: `queue_depth{queue="default"}` (gauge), `tasks_processed_total{status="success|failure"}` (counter), `task_execution_duration_seconds` (histogram) и `task_queue_latency_seconds` (время ожидания задачи в очереди от момента постановки до взятия воркером).

21. **Глубокое погружение в библиотеку Asynq на Go**: Изучите архитектуру `hibiken/asynq`. Напишите сервис генерации PDF-отчетов с использованием Asynq: конфигурация `asynq.RedisClientOpt`, настройка concurrency, обработка ошибок, использование кастомного middleware и подключение Asynq Web UI для мониторинга очереди задач через браузер.

22. **Глубокое погружение в библиотеку River на базе pgx/PostgreSQL**: Создайте воркер на базе `riverqueue/river`. Напишите миграции для служебных таблиц River, настройте драйвер `riverpgxv5`, создайте строго типизированную структуру аргументов `JobArgs`, реализуйте интерфейс `Worker` и покажите вставку задачи в одной транзакции с бизнес-сущностью.

23. **Цепочки и зависимости задач (Job Chaining & Workflows)**: Реализуйте конвейер из связанных задач: Задача A (скачивание видео) -> Задача B (транскодирование) -> Задача C (публикация). При успешном завершении Задачи A воркер автоматически ставит в очередь Задачу B с параметрами результата первого шага. При падении любого шага конвейер останавливается и запускает компенсирующее действие.

24. **Обработка паник (Panic Recovery) и изоляция Poison Pill**: Если задача содержит поврежденный payload, вызывающий разыменование nil-указателя внутри воркера, она не должна ронять весь процесс приложения. Реализуйте защитный middleware с `recover()`, который перехватывает панику, форматирует трассировку стека, помечает задачу как фатально упавшую и немедленно отправляет ее в DLQ.

25. **Обратное давление (Backpressure) и защита от переполнения брокера**: Если очередь насчитывает 5 миллионов задач, а продюсеры продолжают заваливать ее новыми событиями, может закончиться оперативная память Redis или место на диске PostgreSQL. Реализуйте стратегию Backpressure: если размер очереди превышает критический порог, метод `Enqueue` блокирует продюсера или возвращает ошибку `ErrQueueFull` (HTTP 429 / 503).

26. **Профилирование утечек памяти в долгоживущих воркерах через pprof**: Воркеры фоновых задач работают непрерывно месяцами. Неаккуратное сохранение срезов или контекстов в глобальных переменных приводит к медленной утечке памяти. Подключите `net/http/pprof`, сымитируйте утечку в цикле воркера, снимите дамп кучи через `go tool pprof heap` и найдите виновную строчку кода.

27. **Тестирование воркеров: подмена времени и мокирование брокера**: Напишите надежные юнит- и интеграционные тесты для фонового воркера. Используйте библиотеку подмены времени (например, `jonboulle/clockwork`), чтобы мгновенно проверять срабатывание отложенных задач без реального ожидания часов через `time.Sleep`. Проверьте логику инкремента счетчика ретраев.

28. **Сравнение производительности: Redis vs PostgreSQL Queue**: Напишите нагрузочный тест, сравнивающий пропускную способность (throughput в операциях/сек) и задержку (latency) очередей на Redis и PostgreSQL при 100 конкурентных продюсерах и воркерах. Проанализируйте затраты CPU и дискового ввода-вывода (IOPS).

29. **Очереди в геораспределенных окружениях (Multi-Region)**: Рассмотрите специфику очередей при развертывании в нескольких датацентрах: задержка синхронизации реплик БД, риск обработки задачи в двух регионах одновременно (Split-Brain). Спроектируйте архитектуру с региональными очередями и единой точкой координации.

30. **Enterprise Распределенный Менеджер Задач на Go**: Разработайте готовый к продакшену менеджер задач на Go: хранение в PostgreSQL через `pgxpool`, поддержка приоритетов через `SKIP LOCKED`, надежный Heartbeat и восстановление зависших задач, экспоненциальный retry с джиттером, DLQ с API ручного перезапуска, метрики Prometheus и graceful shutdown.
