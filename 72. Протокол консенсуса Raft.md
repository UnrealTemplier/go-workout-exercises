# Протокол консенсуса Raft

В этом файле собраны уникальные упражнения по теме **"Протокол консенсуса Raft"**, отсортированные по возрастанию сложности.

---

1. **Однонодовый кластер.**: Создайте FSM (Finite State Machine) на Go: `map[string]string` с `Apply([]byte)` и `Snapshot()`. Интегрируйте `hashicorp/raft`, запустите один узел с `BootstrapCluster`. Выполните `raft.Apply([]byte("set foo=bar"), timeout)` и покажите, что FSM обновился. Объясните, что `Apply` — это единственный способ изменить состояние в Raft.

2. **Raft концепции**: Изучите 5 ключевых концепций:
    * Leader (один в кластере)
    * Followers (реплицируют state)
    * Candidates (участвуют в выборах)
    * Terms (логические периоды времени)
    * Log entries (команды для state machine)

3. **Bootstrap кластера из 3 узлов.**: Настройте `raft.Config` (LocalID, SnapshotInterval, HeartbeatTimeout), `raft.NetworkTransport` (TCP). Запустите 3 узла на разных портах. Покажите, что кластер автоматически выбирает лидера (LeaderObserved channel). Объясните, почему нужен `BootstrapCluster` только один раз, а потом `AddVoter`.

4. **Raft flow**: Поймите 3 фазы:
    * Leader election (выборы leader'а)
    * Log replication (репликация команд)
    * Safety (гарантии консистентности)

5. **[Raft Setup]**: Настрой Raft-узел. Используй `raft.NewRaft`. Для транспорта используй `raft.NewTCPTransport`, для персистентности — `raftboltdb.BoltStore`, для снапшотов — `raft.FileSnapshotStore`.

6. **HashiCorp Raft setup**: Используйте `github.com/hashicorp/raft` для создания Raft cluster из 3 узлов.

7. **Raft FSM (Finite State Machine)**: Реализуйте `raft.FSM` интерфейс:
    * `Apply(log)` — применяет команду к state
    * `Snapshot()` — создаёт snapshot
    * `Restore(snapshot)` — восстанавливает из snapshot

8. **Raft node bootstrap**: Bootstrap первый узел через `raft.BootstrapCluster()`.

9. **Лидер и Follower.**: Реализуйте endpoint: лидер принимает write-команды, follower отклоняет с `not leader`. Покажите, что чтение с follower возвращает данные, но они могут быть stale (не linearizable). Объясните разницу между `raft.StateLeader`, `StateFollower`, `StateCandidate`.

10. **Raft node join**: Добавьте второй и третий узлы через `raft.AddVoter()`.

11. **Raft transport layer**: Реализуйте transport layer для общения между узлами (TCP/HTTP).

12. **Log Replication.**: Выполните 1000 `raft.Apply` подряд. Покажите, что все 3 узла имеют одинаковый `LastIndex()` и FSM state. Объясните `commitIndex` (применён на majority) vs `lastLogIndex` (записан локально).

13. **[Single Node Cluster]**: Запусти кластер из одного узла. Сделай `raft.BootstrapCluster`. Отправь команду на запись: `raft.Apply([]byte("set key value"), 0)`. Убедись, что FSM применил изменение.

14. **Raft snapshot store**: Реализуйте snapshot store для periodic snapshots state machine.

15. **Snapshotting.**: Реализуйте `FSM.Snapshot()` — сериализация `map[string]string` в `io.Writer` (например, gob/json). Настройте `SnapshotInterval = 20s`, `SnapshotThreshold = 8192`. Покажите, что Raft автоматически вызывает `Snapshot` и создаёт файл снимка. Объясните, зачем нужен snapshot (ограничение роста лога).

16. **Raft Apply**: Leader применяет команду через `raft.Apply(data, timeout)`. Команда реплицируется на majority узлов.

17. **Raft quorum**: Поймите quorum: для 3 узлов quorum = 2. Для 5 узлов quorum = 3. Без quorum кластер не может принимать writes.

18. **Log Compaction и восстановление.**: После snapshot старые логи удаляются. Остановите follower, удалите его log, перезапустите. Покажите, что лидер отправляет `InstallSnapshot` RPC, follower восстанавливает FSM из snapshot, затем догоняет по новым логам. Объясните `Restore(io.ReadCloser)` в FSM.

19. **Raft log replication**: Изучите, как leader реплицирует log entries через AppendEntries RPC.

20. **Запуск одного Raft-узла с in-memory хранилищем.**: Используйте `hashicorp/raft`. Создайте FSM (finite state machine) с методами `Apply`, `Snapshot`, `Restore`. Инициализируйте raft с in-memory транспортом и стабильным хранилищем (например, `/tmp/raft`). Запустите один узел и подайте команду логирования.

21. **[Multi-Node Cluster]**: Подними 3 узла (на разных портах). Вручную добавь 2-й и 3-й узел к лидеру через `raft.AddVoter`.

22. **Raft commit index**: Команда считается committed, когда реплицирована на majority. Только committed entries применяются к FSM.

23. **Добавление узла (Membership Change).**: Используйте `raft.AddVoter` для добавления 4-го узла в работающий кластер. Покажите, что кластер переконфигурируется без downtime. Объясните, как HashiCorp Raft реализует membership changes (одноэтапное добавление, в отличие от joint consensus в оригинальном Raft).

24. **Raft read-only optimization**: Используйте `raft.ReadIndex()` для read-only queries без log replication (быстрее).

25. **Raft log compaction**: Snapshot + log truncation = log compaction. Это предотвращает бесконечный рост log.

26. **Raft membership changes**: Добавляйте/удаляйте узлы через `raft.AddVoter()`, `raft.RemoveServer()`. Raft гарантирует safety при membership changes.

27. **Удаление узла.**: Удалите follower через `raft.RemoveServer`. Покажите, что кластер продолжает работать с новым quorum. Объясните, почему удаление лидера требует перевыборов, и как `RemoveServer` с `ShutdownOnRemove` влияет на поведение.

28. **Кластер из 3 узлов и репликация журнала.**: Настройте три узла на разных портах, используя TCP-транспорт. Добавьте узлы в кластер (bootstrap, join). Отправьте команды на лидера и убедитесь, что они реплицируются на подчинённые узлы.

29. **[Log Replication]**: Отправь команду на запись Лидеру. Убедись, что через полсекунды все 3 FSM (на разных узлах) обновили локальную `map` с одинаковым значением.

30. **Raft single-server cluster**: Для dev/test запустите single-node Raft cluster (bootstrap с одним узлом).

31. **Raft vs Paxos**: Изучите, почему Raft проще для понимания и реализации, чем Paxos, при эквивалентных гарантиях.

32. **Network Partition (Majority/Minority).**: Сымитируйте partition на 5 узлов: 2 узла изолированы от 3. Покажите, что minority (2) не может коммитить записи (не достигает quorum), majority (3) продолжает работать. Объясните, почему это предотвращает split-brain на уровне данных.

33. **Raft-based key-value store**: Реализуйте distributed KV store поверх Raft:
    * `Set(key, value)` → Raft Apply
    * `Get(key)` → read from local FSM (если leader) или forward to leader
    * `Delete(key)` → Raft Apply

34. **Инициализация узла HashiCorp Raft**: Установите популярную библиотеку `github.com/hashicorp/raft`. Напишите конфигурацию локального Raft-узла:
    * Настройте файловое или in-memory хранилище логов (`raft.LogStore`).
    * Настройте стабильное хранилище состояния (`raft.StableStore`) и снапшотов.
    * Создайте TCP-транспорт для связи между узлами с помощью `raft.NewTCPTransport`.

35. **Leader Step Down.**: Изолируйте текущего лидера (drop пакеты к majority). Покажите, что лидер переходит в `StateFollower` (step down) по таймауту, а majority избирает нового лидера. При восстановлении сети старый лидер становится follower. Объясните роль `Term` (epoch) в отклонении stale команд.

36. **[Каверзный кейс — Leader Failover]**: Убей процесс Лидера. Подожди несколько секунд (сработает Election Timeout). Наблюдай, как оставшиеся узлы выбирают нового Лидера. Отправь команду новому Лидеру.

37. **Снэпшоты и восстановление состояния.**: В FSM реализуйте снэпшот каждые N логов. Симулируйте падение узла, затем перезапустите его – он должен догнать лидера из снэпшота и последующих логов.

38. **Raft batching**: Batch multiple Apply calls для снижения overhead.

39. **Raft pipeline**: Pipeline AppendEntries RPCs для повышения throughput.

40. **Linearizable Read.**: Реализуйте read-through-raft: чтение выполняется как `raft.Apply` dummy command (`noop`), после commit возвращается актуальное значение. Сравните с «dirty read» с follower. Объясните, почему `raft.Barrier()` (или `raft.Apply` + `Future.Error()`) даёт linearizable read.

41. **Raft pre-vote**: Реализуйте Pre-Vote extension для предотвращения disruptions при network partitions.

42. **Observability Raft.**: Реализуйте метрики: `raft_state` (leader/follower/candidate), `last_log_index`, `commit_index`, `fsm_apply_latency_seconds`. Настройте алерт: если `commit_index` отстаёт от `last_log_index` на >1000 — возможна network partition или slow follower.

43. **Raft leader lease**: Leader lease для read optimization: если leader уверен, что нет других leaders, можно читать локально.

44. **Raft multi-group**: Для масштабирования разделите data на multiple Raft groups (как в CockroachDB, TiKV).

45. **[Linearizable Reads]**: Включи чтение через Лидера. Если ты читаешь с Follower'а, он может вернуть устаревшие данные. Используй `raft.VerifyLeader()` или `raft.ReadIndex()` перед чтением из FSM, чтобы гарантировать strong consistency (линейзуемость).

46. **Отказ лидера и переизбрание.**: Остановите процесс-лидер. Убедитесь, что кластер выбирает нового лидера и продолжает обрабатывать команды без потерь.

47. **FSM Thread-Safety.**: Реализуйте FSM с `sync.RWMutex`: `Apply` пишет, `Snapshot` читает. Покажите, что `Snapshot` может вызываться параллельно с `Apply` (Raft вызывает Snapshot в отдельной горутине). Объясните, почему `Restore` блокирует Apply и Snapshot.

48. **Raft + application state**: Синхронизируйте application state через Raft:

    * Feature flags
    * Distributed locks metadata
    * Leader election state

49. **Raft snapshot streaming**: Для больших state используйте streaming snapshots вместо in-memory snapshots.

50. **Raft log shipping**: Для disaster recovery ship Raft log в другой datacenter для warm standby.

51. **Persistent FSM с BoltDB.**: Реализуйте FSM, хранящий state в `boltdb` (или `badger`). `Apply` — `db.Update`, `Snapshot` — `db.View` + копия в `io.Writer`. Объясните, почему in-memory map не подходит для production (потеря данных при crash до snapshot).

52. **Raft cluster health**: Мониторьте:

55. **[Snapshots]**: Настрой `SnapshotThreshold` (например, каждые 1000 логов). Отправь 1000 записей. Убедись, что Raft сбросил лог на диск (создал файл `.snap`) и обрезал in-memory логи.

56. **Raft recovery**: После crash узел восстанавливает state из snapshot + log replay.

81. **Применение команды (Apply)**: Если запрос пришел на Лидера, сериализуй команду (`{"op": "set", "key": "foo", "val": "bar"}`) в байты и вызови `raftNode.Apply(bytes, timeout).Response()`. Метод заблокируется, пока команда не реплицируется на большинство фоловеров. После этого она попадет в твой FSM (упр. 852).

82. **Snapshots (Сжатие логов)**: Если ты запишешь миллион ключей, лог Raft станет гигантским, а рестарт ноды займет час. Реализуй методы `Snapshot()` и `Restore()` в своем FSM. В `Snapshot` просто сериализуй текущее состояние твоей `map` в JSON. Raft вызовет этот метод автоматически (согласно настройкам `SnapshotThreshold`), обрежет старые логи и сохранит компактное состояние на диск.

83. **Consistent Reads (Консистентное чтение)**: По правилам Raft, Фоловерам нельзя доверять чтение (у них могут быть старые данные).
    * Вариант 1 (Stale Read): Разреши читать с фоловеров (быстро, но данные могут отставать).
    * Вариант 2 (ReadIndex/Lease): Чтобы получить 100% актуальные данные (Linearizability), чтение должно идти через Лидера. Лидер должен убедиться у большинства фоловеров, что он *всё еще* лидер, прежде чем отдать ответ. Реализуй вызов чтения через метод `raftNode.VerifyLeader()` перед отдачей значения из локальной мапы.
