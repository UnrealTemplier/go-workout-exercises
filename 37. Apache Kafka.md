# Apache Kafka

В этом файле собраны уникальные упражнения по теме **"Apache Kafka"**, отсортированные по возрастанию сложности.

1. **Продюсер Kafka (`segmentio/kafka-go`)**: Установите чисто Go-клиент для Kafka `github.com/segmentio/kafka-go` [395]. Напишите продюсера, который подключается к локальному кластеру Kafka, создает топик `user_events` (с 3 партициями) и отправляет туда сериализованное JSON-сообщение о регистрации пользователя. Обработайте возможные сетевые ошибки отправки.

2. **Кастомное партиционирование по ключу**: По умолчанию Kafka может распределять сообщения по партициям случайно (Round-Robin). Напишите кастомный партиционер (балансировщик). Он должен вычислять хэш от ключа сообщения (например, `UserID`) и на основе этого хэша определять номер партиции. Объясните в комментариях, почему это критически важно для соблюдения строгого порядка обработки событий (Message Ordering) одного пользователя.

3. **Консьюмер-группы и ребалансировка (Rebalance)**: * Напишите консьюмера, входящего в консьюмер-группу `analytics_group`.
    * Запустите три независимых инстанса этого консьюмера (в трех разных терминалах).
    * Отправьте 30 сообщений в топик с 3 партициями. Убедитесь, что каждый инстанс читает строго свою партицию.
    * Остановите один из инстансов консьюмера. Понаблюдайте за процессом ребалансировки (Rebalance), когда оставшиеся консьюмеры перехватывают освободившуюся партицию.

4. **Ручное управление смещениями (Manual Commit)**: По умолчанию консьюмеры коммитят прочитанные сообщения автоматически (Auto-Commit). Настройте консьюмера на ручное подтверждение смещений (`CommitMessages`). Напишите код так, чтобы коммит происходил строго после того, как бизнес-логика обработки сообщения (например, запись в БД) завершилась успешно. Объясните, как это предотвращает потерю сообщений при падении воркера (гарантия At-Least-Once).

5. **Очередь повторных попыток и отравленных сообщений (Retry & DLQ)**: Напишите надежный обработчик платежных событий из Kafka. Если при обработке события возникает временная ошибка (например, недоступен внешний шлюз банка):
    * Программа должна отправить сообщение в топик повторных попыток `payments_retry` с инкрементом счетчика попыток в заголовках (headers).
    * Если количество попыток превысило 3, отправьте сообщение в топик "отравленных" сообщений `payments_dlq` (Dead Letter Queue) для ручного разбора администратором и закомитте смещение в исходном топике, чтобы не заблокировать работу всего консьюмера.

Убедись, что сообщение прочиталось повторно. Напиши код, делающий обработчик идемпотентным (например, запись ID обработанного сообщения в Redis/БД).

80. **[Трассировка (OpenTelemetry)]**: Интегрируй OTel. Продюсер должен инжектить trace context в headers сообщения (Kafka/Rabbit). Консьюмер должен экстрактить контекст из Headers и создавать дочерний span для обработки.

81. Реализуй **Real-time Analytics Pipeline** (Kafka):
- `WebsiteEvents` → Kafka (clickstream, 100K events/sec)
- `Kafka Streams` (или ручной consumer): windowed aggregation (5 min), unique users (HyperLogLog), page views
- Output: `analytics.5min` topic → ClickHouse/Redis for dashboard
- Backfill: replay from `analytics.5min` for any time range

82. **[Мульти-tenant маршрутизация]**: Напиши прокси-продюсер. В зависимости от `tenant_id` в запросе, сообщение должно лететь в Kafka topic `tenant_A_events` или `tenant_B_events`. (Паттерн "Topic per tenant").

83. Реализуй **GDPR-compliant Event Log**:
- Encryption at rest: AES-256 для сообщений в Kafka
- Encryption in transit: TLS 1.3
- Right to be forgotten: `crypto-shredding` (удаление ключа шифрования для пользователя) или `compaction` + tombstone
- Audit log: кто читал/писал какие сообщения
- Data retention: 30 days default, then delete or anonymize

84. Реализуй **Chaos Engineering для MQ**:
- `pumba`/`chaos-mesh`: network partition between Kafka brokers
- Kill leader broker → election → no data loss (if min.insync.replicas met)
- Kill consumer → rebalance → continue from last committed offset
- Inject latency → consumer lag grows → auto-scale consumers (HPA)

85. **Паттерн Outbox (Критически важно!)**: Задача: создать юзера в БД и отправить событие `UserCreated` в брокер. Если БД сохранится, а брокер упадет — консистентность нарушена.
    *   *Решение:* Внутри SQL-транзакции сохраняй юзера в `users` и само сообщение в таблицу `outbox_events`. Делай Commit.
    *   Отдельная горутина (Worker) раз в секунду читает `outbox_events`, отправляет в Kafka и, при успешном `Ack` от Kafka, удаляет строку из БД. Реализуй этот механизм.

86. **Observability**: Инструментируйте producer и consumer OpenTelemetry spans. Каждый send/receive — это отдельный span с атрибутами (topic, partition, offset).

87. Реализуй **Financial Transaction Processing** (Kafka):
- Exactly-once semantics: EOS producer, transactional consumer
- Ordering: `account_id` as partition key → all transactions for account in order
- Idempotency: `transaction_id` deduplication in consumer
- Audit: immutable log, all transactions forever, compacted by account
- Compliance: SOX, PCI-DSS, encryption, access control

88. **Когда использовать Kafka**: High-throughput (миллионы сообщений/сек), event sourcing, log-based архитектура, replay сообщений, stream processing. Overkill для простых задач.
