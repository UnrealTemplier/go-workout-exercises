# Токены аутентификации и авторизация (JWT, PASETO, OAuth2, OIDC)

В этом файле собраны уникальные упражнения по теме **"Токены аутентификации и авторизация (JWT, PASETO, OAuth2, OIDC)"**, отсортированные по возрастанию сложности.

---

1. **Base64url vs Base64**: Покажите разницу между standard и URL-safe кодированием. Почему для токенов в URL/Cookie нужен именно base64url (без `+`, `/`, `=`)?

2. **Атака «alg: none».**: Создайте JWT с `"alg":"none"`, удалите signature, покажите, что наивный парсер может принять его как валидный. Напишите защиту: жёсткий whitelist допустимых алгоритмов (`HS256`, `RS256`, `EdDSA`).

3. **JWT HS256: ручная сборка.**: Сгенерируйте JWT вручную (header + payload + HMAC-SHA256) и через пакет (`github.com/golang-jwt/jwt/v5`). Проверьте подпись. Объясните структуру и почему base64url — не шифрование.

4. **Алгоритмическая путаница (RS256 vs HS256).**: Покажите атаку: сервер проверяет RS256, но атакующий подписывает JWT симметричным HMAC с использованием публичного RSA-ключа как секрета. Напишите защиту: раздельные ключи для симметричных и асимметричных алгоритмов.

5. **JWKS endpoint.**: Реализуйте endpoint `/.well-known/jwks.json`, который отдаёт публичные ключи в формате JWK. Напишите middleware, который загружает JWKS, кэширует и проверяет JWT подпись по `kid` (key ID) из header.

6. **Анатомия JWT**: Без библиотек! Возьми строку `{"alg":"HS256"}` (заголовок) и `{"user_id":42}` (нагрузка). Закодируй обе части в Base64Url. Соедини через точку. Сгенерируй HMAC-SHA256 подпись от этой строки. Добавь подпись третьей частью. Ты только что руками создал валидный JWT.

7. **JWT алгоритмы и атаки**: Покажите 3 критических атаки:
    * `alg: none` bypass
    * Algorithm confusion (RS256 → HS256)
    * JKU/X5U header injection

8. **PASETO v4.local (symmetric).**: Используйте пакет `github.com/o1egl/paseto` (или аналог). Создайте токен с claims (`user_id`, `exp`), зашифруйте ключом из `crypto/rand` (32 байта). Объясните, почему в PASETO нет поля `alg` и почему payload зашифрован, а не просто base64.

9. **JWT всегда verificate алгоритм**: Настройте `jwt.WithValidMethods([]string{"RS256"})`. Без этого ваш код уязвим к algorithm confusion.

10. **JWT не для sessions**: Покажите, почему JWT плохи как сессионные токены (нельзя отозвать без state, большие по размеру, leak в логах).

11. **JWT short-lived access + refresh**: Реализуйте пару: access token (15 мин) + refresh token (30 дней в БД с revocation). Это standard modern pattern.

12. **Уязвимость JWT "alg: none"**: JWT позволяет клиенту самому указывать алгоритм подписи. Возьми библиотеку JWT. Создай токен, где в заголовке указано `"alg": "none"`, и удали подпись. Напиши "наивный" валидатор, который доверяет алгоритму из заголовка, и убедись, что он пропустит этот фейковый токен. (Всегда жестко задавай алгоритм при валидации JWT!).

13. **PASETO v4.public (asymmetric).**: Создайте подписанный токен с Ed25519. Сравните с JWT RS256: размер токена, скорость проверки, отсутствие алгоритмической путаницы. Объясните, почему PASETO «secure by default».

14. **JWT в URL/Cookie — опасность**: Покажите, как JWT в URL попадает в логи nginx/прокси, в Referer header. Используйте HttpOnly Cookie для веб-приложений.

15. **PASETO introduction**: Установите `aidanwoods.dev/go-paseto`. PASETO = Platform-Agnostic Security Tokens, создан чтобы решить все проблемы JWT.

16. **OAuth2 Authorization Code + PKCE.**: Реализуйте клиентское веб-приложение: endpoint `/auth` (редирект на IdP), `/callback` (обмен code на token). Добавьте PKCE (`code_verifier`/`code_challenge`). Объясните, зачем PKCE при отсутствии client secret (SPA, мобильные приложения).

17. **PASETO v4.public**: Используйте Ed25519 для public tokens (аналог JWT с асимметричной подписью). Нет проблем с algorithm confusion.

18. **Знакомство с PASETO (Local)**: Установи библиотеку (например, `aidarkhanov/nanoid` или `aead/paseto`). PASETO (Platform-Agnostic Security Tokens) лишен проблем JWT — версия протокола и алгоритм жестко зафиксированы. Сгенерируй `v4.local` токен (симметричное шифрование). Обрати внимание, что данные внутри зашифрованы (в отличие от JWT, который просто закодирован в Base64).

19. **PASETO v4.local**: Используйте XChaCha20-Poly1305 + BLAKE2b для encrypted tokens (конфиденциальность + аутентичность). У JWT нет standard encrypted mode.

20. **PASETO implicit assertions**: Добавьте в токен данные, которые аутентифицируются, но не включаются в payload (например, IP-адрес, user agent).

21. **OIDC: проверка id_token.**: Реализуйте проверку JWT `id_token` от Google/Auth0: валидация `iss`, `aud`, `exp`, `nonce`. Извлеките claims (`sub`, `email`, `email_verified`). Объясните, чем `id_token` отличается от `access_token`.

22. **PASETO footer**: Используйте footer для public данных (key ID), которые аутентифицируются, но не шифруются.

23. **Создание локального токена PASETO (v2.local).**: Используйте библиотеку `aidantwoods/go-paseto` (или аналог). Создайте симметричный ключ, зашифруйте payload (JSON с `user_id`, `exp`). Расшифруйте и проверьте.

24. **[JWT — База]**: Используй `github.com/golang-jwt/jwt/v5`. Создай HS256 токен с claims (`user_id`, `exp`). Подпиши его секретом.

25. **PASETO (Public)**: Сгенерируй `v4.public` токен, используя Ed25519 ключи (из упр. 721). Это асимметричный токен: сервер подписывает его приватным ключом, а любые микросервисы могут проверить его валидность, имея только публичный ключ.

26. **Macaroons (Bearer tokens с caveats)**: Реализуйте macaroon через `gopkg.in/macaroon.v2`. Caveats позволяют создавать tokens с ограничениями (read-only, IP-bound, time-limited).

27. **Refresh Token Rotation.**: Реализуйте хранение refresh tokens в БД с полями `token_hash`, `family_id`, `issued_at`, `expires_at`, `revoked`. При обмене refresh → access выдавайте новую пару, инвалидируйте старую. Объясните, как это защищает от replay-атак и parallel refresh.

28. **Third-party caveats**: Создайте macaroon с third-party caveat (должен быть discharge от другого сервиса). Это分布式 authorization без central database.

29. **Biscuit tokens**: Изучите `github.com/biscuit-auth/biscuit-go`. Biscuit — современный формат с Datalog-based policies и оффлайн-верификацией.

30. **[Каверзный кейс — alg=none]**: Напиши мок-атаку на JWT: вручную создай токен с заголовком `{"alg":"none"}` и пустой подписью. Убедись, что строгий валидатор (`jwt.Parse` с проверкой метода) отклоняет его.

31. **Session tokens в Redis (simple и надёжно)**: Для веб-приложений используйте 32-байтовый случайный token + Redis для state. Проще, безопаснее, revocable в любой момент.

32. **Server-side sessions vs JWT.**: Реализуйте сессии в Redis с `session_id` в `HttpOnly; Secure; SameSite=Strict` cookie. Сравните с stateless JWT: возможность мгновенной инвалидации (logout), размер cookie, проблема с масштабированием хранилища. Объясните, когда что использовать.

33. **OAuth2 Flow (Клиент)**: Используй пакет `golang.org/x/oauth2`. Зарегистрируй OAuth приложение в GitHub. Сгенерируй `AuthCodeURL`, перенаправь туда пользователя, получи `code` в callback-роуте и обменяй его на Access Token.

34. **OAuth2 Authorization Code Flow**: Реализуйте полный flow: redirect на провайдера → получение code → обмен на access/refresh token → использование access token.

35. **Публичный токен PASETO (v2.public).**: Сгенерируйте пару Ed25519, подпишите токен с утверждениями (claims). Проверьте подпись публичным ключом. Покажите, что без приватного ключа невозможно создать валидный токен.

36. **PKCE (Proof Key for Code Exchange)**: Добавьте PKCE в ваш OAuth2 flow (обязателен для SPA и mobile приложений, рекомендуется для всех). Используйте S256 метод.

37. **OAuth2 state parameter**: Всегда используйте криптографически случайный `state` параметр для защиты от CSRF. Без state ваш OAuth flow уязвим.

38. **API Key с HMAC-подписью запроса.**: Реализуйте AWS Signature v4-style подпись: canonical request → HMAC-SHA256 с секретом. Middleware проверяет подпись, timestamp (±5 минут), replay (nonce cache). Объясните, почему API keys в query string (`?api_key=...`) утечкают в логах.

39. **[PASETO — Замена JWT]**: Установи `github.com/o1egl/paseto`. Создай токен V4 (на базе Ed25519, публичная криптография). Подпиши приватным ключом.

40. **OAuth2 client credentials flow**: Реализуйте machine-to-machine аутентификацию для backend-сервисов.

41. **Защита OAuth2 (State Parameter)**: При генерации `AuthCodeURL` передай криптографически случайную строку в параметр `state`. Сохрани её в HttpOnly куку. В callback-роуте проверь, что `state` от провайдера (GitHub) совпадает с твоей кукой. Это защитит от CSRF-атак на логин.

42. **OAuth2 Device Authorization Grant**: Реализуйте flow для CLI/SmartTV устройств, где пользователь вводит код на другом устройстве.

43. **Refresh token rotation в OAuth2**: Автоматически обновляйте access tokens и обрабатывайте refresh token revocation.

44. **Scope-based access control.**: Реализуйте middleware, который извлекает scopes из токена (OAuth2) и проверяет требуемые scopes для endpoint (`read:users`, `write:posts`). Объясните разницу между scopes (что разрешено делать) и claims (кто пользователь).

45. **Сравнение JWT и PASETO.**: Напишите пример создания JWT с HS256 и с RS256. Покажите уязвимость JWT: подпись `alg=none` (если библиотека это позволяет) или путаница алгоритмов. Продемонстрируйте, как PASETO избавлен от этих проблем.

46. Проверь PASETO токен публичным ключом. Извлеки claims. Объясни, почему PASETO безопаснее JWT (нет гибкости в выборе алгоритма, устраняет уязвимости с `alg`).

47. **OIDC discovery**: Используйте `.well-known/openid-configuration` для получения endpoints и public keys провайдера. Не хардкодьте endpoints.

48. **OIDC ID Token validation**: Верифицируйте ID Token по всем правилам: issuer, audience, expiration, nonce, signature через JWKS.

49. **OpenID Connect (OIDC)**: OAuth2 дает только токен для API. OIDC дает стандартизированный профиль юзера. Используй `github.com/coreos/go-oidc`. Настрой провайдера (например, Google), получи ID Token, валидируй его подписи (через публичные ключи Google) и распарси Email и Имя юзера.

50. **DPoP (Demonstrating Proof-of-Possession).**: Реализуйте упрощённый DPoP: JWT, подписанный ключом клиента (Ed25519), содержащий `htm` (HTTP method) и `htu` (URI). Сервер проверяет подпись и привязку к запросу. Объясните, как это защищает от theft bearer token (токен не работает без приватного ключа клиента).

51. **JWKS (JSON Web Key Set)**: Получайте public keys провайдера через JWKS endpoint. Кэшируйте их, обновляйте по расписанию и по kid miss.

52. **Go OAuth2 client библиотека**: Используйте `golang.org/x/oauth2` для standard flow и `github.com/coreos/go-oidc/v3` для OIDC.

53. **[OAuth2 Client]**: Используй `golang.org/x/oauth2`. Настрой конфиг для провайдера (например, GitHub или Google). Реализуй HTTP-обработчик `/login`, который редиректит пользователя на страницу авторизации.

54. **OAuth2 Authorization Server**: Реализуйте собственный OAuth2 сервер через `github.com/go-oauth2/oauth2/v4`. Поймите internals.

55. **Refresh Token Rotation.**: Реализуйте механизм: при использовании refresh token выпускается новый access token и новый refresh token, старый инвалидируется. Обнаружьте повторное использование refresh token и отзовите все токены пользователя.

56. **Scopes и audience**: Корректно используйте `scope` (права доступа) и `audience` (для какого сервиса токен). audience особенно важен в микросервисах.

57. **Безопасные Session Cookies**: Если ты не используешь токены (у тебя монолит и браузер). Напиши хендлер, который ставит сессионную куку. Установи флаги: `HttpOnly: true` (недоступно из JS/XSS), `Secure: true` (только HTTPS) и `SameSite: http.SameSiteStrictMode` (защита от CSRF).

58. **PASETO с footer.**: Добавьте в токен footer (незашифрованные, но аутентифицированные данные), например, `kid` (Key ID). При проверке токена убедитесь, что footer совпадает с ожидаемым.

59. **Token introspection endpoint**: Реализуйте валидацию opaque access tokens через introspection endpoint (RFC 7662).

60. **Token revocation endpoint**: Реализуйте revocation endpoint (RFC 7009) для immediate invalidation tokens.

61. Реализуй обработчик `/callback`, который принимает `code`, обменивает его на `AccessToken` (`Exchange`) и делает API-запрос к провайдеру для получения email пользователя.

62. **Social login integration**: Интегрируйте Google, GitHub, Apple login в ваше приложение. Покажите особенности каждого провайдера.

63. **Refresh Токены (Лучшие практики)**: Архитектурная задача. Access Token (PASETO) живет 15 минут. Refresh Token — это просто случайная строка на 64 символа (crypto/rand). Храни в БД не сам Refresh Token, а его *хэш* (например, SHA-256 или bcrypt). При получении Refresh Token от клиента, хэшируй его и ищи в БД. Если БД украдут — хакеры не смогут сгенерировать новые Access токены!

64. **Реализация OAuth2 Authorization Code Flow (конфиденциальный клиент).**: Напишите HTTP-сервер, который перенаправляет пользователя на Google/Facebook, получает callback с кодом, обменивает код на токен через `golang.org/x/oauth2`. Сохраните access и refresh токены.

65. **Проверка ID Token (OIDC).**: При аутентификации через Google получите ID Token. Проверьте JWT-подпись с помощью `JWK` (JSON Web Key Set), полученных с `https://accounts.google.com/.well-known/openid-configuration`. Используйте `github.com/coreos/go-oidc`.

66. **Реализация собственного OAuth2-сервера (минимального).**: Создайте сервер, выдающий access token по client credentials grant. Используйте библиотеку `go-oauth2/oauth2`. Защитите ресурс, требующий валидный токен.
