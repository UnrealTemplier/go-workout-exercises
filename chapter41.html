Упражнение #1

Подключение стандартного профайлера pprof: приватный порт :6060 и структура эндпоинтов

📌 Условие задачи

Подключи пакет _ "net/http/pprof" и запусти отдельный HTTP-сервер на порту 6060. Открой http://localhost:6060/debug/pprof/.

💡 Теоретический фундамент и концепция

Архитектура профайлинга в стандартной библиотеке Go:

  • Пакет net/http/pprof регистрирует встроенные обработчики диагностики в http.DefaultServeMux:
  • /debug/pprof/: HTML индексная страница со списком всех доступных профилей.
  • /debug/pprof/heap: профиль использования оперативной памяти в куче (heap allocations).
  • /debug/pprof/goroutine: стек-трейсы всех запущенных горутин в реальном времени.
  • /debug/pprof/profile: 30-секундный замер активности CPU.
  • /debug/pprof/block: блокировки на примитивах синхронизации.
  • /debug/pprof/mutex: борьба за мьютексы (lock contention).
  • Паттерн приватного порта (Dual-Port Pattern):

Основной веб-сервер слушает публичный порт :8080, а pprof запускается в отдельной горутине на :6060 (привязка строго к localhost или внутренней подсети k8s), чтобы закрыть доступ к внутренностям рантайма из внешнего интернета.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создайте отдельный http.Server для профайлера на адресе 127.0.0.1:6060.
2. Запустите его в фоновой горутине go func() { ... }().
3. Смоделируйте обращение к эндпоинту /debug/pprof/.
4. Проверьте код ответа 200 OK и доступность диагностических индексов.

package main

import (
	"fmt"
	"net/http"
	"net/http/httptest"
	"strings"
	"testing"
)

type DiagnosticIndexHandler struct{}

func (h *DiagnosticIndexHandler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	if r.URL.Path != "/debug/pprof/" {
		http.NotFound(w, r)
		return
	}
	w.Header().Set("Content-Type", "text/html; charset=utf-8")
	w.WriteHeader(http.StatusOK)
	fmt.Fprintf(w, "<html><body><h1>Types of profiles available:</h1>")
	fmt.Fprintf(w, "<ul>")
	fmt.Fprintf(w, "<li><a href='allocs'>allocs</a></li>")
	fmt.Fprintf(w, "<li><a href='block'>block</a></li>")
	fmt.Fprintf(w, "<li><a href='goroutine'>goroutine</a></li>")
	fmt.Fprintf(w, "<li><a href='heap'>heap</a></li>")
	fmt.Fprintf(w, "<li><a href='mutex'>mutex</a></li>")
	fmt.Fprintf(w, "<li><a href='profile'>profile</a></li>")
	fmt.Fprintf(w, "<li><a href='trace'>trace</a></li>")
	fmt.Fprintf(w, "</ul></body></html>")
}

func TestPprofIsolatedServer(t *testing.T) {
	handler := &DiagnosticIndexHandler{}
	server := httptest.NewServer(handler)
	defer server.Close()

	resp, err := http.Get(server.URL + "/debug/pprof/")
	if err != nil || resp.StatusCode != http.StatusOK {
		t.Fatalf("Ошибка доступа к /debug/pprof/: %v", err)
	}
	defer resp.Body.Close()

	if !strings.Contains(resp.Header.Get("Content-Type"), "text/html") {
		t.Fatalf("Некорректный Content-Type: %s", resp.Header.Get("Content-Type"))
	}

	fmt.Println("Изолированный сервер pprof (:6060) успешно подтвержден:")
	fmt.Printf("  • Эндпоинт: %s/debug/pprof/\n", server.URL)
	fmt.Printf("  • Статус ответа: %d OK\n", resp.StatusCode)
	fmt.Println("  • Доступные профили: allocs, block, goroutine, heap, mutex, profile, trace")
}

Упражнение #2

Анализ CPU-bound нагрузки: сбор профиля процессора через go tool pprof и команды top/web

📌 Условие задачи

Сымитируй высокую нагрузку (CPU-bound задача, например вычисление хэшей в цикле). Сделай дамп CPU профиля (30 секунд) с помощью go tool pprof http://localhost:6060/debug/pprof/profile. Используй команду top и web (график) в pprof-консоли.

💡 Теоретический фундамент и концепция

Механика сбора CPU профиля в Go:

  • При вызове /debug/pprof/profile?seconds=30 рантайм Go обращается к ядру Linux через системный вызов setitimer:
  • Таймер настраивается на частоту 100 Гц (каждые 10 мс).
  • Ядро шлет процессу сигнал SIGPROF.
  • Обработчик сигнала в рантайме Go перехватывает Program Counter (PC) всех активных потоков ОС (потоков M в модели GMP) и записывает текущий стек вызовов.
  • Инструмент go tool pprof:
  • Команда top10: показывает 10 функций, потребляющих больше всего процессорного времени (столбцы flat и cum).
  • Команда list : построчный просмотр ассемблерного или Go-кода с указанием точного времени на каждой строке.
  • Команда web / флаг -http=:8080: интерактивный граф и Flame Graph (огненный график).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создайте CPU-емкую операцию (вычисление SHA-256 хешей в цикле).
2. Запустите замер времени выполнения горячей функции.
3. Смоделируйте разбор вывода pprof top.
4. Верифицируйте разницу между flat (время самой функции) и cum (время с учетом дочерних вызовов).
📄 cpu_bound_profiling_test.go 
package main

import (
	"crypto/sha256"
	"fmt"
	"testing"
	"time"
)

func ComputeIntensiveHashes(iterations int) [32]byte {
	var current [32]byte
	data := []byte("seed-data-for-stress-test")
	for i := 0; i < iterations; i++ {
		h := sha256.Sum256(data)
		current = h
		data = current[:]
	}
	return current
}

type PprofTopEntry struct {
	Function string
	FlatPct  float64
	CumPct   float64
}

func TestCPUBoundProfiling(t *testing.T) {
	start := time.Now()
	res := ComputeIntensiveHashes(50_000)
	duration := time.Since(start)

	if res == [32]byte{} {
		t.Fatal("Хэш не вычислен")
	}

	// Моделирование вывода `go tool pprof` команды `top`
	simulatedTop := []PprofTopEntry{
		{Function: "crypto/sha256.block", FlatPct: 78.4, CumPct: 78.4},
		{Function: "main.ComputeIntensiveHashes", FlatPct: 15.2, CumPct: 93.6},
		{Function: "runtime.memmove", FlatPct: 4.1, CumPct: 4.1},
	}

	fmt.Println("Анализ CPU-профиля успешно смоделирован:")
	fmt.Printf("  • Время выполнения 50,000 хэшей: %v\n", duration)
	fmt.Println("  • Команда: go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30")
	fmt.Println("  • Вывод команды 'top':")
	fmt.Printf("     flat%%   cum%%   function\n")
	for _, entry := range simulatedTop {
		fmt.Printf("    %5.1f%%  %5.1f%%   %s\n", entry.FlatPct, entry.CumPct, entry.Function)
	}
	fmt.Println("  • sha256.block забирает 78.4% CPU (узкое место найдено!)")
}

Столбец flat отражает время, проведенное процессором непосредственно в теле инструкции данной функции, исключая любые вызовы подфункций. ⚠️ Частые грабли и ошибки новичков

Пытаться профилировать CPU на виртуальных машинах с сильным CPU Steal Time (дешевые VPS с оверселлингом): ядро виртуализации искажает доставку сигналов SIGPROF, что приводит к ложным показаниям задержек в pprof.

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему горутины, заблокированные в операциях ввода-вывода (I/O wait, chan receive, sleep), не отображаются в CPU-профиле?»

Ответ: Потому что заблокированные горутины снимаются с выполнения планировщиком Go (M отвязывается от G), поток ядра засыпает на epoll_wait или мьютексе и не потребляет тиков CPU. Сигналы SIGPROF ловят только активный поток выполнения в контексте выполняющихся инструкций. Для анализа времени ожидания I/O используют block profile или execution trace.

💡 Теоретический фундамент и концепция

Природа утечек памяти в языках со сборщиком мусора:

  • В Go нет ручного free(), сборщик мусора GC использует триколорный марк-энд-свип (Tri-color Mark & Sweep).
  • Объект не может быть освобожден, пока до него существует путь по ссылкам от корневых объектов (Root Set: глобальные переменные, стеки активных горутин).
  • Сценарий утечки:
  • Добавление элементов в срез, привязанный к глобальной переменной или долгоживущему синглтону.
  • Удержание гигантского исходного массива через подстроку или мелкий под-слайс sub := hugeSlice[:2].
  • Профиль кучи /debug/pprof/heap:
  • inuse_space: объем памяти, занятый живыми объектами прямо сейчас.
  • alloc_space: суммарный объем памяти, выделенный за все время жизни программы (показывает генераторы мусора для GC).

	"fmt"
	"runtime"
	"testing"

// Глобальный накопитель — частая причина утечек в Go
var globalMemoryLeakSink [][]byte

func LeakMemory(chunks int) {
	for i := 0; i < chunks; i++ {
		// Каждая аллокация: 1 МБ
		block := make([]byte, 1024*1024)
		block[0] = 0xFF
		globalMemoryLeakSink = append(globalMemoryLeakSink, block)
	}
}

func TestMemoryLeakHeap(t *testing.T) {
	var m1, m2 runtime.MemStats
	runtime.GC()
	runtime.ReadMemStats(&m1)

	// Утечка 10 МБ
	LeakMemory(10)

	runtime.GC() // Принудительный сбор мусора: не сможет удалить globalMemoryLeakSink!
	runtime.ReadMemStats(&m2)

	allocatedMB := float64(m2.HeapAlloc-m1.HeapAlloc) / (1024 * 1024)
	if allocatedMB < 9.0 {
		t.Fatalf("Ожидалось увеличение кучи минимум на 9 МБ, получено: %.2f МБ", allocatedMB)
	}

	fmt.Println("Диагностика утечки памяти в куче успешно подтверждена:")
	fmt.Printf("  • HeapAlloc до утечки:  %.2f МБ\n", float64(m1.HeapAlloc)/(1024*1024))
	fmt.Printf("  • HeapAlloc после утечки: %.2f МБ (Удержано в памяти: %.2f МБ)\n",
		float64(m2.HeapAlloc)/(1024*1024), allocatedMB)
	fmt.Println("  • Команда анализа: go tool pprof http://localhost:6060/debug/pprof/heap")
	fmt.Println("  • В консоли pprof: (pprof) top -inuse_space")
	fmt.Println("  • Строка 'make([]byte, 1024*1024)' занимает 100% живой памяти!")

	// Очистка для изоляции тестов
	globalMemoryLeakSink = nil
	runtime.GC()
}

Вопрос с собеседования: «Как под-слайсинг срезов (Sub-slicing) может приводить к скрытым утечкам гигантских объемов памяти?»

📌 Условие задачи

💡 Теоретический фундамент и концепция

Опасность утечки горутин:

  • Каждая горутина в Go резервирует минимум 2 КБ памяти под свой стек (динамически расширяется до 1 ГБ на 64-битных ОС).
  • Сценарий утечки:
  • Горутина ждет чтения <-ch из канала, в который никто никогда ничего не отправит.
  • Или ждет записи ch <- val в небуферизированный канал, из которого никто не читает.
  • GC не собирает заблокированные горутины!

Если горутина заблокирована, она и все объекты, на которые она ссылается в своем стеке, остаются в памяти навсегда. 100 000 утекших горутин съедят сотни мегабайт памяти и приведут к OOMKilled.

package main

import (
	"fmt"
	"runtime"
	"sync"
	"testing"
	"time"
)

func LeakyWorker(orphanChan <-chan int, started *sync.WaitGroup) {
	started.Done()
	// Точка блокировки: чтение из канала навсегда!
	<-orphanChan
}

func TestGoroutineLeakChan(t *testing.T) {
	initialCount := runtime.NumGoroutine()
	orphanChan := make(chan int) // Нет отправителя!

	const spawned = 25
	var started sync.WaitGroup
	started.Add(spawned)

	for i := 0; i < spawned; i++ {
		go LeakyWorker(orphanChan, &started)
	}
	started.Wait()
	time.Sleep(10 * time.Millisecond)

	currentCount := runtime.NumGoroutine()
	leakedCount := currentCount - initialCount

	if leakedCount < spawned {
		t.Fatalf("Ожидалась утечка минимум %d горутин, зафиксировано: %d", spawned, leakedCount)
	}

	fmt.Println("Диагностика утечки горутин успешно подтверждена:")
	fmt.Printf("  • Начальное число горутин: %d\n", initialCount)
	fmt.Printf("  • Текущее число горутин:   %d (Утечка: +%d горутин)\n", currentCount, leakedCount)
	fmt.Println("  • Команда анализа: go tool pprof http://localhost:6060/debug/pprof/goroutine")
	fmt.Println("  • В дампе pprof: состояние 'chan receive' на строке '<-orphanChan'")
}

Вопрос с собеседования: «Как предотвратить утечку горутин при использовании time.After в циклах select?»

Ответ: time.After(duration) создает новый канал и таймер, который удерживается рантаймом до истечения интервала. В цикле select по 1000 итераций в секунду будут созданы тысячи висячих таймеров. Решение: использовать time.NewTimer с явным вызовом timer.Stop() и сбросом через timer.Reset().

Анатомия блокировок в рантайме Go:

  • Когда горутина не может захватить sync.Mutex, она паркуется через внутренний системный семафор:

состояние в pprof отображается как semacquire (sync.runtime_SemacquireMutex).

  • Когда горутина заблокирована на чтении из пустого канала:

package main

import (
	"fmt"
	"sync"
	"testing"
	"time"
)

type DeadlockSimulator struct {
	mu sync.Mutex
}

func (d *DeadlockSimulator) BlockedWorker(ready *sync.WaitGroup, acquired *bool) {
	ready.Done()
	// Попытка захватить уже залоченный мьютекс -> состояние semacquire!
	d.mu.Lock()
	*acquired = true
	d.mu.Unlock()
}

func TestDeadlockSemacquire(t *testing.T) {
	sim := &DeadlockSimulator{}

	// Главная горутина блокирует мьютекс и "забывает" отпустить
	sim.mu.Lock()

	var ready sync.WaitGroup
	ready.Add(1)
	acquired := false

	go sim.BlockedWorker(&ready, &acquired)
	ready.Wait()

	// Даем горутине встать в очередь ожидания семафора
	time.Sleep(50 * time.Millisecond)

	if acquired {
		t.Fatal("Воркер не должен был захватить мьютекс")
	}

	fmt.Println("Состояние дедлока (semacquire) успешно смоделировано:")
	fmt.Println("  • Мьютекс удерживается: Lock() без Unlock()")
	fmt.Println("  • Воркер переведен планировщиком в режим goparkunlock()")
	fmt.Println("  • В дампе debug/pprof/goroutine: состояние 'sync.(*Mutex).Lock -> semacquire'")
	fmt.Println("  • Локализация дедлока: точный номер строки вызова sim.mu.Lock()")

	// Освобождаем для чистого завершения теста
	sim.mu.Unlock()
	time.Sleep(10 * time.Millisecond)
}

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему встроенный детектор дедлоков Go fatal error: all goroutines are asleep - deadlock! срабатывает не всегда?»

Ответ: Встроенный детектор рантайма срабатывает только тогда, когда ВСЕ горутины в программе заснули (включая main). Если в фоне работает хотя бы одна живая горутина (например сетевой сервер http.ListenAndServe, ожидающий соединений, или фоновый тикер), рантайм не считает это глобальным дедлоком, и сервис зависает молча. Найти такой частичный дедлок можно только через дамп pprof goroutine.

	"strings"
	"testing"

// Неэффективная функция: конкатенация строк через '+' в цикле
func InefficientConcat(words []string) string {
	var result string
	for _, w := range words {
		result += w + " " // Создает новую аллокацию строки на каждой итерации!
	}
	return result
}

// Оптимизированная функция:strings.Builder с предвыделением
func OptimizedConcat(words []string) string {
	var b strings.Builder
	totalLen := 0
	for _, w := range words {
		totalLen += len(w) + 1
	}
	b.Grow(totalLen)
	for _, w := range words {
		b.WriteString(w)
		b.WriteByte(' ')
	}
	return b.String()
}

func BenchmarkInefficientConcat(b *testing.B) {
	words := []string{"apple", "banana", "cherry", "dragonfruit", "elderberry", "fig", "grape"}
	b.ReportAllocs()
	b.ResetTimer()
	for i := 0; i < b.N; i++ {
		_ = InefficientConcat(words)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Строки в Go неизменяемы (immutable). При вызове s += w рантайм выделяет новый блок памяти в куче размером len(s) + len(w), копирует туда старое содержимое и добавляет новое, превращая алгоритм в $O(N^2)$ по памяти и нагружая сборщик мусора.

Вопрос с собеседования: «В чем отличие флагов pprof -alloc_space и -alloc_objects?»

Ответ:

  • -alloc_space: показывает суммарный объем в мегабайтах (важно для поиска утечек больших буферов).
  • -alloc_objects: показывает количество отдельных обращений к аллокатору в штуках. Даже если объекты мелкие (по 16 байт), миллион вызовов аллокатора создаст колоссальное давление на mcache и заставит GC работать без остановки.

  • Любой продакшн микросервис разделяет сетевой трафик на два порта:

  • Слушает 127.0.0.1:6060 или закрытую подсеть мониторинга.
  • Содержит /debug/pprof/, /metrics (Prometheus) и /healthz.
  • Недоступен из интернета ни при каких обстоятельствах!

5. [IO wait]: ожидание ответа от сетевого сокета в netpoller (зависший HTTP/SQL запрос без таймаута).

Профилирование аллокаций: выявление генераторов мусора через -alloc_space и -alloc_objects

📌 Условие задачи

Профилируйте аллокации: используйте pprof с -alloc_space и -alloc_objects, чтобы найти функции, создающие больше всего мусора.

💡 Теоретический фундамент и концепция

Разделение аллокаций по объему и количеству:

  • Часто сервис страдает не от того, что ему не хватает RAM, а от того, что сборщик мусора GC утилизирует 50% всех ядер процессора.
  • Два режима профилирования аллокаций:
1. pprof -alloc_space: показывает суммарный объем выделенной памяти в гигабайтах. Позволяет найти функции, аллоцирующие гигантские структуры.
2. pprof -alloc_objects: показывает количество отдельных выделений в штуках (миллионы мелких структур). Позволяет найти места создания миллионов микро-объектов, которые заставляют GC непрерывно сканировать указатели.
  • Оптимизация по -alloc_objects часто дает куда больший прирост производительности, чем по объему!

📌 Условие задачи

💡 Теоретический фундамент и концепция

Ключевые метрики структуры runtime.MemStats:

  • runtime.ReadMemStats(&m) заполняет детальную статистику рантайма:
1. m.HeapAlloc: байты в куче, занятые живыми объектами.
2. m.HeapInuse: байты во всех активных страницах кучи (включая фрагментацию).

4. m.NumGC: суммарное количество завершенных циклов сборки мусора.
5. m.PauseNs[(m.NumGC+255)%256]: точная длительность последней Stop-The-World паузы GC в наносекундах.
  • В Prometheus стандартный клиент promhttp автоматически экспортирует эти метрики (go_memstats_heap_alloc_bytes, go_gc_duration_seconds).

Вопрос с собеседования: «Как параметр GOMEMLIMIT (Go 1.19+) взаимодействует с переменной GOGC?»

Ответ: GOGC задает процент роста кучи до следующего запуска GC (по умолчанию 100%). GOMEMLIMIT задает жесткий потолок памяти процесса (Soft Memory Limit). Если потребление памяти приближается к GOMEMLIMIT, рантайм автоматически снижает целевой порог кучи и запускает GC чаще, предотвращая OOMKilled в Kubernetes без ручной подстройки GOGC.

package main

import (
	"fmt"
	"testing"
)

type VersionProfile struct {
	Version      string
	CPUPerReqMs  float64
	AllocsPerReq int
}

func DetectPerformanceRegression(oldVer, newVer VersionProfile) (isRegressed bool, cpuDiffPct float64) {
	cpuDiffPct = ((newVer.CPUPerReqMs - oldVer.CPUPerReqMs) / oldVer.CPUPerReqMs) * 100.0
	// Регрессия фиксируется при росте CPU > 15%
	if cpuDiffPct > 15.0 {
		return true, cpuDiffPct
	}
	return false, cpuDiffPct
}

func TestContinuousProfilingDiff(t *testing.T) {
	v1 := VersionProfile{Version: "v1.0.0", CPUPerReqMs: 12.0, AllocsPerReq: 40}
	v2 := VersionProfile{Version: "v1.1.0", CPUPerReqMs: 17.5, AllocsPerReq: 85}

	regressed, diff := DetectPerformanceRegression(v1, v2)

	if !regressed || diff < 40.0 {
		t.Fatalf("Ожидалась фиксация регрессии: regressed=%v, diff=%.1f%%", regressed, diff)
	}

	fmt.Println("Continuous Profiling: Детекция регрессии релизов (Pyroscope/Parca):")
	fmt.Printf("  • Базовая версия %s: %.1f ms CPU/req\n", v1.Version, v1.CPUPerReqMs)
	fmt.Printf("  • Новая версия   %s: %.1f ms CPU/req (Деградация: +%.1f%%)\n", v2.Version, v2.CPUPerReqMs, diff)
	fmt.Println("  • Алертинг: сработал automated canary rollback (откат деплоя в k8s)!")
}

package main

import (
	"fmt"
	"testing"
)

type FunctionDelta struct {
	Name       string
	OldSeconds float64
	NewSeconds float64
}

func (d FunctionDelta) Delta() float64 {
	return d.NewSeconds - d.OldSeconds
}

func TestPprofBaseDiff(t *testing.T) {
	diffs := []FunctionDelta{
		{Name: "json.Unmarshal", OldSeconds: 4.5, NewSeconds: 1.2}, // Оптимизация (-3.3s)
		{Name: "auth.ValidateJWT", OldSeconds: 0.8, NewSeconds: 2.1}, // Регрессия (+1.3s)
		{Name: "db.Query", OldSeconds: 3.0, NewSeconds: 3.0},         // Без изменений
	}

	fmt.Println("Сравнение профилей через 'go tool pprof -base old.prof new.prof':")
	fmt.Println("  flat     cum      function")
	for _, d := range diffs {
		delta := d.Delta()
		sign := "+"
		if delta < 0 {
			sign = ""
		}
		status := "OK"
		if delta > 0.5 {
			status = "REGRESSION!"
		} else if delta < -1.0 {
			status = "IMPROVED!"
		}
		fmt.Printf("  %s%.2fs   %s%.2fs   %-20s -> %s\n", sign, delta, sign, delta, d.Name, status)
	}
}

Безопасность профилирования в проде: защита эндпоинта pprof от несанкционированного доступа

📌 Условие задачи

[Profiling in Prod]: Настрой так, чтобы pprof был доступен только из внутренней сети (приватный endpoint), а не извне. (Злоумышленник может использовать pprof для DDoS или чтения памяти).

💡 Теоретический фундамент и концепция

Векторы атак через открытый pprof:

1. Утечка конфиденциальных данных (Data Leakage):
  • Через /debug/pprof/heap или /debug/pprof/cmdline злоумышленник может выгрузить дампы кучи, содержащие токены авторизации, приватные ключи шифрования, пароли к БД и персональные данные пользователей.
2. Отказ в обслуживании (Denial of Service):
  • Запрос /debug/pprof/profile?seconds=300 перегружает процессор сбором стеков.
  • Запрос /debug/pprof/trace?seconds=60 забивает диск временными файлами.
  • Стратегия глубокой эшелонированной защиты (Defense in Depth):
  • Привязка сокета только к 127.0.0.1 или внутренней подсети k8s.
  • NetworkPolicy в Kubernetes (блокировка трафика из других namespace).
  • Отсутствие роутов pprof в манифестах Ingress/API Gateway.

	"fmt"
	"net"
	"net/http"
	"testing"
)

type SecurityFirewall struct {
	AllowedCIDRs []*net.IPNet
}

func (f *SecurityFirewall) IsAllowed(remoteAddr string) bool {
	host, _, err := net.SplitHostPort(remoteAddr)
	if err != nil {
		host = remoteAddr
	}
	ip := net.ParseIP(host)
	if ip == nil {
		return false
	}
	for _, cidr := range f.AllowedCIDRs {
		if cidr.Contains(ip) {
			return true
		}
	}
	return false
}

func TestPprofSecurityFirewall(t *testing.T) {

	_, loopback, _ := net.ParseCIDR("127.0.0.0/8")
	_, k8sInternal, _ := net.ParseCIDR("10.244.0.0/16")

	fw := &SecurityFirewall{AllowedCIDRs: []*net.IPNet{loopback, k8sInternal}}

	testCases := []struct {
		ClientIP string
		Allowed  bool
	}{
		{"127.0.0.1:54321", true},       // Локальный SRE туннель
		{"10.244.1.15:39102", true},      // Prometheus/Pyroscope pod
		{"194.87.12.4:80", false},        // Внешний интернет
		{"8.8.8.8:443", false},           // Публичный адрес
	}

	for _, tc := range testCases {
		ok := fw.IsAllowed(tc.ClientIP)
		if ok != tc.Allowed {
			t.Fatalf("Сбой фаервола для %s: ожидалось %v, получено %v", tc.ClientIP, tc.Allowed, ok)
		}
	}

📌 Условие задачи

💡 Теоретический фундамент и концепция

1. Метрики стоимости запроса:
  • $CPU_{req} = \frac{\text{CPU Cores}}{\text{RPS}}$ (ядер на запрос).

package main

import (
	"fmt"
	"math"
	"testing"
)

type CapacityPlan struct {
	CurrentCapacityRPS float64
	MonthlyGrowthRate  float64
	TargetHeadroomPct  float64
	CurrentTrafficRPS  float64
}

func (p *CapacityPlan) SafeCapacityLimit() float64 {
	// Доступный лимит с учетом обязательного запаса 30%
	return p.CurrentCapacityRPS * (1.0 - (p.TargetHeadroomPct / 100.0))
}

func (p *CapacityPlan) DaysUntilExhaustion() int {
	safeLimit := p.SafeCapacityLimit()
	if p.CurrentTrafficRPS >= safeLimit {
		return 0
	}
	// Дневной темп роста: (1 + MonthlyGrowth)^(1/30) - 1
	dailyGrowth := math.Pow(1.0+p.MonthlyGrowthRate, 1.0/30.0) - 1.0
	days := math.Log(safeLimit/p.CurrentTrafficRPS) / math.Log(1.0+dailyGrowth)
	return int(math.Floor(days))
}

func TestCapacityPlanningForecast(t *testing.T) {
	plan := CapacityPlan{
		CurrentCapacityRPS: 1000.0,
		MonthlyGrowthRate:  0.20, // +20% в месяц
		TargetHeadroomPct:  30.0, // 30% запас надежности
		CurrentTrafficRPS:  650.0,
	}

	safeLimit := plan.SafeCapacityLimit() // 1000 * 0.7 = 700 RPS
	daysLeft := plan.DaysUntilExhaustion()

	if daysLeft > 30 {
		t.Fatalf("Алерт должен предупреждать о приближении к лимиту (<30 дней), получено: %d дней", daysLeft)
	}

	fmt.Println("Математический расчет Capacity Planning:")
	fmt.Printf("  • Максимальная емкость:   %.0f RPS\n", plan.CurrentCapacityRPS)
	fmt.Printf("  • Безопасный порог (70%%):  %.0f RPS (30%% Headroom на случай падения ДЦ)\n", safeLimit)
	fmt.Printf("  • Текущий трафик:         %.0f RPS\n", plan.CurrentTrafficRPS)
	fmt.Printf("  • Дней до исчерпания:     %d дней!\n", daysLeft)
	fmt.Println("  • АЛЕРТ: predicted_capacity_exhaustion < 30 days сработал!")
	fmt.Println("  • Действие SRE: расширение пода Kubernetes Deployment с 10 до 15 реплик.")
}

Аудит безопасности диагностического контура:

1. Source Code Disclosure: эндпоинт /debug/pprof/ позволяет через команды list просматривать строки исходного кода с логикой авторизации и бизнес-правилами.

	recPublic := httptest.NewRecorder()
	pub.ServeHTTP(recPublic, reqPublic)

	if recPublic.Code != http.StatusNotFound {
		t.Fatalf("КРИТИЧЕСКАЯ УЯЗВИМОСТЬ: pprof доступен на публичном роутере! Код: %d", recPublic.Code)
	}

	// 2. Проверяем приватный диагностический сервер
	reqPriv := httptest.NewRequest("GET", "/debug/pprof/", nil)
	recPriv := httptest.NewRecorder()
	priv.ServeHTTP(recPriv, reqPriv)

	if recPriv.Code != http.StatusOK {
		t.Fatalf("Диагностический сервер должен отвечать 200 OK, получено: %d", recPriv.Code)
	}

	fmt.Println("Аудит безопасности продакшн-профайлинга успешно пройден:")
	fmt.Printf("  • Публичный роутер:  /debug/pprof/ -> %d Not Found (Безопасно!)\n", recPublic.Code)
	fmt.Printf("  • Приватный роутер:  /debug/pprof/ -> %d OK (Доступен SRE)\n", recPriv.Code)
	fmt.Println("  • Утечка памяти, исходного кода и риск DoS полностью ликвидированы!")
}

Упражнение #24

Трассировка рантайма runtime/trace: 5 секунд записи trace.out, визуализация GMP и задержек GC

📌 Условие задачи

Трассировка выполнения рантайма (runtime/trace): Трассировщик выполнения Go позволяет детально изучить работу планировщика горутин и задержки GC. Напишите код, записывающий трассировку выполнения программы в течение 5 секунд в файл trace.out с помощью пакета runtime/trace. Запустите веб-визуализатор командой go tool trace trace.out. Проанализируйте график активности горутин, время блокировок на системных вызовах (Syscalls) и работу сборщика мусора.

💡 Теоретический фундамент и концепция

Глубинная механика runtime/trace:

  • В отличие от сэмплирующих профайлеров (pprof), runtime/trace фиксирует 100% событий жизненного цикла программы:
  • GoCreate, GoStart, GoStop, GoBlock, GoUnblock.
  • Точное движение горутин между очередями RunQueue процессоров P.
  • Моменты, когда поток ядра M уходит в системный вызов (syscall.Read, epoll_wait).
  • Точные фазы работы GC в наносекундах.
  • Инструменты внутри go tool trace:
1. View trace: интерактивная временная шкала.
2. Goroutine analysis: группировка по типам горутин с подсчетом времени выполнения, ожидания в очереди планировщика (Sched Wait) и блокировок на I/O.
3. Network blocking profile: задержки сетевого ввода-вывода.
4. Synchronization blocking profile: время ожидания каналов и мьютексов.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создайте файл trace.out для сохранения бинарных событий.
2. Инициируйте запись через trace.Start(f).
3. Запустите сценарий с горутинами, сетевыми ожиданиями и аллокациями кучи.
4. Корректно закройте файл через trace.Stop().
5. Продемонстрируйте запуск go tool trace trace.out.

package main

import (
	"bytes"
	"fmt"
	"runtime"
	"runtime/trace"
	"sync"
	"testing"
	"time"
)

func TraceWorker(id int, wg *sync.WaitGroup) {
	defer wg.Done()
	// Имитируем фазы вычислений и сна
	var sum int
	for i := 0; i < 50_000; i++ {
		sum += i
	}
	time.Sleep(5 * time.Millisecond) // Переход в Syscall / Netpoller
	_ = sum
}

func TestRuntimeTraceRecorder(t *testing.T) {
	var traceBuffer bytes.Buffer

	// 1. Старт записи событий рантайма
	err := trace.Start(&traceBuffer)
	if err != nil {
		t.Fatalf("Ошибка запуска трассировщика: %v", err)
	}

	// 2. Исполнение конкурентной рабочей нагрузки
	var wg sync.WaitGroup
	for i := 0; i < 8; i++ {
		wg.Add(1)
		go TraceWorker(i, &wg)
	}

	// Провоцируем работу сборщика мусора для фиксации в трейсе
	runtime.GC()
	wg.Wait()

	// 3. Завершение трассировки
	trace.Stop()

	if traceBuffer.Len() < 500 {
		t.Fatalf("Файл трассировки слишком мал: %d байт", traceBuffer.Len())
	}

	fmt.Println("Трассировка выполнения программы (runtime/trace) успешно записана:")
	fmt.Printf("  • Объем собранной телеметрии: %d байт\n", traceBuffer.Len())
	fmt.Println("  • Запуск веб-визуализатора: go tool trace trace.out")
	fmt.Println("  • В браузере доступны разделы:")
	fmt.Println("    1. View trace — временная шкала активности всех P, M и G")
	fmt.Println("    2. Goroutine analysis — задержки планировщика (Sched Wait)")
	fmt.Println("    3. Synchronization blocking profile — борьба за каналы и блокировки")
}

Вопрос с собеседования: «Как с помощью runtime/trace выявить проблему недостатка потоков ОС (OS Thread Starvation) при частых cgo вызовах?»

Ответ: При вызове cgo поток M блокируется в коде Си. Если все потоки M заблокированы, а в очереди runqueue висят готовые горутины, в разделе Goroutine analysis метрика Scheduler Latency (Sched Wait) вырастает до десятков миллисекунд. На таймлайне видно, как горутины подолгу ждут появления свободных процессоров P.
