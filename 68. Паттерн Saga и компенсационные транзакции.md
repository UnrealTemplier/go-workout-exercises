# Паттерн Saga и компенсационные транзакции

В этом файле собраны уникальные упражнения по теме **"Паттерн Saga и компенсационные транзакции"**, отсортированные по возрастанию сложности.

1. **Оркестратор Саги (Orchestrated Saga State Machine)**: Спроектируйте централизованный оркестратор саги создания заказа (`OrderSagaOrchestrator`).
    * Создайте структуру конечного автомата (State Machine) саги. Определите статусы: `SagaStarted`, `PaymentCompleted`, `InventoryReserved`, `SagaFinished`, `PaymentFailed`, `InventoryFailed`, `RollingBack`, `SagaFailed`.
    * Напишите в Go код оркестратора, который последовательно отправляет gRPC-запросы в смежные сервисы и транзакционно сохраняет текущее состояние саги в базу данных на каждом шаге, чтобы при перезапуске оркестратора он мог продолжить выполнение с прерванного места.

2. **Saga Orchestration: центральный координатор.**: Реализуйте Saga-оркестратор, который выполняет последовательность шагов (сервисы A, B, C). Каждый шаг — вызов внешнего сервиса (заглушка). При успехе всех шагов транзакция завершается, при ошибке любого шага запускаются компенсационные транзакции в обратном порядке.

3. **Saga вручную: два сервиса.**: Реализуйте сервисы `Order` и `Payment`. Создайте заказ (`POST /orders`), затем вызовите `Payment` (`POST /payments`). При успехе обоих — заказ в статусе `confirmed`. Объясните, что это «happy path» Saga без компенсации, и почему он не production-ready.

4. **[Хореография (Event-Driven)]**: Создай 3 сервиса (Order, Payment, Inventory). Сервис Order создает заказ и публикует событие `OrderCreated` в RabbitMQ. Payment слушает его и пытается списать деньги.

5. **Базовая Saga структура**: Создайте orchestrator для e-commerce order flow: `CreateOrder` → `ReserveInventory` → `ProcessPayment` → `ShipOrder`. Каждый шаг — отдельный микросервис.

6. **Saga state machine**: Реализуйте state machine для Saga с состояниями: `Started`, `Step1Executing`, `Step1Completed`, `Step2Executing`, ..., `Completed`, `Compensating`, `Failed`.

7. **Step execution**: Для каждого шага отправляйте команду в соответствующий сервис (gRPC/HTTP) и ждите ответ. Timeout + retry logic.

8. **Первая компенсация.**: Добавьте к упр. 257: если `Payment` возвращает 4xx/5xx, вызовите `DELETE /orders/{id}` (компенсация). Объясните разницу между «компенсацией» (семантический откат) и «rollback БД» (невозможен в распределённой системе).

9. **Compensation trigger**: Если `ProcessPayment` fails, запускайте компенсации в обратном порядке: `ReleaseInventory` → `CancelOrder`.

10. **[Счастливый путь (Happy Path)]**: Если Payment успешен, он публикует `PaymentSucceeded`. Inventory слушает его и резервирует товар. Если резерв успешен, он шлет `InventoryReserved`. Order слушает его и меняет статус заказа на `Confirmed`.

11. **Compensation implementation**: Реализуйте компенсационные методы в каждом сервисе: `ReserveInventory` ↔ `ReleaseInventory`, `ProcessPayment` ↔ `RefundPayment`.

12. **Choreography Saga через события.**: Реализуйте на Kafka/RabbitMQ: `OrderService` публикует `OrderCreated`. `PaymentService` слушает, обрабатывает, публикует `PaymentProcessed` или `PaymentFailed`. `OrderService` слушает результат и меняет статус. Объясните, почему нет центрального координатора и как сервисы «самоорганизуются».

При ошибке сервис публикует событие `*.Failed`, на которое подписаны компенсационные обработчики.

72. **Оркестрация (Orchestration - Централизованная Сага)**: У Хореографии есть минус — неявно, кто управляет процессом, сложно дебажить. Создай сервис `SagaOrchestrator`. Это конечный автомат (FSM). Он **командует** микросервисами по gRPC/HTTP: `Call(Billing)`, затем `Call(Inventory)`. Микросервисы просто отвечают ему `OK/Fail`.

73. **Saga + Outbox + Inbox:**
    * Orchestrator использует Outbox для publishing commands
    * Each service uses Inbox для consuming commands
    * Each service uses Outbox для publishing events
    * Orchestrator uses Inbox для consuming events
    Это даёт end-to-end reliability.

74. **Idempotency + Saga**: Каждый шаг Saga идемпотентен через idempotency keys. Retry шага не вызывает side effects дважды.

75. **Outbox + Idempotency**: Outbox poller использует idempotency keys для Kafka publishing. Повторная публикация того же event не создаёт duplicate в Kafka.

76. **Inbox + Idempotency**: Inbox table сама по себе является idempotency mechanism (через unique constraint на message_id).

87. **Движок Саги (Saga Execution Coordinator - SEC)**: Напиши универсальную структуру-движок на Go. Она принимает срез интерфейсов `type Step interface { Execute() error; Compensate() error }`. Метод `Run()` должен идти по срезу вперед, вызывая `Execute`. Если на шаге N ошибка, движок должен пойти в цикле назад от N-1 до 0, вызывая `Compensate`.

88. **Забудьте про 2PC (Two-Phase Commit).**: В микросервисах 2PC не работает (network partitions, heterogeneous systems). Используйте Saga pattern.

89. **Saga Orchestration для complex flows.**: Если у вас 5+ шагов с сложной логикой компенсаций — используйте Orchestration (Temporal/Cadence). Централизованный control проще для debugging.

90. **Saga Choreography для simple flows.**: Если у вас 2-3 шага и simple event-driven flow — используйте Choreography. Loosely coupled, но сложнее отследить overall state.

91. **Pivot Transactions (Точка невозврата)**: Не каждую транзакцию можно отменить. Если ты заказал курьера в Яндекс.Go, курьер уже едет. Шаг заказа курьера — это Pivot. После него шаги могут *только* повторяться до успеха (Retry forever), компенсация больше невозможна. Реализуй в своем SEC движке маркер `IsPivot() bool` и запрети компенсацию после него.

92. **Compensations должны быть идемпотентными.**: `ReleaseInventory` с тем же order_id не должен releasing inventory дважды. Иначе compensation может создать новую inconsistency.

93. **Timeouts обязательны.**: Каждый шаг Saga должен иметь timeout. Overall Saga должна иметь timeout. Без timeouts Saga может висеть вечно.

94. **Monitoring lag критичен.**: Мониторьте outbox lag (unprocessed events), inbox lag (unprocessed messages), saga completion time. Lag = inconsistency.

95. **Разрешение распределенных дедлоков**: В Хореографии Заказ А ждет денег от пользователя, а Заказ Б ждет освобождения склада. Напиши планировщик, который проходится по "зависшим" (PENDING) сагам старше 10 минут, принудительно инициирует событие `TimeoutFailed` и запускает процесс компенсации.

96. **Блок 24 (Idempotency Keys)**: — начните сразу после Блока 18 (Webhooks), так как idempotency — фундамент всего: без него невозможны надёжные ретраи Webhooks, ни Saga, ни Outbox/Inbox.

97. **Test failure scenarios.**: Happy path testing недостаточно. Тестируйте:
    * Service crash во время Saga
    * Network timeout
    * Duplicate requests
    * Duplicate events
    * Compensation failures

98. **Use Temporal/Cadence для production Sagas.**: Эти workflow engines дают persistence, retries, visibility, versioning из коробки. Не изобретайте свой orchestrator.

99. **Изоляция в Сагах (Semantic Lock)**: Пока Сага выполняется (Заказ PENDING), другой микросервис может попытаться изменить этот же заказ или товар. Это нарушает изоляцию (Isolation из ACID). Введи статус `LOCKED` для задействованных сущностей на время работы саги, чтобы любые другие запросы к ним возвращали HTTP 423 Locked.

100. **Блок 22 (Saga)**: — проходите после освоения Idempotency. Каждый шаг Saga **должен** быть идемпотентным, иначе компенсации и ретраи создадут хаос.

101. **Manual intervention UI.**: Для failed compensations создайте admin UI для manual fixes. Не всё можно автоматизировать.

102. **Observability across boundaries.**: Один бизнес-процесс может затрагивать 5 сервисов. Сквозной `trace_id` через все сервисы — это must have для debugging.
103. **Интеграционное тестирование Саги**: Подними 3 сервиса в Docker Compose (или Testcontainers). Напиши Go-скрипт. Инициируй успешную сагу — проверь базу 3-х сервисов.
