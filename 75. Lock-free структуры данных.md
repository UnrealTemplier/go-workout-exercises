# Lock-free структуры данных

В этом файле собраны уникальные упражнения по теме **"Lock-free структуры данных"**, отсортированные по возрастанию сложности.

---

1. **[atomic.Int64]**: Используй новые типы-обертки (Go 1.19+) `atomic.Int64`. Создайте счетчик, инкрементируемый 1000 горутинами без мьютексов.

2. **Atomic vs Mutex.**: Реализуйте счётчик: `atomic.AddUint64` vs `sync.Mutex` + `counter++`. Бенчмарк с 1, 2, 4, 8 goroutine. Покажите, что atomic масштабируется лучше (нет contention на cache line, только hardware lock prefix). Объясните, почему `atomic` — это не «без блокировок», а «блокировка на уровне шины/кэша».

3. **Spinlock на CAS.**: Реализуйте `type Spinlock uint32` с методами `Lock()` (`for !atomic.CompareAndSwapUint32(&l, 0, 1) { runtime.Gosched() }`) и `Unlock()`. Сравните с `sync.Mutex` при очень короткой критической секции (1 инкремент). Объясните, почему spinlock опасен в userspace (приоритет inversion, wasted CPU).

4. **Lock-Free стек (Treiber stack).**: Реализуйте неблокирующий стек на основе односвязного списка с `atomic.Pointer` или `atomic.Value` (используя unsafe.Pointer). Поддержите операции `Push` и `Pop`. Проверьте корректность в конкурентном тесте с `-race`.

5. **[Spinlock]**: Реализуй свой `Spinlock` на основе `atomic.CompareAndSwapInt32`. Напиши бенчмарк, сравнивающий твой Spinlock с `sync.Mutex` в сценарии без конкуренции (uncontended) и с высокой конкуренцией.

6. **Atomic.Pointer (Go 1.19+).**: Реализуйте lock-free стек (Treiber Stack): `Push` через `atomic.CompareAndSwapPointer` на `head`, `Pop` — аналогично. Покажите, что это работает без mutex. Объясните ABA problem в общем случае и почему в вашем тесте его нет (GC не освобождает память немедленно).

7. **SPSC Ring Buffer.**: Реализуйте lock-free кольцевой буфер на массиве фиксированного размера (power of 2) для Single-Producer–Single-Consumer. Используйте `atomic.Uint64` для `head` и `tail` (или `atomic.LoadUint64`/`StoreUint64`). Объясните, почему SPSC не требует CAS на каждой операции ( producer пишет tail, consumer читает head, не пересекаются).

8. **Lock-Free очередь (Michael-Scott queue).**: Реализуйте очередь с двумя указателями (head, tail) через CAS. Обеспечьте корректную работу при одновременных enqueue и dequeue. Сравните производительность с каналами.

9. **[Lock-Free Stack (Treiber Stack)]**: Реализуй стек на связном списке. Используй `atomic.Pointer[Node]` для хранения головы. Операция `Push` должна делать CAS: если голова не изменилась, заменить её на новый узел.

10. **Memory Ordering.**: Добавьте `runtime.Gosched()` в SPSC и покажите, что без `atomic` (plain reads/writes) может произойти reordering. Объясните acquire/release семантику: consumer делает `atomic.LoadUint64(&tail)` (acquire) перед чтением данных, producer — `atomic.StoreUint64` (release) после записи данных.

11. **MPMC Ring Buffer.**: Расширьте до Multi-Producer–Multi-Consumer: используйте `CAS` на `head`/`tail`, power-of-2 размер для маски `(tail+1) & mask`. Реализуйте `Enqueue` и `Dequeue` с возвратом `bool` (full/empty). Объясните, почему MPMC сложнее (contention на одном head/tail, cache line bouncing).

12. **Ring Buffer на атомиках.**: Создайте lock-free кольцевой буфер (циклический массив) фиксированного размера с атомарными операциями для индексов чтения/записи. Реализуйте single-producer single-consumer (SPSC) версию, затем multi-producer multi-consumer.

13. **Атомарный CAS**: Изучи `atomic.CompareAndSwapInt32`. Напиши цикл: `for { old := val; new := old + 1; if atomic.CompareAndSwapInt32(&ptr, old, new) { break } }`. Это основа любой Lock-Free логики — оптимистичная блокировка.

14. **[Lock-Free Queue (MPSC)]**: Реализуй очередь для Multiple Producer, Single Consumer. Используй атомарные указатели на `head` и `tail`. Одиночный консьюмер читает без блокировок, продюсеры делают CAS на `tail`.

15. **Sequence Lock (SeqLock).**: Реализуйте структуру с `sequence uint64` (чётная = чтение без изменений, нечётная = write in progress). Reader: `seq = atomic.LoadUint64(&seq); if seq%2==1 retry; read data; if seq != atomic.LoadUint64(&seq) retry`. Writer: `atomic.AddUint64(&seq, 1); write data; atomic.AddUint64(&seq, 1)`. Объясните, почему это эффективно для read-heavy данных (например, конфигурация).

16. **Спин-блокировка (Spinlock) на атомиках**: Напишите простейший механизм взаимного исключения — Spinlock. Используйте переменную `uint32` в качестве флага блокировки и функции пакета `sync/atomic` (в частности, метод Compare-And-Swap: `atomic.CompareAndSwapUint32`). Воркер должен крутиться в активном цикле (busy wait) до тех пор, пока не захватит блокировку. Сравните производительность Spinlock с обычным `sync.Mutex` в сценариях с экстремально короткими критическими секциями.

17. **Атомарный счётчик и CAS (Compare-And-Swap).**: Реализуйте потокобезопасный инкремент счётчика с использованием `atomic.AddInt64`. Сравните производительность с `sync.Mutex` под высокой конкурентной нагрузкой.

18. **Atomic.Value для горячего кэша.**: Используйте `atomic.Value` для хранения конфигурации, которая обновляется раз в минуту, но читается миллионы раз в секунду. Измерьте overhead по сравнению с мьютексом.

19. **Striped Counters.**: Реализуйте `type StripedCounter [64]PaddedCounter` (по числу CPU). `Add` — `stripe[cpuID].Add`, `Sum` — сумма всех stripes. Покажите, что это масштабируется линейно до числа ядер, в отличие от глобального `atomic.Uint64`. Объясните компромисс: точность `Sum` (eventual) vs скорость.

20. **Проблема ABA (Теория)**: Узнай, почему наивный CAS уязвим к ABA. Процесс 1 прочитал `A`, собирается записать `C`. Процесс 2 успел изменить `A` на `B`, а процесс 3 вернул обратно на `A`. Процесс 1 делает CAS, видит `A` (думает, что ничего не менялось) и пишет `C`. Состояние памяти сломано! (В Go с GC проблема ABA стоит не так остро, как в C/C++, но о ней нужно знать).

21. **[Ring Buffer (SPSC)]**: Реализуй неблокирующий Ring Buffer (Fixed-size queue) для Single Producer, Single Consumer. Используй `atomic.LoadUint64` для `head` и `tail`. *Ключевой момент:* продюсер пишет данные *до* инкремента `tail`, а консьюмер проверяет `tail` *до* чтения данных (Memory Ordering).

22. **Lock-free Hash Table (sharded).**: Реализуйте массив из 256 `sync.RWMutex` или `atomic.Pointer` на bucket. Покажите, что sharding уменьшает contention. Объясните, почему полностью lock-free hash table (например, Java `ConcurrentHashMap`) в Go сложна из-за отсутствия transactional memory.

23. **Spin-Lock с Backoff**: Напиши свой мьютекс поверх `atomic.Bool`. В методе `Lock()` крути бесконечный цикл `CompareAndSwap(false, true)`. Чтобы не сжечь процессор в 100% при конкуренции, добавь `runtime.Gosched()` (отдать контекст) или адаптивный бэкофф (пустой цикл `for i:=0; i<10; i++`).

24. **Сравнение lock-free map (sync.Map) с обычной map+mutex.**: Создайте сценарий: много чтений, редкие записи. Замерьте `Load` и `Store` у `sync.Map` и `map + sync.RWMutex` на большом количестве горутин. Покажите, когда `sync.Map` выигрывает.

25. **Epoch-Based Reclamation (упрощённый).**: Для lock-free stack добавьте механизм: при `Pop` не удаляйте узел, а помещайте в локальный «retired list». Периодически (каждые N операций) освобождайте узлы, которые гарантированно не видны другими goroutine (через глобальный epoch counter). Объясните, почему Go GC делает это за вас, но в C/C++ без EBRM/HP — утечка или use-after-free.

26. **Lock-Free Single-Producer Single-Consumer (SPSC) Ring Buffer**: Напишите кольцевой буфер (Ring Buffer) фиксированного размера на базе слайса. Настройте его работу без мьютексов: одна горутина (Producer) пишет в буфер, вторая (Consumer) читает из него. Используйте атомарные индексы записи и чтения и функцию `atomic.LoadUint64` / `atomic.StoreUint64` для синхронизации смещений без блокировок.

27. **[Каверзный кейс — ABA Problem]**: Напиши симуляцию проблемы ABA в Treiber Stack: Поток A читает голову (указатель на Node X). Поток B выталкивает X, выталкивает Y, затем проталкивает X обратно. Поток A делает CAS, видит старый адрес X и успешно меняет голову, но стек сломан (Y потерян). Реализуй защиту через Tagged Pointers (указатель + счетчик версии).

28. **Lock-Free Treiber Stack**: Реализуй потокобезопасный LIFO-стек без мьютексов. Используй `atomic.Pointer[Node]` (появился в Go 1.19). В методе `Push` создай новую ноду, сделай `new.next = head`, а затем попытайся атомарно подменить `head` через CAS. Если не вышло — повторяй в цикле.

29. **ABA-проблема и её решение.**: Продемонстрируйте ABA-проблему на lock-free стеке (pop A, pop B, push A обратно, затем CAS на A ошибочно срабатывает). Покажите решение с помощью счётчика версий (tagged pointer) через `atomic.Uintptr` с зарезервированными битами или через `unsafe.Pointer` с двойным словом.

30. **[Backoff в CAS]**: Если много горутин борются за один CAS, они будут тратить CPU впустую (Cache Line Ping-Ponging). Реализуй экспоненциальный backoff (через `runtime.Gosched()` или `time.Sleep`) внутри цикла CAS при неудаче. Оцени прирост пропускной способности.

31. **SPSC Ring Buffer (Основа)**: (Single-Producer Single-Consumer). Напиши кольцевой буфер на основе массива. Задай индексы `head` и `tail` как `uint64`. Читатель меняет `head`, писатель меняет `tail`.

32. **Защита от ABA-проблемы в Lock-Free структурах**: Опишите в комментариях классическую ABA-проблему, возникающую при работе с Lock-Free алгоритмами с использованием инструкций Compare-And-Swap (CAS) (когда значение переменной меняется с А на B, а затем обратно на А, и CAS ошибочно считает, что состояние не изменилось). Напишите пример реализации Lock-Free стека на Go с использованием счетчика эпох (epoch/generation counter) или уникальных идентификаторов изменений для предотвращения этой проблемы.

33. **Atomic operations basics**: Изучите `sync/atomic` пакет:
    * `atomic.AddInt64(&x, 1)`
    * `atomic.LoadInt64(&x)`
    * `atomic.StoreInt64(&x, val)`

34. **CAS (Compare-And-Swap)**: Это фундамент lock-free programming. CAS атомарно проверяет, что значение = expected, и если да — обновляет его.

35. **SPSC без блокировок**: Улучши упр. 875. Сделай индексы `head` и `tail` атомарными. Примени знания из Блока 84: разнеси `head` и `tail` по разным кэш-линиям процессора (вставив `_ [64]byte` между ними), иначе False Sharing уничтожит всю производительность твоего Ring Buffer!

36. **Atomic flag**: Реализуйте boolean flag через `atomic.Bool` (Go 1.19+) или `atomic.Int32`.

37. **MPMC (Multi-Producer Multi-Consumer)**: *Продвинутая задача.* Реализуй очередь, в которую конкурентно могут писать и читать многие горутины, без использования каналов и мьютексов. (Рекомендуется изучить исходники библиотеки `github.com/loov/hrtime` или паттерны Disruptor).

38. **Memory ordering**: Изучите memory ordering:
    * `atomic.Load` — relaxed (может reorder)
    * `atomic.LoadAcquire` — acquire (не reorder после)
    * `atomic.StoreRelease` — release (не reorder до)
    * `atomic.CompareAndSwap` — sequential consistency

39. **Sequential consistency**: В Go все atomic operations имеют sequential consistency semantics. Это проще для понимания, но может быть медленнее.

40. **Lock-free linked list**: Реализуйте lock-free singly-linked list с insert и delete. Используйте CAS для pointer updates.

41. **Lock-Free Multi-Producer Multi-Consumer (MPMC) Queue**: Напишите сложную конкурентную очередь фиксированного размера, в которую параллельно пишут несколько горутин и параллельно читают другие горутины. Реализуйте алгоритм без использования мьютексов (на базе атомиков). Используйте массив структур, где каждый элемент содержит атомарный флаг-последовательность (sequence) для координации доступа писателей и читателей.

42. **Lock-free stack (Treiber stack)**: Реализуйте lock-free stack через CAS:
    ```go
    type Node struct {
        value int
        next  *Node
    }
    type Stack struct {
        head atomic.Pointer[Node]
    }
    ```

43. **Lock-free queue (Michael-Scott queue)**: Реализуйте lock-free queue. Это сложнее, чем stack, потому что нужно атомарно обновлять и head, и tail.

44. **Битва архитектур**: Напиши бенчмарк для 3-х вариантов передачи данных между горутинами: стандартный канал `chan`, очередь с `sync.Mutex` и твой Lock-Free SPSC Ring Buffer. Сравни скорость (в наносекундах) и аллокации.

45. **Hazard pointers**: Для safe memory reclamation в lock-free структурах используйте hazard pointers. Это защищает nodes от premature free.

46. **RCU (Read-Copy-Update)**: Для read-heavy workloads используйте RCU: readers не блокируются, writers создают copy и атомарно swap.

47. **Epoch-based reclamation**: Альтернатива hazard pointers — epoch-based reclamation. Проще в реализации, но требует periodic quiescent state.

48. **Lock-free vs wait-free**: Lock-free гарантирует, что хотя бы один thread makes progress. Wait-free гарантирует, что все threads make progress в bounded time. Wait-free сложнее.

49. **Atomic min/max**: Реализуйте atomic min через CAS loop:
    ```go
    for {
        old := atomic.LoadInt64(&x)
        if old <= newVal || atomic.CompareAndSwapInt64(&x, old, newVal) {
            break
        }
    }
    ```

50. **Atomic accumulator для float64**: `sync/atomic` не поддерживает float64 напрямую. Используйте `math.Float64bits` и `math.Float64frombits` для atomic float operations.

51. **Барьеры памяти (Memory Barriers) и Reordering**: Напишите подробный теоретический комментарий, объясняющий концепцию переупорядочивания инструкций компилятором и процессором (Instruction Reordering). Объясните, как атомарные операции в Go неявно выстраивают барьеры памяти (Memory Fences) и гарантируют строгую согласованность памяти (Sequential Consistency) на x86 архитектурах (которые имеют строгую модель памяти TSO) и на ARM архитектурах (со слабой моделью памяти).

52. **Atomic statistics**: Реализуйте lock-free statistics collector: count, sum, min, max через atomic operations.

53. **Single-producer single-consumer (SPSC)**: Простейший case: один producer, один consumer. Не нужен CAS, достаточно atomic load/store.

54. **Cache line padding для SPSC**: Разделите `head` и `tail` в разные cache lines для избежания false sharing:
    ```go
    type SPSCRingBuffer struct {
        _      [40]byte       // padding
        head   atomic.Uint64
        _      [56]byte       // padding
        tail   atomic.Uint64
        _      [56]byte       // padding
        buffer []int64
        mask   uint64
    }
    ```

55. **SPSC producer**: Producer проверяет, что buffer не full (`head - tail < size`), пишет в `buffer[head & mask]`, атомарно инкрементирует `head`.

56. **Ring buffer benchmark**: Сравните производительность:
    * SPSC ring buffer
    * MPMC ring buffer
    * Go channel
    * Mutex-protected queue
    
    SPSC должен быть fastest (10-100x быстрее channel).

57. **ABA problem**: Изучите ABA problem: CAS видит, что значение = A, но не знает, что оно было A → B → A. Решение: version counter или hazard pointers.

58. **Multi-producer multi-consumer (MPMC)**: Сложнее: multiple producers и multiple consumers. Нужен CAS для coordination.

59. **MPMC ring buffer через sequence numbers**: Каждый slot имеет sequence number. Producer CAS'ит sequence number для reservation slot.

60. **MPMC implementation (Disruptor-style)**: Изучите LMAX Disruptor — high-performance MPMC ring buffer. Реализуйте упрощённую версию.

61. **Backpressure в ring buffer**: Если buffer full, producer может:
    * Block (wait for space)
    * Drop oldest (overwrite)
    * Return error
    Выберите стратегию based on use case.

62. **Batch operations**: Для throughput producer может batch write multiple items. Consumer может batch read.

63. **Lock-free только при high contention.**: При low contention mutex быстрее (проще, нет CAS retry loops). Lock-free имеет смысл, когда 100+ threads конкурируют за один resource.

64. **Ring buffer vs channel**: Go channels — это тоже ring buffers internally. Но custom ring buffer может быть быстрее (нет goroutine scheduling overhead).

65. **Zero-copy ring buffer**: Для large items используйте ring buffer of pointers вместо ring buffer of values. Это избегает expensive copy.

66. **Ring buffer для logging**: Используйте ring buffer для high-throughput logging. Logger пишет в ring buffer, background goroutine flushes в file/network.

67. **Ring buffer basics**: Ring buffer — это circular array с `head` и `tail` pointers. Producer пишет в `head`, consumer читает из `tail`.

68. **Power-of-2 size**: Ring buffer size должен быть power of 2. Это позволяет использовать bitmask вместо modulo: `index & mask` вместо `index % size`.

69. **Ring buffer для metrics**: Используйте ring buffer для metrics collection. Application пишет metrics в ring buffer, aggregator periodically reads.

70. **Ring buffer для event processing**: Используйте ring buffer для event-driven architecture. Producers publish events, consumers process events.

71. **Ring buffer sizing**: Размер ring buffer должен быть достаточным для absorbtion burst traffic, но не слишком большим (waste memory).

73. **CAS retry loops — это нормально.**: В lock-free алгоритмах CAS может fail из-за contention, и вы retry. Это expected behavior. Но убедитесь, что retry probability низкая.

74. **SPSC ring buffer — fastest.**: Single-producer single-consumer ring buffer не требует CAS, только atomic load/store. Это в 10-100x быстрее, чем MPMC или Go channels.

75. **Блок 29 (Lock-free)**: — проходите после Блока 1 (GMP), так как lock-free структуры — это альтернатива mutex при высоком contention. Знание `sync/atomic` и memory model критично.
