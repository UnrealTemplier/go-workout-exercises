# Хеширование паролей и криптографическая стойкость

В этом файле собраны уникальные упражнения по теме **"Хеширование паролей и криптографическая стойкость"**, отсортированные по возрастанию сложности.

---

1. **CSPRNG vs псевдослучайность.**: Сгенерируйте 1 млн байт через `crypto/rand` и через `math/rand`. Покажите, что `math/rand` предсказуем (восстановите seed по первым значениям), а `crypto/rand` — нет. Объясните, почему `math/rand` нельзя использовать для ключей и nonce.

2. **Истинный рандом (`crypto/rand`)**: Напиши функцию генерации безопасного токена (например, для сброса пароля). Создай срез `make([]byte, 32)` и заполни его через `rand.Read()`. Закодируй результат в строку через `base64.URLEncoding`.

3. **[MD5/SHA256 — Почему так нельзя]**: Напиши функцию хэширования пароля через `sha256.Sum256`. Объясни, почему хранение паролей в виде обычного SHA-хэша смертельно опасно (уязвимость к радужным таблицам и быстрому перебору на GPU).

4. **crypto/rand vs math/rand**: Напишите код, который использует оба пакета для генерации чисел. Покажите, почему `math/rand` **никогда** нельзя использовать для security-задач (предсказуемость seed, state-based атаки).

5. **Генерация криптографически стойкого токена**: Напишите функцию `GenerateToken(n int) (string, error)`, которая возвращает base64url-закодированные `n` случайных байт через `crypto/rand.Read`.

6. **Session ID generation**: Создайте генератор session ID длиной минимум 128 бит энтропии. Объясните, почему этого достаточно для защиты от brute-force.

7. **[Salt]**: Добавь к паролю случайную "соль" (сгенерируй через `crypto/rand`). Объясни, как соль защищает от радужных таблиц.

8. **Хэширование (SHA-256)**: Хэшируй строку "my_password" с помощью `crypto/sha256`. Выведи результат в hex-формате. *Осознай, почему это КАТЕГОРИЧЕСКИ нельзя использовать для хранения паролей* (современная видеокарта переберет миллиарды SHA-256 хэшей за секунду).

9. **Entropy analysis**: Напишите утилиту, которая оценивает энтропию сгенерированных данных через подсчёт Shannon entropy. Убедитесь, что ваш генератор даёт ~8 бит/байт.

10. **SHA-256 базовое использование**: Вычислите SHA-256 хэш строки через `crypto/sha256`. Покажите, как малейшее изменение входа радикально меняет хэш (avalanche effect).

11. **SHA-256 streaming**: Вычислите хэш большого файла (10GB) без загрузки его целиком в память через `io.Copy(hash, file)`.

12. **[bcrypt]**: Установи `golang.org/x/crypto/bcrypt`. Напиши функцию `HashPassword(password string) (string, error)` (используй `bcrypt.GenerateFromPassword` с cost=12).

13. **Стандарт индустрии (`bcrypt`)**: Установи `golang.org/x/crypto/bcrypt`. Хэшируй пароль с помощью `GenerateFromPassword`. Посмотри на полученную строку (она содержит соль и стоимость). Проверь пароль через `CompareHashAndPassword`.

14. **SHA-3 и BLAKE2b**: Изучите `golang.org/x/crypto/sha3` и `golang.org/x/crypto/blake2b`. BLAKE2b быстрее SHA-256 и используется во многих современных системах.

15. Напиши функцию `CheckPassword(hashedPassword, password string) error` (`bcrypt.CompareHashAndPassword`). Убедись, что bcrypt автоматически извлекает соль из хэша.

16. **SHA-1 и MD5 — никогда не использовать**: Напишите пример использования `crypto/md5` и объясните, почему они криптографически сломаны (collision attacks: 2^18 операций для MD5).

17. **Cost (Стоимость bcrypt)**: Запусти бенчмарк для `bcrypt` с `cost = 10` и `cost = 14`. Убедись, что увеличение стоимости делает хэширование экспоненциально медленнее (что защищает от брутфорса), но сильно грузит CPU сервера.

18. **Constant-time comparison**: Реализуйте собственную функцию constant-time сравнения байтовых слайсов. Покажите, как branching в обычном сравнении раскрывает информацию.

19. **[Argon2id]**: Установи `golang.org/x/crypto/argon2`. Напиши функцию хэширования через `argon2.IDKey`. Argon2 является победителем конкурса Password Hashing Competition и устойчив к атакам на GPU/ASIC за счет настройки потребления памяти.

20. **Современный стандарт (Argon2)**: На сегодня OWASP рекомендует алгоритм Argon2id (он защищен от атак на видеокартах/ASIC за счет требования памяти). Используй `golang.org/x/crypto/argon2`. Напиши функцию хэширования, задав параметры: время (time), память (memory) и потоки (threads).

21. **[Peppering]**: Реализуй паттерн "Pepper" (перец): перед хэшированием в bcrypt конкатенируй пароль с секретной строкой из переменной окружения (`PEPPER_SECRET`). Объясни, чем pepper отличается от salt (соль уникальна для юзера и хранится в БД, перец один для всех и хранится в коде/KMS).

22. **Тайминг-атаки (`crypto/subtle`)**: Тебе прислали API-ключ. Если ты проверишь его как `if input == secretKey`, злоумышленник сможет попиксельно угадать ключ, замеряя наносекунды ответа сервера (сравнение `==` прерывается на первом несовпадающем символе). Замени `==` на `subtle.ConstantTimeCompare()`, которое всегда выполняется за одинаковое время.

23. **[Каверзный кейс — Тайминг-атаки]**: Напиши функцию, которая сравнивает два токена через `==`. Запусти бенчмарк, который показывает, что сравнение строк разной длины занимает разное время. Используй `crypto/subtle.ConstantTimeCompare` для безопасного сравнения секретов.

24. **HMAC (Аутентификация сообщений)**: Тебе нужно передать данные клиенту и убедиться, что он их не подделал. Используй `crypto/hmac` с SHA-256 и секретным ключом сервера, чтобы сгенерировать подпись для строки. Напиши функцию валидации этой подписи.

25. **Деривация ключей (HKDF)**: У пользователя есть пароль, но для AES-шифрования тебе нужен ключ ровно в 32 байта. Используй `golang.org/x/crypto/hkdf`, чтобы безопасно "растянуть" пароль пользователя (с добавлением соли) до 32-байтного криптографического ключа.

26. **argon2id: современный стандарт.**: Реализуйте хеширование через `golang.org/x/crypto/argon2`. Используйте параметры: time=1, memory=64 MB, threads=4, salt=16 байт (из `crypto/rand`), key length=32. Объясните, как подбирать параметры под ваш CPU/память.

27. **Соль: уникальность и хранение.**: Напишите функцию, которая генерирует случайную соль (16 байт) для каждого пользователя. Объясните, почему глобальная соль — уязвимость (rainbow tables), и как хранить соль вместе с хешем (например, `base64(salt+hash)`).

28. **Password-Based KDF.**: Используйте `argon2id` или `bcrypt` для получения ключа из пароля, затем используйте этот ключ в AES-GCM. Объясните разницу между *password hashing* (для проверки) и *key derivation* (для шифрования), и почему `bcrypt` не подходит как KDF для ключей AES.

29. **bcrypt: полный цикл.**: Реализуйте регистрацию и аутентификацию через `golang.org/x/crypto/bcrypt`. Сгенерируйте хеш с `cost=10` и `cost=14`. Замерьте время хеширования. Объясните, почему `bcrypt.CompareHashAndPassword` использует constant-time сравнение.

30. **Transparent hash upgrade.**: Реализуйте middleware: при успешном логине проверяете пароль против старого bcrypt-хеша, если совпало — перехешируете в argon2id и обновляете в БД. Объясните стратегию миграции без сброса паролей всех пользователей.

31. **Timing attacks и constant-time сравнение.**: Напишите наивную проверку API-ключа (`if token == storedToken`) и измерьте время выполнения через `testing.B` с разными префиксами. Затем используйте `crypto/subtle.ConstantTimeCompare`. Объясните, почему `==` на строках уязвим для timing-атак.

32. **Хэширование паролей с `bcrypt`**: Напишите функции регистрации и авторизации пользователей с хэшированием паролей. Используйте стандартный для индустрии пакет `golang.org/x/crypto/bcrypt` [543]. Объясните влияние параметра стоимости (cost factor) на время вычисления хэша [543]. Протестируйте скорость авторизации при стоимости 10, 12 и 14, написав бенчмарк.

33. **Pepper.**: Добавьте application-wide secret (pepper — 32 байта из env) к паролю *перед* хешированием argon2id. Объясните, чем pepper отличается от salt (один на приложение, не хранится в БД, усложняет атаку при утечке БД).

34. **Почему MD5/SHA для паролей — катастрофа**: Покажите, что на современном GPU можно перебирать ~10^10 MD5-хэшей в секунду. БД с MD5-хэшами 10M пользователей ломается за минуты.

35. **bcrypt cost tuning**: Определите оптимальный cost для вашего сервера: должен занимать ~250ms на хэш. Это даёт 4 пароля/сек на ядро — атакующему очень больно.

36. **HMAC-SHA256.**: Реализуйте подпись webhook-запросов или API-ответов через `crypto/hmac` + `sha256`. Покажите, почему `HMAC(key, data)` безопаснее, чем `SHA256(key || data)` (length extension attacks). Реализуйте verify с `subtle.ConstantTimeCompare`.

37. **bcrypt salt встроен**: Покажите, что bcrypt автоматически генерирует salt и хранит его вместе с хэшем в формате `$2a$12$...`. Нет отдельного поля в БД.

38. **bcrypt: хэширование и проверка.**: Захешируйте пароль с bcrypt (cost=12). Проверьте пароль функцией `bcrypt.CompareHashAndPassword`. Покажите, что разные хэши одного пароля не равны, но проверка проходит.

39. **bcrypt length limit**: Покажите, что bcrypt обрезает пароли до 72 байт. Длинный passphrase теряет энтропию! Используйте pre-hashing через SHA-256 для длинных паролей.

40. **Современное хэширование с Argon2id**: Согласно рекомендациям OWASP, Argon2id является наиболее устойчивым алгоритмом к подбору паролей на GPU/ASIC. Реализуйте хэширование паролей с использованием пакета `golang.org/x/crypto/argon2` [544]. Задайте параметры: объем используемой памяти 64 МБ, количество итераций 3, уровень параллелизма 4, длина соли 16 байт [544]. Напишите функцию проверки соответствия введенного пароля сохраненному хэшу.

41. **scrypt**: Используйте `golang.org/x/crypto/scrypt` с параметрами N=32768, r=8, p=1. scrypt memory-hard — атаки через ASIC становятся очень дорогими.

42. **Argon2id — современный стандарт**: Захешируйте пароль через `golang.org/x/crypto/argon2`. Используйте Argon2id (winner Password Hashing Competition 2015).

46. **Argon2id: защита от GPU-атак.**: Реализуйте хэширование паролей с помощью `golang.org/x/crypto/argon2`. Настройте параметры: memory=64MB, iterations=3, parallelism=4. Сгенерируйте случайную соль. Создайте строку хэша в формате PHC (Password Hashing Competition) и функцию проверки.

47. **Password pepper**: Добавьте server-wide secret (pepper) к паролю перед хэшированием. Pepper не в БД — утечка БД не даёт атакующему ничего без pepper.

49. **PASETO-токены вместо JWT**: Стандарт JWT содержит ряд критических уязвимостей в дизайне (например, поддержка алгоритма `"none"`, уязвимости парсинга заголовков). Напишите генератор сессионных токенов авторизации на базе современного стандарта PASETO (Platform-Agnostic Security Tokens) версии 4 (локальные токены с симметричным шифрованием v4.local) [545] с использованием библиотеки `github.com/o1egl/paseto` или аналогичной [545]. Напишите комментарий, почему PASETO безопаснее JWT по умолчанию [545].

50. **Password validation policy**: Реализуйте валидатор: минимум 12 символов, проверка в HaveIBeenPwned database через k-anonymity API (без отправки пароля!).

51. **Bcrypt timing attack protection**: Используйте постоянную стоимость сравнения. Покажите, как разница во времени успешного/неуспешного логина может раскрыть информацию.

52. **Сравнение bcrypt и Argon2 по времени и памяти.**: Напишите бенчмарк, который замеряет время хэширования и верификации для bcrypt (cost=10) и Argon2id (разные параметры). Выберите оптимальные параметры для интерактивной аутентификации.

53. **Механизм ротации ключей подписи (Key Rotation)**: Реализуйте в вашей системе авторизации на базе PASETO/JWT механизм ротации ключей. Сервер должен хранить список активных ключей подписи. Новые токены должны подписываться самым свежим (актуальным) ключом, однако при проверке входящих токенов система должна успешно принимать токены, подписанные старыми ключами, если их время жизни (TTL) еще не истекло.

54. **Авторизация через OAuth2 (Authorization Code Flow)**: Напишите интеграцию вашего веб-сервера со сторонним провайдером авторизации (например, GitHub или Google), используя библиотеку `golang.org/x/oauth2` [547]. Реализуйте два HTTP-обработчика:
    * `/login` — генерирует случайную строку `state` (для защиты от CSRF), сохраняет её в сессию/cookie и перенаправляет пользователя на страницу авторизации провайдера [547].
    * `/callback` — проверяет совпадение `state`, запрашивает у провайдера обмен полученного `code` на `AccessToken` и сохраняет токен [547].

55. **Интеграция с OpenID Connect (OIDC)**: Расширьте OAuth2-авторизацию из предыдущей задачи до стандарта OIDC. Используйте пакет `github.com/coreos/go-oidc`. Напишите код, который запрашивает у провайдера `ID Token` (JWT), автоматически скачивает публичные ключи провайдера из эндпоинта JWKS (JSON Web Key Sets), валидирует подпись и извлекает из токена профиль пользователя (email, имя, ID).

56. **Затирание секретов в оперативной памяти**: Переменные типа `string` в Go неизменяемы, поэтому при обработке пароля или секретного ключа они могут надолго зависнуть в оперативной памяти (в куче) до запуска GC, что позволит злоумышленнику считать их из дампа памяти (heap dump) [554]. Напишите код: принимайте пароли в виде среза байт `[]byte`. После того как пароль проверен, принудительно затрите этот срез байт нулями во всей выделенной под него памяти с помощью функции `copy` или ручного обнуления элементов в цикле [554].
