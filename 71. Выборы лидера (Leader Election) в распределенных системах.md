# Выборы лидера (Leader Election) в распределенных системах

В этом файле собраны уникальные упражнения по теме **"Выборы лидера (Leader Election) в распределенных системах"**, отсортированные по возрастанию сложности.

---

1. **Выборы лидера в etcd через аренду (Lease)**: Подключите официальный клиент etcd: `go.etcd.io/etcd/client/v3`.
    * Создайте аренду (Lease) с TTL (временем жизни) 5 секунд.
    * Настройте периодическую отправку пульса (Keep-Alive) в фоновом режиме для продления аренды.
    * Попробуйте записать ключ `/services/leader` с вашим ID в рамках транзакции `Txn`: если ключа нет, запишите его с привязкой к вашей аренде. Если запись успешна — текущий узел объявляется Лидером.

2. **Базовая блокировка в etcd.**: Реализуйте захват «блокировки» через `clientv3.Put` с `clientv3.WithLease(leaseID)` и `clientv3.WithPrevKV()`. Покажите, что второй процесс не может записать ключ, пока lease активен. Объясните, почему `TTL` + `KeepAlive` — сердце etcd-координации, а не просто `SET`/`GET`.

3. **Подключение к Consul и регистрация сервиса.**: Запустите Consul (dev-режим). Используя `consul/api`, зарегистрируйте экземпляр сервиса с health-check (ttl или http). Получите список здоровых экземпляров через DNS или HTTP API.

4. **Проблема без leader election**: Покажите проблему: 3 инстанса сервиса запускают cron job одновременно. Результат: duplicate processing, data corruption.

5. **Consul session creation**: Создайте session через `consul.Session().Create()` с TTL 15 секунд и behavior `delete` (при session expiry ключ удаляется).

6. **Leader Election через etcd.**: Запустите 3 процесса, которые конкурируют за ключ `/leader`. Используйте `clientv3.Concurrency.Election` (или ручной `Campaign` через `Txn` с `CreateRevision` compare). Покажите, что только один получает `leaderCh`, остальные ждут. Объясните роль `CreateRevision` в определении порядка.

7. **Consul lock acquisition**: Попытайтесь захватить lock через `consul.KV().Acquire()` с session ID. Первый успешный — leader.

8. **Leader detection**: Каждый инстанс проверяет, является ли он leader'ом через проверку session ID в KV. Если `key.Session == mySession` — я leader.

9. **Consul setup**: Поднимите Consul cluster из 3 серверов через Docker Compose. Изучите Consul UI на порту 8500.

10. **Leader heartbeat**: Leader периодически обновляет session через `session.Renew()` для предотвращения expiry.

11. **Создание сессии и захват ключа.**: Реализуйте простой лидерский лок: создайте сессию с TTL и привяжите её к ключу в KV, используя `Acquire`. Если ключ уже занят, сессия не создается – ожидайте освобождения с backoff.

12. **[KeepAlive]**: Если процесс умрет, etcd должен удалить ключ через 10 секунд. Напиши горутину, которая постоянно отправляет `KeepAlive` запросы, чтобы продлить аренду, пока процесс жив.

13. **Consul Session + KV Lock.**: Создайте Consul Session с `TTL=10s` и `Behavior=release`. Захватите KV-пару через `session` в `Acquire`. Покажите, что при `DestroySession` или истечении TTL блокировка снимается автоматически. Сравните с etcd: Consul использует health checks + session, etcd — lease.

14. **Leader failover**: Убейте leader процесс. Через TTL (15s) session expires, lock освобождается, другой инстанс захватывает lock.

15. **Consul watch**: Используйте `consul.Watch()` для уведомления при изменении leader key. Все инстансы узнают о смене leader'а мгновенно.

16. **Обработка потери лидерства.**: В leader-процессе запустите горутину, которая слушает `KeepAlive` ответы (или `Session.RenewPeriodic`). При ошибке (lease expired) — немедленно остановить обработку запросов (`atomic.StoreUint32(&isLeader, 0)`). Объясните, почему продолжение работы после lease expiration — это split-brain.

17. **etcd lease creation**: Создайте lease через `client.Grant()` с TTL 15 секунд.

18. **etcd leader election**: Используйте `client.Campaign()` из `concurrency` пакета для участия в выборах.

19. **[Борьба за лидерство]**: Запусти 3 инстанса твоего Go-приложения. Каждый пытается выполнить `etcd.Txn` (Transaction): `If(key /leader does not exist) Then(Put /leader with lease) Else(Get /leader)`. Убедись, что только один становится лидером, а остальные видят чужой ключ.

20. **Лидерская выборка с мониторингом и фейловером.**: Запустите несколько горутин (эмулирующих узлы). Каждая пытается стать лидером через сессию. Лидер периодически продлевает сессию. При остановке лидера другой узел должен захватить лидерство. Используйте `Session.Renew` или TTL-чек.

21. **Грациозный захват с задержкой (fencing old leader).**: Новый узел при старте видит, что `/leader` занят lease, который ещё не истёк. Реализуйте ожидание `oldTTL * 1.5` перед попыткой захвата. Объясните, зачем нужен «grace period» (network delay может доставить KeepAlive позже, чем lease истекает на сервере).

22. **etcd leader resignation**: Leader может добровольно уйти через `client.Resign()`. Это запускает новые выборы.

23. **Выборы лидера через Concurrency API etcd**: В etcd есть высокоуровневый пакет для координации: `go.etcd.io/etcd/client/v3/concurrency`. Напишите программу, которая создает сессию (`concurrency.NewSession`) и использует готовый менеджер выборов `concurrency.NewElection` для автоматической борьбы за лидерство и отслеживания падений узлов.

24. **Подключение к etcd и создание lease.**: Запустите etcd локально. Подключитесь через `clientv3`. Создайте lease с TTL 10 секунд. Запишите ключ `/election/leader` с этим lease (операция `Put` с `WithLease`).

25. **Consul vs etcd для leader election:**
    * Consul: встроенный DNS, health checks, multi-datacenter
    * etcd: быстрее, проще, часть Kubernetes
    Используйте etcd если уже в K8s, Consul для standalone distributed systems.

26. **Распределённый cron (Leader-Only Scheduler).**: Реализуйте сервис, где только лидер запускает `time.Ticker` и выполняет задачи (например, агрегация статистики). При `OnLeadershipChange` — остановить ticker, при захвате — запустить. Покажите, что при failover задача не дублируется (единственный лидер).

27. **Leader election metrics**: Экспортируйте метрики: `leader_elections_total`, `leader_tenure_seconds`, `failover_count`.

28. **[Watch и Failover]**: Останови инстанс-лидер (убей процесс). Оставшиеся 2 инстанса должны слушать изменения ключа `/leader` через `etcd.Watcher`. Когда ключ исчезнет (TTL истек), они должны мгновенно начать новую борьбу за лидерство.

29. **Оповещение о смене лидера.**: Реализуйте канал, который получает сообщения, когда узел становится лидером или теряет лидерство. Используйте long polling на ключ сессии или watch.

30. **Fencing token в leader election**: При получении leadership генерируйте монотонно возрастающий fencing token. Используйте его для защиты от stale leaders.

31. **Leader Election с приоритетом.**: Узлы имеют `priority` (например, availability zone, hardware class). Реализуйте алгоритм: при попытке захвата лидерства узел записывает `/election/<node_id>` с value=priority. Лидер — узел с наименьшим приоритетом (или наибольшим). Объясните, как `clientv3.Txn` с `Cmp` позволяет реализовать CAS-логику.

32. **Multiple leaders для разных задач**: Используйте разные leader keys для разных задач: `leader/cron`, `leader/reconciliation`, `leader/metrics_aggregation`.

33. **Consul: Service Check + Session.**: Привяжите session к health check сервиса (`CheckTTL` или `CheckHTTP`). Если сервис становится `critical` — session invalidated, lock released автоматически. Покажите, что это даёт «failover по health», а не только по процессу.

34. **Leader election testing**: Напишите интеграционные тесты, которые:
    * Запускают 3 инстанса
    * Проверяют, что только один leader
    * Убивают leader
    * Проверяют, что новый leader избран в течение TTL

35. **client-go leader election**: Используйте `k8s.io/client-go/tools/leaderelection` для production-grade leader election в K8s.

36. **Standby leader**: Один primary leader, один standby. При failover standby становится leader мгновенно (не ждет election).

37. **Лидерская выборка с использованием готовой библиотеки (например, `consul-locker`).**: Инкапсулируйте логику в переиспользуемый компонент, который предоставляет интерфейс `IsLeader()`, `Start()`, `Stop()`. Протестируйте конкурентное поведение с 5 узлами.

38. **[Consul Sessions]**: Реализуй выборы лидера через HashiCorp Consul. Создай сессию (`consul.Session.Create`), затем вызови `consul.KV.Acquire` для ключа `service/leader`.

39. **Leader priority**: Назначьте priority для каждого инстанса. При равных условиях leader'ом становится инстанс с высшим priority.

40. **HA-пair Active/Passive.**: Два узла: active пишет heartbeat в etcd каждые 5 сек (`/heartbeat`), passive мониторит. При пропаже heartbeat > `TTL * 2` passive пытается стать active. Покажите race condition при одновременном promote (оба видят пропажу heartbeat). Реализуйте защиту через fencing token (см. Блок 27).

41. **Geographic leader election**: В multi-region setup избирайте leader в том регионе, где большинство клиентов для снижения latency.

42. **Leader lease extension**: Leader продлевает lease только если успешно выполняет свою работу. Если работа stuck — lease expires, failover.

43. **Split-brain защита через Majority Check.**: Лидер перед обработкой write должен убедиться, что видит большинство узлов кластера. Реализуйте: лидер читает `/members` и проверяет `len(members) >= quorum`. Объясните, почему etcd lease alone не защищает от partition (старый лидер может быть в изолированной partition и продлевать lease локально).

44. **[Каверзный кейс — Split Brain (Network Partition)]**: Раздели сеть между лидером и etcd. Лидер потерял связь, но продолжает работать (он думает, что он все еще лидер). etcd истекает TTL ключа и выбирает нового лидера. Теперь у тебя два лидера! Реализуй паттерн: лидер должен *периодически* проверять свое лидерство (делать `etcd.Txn` с проверкой, что его ключ все еще существует перед выполнением работы).

45. **Leader election в Kubernetes**: Используйте Kubernetes Lease objects для leader election внутри K8s cluster (как делает controller-manager).

46. **Мульти-лидер в partition.**: Сымитируйте network partition (iptables DROP между двумя группами узлов). Покажите, что minority (1 из 3) не может избрать лидера в etcd (quorum=2), но может думать, что он лидер, если lease ещё не истёк. Объясните, почему это не проблема etcd, а проблема приложения, которое не проверяет connectivity.

47. **Leader election callbacks**: Реализуйте callbacks: `OnStartedLeading()`, `OnStoppedLeading()`, `OnNewLeader()`.

48. **Leader election + distributed cron**: Только leader запускает cron jobs. При failover новый leader подхватывает schedule.

49. **Интеграция с gRPC/HTTP.**: Реализуйте middleware: только лидер обрабатывает mutating запросы (`POST`/`PUT`/`DELETE`). Followers отвечают `307 Temporary Redirect` с адресом текущего лидера (или `503` + `X-Current-Leader` header). Объясните, как service discovery (Consul DNS или etcd) помогает клиентам найти лидера.

50. **Leader election + task queue**: Leader координирует распределение задач между worker'ами. При failover новый leader перераспределяет задачи.

51. **[Высокая сложность — Active/Passive Failover]**: Создай систему из двух инстансов: Active и Passive. Passive стоит в режиме горячей замены. Когда Active падает, Passive выигрывает выборы, проматывает локальный кэш/состояние и становится новым Active, начиная принимать трафик.

52. **Кампания лидерства на `concurrency/election`.**: Используйте `clientv3/concurrency`. Создайте сессию и участвуйте в выборах (`Election.Campaign`). Запустите несколько узлов, наблюдайте автоматический выбор лидера.

53. **Leader election + metrics aggregation**: Только leader агрегирует метрики со всех инстансов и публикует в Prometheus.

54. **Мониторинг Leader Election.**: Реализуйте метрики: `leader_election_is_leader` (gauge: 0/1), `leader_transitions_total` (counter), `lease_renew_failures_total`, `leader_heartbeat_latency_seconds`. Настройте алерт: если `leader_transitions > 5 за 5 минут` — flapping (возможно, network instability или GC pauses).

55. **Leader election + cache warming**: Только leader прогревает кэш при startup. Остальные инстансы ждут сигнала от leader'а.

56. **Leader election + garbage collection**: Только leader запускает cleanup jobs (удаление старых записей, orphaned resources).

57. **Leader election observability**: Логируйте каждое election event: `Election started`, `Leader elected: instance-2`, `Leader resigned`, `Failover triggered`.

58. **Graceful Step Down с drain.**: При получении `SIGTERM` лидер должен: (1) отказаться от новых lease renew, (2) дождаться завершения текущих in-flight запросов (context с timeout), (3) удалить `/leader` ключ вручную, (4) exit. Объясните, почему это быстрее, чем ждать TTL expiration.

59. **Выборы лидера в Consul**: Подключите клиент Consul: `github.com/hashicorp/consul/api`.
    * Создайте сессию Consul с таймаутом (TTL).
    * Напишите код, который пытается захватить распределенную блокировку на ключ-значение `service/leader`, используя метод `KV.Acquire` с указанием вашей сессии.
    * Если метод вернул `true` — узел стал лидером.

60. **Leader election alerting**: Алерт при:
    * Частые failover (>3 за час) — признак нестабильности
    * Нет leader > 2x TTL — quorum lost
    * Leader tenure < 1 min — признак crash loop

61. **Наблюдение за лидерством и разрешение конфликтов.**: Используйте `Election.Observe` для получения имени текущего лидера. При потере соединения или истечении сессии другой узел вступает в кампанию. Реализуйте логику graceful shutdown с отзывом лидерства.

62. **Leader election + feature flags**: Leader может включать/выключать feature flags для всего кластера через distributed config.

63. **Симуляция отказа (Failover) и Active-Passive воркер**: Напишите фоновую задачу (например, сборщик метрик), которая должна запускаться *строго* на одном узле кластера. Сэмулируйте распределенное окружение: запустите три экземпляра вашей программы на разных портах. Настройте пассивные узлы на наблюдение за ключом лидера (Watcher в etcd или регулярный опрос блокировки в Consul). Принудительно убейте процесс лидера (`SIGKILL`) и убедитесь, что один из пассивных узлов мгновенно обнаружил потерю аренды и объявил себя новым лидером, продолжив сбор метрик.

64. **Leader election + rate limiting**: Leader координирует global rate limit across all instances.

65. **Leader election chaos testing**: Используйте chaos engineering:
    * Убивайте leader случайно
    * Симулируйте network partitions
    * Замедляйте leader heartbeat
    Проверяйте, что система корректно восстанавливается.

66. **Использование etcd для распределенного конфигурационного хранилища.**: Помимо лидерства, храните общую конфигурацию в etcd. Лидер обновляет ключи `/config` через транзакции (STP), а остальные узлы следят за изменениями (`Watch`).

67. **Consul Session**: Установи клиент `github.com/hashicorp/consul/api`. В Consul механизм выборов работает через сессии и блокировки ключей. Создай сессию (Session) с TTL 10 секунд.

68. **Сравнение Consul vs etcd по времени обнаружения сбоя лидера.**: Настройте одинаковые TTL (например, 5с) и измерьте время от остановки лидера до захвата новым узлом. Проведите стресс-тест с частой сменой лидера.

69. **Предотвращение Split-Brain (Кворумные проверки)**: В случае сетевого разделения (network partition) узел-лидер может оказаться изолирован от остального кластера, но продолжать считать себя лидером, если он не может связаться с координатором. Напишите код проверки кворума: лидер должен периодически выполнять быструю проверку связи со своими смежными узлами или координатором (etcd/Consul). Если связь потеряна, лидер должен добровольно сложить с себя полномочия (Step Down) и остановить выполнение критических операций до восстановления консенсуса.

70. **Consul Watcher (Отслеживание)**: Напиши логику Фоловера. Он должен использовать "блокирующий запрос" (Blocking Query) в Consul, чтобы висеть в ожидании и следить за ключом `service/billing/leader`. Как только Лидер падает (ключ освобождается), Фоловеры просыпаются и пытаются сделать `Acquire`.

71. **etcd Leader Election**: Напиши выборы лидера на etcd (это современнее и чаще используется в Go). Создай `concurrency.NewElection(session, "my-election")`. Вызови `election.Campaign(ctx, "worker_1")`. Метод `Campaign` заблокируется! Как только он отвиснет — ты лидер.

72. **Graceful Resignation (Добровольный отказ)**: Лидер должен уметь корректно уходить (например, при выкате новой версии сервиса). Перехвати `SIGTERM` в Go. В обработчике сигнала вызови `election.Resign(ctx)`. Убедись, что другой узел мгновенно становится лидером, без ожидания таймаута аренды.

73. **Наблюдение за выборами (Observe)**: Напиши API-эндпоинт `/leader`, который возвращает, кто сейчас главный. Используй метод `election.Observe()`, который возвращает канал обновлений. Все узлы должны всегда знать имя текущего лидера (например, для перенаправления к нему трафика).

74. **Split-brain protection**: При network partition оба partition могут считать себя leader'ом. Как защититься? Используйте quorum-based consensus (Consul/etcd уже делают это).

75. **Сетевой раздел (Network Partition Simulation)**: Запусти 3 узла etcd и 3 Go-сервиса. Изолируй лидера (например, через `iptables` в Docker обруби ему связь с кластером etcd). Убедись, что:
    * Изолированный лидер понимает, что потерял кворум, и слагает с себя полномочия.
    * Оставшиеся 2 узла проводят выборы и назначают нового лидера.

76. **Leader health checks**: Leader периодически публикует health status. Если health check fails, другие инстансы форсируют новые выборы.

77. **Election backoff**: После проигрыша в выборах инстанс ждет random backoff перед следующей попыткой. Это предотвращает election storms.

78. **Leader election + graceful shutdown**: При SIGTERM leader добровольно resign'ит, чтобы ускорить failover.

79. **Отмена кампании**: Фоловерам может надоесть ждать выборов. Оберни `election.Campaign` в `context.WithCancel`. Отмени контекст через 5 секунд. Убедись, что узел прекращает попытки стать лидером и завершает работу без ошибок.

80. **Интеграция с Cron**: Возьми библиотеку `github.com/robfig/cron/v3`. Напиши джобу, которая выполняется каждую минуту. Внутри джобы добавь проверку: `if !IsLeader() { return }`. Запусти 3 инстанса сервиса и убедись, что джоба выполняется строго 1 раз в минуту одним сервисом.

81. **Split-Brain защита (Double Check)**: Перед выполнением критической операции, Лидер должен убедиться, что он *всё еще* лидер. Вызови чтение ключа лидера в etcd/Consul непосредственно перед транзакцией в БД. Хоть это и не заменит Fencing Tokens (упр. 836), это радикально снизит вероятность гонки.

---

82. **Leader election обязателен для singleton задач.**: Если задача должна выполняться ровно одним инстансом (cron jobs, migrations, reconciliation) — используйте leader election через Consul/etcd.

83. **Quorum — это закон.**: Для 3 узлов quorum = 2. Для 5 узлов quorum = 3. Без quorum кластер не может принимать writes. Всегда используйте odd number of nodes (3, 5, 7).

84. **Raft для strong consistency.**: Если нужна distributed state machine с linearizable semantics — используйте Raft (etcd, Consul, HashiCorp Raft).

85. **Redlock — это best-effort, не consensus.**: Redlock подходит для non-critical locks. Для critical data используйте etcd/Consul locks или Raft.

86. **Leader failover testing.**: Регулярно тестируйте failover: убивайте leader, проверяйте, что новый leader избирается в течение TTL.

87. **Блок 25 (Leader Election)**: — начните после Блока 24 (Idempotency), так как leader election — это частный случай координации, требующий понимания TTL и race conditions. Знания из Блока 1 (GMP, `sync`) помогут понять, почему in-memory leader election не работает при распределении.

88. **Блок 27 (Distributed Locks)**: — проходите параллельно с Leader Election, так как оба используют etcd/Consul и сталкиваются с одной проблемой: lease expiration + network delay. Fencing Tokens — это мост между блокировками и консистентностью.

89. **Test failure scenarios.**: Happy path testing недостаточно. Тестируйте:
    * Leader crash
    * Network partition
    * Lock holder crash
    * Stale lock holder
    * Quorum loss

90. **Блок 26 (Raft)**: — финальный блок координации. Требует понимания всего предыдущего: почему leader election нужен consensus, почему distributed locks без consensus — ненадёжны, как Raft решает проблему split-brain на уровне алгоритма, а не инфраструктуры.
