# Cache-friendly структуры данных и выравнивание памяти

В этом файле собраны уникальные упражнения по теме **"Cache-friendly структуры данных и выравнивание памяти"**, отсортированные по возрастанию сложности.

---

1. **Выравнивание полей структур в памяти (Memory Alignment)**: Напишите две структуры с абсолютно одинаковым набором полей: `int8`, `int64`, `int16`, `string`, `bool`.
    * В `StructBad` расположите поля хаотично (вперемешку мелкие и крупные типы).
    * В `StructGood` отсортируйте поля по убыванию их размера в байтах.
    Выведите размер обеих структур с помощью `unsafe.Sizeof` [175]. Объясните в комментариях концепцию выравнивания памяти на 64-битной архитектуре и почему компилятор вынужден добавлять пустые байты (padding) в первом случае [175].

2. **Padding в структурах.**: Создайте структуру `struct { a bool; b int64; c bool }`. Измерьте `unsafe.Sizeof`, `unsafe.Offsetof` каждого поля. Нарисуйте байтовую карту: `a` (1 байт) + padding (7) + `b` (8) + `c` (1) + padding (7). Переставьте поля (`b`, `a`, `c`) и покажите уменьшение размера с 24 до 16 байт. Объясните, почему компилятор выравнивает по `unsafe.Alignof` самого большого поля.

3. **Демонстрация cache line и false sharing.**: Создайте две переменные `int64`, лежащие в соседних ячейках памяти (например, поля одной структуры). Запустите две горутины, каждая инкрементирует свою переменную. Сравните производительность с вариантом, где переменные разнесены на разные cache line (добавлен padding `[64]byte`).

4. **Анатомия структуры (Padding)**: Создай структуру `type BadStruct struct { a int8; b int64; c int16 }`. Используй `unsafe.Sizeof`. Посчитай вручную: 1 + 8 + 2 = 11 байт. Но Go покажет 24 байта! Нарисуй на бумаге, куда компилятор вставил "пустые" байты (padding) для выравнивания адресов под 64-битную архитектуру.

5. **Cache line size**: Определите размер cache line на вашем CPU через `/sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size` (обычно 64 байта на x86).

6. **[Memory Alignment]**: Создай структуру `BadStruct { a bool; b int64; c bool }` и `GoodStruct { b int64; a bool; c bool }`. Выведи `unsafe.Sizeof` для обеих. Объясни эффект Padding (выравнивание до 8 байт).

7. **Memory alignment basics**: Изучите, как Go выравнивает поля структур. `unsafe.Alignof` показывает требуемое выравнивание для каждого типа.

8. **Alignof и структурное выравнивание.**: Напишите программу, которая для 10 разных типов (`int8`, `int32`, `int64`, `*byte`, `[]int`, `string`, `time.Time`) выводит `unsafe.Alignof`. Объясните, что alignment структуры = max alignment полей, а alignment слайса = alignment указателя (8 байт на 64-бит).

9. **Optimal field ordering**: Переупорядочьте поля по убыванию размера: `type GoodStruct struct { b int64; a bool; c bool }`. Теперь размер 16 байт — сэкономили 33% памяти.

10. **Array of structs vs Struct of arrays**: Сравните:
    ```go
    type AOS []struct{ x, y int64 }  // Array of Structs
    type SOA struct{ x, y []int64 }  // Struct of Arrays
    ```
    Для итерации по одному полю SOA в 2-4x быстрее (лучше cache locality).

11. **Оптимизация Layout'а**: Перепиши `BadStruct`, сгруппировав поля по убыванию размера. Выведи размер — он должен стать 16 байт. Напиши линтер (или используй готовый `fieldalignment`), который находит неоптимальные структуры в твоем коде.

12. **Профилирование false sharing с помощью perf.**: Используя Linux `perf stat -e cache-misses`, измерьте количество cache-промахов в программе с false sharing и без. Покажите, как выравнивание до 64 байт решает проблему.

13. **Cache line splitting**: Создайте структуру размером 65 байт. Изучите, как она располагается в двух cache lines вместо одной — это expensive для频繁访问.

14. **[Cache Line Simulation]**: Напиши программу, которая создает массив `[8]int64`. Горутина A постоянно инкрементирует `arr[0]`, а горутина B — `arr[1]`. Запусти под профайлером и замерь время. Хотя это разные переменные, они находятся в одной линии кэша (64 байта), что вызывает постоянную инвалидацию кэша (Cache Coherence Ping-Ponging).

15. **Размер cache line.**: Определите размер cache line вашего CPU: создайте массив `[1024]int64`, обходите с шагом 1, затем с шагом 8 (64 байта). Замерьте время. Покажите скачок latency при переходе через границу 64 байт. Объясните L1d cache line (обычно 64 байта, иногда 128 на ARM).

16. **False Sharing: демонстрация.**: Создайте структуру с двумя полями `counterA, counterB uint64`. Запустите 2 goroutine: каждая инкрементит своё поле 100 млн раз. Замерьте время. Объясните, почему производительность падает в 10-20×: оба поля в одной cache line (64 байта), CPU cores гоняются за exclusive ownership (MESI протокол).

17. **Struct embedding alignment**: При embedding структур Go сохраняет alignment requirements. Изучите, как это влияет на overall struct size.

18. **Локальность данных (Pointer Chasing)**: Напиши бенчмарк. Создай Связный список (Linked List) из 10 миллионов узлов и Срез (`[]int`) из 10 миллионов чисел. Напиши две функции, которые суммируют все элементы. Убедись, что срез суммируется в разы быстрее, так как его данные лежат в памяти последовательно и CPU предварительно загружает их в L1-кэш (Prefetching), в то время как список вызывает постоянные промахи кэша (Cache Misses).

19. **Устранение ложного разделения кэш-линий (False Sharing)**: * Объясните в комментариях проблему: процессор читает данные из ОЗУ в кэш линиями по 64 байта. Если два ядра параллельно пишут в независимые переменные, расположенные на одной кэш-линии, это вызывает постоянную инвалидацию кэша (L1/L2 Cache Invalidation) на обоих ядрах, резко снижая производительность.
    * Напишите структуру счетчиков для 4 параллельных воркеров.
    * Смоделируйте падение производительности из-за False Sharing.
    * Оптимизируйте структуру: добавьте отступы (padding) между счетчиками в виде пустых массивов байт `_ [56]byte` (или используйте специальный тип `cpu.CacheLinePad` из пакета `golang.org/x/sys/cpu`) [627]. Напишите бенчмарк и сравните скорость работы до и после оптимизации.

20. **Alignment в слайсах**: Элементы слайса всегда aligned. Но если вы делаете `unsafe.Slice` из arbitrary pointer — убедитесь в alignment, иначе SIGBUS на некоторых архитектурах.

21. **Оптимизация структуры для уменьшения размера (alignment/padding).**: Создайте структуру с неоптимальным порядком полей (`int64`, `bool`, `int64`, `bool`). Проанализируйте размер через `unsafe.Sizeof` и `alignof`. Переставьте поля, чтобы минимизировать паддинг и общий размер структуры.

22. **Cache prefetching hints**: Изучите, как CPU prefetcher работает: sequential access patterns prefetch автоматически, random access — нет. Оптимизируйте access patterns.

23. **[Устранение False Sharing]**: Измени массив из предыдущего задания на структуру `PaddedCounter { val int64; _ [56]byte }`. Создай массив `[8]PaddedCounter`. Замерь время снова. Оно должно ускориться в 5-10 раз, так как каждый счетчик теперь занимает ровно одну линию кэша.

24. **Устранение False Sharing через padding.**: Добавьте между полями `[56]byte` (или `[64]byte` для выравнивания). Повторите бенчмарк. Покажите восстановление производительности. Объясните, почему `runtime` делает то же самое в `runtime/proc.go` (поля `p` разнесены по разным cache lines).

25. **Software prefetch**: Используйте `//go:noescape` и manual prefetch через ассемблер для critical loops (хотя Go не exposes prefetch intrinsics напрямую).

26. **TLB (Translation Lookaside Buffer)**: Поймите, что virtual → physical address translation кэшируется в TLB. Большие страницы (huge pages, 2MB/1GB) снижают TLB misses.

27. **SoA vs AoS (Структура массивов)**: В играх и физических движках используется паттерн SoA. Создай массив структур `[]Point{X, Y, Z float64}` (AoS) и структуру массивов `PointList{X []float64, Y []float64, Z []float64}` (SoA). Напиши бенчмарк, который сдвигает все точки только по оси `X`. Убедись, что SoA работает сильно быстрее из-за идеальной утилизации L1-кэша.

28. **Huge pages в Go**: Включите huge pages через `GODEBUG=memprofilerate=0` и настройте OS для использования transparent huge pages. Измерьте влияние на memory-intensive workloads.

29. **Cache-line aligned счётчик.**: Реализуйте `type PaddedCounter struct { _ [64]byte; v uint64; _ [64]byte }`. Используйте в массиве по одному на CPU core. Покажите linear scaling при увеличении числа goroutine (по числу CPU). Объясните, зачем padding с обеих сторон (защита от соседних переменных).

30. **Доступ к массиву по строкам vs по столбцам (cache locality).**: Напишите обход матрицы `[][]int` (или плоского слайса): построчно и постолбцово. Сравните производительность для больших матриц, объясните влияние cache lines и prefetch.

31. **NUMA-aware allocation**: Для extreme performance аллоцируйте память на том NUMA node, где будет выполняться обработка (через `mbind` syscall).

32. **[Cache-friendly Traversal]**: Напиши бенчмарк, который суммирует элементы матрицы 1024x1024. Сравни обход по строкам (Row-Major) и по столбцам (Column-Major). Объясни, почему обход по столбцам медленнее в 10 раз (Cache Misses).

33. **Struct of Arrays (SoA) vs Array of Structs (AoS).**: Создайте 1 млн объектов `Point { x, y float64 }`. Реализуйте сумму всех `x`: (1) `[]Point` (AoS), (2) `struct { xs, ys []float64 }` (SoA). Бенчмарк. Объясните, почему SoA быстрее (sequential access, prefetcher, меньше cache misses), но сложнее в поддержке.

34. **Cache associativity**: Изучите, что cache имеет ограниченную associativity (обычно 8-way). Access patterns с stride = cache size * associativity могут вызывать conflict misses.

35. **Создание False Sharing (Ложное разделение)**: Создай `type Counters struct { a uint64; b uint64 }`. Запусти две горутины (строго на разных ядрах через `runtime.LockOSThread`). Первая в цикле делает миллион раз `c.a++`, вторая — `c.b++`. Замерь время.

36. **Паттерн AoS против SoA (Array of Structures vs Structure of Arrays)**: Спроектируйте две модели хранения данных о 1 000 000 точек в 3D-пространстве (координаты `X, Y, Z float64`):
    * Срез структур (AoS — Array of Structures): `[]Point{ {X, Y, Z}, ... }`.
    * Структура срезов (SoA — Structure of Arrays): `struct { X []float64; Y []float64; Z []float64 }`.
    Напишите бенчмарк, который вычисляет сумму всех координат `X` для обеих моделей. Объясните, почему модель SoA оказывается значительно быстрее при анализе отдельных атрибутов за счет пространственной локализации данных (Spatial Locality) в кэше процессора.

37. **Cache coloring**: Для critical data structures используйте cache coloring — распределяйте данные так, чтобы они не конфликтовали в cache sets.

38. **Alignment для SIMD**: Для SIMD операций данные должны быть выровнены по 16/32/64 байта. Используйте `//go:build align` или manual padding.

39. **Memory bandwidth**: Измерьте memory bandwidth вашего CPU через `stream` benchmark. Типичные значения: 20-50 GB/s для DDR4, 50-100 GB/s для DDR5.

40. **Alignment для atomic операций.**: Создайте массив счётчиков `[]uint64`. Покажите, что `atomic.AddUint64(&counters[i])` паникует на ARM32/ARM64, если адрес не выровнен на 8 байт. Объясните, почему `sync/atomic` требует alignment и как `struct` padding решает это.

41. **Префетчинг в Go.**: Используйте встроенные инструкции `prefetch` (через ассемблерную вставку или intrinsics на уровне unsafe) для предварительной подгрузки данных в кэш, эмулируя обход связного списка. Сравните скорость обычного обхода и с prefetch.

42. **Cache coherency protocol (MESI)**: Изучите MESI protocol:
    * Modified (эксклюзивно изменён)
    * Exclusive (эксклюзивно чист)
    * Shared (разделён между кэшами)
    * Invalid (недействителен)

43. **Объяснение False Sharing**: Пойми, что поля `a` и `b` лежат рядом (занимают 16 байт) и попадают в **одну** кэш-линию процессора (64 байта). Когда ядро 1 меняет `a`, оно инвалидирует всю кэш-линию для ядра 2 (которое меняет `b`), заставляя процессор постоянно гонять данные по шине между L1-кэшами разных ядер.

44. **[SoA vs AoS (Data Locality)]**: Создай структуру `Entity { ID int; Active bool; Data [50]int }`. Создай слайс из 100 000 таких структур (Array of Structs). Напиши бенчмарк, который суммирует `ID` только активных сущностей. Затем перепиши на Struct of Arrays (SoA): `IDs []int`, `Actives []bool`. Оцени колоссальную разницу в скорости из-за плотности данных в кэше.

45. **Cache line bouncing**: Когда CPU0 пишет в cache line, все другие CPU должны инвалидировать свои копии этой cache line. Это expensive (десятки-сотни наносекунд).

46. **Предотвращение conflict misses.**: Создайте массив размером 8192 `int64` (64 KB, ровно L1 cache size на многих CPU). Обходите с шагом 512 байт (8 элементов). Объясните, почему при определённых размерах (кратных степени 2) возникают conflict misses (associativity limit). Решение: добавить padding к строке (slice of structs с trailing `[X]byte`).

47. **False sharing demonstration**: Создайте структуру:
    ```go
    type Counter struct {
        value int64
    }
    type Counters struct {
        c [8]Counter
    }
    ```
    Запустите 8 горутин, каждая инкрементирует свой `Counter`. Измерьте производительность.

48. **False sharing fix через padding**: Добавьте padding между counters:
    ```go
    type PaddedCounter struct {
        value int64
        _     [56]byte  // pad to 64 bytes
    }
    ```
    Теперь каждый counter в отдельной cache line. Производительность должна вырасти в 5-10x.

49. **Custom allocator с alignment.**: Реализуйте аллокатор, который выделяет `[]byte` и возвращает `unsafe.Pointer` выровненный на 64 байта (для SIMD). Используйте `uintptr(ptr) + (alignment - uintptr(ptr)%alignment)`. Объясните, почему это нужно для `mmap` + SIMD load (`MOVOA` требует 16-byte alignment, `VMOVDQA` — 32-byte).

50. **Per-CPU counters**: Вместо одного global counter используйте per-CPU counters. Каждый CPU пишет в свой counter, периодически aggregate в global.

51. **Устранение False Sharing (Padding)**: Добавь между `a` и `b` мусорное поле-отступ (padding), чтобы они гарантированно оказались в разных кэш-линиях: `_ [56]byte` (или `_ [7]uint64`). Запусти бенчмарк из 865 снова и насладись кратным ускорением!

52. **Batch updates**: Вместо `atomic.Add(&counter, 1)` на каждое событие, accumulate в local variable и flush в global counter каждые 1000 операций.

53. **Оптимизация обхода двумерных массивов**: Создайте матрицу размером `[2000][2000]int`. Напишите две функции суммирования элементов матрицы:
    * Первая обходит матрицу по строкам (row-major order): `matrix[row][col]`.
    * Вторая обходит матрицу по колонкам (column-major order): `matrix[col][row]`.
    Напишите бенчмарк и сравните их производительность. Напишите подробный комментарий, объясняющий, почему обход по строкам эффективнее из-за работы механизма CPU prefetching (последовательное чтение соседних ячеек памяти).

54. **Thread-local storage**: Используйте `sync.Pool` или `g` (goroutine-local storage через `runtime.g`) для thread-local counters.

55. **False sharing detection**: Используйте `perf c2c` (Linux) для детекта false sharing. Это покажет, какие cache lines вызывают наибольшее contention.

56. **CPU Profiling с `perf`**: (Только для Linux). Скомпилируй код из 865 и 867. Запусти их через системную утилиту `perf stat -e cache-misses ./app`. Посмотри на физическое количество промахов кэша процессора и сравни результаты.

57. **False sharing в слайсах**: Если multiple goroutines обращаются к разным элементам слайса, убедитесь, что элементы не в одной cache line (или используйте padding).

58. **False sharing в мапах**: Go мапы имеют internal locking per bucket. Но если вы используете custom concurrent map — избегайте false sharing между buckets.

59. **False sharing в tree structures**: В B-tree или skip list parent и child nodes могут быть в одной cache line. Это вызывает false sharing при concurrent updates.

60. **Column-major vs Row-major**: Напиши двойной цикл для обхода двумерного массива (матрицы 10000x10000). В первом бенчмарке обходи `matrix[i][j]` (по строкам), во втором — `matrix[j][i]` (по колонкам). Пойми, почему второй вариант медленнее в десятки раз.

61. **False sharing в hash tables**: Open addressing hash tables могут иметь false sharing между adjacent slots. Используйте separate chaining или padding.

62. **Поиск без указателей (Pointerless Structs) для оптимизации GC**: Напишите программу, которая создает в оперативной памяти хэш-таблицу на 10 000 000 элементов. Сравните два варианта структур в качестве значений мапы:
    * Структура с указателями: `struct { Name string; Data []byte }` (содержит указатели внутри).
    * Структура без указателей: `struct { Name [32]byte; ID int64 }` (чистые сырые байты на стеке/куче).
    Запустите принудительный сборщик мусора `runtime.GC()` [494]. Замерьте время паузы Stop-The-World (STW). Объясните, почему GC игнорирует структуры без указателей при сканировании кучи, и как этот паттерн помогает бороться с задержками GC на больших объемах данных.

66. **Пул объектов (sync.Pool Cache Locality)**: Докажи на бенчмарках, почему `sync.Pool` работает так быстро: "под капотом" каждый `P` (виртуальный процессор Go) имеет свой собственный приватный пул, к которому обращается без блокировок, и эти объекты "теплые" (уже лежат в кэше ядра).

67. **False sharing в counters array**: Массив counters, где каждый thread пишет в свой элемент. Без padding — false sharing. С padding — нет.

68. **False sharing mitigation checklist:**
    * Per-thread/per-CPU data structures
    * Padding между shared variables
    * Batch updates
    * Thread-local accumulation
    * Cache line alignment

69. **B-tree vs Binary tree**: B-tree имеет лучшую cache locality, чем binary tree, потому что узлы содержат multiple keys в одном cache line.

70. **Struct of Arrays (SoA) для SIMD**: Для vectorized operations используйте SoA:
    ```go
    type Particles struct {
        x []float32
        y []float32
        z []float32
    }
    ```
    Это позволяет SIMD обрабатывать 8 `x` координат одновременно.

71. **Array of Structures (AoS) для OOP**: Для object-oriented кода используйте AoS:
    ```go
    type Particle struct { x, y, z float32 }
    type Particles []Particle
    ```
    Это лучше для итерации по всем полям одного объекта.

72. **Hybrid SoA/AoS**: Для mixed workloads используйте hybrid:
    ```go
    type Particles struct {
        positions []Position  // hot data (frequently accessed)
        metadata  []Metadata  // cold data (rarely accessed)
    }
    ```

73. **Hot/cold splitting**: Разделите структуру на hot fields (часто accessed) и cold fields (редко accessed). Hot fields в одной cache line, cold — отдельно.

74. **False sharing в ring buffers**: Ring buffer с producer и consumer indices в одной cache line — классический false sharing. Разделите их padding'ом.

75. **Pointer-free structures**: Избегайте указателей в структурах, которые итерируются. Pointers cause cache misses (pointer chasing).

76. **Inline small structs**: Для маленьких структур (< 16 байт) используйте value semantics вместо pointer. Это избегает pointer indirection.

77. **Chunked arrays**: Для dynamic arrays используйте chunked arrays (array of arrays). Это избегает expensive reallocation и улучшает cache locality.

78. **Cache-friendly hash table**: Open addressing с linear probing имеет лучшую cache locality, чем separate chaining.

79. **Robin Hood hashing**: Улучшение linear probing, которое снижает variance в probe length и улучшает cache behavior.

80. **Swiss tables (Abseil)**: Изучите Swiss tables (используются в Google Abseil) — cache-friendly hash table с SIMD-ускоренным probing.

81. **Cache-friendly matrix**: Для matrix operations используйте block matrix layout (tiles). Каждый tile влезает в L1 cache.

82. **Cache-friendly tree**: Для деревьев используйте implicit tree layout (array-based heap). Parent at `i`, children at `2i+1` и `2i+2`.

83. **Cache-friendly serialization**: Для serialization используйте flat binary format вместо nested structures. Это sequential read/write.

84. **Cache-friendly stack**: Flat array с pre-allocated capacity. Избегайте linked list stack.

85. **Cache-friendly string pool**: Для множества строк используйте string pool (один большой array + offsets). Это лучше, чем множество отдельных string allocations.

86. **Pointer compression**: Для структур с множеством указателей используйте offset вместо pointer (если все pointers в одном heap allocation). Это снижает memory footprint и улучшает cache locality.

87. **NUMA (Non-Uniform Memory Access)**: На multi-socket servers memory access latency зависит от того, какой CPU обращается к какой памяти. Используйте `numactl` для pinning процессов к NUMA nodes.

88. **Roofline model**: Постройте roofline model для вашего кода: сравните computational intensity (FLOPs/byte) с memory bandwidth и compute throughput. Это покажет, memory-bound или compute-bound ваш код.

89. **Pointer chasing — это cache miss.**: Linked list требует cache miss на каждый элемент. Flat array — sequential access, prefetcher работает. Избегайте linked structures в hot paths.

90. **Cache-oblivious algorithms**: Изучите cache-oblivious B-tree (van Emde Boas layout) — структура, которая оптимальна для любого cache line size без знания этого size.

91. **Cache line — это 64 байта.**: Всё, что вы делаете, должно учитывать этот факт. Структуры, которые используются вместе, должны быть в одной cache line. Структуры, которые используются разными threads, должны быть в разных cache lines.

92. **False sharing — тихий убийца производительности.**: Два thread'а, пишущие в разные переменные в одной cache line, вызывают cache line bouncing. Это может замедлить код в 10-100x. Используйте padding.

93. **Memory alignment обязателен.**: Неaligned access может быть в 10x медленнее или вызвать SIGBUS на некоторых архитектурах. Go автоматически align'ит поля структур, но manual optimization требует понимания.

94. **Batch operations для throughput.**: Вместо одного message за раз, batch process N messages. Это снижает overhead per message и улучшает cache locality.

95. **Блок 28 (Alignment)**: — начните после Блока 2 (аллокатор), так как `mcache`/`mspan` тесно связаны с alignment. Понимание `unsafe` из Блока 4 обязательно для измерения layout.

96. **Software prefetch для predictable access.**: Если вы знаете, какие данные понадобятся через N iterations, используйте software prefetch. Это скрывает memory latency.

97. **Measure, don't guess.**: Всегда benchmark'ите оптимизации. Intuition часто wrong. Используйте `perf`, `vtune`, `pprof` для profiling.

98. **Test на real hardware.**: Microbenchmarks на laptop могут не отражать production behavior. Тестируйте на real servers с similar CPU, memory, NUMA topology.
