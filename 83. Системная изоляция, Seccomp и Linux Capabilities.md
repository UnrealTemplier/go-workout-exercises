# Системная изоляция, Seccomp и Linux Capabilities

В этом файле собраны уникальные упражнения по теме **"Системная изоляция, Seccomp и Linux Capabilities"**, отсортированные по возрастанию сложности.

---

1. **Мониторинг лимитов файловых дескрипторов (ulimit)**: Напишите программу, которая при старте запрашивает и выводит в лог текущие лимиты операционной системы на количество одновременно открытых файлов (файловых дескрипторов) с помощью системного вызова `syscall.Getrlimit(syscall.RLIMIT_NOFILE, &limit)` [665]. Объясните, как слишком низкий лимит `NOFILE` на сервере облегчает задачу злоумышленника по выводу вашей системы из строя (Denial of Service).

2. **CAP_NET_BIND_SERVICE**: В Linux процессы без root-прав не могут слушать порты < 1024. Скомпилируй Go-бинарник, который слушает порт 80 (HTTPS). Запусти его от имени обычного пользователя — получи ошибку `bind: permission denied`. Используй утилиту ОС `sudo setcap cap_net_bind_service=+ep ./app`. Запусти снова от обычного юзера — магия, порт 80 работает без root!

3. **SecComp Basics (libseccomp-golang).**: Напишите Go-программу, которая через `github.com/seccomp/libseccomp-golang` разрешает только `read`, `write`, `exit`, `exit_group`, `rt_sigreturn`, `epoll_wait`, `accept4`, `close`. При попытке `os.Open` (syscall `openat`) — процесс получает `SIGSYS` и умирает. Объясните whitelist-подход.

4. **Ограничение системных вызовов через SecComp**: Напишите подробный комментарий, объясняющий концепцию SecComp (Secure Computing Mode) в Linux [666]. Объясните, как ограничение доступных системных вызовов для бинарного файла Go на уровне ядра операционной системы предотвращает эксплуатацию уязвимостей (даже если злоумышленник найдет уязвимость выполнения удаленного кода RCE, он не сможет выполнить системный вызов `execve` для запуска командной строки `bash`, если этот вызов заблокирован профилем SecComp) [666, 667].

5. **Введение в Seccomp (Secure Computing Mode)**: Seccomp — это файрвол для системных вызовов (syscalls). Установи CGO-библиотеку `github.com/seccomp/libseccomp-golang`.

6. **SecComp BPF вручную.**: Создайте `[]unix.SockFilter` вручную: `BPF_STMT` для загрузки syscall number, `BPF_JUMP` для сравнения. Примените через `unix.Prctl(unix.PR_SET_SECCOMP, unix.SECCOMP_MODE_FILTER, ...)`. Объясните, что SecComp filter — это BPF-программа, выполняемая ядром на каждом syscall.

7. **Seccomp (Блокировка Exec)**: Напиши Go-программу, которая делает `os.Exec("ls")`. Убедись, что она работает. Теперь добавь Seccomp фильтр, который **запрещает** системный вызов `execve` (выполнение других программ). Попробуй сделать `os.Exec` — твоя программа будет мгновенно убита ядром ОС с сигналом `SIGSYS`. *Хакер больше не сможет запустить bash-шелл из твоего сервиса!*

8. **Syscall Audit для Go-приложения.**: Запустите Go HTTP-сервер под `strace -f -e trace=%network,%file -o trace.log`. Проанализируйте все syscall. Составьте whitelist для SecComp на основе реального trace. Объясните, почему Go runtime требует `mmap`, `futex`, `clone`, `sigaltstack`, `epoll_create1`, `getrandom` — и как их не забыть в фильтре.

9. **Написание кастомного JSON-профиля SecComp**: Напишите пример конфигурационного JSON-файла профиля SecComp для Docker / Kubernetes [667]. Настройте белый список разрешенных системных вызовов, необходимых для работы сетевого Go-приложения (например, `read`, `write`, `accept4`, `epoll_pwait`, `futex`, `nanosleep`), и полностью запретите вызовы создания процессов и работы с файловой системой (`execve`, `fork`, `clone`, `chmod`) [667].

10. **Создание Seccomp профиля для Go-приложения.**: С помощью `strace` определите системные вызовы, используемые вашим сервером. Создайте seccomp-профиль, разрешающий только их. Запустите приложение с этим профилем через `docker run --security-opt seccomp=profile.json`.

11. **Seccomp (Whitelist режим)**: Усложни фильтр. Настрой Seccomp так, чтобы по умолчанию убивать процесс при любом сисколле, и добавь в разрешенный белый список (Whitelist) только те сисколлы, которые нужны Go-программе (`read`, `write`, `epoll_wait`, `futex`, `mmap`). Это наивысшая паранойя уровня систем нулевого доверия (Zero Trust).

12. **SecComp Notify (Linux 5.0+).**: Используйте `seccomp_unotify` для перехвата `openat` в userspace. Напишите supervisor (отдельный процесс), который получает уведомление, проверяет путь (`/app/data/*` — разрешить, `/etc/shadow` — запретить), отправляет ответ ядру. Объясните, как это используется в rootless containers (containerd/runc).

13. **SecComp Profile для контейнера.**: Напишите JSON SecComp profile для Docker: `defaultAction: SCMP_ACT_ERRNO`, разрешить `accept4`, `read`, `write`, `epoll_wait`, `futex`, `mmap`, `munmap`, `clone`, `exit`, `exit_group`, `rt_sigreturn`, `getrandom`. Запретить `execve`, `execveat`, `ptrace`, `mount`, `umount2`, `chroot`, `setns`, `unshare`. Объясните, почему `execve` — критично (RCE prevention).

14. **Отбрасывание привилегий (Drop Privileges)**: Твоей программе нужен root для старта (например, чтобы открыть сокет или прочитать сертификат). После старта HTTP-сервера, вызови `unix.Setuid(1000)` и `unix.Setgid(1000)`, чтобы программа "понизила" себя до прав обычного пользователя. Если хакер взломает её позже, у него уже не будет root-прав.

15. **Запуск с минимальными capabilities.**: В Dockerfile задайте `USER nonroot`, удалите все capabilities, кроме необходимых (`NET_BIND_SERVICE` для портов <1024). Проверьте, что приложение не может выполнить `CAP_SYS_ADMIN` операции.

16. **AppArmor Profile.**: Напишите AppArmor profile для Go-бинарника: `network inet stream`, `capability net_bind_service`, `/app/config/** r`, `/app/data/** rwk`, deny `/etc/** w`. Загрузите через `apparmor_parser`. Объясните MAC (Mandatory Access Control) vs DAC: AppArmor ограничивает *программу*, независимо от user ID.

17. **Изоляция Файловой Системы (Chroot)**: Вызови системный вызов `unix.Chroot("/var/www/jail")`. Программа будет думать, что эта папка — это корень диска `/`. Попытайся прочитать `/etc/passwd`. Ты получишь ошибку, потому что программа больше физически не видит файлы за пределами своей "тюрьмы".

18. **Linux Capabilities.**: Напишите Go-программу, которая через `golang.org/x/sys/unix` сбрасывает все capabilities через `capset` (или `prctl(PR_CAP_AMBIENT, PR_CAP_AMBIENT_CLEAR_ALL, 0, 0, 0)`). Оставьте только необходимые (`CAP_NET_BIND_SERVICE` если нужен порт <1024). Объясните, почему `CAP_NET_BIND_SERVICE` не нужен для портов >1024, и зачем `ALL` drop.

19. **AppArmor профиль для Go-сервиса.**: Создайте простой AppArmor профиль, ограничивающий доступ к файловой системе (только чтение конфигурационного файла). Загрузите профиль и запустите сервис в enforce mode.

20. **Защита Docker-образа (Read-Only FS)**: Хакеры часто качают скрипты-майнеры через уязвимости, сохраняя их в папку `/tmp`. Запусти свой Docker-контейнер с флагом `--read-only`. Убедись, что сервер работает (если логи пишутся в stdout). Если твой код попытается создать файл на диске, ОС вернет `Read-only file system`. Это ломает 90% автоматизированных эксплойтов!

21. **Network Namespaces + cgroup v2.**: Создайте network namespace (`ip netns add appns`), запустите Go-приложение внутри через `ip netns exec appns ./app`. Настройте cgroup v2: `echo 100000000 > /sys/fs/cgroup/app/memory.max`, `echo "100000 1000000" > cpu.max`, `echo 100 > pids.max`. Объясните, как изоляция ресурсов защищает от fork bombs и memory exhaustion.

22. **Понижение привилегий в Kubernetes (SecurityContext)**: Настрой свой K8s Deployment. Добавь в `securityContext` следующие строки: `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, `readOnlyRootFilesystem: true`, и сбрось все Linux Capabilities: `capabilities: { drop: ["ALL"] }`. Добейся того, чтобы твое Go-приложение успешно запустилось в такой максимально враждебной/ограниченной среде.

23. **eBPF для Runtime Security.**: Напишите простую eBPF-программу (C + `cilium/ebpf` или `libbpf-go`) для трассировки `tcp_connect` в Go-приложении. При соединении с неожиданным IP (не из whitelist) — отправляйте alert в userspace. Объясните, как eBPF позволяет обнаруживать аномалии без модификации приложения (runtime security, Falco-style).

24. **Воспроизводимые сборки (Reproducible Builds).**: Соберите бинарник с флагами `-trimpath` и `-ldflags="-buildid="`. Убедитесь, что два последовательных запуска дают идентичный хэш (с точностью до `mod_timestamp`). Настройте CI для проверки детерминированности сборки.

25. **AppArmor / SELinux (Интеграция)**: *Исследовательское.* Узнай, как написать AppArmor профиль для твоего бинарника, который разрешает исходящие сетевые подключения только к IP-адресу твоей базы данных (PostgreSQL), и блокирует ЛЮБЫЕ другие коннекты. Примени этот профиль к Docker-контейнеру.

26. **eBPF (Взгляд в будущее)**: (Потребуется пакет `github.com/cilium/ebpf`). eBPF — это способ писать программы, работающие прямо внутри ядра Linux. Напиши простейшую eBPF C-программу, скомпилируй её (через `bpf2go`) и загрузи из своего Go-кода. Заставь её отслеживать каждый системный вызов `connect()` (попытку установить TCP-соединение) на уровне всей операционной системы и выводить IP-адреса в консоль твоего Go-приложения.

**Итог SecOps блока:**
Многие считают, что безопасность — это дело сисадминов. Это фатальная ошибка. Сисадмин не сможет настроить Seccomp или `ReadHeaderTimeout`, потому что это делается *внутри* исходного кода.

Инженер, который понимает, как защитить сокеты от исчерпания FD, как отрубить процессу Capabilities и как собрать Reproducible Build (упр. 926) — это специалист, которому доверяют архитектуру банковских, финтех и государственных систем. Ты на вершине!

27. **Изоляция ядра с помощью `gVisor`**: Напишите аналитическое эссе-сравнение стандартного рантайма Docker (`runc`) и песочницы `gVisor` (рантайм `runsc` от Google) [670]. Объясните, как gVisor перехватывает системные вызовы контейнера и обрабатывает их в пользовательском пространстве на Go (ядро Sentry), полностью изолируя контейнер от реального ядра хост-системы и защищая инфраструктуру от атак класса Container Escape (побег из контейнера на хост) [670].
