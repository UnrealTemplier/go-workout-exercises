# Безопасность веб-приложений и защита API

В этом файле собраны уникальные упражнения по теме **"Безопасность веб-приложений и защита API"**, отсортированные по возрастанию сложности.

---

1. **Защита от тайминг-атак.**: Реализуйте собственную (уязвимую) функцию сравнения строк через `==` и безопасную через `crypto/subtle.ConstantTimeCompare`. Покажите разницу в поведении через измерение времени (искусственно, с пояснением опасности).

2. **Защита от Doс на переполнение памяти (Payload Limit)**: При разборе входящего JSON-тела POST-запроса злоумышленник может отправить файл размером 5 ГБ, что мгновенно вызовет нехватку оперативной памяти (OOM) и падение вашего сервера. Напишите middleware, которое принудительно оборачивает чтение тела запроса `req.Body` в ограничитель размера `http.MaxBytesReader` [549] (например, лимит 1 МБ) перед вызовом `json.NewDecoder` [549]. Протестируйте поведение, отправив файл большего размера.

3. **Ограничение размера тела.**: Реализуйте middleware с `http.MaxBytesReader` (например, 1 MB). Покажите, что JSON на 100 MB вызывает `http: request body too large`. Объясните, почему `json.NewDecoder(r).Decode(&v)` без лимита — уязвимость.

4. **Безопасный JSON Decoder.**: Напишите обёртку над `json.Decoder`, которая: (1) ограничивает глубину вложенности (защита от stack exhaustion через deeply nested JSON), (2) использует `UseNumber` для предотвращения float64 truncation, (3) проверяет количество ключей в объекте. Объясните, почему `encoding/json` по умолчанию не защищён от этих атак.

5. **Защита от SSRF (Server-Side Request Forgery)**: Ваше приложение принимает от пользователя URL картинки, скачивает её по HTTP и сохраняет на диск.
    * Объясните опасность атаки: если пользователь передаст адрес `http://127.0.0.1:8080/admin` или локальные IP-адреса вашей внутренней сети (RFC 1918), ваш сервер сам сделает опасный запрос во внутренний контур [550].
    * Напишите безопасный HTTP-клиент: перед отправкой запроса выполните резолвинг хоста в IP-адрес. Напишите проверку, блокирующую запрос, если IP-адрес относится к приватным диапазонам, loopback (`127.0.0.1`) или link-local (`169.254.169.254`) [550]. Используйте методы `net.IP.IsLoopback` и `net.IP.IsPrivate` [550].

6. **Rate Limiting.**: Реализуйте token bucket rate limiter (per IP и per user) с использованием `golang.org/x/time/rate`. Примените к endpoint `/login` для защиты от brute-force. Объясните, почему rate limit на уровне reverse proxy (nginx) недостаточен для логики приложения.

7. **Защита от OOM (Billion Laughs / Large Body)**: Ты принимаешь JSON от пользователя. Если хакер пришлет 10 ГБ файл, `io.ReadAll(r.Body)` вызовет Out Of Memory и сервер упадет. Оберни чтение в `http.MaxBytesReader(w, r.Body, 1024*1024)` (лимит 1 МБ). Убедись, что при превышении лимита запрос прерывается.

8. **SSRF: атака и защита.**: Реализуйте сервис, который по URL делает HTTP-запрос (например, webhook fetch). Покажите атаку: `http://127.0.0.1:22/`, `http://169.254.169.254/latest/meta-data/` (AWS metadata), `http://internal-service/`. Напишите защиту: parse URL, resolve IP через `net.Resolver`, проверка against blocklist (loopback, link-local, private ranges), deny по умолчанию (whitelist), запрет redirects.

9. **Path Traversal.**: Реализуйте endpoint `/files?name=report.pdf`. Покажите атаку `../../../etc/passwd`. Исправьте: `filepath.Clean`, `filepath.Join` с базовой директорией, проверка `strings.HasPrefix` после clean. Объясните, почему `filepath.Clean` alone недостаточно.

10. **Автоматический аудит уязвимостей (gosec)**: Напишите два SQL-запроса к базе данных: один небезопасный (с конкатенацией пользовательской строки в тело запроса) и один безопасный (с использованием параметров). Установите инструмент статического анализа безопасности Go — `github.com/securego/gosec` [551]. Запустите проверку вашего кода через консоль и убедитесь, что `gosec` находит уязвимую конкатенацию и предупреждает о возможности SQL-инъекции [551].

11. **Защита от Mass Assignment**: Ты парсишь JSON `{"name":"Ivan", "is_admin":true}` в структуру `User`. Если в структуре есть поле `IsAdmin` с тегами json, хакер получит права админа!
    *Решение:* Изолируй DTO (см. упр. 556). А также при парсинге используй `decoder := json.NewDecoder(r.Body); decoder.DisallowUnknownFields()`. Теперь, если хакер пришлет лишнее поле, парсер вернет ошибку.

12. **[SSRF Prevention]**: Напиши HTTP-клиент, который принимает URL от пользователя. Распарси URL, резолви его в IP-адрес (`net.LookupIP`). Проверь, что IP не является приватным (`net.IP.IsPrivate()`, `IsLoopback()`, `IsLinkLocalUnicast()` — защита от доступа к 169.254.169.254 AWS Metadata и локальным сервисам).

13. **HSTS (HTTP Strict Transport Security)**: Установите `Strict-Transport-Security` header для форсированного HTTPS.

14. **SQL Injection через Go**: Покажите, что Go `database/sql` с placeholders защищён от SQLi по дизайну. Но конкатенация строк всё ещё опасна.

15. **Уязвимость SSRF (Server-Side Request Forgery)**: Напиши эндпоинт `/fetch?url=...`, который скачивает картинку по URL и отдает клиенту. Вызови его с `url=http://localhost:8080/admin_metrics` (или `http://169.254.169.254` для AWS). Убедись, что твой сервер услужливо скачал внутренние секретные данные и отдал их хакеру.

16. **XSS (Cross-Site Scripting)**: Напишите код с XSS-уязвимостью в template и исправьте её через `html/template` (автоматический escape) и CSP header.

17. **Command Injection.**: Реализуйте функцию, которая конвертирует изображение через `exec.Command("convert", input, output)`. Покажите уязвимость при `input = "input.jpg; rm -rf /"`. Исправьте: строгая валидация regex, передача аргументов слайсом (без shell), использование `filepath.Ext` whitelist.

18. **[Каверзный кейс — DNS Rebinding]**: В предыдущем задании после проверки IP злоумышленник может сменить DNS-запись. Используй кастомный `net.Dialer` с `Control` функцией, которая проверяет IP-адрес прямо в момент установления TCP-соединения (на уровне сокета), блокируя приватные сети.

19. **SQL Injection.**: Напишите уязвимый запрос через `fmt.Sprintf("SELECT * FROM users WHERE id = %s", userInput)`. Покажите инъекцию `' OR '1'='1`. Исправьте через `db.QueryRow("SELECT * FROM users WHERE id = ?", id)`. Объясните, почему prepared statements — единственный надёжный способ.

20. **CSRF (Cross-Site Request Forgery)**: Реализуйте CSRF protection через double submit cookie + custom header. Покажите, почему SameSite=Strict/Lax в cookies тоже помогает.

21. **Безопасная настройка CORS**: Напишите middleware для настройки заголовков CORS (Cross-Origin Resource Sharing) [552]. Объясните в комментариях опасность использования небезопасной конфигурации `Access-Control-Allow-Origin: *` совместно с разрешением авторизации `Access-Control-Allow-Credentials: true` [552]. Реализуйте безопасную логику: middleware должно динамически проверять входящий заголовок `Origin` по белому списку разрешенных доменов вашей компании перед тем, как записать его в заголовок ответа.

22. **CSRF tokens в forms**: Реализуйте stateful CSRF tokens в forms через hidden input и валидацию на сервере.

23. **Ограничение размера тела запроса.**: Реализуйте HTTP middleware, который ограничивает размер тела запроса (например, 1MB) с помощью `http.MaxBytesReader`. При превышении возвращайте `413 Request Entity Too Large` до того, как тело будет полностью прочитано.

24. **Open Redirect.**: Реализуйте `/login?redirect=https://evil.com`. Покажите phishing-атаку. Защита: whitelist allowed hosts, использование relative paths only (`/dashboard`), или проверка `url.Parse` + `Hostname` against списка доверенных.

25. **CSP (Content Security Policy)**: Настройте strict CSP header: `default-src 'self'; script-src 'self'`. Защитите от XSS даже при успешной инъекции.

26. **Защита от SSRF (Custom Transport)**: Реши проблему из 734. Напиши кастомную функцию `DialContext` для `http.Transport` твоего `http.Client`. Внутри функции резолвь IP-адрес домена и проверяй, не принадлежит ли он приватным/локальным подсетям (используй методы `net.IP.IsPrivate()` и `IsLoopback()`). Блокируй запрос, если IP внутренний!

27. **CORS (Cross-Origin Resource Sharing)**: Настройте CORS корректно: конкретные origins (не `*`), credentials только когда нужно, без отражения Origin в Access-Control-Allow-Origin.

28. **CORS preflight attacks**: Покажите, как атакующий может использовать CORS misconfiguration для data exfiltration.

29. **CORS: безопасная настройка.**: Напишите middleware, который обрабатывает `Access-Control-Allow-Origin` (строгий whitelist, не `*`), `Access-Control-Allow-Methods`, `Access-Control-Allow-Credentials`. Объясните, почему `*` + `Allow-Credentials: true` — уязвимость (CSRF с CORS bypass для публичных API).

30. **SSRF (Server-Side Request Forgery) базовый кейс**: Напишите код, который принимает URL от пользователя и делает HTTP-запрос. Покажите, как атакующий обращается к `http://169.254.169.254/` (AWS metadata service) для получения credentials.

31. **Защита от CSRF (Межсайтовая подделка запроса)**: У тебя форма перевода денег. Если хакер разместит на своем сайте скрытую форму на твой `/transfer`, браузер жертвы автоматически прикрепит куки. Установи пакет `github.com/gorilla/csrf`. Настрой Middleware, сгенерируй токен в GET-запросе и проверяй его в POST-запросе.

32. **SSRF через IP decimal/hex**: Покажите, что `http://2852039166/` = `http://169.254.169.254/`. Наивный валидатор по IP-строке пропускает это.

33. **[XSS (Cross-Site Scripting)]**: Напиши обработчик, который выводит введенный пользователем текст в HTML. Используй `text/template` (уязвимо) и покажи внедрение `<script>alert(1)</script>`. Перепиши на `html/template`, который автоматически экранирует HTML-сущности.

34. **SSRF через DNS rebinding**: Покажите, что валидация IP в момент получения URL не защищает: атакующий возвращает public IP первым DNS-запросом и 127.0.0.1 вторым.

35. **Security Headers.**: Реализуйте middleware, добавляющий: `Strict-Transport-Security` (HSTS), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy`. Объясните назначение каждого заголовка и почему их отсутствие упрощает XSS/clickjacking.

36. **Защита от утечки технической информации (Information Disclosure)**: Напишите middleware обработки паник. Если в кодовой базе произошла паника, middleware должно записать подробный стек вызовов во внутреннюю систему логирования (для разработчиков), но пользователю вернуть строго стандартизированный JSON вида `{"error": "Internal Server Error"}` со статусом 500 [553]. Убедитесь, что наружу не просачиваются пути к файлам сервера, версии пакетов Go и технические детали ошибок.

37. **SSRF mitigation в Go**: Реализуйте защиту:
    * Разрешённые schemes только `https://`
    * Whitelist доменов
    * Запрет private IP ranges (RFC 1918, 169.254.169.254)
    * Custom HTTP-клиент с DialContext, который валидирует IP **перед соединением**

38. **Body size limiting**: Настройте `http.MaxBytesReader` для ограничения размера request body. Без этого ваш сервер уязвим к DoS через большие payload'ы.

39. **XSS и Content-Type Sniffing**: Ты отдаешь загруженный пользователем `.txt` файл. Если там внутри HTML-теги с `<script>`, старые браузеры могут "догадаться" что это HTML и выполнить скрипт. Добавь заголовок `w.Header().Set("X-Content-Type-Options", "nosniff")`. Убедись, что браузер строго парсит это как текст.

40. **Multipart form size limit**: Настройте `http.Request.ParseMultipartForm(maxMemory)` и ограничьте размер загружаемых файлов.

41. **Secure Configuration Checker.**: Напишите модуль, который при старте приложения проверяет: (1) `os.Getenv("SECRET_KEY")` не равен default/empty, (2) TLS включён в production, (3) `pprof` не exposed на public port, (4) `GIN_MODE` / `ENV` не `debug`, (5) пароли БД не захардкожены. При нарушении — `log.Fatal` с описанием. Объясните концепцию «secure by default» и «fail fast».

42. **[CORS]**: Настрой middleware для Cross-Origin Resource Sharing. Разреши запросы только с домена `https://myapp.com`. Убедись, что запросы с `https://evil.com` блокируются браузером.

43. **JSON decoder size limiting**: Используйте `json.Decoder.DisallowUnknownFields()` и ограничивайте глубину вложенности JSON (защита от zip bombs в JSON).

44. **Path Traversal**: Покажите, как атакующий через `../../../etc/passwd` в параметре может читать произвольные файлы. Защититесь через `filepath.Clean` и валидацию пути в рамках базовой директории.

45. **Open Redirect**: Покажите, как параметр `?redirect=evil.com` в login flow используется для phishing. Валидируйте redirect URLs по whitelist.

46. **SQL-инъекция в ORDER BY**: Ты знаешь про плейсхолдеры (`WHERE id = $1`). Но попробуй подставить пользовательский ввод в сортировку: `SELECT * FROM users ORDER BY $1`. Убедись, что это НЕ работает (БД экранирует это как строку). Из-за этого джуны склеивают строки `ORDER BY ` + userInput (уязвимость!). Напиши безопасный `switch / whitelist` в Go, который строго маппит пользовательские слова ("date_asc") в захардкоженные SQL-куски.

47. **[Secure Cookies & HSTS]**: Настрой выдачу cookie с флагами `HttpOnly`, `Secure`, `SameSite=Strict`. Добавьте middleware, которое устанавливает заголовок `Strict-Transport-Security: max-age=31536000; includeSubDomains` для принудительного использования HTTPS.

48. **Clickjacking**: Установите `X-Frame-Options: DENY` и CSP `frame-ancestors` header.

49. **MIME sniffing**: Установите `X-Content-Type-Options: nosniff` для защиты от MIME-based атак.

50. **Защита от SSRF.**: Напишите HTTP-клиент, который принимает URL от пользователя и загружает ресурс. Реализуйте защиту: запретите доступ к внутренним IP-адресам (127.0.0.0/8, 10.0.0.0/8, 169.254.0.0/16), проверяйте DNS-резолвинг, запрещайте редиректы на внутренние адреса. Используйте кастомный `Dialer`.

51. **Security headers bundle**: Напишите middleware, которая добавляет все современные security headers в каждый response: HSTS, CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy.

52. **Никогда не хранить секреты в коде/ENV в plain**: Покажите, как секреты утекают в Git, логи, error messages. Используйте Secret Managers.

53. **Уязвимость Directory Traversal**: Напиши простой файловый сервер: `os.ReadFile(filepath.Join("/var/www/images", req.URL.Query().Get("file")))`. Сделай запрос с `file=../../../../etc/passwd`. Убедись, что сервер отдал пароли Linux. Защити это с помощью `filepath.Clean` и проверки префикса `strings.HasPrefix(path, "/var/www/images")`. (В реальной жизни просто используй `http.FileServer`!).

54. **[CSRF Protection]**: Реализуй паттерн Double Submit Cookie: при GET запросе выдавай CSRF-токен в куки и в мета-тег. При POST запросе middleware должно сравнивать токен из куки и из заголовка `X-CSRF-Token`.

55. **HashiCorp Vault integration**: Настройте Vault в Docker, получите секреты из Go-приложения через AppRole аутентификацию.

56. **Dynamic secrets в Vault**: Настройте Vault для выдачи short-lived PostgreSQL credentials. Каждое приложение получает уникальный логин/пароль с TTL.

57. **AWS Secrets Manager**: Интегрируйтесь с AWS Secrets Manager. Используйте IAM roles вместо access keys.

58. **Финальный босс (Production Security Hardening):**
    Создайте микросервис аутентификации с full-stack security:
    
    **Password Storage:**
    * Argon2id хэширование с tuning под вашу нагрузку
    * Transparent password rehashing при успешном логине
    * Pre-hash длинных паролей через SHA-256
    * Pepper из Secret Manager
    * HaveIBeenPwned проверка через k-anonymity
    
    **Session Management:**
    * 32-byte случайные session tokens
    * Хранение в Redis с TTL 30 дней
    * Session rotation при privilege elevation
    * Concurrent sessions limiting
    
    **API Tokens:**
    * PASETO v4.local для user-bound tokens
    * API keys в формате `prefix_random_checksum`
    * Rate limiting per token через Redis
    * Scope-based permissions в токенах
    
    **OAuth2 Server:**
    * Authorization Code + PKCE flow
    * Short-lived access tokens (PASETO v4.public)
    * Refresh tokens в БД с rotation и revocation detection
    * JWKS endpoint с key rotation
    
    **Cryptographic Features:**
    * E2E encrypted user messages (X25519 + ChaCha20-Poly1305)
    * Hybrid RSA-OAEP + AES-GCM для file sharing
    * Ed25519 signatures для audit log integrity
    
    **Security Headers и Protections:**
    * Все OWASP security headers через middleware
    * CORS strict configuration
    * CSRF double-submit tokens
    * Body size limiting на всех endpoints
    * SSRF protection в URL preview feature
    
    **Secrets и Keys:**
    * Все секреты в Vault с automatic rotation
    * mTLS для service-to-service communication
    * Certificate pinning в clients
    
    **Monitoring:**
    * Failed login attempts alerting
    * Unusual location/device login alerts
    * Token usage anomalies detection
    * HSM-based master keys backup

59. **[Финальное испытание — Secure File Vault API]**
    Создай HTTP API для хранения секретных заметок.
    - **Аутентификация:** PASETO V4 токены.
    - **Хэширование паролей:** Argon2id с солью.
    - **Шифрование данных:** Текст заметки шифруется симметричным AES-GCM. Ключ заметки генерируется случайно и шифруется публичным ключом пользователя (RSA-OAEP) перед сохранением в БД (гибридное шифрование).
    - **AppSec:** Защита от SSRF (если заметка содержит URL для парсинга), лимит размера тела (1MB), Strict CORS, HSTS.
    - **Тайминги:** Использование `subtle.ConstantTimeCompare` при проверке токенов доступа к конкретной заметке.

60. **Secure Headers Middleware**: В финале напиши глобальную Middleware `SecurityHeaders`, которая добавляет ко всем HTTP-ответам стандарты безопасности:
    *   `Strict-Transport-Security: max-age=63072000` (HSTS — заставляет браузер всегда использовать HTTPS).
    *   `X-Frame-Options: DENY` (защита от Clickjacking — запрет встраивать твой сайт в iframe).
