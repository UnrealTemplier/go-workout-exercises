# Server-Sent Events

В этом файле собраны уникальные упражнения по теме **"Server-Sent Events"**, отсортированные по возрастанию сложности.

---

1. **Event ID и возобновление.**: Генерируйте `id: <uuid>` для каждого события. Клиент при reconnect шлёт заголовок `Last-Event-ID`. Сервер читает его и отправляет только события с `id` больше последнего (храните буфер последних N событий в памяти или Redis). Объясните, как это даёт exactly-once perception для клиента.

2. **Named Events.**: Используйте `event: user_update\ndata: {...}` для типизации событий. На клиенте (JavaScript) используйте `eventSource.addEventListener('user_update', ...)`. Объясните, почему `event: message` (default) и кастомные имена event помогают разделить потоки данных.

3. **Простой SSE-сервер с `http.Flusher`.**: Напишите HTTP-обработчик, который устанавливает `Content-Type: text/event-stream`, отправляет комментарий `:ok` каждые 5 секунд и данные события `data: {"time": "..."}` каждые 10 секунд. Используйте `flusher.Flush()`.

4. **Connection Hub.**: Реализуйте Hub: `map[clientID]chan Event`, mutex/RWMutex для безопасности. Каждый клиент — отдельная goroutine, читающая из личного канала и пишущая в `http.ResponseWriter`. При disconnect (ошибка write или `http.CloseNotifier`) — удаление из hub. Объясните, почему `sync.Map` может быть альтернативой при высокой конкуренции.

5. **Использование `http.Flusher`**: Чтобы отправляемые сервером сообщения мгновенно доходили до клиента, а не буферизовались веб-сервером, необходимо принудительно выталкивать данные в сеть. Напишите проверку поддержки интерфейса `http.Flusher` [584] вашим объектом ответа `http.ResponseWriter`:
    ```go
    flusher, ok := w.(http.Flusher)
    ```
    Вызывайте метод `flusher.Flush()` после каждой отправки события [584].

6. **Broadcast.**: Реализуйте broadcast: центральный `chan Event` (или `pub/sub` в Redis), все клиенты подписаны. При событии — fan-out в каждый клиентский канал. Объясните, почему неблокирующая отправка (`select` с `default`) предотвращает slow client от блокировки всего hub.

7. **Именованные события и `id`.**: Расширьте сервер: отправляйте события с полями `event: message`, `id: <порядковый номер>`, `data: ...`. Клиент должен различать типы событий и логировать их.

8. **Heartbeat / Keep-Alive.**: Отправляйте `:heartbeat\n\n` (SSE comment) каждые 15 секунд. Объясните, как это предотвращает разрыв соединения nginx/proxy (`proxy_read_timeout`, `load_balancer idle timeout`). Покажите, что комментарии не вызывают `onmessage` в браузере.

9. **Context cancellation**: Используйте `r.Context().Done()` для детекта отключения клиента. При disconnect освобождайте ресурсы (unsubscribe от channels).

10. **Event types**: Используйте `event: message_type\n` перед `data:` для разных типов событий. Клиент на JS может делать `evtSource.addEventListener('user.updated', ...)`.

11. **Форматирование SSE-сообщений**: Напишите хелпер, который форматирует данные по строгому текстовому стандарту SSE. Блок сообщения должен выглядеть так (обратите внимание на обязательные двойные символы переноса строки `\n\n` в конце сообщения):
    ```text
    event: messageAdded
    data: {"text": "Привет, мир!"}
    id: 42
    retry: 5000
    
    ```

12. **Базовый SSE endpoint.**: Реализуйте HTTP handler с `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`. Используйте `http.Flusher` для принудительной отправки. Пишите в формате `data: {"msg":"hello"}\n\n`. Объясните, почему два `\n` — разделитель событий.

13. **Event IDs**: Добавляйте `id: 12345\n` для каждого события. Это позволяет клиенту автоматически resume с последнего полученного ID при reconnect.

14. **Last-Event-ID header**: При reconnect браузер автоматически отправляет `Last-Event-ID` header. Ваш сервер должен прочитать его и отправить пропущенные события.

15. **Multiplexed SSE.**: Один endpoint `/events`, но клиент подписывается на topics через query: `?topics=orders,alerts`. Сервер фильтрует события: отправляет клиенту только те, что совпадают с подпиской. Реализуйте topic-based routing внутри Hub. Объясните, почему фильтрация на сервере лучше, чем отправка всего и фильтрация на клиенте.

16. **Клиент SSE на Go.**: Реализуйте SSE-клиент, который подключается к серверу, читает поток событий и реконнектится при обрыве, передавая заголовок `Last-Event-Id` для возобновления.

17. **Server-side reconnection buffer**: Храните последние N событий (или события за M минут) в ring buffer. При reconnect с `Last-Event-ID` отправляйте пропущенные из буфера.

18. **Retry interval**: Отправляйте `retry: 3000\n` событие для указания браузеру интервала reconnect в миллисекундах.

19. **Multiline data**: Для данных с переводом строк используйте несколько `data:` строк: `data: line1\ndata: line2\n\n`. Клиент получит их как единое сообщение с `\n` внутри.

20. **Graceful Shutdown.**: При получении `SIGTERM`: (1) закрыть listener для новых HTTP-соединений, (2) дождаться отправки pending events всем клиентам (context с timeout), (3) закрыть существующие SSE-соединения корректно. Объясните, почему `http.Server.Shutdown` не достаточен для long-lived SSE-коннекшнов без дополнительной логики.

21. **JSON в SSE**: Отправляйте JSON как data: `data: {"type":"update","payload":{...}}\n\n`. Это standard practice.

22. **Контроль разрыва соединения**: Запустите бесконечный цикл отправки событий (например, системных метрик раз в секунду). Напишите обработку отключения клиента: внутри `select` прослушивайте канал закрытия контекста запроса `<-req.Context().Done()` [586]. При получении сигнала мгновенно прерывайте цикл и завершайте работу горутины, чтобы избежать утечки ресурсов процессора [586].

23. **Авторизация SSE-соединения.**: Добавьте проверку JWT-токена в query-параметре при установлении SSE-соединения. При невалидном токене возвращайте 401.

24. **Rate Limit per Connection.**: Реализуйте token bucket для каждого SSE-клиента: максимум 100 событий/сек. При превышении — дроп (`select` с `default`) или буферизация с ограниченным размером (drop oldest). Объясните, как slow consumer может вызвать OOM без backpressure.

25. **SSE client в Go**: Реализуйте SSE client через `http.Client` с streaming response body. Парсите события вручную или используйте `github.com/r3labs/sse`.

26. **SSE auto-reconnect client**: Реализуйте client с exponential backoff reconnect и `Last-Event-ID` tracking.

27. **Broadcast через fan-out**: При получении события рассылайте его всем подключённым SSE клиентам через fan-out pattern (один channel → N goroutines).

28. **SSE per-user filtering**: При подключении извлекайте user_id из JWT, подписывайте клиента только на события этого пользователя (через filter в dispatcher).

29. **Возобновление связи (Last-Event-ID)**: При кратковременном разрыве соединения браузерный клиент автоматически переподключается и отправляет заголовок `Last-Event-ID` [587], указывая ID последнего успешно полученного сообщения. Напишите логику на сервере: считайте этот заголовок, найдите пропущенные сообщения в буфере истории событий вашей программы и отправьте их клиенту сразу после восстановления связи до начала трансляции основного потока [587].

30. **SSE vs WebSocket.**: Реализуйте тот же функционал (broadcast с named events) через WebSocket (`gorilla/websocket`). Сравните: SSE — однонаправленный, текстовый, автоматический reconnect, работает через HTTP/1.1; WebSocket — дуплексный, binary, требует ручного reconnect. Объясните, когда SSE предпочтительнее (live dashboards, notifications), а когда WebSocket (чаты, игры).

---

31. **SSE connection tracking**: Храните active connections в потокобезопасной структуре (`sync.Map`). При disconnect удаляйте из map.

32. **Max connections per user**: Ограничьте количество SSE connections на одного пользователя (обычно 1-3). Предотвращает resource exhaustion.

33. **[http.Flusher]**: В цикле пиши данные в `w.Write` в формате `data: {json}\n\n`. Вызывай `w.(http.Flusher).Flush()` после каждой записи, иначе данные останутся в буфере Go/nginx и не уйдут клиенту.

34. **Современный `http.Flusher` (Go 1.20+)**: HTTP-серверы буферизируют ответ. Клиент не увидит твой текст, пока буфер не заполнится. Используй современный механизм (появился в Go 1.20): `rc := http.ResponseController(w)` и вызови `rc.Flush()`. Это немедленно вытолкнет данные в сеть. *(В старом Go использовалось приведение `w.(http.Flusher)`).*

35. **Мультиплексирование SSE для разных пользователей.**: Реализуйте брокер событий, который хранит соединения в map `userID -> []chan Event`. При появлении события для пользователя отправляйте его во все активные SSE-соединения.

36. **Graceful shutdown SSE**: При SIGTERM отправьте всем клиентам событие `event: shutdown\ndata: server stopping\n\n` и закройте соединения.

37. **SSE through reverse proxy**: Настройте Nginx/Envoy для поддержки SSE:
    ```nginx
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
    ```
    Без `proxy_buffering off` события будут задерживаться.

38. **SSE through CDN**: Cloudflare, Fastly поддерживают SSE, но требуют special configuration (disable buffering, set proper timeouts). Изучите особенности каждого CDN.

39. **SSE vs Long Polling vs WebSocket:**
    * SSE: server→client only, auto-reconnect, HTTP-friendly
    * Long Polling: high overhead, не real-time
    * WebSocket: bidirectional, требует protocol upgrade
    Используйте SSE когда нужен только server→client streaming.

40. **Масштабирование SSE через шину (Pub/Sub)**: Напишите менеджер SSE-подключений. Он должен принимать запросы на подписку к определенным топикам, регистрировать каналы клиентов в памяти и при публикации нового сообщения (например, через Redis Pub/Sub) автоматически рассылать его по всем активным клиентским SSE-соединениям, подписанным на этот топик.

---

41. **SSE + HTTP/2 multiplexing**: На HTTP/2 один connection может держать множество SSE streams без overhead. Это эффективно для multi-tenant приложений.

42. **SSE event ordering guarantee**: Обеспечьте in-order delivery событий одному клиенту через serialization (один writer per client).

43. **Бесконечный стрим**: В хендлере запусти цикл `for`. Раз в секунду отправляй `data: {"time": "..."}\n\n` и делай `Flush()`. Как выйти из цикла? Добавь `select` и слушай канал `r.Context().Done()`. Когда клиент закроет вкладку браузера, сервер корректно завершит цикл.

44. **SSE с heartbeat и таймаутами.**: Настройте отправку комментария `:heartbeat` каждые 30 секунд, чтобы поддерживать соединение через прокси. На клиенте переподключайтесь, если heartbeat не получен в течение 60 секунд.

45. **[События и ID]**: Отправляй именованные события: `event: user_joined\ndata: {"name":"Alice"}\nid: 12345\n\n`. Напиши HTML/JS клиент, который слушает `EventSource` и логирует ID.

46. **ChatGPT-style streaming**: Реализуйте streaming LLM responses через SSE: каждый токен — отдельное событие `data: {"token": "Hello"}\n\n`, финальное `data: [DONE]\n\n`.

47. **Server-side filter subscription**: При подключении клиент отправляет filter criteria (например, `?symbols=BTC,ETH`), сервер подписывает его только на matching события.

48. **Presence through SSE**: Отправляйте события `user.online`, `user.typing`, `user.offline` для real-time presence в collaborative приложениях.

49. **Real-time dashboards**: Обновляйте metrics dashboards через SSE: новые данные приходят как события, frontend обновляет графики без polling.

50. **CI/CD live logs**: Streaming build/test logs через SSE (как в GitHub Actions, GitLab CI). Каждая строка лога — событие.

51. **Stock ticker streaming**: Real-time обновление цен акций через SSE с delta-only updates (отправляйте только изменения).

52. **Сложные события (IDs и Events)**: Стандарт SSE позволяет структурировать сообщения. Отправь событие с конкретным типом:
    ```
    id: 101
    event: user_joined
    data: {"name": "Ivan"}
    \n\n
    ```

53. **[Автоматическое переподключение]**: Браузерный `EventSource` автоматически переподключается при разрыве. Он отправит заголовок `Last-Event-ID` с последним полученным ID. На сервере прочитай этот заголовок и отправь пропущенные события.

54. **SSE with authentication**: Аутентифицируйте SSE connections через:
    * Bearer token в `Authorization` header (первый request)
    * Session cookie
    * Token в query string (fallback для `<img src>` use cases, но менее безопасно)

55. **SSE token refresh**: SSE connection может жить часами. Реализуйте graceful token refresh: отправьте событие "reconnect with new token" перед expiration.

56. **SSE multi-tab coordination**: Через `BroadcastChannel` API координируйте SSE connections между вкладками браузера — только одна вкладка держит connection, остальные получают события через BroadcastChannel.

57. **SSE + Server-Side caching**: Кэшируйте последнее состояние per client. При reconnect отправляйте cached state первым событием, затем delta updates.

58. **SSE Брокер (Pub/Sub)**: Спроектируй структуру `Broker`. В ней: канал для новых клиентов (подключение), канал для отключений, мапа активных клиентов `map[chan []byte]bool` и метод `Broadcast(msg)`. Когда срабатывает Broadcast, брокер должен раздать сообщение во все каналы клиентов.

59. **[Heartbeat (Keep-alive)]**: Напиши горутину, которая каждые 15 секунд отправляет SSE-комментарий (`: keep-alive\n\n`). Это не создает событие на клиенте, но держит соединение живым, не давая прокси (nginx, Cloudflare) закрыть его по таймауту.

60. **http.Flusher**: После каждой записи вызывайте `flusher.Flush()`. Без этого reverse proxies и буферы Go будут задерживать события.

61. **Дроп медленных клиентов**: В брокере из упр. 790 что будет, если у одного клиента завис интернет, и его канал переполнился? Твой цикл `Broadcast` заблокируется! Сделай запись в канал клиента неблокирующей (через `select` + `default`). Если канал полон — принудительно отключай клиента (закрывай канал) и освобождай ресурсы.

62. **[Каверзный кейс — Proxy Buffering]**: Если за твоим сервером стоит Nginx, он может буферизовать SSE-ответ, и клиент получит данные разом через минуту. Напиши заголовок `X-Accel-Buffering: no`, чтобы запретить Nginx буферизацию для этого ответа.

63. **Comments для keep-alive**: Отправляйте `: ping\n\n` (строки с `:` в начале — это комментарии, игнорируются клиентом) каждые 15-30 секунд для поддержания connection через proxies с idle timeout.

64. **SSE vs WebSocket benchmark**: Сравните overhead: SSE использует стандартный HTTP (работает через corporate proxies, CDN), WebSocket требует отдельного protocol upgrade. SSE идеален для server→client streaming.

65. **Тестовый JS-клиент**: Напиши простой HTML-файл. Используй встроенный в браузеры объект `new EventSource('http://localhost:8080/stream')`. Добавь обработчик `.onmessage` и выведи прилетающие из Go данные в `console.log`. Убедись, что браузер сам (автоматически!) переподключается, если ты перезапустишь Go-сервер.

---

66. **[Отмена контекста]**: Клент закрыл вкладку. Используй `ctx := r.Context()`. Запусти цикл `select { case <-ctx.Done(): return; case msg := <-ch: ... }`. Убедись, что серверная горутина завершается и не течет.

67. **SSE backpressure**: Если клиент медленно читает (медленный network), накапливайте события в per-client buffer с limit. При overflow — disconnect и force reconnect.

68. **[Высокая сложность — SSE Hub]**: Создай структуру `Hub`, которая хранит каналы всех подключенных клиентов. Реализуй endpoint `/broadcast`, который принимает сообщение и рассылает его всем активным SSE-стримам (Fan-Out). Учти, что если клиент медленно читает, канал может переполниться — разрывай соединение медленного клиента (Backpressure).

69. **`Last-Event-ID` для seamless reconnect.**: Это встроенная фича браузерного `EventSource` API. Ваш сервер должен уметь resume с указанного ID.
