# Garbage Collector и тюнинг памяти

В этом файле собраны уникальные упражнения по теме **"Garbage Collector и тюнинг памяти"**, отсортированные по возрастанию сложности.

---

1. **GC phases**: Изучите 4 фазы GC:
    * Mark Setup (STW - Stop The World, ~0.1ms)
    * Marking (concurrent, с write barriers)
    * Mark Termination (STW, ~0.5ms)
    * Sweeping (concurrent, между аллокациями)

2. **Tri-color marking**: Изучите алгоритм: White (кандидаты на удаление), Grey (в процессе обхода), Black (обработанные). Поймите, как это обеспечивает корректность при concurrent marking.

3. **Write barriers**: Когда указатель модифицируется, write barrier записывает это в buffer для последующей обработки GC. Изучите hybrid write barrier (Dijkstra + Yuasa).

4. **GC pacing**: Runtime решает, когда запускать GC, чтобы завершить marking до того, как heap вырастет слишком сильно. Изучите формулу: `target heap size = live heap * (1 + GOGC/100)`.

5. **GOGC**: Установите `GOGC=20` (агрессивный GC, больше CPU) и `GOGC=200` (ленивый GC, больше памяти). Измерьте влияние на latency и throughput.

6. **GOMEMLIMIT (Go 1.19+)**: Установите soft memory limit через `GOMEMLIMIT=1GiB`. Runtime будет стараться не превышать этот лимит, запуская GC чаще при необходимости.

7. **GC assist**: Когда горутина аллоцирует память во время GC, она может быть "призвана" помочь с marking (GC assist). Это снижает latency, но увеличивает CPU usage для аллоцирующих горутин.

8. **Трехцветный алгоритм разметки (Tri-color Mark-and-Sweep)**: Опишите в виде подробного комментария или ментальной карты концепцию трех цветов, используемую сборщиком мусора Go для определения живых объектов:
    * **Белые объекты** — кандидаты на удаление (в начале фазы разметки все объекты белые).
    * **Серые объекты** — активные объекты, найденные сборщиком, чьи дочерние ссылки еще не исследованы.
    * **Черные объекты** — активные объекты, которые были исследованы (они точно не будут удалены).

9. **Mark workers**: Runtime запускает dedicated goroutines для concurrent marking. Изучите, как они балансируют работу.

10. **Sweep termination**: Изучите, как sweeping происходит в фоне и как runtime гарантирует, что память переиспользуется безопасно.

11. **[Tri-color Mark & Sweep]**: Нарисуй на бумаге или в коде граф объектов (структуры с указателями друг на друга). Объясни, как GC раскрашивает объекты: Белые (не проверены), Серые (проверены, но дочерние нет), Черные (проверены полностью). Объекты, оставшиеся белыми в конце — удаляются.

12. **Finalizers**: Используйте `runtime.SetFinalizer()` для регистрации функций, вызываемых перед удалением объекта. Изучите, почему finalizers — это anti-pattern (непредсказуемое время вызова, могут resurrect объекты).

13. **GC CPU overhead**: Используйте `runtime.ReadMemStats()` для получения `PauseTotalNs` и `NumGC`. Вычислите процент времени, потраченного на GC.

14. **[GC Trace]**: Запусти программу с интенсивной аллокацией с флагом `GODEBUG=gctrace=1`. Расшифруй строку вывода: `gc 1 @0.045s 2%: 0.013+0.36+0.022 ms clock, 0.10+0.17/0.30/0.65+0.18 ms cpu, 4->4->2 MB, 5 MB goal, 0 MB stacks, 0 MB globals, 4 P`.

15. **GC pauses**: Измерьте STW pauses через `MemStats.PauseNs` (массив последних 256 pauses). В Go 1.19+ типичные pauses < 1ms.

16. **Forcing GC**: Вызовите `runtime.GC()` для принудительного запуска сборщика. Изучите, когда это полезно (например, после загрузки больших данных).

17. **[GOGC (Trigger Ratio)]**: По умолчанию `GOGC=100`. Это означает, что следующий цикл GC запустится, когда размер кучи (Heap) удвоится по сравнению с размером после прошлого GC. Напиши программу, которая аллоцирует 100MB. Посмотри в `gctrace`, когда запустится GC (цель `goal` = 2x от живых данных).

18. **Debug.SetMemoryLimit**: Установите `GOMEMLIMIT` программно через `debug.SetMemoryLimit(1 << 30)` (1GB).

19. **Роль барьеров записи (Write Barriers)**: Сборщик мусора Go работает конкурентно (параллельно с выполнением вашего кода). Объясните проблему: если во время разметки ваша программа перепишет указатель (черный объект начнет ссылаться на белый, а серый объект потеряет ссылку на этот же белый), GC может ошибочно удалить живой белый объект. Объясните, как барьер записи (Write Barrier), автоматически включаемый рантаймом на фазе разметки, перехватывает операции записи указателей и принудительно перекрашивает такие объекты в серый цвет, предотвращая потерю данных.

20. **GC traces**: Запустите программу с `GODEBUG=gctrace=1` и расшифруйте вывод:
    ```
    gc 1 @0.015s 0%: 0.015+0.30+0.045 ms clock, 0.12+0.15/0.45/0.15+0.36 ms cpu, 4->4->0 MB, 5 MB goal, 8 P
    ```

21. **[Тюнинг GOGC]**: Установи `GOGC=50` (GC будет запускаться чаще, память будет маленькой, но больше CPU уйдет на GC). Установи `GOGC=200` (память вырастет, но CPU сэкономится). Напиши бенчмарк, который показывает разницу во времени выполнения и пиковой памяти (`B.ReportAllocs` и `runtime.ReadMemStats`).

22. **Live heap vs allocated**: Изучите разницу между `HeapAlloc` (текущее использование) и `TotalAlloc` (кумулятивные аллокации) в `MemStats`.

23. **HeapIdle vs HeapReleased**: `HeapIdle` — память, возвращённая в OS, но может быть переиспользована. `HeapReleased` — память, физически возвращённая в OS через `madvise(MADV_FREE)`.

24. **[Отключение GC]**: Установи `GOGC=off` (`debug.SetGCPercent(-1)`). Запусти программу, которая аллоцирует в цикле. Убедись, что процесс съест всю память и упадет с OOM.

25. **Object pooling**: Используйте `sync.Pool` для переиспользования объектов и снижения давления на GC. Изучите, как `sync.Pool` очищается при каждом GC cycle.

26. **Трехцветный алгоритм (Tricolor Mark-and-Sweep)**: *Мысленный эксперимент.* Объекты бывают Белые (потенциальный мусор), Серые (живые, но их дети не проверены) и Черные (живые, все ссылки из них проверены). Напиши код с глубоко вложенной структурой (деревом). Представь (или нарисуй), как GC стартует из корней (стеков горутин) и перекрашивает узлы дерева из серого в черный. Всё, что останется белым в конце — удаляется.

27. **Pre-allocation**: Используйте `make([]T, 0, capacity)` для предварительной аллокации слайсов. Измерьте разницу в аллокациях через бенчмарки.

28. **Фазы GC (Sweep termination, Mark, Mark termination, Sweep).**: Включите `GODEBUG=gctrace=1` и запустите нагрузку с выделением памяти. Изучите вывод: найдите времена фаз, количество STW (Stop The World), объём выделенной и освобождённой памяти.

29. **Slice reuse**: Реиспользуйте слайсы через `s = s[:0]` вместо создания новых. Это сохраняет базовый массив.

30. **[GOMEMLIMIT (Soft Memory Limit)]**: Установи `GOMEMLIMIT=100MiB` и `GOGC=200`. Запусти программу. Объясни, как GOMEMLIMIT переопределяет GOGC: если лимит в 100MB близок, GC запустится раньше, чтобы не упереться в лимит ОС (спасение для Kubernetes OOMKilled).

31. **String interning**: Для часто используемых строк используйте interning (хранение уникальных копий в map) для снижения memory footprint.

32. **Write Barriers (Барьеры записи)**: Пока GC работает (конкурентно), твоя программа тоже работает. Что если твоя программа возьмет Белый объект (мусор) и положит ссылку на него в Черный объект? (Мусор станет нужным, но GC его удалит, так как Черные объекты больше не проверяются). Компилятор решает это с помощью барьеров записи. Скомпилируй код с присвоением указателя и сделай `go tool compile -S main.go | grep writebarrier`. Увидь, как компилятор вставил спец. функцию, которая принудительно перекрашивает Белый объект в Серый при изменении указателей!

33. **Struct packing**: Упорядочьте поля структуры по размеру (largest first) для снижения padding. Сравните `struct { bool; int64; bool }` (24 bytes) vs `struct { int64; bool; bool }` (16 bytes).

34. **[Write Barriers]**: Во время фазы Marking приложение продолжает работать (мутирует кучу). Если Черный объект (уже пройденный GC) начнет указывать на новый Белый объект, GC его не увидит и удалит. Изучи, как Go решает это через Write Barrier (Dijkstra или Yuasa). Напиши тест, где объект модифицируется во время GC (используя `runtime.GC()`), и убедись, что данные не теряются.

35. **Исследование работы GC через `gctrace`**: Напишите программу, которая непрерывно выделяет память в бесконечном цикле. Запустите её с флагом `GODEBUG=gctrace=1 ./app` [491]. Проанализируйте выводимые строки отчета сборщика мусора. Расшифруйте параметры: время фаз разметки/очистки, процент утилизации процессора сборщиком мусора (GC CPU %, обычно не более 25%), объем кучи до и после сборки.

36. **Pointer-free types**: Используйте типы без указателей (`int`, `float64`, structs с только value types) — GC не сканирует их, что ускоряет marking.

37. **Avoid heap allocations**: Используйте escape analysis (`-gcflags="-m"`) для выявления неожиданных heap аллокаций. Переписывайте код для stack allocation.

38. **Write Barrier и трёхцветная пометка.**: Напишите программу, которая мутирует объектный граф во время работы GC (изменение указателей). Убедитесь, что GC корректен, и объясните роль write barrier (безопасность при одновременной мутации).

39. **Фазы GC (STW)**: GC в Go имеет 4 фазы, две из которых требуют Stop The World (остановки всех горутин). Напиши бенчмарк, измеряющий задержки. Запусти программу с `GODEBUG=gctrace=1`. В выводе консоли ты увидишь строки вида `gc 1 @0.012s 1%: 0.02+1.5+0.04 ms clock...`. Расшифруй их: первая цифра (0.02) — STW при Mark Termination (подготовка барьеров записи), вторая (1.5) — конкурентная маркировка, третья (0.04) — STW при Sweep Termination. Убедись, что паузы STW реально составляют доли миллисекунд.

40. **Buffer pooling для I/O**: Используйте `sync.Pool` для `bytes.Buffer` в HTTP handlers для снижения аллокаций.

41. **[GC Pacing]**: Изучи концепцию Pacing. GC пытается завершить Marking до того, как куча вырастет до `goal` (с учетом GOGC). Если приложение аллоцирует слишком быстро, GC не успевает, и рантайм вынужден остановить приложение (Stop-The-World на аллокации), чтобы дождаться GC.

42. **Memory-mapped files**: Для работы с большими файлами используйте `mmap` (через `golang.org/x/exp/mmap` или syscall) вместо загрузки в heap.

43. **Off-heap memory**: Для экстремальных случаев используйте `mmap` напрямую для off-heap памяти, не управляемой GC (требует ручного освобождения).

44. **[Sweep Termination / Mark Setup / Mark Termination]**: Найди в `gctrace` время STW (Stop-The-World). В современном Go STW бывает только в самом начале (Mark Setup) и в конце (Mark Termination). Напиши программу, которая вызывает панику или задержку в `Mark Termination` (например, много финализаторов `runtime.SetFinalizer`).

45. **GC tuning для low-latency**: Для latency-sensitive приложений используйте `GOGC=20` и `GOMEMLIMIT` для частых, но коротких GC pauses.

46. **GC Pacing (Автопилот GC)**: Когда стартует следующий GC? По умолчанию `GOGC=100`. Это значит, GC стартует, когда объем новой памяти превысит 100% от объема выжившей памяти после прошлого GC (куча выросла в 2 раза). Напиши код, монотонно выделяющий память. В `gctrace` найди `-> 10 MB (target 20 MB)`.

47. Напишите программу, которая создаёт дерево объектов (граф из `struct { left, right *node }`). Запустите `GODEBUG=gctrace=1` и проанализируйте вывод: `gc 1 @...: 10% CPU, ..., 0.015+1.2+0.003 ms clock`. Объясните каждое поле (STW sweep termination, concurrent mark, STW mark termination).

48. **GC tuning для high-throughput**: Для batch-processing используйте `GOGC=200` для снижения CPU overhead от GC.

49. **GC Pacing и GOGC.**: Запустите программу, выделяющую память в цикле. Измерьте пропускную способность и задержки при `GOGC=50`, `100`, `200`, `off`. Найдите оптимальное значение для минимизации задержек.

50. **[runtime.GC() vs debug.FreeOSMemory()]**: Напиши программу. Вызови `runtime.GC()` — это запустит обычный цикл сборки мусора. Затем вызови `debug.FreeOSMemory()` — это заставит mheap вернуть пустые спаны операционной системе (`madvise`). Проследи за изменением RSS.

51. **Monitoring GC**: Экспортируйте GC метрики в Prometheus: `go_gc_duration_seconds`, `go_memstats_alloc_bytes`, `go_goroutines`.

52. **Тюнинг GC через `GOGC`**: Запустите вашу программу с агрессивной аллокацией памяти. Сделайте три замера производительности и потребления оперативной памяти:
    * С дефолтным параметром `GOGC=100` (сборщик запускается, когда размер кучи удваивается относительно размера после предыдущей сборки).
    * С параметром `GOGC=50` (частый запуск GC, минимальный расход памяти, но высокая нагрузка на CPU).
    * С параметром `GOGC=500` (редкий запуск GC, экономия CPU, но высокое потребление памяти).
    Сделайте выводы в комментариях.

53. Создайте программу с большим live set (100 MB строк). Покажите, что при `GOGC=100` следующий GC запускается при ~200 MB heap. Измените `GOGC=200` — покажите сдвиг порога. Нарисуйте график `HeapGoal` от `HeapLive`.

54. **Тюнинг GOGC**: Запусти память-интенсивный сервис из упр. 637. Измерь потребление CPU. Установи `GOGC=50` (куче разрешено вырасти лишь на 50%). Запусти снова: CPU возрастет (GC запускается в 2 раза чаще), но оперативной памяти потратится меньше. Теперь сделай `GOGC=500`. Память взлетит, но CPU почти не будет тратиться на GC. (Баланс CPU vs RAM).

55. Напишите «GC assist simulator» на чистом Go: goroutine, которая аллоцирует память, должна «помочь» GC (потратить время на маркировку пропорционально аллокации). Объясните, почему это предотвращает out-of-control рост heap во время маркировки.

56. **[Pointer-free Objects]**: Создай слайс `[]int` на 10MB и слайс `[]*int` на 10MB. Запусти `gctrace`. Объясни, почему GC обходит слайс `[]int` мгновенно (в нем нет указателей, память помечена как `noscan`), а `[]*int` заставляет GC сканировать каждый элемент.

57. Реализуйте «мутатор, который обманывает GC»: в цикле создавайте белые объекты и сразу теряйте ссылку (становятся мусором). Затем создавайте серые — держите ссылку. Покажите, что GC корректно отличает их через write barrier.

58. **GOMEMLIMIT и мягкий лимит памяти.**: Настройте `GOMEMLIMIT` на значение, близкое к лимиту контейнера. Наблюдайте через `gctrace`, как сборщик мусора учащается при приближении к лимиту, избегая OOM.

59. **GOGC=off и ручное управление**: Выстави `GOGC=off`. Запусти код из 637. Наслаждайся тем, как программа съедает всю память твоего ноутбука и убивается ОС (OOM Killed). Добавь в код вызов `runtime.GC()` каждую секунду по таймеру и посмотри, как программа спасается от OOM.

60. **[Финализаторы]**: Напиши структуру с эмуляцией файлового дескриптора. Используй `runtime.SetFinalizer(&obj, func(o *Obj) { o.Close() })`. Покажи, что `Close()` вызовется автоматически, когда GC соберет объект. Объясни, почему финализаторы считаются анти-паттерном в Go (непредсказуемое время вызова, требуют 2 цикла GC для удаления).

61. Напишите программу с интенсивной записью указателей в существующие структуры во время работы GC (`GODEBUG=gctrace=1`). Покажите, что write barrier (`wbBuf`) накапливает «серые» объекты. Найдите в исходниках (`src/runtime/mwbbuf.go`) размер буфера и механизм сброса.

62. **[runtime.KeepAlive()]**: Напиши код с CGO (или `unsafe`), где Go-объект передается в C-функцию. Если Go-объект больше не используется в Go-коде, GC может удалить его до того, как C-функция закончит с ним работу. Используй `runtime.KeepAlive(obj)` в конце Go-функции, чтобы запретить GC собирать его до этой строки.

63. Создайте ситуацию «нестабильного графа»: goroutine постоянно перестраивает связный список (меняет `next`). Объясните, почему без write barrier объект мог бы быть ошибочно освобождён (чёрный mutator пишет ссылку на белый объект).

64. **Магия GOMEMLIMIT (Go 1.19+)**: До 1.19 `GOGC` не знал про физические лимиты контейнера K8s. Если `GOGC=100`, а предел контейнера 100 МБ, при росте кучи с 60 МБ до 120 МБ контейнер умирал от OOM до того, как GC решал запуститься.
    Установи `GOGC=off` и `GOMEMLIMIT=100MiB`. Запусти память-интенсивный код. Увидь магию: несмотря на выключенный GOGC, сборщик мусора начнет экстренно спасать ситуацию, как только объем памяти приблизится к 100 МБ (Soft Memory Limit).

65. **Тюнинг памяти через `GOMEMLIMIT`**: Одной из главных проблем Go в Docker-контейнерах была уязвимость к OOM-киллеру при резких всплесках трафика. Начиная с Go 1.19, появился параметр `GOMEMLIMIT`. Напишите тест: установите переменную окружения `GOMEMLIMIT=150MiB` и запустите аллокатор. Наблюдайте, как при приближении потребления памяти к 150 МБ сборщик мусора Go начинает работать непрерывно и агрессивно (даже игнорируя настройки `GOGC`), пытаясь удержать потребление памяти в рамках лимита и спасти контейнер от падения по OOM.

66. **Время STW и его влияние на latency.**: Создайте HTTP-сервер с жёсткими требованиями к задержке. Подайте нагрузку и одновременно выделяйте много памяти. Измерьте перцентили задержек до и после тюнинга GC (GOGC, GOMEMLIMIT).

67. **[GOGC и Latency]**: Напиши HTTP-сервер с одним эндпоинтом, который аллоцирует много памяти, и другим, который просто отвечает быстро.
