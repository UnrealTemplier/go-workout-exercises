# Расширяемость систем: Plugins, IPC и WebAssembly (Wazero)

В этом файле собраны уникальные упражнения по теме **"Расширяемость систем: Plugins, IPC и WebAssembly (Wazero)"**, отсортированные по возрастанию сложности.

---

1. **Архитектура расширяемости (Extensibility Architecture)**: Изучите паттерны расширяемости программных систем: микроядро (Microkernel), плагины (Plugins), межпроцессное взаимодействие (IPC) и изолированные песочницы (Sandboxes). Спроектируйте базовый интерфейс расширения для обработки платежей `PaymentGateway` с методами `Authorize` и `Capture` на Go. Сравните компромиссы между изоляцией, безопасностью и задержкой вызовов.

2. **Стандартный пакет plugin и динамические библиотеки .so**: Напишите простой плагин с использованием стандартного пакета Go `plugin`. Скомпилируйте плагин командой `go build -buildmode=plugin -o plugin.so plugin.go`. В основной программе загрузите библиотеку через `p, err := plugin.Open("plugin.so")`, найдите экспортированный символ через `sym, err := p.Lookup("V")` и вызовите функцию через приведение типов.

3. **Фатальные ограничения стандартного пакета plugin**: Проанализируйте, почему стандартный пакет `plugin` практически не используется в production: требование строго одинаковой версии компилятора Go, идентичных версий всех разделяемых зависимостей, одинаковых флагов сборки, обязательное наличие CGO и полное отсутствие поддержки операционной системы Windows.

4. **Внепроцессные плагины через IPC (Out-of-Process Plugins)**: Спроектируйте архитектуру плагинов, работающих как независимые процессы операционной системы: хост-приложение порождает дочерний процесс плагина (`os/exec`) и общается с ним через стандартные потоки ввода-вывода (`stdin/stdout`) или локальный UNIX Domain Socket. Покажите, как достигается независимость версий зависимостей.

5. **Введение во фреймворк HashiCorp go-plugin**: Изучите библиотеку `hashicorp/go-plugin` (используемую в Terraform, Vault, Nomad, Packer): IPC-плагины по протоколу gRPC поверх UNIX сокетов. Разберите структуру рукопожатия (HandshakeConfig): магический ключ (`MagicCookieKey`), значение куки и версия протокола, защищающие хост от случайного подключения посторонних процессов.

6. **Проектирование Protobuf контракта для go-plugin**: Опишите интерфейс плагина в файле `plugin.proto`: сервис `DataProcessor` с методом `ProcessData(DataRequest) returns (DataResponse)`. Сгенерируйте Go-код и реализуйте плагинную обертку `plugin.GRPCPlugin` для интеграции с библиотекой `hashicorp/go-plugin`.

7. **Реализация бинарного сервера плагина**: Напишите отдельный бинарный файл `plugin-csv`: реализуйте бизнес-логику gRPC-сервиса, вызовите `plugin.Serve(&plugin.ServeConfig{ HandshakeConfig: handshake, Plugins: pluginMap, GRPCServer: plugin.DefaultGRPCServer })`. Скомпилируйте независимый исполняемый файл плагина.

8. **Хост-приложение: обнаружение и запуск плагина**: Напишите хост-приложение: создайте клиент `plugin.NewClient(&plugin.ClientConfig{ Cmd: exec.Command("./plugin-csv"), HandshakeConfig: handshake, Plugins: pluginMap })`. Подключитесь к плагину через RPC/gRPC, получите интерфейс `DataProcessor` и выполните тестовую обработку данных.

9. **Изоляция сбоев: защита хоста от аварийного падения плагина**: Что произойдет, если в коде плагина возникнет паника или ошибка сегментации (SIGSEGV)? Смоделируйте крах дочернего процесса (`panic("fatal crash")`). Докажите, что хост-приложение не падает, а получает ошибку RPC `rpc error: code = Unavailable desc = transport is closing`, перехватывает ее и перезапускает плагин.

10. **Версионирование протокола плагинов (Protocol Versioning)**: Реализуйте проверку совместимости версий: при несовпадении версий протокола в `HandshakeConfig` хост-клиент отклоняет запуск плагина с понятным сообщением об ошибке `Incompatible protocol version`. Напишите механизм поддержки нескольких версий контракта плагина одновременно.

11. **Двусторонняя коммуникация: вызов функций хоста из плагина (Callbacks)**: Используя `plugin.GRPCBroker`, реализуйте возможность плагина обращаться назад к хост-приложению (например, для запроса прав доступа или записи в хостовую базу данных). Хост передает ID брокера в заголовках gRPC, и плагин открывает обратное gRPC-соединение.

12. **Введение в WebAssembly (Wasm) для серверного Go**: Изучите технологию WebAssembly (Wasm) как универсальный, безопасный байткод для исполнения недоверенного кода в изолированной песочнице с околонативной скоростью. Сравните Wasm с Docker-контейнерами: мгновенный старт (< 1 мс), минимальное потребление памяти (< 1 МБ) и гранулярный контроль доступа.

13. **Выбор Wasm-рантайма: CGO vs Чистый Go (Wazero)**: Сравните рантаймы WebAssembly для Go: CGO-биндинги (Wasmtime, Wasmer) требуют компилятор C, усложняют кросс-компиляцию и отладку. Изучите `tetratelabs/wazero` — полностью независимый Wasm-рантайм на чистом Go с поддержкой JIT-компиляции (AOT/JIT для amd64 и arm64) и нулевыми внешними зависимостями.

14. **Запуск первого Wasm-модуля с помощью Wazero**: Подключите `github.com/tetratelabs/wazero`. Инициализируйте рантайм: `r := wazero.NewRuntime(ctx)`. Загрузите бинарный Wasm-файл, скомпилируйте модуль `compiled, err := r.CompileModule(ctx, wasmBytes)` и создайте инстанс `mod, err := r.InstantiateModule(ctx, compiled, wazero.NewModuleConfig())`.

15. **Компиляция кода Go в WebAssembly (WASI)**: Напишите плагин фильтрации спама на Go. Скомпилируйте его в Wasm с использованием целевой платформы WASI: `GOOS=wasip1 GOARCH=wasm go build -o spam_filter.wasm main.go`. Проверьте запуск бинарника в рантайме Wazero.

16. **Передача скалярных аргументов в экспортированные Wasm-функции**: Экспортируйте из Wasm-модуля функцию `add(a, b int32) int32`. На стороне Go-хоста найдите функцию: `fn := mod.ExportedFunction("add")`. Вызовите ее через `results, err := fn.Call(ctx, uint64(x), uint64(y))` и проверьте корректность возвращенного значения.

17. **Работа с линейной памятью Wasm: чтение и запись байтов**: Wasm-модуль изолирован в линейном буфере памяти `api.Memory`. Реализуйте передачу строки из Go в Wasm: хост записывает байты в память модуля по заданному смещению через `mod.Memory().Write(offset, data)`, а Wasm-функция считывает их по указателю и длине.

18. **Выделение памяти внутри Wasm: экспорт malloc и free**: Для безопасной передачи произвольных данных хост не должен писать в случайные адреса памяти Wasm. Экспортируйте из Wasm-модуля функции `allocate(size uint32) uint32` и `deallocate(ptr uint32, size uint32)`. Хост запрашивает блок памяти у модуля, записывает данные, вызывает логику и освобождает память.

19. **Хост-функции (Host Functions): предоставление API модулю**: Реализуйте хост-функцию, доступную внутри Wasm: создайте модуль хоста с помощью `r.NewHostModuleBuilder("env").NewFunctionBuilder().WithFunc(hostLog).Export("log").Instantiate(ctx)`. Продемонстрируйте, как Wasm-плагин вызывает хостовую функцию логирования.

20. **Подключение WASI Snapshot Preview 1**: Многие стандартные библиотеки требуют системных интерфейсов (чтение аргументов командной строки, текущее время, stdout). Инициализируйте поддержку WASI в Wazero: `wasi_snapshot_preview1.MustInstantiate(ctx, r)`. Настройте перенаправление stdout/stderr модуля в буферы памяти Go.

21. **Песочница: ограничение системных вызовов в Wasm**: Настройте конфигурацию модуля `wazero.NewModuleConfig()`: запретите доступ к переменным окружения хоста (`WithoutInheritEnvs`), файловой системе хоста и ограничьте доступные аргументы. Убедитесь, что вредоносный код внутри Wasm физически не может получить доступ к `/etc/passwd` хоста.

22. **Ограничение потребления оперативной памяти Wasm-модулем**: Защитите хост от утечек памяти: ограничьте максимальный объем страниц линейной памяти (каждая страница Wasm = 64 КБ). Настройте лимит памяти (например, не более 16 МБ). Продемонстрируйте, что попытка плагина аллоцировать память сверх лимита возвращает ошибку без падения хоста.

23. **Ограничение времени выполнения и Gas Metering (Инструкции CPU)**: Пользовательский скрипт может содержать бесконечный цикл `for {}`. Реализуйте прерывание выполнения: используйте отмену по таймауту через `context.WithTimeout(ctx, 100*time.Millisecond)` или инструмент подсчета инструкций (Gas Metering) для принудительной остановки модуля при превышении лимита операций CPU.

24. **Пул инстансов Wasm-модулей (Instance Pooling)**: Компиляция Wasm-байткода в машинный код (`CompileModule`) занимает время (10–50 мс), но скомпилированный `CompiledModule` потокобезопасен и может использоваться повторно. Реализуйте `sync.Pool` готовых инстансов модулей для субмиллисекундного запуска Wasm-функций на каждый входящий HTTP-запрос.

25. **Изоляция памяти при конкурентных вызовах Wasm**: Линейная память инстанса Wasm (`api.Module`) не является потокобезопасной для одновременной записи из нескольких горутин. Докажите это и постройте архитектуру: каждая параллельная горутина либо берет изолированный инстанс из пула, либо использует механизм создания легковесных инстансов из скомпилированного шаблона.

26. **Передача структурированных данных: Protobuf поверх Wasm Memory**: Для вызова сложных бизнес-методов сериализуйте структуры в бинарный формат Protobuf. Хост сериализует запрос в байты, копирует в линейную память Wasm, передает указатель и размер. Wasm десериализует Protobuf, выполняет расчет, сериализует ответ и возвращает указатель на результат.

27. **Бенчмарк производительности: Direct Call vs go-plugin vs Wazero**: Напишите эталонный бенчмарк `testing.B`, сравнивающий накладные расходы на выполнение одной и той же операции: прямой вызов функции в процессе Go (~1 нс), вызов через HashiCorp `go-plugin` по gRPC UNIX-сокету (~20-50 мкс) и вызов через Wasm-песочницу `wazero` (~200-500 нс).

28. **Горячая перезагрузка плагинов (Hot-Reloading) без даунтайма**: Реализуйте подмену плагина на лету: хост-приложение отслеживает изменение файла плагина на диске. При обновлении `plugin.wasm` хост компилирует новый модуль в фоне, валидирует его здоровье и атомарно подменяет активный инстанс в указателе `atomic.Pointer` без прерывания обслуживания запросов.

29. **Кастомный компилятор DSL-правил в WebAssembly**: Разработайте простой парсер математических выражений или бизнес-правил (например, `price * 0.9 if user.is_vip else price`), генерирующий валидный Wasm-байткод на лету и исполняющий его в Wazero с экстремальной производительностью.

30. **Enterprise Serverless Execution Engine на Go**: Создайте полноценную платформу исполнения бессерверных функций на чистом Go: REST API для загрузки Wasm-файлов пользователей, хранилище модулей, пул воркеров на Wazero, строгая изоляция памяти и CPU (таймауты, memory caps), учет метрик исполнения и логирование выполнения.
