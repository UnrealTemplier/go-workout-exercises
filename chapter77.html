💡 Теоретический фундамент и концепция

Сетевая архитектура стандартной библиотеки Go (net.Listen, net.Conn) базируется на элегантной парадигме «одна горутина на одно сетевое соединение» (goroutine-per-connection). В этой модели каждая горутина выполняет блокирующий вызов conn.Read(). Под капотом среда выполнения Go переводит этот вызов в регистрацию дескриптора сокета в системном netpoller (использующем epoll на Linux, kqueue на macOS/FreeBSD). Когда в сокете нет данных, горутина переводится планировщиком GMP в статус _Gwaiting, освобождая поток M (OS Thread) для исполнения других задач.

Несмотря на потрясающую простоту и удобство разработки, классическая модель Go сталкивается с фундаментальными барьерами на экстремальных нагрузках (C100K и C1M):

1. Потребление оперативной памяти под стек: Начальный стек горутины составляет 2 КБ (с метаданными runtime — порядка 2.5–4 КБ). При 100 000 неактивных (idle keep-alive) соединениях только на пустые стеки горутин расходуется от 250 до 400 МБ RAM. При миллионе соединений оверхед достигает 2.5–4 ГБ.
2. Накладные расходы планировщика (GMP Context Switching): При высокой частоте коротких сетевых транзакций планировщик Go вынужден непрерывно переключать сотни тысяч горутин между очередями runq, что приводит к вымыванию процессорных кэшей L1d/L2 и высокой задержке хвостовых запросов (p99/p999 latency spikes).
3. Аллокации в куче: Передача данных через интерфейс net.Conn влечет за собой экранирование буферов в кучу (heap escape analysis), нагружая трехцветный сборщик мусора (GC).

Фреймворк gnet (github.com/panjf2000/gnet/v2) кардинально меняет сетевую архитектуру приложения, реализуя реакторный паттерн (Reactor Pattern) в пространстве пользователя (Userspace). Вместо модели «горутина на соединение» gnet использует строго фиксированное число потоков/горутин — Event Loops (обычно равное числу ядер процессора runtime.NumCPU()).

Входящие сетевые события мультиплексируются системными вызовами epoll_wait пачками (batching syscalls), а данные из сокетов читаются непосредственно в циклические кольцевые буферы (ring buffers) без дополнительных копирований и аллокаций памяти.

package main

import (
	"fmt"
	"log"

	"github.com/panjf2000/gnet/v2"
)

// EchoServer реализует сетевые обработчики gnet.EventHandler.
type EchoServer struct {
	gnet.BuiltinEventEngine
	addr string
}

// OnBoot вызывается при инициализации движка gnet перед открытием сокетов.
func (es *EchoServer) OnBoot(eng gnet.Engine) (action gnet.Action) {
	log.Printf("[gnet] Движок инициализирован на адресе %s\n", es.addr)
	return gnet.None
}

// OnOpen срабатывает при установке нового входящего TCP-соединения (после accept).
func (es *EchoServer) OnOpen(c gnet.Conn) (out []byte, action gnet.Action) {
	// Соединение успешно открыто, ресурсов под стек горутины не выделялось.
	return nil, gnet.None
}

// OnTraffic вызывается при поступлении сетевых пакетов в сокет (событие EPOLLIN).
func (es *EchoServer) OnTraffic(c gnet.Conn) (action gnet.Action) {
	// Читаем все доступные данные из кольцевого буфера сокета без аллокации
	buf, err := c.Next(-1)
	if err != nil {
		log.Printf("Ошибка чтения буфера: %v", err)
		return gnet.Close
	}

	// Отправляем эхо-ответ обратно клиенту
	if _, err := c.Write(buf); err != nil {
		log.Printf("Ошибка записи в сокет: %v", err)
		return gnet.Close
	}

	return gnet.None
}

// OnClose срабатывает при закрытии соединения со стороны клиента или сервера.
func (es *EchoServer) OnClose(c gnet.Conn, err error) (action gnet.Action) {
	return gnet.None
}

func main() {
	serverAddr := "tcp://127.0.0.1:9000"
	server := &EchoServer{addr: serverAddr}

	// Запуск gnet в режиме фиксированного числа реакторов
	err := gnet.Run(
		server,
		serverAddr,
		gnet.WithMulticore(true),
		gnet.WithReusePort(true),
	)
	if err != nil {
		log.Fatalf("Сбой запуска gnet сервера: %v", err)
	}
	fmt.Println("Сервер завершил работу")
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Под капотом архитектура gnet полностью отвязана от рантайм-планировщика Go:

1. Userspace Event Loop: Вместо системного netpoller Go, gnet создает системные потоки ОС (runtime.LockOSThread()) или ограниченный набор горутин, каждая из которых крутит цикл вызова unix.EpollWait с массивом структур epoll_event. За один сисколл извлекается пачка до сотен готовых файловых дескрипторов.
2. Ring Buffer: При наступлении события EPOLLIN данные считываются системным вызовом readv в циклический буфер памяти (elastic ring buffer). Метод c.Next(-1) возвращает срез (slice) прямо на этот внутренний буфер, избегая вызова аллокатора кучи mallocgc.
3. Syscall Batching: Ответы накапливаются во внутреннем буфере сокета и отправляются клиенту через пакетный writev, что сводит к минимуму общее количество переходов пользователя в ядро ОС (kernel context switches).
⚠️ Частые грабли и ошибки новичков

Главная ловушка реакторной модели: категорически запрещено выполнять блокирующие операции (I/O в базу данных, обращение к диску, тяжелые криптографические вычисления, вызовы time.Sleep) внутри метода OnTraffic. Поскольку один Event Loop обслуживает тысячи сетевых соединений одновременно, любая блокировка на 10 мс мгновенно заморозит обработку трафика для всех остальных клиентов, закрепленных за данным реактором!

🏢 В продакшене BigTech и на собеседованиях

Вопрос на собеседовании (Senior Network Engineer / HighLoad Go Developer):

«Почему gnet способен показать 1 000 000+ RPS на Echo-тестах, в то время как стандартный сервер net/http упирается в 200 000 – 300 000 RPS на той же машине?»

Эталонный ответ:

1. Ликвидация оверхеда горутин: В net/http на каждое соединение создаются 2 горутины (чтение и запись) плюс структуры http.Request/http.response. Это влечет вызовы runtime.newstack, переключения контекста GMP и существенную нагрузку на GC. В gnet сокеты мультиплексируются фиксированным числом потоков без создания горутин на запрос.
2. Батчинг системных вызовов: Стандартный стек Go выполняет read() и write() индивидуально для каждого пакета при пробуждении от netpoller. gnet считывает события пачками через epoll_wait(..., events, maxevents, ...), уменьшая число переходов кольца привилегий CPU (ring 3 -> ring 0).
3. Zero-Copy дизайн буферов: gnet не копирует тело запроса в промежуточный bytes.Buffer, а предоставляет прямой указатель на кольцевой буфер c.Next(), нивелируя давление на сборщик мусора.

💡 Теоретический фундамент и концепция

Исторически первой популярной лаконичной реализацией событийно-ориентированной сети в Go стала библиотека evio (github.com/tidwall/evio), написанная Джошем Бейкером (Josh Baker). Она заложила фундамент для понимания концепции неблокирующего сокетного I/O в обход net.Conn.

Сравнение архитектурных парадигм: Single-Threaded vs Multi-Reactor
1. Модель evio (Single-Threaded / Worker-Loop Reactor):

По умолчанию evio запускает один главный Event Loop. В этом цикле происходит и прием входящих сетевых соединений (accept), и опрос дескрипторов сокетов через epoll_wait/kqueue, и исполнение пользовательских коллбэков обработки данных (events.Data).

Хотя evio позволяет сконфигурировать параметр Loops: N, его внутренняя координация между потоками исторически проще, а модель обработки ориентирована на быструю сериализацию событий без блокировок памяти.

2. Модель gnet (Multi-Reactor / Master-Workers Pattern):

gnet реализует классическую архитектуру Multi-Reactor, вдохновленную Java Netty и Nginx:

  • Main Reactor (Acceptor Loop): Отдельный поток слушает серверный сокет, принимает входящие соединения вызовом accept4() (с флагами SOCK_NONBLOCK | SOCK_CLOEXEC) и распределяет новые файловые дескрипторы между Sub-реакторами по алгоритму Round-Robin или Least Connections.
  • Sub Reactors (Worker Loops): Набор независимых потоков (обычно $N = \text{NumCPU}$), каждый из которых владеет собственным экземпляром epoll_create1 и собственным массивом дескрипторов. Каждый Sub-реактор полностью автономен: он читает байты, вызывает OnTraffic и пишет ответы без межпоточной конкуренции за мьютексы.

package main

import (
	"fmt"
	"log"

	"github.com/tidwall/evio"
)

func main() {
	var events evio.Events

	// Serving срабатывает после старта слушателя сокетов
	events.Serving = func(srv evio.Server) (action evio.Action) {
		log.Printf("evio сервер успешно запущен на %s (число циклов: %d)\n", srv.Addrs, srv.NumLoops)
		return evio.None
	}

	// Opened срабатывает при новом входящем подключении
	events.Opened = func(c evio.Conn) (out []byte, opts evio.Options, action evio.Action) {
		// Опция TCP_NODELAY отключает алгоритм Нагла для минимального RTT
		opts.TCPKeepAlive = 120
		return nil, opts, evio.None
	}

	// Data — ключевой обработчик входящего сетевого трафика.
	// Входной слайс in содержит считанные из сокета байты.
	// Возвращаемый слайс out будет записан обратно в сокет!
	events.Data = func(c evio.Conn, in []byte) (out []byte, action evio.Action) {
		if in == nil {
			return nil, evio.None
		}
		// Эхо-ответ: возвращаем байты обратно
		out = in
		return out, evio.None
	}

	// Closed вызывается при разрыве соединения
	events.Closed = func(c evio.Conn, err error) (action evio.Action) {
		return evio.None
	}

	addr := "tcp://127.0.0.1:9001"
	fmt.Printf("Запуск evio echo на %s...\n", addr)
	if err := evio.Serve(events, addr); err != nil {
		log.Fatalf("Ошибка evio: %v", err)
	}
}

Вопрос на собеседовании (Senior Backend / Infrastructure Engineer):

«В чем заключается фундаментальная разница между Reactor Pattern и Proactor Pattern, и к какому типу относятся gnet/evio и стандартный рантайм Go?»

Эталонный ответ:

  • Reactor (gnet, evio, epoll, Netty): Синхронное уведомление о готовности ввода-вывода. Поток реактора ждет события «сокет *готов* к чтению (EPOLLIN)» или «готов к записи (EPOLLOUT)». После этого сам пользовательский поток выполняет системный вызов read()/write().
  • Proactor (Windows IOCP, Linux io_uring): Асинхронное уведомление о *завершении* операции. Приложение инициирует async_read(buf), ядро ОС само переносит байты из сетевой карты в предоставленный буфер памяти и лишь по окончании посылает сигнал завершения.
  • Стандартный Go: Представляет собой гибрид. С точки зрения Go-разработчика API выглядит как блокирующий синхронный код (или Proactor), но под капотом планировщик Go и netpoller используют Reactor (epoll/kqueue), переводящий горутины в спящий режим.

Понимание Reactor Pattern: Низкоуровневый Event Loop на epoll

📌 Условие задачи

Напишите упрощённый event loop на epoll (см. Блок 6, упр. 86): epoll_create1 → epoll_ctl (add fd) → epoll_wait → callback. Объясните, как gnet оборачивает это в Go: epoll_wait в отдельной goroutine, callback в пул воркеров.

💡 Теоретический фундамент и концепция

Чтобы досконально понимать, как функционируют gnet, evio, Nginx и Redis, необходимо разобрать устройство классического паттерна Reactor на уровне системных вызовов Linux Kernel:

1. Создание дескриптора мультиплексора: Системный вызов epoll_create1(0) создает экземпляр epoll в ядре Linux и возвращает файловый дескриптор.
2. Регистрация слушающего сокета: Серверный TCP-сокет настраивается как неблокирующий (O_NONBLOCK). С помощью epoll_ctl(epfd, EPOLL_CTL_ADD, server_fd, &event) он регистрируется в дереве epoll на событие EPOLLIN.
3. Цикл обработки событий (Event Loop): Поток вызывает epoll_wait(epfd, events, maxevents, timeout). Этот вызов блокирует вызывающий поток ОС до тех пор, пока хотя бы один дескриптор не сгенерирует событие, либо не истечет таймаут.
4. Диспетчеризация событий (Event Dispatcher):
  • Если событие пришло на server_fd, вызывается accept4(server_fd, ...) для получения дескриптора нового клиента (client_fd), который немедленно регистрируется в том же epoll на чтение EPOLLIN.
  • Если событие пришло на client_fd, вызывается read(client_fd, buf). При чтении байт вызывается зарегистрированный коллбэк бизнес-логики. При read == 0 (FIN пакет) соединение закрывается и удаляется из epoll вызовом epoll_ctl(..., EPOLL_CTL_DEL, ...).

В этом состоит абсолютная суть: один поток ОС может обслуживать 100 000 сокетов без создания 100 000 горутин.

2. Создайте серверный сокет unix.Socket(AF_INET, SOCK_STREAM|SOCK_NONBLOCK, 0).
3. Привяжите адрес вызовами unix.Bind и переведите сокет в режим ожидания соединений unix.Listen.
4. Создайте epoll через unix.EpollCreate1(0) и добавьте слушающий дескриптор.
5. Запустите бесконечный цикл unix.EpollWait, разбирая события EPOLLIN для сервера и клиентов.

package main

import (
	"fmt"
	"log"
	"net"
	"syscall"

	"golang.org/x/sys/unix"
)

const (
	MaxEvents = 64
	Backlog   = 1024
)

// MinimalReactor реализует каноничный однопоточный Reactor на epoll
type MinimalReactor struct {
	epfd     int
	serverFd int
}

func NewMinimalReactor(port int) (*MinimalReactor, error) {
	// 1. Создаем TCP-сокет в неблокирующем режиме
	fd, err := unix.Socket(unix.AF_INET, unix.SOCK_STREAM|unix.SOCK_NONBLOCK, 0)
	if err != nil {
		return nil, fmt.Errorf("socket: %w", err)
	}

	// Включаем SO_REUSEADDR
	if err := unix.SetsockoptInt(fd, unix.SOL_SOCKET, unix.SO_REUSEADDR, 1); err != nil {
		unix.Close(fd)
		return nil, fmt.Errorf("setsockopt SO_REUSEADDR: %w", err)
	}

	// 2. Биндим адрес и переводим в Listen
	sockaddr := &unix.SockaddrInet4{Port: port}
	copy(sockaddr.Addr[:], net.ParseIP("0.0.0.0").To4())
	if err := unix.Bind(fd, sockaddr); err != nil {
		unix.Close(fd)
		return nil, fmt.Errorf("bind: %w", err)
	}

	if err := unix.Listen(fd, Backlog); err != nil {
		unix.Close(fd)
		return nil, fmt.Errorf("listen: %w", err)
	}

	// 3. Создаем инстанс epoll
	epfd, err := unix.EpollCreate1(0)
	if err != nil {
		unix.Close(fd)
		return nil, fmt.Errorf("epoll_create1: %w", err)
	}

	// 4. Регистрируем слушающий сокет на входящие соединения (EPOLLIN)
	event := &unix.EpollEvent{
		Events: unix.EPOLLIN,
		Fd:     int32(fd),
	}
	if err := unix.EpollCtl(epfd, unix.EPOLL_CTL_ADD, fd, event); err != nil {
		unix.Close(fd)
		unix.Close(epfd)
		return nil, fmt.Errorf("epoll_ctl add listen fd: %w", err)
	}

	return &MinimalReactor{epfd: epfd, serverFd: fd}, nil
}

// Run запускает Event Loop реактора
func (r *MinimalReactor) Run() error {
	events := make([]unix.EpollEvent, MaxEvents)
	buf := make([]byte, 4096)

	log.Printf("Reactor Event Loop запущен на дескрипторе epoll=%d\n", r.epfd)

	for {
		// Блокирующий опрос готовых дескрипторов пачкой
		nEvents, err := unix.EpollWait(r.epfd, events, -1)
		if err != nil {
			if err == syscall.EINTR {
				continue // Прервано системным сигналом
			}
			return fmt.Errorf("epoll_wait error: %w", err)
		}

		for i := 0; i < nEvents; i++ {
			fd := int(events[i].Fd)

			if fd == r.serverFd {
				// Событие на слушающем сокете: принимаем нового клиента
				for {
					connFd, _, err := unix.Accept4(r.serverFd, unix.SOCK_NONBLOCK|unix.SOCK_CLOEXEC)
					if err != nil {
						if err == syscall.EAGAIN || err == syscall.EWOULDBLOCK {
							// Все входящие соединения на текущий момент приняты
							break
						}
						log.Printf("Ошибка accept: %v", err)
						break
					}

					// Добавляем дескриптора клиента в epoll
					clientEv := &unix.EpollEvent{
						Events: unix.EPOLLIN,
						Fd:     int32(connFd),
					}
					if err := unix.EpollCtl(r.epfd, unix.EPOLL_CTL_ADD, connFd, clientEv); err != nil {
						log.Printf("Ошибка регистрации client fd в epoll: %v", err)
						unix.Close(connFd)
					}
				}
			} else {
				// Событие на клиентском сокете: читаем данные
				n, err := unix.Read(fd, buf)
				if n <= 0 || err != nil {
					// Клиент отключился или ошибка сокета -> удаляем из epoll и закрываем
					unix.EpollCtl(r.epfd, unix.EPOLL_CTL_DEL, fd, nil)
					unix.Close(fd)
				} else {
					// Эхо-ответ: отправляем данные назад
					_, _ = unix.Write(fd, buf[:n])
				}
			}
		}
	}
}

func main() {
	reactor, err := NewMinimalReactor(9002)
	if err != nil {
		log.Fatalf("Ошибка создания Reactor: %v", err)
	}
	log.Println("Запуск Minimal Reactor на порту 9002...")
	if err := reactor.Run(); err != nil {
		log.Fatalf("Ошибка рантайма: %v", err)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Внутри ядра Linux вызов epoll_create1 создает структуру struct eventpoll, включающую в себя красно-черное дерево (rbr), где хранятся зарегистрированные дескрипторы сокетов (сложность поиска и вставки $O(\log N)$), и двусвязный список готовых событий (rdllist).

Когда сетевая карта (NIC) принимает кадр и генерирует аппаратное прерывание, сетевой стек ядра вызывает функцию обратного вызова ep_poll_callback(). Она переносит дескриптор в список rdllist и пробуждает поток, спящий в вызове epoll_wait.

Таким образом, ядро Linux не выполняет линейный перебор всех сокетов ($O(N)$, как в устаревшем вызове select), а возвращает пользователю только те дескрипторы, где реально произошли события ($O(1)$).

⚠️ Частые грабли и ошибки новичков

При работе с epoll критически важно создавать сокеты с флагом SOCK_NONBLOCK. Если сокет оставить блокирующим, то при получении ложного уведомления о готовности (spurious wakeup) или при попытке чтения вызовом read(), поток Event Loop намертво заблокируется внутри ядра ОС, полностью парализуя работу всего сервера!

🏢 В продакшене BigTech и на собеседованиях

Вопрос на собеседовании (Lead SRE / Linux Systems Architect):

«В чем разница между Level-Triggered (LT) и Edge-Triggered (ET) режимами epoll, и почему edge-triggered требует обязательного неблокирующего чтения в цикле до появления EAGAIN?»

Эталонный ответ:

1. Level-Triggered (LT — режим по умолчанию): Ядро возвращает событие готовности сокета при каждом вызове epoll_wait до тех пор, пока в буфере сокета остаются непрочитанные байты. Если мы прочитали только часть данных, следующий epoll_wait немедленно разблокируется снова.
2. Edge-Triggered (ET — флаг EPOLLET): Ядро генерирует уведомление *только один раз*, в момент изменения состояния (когда в пустой буфер поступили новые данные).
3. Почему ET требует цикла с EAGAIN: Если при уведомлении в режиме ET прочитать только часть байт и выйти в epoll_wait, новое уведомление *никогда не будет сгенерировано*, пока в сокет не поступят очередные сетевые пакеты. Из-за этого остаток байт зависнет в буфере. Поэтому в ET-режиме необходимо вызывать read() в цикле for { ... } до тех пор, пока системный вызов не вернет ошибку EAGAIN или EWOULDBLOCK.
Упражнение #4

Length-prefixed protocol: Пользовательский буфер кольца и избежание лишних read()

📌 Условие задачи

Реализуйте codec в gnet: каждое сообщение = 4 байта длина (big-endian) + payload. В OnTraffic читайте c.InboundBuffered(), парсите длину, ждёте полного сообщения. Объясните, почему gnet не вызывает read() на каждый байт, а буферизует в userspace ring buffer.

💡 Теоретический фундамент и концепция

Сетевой протокол TCP является потоковым протоколом (stream-oriented protocol), а не пакетным. Это означает, что TCP не сохраняет границы прикладных сообщений:

  • Сообщение может быть разбито на несколько сегментов TCP (фрагментация).
  • Несколько независимых сообщений могут быть склеены в один TCP-сегмент (пакетирование / склейка).

Для разделения сообщений в высокопроизводительных распределенных системах и RPC-фреймворках чаще всего применяется протокол с префиксом длины (Length-Prefixed Framing):

+-------------------+-----------------------------------+
| Length (4 байта)  | Payload (Length байт)             |
| Big-Endian uint32 | Бинарные данные / JSON / Protobuf |
+-------------------+-----------------------------------+
Проблема традиционного чтения сокетов:

В наивной реализации под каждое сообщение разработчик делает:

1. io.ReadFull(conn, headerBuf) (чтение 4 байт длины) — системный вызов read().
2. Парсинг размера $L$.
3. io.ReadFull(conn, payloadBuf) (чтение $L$ байт данных) — еще один системный вызов read().

Если сервер обрабатывает 100 000 сообщений в секунду, такой подход совершит 200 000+ системных вызовов в секунду только на чтение!

Решение в gnet (Userspace Ring Buffer):

Движок gnet агрегирует поступающие данные в собственном кольцевом буфере в пространстве пользователя.

В методе OnTraffic(c gnet.Conn):

1. Метод c.InboundBuffered() возвращает общее число байт, доступных для чтения без единого системного вызова!
2. Если c.InboundBuffered() < 4, сообщение еще не доехало целиком — сервер просто возвращает gnet.None, дожидаясь следующего события.
3. Сервер читает 4 байта длины методом c.Peek(4) без их сдвига из буфера.
4. Если c.InboundBuffered() < 4 + msgLen, сервер также выходит без копирования.
5. Когда весь кадр в сборе, сервер извлекает полное сообщение и смещает указатель кольца вызовом c.Discard(...).

🔍 Пошаговый ход решения и ход мысли инженера

1. Определите заголовок протокола: 4 байта длины в формате binary.BigEndian.Uint32.
2. В обработчике OnTraffic(c gnet.Conn) организуйте цикл извлечения полных сообщений.
3. Используйте c.InboundBuffered() для проверки объема данных в кольцевом буфере.
4. Примените c.Peek(4) для чтения длины кадра без извлечения.
5. При накоплении полного кадра прочитайте данные и сместите указатель чтения через c.Discard(totalLen).
📄 codec_server.go 
package main

import (
	"encoding/binary"
	"fmt"
	"log"

	"github.com/panjf2000/gnet/v2"
)

const HeaderLen = 4

type LengthPrefixedServer struct {
	gnet.BuiltinEventEngine
}

func (s *LengthPrefixedServer) OnTraffic(c gnet.Conn) gnet.Action {
	// В одном сетевом событии может прийти сразу несколько склеенных сообщений,
	// поэтому обрабатываем их в цикле, пока буфер полон.
	for {
		buffered := c.InboundBuffered()
		if buffered < HeaderLen {
			// Меньше 4 байт — заголовок длины еще не получен целиком.
			// Ждем следующего OnTraffic без блокировки!
			return gnet.None
		}

		// Подглядываем первые 4 байта (Peek не сдвигает указатель чтения)
		header, err := c.Peek(HeaderLen)
		if err != nil {
			log.Printf("Ошибка Peek: %v", err)
			return gnet.Close
		}

		// Декодируем размер полезной нагрузки (Big Endian)
		payloadLen := int(binary.BigEndian.Uint32(header))
		totalMsgLen := HeaderLen + payloadLen

		if buffered < totalMsgLen {
			// Заголовок есть, но тело сообщения доехало не полностью.
			// Ждем докачки оставшихся байтов.
			return gnet.None
		}

		// Все сообщение целиком находится в кольцевом буфере gnet!
		fullMsg, err := c.Peek(totalMsgLen)
		if err != nil {
			log.Printf("Ошибка чтения сообщения: %v", err)
			return gnet.Close
		}

		payload := fullMsg[HeaderLen:totalMsgLen]
		// Обрабатываем сообщение (бизнес-логика)
		handleMessage(c, payload)

		// Сдвигаем указатель чтения в кольцевом буфере на размер обработанного кадра
		if _, err := c.Discard(totalMsgLen); err != nil {
			log.Printf("Ошибка Discard: %v", err)
			return gnet.Close
		}
	}
}

func handleMessage(c gnet.Conn, payload []byte) {
	// Формируем эхо-ответ с префиксом длины
	respPayload := append([]byte("ACK: "), payload...)
	resp := make([]byte, HeaderLen+len(respPayload))
	binary.BigEndian.PutUint32(resp[:HeaderLen], uint32(len(respPayload)))
	copy(resp[HeaderLen:], respPayload)

	_ = c.AsyncWrite(resp, nil)
}

	log.Printf("Запуск Length-Prefixed Codec сервера на %s...\n", addr)
	if err := gnet.Run(server, addr, gnet.WithMulticore(true)); err != nil {
		log.Fatalf("Ошибка gnet: %v", err)
	}
}

Zero-copy ответ: sync.Pool, AsyncWrite и системные вызовы writev и sendfile

📌 Условие задачи

В gnet используйте c.AsyncWrite(buf) или c.Write(buf) с предварительно аллоцированным []byte из sync.Pool. Покажите, что это минимизирует аллокации. Объясните, что gnet использует sendfile (для файлов) и writev (scatter-gather) где возможно.

💡 Теоретический фундамент и концепция

В высоконагруженных сетевых сервисах наибольшая нагрузка на сборщик мусора Go возникает не при чтении данных, а при формировании и отправке ответов.

Если обработчик на каждый запрос создает новый байтовый слайс через make([]byte, size) или bytes.NewBuffer(), при 200 000 RPS это генерирует сотни мегабайт мусора в секунду, вызывая частые циклы Stop-The-World (STW) и деградацию латентности.

Технологии Zero-Copy и Zero-Allocation в сети:
1. Пул буферов (sync.Pool):

Повторное использование предварительно аллоцированных срезов байтов позволяет свести число вызовов mallocgc практически к нулю. Буфер берется из пула, наполняется данными ответа и возвращается обратно после того, как сетевой стек отправил байты в сокет.

2. Векторизованный ввод-вывод (writev / Scatter-Gather I/O):

Системный вызов writev(fd, iov, iovcnt) позволяет отправить клиенту заголовок и тело ответа из разных участков памяти без их объединения в один общий буфер! Это исключает промежуточное копирование (memcpy).

3. Передача файлов через sendfile:

Системный вызов sendfile(out_fd, in_fd, offset, count) осуществляет передачу данных из файлового дескриптора прямо в сокет внутри адресного пространства ядра Linux (Page Cache -> Socket Buffer), минуя копирование в userspace-буфер Go.

3. Сформируйте полезную нагрузку ответа.
4. Отправьте данные через c.AsyncWrite(buf, callback) — где в коллбэке завершения передачи верните буфер обратно в sync.Pool.

package main

import (
	"log"
	"sync"

	"github.com/panjf2000/gnet/v2"
)

const BufferSize = 4096

// Инициализация пула байтовых слайсов для Zero-Allocation ответов
var bufferPool = sync.Pool{
	New: func() any {
		b := make([]byte, BufferSize)
		return &b
	},
}

type ZeroCopyServer struct {
	gnet.BuiltinEventEngine
}

func (s *ZeroCopyServer) OnTraffic(c gnet.Conn) gnet.Action {
	in, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// 1. Берем буфер из пула вместо heap-аллокации
	bufPtr := bufferPool.Get().(*[]byte)
	buf := (*bufPtr)[:0] // сбрасываем длину, сохраняя емкость

	// 2. Заполняем буфер данными ответа
	buf = append(buf, "HTTP/1.1 200 OK\r\nContent-Length: "...)
	buf = append(buf, []byte("13\r\n\r\nHello, World!")...)

	// 3. Отправляем ответ асинхронно через AsyncWrite.
	// Коллбэк вызывается gnet, когда данные полностью записаны в сетевой сокет,
	// после чего буфер можно безопасно вернуть в sync.Pool!
	err = c.AsyncWrite(buf, func(c gnet.Conn, err error) error {
		// Возвращаем буфер в пул
		bufferPool.Put(bufPtr)
		return nil
	})

	if err != nil {
		// Если отправка не удалась сразу, возвращаем буфер
		bufferPool.Put(bufPtr)
		log.Printf("Ошибка AsyncWrite: %v", err)
		return gnet.Close
	}

	_ = in
	return gnet.None
}

func main() {
	server := &ZeroCopyServer{}
	addr := "tcp://127.0.0.1:9004"
	log.Printf("Запуск Zero-Copy сервера на %s...\n", addr)
	if err := gnet.Run(server, addr, gnet.WithMulticore(true)); err != nil {
		log.Fatalf("Ошибка gnet: %v", err)
	}
}
ℹ️ Безопасное переиспользование буферов через sync.Pool и коллбэк завершения AsyncWrite
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Когда приложение вызывает c.Write() или c.AsyncWrite(), gnet пытается записать байты немедленно в неблокирующий сокет через системный вызов write(). Если буфер отправки сокета в ядре (SO_SNDBUF) переполнен, вызов возвращает EAGAIN.

В этот момент gnet помещает неотправленный остаток во внутренний кольцевой буфер очереди сокета и регистрирует дескриптор в epoll на событие EPOLLOUT.

Когда ядро освобождает буфер TCP-окна, epoll_wait триггерит реактор, и gnet отправляет оставшиеся фрагменты через системный вызов writev(), объединяя заголовочные и пользовательские буферы без единой memcpy в памяти.

⚠️ Частые грабли и ошибки новичков

Критическая ошибка при работе с sync.Pool в сетевых библиотеках: возврат буфера в пул до фактической отправки данных. Если вы вернете buf в sync.Pool сразу после вызова c.AsyncWrite(), другой поток может забрать этот буфер и перетереть его новыми данными в то время, как сокет еще передает байты в сеть! Результат — повреждение данных у клиента (Data Corruption). Возвращать буфер разрешено только внутри completion callback.

«Как устроен механизм scatter-gather I/O (системный вызов writev) и почему он критичен для высоконагруженных прокси (Envoy, Nginx, Traefik)?»

💡 Теоретический фундамент и концепция

При классической архитектуре серверов один сокет слушает порт (bind + listen), а входящие соединения принимаются главным потоком (Main Reactor).

Однако при сотнях тысяч соединений в секунду одиночный слушающий сокет становится узким горлышком:

1. Блокировка мьютекса слушателя в ядре: При одновременном вызове accept() несколькими потоками ядро Linux захватывает внутренний спинлок очереди соединений (listen socket lock), создавая процессорную конкуренцию (Lock Contention).
2. Проблема «стада» (Thundering Herd Problem): Исторически при появлении нового соединения пробуждались все спящие в epoll_wait потоки, хотя соединение мог забрать только один.
Опция сокета SO_REUSEPORT (Linux 3.9+)

Опция SO_REUSEPORT позволяет нескольким независимым сокетам (и процессам) одновременно биндиться на один и тот же TCP-порт:

CPU Core 0  ──►  Socket 0 (fd 5)  ──►  epoll 0  ──►  Sub-Reactor 0
CPU Core 1  ──►  Socket 1 (fd 6)  ──►  epoll 1  ──►  Sub-Reactor 1
CPU Core 2  ──►  Socket 2 (fd 7)  ──►  epoll 2  ──►  Sub-Reactor 2
CPU Core 3  ──►  Socket 3 (fd 8)  ──►  epoll 3  ──►  Sub-Reactor 3

Ядро Linux автоматически распределяет входящие SYN-пакеты между сокетами слушателей, вычисляя 4-tuple хеш (hash(src_ip, src_port, dst_ip, dst_port) % N_sockets).

Каждое ядро CPU получает собственный независимый сетевой стек, исключая межъядерную инвалидацию L1/L2 кэшей и кардинально снижая задержку на 99-м перцентиле (p99 latency) при 10 000+ одновременных соединений.

}

func (s *MultiReactorServer) OnBoot(eng gnet.Engine) gnet.Action {

Когда включен SO_REUSEPORT, каждый Event Loop открывает свой собственный слушающий сокет через bind() на один и тот же порт. Ядро Linux создает структуру struct sock_reuseport, которая хранит массив указателей на все сокеты группы.

При приходе TCP SYN-пакета ядро выполняет хеширование заголовков пакета и напрямую помещает входящее соединение в очередь SYN queue конкретного сокета, привязанного к соответствующему ядру CPU. Таким образом, обработка accept() полностью распараллеливается на уровне аппаратных очередей сетевой карты (RSS) и планировщика Linux.

⚠️ Частые грабли и ошибки новичков

При динамическом изменении количества сокетов (например, при graceful reload одного из воркеров) хеш-функция ядра перераспределяет сокеты в массиве SO_REUSEPORT. Если клиент отправил ACK для завершения TCP 3-way handshake в момент, когда сокет был закрыт, соединение сбросится с RST. Для бесшовного перезапуска на Linux 4.5+ используют флаг SO_ATTACH_REUSEPORT_CBPF.

В отличие от стандартного интерфейса Go net.Conn, где чтение и закрытие вызываются императивно, архитектура gnet является строго декларативной и управляемой событиями (Event-Driven Framework).

Методы интерфейса gnet.EventHandler:
  • OnBoot(eng gnet.Engine) (action gnet.Action): Вызывается один раз при инициализации движка. Здесь инициализируются глобальные ресурсы, пулы памяти и метрики.
  • OnOpen(c gnet.Conn) (out []byte, action gnet.Action): Срабатывает сразу после завершения TCP 3-way handshake. Если сервер хочет немедленно отправить приветственное сообщение (например, баннер SSH или приветствие SMTP), он может вернуть срез байт в out.
  • OnTraffic(c gnet.Conn) (action gnet.Action): Главный обработчик входящего трафика. Вызывается при готовности данных в сокете.
  • OnClose(c gnet.Conn, err error) (action gnet.Action): Вызывается при закрытии сокета со стороны удаленного узла (FIN/RST) либо по инициативе сервера. Гарантирует очистку контекста соединения.
  • OnTick() (delay time.Duration, action gnet.Action): Опциональный таймер, вызываемый циклически внутри Event Loop (для heartbeat, сбора метрик или очистки протухших сессий без создания фоновых горутин).

import (
	"fmt"
	"log"
	"sync/atomic"
	"time"

	"github.com/panjf2000/gnet/v2"
)

// SessionState хранит контекст отдельного клиентского подключения
type SessionState struct {
	ID        int64
	OpenedAt  time.Time
	BytesRead int64
}

type SingleLoopEchoServer struct {
	gnet.BuiltinEventEngine
	connCounter int64
}

// OnBoot инициализирует сервер
func (s *SingleLoopEchoServer) OnBoot(eng gnet.Engine) (action gnet.Action) {
	log.Println("[SingleLoop] Сервер успешно загружен и готов принимать соединения")
	return gnet.None
}

// OnOpen инициализирует состояние сессии
func (s *SingleLoopEchoServer) OnOpen(c gnet.Conn) (out []byte, action gnet.Action) {
	id := atomic.AddInt64(&s.connCounter, 1)
	state := &SessionState{
		ID:       id,
		OpenedAt: time.Now(),
	}
	// Сохраняем состояние сессии в метаданных соединения
	c.SetContext(state)

	// Отправляем приветственный баннер без heap-аллокаций
	welcome := []byte(fmt.Sprintf("WELCOME_CONN_%d\n", id))
	return welcome, gnet.None
}

// OnTraffic обрабатывает входящие данные
func (s *SingleLoopEchoServer) OnTraffic(c gnet.Conn) (action gnet.Action) {
	state, ok := c.Context().(*SessionState)
	if !ok {
		return gnet.Close
	}

	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	state.BytesRead += int64(len(buf))

	// Эхо-ответ
	if _, err := c.Write(buf); err != nil {
		return gnet.Close
	}

	return gnet.None
}

// OnClose очищает контекст соединения
func (s *SingleLoopEchoServer) OnClose(c gnet.Conn, err error) (action gnet.Action) {
	if state, ok := c.Context().(*SessionState); ok {
		duration := time.Since(state.OpenedAt)
		log.Printf("[Conn %d] Закрыто. Время жизни: %v, Обработано байт: %d, Ошибка: %v\n",
			state.ID, duration, state.BytesRead, err)
	}
	return gnet.None
}

		gnet.WithMulticore(false),

Внутри gnet объект c gnet.Conn не является интерфейсной оберткой вокруг файлового дескриптора на каждую операцию. Это долгоживущая структура, которая переиспользуется из внутреннего пула объектов ядра gnet.

Поле c.SetContext(val) позволяет ассоциировать любые пользовательские данные с соединением. Это исключает необходимость заводить внешнюю потокобезопасную карту sync.Map для хранения сессий: пока соединение живо, контекст доступен по прямому указателю без синхронизации мьютексами, поскольку вызовы OnTraffic для данного сокета гарантированно последовательны в рамках одного Event Loop!

⚠️ Частые грабли и ошибки новичков

Хотя c.Context() доступен без синхронизации внутри методов OnTraffic и OnClose, если вы передаете указатель на этот контекст в сторонние горутины (Worker Pool), возникает состояние гонки данных (Data Race). Либо копируйте состояние, либо используйте атомики внутри полей SessionState.

🏢 В продакшене BigTech и на собеседованиях

Вопрос на собеседовании (Senior Go Developer / Infrastructure):

«Зачем в gnet предусмотрен метод OnTick(), если в Go можно в любой момент запустить горутину с time.NewTicker()? В чем преимущество OnTick с точки зрения профилирования CPU?»

Эталонный ответ:

Каждая отдельная горутина с time.Ticker требует отдельного стека памяти, а срабатывание таймера в рантайме Go приводит к пробуждению планировщика GMP (sysmon или runtime timer heap) и переключению контекста на поток M.

Метод OnTick() исполняется прямо внутри самого цикла epoll_wait (за счет таймаута системного вызова epoll). Это гарантирует, что периодическая работа (heartbeat сокетов, сброс метрик) выполняется в контексте уже активного сетевого потока без создания горутин, без захвата блокировок планировщика и с минимальным CPU cache miss.

import (
	"fmt"
	"log"
	"os"
	"os/signal"
	"sync/atomic"
	"syscall"
	"time"

type BenchEchoServer struct {
	gnet.BuiltinEventEngine
	addr       string
	totalReqs  int64
	totalBytes int64
}

func (b *BenchEchoServer) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	atomic.AddInt64(&b.totalReqs, 1)
	atomic.AddInt64(&b.totalBytes, int64(len(buf)))

	// Пишем эхо-ответ обратно
	_, _ = c.Write(buf)
	return gnet.None
}

func main() {
	server := &BenchEchoServer{addr: "tcp://127.0.0.1:9007"}

	// Фоновый сборщик метрик в консоль
	go func() {
		ticker := time.NewTicker(2 * time.Second)
		defer ticker.Stop()
		var lastReqs int64

		for range ticker.C {
			current := atomic.LoadInt64(&server.totalReqs)
			bytes := atomic.LoadInt64(&server.totalBytes)
			rps := (current - lastReqs) / 2
			lastReqs = current

			fmt.Printf("[METRICS] Текущий RPS: %d req/s | Всего обработано: %d пакетов (%d MB)\n",
				rps, current, bytes/(1024*1024))
		}
	}()

	// Graceful shutdown по сигналам SIGINT/SIGTERM
	sigChan := make(chan os.Signal, 1)
	signal.Notify(sigChan, syscall.SIGINT, syscall.SIGTERM)
	go func() {
		<-sigChan
		log.Println("Остановка сервера по сигналу...")
		_ = gnet.Stop(nil, server.addr)
	}()

	log.Printf("Запуск Bench Echo сервера на %s...\n", server.addr)
	err := gnet.Run(
		server,
		server.addr,
		gnet.WithMulticore(true),
		gnet.WithReusePort(true),
	)
	if err != nil {
		log.Fatalf("Ошибка gnet: %v", err)
	}

«Что такое Coordinated Omission (скоординированный пропуск) в бенчмарках сетевых серверов, и почему стандартные замеры latency могут быть обманчиво оптимистичными?»

Эталонный ответ:

Coordinated Omission — фундаментальная ошибка многих генераторов нагрузки (например, старых версий JMeter или наивных скриптов на Go), работающих по принципу синхронных циклов for { send(); recv() }.

Если сервер зависает на 500 мс (например, из-за блокировки Event Loop или паузы GC), клиентский генератор тоже блокируется в ожидании ответа и не отправляет новые запросы во время этого сбоя. В результате в статистику попадает всего один «медленный» запрос, а тысячи запросов, которые должны были прийти в этот интервал и получить чудовищную задержку, просто не были отправлены! Реальная задержка p99 при этом искажается в десятки раз в лучшую сторону. Профессиональные генераторы (wrk2, tcpkali) используют генерацию запросов по расписанию независимо от времени отклика сервера.

Worker Pool в gnet: Разделение сетевого I/O и вычислительной бизнес-логики

📌 Условие задачи

💡 Теоретический фундамент и концепция

Фундаментальная заповедь любого асинхронного сетевого фреймворка (Netty, Node.js, libuv, gnet, evio): Event Loop никогда не должен блокироваться!

Если обработчик OnTraffic выполняет синхронный запрос к SQL-базе данных (латентность 5–20 мс), обращается к микросервису по REST или производит тяжелое криптографическое хеширование Argon2/Bcrypt, поток реактора замирает на всё это время.

В архитектуре gnet один Sub-Reactor обслуживает тысячи сокетов. Задержка одного реактора на 20 мс означает, что все остальные тысячи клиентов, закрепленных за данным потоком epoll, не смогут ни отправить, ни получить ни единого байта, их p99 латентность мгновенно катапультируется в секунды!

Архитектурный паттерн: Event Loop + Worker Pool

Для преодоления этой проблемы применяется четкое разделение ответственности:

[Сетевые клиенты]
       │ (TCP сокеты)
       ▼
[Sub-Reactor (Event Loop)]  <── Быстрое чтение байтов из сокета (O(1), неблокирующее)
       │
       ▼ (push задачи в очередь chan / lock-free ring)
[Worker Pool (ants / goroutines)]  <── Выполнение тяжелой бизнес-логики (SQL, CPU, Disk)
       │
       ▼ (c.AsyncWrite)
[Отправка ответа в сокет]
Разница между react (sync) и serve (async):
  • Синхронный подход (react / In-Loop): Полезен исключительно для тривиальных операций (Echo, быстрый парсинг в памяти, проверка in-memory кэша без блокировок). Ответ возвращается прямо из OnTraffic.
  • Асинхронный подход (serve / Offload): Данные копируются из кольцевого буфера в задачу, задача отправляется в ограниченный пул воркеров (Bounded Worker Pool, например библиотеку panjf2000/ants), а ответ отправляется через неблокирующий метод c.AsyncWrite().

🔍 Пошаговый ход решения и ход мысли инженера

1. Создайте структуру пула воркеров или используйте буферизованный канал задач chan Task.
2. В методе OnTraffic прочитайте поступившие данные методом c.Next(-1).
3. Скопируйте байты в новую структуру задачи (поскольку кольцевой буфер gnet будет перезаписан).
4. Отправьте задачу в воркер-пул без блокировки сетевого цикла (с проверкой переполнения).
5. Внутри воркера выполните бизнес-логику и отправьте ответ вызовом c.AsyncWrite(result, nil).

package main

import (
	"fmt"
	"log"
	"sync"
	"time"

	"github.com/panjf2000/gnet/v2"
)

// Task представляет собой сетевую задачу для пула воркеров
type Task struct {
	Conn gnet.Conn
	Data []byte
}

type WorkerPoolServer struct {
	gnet.BuiltinEventEngine
	taskQueue chan Task
	workersWg sync.WaitGroup
}

func NewWorkerPoolServer(workers int, queueSize int) *WorkerPoolServer {
	s := &WorkerPoolServer{
		taskQueue: make(chan Task, queueSize),
	}

	// Запуск пула фоновых горутин-воркеров
	for i := 0; i < workers; i++ {
		s.workersWg.Add(1)
		go s.workerLoop(i)
	}

	return s
}

// workerLoop обрабатывает тяжелые задачи вне сетевого Event Loop
func (s *WorkerPoolServer) workerLoop(id int) {
	defer s.workersWg.Done()
	for task := range s.taskQueue {
		// Имитация блокирующей бизнес-логики (например, вызов к СУБД или кэшу)
		time.Sleep(10 * time.Millisecond)

		// Формируем результат обработки
		response := append([]byte(fmt.Sprintf("[Worker-%d ACK]: ", id)), task.Data...)

		// Отправляем ответ клиенту через потокобезопасный асинхронный API gnet
		_ = task.Conn.AsyncWrite(response, nil)
	}
}

// OnTraffic исполняется сетевым потоком реактора! Никаких блокировок здесь быть не должно!
func (s *WorkerPoolServer) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// КРИТИЧЕСКИ ВАЖНО: копируем байты, так как буфер gnet переиспользуется
	dataCopy := make([]byte, len(buf))
	copy(dataCopy, buf)

	// Неблокирующая отправка в очередь воркеров
	select {
	case s.taskQueue <- Task{Conn: c, Data: dataCopy}:
		// Задача успешно передана воркерам
		return gnet.None
	default:
		// Очередь переполнена (Backpressure) — отклоняем запрос без зависания Event Loop
		log.Println("[WARN] Очередь задач переполнена, сброс запроса")
		_ = c.AsyncWrite([]byte("ERR: SERVER_BUSY_BACKPRESSURE\n"), nil)
		return gnet.None
	}
}

func main() {
	server := NewWorkerPoolServer(16, 10000)
	addr := "tcp://127.0.0.1:9008"

	log.Printf("Запуск сервера с пулом воркеров на %s...\n", addr)

ℹ️ Паттерн Worker Pool для изоляции сетевых Event Loops от блокирующей бизнес-логики
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Когда воркер вызывает метод task.Conn.AsyncWrite(response, cb), данные не записываются в сокет немедленно из потока воркера.

Вместо этого gnet использует внутреннюю потокобезопасную очередь задач (Lock-Free MPSC Ring или системный eventfd), привязанный к конкретному Sub-Reactor данного соединения. Системный вызов eventfd_write() пробуждает поток epoll_wait, и уже сам сетевой реактор регистрирует событие EPOLLOUT и выполняет атомарную запись в сокет. Это полностью исключает состояние гонки при одновременной записи нескольких горутин в один и тот же файловый дескриптор сокета.

⚠️ Частые грабли и ошибки новичков

Самая фатальная ошибка: передача среза buf из c.Next(-1) прямо в горутину воркера без создания копии (copy(dataCopy, buf)). Кольцевой буфер gnet является циклическим. Пока воркер проснется и начнет читать задачу, сетевой реактор уже считает новые сетевые пакеты в ту же самую физическую память, что приведет к катастрофической порче данных (Silent Data Corruption).

package main

import (
	"bytes"
	"fmt"
	"log"
	"strconv"

	"github.com/panjf2000/gnet/v2"
)

var (
	crlfDouble = []byte("\r\n\r\n")
	crlf       = []byte("\r\n")
	space      = []byte(" ")
	contentLen = []byte("content-length:")

	httpOkResponse = []byte("HTTP/1.1 200 OK\r\nServer: gnet-fast-http\r\nContent-Type: application/json\r\nContent-Length: 17\r\n\r\n{\"status\":\"ok\"}\r\n")
)

type FastHTTPServer struct {
	gnet.BuiltinEventEngine
}

func (s *FastHTTPServer) OnTraffic(c gnet.Conn) gnet.Action {
	for {
		buffered := c.InboundBuffered()
		if buffered < 14 { // Минимальный валидный HTTP запрос: "GET / HTTP/1.1\r\n"
			return gnet.None
		}

		// Заглядываем в буфер без сдвига указателя
		data, err := c.Peek(buffered)
		if err != nil {
			return gnet.Close
		}

		// 1. Ищем маркер окончания HTTP-заголовков (\r\n\r\n)
		headerEnd := bytes.Index(data, crlfDouble)
		if headerEnd == -1 {
			// Заголовки получены еще не полностью, ждем
			return gnet.None
		}

		headerBytes := data[:headerEnd]
		totalHeaderLen := headerEnd + len(crlfDouble)

		// 2. Извлекаем Content-Length для проверки наличия тела POST/PUT
		bodyLen := 0
		lowerData := bytes.ToLower(headerBytes)
		if idx := bytes.Index(lowerData, contentLen); idx != -1 {
			valStart := idx + len(contentLen)
			valEnd := bytes.Index(headerBytes[valStart:], crlf)
			if valEnd != -1 {
				lenStr := string(bytes.TrimSpace(headerBytes[valStart : valStart+valEnd]))
				bodyLen, _ = strconv.Atoi(lenStr)
			}
		}

		totalReqLen := totalHeaderLen + bodyLen
		if buffered < totalReqLen {
			// Тело запроса еще не доехало целиком
			return gnet.None
		}

		// 3. Парсим строку запроса (METHOD /PATH HTTP/1.1)
		firstLineEnd := bytes.Index(headerBytes, crlf)
		if firstLineEnd != -1 {
			requestLine := headerBytes[:firstLineEnd]
			parts := bytes.Split(requestLine, space)
			if len(parts) >= 2 {
				method := parts[0]
				path := parts[1]
				_ = method
				_ = path
			}
		}

		// 4. Отправляем сверхбыстрый ответ
		_, _ = c.Write(httpOkResponse)

		// 5. Сдвигаем кольцевой буфер на размер всего обработанного HTTP-запроса
		_, _ = c.Discard(totalReqLen)
	}
}

func main() {
	server := &FastHTTPServer{}
	addr := "tcp://127.0.0.1:8080"
	log.Printf("Запуск высокопроизводительного HTTP/1.1 сервера на %s...\n", addr)
	fmt.Println("Тестируйте с помощью wrk: wrk -c100 -t4 -d10s http://127.0.0.1:8080/")

	err := gnet.Run(server, addr, gnet.WithMulticore(true))
	if err != nil {
		log.Fatalf("Ошибка запуска: %v", err)
	}
}

В отличие от net/http, который аллоцирует структуры http.Request на каждый входящий запрос через кучу, данный парсер использует алгоритм поиска подстрок Бойера-Мура или векторизованные инструкции AVX2/SSE4.2 (bytes.Index в Go оптимизирован на Plan 9 ассемблере с использованием SIMD-инструкций PCMPEQB). [Коварный кейс] Блокировка в Event Loop: Зависание всех клиентов на Sub-Reactor

📌 Условие задачи

В OnTraffic сделай time.Sleep(1 * time.Second) (эмуляция блокирующего вызова к БД). Подключись 10 клиентами. Объясни, почему *все* 10 клиентов зависнут, хотя в net/http они обрабатывались бы параллельно. (Event Loop заблокирован).

💡 Теоретический фундамент и концепция

Этот практический эксперимент наглядно демонстрирует фундаментальное архитектурное отличие между классической моделью Go (net/http) и событийно-ориентированными движками (gnet, evio, Nginx, Redis).

Что происходит в net/http при блокировке:

В стандартной библиотеке Go обработка каждого соединения изолирована в собственной независимой горутине:

go c.serve(connCtx) // net/http/server.go

Если обработчик внутри одной горутины выполняет блокирующий вызов:

time.Sleep(1 * time.Second) // или медленный SQL select

Планировщик GMP переводит данную горутину в состояние ожидания _Gwaiting и передает поток M другим горутинам. Все остальные 999 подключенных клиентов продолжают обслуживаться параллельно и не замечают задержки!

Что происходит в gnet при блокировке:

В gnet все события ввода-вывода сотен или тысяч сокетов мультиплексируются одним единственным системным потоком Event Loop (Sub-Reactor).

Если вы напишете time.Sleep(1 * time.Second) внутри OnTraffic:

func (s *Server) OnTraffic(c gnet.Conn) gnet.Action {
    time.Sleep(1 * time.Second) // КАТАСТРОФА!
    ...
}

Поток операционной системы, исполняющий epoll_wait, замирает на целую секунду.

Все 10, 100 или 10 000 клиентов, дескрипторы которых были привязаны к данному Event Loop, оказываются заблокированными:

  • Новые TCP SYN пакеты не подтверждаются (если заблокирован Main Reactor).
  • Принятые пакеты застревают в очереди ядра сокета Receive-Q.
  • Ни один ответ не отправляется в сеть.
  • Происходит лавинообразный всплеск задержки (Head-of-Line Blocking на уровне реактора).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создайте сервер gnet с одним потоком событий gnet.WithNumEventLoop(1).
2. Внутри OnTraffic добавьте искусственную задержку time.Sleep(1 * time.Second).
3. Запустите 10 параллельных клиентов, отправляющих TCP-пакеты.
4. Замерьте время ответа: клиенты будут обслуживаться строго последовательно, а суммарное время составит 10 секунд вместо 1 секунды!
5. Сделайте вывод об архитектурных правилах работы с Event Loops.

package main

import (
	"fmt"
	"net"
	"sync"
	"time"
)

func main() {
	const totalClients = 10
	var wg sync.WaitGroup
	startAll := time.Now()

	fmt.Printf("Подключение %d параллельных клиентов к блокирующему серверу...\n", totalClients)

	for i := 1; i <= totalClients; i++ {
		wg.Add(1)
		clientID := i
		go func() {
			defer wg.Done()
			clientStart := time.Now()

			conn, err := net.Dial("tcp", "127.0.0.1:9009")
			if err != nil {
				fmt.Printf("[Client %d] Ошибка подключения: %v\n", clientID, err)
				return
			}
			defer conn.Close()

			// Отправляем сообщение
			_, _ = conn.Write([]byte(fmt.Sprintf("REQ_%d", clientID)))

			// Ждем ответ
			buf := make([]byte, 128)
			n, _ := conn.Read(buf)

			elapsed := time.Since(clientStart)
			fmt.Printf("[Client %d] Ответ: %q | Время отклика: %.2f сек\n",
				clientID, string(buf[:n]), elapsed.Seconds())
		}()
	}

	wg.Wait()
	totalElapsed := time.Since(startAll)
	fmt.Printf("\n=== ИТОГ: Все %d клиентов завершены за %.2f сек (вместо ~1 сек при параллелизме)! ===\n",
		totalClients, totalElapsed.Seconds())
}
ℹ️ Клиентский тест, демонстрирующий последовательное зависание параллельных запросов
⚙️ Под капотом Go (Compiler, Linker & Runtime)

В ядре Linux каждый TCP-сокет имеет буфер приема sk_rcvbuf. Когда сетевой поток gnet спит в time.Sleep(), он не вызывает epoll_wait и не вычитывает байты из очереди ядра.

TCP-стек ядра Linux принимает входящие пакеты и складывает их в sk_receive_queue. Когда этот буфер заполняется, TCP стек отправляет клиенту сообщение Zero Window (окно приема TCP равно 0), запрещая дальнейшую передачу. Клиенты встают на паузу на уровне сетевого стека ядра, пока Event Loop наконец не проснется и не вызовет системный вызов read().

⚠️ Частые грабли и ошибки новичков

В реальных проектах блокировка часто бывает не явной (time.Sleep), а скрытой:

1. Захват глобального мьютекса sync.Mutex, который удерживается другой горутиной.
2. Небуферизованная запись в канал Go ch <- val, из которого временно никто не читает.
3. Логирование в файл через log.Println или обращение к диску при медленном дисковом I/O (iowait).

Любая из этих причин способна положить высоконагруженный реактор!

Вопрос на собеседовании (Head of Backend / HighLoad Architect):

«Как в архитектуре Node.js, Redis и gnet решается проблема блокирующих вызовов? Почему Redis однопоточный, но не страдает от этой проблемы?»

Эталонный ответ:

1. Почему Redis быстрый: Все операции Redis (GET, SET, LPUSH) выполняются исключительно со структурами данных в оперативной памяти с алгоритмической сложностью $O(1)$ или $O(\log N)$ (наносекунды). Все тяжелые операции (сброс снапшотов RDB, AOF fsync, освобождение больших ключей UNLINK) вынесены в отдельные фоновые потоки (bio.c).

Многопоточность в gnet: Настройка NumEventLoop и горизонтальное масштабирование

📌 Условие задачи

Установите NumEventLoop равным runtime.NumCPU(). Сравните производительность (RPS, задержку) с однопоточным режимом и с обычным TCP-сервером на net.

💡 Теоретический фундамент и концепция

В многоядерных серверных архитектурах (от 16 до 128 ядер) производительность однопоточного реактора упирается в предел пропускной способности одного процессорного ядра (около 150 000 – 300 000 RPS).

Для полного раскрытия потенциала современного серверного оборудования gnet позволяет сконфигурировать параметр NumEventLoop:

  • Если NumEventLoop = 1: запускается классический однопоточный реактор.
  • Если NumEventLoop = runtime.NumCPU() и Multicore = true: запускается многопоточный Multi-Reactor, где каждое ядро CPU обрабатывает свой независимый набор сокетов.
Привязка потоков к ядрам (CPU Affinity / Thread Pinning):

Для предотвращения миграции потоков между ядрами ОС (что приводит к сбросу кэшей процессора L1i/L1d и задержкам на межпроцессорной шине NUMA), gnet предоставляет опцию:

gnet.WithLockOSThread(true)

Каждый Event Loop жестко связывается со своим системным потоком OS Thread вызовом runtime.LockOSThread(), обеспечивая максимальную локальность кэша (Cache Locality).

«Что такое NUMA (Non-Uniform Memory Access) и почему привязка потоков к ядрам (Thread Affinity) критична на двухсокетных серверах?»

Эталонный ответ:

На двухсокетных материнских платах каждый процессор имеет собственный контроллер памяти и локальные планки RAM. Доступ к памяти соседнего сокета (Remote Memory Access) идет через шину Ultra Path Interconnect (UPI / QPI) с задержкой в 2–3 раза выше, чем к локальной памяти.

Если поток сетевого Event Loop мигрирует между ядрами разных физических процессоров, он вынужден постоянно обращаться к удаленным узлам NUMA, вызывая резкие просадки производительности. Привязка потоков (pthread_setaffinity_np / LockOSThread) гарантирует исполнение кода строго на локальном NUMA-узле.

💡 Теоретический фундамент и концепция

Модель параллелизма Go (CSP — Communicating Sequential Processes) и концепция «одна горутина на соединение» стали революцией в бэкенд-разработке 2010-х годов. Разработчикам больше не нужно было писать сложные машины состояний (State Machines) и путаться в асинхронных коллбэках (Callback Hell), как в C++ или Node.js. Код читался последовательно и синхронно.

Однако при переходе от масштаба десятков тысяч подключений к масштабу миллионов одновременных соединений (проблема C10M) стандартный сетевой стек net сталкивается с непреодолимыми физическими ограничениями архитектуры рантайма Go.

Четыре фундаментальных барьера модели goroutine-per-connection:
1. Память под стеки горутин:

Минимальный размер стека горутины в Go составляет 2048 байт (2 КБ), плюс около 1–2 КБ служебных структур рантайма (runtime.g).

  • При 1 000 000 соединений: $10^6 \times 3.5 \text{ КБ} \approx 3.5 \text{ ГБ}$ оперативной памяти расходуется исключительно на поддержание пустых соединений, в которых клиенты не передают никаких данных (Idle Keep-Alive)!
2. Конкуренция в Go Runtime Netpoller:

Внутренний netpoller Go использует один или несколько дескрипторов epoll. Когда сокет готов к чтению, сетевой поллер должен найти соответствующую горутину g и перевести ее из статуса _Gwaiting в _Grunnable, поместив в очередь выполнения p.runq. При миллионе сокетов операции с очередями планировщика и мьютексы рантайма вызывают сильнейшую деградацию масштабируемости (Lock Contention).

3. Фаза разметки сборщика мусора (GC Mark Phase):

Трехцветный сборщик мусора Go во время каждого цикла сканирует стек каждой активной горутины как корневой набор ссылок (Root Set). Проход по миллиону стеков горутин приводит к резкому росту процессорного времени, отдаваемого на нужды сборщика мусора (GC Assist), отнимая до 25% CPU у бизнес-логики.

4. Вымывание процессорных кэшей (Cache Thrashing):

При переключении между сотнями тысяч горутин регистры процессора и указатель стека SP непрерывно перезаписываются, вымывая данные из сверхбыстрых L1d/L2 кэшей процессора.

import "fmt"

// ConnectionMemoryProfile рассчитывает теоретический расход памяти под сетевые соединения
type ConnectionMemoryProfile struct {
	Connections       int
	StackPerConnBytes int
	RuntimeOverhead   int
}

func (p ConnectionMemoryProfile) TotalMemoryMB() float64 {
	totalBytes := p.Connections * (p.StackPerConnBytes + p.RuntimeOverhead)
	return float64(totalBytes) / (1024 * 1024)
}

func main() {
	conns := []int{10_000, 100_000, 500_000, 1_000_000, 10_000_000}

	fmt.Println("=== Анализ потребления памяти: goroutine-per-connection vs Event-Loop ===")
	fmt.Printf("%-12s | %-25s | %-20s\n", "Соединений", "Go net (goroutine-per-conn)", "gnet (Event Loop)")
	fmt.Println("-------------------------------------------------------------------------")

	for _, c := range conns {
		// Go net: 2048 байт минимальный стек + ~1500 байт структуры runtime.g и дескриптор
		goNetMem := ConnectionMemoryProfile{
			Connections:       c,
			StackPerConnBytes: 2048,
			RuntimeOverhead:   1536,

			RuntimeOverhead:   256,
		}.TotalMemoryMB()

import (
	"fmt"
	"io"
	"log"
	"net"
	"net/http"
	_ "net/http/pprof"
	"runtime"
	"sync/atomic"
	"time"

var activeConnections int64

func handleConn(c net.Conn) {
	defer func() {
		_ = c.Close()
		atomic.AddInt64(&activeConnections, -1)
	}()

	atomic.AddInt64(&activeConnections, 1)

Упражнение #16

gnet + Protobuf: Высокопроизводительный RPC-сервер без оверхеда gRPC

📌 Условие задачи

Реализуйте TCP-сервер на gnet, который принимает length-prefixed protobuf-сообщения (Request), парсит через proto.Unmarshal, выполняет RPC-логику, сериализует Response и отправляет обратно. Объясните, как это заменяет gRPC для внутренних высоконагруженных сервисов, и почему gRPC (HTTP/2) имеет больше оверхеда.

💡 Теоретический фундамент и концепция

Фреймворк gRPC является стандартом де-факто для микросервисной коммуникации в современной индустрии. Однако gRPC базируется на протоколе HTTP/2:

  • Каждый RPC-вызов оборачивается в поток HTTP/2 (Stream ID).
  • Сериализуются бинарные кадры HEADERS, DATA, SETTINGS, WINDOW_UPDATE.
  • Применяется алгоритм сжатия заголовков HPACK (требующий поддержания динамической таблицы сжатия в памяти для каждого соединения).
  • Каждое соединение gRPC обслуживается множеством внутренних горутин.

В сверхвысоконагруженных внутренних сценариях (High-Frequency Trading, обработка телеметрии в реальном времени, внутренние брокеры очередей с миллионами RPC в секунду) оверхед HTTP/2 становится неприемлемым.

Альтернатива: Чистый TCP + Length-Prefixed Protobuf поверх gnet

Архитектура прямого бинарного RPC:

[Заголовок 4 байта: uint32 длина Payload]  +  [Protobuf Payload: proto.Marshal(Message)]
1. Нулевой оверхед протокола: Нет HTTP/2 фреймов, нет сжатия HPACK, нет согласования заголовков.
2. Максимальная плотность упаковки: Protobuf кодирует данные в компактном бинарном формате Varint/Wire-Type.
3. Обслуживание в реакторе gnet: Поток реактора читает кадр, десериализует через proto.Unmarshal и отправляет ответ через AsyncWrite без создания горутин на каждый RPC.

🔍 Пошаговый ход решения и ход мысли инженера

1. Определите бинарный формат кадра: 4 байта Big-Endian длины + Protobuf сообщение.
2. В обработчике OnTraffic извлеките полный кадр с помощью c.InboundBuffered() и c.Peek().
3. Вызовите proto.Unmarshal для извлечения полей RPC-запроса.
4. Выполните бизнес-логику и сформируйте ответную структуру Protobuf.
5. Сериализуйте ответ через proto.Marshal и запишите результат в сокет с 4-байтным префиксом длины.

package main

import (
	"encoding/binary"
	"fmt"
	"log"

	"github.com/panjf2000/gnet/v2"
	"google.golang.org/protobuf/proto"
	"google.golang.org/protobuf/types/known/timestamppb"

	// Используем сгенерированный Protobuf пакет (или эмуляцию для демонстрации структуры)
)

// Эмуляция сгенерированных Protobuf структур (для автономности компиляции)
type PingRequest struct {
	ClientTime int64
	Payload    string
}

func (p *PingRequest) Unmarshal(b []byte) error {
	// В реальном коде: proto.Unmarshal(b, p)
	if len(b) < 8 {
		return fmt.Errorf("недостаточно байт для RPC request")
	}
	p.ClientTime = int64(binary.BigEndian.Uint64(b[:8]))
	p.Payload = string(b[8:])
	return nil
}

type PingResponse struct {
	ServerTime int64
	Reply      string
}

func (p *PingResponse) Marshal() []byte {
	// В реальном коде: proto.Marshal(p)
	replyBytes := []byte(p.Reply)
	out := make([]byte, 8+len(replyBytes))
	binary.BigEndian.PutUint64(out[:8], uint64(p.ServerTime))
	copy(out[8:], replyBytes)
	return out
}

type ProtobufRPCServer struct {
	gnet.BuiltinEventEngine
}

func (s *ProtobufRPCServer) OnTraffic(c gnet.Conn) gnet.Action {
	for {
		buffered := c.InboundBuffered()
		if buffered < 4 {
			return gnet.None
		}

		// Читаем 4 байта размера
		header, err := c.Peek(4)
		if err != nil {
			return gnet.Close
		}

		msgLen := int(binary.BigEndian.Uint32(header))
		totalLen := 4 + msgLen

		if buffered < totalLen {
			// Ожидаем полного кадра
			return gnet.None
		}

		fullData, err := c.Peek(totalLen)
		if err != nil {
			return gnet.Close
		}

		protoBytes := fullData[4:totalLen]

		// Десериализация Protobuf сообщения
		var req PingRequest
		if err := req.Unmarshal(protoBytes); err != nil {
			log.Printf("Сбой Protobuf Unmarshal: %v", err)
			return gnet.Close
		}

		// Обработка RPC вызова
		resp := PingResponse{
			ServerTime: timestamppb.Now().Seconds,
			Reply:      "PONG_RPC: " + req.Payload,
		}
		respBytes := resp.Marshal()

		// Формирование исходящего фрейма
		frame := make([]byte, 4+len(respBytes))
		binary.BigEndian.PutUint32(frame[:4], uint32(len(respBytes)))
		copy(frame[4:], respBytes)

		// Отправка ответа
		_ = c.AsyncWrite(frame, nil)

		// Сдвиг буфера
		_, _ = c.Discard(totalLen)
	}
}

func main() {
	server := &ProtobufRPCServer{}
	addr := "tcp://127.0.0.1:9012"

	log.Printf("Запуск ультрабыстрого Protobuf RPC сервера на %s...\n", addr)
	err := gnet.Run(server, addr, gnet.WithMulticore(true))
	if err != nil {
		log.Fatalf("Ошибка запуска: %v", err)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Почему Protobuf поверх gnet быстрее стандартного gRPC в 2–4 раза:

1. Отсутствие HTTP/2 парсера: В gRPC каждое сообщение разбивается на HTTP/2 фреймы DATA с 9-байтным заголовком. При высоких скоростях парсинг заголовков HTTP/2 отнимает значительную часть CPU.
2. Ликвидация HPACK таблицы: Динамическая таблица HPACK требует непрерывной синхронизации состояния между запросами в рамках HTTP/2 соединения. В сыром TCP-протоколе состояние соединения отсутствует (stateless framing).
3. Меньший размер памяти на сокет: gRPC держит в памяти структуры потоков (Streams), буферы управления потоком (Flow Control Windows) и очереди отправки. В gnet сокет потребляет только память кольцевого буфера.
⚠️ Частые грабли и ошибки новичков

Отказываясь от gRPC в пользу сырого Protobuf по TCP, вы теряете встроенные фичи gRPC «из коробки»:

1. Автоматический Client-Side Load Balancing (gRPC Resolver).
2. Распределенный контекст и отмену вызовов (context.Context cancellation / deadlines propagation).
3. Готовые интерцепторы (Interceptors) для метрик, авторизации и трейсинга OpenTelemetry.

Если эти возможности критичны, вам придется реализовывать их вручную.

Упражнение #17

[Правильный дизайн] Worker Pool: Неблокирующий OnTraffic и AsyncWrite

📌 Условие задачи

Перепиши gnet сервер: OnTraffic не должен ничего вычислять. Он должен читать []byte из сокета и кидать их в неблокирующий go channel. Пул горутин (воркеры) читают канал, обрабатывают запрос и отправляют ответ обратно через conn.AsyncWrite(data).

💡 Теоретический фундамент и концепция

В производственных HighLoad-системах паттерн «Неблокирующий OnTraffic + Worker Pool» является ключевым архитектурным решением, позволяющим совместить ультравысокую пропускную способность сетевого ввода-вывода (I/O Bound) и стабильную обработку ресурсоемких вычислений (CPU/DB Bound).

Механика конвейера:
1. Фаза I/O (Сетевой поток Sub-Reactor):

При срабатывании EPOLLIN реактор мгновенно забирает байты из внутреннего кольцевого буфера c.Next(-1). Это занимает доли микросекунды.

2. Фаза передачи (Offload):

Реактор копирует байты в структуру задачи и отправляет ее в ограниченную очередь задач (Bounded Channel или Ring Buffer). Если очередь полна, реактор применяет политику Backpressure (сброс пакета или ответ с ошибкой 429/503), но никогда не блокируется в вызове send.

3. Фаза выполнения (Worker Goroutines):

Пул фоновых воркеров вычитывает задачи из канала, десериализует полезную нагрузку, делает запросы к СУБД/кэшу или проводит вычисления.

4. Фаза ответа (AsyncWrite):

Воркер вызывает метод conn.AsyncWrite(responseData, callback).

Этот метод является строго потокобезопасным: он регистрирует исходящий буфер во внутренней очереди сокета и пробуждает локальный Sub-Reactor через системный вызов eventfd или pipe, гарантируя, что запись в сокет произойдет в правильном потоке без Data Race.

4. Внутри цикла воркера выполните обработку и вызовите c.AsyncWrite(...).
5. Убедитесь в потокобезопасности передачи данных и корректности освобождения памяти.

package main

import (
	"log"
	"runtime"
	"sync/atomic"
	"time"

	"github.com/panjf2000/gnet/v2"
)

// Job инкапсулирует входящий сетевой пакет и дескриптор соединения
type Job struct {
	Conn    gnet.Conn
	Payload []byte
}

type ProductionWorkerServer struct {
	gnet.BuiltinEventEngine
	jobChan    chan Job
	droppedJobs int64
}

func NewProductionWorkerServer(numWorkers int, queueCap int) *ProductionWorkerServer {
	s := &ProductionWorkerServer{
		jobChan: make(chan Job, queueCap),
	}

	// Запуск пула независимых воркеров
	for i := 0; i < numWorkers; i++ {
		go s.worker(i)
	}

	return s
}

func (s *ProductionWorkerServer) worker(workerID int) {
	for job := range s.jobChan {
		// 1. Имитация полезной вычислительной нагрузки
		time.Sleep(5 * time.Millisecond)

		// 2. Формирование ответа
		resp := append([]byte("PROCESSED_OK: "), job.Payload...)

		// 3. Потокобезопасная асинхронная запись в сокет
		err := job.Conn.AsyncWrite(resp, func(c gnet.Conn, err error) error {
			if err != nil {
				log.Printf("[Worker %d] Ошибка AsyncWrite: %v", workerID, err)
			}
			return nil
		})
		if err != nil {
			log.Printf("[Worker %d] Сбой постановки в очередь записи: %v", workerID, err)
		}
	}
}

// OnTraffic исполняется исключительно в потоке Sub-Reactor
func (s *ProductionWorkerServer) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// Обязательное копирование: буфер gnet будет перезаписан следующим сетевым пакетом!
	packetData := make([]byte, len(buf))
	copy(packetData, buf)

	// Неблокирующая передача в очередь воркеров
	select {
	case s.jobChan <- Job{Conn: c, Payload: packetData}:
		return gnet.None
	default:
		// Очередь заполнена — защита от OOM (Backpressure)
		atomic.AddInt64(&s.droppedJobs, 1)
		_ = c.AsyncWrite([]byte("ERR: SERVER_OVERLOADED_BACKPRESSURE\n"), nil)
		return gnet.None
	}
}

func main() {
	workers := runtime.NumCPU() * 4
	server := NewProductionWorkerServer(workers, 20000)
	addr := "tcp://127.0.0.1:9017"

	log.Printf("Запуск сервера с Worker Pool (%d воркеров) на %s...\n", workers, addr)
	err := gnet.Run(server, addr, gnet.WithMulticore(true))
	if err != nil {
		log.Fatalf("Ошибка запуска: %v", err)
	}
}
ℹ️ Эталонная архитектура неблокирующего реактора с пулом воркеров и AsyncWrite
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Что происходит внутри conn.AsyncWrite():

1. AsyncWrite упаковывает байты в буферную очередь структуры conn.
2. Если вызов совершен из потока, отличного от владельца данного Sub-Reactor (например, из горутины-воркера), gnet не может напрямую писать в сокет, так как это нарушило бы потокобезопасность epoll.
3. gnet вызывает системный вызов unix.Write(reactor.eventfd, ...) (Linux eventfd).
4. Поток реактора, спящий в epoll_wait, мгновенно пробуждается по событию eventfd, считывает накопившиеся в очереди задачи и безопасно отправляет их клиенту через write() или writev().
⚠️ Частые грабли и ошибки новичков

Использование небуферизованного или неограниченного канала для передачи задач:

  • Если канал небуферизован (make(chan Job)), сетевой реактор мгновенно зависнет при попытке записи ch <- job, превращаясь в блокирующий сервер!
  • Если канал бесконечен (или вы запускаете go worker(job) на каждый запрос), при всплеске нагрузки сервер создаст сотни тысяч горутин и упадет по OOM (Out Of Memory). Очередь обязана иметь строгий лимит емкости (Bounded Queue) и логику Backpressure.

«Как в Linux устроен механизм eventfd и почему высокопроизводительные сетевые библиотеки используют его вместо каналов Go или мьютексов для межпоточного пробуждения?»

Эталонный ответ:

Системный вызов eventfd(0, EFD_NONBLOCK | EFD_CLOEXEC) создает 64-битный счетчик в ядре Linux, представленный обычным файловым дескриптором.

Главное преимущество eventfd — его можно зарегистрировать в системном вызове epoll_wait наряду с тысячами сетевых TCP-сокетов!

Когда фоновому воркеру нужно разбудить спящий сетевой поток, он делает запись 8 байт write(eventfd, &val, 8). Ядро Linux атомарно увеличивает счетчик и немедленно пробуждает epoll_wait. Это избавляет от необходимости использовать мьютексы, условные переменные (pthread_cond_t) или периодический поллинг таймерами.

Кастомный кодек поверх gnet: Line-based протокол и пакетная обработка

📌 Условие задачи

Реализуйте простой текстовый протокол: сообщения заканчиваются \n. Используйте gnet.Reader/gnet.Writer для буферизации и разбора кадров. Поддержите пакетную обработку нескольких сообщений в одном OnTraffic.

💡 Теоретический фундамент и концепция

Протоколы с разделителями строк (Line-Based Protocols, где каждое сообщение завершается символом \n или \r\n) лежат в основе сотен промышленных стандартов:

  • Текстовый протокол Redis (Inline Commands, например PING\r\n).
  • Протокол Memcached.
  • SMTP / POP3 / IMAP почтовые команды.
  • Логирование и сбор метрик по протоколу StatsD / Syslog.
Проблема склеенных пакетов (Pipelining):

В высоконагруженных сетевых протоколах клиент часто использует Pipelining — отправляет несколько строк подряд в одном TCP-сегменте:

SET user:1 John\nGET user:1\nINCR views\n

Если обработчик OnTraffic разберет только первую команду SET user:1 John\n и выйдет из функции, остальные две команды останутся лежать в кольцевом буфере до тех пор, пока клиент не пришлет еще один пакет данных. Возникнет искусственная задержка (Stall / Pipeline Lag).

Пакетная обработка (Batch Processing):

Обработчик OnTraffic обязан запускать цикл обработки строк for { ... }, сканируя кольцевой буфер на наличие символа перевода строки \n (bytes.IndexByte(buf, '\n')), исполняя все накопившиеся команды за один вызов реактора и возвращая сдвиг кольца через c.Discard().

🔍 Пошаговый ход решения и ход мысли инженера

1. В методе OnTraffic организуйте бесконечный цикл парсинга строк.
2. Используйте c.InboundBuffered() и c.Peek(...) для поиска разделителя \n.
3. Если символ \n не найден, выйдите из цикла (ждем досылки остатка строки).
4. Извлеките срез строки, удалите символы \r и \n и передайте на исполнение.
5. Сдвиньте указатель кольцевого буфера на размер строки плюс 1 байт (\n).

package main

import (
	"bytes"
	"fmt"
	"log"

	"github.com/panjf2000/gnet/v2"
)

type LineProtocolServer struct {
	gnet.BuiltinEventEngine
}

func (s *LineProtocolServer) OnTraffic(c gnet.Conn) gnet.Action {
	// Пакетная обработка всех строк, поступивших в сокет
	for {
		buffered := c.InboundBuffered()
		if buffered == 0 {
			return gnet.None
		}

		// Заглядываем во весь доступный буфер чтения
		buf, err := c.Peek(buffered)
		if err != nil {
			return gnet.Close
		}

		// Ищем индекс символа новой строки \n
		newlineIdx := bytes.IndexByte(buf, '\n')
		if newlineIdx == -1 {
			// Строка еще не получена целиком — ждем следующего OnTraffic
			return gnet.None
		}

		// Выделяем полную строку (включая символ \n)
		lineWithDelim := buf[:newlineIdx+1]
		// Очищаем от \r и \n для бизнес-логики
		cleanLine := bytes.TrimRight(lineWithDelim, "\r\n")

		// Обработка текстовой команды
		s.handleCommandLine(c, cleanLine)

		// Сдвигаем кольцевой буфер на точный размер обработанной строки
		if _, err := c.Discard(len(lineWithDelim)); err != nil {
			return gnet.Close
		}
	}
}

func (s *LineProtocolServer) handleCommandLine(c gnet.Conn, cmd []byte) {
	if len(cmd) == 0 {
		return
	}

	strCmd := string(cmd)
	var response string

	switch strCmd {
	case "PING":
		response = "+PONG\r\n"
	case "TIME":
		response = fmt.Sprintf("+TIME 1700000000\r\n")
	case "QUIT":
		_ = c.AsyncWrite([]byte("+OK Bye\r\n"), func(c gnet.Conn, err error) error {
			return c.Close()
		})
		return
	default:
		response = fmt.Sprintf("-ERR Unknown command '%s'\r\n", strCmd)
	}

	_ = c.AsyncWrite([]byte(response), nil)
}

func main() {
	server := &LineProtocolServer{}
	addr := "tcp://127.0.0.1:9018"

	log.Printf("Запуск Line-based протокол сервера на %s...\n", addr)
	fmt.Println("Тестируйте с помощью nc / telnet: nc 127.0.0.1 9018")

	err := gnet.Run(server, addr, gnet.WithMulticore(true))
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}

Она проверяет совпадение сразу 32 байт за один процессорный такт. Поиск символа \n в буфере размером 4 КБ занимает всего 10–15 наносекунд.

Атака Slowloris на строковый протокол:

Если недобросовестный клиент отправляет 1 байт в 10 секунд и никогда не присылает символ \n, буфер c.InboundBuffered() будет непрерывно расти. Вопрос на собеседовании (Senior Backend / Infrastructure):

«Что такое TCP Pipelining и чем он отличается от мультиплексирования HTTP/2?»

Эталонный ответ:

  • TCP Pipelining (HTTP/1.1 Pipelining, Redis Pipelining): Клиент отправляет несколько запросов подряд в один сокет, не дожидаясь ответа на первый запрос. Однако сервер обязан возвращать ответы строго в том же порядке, в каком поступили запросы (FIFO). Если первый запрос тяжелый (Head-of-Line Blocking), все последующие ответы блокируются.
  • HTTP/2 Multiplexing: Запросы разбиваются на независимые бинарные кадры с уникальным идентификатором потока (Stream ID). Сервер может обрабатывать запросы асинхронно и отдавать фрагменты ответов в произвольном порядке, ликвидируя прикладной Head-of-Line Blocking.

Graceful Shutdown в gnet: Остановка сокетов, дренаж соединений и sync.WaitGroup

📌 Условие задачи

Реализуйте обработку SIGTERM: Stop() останавливает accept, дожидается завершения OnTraffic для текущих соединений (через sync.WaitGroup), затем закрывает все fd. Объясните, почему gnet требует ручного управления lifecycle, в отличие от http.Server.Shutdown.

💡 Теоретический фундамент и концепция

В микросервисной архитектуре под управлением Kubernetes поды непрерывно перезапускаются в ходе деплоев, Rolling Updates и автомасштабирования (HPA).

Когда pod получает сигнал SIGTERM, приложение обязано корректно завершить работу (Graceful Shutdown):

1. Перестать принимать новые входящие TCP-соединения (close(listen_fd)).
2. Дать активным сетевым запросам время на завершение (дренаж соединений).
3. Дождаться окончания фоновых задач в Worker Pool.
4. Закрыть открытые сокеты с отправкой клиентам корректного FIN-пакета (без аварийного сброса TCP RST).
Разница с http.Server.Shutdown:

В стандартном net/http метод srv.Shutdown(ctx) инкапсулирует всю механику: закрывает слушатель, переводит сокеты в статус idle и ждет завершения горутин.

В gnet жизненным циклом управляет сам разработчик:

  • Функция gnet.Stop(ctx, addr) останавливает слушающие сокеты и прерывает циклы epoll_wait.
  • Задачи, переданные в Worker Pool, должны отслеживаться через sync.WaitGroup.
  • При вызове shutdown необходимо установить флаг состояния сервера (Atomic Flag), отклоняя новые входящие запросы.

🔍 Пошаговый ход решения и ход мысли инженера

1. Инициализируйте перехват системных сигналов os.Interrupt, syscall.SIGTERM через signal.Notify.
2. Используйте sync.WaitGroup для учета всех in-flight сетевых задач.
3. При получении сигнала вызовите gnet.Stop(context.Background(), addr).
4. Дождитесь завершения всех активных воркеров через wg.Wait() с заданным таймаутом.
5. Завершите процесс с кодом возврата 0.
📄 graceful_server.go 
package main

import (
	"context"
	"log"
	"os"
	"os/signal"
	"sync"
	"sync/atomic"
	"syscall"
	"time"

	"github.com/panjf2000/gnet/v2"
)

type GracefulServer struct {
	gnet.BuiltinEventEngine
	addr       string
	inShutdown int32
	inflightWg sync.WaitGroup
}

func (s *GracefulServer) OnTraffic(c gnet.Conn) gnet.Action {
	// Проверяем, не находится ли сервер в фазе остановки
	if atomic.LoadInt32(&s.inShutdown) == 1 {
		_ = c.AsyncWrite([]byte("ERR: SERVER_SHUTTING_DOWN\n"), func(c gnet.Conn, err error) error {
			return c.Close()
		})
		return gnet.None
	}

	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// Увеличиваем счетчик активных задач
	s.inflightWg.Add(1)
	taskData := append([]byte(nil), buf...)

	// Передаем задачу в фоновую обработку
	go func(conn gnet.Conn, data []byte) {
		defer s.inflightWg.Done()

		// Имитация полезной работы
		time.Sleep(100 * time.Millisecond)

		_ = conn.AsyncWrite(append([]byte("ACK: "), data...), nil)
	}(c, taskData)

	return gnet.None
}

func main() {
	serverAddr := "tcp://127.0.0.1:9019"
	server := &GracefulServer{addr: serverAddr}

	// Канал системных сигналов ОС
	sigChan := make(chan os.Signal, 1)
	signal.Notify(sigChan, syscall.SIGINT, syscall.SIGTERM)

	go func() {
		sig := <-sigChan
		log.Printf("[SHUTDOWN] Получен сигнал %v. Инициализация Graceful Shutdown...\n", sig)

		// 1. Устанавливаем флаг отключения
		atomic.StoreInt32(&server.inShutdown, 1)

		// 2. Останавливаем движок gnet (перестает принимать новые подключения)
		shutdownCtx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
		defer cancel()

		if err := gnet.Stop(shutdownCtx, serverAddr); err != nil {
			log.Printf("[SHUTDOWN] Ошибка gnet.Stop: %v\n", err)
		}

		// 3. Ждем завершения всех in-flight задач воркеров
		log.Println("[SHUTDOWN] Ожидание завершения текущих задач...")
		done := make(chan struct{})
		go func() {
			server.inflightWg.Wait()
			close(done)
		}()

		select {
		case <-done:
			log.Println("[SHUTDOWN] Все задачи успешно завершены. Выход.")
		case <-time.After(4 * time.Second):
			log.Println("[SHUTDOWN] Истек таймаут дренажа задач. Принудительный выход.")
		}

		os.Exit(0)
	}()

	log.Printf("Сервер запущен на %s. Для остановки нажмите Ctrl+C.\n", serverAddr)
	if err := gnet.Run(server, serverAddr, gnet.WithMulticore(true)); err != nil {
		log.Printf("Работа сервера завершена: %v\n", err)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Когда вызывается gnet.Stop(ctx, addr):

1. Движок gnet закрывает слушающие файловые дескрипторы сокетов (listen_fd), поэтому ядро Linux немедленно прекращает отвечать SYN-ACK на новые запросы клиентов.
2. gnet отправляет внутреннее прерывание во все Sub-Reactors через eventfd.
3. Потоки реакторов завершают последний цикл обработки активных событий epoll_wait, закрывают клиентские файловые дескрипторы и выходят из системного вызова.

Использование os.Exit(0) сразу при получении сигнала SIGTERM. Это грубая ошибка, которая приводит к моментальному закрытию TCP-сокетов с флагом RST. Клиенты получают ошибку Connection reset by peer, их сетевые запросы падают с кодом 502/504, а в микросервисной сети возникают ложные алерты.

Вопрос на собеседовании (DevSecOps / Cloud Platform Lead):

«Как в Kubernetes устроен жизненный цикл завершения Pod (Terminating Phase) и почему правильный Graceful Shutdown требует паузы (preStop hook) перед закрытием сокетов?»

Эталонный ответ:

1. Kubelet посылает контейнеру сигнал SIGTERM.
2. Kube-proxy / CNI исключает IP-адрес пода из таблицы маршрутизации EndpointSlice / iptables / IPVS.

Библиотека github.com/panjf2000/gnet/v2 — это высокопроизводительный, легковесный, событийно-ориентированный сетевой фреймворк для Go, разработанный как прямая замена стандартному сетевому стеку в задачах с экстремальной нагрузкой.

Ключевые архитектурные новшества gnet/v2:

  • Linux: epoll с режимами Edge-Triggered / Level-Triggered.
  • macOS / FreeBSD / OpenBSD: kqueue.
  • Windows: Реактор на базе механизма poll/WSAEventSelect (для локальной разработки).
4. Встроенный балансировщик нагрузки сокетов (Load Balancer):

Main Reactor распределяет новые подключения между Sub-Reactors по одной из стратегий:

  • RoundRobin: Циклическое распределение.
  • LeastConnections: Отправка сокета наименее загруженному реактору.
  • SourceAddrHash: Хеширование IP-адреса клиента для поддержания аффинности сессий.

Метод c.Fd() возвращает числовой дескриптор файла сокета ОС. Категорически запрещено вызывать стандартные функции закрытия (unix.Close(c.Fd())) или менять флаги сокета напрямую без уведомления gnet. Если дескриптор будет закрыт в обход gnet, в epoll останется «висячая» ссылка (Dangling FD), что приведет к ошибкам EBADF при следующем системном вызове!

Вопрос на собеседовании (HighLoad Go Developer):

«Зачем в сетевых приложениях отключать алгоритм Нагла опцией TCP_NODELAY, и когда его отключение может навредить?»

Эталонный ответ:

  • Что делает алгоритм Нагла (Nagle's Algorithm): Он объединяет несколько мелких исходящих сообщений в один крупный TCP-пакет, задерживая отправку до тех пор, пока от клиента не придет подтверждение (TCP ACK) на предыдущий сегмент.

  • Когда отключение может навредить: Если приложение делает тысячи вызовов write() размером по 2–5 байт, отключение Нагла приведет к генерации огромного количества микропакетов (40 байт TCP/IP заголовков на 2 байта данных), перегружая коммутаторы и сетевые каналы.

package main

import (
	"fmt"
	"syscall"

	"golang.org/x/sys/unix"
)

// LinuxEpollPoller реализует мультиплексирование на базе системных вызовов Linux epoll
type LinuxEpollPoller struct {
	epfd   int
	events []unix.EpollEvent
}

func NewPoller() (Poller, error) {
	epfd, err := unix.EpollCreate1(unix.EPOLL_CLOEXEC)
	if err != nil {
		return nil, fmt.Errorf("epoll_create1: %w", err)
	}
	return &LinuxEpollPoller{
		epfd:   epfd,
		events: make([]unix.EpollEvent, 128),
	}, nil
}

func (p *LinuxEpollPoller) AddRead(fd int) error {
	ev := &unix.EpollEvent{
		Events: unix.EPOLLIN,
		Fd:     int32(fd),
	}
	return unix.EpollCtl(p.epfd, unix.EPOLL_CTL_ADD, fd, ev)
}

func (p *LinuxEpollPoller) Delete(fd int) error {
	return unix.EpollCtl(p.epfd, unix.EPOLL_CTL_DEL, fd, nil)
}

func (p *LinuxEpollPoller) Polling(onEvent func(fd int) error) error {
	for {
		n, err := unix.EpollWait(p.epfd, p.events, -1)
		if err != nil {
			if err == syscall.EINTR {
				continue
			}
			return err
		}

		for i := 0; i < n; i++ {
			fd := int(p.events[i].Fd)
			if err := onEvent(fd); err != nil {
				// Ошибка обработки
			}
		}
	}
}

func (p *LinuxEpollPoller) Close() error {
	return unix.Close(p.epfd)
}

Почему epoll на Linux быстрее kqueue на macOS при больших объемах:

Упражнение #22

[Custom Codec] Framing в потоковом TCP: Машина состояний неполных кадров

📌 Условие задачи

TCP потоковый. Напиши свой парсер кадров (Framing) в OnTraffic. Протокол: 4 байта длины (Big Endian) + Payload. Если в буфере меньше 4 байт или длина Payload не совпадает — подожди следующий OnTraffic вызов.

💡 Теоретический фундамент и концепция

При разработке сетевых приложений новички часто совершают фундаментальную ошибку: предполагают, что один вызов conn.Write(msg) на клиенте приведет ровно к одному вызову OnTraffic на сервере с точно таким же размером данных.

В реальной сети TCP:

1. Фрагментация (Segmentation): Кадр размером 10 КБ может быть разбит на 7 мелких TCP-сегментов по размеру MTU (1500 байт). В OnTraffic сначала приедут первые 1460 байт, затем 1460 байт и так далее.
2. Склейка (Coalescing): Десять маленьких сообщений по 50 байт, отправленных подряд, склеятся сетевой картой в один буфер размером 500 байт.
Машина состояний кадрирования (Framing State Machine):

Для 100% надежного разбора потока байтов в условиях произвольной фрагментации обработчик OnTraffic должен реализовывать строгую конечную машину состояний:

                ┌──────────────────────────────────┐
                ▼                                  │
    [Ожидание 4 байт длины]                        │
                │                                  │
    Buffered >= 4 ?                                │
           ├── НЕТ ──► return gnet.None            │
           └── ДА  ──► Peek(4) -> Читаем Length L  │
                            │                      │
                [Ожидание Payload длины L]         │
                            │                      │
                Buffered >= 4 + L ?                │
                       ├── НЕТ ──► return gnet.None│
                       └── ДА  ──► Извлекаем кадр ─┘
                                   c.Discard(4 + L)

🔍 Пошаговый ход решения и ход мысли инженера

1. Реализуйте обработчик OnTraffic с конечным автоматом состояний.
2. Проверьте, содержит ли входной буфер минимум 4 байта заголовка длины.
3. Раскодируйте размер полезной нагрузки payloadLen.
4. Если InboundBuffered() < 4 + payloadLen, верните gnet.None без сдвига буфера.
5. Если полный кадр накопился, извлеките его, обработайте и сдвиньте буфер вызовом c.Discard.
📄 framer_server.go 
package main

import (
	"encoding/binary"
	"fmt"
	"log"

	"github.com/panjf2000/gnet/v2"
)

const (
	HeaderSize   = 4
	MaxFrameSize = 10 * 1024 * 1024 // Защита: не более 10 МБ на один кадр
)

type RobustFramerServer struct {
	gnet.BuiltinEventEngine
}

func (s *RobustFramerServer) OnTraffic(c gnet.Conn) gnet.Action {
	// Обрабатываем все завершенные кадры, которые успели накопиться в буфере
	for {
		buffered := c.InboundBuffered()

		// Шаг 1: Проверка наличия заголовка длины
		if buffered < HeaderSize {
			// Данных меньше 4 байт: заголовок фрагментирован.
			// Возвращаем None — реактор позовет нас снова, когда ядро дошлет байты!
			return gnet.None
		}

		// Шаг 2: Читаем длину без извлечения (Peek)
		header, err := c.Peek(HeaderSize)
		if err != nil {
			return gnet.Close
		}

		payloadSize := binary.BigEndian.Uint32(header)

		// Защита от DoS-атак переполнения буфера
		if payloadSize > MaxFrameSize {
			log.Printf("[SECURITY] Превышен максимальный размер кадра: %d байт. Разрыв соединения!\n", payloadSize)
			return gnet.Close
		}

		totalFrameSize := HeaderSize + int(payloadSize)

		// Шаг 3: Проверка накопления полного тела кадра
		if buffered < totalFrameSize {
			// Тело кадра еще фрагментировано (доехало лишь частично).
			// Ждем следующий вызов OnTraffic!
			return gnet.None
		}

		// Шаг 4: Полный кадр гарантированно собран в кольцевом буфере!
		frameData, err := c.Peek(totalFrameSize)
		if err != nil {
			return gnet.Close
		}

		payload := frameData[HeaderSize:totalFrameSize]
		// Исполнение бизнес-логики над полным кадром
		s.processMessage(c, payload)

		// Шаг 5: Сдвиг указателя кольцевого буфера
		if _, err := c.Discard(totalFrameSize); err != nil {
			return gnet.Close
		}
	}
}

func (s *RobustFramerServer) processMessage(c gnet.Conn, payload []byte) {
	// Эхо-ответ с префиксом длины
	respPayload := append([]byte("PROCESSED: "), payload...)
	resp := make([]byte, HeaderSize+len(respPayload))
	binary.BigEndian.PutUint32(resp[:HeaderSize], uint32(len(respPayload)))
	copy(resp[HeaderSize:], respPayload)

	_ = c.AsyncWrite(resp, nil)
}

func main() {
	server := &RobustFramerServer{}
	addr := "tcp://127.0.0.1:9022"

	log.Printf("Запуск сервера с надежным TCP-кадрированием на %s...\n", addr)
	err := gnet.Run(server, addr, gnet.WithMulticore(true))
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}

Когда приложение вызывает c.Peek(n), gnet возвращает срез на непрерывную область памяти внутреннего кольцевого буфера. Если данные кадра пересекают физический конец буфера (wrap-around), gnet копирует этот фрагмент во временный кольцевой кэш, возвращая сплошной срез.

Если полный кадр еще не поступил, возврат gnet.None сообщает реактору оставить дескриптор в epoll. При поступлении следующего сетевого пакета ядро дописывает байты в конец кольца, и повторный вызов Peek() успешно считывает весь кадр.

Попытка вызвать c.Discard() до завершения обработки полезной нагрузки payload.

🏢 В продакшене BigTech и на собеседованиях

Вопрос на собеседовании (Principal Network Architect):

«Что такое Nagle's Algorithm + Delayed ACK interaction (deadlock Нагла), и как протоколы кадрирования могут случайно активировать эту 200-миллисекундную задержку?»

Эталонный ответ:

Если клиент отправляет сначала заголовок кадра (4 байта) отдельным вызовом write(), а затем тело кадра (1 КБ) вторым вызовом write():

1. Алгоритм Нагла отправляет первые 4 байта, но задерживает отправку тела, ожидая подтверждения (ACK) на первый сегмент.
2. Сервер, получив 4 байта заголовка, ждет тело сообщения и не отправляет ответ. Сетевой стек сервера откладывает отправку чистого TCP ACK в надежде объединить его с ответом приложения (Delayed ACK, таймаут ядра Linux от 40 до 200 мс).
3. Возникает взаимное ожидание (Deadlock) на 200 мс!

Решение: всегда объединять заголовок и тело в один буфер перед вызовом write() либо использовать writev().

	}

	data, err := c.Peek(buffered)
	if err != nil {
		return gnet.Close
	}

	// Проверяем окончание заголовков HTTP-запроса
	idx := bytes.Index(data, crlfHeaderEnd)
	if idx == -1 {
		return gnet.None
	}

	// Сдвигаем входящий буфер
	_, _ = c.Discard(idx + len(crlfHeaderEnd))

	// Берем буфер из пула
	bufPtr := httpBufPool.Get().(*[]byte)
	buf := (*bufPtr)[:0]

	// 1. Статус и Content-Length без аллокаций
	buf = append(buf, httpHeaderStatus...)
	buf = strconv.AppendInt(buf, int64(len(responseBody)), 10)

	// 2. Заголовок Date (RFC1123) прямо в буфер
	buf = append(buf, httpHeaderDate...)
	buf = time.Now().AppendFormat(buf, time.RFC1123)

	// 3. Тело ответа
	buf = append(buf, httpHeaderBodySep...)
	buf = append(buf, responseBody...)

	// Отправка в сокет
	_, _ = c.Write(buf)

	// Возврат буфера в пул
	*bufPtr = buf
	httpBufPool.Put(bufPtr)

	return gnet.None
}

func main() {
	server := &FastHTTPPoolServer{}
	addr := "tcp://127.0.0.1:8082"

	log.Printf("Запуск Zero-Allocation HTTP сервера на %s...\n", addr)
	err := gnet.Run(server, addr, gnet.WithMulticore(true))
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

В функции FastHTTPPoolServer.OnTraffic не происходит ни одного вызова runtime.newobject или runtime.makeslice:

1. sync.Pool возвращает указатель *[]byte, ссылающийся на уже существующий непрерывный массив в памяти.
2. strconv.AppendInt(buf, n, 10) работает прямо со срезом байтов, деля число на 10 и заполняя символы цифр с конца без создания временной строки string.
3. time.Now().AppendFormat(buf, ...) форматирует дату прямо в переданный срез.

В результате нагрузка на Garbage Collector сводится к абсолютному нулю, позволяя обрабатывать миллионы HTTP-запросов с минимальной дисперсией задержки.

⚠️ Частые грабли и ошибки новичков

Если размер сформированного HTTP-ответа превысит исходную емкость буфера из пула (cap(buf) = 4096), вызов append() аллоцирует новый массив большего размера. Помещение такого разросшегося буфера обратно в пул может привести к постепенному раздуванию пула памяти (Pool Memory Bloat). Рекомендуется сбрасывать буфер, если его емкость превысила лимит: if cap(buf) > MaxPoolBufCap { /* не возвращаем в пул */ }.

🏢 В продакшене BigTech и на собеседованиях

Вопрос на собеседовании (HighLoad Go Specialist):

«Как sync.Pool взаимодействует со сборщиком мусора Go, и почему данные из sync.Pool могут неожиданно исчезнуть?»

Эталонный ответ:

В рантайме Go структуры sync.Pool очищаются сборщиком мусора. До версии Go 1.13 пул полностью очищался при каждом цикле GC.

Начиная с Go 1.13, механизм оптимизирован через двухфазную модель (victim cache):

  • При наступлении GC объекты из первичного пула переносятся в резервный пул (Victim Cache), а старый Victim Cache очищается.
  • Если объект не был востребован в течение двух полных циклов GC, он освобождается.

Это сглаживает просадки производительности (Cold Cache Spikes), но разработчик обязан помнить: sync.Pool — это не постоянный кэш, любой объект из него может быть удален в любой момент.

Паттерн Multi-Reactor: Архитектура Main Reactor и Sub-Reactors в gnet

📌 Условие задачи

В отличие от горутин, gnet запускает ровно столько потоков, сколько ядер у твоего CPU (Event Loops). Главный реактор (Main Reactor) принимает соединения (Accept), а Sub-реакторы слушают события Read/Write и вызывают твои коллбеки (OnTraffic). Запусти свой сервер с флагом Multicore: true.

💡 Теоретический фундамент и концепция

Архитектурный паттерн Multi-Reactor (также известный как Master-Worker Reactor) является стандартом де-факто в мировой индустрии высокопроизводительных серверов (Nginx, Netty, Envoy, Node.js cluster, gnet).

Внутреннее разделение ролей:
                      [ Сетевые клиенты (TCP Connect) ]
                                      │
                                      ▼
                      ┌───────────────────────────────┐
                      │  Main Reactor (Acceptor Loop) │
                      │       - epoll_wait            │
                      │       - accept4(listen_fd)    │
                      └───────────────┬───────────────┘
                                      │ (Round-Robin / Least-Conns)
              ┌───────────────────────┼───────────────────────┐
              ▼                       ▼                       ▼
    ┌──────────────────┐    ┌──────────────────┐    ┌──────────────────┐
    │  Sub-Reactor 0   │    │  Sub-Reactor 1   │    │  Sub-Reactor 2   │
    │  - epoll 0       │    │  - epoll 1       │    │  - epoll 2       │
    │  - Sockets: 0..K │    │  - Sockets: 0..K │    │  - Sockets: 0..K │
    │  - OnTraffic()   │    │  - OnTraffic()   │    │  - OnTraffic()   │
    └──────────────────┘    └──────────────────┘    └──────────────────┘
1. Главный реактор (Main Reactor / Acceptor):
  • Выполняет ровно одну задачу: непрерывно ожидает события готовности слушающего сокета (EPOLLIN на listen_fd) и вызывает системный вызов accept4().
  • Получив новый дескриптор client_fd, Main Reactor не читает из него данные! Он выбирает один из дочерних Sub-реакторов по заданному алгоритму балансировки (Load Balancer) и регистрирует дескриптор в epoll выбранного Sub-реактора.
2. Дочерние реакторы (Sub-Reactors / Worker Loops):
  • Число дочерних реакторов строго равно числу процессорных ядер (NumCPU).
  • Каждый Sub-Reactor имеет собственный независимый инстанс epoll.
  • При появлении данных в сокете Sub-Reactor считывает байты и вызывает пользовательский обработчик OnTraffic().

Преимущество: полное отсутствие взаимных блокировок между процессами accept() и передачей данных, а также равномерная утилизация всех ядер CPU.

🔍 Пошаговый ход решения и ход мысли инженера

1. Инициализируйте gnet с опцией gnet.WithMulticore(true).
2. Задайте алгоритм балансировки между Sub-реакторами gnet.WithLoadBalancing(gnet.RoundRobin).
3. В обработчике OnOpen выведите идентификатор соединения и адрес клиента.
4. Запустите сервер и убедитесь через pidstat -t -p <PID>, что создано ровно $N$ потоков, равномерно нагружающих процессор.

package main

import (
	"fmt"
	"log"
	"runtime"
	"sync/atomic"

	"github.com/panjf2000/gnet/v2"
)

type MultiReactorEngine struct {
	gnet.BuiltinEventEngine
	totalConns int64
}

func (e *MultiReactorEngine) OnBoot(eng gnet.Engine) gnet.Action {
	log.Printf("[Multi-Reactor] Инициализирован Главный Реактор (Main Reactor) и %d Sub-Реакторов\n",
		runtime.NumCPU())
	return gnet.None
}

func (e *MultiReactorEngine) OnOpen(c gnet.Conn) (out []byte, action gnet.Action) {
	connID := atomic.AddInt64(&e.totalConns, 1)
	if connID%1000 == 0 {
		log.Printf("[Main Reactor] Принято %d соединений. Клиент %s привязан к Sub-Reactor\n",
			connID, c.RemoteAddr())
	}
	return nil, gnet.None
}

func (e *MultiReactorEngine) OnTraffic(c gnet.Conn) gnet.Action {
	// Исполняется локальным Sub-Reactor
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// Отправляем эхо-ответ
	_, _ = c.Write(buf)
	return gnet.None
}

func main() {
	engine := &MultiReactorEngine{}
	addr := "tcp://127.0.0.1:9025"

	fmt.Printf("Запуск сервера Multi-Reactor на %s (Ядер CPU: %d)...\n", addr, runtime.NumCPU())

	err := gnet.Run(
		engine,
		addr,
		gnet.WithMulticore(true),
		gnet.WithLoadBalancing(gnet.RoundRobin),
		gnet.WithTCPNoDelay(gnet.TCPNoDelay),
	)
	if err != nil {
		log.Fatalf("Ошибка запуска: %v", err)
	}
}
ℹ️ Паттерн Multi-Reactor с распределением соединений по алгоритму Round-Robin
⚙️ Под капотом Go (Compiler, Linker & Runtime)

В исходном коде gnet при WithMulticore(true) создается структура engine:

1. Создается массив структур subEventLoop размером NumEventLoop.
2. Каждый subEventLoop в конструкторе вызывает unix.EpollCreate1(0) и запускает отдельную горутину, привязанную к потоку ОС (runtime.LockOSThread()).
3. Слушающий сокет listener регистрируется в отдельном mainLoop. Когда mainLoop принимает клиентский сокет fd через accept4, он вызывает lb.register(c), который добавляет fd в epoll соответствующего subEventLoop с помощью системного вызова epoll_ctl(sub_epfd, EPOLL_CTL_ADD, fd, &ev).
⚠️ Частые грабли и ошибки новичков

Если один из клиентов отправляет непрерывный поток данных гигантского объема (например, заливает файл 10 ГБ по TCP со скоростью 10 Gbps), соответствующий Sub-Reactor будет непрерывно загружен обработкой его пакетов, что приведет к задержке обработки других клиентов, оказавшихся на этом же Sub-Reactor. В промышленных системах для защиты применяют квоты на объем вычитывания байт за одну итерацию (Rate Limiting per Connection / Fair Dispatch).

🏢 В продакшене BigTech и на собеседованиях

Вопрос на собеседовании (Staff Engineer / Distributed Systems):

«В чем разница между архитектурой Nginx (Process-per-Core + SO_REUSEPORT) и Netty/gnet (Multi-Reactor с потоками в одном адресном пространстве)?»

Эталонный ответ:

  • Nginx (Multi-Process): Архитектура с независимыми процессами (Master + N Workers). Процессы изолированы на уровне виртуальной памяти: если один воркер упадет с Segfault, остальные продолжат работу. Однако межпроцессный обмен (IPC / Shared Memory) сложен и требует мьютексов в разделяемой памяти (shm).
  • Netty / gnet (Multi-Threaded): Все реакторы работают в едином адресном пространстве одного процесса. Это дает мгновенный обмен данными через указатели без копирования (Zero-Copy IPC), общие пулы памяти (sync.Pool) и простоту управления состоянием, но требует строгой потокобезопасности.

[Highload Benchmarking] Нагрузочное тестирование с wrk: Почему gnet быстрее net/http в 3-5 раз

📌 Условие задачи

Используй утилиту wrk (wrk -c10000 -d10s ...). Сравни gnet Echo сервер (с 1 Event Loop) и net/http (с Go планировщиком) по RPS и Latency. Оцени, почему gnet выигрывает в 3-5 раз по RPS на echo-задачах.

💡 Теоретический фундамент и концепция

При тестировании пропускной способности (Throughput) сетевых серверов утилита wrk (wrk -c 10000 -t 8 -d 10s) является золотым отраслевым стандартом благодаря использованию собственного event-loop на базе epoll внутри генератора нагрузки.

Эксперимент:

Мы сравниваем два сервера под нагрузкой 10 000 соединений:

1. gnet с 1 Event Loop.
2. net/http стандартной библиотеки Go с пулом горутин планировщика GMP.
Почему gnet побеждает с 3–5-кратным отрывом:
1. Отсутствие планирования горутин: В net/http планировщик непрерывно перебирает очереди p.runq, выполняет work stealing и инициирует системные вызовы переключения контекста futex при пробуждении спящих потоков M. В gnet поток крутит непрерывный цикл epoll_wait -> user callback без единого вызова планировщика Go.
2. Локальность кэша инструкций (I-Cache) и данных (D-Cache): Поскольку один и тот же цикл непрерывно обрабатывает однотипные пакеты в одном потоке, код обработчика всегда находится в кэше первого уровня L1i (32 КБ), а структуры — в L1d.
3. Отсутствие аллокаций структур запроса: В gnet не создаются объекты http.Request, парсеры Cookie, формы и заголовки, экономя такты CPU.

На фоне 10 миллисекунд ожидания базы данных оверхед сетевого стека Go в 5 микросекунд составляет всего 0.05% от времени транзакции! Поэтому переходить на gnet имеет смысл только там, где сам бэкенд не завязан на медленный внешний I/O.

Сравнительный анализ трех технологий:
1. Standard net (Go Standard Library):
  • *Архитектура:* Блокирующий API с рантайм-мультиплексированием через netpoller и моделью goroutine-per-connection.
  • *Плюсы:* Идеальный Developer Experience, полная поддержка всей экосистемы Go (context, io.Reader, http.Handler, pprof), потокобезопасность «из коробки», предельная простота сопровождения.
  • *Минусы:* Высокое потребление памяти под стеки горутин при сотнях тысяч соединений, оверхед переключения контекста GMP.
  • *Сфера применения:* 95% типичных бэкенд-сервисов, REST API, микросервисы с базами данных.
2. evio (Minimalist Reactor):
  • *Архитектура:* Упрощенный реактор на базе epoll/kqueue с коллбэк-интерфейсом events.Data(in) -> out.
  • *Плюсы:* Предельно компактная кодовая база, минималистичный API, низкое потребление RAM.
  • *Минусы:* Отсутствие встроенного эластичного кольцевого буфера, риск повреждения памяти при передаче срезов в горутины, отсутствие промышленной поддержки.
  • *Сфера применения:* Простые встраиваемые сетевые утилиты, быстрые прототипы.
3. gnet (Production Enterprise Multi-Reactor):
  • *Архитектура:* Полноценный Multi-Reactor (Main/Sub), кольцевые буферы RingBuffer, встроенные кодеки, пулы памяти, AsyncWrite, поддержка SO_REUSEPORT и epoll/kqueue/io_uring.
  • *Плюсы:* Максимально возможная производительность в Go (миллионы RPS), плоское потребление памяти при 1M соединений, минимальные задержки p99.
  • *Минусы:* Повышенная сложность разработки, необходимость ручного управления буферами и Worker Pools, высокий порог входа.
  • *Сфера применения:* HFT-шлюзы, IoT брокеры, прокси-серверы, брокеры сообщений (Kafka/NATS аналоги), push-гейтвеи.

Упражнение #28

Zero-Copy в сети: Парсинг протокола Redis RESP без аллокаций памяти

📌 Условие задачи

В gnet данные в OnTraffic приходят как срез байт c.Next(-1). Эти байты лежат прямо во внутреннем кольцевом буфере сети. Напиши логику, которая парсит эти байты (например, Redis-протокол RESP), не копируя их в новые переменные (используй unsafe.String, если нужно).

💡 Теоретический фундамент и концепция

Протокол RESP (REdis Serialization Protocol) лежит в основе сервера Redis и широко используется во внутренних кэширующих системах.

Формат команды Redis RESP (массив строк):

*3\r\n        <-- Массив из 3 элементов
$3\r\nSET\r\n <-- Строка из 3 байт "SET"
$4\r\nuser\r\n<-- Строка из 4 байт "user"
$4\r\nJohn\r\n<-- Строка из 4 байт "John"
Проблема традиционного парсинга в Go:

Традиционный парсер преобразует байты в строки: cmd := string(buf).

В языке Go преобразование среза байт в строку string([]byte) всегда приводит к аллокации памяти в куче и вызову функции runtime.slicebytetostring, поскольку строки в Go неизменяемы (immutable), а слайс байт может быть изменен в любой момент!

При миллионе команд в секунду такой парсер сгенерирует сотни мегабайт мусора.

Революция Zero-Copy в gnet:
1. Метод c.Next(-1) возвращает байты, которые уже лежат в кольцевом буфере реактора.
2. Для чтения строковых команд мы используем функцию unsafe.String(&buf[0], len(buf)) (доступную начиная с Go 1.20) либо байтовые срезы напрямую.
3. Команда и аргументы валидируются с помощью побайтового сравнения bytes.Equal() без единой аллокации!

🔍 Пошаговый ход решения и ход мысли инженера

1. Изучите спецификацию формата RESP (префиксы *, $, +, -, :).
2. В обработчике OnTraffic получите срез байтов c.Next(-1).
3. Реализуйте Zero-Copy парсер массива аргументов, извлекающий команды PING, SET, GET без преобразования string([]byte).
4. Сформируйте статические RESP-ответы (+PONG\r\n, +OK\r\n) и отправьте клиенту.

package main

import (
	"bytes"
	"fmt"
	"log"
	"sync"
	"unsafe"

	"github.com/panjf2000/gnet/v2"
)

var (
	respPong = []byte("+PONG\r\n")
	respOk   = []byte("+OK\r\n")
	respNil  = []byte("$-1\r\n")
)

type MiniRedisServer struct {
	gnet.BuiltinEventEngine
	store sync.Map // Потокобезопасное хранилище ключ-значение
}

func (s *MiniRedisServer) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// 1. Быстрая проверка inline команды "PING\r\n"
	if bytes.Equal(bytes.TrimSpace(buf), []byte("PING")) {
		_, _ = c.Write(respPong)
		return gnet.None
	}

	// 2. Разбор бинарного массива RESP (*<count>\r\n...)
	if len(buf) > 0 && buf[0] == '*' {
		args := parseRESPArgs(buf)
		if len(args) == 0 {
			return gnet.None
		}

		// Выполняем команду с нулевыми аллокациями
		s.executeCommand(c, args)
	}

	return gnet.None
}

// parseRESPArgs извлекает аргументы команды без единой аллокации строк!
func parseRESPArgs(buf []byte) [][]byte {
	var args [][]byte
	pos := 0

	// Пропускаем *<count>\r\n
	idx := bytes.Index(buf[pos:], []byte("\r\n"))
	if idx == -1 {
		return nil
	}
	pos += idx + 2

	for pos < len(buf) {
		if buf[pos] != '$' {
			break
		}
		// Ищем конец строки длины $<len>\r\n
		lenEnd := bytes.Index(buf[pos:], []byte("\r\n"))
		if lenEnd == -1 {
			break
		}
		pos += lenEnd + 2

		// Ищем конец аргумента <data>\r\n
		argEnd := bytes.Index(buf[pos:], []byte("\r\n"))
		if argEnd == -1 {
			break
		}

		// Срез указывает прямо во внутренний кольцевой буфер сети!
		arg := buf[pos : pos+argEnd]
		args = append(args, arg)
		pos += argEnd + 2
	}

	return args
}

func (s *MiniRedisServer) executeCommand(c gnet.Conn, args [][]byte) {
	if len(args) == 0 {
		return
	}

	cmd := bytes.ToUpper(args[0])

	switch {
	case bytes.Equal(cmd, []byte("PING")):
		_, _ = c.Write(respPong)

	case bytes.Equal(cmd, []byte("SET")):
		if len(args) >= 3 {
			// Zero-Copy преобразование среза байт в строку для ключа мапы
			key := unsafeString(args[1])
			val := make([]byte, len(args[2]))
			copy(val, args[2]) // Значение сохраняем в куче
			s.store.Store(key, val)
			_, _ = c.Write(respOk)
		}

	case bytes.Equal(cmd, []byte("GET")):
		if len(args) >= 2 {
			key := unsafeString(args[1])
			if val, ok := s.store.Load(key); ok {
				data := val.([]byte)
				resp := fmt.Sprintf("$%d\r\n%s\r\n", len(data), string(data))
				_, _ = c.Write([]byte(resp))
			} else {
				_, _ = c.Write(respNil)
			}
		}

	default:
		_, _ = c.Write([]byte("-ERR unknown command\r\n"))
	}
}

// unsafeString преобразует []byte в string без аллокации памяти
func unsafeString(b []byte) string {
	if len(b) == 0 {
		return ""
	}
	return unsafe.String(&b[0], len(b))
}

func main() {
	server := &MiniRedisServer{}
	addr := "tcp://127.0.0.1:6379"

	log.Printf("Запуск Zero-Copy Redis клона на %s...\n", addr)
	fmt.Println("Тестируйте через redis-cli: redis-cli -p 6379 PING")

	err := gnet.Run(server, addr, gnet.WithMulticore(true))
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Функция unsafe.String(ptr, len) (введенная в Go 1.20) создает заголовок строки StringHeader { Data: ptr, Len: len } без выделения памяти в куче.

При выполнении операции s.store.Load(unsafeString(args[1])) среда выполнения Go использует указатель на существующий буфер сети только для вычисления хеша и поиска в бакетах мапы. Память не копируется!

⚠️ Частые грабли и ошибки новичков

Строка, созданная через unsafe.String, валидна только до тех пор, пока жив и не изменен исходный массив байт. Если вы сохраните такую строку в долгоживущую структуру данных или мапу (например, в качестве постоянного ключа хранилища), а кольцевой буфер сети затем перезапишется новыми данными, ключ мапы мгновенно повредится! Для долговременного хранения в мапе обязательно создавайте постоянную копию: permanentKey := string(args[1]).

🏢 В продакшене BigTech и на собеседованиях

Вопрос на собеседовании (Principal Go Engineer):

«Как компилятор Go оптимизирует поиск в map[string]T по срезу []byte (m[string(b)]), и почему не всегда нужно использовать unsafe.String?»

Эталонный ответ:

Компилятор Go имеет встроенную оптимизацию для выражения вида val, ok := m[string(b)].

В этом конкретном синтаксическом контексте компилятор не вызывает runtime.slicebytetostring и не аллоцирует строку в куче! Он вызывает специализированную внутреннюю функцию рантайма runtime.mapaccess1_faststr или runtime.mapassign_faststr, используя байтовый срез b напрямую для вычисления хеша.

Однако эта оптимизация работает *только* если преобразование string(b) происходит непосредственно внутри квадратных скобок доступа к мапе! Во всех остальных случаях string(b) аллоцирует память, и там оправдано использование unsafe.String.

package main

import (
	"encoding/binary"
	"fmt"
	"log"
	"runtime"
	"sync"
	"sync/atomic"
	"time"

	"github.com/panjf2000/gnet/v2"
)

// Бинарная структура торгового ордера
const (
	OrderPacketSize = 25 // 4 байта длина (21) + 8 OrderID + 8 Price + 4 Qty + 1 Side
)

type Order struct {
	Conn    gnet.Conn
	OrderID uint64
	Price   uint64
	Qty     uint32
	Side    byte
}

var orderPool = sync.Pool{
	New: func() any {
		return new(Order)
	},
}

type HFTGateway struct {
	gnet.BuiltinEventEngine
	orderQueue chan *Order
	ordersDone int64
}

func NewHFTGateway(queueCapacity int) *HFTGateway {
	gw := &HFTGateway{
		orderQueue: make(chan *Order, queueCapacity),
	}

	// Запуск сверхбыстрого движка обработки (Matching / Risk Check)
	go gw.matchingEngine()

	return gw
}

func (gw *HFTGateway) matchingEngine() {
	// Привязываем движок матчинга к выделенному ядру CPU
	runtime.LockOSThread()
	defer runtime.UnlockOSThread()

	respBuf := make([]byte, 13) // 4 байта длина + 8 OrderID + 1 статус
	binary.BigEndian.PutUint32(respBuf[:4], 9)
	respBuf[12] = 0x01 // Status: FILLED

	for order := range gw.orderQueue {
		// 1. Сверхбыстрая проверка рисков в оперативной памяти (O(1))
		orderID := order.OrderID
		conn := order.Conn

		// Возвращаем структуру ордера в пул
		orderPool.Put(order)

		// 2. Формируем бинарный ответ
		binary.BigEndian.PutUint64(respBuf[4:12], orderID)

		// 3. Отправляем подтверждение клиенту через неблокирующий AsyncWrite
		_ = conn.AsyncWrite(respBuf, nil)

		atomic.AddInt64(&gw.ordersDone, 1)
	}
}

func (gw *HFTGateway) OnTraffic(c gnet.Conn) gnet.Action {
	for {
		buffered := c.InboundBuffered()
		if buffered < OrderPacketSize {
			return gnet.None
		}

		data, err := c.Peek(OrderPacketSize)
		if err != nil {
			return gnet.Close
		}

		// Проверка длины кадра
		frameLen := binary.BigEndian.Uint32(data[:4])
		if frameLen != 21 {
			return gnet.Close // Невалидный пакет
		}

		// Извлекаем поля ордера напрямую из кольцевого буфера
		order := orderPool.Get().(*Order)
		order.Conn = c
		order.OrderID = binary.BigEndian.Uint64(data[4:12])
		order.Price = binary.BigEndian.Uint64(data[12:20])
		order.Qty = binary.BigEndian.Uint32(data[20:24])
		order.Side = data[24]

		// Сдвигаем кольцевой буфер сети
		_, _ = c.Discard(OrderPacketSize)

		// Передаем ордер в очередь матчинга без блокировки
		select {
		case gw.orderQueue <- order:
		default:
			orderPool.Put(order)
			// Очередь переполнена
			_ = c.AsyncWrite([]byte("ERR_DROP\n"), nil)
		}
	}
}

func main() {
	gateway := NewHFTGateway(100000)
	addr := "tcp://127.0.0.1:9029"

	log.Printf("Запуск HFT Gateway на %s (Ядер: %d)...\n", addr, runtime.NumCPU())

	// Мониторинг производительности
	go func() {
		ticker := time.NewTicker(1 * time.Second)
		var last int64
		for range ticker.C {
			curr := atomic.LoadInt64(&gateway.ordersDone)
			fmt.Printf("[HFT GATEWAY] Скорость обработки: %d ордеров/сек\n", curr-last)
			last = curr
		}
	}()

	err := gnet.Run(
		gateway,
		addr,
		gnet.WithMulticore(true),
		gnet.WithLockOSThread(true),
		gnet.WithTCPNoDelay(gnet.TCPNoDelay),
		gnet.WithReusePort(true),
	)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}

package main

import (
	"bytes"
	"fmt"
	"log"
	"runtime"
	"sync"
	"unsafe"

	"github.com/panjf2000/gnet/v2"
)

const NumShards = 64

// Shard представляет собой изолированный сегмент хранилища со своим мьютексом
type Shard struct {
	sync.RWMutex
	data map[string][]byte
}

type ShardedStore struct {
	shards [NumShards]*Shard
}

func NewShardedStore() *ShardedStore {
	store := &ShardedStore{}
	for i := 0; i < NumShards; i++ {
		store.shards[i] = &Shard{
			data: make(map[string][]byte),
		}
	}
	return store
}

func fnvHash(key string) uint32 {
	var h uint32 = 2166136261
	for i := 0; i < len(key); i++ {
		h ^= uint32(key[i])
		h *= 16777619
	}
	return h
}

func (s *ShardedStore) Get(key string) ([]byte, bool) {
	shard := s.shards[fnvHash(key)%NumShards]
	shard.RLock()
	val, ok := shard.data[key]
	shard.RUnlock()
	return val, ok
}

func (s *ShardedStore) Set(key string, val []byte) {
	shard := s.shards[fnvHash(key)%NumShards]
	shard.Lock()
	shard.data[key] = val
	shard.Unlock()
}

type MiniRedisEngine struct {
	gnet.BuiltinEventEngine
	store *ShardedStore
}

func (e *MiniRedisEngine) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// Разбор команд (RESP или Inline)
	if bytes.Equal(bytes.TrimSpace(buf), []byte("PING")) {
		_, _ = c.Write([]byte("+PONG\r\n"))
		return gnet.None
	}

	// Упрощенный парсинг бинарного протокола RESP
	if len(buf) > 0 && buf[0] == '*' {
		e.handleRESP(c, buf)
	}

	return gnet.None
}

func (e *MiniRedisEngine) handleRESP(c gnet.Conn, buf []byte) {
	// Декодирование аргументов
	lines := bytes.Split(buf, []byte("\r\n"))
	var args [][]byte
	for i := 1; i < len(lines); i++ {
		if len(lines[i]) > 0 && lines[i][0] != '$' {
			args = append(args, lines[i])
		}
	}

	if len(args) == 0 {
		return
	}

	cmd := bytes.ToUpper(args[0])
	switch string(cmd) {
	case "PING":
		_, _ = c.Write([]byte("+PONG\r\n"))
	case "SET":
		if len(args) >= 3 {
			key := unsafeString(args[1])
			val := make([]byte, len(args[2]))
			copy(val, args[2])
			e.store.Set(key, val)
			_, _ = c.Write([]byte("+OK\r\n"))
		}
	case "GET":
		if len(args) >= 2 {
			key := unsafeString(args[1])
			if val, ok := e.store.Get(key); ok {
				_, _ = c.Write([]byte(fmt.Sprintf("$%d\r\n%s\r\n", len(val), val)))
			} else {
				_, _ = c.Write([]byte("$-1\r\n"))
			}
		}
	default:
		_, _ = c.Write([]byte("-ERR unknown command\r\n"))
	}
}

func unsafeString(b []byte) string {
	if len(b) == 0 {
		return ""
	}
	return unsafe.String(&b[0], len(b))
}

При проектировании промышленных сетевых шлюзов на базе gnet + Worker Pool ключевой инженерной задачей является защита системы от перегрузки (Backpressure & Load Shedding).

Если скорость поступления сетевых запросов ($150\,000 \ \text{RPS}$) превышает предельную производительность пула воркеров ($50\,000 \ \text{RPS}$), возникает лавинообразное накопление задач в очереди:

  • Если очередь не ограничена, приложение исчерпает оперативную память и будет убито ядром Linux (OOM Killer).
  • Если очередь ограничена, но Event Loop заблокируется в попытке вставить задачу в канал ch <- task, весь сетевой сервер зависнет.
Паттерн неблокирующего Backpressure:
1. Очередь задач имеет строгий фиксированный лимит емкости.
2. Сетевой поток OnTraffic выполняет неблокирующую попытку постановки задачи через select-default.
3. При заполнении очереди сервер применяет одну из стратегий Load Shedding:
  • Мгновенный ответ с ошибкой перегрузки (HTTP 429 Too Many Requests / 503 Service Unavailable).
  • Приостановка вычитывания из сокета (Flow Control): реактор временно удаляет флаг EPOLLIN для данного сокета, заставляя буфер TCP ядра заполниться и применить аппаратное противодавление на клиента!

package main

import (
	"fmt"
	"log"
	"sync/atomic"
	"time"

	"github.com/panjf2000/gnet/v2"
)

type WorkerTask struct {
	Conn gnet.Conn
	Data []byte
}

type BackpressureServer struct {
	gnet.BuiltinEventEngine
	taskQueue   chan WorkerTask
	droppedReqs int64
	successReqs int64
}

func NewBackpressureServer(workers int, queueCap int) *BackpressureServer {
	s := &BackpressureServer{
		taskQueue: make(chan WorkerTask, queueCap),
	}

	for i := 0; i < workers; i++ {
		go s.worker(i)
	}

	return s
}

func (s *BackpressureServer) worker(id int) {
	for task := range s.taskQueue {
		// Имитация тяжелой обработки
		time.Sleep(20 * time.Millisecond)

		resp := append([]byte("PROCESSED: "), task.Data...)
		_ = task.Conn.AsyncWrite(resp, nil)
		atomic.AddInt64(&s.successReqs, 1)
	}
}

func (s *BackpressureServer) OnTraffic(c gnet.Conn) gnet.Action {
	buf, err := c.Next(-1)
	if err != nil {
		return gnet.Close
	}

	// Копируем данные для воркера
	data := append([]byte(nil), buf...)

	// Неблокирующая попытка постановки в очередь (Backpressure)
	select {
	case s.taskQueue <- WorkerTask{Conn: c, Data: data}:
		return gnet.None
	default:
		// Очередь переполнена! Сбрасываем нагрузку без блокировки Event Loop!
		atomic.AddInt64(&s.droppedReqs, 1)
		_ = c.AsyncWrite([]byte("ERR: 429_TOO_MANY_REQUESTS_BACKPRESSURE\n"), nil)
		return gnet.None
	}
}

func main() {
	// Намеренно создаем мало воркеров (4 воркера = ~200 RPS предел)
	server := NewBackpressureServer(4, 500)
	addr := "tcp://127.0.0.1:9031"

	// Мониторинг отброшенных запросов
	go func() {
		ticker := time.NewTicker(2 * time.Second)
		for range ticker.C {
			fmt.Printf("[METRICS] Успешно: %d | Сброшено (Backpressure): %d | В очереди: %d/%d\n",
				atomic.LoadInt64(&server.successReqs),
				atomic.LoadInt64(&server.droppedReqs),
				len(server.taskQueue),
				cap(server.taskQueue),
			)
		}
	}()

	log.Printf("Запуск сервера с защитой Backpressure на %s...\n", addr)
	err := gnet.Run(server, addr, gnet.WithMulticore(true))
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

В сетевых системах существует два типа Backpressure:

1. Прикладной (Application-Level Backpressure): Сервер мгновенно отвечает кодом 429 / 503, сообщая клиенту о необходимости применить экспоненциальную задержку (Exponential Backoff with Jitter).
2. Сетевой (TCP Flow Control Backpressure): Если сервер перестает вызывать системный вызов read() для данного сокета, входящие пакеты заполняют буфер сокета ядра sk_receive_queue. Когда буфер полон, TCP-стек Linux уменьшает рекламируемое окно приема (TCP Window Size) до 0 (Zero Window). Сетевая карта отправителя физически останавливает передачу данных по кабелю. Это предотвращает переполнение памяти на стороне сервера.
⚠️ Частые грабли и ошибки новичков

Отправка сообщения об ошибке ERR: 429 через синхронный вызов c.Write() при перегрузке. Если сокет клиента медленный или заблокирован (Slow Client), вызов c.Write() может заблокироваться. Всегда используйте асинхронный c.AsyncWrite() с таймаутом ожидания отправки.

🏢 В продакшене BigTech и на собеседованиях

Вопрос на собеседовании (Reliability Architect / Principal SRE):

«В чем разница между Rate Limiting, Backpressure и Load Shedding в распределенных высоконагруженных системах?»

Эталонный ответ:

  • Rate Limiting: Проактивное ограничение числа запросов от конкретного клиента или токена на основе политик (например, алгоритм Token Bucket: не более 100 req/s на пользователя).
  • Backpressure: Реактивный сигнал от перегруженного потребителя (Consumer) к производителю (Producer) с требованием снизить скорость передачи данных (TCP Zero Window, реактивные потоки Rx).
  • Load Shedding: Аварийный механизм самосохранения системы при превышении критической нагрузки. Сервер намеренно отбрасывает часть запросов (наименее приоритетных), чтобы не упасть целиком и сохранить доступность для критического трафика.

💡 Теоретический фундамент и концепция

Завершающее упражнение главы посвящено глубокому анатомическому анализу внутреннего механизма RingBuffer (кольцевого буфера памяти) во фреймворке gnet и ликвидации аллокаций мусора при обработке тяжелых потоков данных.

Анатомия циклического кольцевого буфера:

В стандартных слайсах Go при удалении обработанных элементов в начале массива разработчик вынужден либо сдвигать оставшиеся байты влево вызовом copy(buf, buf[n:]) ($O(N)$, трата тактов CPU), либо создавать новый слайс в куче.

В кольцевом буфере память организована по кругу фиксированного размера $S$ (степень двойки, $S = 2^k$):

        [0]  [1]  [2]  [3]  [4]  [5]  [6]  [7]
         ▲                   ▲
         │                   │
      ReadPtr             WritePtr
  • Запись: Новые байты из сокета пишутся по индексу WritePtr. Указатель увеличивается: WritePtr = (WritePtr + n) & (S - 1).
  • Чтение: Приложение читает байты по индексу ReadPtr. Указатель увеличивается: ReadPtr = (ReadPtr + n) & (S - 1).
  • Нулевые аллокации: Память выделяется один раз при создании сокета. Никаких перемещений элементов (memcpy) не происходит! Если буфер переполняется, его емкость удваивается (Elastic Expansion).

Использование встроенных методов c.InboundBuffered(), c.Peek() и c.Discard() позволяет проводить сложнейший сетевой анализ без создания ни одного временного объекта в куче Go.

package main

import (
	"encoding/binary"
	"fmt"
	"log"
	"runtime"
	"time"

	"github.com/panjf2000/gnet/v2"
)

// ZeroAllocMetricServer демонстрирует работу с кольцевым буфером с нулевыми аллокациями
type ZeroAllocMetricServer struct {
	gnet.BuiltinEventEngine
	totalPackets int64
}

func (s *ZeroAllocMetricServer) OnTraffic(c gnet.Conn) gnet.Action {
	for {
		// 1. Проверяем доступный объем данных в кольцевом буфере
		buffered := c.InboundBuffered()
		if buffered < 8 { // Минимальный телеметрический пакет: 4 байта ID + 4 байта Value
			return gnet.None
		}

		// 2. Заглядываем в кольцевой буфер без аллокаций
		data, err := c.Peek(8)
		if err != nil {
			return gnet.Close
		}

		// 3. Декодируем поля пакета через ассемблерные инструкции BSWAP
		metricID := binary.BigEndian.Uint32(data[:4])
		metricVal := binary.BigEndian.Uint32(data[4:8])

		// Исполняем вычисления над метрикой на месте (in-place)
		_ = metricID
		_ = metricVal

		// 4. Сдвигаем указатель чтения в кольцевом буфере на 8 байт
		if _, err := c.Discard(8); err != nil {
			return gnet.Close
		}

		s.totalPackets++
	}
}

func main() {
	server := &ZeroAllocMetricServer{}
	addr := "tcp://127.0.0.1:9032"

	// Мониторинг GC пауз и аллокаций
	go func() {
		var m runtime.MemStats
		ticker := time.NewTicker(3 * time.Second)
		for range ticker.C {
			runtime.ReadMemStats(&m)
			fmt.Printf("[RING-BUFFER TUNING] Обработано пакетов: %d | TotalAlloc: %d KB | NumGC: %d\n",
				server.totalPackets, m.TotalAlloc/1024, m.NumGC)
		}
	}()

	log.Printf("Запуск Zero-Allocation сетевого мультиплексора на %s...\n", addr)

	err := gnet.Run(
		server,
		addr,
		gnet.WithMulticore(true),
		gnet.WithTCPNoDelay(gnet.TCPNoDelay),
		gnet.WithReadBufferCap(64*1024), // Начальная емкость кольцевого буфера 64 KB
	)
	if err != nil {
		log.Fatalf("Ошибка: %v", err)
	}
}

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Когда сетевая карта принимает трафик, gnet выполняет вызов системного вызова readv(fd, iov, 2). В структуре iovec передаются два сегмента:

1. iov[0] указывает от текущего индекса записи до конца кольцевого массива памяти.
2. iov[1] указывает от начала массива до индекса чтения.

Ядро Linux за один системный вызов заполняет оба непрерывных сегмента. Это исключает необходимость кольцевого выравнивания или сдвига байт в пользовательском пространстве, обеспечивая максимальную скорость обмена данными между ядром ОС и приложением на Go.

⚠️ Частые грабли и ошибки новичков

Если приложение сохраняет ссылку на срез байт data, возвращенный методом c.Peek(), за пределами вызова c.Discard(), эти данные будут перезаписаны ядром в момент следующего сетевого события. Если данные необходимо сохранить для долговременного использования, всегда выполняйте явное копирование в собственный буфер.

Вопрос на собеседовании (Principal Performance Architect / Staff Engineer):

«Каковы ключевые инженерные компромиссы (Trade-offs) между использованием системного кольцевого буфера (Userspace Ring Buffer) и аллокацией свежих срезов памяти под каждый запрос?»

Эталонный ответ:

  • Userspace Ring Buffer (gnet, Netty):
  • *Плюсы:* Нулевая нагрузка на сборщик мусора Go, отсутствие пауз GC Stop-The-World, стабильная хвостовая задержка p999, низкий расход оперативной памяти.
  • *Минусы:* Опасность повреждения данных при преждевременном сдвиге буфера, необходимость ручного управления временем жизни срезов байтов, сложность отладки гонок данных.
  • Свежие срезы в куче (Standard net/http):
  • *Плюсы:* 100% безопасность памяти (Memory Safety), данные изолированы и принадлежат конкретной горутине, тривиальная читаемость кода.
  • *Минусы:* Высокое давление на GC при сотнях тысяч RPS, фрагментация памяти, деградация латентности при пиковых нагрузках.
