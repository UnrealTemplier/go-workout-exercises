# Высокопроизводительные API Gateway и Reverse Proxy на чистом Go

В этом файле собраны уникальные упражнения по теме **"Высокопроизводительные API Gateway и Reverse Proxy на чистом Go"**, отсортированные по возрастанию сложности.

---

1. **Концепция обратного прокси (Reverse Proxy) и API Gateway**: Изучите архитектурные различия между прямым прокси (Forward Proxy), обратным прокси (Reverse Proxy) и полнофункциональным API-шлюзом (API Gateway). Сформулируйте ключевые обязанности шлюза: маршрутизация трафика, терминация TLS, балансировка нагрузки, защита от DoS, централизованная аутентификация и наблюдаемость.

2. **Устройство net/http/httputil.ReverseProxy**: Изучите внутреннее устройство структуры `httputil.ReverseProxy` из стандартной библиотеки Go. Разберите ее ключевые поля: `Director`, `Transport`, `FlushInterval`, `ErrorLog`, `ModifyResponse`, `ErrorHandler`. Создайте минимальный проксирующий сервер через `httputil.NewSingleHostReverseProxy`.

3. **Функция Director: модификация входящих запросов**: Реализуйте кастомную функцию `Director(req *http.Request)`: динамическая смена целевого хоста (`req.URL.Host = target.Host`), перезапись схемы (`req.URL.Scheme = target.Scheme`), нормализация путей и передача параметров запроса.

4. **Управление служебными заголовками X-Forwarded-***: Реализуйте правильное формирование заголовков проксирования: добавление клиентского IP в `X-Forwarded-For` (с учетом цепочки предыдущих прокси), сохранение оригинального хоста в `X-Forwarded-Host` и протокола (`http`/`https`) в `X-Forwarded-Proto`. Избегайте уязвимости подделки IP-адреса (IP Spoofing).

5. **Очистка транзитных заголовков (Hop-by-Hop Headers)**: По стандарту RFC 2616 транзитные заголовки hop-by-hop не должны пересылаться дальше прокси-сервером. Напишите функцию удаления заголовков: `Connection`, `Keep-Alive`, `Proxy-Authenticate`, `Proxy-Authorization`, `TE`, `Trailers`, `Transfer-Encoding`, `Upgrade` (если это не WebSocket-рукопожатие).

6. **Модификация ответов через ModifyResponse**: Реализуйте функцию `ModifyResponse(resp *http.Response) error`: добавление корпоративных заголовков безопасности (`X-Content-Type-Options: nosniff`, `Strict-Transport-Security`, `X-Frame-Options: DENY`), удаление заголовка `Server: internal-tech`, и маскирование чувствительных данных в JSON-ответах при ошибках.

7. **Кастомная обработка сбоев бэкенда через ErrorHandler**: Если бэкенд-сервис недоступен или вернул таймаут, стандартный прокси возвращает пустой ответ `502 Bad Gateway`. Реализуйте `ErrorHandler(w http.ResponseWriter, r *http.Request, err error)`: классифицируйте сетевую ошибку (таймаут контекста, connection refused, DNS lookup fail) и верните структурированный JSON-ответ с кодом 504 или 502.

8. **Потоковая передача данных (Zero-Allocation Streaming) и FlushInterval**: По умолчанию прокси буферизует ответы в памяти, что приводит к задержкам при стриминге больших файлов или Server-Sent Events. Настройте параметр `FlushInterval`: значение `-1` для немедленной передачи каждого полученного чанка клиенту. Замерьте задержку доставки SSE-событий через прокси.

9. **Защита от переполнения памяти: ограничение размера тела запроса**: Злоумышленник может отправить HTTP POST запрос с бесконечным телом, исчерпав память шлюза. Оберните тело запроса в `http.MaxBytesReader(w, r.Body, 10 << 20)` (лимит 10 МБ). Убедитесь, что при превышении лимита прокси разрывает соединение с кодом `413 Request Entity Too Large`.

10. **Глубокий тюнинг сетевого транспорта (http.Transport)**: Производительность прокси критически зависит от конфигурации `http.Transport`. Оптимизируйте пул соединений: `MaxIdleConns: 10000`, `MaxIdleConnsPerHost: 2000`, `IdleConnTimeout: 90 * time.Second`, `TLSHandshakeTimeout: 10 * time.Second`, `ExpectContinueTimeout: 1 * time.Second`, `ForceAttemptHTTP2: true`.

11. **Балансировка нагрузки: алгоритм Round-Robin**: Спроектируйте пул апстрим-серверов `UpstreamPool`. Реализуйте потокобезопасный алгоритм кругового распределения Round-Robin с использованием атомарного счетчика `atomic.AddUint64(&idx, 1) % uint64(len(servers))`. Проверьте равномерность распределения 10 000 запросов между 3 бэкендами.

12. **Балансировка по наименьшему числу соединений (Least Connections)**: Реализуйте алгоритм Least Connections: шлюз отслеживает количество активных запросов, обрабатываемых каждым бэкендом в текущий момент (`activeConns int64`). Входящий запрос направляется на сервер с минимальной текущей нагрузкой, что эффективно предотвращает перегрузку медленных реплик.

13. **Консистентное хэширование (Consistent Hashing) и Sticky Sessions**: Для кэширующих серверов важно направлять запросы одного пользователя на один и тот же бэкенд. Реализуйте кольцо консистентного хэширования (Consistent Hash Ring с виртуальными нодами) по IP-адресу клиента или сессионной куке. Докажите минимальное перераспределение ключей при падении одной ноды.

14. **Активный опрос здоровья (Active Health Checking)**: Напишите фоновый монитор бэкендов: горутина раз в 5 секунд отправляет легковесный запрос `GET /healthz` на каждый сервер пула. Если сервер не ответил за 1 секунду или вернул статус отличный от 200 три раза подряд, он временно помечается как `Unhealthy` и исключается из балансировки.

15. **Пассивный опрос здоровья (Passive / Outlier Detection)**: Активный опрос может не замечать сбои под реальной нагрузкой. Реализуйте пассивный мониторинг: если в процессе проксирования реальных запросов сервер возвращает 5 подряд ошибок сетевого подключения или статус `503`, прокси автоматически переводит его в карантин на 30 секунд.

16. **Динамическая маршрутизация по префиксам путей (Path Routing)**: Создайте дерево префиксных маршрутов (Radix Tree или префиксный роутер): маршрут `/api/v1/users/*` направляется на кластер сервиса пользователей, а `/api/v1/orders/*` — на кластер заказов. Реализуйте стриппинг префиксов (`TrimPrefix`) перед отправкой запроса апстриму.

17. **Маршрутизация по заголовкам и кукам (Header-based Routing)**: Настройте роутинг для внутреннего тестирования: если входящий запрос содержит заголовок `X-Beta-Tester: true`, прокси направляет его на экспериментальный кластер бэкендов (Canary), а остальные запросы — на стабильный production-кластер.

18. **Поддержка проксирования WebSockets**: Реализуйте прозрачное проксирование WebSockets: перехватите запрос с заголовками `Upgrade: websocket` и `Connection: Upgrade`, выполните ручное установление TCP-соединения с бэкендом, переключите соединение клиента через `http.Hijacker` и запустите двунаправленное копирование байт (`io.Copy`) между сокетами.

19. **Сквозное проксирование gRPC (HTTP/2 Cleartext h2c)**: Настройте шлюз на проксирование gRPC вызовов: убедитесь, что транспорт поддерживает протокол HTTP/2 без обязательного TLS шифрования (`golang.org/x/net/http2/h2c`), корректно обрабатывает мультиплексированные потоки и не ломает gRPC-трейлеры в конце ответа.

20. **Централизованная аутентификация: JWT Middleware на шлюзе**: Реализуйте проверку JWT на входе в шлюз: валидация подписи алгоритмом RSA-256 или Ed25519, проверка срока действия `exp`, извлечение `user_id` и ролей и инъекция их в виде безопасного внутреннего заголовка `X-Auth-User: 123` перед отправкой в приватную сеть.

21. **Распределенный Rate Limiter per Route на базе Redis**: Защитите API от злоупотреблений: реализуйте Rate Limiting на базе алгоритма скользящего окна (Sliding Window Log) в Redis с использованием Lua-скрипта. Настройте раздельные лимиты: 100 запросов/мин для анонимных пользователей и 10 000 запросов/мин для авторизованных клиентов.

22. **Паттерн Circuit Breaker на уровне API Gateway**: Оберните вызовы к каждому кластеру апстримов в Circuit Breaker. Если сервис заказов начинает падать с ошибками, цепь размыкается, и шлюз мгновенно возвращает клиенту `503 Service Temporarily Unavailable` без расхода соединений и тайм-аутов, предотвращая каскадный коллапс всей системы.

23. **Динамическое сжатие HTTP-ответов (Gzip / Brotli / zstd)**: Напишите middleware сжатия ответов на шлюзе: если клиент передал заголовок `Accept-Encoding: gzip, br, zstd`, шлюз динамически сжимает тело ответа для текстовых MIME-типов (`application/json`, `text/html`) с использованием буферов из `sync.Pool`. Оцените снижение трафика.

24. **HTTP Caching на шлюзе: поддержка ETag и Cache-Control**: Реализуйте кэширующий прокси: если бэкенд возвращает заголовок `ETag: "hash123"`, шлюз сохраняет ответ в Redis/In-Memory. При получении запроса с заголовком `If-None-Match: "hash123"` шлюз мгновенно возвращает `304 Not Modified` без обращения к бэкенду.

25. **Сквозная трассировка: инъекция W3C Trace Context**: Подключите OpenTelemetry: шлюз проверяет наличие заголовка `traceparent`. Если заголовок отсутствует, шлюз генерирует новый `TraceID` и `SpanID`, создает корневой спан, логирует время проксирования и пробрасывает заголовок во внутренний микросервис.

26. **Мониторинг шлюза: экспорт Prometheus метрик**: Оснастите прокси метриками: `gateway_requests_total{route, method, status}`, `gateway_upstream_latency_seconds{upstream}`, `gateway_active_connections`. Настройте панели мониторинга и алерты на рост ошибок 5xx и задержки p99.

27. **Структурированный Access Log на базе log/slog**: Реализуйте высокоскоростной Access Log в формате JSON: логирование полей `remote_ip`, `method`, `path`, `status`, `bytes_sent`, `duration_ms`, `upstream_addr`, `user_agent`, `trace_id`. Обеспечьте нулевые аллокации при форматировании записей журнала.

28. **Горячая перезагрузка конфигурации маршрутов (Hot Reload)**: Реализуйте обновление таблицы маршрутизации без перезапуска процесса: шлюз хранит указатель `atomic.Pointer[RouteTable]`. При изменении конфигурационного файла или команды по API создается новая таблица маршрутов и атомарно подменяется указатель без потери активных соединений.

29. **Системный тюнинг сокетов для HighLoad Gateway**: Настройте параметры сетевого стека Linux для прокси, обрабатывающего 100k+ соединений: системные вызовы `SO_REUSEPORT` через `net.ListenConfig.Control`, тюнинг параметров `sysctl` (`net.core.somaxconn=65535`, `net.ipv4.tcp_tw_reuse=1`, увеличение лимитов `nofile`).

30. **Комплексный Production-Ready API Gateway на чистом Go**: Разработайте полнофункциональный API-шлюз на чистом Go: динамический обратный прокси с балансировкой Least Connections, активными проверками здоровья бэкендов, JWT-валидацией, распределенным Rate Limiting, поддержкой WebSockets, метриками Prometheus и graceful shutdown.
