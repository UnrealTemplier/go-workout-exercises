# Логическая репликация и Change Data Capture

В этом файле собраны уникальные упражнения по теме **"Логическая репликация и Change Data Capture"**, отсортированные по возрастанию сложности.

---

1. Настрой PostgreSQL в Docker: включи `wal_level=logical` и `max_replication_slots=10`.

2. Создай публикацию (`CREATE PUBLICATION my_pub FOR ALL TABLES;`) и слот логической репликации через Go-код (`pglogrepl.CreateReplicationSlot`).

3. **Чтение WAL через Go.**: Используйте `jackc/pglogrepl` для подключения к слоту: `StartReplication`, цикл `WaitForReplicationMessage`. Обрабатывайте `PrimaryKeepaliveMessage` (отправляйте `StandbyStatusMessage` с `replyRequested`). Объясните, почему PostgreSQL может отключить клиента, если он не шлёт feedback.

4. Запусти репликацию (`pglogrepl.StartReplication`). Напиши бесконечный цикл, который читает WAL (Write-Ahead Log) сообщения.

5. **Logical replication в PostgreSQL**: Включите `wal_level = logical` в `postgresql.conf`. Создайте publication для таблиц.

6. **Replication slots**: Создайте replication slot через `pg_create_logical_replication_slot('slot_name', 'pgoutput')`. Поймите, что slot предотвращает удаление WAL до прочтения.

7. **Декодирование pgoutput.**: Распарсите поток WAL: `BeginMessage` (транзакция началась), `RelationMessage` (схема таблицы), `InsertMessage` (новая строка), `UpdateMessage` (старая + новая), `DeleteMessage`, `CommitMessage`. Выведите человекочитаемый лог изменений.

8. **pgoutput protocol**: Используйте `pglogrepl` пакет (`github.com/jackc/pglogrepl`) для чтения изменений через pgoutput protocol.

9. **StartReplication**: Вызовите `StartReplication` с `StartReplicationOptions{PluginArgs: ...}`. Поймите LSN (Log Sequence Number).

10. Обрабатывай сообщения типа `*pglogrepl.RelationMessage` (сохраняй структуру таблиц в памяти) и `*pglogrepl.InsertMessage` (декодируй кортеж данных в Go-структуру).

11. **Parse WAL messages**: Парсите `XLogData` сообщения: `Begin`, `Commit`, `Insert`, `Update`, `Delete`, `Relation`, `Type`.

12. **Обработка TOAST.**: Создайте таблицу с колонкой `TEXT` (>2 KB). При обновлении другой колонки покажите, что TOAST-поле передаётся как `ToastUnchanged` (не передаётся в WAL). Объясните, как обработать: либо хранить полную копию в consumer, либо делать `SELECT` из таблицы по ключу.

13. **Tuple data parsing**: Декодируйте `TupleData` в Go-структуры с учётом типов PostgreSQL (text, int4, timestamp, jsonb, uuid).

14. **LSN tracking**: Сохраняйте последний обработанный LSN в БД или Redis. При рестарте resume с этого LSN.

15. **[Каверзный кейс — Schema Changes]**: Что будет, если во время репликации в Postgres добавят новую колонку? Реализуй обновление локального кэша схем при получении нового `RelationMessage`.

16. **SendStandbyStatusUpdate**: Регулярно отправляйте `StandbyStatusUpdate` для подтверждения получения WAL. Иначе slot разрастётся и заполнит диск.

17. **Schema cache.**: Постройте in-memory map: `relation_id → []column_name + []column_type`. Обновляйте при получении `RelationMessage`. Используйте для динамического маппинга `TupleData` в `map[string]any`. Объясните, почему `RelationMessage` может приходить не для каждой транзакции.

18. **Debezium альтернатива**: Напишите собственный Debezium-подобный коннектор для вашего use case.

19. **Relation messages**: Обрабатывайте Relation messages для получения схемы таблиц (column names, types). Кэшируйте их.

20. **CDC → Kafka pipeline**: Настройте CDC reader, который публикует изменения в Kafka topic в формате `{"op": "c/u/d", "before": {...}, "after": {...}}`.

21. **[Acknowledging LSN]**: Реализуй отправку `StandbyStatusUpdate` обратно в Postgres каждые 5 секунд (подтверждение позиций WAL, чтобы Postgres не хранил логи вечно). Если не слать апдейты, слот будет разрастаться и переполнит диск.

22. **CDC → Elasticsearch**: Синхронизируйте PostgreSQL таблицу с Elasticsearch индексом в real-time через CDC.

23. **CDC → ClickHouse**: Синхронизируйте transactional данные в аналитическую БД через CDC + Kafka.

24. **PostgreSQL → Kafka.**: Реализуйте producer: читаете WAL, сериализуете в Avro/JSON, публикуете в Kafka topic `db.users`, `db.orders` с key = `primary_key`. Обеспечьте ordering (same partition for same key). Объясните, как Kafka Connect Debezium делает то же самое.

25. **Настройка PostgreSQL.**: Включите `wal_level = logical`, `max_replication_slots = 4`, `max_wal_senders = 10`. Создайте публикацию `CREATE PUBLICATION mypub FOR TABLE users, orders`. Создайте слот репликации (`pg_create_logical_replication_slot`). Объясните разницу между `pgoutput` (native) и `wal2json` (текстовый).

26. **Outbox pattern**: Реализуйте transactional outbox в приложении: бизнес-операция + запись в outbox table в одной транзакции. Отдельный процесс читает outbox через CDC.

27. **[High Availability]**: Если твой CDC-воркер упал, поднялся заново — он должен продолжить чтение с того места, где остановился. Сохраняй последний подтвержденный LSN (Log Sequence Number) в Redis или локальный файл перед стартом репликации (`StartReplication` с `lsn`).

28. **Handling large transactions**: Большие транзакции могут исчерпать память. Реализуйте streaming processing и backpressure.

29. **CDC → ClickHouse (Upsert).**: Реализуйте consumer: CDC-события вставляются в `ReplacingMergeTree` с дополнительными колонками `_version` (LSN) и `_sign` (1 для insert/update, -1 для delete). Покажите, как `FINAL` и `OPTIMIZE` дают актуальное состояние. Объясните, почему ClickHouse не любит deletes и как `_sign` решает это.

30. **[Маршрутизация событий]**: Изменения таблицы `users` отправляй в Kafka topic `users_cdc`, а изменения `orders` — в `orders_cdc`.

31. **CDC → Elasticsearch.**: Реализуйте consumer: `InsertMessage` → `index`, `UpdateMessage` → `update` с `doc`, `DeleteMessage` → `delete`. Обработайте partial update (только изменённые поля). Объясните, почему Elasticsearch не идеален для CDC (нет транзакций, возможны out-of-order updates).

32. **Подключение к репликационному слоту PostgreSQL**: * Настройте локальный PostgreSQL: установите параметр `wal_level = logical`.
    * Создайте публикацию `CREATE PUBLICATION my_pub FOR ALL TABLES`.
    * Напишите Go-код, который открывает специализированное подключение к PostgreSQL в режиме репликации с помощью пакета `github.com/jackc/pgx/v5/pgconn` (передав параметр `replication=database` в строке подключения) [572].
    * Создайте логический слот репликации с помощью метода `pgconn.CreateReplicationSlot` [572], указав плагин вывода `pgoutput`.

33. **[Graceful Shutdown CDC]**: Напиши обработчик `SIGINT`. При выключении воркер должен: доситать текущий WAL-сегмент, отправить финальный `StandbyStatusUpdate` в Postgres, закрыть соединение и сохранить LSN. Если этого не сделать, при следующем старте воркер может прочитать часть данных повторно (at-least-once).

34. **Fault tolerance и LSN tracking.**: Реализуйте механизм: consumer обрабатывает батч, коммитит offset (LSN) в PostgreSQL через `SendStandbyStatus` только после успешной записи в downstream. При рестарте читайте с `restart_lsn`. Объясните at-least-once vs exactly-once semantics.

35. **[Финальное испытание — Real-time Analytics Pipeline]**
    Построй сквозную систему аналитики в реальном времени:

36. **Настройка PostgreSQL**: В файле `postgresql.conf` (или в настройках Docker) включи `wal_level = logical`. Выполни в SQL-консоли `CREATE PUBLICATION my_pub FOR ALL TABLES;` и `SELECT pg_create_logical_replication_slot('my_slot', 'pgoutput');`. Теперь база готова стримить данные.

37. **Мониторинг и lag.**: Напишите метрики: `pg_stat_replication` → `pg_current_wal_lsn() - confirmed_flush_lsn` (lag в байтах). Выведите в Prometheus. Настройте алерт при lag > 100 MB. Объясните, почему рост lag приводит к bloat WAL и потенциальному OOM.

38. **Низкоуровневый разбор протокола `pgoutput`**: Напишите код, который в бесконечном цикле считывает сырой поток сообщений WAL из открытого слота репликации с помощью `pgconn.StartReplication`. Напишите парсер байт, который идентифицирует типы сообщений протокола `pgoutput`:
    * `'B'` (Begin) — начало транзакции.
    * `'R'` (Relation) — метаданные схемы таблицы (имена колонок и их типы).
    * `'I'` (Insert) — вставка новой строки (содержит значения колонок).
    * `'U'` (Update) — изменение строки.
    * `'D'` (Delete) — удаление строки.
    * `'C'` (Commit) — фиксация транзакции.

39. **Источник**: PostgreSQL (OLTP). Туда постоянно (через скрипт или HTTP API) идут INSERT'ы новых заказов.

40. **Schema evolution.**: Выполните `ALTER TABLE users ADD COLUMN phone VARCHAR`. Покажите, что `RelationMessage` приходит с новой версией схемы. Реализуйте consumer, который динамически адаптируется (добавляет nullable колонку в downstream). Объясните backward compatibility: новые поля → nullable, удаление → soft delete.

41. **Подключение как Реплика**: Используй библиотеку `github.com/jackc/pglogrepl` (от создателей `pgx`). Напиши Go-код, который подключается к Postgres не как обычный клиент, а притворяется **сервером-репликой** (передавая спец. параметры при соединении).

42. **CDC Worker**: Go-сервис с `pglogrepl` читает инсерты, декодирует их.

43. **Replication slots требуют мониторинга.**: Неухоженный slot заполнит диск primary БД. Мониторьте `pg_replication_slots`.

44. **Чтение WAL (Write-Ahead Log)**: Запусти стриминг сообщений. В бесконечном цикле читай байты из `pglogrepl`. Ты начнешь получать первичные пакеты (KeepAlive, XLogData). Распарси `XLogData` — это сырые данные транзакций Postgres.

45. **LSN tracking обязателен.**: Без сохранения LSN вы потеряете события при рестарте.

46. **Построение CDC-пайплайна**: Объедините ваш парсер `pgoutput` и продюсера Kafka (из раздела №36). Напишите полноценного CDC-демона: при изменении строки в таблице `users` в PostgreSQL, демон должен мгновенно перехватить это изменение, преобразовать его в структурированное JSON-событие `"UserChanged"` и отправить в топик Kafka.

47. **Буфер/Очередь**: Декодированные события пушатся в NATS JetStream (с гарантией доставки и персистентностью).

48. **Schema evolution — это боль.**: Готовьтесь к ALTER TABLE в source БД. Relation messages в pgoutput — ваш друг.

49. **Чтение изменений через pgoutput и их обработка.**: Используйте библиотеку `pgx` или `wal-listener`. Подключитесь к слоту, читайте сообщения репликации (insert, update, delete). Десериализуйте `pgoutput.Message` в структуру и логируйте.

50. **Outbox pattern для reliable events.**: Если нужна гарантия доставки вместе с бизнес-транзакцией — используйте outbox, а не direct publish.

51. **Тестируйте failure scenarios.**: Что будет, если consumer упадёт на час? Если Kafka недоступен? Если schema изменится?

52. **Декодирование `pgoutput`**: Сырые XLogData закодированы в формате плагина `pgoutput`. Используй пакет `pglogrepl`, чтобы распарсить сообщения типа `Relation` (схема таблицы) и `Insert / Update / Delete` (сами данные). Вставь строку в любую таблицу базы через обычный SQL клиент, и убедись, что твой Go-код мгновенно распечатал это событие!

53. **Аналитический приемник**: Второй Go-воркер читает батчами из NATS и пушит через Native Protocol прямо в ClickHouse.

54. **Управление LSN и Итог (CDC Pipeline)**: Каждое сообщение в WAL имеет `LSN` (Log Sequence Number). Твой Go-код **обязан** периодически отправлять базе статус (Standby Status Update), сообщая последний обработанный LSN.
    *Опасность:* Если ты не будешь "подтверждать" LSN, Postgres будет хранить WAL на диске вечно, ожидая, пока ты его прочитаешь, и в итоге диск сервера переполнится (база упадет). 
    *Задача:* Напиши надежный конвейер, который читает CDC, кидает данные в Kafka/RabbitMQ и только после подтверждения (Ack) от брокера — коммитит LSN обратно в PostgreSQL. Это индустриальный стандарт синхронизации (альтернатива тяжелому Debezium)!

56. **Управление подтверждениями LSN (Log Sequence Number)**: Если ваш CDC-демон упадет и перезапустится, он должен продолжить чтение WAL строго с того места, на котором остановился, не дублируя события. Напишите код периодической отправки подтверждений LSN (Standby Status Update) обратно в PostgreSQL. Демон должен сохранять максимальный успешно обработанный и отправленный в Kafka LSN и раз в 10 секунд отправлять статус-сообщение серверу PostgreSQL, подтверждая, что эти сегменты WAL можно безопасно очистить с диска.

57. **Построение микросервиса, реагирующего на изменения.**: Реализуйте микросервис, который слушает слот репликации, при появлении новой записи в `users` отправляет приветственное письмо (заглушка) и обновляет кэш Redis. Учтите обработку ошибок и перезапуск слота с сохранением LSN.
