Упражнение #1

Проверка версии Go и архитектура компилятора

📌 Условие задачи

Установи Go (если еще не установлен). Выведи версию Go в консоль с помощью команды go version.

💡 Теоретический фундамент и концепция

Команда go version — первая команда любого Go-разработчика.

Она сообщает три ключевых параметра среды:

1. Точную версию компилятора (например, go1.22.5);
2. Целевую операционную систему (linux, darwin, windows);
3. Архитектуру процессора (amd64, arm64, arm).

Архитектура компилятора Go:

В отличие от C++ (где компилятор gcc/clang зависит от системных библиотек libc) или Java (где байткод исполняется в JVM), компилятор Go (cmd/compile, cmd/link) полностью написан на самом Go (Self-Hosting Compiler начиная с Go 1.5). Он напрямую переводит абстрактное синтаксическое дерево (AST) через форму SSA (Static Single Assignment) в нативные машинные инструкции x86-64 или ARM64 без промежуточных C-компиляторов.

🔍 Пошаговый ход решения и ход мысли инженера

1. Открываем терминал.
2. Выполняем команду go version.
3. Проверяем также подробную информацию о сборщике через go env GOVERSION.
📄 Терминал 
go version
# Вывод:
# go version go1.22.5 linux/amd64

# Получение чистой строки версии для скриптов автоматизации:
go env GOVERSION
# go1.22.5
ℹ️ Проверка версии Go в системе
⚙️ Под капотом Go (Compiler, Linker & Runtime)

При запуске go version бинарник go считывает константу runtime.Version() из встроенной в сам тулчейн стандартной библиотеки.

⚠️ Частые грабли и ошибки новичков
  • Наличие нескольких установленных версий Go в системе (например, системный пакет apt/dnf и ручная установка в /usr/local/go). Всегда проверяйте which go, чтобы убедиться, какой бинарник вызывается из PATH.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Что такое Toolchain Switching, появившийся в Go 1.21?»

Ответ: Если в файле go.mod указана версия go 1.23.0, а на вашей машине установлен go1.21.0, тулчейн Go автоматически скачает официальный бинарник Go 1.23 в $GOPATH/bin и прозрачно выполнит сборку на нем.

Упражнение #2

Мгновенный запуск: команда go run и временные директории

📌 Условие задачи

Создайте файл main.go, напишите простейшую программу "Hello, World!" и запустите её командой go run.

💡 Теоретический фундамент и концепция

Команда go run объединяет два этапа:

1. Компиляцию и линковку во временный исполняемый файл;
2. Немедленный запуск этого файла.

Это обеспечивает высокую скорость итераций при локальной разработке.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем файл main.go.
2. Пишем функцию main с выводом строки.
3. Запускаем команду go run main.go.
📄 main.go 
package main

import "fmt"

func main() {
	fmt.Println("Hello, World! Привет из компилятора Go.")
}
ℹ️ Исходный файл main.go
📄 Терминал 
go run main.go
# Вывод:
# Hello, World! Привет из компилятора Go.
ℹ️ Запуск программы
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Если запустить команду с флагом отладки go run -work main.go, Go выведет путь к временной сборочной директории:

WORK=/tmp/go-build123456789/b001/

Внутри этого каталога создается скомпилированный бинарник exe/main. После завершения процесса go run автоматически очищает этот каталог.

⚠️ Частые грабли и ошибки новичков
  • Запуск go run в production-окружении (Docker-контейнерах на проде). На проде должен запускаться заранее скомпилированный бинарник.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Как передать аргументы командной строки в программу при запуске через go run?»

Ответ: Аргументы передаются после имени файла или пакета: go run . --port=8080 --env=prod. Все параметры после . попадают в срез os.Args.

Упражнение #3

Компиляция в нативный исполняемый файл: go build

📌 Условие задачи

Скомпилируйте ту же программу командой go build и запустите полученный бинарник.

💡 Теоретический фундамент и концепция

В отличие от go run, команда go build:

1. Компилирует пакет и все его зависимости;
2. Выполняет статическую компоновку (линковку);
3. Сохраняет готовый исполняемый файл на диск в текущую директорию;
4. Не запускает программу.

Полученный бинарный файл является полностью автономным.

🔍 Пошаговый ход решения и ход мысли инженера

1. Выполняем go build . в папке с main.go.
2. Проверяем появившийся бинарник через ls -lh.
3. Запускаем бинарник напрямую: ./hello_world.
📄 Терминал 
# Сборка бинарника
go build .

# Проверка созданного файла
ls -lh hello_world
# -rwxr-xr-x 1 ut ut 1.8M Sep 2 12:40 hello_world

# Прямой запуск
./hello_world
# Hello, World! Привет из компилятора Go.
ℹ️ Сборка и запуск бинарного файла
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Бинарник содержит заголовки формата ELF (в Linux), Mach-O (в macOS) или PE32+ (в Windows). В секцию .text помещаются машинные инструкции x86_64, в .rodata — строковые литералы, а также таблицы метаданных для сборщика мусора (GC Type Maps) и планировщика горутин.

⚠️ Частые грабли и ошибки новичков
  • Забыть выставить права на исполнение (chmod +x), если бинарник перемещался между серверами или архивировался без сохранения прав.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему простейший Hello World на Go весит около 1.5–2 МБ, тогда как на C он весит 15 КБ?»

Ответ: В Go-бинарник статически вшит полноценный Runtime: планировщик горутин (GMP), многопоточный менеджер памяти с бадди-аллокатором (tcmalloc-like), параллельный Garbage Collector, сетевой поллер на основе epoll/kqueue и метаданные типов для рефлексии и форматирования fmt.

Упражнение #4

Сборка модуля hello_mod и прямой запуск из консоли

📌 Условие задачи

Компиляция исполняемого файла: Скомпилируйте ваш проект hello_mod с помощью команды go build. Найдите появившийся исполняемый файл (бинарник) в директории и запустите его из консоли напрямую (например, ./hello_mod или hello_mod.exe).

💡 Теоретический фундамент и концепция

Когда проект инициализирован как модуль (go mod init hello_mod), команда go build по умолчанию присваивает скомпилированному бинарнику имя модуля (или имя текущей директории).

Это гарантирует предсказуемость сборки в CI/CD скриптах.

🔍 Пошаговый ход решения и ход мысли инженера

1. Переходим в директорию hello_mod.
2. Выполняем go build ..
3. Запускаем созданный бинарник ./hello_mod.
📄 Терминал 
cd hello_mod
go build .

# Запуск
./hello_mod
ℹ️ Сборка модульного проекта
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Имя выходного файла берется из директивы module в go.mod (последний сегмент пути).

⚠️ Частые грабли и ошибки новичков
  • Запуск go build в папке, где нет пакета package main: бинарник не создастся (Go просто проверит компилируемость библиотеки и сохранит объектный файл в кэш).
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Что происходит, если запустить go build в библиотечном пакете без package main?»

Ответ: Компилятор выполняет проверку синтаксиса и типов, компилирует пакет в кэш сборки GOCACHE, но исполняемый файл не генерируется, так как нет точки входа func main().

Упражнение #5

Основы кросс-компиляции: переменные GOOS и GOARCH

📌 Условие задачи

Кросс-компиляция: Скомпилируй свою программу для другой операционной системы (например, если ты на Windows, скомпилируй под Linux, используя переменные GOOS и GOARCH).

💡 Теоретический фундамент и концепция

Кросс-компиляция в Go — одна из сильнейших фич языка:

  • GOOS (Go Operating System): linux, windows, darwin, freebsd, openbsd;
  • GOARCH (Go Architecture): amd64, arm64, arm, 386, riscv64, mips64.

Вы можете находясь на любой ОС одной командой скомпилировать бинарник для серверов Linux на процессорах ARM или x86_64 без C-компиляторов и виртуалок!

🔍 Пошаговый ход решения и ход мысли инженера

1. Для Linux x86_64: GOOS=linux GOARCH=amd64 go build -o server-linux ..
2. Для Windows: GOOS=windows GOARCH=amd64 go build -o server-win.exe ..
3. Для macOS ARM64 (Apple Silicon M1/M2/M3): GOOS=darwin GOARCH=arm64 go build -o server-mac ..
📄 Терминал 
# Кросс-компиляция под Linux
GOOS=linux GOARCH=amd64 go build -o bin/server-linux-amd64 .

# Кросс-компиляция под Windows
GOOS=windows GOARCH=amd64 go build -o bin/server-windows.exe .

# Кросс-компиляция под Mac M-серии
GOOS=darwin GOARCH=arm64 go build -o bin/server-darwin-arm64 .
ℹ️ Кросс-платформенная сборка
⚙️ Под капотом Go (Compiler, Linker & Runtime)

При изменении GOOS/GOARCH компилятор переключает таблицы генерации опкодов ассемблера и фильтрует системные файлы стандартной библиотеки по суффиксам (например, file_linux.go, file_windows.go).

⚠️ Частые грабли и ошибки новичков
  • Наличие CGO (import "C"). Если включен CGO_ENABLED=1, стандартная кросс-компиляция сломается, так как CGO требует реальный C-кросс-компилятор под целевую ОС. Всегда собирайте с CGO_ENABLED=0.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Как в Go устроен механизм билд-тегов по именам файлов?»

Ответ: Компилятор автоматически отбирает файлы по суффиксам _linux.go, _windows.go, _amd64.go, _arm64.go. Файл net_linux.go будет включен в сборку только при GOOS=linux.

Упражнение #6

Полный цикл компиляции и прямого запуска бинарника

📌 Условие задачи

Скомпилируй программу в бинарный файл с помощью go build. Запусти полученный исполняемый файл напрямую из консоли.

💡 Теоретический фундамент и концепция

Закрепляем разницу в жизненном цикле:

1. go build выполняется на машине разработчика или в сборочном контуре CI;
2. На сервер деплоится только один бинарник;
3. Запуск осуществляется через systemd, Docker или напрямую ./app.

🔍 Пошаговый ход решения и ход мысли инженера

1. Компилируем проект: go build -o app ..
2. Запускаем: ./app.
📄 Терминал 
go build -o app .
./app
# Hello, World!
ℹ️ Сборка и вызов
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Операционная система через системный вызов execve загружает ELF-файл в адресное пространство нового процесса, инициализирует регистры и передает управление точке входа _rt0_amd64_linux.

⚠️ Частые грабли и ошибки новичков
  • Попытка запуска бинарника другой архитектуры (например, запуск ARM64-бинарника на x86_64) приведет к ошибке ядра: cannot execute binary file: Exec format error.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Что делает системная точка входа _rt0_amd64_linux в рантайме Go?»

Ответ: Она считывает аргументы argc/argv из стека ядра, инициализирует структуру m0 (главный поток ОС), g0 (системная горутина стека), настраивает сборщик мусора и запускает планировщик runtime.schedinit().

Упражнение #7

Установка утилит в систему через go install

📌 Условие задачи

Установка в систему: Используйте команду go install. Найдите, куда Go сохранил скомпилированный бинарный файл (проверьте директорию $GOPATH/bin или $HOME/go/bin). Попробуйте вызвать программу из консоли из любой другой директории.

💡 Теоретический фундамент и концепция

Команда go install:

1. Компилирует программу с оптимизациями;
2. Копирует полученный исполняемый файл в глобальную системную директорию $GOBIN (или $GOPATH/bin = ~/go/bin).
3. Если эта папка прописана в системной переменной $PATH, вы можете запускать утилиту по имени из абсолютно любого каталога терминала!

🔍 Пошаговый ход решения и ход мысли инженера

1. В папке проекта выполняем go install ..
2. Проверяем наличие бинарника в $(go env GOPATH)/bin.
3. Переходим в любую другую папку (например, cd ~) и запускаем утилиту.
📄 Терминал 
# Установка
go install .

# Проверка расположения бинарника
ls -l $(go env GOPATH)/bin/hello_mod

# Запуск из любого каталога
cd /tmp
hello_mod
# Hello, World! Привет из компилятора Go.
ℹ️ Глобальная установка через go install
⚙️ Под капотом Go (Compiler, Linker & Runtime)

go install атомарно записывает бинарник во временный файл в $GOBIN и делает операцию rename, чтобы работающие параллельно процессы не упали от частичной перезаписи файла.

⚠️ Частые грабли и ошибки новичков
  • Если после go install терминал пишет command not found: hello_mod, значит директория $(go env GOPATH)/bin не добавлена в переменную $PATH.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Куда устанавливаются бинарники, если переменная GOBIN задана явно?»

Ответ: Если GOBIN задана (например, export GOBIN=/usr/local/bin), go install сохраняет бинарники строго в GOBIN, игнорируя $GOPATH/bin.

Упражнение #11

Кросс-компиляция под Linux x86_64 и инспекция заголовков ELF

📌 Условие задачи

Кросс-компиляция: Находясь на своей текущей операционной системе, скомпилируйте исполняемый файл для другой ОС (например, если вы на Windows, скомпилируйте для Linux с помощью команды GOOS=linux GOARCH=amd64 go build, или наоборот). Убедитесь, что создался файл другого формата.

💡 Теоретический фундамент и концепция

Форматы исполняемых файлов:

  • ELF (Executable and Linkable Format): стандартный формат бинарников в Linux;
  • Mach-O: формат исполняемых файлов в macOS;
  • PE32+ (Portable Executable): формат исполняемых файлов .exe в Windows.

🔍 Пошаговый ход решения и ход мысли инженера

1. Собираем Linux бинарник: GOOS=linux GOARCH=amd64 go build -o app-linux ..
2. Проверяем тип файла системной утилитой file app-linux.
📄 Терминал 
GOOS=linux GOARCH=amd64 go build -o app-linux .

# Инспекция формата
file app-linux
# app-linux: ELF 64-bit LSB executable, x86-64, version 1 (SYSV), statically linked, not stripped
ℹ️ Проверка формата файла
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Утилита file считывает первые 4 байта (Magic Bytes) файла: для ELF это 0x7F 'E' 'L' 'F', для Mach-O — 0xCF 0xFA 0xED 0xFE, для Windows — 0x4D 0x5A ('MZ').

⚠️ Частые грабли и ошибки новичков
  • Попытка запуска полученного ELF-бинарника напрямую в Windows без подсистемы WSL приведет к системной ошибке.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Что означает надпись statically linked в выводе утилиты file для Go-бинарника?»

Ответ: Это означает, что бинарник не содержит ссылок на динамические библиотеки (.so / .dll) и содержит весь рантайм внутри себя. Он запустится на любом Linux-дистрибутиве (Ubuntu, Alpine, RHEL, Arch) с подходящей версией ядра без установки сторонних пакетов.

Упражнение #12

Детектор состояний гонки (Data Race Detector) и флаг -race

📌 Условие задачи

Изучи флаг -race. Напиши простейшую программу с горутинами (можно подсмотреть в инете) и запусти её с флагом go run -race main.go.

💡 Теоретический фундамент и концепция

Состояние гонки (Data Race):

Ситуация в многопоточном коде, когда две или более горутины одновременно обращаются к одной и той же ячейке памяти, и как минимум одно из обращений — это запись, без использования механизмов синхронизации (sync.Mutex, каналов или sync/atomic).

Флаг -race включает встроенный в компилятор Go детектор гонок ThreadSanitizer (разработка Google). Он отслеживает каждое чтение и запись памяти в рантайме.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем программу с гонкой данных (две горутины инкрементируют счетчик counter++ без блокировки).
2. Запускаем go run -race main.go.
3. Анализируем подробный отчет детектора гонок с указанием точных строк кода.
📄 main.go 
package main

import (
	"fmt"
	"time"
)

func main() {
	counter := 0

	// Горутина 1: пишет в counter
	go func() {
		for i := 0; i < 1000; i++ {
			counter++
		}
	}()

	// Горутина 2: тоже пишет в counter без мьютекса!
	go func() {
		for i := 0; i < 1000; i++ {
			counter++
		}
	}()

	time.Sleep(100 * time.Millisecond)
	fmt.Printf("Итоговое значение: %d\n", counter)
}
ℹ️ Программа с Data Race
📄 Терминал 
go run -race main.go
# ==================
# WARNING: DATA RACE
# Write at 0x00c00001c0a8 by goroutine 8:
#   main.main.func2()
#       /home/ut/work/go-workout/main.go:20 +0x44
# 
# Previous Write at 0x00c00001c0a8 by goroutine 7:
#   main.main.func1()
#       /home/ut/work/go-workout/main.go:13 +0x44
# ==================
# Found 1 data race(s)
ℹ️ Предупреждение детектора гонок
⚙️ Под капотом Go (Compiler, Linker & Runtime)

При флаге -race компилятор заменяет каждую операцию доступа к памяти вызовом функций рантайма runtime.raceread и runtime.racewrite, а также выделяет теневую память (Shadow Memory) для отслеживания истории обращений и векторных часов (Vector Clocks).

⚠️ Частые грабли и ошибки новичков
  • Сборка с флагом -race увеличивает потребление памяти в 5–10 раз и замедляет выполнение в 2–3 раза. Поэтому -race включают в тестах (go test -race ./...) и на staging-серверах, но не в боевом highload-продакшене.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Гарантирует ли успешное прохождение go test -race, что в коде на 100% нет гонок данных?»

Ответ: Нет! Детектор гонок является динамическим анализатором. Он обнаруживает гонки только на тех путях выполнения кода, которые реально выполнились во время работы теста. Если проблемная ветка кода не была вызвана в тесте, гонка не будет обнаружена. Поэтому критически важно высокое покрытие тестами (Code Coverage).

Матричная кросс-компиляция под Windows и Linux

📌 Условие задачи

Соберите кросс-компиляцией бинарники для Windows и Linux с помощью GOOS и GOARCH.

💡 Теоретический фундамент и концепция

В современных пайплайнах релиза (например, в GoReleaser или GitHub Actions) сервис автоматически компилируется под матрицу платформ:

  • linux/amd64 (основные серверы)
  • linux/arm64 (AWS Graviton, Apple Silicon серверы)
  • windows/amd64 (рабочие станции Windows)
  • darwin/arm64 (macOS M-series)

🔍 Пошаговый ход решения и ход мысли инженера

1. Пишем bash-скрипт сборки под матрицу целевых платформ.
2. Проверяем созданные бинарники в директории dist/.
📄 build_matrix.sh 
#!/usr/bin/env bash
set -e

PLATFORMS=("linux/amd64" "linux/arm64" "windows/amd64" "darwin/arm64")

mkdir -p dist

for PLATFORM in "${PLATFORMS[@]}"; do
    GOOS=${PLATFORM%/*}
    GOARCH=${PLATFORM#*/}
    OUTPUT="dist/app-${GOOS}-${GOARCH}"
    if [ "$GOOS" = "windows" ]; then
        OUTPUT+=".exe"
    fi

    echo "==> Сборка для ${GOOS}/${GOARCH}..."
    CGO_ENABLED=0 GOOS=$GOOS GOARCH=$GOARCH go build -ldflags="-s -w" -o $OUTPUT .
done

echo "==> Все бинарники успешно собраны:"
ls -lh dist/
ℹ️ Скрипт матричной сборки
⚙️ Под капотом Go (Compiler, Linker & Runtime)

При смене GOARCH бэкенд компилятора подставляет соответствующий генератор машинных инструкций (например, генератор инструкций Thumb/AArch64 для ARM).

⚠️ Частые грабли и ошибки новичков
  • Забыть добавить расширение .exe для сборок под Windows.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Что такое fat binary (Universal Binary в macOS) и поддерживает ли Go их создание?»

Ответ: Fat Binary содержит машинный код для нескольких архитектур (x86_64 и ARM64) в одном файле. Go компилирует файлы под каждую архитектуру отдельно, после чего на macOS их можно объединить системной утилитой lipo -create app-amd64 app-arm64 -output app-universal.

Функция init() в Go имеет фиксированное поведение:

2. Не может быть вызвана разработчиком вручную;

2. Объявляем func init() { fmt.Println("Init started") }.
3. Объявляем func main() { fmt.Println("Main started") }.
4. Запускаем и проверяем вывод.
📄 main.go 
package main

import "fmt"

func init() {
	fmt.Println("Init started")
}

func main() {
	fmt.Println("Main started")
}
ℹ️ Хронология init и main
📄 Терминал 
go run .
# Вывод:
# Init started
# Main started
ℹ️ Вывод программы
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Компилятор регистрирует адрес функции init в специальной таблице инициализаторов. Главный поток рантайма обходит эту таблицу перед вызовом функции main.main.

  • Выполнение в init() долгих сетевых операций без таймаутов, что может заблокировать запуск программы.

Ответ: Все функции init() исполняются строго последовательно в главном системном потоке M0 (Main Thread) до запуска горутин пользовательского кода.

Упражнение #18

Стриппинг отладочной информации и уменьшение размера бинарника (-ldflags="-s -w")

📌 Условие задачи

Сборка с флагами: Скомпилируй программу с флагом -ldflags="-s -w", чтобы удалить отладочную информацию. Сравни размер полученного бинарника с обычным.

💡 Теоретический фундамент и концепция

По умолчанию Go включает в бинарник:

1. Таблицу символов (Symbol Table);
2. Отладочную информацию DWARF (номера строк, имена переменных для отладчика Delve/GDB).

Флаги линкера:

  • -s (Strip Symbol Table): удаляет таблицу символов;
  • -w (Strip DWARF): отключает генерацию отладочной информации DWARF.

Это уменьшает размер бинарника на 30–40% без влияния на скорость работы программы!

🔍 Пошаговый ход решения и ход мысли инженера

1. Собираем обычный бинарник: go build -o app-standard ..
2. Собираем оптимизированный бинарник: go build -ldflags="-s -w" -o app-stripped ..
3. Сравниваем размеры файлов через ls -lh.

⚙️ Под капотом Go (Compiler, Linker & Runtime)

Стриппинг удаляет секции .debug_info, .debug_line, .debug_frame из заголовков ELF. При этом стек-трейсы паник (panic()) в рантайме по-прежнему будут содержать имена функций и файлов, так как Go сохраняет минимальную таблицу для раскрутки стека (PCLNTAB).

  • Если скомпилировать бинарник с -s -w, к нему нельзя будет подключиться интерактивным отладчиком dlv attach для пошаговой отладки. Поэтому флаг используется для релизных сборок (Release / Production), но отключается в Debug-режиме.

Ответ: Да! Go сохраняет специальную таблицу соответствия счетчика команд и номеров строк (runtime.pclntab), поэтому даже в стрипнутом бинарнике при панике вы увидите точный номер строки и стек вызовов.

💡 Теоретический фундамент и концепция

  • flag.StringVar(&name, "name", "Гость", "Описание")

Упражнение #20

Реализация подкоманд (Subcommands) через flag.NewFlagSet

📌 Условие задачи

Реализуй подкоманду через flag: app add --x 5 --y 3 → 8, app sub --x 5 --y 3 → 2. Используй flag.NewFlagSet.

💡 Теоретический фундамент и концепция

Для создания утилит с несколькими действиями (по аналогии с git commit, git push, docker run) используется flag.NewFlagSet.

Каждый FlagSet представляет собой независимый набор флагов со своими правилами парсинга:

  • addCmd = flag.NewFlagSet("add", flag.ExitOnError)
  • subCmd = flag.NewFlagSet("sub", flag.ExitOnError)

🔍 Пошаговый ход решения и ход мысли инженера

1. Проверяем наличие подкоманды через os.Args[1].
2. Используем конструкцию switch os.Args[1].
3. Парсим срез cmd.Parse(os.Args[2:]) для выбранной команды.
4. Выполняем соответствующую математическую операцию.
📄 main.go 
package main

import (
	"flag"
	"fmt"
	"os"
)

func main() {
	if len(os.Args) < 2 {
		fmt.Println("Использование: app <add|sub> [флаги]")
		os.Exit(1)
	}

	// 1. Подкоманда add
	addCmd := flag.NewFlagSet("add", flag.ExitOnError)
	addX := addCmd.Int("x", 0, "Первое слагаемое")
	addY := addCmd.Int("y", 0, "Второе слагаемое")

	// 2. Подкоманда sub
	subCmd := flag.NewFlagSet("sub", flag.ExitOnError)
	subX := subCmd.Int("x", 0, "Уменьшаемое")
	subY := subCmd.Int("y", 0, "Вычитаемое")

	switch os.Args[1] {
	case "add":
		addCmd.Parse(os.Args[2:])
		fmt.Printf("%d + %d = %d\n", *addX, *addY, *addX+*addY)
	case "sub":
		subCmd.Parse(os.Args[2:])
		fmt.Printf("%d - %d = %d\n", *subX, *subY, *subX-*subY)
	default:
		fmt.Printf("Неизвестная команда: %s. Доступны: add, sub\n", os.Args[1])
		os.Exit(1)
	}
}

# Тестирование вычитания

⚠️ Частые грабли и ошибки новичков
  • Передача в cmd.Parse(os.Args[1:]) вместо os.Args[2:]: приведет к ошибке разбора, так как имя самой подкоманды попадет в парсер флагов.

Упражнение #22

Воспроизведение и устранение Data Race с детектором гонок

📌 Условие задачи

Скомпилируй программу с race detector: go run -race. Создай data race (два горутины пишут в одну переменную без синхронизации). Запусти с -race и без него, сравни поведение.

💡 Теоретический фундамент и концепция

Разница поведения с -race и без него:

  • Без -race: программа может годами работать на проде, пока при пиковой нагрузке не произойдет повреждение памяти (Silent Memory Corruption), приводящее к списанию денег у чужого пользователя или панике в случайном месте.
  • С -race: программа мгновенно падает с точным стек-трейсом гонки.

Устранение гонки:

Использование sync.Mutex или атомиков sync/atomic.

🔍 Пошаговый ход решения и ход мысли инженера

1. Пишем программу с гонкой данных.
2. Исправляем её с помощью sync.Mutex.
3. Запускаем с -race и убеждаемся в отсутствии предупреждений.
📄 main_fixed.go 
package main

import (
	"fmt"
	"sync"
)

type SafeCounter struct {
	mu    sync.Mutex
	value int
}

func (c *SafeCounter) Inc() {
	c.mu.Lock()
	defer c.mu.Unlock()
	c.value++
}

func (c *SafeCounter) Value() int {
	c.mu.Lock()
	defer c.mu.Unlock()
	return c.value
}

func main() {
	counter := &SafeCounter{}
	var wg sync.WaitGroup

	// Запуск 100 параллельных горутин
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for j := 0; j < 1000; j++ {
				counter.Inc()
			}
		}()
	}

	wg.Wait()
	fmt.Printf("Итоговое безопасное значение счетчика: %d\n", counter.Value())
}
ℹ️ Потокобезопасный счетчик с sync.Mutex
📄 Терминал 
go run -race main_fixed.go
# Вывод:
# Итоговое безопасное значение счетчика: 100000
# Никаких предупреждений Data Race!
ℹ️ Проверка исправленного кода
⚙️ Под капотом Go (Compiler, Linker & Runtime)

sync.Mutex использует атомарные инструкции процессора LOCK CMPXCHG (Compare-And-Swap). Если мьютекс свободен, захват происходит за единицы наносекунд без системных вызовов ядра (Fast-path).

⚠️ Частые грабли и ошибки новичков
  • Забыть вызвать wg.Wait(): функция main() завершится раньше горутин, и программа завершится аварийно или не выполнит работу.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Когда для счетчика лучше использовать sync/atomic вместо sync.Mutex?»

Ответ: Для простых числовых счетчиков atomic.AddInt64(&counter, 1) работает в 2–4 раза быстрее мьютекса, так как не требует аллокации структуры блокировки и переключения контекста горутины.

Упражнение #23

Graceful Shutdown: перехват сигналов ОС (SIGINT, SIGTERM) и мягкое завершение

📌 Условие задачи

Создай программу с graceful shutdown: перехватывай сигналы os.Interrupt, syscall.SIGTERM. При получении сигнала — выведи сообщение и корректно завершись.

💡 Теоретический фундамент и концепция

Graceful Shutdown (Мягкая остановка сервиса):

Когда оркестратор Kubernetes останавливает под (Pod) или вы нажимаете Ctrl+C, процесс получает системный сигнал:

  • SIGINT (Ctrl+C в терминале);
  • SIGTERM (сигнал остановки от Kubernetes / Docker).

Сервер не должен обрывать соединения клиентов на полуслове!

Он обязан:

1. Прекратить прием новых HTTP-запросов;
2. Дождаться завершения уже обрабатываемых запросов (в пределах таймаута);
3. Закрыть соединения с БД и сбросить буферы логов;
4. Завершить процесс с кодом 0.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем канал сигналов sigChan := make(chan os.Signal, 1).
2. Регистрируем перехват через signal.Notify(sigChan, os.Interrupt, syscall.SIGTERM).
3. Блокируемся на чтении из канала <-sigChan.
4. Выполняем очистку ресурсов с таймаутом через context.WithTimeout.
📄 main.go 
package main

import (
	"context"
	"fmt"
	"net/http"
	"os"
	"os/signal"
	"syscall"
	"time"
)

func main() {
	server := &http.Server{
		Addr: ":8080",
		Handler: http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
			time.Sleep(2 * time.Second) // Имитация долгого запроса
			fmt.Fprintln(w, "Запрос успешно обработан!")
		}),
	}

	// Запуск HTTP-сервера в фоновой горутине
	go func() {
		fmt.Println("🚀 Сервер запущен на порту :8080...")
		if err := server.ListenAndServe(); err != nil && err != http.ErrServerClosed {
			fmt.Printf("Ошибка сервера: %v\n", err)
		}
	}()

	// Канал для перехвата сигналов ОС
	quit := make(chan os.Signal, 1)
	signal.Notify(quit, os.Interrupt, syscall.SIGTERM)

	// Блокировка до получения сигнала остановки
	sig := <-quit
	fmt.Printf("\n⚠️  Получен сигнал [%v]. Начинаем Graceful Shutdown...\n", sig)

	// Даем серверу 5 секунд на завершение текущих соединений
	ctx, cancel := context.WithTimeout(context.Background(), 5*time.Second)
	defer cancel()

	if err := server.Shutdown(ctx); err != nil {
		fmt.Printf("✖ Принудительная остановка сервера по таймауту: %v\n", err)
	} else {
		fmt.Println("✔ Все клиентские соединения успешно закрыты.")
	}

	fmt.Println("🛑 Сервер корректно остановлен. Выход.")
}
ℹ️ Промышленный Graceful Shutdown HTTP-сервера
📄 Терминал

# (Нажимаем Ctrl+C)
# ^C
# ⚠️  Получен сигнал [interrupt]. Начинаем Graceful Shutdown...
# ✔ Все клиентские соединения успешно закрыты.
# 🛑 Сервер корректно остановлен. Выход.
ℹ️ Мягкая остановка процесса
⚙️ Под капотом Go (Compiler, Linker & Runtime)

signal.Notify перехватывает системные сигналы ядра Linux. Метод server.Shutdown(ctx) переводит внутренний слушатель сокета в закрытое состояние и ожидает завершения горутин активных HTTP-соединений.

⚠️ Частые грабли и ошибки новичков
  • Создание небуферизированного канала make(chan os.Signal): если сигнал придет в момент, когда горутина не читает канал, сигнал может быть потерян. Канал под сигналы всегда создается с емкостью 1 (make(chan os.Signal, 1)).
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Что происходит при деплое нового пода в Kubernetes (Zero Downtime Deployment)?»

Ответ: K8s посылает старому поду сигнал SIGTERM и одновременно удаляет его из эндпоинтов балансировщика Service. Pod выполняет Graceful Shutdown в течение terminationGracePeriodSeconds (по умолчанию 30с), после чего K8s принудительно убивает процесс через SIGKILL.

Упражнение #24

Автоматизационный сборочный скрипт CI/CD пайплайна

📌 Условие задачи

Напиши скрипт на bash/powershell, который: компилирует Go-программу, запускает тесты, проверяет форматирование (go fmt), запускает линтер (golangci-lint или go vet).

💡 Теоретический фундамент и концепция

В корпоративной разработке локальная проверка кода перед отправкой коммита (Pre-commit hook) автоматизируется единым скриптом проверки качества:

1. Проверка форматирования;
2. Статический анализ (go vet);
3. Прогон тестов с детектором гонок (go test -race);
4. Сборка продакшен-бинарника.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем скрипт ci.sh.
2. Добавляем флаги строгости Bash set -euo pipefail.
3. Реализуем пошаговую валидацию.
📄 ci.sh 
#!/usr/bin/env bash
set -euo pipefail

echo "========================================="
echo "   ЗАПУСК ПРОВЕРОК CI/CD ДЛЯ GO-ПРОЕКТА "
echo "========================================="

# 1. Проверка форматирования
echo "--> [1/4] Проверка gofmt..."
UNFORMATTED=$(gofmt -l .)
if [ -n "$UNFORMATTED" ]; then
    echo "✖ Ошибка: следующие файлы не отформатированы:"
    echo "$UNFORMATTED"
    exit 1
fi
echo "✔ Форматирование в порядке."

# 2. Статический анализ
echo "--> [2/4] Запуск go vet..."
go vet ./...
echo "✔ go vet пройден успешно."

# 3. Запуск тестов
echo "--> [3/4] Запуск тестов с детектором гонок..."
go test -v -race -cover ./...
echo "✔ Тесты успешно пройдены."

# 4. Сборка релизного бинарника
echo "--> [4/4] Сборка релизного артефакта..."
mkdir -p bin
CGO_ENABLED=0 go build -ldflags="-s -w" -o bin/server .
echo "✔ Бинарник успешно собран в папку bin/server"

echo "========================================="
echo "🎉 ВСЕ ПРОВЕРКИ УСПЕШНО ПРОЙДЕНЫ!"
echo "========================================="
ℹ️ Скрипт CI валидации
📄 Терминал 
chmod +x ci.sh
./ci.sh
ℹ️ Запуск проверок
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Флаг set -euo pipefail заставляет Bash немедленно прерывать выполнение скрипта, если хотя бы одна команда или конвейер завершились с ненулевым кодом ошибки.

⚠️ Частые грабли и ошибки новичков
  • Игнорирование кода возврата тестов в скриптах CI.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Зачем в CI использовать git diff --exit-code после генерации кода?»

Ответ: Если в проекте используется кодогенерация (Protobuf, Mockgen, Stringer), команда go generate ./... && git diff --exit-code гарантирует, что разработчик не забыл обновить сгенерированные файлы перед коммитом.

Упражнение #25

Многоэтапная Docker-контейнеризация: от Alpine к 5 МБ Scratch

📌 Условие задачи

Создай Docker-контейнер для Go-приложения (multi-stage build). Первый этап — сборка, второй — минимальный образ scratch или alpine с бинарником.

💡 Теоретический фундамент и концепция

Multi-Stage Builds (Многоэтапная сборка Docker):

В Go нет необходимости тащить компилятор, Git и Go SDK в продакшен-образ контейнера!

Двухэтапная сборка:

1. Этап 1 (Builder): образ golang:1.22-alpine компилирует статический бинарник (CGO_ENABLED=0).
2. Этап 2 (Runner): абсолютно пустой образ FROM scratch (размер 0 байт) или минимальный alpine (5 МБ). В него копируется только один скомпилированный бинарник и системные SSL-сертификаты (ca-certificates).

Итоговый размер Docker-образа составляет всего 10–15 МБ вместо 1 ГБ!

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем файл Dockerfile.
2. Описываем стадию сборщика AS builder.
3. Описываем стадию финального образа FROM scratch.
4. Собираем и проверяем размер образа командой docker build -t myapp:latest ..
📄 Dockerfile 
# ==========================================
# ЭТАП 1: Сборщик (Builder)
# ==========================================
FROM golang:1.22-alpine AS builder

# Установка корневых сертификатов для исходящих HTTPS-запросов
RUN apk --no-cache add ca-certificates tzdata

WORKDIR /app

# Кэширование слоя зависимостей
COPY go.mod go.sum* ./
RUN go mod download

# Копирование исходного кода
COPY . .

# Статическая компиляция бинарника без CGO
RUN CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build \
    -ldflags="-s -w -X main.Version=v1.0.0" \
    -o /bin/server .

# ==========================================
# ЭТАП 2: Минимальный продакшен-образ
# ==========================================
FROM scratch

# Копируем сертификаты и таймзоны из сборочного образа
COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/
COPY --from=builder /usr/share/zoneinfo /usr/share/zoneinfo
COPY --from=builder /bin/server /server

# Запуск от непривилегированного пользователя nobody (UID 65534)
USER 65534:65534

EXPOSE 8080

ENTRYPOINT ["/server"]
ℹ️ Production-grade Dockerfile для Go
📄 Терминал 
# Сборка Docker-образа
docker build -t go-service:v1 .

# Проверка размера образа
docker images go-service:v1
# REPOSITORY   TAG       IMAGE ID       SIZE
# go-service   v1        a1b2c3d4e5f6   12.4MB

# Запуск контейнера
docker run -p 8080:8080 go-service:v1
ℹ️ Сборка ультра-компактного образа
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Образ scratch — зарезервированное ключевое слово Docker, означающее пустую файловую систему. Статический Go-бинарник общается с ядром хостовой Linux-машины напрямую через системные вызовы syscall, не требуя ни glibc, ни оболочки /bin/sh.

⚠️ Частые грабли и ошибки новичков
  • Если ваше приложение делает исходящие HTTPS-запросы к внешним API (например, к Telegram Bot API или платежному шлюзу), в образе FROM scratch обязательно должен быть файл ca-certificates.crt, иначе любые TLS-рукопожатия завершатся ошибкой x509: certificate signed by unknown authority.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Почему в продакшен Dockerfile на этапе FROM scratch обязательно указывают USER 65534:65534?»

Ответ: По умолчанию контейнеры запускаются от пользователя root (UID 0). Если злоумышленник найдет уязвимость в приложении и выполнит побег из контейнера (Container Escape), он получит права root на хостовой ноде Kubernetes. Запуск от непривилегированного пользователя nobody (UID 65534) — базовый стандарт безопасности DevSecOps.
