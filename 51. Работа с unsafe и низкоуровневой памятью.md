# Работа с unsafe и низкоуровневой памятью

В этом файле собраны уникальные упражнения по теме **"Работа с unsafe и низкоуровневой памятью"**, отсортированные по возрастанию сложности.

---

1. **Приведение несовместимых типов**: Создайте срез типа `[]float64` с несколькими элементами. Используя тип `unsafe.Pointer`, преобразуйте этот срез в срез типа `[]int64` напрямую в памяти без копирования данных и выделения новой памяти. Выведите значения элементов до и после приведения и объясните, как интерпретируются биты вещественного числа в формате целочисленного типа.

2. Напишите программу, которая через `unsafe.Pointer` преобразует `*int64` в `*float64` (без изменения битового паттерна). Выведите hex-дамп до и после. Объясните, почему GC не мешает при короткой жизни `unsafe.Pointer`, но почему хранение промежуточного `uintptr` в переменной — опасно.

3. **Преобразование между типами через unsafe.**: Объявите два различных типа с одинаковой структурой памяти (например, `type A struct { X int; Y float64 }`, `type B struct { A int; B float64 }`). Преобразуйте `*A` в `*B` через `unsafe.Pointer`, измените поле и проверьте результат.

4. Используй `unsafe.Sizeof` для вывода размера структур `int`, `string`, `slice`, `bool`. Посчитай размер пустой структуры `struct{}` (должен быть 0) и размер структуры с полем `bool` и `int64` (выравнивание/padding).

5. **Первое знакомство**: Создайте переменную `int`, получите её адрес как `*int`, сконвертируйте в `unsafe.Pointer`, затем в `uintptr` и выведите адрес. Сравните с `%p` форматом.

6. **Исследование памяти (`unsafe.Sizeof`, `Alignof`)**: Создай структуру с разными типами полей. Используй `unsafe.Sizeof` для получения её размера в байтах и `unsafe.Alignof` для получения выравнивания.

7. **Правила конверсии**: Изучите 4 легальных способа конверсии в unsafe:
    * `*T` → `unsafe.Pointer` (и обратно)
    * `unsafe.Pointer` → `uintptr` (и обратно, но опасно!)
    * `unsafe.Pointer` → `unsafe.Pointer` другого типа
    * `reflect.SliceHeader`/`StringHeader` → `unsafe.Pointer`

8. **Прямое приведение типов**: Создайте `float64`, получите указатель на него, приведите к `*int64` через `unsafe.Pointer` и прочитайте битовое представление числа.

9. Реализуйте функцию `ptrAdd(ptr unsafe.Pointer, offset uintptr) unsafe.Pointer`, эмулирующую C-арифметику указателей. Протестируйте на массиве `[5]int`. Объясните правило: *«`uintptr` — это целое число, а не указатель для GC»*.

10. **Реинтерпретация памяти**: Создайте `[4]byte`, получите указатель, приведите к `*uint32` и прочитайте как одно число. Изучите endianness (little-endian на x86).

11. **Анатомия структуры (`unsafe.Offsetof`)**: Используй `unsafe.Offsetof`, чтобы узнать точный сдвиг (в байтах) каждого поля структуры относительно её начала. Докажи с помощью этих цифр, почему порядок полей влияет на итоговый размер структуры (из-за паддингов).

12. **[Выравнивание (Padding)]**: Создай структуру `A { a bool; b int64; c bool }` и структуру `B { b int64; a bool; c bool }`. Выведи `unsafe.Sizeof` для обеих. Объясни, почему они занимают разный объем памяти (выравнивание по 8 байтам).

13. **Прямой доступ к полям структуры через смещения.**: Используйте `unsafe.Offsetof` и `unsafe.Pointer` для чтения и модификации приватного (неэкспортируемого) поля структуры из другого пакета. Покажите опасность такого подхода.

14. **Zero-copy string conversion**: Реализуйте функцию `StringToBytes(s string) []byte` без аллокаций через `unsafe.Pointer` и `reflect.SliceHeader`. **Почему это опасно?** (строки неизменяемы!)

43. **Смертельная ловушка `uintptr` (GC-аномалия)**: *Теоретически-практическое.* `uintptr` — это просто число, а не указатель. Если ты сохранишь адрес объекта в `uintptr`, Garbage Collector не будет знать об этой связи. Если GC запустится и решит переместить объект (например, при сжатии стека), твой `uintptr` будет указывать на мусор. Осознай правило: **преобразования Pointer -> uintptr -> Pointer должны происходить в рамках одного выражения!**
