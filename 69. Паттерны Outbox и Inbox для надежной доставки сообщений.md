# Паттерны Outbox и Inbox для надежной доставки сообщений

В этом файле собраны уникальные упражнения по теме **"Паттерны Outbox и Inbox для надежной доставки сообщений"**, отсортированные по возрастанию сложности.

---

1. **Проблема dual write**: Покажите проблему: `db.UpdateOrder()` + `kafka.Publish(OrderUpdated)` — если Kafka unavailable, БД обновлена, но event не отправлен. Inconsistency.

2. **Polling strategy**: Используйте `SELECT ... FOR UPDATE SKIP LOCKED` для конкурентного polling без блокировок.

3. **Batch publishing**: Poller читает batch events (например, 100) и публикует их в Kafka одним batch для эффективности.

4. **Transactional Outbox: атомарная запись события.**: Сервис заказов в одной транзакции БД сохраняет заказ и вставляет запись в таблицу `outbox` (событие `OrderCreated`). Реализуйте это с PostgreSQL, используя `BEGIN/COMMIT`.

5. **Exponential backoff для failed events**: Для events, которые fail repeatedly, используйте exponential backoff (не пытайтесь публиковать их каждые 100ms).

6. **Dual-write problem.**: Напишите код, который «сначала INSERT в БД, потом Publish в Kafka». Сымитируйте crash между двумя операциями. Покажите, что заказ создан, но событие не отправлено (или наоборот). Объясните, почему распределённые транзакции (XA) между БД и Kafka — антипаттерн.

7. **Outbox table**: Создайте таблицу `outbox` в той же БД, что и бизнес-данные:
    ```sql
    CREATE TABLE outbox (
        id UUID PRIMARY KEY,
        aggregate_id UUID,
        aggregate_type VARCHAR,
        event_type VARCHAR,
        payload JSONB,
        created_at TIMESTAMP,
        processed BOOLEAN DEFAULT FALSE
    );
    ```

8. **Outbox per aggregate type**: Для high-volume систем создайте отдельные outbox tables per aggregate type (`orders_outbox`, `users_outbox`) для снижения contention.

9. **[Проблема Dual Write]**: Напиши код, который делает `db.Exec("INSERT INTO orders...")`, а затем `kafka.Send(...)`. Сымитируй крах программы между этими двумя строками. Объясни, почему заказ в БД есть, а сообщения в Kafka нет.

10. **CDC alternative (Debezium)**: Вместо poller используйте Debezium для CDC (Change Data Capture) из outbox table в Kafka. Debezium читает WAL/binlog и публикует changes.

11. **Atomic write**: В одной транзакции обновляйте бизнес-данные и вставляйте event в outbox:
    ```go
    tx.Begin()
    tx.Exec("UPDATE orders SET status = 'paid' WHERE id = $1", orderID)
    tx.Exec("INSERT INTO outbox (aggregate_id, event_type, payload) VALUES ($1, $2, $3)", orderID, "OrderPaid", payload)
    tx.Commit()
    ```

12. **Debezium setup**: Настройте Debezium connector для PostgreSQL outbox table. Изучите at-least-once semantics.

13. **Продвинутый Outbox-воркер (SKIP LOCKED)**: В предыдущих упражнениях мы создали простой Outbox. В высоконагруженных системах запуск одного Outbox-воркера создает бутылочное горлышко. Напишите в Go параллельный Outbox-воркер. Для того чтобы несколько инстансов воркера могли безопасно и без блокировок разбирать задачи из таблицы `outbox` в PostgreSQL, напишите SQL-запрос с использованием конструкции `SELECT ... FOR UPDATE SKIP LOCKED` [601]:
    ```sql
    SELECT id, payload FROM outbox_events WHERE status = 'pending' LIMIT 100 FOR UPDATE SKIP LOCKED;
    ```
    Это позволит параллельным горутинам/сервисам мгновенно забирать непересекающиеся пакеты событий на отправку [601].

14. **Outbox poller**: Отдельный процесс (или горутина) читает unprocessed events из outbox и публикует их в Kafka.

15. **Outbox Publisher (ретранслятор событий).**: Напишите фоновый процесс (горутина), который читает неотправленные записи из `outbox`, публикует их в брокер (Kafka/RabbitMQ) и помечает как отправленные в БД. Гарантируйте at-least-once семантику.

16. **Outbox в MongoDB**: Для MongoDB используйте Change Streams как альтернативу outbox (встроенная фича MongoDB).

17. **Mark as processed**: После успешной публикации в Kafka помечайте events как `processed = TRUE`.

18. **Атомарная транзакция**: Напиши функцию `CreateOrder`. Открой транзакцию `tx, _ := db.Begin()`. 1) Сделай `INSERT INTO orders`. 2) Сделай `INSERT INTO outbox_events` (status='PENDING', payload=сериализованный заказ). 3) `tx.Commit()`. Теперь бизнес-сущность и событие записаны со 100% гарантией консистентности.

19. **Outbox Relay (Poller).**: Реализуйте отдельный процесс, который каждые 500 мс читает `outbox WHERE sent_at IS NULL`, отправляет в Kafka, обновляет `sent_at`. Объясните, почему polling — простой, но создаёт нагрузку на БД, и как индекс на `(sent_at, id)` помогает.

20. **Outbox schema evolution**: При изменении event schema поддерживайте versioning в payload (`{"version": 2, "data": {...}}`).

21. **Cleanup old events**: Периодически удаляйте processed events старше N дней (например, 30 дней) для предотвращения роста таблицы.

22. **Outbox testing**: Напишите интеграционные тесты, которые проверяют: бизнес-операция + event в outbox в одной транзакции.

23. **Outbox monitoring**: Мониторьте lag: количество unprocessed events в outbox. Алерт, если lag растёт.

24. **Проблема at-least-once delivery**: Kafka/RabbitMQ гарантируют at-least-once delivery. Message может быть доставлен дважды. Consumer должен быть идемпотентным.

25. **Retry logic в poller**: Если Kafka publish failed, не помечайте event как processed. Retry на следующей итерации.

26. **Exactly-once с Outbox.**: Покажите, что Kafka может доставить сообщение дважды (producer retry). Consumer должен быть идемпотентным (см. Inbox). Объясните, что Outbox гарантирует exactly-once *публикацию* (атомарность с БД), но exactly-once *обработку* требует Idempotency/Inbox.

33. **Transactional Inbox (Идемпотентный потребитель)**: Даже при использовании Outbox брокеры сообщений (такие как Kafka) гарантируют доставку только класса At-Least-Once (минимум один раз), что приводит к дублированию сообщений на стороне приемника. Реализуйте паттерн Transactional Inbox. На стороне принимающего сервиса:
    * При получении сообщения из брокера откройте транзакцию в БД.
    * Попробуйте вставить ID сообщения в таблицу `inbox_events` (`INSERT INTO inbox_events (message_id) VALUES ($1)`).
    * В рамках этой же транзакции выполните обновление бизнес-данных.
    * Если вставка ID сообщения упала по нарушению уникальности ключа (уникальный индекс по `message_id`), сделайте откат (`Rollback`) всей транзакции, проигнорировав дубликат.

ON CONFLICT DO NOTHING; IF inserted THEN обработка; COMMIT;`. Объясните, как это защищает от дублей и обеспечивает at-least-once обработку ровно один раз.

37. **[Публикация и Ack]**: Relay Worker читает записи, отправляет их в Kafka/RabbitMQ. Только *после* успешного ответа от брокера он делает `UPDATE outbox SET processed = true WHERE id = ...`.

38. **Inbox Deduplication.**: Добавьте unique constraint `UNIQUE(event_id, consumer_name)`. При повторном получении — игнорировать. Покажите, что разные consumers (OrderService и AnalyticsService) могут обработать один event_id независимо.

39. **Batch processing**: Poller читает batch messages и обрабатывает их в одной транзакции (если бизнес-логика позволяет).

40. **Transactional Inbox: идемпотентный приём сообщений.**: Сервис-подписчик получает сообщение из брокера, проверяет наличие `message_id` в таблице `inbox`. Если сообщение уже обработано — игнорирует. Если нет — вставляет запись в `inbox` и выполняет бизнес-логику в одной транзакции БД.

41. **Outbox Ordering.**: Гарантируйте порядок событий для одного aggregate: partition key в Kafka = `aggregate_id` (например, `order_id`). Покажите, что события `OrderCreated`, `OrderPaid`, `OrderShipped` приходят в том же порядке. Объясните, почему глобальный порядок всех событий — невозможен и не нужен.

42. **[Каверзный кейс — Дубликаты (At-least-once)]**: Relay Worker отправил сообщение в Kafka, но сеть упала до того, как Worker успел сделать `UPDATE processed = true`. При рестарте Worker отправит это сообщение *повторно*. Объясни, почему Outbox гарантирует *At-least-once* (минимум один раз), а не *Exactly-once* (ровно один раз).

43. **Listen/Notify (Push модель)**: Поллинг каждую секунду грузит базу. Улучши воркер. Используй PostgreSQL `LISTEN outbox_channel`. В триггере таблицы `outbox_events` после инсерта делай `NOTIFY outbox_channel`. Твоя горутина проснется мгновенно и отправит событие в брокер без холостых поллингов!

44. **Очистка Inbox-таблицы (Pruning Daemon)**: Если хранить ID всех обработанных сообщений в таблице `inbox_events` бесконечно, её размер вырастет до гигабайт, что замедлит проверку уникальности. Напишите фоновую задачу-чистильщик (Pruning Daemon) в Go, которая раз в сутки удаляет из таблицы `inbox_events` записи старше 7 дней, гарантируя, что мы защищены от дубликатов в рамках недельного окна повторов.

45. **Outbox + Inbox Chain.**: Реализуйте цепочку: Service A (Outbox) → Kafka → Service B (Inbox → Business Logic → Outbox) → Kafka → Service C (Inbox). Покажите end-to-end trace: `order_id` propagates через все события. Объясните, как `correlation_id` помогает в логировании.

46. **Inbox в Redis**: Для Redis используйте Redis SET с `NX` (set if not exists) для idempotent message tracking.

47. **Inbox в MongoDB**: Для MongoDB используйте unique index на `message_id` для deduplication.

48. **[Transactional Inbox]**: На стороне консьюмера создай таблицу `inbox` (поля: `message_id`, `processed`). При получении сообщения из Kafka, консьюмер сначала делает `INSERT INTO inbox (message_id) VALUES (...)` в рамках бизнес-транзакции.

49. **Схема Inbox**: Переходим в сервис Склада (Inventory Service), который слушает Kafka. Создай таблицу `inbox_events (event_id UUID PRIMARY KEY, processed_at TIMESTAMP)`.

50. **Inbox schema evolution**: Поддерживайте versioning в payload для backward compatibility.

51. **CDC-based Outbox (без polling).**: Настройте Debezium на таблицу `outbox`. Покажите, что relay больше не нужен — PostgreSQL WAL → Kafka Connect → Kafka Topic напрямую. Сравните latency: polling (500 мс) vs CDC (<100 мс). Объясните trade-off: сложность инфраструктуры vs простота кода.

52. **Inbox testing**: Напишите тесты, которые отправляют duplicate messages и проверяют, что бизнес-логика выполняется только один раз.

53. **Outbox + Inbox сквозная демонстрация.**: Реализуйте сценарий: Сервис A записывает событие в Outbox, ретранслятор отправляет в Kafka, Сервис B получает через Inbox, обеспечивая ровно-однократную (effective exactly-once) обработку.

54. **Inbox vs application-level deduplication:**
    * Inbox: reliable, но требует БД
    * Application-level (Redis): faster, но Redis может потерять данные
    Используйте Inbox для critical messages, Redis для high-volume non-critical.

55. **Relay с Backoff и DLQ.**: Если Kafka недоступен, relay должен использовать exponential backoff для failed записей, не блокируя другие events. При `error_count > 10` — перемещать в `outbox_dlq`. Реализуйте отдельный обработчик DLQ с алертом.

56. **Атомарный Inbox (Дедупликация)**: Брокеры могут доставить событие дважды (At-Least-Once). При получении сообщения из Kafka, открой `sql.Tx`. 1) Сделай `INSERT INTO inbox_events (event_id)`. Если ловишь ошибку `UniqueViolation` (событие уже было) — делай `Rollback`, `Ack` брокеру и игнорируй. 2) Если ок, делай бизнес-логику (резервируй товары). 3) `tx.Commit()`.

57. **[Дедупликация]**: Если в Kafka прилетит дубликат (из задания 890), `INSERT INTO inbox` упадет с ошибкой `unique constraint violation` (так как `message_id` первичный ключ). Консьюмер должен проигнорировать эту ошибку (считать сообщение уже обработанным) и заакать (ack) сообщение в брокере.

58. **Сквозной Exactly-Once пайплайн**: Объедините ваши наработки: Сервис А (БД + Outbox) -> Kafka -> Воркер Б (Inbox + БД). Протестируйте систему: сымитируйте сетевой сбой (отправьте одно и то же сообщение в Kafka 3 раза подряд). Убедитесь, что на стороне Сервиса Б бизнес-данные обновились строго один раз, а в таблице `inbox_events` осталась только одна запись.

59. **Outbox в MongoDB.**: Используйте multi-document transaction (MongoDB 4.0+): в одной сессии `session.WithTransaction` — `orders.InsertOne()` + `outbox.InsertOne()`. Альтернатива: embedded array `events` внутри документа order (если events не нужны отдельно). Объясните ограничения размера документа (16 MB).

65. **[Высокая сложность — CDC вместо Polling]**: Опрос (`SELECT ... WHERE processed=false`) нагружает БД. Вместо Relay Worker используй CDC (Change Data Capture, `pglogrepl`). При INSERT в `outbox` PostgreSQL генерирует WAL-запись. Воркер читает WAL и отправляет в Kafka. Изучи библиотеку `github.com/riferrei/srclient` или Debezium.

66. **Очистка (Garbage Collection)**: Таблицы Outbox и Inbox растут бесконечно. Напиши Cron-джобу (на `time.Ticker`), которая раз в сутки делает `DELETE FROM outbox_events WHERE status = 'PROCESSED' AND created_at < NOW() - INTERVAL '7 days'`.

67. **Outbox Batching & Publisher Confirms**: Напишите Outbox-воркер для RabbitMQ. Воркер должен считывать пакет из 100 событий из таблицы `outbox`, отправлять их в RabbitMQ, дожидаться группового подтверждения доставки (Publisher Confirms, задача №404) и только после этого одной транзакцией помечать весь пакет как успешно отправленный в базе данных.

70. **Outbox poller vs CDC (Debezium):**
    * Poller: simpler, но polling overhead (100ms-1s latency)
    * CDC: real-time (ms latency), но сложнее в эксплуатации
    Используйте CDC для high-volume, poller для simpler setups.

71. **Inbox + Outbox combo**: Producer использует Outbox для publishing, Consumer использует Inbox для consuming. Это даёт end-to-end exactly-once semantics (на уровне бизнес-логики).

72. **Transactional Outbox — это must have.**: Никогда не делайте dual write (БД + Kafka) без Outbox. Это guaranteed source of inconsistency.
