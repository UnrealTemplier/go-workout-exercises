# Архитектурный контроль: Разработка корпоративных линтеров для golangci-lint

В этом файле собраны уникальные упражнения по теме **"Архитектурный контроль: Разработка корпоративных линтеров для golangci-lint"**, отсортированные по возрастанию сложности.

---

1. **Роль статического анализа в поддержании архитектуры Monorepo**: Изучите, почему ручное ревью кода (Code Review) не защищает крупные проекты от архитектурной деградации. Сформулируйте цель: автоматический контроль архитектурных правил, предотвращение утечек абстракций и обнаружение опасных антипаттернов Go на этапе компиляции и CI.

2. **Архитектура фреймворка golang.org/x/tools/go/analysis**: Разберите устройство стандартного фреймворка статического анализа Go: структура analysis.Analyzer, контекст выполнения analysis.Pass, сообщения об ошибках analysis.Diagnostic и механизм передачи межпакетных фактов analysis.Fact.

3. **Анатомия абстрактного синтаксического дерева (go/ast)**: Изучите ключевые интерфейсы и типы пакета go/ast: ast.Node, узлы объявлений ast.Decl (FuncDecl, GenDecl), операторы ast.Stmt (IfStmt, ForStmt, ReturnStmt) и выражения ast.Expr (CallExpr, Ident, SelectorExpr). Напишите утилиту визуализации AST.

4. **Информация о типах (go/types): переход от синтаксиса к семантике**: Анализ только синтаксического дерева слеп к реальным типам данных. Изучите структуру types.Info в analysis.Pass: карты Types, Defs, Uses. Покажите, как определить, реализует ли переменная интерфейс io.Closer или error.

5. **Создание первого статического анализатора на Go**: Напишите минимальный анализатор noempty: структура var Analyzer = &analysis.Analyzer{ Name: "noempty", Doc: "finds empty functions", Run: run }. Функция run обходит AST и выводит предупреждение при обнаружении функций с пустым телом.

6. **Обход AST с помощью ast.Inspect**: Изучите функцию ast.Inspect(node, func(n ast.Node) bool): покажите, как останавливать обход ненужных веток синтаксического дерева, возвращая false (например, не заходить внутрь тел анонимных функций).

7. **Регистрация предупреждений и позиционирование в коде**: Используйте метод pass.Reportf(node.Pos(), "format message %s", args): объясните, как структура token.Pos и token.FileSet преобразуют внутреннее смещение в точный номер строки и столбца в исходном файле разработчика.

8. **Фреймворк тестирования анализаторов: analysistest**: Подключите пакет golang.org/x/tools/go/analysis/analysistest. Организуйте тестовые файлы в папке testdata/src/a/. Используйте специальные маркерные комментарии // want "expected error message" для проверки срабатывания линтера.

9. **Линтер 1: Запрет context.Background() вне main() и тестов**: Разработайте анализатор nobackground: находит вызовы context.Background() или context.TODO() внутри бизнес-функций. Требуйте проброса входящего контекста через первый аргумент ctx context.Context.

10. **Линтер 2: Запрет хранения context.Context в структурах**: Разработайте анализатор structcontext: сканирует объявления структур ast.StructType и запрещает наличие полей типа context.Context (за исключением структур запросов). Объясните, почему хранение контекста в полях приводит к утечкам горутин.

11. **Линтер 3: Детекция пропущенных проверок ошибок (unhandled errors)**: Разработайте анализатор checkerr: находит вызовы функций, возвращающих тип error, результат которых присваивается пустому идентификатору _ = fn() или полностью игнорируется fn().

12. **Линтер 4: Контроль слоев Clean Architecture (Layer Imports)**: Разработайте архитектурный линтер cleanarch: запретите импорт пакета инфраструктуры (mycompany/pkg/infrastructure/*) или базы данных внутрь пакета доменных сущностей (mycompany/pkg/domain/*). Обеспечьте строгое соблюдение Dependency Inversion Principle.

13. **Инспекция директив импорта (ast.ImportSpec)**: В анализаторе слоев реализуйте проверку путей импортов: парсинг pass.Pkg.Imports() и синтаксических узлов ast.ImportSpec.Path.Value. Добавьте белый список разрешенных стандартных библиотек для доменного слоя.

14. **Линтер 5: Детекция неконтролируемых горутин (Unguarded Goroutines)**: Разработайте анализатор safego: находит ключевые слова go func() или go myFunc(). Требуйте, чтобы запуск горутины сопровождался увеличением счетчика sync.WaitGroup.Add(1) перед ней или выполнялся через одобренный корпоративный воркер-пул.

15. **Линтер 6: Запрет глобальных мутабельных переменных**: Разработайте анализатор noglobalstate: находит объявления var на уровне пакета. Разрешайте только константы const, ошибки var ErrNotFound = ... и потокобезопасные синглтоны, запрещая изменяемые глобальные мапы и срезы.

16. **Линтер 7: Проверка правильного вызова defer Body.Close()**: Разработайте анализатор httpclose: проверяет вызовы http.Get и client.Do. Убедитесь, что вызов defer resp.Body.Close() размещен СТРОГО ПОСЛЕ проверки if err != nil, предотвращая панику разыменования nil-указателя при сетевой ошибке.

17. **Линтер 8: Оптимизация выравнивания памяти структур (Field Alignment)**: Разработайте анализатор fieldalign: использует pass.TypesSizes для расчета размера структур и размера паддинга (Memory Padding). Если перестановка полей структуры уменьшает ее размер в памяти (например, с 24 байт до 16 байт), выводите предупреждение с рекомендацией оптимального порядка полей.

18. **Линтер 9: Запрет непроверенного приведения типов (Type Assertion Panic)**: Разработайте анализатор safetypeassert: находит выражения приведения типов x.(MyType). Требуйте обязательного использования безопасной формы с двумя переменными val, ok := x.(MyType) для предотвращения паники рантайма.

19. **Автоматическое исправление кода: SuggestedFixes**: Линтер должен не только ругать разработчика, но и уметь чинить ошибку! Реализуйте генерацию исправлений: создайте структуру analysis.SuggestedFix с заменой текста через analysis.TextEdit. Проверьте работу автоисправления через флаг -fix.

20. **Передача фактов между пакетами (Modular Analysis Facts)**: Некоторые проверки требуют анализа цепочки вызовов через несколько пакетов. Изучите экспорт и импорт фактов: pass.ExportObjectFact(obj, &myFact{}) и pass.ImportObjectFact(targetObj, &importedFact). Покажите, как пометить функцию как «блокирующую» и проверять ее вызовы в других пакетах.

21. **Сборка кастомного линтера как плагина golangci-lint**: Изучите систему плагинов golangci-lint: создайте интерфейс New(conf any) ([]*analysis.Analyzer, error). Скомпилируйте плагин командой go build -buildmode=plugin -o mylinters.so и подключите его в локальный запуск.

22. **Интеграция через Module Plugins в golangci-lint**: Начиная с современных версий golangci-lint, плагины можно компилировать напрямую без CGO с помощью утилиты сборки кастомного бинарника. Настройте конфигурацию сборки кастомного golangci-lint со встроенными корпоративными анализаторами компании.

23. **Конфигурация .golangci.yml для корпоративных проверок**: Напишите продакшен-файл .golangci.yml: включение стандартных линтеров (govet, staticcheck, errcheck, gocritic, revive), настройка исключений для тестов и интеграция кастомных правил анализа слоев.

24. **Оптимизация производительности анализатора**: В кодовой базе на 1 000 000 строк линтер не должен работать дольше нескольких секунд. Избегайте глубокого обхода типов там, где достаточно синтаксического анализа AST. Замерьте время работы анализатора с помощью флага профилирования go test -bench.

25. **Линтер 10: Запрет использования SQL-конкатенации (SQL Injection Prevention)**: Разработайте анализатор nosqlinjection: анализирует аргументы методов db.Query, db.Exec. Запретите использование fmt.Sprintf или конкатенации строк + при формировании SQL-запросов, принуждая разработчиков использовать позиционные плейсхолдеры ($1, ?).

26. **Интеграция линтеров в pre-commit хуки (Lefthook)**: Настройте быстрый запуск анализаторов перед коммитом с помощью lefthook или pre-commit: запуск проверок только для измененных файлов (git diff --staged) для мгновенной обратной связи разработчику (менее 1 секунды).

27. **Запуск линтеров в GitHub Actions с аннотациями в PR**: Настройте CI-пайплайн: запуск golangci-lint run --out-format=github-actions. Продемонстрируйте, как сообщения об ошибках вашего кастомного линтера автоматически подсвечиваются прямо в интерфейсе GitHub Pull Request на строках коммита.

28. **Минимизация ложноположительных срабатываний (False Positives)**: Протестируйте анализатор на популярных open-source проектах (например, gin, prometheus). Найдите ложные срабатывания, добавьте учет директив подавления //nolint:myanalyzer и специальных интерфейсных исключений.

29. **Линтер архитектурного соответствия API DTO и Domain Entities**: Разработайте линтер nodomaininapi: запрещает использование внутренних доменных сущностей (Domain Entities) в качестве аргументов или ответов внешних HTTP/gRPC хэндлеров, принуждая разработчиков создавать отдельные DTO-структуры (Data Transfer Objects).

30. **Корпоративный мета-линтер Enterprise Linter Suite на Go**: Объедините все созданные анализаторы в единый законченный пакет: правила Clean Architecture, контроль контекстов, проверка закрытия ресурсов, защита от SQL-инъекций, детектирование утечек горутин, автоисправление ошибок и документация по интеграции в корпоративный CI/CD.
