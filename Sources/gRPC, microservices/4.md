### Тема 79: Resilience и отказоустойчивость

692. Реализуйте **bulkhead pattern**: ограничьте количество параллельных запросов к каждому сервису через semaphore, чтобы падение одного сервиса не уронило всю систему.

694. **Финальный босс (Микросервисная платформа e-commerce):**
    Создайте систему из 5 сервисов:
    * **User Service:** gRPC для управления пользователями, JWT-аутентификация, mTLS.

    * Все сервисы используют interceptors для логирования, аутентификации, метрик.

### 💡 Золотые правила gRPC и микросервисов:

1. **Контракт превыше всего.** `.proto` файл — это API-контракт. Всегда версионируйте его (например, `package user.v1;`) и никогда не ломайте backward compatibility (не удаляйте поля, не меняйте их номера).

2. **Используйте interceptors для cross-cutting concerns.** Логирование, метрики, аутентификация, retry — всё это должно быть в interceptor'ах, а не в бизнес-логике каждого хендлера.

3. **Всегда устанавливайте deadline.** Без deadline RPC может висеть вечно, исчерпывая ресурсы. Используйте `context.WithTimeout` на клиенте и проверяйте `ctx.Err()` на сервере.

4. **Streaming требует backpressure.** Если сервер генерирует данные быстрее, чем клиент читает — TCP-буферы переполнятся и соединение разорвется. Всегда думайте о скорости потребления.

5. **gRPC-Gateway — это компромисс.** Он удобен для внешних API (где нужен REST/JSON), но для межсервисного общения используйте чистый gRPC (быстрее, эффективнее, поддерживает streaming).

6. **Observability обязателен.** В распределенной системе без distributed tracing (OpenTelemetry) вы не сможете отладить проблему, которая затрагивает 3+ сервиса.

7. **Resilience patterns — не опциональны.** Retry, circuit breaker, bulkhead, deadline propagation — это не "nice to have", это must have для production-систем.

8. **Service discovery через DNS.** В Kubernetes используйте DNS-имена сервисов (`service-name.namespace.svc.cluster.local`) и client-side load balancing. Не хардкодьте IP-адреса.

9. **Безопасность по умолчанию.** Используйте mTLS для межсервисного общения (Service Mesh типа Istio делает это автоматически). Для внешних API используйте JWT/OAuth2.

10. **Тестируйте контракты.** Используйте `buf breaking` для проверки, что изменения в `.proto` не ломают совместимость. Пишите интеграционные тесты для каждого сервиса.
