## Блок 25. Leader Election (Consul / etcd)

### Уровень 1. Базовые механизмы
297. **Базовая блокировка в etcd.** Реализуйте захват «блокировки» через `clientv3.Put` с `clientv3.WithLease(leaseID)` и `clientv3.WithPrevKV()`. Покажите, что второй процесс не может записать ключ, пока lease активен. Объясните, почему `TTL` + `KeepAlive` — сердце etcd-координации, а не просто `SET`/`GET`.
298. **Leader Election через etcd.** Запустите 3 процесса, которые конкурируют за ключ `/leader`. Используйте `clientv3.Concurrency.Election` (или ручной `Campaign` через `Txn` с `CreateRevision` compare). Покажите, что только один получает `leaderCh`, остальные ждут. Объясните роль `CreateRevision` в определении порядка.
299. **Consul Session + KV Lock.** Создайте Consul Session с `TTL=10s` и `Behavior=release`. Захватите KV-пару через `session` в `Acquire`. Покажите, что при `DestroySession` или истечении TTL блокировка снимается автоматически. Сравните с etcd: Consul использует health checks + session, etcd — lease.
300. **Обработка потери лидерства.** В leader-процессе запустите горутину, которая слушает `KeepAlive` ответы (или `Session.RenewPeriodic`). При ошибке (lease expired) — немедленно остановить обработку запросов (`atomic.StoreUint32(&isLeader, 0)`). Объясните, почему продолжение работы после lease expiration — это split-brain.

### Уровень 2. Отказоустойчивость и сетевые разделы
301. **Грациозный захват с задержкой (fencing old leader).** Новый узел при старте видит, что `/leader` занят lease, который ещё не истёк. Реализуйте ожидание `oldTTL * 1.5` перед попыткой захвата. Объясните, зачем нужен «grace period» (network delay может доставить KeepAlive позже, чем lease истекает на сервере).
302. **Распределённый cron (Leader-Only Scheduler).** Реализуйте сервис, где только лидер запускает `time.Ticker` и выполняет задачи (например, агрегация статистики). При `OnLeadershipChange` — остановить ticker, при захвате — запустить. Покажите, что при failover задача не дублируется (единственный лидер).
303. **Leader Election с приоритетом.** Узлы имеют `priority` (например, availability zone, hardware class). Реализуйте алгоритм: при попытке захвата лидерства узел записывает `/election/<node_id>` с value=priority. Лидер — узел с наименьшим приоритетом (или наибольшим). Объясните, как `clientv3.Txn` с `Cmp` позволяет реализовать CAS-логику.
304. **Consul: Service Check + Session.** Привяжите session к health check сервиса (`CheckTTL` или `CheckHTTP`). Если сервис становится `critical` — session invalidated, lock released автоматически. Покажите, что это даёт «failover по health», а не только по процессу.

### Уровень 3. Интеграция и split-brain защита
305. **HA-пair Active/Passive.** Два узла: active пишет heartbeat в etcd каждые 5 сек (`/heartbeat`), passive мониторит. При пропаже heartbeat > `TTL * 2` passive пытается стать active. Покажите race condition при одновременном promote (оба видят пропажу heartbeat). Реализуйте защиту через fencing token (см. Блок 27).
306. **Split-brain защита через Majority Check.** Лидер перед обработкой write должен убедиться, что видит большинство узлов кластера. Реализуйте: лидер читает `/members` и проверяет `len(members) >= quorum`. Объясните, почему etcd lease alone не защищает от partition (старый лидер может быть в изолированной partition и продлевать lease локально).
307. **Мульти-лидер в partition.** Сымитируйте network partition (iptables DROP между двумя группами узлов). Покажите, что minority (1 из 3) не может избрать лидера в etcd (quorum=2), но может думать, что он лидер, если lease ещё не истёк. Объясните, почему это не проблема etcd, а проблема приложения, которое не проверяет connectivity.
308. **Интеграция с gRPC/HTTP.** Реализуйте middleware: только лидер обрабатывает mutating запросы (`POST`/`PUT`/`DELETE`). Followers отвечают `307 Temporary Redirect` с адресом текущего лидера (или `503` + `X-Current-Leader` header). Объясните, как service discovery (Consul DNS или etcd) помогает клиентам найти лидера.

### Уровень 4. Production и observability
309. **Мониторинг Leader Election.** Реализуйте метрики: `leader_election_is_leader` (gauge: 0/1), `leader_transitions_total` (counter), `lease_renew_failures_total`, `leader_heartbeat_latency_seconds`. Настройте алерт: если `leader_transitions > 5 за 5 минут` — flapping (возможно, network instability или GC pauses).
310. **Graceful Step Down с drain.** При получении `SIGTERM` лидер должен: (1) отказаться от новых lease renew, (2) дождаться завершения текущих in-flight запросов (context с timeout), (3) удалить `/leader` ключ вручную, (4) exit. Объясните, почему это быстрее, чем ждать TTL expiration.

## Блок 26. Интеграция протокола Raft (HashiCorp Raft)

### Уровень 1. Запуск и базовые операции
311. **Однонодовый кластер.** Создайте FSM (Finite State Machine) на Go: `map[string]string` с `Apply([]byte)` и `Snapshot()`. Интегрируйте `hashicorp/raft`, запустите один узел с `BootstrapCluster`. Выполните `raft.Apply([]byte("set foo=bar"), timeout)` и покажите, что FSM обновился. Объясните, что `Apply` — это единственный способ изменить состояние в Raft.
312. **Bootstrap кластера из 3 узлов.** Настройте `raft.Config` (LocalID, SnapshotInterval, HeartbeatTimeout), `raft.NetworkTransport` (TCP). Запустите 3 узла на разных портах. Покажите, что кластер автоматически выбирает лидера (LeaderObserved channel). Объясните, почему нужен `BootstrapCluster` только один раз, а потом `AddVoter`.
313. **Лидер и Follower.** Реализуйте endpoint: лидер принимает write-команды, follower отклоняет с `not leader`. Покажите, что чтение с follower возвращает данные, но они могут быть stale (не linearizable). Объясните разницу между `raft.StateLeader`, `StateFollower`, `StateCandidate`.
314. **Log Replication.** Выполните 1000 `raft.Apply` подряд. Покажите, что все 3 узла имеют одинаковый `LastIndex()` и FSM state. Объясните `commitIndex` (применён на majority) vs `lastLogIndex` (записан локально).

### Уровень 2. Snapshotting и membership
315. **Snapshotting.** Реализуйте `FSM.Snapshot()` — сериализация `map[string]string` в `io.Writer` (например, gob/json). Настройте `SnapshotInterval = 20s`, `SnapshotThreshold = 8192`. Покажите, что Raft автоматически вызывает `Snapshot` и создаёт файл снимка. Объясните, зачем нужен snapshot (ограничение роста лога).
316. **Log Compaction и восстановление.** После snapshot старые логи удаляются. Остановите follower, удалите его log, перезапустите. Покажите, что лидер отправляет `InstallSnapshot` RPC, follower восстанавливает FSM из snapshot, затем догоняет по новым логам. Объясните `Restore(io.ReadCloser)` в FSM.
317. **Добавление узла (Membership Change).** Используйте `raft.AddVoter` для добавления 4-го узла в работающий кластер. Покажите, что кластер переконфигурируется без downtime. Объясните, как HashiCorp Raft реализует membership changes (одноэтапное добавление, в отличие от joint consensus в оригинальном Raft).
318. **Удаление узла.** Удалите follower через `raft.RemoveServer`. Покажите, что кластер продолжает работать с новым quorum. Объясните, почему удаление лидера требует перевыборов, и как `RemoveServer` с `ShutdownOnRemove` влияет на поведение.

### Уровень 3. Сетевые разделы и consistency
319. **Network Partition (Majority/Minority).** Сымитируйте partition на 5 узлов: 2 узла изолированы от 3. Покажите, что minority (2) не может коммитить записи (не достигает quorum), majority (3) продолжает работать. Объясните, почему это предотвращает split-brain на уровне данных.
320. **Leader Step Down.** Изолируйте текущего лидера (drop пакеты к majority). Покажите, что лидер переходит в `StateFollower` (step down) по таймауту, а majority избирает нового лидера. При восстановлении сети старый лидер становится follower. Объясните роль `Term` (epoch) в отклонении stale команд.
321. **Linearizable Read.** Реализуйте read-through-raft: чтение выполняется как `raft.Apply` dummy command (`noop`), после commit возвращается актуальное значение. Сравните с «dirty read» с follower. Объясните, почему `raft.Barrier()` (или `raft.Apply` + `Future.Error()`) даёт linearizable read.
322. **FSM Thread-Safety.** Реализуйте FSM с `sync.RWMutex`: `Apply` пишет, `Snapshot` читает. Покажите, что `Snapshot` может вызываться параллельно с `Apply` (Raft вызывает Snapshot в отдельной горутине). Объясните, почему `Restore` блокирует Apply и Snapshot.

### Уровень 4. Интеграция и production
323. **Persistent FSM с BoltDB.** Реализуйте FSM, хранящий state в `boltdb` (или `badger`). `Apply` — `db.Update`, `Snapshot` — `db.View` + копия в `io.Writer`. Объясните, почему in-memory map не подходит для production (потеря данных при crash до snapshot).
324. **Observability Raft.** Реализуйте метрики: `raft_state` (leader/follower/candidate), `last_log_index`, `commit_index`, `fsm_apply_latency_seconds`. Настройте алерт: если `commit_index` отстаёт от `last_log_index` на >1000 — возможна network partition или slow follower.
325. **Raft как распределённый WAL.** Используйте Raft только для согласования порядка записей, а FSM — это projection в PostgreSQL/ClickHouse. Покажите, что Raft гарантирует порядок, а FSM может быть восстановлена из лога. Свяжите с Блоком 23 (Outbox): Raft-лог как единый источник правды.

## Блок 27. Распределённые блокировки и Fencing Tokens

### Уровень 1. Базовые блокировки
326. **Redis SET NX EX.** Реализуйте lock: `SET lock:resource <random_value> NX EX 30`. Unlock через Lua-скрипт: удалить только если `value` совпадает. Объясните, почему нужен уникальный `random_value` (UUID) и почему `DEL` без проверки — опасен (можно удалить чужой lock).
327. **etcd Mutex.** Используйте `clientv3/concurrency.Mutex`. Захватите `Lock(ctx)`, выполните критическую секцию, `Unlock()`. Покажите, что при crash процесса lease истекает и lock автоматически освобождается. Объясните, почему это надёжнее Redis (lease bound to TTL, not client connection).
328. **PostgreSQL Advisory Lock.** Реализуйте `pg_advisory_lock(key)` и `pg_advisory_unlock(key)` через `database/sql`. Сравните с Redis/etcd: нет network partition между БД и приложением (если они в одном DC), но нет автоматического release при смерти приложения (требуется session termination).

### Уровень 2. Redlock, Lease и Race Conditions
329. **Redlock Algorithm (упрощённый).** Реализуйте: 5 Redis-нод, acquire lock на majority (>=3) с одинаковым TTL, clock drift margin. Release — удаление на всех нодах. Объясните критику Martin Kleppmann: clock skew, delay между acquire и actual lock, феномен «временной дыры» (lock истекает до окончания работы).
330. **Keepalive при длинной операции.** Операция занимает 60 сек, lock TTL = 30 сек. Реализуйте горутину, которая каждые 10 сек продлевает lease (Redis `PEXPIRE` или etcd `KeepAlive`). При завершении операции — stop renew, release lock. Объясните, почему `max_extension_count` защищает от infinite loop при hung process.
331. **Проблема Delay (GC Pause, Network Lag).** Реализуйте симуляцию: узел захватил lock (TTL=5с), затем GC pause 10 сек (или `time.Sleep`). Lease истекает, другой узел захватывает lock. Первый узел просыпается и продолжает работу в критической секции. Покажите, что **два узла одновременно владеют lock**.

### Уровень 3. Fencing Tokens
332. **Fencing Token: Monotonic Counter.** Реализуйте центральный сервис (etcd или PostgreSQL sequence), который выдаёт monotonic token при каждом захвате lock. Процесс получает token=42, выполняет `UPDATE accounts SET balance = 100, token = 42 WHERE token < 42`. Объясните, как storage отклоняет stale операции (token < current).
333. **Fencing с etcd Revision.** Используйте `CreateRevision` из etcd как fencing token. При захвате lock через `clientv3.Txn` получите `CreateRevision`. Все последующие writes в БД включают `WHERE revision >= $createRevision`. Объясните, почему etcd revision — идеальный fencing token (strictly monotonic, persistent, replicated).
334. **Distributed Lock в Saga.** Свяжите с Блоком 22: Saga Orchestrator перед выполнением шага захватывает lock на `saga_id` + `step_index`. Это предотвращает dual execution при split-brain (два orchestrator-а думают, что они primary). Покажите интеграцию: `Lock` → `Execute Step` → `Store Result` → `Unlock`.
335. **Guard Row в БД.** Реализуйте fencing без внешнего coordinator: в таблице `locks` храните `resource_id`, `owner_id`, `token`, `expires_at`. При захвате: `INSERT ... ON CONFLICT DO UPDATE SET token = token + 1, expires_at = NOW() + TTL`. При операции: проверяйте `token` в `WHERE`. Объясните, почему это работает даже при delay (storage — единственный источник truth).

### Уровень 4. Семафоры, Fairness и Production
336. **Распределённый Semaphore.** Реализуйте semaphore с max=5 через Redis (`ZADD` с timestamp + `ZREMRANGEBYSCORE` для cleanup) или etcd (lease-based counting). Покажите fair vs unfair: fair — FIFO очередь ожидания, unfair — первый кто успел. Объясните, почему Redis Redlock не подходит для fair semaphore.
337. **TryLock с Deadline.** Реализуйте `TryLock(ctx, timeout)` через etcd Watch: если ключ занят, ждём `DELETE` event с `ctx.Done()` таймаутом. Сравните с busy-polling. Объясните, почему Watch эффективнее (нет нагрузки на etcd), но сложнее в реализации.
338. **RMW с Lock + Fencing.** Реализуйте полный цикл: (1) acquire lock + получить token, (2) `SELECT balance FROM accounts WHERE id = 1`, (3) `UPDATE accounts SET balance = balance - 10, token = $token WHERE token < $token`. Покажите, что даже если lock «висит» (delay), stale process не может перезаписать данные.
339. **Производительность: сравнение.** Бенчмарк: 1000 конкурентных goroutines, каждая пытается захватить lock, увеличить counter, release. Сравните: Redis (single node), Redis Redlock (5 nodes), etcd, PostgreSQL advisory lock, ZooKeeper. Объясните latency/throughput trade-offs и когда что выбирать.
340. **Production Checklist.** Реализуйте защиту: `max_lock_hold_time` (алерт, если lock held > 60s), `lease_renew_limit` (не более 10 renews), `lock_staleness_check` (heartbeat внутри критической секции). Объясните, почему distributed lock — это не mutex, а «вероятностная защита с fencing», и без fencing token production-небезопасен.

## Как встроить в общий план обучения

**Рекомендуемый порядок прохождения:**

1. **Блок 25 (Leader Election)** — начните после Блока 24 (Idempotency), так как leader election — это частный случай координации, требующий понимания TTL и race conditions. Знания из Блока 1 (GMP, `sync`) помогут понять, почему in-memory leader election не работает при распределении.
2. **Блок 27 (Distributed Locks)** — проходите параллельно с Leader Election, так как оба используют etcd/Consul и сталкиваются с одной проблемой: lease expiration + network delay. Fencing Tokens — это мост между блокировками и консистентностью.
3. **Блок 26 (Raft)** — финальный блок координации. Требует понимания всего предыдущего: почему leader election нужен consensus, почему distributed locks без consensus — ненадёжны, как Raft решает проблему split-brain на уровне алгоритма, а не инфраструктуры.

**Ключевые инструменты и команды для тренировки:**
```bash
# etcd
etcdctl put --lease=12345 /leader "node-1"
etcdctl watch /leader --prev-kv
etcdctl lease keep-alive 12345

# Consul
curl -X PUT "http://localhost:8500/v1/session/create" -d '{"TTL":"10s"}'
curl -X PUT "http://localhost:8500/v1/kv/leader?acquire=<session_id>" -d "node-1"

# Redis Redlock
redis-cli -p 6371 SET lock:resource "val" NX PX 30000
redis-cli -p 6371 EVAL "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end" 1 lock:resource val

# Raft cluster
# Запуск 3 узлов с разными -raft-addr и -http-addr
# Проверка лидера: curl http://localhost:11001/raft/stats
```

**Что фиксировать в результатах:**
- Для Leader Election: логи переключений (timestamp old leader → new leader), метрики flapping, proof of no split-brain (iptables + concurrent writes).
- Для Raft: `raft stats` (term, commit_index, last_log_index), демонстрация partition (minority rejects writes), snapshot files.
- Для Locks: симуляция delay (`time.Sleep` > TTL) + proof, что fencing token отклоняет stale write, бенчмарк latency.

Если нужно — могу детально расписать **любое конкретное упражнение** с шаблоном кода, или выдать финальный блок на тему *«Каналы в рантайме, netpoller, sync.Pool, memory model и race detector»*.
