### Тема 176: Leader Election — Основы (Consul, etcd)
*Leader Election решает проблему: в кластере из N узлов только один должен выполнять критическую работу (например, запуск cron jobs, координация).*

1881. **Проблема без leader election:** Покажите проблему: 3 инстанса сервиса запускают cron job одновременно. Результат: duplicate processing, data corruption.

1882. **Consul setup:** Поднимите Consul cluster из 3 серверов через Docker Compose. Изучите Consul UI на порту 8500.

1883. **Consul session creation:** Создайте session через `consul.Session().Create()` с TTL 15 секунд и behavior `delete` (при session expiry ключ удаляется).

1884. **Consul lock acquisition:** Попытайтесь захватить lock через `consul.KV().Acquire()` с session ID. Первый успешный — leader.

1885. **Leader detection:** Каждый инстанс проверяет, является ли он leader'ом через проверку session ID в KV. Если `key.Session == mySession` — я leader.

1886. **Leader heartbeat:** Leader периодически обновляет session через `session.Renew()` для предотвращения expiry.

1887. **Leader failover:** Убейте leader процесс. Через TTL (15s) session expires, lock освобождается, другой инстанс захватывает lock.

1888. **Consul watch:** Используйте `consul.Watch()` для уведомления при изменении leader key. Все инстансы узнают о смене leader'а мгновенно.

1889. **etcd setup:** Поднимите etcd cluster из 3 узлов через Docker Compose. Изучите etcd API.

1890. **etcd lease creation:** Создайте lease через `client.Grant()` с TTL 15 секунд.

1891. **etcd leader election:** Используйте `client.Campaign()` из `concurrency` пакета для участия в выборах.

1892. **etcd leader observation:** Используйте `client.Observe()` для отслеживания текущего leader'а.

1893. **etcd leader resignation:** Leader может добровольно уйти через `client.Resign()`. Это запускает новые выборы.

1894. **Consul vs etcd для leader election:**
    * Consul: встроенный DNS, health checks, multi-datacenter
    * etcd: быстрее, проще, часть Kubernetes
    Используйте etcd если уже в K8s, Consul для standalone distributed systems.

1895. **Leader election metrics:** Экспортируйте метрики: `leader_elections_total`, `leader_tenure_seconds`, `failover_count`.

1896. **Split-brain protection:** При network partition оба partition могут считать себя leader'ом. Как защититься? Используйте quorum-based consensus (Consul/etcd уже делают это).

1897. **Fencing token в leader election:** При получении leadership генерируйте монотонно возрастающий fencing token. Используйте его для защиты от stale leaders.

1898. **Leader election + graceful shutdown:** При SIGTERM leader добровольно resign'ит, чтобы ускорить failover.

1899. **Multiple leaders для разных задач:** Используйте разные leader keys для разных задач: `leader/cron`, `leader/reconciliation`, `leader/metrics_aggregation`.

1900. **Leader election testing:** Напишите интеграционные тесты, которые:
    * Запускают 3 инстанса
    * Проверяют, что только один leader
    * Убивают leader
    * Проверяют, что новый leader избран в течение TTL

### Тема 177: Leader Election — Продвинутые паттерны
1901. **Standby leader:** Один primary leader, один standby. При failover standby становится leader мгновенно (не ждет election).

1902. **Leader priority:** Назначьте priority для каждого инстанса. При равных условиях leader'ом становится инстанс с высшим priority.

1903. **Geographic leader election:** В multi-region setup избирайте leader в том регионе, где большинство клиентов для снижения latency.

1904. **Leader health checks:** Leader периодически публикует health status. Если health check fails, другие инстансы форсируют новые выборы.

1905. **Leader lease extension:** Leader продлевает lease только если успешно выполняет свою работу. Если работа stuck — lease expires, failover.

1906. **Election backoff:** После проигрыша в выборах инстанс ждет random backoff перед следующей попыткой. Это предотвращает election storms.

1907. **Leader election в Kubernetes:** Используйте Kubernetes Lease objects для leader election внутри K8s cluster (как делает controller-manager).

1908. **client-go leader election:** Используйте `k8s.io/client-go/tools/leaderelection` для production-grade leader election в K8s.

1909. **Leader election callbacks:** Реализуйте callbacks: `OnStartedLeading()`, `OnStoppedLeading()`, `OnNewLeader()`.

1910. **Leader election + distributed cron:** Только leader запускает cron jobs. При failover новый leader подхватывает schedule.

1911. **Leader election + task queue:** Leader координирует распределение задач между worker'ами. При failover новый leader перераспределяет задачи.

1912. **Leader election + metrics aggregation:** Только leader агрегирует метрики со всех инстансов и публикует в Prometheus.

1913. **Leader election + cache warming:** Только leader прогревает кэш при startup. Остальные инстансы ждут сигнала от leader'а.

1914. **Leader election + schema migrations:** Только leader запускает БД миграции при деплое. Остальные инстансы ждут завершения.

1915. **Leader election + garbage collection:** Только leader запускает cleanup jobs (удаление старых записей, orphaned resources).

1916. **Leader election observability:** Логируйте каждое election event: `Election started`, `Leader elected: instance-2`, `Leader resigned`, `Failover triggered`.

1917. **Leader election alerting:** Алерт при:
    * Частые failover (>3 за час) — признак нестабильности
    * Нет leader > 2x TTL — quorum lost
    * Leader tenure < 1 min — признак crash loop

1918. **Leader election + feature flags:** Leader может включать/выключать feature flags для всего кластера через distributed config.

1919. **Leader election + rate limiting:** Leader координирует global rate limit across all instances.

1920. **Leader election chaos testing:** Используйте chaos engineering:
    * Убивайте leader случайно
    * Симулируйте network partitions
    * Замедляйте leader heartbeat
    Проверяйте, что система корректно восстанавливается.

### Тема 178: Raft Protocol — Основы
*Raft — это consensus algorithm для управления replicated state machine. Используется в etcd, Consul, CockroachDB, TiKV.*

1921. **Raft концепции:** Изучите 5 ключевых концепций:
    * Leader (один в кластере)
    * Followers (реплицируют state)
    * Candidates (участвуют в выборах)
    * Terms (логические периоды времени)
    * Log entries (команды для state machine)

1922. **Raft flow:** Поймите 3 фазы:
    * Leader election (выборы leader'а)
    * Log replication (репликация команд)
    * Safety (гарантии консистентности)

1923. **HashiCorp Raft setup:** Используйте `github.com/hashicorp/raft` для создания Raft cluster из 3 узлов.

1924. **Raft node bootstrap:** Bootstrap первый узел через `raft.BootstrapCluster()`.

1925. **Raft node join:** Добавьте второй и третий узлы через `raft.AddVoter()`.

1926. **Raft transport layer:** Реализуйте transport layer для общения между узлами (TCP/HTTP).

1927. **Raft log store:** Используйте `raft-boltdb` для persistent storage Raft log.

1928. **Raft snapshot store:** Реализуйте snapshot store для periodic snapshots state machine.

1929. **Raft FSM (Finite State Machine):** Реализуйте `raft.FSM` интерфейс:
    * `Apply(log)` — применяет команду к state
    * `Snapshot()` — создаёт snapshot
    * `Restore(snapshot)` — восстанавливает из snapshot

1930. **Raft Apply:** Leader применяет команду через `raft.Apply(data, timeout)`. Команда реплицируется на majority узлов.

1931. **Raft quorum:** Поймите quorum: для 3 узлов quorum = 2. Для 5 узлов quorum = 3. Без quorum кластер не может принимать writes.

1932. **Raft leader election:** Изучите, как Raft избирает leader'а через RequestVote RPC.

1933. **Raft log replication:** Изучите, как leader реплицирует log entries через AppendEntries RPC.

1934. **Raft commit index:** Команда считается committed, когда реплицирована на majority. Только committed entries применяются к FSM.

1935. **Raft snapshots:** При достижении threshold (например, 10000 log entries) создавайте snapshot и truncate log.

1936. **Raft log compaction:** Snapshot + log truncation = log compaction. Это предотвращает бесконечный рост log.

1937. **Raft membership changes:** Добавляйте/удаляйте узлы через `raft.AddVoter()`, `raft.RemoveServer()`. Raft гарантирует safety при membership changes.

1938. **Raft single-server cluster:** Для dev/test запустите single-node Raft cluster (bootstrap с одним узлом).

1939. **Raft metrics:** Экспортируйте метрики: `raft_state` (leader/follower/candidate), `raft_term`, `raft_commit_index`, `raft_applied_index`.

1940. **Raft vs Paxos:** Изучите, почему Raft проще для понимания и реализации, чем Paxos, при эквивалентных гарантиях.

### Тема 179: Raft — Продвинутая реализация
1941. **Raft-based key-value store:** Реализуйте distributed KV store поверх Raft:
    * `Set(key, value)` → Raft Apply
    * `Get(key)` → read from local FSM (если leader) или forward to leader
    * `Delete(key)` → Raft Apply

1942. **Raft linearizable reads:** Для strong consistency reads forwarding to leader обязателен. Иначе можете прочитать stale data.

1943. **Raft read-only optimization:** Используйте `raft.ReadIndex()` для read-only queries без log replication (быстрее).

1944. **Raft batching:** Batch multiple Apply calls для снижения overhead.

1945. **Raft pipeline:** Pipeline AppendEntries RPCs для повышения throughput.

1946. **Raft pre-vote:** Реализуйте Pre-Vote extension для предотвращения disruptions при network partitions.

1947. **Raft leader lease:** Leader lease для read optimization: если leader уверен, что нет других leaders, можно читать локально.

1948. **Raft multi-group:** Для масштабирования разделите data на multiple Raft groups (как в CockroachDB, TiKV).

1949. **Raft + application state:** Синхронизируйте application state через Raft:
    * Configuration

    * Leader election state

1950. **Raft snapshot streaming:** Для больших state используйте streaming snapshots вместо in-memory snapshots.

1951. **Raft log shipping:** Для disaster recovery ship Raft log в другой datacenter для warm standby.

1952. **Raft cluster health:** Мониторьте:

1953. **Raft failure scenarios:** Тестируйте:

1954. **Raft recovery:** После crash узел восстанавливает state из snapshot + log replay.

1955. **Raft + etcd:** Изучите, как etcd использует Raft internally. etcd — это Raft-based KV store.

1956. **Raft + Consul:** Изучите, как Consul использует Raft для consensus в server nodes.

1957. **Raft performance tuning:**
    * Optimize snapshot threshold

    * Batch Apply calls

1958. **Raft observability:** Логируйте:
    * Leadership changes

### Тема 180: Distributed Locks — Redlock, etcd locks
*Распределенные блокировки нужны, когда несколько процессов должны эксклюзивно accessing shared resource.*

1961. **Проблема без distributed locks:** Два инстанса одновременно обрабатывают один order. Результат: double payment, data corruption.

1962. **Redis single-node lock:** Простейший distributed lock:
    ```
    SET lock_key "owner" NX EX 30
    ```
    Проблема: если Redis упадёт, lock потерян.

1963. **Redlock algorithm:** Изучите Redlock от Salvatore Sanfilippo (antirez):
    * 5 независимых Redis instances
    * Lock acquired, если majority (3/5) согласились
    * Timeout + retry logic

1964. **Redlock implementation:** Реализуйте Redlock через `github.com/go-redsync/redsync`:
    ```go
    rs := redsync.New(pools)
    mutex := rs.NewMutex("my-lock", redsync.WithExpiry(30*time.Second))
    mutex.Lock()
    defer mutex.Unlock()
    ```

1965. **Redlock controversy:** Изучите критику Redlock от Martin Kleppmann. Redlock не даёт true distributed consensus, только best-effort locking.

1966. **etcd distributed lock:** Используйте etcd для reliable distributed locks:
    ```go
    session, _ := concurrency.NewSession(client)
    mutex := concurrency.NewMutex(session, "/locks/my-lock")
    mutex.Lock(ctx)
    defer mutex.Unlock(ctx)
    ```

1967. **etcd lock + lease:** etcd lock автоматически освобождается при session expiry (lease TTL).

1968. **etcd lock + fencing token:** При получении lock извлекайте `CreateRevision` как fencing token. Используйте его для защиты от stale locks.

1969. **Consul distributed lock:** Используйте Consul для locks:
    ```go
    lock, _ := consul.LockKey("my-lock")
    leaderCh, _ := lock.Lock(nil)
    defer lock.Unlock()
    ```

1970. **Lock timeout:** Всегда устанавливайте timeout на lock acquisition. Иначе deadlock при hung process.

1971. **Lock retry with backoff:** Если lock не получен, retry с exponential backoff + jitter.

1972. **Lock heartbeating:** Для long-running operations периодически продлевайте lock (extend TTL).

1973. **Lock scope:** Минимизируйте critical section под lock. Не держите lock дольше необходимого.

1974. **Read-write locks:** Для read-heavy workloads используйте read-write locks (multiple readers, single writer).

1975. **Lock hierarchy:** Для multiple locks всегда захватывайте в одинаковом порядке для предотвращения deadlocks.

1976. **Lock metrics:** Мониторьте:
    * Lock acquisition latency
    * Lock hold time
    * Lock contention rate
    * Lock timeout rate

1977. **Lock alerting:** Алерт при:
    * High lock contention (>50% timeout rate)
    * Long lock hold times (>1 min)
    * Lock acquisition failures

1978. **Lock testing:** Напишите тесты, которые:
    * Запускают N concurrent goroutines
    * Каждая пытается захватить lock
    * Проверяют, что только одна goroutine в critical section одновременно

1979. **Lock chaos testing:**
    * Kill process holding lock
    * Simulate network partition
    * Verify lock released after TTL

1980. **Финальный босс (Distributed Task Scheduler):**
    Создайте production-grade distributed task scheduler:
    
    **Architecture:**
    * **3 scheduler nodes** для HA
    * **Leader election** через etcd для coordinator
    * **Raft cluster** для distributed state (task queue, worker registry)
    * **Distributed locks** для task execution (один worker per task)
    
    **Leader responsibilities:**
    * Task assignment to workers
    * Worker health monitoring
    * Task timeout detection
    * Metrics aggregation
    
    **Worker responsibilities:**
    * Execute assigned tasks
    * Heartbeat to leader
    * Acquire distributed lock before task execution
    * Use fencing tokens для защиты от stale workers
    
    **Task lifecycle:**
    1. Client submits task → leader adds to Raft state
    2. Leader assigns task to worker → Raft Apply
    3. Worker acquires lock → executes task
    4. Worker reports completion → leader updates Raft state
    5. If worker fails → leader reassigns task (with fencing token)
    
    **Reliability:**
    * **Raft replication** для task queue persistence
    * **Leader failover** при crash (automatic через etcd)
    * **Worker failover** при crash (task reassigned)
    * **Fencing tokens** для защиты от stale workers
    * **Idempotency** для task execution (task ID как idempotency key)
    
    **Scaling:**
    * **Horizontal scaling:** add more scheduler nodes
    * **Worker pool:** dynamic worker scaling
    * **Task prioritization:** high-priority tasks first
    * **Rate limiting:** per-client task submission limits
    
    **Observability:**
    * **Metrics:** task queue depth, task latency, worker utilization, leader election frequency
    * **Traces:** каждый task как distributed trace
    * **Logs:** task lifecycle events, lock acquisition, leader changes
    * **Alerts:** high task queue depth, worker failures, leader instability
    
    **Testing:**
    * **Unit tests:** task scheduling logic, lock acquisition
    * **Integration tests:** Raft replication, leader election
    * **Chaos tests:** kill leader, kill workers, network partitions
    * **Load tests:** 10k tasks/minute, 100 concurrent workers
    
    **Production features:**
    * **Task retries** с exponential backoff
    * **Dead letter queue** для failed tasks
    * **Task cancellation** через distributed signal
    * **Task dependencies** (DAG execution)
    * **Multi-tenancy** с per-tenant quotas
    * **Webhook notifications** для task completion

### 💡 Золотые правила распределенного консенсуса:

1. **Leader election обязателен для singleton задач.** Если задача должна выполняться ровно одним инстансом (cron jobs, migrations, reconciliation) — используйте leader election через Consul/etcd.

2. **Quorum — это закон.** Для 3 узлов quorum = 2. Для 5 узлов quorum = 3. Без quorum кластер не может принимать writes. Всегда используйте odd number of nodes (3, 5, 7).

3. **Fencing tokens защищают от stale leaders/workers.** При получении leadership/lock генерируйте монотонно возрастающий token. Используйте его для защиты от race conditions.

4. **TTL обязателен для locks.** Без TTL hung process будет держать lock вечно. Всегда устанавливайте expiry и heartbeating для long-running operations.

5. **Raft для strong consistency.** Если нужна distributed state machine с linearizable semantics — используйте Raft (etcd, Consul, HashiCorp Raft).

6. **Redlock — это best-effort, не consensus.** Redlock подходит для non-critical locks. Для critical data используйте etcd/Consul locks или Raft.

7. **Minimize critical section.** Держите lock только для essential operations. Не делайте I/O, network calls под lock если возможно.

8. **Lock hierarchy для multiple locks.** Всегда захватывайте locks в одинаковом порядке для предотвращения deadlocks.

9. **Leader failover testing.** Регулярно тестируйте failover: убивайте leader, проверяйте, что новый leader избирается в течение TTL.

10. **Split-brain protection.** При network partition оба partition могут считать себя leader'ом. Используйте quorum-based consensus (Consul/etcd/Raft) для защиты.

11. **Election backoff.** После проигрыша в выборах ждите random backoff перед следующей попыткой. Это предотвращает election storms.

12. **Leader health checks.** Leader должен периодически публиковать health status. Если health check fails — форсируйте новые выборы.

13. **Raft snapshot threshold.** Настройте snapshot threshold (например, 10k log entries) для предотвращения бесконечного роста log.

14. **Raft linearizable reads.** Для strong consistency reads forwarding to leader обязателен. Иначе можете прочитать stale data.

15. **Lock metrics критичны.** Мониторьте lock acquisition latency, hold time, contention rate. High contention = performance bottleneck.

16. **Idempotency + distributed locks.** Даже с distributed locks используйте idempotency keys. Lock может быть lost (TTL expiry), task может быть executed twice.

17. **Fencing token use case:** Worker A получает lock с token=100, начинает task. Worker A crashes. Lock expires. Worker B получает lock с token=101, начинает task. Worker A восстанавливается, пытается завершить task с token=100. Storage system rejects write с stale token=100. Это защита от split-brain.

18. **Raft production deployment:**
    * Odd number of nodes (3, 5, 7)
    * Geographically distributed для HA
    * Regular backups of snapshots
    * Monitoring + alerting
    * Chaos testing

19. **Leader election + graceful shutdown.** При SIGTERM leader добровольно resign'ит для ускорения failover.

20. **Test failure scenarios.** Happy path testing недостаточно. Тестируйте:
    * Leader crash
    * Network partition
    * Lock holder crash
    * Stale lock holder
    * Quorum loss
