Распределенный консенсус — это вершина компьютерной науки, с которой сталкиваются бэкенд-разработчики. Когда ты строишь высокодоступные системы (HA), тебе нужно, чтобы несколько серверов договорились, кто из них главный (Leader Election), и чтобы все они имели одинаковое состояние (Replicated State Machine). 

А еще распределенные блокировки таят в себе страшную опасность — гонки из-за GC пауз, от которых спасают только Fencing Tokens.

Здесь **25 упражнений** (с 906 по 930), которые проведут тебя через консенсус, Raft и защиту от самых коварных race conditions.

---

### Блок 101: Выборы лидера (Leader Election) через Consul и etcd
*Цель: Научиться координировать работу нескольких инстансов приложения, гарантируя, что только один из них выполняет критическую работу.*

906. **[etcd Lease]** Подними etcd в Docker. Подключись через `go.etcd.io/etcd/client/v3`. Создай Lease (аренду) с TTL 10 секунд. Запиши ключ `/leader` с этим lease.
907. **[KeepAlive]** Если процесс умрет, etcd должен удалить ключ через 10 секунд. Напиши горутину, которая постоянно отправляет `KeepAlive` запросы, чтобы продлить аренду, пока процесс жив.
908. **[Борьба за лидерство]** Запусти 3 инстанса твоего Go-приложения. Каждый пытается выполнить `etcd.Txn` (Transaction): `If(key /leader does not exist) Then(Put /leader with lease) Else(Get /leader)`. Убедись, что только один становится лидером, а остальные видят чужой ключ.
909. **[Watch и Failover]** Останови инстанс-лидер (убей процесс). Оставшиеся 2 инстанса должны слушать изменения ключа `/leader` через `etcd.Watcher`. Когда ключ исчезнет (TTL истек), они должны мгновенно начать новую борьбу за лидерство.
910. **[Consul Sessions]** Реализуй выборы лидера через HashiCorp Consul. Создай сессию (`consul.Session.Create`), затем вызови `consul.KV.Acquire` для ключа `service/leader`.
911. **[Каверзный кейс — Split Brain (Network Partition)]** Раздели сеть между лидером и etcd. Лидер потерял связь, но продолжает работать (он думает, что он все еще лидер). etcd истекает TTL ключа и выбирает нового лидера. Теперь у тебя два лидера! Реализуй паттерн: лидер должен *периодически* проверять свое лидерство (делать `etcd.Txn` с проверкой, что его ключ все еще существует перед выполнением работы).
912. **[Высокая сложность — Active/Passive Failover]** Создай систему из двух инстансов: Active и Passive. Passive стоит в режиме горячей замены. Когда Active падает, Passive выигрывает выборы, проматывает локальный кэш/состояние и становится новым Active, начиная принимать трафик.

### Блок 102: Интеграция протокола Raft (HashiCorp Raft)
*Цель: Построить собственный Replicated State Machine (RSM) без внешних зависимостей вроде etcd. Кластер сам договаривается о состоянии.*
*Пакет: `github.com/hashicorp/raft`*

913. **[FSM (Finite State Machine)]** Реализуй интерфейс `raft.FSM`. Методы `Apply(log *raft.Log)`, `Snapshot()`, `Restore(rc io.ReadCloser)`. Внутри FSM может быть просто `map[string]string` с мьютексом.
914. **[Raft Setup]** Настрой Raft-узел. Используй `raft.NewRaft`. Для транспорта используй `raft.NewTCPTransport`, для персистентности — `raftboltdb.BoltStore`, для снапшотов — `raft.FileSnapshotStore`.
915. **[Single Node Cluster]** Запусти кластер из одного узла. Сделай `raft.BootstrapCluster`. Отправь команду на запись: `raft.Apply([]byte("set key value"), 0)`. Убедись, что FSM применил изменение.
916. **[Multi-Node Cluster]** Подними 3 узла (на разных портах). Вручную добавь 2-й и 3-й узел к лидеру через `raft.AddVoter`.
917. **[Log Replication]** Отправь команду на запись Лидеру. Убедись, что через полсекунды все 3 FSM (на разных узлах) обновили локальную `map` с одинаковым значением.
918. **[Каверзный кейс — Leader Failover]** Убей процесс Лидера. Подожди несколько секунд (сработает Election Timeout). Наблюдай, как оставшиеся узлы выбирают нового Лидера. Отправь команду новому Лидеру.
919. **[Linearizable Reads]** Включи чтение через Лидера. Если ты читаешь с Follower'а, он может вернуть устаревшие данные. Используй `raft.VerifyLeader()` или `raft.ReadIndex()` перед чтением из FSM, чтобы гарантировать strong consistency (линейзуемость).
920. **[Snapshots]** Настрой `SnapshotThreshold` (например, каждые 1000 логов). Отправь 1000 записей. Убедись, что Raft сбросил лог на диск (создал файл `.snap`) и обрезал in-memory логи.
921. **[Restore from Snapshot]** Останови один из узлов. Удали его папку с логами (оставив только снапшот). Запусти снова. Узел должен восстановить состояние из снапшота и догнать кластер по оставшимся логам.
922. **[Высокая сложность — Dynamic Cluster Membership]** Напиши API для управления кластером. Добавь endpoint `/remove-node`, который вызывает `raft.RemoveServer`. Убедись, что кластер корректно перебалансирует квorum (например, при переходе с 5 на 3 узла).

### Блок 103: Распределенные блокировки и Fencing Tokens
*Цель: Эксклюзивный доступ к ресурсам в распределенной системе и защита от "зомби"-процессов.*

923. **[Redlock Basic]** Установи `github.com/go-redsync/redsync/v2`. Реализуй захват блокировки на 3 независимых инстансах Redis. Убедись, что если 2 Redis упадут, блокировка не будет получена.
924. **[Lock with Context]** Используй `redsunc.LockContext`. Если контекст отменяется (таймаут), блокировка должна автоматически сниматься.
925. **[Каверзный кейс — The GC Pause Problem]** Напиши симуляцию: Горутина A берет Redlock на 2 секунды. Локально она начинает выполнять работу. Но тут происходит Stop-The-World (GC) на 3 секунды (сэмулируй через `runtime.GC()` в цикле или `debug.SetGCPercent(-1)`). Lock в Redis истекает. Горутина B берет блокировку и начинает писать в файл/БД. Горутина A просыпается после GC и *продолжает* писать, думая, что держит лок. Происходит повреждение данных.
926. **[Fencing Token — Концепция]** Изучи проблему предыдущего задания. Решением являются Fencing Tokens. Каждый раз, когда блокировка берется, она возвращает монотонно возрастающий токен (Token 1, Token 2, ...).
927. **[Fencing через etcd]** Реализуй распределенную блокировку в etcd с использованием транзакций. Вместо обычной записи, используй `etcd.Txn`. Возвращай `revision` ключа — это и будет твой Fencing Token.
928. **[Защита на стороне хранилища]** Клиент A (токен 1) берет лок, получает GC паузу. Клиент B (токен 2) берет лок. Когда B пишет в хранилище (например, PostgreSQL), он передает токен 2. Хранилище запоминает `last_token = 2`. Когда просыпается A и пытается записать с токеном 1, PostgreSQL отклоняет операцию (через триггер или middleware), так как `1 < 2`.
929. **[Высокая сложность — Distributed Job Queue with Locks]** Реализуй систему воркеров, обрабатывающих задачи из БД. Когда воркер берет задачу, он ставит Redlock по `task_id`, чтобы другой воркер не взял её параллельно. В конце работы воркер удаляет задачу. Реализуй передачу Fencing Token в БД при удалении, чтобы "зомби"-воркер не удалил уже переработанную задачу.
930. **[Финальное испытание — HA Distributed Cache]**
    Построй отказоустойчивый кэш-сервис.
    - Кластер из 3 узлов, использующих **HashiCorp Raft** для репликации мапы `key-value`.
    - Только Лидер принимает запросы на запись (`POST /cache`). Follower'ы проксируют запросы на Лидера (или возвращают 307 Redirect).
    - Чтение (`GET /cache`) доступно на всех узлах (с использованием `ReadIndex` для консистентности).
    - При падении Лидера кластер автоматически переизбирает нового.
    - Фоновый процесс сборщика мусора (Evictor) удаляет устаревшие ключи. Используй **etcd Leader Election**, чтобы только один Evictor во всем кластере чистил кэш.
    - При записи в лог аудита (внешняя БД), передавай Fencing Token, полученный от etcd выборов, чтобы старый лидер не затер логи нового.
