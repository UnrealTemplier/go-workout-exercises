### Раздел 47: Распределенный консенсус и координация (Задачи 611–625)

#### Подраздел 47.1: Выборы лидера (Leader Election) через etcd и Consul (Задачи 611–615)

*Выборы лидера позволяют распределенному кластеру координировать задачи по принципу Active-Passive (один активный узел выполняет запись, остальные находятся в горячем резерве).*

611. **Выборы лидера в etcd через аренду (Lease)**: Подключите официальный клиент etcd: `go.etcd.io/etcd/client/v3`.
    * Создайте аренду (Lease) с TTL (временем жизни) 5 секунд.
    * Настройте периодическую отправку пульса (Keep-Alive) в фоновом режиме для продления аренды.
    * Попробуйте записать ключ `/services/leader` с вашим ID в рамках транзакции `Txn`: если ключа нет, запишите его с привязкой к вашей аренде. Если запись успешна — текущий узел объявляется Лидером.
612. **Выборы лидера через Concurrency API etcd**: В etcd есть высокоуровневый пакет для координации: `go.etcd.io/etcd/client/v3/concurrency`. Напишите программу, которая создает сессию (`concurrency.NewSession`) и использует готовый менеджер выборов `concurrency.NewElection` для автоматической борьбы за лидерство и отслеживания падений узлов.
613. **Выборы лидера в Consul**: Подключите клиент Consul: `github.com/hashicorp/consul/api`.
    * Создайте сессию Consul с таймаутом (TTL).
    * Напишите код, который пытается захватить распределенную блокировку на ключ-значение `service/leader`, используя метод `KV.Acquire` с указанием вашей сессии.
    * Если метод вернул `true` — узел стал лидером.
614. **Симуляция отказа (Failover) и Active-Passive воркер**: Напишите фоновую задачу (например, сборщик метрик), которая должна запускаться *строго* на одном узле кластера. Сэмулируйте распределенное окружение: запустите три экземпляра вашей программы на разных портах. Настройте пассивные узлы на наблюдение за ключом лидера (Watcher в etcd или регулярный опрос блокировки в Consul). Принудительно убейте процесс лидера (`SIGKILL`) и убедитесь, что один из пассивных узлов мгновенно обнаружил потерю аренды и объявил себя новым лидером, продолжив сбор метрик.
615. **Предотвращение Split-Brain (Кворумные проверки)**: В случае сетевого разделения (network partition) узел-лидер может оказаться изолирован от остального кластера, но продолжать считать себя лидером, если он не может связаться с координатором. Напишите код проверки кворума: лидер должен периодически выполнять быструю проверку связи со своими смежными узлами или координатором (etcd/Consul). Если связь потеряна, лидер должен добровольно сложить с себя полномочия (Step Down) и остановить выполнение критических операций до восстановления консенсуса.

#### Подраздел 47.2: Интеграция протокола Raft (HashiCorp Raft) (Задачи 616–620)

*Протокол Raft обеспечивает синхронизацию состояния узлов (FSM) в кластере на основе консенсуса большинства. Вы построите локальный Raft-кластер на Go.*

616. **Инициализация узла HashiCorp Raft**: Установите популярную библиотеку `github.com/hashicorp/raft`. Напишите конфигурацию локального Raft-узла:
    * Настройте файловое или in-memory хранилище логов (`raft.LogStore`).
    * Настройте стабильное хранилище состояния (`raft.StableStore`) и снапшотов.
    * Создайте TCP-транспорт для связи между узлами с помощью `raft.NewTCPTransport`.
617. **Конечный автомат Raft (FSM)**: Реализуйте интерфейс конечного автомата `raft.FSM`:
    * Метод `Apply(log *raft.Log)` — принимает команду (например, запись ключа в JSON-формате) и применяет её к локальной мапе в оперативной памяти.
    * Методы `Snapshot()` и `Restore()` — для создания снимков состояния и их восстановления при перезапуске узла.
618. **Бутстрап и динамическое объединение в кластер**: Напишите логику запуска кластера из трех узлов. Реализуйте HTTP/gRPC эндпоинт `/join` на стороне лидера. При старте узлы 2 и 3 должны отправлять POST-запрос на этот эндпоинт лидера, а лидер должен динамически добавлять их в консенсус-группу с помощью метода `raft.AddVoter`.
619. **Репликация логов консенсуса (Log Replication)**: Создайте HTTP API эндпоинт `POST /set` на стороне лидера для изменения данных в вашей FSM-мапе. Настройте логику: лидер не должен напрямую менять свою локальную мапу. Он должен отправить команду в Raft-кластер с помощью метода `raft.Apply(...)`. Убедитесь, что команда применяется к локальным конечным автоматам на всех трех узлах только после того, как лог успешно распределился и закоммитился на большинстве узлов.
620. **Имитация потери консенсуса**: Запустите ваш 3-узельный Raft-кластер. 
    * Напишите прослушиватель событий смены лидера через канал `raft.LeaderCh()`.
    * Отключите один из узлов. Убедитесь, что оставшиеся два узла (большинство) продолжают успешно принимать записи.
    * Отключите второй узел (остался один). Убедитесь, что единственный выживший узел автоматически теряет статус лидера, переходит в режим ожидания и блокирует любые операции записи, так как кворум большинства недостижим.

*Распределенные блокировки защищают разделяемые ресурсы от состояния гонки, но требуют специальных архитектурных решений против задержек рантайма (GC pauses).*

621. **Распределенная блокировка на etcd**: Напишите программу координированного изменения текстового файла на сетевом диске. Используйте etcd concurrency-блокировку `concurrency.NewMutex`. Запустите параллельно три процесса Go, которые конкурируют за файл, блокируя мьютекс (`mutex.Lock(ctx)`), дописывая в файл строку и освобождая мьютекс (`mutex.Unlock(ctx)`). Убедитесь, что строки в файле не перемешиваются.
