Это уровень системной инженерии (System Design), где мы боремся с теоремой CAP, сетевыми партициями (Split-Brain) и рассинхронизацией времени на серверах. Когда у тебя 5 экземпляров микросервиса, и только один должен списывать деньги по расписанию, обычная БД уже не спасет.

Впереди **30 хардкорных упражнений (с 831 по 860)**, которые погрузят тебя в мир распределенного консенсуса.

*(Для выполнения потребуется локально поднять Docker-контейнеры с Redis, Consul и etcd).*

### Блок 81. Распределенные блокировки и Fencing Tokens (831–840)
Обычный `sync.Mutex` работает только внутри одного процесса. Учимся блокировать ресурсы между разными серверами безопасно.

831. **Базовый Redis Lock:** Реализуй блокировку. Используй `SET resource_name my_random_value NX PX 10000`. `NX` (только если ключа нет) гарантирует эксклюзивность, `PX 10000` (TTL 10 сек) спасает от дедлока, если сервер умрет с блокировкой.
832. **Безопасное снятие блокировки (Lua-скрипт):** Клиент должен удалять *только свою* блокировку. Если просто сделать `GET` и `DEL`, то между ними другой процесс может перехватить ключ (Race Condition). Напиши Lua-скрипт `if redis.call("get",KEYS[1]) == ARGV[1] then return redis.call("del",KEYS[1]) else return 0 end`. Выполни его через `client.Eval()`.
833. **Продление TTL (Watchdog Pattern):** Бизнес-логика занимает больше 10 секунд, но ставить TTL = 1 час опасно (вдруг воркер упал). Напиши фоновую горутину ("сторожевой пес"). Пока основная горутина работает, "пес" каждые 3 секунды отправляет в Redis команду на продление TTL (`PEXPIRE`) текущего лока. При выходе из функции убивай "пса" через `context`.
834. **Уязвимость одиночного Redis (Redlock):** Redis кластер асинхронен. Ты взял лок на мастере, мастер упал, данные не успели реплицироваться на слейв, слейв стал мастером. Другой сервис берет лок на те же данные! Изучи алгоритм **Redlock**. Установи библиотеку `github.com/go-redsync/redsync`. Подними 3 независимых Redis-сервера и настрой блокировку, требующую кворума (минимум 2 из 3 серверов должны подтвердить лок).
835. **Ужас Split-Brain (Пауза сборщика мусора):** *Мысленный и практический тест.* Воркер А взял лок на 5 секунд. Внезапно Go ловит тяжелую GC-паузу (или гипервизор ОС фризит виртуалку) на 6 секунд. Лок в Redis истек. Воркер Б берет лок и пишет в БД. Тут Воркер А "отвисает" и ТОЖЕ пишет в БД (он же уверен, что лок его!). Осознай, почему *любые* TTL-локи уязвимы к рассинхронизации времени.
836. **Fencing Token (Защита от Split-Brain):** Решение проблемы 835. Токен ограждения (Fencing) — это монотонно возрастающее число. В Redis/etcd при взятии блокировки получай инкрементный токен (например, `Token: 42`). Воркер передает этот токен в БД вместе с запросом на изменение данных.
837. **Валидация Fencing Token на ресурсе:** Модифицируй таблицу в PostgreSQL, добавив `last_token_id INT`. Когда Воркер А (отвисший) присылает запрос с `Token=42`, а БД уже обработала запрос от Воркера Б с `Token=43`, база должна отклонить запрос А (42 < 43). Напиши логику, где ресурс сам защищается от устаревших локов!
838. **Знакомство с etcd:** `etcd` (движок Kubernetes) — это консистентное хранилище на базе протокола Raft. Подключи клиент `go.etcd.io/etcd/client/v3`. Сделай базовые `Put`, `Get` и `Delete`. Убедись, что etcd требует передачи контекста в каждый вызов.
839. **etcd Distributed Lock:** etcd решает проблемы Redis-локов за счет строгого консенсуса. Используй встроенный пакет `go.etcd.io/etcd/client/v3/concurrency`. Создай сессию `concurrency.NewSession()` и мьютекс `concurrency.NewMutex()`. Вызови `Lock()` и `Unlock()`.
840. **Управление Lease (Аренда в etcd):** Механизм локов в etcd построен на Арендах (Lease). Создай Lease на 5 секунд. Привяжи к нему ключ. Пока твоя Go-программа жива, клиент etcd автоматически шлет keep-alive (продлевая аренду). Принудительно убей программу. Убедись, что через 5 секунд ключ сам исчез из etcd.

### Блок 82. Leader Election: Выборы лидера (Active-Passive) (841–850)
У тебя 5 инстансов сервиса рассылки уведомлений. Если все начнут читать БД и слать письма, юзеры получат спам. Только один должен быть Лидером, а остальные 4 — спать в горячем резерве (Followers).

841. **Consul Session:** Установи клиент `github.com/hashicorp/consul/api`. В Consul механизм выборов работает через сессии и блокировки ключей. Создай сессию (Session) с TTL 10 секунд.
842. **Consul Acquire Lock:** Попытайся захватить ключ `service/billing/leader` с помощью метода `KV().Acquire()`, передав ID своей сессии. Если метод вернул `true` — твой сервис стал Лидером.
843. **Consul Watcher (Отслеживание):** Напиши логику Фоловера. Он должен использовать "блокирующий запрос" (Blocking Query) в Consul, чтобы висеть в ожидании и следить за ключом `service/billing/leader`. Как только Лидер падает (ключ освобождается), Фоловеры просыпаются и пытаются сделать `Acquire`.
844. **etcd Leader Election:** Напиши выборы лидера на etcd (это современнее и чаще используется в Go). Создай `concurrency.NewElection(session, "my-election")`. Вызови `election.Campaign(ctx, "worker_1")`. Метод `Campaign` заблокируется! Как только он отвиснет — ты лидер.
845. **Graceful Resignation (Добровольный отказ):** Лидер должен уметь корректно уходить (например, при выкате новой версии сервиса). Перехвати `SIGTERM` в Go. В обработчике сигнала вызови `election.Resign(ctx)`. Убедись, что другой узел мгновенно становится лидером, без ожидания таймаута аренды.
846. **Наблюдение за выборами (Observe):** Напиши API-эндпоинт `/leader`, который возвращает, кто сейчас главный. Используй метод `election.Observe()`, который возвращает канал обновлений. Все узлы должны всегда знать имя текущего лидера (например, для перенаправления к нему трафика).
847. **Сетевой раздел (Network Partition Simulation):** Запусти 3 узла etcd и 3 Go-сервиса. Изолируй лидера (например, через `iptables` в Docker обруби ему связь с кластером etcd). Убедись, что:
    * Изолированный лидер понимает, что потерял кворум, и слагает с себя полномочия.
    * Оставшиеся 2 узла проводят выборы и назначают нового лидера.
848. **Отмена кампании:** Фоловерам может надоесть ждать выборов. Оберни `election.Campaign` в `context.WithCancel`. Отмени контекст через 5 секунд. Убедись, что узел прекращает попытки стать лидером и завершает работу без ошибок.
849. **Интеграция с Cron:** Возьми библиотеку `github.com/robfig/cron/v3`. Напиши джобу, которая выполняется каждую минуту. Внутри джобы добавь проверку: `if !IsLeader() { return }`. Запусти 3 инстанса сервиса и убедись, что джоба выполняется строго 1 раз в минуту одним сервисом.
850. **Split-Brain защита (Double Check):** Перед выполнением критической операции, Лидер должен убедиться, что он *всё еще* лидер. Вызови чтение ключа лидера в etcd/Consul непосредственно перед транзакцией в БД. Хоть это и не заменит Fencing Tokens (упр. 836), это радикально снизит вероятность гонки.

### Блок 83. Интеграция Raft (HashiCorp Raft) (851–860)
Зачем нужен Redis или etcd, если твой Go-код *сам* может стать распределенной консистентной базой данных? Изучаем библиотеку `github.com/hashicorp/raft` (на ней построены Consul и Nomad).

851. **Анатомия Raft (Подготовка):** Установи библиотеку `hashicorp/raft`. Пойми 3 основных компонента, которые тебе нужно предоставить: 
    * `LogStore` (хранилище логов, можно использовать `hashicorp/raft-boltdb`), 
    * `SnapshotStore` (для сжатия логов),
    * `Transport` (для связи узлов по сети). 
    Создай минимальный конфиг узла.
852. **Реализация FSM (Finite State Machine):** Твоя бизнес-логика. Напиши структуру, реализующую `raft.FSM`. В ней главное — метод `Apply(*raft.Log) any`. Напиши там логику: парси JSON из лога и применяй команду `SET key value` к локальной Go-мапе (`map[string]string`).
853. **In-Memory Cluster (Локальный тест):** Для начала протестируй алгоритм без сети. Используй `raft.NewInmemTransport`. Создай 3 Raft-ноды прямо в одной Go-программе. Свяжи их in-memory транспортом. Дождись, пока они выберут лидера.
854. **TCP Transport:** Переносим в сеть. Создай `raft.NewTCPTransport`. Подними 3 независимых Go-процесса на портах 7001, 7002, 7003. 
855. **Bootstrapping кластера:** Чтобы кластер запустился, узлы должны знать друг о друге. Укажи `raft.Configuration` с адресами 3-х узлов при запуске. Запусти 3 бинарника. Посмотри в консоль: они должны пообщаться и выбрать одного Leader, а два других станут Follower.
856. **Динамическое добавление узлов (Join API):** Запускать кластер с захардкоженными IP неудобно. Сделай Bootstrap только для одной ноды (она сразу станет лидером). Напиши HTTP-эндпоинт `POST /join` на лидере, который вызывает `raftNode.AddVoter(serverID, serverAddress)`. Подними второй бинарник и пошли запрос на этот эндпоинт, чтобы присоединиться к кластеру.
857. **Write Forwarding (Перенаправление записи):** По правилам Raft, писать данные может только Лидер! Сделай HTTP-эндпоинт `POST /key` на каждом узле. Внутри проверяй: `if raftNode.State() != raft.Leader`. Если не лидер — возвращай HTTP 307 Temporary Redirect (или проксируй запрос под капотом) на IP адрес текущего лидера (узнай его через `raftNode.Leader()`). 
858. **Применение команды (Apply):** Если запрос пришел на Лидера, сериализуй команду (`{"op": "set", "key": "foo", "val": "bar"}`) в байты и вызови `raftNode.Apply(bytes, timeout).Response()`. Метод заблокируется, пока команда не реплицируется на большинство фоловеров. После этого она попадет в твой FSM (упр. 852).
859. **Snapshots (Сжатие логов):** Если ты запишешь миллион ключей, лог Raft станет гигантским, а рестарт ноды займет час. Реализуй методы `Snapshot()` и `Restore()` в своем FSM. В `Snapshot` просто сериализуй текущее состояние твоей `map` в JSON. Raft вызовет этот метод автоматически (согласно настройкам `SnapshotThreshold`), обрежет старые логи и сохранит компактное состояние на диск.
860. **Consistent Reads (Консистентное чтение):** По правилам Raft, Фоловерам нельзя доверять чтение (у них могут быть старые данные). 
    * Вариант 1 (Stale Read): Разреши читать с фоловеров (быстро, но данные могут отставать).
    * Вариант 2 (ReadIndex/Lease): Чтобы получить 100% актуальные данные (Linearizability), чтение должно идти через Лидера. Лидер должен убедиться у большинства фоловеров, что он *всё еще* лидер, прежде чем отдать ответ. Реализуй вызов чтения через метод `raftNode.VerifyLeader()` перед отдачей значения из локальной мапы.
