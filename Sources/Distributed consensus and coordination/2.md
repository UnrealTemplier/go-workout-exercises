### 23. Распределенный консенсус и координация (Leader Election, Raft, Distributed Locks)

#### 23.1 Лидерская выборка через Consul
721. **Подключение к Consul и регистрация сервиса.** Запустите Consul (dev-режим). Используя `consul/api`, зарегистрируйте экземпляр сервиса с health-check (ttl или http). Получите список здоровых экземпляров через DNS или HTTP API.
722. **Создание сессии и захват ключа.** Реализуйте простой лидерский лок: создайте сессию с TTL и привяжите её к ключу в KV, используя `Acquire`. Если ключ уже занят, сессия не создается – ожидайте освобождения с backoff.
723. **Лидерская выборка с мониторингом и фейловером.** Запустите несколько горутин (эмулирующих узлы). Каждая пытается стать лидером через сессию. Лидер периодически продлевает сессию. При остановке лидера другой узел должен захватить лидерство. Используйте `Session.Renew` или TTL-чек.
724. **Оповещение о смене лидера.** Реализуйте канал, который получает сообщения, когда узел становится лидером или теряет лидерство. Используйте long polling на ключ сессии или watch.
725. **Лидерская выборка с использованием готовой библиотеки (например, `consul-locker`).** Инкапсулируйте логику в переиспользуемый компонент, который предоставляет интерфейс `IsLeader()`, `Start()`, `Stop()`. Протестируйте конкурентное поведение с 5 узлами.

#### 23.2 Лидерская выборка через etcd
726. **Подключение к etcd и создание lease.** Запустите etcd локально. Подключитесь через `clientv3`. Создайте lease с TTL 10 секунд. Запишите ключ `/election/leader` с этим lease (операция `Put` с `WithLease`).
727. **Кампания лидерства на `concurrency/election`.** Используйте `clientv3/concurrency`. Создайте сессию и участвуйте в выборах (`Election.Campaign`). Запустите несколько узлов, наблюдайте автоматический выбор лидера.
728. **Наблюдение за лидерством и разрешение конфликтов.** Используйте `Election.Observe` для получения имени текущего лидера. При потере соединения или истечении сессии другой узел вступает в кампанию. Реализуйте логику graceful shutdown с отзывом лидерства.
729. **Использование etcd для распределенного конфигурационного хранилища.** Помимо лидерства, храните общую конфигурацию в etcd. Лидер обновляет ключи `/config` через транзакции (STP), а остальные узлы следят за изменениями (`Watch`).
730. **Сравнение Consul vs etcd по времени обнаружения сбоя лидера.** Настройте одинаковые TTL (например, 5с) и измерьте время от остановки лидера до захвата новым узлом. Проведите стресс-тест с частой сменой лидера.

#### 23.3 Синхронизация состояний через Raft (HashiCorp Raft)
731. **Запуск одного Raft-узла с in-memory хранилищем.** Используйте `hashicorp/raft`. Создайте FSM (finite state machine) с методами `Apply`, `Snapshot`, `Restore`. Инициализируйте raft с in-memory транспортом и стабильным хранилищем (например, `/tmp/raft`). Запустите один узел и подайте команду логирования.
732. **Кластер из 3 узлов и репликация журнала.** Настройте три узла на разных портах, используя TCP-транспорт. Добавьте узлы в кластер (bootstrap, join). Отправьте команды на лидера и убедитесь, что они реплицируются на подчинённые узлы.
733. **Снэпшоты и восстановление состояния.** В FSM реализуйте снэпшот каждые N логов. Симулируйте падение узла, затем перезапустите его – он должен догнать лидера из снэпшота и последующих логов.
734. **Отказ лидера и переизбрание.** Остановите процесс-лидер. Убедитесь, что кластер выбирает нового лидера и продолжает обрабатывать команды без потерь.
735. **Пользовательский конечный автомат: Key-Value хранилище.** Реализуйте FSM, который хранит map и обрабатывает команды `set`, `delete`, `cas`. Клиент взаимодействует с кластером через HTTP или gRPC, перенаправляя запросы к лидеру.
736. **Raft в роли координатора распределённых заданий.** Постройте систему, где лидер назначает задачи (через raft-лог) подчинённым узлам. Завершение задач записывается обратно в лог. При смене лидера состояние задач не теряется.
737. **Тюнинг параметров Raft (heartbeat timeout, election timeout).** Экспериментируйте с `HeartbeatTimeout` и `ElectionTimeout` для достижения быстрого фейловера и минимизации ложных переизбраний.

#### 23.4 Распределенные блокировки и Fencing Tokens
738. **Простая распределенная блокировка на Redis (один экземпляр).** Реализуйте блокировку с `SET NX PX`, используя `go-redis`. Захватите блокировку с уникальным токеном (UUID), выполните критическую секцию, освободите с проверкой токена (Lua-скрипт).
739. **Redlock: блокировка через несколько Redis-узлов.** Реализуйте алгоритм Redlock: попытайтесь захватить блокировку на N независимых Redis-серверах (минимум 3), используя одинаковый ключ и случайный токен. Блокировка считается успешной, если захвачено большинство за время таймаута.
740. **Проблема Redlock и Fencing Token.** Продемонстрируйте сценарий, где долгая GC-пауза приводит к истечению блокировки, но клиент продолжает работу. Усилите безопасность, добавив монотонно возрастающий fencing token (версию) из Redis, который проверяется на целевом сервисе перед модификацией данных.
741. **Распределенная блокировка на etcd с lease и watchdog.** Реализуйте блокировку через etcd: создайте lease, запишите ключ с транзакцией `If(NotExists(...))`. Для долгих операций запустите горутину-«watchdog», продлевающую lease.
742. **Распределенная блокировка на Consul с сессией и fencing.** Используйте Consul сессию с монотонным ID (`Session.Create` возвращает ID). Этот ID можно использовать как fencing token. Передавайте его в запросы к сервису, сервис проверяет, что ID не меньше предыдущего использованного.
743. **Тестирование гонок с потерей блокировки.** Напишите тест, в котором два конкурента пытаются одновременно захватить блокировку и увеличить общий счётчик. Без блокировки – гонка. С блокировкой – строгая последовательность.
744. **Сравнение производительности распределенных блокировок.** Проведите бенчмарк: захват и освобождение блокировки 1000 раз для Redis (один), Redlock, etcd, Consul. Измерьте задержку и пропускную способность.
745. **Итоговый проект: координатор заданий с leader election + raft + блокировки.** Разработайте микросервис, который использует etcd для лидерской выборки, Raft для хранения состояния задач и распределенные блокировки для предотвращения параллельного выполнения одного задания разными узлами. Обеспечьте отказоустойчивость и мониторинг.
