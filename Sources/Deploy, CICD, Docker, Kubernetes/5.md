Код, который работает только на твоем ноутбуке — это еще не продукт. Продукт начинается там, где код безопасно, автоматически и масштабируемо доставляется на сервера (или в облако) и живет там под управлением оркестраторов. 

Поскольку Go компилируется в один независимый бинарный файл, он является абсолютным королем контейнеризации и облачной инфраструктуры (Cloud-Native). 

Продолжаем нашу нумерацию. Впереди **40 упражнений** (с 576 по 615), которые превратят тебя из просто программиста в инженера, умеющего настраивать CI/CD и выкатывать код в Kubernetes.

*(Для этих упражнений установи локально Docker, утилиту `kubectl` и локальный кластер Kubernetes — например, **Kind** или **Minikube**).*

### Блок 53. Docker и Контейнеризация Go-приложений (576–585)
Учимся правильно и безопасно упаковывать Go-код.

576. **Базовый Dockerfile:** Напиши простой HTTP-сервер на Go. Создай файл `Dockerfile`. Используй базовый образ `golang:1.22` (или новее). Скопируй исходники (`COPY . .`), скачай зависимости, скомпилируй бинарник внутри контейнера и укажи `CMD` для запуска. Собери образ (`docker build`) и запусти контейнер с пробросом портов (`docker run -p 8080:8080`).
577. **Кэширование слоев (Секрет скорости):** Измени упр. 576. Сначала скопируй **только** `go.mod` и `go.sum`. Затем выполни `RUN go mod download`. И только после этого делай `COPY . .` и `go build`. Попробуй изменить одну строчку в `main.go` и пересобрать образ. Убедись, что скачивание библиотек берется из кэша Docker, экономя уйму времени!
578. **Multi-stage сборка (Золотой стандарт):** Образ из упр. 576 весит около 800+ МБ (потому что содержит исходники Go, компилятор, ОС Linux). Напиши Dockerfile из двух этапов (stages):
    * Этап 1 (`builder`): образ `golang`, собираем бинарник.
    * Этап 2: берем легковесный образ `alpine:latest`. Копируем туда бинарник из `builder`. Убедись, что итоговый образ весит около 15-20 МБ!
579. **Статическая линковка и `scratch`:** Alpine Linux — это здорово, но образ `scratch` (абсолютно пустой образ) — еще лучше. В этапе сборки укажи `CGO_ENABLED=0 GOOS=linux go build -o app .`. На втором этапе используй `FROM scratch` и скопируй бинарник. Теперь твой Docker-образ весит ровно столько же, сколько сам бинарный файл (около 10 МБ).
580. **Проблема SSL-сертификатов в `scratch`:** Добавь в приложение HTTP-запрос к любому HTTPS-сайту (например, `google.com`). Собери в `scratch` и запусти. Получишь ошибку проверки сертификата! В этапе сборки скопируй файл `/etc/ssl/certs/ca-certificates.crt` из `builder` в `scratch`. Проверь, что HTTPS заработал.
581. **Безопасность (Non-root user):** Запускать приложение в контейнере от имени пользователя `root` — угроза безопасности. В `alpine` (или другом образе) создай пользователя `appuser`, дай ему права на приложение и укажи директиву `USER appuser` перед `CMD`.
582. **Docker Compose для локальной разработки:** Твоему сервису нужен PostgreSQL. Создай файл `docker-compose.yml`. Опиши два сервиса: `app` (собирается из твоего Dockerfile) и `db` (образ `postgres:15`). Настрой сеть, чтобы `app` подключался к БД по имени хоста `db`. Подними всё одной командой `docker compose up -d`.
583. **Проблема "Упал до поднятия базы" (Wait-for-it):** Если `app` стартует быстрее, чем БД инициализируется, Go-приложение упадет при попытке подключения (упр. 366). Настрой переподключение в самом Go-коде (retry-цикл при старте) ИЛИ используй директиву `depends_on` с условием `condition: service_healthy` в docker-compose.
584. **Docker Volumes (Постоянство данных):** Убей контейнеры из упр. 582 (`docker compose down`). Подними снова. Убедись, что все данные из базы исчезли. Настрой именованный Volume в `docker-compose.yml` и примонтируй его в `db` (в `/var/lib/postgresql/data`), чтобы данные переживали рестарт контейнеров.
585. **Makefile обертка:** Создай `Makefile` в корне проекта. Напиши таски: `make build` (собирает образ), `make up` (поднимает compose), `make down`, `make logs`. Инженеры любят Makefiles за короткие команды.

### Блок 54. CI/CD (Автоматизация: GitHub Actions / GitLab CI) (586–595)
Твой код должен автоматически проверяться и собираться при каждом пуше в репозиторий. *(Примеры приведены для GitHub Actions, но концепция едина).*

586. **Первый Pipeline:** Создай папку `.github/workflows/` и файл `ci.yml`. Настрой триггер: срабатывать при `push` в ветку `main`. Добавь шаг, который делает `actions/checkout` (скачивает код) и `actions/setup-go` (устанавливает нужную версию Go). Добавь команду `go test ./...`. Сделай пуш и проверь зеленую галочку в GitHub.
587. **Кэширование в CI:** Скачивание модулей (`go mod download`) при каждом запуске пайплайна тратит время. Добавь шаг кэширования директорий `~/.cache/go-build` и `~/go/pkg/mod` (в GitHub Actions у `setup-go` есть встроенный флаг `cache: true`). Замерь, на сколько секунд ускорилась сборка.
588. **CI: Линтер на страже:** Никогда не мерджи грязный код! Добавь шаг с использованием `golangci-lint` (есть готовый GitHub Action `golangci/golangci-lint-action`). Намеренно закоммить код с неиспользуемой переменной. Убедись, что пайплайн **падает** и не дает коду пройти дальше.
589. **CI: Сканирование уязвимостей:** Установи официальный инструмент сканирования уязвимостей в Go: `govulncheck`. Добавь его запуск в пайплайн. Он проверит, нет ли в твоем `go.mod` пакетов с известными CVE (уязвимостями).
590. **CI: Test Coverage Artifacts:** Добавь генерацию отчета о покрытии кода тестами (`go test -coverprofile=coverage.out`). Настрой пайплайн так, чтобы он сохранял этот файл как Artifact (артефакт сборки), который можно скачать после завершения пайплайна.
591. **CD: Сборка и Push образа:** Создай секрет в настройках GitHub (токен от DockerHub или GitHub Container Registry). Напиши новую джобу (Job) в пайплайне: если тесты прошли успешно, собирай Docker-образ и делай `docker push` с тегом, равным хэшу коммита (`${{ github.sha }}`).
592. **Интеграционные тесты в CI (Service Containers):** Твои тесты требуют реального Redis. В GitHub Actions настрой *Service Container* с Redis. Пайплайн должен поднять контейнер с редисом, выполнить твои интеграционные `go test`, а затем убить контейнер.
593. **Автоматические релизы (GoReleaser):** Установи утилиту `GoReleaser`. Создай файл `.goreleaser.yaml`. Настрой GitHub Action, который срабатывает только при пуше Git-тега (например, `v1.0.0`). GoReleaser автоматически скомпилирует бинарники под Windows, Linux, macOS, запакует их в архивы и прикрепит к релизу на GitHub.
594. **Simple CD (Deploy via SSH):** *Учебный деплой.* Добавь шаг, который с помощью SSH-ключа логинится на твой удаленный сервер (VPS), делает `docker pull` нового образа, останавливает старый контейнер и запускает новый.
595. **Branch Protection:** Настрой репозиторий (в UI GitHub/GitLab). Запрети прямой пуш в ветку `main`. Обяжи делать Pull Requests, и поставь галочку: "Слить код можно только если CI-пайплайн (линтер и тесты) пройден успешно".

### Блок 55. Kubernetes (K8s): Базовые примитивы (596–605)
Запускаем наше Go-приложение в распределенном кластере. Используй Kind (Kubernetes IN Docker) для тестов на ноутбуке.

596. **Подготовка (Pod):** Напиши файл `pod.yaml`. Опиши в нем сущность `Pod`, укажи свой Docker-образ (из упр. 591). Запусти через `kubectl apply -f pod.yaml`. Проверь статус через `kubectl get pods`. Посмотри логи через `kubectl logs my-pod`.
597. **Развертывание (Deployment):** Поды смертны. Если под удалят, он не воскреснет. Удали под. Напиши `deployment.yaml`. Опиши `Deployment`, который управляет 3 репликами (копиями) твоего приложения. Примени его. `kubectl get pods` должен показать 3 работающих пода.
598. **Самовосстановление (Self-healing):** Намеренно удали один из подов Deployment'а (`kubectl delete pod <имя>`). Быстро сделай `kubectl get pods`. Увидь, как Kubernetes мгновенно создает новый под на замену убитому, чтобы поддержать требуемое число реплик = 3.
599. **Доступ внутри кластера (Service):** Поды имеют динамические IP, к ним нельзя обращаться напрямую. Создай `service.yaml` (тип `ClusterIP`). Он создаст стабильный внутренний IP и DNS-имя, балансируя нагрузку между твоими тремя подами.
600. **Тест Service (Port-Forward):** Используй команду `kubectl port-forward svc/my-service 8080:80`. Открой в браузере `localhost:8080`. Запросы пойдут с ноутбука в кластер K8s прямо на твой сервис, а оттуда на один из подов с Go-приложением.
601. **Конфигурация (ConfigMap):** Зашивать настройки в Docker-образ — антипаттерн. Создай `configmap.yaml` со словарем (ключ `SERVER_PORT: 8080`). Прокинь это значение внутрь пода как переменную окружения (Env Var). Сделай так, чтобы твое Go-приложение читало порт из `os.Getenv()`.
602. **Секреты (Secrets):** Создай `secret.yaml` для хранения пароля от БД (значения в yaml должны быть в base64). Прокинь его в под аналогично ConfigMap. Никогда не коммить секреты в Git в открытом виде!
603. **Монтирование файлов (Volumes):** Твоему приложению нужен файл `config.yaml`. Помести содержимое этого файла в ConfigMap. Настрой Deployment так, чтобы он примонтировал (Volume Mount) этот ConfigMap внутрь пода как реальный физический файл (например, в путь `/etc/config/config.yaml`).
604. **Обновление версии (Rollout):** Внеси изменение в код (например, поменяй текст ответа HTTP сервера). Собери и запушь образ с новым тегом (`v1.1.0`). Измени тег в `deployment.yaml` и сделай `kubectl apply`. K8s сделает *Rolling Update*: будет аккуратно гасить старые поды и поднимать новые без даунтайма (Zero Downtime).
605. **Откат (Rollback):** Ты понял, что версия `v1.1.0` с багом. Выполни команду `kubectl rollout undo deployment/my-app`. Кластер автоматически вернет старую рабочую версию приложения.

### Блок 56. Kubernetes: Продакшн-настройки Go-сервиса (606–615)
Настраиваем отказоустойчивость, лимиты памяти и автоскейлинг.

606. **Пробы жизни (Liveness Probe):** Что если Go-приложение поймало deadlock (зависло), но процесс не упал? K8s этого не поймет. Напиши в Go хендлер `/health`. В манифесте добавь `livenessProbe`, которая делает HTTP-запрос на этот роут каждые 10 секунд. Если Go ответит 500 (или таймаут) 3 раза подряд — K8s сам убьет и перезапустит контейнер.
607. **Пробы готовности (Readiness Probe):** Твое приложение стартует 5 секунд (подключается к БД, греет кэш). В это время ему нельзя слать трафик. Добавь `readinessProbe`. K8s не пустит пользовательский трафик в под (он не добавится в endpoints Service), пока эта проба не вернет 200 OK.
608. **Graceful Shutdown в K8s:** Когда K8s решает убить под, он сначала шлет сигнал `SIGTERM`, ждет (по умолчанию 30с - `terminationGracePeriodSeconds`), а затем делает `SIGKILL`. Убедись, что твое приложение (из упр. 353) правильно ловит `SIGTERM`, завершает работу `http.Server` и закрывает коннекты к БД. *Проверь по логам кластера, что приложение завершается без ошибок.*
609. **Защита от OOM (Resources & GOMEMLIMIT):** Укажи в манифесте `resources.requests` (гарантированные ресурсы: 100m CPU, 64Mi RAM) и `resources.limits` (потолок: 200m CPU, 128Mi RAM). В Go 1.19+ появилась переменная `GOMEMLIMIT`. Если под потребляет память и упирается в 128Mi, Linux убьет его (OOMKilled). Передай `GOMEMLIMIT=100MiB` в под. Теперь сборщик мусора (GC) в Go будет работать агрессивнее при подходе к этому порогу, спасая приложение от смерти в кластере!
610. **Публичный доступ (Ingress):** Service ClusterIP работает только внутри. Чтобы пользователи могли зайти снаружи по красивому URL, установи Ingress Controller (например, NGINX Ingress для Kind). Создай `ingress.yaml` с правилом: трафик для `myapp.local` направить в твой Service. Настрой `/etc/hosts` на ноутбуке и проверь работу.
611. **Автомасштабирование (HPA - Horizontal Pod Autoscaler):** Если нагрузка выросла, K8s может сам увеличивать число подов. Создай HPA-ресурс, который следит за CPU. Укажи правило: если среднее использование CPU > 70%, масштабировать до 10 реплик. Запусти утилиту нагрузочного тестирования (например, `hey`) на свой Ingress и смотри (`kubectl get hpa`), как кластер сам поднимает новые инстансы твоего приложения!
612. **Пакетный менеджер Helm:** YAML-файлов стало слишком много, и они не переиспользуемые. Установи `Helm`. Сделай `helm create my-go-app`. Перенеси свои манифесты в шаблоны (Templates). Теперь ты можешь деплоить приложение целиком одной командой `helm install ...`.
613. **Helm Values (Мульти-среда):** Используй файл `values.yaml` в Helm-чарте. Настрой шаблоны так, чтобы при деплое на `staging` создавалась 1 реплика пода, а при деплое на `production` — 5 реплик, используя один и тот же чарт, но разные `values-*.yaml` файлы.
614. **Безопасность (Network Policies):** Напиши `NetworkPolicy`, которая запрещает ЛЮБЫЕ входящие сетевые соединения к поду с твоей базой данных, КРОМЕ подов твоего Go-приложения (фильтрация по меткам/labels).
615. **Основы GitOps (Взгляд в будущее):** Ручной `kubectl apply` или деплой прямо из GitHub Actions считается устаревающим подходом. Установи в кластер (локально) **ArgoCD**. Скажи ему следить за твоим Git-репозиторием с YAML-манифестами. Измени количество реплик прямо в Гитхабе, закоммить. Увидь, как ArgoCD заметит изменение в Git и сам синхронизирует состояние твоего кластера, не требуя никаких секретов кластера в самом GitHub!
