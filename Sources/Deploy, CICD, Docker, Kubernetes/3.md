Деплой, контейнеризация и оркестрация — это то, что превращает твой Go-код в работающий продакшен-сервис. Go идеально подходит для Kubernetes: маленькие бинарники, быстрый старт, низкое потребление памяти и предсказуемый graceful shutdown.

### Блок 71: Docker и сборка артефактов
*Цель: Научиться создавать минимальные, безопасные и кэшируемые Docker-образы для Go.*

641. Напиши простейший `Dockerfile` для Go-приложения (один этап `FROM golang:1.22`, `go build`, `CMD`). Запусти через `docker run`. Обрати внимание на размер образа (он будет огромным, ~800MB).
642. **[Multi-stage build]** Раздели Dockerfile на 2 этапа: `builder` (где компилируется бинарник) и `runner` (где бинарник запускается, например, `FROM alpine`). Убедись, что размер образа уменьшился до ~20MB.
643. **[Scratch / Distroless]** Используй `FROM scratch` (или `gcr.io/distroless/static-debian12`). Запусти бинарник. Поймай ошибку отсутствия SSL сертификатов (если делаешь HTTPS-запросы) и добавь их через `COPY --from=builder /etc/ssl/certs/ca-certificates.crt /etc/ssl/certs/`.
644. **[Кэширование модулей]** Оптимизируй Dockerfile: скопируй сначала только `go.mod` и `go.sum`, выполни `go mod download`, и только потом копируй остальной код. Убедись, что при изменении кода этап `download` берется из кэша.
645. **[Каверзный кейс — CGO]** Включи CGO в своем коде (например, используй `github.com/mattn/go-sqlite3`). Попробуй запустить бинарник, собранный в `golang:alpine`, в `FROM scratch`. Поймай ошибку динамического линковера (libc). Исправь, включив `CGO_ENABLED=0` или использовав `alpine` как runner.
646. **[Внедрение версии]** Используй `ARG` и `-ldflags "-X main.version=1.0.0"` в Dockerfile, чтобы передавать тег версии в бинарник во время сборки.
647. **[Makefile / Taskfile]** Напиши `Makefile` с командами `build`, `test`, `docker-build`, `docker-run`, `clean` для автоматизации рутинных задач.
648. **[Docker Compose]** Напиши `docker-compose.yml`, который поднимает твое Go-приложение, PostgreSQL и Redis. Настрой `depends_on` с `condition: service_healthy` (healthcheck для БД).
649. **[Hot Reload в Docker]** Настрой Docker Compose для локальной разработки с использованием утилиты `air` (горячая перезагрузка кода). Смонтируй локальную папку в контейнер.

### Блок 72: CI/CD (Continuous Integration / Continuous Deployment)
*Цель: Автоматизировать проверку кода и сборку артефактов при пуше в Git.*

650. **[GitHub Actions / GitLab CI]** Напиши пайплайн, который срабатывает при пуше в ветку `main`. Пайплайн должен запускать `go test ./...` и `golangci-lint run`.
651. **[Кэширование в CI]** Настрой кэширование папки `/go/pkg/mod` в CI-пайплайне, чтобы ускорить прохождение тестов.
652. **[Сборка и пуш образа]** Добавь шаг в пайплайн: логин в Docker Hub (через secrets), сборка образа с тегом текущего коммита (SHA) и пуш в registry.
653. **[Multi-arch сборка]** Используй `docker buildx` в CI для сборки образов под архитектуры `linux/amd64` и `linux/arm64` (чтобы твой образ работал и на Intel-серверах, и на Apple Silicon / ARM-инстансах AWS).
654. **[Матричное тестирование]** Настрой матричный билд в CI: прогон тестов одновременно на Go 1.21, 1.22 и 1.23.
655. **[Релизный пайплайн (Tags)]** Настрой триггер на создание Git-тега (например, `v1.0.0`). Пайплайн должен собрать бинарники под разные ОС (linux, windows, darwin), заархивировать их и создать Release в GitHub.
656. **[SemVer и Changelog]** Автоматизируй генерацию changelog при релизе (например, с помощью `release-please` или интеграции с Jira/Issues).
657. **[GitOps trigger]** После успешного пуша образа в registry, пайплайн должен клонировать отдельный репозиторий с Kubernetes-манифестами (Infrastructure Repo), заменить в нем тег образа на новый, сделать коммит и запушить. (Это триггер для ArgoCD).

### Блок 73: Kubernetes — Основы деплоя
*Цель: Запустить Go-приложение в локальном K8s (Minikube / Kind).*

658. Напиши `Deployment.yaml` для своего Go-приложения (replicas: 3). Примени `kubectl apply -f`. Проверь статус подов.
659. Напиши `Service.yaml` (ClusterIP), чтобы暴露 (expose) деплоймент внутри кластера.
660. **[ConfigMap & Secret]** Вынеси конфигурацию (порт, лог-уровень) в `ConfigMap`. Чувствительные данные (DSN БД) помести в `Secret`. Подключи их в Pod через `envFrom` или `valueFrom`.
661. **[Ingress]** Настрой `Ingress` (с использованием NGINX Ingress Controller), чтобы маршрутизировать HTTP-трафик с локального хоста на твой `Service`.
662. **[Каверзный кейс — GOMEMLIMIT]** Установи в контейнере лимит памяти `resources.limits.memory: 128Mi`. В коде Go сделай аллокацию большого слайса. Поймай `OOMKilled` (Out of Memory). Установи переменную окружения `GOMEMLIMIT=120MiB`, чтобы GC Go понимал лимиты cgroup и работал эффективнее.
663. **[Init Containers]** Напиши Pod с `initContainer`, который ждет, пока PostgreSQL поднимется (использует `pg_isready` или `nc -z`). Только после успеха должен стартовать основной контейнер с твоим приложением.
664. **[Probes (Liveness, Readiness)]** Настрой в Deployment `livenessProbe` (HTTP GET `/healthz`) и `readinessProbe` (HTTP GET `/readyz`). Сымитируй зависание приложения — K8s должен перезапустить под (Liveness). Сымитируй потерю соединения с БД — K8s должен убрать под из балансировщика (Readiness).
665. **[Startup Probe]** Если твое приложение долго стартует (например, мигрирует БД 30 секунд), Liveness-проба может убить его до старта. Добавь `startupProbe` с `failureThreshold: 30`.
666. **[Jobs / CronJobs]** Напиши `CronJob`, которая запускается каждый день в 2:00 ночи и выполняет Go-скрипт очистки старых записей из БД.
667. **[Каверзный кейс — Graceful Shutdown в K8s]** Настрой в K8s `terminationGracePeriodSeconds: 30`. Когда ты удаляешь Pod, K8s отправляет `SIGTERM`. Убедись, что твое Go-приложение ловит сигнал, прекращает принимать новые запросы (K8s через `preStop` hook удаляет Pod из Endpoints/Service), дорабатывает текущие запросы и завершается, не дожидаясь `SIGKILL`.

### Блок 74: Helm, Kustomize и GitOps
*Цель: Управлять конфигурациями для разных сред (Dev, Staging, Prod) без дублирования YAML.*

668. **[Helm Basics]** Создай Helm-чарт для своего приложения (`helm create myapp`). Изучи структуру (`templates/`, `values.yaml`). Задеплой через `helm install`.
669. **[Templating]** Параметризуй количество реплик, образ и переменные окружения в `deployment.yaml` с помощью Go-шаблонов (`.Values.replicaCount`).
670. **[Helm Dependencies]** В `Chart.yaml` добавь зависимость от PostgreSQL (Bitnami chart). Установи чарт так, чтобы вместе с приложением поднялась база данных.
671. **[Kustomize]** Перепиши деплой с Helm на Kustomize. Создай `base/` с манифестами и два оверлея: `overlays/dev` (1 replica, ConfigMap для dev) и `overlays/prod` (3 replicas, ингресс, prod secrets). Запусти `kubectl apply -k overlays/prod`.
672. **[ArgoCD / Flux (GitOps)]** Установи ArgoCD в локальный K8s. Подключи свой Git-репозиторий с манифестами. Настрой App-of-Apps паттерн: когда ты делаешь пуш в репозиторий с манифестами (меняешь тег образа), ArgoCD автоматически синхронизирует это в кластере (деплоит новую версию).

### Блок 75: Observability и Networking в K8s
*Цель: Интегрировать метрики, логи и трейсы в кластер.*

673. **[Metrics Server & HPA]** Установи Metrics Server в K8s. Настрой `HorizontalPodAutoscaler` для твоего Deployment: таргет CPU utilization = 70%. Сгенерируй нагрузку (busybox в K8s) и посмотри, как K8s автоскейлит поды с 1 до 5.
674. **[Prometheus Stack]** Установи `kube-prometheus-stack` через Helm. Настрой `ServiceMonitor`, чтобы Prometheus начал собирать метрики с твоего Go-приложения (`/metrics`). Проверь метрики в Grafana.
675. **[Loki for Logs]** Установи Grafana Loki. Настрой логирование приложения в stdout. Настрой Promtail (агент) для сбора логов подов и отправки в Loki. Найди логи своего пода в Grafana, отфильтруй по `namespace` и `app`.
676. **[OpenTelemetry Collector]** Установи OTel Collector в K8s. Настрой Go-приложение на отправку трейсов на адрес `otel-collector:4317`. Collector должен пересылать трейсы в Jaeger.
677. **[Network Policies]** Напиши `NetworkPolicy`, которая запрещает ВСЕ входящие подключения к твоему поду, кроме трафика от Pod'а с Ingress-контроллером и от Prometheus.
678. **[Каверзный кейс — Ephemeral Containers]** Собери образ `FROM scratch`. В поде упало приложение, но там нет ни `sh`, ни `ls`, ни `cat` для дебага. Используй `kubectl debug -it <pod> --image=busybox --target=<container>` чтобы прицепить контейнер с инструментами к тому же неймспейсу процессов (PID namespace) и изучить файловую систему упавшего приложения.

### Блок 76: Финальное Capstone (End-to-End Production)
*Цель: Пройти полный цикл от написания кода до деплоя в отказоустойчивый кластер.*

679. **[Multi-tier App in K8s]** Разверни систему из трех микросервисов (API Gateway, User Service, Order Service).
    - API Gateway доступен извне через Ingress.
    - Сервисы общаются между собой по gRPC через K8s Service Discovery (DNS имена вроде `user-service.default.svc.cluster.local`).
    - Настрои Liveness/Readiness пробы.
    - Настрой HPA для каждого сервиса.
    - Разверни PostgreSQL (StatefulSet + PersistentVolume) и Redis.
    - Настрой Network Policies (API Gateway может говорить с User/Order, но User/Order не могут принимать трафик извне кластера).
    - Все логи и метрики собираются в Grafana/Prometheus/Loki.

680. **[Zero-Downtime Deployment & Chaos]**
    - Настрой CI/CD пайплайн, который собирает образ и обновляет Helm-чарт.
    - ArgoCD разворачивает новую версию с использованием `RollingUpdate` (`maxSurge: 1`, `maxUnavailable: 0`).
    - Во время деплоя запусти скрипт, который постоянно делает HTTP-запросы к API Gateway.
    - **Критерий успеха:** В процессе обновления подов не должно быть ни одной 5xx ошибки или таймаута (благодаря Graceful Shutdown, readiness probes и preStop hooks).
    - **[Chaos Engineering]:** Используй `litmuschaos` или просто удаляй случайные поды (`kubectl delete pod -l app=user-service`). Убедись, что система остается доступной (показывает resilient behavior).
