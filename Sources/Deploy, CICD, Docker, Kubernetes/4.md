Развёртывание и эксплуатация Go-приложений в production — это отдельная вселенная, где код встречается с инфраструктурой. Грамотный Go-разработчик уровня Senior должен не просто писать код, но и понимать, как он будет жить в контейнерах, кластерах и пайплайнах.

Ниже представлен **масштабный блок из 100 упражнений (с 1046 по 1145)**, который проведет вас от первого `docker build` до построения enterprise-grade CI/CD пайплайнов с GitOps, zero-downtime deployments и supply chain security.

### Тема 109: Docker для Go-приложений (Основы и оптимизация)
1046. Напишите простейший Dockerfile для Go-приложения: `FROM golang:1.22`, `COPY . .`, `RUN go build`, `CMD ["./app"]`. Запустите и изучите размер образа (~1GB).
1047. **Multi-stage build:** Разделите Dockerfile на `builder` stage (с полным Go) и `runtime` stage (с минимальным базовым образом). Сравните размеры.
1048. Используйте `golang:1.22-alpine` вместо `golang:1.22` для builder stage — это уменьшит размер и ускорит сборку.
1049. Соберите полностью статический бинарник: `CGO_ENABLED=0 GOOS=linux go build -a -installsuffix cgo -ldflags="-w -s" -o app`.
1050. Используйте `FROM scratch` в runtime stage — это пустой образ размером 0 байт, содержащий только ваш бинарник.
1051. **Distroless:** Используйте `gcr.io/distroless/static-debian12` — минимальный образ от Google с базовыми библиотеками, но без shell (лучше для безопасности).
1052. Добавьте `ca-certificates` в distroless образ для работы с HTTPS: `FROM gcr.io/distroless/static-debian12:nonroot`.
1053. Оптимизируйте кэш Docker-слоёв: скопируйте сначала `go.mod` и `go.sum`, сделайте `go mod download`, затем копируйте остальной код. Теперь изменения в коде не будут вызывать перекачку зависимостей.
1054. Используйте `.dockerignore` для исключения `.git`, `vendor`, `*.md`, `tests` из контекста сборки.
1055. **Build-time variables:** Передавайте Git commit hash и версию через `--build-arg` и `ldflags`: `RUN go build -ldflags="-X main.version=${VERSION} -X main.commit=${COMMIT}"`.
1056. Запускайте контейнер от непривилегированного пользователя: `USER nonroot:nonroot` (в distroless это пользователь 65532).
1057. Добавьте health check в Dockerfile: `HEALTHCHECK --interval=30s CMD ["/app", "health"]` (если ваше приложение поддерживает subcommand для health check).
1058. Используйте `ENTRYPOINT` вместо `CMD` для бинарника, чтобы аргументы при запуске контейнера добавлялись к основной команде, а не заменяли её.
1059. Соберите multi-architecture образ для amd64 и arm64 через `docker buildx build --platform linux/amd64,linux/arm64 -t app .`
1060. Проанализируйте слои образа через `docker history app` и `dive app` (инструмент для глубокого анализа Docker-образов).

### Тема 112: Kubernetes — Базовые объекты

### Тема 116: Стратегии деплоя и Zero-Downtime
1140. **Rolling Update:** Настройте `strategy.rollingUpdate.maxSurge: 25%` и `maxUnavailable: 0` для zero-downtime деплоя.
1141. **Recreate:** Используйте для приложений, которые не могут работать в нескольких версиях одновременно (например, с несовместимыми миграциями БД).
1142. **Blue-Green:** Создайте два идентичных окружения, переключайте трафик через Service selector. Мгновенный rollback.
1143. **Canary:** Направляйте 5% трафика на новую версию, мониторьте метрики, постепенно увеличивайте до 100%.
1144. Настройте **preStop hook** с `sleep 15` для graceful termination: K8s отправляет SIGTERM, приложение завершает текущие запросы, но load balancer ещё некоторое время отправляет трафик.
1145. **Финальный босс (Production-Ready Go Deployment Pipeline):**

### 💡 Золотые правила деплоя Go-приложений:

1. **Статический бинарник + scratch/distroless.** Всегда собирайте Go-приложения с `CGO_ENABLED=0` и используйте минимальные базовые образы. Это уменьшает поверхность атаки, размер образа и время деплоя.

2. **Multi-stage builds обязательны.** Никогда не тащите полный Go toolchain в production образ. Builder stage компилирует, runtime stage содержит только бинарник + необходимые библиотеки.

3. **Graceful shutdown — это закон.** Обрабатывайте SIGTERM в приложении, закрывайте соединения, дожидайтесь завершения текущих запросов. Используйте preStop hook в K8s для синхронизации с load balancer'ом.

4. **Health checks — три типа.** Liveness (перезапускать при hang), Readiness (убирать из service при недоступности зависимостей), Startup (для медленно стартующих приложений). Без них K8s не сможет корректно управлять вашим приложением.

5. **GitOps — современный стандарт.** Git — это source of truth. Все изменения в инфраструктуре через PR. ArgoCD/Flux автоматически синхронизируют состояние кластера с Git. Ручные `kubectl apply` — это антипаттерн.

6. **Не хардкодьте конфигурацию.** Используйте ConfigMap для не-sensitive данных, Secrets (или лучше External Secrets Operator + Vault) для sensitive. Environment-specific values через overlays.

7. **Observability вшита с day one.** Prometheus metrics, structured logs, distributed tracing должны работать с первого деплоя. ServiceMonitor для автоматического discovery в Prometheus Operator.

8. **Security by default:**
   * Non-root user в контейнере.
   * Read-only root filesystem.
   * Minimal base image (distroless/scratch).
   * Network policies для изоляции.
   * Image signing (cosign) и scanning (trivy).
   * SBOM для supply chain transparency.

9. **Canary deployments для продакшена.** Никогда не деплойте сразу на 100% трафика. Используйте Argo Rollouts или Flagger с автоматическим анализом метрик. Если error rate растёт — автоматический rollback.

10. **Тестируйте disaster recovery.** Backup'ы, которые никто не восстанавливал — это не backup'ы. Регулярно тестируйте Velero restore, failover в DR регион, chaos engineering (убийство подов, network partition).

11. **Cost optimization:**
    * Правильные requests/limits (слишком большие — трата денег, слишком маленькие — OOM/throttling).
    * Spot/Preemptible instances для stateless workloads.
    * Karpenter для эффективного node autoscaling.
    * VPA для автоматической оптимизации resources.
