### Раздел 19: Основы горутин и каналов (Задачи 233–242)

*Горутины и каналы — фундаментальные строительные блоки конкурентности в Go. Эти задачи помогут понять модель планировщика (GMP), правила блокировок и передачу данных.*

233. **Запуск первой горутины**: Напишите программу, которая запускает горутину, выводящую текст `"Привет из горутины!"`. В основной функции `main` напишите обычный вывод. Запустите программу несколько раз. Почему вывод из горутины то появляется, то исчезает? (Изучите поведение планировщика: `main` не ждет завершения фоновых горутин).
234. **Замыкание переменной цикла в горутине**: Напишите цикл `for i := 0; i < 10; i++`, внутри которого запускается горутина `go func() { fmt.Println(i) }()`. Запустите код на версии Go ниже 1.22 (или смоделируйте старое поведение, передавая значение не через аргумент). Почему выводится много одинаковых чисел (например, девяток или десяток)? Исправьте это, явно передавая `i` в качестве аргумента анонимной функции: `go func(val int) { ... }(i)`.
235. **Небуферизованный канал (Блокировка)**: Создайте небуферизованный канал `ch := make(chan int)`. Попробуйте записать туда число `ch <- 42` прямо в функции `main` без запуска других горутин. Объясните причину возникновения дедлока (`all goroutines are asleep - deadlock!`). Исправьте код, запустив фоновую горутину, которая считывает данные из этого канала.
236. **Буферизованный канал**: Создайте буферизованный канал емкостью 3 элемента `make(chan int, 3)`. Запишите туда три числа подряд в функции `main`. Заблокируется ли программа? Попробуйте записать четвертое число. Объясните разницу между поведением буферизованных и небуферизованных каналов.
237. **Закрытие канала и Comma-ok**: Создайте канал, запустите горутину, которая пишет туда числа 1, 2, 3 и закрывает канал с помощью `close(ch)`. В основной горутине считывайте данные в бесконечном цикле, используя синтаксис `val, ok := <-ch`. Выведите значение `ok`. Что возвращает канал после закрытия и как понять, что передача данных завершена?
238. **Бесконечное чтение из закрытого канала (Баг с CPU 100%)**: Напишите программу, которая закрывает канал, а затем в бесконечном цикле `for` читает из него значения без проверки `ok`. Убедитесь, что цикл никогда не завершается, потребляя 100% процессора и возвращая нулевые значения (zero values). Напишите комментарий о том, как избегать этого бага.
239. **Однонаправленные каналы**: Напишите две функции:
    * `produce(ch chan<- int)` — только записывает данные в канал.
    * `consume(ch <-chan int)` — только читает данные из канала.
    Попробуйте внутри `produce` прочитать из канала или внутри `consume` записать в него. Убедитесь, что компилятор предотвращает такие действия на этапе сборки.
240. **Итерация по каналу через `range`**: Создайте канал, запишите туда несколько строк в фоновой горутине, а затем закройте канал. В основной горутине обойдите канал с помощью цикла `for val := range ch`. Убедитесь, что цикл автоматически завершается, когда канал закрыт. Что произойдет, если забыть закрыть канал в фоновой горутине?
241. **Мультиплексирование с `select`**: Создайте два канала, в которые фоновые горутины отправляют сообщения с разной задержкой (`time.Sleep`). С помощью конструкции `select` ожидайте сообщения из обоих каналов в цикле `for` и выводите то сообщение, которое пришло быстрее.
242. **Неблокирующее чтение (`default` в `select`)**: Напишите программу, которая пытается прочитать сообщение из канала. Если сообщения в канале прямо сейчас нет, программа не должна блокироваться и ждать — она должна мгновенно вывести сообщение `"Данных нет"` и продолжить работу. Реализуйте это с помощью ветки `default` внутри `select`.

### Раздел 20: Синхронизация и примитивы пакета `sync` (Задачи 243–255)

*Когда несколько горутин работают с общими данными, возникает необходимость в явной синхронизации. В этом блоке вы разберете мьютексы, атомики, группы ожидания и дедлоки.*

243. **Использование `sync.WaitGroup`**: Перепишите задачу №233. Вместо использования костылей в виде `time.Sleep` для ожидания горутины, примените `sync.WaitGroup`. Объясните правила вызова методов `Add()`, `Done()` и `Wait()`.
244. **Ошибка копирования `WaitGroup`**: Создайте функцию `worker(wg sync.WaitGroup)`, которая выполняет работу и вызывает `wg.Done()`. Запустите её в горутине, передав `wg` по значению. Объясните, почему программа зависает в бесконечном ожидании дедлока. Исправьте ошибку, передавая `WaitGroup` по указателю `*sync.WaitGroup`.
245. **Состояние гонки (Race Condition)**: Создайте глобальную переменную `counter := 0`. Запустите 1000 горутин, каждая из которых инкрементирует счетчик: `counter++`. Дождитесь завершения всех горутин через `WaitGroup` и выведите `counter`. Почему результат почти никогда не равен 1000? Запустите компиляцию программы с флагом обнаружения гонок: `go run -race main.go` и изучите отчет.
246. **Защита данных через `sync.Mutex`**: Исправьте предыдущую задачу №245. Добавьте `sync.Mutex` и защитите операцию инкремента критической секцией (`mutex.Lock()` / `mutex.Unlock()`). Убедитесь, что теперь результат всегда равен 1000, а детектор гонок больше не выдает предупреждений.
247. **Безопасная разблокировка с `defer`**: Напишите функцию, которая блокирует мьютекс, делает сложные вычисления, которые могут вернуть ошибку (`return err`), и разблокирует мьютекс. Используйте `defer mutex.Unlock()` сразу после блокировки. Объясните, почему ручной вызов `Unlock()` перед каждым `return` считается плохой практикой.
248. **Оптимизация чтения с `sync.RWMutex`**: Создайте структуру "База данных в памяти" (под капотом обычная мапа). Напишите методы записи и чтения. Предполагая, что чтение происходит в 99% случаев, а запись — в 1%, используйте `sync.RWMutex`. Продемонстрируйте параллельный вызов методов чтения (`RLock` / `RUnlock`), не блокирующих друг друга.
249. **Однократное выполнение (`sync.Once`)**: Напишите потокобезопасный синглтон инициализации подключения к базе данных. Используйте `sync.Once`, чтобы гарантировать, что тяжелая функция инициализации выполнится ровно один раз, даже если её параллельно вызывают 100 горутин.
250. **Условные переменные (`sync.Cond`)**: Напишите программу, где несколько горутин-воркеров ждут сигнала о готовности данных. Используйте `sync.Cond` с методом `Wait()`. Главная горутина подготавливает данные и будит все воркеры сразу с помощью метода `Broadcast()`.
251. **Потокобезопасная мапа (`sync.Map`)**: Напишите программу, где 50 горутин параллельно пишут и читают данные из одной мапы. Обычная мапа упадет с паникой `concurrent map writes`. Решите эту проблему с помощью встроенной структуры `sync.Map` и её методов `Store`, `Load` и `Delete`.
252. **Пул объектов (`sync.Pool`)**: Создайте структуру `Buffer` большого размера. Напишите код, который часто создает и уничтожает эти буферы, перегружая сборщик мусора (GC). Оптимизируйте программу, используя `sync.Pool` для переиспользования выделенной памяти под буферы.
253. **Атомарные операции (`sync/atomic`)**: Перепишите задачу №245 (инкремент счетчика 1000 горутинами) без использования мьютексов. Примените функцию `atomic.AddInt64` (или `atomic.Int64` в новых версиях Go). Сравните производительность атомиков и мьютексов.
254. **Классический дедлок (Deadlock)**: Создайте две горутины и два мьютекса `A` и `B`. Напишите код так, чтобы первая горутина блокировала мьютекс `A` и пыталась заблокировать `B`, а вторая горутина в это же время блокировала мьютекс `B` и пыталась заблокировать `A`. Запустите код и проанализируйте панику планировщика.
255. **Утечка горутин (Goroutine Leak)**: Напишите функцию, которая запускает горутину, ожидающую запись в небуферизованный канал. Однако функция завершается раньше, и никто никогда в этот канал ничего не запишет. Объясните, почему запущенная горутина останется в памяти навсегда и как такие утечки могут исчерпать ресурсы сервера.

### Раздел 21: Пакет `context` и управление жизненным циклом (Задачи 256–263)

*Пакет `context` используется для отмены долгоиграющих операций, обработки таймаутов и передачи метаданных сквозь цепочки вызовов.*

256. **Ручная отмена (`context.WithCancel`)**: Создайте контекст с возможностью отмены. Запустите фоновую горутину, которая в цикле `for` выполняет фоновую работу (например, раз в секунду). Горутина должна проверять канал `<-ctx.Done()`. В основной горутине подождите 3 секунды и вызовите функцию `cancel()`. Убедитесь, что фоновая горутина корректно завершила работу.
257. **Таймаут операции (`context.WithTimeout`)**: Напишите функцию, имитирующую тяжелый сетевой запрос, занимающий 5 секунд. Вызовите эту функцию с контекстом, у которого установлен таймаут в 2 секунды. Функция должна вернуть ошибку `context.DeadlineExceeded` по истечении таймаута.
258. **Передача метаданных (`context.WithValue`)**: Создайте цепочку вызовов функций (например, `Middleware -> Handler -> Controller`). Положите в контекст на самом верхнем уровне уникальный ID запроса (`RequestID`). Извлеките и выведите его на самом глубоком уровне в контроллере. Объясните, почему не стоит использовать контекст для передачи опциональных параметров бизнес-логики.
259. **Обработка `ctx.Done()` в `select`**: Напишите горутину-генератор случайных чисел, которая бесконечно пишет числа в канал. Настройте `select` внутри генератора так, чтобы при получении сигнала из `ctx.Done()` генератор закрывал свой канал и завершал работу, предотвращая утечку ресурсов.
260. **Обязательный вызов `cancel()`**: Напишите функцию, которая создает `context.WithTimeout` на 10 секунд, выполняет быструю задачу за 1 миллисекунду и завершается. Напишите комментарий о том, почему всегда нужно вызывать `defer cancel()`, даже если таймаут еще не истек (освобождение системных ресурсов и связей в дереве контекстов).
261. **Контекст в HTTP-клиенте**: Напишите простой HTTP-запрос к медленному серверу с помощью пакета `net/http`. Привяжите к HTTP-запросу контекст с таймаутом в 500 миллисекунд с помощью `http.NewRequestWithContext`. Проверьте, как клиент обрывает соединение, если сервер не ответил вовремя.
262. **Иерархия контекстов (Пропагация отмены)**: Создайте родительский контекст с возможностью отмены. От него создайте дочерний контекст. Запустите две горутины (одну на родительском, другую на дочернем контекстах). Отмените родительский контекст. Убедитесь, что дочерний контекст отменился автоматически. Попробуйте сделать наоборот (отменить дочерний) и проверьте, повлияло ли это на родительский.
263. **Использование `context.AfterFunc` (Go 1.21+)**: Создайте контекст с таймаутом. С помощью функции `context.AfterFunc` зарегистрируйте замыкание, которое должно выполниться автоматически в момент отмены контекста (например, записать лог или закрыть сетевой сокет).

### Раздел 22: Сложные паттерны и каверзные сценарии конкурентности (Задачи 264–277)

*Продвинутые шаблоны проектирования конкурентных систем. В этом блоке вы соберете классические паттерны: конвейеры, пулы воркеров, ограничители частоты и динамические системы.*

264. **Паттерн "Конвейер" (Pipeline)**: Напишите конвейер обработки чисел из трех стадий (каждая стадия — это функция, принимающая канал и возвращающая новый канал):
    * Стадия 1: Генерация чисел от 1 до 100.
    * Стадия 2: Фильтрация (пропускает только нечетные числа).
    * Стадия 3: Возведение в квадрат.
    В функции `main` прочитайте финальные результаты из выходного канала.
265. **Паттерн "Worker Pool" (Пул воркеров)**: Напишите классический пул воркеров. У вас есть канал задач `jobs` и канал результатов `results`. Запустите фиксированное количество горутин-воркеров (например, 3 воркера), которые разбирают задачи из канала `jobs`, имитируют работу и отправляют результаты в канал `results`.
266. **Паттерн "Fan-In" (Слияние каналов)**: Напишите функцию `FanIn(channels ...<-chan int) <-chan int`. Она должна принимать произвольное количество каналов, запускать горутины для чтения из каждого и сливать все полученные данные в один результирующий канал. Обеспечьте корректное закрытие результирующего канала только после того, как закроются ВСЕ входные каналы (используйте `sync.WaitGroup`).
267. **Паттерн "Fan-Out" (Раздача задач)**: Напишите программу, которая берет поток данных из одного канала и распределяет его по нескольким разным каналам-слушателям (каждое сообщение должно дублироваться во все каналы-слушатели).
268. **Ограничение частоты запросов (Rate Limiting)**: Напишите программу, имитирующую отправку запросов к внешнему API. API разрешает обрабатывать не более 5 запросов в секунду. Используйте тикер `time.NewTicker`, чтобы ограничить частоту отправки запросов (ровно 1 запрос каждые 200 миллисекунд).
269. **Rate Limiting с очередью (Bursting)**: Перепишите предыдущую задачу. Настройте ограничение частоты так, чтобы система могла обрабатывать всплески (bursts) до 3 запросов одновременно, но при этом средняя скорость не превышала 5 запросов в секунду (реализуйте это с помощью буферизованного канала емкостью 3 элемента, который постепенно наполняется по тикеру).
270. **Семафор на каналах (Concurrency Limiter)**: Напишите функцию, которая должна параллельно скачать 100 файлов. Однако жесткий лимит операционной системы разрешает одновременно открывать не более 10 сетевых соединений. Реализуйте этот ограничитель конкурентности, используя буферизованный канал емкостью 10 в качестве семафора (запись в канал перед стартом задачи, чтение из канала при завершении задачи).
271. **Паттерн "Future/Promise"**: Напишите функцию `FetchData() <-chan string`, которая мгновенно возвращает канал (обещание результата), а внутри запускает фоновую горутину для тяжелого вычисления. Когда вычисление завершено, горутина пишет результат в канал и закрывает его. В основной горутине выполните другие полезные действия, а затем заберите результат из канала, когда он понадобится.
272. **Паттерн "Publish-Subscribe" (Pub-Sub)**: Напишите простую шину сообщений на чистом Go. Должна быть структура `PubSub` с методами `Subscribe(topic string) <-chan string` и `Publish(topic string, msg string)`. Обеспечьте потокобезопасность шины (используйте мьютексы).
273. **Безопасный пуск горутин (`SafeGo`)**: Напишите функцию `SafeGo(fn func())`. Она должна запускать переданную функцию `fn` в горутине, но при этом защищать приложение от падения, если внутри `fn` произойдет паника (panic). Внутри `SafeGo` должен быть перехватчик `recover()`, который логирует панику, но не дает завершиться всему процессу.
274. **Динамический пул воркеров**: Напишите сложный пул воркеров, который умеет масштабироваться во время работы. Если очередь задач в канале превышает определенный лимит, пул должен запускать дополнительные горутины-воркеры. Если задачи заканчиваются и канал пустеет — лишние воркеры должны автоматически завершать свою работу, освобождая ресурсы.
275. **Использование `errgroup.Group`**: Импортируйте пакет `golang.org/x/sync/errgroup`. Напишите программу, которая параллельно выполняет 5 сетевых запросов. Если хотя бы один из запросов завершается с ошибкой, группа должна мгновенно отменить все остальные активные запросы (используя встроенный контекст) и вернуть первую возникшую ошибку.
276. **Конкурентное слияние отсортированных данных (K-Way Merge)**: У вас есть 3 канала, в которые фоновые горутины отправляют отсортированные числа (например, в первом канале: `1, 4, 7...`, во втором: `2, 5, 8...`, в третьем: `3, 6, 9...`). Напишите функцию, которая считывает данные из этих каналов и сливает их в один выходной канал так, чтобы на выходе числа шли строго по возрастанию (`1, 2, 3, 4, 5, 6...`).
277. **Плавное завершение работы (Graceful Shutdown)**: Напишите каркас серверного приложения.
    * Программа должна запускать фоновый воркер, обрабатывающий задачи в цикле.
    * Напишите прослушиватель системных сигналов ОС (например, `SIGINT`, `SIGTERM` через пакет `os/signal`).
    * При получении сигнала о закрытии (например, нажатие Ctrl+C в консоли), программа не должна обрываться мгновенно. Она должна остановить прием новых задач, дождаться завершения текущих активных задач, закрыть все каналы и файлы, и только после этого корректно завершить работу процесса.
