## Часть XIV. Конкурентность (Concurrency)

### 39. Горутины и WaitGroup

**Упражнение 14.1.** Запусти функцию `sayHello()` как горутину: `go sayHello()`. Покажи, что `main` завершается раньше, чем горутина успевает выполниться. Добавь `time.Sleep` как временное решение.

**Упражнение 14.2.** Используй `sync.WaitGroup` для ожидания завершения 3 горутин. Каждая горутина печатает свой номер и вызывает `wg.Done()`. В `main` — `wg.Wait()`.

**Упражнение 14.3.** Напиши функцию `spawnWorkers(n int, wg *sync.WaitGroup)`. Создай `n` горутин, каждая спит `time.Duration(id)*100ms` и печатает `"worker X done"`. Дождись всех через `wg.Wait()`.

**Упражнение 14.4.** Покажи, что **передача WaitGroup по значению** в горутину ломает синхронизацию (копия счётчика). Исправь: передавай по указателю или используй замыкание с внешней `wg`.

**Упражнение 14.5.** Запусти 1000 горутин, каждая инкрементирует **глобальную** переменную `counter` (`counter++`). Без синхронизации запусти с `go run -race`. Проанализируй отчёт race detector'а.

**Упражнение 14.6.** Исправь data race из 14.5 через `sync.Mutex` (пока просто познакомься, детали в следующей секции). Убедись, что `-race` больше не ругается.

**Упражнение 14.7.** Напиши программу, которая вычисляет сумму чисел от 1 до N **параллельно**: разбивает диапазон на 4 части, каждая горутина считает свою часть, результат отправляет в канал, `main` суммирует.

**Упражнение 14.8.** Создай горутину с **бесконечным циклом** и попробуй остановить её извне через `bool` флаг (читаемый в цикле). Покажи, что без `sync/atomic` или mutex это **data race**. Исправь через `atomic.Bool` (или `atomic.Value`).

**Упражнение 14.9.** Напиши функцию `ParallelMap(inputs []int, fn func(int) int) []int`, запускающую обработку каждого элемента в отдельной горутине. Собери результаты в правильном порядке (используй слайс с индексами).

**Упражнение 14.10.** Покажи **goroutine leak**: запусти горутину, которая пишет в канал, но никто не читает. Горутина зависнет навечно. Используй `runtime.NumGoroutine()` до и после, чтобы показать утечку.

**Упражнение 14.11.** Напиши программу с `GOMAXPROCS`. Выведи `runtime.GOMAXPROCS(0)` (по умолчанию = число CPU). Установи в 1 и запусти CPU-bound задачу в нескольких горутинах. Замерь время до и после.

**Упражнение 14.12.** Напиши программу, которая демонстрирует: горутины — ** cooperatively scheduled**. Создай CPU-bound горутину (бесконечный цикл без вызовов функций/каналов) и попробуй запустить вторую. Покажи, что в Go 1.14+ preemption работает даже для чистых циклов, но раньше была проблема.

**Упражнение 14.13.** Создай горутину с **recover**. Покажи, что паника в горутине **не убивает** программу, если есть `defer recover()`. Напиши `SafeGo(fn func())`, которая запускает функцию в горутине с защитой от panic.

**Упражнение 14.14.** Напиши программу с `sync.WaitGroup`, где количество горутин определяется динамически (например, список URL). Обработай каждый URL в горутине, собери статус-коды. Используй `wg.Add(1)` перед запуском, а не `wg.Add(n)` заранее.

**Упражнение 14.15.** Напиши программу с **"потерянной" горутиной**: `go func() { for { select {} } }()`. Покажи, что она никогда не завершится. Объясни, как это обнаружить через `pprof` или `runtime.NumGoroutine()`.

### 40. Каналы — основы

**Упражнение 14.16.** Создай **unbuffered канал** `ch := make(chan int)`. Запусти горутину, которая пишет в канал. В `main` прочитай. Покажи, что запись блокируется, пока нет читателя (синхронизация "рука об руку").

**Упражнение 14.17.** Создай **buffered канал** `ch := make(chan int, 3)`. Напиши 3 значения без читателя. Покажи, что 4-я запись заблокируется. Затем прочитай все значения.

**Упражнение 14.18.** Напиши программу с **"deadlock"** через канал: `main` пишет в unbuffered канал без горутины-читателя. Получи `fatal error: all goroutines are asleep - deadlock!`. Объясни, почему Go обнаруживает это.

**Упражнение 14.19.** Используй `close(ch)` для сигнализации о завершении. Запусти горутину-продюсер, которая пишет 10 чисел и закрывает канал. В `main` читай через `for v := range ch`. Покажи, что цикл завершается при закрытии.

**Упражнение 14.20.** Покажи, что **чтение из закрытого канала** возвращает zero value и `ok=false`: `v, ok := <-ch`. Напиши функцию `Drain(ch <-chan int) []int`, которая забирает все оставшиеся значения после закрытия.

**Упражнение 14.21.** Напиши функцию `Generate(nums ...int) <-chan int`, возвращающую канал. Горутина внутри пишет числа и закрывает канал. Покажи **"generator pattern"**.

**Упражнение 14.22.** Напиши функцию `Square(in <-chan int) <-chan int`, читающую из входного канала, возводящую в квадрат и пишущую в выходной. Закрой выходной канал при закрытии входного. Это **pipeline stage**.

**Упражнение 14.23.** Соедини генератор и `Square` в pipeline: `for v := range Square(Generate(2, 3, 4, 5)) { fmt.Println(v) }`. Покажи композицию стадий.

**Упражнение 14.24.** Напиши функцию `Merge(chs ...<-chan int) <-chan int`, которая мержит несколько входных каналов в один выходной. Используй `sync.WaitGroup` + горутину на каждый входной канал. Закрой выходной, когда все входные закрыты.

**Упражнение 14.25.** Покажи **"panic на закрытии закрытого канала"**: закрой канал дважды. Получи `panic: close of closed channel`. Напиши `SafeClose(ch chan int)` с `recover` или `sync.Once`.

**Упражнение 14.26.** Напиши программу с **"nil channel"**: `var ch chan int` (nil). Покажи, что запись в nil канал **блокирует навечно** (deadlock, если нет других горутин). Чтение из nil канала тоже блокирует навечно.

**Упражнение 14.27.** Напиши **"done channel" pattern**: функция `LongRunning(done <-chan struct{})` читает из `done` в `select`. При получении сигнала — выходит. Покажи graceful cancellation через закрытие done-канала.

**Упражнение 14.28.** Напиши **"quit channel"** с обратной связью: горутина получает сигнал на остановку, делает cleanup и пишет в `quit` канал подтверждение. `main` ждёт подтверждения через `select`.

**Упражнение 14.29.** Реализуй **bounded parallelism** через канал-семафор: `semaphore := make(chan struct{}, 3)`. Каждая горутина захватывает слот (`semaphore <- struct{}{}`), выполняет работу, освобождает (`<-semaphore`). Ограничь одновременные горутины.

**Упражнение 14.30.** Напиши программу, демонстрирующую **"channel direction"**: функция принимает `send chan<- int` (только для записи) и `receive <-chan int` (только для чтения). Попробуй записать в `receive` — получи ошибку компиляции.

### 41. Select и мультиплексирование

**Упражнение 14.31.** Напиши программу с `select` между двумя каналами: `ch1` и `ch2`. Одна горутина пишет в `ch1` через 100ms, другая в `ch2` через 200ms. В `main` читай в цикле `for` с `select` и печатай, откуда пришло значение. Покажи, что `select` выбирает **готовый** канал.

**Упражнение 14.32.** Покажи **случайный выбор** в `select`: запусти 10 горутин, каждая пишет в свой канал. В `select` с 10 case'ами — покажи, что при одновременной готовности выбор **равновероятен** (random uniform).

**Упражнение 14.33.** Напиши **"non-blocking select"** с `default`: проверь, есть ли данные в канале, не блокируясь. Если нет — сделай что-то другое (например, `fmt.Println("no data")`).

**Упражнение 14.34.** Напиши **"timeout pattern"** с `select`: читай из канала `ch`, но если данных нет в течение 2 секунд — выведи `"timeout"` и выйди. Используй `time.After(2 * time.Second)`.

**Упражнение 14.35.** Напиши **"heartbeat"** pattern: горутина каждые 500ms пишет `"ping"` в канал. В `main` читай с `select` и таймаутом 1s. Если нет ping'a в течение 1s — считай, что горутина зависла.

**Упражнение 14.36.** Напиши программу с `select` в цикле, где один case — чтение из `done` канала (завершение), другой — основная работа. При закрытии `done` — корректно выйди из цикла.

**Упражнение 14.37.** Напиши **"priority select"** через `for` с `select` и `default`: сначала проверяй высокоприоритетный канал (с `case`), если он не готов — проверяй низкоприоритетный через `default` и вложенный `select`. Обсуди, почему в Go нет встроенного приоритета в `select`.

**Упражнение 14.38.** Напиши **"fan-in"** через `select` в одной горутине: два входных канала мержатся в один выходной. Используй `select` с двумя case'ами в цикле. Закрой выходной, когда оба входных закрыты (используй флаги или `sync.WaitGroup`).

**Упражнение 14.39.** Напиши программу с `select` и **закрытым каналом**: один из case'ов читает из закрытого канала. Покажи, что закрытый канал **всегда готов** для чтения (возвращает zero value). Это может привести к "busy loop" если не обрабатывать `ok`.

**Упражнение 14.40.** Напиши **"rate limiter"** через `select` + `time.Ticker`: ограничь обработку до 5 запросов в секунду. Запросы поступают в канал, `select` ждёт либо запрос, либо тика таймера.

**Упражнение 14.41.** Напиши **"debounce"** через `select` + `time.After`: при поступлении события запускай таймер. Если за время таймера пришло новое событие — сбрасывай старый таймер и запускай новый. Обработай только последнее событие в серии.

**Упражнение 14.42.** Напиши **"throttle"**: пропускай события не чаще, чем раз в N миллисекунд. Если событие пришло раньше — игнорируй (или буферизуй одно). Используй `select` с `time.After`.

**Упражнение 14.43.** Напиши **"graceful shutdown"**: `select` между рабочим каналом и `os.Signal` каналом (`signal.Notify`). При получении `os.Interrupt` — закрой рабочий канал, дождись `sync.WaitGroup`, выведи `"shutting down gracefully"`.

**Упражнение 14.44.** Напиши программу с `select` и **nil каналом**: динамически "выключай" case, присваивая каналу `nil`. Покажи, что case с nil каналом **никогда не выбирается** (это способ временно отключить case).

**Упражнение 14.45.** Напиши **"round-robin"** через `select`: три канала-источника. Используй `select` в цикле, но после чтения из канала A — временно "отключай" его (nil) на одну итерацию, чтобы дать возможность B и C. Обсуди, почему это сложно сделать чисто через select.

### 42. Синхронизация: Mutex, RWMutex, Once, Pool, Map

**Упражнение 14.46.** Реализуй `SafeCounter` с `sync.Mutex`. Методы: `Inc()`, `Dec()`, `Value() int`. Запусти 1000 горутин, каждая инкрементирует 1000 раз. Проверь через `-race`, что гонок нет.

**Упражнение 14.47.** Покажи **deadlock с Mutex**: рекурсивный вызов `Lock()` внутри метода с `sync.Mutex` (не `RWMutex`). Получи deadlock. Объясни, почему `sync.Mutex` не reentrant. Исправь через вынесение логики или `sync.RWMutex` (если чтение).

**Упражнение 14.48.** Реализуй `SafeMap` с `sync.RWMutex`. Методы: `Get(key string) (int, bool)`, `Set(key string, value int)`, `Delete(key string)`. Запусти читателей и писателей. Покажи, что `RLock` позволяет параллельное чтение.

**Упражнение 14.49.** Сравни производительность: `sync.Mutex` vs `sync.RWMutex` при 90% чтений и 10% записей. Замерь `time.Now()` до/после 1M операций. Покажи, что `RWMutex` выигрывает при преобладании чтений.

**Упражнение 14.50.** Используй `sync.Map` для хранения `map[string]int`. Запусти конкурентные чтения/записи. Покажи, что `sync.Map` безопасен без ручного mutex. Напиши `Range` с `func(key, value any) bool`.

**Упражнение 14.51.** Сравни `sync.Map` и `map + sync.RWMutex` по производительности. Напиши бенчмарк (`testing.B`). Покажи, что `sync.Map` оптимизирован под **read-mostly** сценарии с редкими записами, а для write-heavy — обычная map + mutex быстрее.

**Упражнение 14.52.** Используй `sync.Once` для **lazy initialization**: `var once sync.Once; var instance *Singleton`. Функция `GetInstance()` вызывает `once.Do(func() { instance = &Singleton{} })`. Покажи, что инициализация происходит ровно один раз, даже при конкурентных вызовах.

**Упражнение 14.53.** Покажи, что `sync.Once` **не сбрасывается**: если `Do` паникует, `Once` считает выполненным и повторно не вызовет функцию. Напиши программу, демонстрирующую это (используй `recover` внутри `Do`).

**Упражнение 14.54.** Используй `sync.Pool` для переиспользования `bytes.Buffer`. Напиши функцию, которая берёт буфер из пула, пишет в него, возвращает строку, и **обязательно** возвращает буфер в пул через `defer`. Покажи снижение аллокаций.

**Упражнение 14.55.** Напиши программу с `sync.Pool`, где забываешь `Put` — покажи, что это не утечка памяти (GC соберёт), но теряется преимущество пула. Замерь аллокации через `runtime.ReadMemStats`.

**Упражнение 14.56.** Используй `sync.Cond` (условная переменная): создай `sync.Cond` с `sync.Mutex`. Одна горутина ждёт `cond.Wait()`, пока другая не вызовет `cond.Signal()` или `cond.Broadcast()`. Реализуй "очередь ожидания" или "barrier".

**Упражнение 14.57.** Реализуй **barrier** на `sync.WaitGroup`: N горутин должны достичь точки, прежде чем все продолжат. Используй `sync.WaitGroup` дважды: первый — достижение барьера, второй — завершение.

**Упражнение 14.58.** Реализуй **"try lock"** через `sync.Mutex` + канал: `TryLock()` захватывает мьютекс с `select` и `default` (или используй `atomic` для флага). Объясни, почему в `sync.Mutex` нет встроенного `TryLock` (до Go 1.18; с 1.18 есть `TryLock()` — покажи его).

**Упражнение 14.59.** Напиши программу с **"priority inversion"** (симуляция): высокоприоритетная горутина ждёт мьютекс, захваченный низкоприоритетной. Покажи, что в Go планировщик не гарантирует приоритеты, но мьютекс fair (очередь FIFO с Go 1.19+).

**Упражнение 14.60.** Используй `sync/atomic` для lock-free счётчика: `atomic.AddInt64(&counter, 1)`. Запусти 1M инкрементов из 100 горутин. Сравни производительность с `sync.Mutex`.

### 43. Атомарные операции (sync/atomic)

**Упражнение 14.61.** Реализуй счётчик через `atomic.Int64` (Go 1.19+): `var counter atomic.Int64`. Методы: `counter.Add(1)`, `counter.Load()`, `counter.Store(0)`. Запусти конкурентные инкременты.

**Упражнение 14.62.** Реализуй **lock-free стек** через `atomic.Pointer` (Go 1.19+): `type Node[T any] struct { value T; next atomic.Pointer[Node[T]] }`. Методы `Push` и `Pop` через `atomic.CompareAndSwapPointer` (или `CompareAndSwap` в `atomic.Pointer`).

**Упражнение 14.63.** Напиши программу с `atomic.Value`. Сохрани в неё `config struct{ Host string; Port int }`. Покажи, что `atomic.Value` позволяет **атомарно** заменить конфиг целиком. Читатели получают либо старую, либо новую версию, но не "смешанную".

**Упражнение 14.64.** Напиши **spin-lock** через `atomic.Bool`: `for !lock.CompareAndSwap(false, true) { runtime.Gosched() }`. Объясни, когда spin-lock уместен (короткие критические секции), а когда лучше `sync.Mutex`.

**Упражнение 14.65.** Напиши программу с `atomic.AddUint64` и **memory ordering**: покажи, что атомарные операции гарантируют **happens-before** отношения между горутинами. Без `atomic` (или `sync`) компилятор может переупорядочить инструкции.

**Упражнение 14.66.** Реализуй **lock-free max** через `atomic.Int64`: `UpdateMax(newVal int64)` атомарно обновляет значение, только если `newVal > current`. Используй цикл `for` с `Load` и `CompareAndSwap`.

**Упражнение 14.67.** Напиши программу с `atomic.Pointer` и **ABA-problem**: покажи, что `CompareAndSwap` может "пропустить" изменение, если указатель вернулся к тому же значению. Обсуди, почему в Go managed memory это менее критично, чем в C++.

**Упражнение 14.68.** Напиши **"one-shot"** сигнал через `atomic.Bool`: `var ready atomic.Bool`. Горутина-продюсер делает `ready.Store(true)` после инициализации. Потребители ждут в цикле `for !ready.Load() { runtime.Gosched() }`. Покажи, что это работает без mutex.

**Упражнение 14.69.** Сравни `atomic` vs `sync.Mutex` на бенчмарке: 1M инкрементов, 100 горутин. Покажи, что `atomic` быстрее на порядок для простых операций.

**Упражнение 14.70.** Напиши программу с **"false sharing"**: два `atomic.Int64` на соседних полях одной структуры. Запусти две горутины, каждая инкрементирует свой счётчик. Покажи, что из-за кэш-линии (64 байта) они конкурируют за одну линию. Исправь через **padding** (`_ [56]byte` между полями).

### 44. Context

**Упражнение 14.71.** Создай `context.Background()` и `context.WithCancel()`. Запусти горутину, которая читает из `ctx.Done()`. Вызови `cancel()` — покажи, что горутина получает сигнал и завершается.

**Упражнение 14.72.** Используй `context.WithTimeout()`. Запусти HTTP-запрос (или `time.Sleep`) в горутине. Если не успевает за 2 секунды — `ctx.Done()` срабатывает, программа выводит `"timeout"`.

**Упражнение 14.73.** Используй `context.WithDeadline()`. Установи дедлайн на `time.Now().Add(5 * time.Second)`. Покажи разницу между `deadline` и `timeout` (deadline — абсолютное время, timeout — относительное).

**Упражнение 14.74.** Напиши функцию `ProcessWithContext(ctx context.Context, data []int) (int, error)`, которая суммирует числа, но проверяет `ctx.Err()` в цикле. Если контекст отменён — верни ошибку немедленно.

**Упражнение 14.75.** Покажи **"context propagation"**: `main` создаёт `ctx` с таймаутом. Передаёт в функцию A, которая создаёт `ctx2, cancel := context.WithCancel(ctx)`. Отменяет `ctx2`. Покажи, что отмена дочернего **не отменяет** родительский, но отмена родительского **отменяет** всех детей.

**Упражнение 14.76.** Используй `context.WithValue()` для передачи `requestID` через цепочку вызовов. Напиши middleware, который извлекает `requestID` из `ctx` и логирует. Покажи, что значение доступно во всех дочерних функциях.

**Упражнение 14.77.** Напиши **"context tree"**: создай родительский `ctx`, от него 3 дочерних `WithCancel`, от каждого — ещё по 2. Отмени родительский. Покажи, что **все** дочерние контексты отменились (через `select` на `Done()` в каждом).

**Упражнение 14.78.** Напиши функцию `Or(ctx1, ctx2 context.Context) context.Context`, возвращающую контекст, который отменяется, когда отменяется **любой** из входных. Используй горутину + `select` на `ctx1.Done()` и `ctx2.Done()`.

**Упражнение 14.79.** Покажи **"context leak"**: создаёшь `context.WithCancel` в цикле, но не вызываешь `cancel()`. Горутина из `WithCancel` остаётся висеть. Используй `runtime.NumGoroutine()` для демонстрации. Исправь через `defer cancel()`.

**Упражнение 14.80.** Напиши **"graceful shutdown with context"**: `main` создаёт `ctx` с `signal.NotifyContext`. При `Ctrl+C` — контекст отменяется. Все worker'ы читают `ctx.Done()`, завершают текущую работу, делают cleanup и выходят.

**Упражнение 14.81.** Напиши программу с `context.WithValue`, пытающуюся передать **неэкспортируемый ключ** (unexported type). Покажи, что это **best practice** для избежания коллизий ключей между пакетами. Создай `type contextKey string` в пакете.

**Упражнение 14.82.** Напиши функцию `SleepWithContext(ctx context.Context, d time.Duration) error`, которая спит `d` или просыпается раньше при отмене `ctx`. Используй `select` между `time.After(d)` и `ctx.Done()`.

**Упражнение 14.83.** Напиши **"worker pool with context"**: N горутин читают задачи из канала. Если `ctx` отменён — все воркеры выходят. Задачи — это функции `func()`. Покажи, что воркеры завершаются, даже если в канале остались задачи.

**Упражнение 14.84.** Напиши **"parallel fetch with context"**: запускаешь 5 HTTP-запросов (или `time.Sleep` как симуляцию) в горутинах. Если один упал с ошибкой или таймаут — отменяй остальные через `cancel()`. Собери первую ошибку или все результаты.

**Упражнение 14.85.** Напиши **"context deadline exceeded"** обработку: функция делает `select` между `ctx.Done()` и результатом. Если `ctx.Done()` — проверяй `ctx.Err() == context.DeadlineExceeded` vs `context.Canceled` и логируй разные сообщения.

### 45. Паттерны конкурентности

**Упражнение 14.86.** Реализуй **Worker Pool**: фиксированное число воркеров (например, 3), канал задач (`chan func() error`), канал результатов. Воркеры читают задачи, выполняют, отправляют результат. `main` закрывает канал задач и ждёт `sync.WaitGroup`.

**Упражнение 14.87.** Реализуй **Pipeline** из 3 стадий: `Generator` → `Square` → `Printer`. Каждая стадия — горутина + канал. Замерь throughput: сколько чисел обработано за 1 секунду.

**Упражнение 14.88.** Реализуй **Fan-Out / Fan-In**: один генератор, 4 воркера (fan-out), один мержер (fan-in). Воркеры обрабатывают задачи параллельно, результаты собираются в один канал. Используй `sync.WaitGroup` для fan-in.

**Упражнение 14.89.** Реализуй **Future / Promise**: функция `AsyncCompute(fn func() int) <-chan int` запускает `fn` в горутине и возвращает канал с результатом. Вызвающий читает из канала, когда результат нужен.

**Упражнение 14.90.** Реализуй **Semaphore** через канал: `type Semaphore chan struct{}`. Методы: `Acquire()`, `Release()`. Ограничь доступ к ресурсу (например, 2 одновременных запроса к "базе данных").

**Упражнение 14.91.** Реализуй **Rate Limiter** (token bucket): канал `tokens` с буфером N. Каждый запрос берёт токен (`<-tokens`). Пополняющая горутина добавляет токен каждые `interval`. Если токенов нет — запрос блокируется.

**Упражнение 14.92.** Реализуй **Rate Limiter** (leaky bucket): запросы поступают в буферизованный канал. Обрабатывающая горутина читает из канала с фиксированной частотой (`time.Ticker`). Если буфер переполнен — запрос отклоняется.

**Упражнение 14.93.** Реализуй **Pub/Sub** через каналы: `type PubSub struct { subscribers map[string][]chan string; mu sync.RWMutex }`. Методы: `Subscribe(topic string) <-chan string`, `Publish(topic, msg string)`. Подписчики получают сообщения.

**Упражнение 14.94.** Реализуй **Bounded Queue** через канал: `type Queue struct { ch chan int }`. Методы `Enqueue(v int) bool` (false если полон), `Dequeue() (int, bool)`. Используй канал как синхронизированную очередь.

**Упражнение 14.95.** Реализуй **Circuit Breaker** (упрощённый): три состояния — `Closed`, `Open`, `HalfOpen`. При N ошибок подряд — переход в `Open`. В `Open` — быстрый fail. Через таймаут — `HalfOpen`, где один запрос пробует пройти. Используй `sync/atomic` для состояния.

**Упражнение 14.96.** Реализуй **Retry with backoff**: функция пытается выполнить операцию 3 раза. Между попытками — экспоненциальная задержка (100ms, 200ms, 400ms). Если контекст отменён — прерывай сразу.

**Упражнение 14.97.** Реализуй **Parallel For** (аналог `Parallel.ForEach` в C#): `ParallelFor(items []int, fn func(int))`. Запускает обработку каждого элемента в горутине, но ограничивает concurrency через семафор.

**Упражнение 14.98.** Реализуй **Map-Reduce**: фаза Map — N горутин обрабатывают входные данные, фаза Reduce — одна горутина агрегирует результаты из канала. Используй `sync.WaitGroup` для барьера между фазами.

**Упражнение 14.99.** Реализуй **"errgroup"** вручную (или используй `golang.org/x/sync/errgroup`): запускаешь N горутин, если **любая** возвращает ошибку — отменяешь остальные через `context.WithCancel`. Собери первую ошибку.

**Упражнение 14.100.** Реализуй **"pipeline cancellation"**: pipeline из 3 стадий. Если стадия 2 получает ошибку — она закрывает свой выходной канал, стадия 3 завершает чтение, стадия 1 должна узнать об отмене через `select` на `done` канале.

**Упражнение 14.101.** Реализуй **"streaming"** обработку: читаешь большой файл построчно, отправляешь строки в pipeline (стадия 1), фильтруешь (стадия 2), агрегируешь статистику (стадия 3). Всё — через каналы, без загрузки файла целиком в память.

**Упражнение 14.102.** Реализуй **"throttled parallel download"**: скачивай 10 URL параллельно, но не более 3 одновременных запросов. Используй семафор + `sync.WaitGroup`. Собери результаты (размер или статус) в канал.

**Упражнение 14.103.** Реализуй **"timeout per task"** в worker pool: каждая задача имеет свой дедлайн. Если задача не уложилась — воркер отменяет её (через `context.WithDeadline`) и берёт следующую.

**Упражнение 14.104.** Реализуй **"priority queue"** с конкурентным доступом: `type PriorityQueue struct { items []Item; mu sync.Mutex; cond *sync.Cond }`. Воркеры забирают задачи с наивысшим приоритетом. Продюсеры добавляют задачи. Используй `heap.Interface` + `sync.Mutex`.

### 46. Каверзные случаи и антипаттерны

**Упражнение 14.105.** Напиши программу с **"data race на слайсе"**: две горутины `append`ят в один слайс. Запусти с `-race`. Покажи, что `append` — не атомарная операция (чтение len/cap, выделение памяти, копирование, запись).

**Упражнение 14.106.** Напиши программу с **"channel deadlock"**: две горутины пытаются записать друг в друга (A пишет в ch1, читает из ch2; B пишет в ch2, читает из ch1). Никакой `select` — чистый deadlock. Покажи, как `select` с `default` или таймаутом решает это.

**Упражнение 14.107.** Напиши программу с **"closing nil channel"**: `var ch chan int; close(ch)`. Получи панику. Напиши защиту: проверяй `if ch != nil` перед закрытием.

**Упражнение 14.108.** Напиши программу с **"send on closed channel"**: закрой канал, затем отправь в него значение. Получи панику. Напиши `SafeSend(ch chan int, v int) bool`, которая возвращает `false` вместо паники (используй `recover` или `select` с `default` + проверка, но лучше — не закрывай канал, если есть писатели).

**Упражнение 14.109.** Напиши программу с **"multiple closers"**: две горутины могут закрыть канал. Получи панику. Решение: только **писатель** закрывает канал, или используй `sync.Once`.

**Упражнение 14.110.** Напиши программу с **"goroutine leak in range"**: `for v := range ch` никогда не завершится, если кто-то не закроет `ch`. Покажи, что если писатель завис/упал — читатель тоже зависнет. Используй `select` с `ctx.Done()` для выхода.

**Упражнение 14.111.** Напиши программу с **"select on send without default"**: `select { case ch <- v: }`. Если канал небуферизованный и нет читателя — это **блокировка**. Добавь `default` для non-blocking send.

**Упражнение 14.112.** Напиши программу с **"broadcast через закрытие канала"**: создаёшь `done := make(chan struct{})`, передаёшь 100 горутинам. Закрываешь `done` — все 100 мгновенно получают сигнал. Покажи, что это **идиоматичный** способ broadcast в Go.

**Упражнение 14.113.** Напиши программу с **"потерянный send после закрытия"**: писатель не знает, что канал закрыт (гонка), и пытается отправить. Используй `select` с `case <-done:` для координации: писатель видит `done` и выходит, не пытаясь писать.

**Упражнение 14.114.** Напиши программу с **"copying mutex"**: передаёшь структуру с `sync.Mutex` по значению в горутину. Покажи, что это **копия** мьютекса, и синхронизация не работает. Исправь: передавай указатель.

**Упражнение 14.115.** Напиши программу с **"defer в цикле"**: `for _, v := range items { go func() { fmt.Println(v) }() }`. Покажи, что все горутины выводят **последнее** значение (closure captures variable by reference). Исправь: `go func(v string) { ... }(v)`.

**Упражнение 14.116.** Напиши программу с **"defer wg.Done" в цикле**: `for i := 0; i < 3; i++ { go func() { defer wg.Done(); ... }() }`. Покажи, что `wg.Add(3)` должен быть **до** цикла, иначе `wg.Wait()` может сработать раньше запуска горутин.

**Упражнение 14.117.** Напиши программу с **"паника в горутине убивает программу"**: если нет `recover` внутри горутины, паника распространяется и убивает весь процесс. Покажи, что `defer recover` в `main` **не спасает** панику в горутине. Исправь: оборачивай тело каждой горутины в `defer recover`.

**Упражнение 14.118.** Напиши программу с **"context.Value misuse"**: передаёшь большой объект через `ctx.Value`. Покажи, что это антипаттерн (контекст — для **метаданных** запроса, а не для бизнес-данных). Перепиши: передавай данные через каналы/аргументы.

**Упражнение 14.119.** Напиши программу с **"forgetting to drain channel"**: после `break` из `select` или раннего `return` канал остаётся непрочитанным, писатели блокируются. Используй `defer` с дренажем или `context` для отмены писателей.

**Упражнение 14.120.** Напиши программу с **"race on interface method"**: две горутины вызывают метод у одного и того же объекта (не через мьютекс, а просто метод, который меняет состояние). Покажи, что `-race` ловит это, даже если объект "скрыт" за интерфейсом.

### 47. Комплексные задачи

**Упражнение 14.121.** Реализуй **"concurrent cache"**: `type Cache struct { data map[string]any; mu sync.RWMutex; ttl map[string]time.Time }`. Методы: `Get`, `Set` с TTL, `Delete`. Добавь фоновую горутину, которая раз в минуту чистит протухшие записи.

**Упражнение 14.122.** Реализуй **"connection pool"**: фиксированный пул соединений (например, 10). Клиент берёт соединение из канала, использует, возвращает. Если пул исчерпан — блокировка или таймаут. Используй `select` + `time.After` для таймаута ожидания.

**Упражнение 14.123.** Реализуй **"load balancer"** (round-robin): входящие запросы в канал, 3 бэкенд-воркера забирают по одному. Каждый воркер обрабатывает и отправляет результат в общий канал. Используй `select` + `case req := <-requests:`.

**Упражнение 14.124.** Реализуй **"leader election"** (упрощённый): N горутин, каждая пытается стать лидером через `atomic.CompareAndSwapInt32` (или `atomic.Bool`). Лидер выполняет работу, остальные ждут. При смерти лидера — новый выборы.

**Упражнение 14.125.** Реализуй **"graceful HTTP server shutdown"**: `http.Server` + `Shutdown(ctx)` с `context.WithTimeout`. При `SIGINT` — отменяешь контекст, сервер завершает текущие запросы, но не принимает новые. Используй `signal.NotifyContext` + `errgroup`.

### Ключевые моменты для освоения конкурентности:

1. **"Do not communicate by sharing memory; instead, share memory by communicating"** — каналы — предпочтительный способ координации. Но `sync.Mutex` тоже нужен, особенно для сложных структур данных.
2. **Закрытие каналов** — только писатель закрывает канал. Никогда закрывай канал, если не уверен, что писателей больше нет.
3. **Context** — основной механизм отмены и передачи дедлайнов. Всегда принимай `ctx context.Context` первым аргументом в функциях, которые могут долго выполняться.
4. **Race detector** — запускай `go run -race` и `go test -race` постоянно. Он ловит ~90% гонок, но не заменяет правильного дизайна.
5. **Goroutine leak** — всегда думай, кто и когда закроет канал/отменит контекст. `defer leakWg.Done()` — хорошая привычка.
6. **Select** — случайный выбор готовых case'ов. Если нужен приоритет — используй вложенные `select` или `default`.
7. **Atomic vs Mutex** — для простых счётчиков и флагов — `atomic` в 10-100 раз быстрее. Для сложных инвариантов — `sync.Mutex`.

Если нужно — следующий этап: **тестирование (`testing`, `testify`, fuzzing, бенчмарки), HTTP-серверы и клиенты, работа с базами данных (database/sql), gRPC/JSON-RPC, reflection, unsafe, cgo, оптимизация и профилирование (pprof, trace)**. 🚀
