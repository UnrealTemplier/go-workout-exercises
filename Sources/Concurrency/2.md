### 6. Конкурентность (горутины, каналы, синхронизация, контекст, паттерны)

#### 6.1 Запуск горутин и ожидание завершения
241. Запустите горутину, которая печатает «Hello from goroutine», а main продолжает выполняться и завершается через `time.Sleep`.
242. Объясните, почему без синхронизации горутина может не успеть выполниться. Исправьте с помощью `sync.WaitGroup`: запустите 5 горутин, каждая печатает свой индекс, дождитесь всех.
243. Запустите 3 горутины, каждая считает и выводит числа от 1 до 5 с задержкой. Сравните выводы: порядок не детерминирован.
244. Покажите проблему гонки данных: две горутины инкрементируют общую переменную без синхронизации. Запустите с `go run -race` и увидьте предупреждение.
245. Исправьте гонку с помощью `sync.Mutex`: общая структура со счётчиком и метод `Inc`.

#### 6.2 Каналы (небуферизированные и буферизированные)
246. Создайте небуферизированный канал `chan string`. Основная горутина отправляет сообщение, другая принимает и печатает.
247. Два небуферизированных канала: одна горутина пишет в `ch1`, другая читает из `ch1` и пишет в `ch2`, main читает из `ch2` — цепочка передачи.
248. Буферизированный канал ёмкостью 3: отправьте 5 значений в горутине, читайте в main с задержкой. Проверьте блокировку отправителя при заполнении.
249. Используйте `for range` для чтения из канала, пока он не закрыт. Отправитель закрывает канал после нескольких сообщений.
250. Паттерн «сигнал завершения»: горутина-воркер читает из канала, пока не получит специальное значение `"stop"`.
251. Напишите функцию `generate(n int) <-chan int`, которая возвращает канал и в горутине отправляет числа от 1 до n, затем закрывает канал.
252. Реализуйте `filter(in <-chan int, fn func(int) bool) <-chan int`, которая пропускает только удовлетворяющие условию числа.

#### 6.3 Select и мультиплексирование
253. Два канала, горутины отправляют в них с разной периодичностью. В main используйте `select` для чтения из того, который готов, с выводом идентификатора.
254. Добавьте `time.After` в `select`, чтобы выйти из цикла, если ничего не пришло за 2 секунды.
255. Неблокирующая отправка/чтение с `default`: попробуйте отправить в канал, если он заполнен — выведите «channel full» и пропустите.
256. Утечка горутин: горутина блокируется на отправке в канал, который никто не читает. Исправьте с помощью `select` с таймаутом или буфера.
257. Мультиплексор: функция `fanIn(ch1, ch2 <-chan int) <-chan int`, сливающая два канала в один. Используйте `select` в цикле.
258. Тикер: каждые 500 мс отправлять в канал `time.Tick`, основная горутина читает и выводит «tick», пока не истечёт таймаут.

#### 6.4 Синхронизация (Mutex, RWMutex, Once, WaitGroup, Cond)
259. Безопасный счётчик: структура `SafeCounter` с `sync.Mutex`, методы `Inc`, `Value`.
260. `sync.RWMutex`: `SafeMap` с методами `Get`, `Set`, `Delete`. Много читателей могут читать одновременно, писатель эксклюзивно.
261. `sync.Once`: инициализация дорогого ресурса (например, чтение конфигурации из файла) только один раз при конкурентных вызовах.
262. `sync.Cond`: реализуйте очередь задач с ожиданием: горутины ждут `Cond.Wait()`, пока не появятся задачи. Поставщик вызывает `Signal()`.
263. Используйте `errgroup.Group` (из `golang.org/x/sync/errgroup`) для параллельных HTTP-запросов с обработкой первой же ошибки.

#### 6.5 Паттерны конкурентности
264. Worker Pool: фиксированное число воркеров читают задания из канала, результат отправляют в другой. Main собирает результаты.
265. Fan-out/Fan-in: генератор чисел, несколько горутин умножают числа на 2, затем объединяют результаты в один канал.
266. Pipeline: стадии `generate` → `square` → `print`. Используйте каналы для связи.
267. «Graceful shutdown»: запустите воркер, который читает из канала. При получении SIGINT (или через контекст) завершите воркер, дождавшись окончания текущих задач.
268. Семафор на основе канала (буферизированный канал ёмкостью N): ограничьте количество одновременно выполняющихся горутин, которые обращаются к внешнему ресурсу.
269. Барьерная синхронизация: используйте канал, чтобы заставить несколько горутин дождаться друг друга перед стартом следующей фазы.

#### 6.6 Контекст (context.Context): отмена, таймауты, значения
270. Передайте `context.Background()` в цепочку функций. Функция-воркер проверяет `ctx.Done()` в цикле и завершается.
271. `context.WithCancel`: main отменяет контекст через 3 секунды, все горутины, получившие контекст, должны корректно завершиться.
272. `context.WithTimeout`: горутина выполняет долгую работу, но если не укладывается в таймаут, должна вернуть ошибку `ctx.Err()`.
273. `context.WithDeadline`: аналогично таймауту, но задайте конкретное время завершения.
274. `context.WithValue`: передайте идентификатор запроса через контекст в несколько вложенных вызовов. Логируйте его при обработке.
275. Пирамида контекстов: родительский контекст с таймаутом 5с, дочерний с таймаутом 3с. Проверьте, что дочерний отменяется раньше, а родительский продолжается.
276. Игнорирование отмены: покажите ошибку, когда горутина игнорирует `ctx.Done()` и продолжает работать после отмены. Исправьте, добавив проверку в цикле.

#### 6.7 Продвинутые темы и каверзные случаи
277. Deadlock: создайте ситуацию взаимной блокировки (две горутины, два мьютекса, захватываемых в разном порядке). Обнаружьте с `-race`.
278. Избегайте deadlock с помощью упорядочивания захвата мьютексов или `sync.Map`.
279. Утечка горутин: горутина пишет в канал, который никто не читает. Найдите утечку с помощью профилировщика или счётчика горутин (`runtime.NumGoroutine`). Исправьте, закрыв канал или добавив буфер/select.
280. Закрытие закрытого канала: продемонстрируйте панику. Исправьте, используя флаг или `sync.Once` для безопасного закрытия.
281. «Broadcast» через закрытие канала: несколько горутин ждут сигнала старта, читая из одного канала. Закрытие канала разблокирует всех.
282. `nil`-канал в `select`: покажите, что `select` игнорирует case с `nil`-каналом, что можно использовать для динамического отключения веток.
283. Обработка ошибок в горутинах: канал для ошибок, main собирает ошибки от воркеров и агрегирует их.
284. Конкурентный доступ к слайсу: покажите, что конкурентное чтение безопасно, а запись — нет. Защитите мьютексом.
285. `sync.Pool`: используйте для переиспользования временных объектов (буферов) в конкурентной среде.
286. Атомарные операции: `atomic.AddInt64`, `atomic.LoadInt64` для неблокирующего счётчика. Сравните производительность с мьютексом.
287. Канал с таймаутом и повторной попыткой: если ответ не пришёл за таймаут, повторить отправку (с использованием `select` и счётчика попыток).
288. Динамическое управление числом воркеров: main может добавлять или убирать воркеров через каналы команд.
289. Конкурентная карта: реализуйте свою `ConcurrentMap[K comparable, V any]` с сегментированным замком (шардирование мьютексов для повышения производительности).
290. Микросервис-заглушка: запустите HTTP-сервер с хендлером, который имитирует задержку. Сделайте несколько конкурентных GET-запросов с таймаутом через `http.Client` + `context`, отменяйте долгие запросы.
