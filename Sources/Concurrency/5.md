Конкурентность (concurrency) — это главная "киллер-фича" Go. Но именно здесь новички (и не только) собирают больше всего граблей: дедлоки, гонки данных, утечки горутин.

Этот пласт — твой пропуск в мир highload-разработки на Go. Мы продолжаем нашу нумерацию с **253-го упражнения** и погружаемся в пучину горутин, каналов, блокировок и сложных паттернов. Ниже **73 мощных упражнения** по конкурентности.

### Блок 17. Горутины и основы `sync.WaitGroup` (253–263)
Учимся запускать легковесные потоки и правильно их дожидаться.

253. **Первая горутина:** Напиши функцию `PrintNumbers()`. В `main` вызови её через ключевое слово `go`. Запусти программу. Убедись, что программа завершилась без вывода чисел.
254. **Сон для ожидания (Плохая практика):** Добавь `time.Sleep(time.Second)` в конце `main` из упр. 253. Убедись, что теперь вывод есть. Осознай правило: *если завершается main, убиваются все горутины*.
255. **Базовый `sync.WaitGroup`:** Убери `time.Sleep`. Создай `var wg sync.WaitGroup`. Вызови `wg.Add(1)` перед запуском горутины. Внутри горутины вызови `wg.Done()`. В конце `main` вызови `wg.Wait()`. Это правильный способ ожидания.
256. **Много горутин:** Запусти в цикле от 1 до 10 анонимные горутины, выводящие номер итерации. Используй `WaitGroup` для ожидания всех десяти. Обрати внимание на порядок вывода (он случайный).
257. **Каверзный случай: Захват переменной цикла (До Go 1.22):** Если в упр. 256 ты просто выводил `i` внутри анонимной горутины, запусти это на старой версии Go (или почитай об этом). Объясни, почему все 10 горутин могли вывести число `11`.
258. **Правильный захват:** Передай переменную `i` как аргумент в анонимную горутину: `go func(id int) { ... }(i)`. Убедись, что вывод корректен.
259. **Каверзный случай: Передача WaitGroup по значению:** Напиши функцию `Worker(wg sync.WaitGroup)`. Передай туда `wg` без указателя. Внутри сделай `wg.Done()`. Запусти. Поймай *deadlock* (потому что функция получила копию, а оригинальный WaitGroup в `main` так и остался ждать).
260. **Правильная передача WG:** Перепиши упр. 259, передавая указатель `*sync.WaitGroup`.
261. **Паника отрицательного счетчика:** Вызови `wg.Done()` больше раз, чем было вызвано `wg.Add()`. Изучи сообщение о панике.
262. **Анонимные функции и defer:** Используй `defer wg.Done()` внутри горутины (сразу после её начала) — это стандартный паттерн, гарантирующий, что счетчик уменьшится даже при панике внутри горутины.
263. **Управление ядрами:** Импортируй `runtime`. Выведи `runtime.NumCPU()`. С помощью `runtime.GOMAXPROCS(1)` заставь программу работать только на одном логическом ядре, запусти 100 горутин и посмотри, изменилось ли поведение.

### Блок 18. Каналы (Channels): Основы и механика (264–281)
Каналы — это трубы, по которым горутины безопасно передают данные. *«Не общайтесь, разделяя память; разделяйте память, общаясь»*.

264. **Небуферизированный канал:** Создай канал `ch := make(chan int)`. В `main` отправь в него число: `ch <- 42`. Запусти и поймай `fatal error: all goroutines are asleep - deadlock!`. (Запись в такой канал блокирует выполнение, пока кто-то не прочитает из него).
265. **Писатель и Читатель:** Реши проблему из 264: запусти горутину, которая пишет в канал, а чтение `<-ch` сделай в `main`. Программа должна успешно завершиться.
266. **Буферизированный канал:** Создай канал `ch := make(chan int, 2)`. Отправь в него два числа подряд прямо в `main` (без горутин). Считай их. Убедись, что дедлока нет (канал с буфером не блокирует запись, пока буфер не заполнится).
267. **Переполнение буфера:** Добавь в упр. 266 отправку третьего числа (при буфере 2). Поймай дедлок.
268. **Закрытие канала (`close`):** Запиши в канал 3 числа. Вызови `close(ch)`. Считай из него 4 числа. Что вернет 4-е чтение? (Спойлер: zero value, т.е. `0`).
269. **Идиома `comma ok` в каналах:** Считай данные как `val, ok := <-ch`. Выведи `ok` для открытого и для закрытого канала, из которого уже всё прочитали.
270. **Паника при закрытии:** Попробуй записать данные в закрытый канал. Изучи панику `send on closed channel`.
271. **Двойное закрытие:** Попробуй закрыть уже закрытый канал. Снова паника.
272. **Итерация по каналу (`for range`):** Запусти горутину, которая пишет 5 чисел в канал и **закрывает его**. В `main` используй `for val := range ch { ... }`. Убедись, что цикл сам завершается при закрытии канала.
273. **Каверзный случай: Забыл закрыть:** Убери `close(ch)` из упр. 272. Посмотри, как `for range` ловит дедлок, ожидая новых данных вечно.
274. **Направленные каналы:** Напиши функцию `Producer(ch chan<- int)` (только на запись) и `Consumer(ch <-chan int)` (только на чтение). Передай им обычный двунаправленный канал из `main`.
275. **Nil-каналы:** Объяви `var ch chan int` без `make`. Попробуй написать в него. Затем попробуй прочитать из него. Узнай, что операции с nil-каналом блокируются **навсегда**.
276. **Сигнальный канал:** Создай `done := make(chan struct{})`. Горутина-воркер делает долгую работу, а по завершении делает `done <- struct{}{}`. В `main` жди этого сигнала `<-done`. Пустая структура не занимает памяти!
277. **Мультиплексирование с `select`:** Создай два канала. Две горутины пишут в них с разными задержками. В `main` напиши `select` (с двумя `case`), который прочитает из того канала, который первым отдаст данные.
278. **`select` в цикле:** Помести `select` в бесконечный `for { select { ... } }`, чтобы читать из нескольких каналов непрерывно.
279. **Non-blocking чтение:** В `select` добавь ветку `default`. Убедись, что если ни один канал не готов, мгновенно срабатывает `default`, и программа не блокируется.
280. **Таймаут через `select`:** Добавь в `select` case: `case <-time.After(2 * time.Second):`. Убедись, что если данные не приходят 2 секунды, срабатывает этот таймаут.
281. **Каверзный `time.After` в цикле:** Напиши `for` с `select`, внутри которого есть `case <-time.After(...)`. Изучи (в теории или профилировщиком), почему это вызывает **утечку памяти** (на каждой итерации создается новый таймер, который висит в памяти до срабатывания). Вынеси `time.NewTimer` перед циклом.

### Блок 19. Гонки данных и примитивы синхронизации (282–295)
Когда каналов недостаточно, мы обращаемся к `sync` и атомарным операциям.

282. **Создание гонки данных (Data Race):** Создай переменную `counter := 0`. Запусти 1000 горутин, каждая делает `counter++` 1000 раз. В конце выведи `counter`. Ты увидишь, что результат сильно меньше 1 000 000.
283. **Детектор гонок:** Запусти код из 282 с флагом `go run -race`. Изучи красный пугающий лог "WARNING: DATA RACE".
284. **Исправление через `sync.Mutex`:** Добавь мьютекс. Делай `mu.Lock()` перед инкрементом и `mu.Unlock()` после. Убедись, что счетчик равен миллиону и `-race` молчит.
285. **Забытый Unlock (Deadlock):** В упр. 284 напиши условие `if counter == 5000 { return }` внутри горутины, до `Unlock()`. Увидь, как все остальные горутины зависают навсегда. 
286. **Правильный `defer`:** Замени ручной вызов на `defer mu.Unlock()` сразу после `mu.Lock()`.
287. **RW Mutex (`sync.RWMutex`):** Создай мапу-кэш. Запусти 100 горутин на чтение (`mu.RLock()`) и 10 на запись (`mu.Lock()`). Пойми, что `RLock` позволяет параллельное чтение, но блокирует запись.
288. **Исправление через `sync/atomic`:** Убери мьютексы. Замени `counter` на `var counter int64`. Используй `atomic.AddInt64(&counter, 1)` в горутинах. Сравни скорость (в уме: атомики сильно быстрее мьютексов для простых счетчиков).
289. **Сложный атомик (Atomic Pointer):** В Go 1.19+ используй `atomic.Pointer[T]` для безопасной замены целой структуры конфигурации на лету без блокировок.
290. **Синглтон через `sync.Once`:** Напиши функцию `InitConfig()`. Создай `var once sync.Once`. В цикле запусти 100 горутин, каждая вызывает `once.Do(InitConfig)`. Убедись, что инициализация отработала ровно **один** раз.
291. **Базовый `sync.Map`:** Когда нужна конкурентная мапа (много горутин читают и пишут), используй `sync.Map`. Попробуй методы `Store`, `Load`, `LoadOrStore` и `Delete`.
292. **Обход `sync.Map`:** Используй метод `Range` для итерации по `sync.Map`. Обрати внимание, что он принимает callback-функцию.
293. **Повторное использование с `sync.Pool`:** Создай пул тяжелых структур `pool := &sync.Pool{ New: func() any { return new(HeavyObject) } }`. Забирай объекты `pool.Get()`, работай с ними и возвращай `pool.Put()`.
294. **Условные переменные (`sync.Cond`):** Создай `cond := sync.NewCond(&sync.Mutex{})`. 10 воркеров вызывают `cond.Wait()` (ожидая старта). В `main` вызови `cond.Broadcast()`, чтобы мгновенно разбудить их всех.
295. **Каверзный случай: Копирование Mutex:** Передай структуру, содержащую `sync.Mutex`, в функцию по значению. Используй `go vet` — он покажет ошибку "locks by value". Никогда не копируй мьютексы!

### Блок 20. Контекст (`context`): Управление жизненным циклом (296–306)
Стандарт для отмены операций, таймаутов и передачи request-scoped данных.

296. **Базовый контекст:** Создай `ctx := context.Background()`. Напиши воркер, который принимает `ctx` первым аргументом (это стандарт) и крутится в `for { select { case <-ctx.Done(): return default: ... } }`.
297. **Отмена (`WithCancel`):** Оберни `ctx` в `ctx, cancel := context.WithCancel(context.Background())`. Передай в воркер. В `main` вызови `cancel()` через 2 секунды. Убедись, что воркер корректно завершился.
298. **Каскадная отмена:** Создай `ctx1` (с отменой). От него создай `ctx2` (с отменой). Передай `ctx2` в воркер. Отмени **первый** контекст `ctx1`. Убедись, что `ctx2` тоже автоматически отменился.
299. **Таймаут (`WithTimeout`):** Создай `ctx, cancel := context.WithTimeout(context.Background(), 1*time.Second)`. Обязательно добавь `defer cancel()`. Воркер должен спать 3 секунды. Проверь, что `ctx.Done()` срабатывает раньше завершения работы воркера.
300. **Deadline (`WithDeadline`):** Аналогично таймауту, но передай конкретное время: `time.Now().Add(2 * time.Second)`.
301. **Передача данных (`WithValue`):** Добавь в контекст UserID: `ctx = context.WithValue(ctx, "userID", 42)`. Достань его в воркере: `id := ctx.Value("userID")`.
302. **Антипаттерн строковых ключей:** Перепиши упр. 301 правильно. Создай свой тип `type ctxKey string`. Используй константу этого типа как ключ для `WithValue`, чтобы избежать коллизий с другими пакетами.
303. **Ошибка контекста (`ctx.Err()`):** После того как контекст отменен, вызови `ctx.Err()`. Изучи ошибки `context.Canceled` и `context.DeadlineExceeded`.
304. **Принудительная проверка в цикле:** В долгоиграющем цикле (который не использует каналы) добавь `if ctx.Err() != nil { return ctx.Err() }`, чтобы не делать лишнюю работу, если клиент отвалился.
305. **Утечка контекста:** Создай `WithTimeout` в цикле на миллион итераций, но **не вызывай** `cancel()` в defer. Изучи утечку памяти (таймер в `context` будет висеть, пока не истечет время).
306. **`context.AfterFunc` (Go 1.21+):** Зарегистрируй функцию, которая вызовется автоматически, когда контекст будет отменен (без необходимости писать горутину с `select`).

### Блок 21. Паттерны конкурентности (Concurrency Patterns) (307–318)
Архитектурные подходы для элегантного решения сложных задач.

307. **Генератор (Generator):** Напиши функцию, которая внутри себя создает канал, запускает горутину (которая пишет туда числа 1..10 и закрывает его) и возвращает этот канал (`<-chan int`).
308. **Пул воркеров (Worker Pool):** Создай канал `jobs` и канал `results`. Запусти 3 горутины-воркера, которые читают из `jobs`, умножают число на 2 и пишут в `results`. Из `main` отправь 10 задач в `jobs` и собери 10 ответов.
309. **Fan-out (Разветвление):** Улучши упр. 308. Один "генератор" пишет задачи в канал, а 5 воркеров конкурируют за чтение из этого канала.
310. **Fan-in (Слияние):** Напиши функцию `Merge(ch1, ch2 <-chan int) <-chan int`. Внутри запусти горутину, которая читает из обоих каналов (через `select` или горутины с WaitGroup) и пишет данные в один общий выходной канал.
311. **Пайплайн (Pipeline):** Создай конвейер: Генератор -> Сквер (возводит в квадрат) -> Принтер (выводит). Каждая стадия — это функция, принимающая входной канал и возвращающая выходной.
312. **Семафор (Semaphore):** У тебя 100 задач. Используй буферизированный канал `sem := make(chan struct{}, 5)`, чтобы ограничить максимальное количество *одновременно* работающих горутин до 5. (Пиши в `sem` перед стартом, читай в конце).
313. **Tee-канал (Тройник):** Напиши функцию, которая читает из одного канала и дублирует каждое значение в **два** исходящих канала. 
314. **Debouncer (Подавитель дребезга):** Напиши функцию, которая принимает канал событий (кликов). Она должна передавать событие дальше, только если с момента прошлого события прошло более 500 мс. (Используй `time.Timer`).
315. **Rate Limiter (Ограничитель):** Используй `time.Ticker`, чтобы разрешать выполнение не более 3 задач в секунду (выполняй задачу только после получения тика из `ticker.C`).
316. **Or-Channel (Или-канал):** Напиши функцию `Or(channels ...<-chan struct{}) <-chan struct{}`. Она должна вернуть канал, который закроется, как только закроется **хотя бы один** из переданных каналов.
317. **Пакет `errgroup` (golang.org/x/sync/errgroup):** Запусти 3 задачи параллельно через `eg.Go()`. Пусть одна из них вернет ошибку. Сделай `eg.Wait()` в `main` и убедись, что ошибка поймана корректно. (Это намного удобнее голого WaitGroup с ошибками).
318. **Graceful Shutdown (Мягкое завершение):** Используй `os/signal.Notify` для перехвата `SIGINT` (Ctrl+C). При получении сигнала инициируй отмену через Context, дождись завершения воркеров через `WaitGroup` и только потом выходи из `main`.

### Блок 22. Каверзные задачи и выстрелы в ногу (319–325)
Для самых пытливых.

319. **Утечка горутины (Goroutine Leak):** Напиши горутину, которая читает из небуферизированного канала, но в `main` никто в этот канал ничего не пишет, и `main` завершает работу (с имитацией долгой жизни сервера). Горутина останется висеть в памяти навсегда.
320. **Выключение ветки `select`:** В `select` у тебя есть чтение из канала. Сделай так, чтобы при закрытии канала эта ветка больше никогда не срабатывала. (Секрет: присвой переменной канала `nil` внутри ветки, `select` игнорирует nil-каналы).
321. **Псевдослучайность `select`:** Создай два канала, положи в оба по значению. Напиши `select`, готовый читать из обоих. Запусти в цикле 100 раз. Убедись, что Go выбирает ветки случайным образом (примерно 50/50), а не по порядку написания.
322. **Перекрытие горутин в HTTP-хендлере:** Представь (и напиши мок), что HTTP-хендлер запускает горутину на запрос, но клиент отключается (context canceled). Убедись, что горутина тоже прерывает работу, иначе при DDoS сервер ляжет от нехватки памяти (OOM).
323. **Очередность мьютексов (Deadlock):** Горутина А делает `Lock(mu1)`, затем `Lock(mu2)`. Горутина Б делает `Lock(mu2)`, затем `Lock(mu1)`. Запусти их параллельно. Насладись классическим взаимным дедлоком.
324. **Starvation (Голодание):** Создай "жадную" горутину (цикл без сна, захватывающий мьютекс надолго) и "вежливую" (спящую между блокировками). Посмотри, как вежливая горутина почти не получает шанса поработать.
325. **"Грязный" вывод в консоль:** Запусти 10 горутин, которые пишут длинные строки через `fmt.Print`. Посмотри, как символы перемешиваются. Создай мьютекс специально для логирования (или используй пакет `log`, который под капотом использует мьютексы), чтобы решить эту проблему.

---
**Итог:** Конкурентность требует изменения мышления. Главное правило Go: **Владелец канала (тот, кто в него пишет) должен закрывать его.** Практикуй эти упражнения с детектором гонок (`-race`), и твой код будет быстрым, масштабируемым и, самое главное, надежным.
