## Блок 28. Memory Alignment и Cache-friendly структуры

### Уровень 1. Измерение и понимание layout
341. **Padding в структурах.** Создайте структуру `struct { a bool; b int64; c bool }`. Измерьте `unsafe.Sizeof`, `unsafe.Offsetof` каждого поля. Нарисуйте байтовую карту: `a` (1 байт) + padding (7) + `b` (8) + `c` (1) + padding (7). Переставьте поля (`b`, `a`, `c`) и покажите уменьшение размера с 24 до 16 байт. Объясните, почему компилятор выравнивает по `unsafe.Alignof` самого большого поля.
342. **Alignof и структурное выравнивание.** Напишите программу, которая для 10 разных типов (`int8`, `int32`, `int64`, `*byte`, `[]int`, `string`, `time.Time`) выводит `unsafe.Alignof`. Объясните, что alignment структуры = max alignment полей, а alignment слайса = alignment указателя (8 байт на 64-бит).
343. **Размер cache line.** Определите размер cache line вашего CPU: создайте массив `[1024]int64`, обходите с шагом 1, затем с шагом 8 (64 байта). Замерьте время. Покажите скачок latency при переходе через границу 64 байт. Объясните L1d cache line (обычно 64 байта, иногда 128 на ARM).

### Уровень 2. False Sharing и его устранение
344. **False Sharing: демонстрация.** Создайте структуру с двумя полями `counterA, counterB uint64`. Запустите 2 goroutine: каждая инкрементит своё поле 100 млн раз. Замерьте время. Объясните, почему производительность падает в 10-20×: оба поля в одной cache line (64 байта), CPU cores гоняются за exclusive ownership (MESI протокол).
345. **Устранение False Sharing через padding.** Добавьте между полями `[56]byte` (или `[64]byte` для выравнивания). Повторите бенчмарк. Покажите восстановление производительности. Объясните, почему `runtime` делает то же самое в `runtime/proc.go` (поля `p` разнесены по разным cache lines).
346. **Cache-line aligned счётчик.** Реализуйте `type PaddedCounter struct { _ [64]byte; v uint64; _ [64]byte }`. Используйте в массиве по одному на CPU core. Покажите linear scaling при увеличении числа goroutine (по числу CPU). Объясните, зачем padding с обеих сторон (защита от соседних переменных).
347. **Struct of Arrays (SoA) vs Array of Structs (AoS).** Создайте 1 млн объектов `Point { x, y float64 }`. Реализуйте сумму всех `x`: (1) `[]Point` (AoS), (2) `struct { xs, ys []float64 }` (SoA). Бенчмарк. Объясните, почему SoA быстрее (sequential access, prefetcher, меньше cache misses), но сложнее в поддержке.

### Уровень 3. Продвинутые техники
348. **Alignment для atomic операций.** Создайте массив счётчиков `[]uint64`. Покажите, что `atomic.AddUint64(&counters[i])` паникует на ARM32/ARM64, если адрес не выровнен на 8 байт. Объясните, почему `sync/atomic` требует alignment и как `struct` padding решает это.
349. **Предотвращение conflict misses.** Создайте массив размером 8192 `int64` (64 KB, ровно L1 cache size на многих CPU). Обходите с шагом 512 байт (8 элементов). Объясните, почему при определённых размерах (кратных степени 2) возникают conflict misses (associativity limit). Решение: добавить padding к строке (slice of structs с trailing `[X]byte`).
350. **Custom allocator с alignment.** Реализуйте аллокатор, который выделяет `[]byte` и возвращает `unsafe.Pointer` выровненный на 64 байта (для SIMD). Используйте `uintptr(ptr) + (alignment - uintptr(ptr)%alignment)`. Объясните, почему это нужно для `mmap` + SIMD load (`MOVOA` требует 16-byte alignment, `VMOVDQA` — 32-byte).

## Блок 29. Lock-Free структуры на `sync/atomic`

### Уровень 1. Атомики и базовые примитивы
351. **Atomic vs Mutex.** Реализуйте счётчик: `atomic.AddUint64` vs `sync.Mutex` + `counter++`. Бенчмарк с 1, 2, 4, 8 goroutine. Покажите, что atomic масштабируется лучше (нет contention на cache line, только hardware lock prefix). Объясните, почему `atomic` — это не «без блокировок», а «блокировка на уровне шины/кэша».
352. **Spinlock на CAS.** Реализуйте `type Spinlock uint32` с методами `Lock()` (`for !atomic.CompareAndSwapUint32(&l, 0, 1) { runtime.Gosched() }`) и `Unlock()`. Сравните с `sync.Mutex` при очень короткой критической секции (1 инкремент). Объясните, почему spinlock опасен в userspace (приоритет inversion, wasted CPU).
353. **Atomic.Pointer (Go 1.19+).** Реализуйте lock-free стек (Treiber Stack): `Push` через `atomic.CompareAndSwapPointer` на `head`, `Pop` — аналогично. Покажите, что это работает без mutex. Объясните ABA problem в общем случае и почему в вашем тесте его нет (GC не освобождает память немедленно).

### Уровень 2. Lock-free очереди и кольцевые буферы
354. **SPSC Ring Buffer.** Реализуйте lock-free кольцевой буфер на массиве фиксированного размера (power of 2) для Single-Producer–Single-Consumer. Используйте `atomic.Uint64` для `head` и `tail` (или `atomic.LoadUint64`/`StoreUint64`). Объясните, почему SPSC не требует CAS на каждой операции ( producer пишет tail, consumer читает head, не пересекаются).
355. **Memory Ordering.** Добавьте `runtime.Gosched()` в SPSC и покажите, что без `atomic` (plain reads/writes) может произойти reordering. Объясните acquire/release семантику: consumer делает `atomic.LoadUint64(&tail)` (acquire) перед чтением данных, producer — `atomic.StoreUint64` (release) после записи данных.
356. **MPMC Ring Buffer.** Расширьте до Multi-Producer–Multi-Consumer: используйте `CAS` на `head`/`tail`, power-of-2 размер для маски `(tail+1) & mask`. Реализуйте `Enqueue` и `Dequeue` с возвратом `bool` (full/empty). Объясните, почему MPMC сложнее (contention на одном head/tail, cache line bouncing).

### Уровень 3. Продвинутые lock-free паттерны
357. **Sequence Lock (SeqLock).** Реализуйте структуру с `sequence uint64` (чётная = чтение без изменений, нечётная = write in progress). Reader: `seq = atomic.LoadUint64(&seq); if seq%2==1 retry; read data; if seq != atomic.LoadUint64(&seq) retry`. Writer: `atomic.AddUint64(&seq, 1); write data; atomic.AddUint64(&seq, 1)`. Объясните, почему это эффективно для read-heavy данных (например, конфигурация).
358. **Striped Counters.** Реализуйте `type StripedCounter [64]PaddedCounter` (по числу CPU). `Add` — `stripe[cpuID].Add`, `Sum` — сумма всех stripes. Покажите, что это масштабируется линейно до числа ядер, в отличие от глобального `atomic.Uint64`. Объясните компромисс: точность `Sum` (eventual) vs скорость.
359. **Lock-free Hash Table (sharded).** Реализуйте массив из 256 `sync.RWMutex` или `atomic.Pointer` на bucket. Покажите, что sharding уменьшает contention. Объясните, почему полностью lock-free hash table (например, Java `ConcurrentHashMap`) в Go сложна из-за отсутствия transactional memory.

### Уровень 4. Интеграция и reclamation
360. **Epoch-Based Reclamation (упрощённый).** Для lock-free stack добавьте механизм: при `Pop` не удаляйте узел, а помещайте в локальный «retired list». Периодически (каждые N операций) освобождайте узлы, которые гарантированно не видны другими goroutine (через глобальный epoch counter). Объясните, почему Go GC делает это за вас, но в C/C++ без EBRM/HP — утечка или use-after-free.

## Блок 30. Go Assembly (Plan 9) и SIMD

### Уровень 1. Чтение и понимание ассемблера
361. **Objdump и hot path.** Напишите функцию `SumSlice([]int64) int64`. Соберите через `go build -gcflags="-S"` или `go tool objdump -s SumSlice`. Найдите цикл, инструкции `MOVQ`, `ADDQ`, bounds check (`CMPQ`, `JAE`). Объясните, как компилятор Go (SSA backend) генерирует код.
362. **Calling Convention Go.** Изучите `src/runtime/sys_amd64.s` или документацию. Объясните: параметры передаются в `AX`, `BX`, `CX`, `DX`, `DI`, `SI`, стек; возврат в `AX` (для int/pointer). Напишите функцию `func Add(a, b int64) int64` на Plan 9 assembly (`TEXT ·Add(SB), NOSPLIT, $0-24; MOVQ a+0(FP), AX; ADDQ b+8(FP), AX; MOVQ AX, ret+16(FP); RET`). Объясните синтаксис `a+0(FP)`.
363. **Bounds Check Elimination.** Напишите функцию, которая суммирует слайс с `for i := 0; i < len(s); i++`. Затем оптимизированную версию: `n := len(s); for i := 0; i < n; i++`. Сравните ассемблерный вывод. Объясните, почему compiler иногда убирает bounds check, а иногда нет (зависит от proof в SSA).

### Уровень 2. Написание функций на assembly
364. **Простая функция на asm.** Напишите на Plan 9 assembly функцию `Max(a, b int64) int64`, которая возвращает максимум. Соберите через `go test`. Объясните директиву `//go:linkname` и `//go:noescape` (если используете unsafe).
365. **Assembly + unsafe: memcpy.** Напишите функцию `FastCopy(dst, src []byte) int` на assembly, копирующую байты через `MOVQ` (8 байт за раз) и `MOVB` для остатка. Сравните с `copy(builtin)`. Объясните, почему builtin `copy` может использовать `REP MOVSB` или `AVX` и обычно быстрее ручного кода.
366. **SIMD через cgo.** Напишите C-функцию с AVX2 intrinsics (`_mm256_add_epi32` или `_mm256_loadu_si256`), скомпилируйте через cgo. Вызовите из Go для суммирования двух массивов `[]int32`. Сравните с pure Go. Объясните оверхед cgo (~100 ns) и когда он амортизируется (большие массивы).
367. **SIMD через Go Assembly (AVX2).** Напишите функцию `SumFloat32AVX2(f []float32) float32` на Plan 9 assembly с использованием AVX2 инструкций: `VMOVUPS`, `VADDPS`, `VEXTRACTF128`. Объясните, что Go assembler поддерживает AVX/AVX2 через префиксы `V` и операнды `Y0`-`Y15`. Сравните с scalar loop.

### Уровень 3. Оптимизация hot paths
368. **Unrolled loop.** Напишите суммирование массива `[]int64` с разворотом цикла (4 итерации за проход). Объясните, почему unrolling уменьшает branch misprediction и позволяет ILP (Instruction Level Parallelism). Сравните с ассемблерным выводом компилятора (Go compiler делает unrolling автоматически при `-gcflags="-B"`? Нет, Go compiler редко unroll, покажите ручное).
369. **Branchless code.** Реализуйте `Abs(x int64) int64` через `mask := x >> 63; return (x ^ mask) - mask` (без `if`). Покажите в objdump отсутствие `JMP`. Объясните, почему branchless предпочтителен в hot loops (нет branch prediction misses).
370. **Профилирование + оптимизация.** Используйте `perf` (Linux) или `go test -cpuprofile`: найдите функцию, которая занимает >30% CPU. Перепишите её критический участок на assembly или измените структуру данных (SoA). Покажите до/после в `go tool pprof`.

## Блок 31. Userspace сетевые мультиплексоры (`gnet`, `evio`)

### Уровень 1. Базовые серверы и сравнение
371. **Echo на `gnet`.** Реализуйте TCP echo-сервер на `github.com/panjf2000/gnet`. Настройте `gnet.Events{OnTraffic: ...}`. Сравните throughput (wrk/`hey`) с `net/http` Server и `fasthttp`. Объясните, почему `gnet` быстрее: userspace event loop, zero-copy, batching syscalls, отсутствие goroutine-per-connection.
372. **Echo на `evio`.** Реализуйте то же на `github.com/tidwall/evio`. Сравните API с `gnet`. Объясните, почему `evio` — single-threaded reactor (по умолчанию), а `gnet` — multi-reactor (main reactor + sub reactors).
373. **Понимание reactor pattern.** Напишите упрощённый event loop на `epoll` (см. Блок 6, упр. 86): `epoll_create1` → `epoll_ctl` (add fd) → `epoll_wait` → callback. Объясните, как `gnet` оборачивает это в Go: `epoll_wait` в отдельной goroutine, callback в пул воркеров.

### Уровень 2. Протоколы и zero-copy
374. **Length-prefixed protocol.** Реализуйте codec в `gnet`: каждое сообщение = 4 байта длина (big-endian) + payload. В `OnTraffic` читайте `c.InboundBuffered()`, парсите длину, ждёте полного сообщения. Объясните, почему `gnet` не вызывает `read()` на каждый байт, а буферизует в userspace ring buffer.
375. **Zero-copy ответ.** В `gnet` используйте `c.AsyncWrite(buf)` или `c.Write(buf)` с предварительно аллоцированным `[]byte` из `sync.Pool`. Покажите, что это минимизирует аллокации. Объясните, что `gnet` использует `sendfile` (для файлов) и `writev` (scatter-gather) где возможно.
376. **SO_REUSEPORT + Multi-Reactor.** Настройте `gnet` с `SO_REUSEPORT` и `NumEventLoop = runtime.NumCPU()`. Покажите, что каждое CPU core обрабатывает свой набор соединений (kernel балансирует accept). Сравните latency p99 при 10K соединений: single reactor vs multi-reactor.

### Уровень 3. Интеграция и масштабирование
377. **Worker Pool в `gnet`.** Реализуйте: `OnTraffic` не выполняет бизнес-логику, а отправляет задачу в `ants` pool (или собственный `chan` + worker goroutines). Объясните, почему нельзя блокировать event loop (все соединения на этом reactor зависнут). Покажите разницу между `react` (async) и `serve` (sync) подходами.
378. **Protocol codec: HTTP/1.1 parser.** Реализуйте упрощённый HTTP parser в `gnet`: парсинг `METHOD PATH HTTP/1.1\r\n` и `Content-Length`. Ответ: `HTTP/1.1 200 OK\r\nContent-Length: ...\r\n\r\nbody`. Сравните с `net/http`: `gnet` не создаёт `Request`/`ResponseWriter` объектов, минимизируя аллокации.
379. **C10K Benchmark.** Проведите бенчмарк: `gnet` vs `net/http` vs `fasthttp` при 10 000 keep-alive соединений, размер payload 1 KB. Замерьте: throughput (req/sec), latency p50/p99/p999, CPU usage, memory RSS. Постройте график (через `ipython` или gnuplot). Объясните, где `net/http` теряет производительность (goroutine stack per conn, context switches).

### Уровень 4. Production-архитектура
380. **gnet + Protobuf.** Реализуйте TCP-сервер на `gnet`, который принимает length-prefixed protobuf-сообщения (`Request`), парсит через `proto.Unmarshal`, выполняет RPC-логику, сериализует `Response` и отправляет обратно. Объясните, как это заменяет gRPC для внутренних высоконагруженных сервисов, и почему gRPC (HTTP/2) имеет больше оверхеда.
381. **Graceful Shutdown в `gnet`.** Реализуйте обработку `SIGTERM`: `Stop()` останавливает accept, дожидается завершения `OnTraffic` для текущих соединений (через `sync.WaitGroup`), затем закрывает все fd. Объясните, почему `gnet` требует ручного управления lifecycle, в отличие от `http.Server.Shutdown`.
382. **Custom Poller в `gnet`.** Покажите, как `gnet` выбирает poller: `epoll` (Linux), `kqueue` (BSD), `iocp` (Windows). Напишите условную компиляцию (`//go:build linux`) для использования `epoll` напрямую через `syscall` (см. Блок 6). Объясните, почему `gnet` — это «Go-обёртка» вокруг epoll/kqueue с zero-copy buffer management.

## Как встроить в общий план обучения

**Рекомендуемый порядок прохождения:**

1. **Блок 28 (Alignment)** — начните после Блока 2 (аллокатор), так как `mcache`/`mspan` тесно связаны с alignment. Понимание `unsafe` из Блока 4 обязательно для измерения layout.
2. **Блок 29 (Lock-free)** — проходите после Блока 1 (GMP), так как lock-free структуры — это альтернатива mutex при высоком contention. Знание `sync/atomic` и memory model критично.
3. **Блок 30 (Assembly/SIMD)** — после Блока 28-29, так как требует понимания CPU pipeline, cache lines и alignment. `cgo` из Блока 5 используется для SIMD intrinsics.
4. **Блок 31 (gnet/evio)** — финальный блок, требует знаний `epoll` (Блок 6), `sync.Pool` (упоминается в контексте zero-copy), lock-free ring buffers (Блок 29) и memory alignment (Блок 28) для userspace buffers.

**Ключевые инструменты и команды для тренировки:**
```bash
# Memory alignment
go test -bench=BenchmarkFalseSharing -benchmem -count=5
go build -gcflags="-m -m" main.go  # escape analysis

# Assembly
go tool objdump -s "SumSlice" ./binary > asm.txt
go build -gcflags="-S" main.go     # compiler output

# Perf
perf stat -e cache-misses,cache-references,instructions,cycles ./binary
perf record -g ./binary && perf report

# gnet benchmark
wrk -t10 -c10000 -d30s --latency http://localhost:8080/
```

**Что фиксировать в результатах:**
- Для Alignment: байтовые карты структур, графики `ns/op` до/после padding, proof of linear scaling.
- Для Lock-free: бенчмарки SPSC/MPMC throughput, демонстрация race-free через `go test -race`.
- Для Assembly: файлы `.s`, `go test` бенчмарки scalar vs SIMD, `perf` отчёты.
- Для gnet: графики latency/throughput, сравнительная таблица с `net/http`, архитектурная схема event loop.
