### Тема 181: Memory Alignment и Cache Lines
*Современные CPU работают с памятью не байт за байтом, а cache lines (обычно 64 байта). Понимание этого — ключ к производительности.*

1981. **Cache line size:** Определите размер cache line на вашем CPU через `/sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size` (обычно 64 байта на x86).

1982. **Memory alignment basics:** Изучите, как Go выравнивает поля структур. `unsafe.Alignof` показывает требуемое выравнивание для каждого типа.

1983. **Struct padding:** Создайте структуру `type BadStruct struct { a bool; b int64; c bool }`. Измерьте размер через `unsafe.Sizeof` — это 24 байта, а не 10! Из-за padding.

1984. **Optimal field ordering:** Переупорядочьте поля по убыванию размера: `type GoodStruct struct { b int64; a bool; c bool }`. Теперь размер 16 байт — сэкономили 33% памяти.

1985. **Array of structs vs Struct of arrays:** Сравните:
    ```go
    type AOS []struct{ x, y int64 }  // Array of Structs
    type SOA struct{ x, y []int64 }  // Struct of Arrays
    ```
    Для итерации по одному полю SOA в 2-4x быстрее (лучше cache locality).

1986. **Cache line splitting:** Создайте структуру размером 65 байт. Изучите, как она располагается в двух cache lines вместо одной — это expensive для频繁访问.

1987. **Alignment для SIMD:** Для SIMD операций данные должны быть выровнены по 16/32/64 байта. Используйте `//go:build align` или manual padding.

1988. **Pointer compression:** Для структур с множеством указателей используйте offset вместо pointer (если все pointers в одном heap allocation). Это снижает memory footprint и улучшает cache locality.

1989. **Struct embedding alignment:** При embedding структур Go сохраняет alignment requirements. Изучите, как это влияет на overall struct size.

1990. **Alignment в слайсах:** Элементы слайса всегда aligned. Но если вы делаете `unsafe.Slice` из arbitrary pointer — убедитесь в alignment, иначе SIGBUS на некоторых архитектурах.

1991. **Cache prefetching hints:** Изучите, как CPU prefetcher работает: sequential access patterns prefetch автоматически, random access — нет. Оптимизируйте access patterns.

1992. **Software prefetch:** Используйте `//go:noescape` и manual prefetch через ассемблер для critical loops (хотя Go не exposes prefetch intrinsics напрямую).

1993. **TLB (Translation Lookaside Buffer):** Поймите, что virtual → physical address translation кэшируется в TLB. Большие страницы (huge pages, 2MB/1GB) снижают TLB misses.

1994. **Huge pages в Go:** Включите huge pages через `GODEBUG=memprofilerate=0` и настройте OS для использования transparent huge pages. Измерьте влияние на memory-intensive workloads.

1995. **NUMA (Non-Uniform Memory Access):** На multi-socket servers memory access latency зависит от того, какой CPU обращается к какой памяти. Используйте `numactl` для pinning процессов к NUMA nodes.

1996. **NUMA-aware allocation:** Для extreme performance аллоцируйте память на том NUMA node, где будет выполняться обработка (через `mbind` syscall).

1997. **Cache associativity:** Изучите, что cache имеет ограниченную associativity (обычно 8-way). Access patterns с stride = cache size * associativity могут вызывать conflict misses.

1998. **Cache coloring:** Для critical data structures используйте cache coloring — распределяйте данные так, чтобы они не конфликтовали в cache sets.

1999. **Memory bandwidth:** Измерьте memory bandwidth вашего CPU через `stream` benchmark. Типичные значения: 20-50 GB/s для DDR4, 50-100 GB/s для DDR5.

2000. **Roofline model:** Постройте roofline model для вашего кода: сравните computational intensity (FLOPs/byte) с memory bandwidth и compute throughput. Это покажет, memory-bound или compute-bound ваш код.

### Тема 182: False Sharing и Cache Coherency
*False sharing — это когда два потока обращаются к разным переменным, которые находятся в одной cache line. Это вызывает expensive cache coherency traffic.*

2001. **Cache coherency protocol (MESI):** Изучите MESI protocol:
    * Modified (эксклюзивно изменён)
    * Exclusive (эксклюзивно чист)
    * Shared (разделён между кэшами)
    * Invalid (недействителен)

2002. **Cache line bouncing:** Когда CPU0 пишет в cache line, все другие CPU должны инвалидировать свои копии этой cache line. Это expensive (десятки-сотни наносекунд).

2003. **False sharing demonstration:** Создайте структуру:
    ```go
    type Counter struct {
        value int64
    }
    type Counters struct {
        c [8]Counter
    }
    ```
    Запустите 8 горутин, каждая инкрементирует свой `Counter`. Измерьте производительность.

2004. **False sharing fix через padding:** Добавьте padding между counters:
    ```go
    type PaddedCounter struct {
        value int64
        _     [56]byte  // pad to 64 bytes
    }
    ```
    Теперь каждый counter в отдельной cache line. Производительность должна вырасти в 5-10x.

2005. **Per-CPU counters:** Вместо одного global counter используйте per-CPU counters. Каждый CPU пишет в свой counter, периодически aggregate в global.

2006. **Batch updates:** Вместо `atomic.Add(&counter, 1)` на каждое событие, accumulate в local variable и flush в global counter каждые 1000 операций.

2007. **Thread-local storage:** Используйте `sync.Pool` или `g` (goroutine-local storage через `runtime.g`) для thread-local counters.

2008. **False sharing detection:** Используйте `perf c2c` (Linux) для детекта false sharing. Это покажет, какие cache lines вызывают наибольшее contention.

2009. **Cache line alignment attribute:** Используйте `//go:build` теги или manual padding для гарантии cache line alignment.

2010. **False sharing в слайсах:** Если multiple goroutines обращаются к разным элементам слайса, убедитесь, что элементы не в одной cache line (или используйте padding).

2011. **False sharing в мапах:** Go мапы имеют internal locking per bucket. Но если вы используете custom concurrent map — избегайте false sharing между buckets.

2012. **False sharing в ring buffers:** Ring buffer с producer и consumer indices в одной cache line — классический false sharing. Разделите их padding'ом.

2013. **False sharing в tree structures:** В B-tree или skip list parent и child nodes могут быть в одной cache line. Это вызывает false sharing при concurrent updates.

2014. **False sharing в hash tables:** Open addressing hash tables могут иметь false sharing между adjacent slots. Используйте separate chaining или padding.

2015. **False sharing benchmarks:** Напишите бенчмарк, который измеряет влияние false sharing:
    ```go
    func BenchmarkFalseSharing(b *testing.B) { ... }
    func BenchmarkNoFalseSharing(b *testing.B) { ... }
    ```
    Разница должна быть в 5-20x.

2016. **False sharing в Go runtime:** Изучите, как Go runtime избегает false sharing в `schedt` (per-P scheduler state) и `mcache` (per-P memory cache).

2017. **Cache line size detection:** Напишите код, который определяет cache line size через empirical testing (measure latency vs stride).

2018. **False sharing в producer-consumer:** Producer пишет в `head`, consumer читает `tail`. Если они в одной cache line — false sharing. Разделите их.

2019. **False sharing в counters array:** Массив counters, где каждый thread пишет в свой элемент. Без padding — false sharing. С padding — нет.

2020. **False sharing mitigation checklist:**
    * Per-thread/per-CPU data structures
    * Padding между shared variables
    * Batch updates
    * Thread-local accumulation
    * Cache line alignment

### Тема 183: Cache-friendly структуры данных
*Проектирование структур данных с учётом cache behavior — это искусство.*

2021. **B-tree vs Binary tree:** B-tree имеет лучшую cache locality, чем binary tree, потому что узлы содержат multiple keys в одном cache line.

2022. **Cache-oblivious algorithms:** Изучите cache-oblivious B-tree (van Emde Boas layout) — структура, которая оптимальна для любого cache line size без знания этого size.

2023. **Struct of Arrays (SoA) для SIMD:** Для vectorized operations используйте SoA:
    ```go
    type Particles struct {
        x []float32
        y []float32
        z []float32
    }
    ```
    Это позволяет SIMD обрабатывать 8 `x` координат одновременно.

2024. **Array of Structures (AoS) для OOP:** Для object-oriented кода используйте AoS:
    ```go
    type Particle struct { x, y, z float32 }
    type Particles []Particle
    ```
    Это лучше для итерации по всем полям одного объекта.

2025. **Hybrid SoA/AoS:** Для mixed workloads используйте hybrid:
    ```go
    type Particles struct {
        positions []Position  // hot data (frequently accessed)
        metadata  []Metadata  // cold data (rarely accessed)
    }
    ```

2026. **Hot/cold splitting:** Разделите структуру на hot fields (часто accessed) и cold fields (редко accessed). Hot fields в одной cache line, cold — отдельно.

2027. **Pointer-free structures:** Избегайте указателей в структурах, которые итерируются. Pointers cause cache misses (pointer chasing).

2028. **Inline small structs:** Для маленьких структур (< 16 байт) используйте value semantics вместо pointer. Это избегает pointer indirection.

2029. **Flat arrays вместо linked lists:** Linked list — это cache miss на каждый элемент. Flat array — sequential access, prefetcher работает.

2030. **Chunked arrays:** Для dynamic arrays используйте chunked arrays (array of arrays). Это избегает expensive reallocation и улучшает cache locality.

2031. **Cache-friendly hash table:** Open addressing с linear probing имеет лучшую cache locality, чем separate chaining.

2032. **Robin Hood hashing:** Улучшение linear probing, которое снижает variance в probe length и улучшает cache behavior.

2033. **Swiss tables (Abseil):** Изучите Swiss tables (используются в Google Abseil) — cache-friendly hash table с SIMD-ускоренным probing.

2034. **Cache-friendly graph representation:** Для графов используйте adjacency array (CSR format) вместо adjacency list. Это sequential access.

2035. **Cache-friendly matrix:** Для matrix operations используйте block matrix layout (tiles). Каждый tile влезает в L1 cache.

2036. **Cache-friendly tree:** Для деревьев используйте implicit tree layout (array-based heap). Parent at `i`, children at `2i+1` и `2i+2`.

2037. **Cache-friendly queue:** Ring buffer с cache line alignment для head и tail. Избегайте false sharing.

2038. **Cache-friendly stack:** Flat array с pre-allocated capacity. Избегайте linked list stack.

2039. **Cache-friendly string pool:** Для множества строк используйте string pool (один большой array + offsets). Это лучше, чем множество отдельных string allocations.

2040. **Cache-friendly serialization:** Для serialization используйте flat binary format вместо nested structures. Это sequential read/write.

### Тема 184: Lock-Free программирование (sync/atomic)
*Lock-free структуры данных избегают mutex'ов через atomic operations. Это даёт лучшую производительность при high contention.*

2041. **Atomic operations basics:** Изучите `sync/atomic` пакет:
    * `atomic.AddInt64(&x, 1)`
    * `atomic.LoadInt64(&x)`
    * `atomic.StoreInt64(&x, val)`
    * `atomic.CompareAndSwapInt64(&x, old, new)`

2042. **CAS (Compare-And-Swap):** Это фундамент lock-free programming. CAS атомарно проверяет, что значение = expected, и если да — обновляет его.

2043. **Atomic counter:** Реализуйте thread-safe counter через `atomic.AddInt64`. Сравните производительность с `sync.Mutex`.

2044. **Atomic flag:** Реализуйте boolean flag через `atomic.Bool` (Go 1.19+) или `atomic.Int32`.

2045. **Atomic pointer:** Используйте `atomic.Pointer[T]` (Go 1.19+) для lock-free pointer updates.

2046. **ABA problem:** Изучите ABA problem: CAS видит, что значение = A, но не знает, что оно было A → B → A. Решение: version counter или hazard pointers.

2047. **Memory ordering:** Изучите memory ordering:
    * `atomic.Load` — relaxed (может reorder)
    * `atomic.LoadAcquire` — acquire (не reorder после)
    * `atomic.StoreRelease` — release (не reorder до)
    * `atomic.CompareAndSwap` — sequential consistency

2048. **Sequential consistency:** В Go все atomic operations имеют sequential consistency semantics. Это проще для понимания, но может быть медленнее.

2049. **Lock-free stack (Treiber stack):** Реализуйте lock-free stack через CAS:
    ```go
    type Node struct {
        value int
        next  *Node
    }
    type Stack struct {
        head atomic.Pointer[Node]
    }
    ```

2050. **Lock-free queue (Michael-Scott queue):** Реализуйте lock-free queue. Это сложнее, чем stack, потому что нужно атомарно обновлять и head, и tail.

2051. **Lock-free linked list:** Реализуйте lock-free singly-linked list с insert и delete. Используйте CAS для pointer updates.

2052. **Hazard pointers:** Для safe memory reclamation в lock-free структурах используйте hazard pointers. Это защищает nodes от premature free.

2053. **RCU (Read-Copy-Update):** Для read-heavy workloads используйте RCU: readers не блокируются, writers создают copy и атомарно swap.

2054. **Epoch-based reclamation:** Альтернатива hazard pointers — epoch-based reclamation. Проще в реализации, но требует periodic quiescent state.

2055. **Lock-free vs wait-free:** Lock-free гарантирует, что хотя бы один thread makes progress. Wait-free гарантирует, что все threads make progress в bounded time. Wait-free сложнее.

2056. **Atomic min/max:** Реализуйте atomic min через CAS loop:
    ```go
    for {
        old := atomic.LoadInt64(&x)
        if old <= newVal || atomic.CompareAndSwapInt64(&x, old, newVal) {
            break
        }
    }
    ```

2057. **Atomic accumulator для float64:** `sync/atomic` не поддерживает float64 напрямую. Используйте `math.Float64bits` и `math.Float64frombits` для atomic float operations.

2058. **Atomic statistics:** Реализуйте lock-free statistics collector: count, sum, min, max через atomic operations.

2059. **Lock-free benchmark:** Сравните производительность lock-free counter vs mutex-protected counter при high contention (100 goroutines). Lock-free должен быть в 10-100x быстрее.

2060. **When to use lock-free:** Lock-free имеет смысл только при high contention. При low contention mutex быстрее (проще, нет CAS retry loops).

### Тема 185: Lock-Free Ring Buffer
*Ring buffer — это классическая lock-free структура для producer-consumer patterns.*

2061. **Ring buffer basics:** Ring buffer — это circular array с `head` и `tail` pointers. Producer пишет в `head`, consumer читает из `tail`.

2062. **Single-producer single-consumer (SPSC):** Простейший case: один producer, один consumer. Не нужен CAS, достаточно atomic load/store.

2063. **SPSC ring buffer implementation:**
    ```go
    type SPSCRingBuffer struct {
        buffer []int64
        head   atomic.Uint64  // producer writes
        tail   atomic.Uint64  // consumer reads
        mask   uint64
    }
    ```

2064. **Power-of-2 size:** Ring buffer size должен быть power of 2. Это позволяет использовать bitmask вместо modulo: `index & mask` вместо `index % size`.

2065. **Cache line padding для SPSC:** Разделите `head` и `tail` в разные cache lines для избежания false sharing:
    ```go
    type SPSCRingBuffer struct {
        _      [40]byte       // padding
        head   atomic.Uint64
        _      [56]byte       // padding
        tail   atomic.Uint64
        _      [56]byte       // padding
        buffer []int64
        mask   uint64
    }
    ```

2066. **SPSC producer:** Producer проверяет, что buffer не full (`head - tail < size`), пишет в `buffer[head & mask]`, атомарно инкрементирует `head`.

2067. **SPSC consumer:** Consumer проверяет, что buffer не empty (`head != tail`), читает из `buffer[tail & mask]`, атомарно инкрементирует `tail`.

2068. **Multi-producer multi-consumer (MPMC):** Сложнее: multiple producers и multiple consumers. Нужен CAS для coordination.

2069. **MPMC ring buffer через sequence numbers:** Каждый slot имеет sequence number. Producer CAS'ит sequence number для reservation slot.

2070. **MPMC implementation (Disruptor-style):** Изучите LMAX Disruptor — high-performance MPMC ring buffer. Реализуйте упрощённую версию.

2071. **Backpressure в ring buffer:** Если buffer full, producer может:
    * Block (wait for space)
    * Drop oldest (overwrite)
    * Return error
    Выберите стратегию based on use case.

2072. **Batch operations:** Для throughput producer может batch write multiple items. Consumer может batch read.

2073. **Ring buffer vs channel:** Go channels — это тоже ring buffers internally. Но custom ring buffer может быть быстрее (нет goroutine scheduling overhead).

2074. **Zero-copy ring buffer:** Для large items используйте ring buffer of pointers вместо ring buffer of values. Это избегает expensive copy.

2075. **Ring buffer benchmark:** Сравните производительность:
    * SPSC ring buffer
    * MPMC ring buffer
    * Go channel
    * Mutex-protected queue
    
    SPSC должен быть fastest (10-100x быстрее channel).

2076. **Ring buffer для logging:** Используйте ring buffer для high-throughput logging. Logger пишет в ring buffer, background goroutine flushes в file/network.

2077. **Ring buffer для metrics:** Используйте ring buffer для metrics collection. Application пишет metrics в ring buffer, aggregator periodically reads.

2078. **Ring buffer для event processing:** Используйте ring buffer для event-driven architecture. Producers publish events, consumers process events.

2079. **Ring buffer sizing:** Размер ring buffer должен быть достаточным для absorbtion burst traffic, но не слишком большим (waste memory).

2080. **Финальный босс (High-Performance Message Passing Framework):**
    Создайте production-grade message passing framework:
    
    **Architecture:**
    * **SPSC ring buffers** для dedicated producer-consumer pairs
    * **MPMC ring buffers** для shared queues
    * **Lock-free counters** для statistics
    * **Cache-friendly structures** для message payloads
    
    **Features:**
    * **Zero-copy messaging:** Messages передаются через pointers, не copy
    * **Batch operations:** Producer и consumer могут batch process
    * **Backpressure:** Configurable strategy (block/drop/error)
    * **Metrics:** Lock-free counters для throughput, latency, queue depth
    * **Monitoring:** Prometheus metrics export
    
    **Performance targets:**
    * SPSC: 100M messages/sec на core
    * MPMC: 10M messages/sec на core
    * Latency: <100ns для SPSC, <1μs для MPMC
    * Zero allocations в hot path
    
    **Use cases:**
    * **High-frequency trading:** Order book updates через SPSC ring buffers
    * **Real-time analytics:** Event streaming через MPMC ring buffers
    * **Logging framework:** High-throughput logging через ring buffers
    * **Metrics collection:** Lock-free metrics aggregation
    
    **Optimizations:**
    * **Cache line padding** для избежания false sharing
    * **Power-of-2 sizing** для fast modulo через bitmask
    * **Memory alignment** для SIMD operations
    * **Huge pages** для снижения TLB misses
    * **NUMA-aware allocation** для multi-socket servers
    
    **Testing:**
    * **Correctness tests:** Все messages доставлены в правильном порядке
    * **Performance tests:** Throughput и latency benchmarks
    * **Stress tests:** High contention, burst traffic
    * **Chaos tests:** Producer/consumer crashes, recovery
    
    **Production features:**
    * **Graceful shutdown:** Drain ring buffers перед shutdown
    * **Monitoring:** Real-time metrics и alerting
    * **Configuration:** Dynamic sizing, backpressure strategy
    * **Multi-tenancy:** Isolated ring buffers per tenant

### 💡 Золотые правила hardware-level оптимизации:

1. **Cache line — это 64 байта.** Всё, что вы делаете, должно учитывать этот факт. Структуры, которые используются вместе, должны быть в одной cache line. Структуры, которые используются разными threads, должны быть в разных cache lines.

2. **False sharing — тихий убийца производительности.** Два thread'а, пишущие в разные переменные в одной cache line, вызывают cache line bouncing. Это может замедлить код в 10-100x. Используйте padding.

3. **Memory alignment обязателен.** Неaligned access может быть в 10x медленнее или вызвать SIGBUS на некоторых архитектурах. Go автоматически align'ит поля структур, но manual optimization требует понимания.

4. **Struct of Arrays > Array of Structs для SIMD.** Если вы обрабатываете одно поле множества объектов (например, все X координаты), SoA позволяет SIMD обрабатывать 8 значений одновременно.

5. **Pointer chasing — это cache miss.** Linked list требует cache miss на каждый элемент. Flat array — sequential access, prefetcher работает. Избегайте linked structures в hot paths.

6. **Lock-free только при high contention.** При low contention mutex быстрее (проще, нет CAS retry loops). Lock-free имеет смысл, когда 100+ threads конкурируют за один resource.

7. **CAS retry loops — это нормально.** В lock-free алгоритмах CAS может fail из-за contention, и вы retry. Это expected behavior. Но убедитесь, что retry probability низкая.

8. **ABA problem реален.** CAS видит, что значение = A, но не знает, что оно было A → B → A. Используйте version counters или hazard pointers для защиты.

9. **Ring buffer size = power of 2.** Это позволяет использовать bitmask (`index & mask`) вместо modulo (`index % size`). Bitmask в 10x быстрее.

10. **SPSC ring buffer — fastest.** Single-producer single-consumer ring buffer не требует CAS, только atomic load/store. Это в 10-100x быстрее, чем MPMC или Go channels.

11. **Cache line padding для producer/consumer.** В ring buffer `head` и `tail` должны быть в разных cache lines. Иначе false sharing между producer и consumer.

12. **Batch operations для throughput.** Вместо одного message за раз, batch process N messages. Это снижает overhead per message и улучшает cache locality.

13. **Zero-copy для large data.** Для больших messages используйте pointers вместо copy. Это избегает expensive memory copy и улучшает cache behavior.

14. **Huge pages для memory-intensive workloads.** TLB misses expensive. Huge pages (2MB/1GB) снижают TLB misses в 512x/262144x. Используйте для больших data structures.

15. **NUMA-aware для multi-socket servers.** На multi-socket servers memory access latency зависит от NUMA node. Аллоцируйте память на том node, где будет выполняться обработка.

16. **Software prefetch для predictable access.** Если вы знаете, какие данные понадобятся через N iterations, используйте software prefetch. Это скрывает memory latency.

17. **Roofline model для bottleneck analysis.** Постройте roofline model: computational intensity vs memory bandwidth vs compute throughput. Это покажет, memory-bound или compute-bound ваш код.

18. **Measure, don't guess.** Всегда benchmark'ите оптимизации. Intuition часто wrong. Используйте `perf`, `vtune`, `pprof` для profiling.

19. **Cache-oblivious algorithms для portability.** Cache-oblivious algorithms оптимальны для любого cache line size без знания этого size. Это future-proof.

20. **Test на real hardware.** Microbenchmarks на laptop могут не отражать production behavior. Тестируйте на real servers с similar CPU, memory, NUMA topology.
