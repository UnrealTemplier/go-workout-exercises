Ниже представлен новый глубокий блок практических упражнений, посвященных **низкоуровневой оптимизации производительности на аппаратном уровне (Hardware-level)** (задачи 626–640).

Этот раздел ориентирован на **инженеров по высокой производительности (High-Performance & Low-Latency Engineers)**. Вы научитесь проектировать структуры данных с учетом кэш-линий процессора, устранять ложное разделение кэша (False Sharing), разрабатывать полностью неблокирующие алгоритмы (Lock-Free) на базе атомарных инструкций процессора, писать оптимизированный код на ассемблере Go (Plan 9 Assembly) с использованием векторных инструкций SIMD, а также работать с сетевыми мультиплексорами пользовательского пространства (gnet) для обхода ограничений стандартной модели сетевых потоков Go.

### Раздел 48: Низкоуровневая оптимизация производительности (Hardware-level) (Задачи 626–640)

#### Подраздел 48.1: Cache-Friendly структуры данных и False Sharing (Задачи 626–630)

*Архитектура современных CPU оптимизирована под последовательное чтение данных из кэш-памяти (L1/L2/L3). Вы научитесь проектировать структуры с учетом выравнивания, Spatial Locality и избегать коллизий кэша.*

626. **Выравнивание полей структур в памяти (Memory Alignment)**: Напишите две структуры с абсолютно одинаковым набором полей: `int8`, `int64`, `int16`, `string`, `bool`. 
    * В `StructBad` расположите поля хаотично (вперемешку мелкие и крупные типы).
    * В `StructGood` отсортируйте поля по убыванию их размера в байтах.
    Выведите размер обеих структур с помощью `unsafe.Sizeof` [175]. Объясните в комментариях концепцию выравнивания памяти на 64-битной архитектуре и почему компилятор вынужден добавлять пустые байты (padding) в первом случае [175].
627. **Устранение ложного разделения кэш-линий (False Sharing)**:
    * Объясните в комментариях проблему: процессор читает данные из ОЗУ в кэш линиями по 64 байта. Если два ядра параллельно пишут в независимые переменные, расположенные на одной кэш-линии, это вызывает постоянную инвалидацию кэша (L1/L2 Cache Invalidation) на обоих ядрах, резко снижая производительность.
    * Напишите структуру счетчиков для 4 параллельных воркеров.
    * Смоделируйте падение производительности из-за False Sharing.
    * Оптимизируйте структуру: добавьте отступы (padding) между счетчиками в виде пустых массивов байт `_ [56]byte` (или используйте специальный тип `cpu.CacheLinePad` из пакета `golang.org/x/sys/cpu`) [627]. Напишите бенчмарк и сравните скорость работы до и после оптимизации.
628. **Паттерн AoS против SoA (Array of Structures vs Structure of Arrays)**: Спроектируйте две модели хранения данных о 1 000 000 точек в 3D-пространстве (координаты `X, Y, Z float64`):
    * Срез структур (AoS — Array of Structures): `[]Point{ {X, Y, Z}, ... }`.
    * Структура срезов (SoA — Structure of Arrays): `struct { X []float64; Y []float64; Z []float64 }`.
    Напишите бенчмарк, который вычисляет сумму всех координат `X` для обеих моделей. Объясните, почему модель SoA оказывается значительно быстрее при анализе отдельных атрибутов за счет пространственной локализации данных (Spatial Locality) в кэше процессора.
629. **Оптимизация обхода двумерных массивов**: Создайте матрицу размером `[2000][2000]int`. Напишите две функции суммирования элементов матрицы:
    * Первая обходит матрицу по строкам (row-major order): `matrix[row][col]`.
    * Вторая обходит матрицу по колонкам (column-major order): `matrix[col][row]`.
    Напишите бенчмарк и сравните их производительность. Напишите подробный комментарий, объясняющий, почему обход по строкам эффективнее из-за работы механизма CPU prefetching (последовательное чтение соседних ячеек памяти).
630. **Поиск без указателей (Pointerless Structs) для оптимизации GC**: Напишите программу, которая создает в оперативной памяти хэш-таблицу на 10 000 000 элементов. Сравните два варианта структур в качестве значений мапы:
    * Структура с указателями: `struct { Name string; Data []byte }` (содержит указатели внутри).
    * Структура без указателей: `struct { Name [32]byte; ID int64 }` (чистые сырые байты на стеке/куче).
    Запустите принудительный сборщик мусора `runtime.GC()` [494]. Замерьте время паузы Stop-The-World (STW). Объясните, почему GC игнорирует структуры без указателей при сканировании кучи, и как этот паттерн помогает бороться с задержками GC на больших объемах данных.

#### Подраздел 48.2: Lock-Free и атомарные структуры данных (Задачи 631–635)

*Использование блокировок (Mutex) приводит к переключению контекста на уровне ОС. Lock-Free структуры данных используют атомарные инструкции процессора для бесконфликтной синхронизации.*

631. **Спин-блокировка (Spinlock) на атомиках**: Напишите простейший механизм взаимного исключения — Spinlock. Используйте переменную `uint32` в качестве флага блокировки и функции пакета `sync/atomic` (в частности, метод Compare-And-Swap: `atomic.CompareAndSwapUint32`). Воркер должен крутиться в активном цикле (busy wait) до тех пор, пока не захватит блокировку. Сравните производительность Spinlock с обычным `sync.Mutex` в сценариях с экстремально короткими критическими секциями.
632. **Lock-Free Single-Producer Single-Consumer (SPSC) Ring Buffer**: Напишите кольцевой буфер (Ring Buffer) фиксированного размера на базе слайса. Настройте его работу без мьютексов: одна горутина (Producer) пишет в буфер, вторая (Consumer) читает из него. Используйте атомарные индексы записи и чтения и функцию `atomic.LoadUint64` / `atomic.StoreUint64` для синхронизации смещений без блокировок.
633. **Защита от ABA-проблемы в Lock-Free структурах**: Опишите в комментариях классическую ABA-проблему, возникающую при работе с Lock-Free алгоритмами с использованием инструкций Compare-And-Swap (CAS) (когда значение переменной меняется с А на B, а затем обратно на А, и CAS ошибочно считает, что состояние не изменилось). Напишите пример реализации Lock-Free стека на Go с использованием счетчика эпох (epoch/generation counter) или уникальных идентификаторов изменений для предотвращения этой проблемы.
634. **Lock-Free Multi-Producer Multi-Consumer (MPMC) Queue**: Напишите сложную конкурентную очередь фиксированного размера, в которую параллельно пишут несколько горутин и параллельно читают другие горутины. Реализуйте алгоритм без использования мьютексов (на базе атомиков). Используйте массив структур, где каждый элемент содержит атомарный флаг-последовательность (sequence) для координации доступа писателей и читателей.
635. **Барьеры памяти (Memory Barriers) и Reordering**: Напишите подробный теоретический комментарий, объясняющий концепцию переупорядочивания инструкций компилятором и процессором (Instruction Reordering). Объясните, как атомарные операции в Go неявно выстраивают барьеры памяти (Memory Fences) и гарантируют строгую согласованность памяти (Sequential Consistency) на x86 архитектурах (которые имеют строгую модель памяти TSO) и на ARM архитектурах (со слабой моделью памяти).

#### Подраздел 48.3: Ассемблер Go (Plan 9 Assembly) и SIMD (Задачи 636–637)

*Написание ассемблерного кода позволяет использовать аппаратные особенности процессора (например, векторные инструкции SIMD) для кратного ускорения вычислений.*

636. **Ваша первая ассемблерная функция (Plan 9)**: Объявите в Go-файле функцию `AddASM(a, b int64) int64` без тела. В этой же директории создайте файл `add_amd64.s` (или под вашу архитектуру) с синтаксисом Plan 9 Assembly. Напишите ассемблерную реализацию функции:
    * Считайте аргументы из стека/регистров (учитывая соглашение о вызовах Go Calling Convention — регистровое в Go 1.17+).
    * Сложите значения.
    * Верните результат.
    Протестируйте вызов этой функции из Go.
637. **Векторные вычисления SIMD (AVX2 / SSE / NEON)**: Напишите ресурсоемкую математическую задачу: покомпонентное сложение двух огромных векторов (слайсов) `[]float32` (размером 10 000 000 элементов).
    * Реализуйте базовый вариант на чистом Go (в цикле).
    * Напишите оптимизированную версию на ассемблере Plan 9, используя векторные SIMD-инструкции процессора (например, `VADDPS` для параллельного сложения 8 вещественных чисел за одну инструкцию на x86 AVX2).
    Запустите бенчмарк сравнения обеих функций и проанализируйте разницу в скорости.

#### Подраздел 48.4: Сетевые мультиплексоры пользовательского пространства (Задачи 638–640)

*Стандартная сетевая модель Go выделяет по одной горутине на каждое соединение. Сетевые мультиплексоры обходят это ограничение, реализуя неблокирующий ввод-вывод на меньшем числе потоков.*

638. **Анализ ограничений стандартного пакета `net`**: Напишите аналитический комментарий: почему модель Go "одна горутина на одно соединение" отлично масштабируется до десятков тысяч подключений, но становится неэффективной (из-за накладных расходов на переключение контекста планировщика и потребление памяти под стеки горутин) при миллионах одновременных соединений (проблема C10M).
639. **Высокопроизводительный TCP-сервер на `gnet`**: Установите популярный асинхронный сетевой фреймворк `github.com/panjf2000/gnet/v2` (работающий по событийно-ориентированной модели epoll/kqueue в пользовательском пространстве). Реализуйте на нем Echo-сервер, обрабатывающий события жизненного цикла соединений: `OnBoot`, `OnOpen`, `OnTraffic`. Сравните потребление памяти этим сервером и вашим стандартным TCP-сервером из раздела №23 под нагрузкой в 50 000 неактивных (keep-alive) соединений.
640. **Оптимизация аллокаций в сетевом мультиплексоре**: Напишите `gnet`-сервер, который распределяет поступающие тяжелые задачи по неблокирующему пулу воркеров (Worker Pool). Для того чтобы избежать выделения памяти (garbage) при чтении входящих пакетов, используйте встроенный в `gnet` кольцевой буфер `gnet.RingBuffer` для переиспользования байтовых массивов и минимизации нагрузки на сборщик мусора Go.
