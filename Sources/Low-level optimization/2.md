### 24. Низкоуровневая оптимизация производительности (Cache-friendly, Lock-Free, Assembly, gnet)

#### 24.1 Cache-friendly структуры и выравнивание памяти
746. **Демонстрация cache line и false sharing.** Создайте две переменные `int64`, лежащие в соседних ячейках памяти (например, поля одной структуры). Запустите две горутины, каждая инкрементирует свою переменную. Сравните производительность с вариантом, где переменные разнесены на разные cache line (добавлен padding `[64]byte`).
747. **Профилирование false sharing с помощью perf.** Используя Linux `perf stat -e cache-misses`, измерьте количество cache-промахов в программе с false sharing и без. Покажите, как выравнивание до 64 байт решает проблему.
748. **Оптимизация структуры для уменьшения размера (alignment/padding).** Создайте структуру с неоптимальным порядком полей (`int64`, `bool`, `int64`, `bool`). Проанализируйте размер через `unsafe.Sizeof` и `alignof`. Переставьте поля, чтобы минимизировать паддинг и общий размер структуры.
749. **Доступ к массиву по строкам vs по столбцам (cache locality).** Напишите обход матрицы `[][]int` (или плоского слайса): построчно и постолбцово. Сравните производительность для больших матриц, объясните влияние cache lines и prefetch.
750. **Префетчинг в Go.** Используйте встроенные инструкции `prefetch` (через ассемблерную вставку или intrinsics на уровне unsafe) для предварительной подгрузки данных в кэш, эмулируя обход связного списка. Сравните скорость обычного обхода и с prefetch.

#### 24.2 Lock-Free структуры данных на `sync/atomic`
751. **Атомарный счётчик и CAS (Compare-And-Swap).** Реализуйте потокобезопасный инкремент счётчика с использованием `atomic.AddInt64`. Сравните производительность с `sync.Mutex` под высокой конкурентной нагрузкой.
752. **Lock-Free стек (Treiber stack).** Реализуйте неблокирующий стек на основе односвязного списка с `atomic.Pointer` или `atomic.Value` (используя unsafe.Pointer). Поддержите операции `Push` и `Pop`. Проверьте корректность в конкурентном тесте с `-race`.
753. **Lock-Free очередь (Michael-Scott queue).** Реализуйте очередь с двумя указателями (head, tail) через CAS. Обеспечьте корректную работу при одновременных enqueue и dequeue. Сравните производительность с каналами.
754. **Ring Buffer на атомиках.** Создайте lock-free кольцевой буфер (циклический массив) фиксированного размера с атомарными операциями для индексов чтения/записи. Реализуйте single-producer single-consumer (SPSC) версию, затем multi-producer multi-consumer.
755. **Atomic.Value для горячего кэша.** Используйте `atomic.Value` для хранения конфигурации, которая обновляется раз в минуту, но читается миллионы раз в секунду. Измерьте overhead по сравнению с мьютексом.
756. **Сравнение lock-free map (sync.Map) с обычной map+mutex.** Создайте сценарий: много чтений, редкие записи. Замерьте `Load` и `Store` у `sync.Map` и `map + sync.RWMutex` на большом количестве горутин. Покажите, когда `sync.Map` выигрывает.
757. **ABA-проблема и её решение.** Продемонстрируйте ABA-проблему на lock-free стеке (pop A, pop B, push A обратно, затем CAS на A ошибочно срабатывает). Покажите решение с помощью счётчика версий (tagged pointer) через `atomic.Uintptr` с зарезервированными битами или через `unsafe.Pointer` с двойным словом.

#### 24.3 Ассемблер Go (Plan 9 Assembly) и SIMD
758. **Первая функция на ассемблере Go.** Напишите ассемблерный файл `.s` с функцией `Add(x, y int) int`, использующей инструкции `ADDQ`. Свяжите с Go-функцией, объявленной как `func Add(x, y int) int` без тела.
759. **Ассемблерная оптимизация хот-спота.** Найдите узкое место в Go-коде (например, вычисление хэша), перепишите критический цикл на asm с использованием регистров. Сравните бенчмарком.
760. **Использование SIMD для пакетной обработки.** Реализуйте функцию суммирования слайса `[]int32` с помощью AVX2 инструкций через план9 asm (или cgo + интринсики). Сравните скорость с обычным циклом на больших массивах.
761. **Работа с флагами процессора.** Определите поддержку AVX2/SSE4.2 через `runtime` или `golang.org/x/sys/cpu`. Используйте условный вызов asm-функции при наличии SIMD, иначе – fallback на Go.
762. **Умножение матриц через SIMD.** Реализуйте умножение двух матриц 4x4 float32 с помощью SSE/NEON инструкций на ассемблере. Сравните производительность с наивной реализацией на Go.
763. **Инлайн-ассемблер через `unsafe` (функционально).** Продемонстрируйте вставку машинных инструкций в срез байт, изменение разрешения памяти на исполнение (через `syscall.Mmap` с `PROT_EXEC`) и вызов. Обсудите риски.
764. **Профилирование на уровне инструкций с `perf` и `objdump`.** Скомпилируйте Go-бинарник с `-gcflags="-S"` для вывода asm, найдите неэффективные участки с помощью `perf record`, `perf annotate`. Оптимизируйте на основе анализа.

#### 24.4 Высокопроизводительные сетевые фреймворки (gnet/evio)
765. **Первый сервер на gnet (или evio).** Напишите эхо-сервер, использующий событийно-ориентированный движок `gnet`. Реализуйте обработчики `OnInitComplete`, `OnTraffic`, `OnClose`. Запустите и проверьте нагрузочным тестом.
766. **Многопоточность в gnet: настройка количества event-loop.** Установите `NumEventLoop` равным `runtime.NumCPU()`. Сравните производительность (RPS, задержку) с однопоточным режимом и с обычным TCP-сервером на `net`.
767. **Кастомный кодек поверх gnet (line-based протокол).** Реализуйте простой текстовый протокол: сообщения заканчиваются `\n`. Используйте `gnet.Reader`/`gnet.Writer` для буферизации и разбора кадров. Поддержите пакетную обработку нескольких сообщений в одном `OnTraffic`.
768. **HTTP-подобный сервер на gnet.** Постройте минимальный HTTP/1.x сервер, который парсит запросы, отдаёт статический ответ и измеряет заголовки. Используйте пулы байтовых буферов (sync.Pool) для снижения аллокаций.
769. **Сравнение gnet, evio и net (Go standard).** Напишите один и тот же функционал (эхо-сервер) на трёх подходах. Проведите бенчмарк с 10k одновременных соединений, малыми сообщениями, измерьте пропускную способность и использование CPU.
770. **Интеграция gnet с кастомным сетевым протоколом и worker pool.** Реализуйте сервер, который получает сообщения в event-loop, но тяжелую обработку делегирует горутинам через асинхронный API `gnet.Conn.AsyncWrite`. Поддержите backpressure при переполнении очереди задач.
