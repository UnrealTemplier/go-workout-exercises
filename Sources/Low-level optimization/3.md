Низкоуровневая оптимизация (Hardware-level performance) — это территория создателей баз данных, высокочастотных торговых систем (HFT) и фреймворков вроде `fasthttp`. Здесь Go соприкасается с C и Ассемблером. Ты напрямую работаешь с кэшем процессора (L1/L2/L3), линиями кэша и инструкциями SIMD.

Это **24 упражнения** (с 931 по 954), которые потребуют от тебя понимания архитектуры x86/ARM и умения читать ассемблер.

### Блок 104: Cache-Friendly структуры и False Sharing
*Цель: Понять, как процессор читает память (линиями по 64 байта), и писать код, который не ломает L1 кэш.*

931. **[Memory Alignment]** Создай структуру `BadStruct { a bool; b int64; c bool }` и `GoodStruct { b int64; a bool; c bool }`. Выведи `unsafe.Sizeof` для обеих. Объясни эффект Padding (выравнивание до 8 байт).
932. **[Cache Line Simulation]** Напиши программу, которая создает массив `[8]int64`. Горутина A постоянно инкрементирует `arr[0]`, а горутина B — `arr[1]`. Запусти под профайлером и замерь время. Хотя это разные переменные, они находятся в одной линии кэша (64 байта), что вызывает постоянную инвалидацию кэша (Cache Coherence Ping-Ponging).
933. **[Устранение False Sharing]** Измени массив из предыдущего задания на структуру `PaddedCounter { val int64; _ [56]byte }`. Создай массив `[8]PaddedCounter`. Замерь время снова. Оно должно ускориться в 5-10 раз, так как каждый счетчик теперь занимает ровно одну линию кэша.
934. **[Cache-friendly Traversal]** Напиши бенчмарк, который суммирует элементы матрицы 1024x1024. Сравни обход по строкам (Row-Major) и по столбцам (Column-Major). Объясни, почему обход по столбцам медленнее в 10 раз (Cache Misses).
935. **[SoA vs AoS (Data Locality)]** Создай структуру `Entity { ID int; Active bool; Data [50]int }`. Создай слайс из 100 000 таких структур (Array of Structs). Напиши бенчмарк, который суммирует `ID` только активных сущностей. Затем перепиши на Struct of Arrays (SoA): `IDs []int`, `Actives []bool`. Оцени колоссальную разницу в скорости из-за плотности данных в кэше.

### Блок 105: Lock-Free структуры (sync/atomic)
*Цель: Избавиться от мьютексов (которые дорогие — ~25ns на Lock/Unlock и вызывают context switch) и использовать неблокирующие алгоритмы на CAS (Compare-And-Swap).*

936. **[atomic.Int64]** Используй новые типы-обертки (Go 1.19+) `atomic.Int64`. Создайте счетчик, инкрементируемый 1000 горутинами без мьютексов.
937. **[Spinlock]** Реализуй свой `Spinlock` на основе `atomic.CompareAndSwapInt32`. Напиши бенчмарк, сравнивающий твой Spinlock с `sync.Mutex` в сценарии без конкуренции (uncontended) и с высокой конкуренцией.
938. **[Lock-Free Stack (Treiber Stack)]** Реализуй стек на связном списке. Используй `atomic.Pointer[Node]` для хранения головы. Операция `Push` должна делать CAS: если голова не изменилась, заменить её на новый узел.
939. **[Lock-Free Queue (MPSC)]** Реализуй очередь для Multiple Producer, Single Consumer. Используй атомарные указатели на `head` и `tail`. Одиночный консьюмер читает без блокировок, продюсеры делают CAS на `tail`.
940. **[Ring Buffer (SPSC)]** Реализуй неблокирующий Ring Buffer (Fixed-size queue) для Single Producer, Single Consumer. Используй `atomic.LoadUint64` для `head` и `tail`. *Ключевой момент:* продюсер пишет данные *до* инкремента `tail`, а консьюмер проверяет `tail` *до* чтения данных (Memory Ordering).
941. **[Каверзный кейс — ABA Problem]** Напиши симуляцию проблемы ABA в Treiber Stack: Поток A читает голову (указатель на Node X). Поток B выталкивает X, выталкивает Y, затем проталкивает X обратно. Поток A делает CAS, видит старый адрес X и успешно меняет голову, но стек сломан (Y потерян). Реализуй защиту через Tagged Pointers (указатель + счетчик версии).
942. **[Backoff в CAS]** Если много горутин борются за один CAS, они будут тратить CPU впустую (Cache Line Ping-Ponging). Реализуй экспоненциальный backoff (через `runtime.Gosched()` или `time.Sleep`) внутри цикла CAS при неудаче. Оцени прирост пропускной способности.

### Блок 106: Plan 9 Assembly и SIMD
*Цель: Использовать векторные инструкции процессора для обработки данных параллельно (Single Instruction, Multiple Data).*

943. **[Базовый ассемблер]** Создай файл `add.s`. Напиши функцию на Go Plan 9 Assembly, которая складывает два `int64` и возвращает результат (`ADDQ R8, R9, AX` / `RET`). Вызови её из Go.
944. **[SIMD: AVX2 (Addition)]** Напиши ассемблерную функцию `AddFloatsAVX2(a, b []float32, res []float32)`. Используй инструкции `VMOVDQU` (загрузка 256-бит / 8 float32), `VADDPS` (сложение 8 чисел за один такт), `VMOVDQU` (выгрузка). Сравни скорость с обычным Go-циклом.
945. **[Каверзный кейс — Assembly BYTE Directives]** Plan 9 ассемблер не поддерживает новейшие инструкции AVX-512. Напиши функцию, использующую `BYTE` директивы (прямая запись опкодов процессора) для вызова инструкции, которой нет в Go ASM.
946. **[Строки и SIMD]** Реализуй `IndexByte` (поиск байта в слайсе) на ассемблере с использованием `PCMPEQB` (сравнение 16 байт одновременно). Сравни со стандартным `bytes.IndexByte`.
947. **[Avo / PeachPy]** Изучи кодогенераторы ассемблера для Go (например, `github.com/mmcloughlin/avo`). Напиши генератор, который создает AVX2 код для умножения матриц, чтобы не писать опкоды вручную.
948. **[Memory Fences]** Используй `runtime.StoreLoadFence()` или `MFENCE` в ассемблере. Объясни, почему на слабых архитектурах памяти (ARM) переупорядочивание инструкций процессором может сломать Lock-Free алгоритмы, написанные для x86 (где модель памяти строгая — Total Store Order).

### Блок 107: User-Space Network Multiplexers (gnet / evio)
*Цель: Обойти модель "горутина на соединение" (которая жрет 4КБ стека на клиента) и использовать Event-Loop архитектуру (как в Nginx / Node.js), но на Go.*

949. **[gnet Echo Server]** Установи `github.com/panjf2000/gnet`. Напиши Echo-сервер, реализующий интерфейс `gnet.EventHandler` (`OnInit`, `OnTraffic`, `OnClose`). Запусти его в одном потоке (`WithNumEventLoop(1)`).
950. **[Коварный кейс — Blocking в Event Loop]** В `OnTraffic` сделай `time.Sleep(1 * time.Second)` (эмуляция блокирующего вызова к БД). Подключись 10 клиентами. Объясни, почему *все* 10 клиентов зависнут, хотя в `net/http` они обрабатывались бы параллельно. (Event Loop заблокирован).
951. **[Правильный дизайн (Worker Pool)]** Перепиши `gnet` сервер: `OnTraffic` не должен ничего вычислять. Он должен читать `[]byte` из сокета и кидать их в неблокирующий `go channel`. Пул горутин (воркеры) читают канал, обрабатывают запрос и отправляют ответ обратно через `conn.AsyncWrite(data)`.
952. **[Custom Codec (Framing)]** TCP потоковый. Напиши свой парсер кадров (Framing) в `OnTraffic`. Протокол: 4 байта длины (Big Endian) + Payload. Если в буфере меньше 4 байт или длина Payload не совпадает — подожди следующий `OnTraffic` вызов.
953. **[Highload Benchmarking]** Используй утилиту `wrk` (wrk -c10000 -d10s ...). Сравни `gnet` Echo сервер (с 1 Event Loop) и `net/http` (с Go планировщиком) по RPS и Latency. Оцени, почему `gnet` выигрывает в 3-5 раз по RPS на echo-задачах.
954. **[Финальное испытание — HFT TCP Gateway]**
    Построй высокопроизводительный шлюз данных.
    - Принимает 10 000 TCP соединений через `gnet` (Использовать `WithMulticore(true)` и `WithLockOSThread(true)` для привязки Event Loop к ядрам CPU).
    - Реализует парсинг бинарного протокола (Length-Prepended).
    - Использует `sync.Pool` для переиспользования буферов `[]byte` (Zero-Allocation).
    - Для тяжелой бизнес-логики использует Lock-Free MPSC очередь (из Блока 105), чтобы передавать данные пулу воркеров, не блокируя Event Loop.
    - Воркеры обрабатывают данные и отправляют ответ через `conn.AsyncWrite`.
    - Добейся < 1ms p99 latency при 100k RPS на локальной машине.
