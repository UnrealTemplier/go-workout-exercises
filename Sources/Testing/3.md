Тестирование в Go — это не просто библиотека, это целая философия. В отличие от других языков, где нужно ставить сторонние фреймворки (типа JUnit или pytest), в Go тестирование встроено в саму экосистему (`go test`), а табличные тесты (table-driven tests) считаются стандартом де-факто.

Здесь **45 упражнений** (с 426 по 470), которые научат тебя писать юнит-тесты, бенчмарки, тестировать HTTP-сервера и БД, а также использовать фаззинг (Fuzzing).

### Блок 39: Базовое тестирование и `go test`
*Цель: Освоить встроенный фреймворк, команды консоли и основные идиомы.*

426. Напиши функцию `Add(a, b int) int`. Создай файл `math_test.go`. Напиши функцию `TestAdd(t *testing.T)`, которая проверяет результат с помощью `if` и вызывает `t.Errorf` при несовпадении.
427. Запусти тесты с помощью `go test`. Запусти с флагом `-v` (verbose), чтобы видеть детальный вывод.
428. Используй `t.Fatalf` вместо `t.Errorf` в месте, где дальнейшее выполнение теста не имеет смысла (например, если функция вернула ошибку, а мы пытаемся прочитать результат).
429. **Табличный тест (Table-driven test):** Создай структуру `testCase` с полями `name`, `inputA`, `inputB`, `expected`. Создай слайс кейсов. Пройдись по ним в цикле и вызови `t.Run(tc.name, func(t *testing.T) { ... })`.
430. Изучи флаг `-run`. Напиши 3 теста: `TestAdd`, `TestSub`, `TestMul`. Запусти `go test -run TestAdd -v`, чтобы выполнился только один.
431. **[Каверзный кейс]** Используй `t.Skip("Skipping because feature is not ready")` внутри теста. Запусти `go test -v` и убедись, что тест помечен как SKIP, а не FAIL.
432. Изучи флаг `-count`. Запусти тест 10 раз с помощью `go test -count=10` (полезно для поиска плавающих багов / flaky tests).
433. Создай функцию `setup()` и `teardown()`. Вызывай их в начале и конце `TestMain(m *testing.M)`. Внутри `TestMain` вызови `os.Exit(m.Run())`.
434. **[Каверзный кейс]** Используй `t.Cleanup(func() { ... })` внутри теста. Убедись, что функции очистки вызываются в обратном порядке (LIFO), даже если тест упал с `t.Fatal`.
435. Напиши тест, который проверяет, что функция возвращает ожидаемую ошибку. Используй `errors.Is` или сравнение с сентинель-ошибкой.

### Блок 40: Утверждения (Assertions) и Мокирование (Mocking)

439. Используй `github.com/stretchr/testify/mock`. Создай мок для `EmailSender`. Настрой ожидание: `mockObj.On("Send", "test@test.com", "Hello").Return(nil)`. Вызови метод и проверь `mockObj.AssertExpectations(t)`.
440. **[Каверзный кейс]** Тестирование зависящее от времени. Напиши функцию, которая ведет себя по-разному днем и ночью. Выдели `time.Now` в переменную или интерфейс. В тесте подменивай время на фиксированное.
441. Используй пакет `gomonkey` (или аналогичный) для monkey-patching (подмена функций во время выполнения, например `gomonkey.ApplyFunc(time.Now, func() time.Time { return fixedTime })`). *Примечание: работает только на Linux/macOS, на Windows требует выключения CFG.*

### Блок 42: Тестирование БД (`go-sqlmock` и Testcontainers)

449. Настрой мок так, чтобы база вернула ошибку (например, симуляция потери соединения). Проверь, что твоя функция корректно обрабатывает эту ошибку.

### Блок 43: Бенчмарки (Benchmarking) и Покрытие (Coverage)
*Цель: Измерять производительность кода и проверять, какие строки кода покрыты тестами.*

453. Напиши функцию `ReverseString(s string) string`. Создай бенчмарк `func BenchmarkReverseString(b *testing.B)`. Внутри используй цикл `for i := 0; i < b.N; i++ { ReverseString("hello") }`.
454. Запусти бенчмарк с помощью `go test -bench=.`. Посмотри на количество наносекунд на операцию (`ns/op`).
455. Используй `b.ReportAllocs()` в бенчмарке. Посмотри на количество выделений памяти на операцию (`allocs/op`).
456. Напиши два варианта конкатенации строк (через `+` и через `strings.Builder`). Напиши для них бенчмарки и сравни производительность.
457. **[Каверзный кейс]** Сброс таймера: если подготовка данных для бенчмарка занимает много времени, используй `b.ResetTimer()` перед циклом, чтобы время подготовки не учитывалось.
458. Запусти тесты с флагом покрытия: `go test -cover`. Посмотри процент покрытия (например, `coverage: 85.2% of statements`).
459. Сгенерируй HTML-отчет о покрытии: `go test -coverprofile=coverage.out && go tool cover -html=coverage.out`. Открой его в браузере и найди непокрытые строки (красным цветом).
460. **[Суб-бенчмарки]** Напиши бенчмарк, который использует `b.Run("small", func(b *testing.B){...})` и `b.Run("large", ...)` для тестирования функции на слайсах разной длины.

### Блок 44: Фаззинг (Fuzzing) — Go 1.18+
*Цель: Автоматический поиск паник и багов при случайных/некорректных входных данных.*

461. Напиши функцию `ParseDuration(s string) (int, error)`, которая парсит строки вида "10s", "5m". Создай Fuzz-тест: `func FuzzParseDuration(f *testing.F)`.
462. Добавь начальные данные (seeds) для фаззера: `f.Add("10s")`, `f.Add("5m")`, `f.Add("invalid")`.
463. Внутри `f.Fuzz(func(t *testing.T, s string) { ... })` вызови свою функцию. Если она не вернула ошибку, убедись, что результат имеет смысл. Если вернула панику — тест упадет.
464. Запусти фаззинг с помощью `go test -fuzz=FuzzParseDuration`. Позволь ему поработать несколько секунд (он будет генерировать мутации строк). Останови (Ctrl+C).
465. Если фаззер нашел падение (crash), он сохранит данные в папку `testdata/fuzz/`. Запусти обычный `go test` — он автоматически подхватит этот кейс как обычный юнит-тест и упадет. Исправь баг в коде.

### Блок 45: Сложные, каверзные и комплексные случаи
*Цель: Решение реальных проблем тестирования в Go.*

466. **[Параллельные тесты]** Напиши 3 теста. В начале каждого вызови `t.Parallel()`. Запусти `go test -v`. Убедись, что тесты выполняются одновременно (в выводе будет `PAUSE`, затем `CONT`).
467. **[Каверзный кейс с `t.Parallel()`]** Напиши табличный тест с `t.Parallel()` внутри `t.Run`. Переменная `tc` (testCase) будет захвачена по ссылке! Исправь это, создав копию переменной внутри цикла: `tc := tc`.
468. **Тестирование паник:** Напиши функцию, которая паникует при отрицательном аргументе. Напиши тест, который использует `defer func() { if r := recover(); r != nil { ... } }()` для проверки, что паника действительно произошла, и тест при этом не упал.
469. **[Высокая сложность — Golden Files]:** Напиши функцию, которая генерирует сложный JSON-отчет. В тесте сгенерируй результат. Если файла `testdata/expected.json` не существует — создай его. Если существует — сравни результат с содержимым файла (`os.ReadFile`). Если тесты падают из-за изменения логики, удали файл, чтобы он перегенерировался.
470. **[Финальное испытание по тестированию]** Напиши CLI-утилиту (работает с флагами, читает файл, делает HTTP-запрос). Покрой её полностью:
    - Логику работы с флагами (передавай `os.Args` в функцию `Run(args []string) error`).
    - Чтение файла (через интерфейс или `os.ReadFile`).
    - HTTP-запрос (через `httptest.NewServer`).
    - Напиши бенчмарк для парсинга.
    - Добейся покрытия кода 90%+.
