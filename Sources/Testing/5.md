Тестирование в Go — это не просто полезная привычка, а часть культуры языка. В Go нет необходимости в тяжеловесных тестовых фреймворках: стандартный пакет `testing` настолько хорош, что покрывает 90% нужд. А для всего остального есть пара проверенных инструментов сообщества.

Продолжаем нашу нумерацию. Впереди **40 интенсивных упражнений** (с 401 по 440), от простейших юнит-тестов до бенчмарков, фаззинга и интеграционного тестирования с Testcontainers.

### Блок 30. Базовое тестирование (Unit Tests) и стандартный `testing` (401–415)
Учимся писать, запускать и анализировать стандартные тесты в стиле Go.

401. **Первый тест:** Напиши простую функцию `Add(a, b int) int` в файле `math.go`. Создай файл `math_test.go` (правило именования!). Напиши функцию `TestAdd(t *testing.T)`. Вызови `Add(2, 2)` и сравни с `4`. Если не равно — вызови `t.Errorf("Ожидалось 4, получили %d", result)`. Запусти `go test`.
402. **Error vs Fatal:** В тесте добавь вызов `t.Error()`, а затем `t.Log("Продолжение")`. Убедись, что после `Error` тест продолжается. Замени `Error` на `t.Fatal()`. Убедись, что `Fatal` немедленно прерывает выполнение текущего теста.
403. **Table-Driven Tests (Золотой стандарт Go):** Перепиши `TestAdd`. Создай срез анонимных структур: `tests := []struct{ a, b, expected int }{ ... }`. Заполни его 5-ю разными кейсами (включая отрицательные числа и нули). В цикле обойди срез и проверь каждый кейс.
404. **Подтесты (`t.Run`):** Доработай упр. 403. Оберни проверку каждого кейса в таблице в `t.Run(name, func(t *testing.T) { ... })`. Запусти `go test -v` и посмотри, как красиво и структурированно выводится результат каждого кейса.
405. **Фильтрация тестов:** Используй флаг `go test -run=TestAdd/имя_конкретного_кейса`, чтобы запустить только один конкретный подтест из твоей таблицы.
406. **Покрытие кода (Coverage):** Напиши функцию с ветвлением (например, валидацию возраста: <0 ошибка, 0-18 ребенок, 18+ взрослый). Напиши тест только для одного условия. Запусти `go test -cover`. Посмотри процент покрытия.
407. **Визуализация покрытия (HTML):** Выполни `go test -coverprofile=c.out`. Затем вызови `go tool cover -html=c.out`. Браузер откроет твой код: зеленым подсвечены протестированные строки, красным — то, куда тесты не зашли. Допиши тесты до 100%.
408. **Пропуск тестов (`t.Skip`):** Напиши тест, который проверяет что-то тяжелое (или требует интернета). В начале теста добавь `if testing.Short() { t.Skip("Пропуск долгого теста") }`. Запусти обычный `go test -v` (тест пройдет), а затем `go test -v -short` (тест будет пропущен).
409. **Функции-помощники (`t.Helper`):** Напиши отдельную функцию `assertMatch(t *testing.T, expected, actual string)`, чтобы не дублировать код в тестах. Внутри нее вызови `t.Helper()`. Сделай так, чтобы тест упал. Убедись, что ошибка в логах указывает на строку в самом тесте, а не внутри твоей функции-помощника.
410. **Черный ящик vs Белый ящик:** Твой код лежит в пакете `calculator`. Напиши тесты в пакете `calculator_test` (в том же файле добавь `_test` к названию пакета). Попробуй протестировать приватную функцию (с маленькой буквы) и убедись, что теперь она недоступна. (Тестирование публичного контракта пакета).
411. **Параллельные тесты (`t.Parallel`):** Создай 3 долгих теста (поставь `time.Sleep(1 * time.Second)` в каждый). Запусти `go test`. Они выполнятся за 3 секунды. Добавь `t.Parallel()` в начало каждого. Запусти снова — они должны выполниться за 1 секунду.
412. **Каверзная ловушка параллельных табличных тестов:** Используй таблицу из упр. 403 и вызови `t.Parallel()` внутри `t.Run`. Если у тебя Go ниже 1.22, тесты могут упасть или проверить только последний кейс (из-за захвата переменной цикла). Осознай, зачем внутри цикла раньше писали `tc := tc` (shadowing).
413. **Очистка ресурсов (`t.Cleanup`):** В тесте создай временный файл. Вместо `defer os.Remove(file.Name())` используй `t.Cleanup(func() { os.Remove(...) })`. `t.Cleanup` надежнее при использовании `t.Parallel()` и подтестов.
414. **Настройка окружения (Setenv):** Напиши функцию, читающую конфигурацию из переменной окружения (например `PORT`). В тесте используй `t.Setenv("PORT", "8080")`. (Go сам вернет старое значение после завершения теста).
415. **Глобальный Setup и Teardown (`TestMain`):** Создай функцию `func TestMain(m *testing.M)`. Внутри напиши код инициализации (например, логов), затем вызови `code := m.Run()`, и после него — код очистки ресурсов. Вызови `os.Exit(code)`.

### Блок 31. Производительность: Бенчмарки, Профилирование и Фаззинг (416–425)
Доказываем эффективность кода с цифрами в руках и ломаем его рандомом.

416. **Базовый бенчмарк:** Создай функцию `BenchmarkAdd(b *testing.B)`. Напиши цикл `for i := 0; i < b.N; i++`, внутри которого вызывай функцию `Add`. Запусти `go test -bench=.`.
417. **Сравнение алгоритмов:** Напиши две функции конкатенации строк. Одна через `+=`, другая через `strings.Builder`. Напиши два бенчмарка для них. Сравни скорость.
418. **Аллокации памяти (`-benchmem`):** Запусти бенчмарки из упр. 417 с флагом `go test -bench=. -benchmem`. Изучи колонки `B/op` (байты за операцию) и `allocs/op` (выделения памяти). Осознай, почему `strings.Builder` лучше.
419. **Сброс таймера (`b.ResetTimer`):** В бенчмарке сгенерируй гигантский массив случайных данных (это занимает время), а затем вызови `b.ResetTimer()` ПЕРЕД циклом `for i := 0; i < b.N...`. Это исключит время подготовки из результатов теста.
420. **Параллельные бенчмарки (`b.RunParallel`):** Протестируй производительность конкурентной мапы `sync.Map`. Используй метод `b.RunParallel(func(pb *testing.PB) { for pb.Next() { ... } })`, чтобы запустить бенчмарк одновременно на всех ядрах процессора.
421. **Базовый Фаззинг (Fuzzing, Go 1.18+):** Напиши функцию `Reverse(s string) string`. Создай тест `func FuzzReverse(f *testing.F)`. Добавь базовый кейс: `f.Add("hello")`. Внутри напиши `f.Fuzz(func(t *testing.T, s string) { ... })` и проверь, что `Reverse(Reverse(s)) == s`. Запусти `go test -fuzz=.`.
422. **Поиск бага с помощью Фаззинга:** Если ты написал `Reverse` перебирая строку байт за байтом (через индексы), фаззер быстро упадет, когда сгенерирует не-ASCII символ (например, иероглиф). Посмотри, как фаззер нашел баг, сохранив падающий кейс в папку `testdata/fuzz`.
423. **Исправление кода после Фаззинга:** Перепиши `Reverse`, работая с рунами (тип `[]rune`), чтобы она корректно поддерживала любые Unicode-символы. Запусти фаззинг снова (оставь на пару минут) — он должен работать без ошибок.
424. **CPU Профайлинг:** Запусти бенчмарк (например, сортировку большого массива) с флагом `go test -bench=. -cpuprofile=cpu.prof`.
425. **Анализ профиля (pprof):** Вызови встроенную утилиту: `go tool pprof cpu.prof`. Внутри консоли pprof введи `top10` (чтобы увидеть самые тяжелые функции) и `web` (чтобы сгенерировать граф вызовов в браузере, потребуется установленный Graphviz).

### Блок 32. Продвинутое тестирование: Testify, Моки и DI (426–435)
Пишем читаемые тесты и учимся изолировать код от внешних зависимостей.

426. **Библиотека Testify (Assert):** Установи `github.com/stretchr/testify`. Перепиши тест с `if expected != result { t.Errorf(...) }` на короткий и выразительный `assert.Equal(t, expected, result)`.
427. **Assert vs Require:** В `testify` есть пакет `require`. Напиши тест, где сначала парсится JSON (`json.Unmarshal`), а потом проверяются его поля. Ошибку парсинга проверь через `require.NoError(t, err)`. Пойми, что `require` (в отличие от `assert`) делает `t.Fatal` и останавливает тест (чтобы не словить панику при проверке полей nil-объекта).
428. **Сравнение JSON:** Тебе нужно протестировать функцию, генерирующую JSON. Используй `assert.JSONEq(t, expectedJSON, actualJSON)`. Обрати внимание, что этот метод успешно сравнит JSON, даже если ключи идут в другом порядке!
429. **Ручные моки (Dependency Injection):** Напиши интерфейс `EmailSender` (метод `Send(to, body string) error`). Напиши структуру `UserService`, которая принимает этот интерфейс. В тестах создай `MockSender`, который просто сохраняет переданные email-ы в локальный срез (slice) и возвращает `nil`. Убедись, что сервис "отправил" письмо через мок.
430. **Симуляция ошибок (Mocking errors):** В ручном моке из упр. 429 добавь поле `ReturnError error`. Настрой мок так, чтобы он возвращал ошибку (симуляция отвала почтового сервера), и протестируй, как твой `UserService` корректно обрабатывает это падение.
431. **Mockgen / Gomock (Генерация):** Установи `go.uber.org/mock/mockgen`. Сгенерируй мок для интерфейса `EmailSender` из консоли.
432. **Использование Gomock:** В тесте инициализируй сгенерированный мок: `ctrl := gomock.NewController(t)`. Настрой ожидание: `mockSender.EXPECT().Send("test@ya.ru", gomock.Any()).Return(nil).Times(1)`. Если сервис не вызовет метод (или вызовет не с теми аргументами) — тест автоматически упадет.
433. **Заморозка времени (Time Mocking):** Твоя функция использует `time.Now()`. Создай интерфейс `Clock` с методом `Now() time.Time`. В проде передавай реализацию с реальным `time.Now`, а в тестах — мок, который всегда возвращает жестко заданную дату. (Так тесты не будут падать по ночам или в високосные годы).
434. **Тестирование HTTP API изнутри (`httptest.ResponseRecorder`):** Напиши HTTP-хендлер. В тесте создай фейковый запрос `req := httptest.NewRequest(...)` и фейковый писатель `rec := httptest.NewRecorder()`. Вызови `handler(rec, req)`. Проверь статускод через `rec.Code` и тело ответа через `rec.Body.String()`.
435. **Мокирование внешнего API (`httptest.Server`):** Твой код делает запросы к стороннему API (например, к Telegram). В тесте создай `ts := httptest.NewServer(http.HandlerFunc(func(w, r) { w.Write([]byte(`{"status": "ok"}`)) }))`. Переопредели URL в твоем клиенте на `ts.URL`. Теперь код делает реальные HTTP-запросы, но обращается к твоему локальному тестовому серверу.

### Блок 33. Интеграционное тестирование и Testcontainers (436–440)
Тестируем приложение в условиях, максимально приближенных к боевым.

436. **Golden Files:** У тебя есть функция, генерирующая сложный HTML-отчет (или PDF). Запиши ожидаемый идеальный результат в файл `testdata/report.golden`. В тесте считывай этот файл и сравнивай с результатом функции. Добавь флаг `go test -update`, при передаче которого тест сам перезапишет `.golden` файл новыми данными (удобно при намеренных изменениях формата).
437. **Testcontainers (База):** Установи `github.com/testcontainers/testcontainers-go`. Напиши тест, который программно скачивает и запускает Docker-контейнер с PostgreSQL перед выполнением теста и убивает его в `t.Cleanup`. (Убедись, что Docker запущен локально).
438. **Миграции в интеграционных тестах:** Подняв контейнер с Postgres (упр. 437), получи случайный порт контейнера, собери строку подключения `postgres://...`, подключись к БД и накати миграции из папки (используя пакет миграций).
439. **Полноценный тест БД:** Используя поднятую БД из упр. 438, инициализируй свой реальный `UserRepository` (из прошлых блоков). Вызови `Create(user)`, затем `GetByID(user.ID)`. Убедись, что данные физически записались в реальную базу и корректно прочитались обратно.
440. **Testcontainers Redis:** Аналогично подними контейнер с Redis. Протестируй свой паттерн Cache-Aside (из блока 29), убедившись, что данные берутся из PostgreSQL, помещаются в реальный Redis (проверь ключ напрямую через Redis-клиент в тесте), и при повторном запросе достаются из кэша.

**Совет к этому этапу:** Отличай юнит-тесты от интеграционных. Юнит-тесты должны выполняться за миллисекунды — для этого мы изолируем БД и сеть с помощью интерфейсов и моков (Блок 32). А вот интеграционные тесты (Блок 33) гарантируют, что твои SQL-запросы реально работают — но их запуск может занимать 10-30 секунд из-за поднятия контейнеров. Хорошая практика: разделять их (например, скрывать интеграционные за build tags `//go:build integration`).
