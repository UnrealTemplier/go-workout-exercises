## Часть XVII. Тестирование

### 65. Базовое тестирование (testing)

**Упражнение 17.1.** Напиши функцию `Add(a, b int) int`. Создай файл `add_test.go`. Напиши тест `TestAdd`, использующий `if got := Add(2, 3); got != 5 { t.Errorf("Add(2, 3) = %d; want 5", got) }`. Запусти `go test`.

**Упражнение 17.2.** Напиши **табличный тест (table-driven test)** для `Add`: слайс структур `{a, b, want int}`. Пройди циклом, вызывай `t.Run(fmt.Sprintf("%d+%d", tc.a, tc.b), func(t *testing.T) { ... })`. Покажи, что `t.Run` создаёт подтесты с именами.

**Упражнение 17.3.** Напиши тест с **несколькими `t.Run` в цикле**, где один case падает. Покажи, что остальные case'и **продолжают выполняться** (Go 1.7+). До этого — `t.Fatalf` останавливал весь тест.

**Упражнение 17.4.** Напиши функцию `Divide(a, b float64) (float64, error)`. Напиши тесты на: нормальное деление, деление на ноль (проверь `err != nil`), отрицательные числа.

**Упражнение 17.5.** Напиши тест с **`t.Fatal` vs `t.Errorf`**: `t.Fatal` немедленно останавливает текущий тест (горутину), `t.Errorf` продолжает. Покажи разницу на примере: после `Fatal` — код не выполняется.

**Упражнение 17.6.** Напиши тест с **`t.Skip`**: если `runtime.GOOS == "windows"` — пропусти тест с сообщением `"unix-specific test"`. Покажи, что `go test` отмечает его как `SKIP`.

**Упражнение 17.7.** Напиши тест с **`t.Parallel()`**: `func TestFoo(t *testing.T) { t.Parallel(); ... }`. Запусти `go test -parallel 4`. Покажи, что тесты выполняются параллельно (порядок вывода перемешан).

**Упражнение 17.8.** Напиши **несколько параллельных тестов**, которые модифицируют **глобальную переменную** без синхронизации. Запусти с `-race`. Покажи, что race detector ловит гонку даже в тестах.

**Упражнение 17.9.** Напиши тест с **`t.Cleanup(func())`**: создай временный файл в тесте, зарегистрируй `t.Cleanup(func() { os.Remove(file) })`. Покажи, что cleanup выполняется даже при `t.Fatal` или панике.

**Упражнение 17.10.** Напиши тест с **`t.Helper()`**: создай вспомогательную функцию `assertEqual(t *testing.T, got, want int)`, вызывай `t.Helper()` в начале. Покажи, что при ошибке stack trace указывает на строку вызова `assertEqual`, а не на `t.Errorf` внутри неё.

**Упражнение 17.11.** Напиши тест с **`t.TempDir()`**: создай файл в `t.TempDir()`. Покажи, что директория автоматически удаляется после теста. Сравни с ручным `os.MkdirTemp` + `defer os.RemoveAll`.

**Упражнение 17.12.** Напиши тест с **`t.Chdir()`** (Go 1.24+) или ручным `os.Chdir` + `defer` для возврата. Покажи, что тест может менять рабочую директорию, не влияя на другие тесты.

### 66. Тестирование с testify

**Упражнение 17.13.** Перепиши тесты из 17.1–17.4 с `github.com/stretchr/testify/assert`. Используй `assert.Equal(t, want, got)`, `assert.NoError(t, err)`, `assert.Error(t, err)`. Сравни читаемость.

**Упражнение 17.14.** Используй `assert` vs `require`: `require.NoError(t, err)` останавливает тест немедленно (как `t.Fatal`), `assert.NoError` — продолжает. Покажи разницу на примере цепочки проверок.

**Упражнение 17.15.** Используй `assert.Contains(t, slice, element)`, `assert.Len(t, slice, 3)`, `assert.NotNil(t, ptr)`. Напиши тесты для функций, работающих со слайсами и мапами.

**Упражнение 17.16.** Используй `assert.Panics(t, func() { ... })` и `assert.NotPanics(t, func() { ... })`. Тестируй функцию, которая должна паниковать при неверных аргументах.

**Упражнение 17.17.** Используй `assert.Eventually(t, condition, timeout, tick)` для тестирования асинхронного кода. Например: запусти горутину, которая через 100ms меняет флаг. Проверь, что флаг стал true в течение 1 секунды.

**Упражнение 17.18.** Используй `assert.InDelta(t, expected, actual, delta)` для сравнения float64 с допустимой погрешностью. Покажи, почему `assert.Equal` плох для float.

**Упражнение 17.19.** Используй `assert.ElementsMatch(t, expected, actual)` для сравнения слайсов без учёта порядка. Покажи разницу с `assert.Equal`, который требует точного порядка.

**Упражнение 17.20.** Используй `assert.Implements(t, (*io.Reader)(nil), obj)` для проверки, что тип реализует интерфейс. Покажи, что это runtime-проверка, а не compile-time.

### 73. Фаззинг (Fuzzing)

**Упражнение 17.63.** Напиши функцию `Reverse(s string) string`, переворачивающую строку (руны!). Напиши фазз-тест: `func FuzzReverse(f *testing.F) { f.Add("hello"); f.Fuzz(func(t *testing.T, orig string) { rev := Reverse(orig); rev2 := Reverse(rev); if orig != rev2 { t.Fatalf("Reverse(Reverse(%q)) = %q", orig, rev2) } }) }`. Запусти `go test -fuzz=FuzzReverse`.

**Упражнение 17.64.** Покажи, что фаззер находит баг: если `Reverse` работает с байтами, а не рунами, фаззер найдёт строку с Unicode (например, `"Hello, 世界"`), где `Reverse(Reverse(s)) != s`.

**Упражнение 17.66.** Напиши фазз-тест для **криптографической функции**: `Hash(data []byte) []byte`. Проверь свойства: длина хеша фиксирована, малое изменение входа → большое изменение выхода (hamming distance).

**Упражнение 17.67.** Напиши фазз-тест с **кастомным mutator'ом** (упрощённо): используй `f.Add(seed...)` с разными типами данных. Покажи, что seed corpus помогает фаззеру быстрее найти интересные входы.

### 76. Property-based testing и продвинутые техники

### Ключевые моменты для освоения тестирования:

1. **Table-driven tests** — идиома Go. Всегда используй `t.Run` с именем для каждого case'а. Это даёт читаемый вывод и возможность запускать отдельные case'и.
2. **`t.Helper()`** — всегда вызывай в вспомогательных функциях. Stack trace будет указывать на строку вызова, а не на `t.Errorf` внутри helper'а.
3. **`-race` в CI** — запускай `go test -race` в CI всегда. Race detector ловит ~90% гонок, но замедляет в 10-20 раз.
4. **Не мокай то, что не контролируешь** — мокай интерфейсы своего приложения (repository, service), а не внешние библиотеки (HTTP client, DB driver). Используй `httptest` и `sqlmock` для интеграции.
5. **Fuzzing** — запускай регулярно, особенно для парсеров и валидаторов. Сохраняй найденные crash'и в `testdata/fuzz/`.
6. **Golden files** — отличны для сложных выводов (SQL, HTML, JSON). Не забывай `-update` флаг для обновления.
7. **Testcontainers** — must have для интеграционных тестов с БД. Каждый тест получает чистое окружение.
8. **Бенчмарки** — измеряй до оптимизации. `benchstat` для статистически значимого сравнения. Не оптимизируй без данных.

Если нужно — следующий этап: **reflection, `unsafe`, cgo, профилирование (`pprof`, `trace`), CI/CD, Docker, Kubernetes, gRPC, GraphQL, message queues (Kafka, RabbitMQ, NATS), observability (OpenTelemetry, Prometheus, Grafana), security (JWT, OAuth2, TLS)**. 🚀
