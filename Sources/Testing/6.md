### Раздел 28: Базовое модульное тестирование (Unit Testing) (Задачи 331–340)

*Написание модульных тестов — основа обеспечения надежности кода. Здесь вы разберете стандартный инструментарий Go, идиоматичный подход к организации тестов и работу с тестовым окружением.*

331. **Первый модульный тест**: Создайте файл `calc.go` и напишите простую функцию `Add(a, b int) int`. В той же директории создайте файл `calc_test.go` с пакетом `package main`. Напишите тест `TestAdd(t *testing.T)`, который проверяет правильность сложения. Запустите его из терминала с помощью команды `go test`.
332. **Табличные тесты (Table-Driven Tests)**: Напишите функцию проверки палиндромов `IsPalindrome(s string) bool` [332]. Напишите для неё табличный тест — идиоматичный паттерн для Go [332]. Создайте анонимную структуру со сценариями (поля: название теста, входные данные, ожидаемый результат) и обойдите их в цикле `for`, проверяя корректность работы функции для каждого случая [332].
333. **Fatal против Error**: Продемонстрируйте разницу между методами логирования ошибок в тестах. Напишите тест, который проверяет два независимых условия. В первом случае при ошибке вызовите `t.Errorf()`, а во втором — `t.Fatalf()`. Запустите тест и убедитесь, что `t.Error` позволяет тесту продолжить выполнение и проверить следующие условия, в то время как `t.Fatal` мгновенно останавливает текущий тест [333].
334. **Субтесты (`t.Run`)**: Перепишите ваши табличные тесты из задачи №332 с использованием метода `t.Run(name, func(t *testing.T) { ... })` [334]. Запустите тесты с флагом подробного вывода `go test -v` и посмотрите, как красиво группируются результаты для каждого тест-кейса [334]. Попробуйте запустить только один конкретный субтест с помощью флага фильтрации, например: `go test -run=TestIsPalindrome/empty_string`.
335. **Параллельное выполнение тестов**: Сделайте ваши субтесты параллельными, добавив вызов `t.Parallel()` внутри `t.Run` [335]. Объясните в комментариях, почему при запуске параллельных тестов в цикле `for` критически важно правильно передавать переменную итератора цикла в анонимную функцию (или переопределять её внутри цикла локально) [335].
336. **Очистка ресурсов через `t.Cleanup`**: Напишите тест, который создает временный файл на диске с помощью `os.CreateTemp`, записывает в него данные, выполняет проверку их чтения, а очистку (удаление файла) регистрирует через `t.Cleanup(func() { ... })` [336]. Напишите комментарий, чем `t.Cleanup` удобнее и безопаснее, чем обычный `defer` внутри теста [336].
337. **Покрытие кода тестами (Code Coverage)**: Напишите функцию со сложной логикой разветвления (`if-else` цепочки). Напишите для неё несколько тестов, покрывающих лишь часть логики. Запустите тесты с генерацией отчета о покрытии: `go test -coverprofile=coverage.out` [337]. Откройте интерактивный HTML-отчет в браузере с помощью команды `go tool cover -html=coverage.out` [337] и посмотрите, какие строки кода подсвечены красным (не покрыты тестами).
338. **Тестирование недетерминированного кода**: Напишите функцию `Greet() string`, которая возвращает `"Доброе утро"`, `"Добрый день"` или `"Добрый вечер"` в зависимости от текущего системного времени (`time.Now()`). Сделайте эту функцию тестируемой, передав интерфейс-зависимость `Clock` (с методом `Now() time.Time`) в качестве параметра. Напишите тест, передав туда фейковые (mock) часы, возвращающие фиксированное время.
339. **Использование библиотеки `testify`**: Установите популярный пакет утверждений `github.com/stretchr/testify`. Перепишите ваши базовые проверки в тестах с использованием пакетов `assert` и `require` (например, `assert.Equal(t, expected, actual)`). Объясните в комментариях разницу между поведением `assert` и `require` при падении теста [339].
340. **Управление запуском пакета тестов (`TestMain`)**: Напишите функцию `TestMain(m *testing.M)` для вашего пакета [340]. Настройте её так, чтобы перед запуском тестов создавалась временная директория для логов, затем выполнялись все тесты с помощью `m.Run()`, а после завершения тестов временная директория гарантированно удалялась [340].

### Раздел 29: Тестирование производительности и документация (Задачи 341–347)

*Написание бенчмарков помогает находить узкие места в производительности и аллокациях памяти, а фаззинг и примеры защищают код от непредвиденных крайних случаев.*

341. **Написание бенчмарка**: Напишите две функции конкатенации слайса строк в одну большую строку: первая использует обычное сложение `+=` в цикле, а вторая использует `strings.Builder`. Напишите для обеих функций бенчмарки (`BenchmarkConcat1` и `BenchmarkConcat2` на основе `testing.B` и цикла `b.N`) [341]. Запустите замер производительности и аллокаций памяти с помощью команды: `go test -bench=. -benchmem` [341]. Проанализируйте результаты.
342. **Сброс таймера в бенчмарках**: Напишите бенчмарк для функции, которая перед началом работы требует тяжелой подготовки данных (например, генерации массива из 1 000 000 случайных чисел). Используйте метод `b.ResetTimer()`, чтобы время этой подготовки не учитывалось в итоговом результате работы бенчмарка [342].
343. **Параметризованные бенчмарки**: Напишите бенчмарк, который измеряет скорость сортировки слайсов разного размера (10, 100, 1000 элементов). Реализуйте это с помощью суббенчмарков `b.Run` в цикле, передавая размер слайса в качестве параметра.
344. **Фаззинг-тестирование (Fuzz Testing)**: Напишите функцию `ReverseString(s string) string`, которая разворачивает строку задом наперед. Напишите для неё фаззинг-тест `FuzzReverse(f *testing.F)` [344]. Запустите фаззинг с помощью команды `go test -fuzz=Fuzz`. Посмотрите, как Go генерирует случайные входные данные, и найдите баг, связанный с некорректной работой функции с многобайтными символами UTF-8 (кириллица, эмодзи). Исправьте функцию, работая с рунами вместо байт.
345. **Тестирование на примерах (Examples)**: Напишите функцию `FormatMoney(amount int) string`. В файле тестов напишите функцию-документацию `ExampleFormatMoney()` [345]. Внутри тела функции вызовите `fmt.Println(FormatMoney(1000))` и добавьте в самом конце специальный комментарий `// Output: 1 000 руб.` [345]. Убедитесь, что `go test` автоматически валидирует соответствие вывода программы вашему комментарию.
346. **Разделение тестов по тегам (Build Tags)**: Напишите медленный интеграционный тест, который не должен запускаться при обычном вызове `go test` (чтобы не замедлять CI). Добавьте в самое начало файла теста тег сборки (например, `//go:build integration` [346]). Проверьте, что обычный вызов `go test` игнорирует этот файл. Запустите только интеграционные тесты с помощью `go test -tags=integration` [346].
347. **Детектор гонок в тестах**: Напишите тест, который запускает несколько горутин, параллельно пишущих данные в общую мапу без синхронизации. Запустите тесты с флагом детектора гонок `go test -race` [347] и проанализируйте подробный отчет о возникновении состояния гонки в выводе теста.

### Раздел 30: Мокирование и тестирование сети/БД (Задачи 348–358)

*Тестирование кода, зависящего от внешних систем (базы данных, сетевые API, файловая система), требует изоляции тестируемой логики с помощью заглушек и моков.*

348. **Ручное мокирование интерфейсов**: Создайте интерфейс `SMSClient` с методом `Send(phone, msg string) error`. Напишите структуру `NotificationService`, которая использует этот клиент. Для тестов `NotificationService` напишите ручной мок `MockSMSClient`, который не отправляет реальные SMS, а просто сохраняет отправленные сообщения в срез внутри структуры мока для последующей проверки.
349. **Мокирование с помощью `testify/mock`**: Перепишите задачу №348, используя встроенный пакет моков из библиотеки testify [349]. Настройте ожидания вызовов методов с помощью `.On("Send", "12345", "Привет").Return(nil)` [349] и проверьте их выполнение в конце теста с помощью метода `.AssertExpectations(t)`.
350. **Тестирование HTTP-обработчиков (`httptest`)**: Напишите HTTP-обработчик `/ping`, который возвращает статус `200 OK` и строку `"pong"`. Напишите для него unit-тест без реального запуска веб-сервера. Используйте пакет `net/http/httptest` [350]: создайте виртуальный запрос с помощью `httptest.NewRequest` [350] и запишите ответ в `httptest.NewRecorder` [350]. Сделайте проверку статус-кода и тела ответа.
351. **Тестирование HTTP-клиента с заглушкой сервера**: Напишите функцию `GetWeather(city string) (float64, error)`, которая делает GET-запрос к внешнему платному API погоды. Чтобы протестировать эту функцию без реальных сетевых запросов к платному API, запустите локальный тестовый HTTP-сервер в кодовой базе теста с помощью `httptest.NewServer` [351]. Настройте этот сервер так, чтобы он возвращал фиксированный JSON-ответ с температурой, и передайте его локальный URL в тестируемый HTTP-клиент [351].
352. **Мокирование SQL-запросов к БД (`sqlmock`)**: Установите библиотеку `github.com/DATA-DOG/go-sqlmock`. Напишите тест для функции, которая сохраняет пользователя в PostgreSQL с помощью `db.Exec`. Используйте `sqlmock` для имитации успешного подключения к БД, настройки ожидаемого INSERT-запроса с конкретными аргументами и проверки корректности выполнения логики вашей программы без реального запуска PostgreSQL [352].
353. **Интеграционное тестирование в Docker (`testcontainers`)**: Напишите интеграционный тест с использованием библиотеки `testcontainers-go` [353]. Настройте тест так, чтобы перед запуском проверок он автоматически скачивал и поднимал реальный Docker-контейнер с PostgreSQL, накатывал миграции, выполнял реальные SQL-запросы вашей программы и тушил контейнер после завершения тестов [353].
354. **Тестирование переменных окружения**: Напишите функцию, которая считывает порт сервера из переменной окружения `PORT`. Напишите тест для этой функции, который временно устанавливает переменную окружения с помощью встроенного метода `t.Setenv("PORT", "9090")` [354] и проверяет корректность парсинга значения. Убедитесь, что после завершения теста значение переменной окружения автоматически сбрасывается в исходное состояние.
355. **Проверка утечек горутин (`goleak`)**: Установите библиотеку `go.uber.org/goleak`. Напишите функцию, которая запускает горутину и по ошибке оставляет её висеть в заблокированном состоянии навсегда (утечка) [355]. Напишите unit-тест для этой функции, вызвав проверку `defer goleak.VerifyNone(t)` [355], и убедитесь, что библиотека ловит утечку горутины и валит тест.
356. **Тестирование файловой системы через виртуальный FS**: Напишите парсер файлов конфигурации. Используйте библиотеку `github.com/spf13/afero` для работы с файловой системой [356]. Напишите тест, заменив реальную файловую систему ОС на виртуальную файловую систему в оперативной памяти (`afero.NewMemMapFs()`) [356], чтобы избежать создания реальных файлов на жестком диске во время прохождения тестов.
357. **Черный ящик против Белого ящика (Black-box vs White-box)**: Объясните разницу между тестированием приватных методов и тестированием только публичного интерфейса.
    * Напишите тест "белого ящика" в файле `service_test.go` с пакетом `package main` (чтобы иметь доступ к неэкспортируемым полям структуры).
    * Напишите тест "черного ящика" в файле `service_blackbox_test.go` с пакетом `package main_test` [357]. Импортируйте ваш пакет и протестируйте только публичные функции.
358. **Тестирование CLI-приложений**: Напишите функцию для CLI-утилиты: `RunCLI(args []string, stdout io.Writer, stderr io.Writer) int` [358]. Напишите тест, который передает в качестве аргументов неверные флаги, а в качестве `stdout`/`stderr` передает буферы `bytes.Buffer` [358]. Проверьте правильность вывода сообщений об ошибках в буферы и возвращаемый утилитой код ошибки [358].
