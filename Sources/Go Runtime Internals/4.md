Ниже представлен **блок из 95 упражнений (с 1146 по 1240)**, который погрузит вас во внутреннюю кухню Go runtime. Вы научитесь "видеть матрицу" — понимать, что происходит под капотом при создании горутин, аллокации памяти и работе сборщика мусора.

### Тема 117: Модель выполнения Go и планировщик GMP (Основы)
*Go использует модель M:N scheduling — множество горутин (G) мультиплексируются на меньшее количество OS потоков (M) через логические процессоры (P).*

1146. **GOMAXPROCS:** Изучите `runtime.GOMAXPROCS(0)`. Установите его в 1, 2, 4, `runtime.NumCPU()`. Запустите CPU-bound задачу и измерьте разницу в производительности.
1147. **Кооперативное вытеснение:** Напишите горутину с бесконечным циклом без syscall'ов и函数 вызовов (`for {}`). Убедитесь, что она блокирует весь P (в Go < 1.14). Изучите, как Go 1.14+ решил это через preemptive scheduling.
1148. **Sysmon thread:** Изучите роль sysmon — специального потока, который просыпается каждые 10ms для проверки зависших горутин и принудительного вытеснения. Используйте `GODEBUG=schedtrace=1000` для наблюдения.
1149. **Local Run Queue (LRQ):** Создайте 10000 горутин. Используйте `GODEBUG=scheddetail=1,schedtrace=100` для наблюдения, как горутины распределяются по P's local queues.
1150. **Global Run Queue (GRQ):** Запустите программу, которая создаёт горутины быстрее, чем P's могут их обрабатывать. Наблюдайте, как горутины попадают в global queue.
1151. **Work Stealing:** Запустите программу с 4 P, где один P выполняет долгую задачу, а остальные завершаются быстро. Наблюдайте, как idle P's "крадут" горутины из LRQ других P's или из GRQ.
1152. **Handoff:** Когда M блокируется на syscall, P передаётся другому M. Создайте множество горутин, делающих блокирующие syscall'ы (например, `time.Sleep`), и наблюдайте handoff через `schedtrace`.
1153. **Spinning threads:** Изучите концепцию spinning M's — потоков, которые активно ищут работу перед тем как заснуть. Это снижает latency при появлении новых горутин.
1154. **Goroutine states:** Используйте `runtime.Stack()` для дампа стека всех горутин. Изучите состояния: `_Grunnable`, `_Grunning`, `_Gsyscall`, `_Gwaiting`, `_Gdead`.
1155. **Netpoller:** Создайте множество горутин, блокирующихся на network I/O. Изучите, как netpoller (epoll/kqueue) интегрирован с планировщиком и не блокирует M.
1156. **Channel operations и planning:** Отправьте/получите данные из канала. Изучите, как `gopark` и `goready` переводят горутину в `_Gwaiting` и обратно в `_Grunnable`.
1157. **Mutex и planning:** Захватите `sync.Mutex` в одной горутине, попробуйте захватить в другой. Изучите, как semaphore и `gopark` используются для блокировки.
1158. **Timer goroutines:** Создайте множество `time.After()` таймеров. Изучите, как runtime использует timer heap и dedicated goroutine для обработки таймеров.
1159. **Preemption points:** Изучите, где runtime вставляет проверки на preemption (function prologue, loop backedges). Напишите код, который избегает этих точек (tight loop без вызовов).

### Тема 118: Продвинутый scheduling и отладка
1160. **GODEBUG=schedtrace:** Запустите программу с `GODEBUG=schedtrace=1000` и расшифруйте вывод: `SCHED 1000ms: gomaxprocs=4 idleprocs=2 threads=6 spinningthreads=0`.
1161. **GODEBUG=scheddetail:** Используйте `scheddetail=1` для детального дампа состояния всех G, M, P. Изучите формат вывода.
1162. **runtime/trace:** Используйте `trace.Start()` и `trace.Stop()` для записи execution trace. Визуализируйте через `go tool trace` и изучите timeline горутин, GC pauses, syscalls.
1163. **Goroutine leaks detection:** Создайте goroutine leak (заблокированная горутина). Используйте `runtime.NumGoroutine()` и `pprof goroutine profile` для обнаружения.
1164. **Gosched():** Вызовите `runtime.Gosched()` для явной передачи управления планировщику. Сравните с `time.Sleep(0)`.
1165. **LockOSThread:** Используйте `runtime.LockOSThread()` для привязки горутины к OS потоку (необходимо для Cgo, GUI-потоков). Изучите последствия для scheduling.
1166. **UnlockOSThread:** Вызовите `runtime.UnlockOSThread()` и изучите, когда это безопасно (после завершения Cgo вызовов).
1167. **NumCPU vs GOMAXPROCS:** Изучите разницу. `NumCPU()` — это hardware cores, `GOMAXPROCS` — это logical processors для Go scheduler. В контейнерах с cgroups они могут отличаться.
1168. **Container-aware GOMAXPROCS:** Используйте `go.uber.org/automaxprocs` для автоматической настройки GOMAXPROCS based on container CPU quota (важно для Kubernetes).
1169. **Fairness:** Создайте сценарий, где одна горутина monopolizes CPU. Изучите, как preemption обеспечивает fairness.
1170. **Priority inversion:** Go не поддерживает приоритеты горутин. Изучите, как это влияет на latency-sensitive задачи и какие workarounds существуют (separate P's, goroutine pools).

### Тема 119: Аллокатор памяти (TCMalloc-inspired)
*Go runtime использует аллокатор, вдохновлённый TCMalloc от Google. Он оптимизирован для многопоточности и малых аллокаций.*

1171. **Size classes:** Изучите size classes в Go (8, 16, 32, 48, 64, 80, 96, ... до 32KB). Каждая аллокация округляется до ближайшего size class. Используйте `runtime.MemStats` для наблюдения.
1172. **Tiny, Small, Large allocations:**
    * Tiny: < 16 bytes (special handling, может объединять несколько аллокаций)
    * Small: 16 bytes - 32 KB (через mspan)
    * Large: > 32 KB (напрямую из mheap)
1173. **mcache:** Каждый P имеет свой `mcache` — локальный кэш `mspan`'ов для разных size classes. Это позволяет аллоцировать без блокировок.
1174. **mcentral:** Когда `mcache` истощается, он запрашивает новые `mspan`'ы из `mcentral` (глобальный для каждого size class, с блокировкой).
1175. **mheap:** Глобальный heap, управляющий всей памятью процесса. Содержит все `mspan`'ы, организованные в radix tree для быстрого поиска.
1176. **mspan:** Непрерывный блок памяти, состоящий из нескольких страниц (8KB каждая). Содержит объекты одного size class.
1177. **Page allocation:** Изучите, как runtime запрашивает страницы у ОС через `mmap`/`VirtualAlloc` и возвращает через `munmap`/`VirtualFree`.
1178. **Span coalescing:** Когда смежные `mspan`'ы освобождаются, runtime объединяет их для снижения фрагментации.
1179. **Memory fragmentation:** Создайте паттерн аллокаций, вызывающий фрагментацию (множество мелких аллокаций с последующим освобождением через одного). Изучите влияние на memory usage.
1180. **Arena:** Go резервирует большие регионы виртуальной памяти (arenas, 64MB на 64-bit системах) для эффективного управления памятью.
1181. **Heap growth:** Изучите, как runtime решает, когда запрашивать больше памяти у ОС (heuristic based on GC cycles and memory usage).
1182. **Memory profiling:** Используйте `pprof heap profile` с флагом `-inuse_space` и `-alloc_space`. Изучите разницу: "что сейчас в памяти" vs "что было аллоцировано за всё время".
1183. **Escape analysis:** Напишите код с переменными, которые "убегают" в heap (возвращаются из функции, передаются в горутины). Используйте `go build -gcflags="-m"` для наблюдения escape analysis.
1184. **Stack allocation:** Изучите, как Go аллоцирует стеки горутин (начальный размер 2KB, динамически растёт/сжимается). Сравните с фиксированными стеками в Java/C++.
1185. **Stack growth:** Создайте глубокую рекурсию. Изучите, как runtime копирует стек в новое место при переполнении (stack copying).

### Тема 120: Garbage Collector (Concurrent Mark-Sweep)
*Go использует concurrent, non-generational, tri-color mark-sweep GC с write barriers.*

1186. **GC phases:** Изучите 4 фазы GC:
    * Mark Setup (STW - Stop The World, ~0.1ms)
    * Marking (concurrent, с write barriers)
    * Mark Termination (STW, ~0.5ms)
    * Sweeping (concurrent, между аллокациями)
1187. **Tri-color marking:** Изучите алгоритм: White (кандидаты на удаление), Grey (в процессе обхода), Black (обработанные). Поймите, как это обеспечивает корректность при concurrent marking.
1188. **Write barriers:** Когда указатель модифицируется, write barrier записывает это в buffer для последующей обработки GC. Изучите hybrid write barrier (Dijkstra + Yuasa).
1189. **GC pacing:** Runtime решает, когда запускать GC, чтобы завершить marking до того, как heap вырастет слишком сильно. Изучите формулу: `target heap size = live heap * (1 + GOGC/100)`.
1190. **GOGC:** Установите `GOGC=20` (агрессивный GC, больше CPU) и `GOGC=200` (ленивый GC, больше памяти). Измерьте влияние на latency и throughput.
1191. **GOMEMLIMIT (Go 1.19+):** Установите soft memory limit через `GOMEMLIMIT=1GiB`. Runtime будет стараться не превышать этот лимит, запуская GC чаще при необходимости.
1192. **GC assist:** Когда горутина аллоцирует память во время GC, она может быть "призвана" помочь с marking (GC assist). Это снижает latency, но увеличивает CPU usage для аллоцирующих горутин.
1193. **Mark workers:** Runtime запускает dedicated goroutines для concurrent marking. Изучите, как они балансируют работу.
1194. **Sweep termination:** Изучите, как sweeping происходит в фоне и как runtime гарантирует, что память переиспользуется безопасно.
1195. **Finalizers:** Используйте `runtime.SetFinalizer()` для регистрации функций, вызываемых перед удалением объекта. Изучите, почему finalizers — это anti-pattern (непредсказуемое время вызова, могут resurrect объекты).
1196. **GC CPU overhead:** Используйте `runtime.ReadMemStats()` для получения `PauseTotalNs` и `NumGC`. Вычислите процент времени, потраченного на GC.
1197. **GC pauses:** Измерьте STW pauses через `MemStats.PauseNs` (массив последних 256 pauses). В Go 1.19+ типичные pauses < 1ms.
1198. **Forcing GC:** Вызовите `runtime.GC()` для принудительного запуска сборщика. Изучите, когда это полезно (например, после загрузки больших данных).
1199. **Debug.SetGCPercent:** Измените `GOGC` программно через `debug.SetGCPercent(50)`.
1200. **Debug.SetMemoryLimit:** Установите `GOMEMLIMIT` программно через `debug.SetMemoryLimit(1 << 30)` (1GB).
1201. **GC traces:** Запустите программу с `GODEBUG=gctrace=1` и расшифруйте вывод:
    ```
    gc 1 @0.015s 0%: 0.015+0.30+0.045 ms clock, 0.12+0.15/0.45/0.15+0.36 ms cpu, 4->4->0 MB, 5 MB goal, 8 P
    ```
1202. **Live heap vs allocated:** Изучите разницу между `HeapAlloc` (текущее использование) и `TotalAlloc` (кумулятивные аллокации) в `MemStats`.
1203. **HeapIdle vs HeapReleased:** `HeapIdle` — память, возвращённая в OS, но может быть переиспользована. `HeapReleased` — память, физически возвращённая в OS через `madvise(MADV_FREE)`.

### Тема 121: Оптимизация памяти и GC
1204. **Object pooling:** Используйте `sync.Pool` для переиспользования объектов и снижения давления на GC. Изучите, как `sync.Pool` очищается при каждом GC cycle.
1205. **Pre-allocation:** Используйте `make([]T, 0, capacity)` для предварительной аллокации слайсов. Измерьте разницу в аллокациях через бенчмарки.
1206. **Slice reuse:** Реиспользуйте слайсы через `s = s[:0]` вместо создания новых. Это сохраняет базовый массив.
1207. **String interning:** Для часто используемых строк используйте interning (хранение уникальных копий в map) для снижения memory footprint.
1208. **Struct packing:** Упорядочьте поля структуры по размеру (largest first) для снижения padding. Сравните `struct { bool; int64; bool }` (24 bytes) vs `struct { int64; bool; bool }` (16 bytes).
1209. **Pointer-free types:** Используйте типы без указателей (`int`, `float64`, structs с только value types) — GC не сканирует их, что ускоряет marking.
1210. **Avoid heap allocations:** Используйте escape analysis (`-gcflags="-m"`) для выявления неожиданных heap аллокаций. Переписывайте код для stack allocation.
1211. **Buffer pooling для I/O:** Используйте `sync.Pool` для `bytes.Buffer` в HTTP handlers для снижения аллокаций.
1212. **Memory-mapped files:** Для работы с большими файлами используйте `mmap` (через `golang.org/x/exp/mmap` или syscall) вместо загрузки в heap.
1213. **Off-heap memory:** Для экстремальных случаев используйте `mmap` напрямую для off-heap памяти, не управляемой GC (требует ручного освобождения).
1214. **GC tuning для low-latency:** Для latency-sensitive приложений используйте `GOGC=20` и `GOMEMLIMIT` для частых, но коротких GC pauses.
1215. **GC tuning для high-throughput:** Для batch-processing используйте `GOGC=200` для снижения CPU overhead от GC.
1216. **Monitoring GC:** Экспортируйте GC метрики в Prometheus: `go_gc_duration_seconds`, `go_memstats_alloc_bytes`, `go_goroutines`.

### 💡 Золотые правила работы с Go Runtime:

1. **Понимайте GMP модель.** Знание, как горутины мультиплексируются на OS потоки через P's, критично для написания эффективного concurrent кода и отладки performance issues.

2. **Escape analysis — ваш друг.** Всегда проверяйте через `-gcflags="-m"`, где аллоцируются переменные. Stack allocation в 10-100x быстрее heap allocation и не нагружает GC.

3. **GOGC и GOMEMLIMIT — это knobs, не магия.** Настройте их based on your workload:
   * Low-latency: `GOGC=20`, `GOMEMLIMIT=<80% of container memory>`
   * High-throughput: `GOGC=200`
   * Memory-constrained: `GOMEMLIMIT` обязателен

4. **GC pauses в современном Go — это не проблема.** В Go 1.19+ типичные pauses < 1ms. Если у вас большие pauses — это признак проблем (слишком большой live heap, pointer-heavy data structures).

5. **Profilers обязательны в production.** CPU profile, heap profile, goroutine profile, block profile, mutex profile — все должны быть доступны (через internal port) для быстрой диагностики проблем.

6. **sync.Pool для hot objects.** Если вы создаёте и удаляете множество однотипных объектов (buffers, structs) в hot path — используйте `sync.Pool`. Это снижает GC pressure на 50-90%.

7. **Pre-allocation слайсов.** `make([]T, 0, expectedCap)` вместо `make([]T, 0)` + множество `append`'ов. Это снижает количество реаллокаций с O(log N) до 1.

8. **Избегайте finalizers.** `runtime.SetFinalizer` — это anti-pattern. Используйте явное `Close()`/`Cleanup()` через `defer`. Finalizers непредсказуемы и могут resurrect объекты.

9. **Monitor runtime metrics.** Экспортируйте в Prometheus:
   * `go_goroutines` — утечки горутин
   * `go_gc_duration_seconds` — GC overhead
   * `go_memstats_alloc_bytes` — memory usage
   * `go_threads` — OS threads (должно быть ~GOMAXPROCS + syscalls)

10. **Trace — это superpower.** `runtime/trace` даёт вам timeline всех горутин, GC cycles, syscalls. Это незаменимо для отладки сложных concurrency и performance проблем.

11. **Понимайте size classes.** Аллокации округляются до ближайшего size class. `make([]byte, 17)` аллоцирует 32 bytes. Это важно для memory-constrained приложений.

12. **Stack growth — это copy.** Когда стек горутины переполняется, runtime копирует его в новое место. Это означает, что указатели на stack variables могут стать невалидными (поэтому Go запрещает брать адрес stack variable и сохранять его после возврата).

13. **Syscalls блокируют M, но не P.** Когда горутина делает блокирующий syscall, P передаётся другому M. Это позволяет другим горутинам продолжать работу. Но если все M заблокированы, runtime создаст новые M (до лимита в 10000).

14. **Preemption не мгновенный.** Runtime проверяет preemption только в определённых точках (function prologue, loop backedges). Tight loops без вызовов могут monopolize P до следующей проверки.

15. **Read the source.** Исходники Go runtime (`$GOROOT/src/runtime/`) — это well-written C/assembly код с отличными комментариями. Изучение `proc.go`, `malloc.go`, `mgc.go` даст вам глубочайшее понимание языка.
