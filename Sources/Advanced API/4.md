### Тема 161: Webhooks — Основы платформы обратных вызовов
*Webhooks — это "reverse API": ваш сервер инициирует HTTP-запросы к клиентским endpoints при возникновении событий.*

1676. **Регистрация webhook endpoint:** Создайте API для регистрации webhook: `POST /webhooks` с полями `url`, `events[]`, `secret`. Валидируйте URL (схема HTTPS, reachable host).

1677. **Endpoint verification (Stripe-style):** При регистрации отправляйте GET-запрос с `challenge` параметром. Клиент должен вернуть challenge в теле ответа — это подтверждает владение доменом.

1678. **HMAC signature генерация:** При отправке webhook события подписывайте body через HMAC-SHA256 с общим secret. Добавляйте подпись в header `X-Webhook-Signature: sha256=...`.

1679. **Timestamp в подписи:** Включайте `X-Webhook-Timestamp` header и подписывайте `timestamp.body` конкатенацию. Это защита от replay attacks.

1680. **Верификация на стороне клиента:** Реализуйте Go-клиент, который получает webhook, проверяет timestamp (не старше 5 минут), вычисляет HMAC и сравнивает через `hmac.Equal` (constant-time).

1681. **Webhook dispatcher:** Создайте систему, которая при возникновении события (`order.paid`) находит все подписанные endpoints и ставит delivery задачи в очередь (Redis/Kafka).

1682. **Асинхронная доставка:** Никогда не доставляйте webhooks синхронно в request handler. Всегда через background worker — иначе slow endpoints заблокируют ваш API.

1683. **Event payload структура:** Стандартизируйте payload: `{"id": "evt_...", "type": "order.paid", "created_at": "...", "data": {...}}`. ID события критичен для idempotency.

1684. **Event ordering:** Обеспечьте доставку событий для одной сущности (`user_id`, `order_id`) в порядке возникновения. Используйте Kafka partition key или Redis stream с ordering.

1685. **Multiple events per webhook:** Позвольте клиентам подписываться на `*` (все события) или на конкретные типы (`order.*`, `payment.failed`).

1686. **Webhook filtering:** Добавьте filter rules: "доставлять только если `amount > 1000`" или "только для `region = EU`". Реализуйте через CEL (Common Expression Language) или JMESPath.

1687. **Secret rotation:** Реализуйте dual-secret систему: при ротации оба секрета валидны в течение grace period (24 часа). Это позволяет клиентам мигрировать без downtime.

1688. **Webhook logs и retries UI:** Создайте dashboard, где клиенты видят историю доставок: timestamp, status code, response body, retry count, next attempt.

1689. **Manual retry endpoint:** Дайте клиентам кнопку "Retry" для failed webhook delivery. Это критично для debugging.

1690. **Test event endpoint:** Предоставьте `POST /webhooks/:id/test` для отправки тестового события. Stripe-style: `evt_test_...` с пометкой в payload.

### Тема 162: Webhooks — Delivery и Retry mechanics
*90% проблем webhook-платформ — в ненадёжной доставке. Это отдельная наука.*

1691. **Exponential backoff:** Реализуйте retries по формуле `delay = base * 2^attempt`: 1min, 5min, 30min, 2h, 8h, 24h, 3 days, 7 days (типичный Stripe schedule).

1692. **Jitter (обязательно!):** Добавьте случайный jitter (±20%) к каждому delay. Без jitter при массовом сбое все retries "схлопываются" в один момент и DoS-ят failing endpoint.

1693. **Full jitter pattern:** Используйте `delay = random(0, base * 2^attempt)` — более агрессивная версия jitter, рекомендованная AWS Architecture Blog.

1694. **Max retries и dead letter:** После N неудачных попыток (обычно 15-20) помечайте webhook как disabled и отправляйте событие в dead letter queue для ручного разбора.

1695. **Circuit breaker per endpoint:** Если endpoint failing подряд N раз, временно переставайте доставлять ему события (circuit open). Через M минут — half-open, пробуем один запрос.

1696. **Slow endpoint detection:** Установите жесткий timeout на доставку (10-15 секунд). Slow endpoints не должны блокировать delivery других клиентов.

1697. **Concurrent delivery limiting:** Ограничьте количество одновременных deliveries на один endpoint (например, не более 10). Иначе burst событий положит клиентский сервер.

1698. **Idempotency через event ID:** Клиент должен использовать `event.id` для deduplication. Один и тот же event может быть доставлен несколько раз (at-least-once semantics).

1699. **Idempotency-Key header:** Отправляйте `Idempotency-Key: evt_...` header, чтобы клиенты могли использовать свои idempotency libraries.

1700. **Batch delivery (опционально):** Для high-volume клиентов группируйте события в batch webhook: `{"events": [...]}`. Снижает overhead в 100x.

1701. **Webhook signature versioning:** Поддерживайте несколько версий signature algorithm (`v1`, `v2`). При миграции на более безопасный алгоритм отправляйте обе подписи в переходный период.

1702. **IP whitelisting:** Публикуйте статический IP-диапазон ваших webhook sender'ов. Крупные клиенты часто требуют whitelist по firewall rules.

1703. **Egress through proxies:** Для enterprise-клиентов настройте delivery через их HTTPS proxy (forward proxy support).

1704. **mTLS для webhook delivery:** Предложите премиум-опцию: mTLS, где и ваш сервер, и клиент аутентифицируют друг друга сертификатами.

1705. **Custom headers per webhook:** Позвольте клиентам задавать custom headers (например, `X-Api-Key` для их internal routing).

1706. **Timeout configuration per endpoint:** Дайте клиентам настраивать timeout под их SLA (1s для real-time, 30s для batch processing).

1707. **Delivery attempts tracking:** Сохраняйте каждый attempt: timestamp, request body, response code, response body, latency. Это gold для debugging.

1708. **Redacting sensitive data в logs:** При сохранении request/response body маскируйте PII и секреты перед записью в БД.

1709. **Webhook delivery metrics:**
    * Delivery success rate
    * Mean/median/p99 latency
    * Retry rate
    * Dead letter queue size
    * Disabled endpoints count
    Экспортируйте всё в Prometheus.

1710. **Alerting на disabled endpoints:** Алерт клиенту (email/Slack), когда его webhook disabled из-за repeated failures. Это proactive support.

### Тема 163: Webhooks — Безопасность и edge cases
1711. **SSRF protection в webhook registration:** При регистрации webhook не делайте verification request с вашего production server — атакующий может направить его на internal ресурсы (`http://169.254.169.254`, `http://metadata.google.internal`). Используйте isolated verification service.

1712. **DNS rebinding protection:** При delivery разрешайте hostname и проверяйте, что IP не из private ranges (RFC 1918, 169.254.0.0/16). Иначе атакующий может redirect webhook на internal сеть.

1713. **Redirect following policy:** Не следуйте за redirect'ами при webhook delivery или следуйте максимум 1 redirect на тот же host. Open redirect может быть использован для SSRF.

1714. **Large payload handling:** Установите max payload size (например, 256KB). Большие payloads DoS-ят клиентские endpoints и вашу сеть.

1715. **Gzip compression:** Сжимайте webhook body через gzip для снижения трафика. Добавляйте `Content-Encoding: gzip` header.

1716. **Rate limiting per endpoint:** Защищайте клиентов от burst'ов: не более N deliveries/сек на один endpoint, даже если у вас миллион событий в очереди.

1717. **Global rate limiting:** Защищайте свою инфраструктуру: общий outbound webhook RPS limit, чтобы не перегрузить own network.

1718. **Backpressure при перегрузке:** Если delivery queue переполнена, временно переставайте принимать новые webhook registrations или переводите на degraded mode.

1719. **Webhook payload versioning:** Добавляйте `api_version` в payload. При breaking changes в схеме увеличивайте версию, чтобы клиенты могли мигрировать постепенно.

1720. **Webhook fan-out optimization:** Для события, на которое подписаны 1000 endpoints, не делайте 1000 serial deliveries. Используйте worker pool и batch fetching из очереди.

1721. **Hot endpoint detection:** Детектируйте endpoints, которые генерируют disproportional трафик (один клиент потребляет 50% delivery capacity). Предлагайте им batch mode или отдельный tier.

1722. **Webhook signature timing attack protection:** Всегда вычисляйте signature, даже если timestamp expired или невалидный. Иначе timing difference раскроет, какая проверка провалилась.

1723. **Clock skew tolerance:** При timestamp verification допускайте ±5 минут clock skew между вашим и клиентским сервером.

1724. **Webhook delivery from multiple regions:** Для low-latency delivery клиентам в разных регионах используйте regional webhook sender'ы (US, EU, APAC).

1725. **Webhook event retention:** Храните историю events 30-90 дней для manual retries и audit. Используйте ClickHouse для efficient storage.

### Тема 164: Server-Sent Events (SSE)
*SSE — это однонаправленный real-time streaming от сервера к клиенту поверх HTTP. Проще WebSocket, автоматически реконнектится, работает через corporate proxies.*

1726. **Базовый SSE endpoint:** Создайте handler, который устанавливает заголовки:
    ```
    Content-Type: text/event-stream
    Cache-Control: no-cache
    Connection: keep-alive
    ```
    И пишет события в формате `data: message\n\n`.

1727. **http.Flusher:** После каждой записи вызывайте `flusher.Flush()`. Без этого reverse proxies и буферы Go будут задерживать события.

1728. **Context cancellation:** Используйте `r.Context().Done()` для детекта отключения клиента. При disconnect освобождайте ресурсы (unsubscribe от channels).

1729. **Event types:** Используйте `event: message_type\n` перед `data:` для разных типов событий. Клиент на JS может делать `evtSource.addEventListener('user.updated', ...)`.

1730. **Event IDs:** Добавляйте `id: 12345\n` для каждого события. Это позволяет клиенту автоматически resume с последнего полученного ID при reconnect.

1731. **Last-Event-ID header:** При reconnect браузер автоматически отправляет `Last-Event-ID` header. Ваш сервер должен прочитать его и отправить пропущенные события.

1732. **Server-side reconnection buffer:** Храните последние N событий (или события за M минут) в ring buffer. При reconnect с `Last-Event-ID` отправляйте пропущенные из буфера.

1733. **Retry interval:** Отправляйте `retry: 3000\n` событие для указания браузеру интервала reconnect в миллисекундах.

1734. **Multiline data:** Для данных с переводом строк используйте несколько `data:` строк: `data: line1\ndata: line2\n\n`. Клиент получит их как единое сообщение с `\n` внутри.

1735. **JSON в SSE:** Отправляйте JSON как data: `data: {"type":"update","payload":{...}}\n\n`. Это standard practice.

1736. **Comments для keep-alive:** Отправляйте `: ping\n\n` (строки с `:` в начале — это комментарии, игнорируются клиентом) каждые 15-30 секунд для поддержания connection через proxies с idle timeout.

1737. **SSE vs WebSocket benchmark:** Сравните overhead: SSE использует стандартный HTTP (работает через corporate proxies, CDN), WebSocket требует отдельного protocol upgrade. SSE идеален для server→client streaming.

1738. **SSE client в Go:** Реализуйте SSE client через `http.Client` с streaming response body. Парсите события вручную или используйте `github.com/r3labs/sse`.

1739. **SSE auto-reconnect client:** Реализуйте client с exponential backoff reconnect и `Last-Event-ID` tracking.

1740. **Broadcast через fan-out:** При получении события рассылайте его всем подключённым SSE клиентам через fan-out pattern (один channel → N goroutines).

1741. **SSE per-user filtering:** При подключении извлекайте user_id из JWT, подписывайте клиента только на события этого пользователя (через filter в dispatcher).

1742. **SSE connection tracking:** Храните active connections в потокобезопасной структуре (`sync.Map`). При disconnect удаляйте из map.

1743. **Max connections per user:** Ограничьте количество SSE connections на одного пользователя (обычно 1-3). Предотвращает resource exhaustion.

1744. **Graceful shutdown SSE:** При SIGTERM отправьте всем клиентам событие `event: shutdown\ndata: server stopping\n\n` и закройте соединения.

1745. **SSE through reverse proxy:** Настройте Nginx/Envoy для поддержки SSE:
    ```nginx
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 3600s;
    ```
    Без `proxy_buffering off` события будут задерживаться.

1746. **SSE through CDN:** Cloudflare, Fastly поддерживают SSE, но требуют special configuration (disable buffering, set proper timeouts). Изучите особенности каждого CDN.

1747. **SSE vs Long Polling vs WebSocket:**
    * SSE: server→client only, auto-reconnect, HTTP-friendly
    * Long Polling: high overhead, не real-time
    * WebSocket: bidirectional, требует protocol upgrade
    Используйте SSE когда нужен только server→client streaming.

1748. **SSE + HTTP/2 multiplexing:** На HTTP/2 один connection может держать множество SSE streams без overhead. Это эффективно для multi-tenant приложений.

1749. **SSE event ordering guarantee:** Обеспечьте in-order delivery событий одному клиенту через serialization (один writer per client).

1750. **SSE backpressure:** Если клиент медленно читает (медленный network), накапливайте события в per-client buffer с limit. При overflow — disconnect и force reconnect.

### Тема 165: SSE — Production patterns
1751. **ChatGPT-style streaming:** Реализуйте streaming LLM responses через SSE: каждый токен — отдельное событие `data: {"token": "Hello"}\n\n`, финальное `data: [DONE]\n\n`.

1752. **Server-side filter subscription:** При подключении клиент отправляет filter criteria (например, `?symbols=BTC,ETH`), сервер подписывает его только на matching события.

1753. **Presence through SSE:** Отправляйте события `user.online`, `user.typing`, `user.offline` для real-time presence в collaborative приложениях.

1754. **Real-time dashboards:** Обновляйте metrics dashboards через SSE: новые данные приходят как события, frontend обновляет графики без polling.

1755. **CI/CD live logs:** Streaming build/test logs через SSE (как в GitHub Actions, GitLab CI). Каждая строка лога — событие.

1756. **Stock ticker streaming:** Real-time обновление цен акций через SSE с delta-only updates (отправляйте только изменения).

1757. **SSE with authentication:** Аутентифицируйте SSE connections через:
    * Bearer token в `Authorization` header (первый request)
    * Session cookie
    * Token в query string (fallback для `<img src>` use cases, но менее безопасно)

1758. **SSE token refresh:** SSE connection может жить часами. Реализуйте graceful token refresh: отправьте событие "reconnect with new token" перед expiration.

1759. **SSE multi-tab coordination:** Через `BroadcastChannel` API координируйте SSE connections между вкладками браузера — только одна вкладка держит connection, остальные получают события через BroadcastChannel.

1760. **SSE + Server-Side caching:** Кэшируйте последнее состояние per client. При reconnect отправляйте cached state первым событием, затем delta updates.

### Тема 166: JSON-RPC 2.0
*JSON-RPC — это простой, stateless RPC-протокол поверх JSON. Используется в LSP (Language Server Protocol), Ethereum API, Bitcoin Core.*

1761. **Спецификация:** Изучите 4 типа сообщений:
    * Request: `{"jsonrpc":"2.0","method":"add","params":[1,2],"id":1}`
    * Response success: `{"jsonrpc":"2.0","result":3,"id":1}`
    * Response error: `{"jsonrpc":"2.0","error":{"code":-32601,"message":"Method not found"},"id":1}`
    * Notification (без id, без response)

1762. **Базовый JSON-RPC server:** Реализуйте endpoint `/rpc`, который парсит request, диспатчит по method name, возвращает response.

1763. **Standard error codes:** Используйте standard codes: `-32700` Parse error, `-32600` Invalid Request, `-32601` Method not found, `-32602` Invalid params, `-32603` Internal error.

1764. **Batch requests:** Поддерживайте batch: `[req1, req2, req3]` → `[resp1, resp2, resp3]`. Responses могут приходить в любом порядке (server может обрабатывать параллельно).

1765. **Batch ordering guarantee:** Для use cases, где порядок важен, гарантируйте in-order responses или документируйте, что порядок не гарантирован.

1766. **Method registration через reflection:** Используйте reflect для автоматической регистрации Go-методов как JSON-RPC методов (с валидацией signatures).

1767. **Code-generated dispatcher:** Альтернатива reflection — кодогенерация type-safe dispatcher из Go интерфейса (быстрее, type-safe).

1768. **Named vs positional params:** Поддерживайте оба варианта: `{"params":{"a":1,"b":2}}` и `{"params":[1,2]}`. Spec разрешает оба.

1769. **Notifications (без response):** Реализуйте обработку notifications (без `id` field). Сервер не должен отправлять response, даже при ошибке.

1770. **Middleware chain:** Реализуйте middleware для JSON-RPC: logging, auth, rate limiting, request validation — по аналогии с HTTP middleware.

1771. **Custom error types:** Расширьте error object полем `data` для machine-readable деталей: `{"code":-32000,"message":"validation failed","data":{"field":"email","reason":"invalid"}}`.

1772. **JSON-RPC over WebSocket:** Используйте JSON-RPC поверх WebSocket для bidirectional RPC (client и server оба могут инициировать calls). Это основа LSP.

1773. **JSON-RPC client library:** Напишите type-safe Go client с code-generated методами из JSON schema или OpenRPC spec.

1774. **OpenRPC specification:** Изучите OpenRPC (аналог OpenAPI для JSON-RPC). Генерируйте documentation и clients из spec.

1775. **JSON-RPC vs REST vs gRPC:**
    * JSON-RPC: simple, one endpoint, batch support
    * REST: resource-oriented, HTTP semantics, cacheable
    * gRPC: typed, streaming, high-performance
    JSON-RPC идеален, когда у вас много "действий", а не "ресурсов".

### Тема 167: gRPC-Web и Connect
*gRPC-Web решает проблему: браузеры не поддерживают full HTTP/2 streaming, необходимый для gRPC.*

1776. **Проблема gRPC в браузерах:** Изучите, почему чистый gRPC не работает из браузера (нет доступа к HTTP/2 trailers, нет client streaming без XHR/fetch limitations).

1777. **Envoy gRPC-Web proxy:** Настройте Envoy как proxy между браузером (HTTP/1.1 + gRPC-Web format) и backend gRPC сервером (HTTP/2).

1778. **Connect-go (современный стандарт):** Используйте `connectrpc.com/connect` — альтернатива gRPC, которая:
    * Работает в браузерах без proxy
    * Поддерживает Protobuf, JSON, text форматы
    * Совместима с gRPC clients
    * Использует standard library `net/http`

1779. **Connect handler:** Реализуйте handler через `connect.NewUnaryHandler` и подключите к стандартному `http.ServeMux`.

1780. **Connect streaming:** Используйте `connect.StreamingHandlerFunc` для server/client/bidirectional streaming, который работает в браузерах через multiple HTTP requests.

1781. **Connect code generation:** Используйте `protoc-gen-connect-go` и `protoc-gen-connect-es` (для TypeScript) для type-safe clients.

1782. **Connect vs gRPC-Web:** Connect не требует Envoy proxy, поддерживает JSON out-of-the-box, более идиоматичен для Go. Предпочитайте Connect для новых проектов.

1783. **CORS для Connect:** Настройте CORS middleware для Connect endpoints: `connectcors.New()` с proper allowed headers (`Connect-Protocol-Version`, `Content-Type`).

1784. **Connect interceptors:** Используйте interceptors для auth, logging, metrics — аналог gRPC interceptors.

1785. **Connect error handling:** Используйте `connect.NewError(codes.NotFound, err)` для standard gRPC-style errors, которые сериализуются и в JSON, и в Protobuf.

1786. **Connect client в браузере:** Сгенерируйте TypeScript client через `protoc-gen-connect-es`, используйте из React/Vue/Svelte приложения.

1787. **Connect streaming в браузере:** Реализуйте ChatGPT-style streaming response через Connect server streaming — работает без WebSocket/SSE.

1788. **Connect + TanStack Query:** Интегрируйте Connect client с TanStack Query (React Query) для caching, retries, optimistic updates.

1789. **Connect vs tRPC:**
    * Connect: Protobuf-first, multi-language, code-gen из .proto
    * tRPC: TypeScript-first, end-to-end type safety без code-gen
    Connect для multi-language backends, tRPC для full-stack TypeScript.

1790. **Migration gRPC → Connect:** Переведите существующий gRPC сервер на Connect, сохранив compatibility с existing gRPC clients (Connect умеет говорить по gRPC protocol).

### Тема 168: Сравнение и выбор технологий
1791. **Матрица выбора real-time технологий:**
    | Use Case | Технология |
    |----------|-----------|
    | Server→Client updates, auto-reconnect нужен | SSE |
    | Bidirectional чат, игры | WebSocket |
    | Streaming LLM tokens | SSE или Connect streaming |
    | Server→Client, corporate proxies | SSE |
    | Bidirectional, binary data | WebSocket |
    | Server→Client с multiplexing (HTTP/2) | SSE over HTTP/2 |

1792. **Матрица выбора API стилей:**
    | Use Case | Стиль |
    |----------|-------|
    | CRUD ресурсы, public API | REST |
    | Flexible queries, mobile clients | GraphQL |
    | Межсервисное общение, streaming | gRPC/Connect |
    | Browser → backend, type-safe | Connect |
    | Много "действий", batch calls | JSON-RPC |
    | Event notification third parties | Webhooks |

1793. **Webhooks vs Polling vs SSE:**
    * Webhooks: server-initiated, требует public endpoint у клиента
    * Polling: simple, но wasteful
    * SSE: client-initiated persistent connection
    Используйте webhooks для third-party integrations, SSE для own-client real-time.

1794. **Cost comparison:**
    * Webhooks: outbound HTTP calls, cheap per delivery
    * SSE: persistent connection, требует connection tracking
    * WebSocket: persistent, bidirectional, более сложный state
    SSE/WebSocket требуют больше server resources per client.

1795. **Observability across protocols:** Унифицируйте трейсинг: каждый webhook delivery, SSE event, JSON-RPC call, Connect request — это OpenTelemetry span с proper attributes.

### 💡 Золотые правила продвинутого API-дизайна:

#### Webhooks:
1. **Webhooks — это at-least-once delivery.** Всегда документируйте это. Клиенты обязаны реализовать idempotency через `event.id`. Одна и та же доставка может прийти дважды.

2. **HMAC signatures обязательны.** Без подписи любой может подделать webhook и выполнить действия от имени вашей платформы. Используйте HMAC-SHA256 + timestamp + constant-time comparison.

3. **Exponential backoff + jitter — не опция, а must.** Без jitter массовый сбой у крупного клиента DoS-нет его сервера retries от всех ваших webhook'ов одновременно.

4. **Никогда не доставляйте webhooks синхронно.** Всегда через background worker queue. Slow endpoint не должен блокировать весь delivery pipeline.

5. **Dead letter queue и manual retry.** После N failures отключайте endpoint и алертите клиента. Дайте ему UI для просмотра failed deliveries и manual retry.

#### SSE:
1. **`http.Flusher` обязателен.** Без `flusher.Flush()` reverse proxies и Go-буферы задержат события на секунды/минуты.

2. **`Last-Event-ID` для seamless reconnect.** Это встроенная фича браузерного `EventSource` API. Ваш сервер должен уметь resume с указанного ID.

3. **Keep-alive через комментарии.** Отправляйте `: ping\n\n` каждые 15-30 секунд, иначе proxies с idle timeout (часто 60s) закроют connection.

4. **SSE > WebSocket для server→client streaming.** SSE автоматически реконнектится, работает через corporate proxies, не требует отдельного protocol handling.

5. **Backpressure per client.** Медленный клиент не должен накапливать гигабайты буферизованных событий. При overflow — disconnect и force reconnect.

#### JSON-RPC:
1. **Batch support — ключевая фича.** Один HTTP request может нести 100 RPC calls. Это решает N+1 проблему и снижает latency.

2. **Notifications для fire-and-forget.** Если response не нужен (telemetry, analytics), отправляйте без `id` field — сервер не будет тратить ресурсы на response.

3. **Standard error codes соблюдайте.** `-32700`, `-32600`, `-32601`, `-32602`, `-32603` — это universal language для JSON-RPC clients.

#### gRPC-Web / Connect:
1. **Connect > gRPC-Web для новых проектов.** Connect не требует Envoy proxy, поддерживает JSON, более идиоматичен. Используйте `connectrpc.com/connect`.

2. **Connect streaming заменяет SSE во многих случаях.** Server streaming через Connect работает в браузерах без SSE/WebSocket, с Protobuf serialization.

3. **Protobuf-first подход.** Определяйте API в `.proto` файлах, генерируйте type-safe clients для всех языков. Это single source of truth.

#### Общие правила:
1. **Observability across protocols.** Один request может пройти через REST → gRPC → webhook delivery. Сквозной `trace_id` через все protocols — это must have для debugging.

2. **Right tool for the job:**
   - Public API, ресурсы → REST
   - Mobile, flexible queries → GraphQL  
   - Межсервисное → gRPC/Connect
   - Real-time server→client → SSE
   - Third-party events → Webhooks
   - Bidirectional chat → WebSocket

3. **CORS и preflight — боль multi-protocol API.** Connect требует specific allowed headers. SSE не требует preflight. WebSocket использует own handshake. Настраивайте per-protocol.

4. **Authentication единый, protocols разные.** JWT/OAuth2 token должен работать на всех protocols. Middleware-слой, который извлекает identity независимо от protocol.

5. **Rate limiting per client, не per protocol.** Клиент с 1000 RPS лимитом не должен иметь 1000 RPS на REST + 1000 на Connect + 1000 на SSE. Unified quota across protocols.

6. **Documentation auto-generation.** OpenAPI для REST, GraphQL introspection, Protobuf reflection для Connect/gRPC. Hand-written docs устаревают мгновенно.

7. **SDK generation из единой schema.** Один OpenAPI/Protobuf/GraphQL spec → auto-generated clients для TypeScript, Python, Go, Java, Swift, Kotlin. Это force multiplier для adoption.

8. **Backward compatibility — закон.** Public API не должен ломать existing clients. Deprecation period минимум 6-12 месяцев. Versioning через URL (`/v2/`) или headers.

9. **Test all protocols в CI.** Интеграционные тесты должны покрывать каждый protocol: REST endpoint, GraphQL query, Connect call, webhook delivery, SSE event, JSON-RPC batch.

10. **Performance budgets per protocol.** SSE connection overhead ~10KB memory, WebSocket ~20KB, REST request ~1KB. При 1M concurrent connections это разница в 10GB vs 20GB vs 1GB.
