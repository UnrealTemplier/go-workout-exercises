Архитектура API не ограничивается стандартным REST (запрос-ответ). Когда системы усложняются, возникает потребность в асинхронных уведомлениях, потоковой передаче данных в реальном времени и оптимизированных протоколах вызова удаленных процедур.

Продолжаем наш марафон! Впереди **25 упражнений (с 776 по 800)**, где мы спроектируем систему вебхуков уровня Stripe, настроим SSE (Server-Sent Events) и разберем альтернативы gRPC.

### Блок 75. Webhooks: Проектирование платформы обратных вызовов (776–785)
Вебхуки — это когда *твой* сервер делает HTTP-запросы на сервер *клиента* при наступлении события. Звучит просто, но в продакшене это сущий ад из-за мертвых клиентов, таймаутов и безопасности.

776. **Базовый Webhook Dispatcher:** Напиши воркер (горутину), который читает события из канала (например, `OrderPaid`), сериализует их в JSON и делает `http.Post` на URL, сохраненный в настройках клиента.
777. **Безопасность (Подпись HMAC):** Твой клиент должен знать, что вебхук пришел именно от тебя, а не от хакера. Перед отправкой вычисли HMAC-SHA256 подпись от тела (body) JSON, используя уникальный `secret_key` клиента. Добавь эту подпись в HTTP-заголовок `X-Signature`.
778. **Защита от Replay Attacks (Атак повторного воспроизведения):** Хакер перехватил подписанный вебхук и шлет его клиенту снова и снова. Добавь в генерируемый JSON (или заголовок `X-Timestamp`) текущее время (Unix timestamp). Подписывай конкатенацию `timestamp.body`. Клиент сможет отклонять вебхуки, которые старше 5 минут.
779. **Receiver (Пишем надежного получателя):** Напиши HTTP-хендлер для приема вебхуков. Внутри него:
    * Проверь `X-Timestamp`.
    * Вычисли ожидаемый HMAC и сравни его с `X-Signature` через безопасное сравнение `subtle.ConstantTimeCompare()`.
780. **Жесткие таймауты:** Клиентский сервер завис и не закрывает соединение. Если твой воркер будет висеть в ожидании, у тебя кончатся горутины. Оберни отправку вебхука в `context.WithTimeout(ctx, 3*time.Second)`. Никогда не жди клиента долго!
781. **Экспоненциальный Backoff (Ретраи):** Клиент ответил 503 или отвалился по таймауту. Напиши логику повторных попыток. Попытайся отправить вебхук 4 раза с паузами: 2 сек, 4 сек, 8 сек, 16 сек.
782. **Full Jitter (Предотвращение шторма):** Если упал крупный клиент, у тебя скопятся тысячи вебхуков. Когда клиент оживет, твои ретраи ударят по нему одновременно, снова положив сервер (Thundering Herd). Модифицируй паузу из упр. 781: добавляй к каждому интервалу случайный шум (Jitter). Например, вместо строго 4 секунд жди от 2 до 4 секунд (`random(0, delay/2) + delay/2`).
783. **Пул воркеров для вебхуков:** Не создавай новую горутину на каждый вебхук, иначе всплеск событий выест всю память. Напиши Worker Pool на 100 воркеров. Они должны читать задачи из очереди (канала) и выполнять логику с ретраями.
784. **Dead Letter Queue (DLQ):** Если вебхук не доставился после всех попыток, не выкидывай его. Сохрани его в таблицу БД `failed_webhooks` со статусом `exhausted`. Напиши админский эндпоинт, который позволяет нажать кнопку и переотправить протухший вебхук вручную.
785. **Идемпотентность Получателя (Receiver Idempotency):** Твой Dispatcher может отправить один и тот же вебхук дважды (ошибка сети при получении 200 OK). На стороне Получателя (Receiver) добавь проверку по `Webhook-ID` в базу данных. Убедись, что бизнес-логика (например, зачисление бонусов) отрабатывает только один раз.

### Блок 76. Server-Sent Events (SSE): Однонаправленный Real-Time (786–792)
WebSockets — это двунаправленный, сложный и тяжелый протокол. Если тебе нужно просто стримить обновления клиенту (котировки акций, статус доставки, ответы ChatGPT), SSE — идеальный и легкий выбор поверх стандартного HTTP.

786. **Базовый SSE Хендлер:** Напиши HTTP-хендлер. Установи три обязательных заголовка: `Content-Type: text/event-stream`, `Cache-Control: no-cache` и `Connection: keep-alive`. Отправь клиенту строку `data: Hello\n\n` (двойной перенос строки обязателен в стандарте SSE!).
787. **Современный `http.Flusher` (Go 1.20+):** HTTP-серверы буферизируют ответ. Клиент не увидит твой текст, пока буфер не заполнится. Используй современный механизм (появился в Go 1.20): `rc := http.ResponseController(w)` и вызови `rc.Flush()`. Это немедленно вытолкнет данные в сеть. *(В старом Go использовалось приведение `w.(http.Flusher)`).*
788. **Бесконечный стрим:** В хендлере запусти цикл `for`. Раз в секунду отправляй `data: {"time": "..."}\n\n` и делай `Flush()`. Как выйти из цикла? Добавь `select` и слушай канал `r.Context().Done()`. Когда клиент закроет вкладку браузера, сервер корректно завершит цикл.
789. **Сложные события (IDs и Events):** Стандарт SSE позволяет структурировать сообщения. Отправь событие с конкретным типом:
    ```
    id: 101
    event: user_joined
    data: {"name": "Ivan"}
    \n\n
    ```
790. **SSE Брокер (Pub/Sub):** Спроектируй структуру `Broker`. В ней: канал для новых клиентов (подключение), канал для отключений, мапа активных клиентов `map[chan []byte]bool` и метод `Broadcast(msg)`. Когда срабатывает Broadcast, брокер должен раздать сообщение во все каналы клиентов.
791. **Дроп медленных клиентов:** В брокере из упр. 790 что будет, если у одного клиента завис интернет, и его канал переполнился? Твой цикл `Broadcast` заблокируется! Сделай запись в канал клиента неблокирующей (через `select` + `default`). Если канал полон — принудительно отключай клиента (закрывай канал) и освобождай ресурсы.
792. **Тестовый JS-клиент:** Напиши простой HTML-файл. Используй встроенный в браузеры объект `new EventSource('http://localhost:8080/stream')`. Добавь обработчик `.onmessage` и выведи прилетающие из Go данные в `console.log`. Убедись, что браузер сам (автоматически!) переподключается, если ты перезапустишь Go-сервер.

### Блок 77. JSON-RPC 2.0 и gRPC-Web (793–800)
Изучаем альтернативы стандартному REST и классическому gRPC.

793. **Основы JSON-RPC 2.0:** Изучи спецификацию. Это протокол поверх HTTP (или WebSocket), где запрос и ответ всегда одного формата. Напиши HTTP-хендлер, который парсит JSON:
    `{"jsonrpc": "2.0", "method": "math.sum", "params": [42, 23], "id": 1}`. Вызови нужную функцию, сложи числа и верни стандартный ответ: `{"jsonrpc": "2.0", "result": 65, "id": 1}`.
794. **Обработка ошибок JSON-RPC:** Если метода не существует, верни объект `{"jsonrpc": "2.0", "error": {"code": -32601, "message": "Method not found"}, "id": 1}`. Реализуй обработку некорректных параметров (код -32602) и внутренних ошибок сервера.
795. **Пакетные запросы (Batching):** Уникальная фича JSON-RPC. Если клиент присылает массив объектов-запросов, сервер должен выполнить их (можно конкурентно) и вернуть массив ответов в одном HTTP-ответе. Реализуй этот функционал.
796. **JSON-RPC поверх WebSockets:** Сделай WebSocket-соединение. Внутри соединения обменивайтесь сообщениями строго в формате JSON-RPC 2.0. Это идеальный вариант для игр или тяжелых SPA, где нужен двунаправленный RPC без сложной настройки gRPC.
797. **Проблема gRPC-Web (Теория):** Стандартный gRPC использует HTTP/2 Trailers (заголовки в конце тела ответа) для передачи статуса (ошибок). Браузеры (Fetch API/XHR) не дают доступа к Trailers. Поэтому вызывать чистый gRPC из JS нельзя. Осознай эту архитектурную боль.
798. **Envoy Proxy:** Классическое решение проблемы 797. Подними gRPC сервер на Go (на порту 50051). Подними Envoy Proxy в Docker. Настрой Envoy так, чтобы он слушал порт 8080, принимал запросы `application/grpc-web`, транслировал их в нормальный gRPC и отдавал твоему Go-серверу.
799. **In-process gRPC-Web (Без Envoy):** Использовать Envoy не всегда удобно (лишний компонент). Установи библиотеку `github.com/improbable-eng/grpc-web/go/grpcweb`. Оберни свой стандартный `grpc.Server` в `grpcweb.WrapServer`. Теперь твой Go-сервер сам может принимать gRPC-Web запросы прямо от браузера на стандартном HTTP порту!
800. **Bidirectional Streaming Fallback:** В gRPC-Web из браузера не работает двунаправленный (Bidirectional) стриминг, а клиентский стриминг поддерживается очень ограниченно. Перепиши свой `.proto` файл так, чтобы использовать только Unary (запрос-ответ) и Server Streaming. Сгенерируй TS/JS код через `protoc-gen-grpc-web` и сделай успешный вызов из браузера к твоему Go-серверу из упр. 799.
