## Блок 18. Webhooks

### Уровень 1. Базовая инфраструктура
217. **Базовая отправка и статусы.** Реализуйте сервис, который отправляет HTTP POST с JSON-payload на URL подписчика. Обработайте статусы: 2xx — успех, 4xx — permanent failure (не ретраить), 5xx/timeout — temporary failure (ретрай). Объясните, почему 410 Gone означает «отпишите подписчика навсегда».
218. **HMAC-SHA256 подпись.** Реализуйте подпись на стороне отправителя: `HMAC-SHA256(secret, timestamp + "." + body)`, заголовок `X-Signature`. На приёмнике — проверка с `subtle.ConstantTimeCompare`. Объясните, зачем добавлять timestamp в подпись (replay protection) и как обрабатывать clock skew (±5 минут).
219. **Idempotency-Key.** Генерируйте `Idempotency-Key` (UUID v4) для каждого события. Приёмник хранит обработанные ключи в Redis с TTL 24 часа. При повторном получении — возвращает 200, но не обрабатывает. Объясните разницу между idempotency на уровне HTTP и на уровне бизнес-логики.

### Уровень 2. Надёжная доставка
220. **Exponential Backoff.** Реализуйте ретраи с интервалами: 1с, 2с, 4с, 8с, 16с (макс 5 попыток). Храните `attempt_count` и `next_retry_at` в БД. Напишите worker, который выбирает failed webhooks по `next_retry_at <= NOW()`. Объясните, почему max backoff ограничен (например, 1 час).
221. **Jitter.** Добавьте к backoff случайную составляющую: Full Jitter (`random(0, base)`) или Equal Jitter (`base/2 + random(0, base/2)`). Сымитируйте 1000 одновременных failed webhooks и покажите, что pure exponential создаёт thundering herd, а jitter — распределяет нагрузку.
222. **Circuit Breaker.** Внедрите circuit breaker (ручная реализация или `github.com/sony/gobreaker`) перед отправкой: при 5 consecutive 5xx/timeout → состояние Open (30 сек), затем Half-Open (1 пробный запрос). Объясните, как это защищает и ваш сервис, и подписчика от DDoS.

### Уровень 3. Управление подписками и безопасность
223. **Delivery Log.** Реализуйте таблицу `webhook_deliveries`: `id`, `subscription_id`, `endpoint`, `event_type`, `payload_hash`, `signature`, `attempts[]` (JSONB), `http_status`, `final_status` (delivered/failed). Напишите dashboard-запрос: failed за последние 24 часа с группировкой по endpoint.
224. **Subscription Management.** Реализуйте CRUD подписок: `endpoint` (URL), `secret` (генерируется автоматически), `event_types[]` (whitelist), `active` (bool). Добавьте валидацию URL: запрет private ranges (SSRF-защита через resolve IP), обязательный HTTPS в production. Объясните, почему wildcard `event_types: ["*"]` — антипаттерн.
225. **Batch Webhooks.** Реализуйте batch-режим: накапливайте события 500 мс или до 100 штук, отправляйте одним POST с массивом payloads. Приёмник обрабатывает атомарно (все или ни одного) или поштучно с индивидуальными статусами в ответе. Объясните throughput/latency компромисс.

### Уровень 4. Архитектура и масштабирование
226. **Webhook Worker Queue.** Реализуйте полный pipeline: `event` → Redis Stream/RabbitMQ → worker pool (N goroutine) → sender → retry scheduler (dead-letter queue при исчерпании попыток). Объясните at-least-once delivery: почему acknowledgment происходит только после HTTP 2xx, и как избежать дублирования при ребалансировке воркеров.

## Блок 19. Server-Sent Events (SSE)

### Уровень 1. Протокол и базовые паттерны
227. **Базовый SSE endpoint.** Реализуйте HTTP handler с `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`. Используйте `http.Flusher` для принудительной отправки. Пишите в формате `data: {"msg":"hello"}\n\n`. Объясните, почему два `\n` — разделитель событий.
228. **Event ID и возобновление.** Генерируйте `id: <uuid>` для каждого события. Клиент при reconnect шлёт заголовок `Last-Event-ID`. Сервер читает его и отправляет только события с `id` больше последнего (храните буфер последних N событий в памяти или Redis). Объясните, как это даёт exactly-once perception для клиента.
229. **Named Events.** Используйте `event: user_update\ndata: {...}` для типизации событий. На клиенте (JavaScript) используйте `eventSource.addEventListener('user_update', ...)`. Объясните, почему `event: message` (default) и кастомные имена event помогают разделить потоки данных.

### Уровень 2. Управление соединениями
230. **Connection Hub.** Реализуйте Hub: `map[clientID]chan Event`, mutex/RWMutex для безопасности. Каждый клиент — отдельная goroutine, читающая из личного канала и пишущая в `http.ResponseWriter`. При disconnect (ошибка write или `http.CloseNotifier`) — удаление из hub. Объясните, почему `sync.Map` может быть альтернативой при высокой конкуренции.
231. **Broadcast.** Реализуйте broadcast: центральный `chan Event` (или `pub/sub` в Redis), все клиенты подписаны. При событии — fan-out в каждый клиентский канал. Объясните, почему неблокирующая отправка (`select` с `default`) предотвращает slow client от блокировки всего hub.
232. **Heartbeat / Keep-Alive.** Отправляйте `:heartbeat\n\n` (SSE comment) каждые 15 секунд. Объясните, как это предотвращает разрыв соединения nginx/proxy (`proxy_read_timeout`, `load_balancer idle timeout`). Покажите, что комментарии не вызывают `onmessage` в браузере.

### Уровень 3. Продвинутые сценарии
233. **Multiplexed SSE.** Один endpoint `/events`, но клиент подписывается на topics через query: `?topics=orders,alerts`. Сервер фильтрует события: отправляет клиенту только те, что совпадают с подпиской. Реализуйте topic-based routing внутри Hub. Объясните, почему фильтрация на сервере лучше, чем отправка всего и фильтрация на клиенте.
234. **Graceful Shutdown.** При получении `SIGTERM`: (1) закрыть listener для новых HTTP-соединений, (2) дождаться отправки pending events всем клиентам (context с timeout), (3) закрыть существующие SSE-соединения корректно. Объясните, почему `http.Server.Shutdown` не достаточен для long-lived SSE-коннекшнов без дополнительной логики.
235. **Rate Limit per Connection.** Реализуйте token bucket для каждого SSE-клиента: максимум 100 событий/сек. При превышении — дроп (`select` с `default`) или буферизация с ограниченным размером (drop oldest). Объясните, как slow consumer может вызвать OOM без backpressure.

### Уровень 4. Интеграция и сравнение
236. **SSE vs WebSocket.** Реализуйте тот же функционал (broadcast с named events) через WebSocket (`gorilla/websocket`). Сравните: SSE — однонаправленный, текстовый, автоматический reconnect, работает через HTTP/1.1; WebSocket — дуплексный, binary, требует ручного reconnect. Объясните, когда SSE предпочтительнее (live dashboards, notifications), а когда WebSocket (чаты, игры).

## Блок 20. JSON-RPC 2.0

### Уровень 1. Базовый сервер и клиент
237. **Базовый сервер.** Реализуйте HTTP handler, парсящий JSON-RPC 2.0 Request: `{"jsonrpc":"2.0","method":"add","params":[1,2],"id":"uuid"}`. Dispatch по `method` через `map[string]func`. Возвращайте Response: `{"jsonrpc":"2.0","result":3,"id":"uuid"}`. Объясните, почему `jsonrpc: "2.0"` — обязательное поле.
238. **Method Registry.** Реализуйте type-safe registry: `Register(name string, fn any)`, где `fn` — функция с сигнатурой `func(ctx, T) (R, error)`. Используйте `reflect` для вызова и валидации аргументов. Объясните компромисс: reflection vs code generation (как в `go-jsonrpc` от Filecoin).
239. **Notifications.** Обработайте Request без поля `id`: это notification, не требует ответа (HTTP 204 или пустое тело). Реализуйте fire-and-forget метод `logEvent`. Объясните, почему notification не может иметь `error` в ответе — и как обрабатывать failures на стороне сервера (async logging).

### Уровень 2. Batch и ошибки
240. **Batch Requests.** Реализуйте обработку массива запросов: `[]Request`. Выполняйте параллельно (goroutine per request), сохраняйте порядок `id` в ответе. Обработайте partial failure: если один запрос падает, остальные возвращают результат. Объясните, почему пустой batch (`[]`) — ошибка `-32600`.
241. **Стандартные коды ошибок.** Реализуйте иерархию ошибок: `ParseError` (-32700), `InvalidRequest` (-32600), `MethodNotFound` (-32601), `InvalidParams` (-32602), `InternalError` (-32603). Добавьте custom errors: `-32000` Application Error. Объясните, почему `error.data` — полезно для деталей, но опасно для утечки stack trace.
242. **Клиент.** Реализуйте JSON-RPC клиент: генерирует `id` (UUID), отправляет POST, парсит Response. Обрабатывайте: HTTP 200 с `error` в теле (это валидный JSON-RPC error, не HTTP error), timeout, HTTP 500. Объясните, почему `id` в ответе должен совпадать с запросом (out-of-order в HTTP/1.1 pipelining).

### Уровень 3. Middleware и валидация
243. **Middleware stack.** Реализуйте onion-мiddleware для JSON-RPC: Logging (method, duration, id), Metrics (Prometheus counters), Recovery (panic → `-32603 InternalError`). Объясните, как middleware работает с batch (один лог на batch или per-request).
244. **Валидация параметров.** Парсите `params` в struct через `json.Unmarshal` + `go-playground/validator`. Возвращайте `-32602 InvalidParams` с детализацией (какое поле невалидно). Объясните, почему `json.RawMessage` + delayed unmarshal — лучше, чем `map[string]any` для типобезопасности.
245. **Bidirectional JSON-RPC.** Реализуйте duplex channel через WebSocket: клиент и сервер могут отправлять notifications друг другу. Используйте `jsonrpc2` поверх `gorilla/websocket`. Объясните, как `id` помогает коррелировать request-response в дуплексном потоке.

### Уровень 4. Транспорт и производительность
246. **HTTP/1.1 vs HTTP/2.** Объясните проблемы JSON-RPC over HTTP/1.1: head-of-line blocking, нет multiplexing. Реализуйте клиент с connection pool (`http.Transport.MaxConnsPerHost`, `DisableKeepAlives: false`). Сравните latency batch-запросов через HTTP/1.1 и HTTP/2 (gRPC использует HTTP/2 именно поэтому). Объясните, почему JSON-RPC 2.0 спецификация транспорт-агностична.

## Блок 21. gRPC-Web

### Уровень 1. Базовая настройка и unary
247. **Unary gRPC-Web.** Настройте сервер с `github.com/improbable-eng/grpc-web` или `connectrpc.com/connect`. Оберните gRPC-server в `grpcweb.WrapServer`. Реализуйте простой unary RPC (например, `GetUser`). Покажите, как браузерный fetch с `Content-Type: application/grpc-web` вызывает метод. Объясните, почему нативный gRPC не работает в браузере напрямую (HTTP/2 trailers).
248. **Протокольные отличия.** Объясните формат gRPC-Web: при HTTP/1.1 payload может быть base64-encoded, `Content-Type: application/grpc-web` (не `application/grpc`), trailers передаются либо в конце body (gRPC-Web), либо через headers. Напишите дешифратор фреймов: 1 byte flag (compressed/trailer) + 4 bytes length + payload.
249. **Code Generation.** Используйте `protoc` с `protoc-gen-grpc-web` для генерации TypeScript/JavaScript клиента и `protoc-gen-go` для сервера. Соберите pipeline: `.proto` → `.pb.go` + `.grpc-web.js`. Объясните, зачем нужен proxy (Envoy/improbable) между браузером и gRPC-сервером.

### Уровень 2. Стриминг и метаданные
250. **Server Streaming.** Реализуйте gRPC server streaming RPC (например, `StreamNotifications`). Покажите, как gRPC-Web proxy преобразует HTTP/2 streaming trailers в chunked HTTP/1.1 ответ. Объясните, почему client streaming в gRPC-Web ограничен (нужен HTTP/2 или duplex emulation).
251. **Metadata.** Передайте metadata из браузера: custom headers (`X-Request-ID`, `Authorization`). На сервере извлеките через `metadata.FromIncomingContext(ctx)`. Объясните, как CORS preflight обрабатывает custom headers, и почему `Access-Control-Allow-Headers` должен включать `X-Grpc-Web` и `X-User-Agent`.
252. **Error Handling.** Реализуйте mapping gRPC status codes → HTTP-совместимый ответ. В JavaScript клиенте обработайте `grpc.web.Error` с `code` и `message`. Объясните, почему gRPC-Web не использует HTTP status codes напрямую (всё 200 OK, ошибка в body).

### Уровень 3. Инфраструктура и безопасность
253. **CORS.** Настройте CORS для gRPC-Web: `Access-Control-Allow-Origin` (whitelist), `Access-Control-Allow-Methods: POST, OPTIONS`, `Access-Control-Allow-Headers` (content-type, x-grpc-web, authorization). Реализуйте preflight handler. Объясните, почему `*` с `Allow-Credentials: true` — уязвимость.
254. **Interceptors.** Реализуйте gRPC interceptors (unary): Logging (method, duration), Auth (JWT из metadata), Rate Limiting. Объясните разницу между unary interceptor и stream interceptor. Покажите, как interceptor в Go — это higher-order function, оборачивающая `UnaryHandler`.
255. **Компрессия.** Настройте gzip на gRPC-Web proxy (Envoy) или через `grpc.UseCompressor(gzip.Name)` на сервере. Объясните, что gRPC-Web не поддерживает per-message compression negotiation как нативный gRPC (HTTP/2 SETTINGS), поэтому compression обычно на уровне HTTP (Content-Encoding).

### Уровень 4. Production-архитектура
256. **Production Setup.** Напишите конфигурацию Envoy proxy для gRPC-Web: listener → `envoy.filters.http.grpc_web` → cluster (gRPC backend). Добавьте TLS termination, load balancing (round_robin), health checks (`/grpc.health.v1.Health/Check`). Сравните с `connectrpc` (Buf), который устраняет необходимость proxy, генерируя HTTP/1.1-совместимый API напрямую. Объясните, когда gRPC-Web всё ещё нужен (совместимость с существующими protobuf-сервисами), а когда Connect — предпочтительнее.

## Как встроить в общий план обучения

**Рекомендуемый порядок прохождения:**

1. **Блок 18 (Webhooks)** — начните после Блока 13 (AppSec), так как Webhooks напрямую используют HMAC из Блока 10 и защиту от SSRF из Блока 13. Понимание retry/backoff требует знаний о concurrency из Блока 1 (GMP).
2. **Блок 19 (SSE)** — проходите после Webhooks, так как SSE — это тот же HTTP, но с long-lived соединениями. Знание `http.Flusher` и `CloseNotifier` связывается с `netpoller` и `epoll` из Блока 6.
3. **Блок 20 (JSON-RPC 2.0)** — после SSE, так как JSON-RPC часто используется как альтернатива REST для внутренних сервисов. Batch processing и reflection требуют знаний из Блока 7 (reflect).
4. **Блок 21 (gRPC-Web)** — финальный блок, требует понимания HTTP/2, protobuf, CORS и proxy-архитектуры. Знание `cgo` (Блок 5) не требуется напрямую, но понимание транспортных протоколов из Блока 6 (syscall, `epoll`) помогает осознать, почему gRPC использует HTTP/2.

**Ключевые инструменты и переменные для тренировки:**
```bash
# Для Webhooks
ngrok http 8080  # публичный endpoint для тестирования webhook receiver
curl -X POST -H "X-Signature: ..." -d '{"event":"test"}' https://your-ngrok/webhook

# Для SSE
curl -N -H "Accept: text/event-stream" http://localhost:8080/events
# Или в браузере: new EventSource('/events')

# Для JSON-RPC
curl -X POST -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","method":"add","params":[1,2],"id":"1"}' \
  http://localhost:8080/rpc

# Для gRPC-Web
protoc --go_out=. --go-grpc_out=. --grpc-web_out=import_style=typescript,mode=grpcwebtext:. service.proto
# Envoy config test: envoy -c envoy.yaml --mode validate
```

**Что фиксировать в результатах:**
- Для Webhooks: sequence-диаграмма (event → queue → worker → HTTP POST → retry → DLQ), таблица retry-политик.
- Для SSE: график количества открытых соединений (`netstat`/`ss`), демонстрация reconnect с `Last-Event-ID`.
- Для JSON-RPC: middleware chain diagram, пример batch request/response с 10 параллельными методами.
- Для gRPC-Web: архитектурная схема (Browser → Envoy → gRPC Server), сравнение latency unary vs streaming.
