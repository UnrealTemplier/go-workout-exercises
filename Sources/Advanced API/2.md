### 21. Продвинутое проектирование API (Webhooks, SSE, JSON-RPC, gRPC-Web)

#### 21.1 Webhooks: безопасность и надёжная доставка
676. **Проектирование отправителя webhook с HMAC-подписью.** Реализуйте HTTP-клиент, который отправляет webhook с JSON-телом. Подпишите тело с помощью HMAC-SHA256, используя общий секрет. Передайте подпись в заголовке `X-Webhook-Signature`.
677. **Приёмник webhook: проверка подписи и предотвращение replay-атак.** Напишите HTTP-обработчик, который принимает webhook. Проверьте HMAC-подпись, сравните время запроса (`X-Request-Timestamp`) с текущим временем (отклонение не более 5 минут), и сохраните использованный `nonce` в Redis для предотвращения повторов.
678. **Идемпотентность webhook-обработчика.** Приёмник должен быть идемпотентным: используйте уникальный `idempotency-key` из тела или заголовка, чтобы повторная доставка одного и того же события не вызывала дублирования действий. Реализуйте проверку ключа в БД.
679. **Ретраи (повторная отправка) с Exponential Backoff и Jitter.** Если получатель webhook возвращает ошибку 5xx или не отвечает, отправитель должен повторить попытку через 1с, 2с, 4с, 8с, 16с (с jitter ±15%). Реализуйте очередь повторов с ограничением максимального числа попыток.
680. **Dead Letter Queue для не доставленных webhook.** После исчерпания попыток поместите webhook-сообщение в отдельную таблицу БД или Kafka-топик «dead-letters» для ручного анализа и возможности повторной отправки администратором.
681. **Webhook с подписью тела (Signature v2: payload digest).** Модифицируйте подпись, включив в неё HTTP-метод, путь и digest тела (SHA-256), чтобы избежать подделки на уровне прокси.
682. **Массовая рассылка webhook с контролем скорости.** Реализуйте диспетчер, который отправляет webhooks нескольким подписчикам, ограничивая количество одновременных исходящих запросов (rate limiting на уровне горутин через семафор).

#### 21.2 Server-Sent Events (SSE)
683. **Простой SSE-сервер с `http.Flusher`.** Напишите HTTP-обработчик, который устанавливает `Content-Type: text/event-stream`, отправляет комментарий `:ok` каждые 5 секунд и данные события `data: {"time": "..."}` каждые 10 секунд. Используйте `flusher.Flush()`.
684. **Именованные события и `id`.** Расширьте сервер: отправляйте события с полями `event: message`, `id: <порядковый номер>`, `data: ...`. Клиент должен различать типы событий и логировать их.
685. **Клиент SSE на Go.** Реализуйте SSE-клиент, который подключается к серверу, читает поток событий и реконнектится при обрыве, передавая заголовок `Last-Event-Id` для возобновления.
686. **Авторизация SSE-соединения.** Добавьте проверку JWT-токена в query-параметре при установлении SSE-соединения. При невалидном токене возвращайте 401.
687. **Мультиплексирование SSE для разных пользователей.** Реализуйте брокер событий, который хранит соединения в map `userID -> []chan Event`. При появлении события для пользователя отправляйте его во все активные SSE-соединения.
688. **SSE с heartbeat и таймаутами.** Настройте отправку комментария `:heartbeat` каждые 30 секунд, чтобы поддерживать соединение через прокси. На клиенте переподключайтесь, если heartbeat не получен в течение 60 секунд.

#### 21.3 JSON-RPC 2.0
689. **Реализация JSON-RPC 2.0 сервера (HTTP).** Создайте HTTP-обработчик, который принимает JSON-RPC запрос (`method`, `params`, `id`). Реализуйте метод `echo` (возвращает переданную строку). Обработайте `id` – запросы с `id` должны вернуть ответ, без `id` – это уведомление (не отвечать).
690. **Параметры по имени и по позиции.** Поддержите оба варианта: `"params": ["hello"]` и `"params": {"text": "hello"}`. Используйте рефлексию для вызова обработчиков.
691. **Batch-запросы JSON-RPC.** Если приходит массив запросов, обработайте их параллельно и верните массив ответов. Обработайте пустой batch (должен вернуть пустой массив).
692. **Стандартные ошибки JSON-RPC.** Реализуйте возврат ошибок в формате `{"code": -32601, "message": "Method not found"}` для неизвестных методов. При ошибке в обработчике возвращайте код `-32000` с деталями.
693. **JSON-RPC клиент на Go.** Напишите клиент, который формирует запрос с `id`, отправляет HTTP POST и парсит ответ. Поддержите таймаут и обработку ошибок транспорта.
694. **JSON-RPC поверх WebSocket.** Расширьте сервер: принимайте WebSocket-соединения и ожидайте JSON-RPC запросы в каждом сообщении. Ответ отправляйте в то же соединение. Клиент должен отправлять несколько запросов по одному соединению.
695. **Сравнение JSON-RPC и gRPC.** Реализуйте один и тот же простой сервис (калькулятор) через JSON-RPC и через gRPC. Сравните размер передаваемых данных и скорость (бенчмарк).

#### 21.4 gRPC-Web
696. **Настройка gRPC-Web прокси (Envoy или встроенный).** Запустите gRPC-сервер с поддержкой рефлексии. Настройте Envoy для трансляции gRPC-Web запросов в gRPC. Проверьте вызов с помощью `grpcurl`.
697. **Клиент gRPC-Web на Go.** Используйте библиотеку `github.com/improbable-eng/grpc-web` для вызова сервиса через gRPC-Web с Go-клиента (эмулируя браузерное окружение). Отправьте unary запрос и получите ответ.
698. **Server-streaming через gRPC-Web.** Реализуйте серверный стриминг, который отдаёт поток логов. Клиент на gRPC-Web читает поток в браузере (или Go-клиент имитирует) и выводит сообщения по мере получения.
699. **Обработка ошибок gRPC-Web.** Сервер возвращает статус `NotFound`. Убедитесь, что gRPC-Web клиент корректно получает код и сообщение ошибки (с учетом CORS, если необходимо).
700. **Сравнение gRPC-Web и SSE для стриминга данных клиенту.** Реализуйте один и тот же функционал (поток уведомлений) через gRPC-Web server-streaming и через SSE. Сравните задержку первого сообщения и возможность двунаправленности.
