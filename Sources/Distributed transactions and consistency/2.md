### 22. Распределённые транзакции и консистентность (Saga, Outbox/Inbox, Idempotency)

#### 22.1 Saga: Оркестрация и Хореография
701. **Saga Orchestration: центральный координатор.** Реализуйте Saga-оркестратор, который выполняет последовательность шагов (сервисы A, B, C). Каждый шаг — вызов внешнего сервиса (заглушка). При успехе всех шагов транзакция завершается, при ошибке любого шага запускаются компенсационные транзакции в обратном порядке.
702. **Saga Choreography: события как координатор.** Реализуйте ту же бизнес-логику, но без оркестратора: сервис A публикует событие `A.Completed`, сервис B слушает его и выполняет своё действие, публикуя `B.Completed`, и т.д. При ошибке сервис публикует событие `*.Failed`, на которое подписаны компенсационные обработчики.
703. **Компенсационные транзакции (Compensating Actions).** Для каждого шага реализуйте не только прямое действие, но и компенсирующее (например, `ReserveInventory` → `ReleaseInventory`, `ChargePayment` → `RefundPayment`). Покажите, что при сбое на шаге 3 откатываются шаги 2 и 1.
704. **Сага с таймаутами и автоматической компенсацией.** Добавьте в оркестратор тайм-аут для каждого шага. Если сервис не отвечает за заданное время, автоматически запускайте компенсацию. Реализуйте это через `context.WithTimeout` и каналы.
705. **Хранение состояния саги в БД.** Сохраняйте текущий шаг и статус саги в отдельную таблицу `saga_state`. При перезапуске оркестратор должен восстановить незавершённые саги и продолжить или откатить их.
706. **Тестирование саги с симуляцией сбоев.** Напишите интеграционный тест, который намеренно вызывает сбой на одном из шагов и проверяет, что все компенсации выполнились, а состояние системы вернулось к исходному.

#### 22.2 Transactional Outbox и Transactional Inbox
707. **Transactional Outbox: атомарная запись события.** Сервис заказов в одной транзакции БД сохраняет заказ и вставляет запись в таблицу `outbox` (событие `OrderCreated`). Реализуйте это с PostgreSQL, используя `BEGIN/COMMIT`.
708. **Outbox Publisher (ретранслятор событий).** Напишите фоновый процесс (горутина), который читает неотправленные записи из `outbox`, публикует их в брокер (Kafka/RabbitMQ) и помечает как отправленные в БД. Гарантируйте at-least-once семантику.
709. **Outbox с гарантией порядка по агрегату.** Доработайте Outbox: обеспечьте, что события по одному агрегату (например, `order_id`) публикуются строго в том порядке, в котором они были записаны.
710. **Transactional Inbox: идемпотентный приём сообщений.** Сервис-подписчик получает сообщение из брокера, проверяет наличие `message_id` в таблице `inbox`. Если сообщение уже обработано — игнорирует. Если нет — вставляет запись в `inbox` и выполняет бизнес-логику в одной транзакции БД.
711. **Outbox + Inbox сквозная демонстрация.** Реализуйте сценарий: Сервис A записывает событие в Outbox, ретранслятор отправляет в Kafka, Сервис B получает через Inbox, обеспечивая ровно-однократную (effective exactly-once) обработку.
712. **Debezium-style CDC для Outbox (эмуляция).** Вместо ручного ретранслятора, используйте логическую репликацию PostgreSQL (как в упражнениях 673-675), чтобы читать изменения таблицы `outbox` напрямую и отправлять в брокер. Сравните с опросом таблицы по таймеру.

#### 22.3 Middleware для идемпотентности (Idempotency Keys)
713. **Генерация и валидация Idempotency Key на клиенте.** Клиент генерирует уникальный ключ (UUID) и передаёт его в заголовке `Idempotency-Key`. Реализуйте HTTP-middleware на сервере, который проверяет ключ, сохраняет его в Redis с TTL 24 часа и возвращает сохранённый ответ при повторе.
714. **Уникальный constraint на уровне БД для идемпотентности.** Вместо Redis, сохраняйте `idempotency_key` в таблицу БД с уникальным индексом. В middleware выполните вставку ключа в начале обработки. При нарушении уникальности верните ранее сохранённый ответ (или 409 Conflict).
715. **Идемпотентность операций с внешними сервисами.** Доработайте middleware: если запрос уже обработан, но внешний сервис (например, платёжный шлюз) недополучил вызов в первой попытке (сбой после ответа клиенту), реализуйте механизм «допосылки» через фоновую задачу, не дублируя основную операцию.
716. **Идемпотентность в gRPC с перехватчиком.** Реализуйте gRPC-перехватчик (interceptor), который проверяет idempotency key в метаданных запроса и гарантирует идемпотентность вызова.
717. **Идемпотентность для асинхронных операций.** Реализуйте обработку, где операция длительная (статус `processing`), а клиент повторяет запрос с тем же ключом. Сервер должен вернуть статус выполнения, не запуская повторно. При завершении — вернуть результат.
718. **Комбинированная стратегия: Idempotency Key + ETag.** Добавьте условные запросы: клиент отправляет `If-Match` с ETag ресурса. Сервер выполняет операцию только если ресурс не изменился. Реализуйте middleware, проверяющий ETag.
719. **Очистка старых ключей идемпотентности.** Реализуйте фоновую задачу, которая удаляет просроченные idempotency-ключи из БД/Redis, предотвращая бесконечный рост хранилища.
720. **Сквозной тест идемпотентной распределённой транзакции.** Объедините паттерны: клиент → API Gateway (проверка idempotency) → Оркестратор саги (с хранением статуса) → Outbox → Брокер → Inbox сервисов. Проверьте, что повторный запрос с тем же ключом не приводит к дублированию заказа.
