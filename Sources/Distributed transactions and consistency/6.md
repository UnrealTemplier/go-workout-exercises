Ниже представлен новый глубокий блок практических упражнений, посвященных **распределенным транзакциям, паттернам консистентности (Saga, Outbox/Inbox) и разработке отказоустойчивых промежуточных слоев (Middleware) для обеспечения идемпотентности** (задачи 596–610).

Эти задачи ориентированы на проектирование надежных и отказоустойчивых распределенных систем, способных корректно обрабатывать сетевые сбои, повторные запросы клиентов и рассинхронизацию данных между микросервисами.

### Раздел 46: Распределенные транзакции и консистентность (Задачи 596–610)

#### Подраздел 46.1: Паттерны Saga (Orchestration & Choreography) (Задачи 596–600)

*Паттерн Saga используется для управления распределенными транзакциями в микросервисной архитектуре без блокирования общих ресурсов. Вы спроектируете оба варианта саги (оркестрацию и хореографию) с поддержкой компенсаций.*

596. **Оркестратор Саги (Orchestrated Saga State Machine)**: Спроектируйте централизованный оркестратор саги создания заказа (`OrderSagaOrchestrator`). 
    * Создайте структуру конечного автомата (State Machine) саги. Определите статусы: `SagaStarted`, `PaymentCompleted`, `InventoryReserved`, `SagaFinished`, `PaymentFailed`, `InventoryFailed`, `RollingBack`, `SagaFailed`.
    * Напишите в Go код оркестратора, который последовательно отправляет gRPC-запросы в смежные сервисы и транзакционно сохраняет текущее состояние саги в базу данных на каждом шаге, чтобы при перезапуске оркестратора он мог продолжить выполнение с прерванного места.
597. **Разработка идемпотентных компенсирующих транзакций**: Напишите компенсирующие транзакции для Саги (например, возврат денег `RefundPayment` или снятие брони товара `CancelInventoryReservation`).
    * Объясните в комментариях, почему компенсирующие транзакции в Саге *обязаны* быть идемпотентными (из-за возможных сетевых повторов) и коммутативными (должны уметь корректно обрабатывать ситуацию, когда запрос на отмену брони пришел *раньше*, чем сам запрос на бронирование, из-за сетевых задержек — паттерн "Graceful Cancelation/No-op Rollback").
598. **Децентрализованная Сага (Choreographed Saga)**: Реализуйте хореографическую сагу без центрального оркестратора на базе брокера сообщений (Kafka или NATS JetStream).
    * Сервис `OrderService` создает заказ и публикует событие `OrderCreated`.
    * Сервис `PaymentService` слушает `OrderCreated`, списывает средства и публикует `PaymentAuthorized` (или `PaymentFailed`).
    * Сервис `InventoryService` слушает `PaymentAuthorized`, бронирует товар и публикует `InventoryAllocated`. Если бронирование не удалось — он публикует `InventoryAllocationFailed`.
    * Настройте `PaymentService` на прослушивание события `InventoryAllocationFailed` для автоматического запуска компенсации списания денег.
599. **Борьба с "зависшими" сагами (Saga Janitor/Supervisor)**: Что делать, если один из сервисов-участников саги завис и не вернул ни успешный ответ, ни ошибку? Напишите фонового демона-наблюдателя (Janitor Task) в Go, который раз в минуту сканирует таблицу состояний саг в базе данных. Если сага находится в промежуточном состоянии (например, `PaymentCompleted`) дольше 5 минут, демон должен принудительно перевести сагу в режим компенсации (`RollingBack`) и запустить отмену транзакций.
600. **Событийно-ориентированная сага (Event-Sourced Saga)**: Реализуйте подход Event Sourcing для ведения истории саги. Вместо перезаписи текущего статуса саги в БД, записывайте последовательную цепочку событий саги в таблицу `saga_events` (например: `SagaStarted` -> `PaymentCharged` -> `InventoryAllocationFailed` -> `PaymentRefundStarted` -> `SagaAborted`). Напишите код восстановления (воспроизведения) текущего состояния саги на основе истории её событий.

#### Подраздел 46.2: Паттерны Transactional Outbox & Transactional Inbox (Задачи 601–605)

*Паттерны Outbox и Inbox обеспечивают надежную доставку сообщений между микросервисами по принципу Exactly-Once (строго однократная обработка) без использования тяжелых двухфазных коммитов (2PC).*

601. **Продвинутый Outbox-воркер (SKIP LOCKED)**: В предыдущих упражнениях мы создали простой Outbox. В высоконагруженных системах запуск одного Outbox-воркера создает бутылочное горлышко. Напишите в Go параллельный Outbox-воркер. Для того чтобы несколько инстансов воркера могли безопасно и без блокировок разбирать задачи из таблицы `outbox` в PostgreSQL, напишите SQL-запрос с использованием конструкции `SELECT ... FOR UPDATE SKIP LOCKED` [601]:
    ```sql
    SELECT id, payload FROM outbox_events WHERE status = 'pending' LIMIT 100 FOR UPDATE SKIP LOCKED;
    ```
    Это позволит параллельным горутинам/сервисам мгновенно забирать непересекающиеся пакеты событий на отправку [601].
602. **Transactional Inbox (Идемпотентный потребитель)**: Даже при использовании Outbox брокеры сообщений (такие как Kafka) гарантируют доставку только класса At-Least-Once (минимум один раз), что приводит к дублированию сообщений на стороне приемника. Реализуйте паттерн Transactional Inbox. На стороне принимающего сервиса:
    * При получении сообщения из брокера откройте транзакцию в БД.
    * Попробуйте вставить ID сообщения в таблицу `inbox_events` (`INSERT INTO inbox_events (message_id) VALUES ($1)`).
    * В рамках этой же транзакции выполните обновление бизнес-данных.
    * Если вставка ID сообщения упала по нарушению уникальности ключа (уникальный индекс по `message_id`), сделайте откат (`Rollback`) всей транзакции, проигнорировав дубликат.
603. **Очистка Inbox-таблицы (Pruning Daemon)**: Если хранить ID всех обработанных сообщений в таблице `inbox_events` бесконечно, её размер вырастет до гигабайт, что замедлит проверку уникальности. Напишите фоновую задачу-чистильщик (Pruning Daemon) в Go, которая раз в сутки удаляет из таблицы `inbox_events` записи старше 7 дней, гарантируя, что мы защищены от дубликатов в рамках недельного окна повторов.
604. **Сквозной Exactly-Once пайплайн**: Объедините ваши наработки: Сервис А (БД + Outbox) -> Kafka -> Воркер Б (Inbox + БД). Протестируйте систему: сымитируйте сетевой сбой (отправьте одно и то же сообщение в Kafka 3 раза подряд). Убедитесь, что на стороне Сервиса Б бизнес-данные обновились строго один раз, а в таблице `inbox_events` осталась только одна запись.
605. **Outbox Batching & Publisher Confirms**: Напишите Outbox-воркер для RabbitMQ. Воркер должен считывать пакет из 100 событий из таблицы `outbox`, отправлять их в RabbitMQ, дожидаться группового подтверждения доставки (Publisher Confirms, задача №404) и только после этого одной транзакцией помечать весь пакет как успешно отправленный в базе данных.

#### Подраздел 46.3: Разработка Middleware для обработки ключей идемпотентности (Задачи 606–610)

*Ключи идемпотентности гарантируют, что повторные сетевые запросы от клиентов не приведут к дублированию операций на бэкенде.*

606. **Idempotency Middleware: обработка параллельных запросов (In-Progress Lock)**: Если клиент отправляет два идентичных запроса с одним ключом идемпотентности практически одновременно (до того, как первый запрос успел завершиться), обычная проверка кэша не сработает. Напишите HTTP-middleware в Go, реализующее распределенную блокировку в Redis:
    * При получении запроса выполните команду `SET key "IN_PROGRESS" NX PX 10s`.
    * Если Redis возвращает ошибку (ключ уже занят), а значение равно `"IN_PROGRESS"`, middleware должно приостановить выполнение второго запроса (например, опрашивать Redis раз в 100 миллисекунд или слушать Pub/Sub канал) или мгновенно вернуть статус `409 Conflict`, сообщив, что запрос уже обрабатывается.
607. **Idempotency Middleware: захват и сохранение ответов**: Чтобы API вел себя полностью идемпотентно, повторный запрос должен вернуть клиенту точно такой же HTTP-статус, заголовки и тело ответа, какие вернул оригинальный запрос. Напишите кастомную обертку для `http.ResponseWriter` в Go, которая перехватывает записываемый статус-код, заголовки и тело ответа:
    ```go
    type responseCapturer struct {
        http.ResponseWriter
        body       *bytes.Buffer
        statusCode int
    }
    ```
    После успешного выполнения HTTP-обработчика сериализуйте эти данные в JSON и сохраните в Redis, сменив статус ключа с `"IN_PROGRESS"` на `"FINISHED"`.
608. **Игнорирование транзитных ошибок (5xx)**: Если во время обработки первого запроса произошел внутренний сбой (например, база данных вернула `500 Internal Server Error` или таймаут), мы не имеем права кэшировать этот ответ, так как операция фактически не завершилась успехом. Настройте логику вашего middleware: если обработчик вернул статус-код `>= 500`, middleware должно мгновенно удалить блокировку из Redis, позволив клиенту совершить повторный запрос. Кэшируйте только успешные коды ответов (`2xx`) и некоторые ошибки бизнес-логики (`4xx`).
609. **Защита от подмены тела запроса (Request Hashing)**: Злоумышленник или баг в коде клиента может отправить запрос с чужим ключом идемпотентности, но с абсолютно другим телом запроса. Напишите защиту: middleware должно вычислять криптографический хэш (SHA-256) от тела входящего HTTP-запроса и сохранять его в Redis вместе с ключом идемпотентности. При получении повторного запроса сверяйте хэш входящего тела с сохраненным в Redis. Если они не совпадают, возвращайте ошибку `400 Bad Request` (несоответствие тела запроса ключу идемпотентности).
610. **Реализация транзакционной идемпотентности в СУБД (PostgreSQL)**: Если у вас нет Redis, идемпотентность можно гарантировать на уровне реляционной БД. Напишите middleware, которое перед запуском обработчика делает вставку в таблицу `idempotency_keys` в PostgreSQL:
    ```sql
    INSERT INTO idempotency_keys (key, request_hash) VALUES ($1, $2) ON CONFLICT DO NOTHING;
    ```
    Проверьте результат выполнения: если строка не была вставлена (возник конфликт уникального ключа), обработайте это событие в Go как повторный запрос, считайте залогированный ранее ответ из таблицы `idempotency_keys` и отдайте его клиенту. Если вставка прошла успешно — продолжите выполнение обработчика.
