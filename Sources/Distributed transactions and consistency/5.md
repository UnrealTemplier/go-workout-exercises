Это действительно уровень Staff/Principal инженера. Когда система разбивается на микросервисы, классические ACID-транзакции (BEGIN...COMMIT) перестают работать, потому что базы данных становятся разными. Начинается эпоха eventual consistency (в конечном счете согласованности).

Продолжаем наш хардкорный марафон. Впереди **30 архитектурных упражнений (с 801 по 830)**, которые научат тебя управлять хаосом распределенных систем.

### Блок 78. Idempotency (Идемпотентность): Защита от дублирования (801–810)
Идемпотентность гарантирует, что если клиент (например, мобилка, потерявшая сеть) отправит запрос на списание денег дважды, деньги спишутся только один раз.

801. **Концепция ключа:** Добавь в API эндпоинт `POST /payments`. Требуй обязательный HTTP-заголовок `Idempotency-Key` (в идеале — UUIDv4). Если заголовка нет, возвращай HTTP 400 Bad Request.
802. **Redis Idempotency Store:** Напиши структуру `IdempotencyManager`, использующую Redis. При получении запроса делай `SETNX` (Set if Not Exists) с ключом `idemp:{user_id}:{idempotency_key}` и значением `STARTED`. Если Redis вернул `false` — запрос с таким ключом уже существует!
803. **Обработка конкурентных дублей (Race Condition):** Что если второй запрос пришел, пока первый еще выполняется (статус `STARTED`)? Твой сервер не должен выполнять бизнес-логику во второй раз, но и ответа у него еще нет. В этом случае возвращай клиенту HTTP 409 Conflict с сообщением "Запрос уже обрабатывается, повторите позже".
804. **Сохранение ответа (The Golden Rule):** Истинная идемпотентность означает, что на дублирующийся запрос клиент должен получить **ровно тот же ответ**, что и в первый раз. В конце успешного `POST /payments` сохрани в Redis HTTP-статус (200) и JSON-тело ответа. При повторном запросе с тем же ключом доставай ответ из Redis и отдавай клиенту без похода в БД.
805. **Умный Idempotency Middleware:** Вынеси логику из упр. 802-804 в универсальную `http.Middleware`. Она должна перехватывать входящие запросы. Используй кастомный `http.ResponseWriter` (паттерн Recorder), чтобы "записать" ответ хендлера перед отправкой клиенту и автоматически сохранить его в Redis.
806. **Идемпотентность при ошибках:** Если бизнес-логика упала (HTTP 500, БД недоступна), ключ идемпотентности **нужно удалить** (или пометить как `FAILED`). Клиент *должен* иметь право безопасно повторить (retry) упавший запрос с тем же ключом. Реализуй эту логику в Middleware.
807. **TTL ключей (Garbage Collection):** Ключи идемпотентности не должны храниться вечно (Redis лопнет). При сохранении ключа ставь ему Expire = 24 часа. Считается, что если клиент не повторил запрос за сутки, он уже и не повторит.
808. **Защита от смены Payload (Мутаций):** Клиент послал `POST /payments` с ключом `Key-1` и телом `{"amount": 100}`. А через секунду послал запрос с тем же `Key-1`, но телом `{"amount": 5000}`. Это может быть баг или попытка взлома. На стороне сервера хэшируй (SHA-256) тело первого запроса и сохраняй в Redis. Сравнивай хэш тела повторного запроса. Если они отличаются — возвращай HTTP 422 Unprocessable Entity.
809. **Идемпотентность на уровне БД (Альтернатива Redis):** Redis может потерять данные при рестарте. Создай таблицу `idempotency_keys (key, user_id, response_status, response_body, created_at)`. Делай `INSERT ... ON CONFLICT DO NOTHING`. Это медленнее Redis, но дает 100% гарантию на уровне PostgreSQL.
810. **Безопасные методы:** Убедись, что твой Idempotency Middleware игнорирует методы GET, HEAD, OPTIONS и TRACE (они идемпотентны по спецификации HTTP) и применяется только к POST, PUT, PATCH, DELETE.

### Блок 79. Transactional Outbox & Inbox (811–820)
Проблема двойной записи (Dual Write): ты сохранил заказ в PostgreSQL, но при отправке события в Kafka моргнула сеть. Заказ висит, а микросервисы о нем не знают. Outbox — решение этой проблемы индустриального стандарта.

811. **Схема Outbox:** В сервисе Заказов (Order Service) создай таблицу `outbox_events (id UUID, aggregate_type VARCHAR, aggregate_id VARCHAR, type VARCHAR, payload JSONB, status VARCHAR, created_at TIMESTAMP)`.
812. **Атомарная транзакция:** Напиши функцию `CreateOrder`. Открой транзакцию `tx, _ := db.Begin()`. 1) Сделай `INSERT INTO orders`. 2) Сделай `INSERT INTO outbox_events` (status='PENDING', payload=сериализованный заказ). 3) `tx.Commit()`. Теперь бизнес-сущность и событие записаны со 100% гарантией консистентности.
813. **Outbox Relay Worker (Polling):** Напиши фоновую горутину, которая раз в секунду делает `SELECT * FROM outbox_events WHERE status = 'PENDING' FOR UPDATE SKIP LOCKED` (чтобы воркеры не мешали друг другу). 
814. **Гарантированная отправка:** Воркер из 813 берет событие, отправляет его в брокер (Kafka/RabbitMQ) и **после получения ACK от брокера** делает `UPDATE outbox_events SET status = 'PROCESSED'`.
815. **Listen/Notify (Push модель):** Поллинг каждую секунду грузит базу. Улучши воркер. Используй PostgreSQL `LISTEN outbox_channel`. В триггере таблицы `outbox_events` после инсерта делай `NOTIFY outbox_channel`. Твоя горутина проснется мгновенно и отправит событие в брокер без холостых поллингов!
816. **Схема Inbox:** Переходим в сервис Склада (Inventory Service), который слушает Kafka. Создай таблицу `inbox_events (event_id UUID PRIMARY KEY, processed_at TIMESTAMP)`.
817. **Атомарный Inbox (Дедупликация):** Брокеры могут доставить событие дважды (At-Least-Once). При получении сообщения из Kafka, открой `sql.Tx`. 1) Сделай `INSERT INTO inbox_events (event_id)`. Если ловишь ошибку `UniqueViolation` (событие уже было) — делай `Rollback`, `Ack` брокеру и игнорируй. 2) Если ок, делай бизнес-логику (резервируй товары). 3) `tx.Commit()`.
818. **Интеграция Outbox + Inbox (Exactly-Once):** Удали всю инфраструктуру брокеров. Сделай прямой HTTP вызов из Outbox Relay сервиса Заказов в Inbox API сервиса Склада. Пойми, что связка этих паттернов делает систему отказоустойчивой *даже без Kafka*, переживая любые сетевые таймауты и 502 Bad Gateway.
819. **Очистка (Garbage Collection):** Таблицы Outbox и Inbox растут бесконечно. Напиши Cron-джобу (на `time.Ticker`), которая раз в сутки делает `DELETE FROM outbox_events WHERE status = 'PROCESSED' AND created_at < NOW() - INTERVAL '7 days'`.
820. **Паттерн Transaction Log Tailing (Debezium):** *Теоретически-практическое.* Вместо написания Go-воркера (упр. 813), настрой логическую репликацию PostgreSQL (CDC из Блока 74). Пусть Kafka Connect (или твой Go CDC стример) читает WAL логи таблицы `outbox_events` на лету. Это снимает нагрузку `SELECT FOR UPDATE` с базы данных.

### Блок 80. Паттерн Saga: Оркестрация и Хореография (821–830)
Распределенная транзакция: создаем Заказ -> Списываем Деньги -> Резервируем Склад. Если склад пуст — деньги нужно вернуть, а заказ отменить.

821. **Хореография (Choreography - Децентрализованная Сага):** Напиши 3 микросервиса. `Order` создает заказ (статус PENDING) и шлет событие. `Billing` ловит событие, списывает деньги и шлет свое. `Inventory` ловит событие биллинга, резервирует товар и шлет `InventoryReserved`. `Order` ловит это и ставит статус APPROVED. Реализуй этот "танец" событий.
822. **Хореография (Компенсация):** В упр. 821 захардкодь нехватку товара на Складе. `Inventory` должен отправить событие `InventoryFailed`. 
    * `Billing` должен поймать его и вернуть деньги (компенсирующая транзакция).
    * `Order` должен поймать его и изменить статус на `CANCELLED`. Реализуй этот флоу возврата.
823. **Оркестрация (Orchestration - Централизованная Сага):** У Хореографии есть минус — неявно, кто управляет процессом, сложно дебажить. Создай сервис `SagaOrchestrator`. Это конечный автомат (FSM). Он **командует** микросервисами по gRPC/HTTP: `Call(Billing)`, затем `Call(Inventory)`. Микросервисы просто отвечают ему `OK/Fail`.
824. **Состояние Саги (State Machine):** Оркестратор может упасть (перезагрузиться). Создай БД для оркестратора: таблица `saga_states (saga_id, current_step, status)`. Перед каждым вызовом внешнего микросервиса сохраняй стейт (`Executing_Payment`, `Executing_Inventory`).
825. **Оркестрация (Компенсация):** Если Оркестратор вызвал `Inventory` и получил ошибку, он берет `saga_states`, смотрит, какие шаги уже были успешно выполнены (Payment), и по цепочке отправляет компенсирующие команды: `Call(Billing_Refund)`. Напиши этот механизм отката (Rollback).
826. **Движок Саги (Saga Execution Coordinator - SEC):** Напиши универсальную структуру-движок на Go. Она принимает срез интерфейсов `type Step interface { Execute() error; Compensate() error }`. Метод `Run()` должен идти по срезу вперед, вызывая `Execute`. Если на шаге N ошибка, движок должен пойти в цикле назад от N-1 до 0, вызывая `Compensate`.
827. **Pivot Transactions (Точка невозврата):** Не каждую транзакцию можно отменить. Если ты заказал курьера в Яндекс.Go, курьер уже едет. Шаг заказа курьера — это Pivot. После него шаги могут *только* повторяться до успеха (Retry forever), компенсация больше невозможна. Реализуй в своем SEC движке маркер `IsPivot() bool` и запрети компенсацию после него.
828. **Разрешение распределенных дедлоков:** В Хореографии Заказ А ждет денег от пользователя, а Заказ Б ждет освобождения склада. Напиши планировщик, который проходится по "зависшим" (PENDING) сагам старше 10 минут, принудительно инициирует событие `TimeoutFailed` и запускает процесс компенсации.
829. **Изоляция в Сагах (Semantic Lock):** Пока Сага выполняется (Заказ PENDING), другой микросервис может попытаться изменить этот же заказ или товар. Это нарушает изоляцию (Isolation из ACID). Введи статус `LOCKED` для задействованных сущностей на время работы саги, чтобы любые другие запросы к ним возвращали HTTP 423 Locked.
830. **Интеграционное тестирование Саги:** Подними 3 сервиса в Docker Compose (или Testcontainers). Напиши Go-скрипт. Инициируй успешную сагу — проверь базу 3-х сервисов. Инициируй сагу с ошибкой на последнем шаге. Убедись, что баланс вернулся к исходному (компенсация прошла), а заказ в статусе `CANCELLED`. Это тест, который доказывает, что твоя система реально консистентна!
