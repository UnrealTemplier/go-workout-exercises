### 103. OpenTelemetry — основы

**Упражнение 21.1.** Установи OpenTelemetry SDK: `go.opentelemetry.io/otel`, `go.opentelemetry.io/otel/sdk`, `go.opentelemetry.io/otel/exporters/stdout/stdouttrace`. Создай `TracerProvider` с `BatchSpanProcessor` и `stdout` exporter. Получи tracer: `tp.Tracer("my-service")`. Создай span: `ctx, span := tracer.Start(ctx, "operation-name")`. Заверши `defer span.End()`.

**Упражнение 21.2.** Добави **attributes** в span: `span.SetAttributes(attribute.String("user.id", "123"), attribute.Int("http.status_code", 200))`. Покажи, как structured metadata обогащает трассировку.

**Упражнение 21.3.** Добави **events** в span: `span.AddEvent("cache-miss", trace.WithAttributes(attribute.String("key", "user:123")))`. Используй для отметки значимых моментов внутри операции.

**Упражнение 21.4.** Добави **status и error recording**: при ошибке `span.SetStatus(codes.Error, "database connection failed")`, `span.RecordError(err, trace.WithAttributes(attribute.String("db.instance", "postgres-primary")))`. Покажи разницу между status (semantic) и error event (detailed).

**Упражнение 21.5.** Создай **nested spans**: родительский span `processOrder`, дочерние `validateInventory`, `chargePayment`, `sendNotification`. Передавай `ctx` через `trace.ContextWithSpan`. Покажи иерархию в stdout выводе.

**Упражнение 21.6.** Создай **span links**: при обработке batch сообщения из Kafka — создай span для каждого сообщения, но link'ай к span'у producer'а через `span.AddLink(trace.Link{SpanContext: producerSpanCtx})`. Покажи, что link — не parent-child, а causal connection.

**Упражнение 21.7.** Настрой **W3C Trace Context propagation**: `prop := propagation.NewCompositeTextMapPropagator(propagation.TraceContext{}, propagation.Baggage{})`. Inject в HTTP headers: `prop.Inject(ctx, propagation.HeaderCarrier(req.Header))`. Extract из входящего запроса: `ctx := prop.Extract(r.Context(), propagation.HeaderCarrier(r.Header))`. Покажи сквозную трассировку между сервисами.

**Упражнение 21.8.** Настрой **Baggage**: `ctx = baggage.ContextWithBaggage(ctx, baggage.MustNewMember("tenant.id", "acme-corp"))`. Читай: `tenantID := baggage.FromContext(ctx).Member("tenant.id").Value()`. Покажи, как baggage передаёт бизнес-контекст через все span'ы.

**Упражнение 21.9.** Настрой **OTLP exporter** (OpenTelemetry Protocol): `otlptracegrpc.New(ctx, otlptracegrpc.WithEndpoint("localhost:4317"), otlptracegrpc.WithInsecure())`. Отправляй spans в **Jaeger** или **Tempo**. Проверь в UI.

**Упражнение 21.10.** Настрой **Resource** для идентификации сервиса: `resource.NewWithAttributes(semconv.SchemaURL, semconv.ServiceNameKey.String("order-service"), semconv.ServiceVersionKey.String("v2.1.0"), semconv.DeploymentEnvironmentKey.String("production"), attribute.String("k8s.pod.name", os.Getenv("HOSTNAME")))`. Покажи, как resource атрибуты группируют spans в Jaeger.

### 104. OpenTelemetry — инструментирование

**Упражнение 21.11.** Инструментируй **HTTP server** автоматически: `otelhttp.NewHandler(next, "http-server", otelhttp.WithPropagators(prop), otelhttp.WithSpanNameFormatter(func(operation string, r *http.Request) string { return r.Method + " " + r.URL.Path }))`. Каждый request — span с атрибутами `http.method`, `http.url`, `http.status_code`.

**Упражнение 21.12.** Инструментируй **HTTP client** автоматически: `client := http.Client{Transport: otelhttp.NewTransport(http.DefaultTransport)}`. Каждый outgoing request — span, propagation заголовков автоматический.

**Упражнение 21.13.** Инструментируй **gRPC server**: `grpc.NewServer(grpc.UnaryInterceptor(otelgrpc.UnaryServerInterceptor()), grpc.StreamInterceptor(otelgrpc.StreamServerInterceptor()))`. Покажи spans для каждого RPC с `rpc.method`, `rpc.service`, `rpc.system`.

**Упражнение 21.14.** Инструментируй **gRPC client**: `grpc.Dial(..., grpc.WithUnaryInterceptor(otelgrpc.UnaryClientInterceptor()))`. Покажи distributed trace: client span → server span → database span.

**Упражнение 21.15.** Инструментируй **database/sql**: `github.com/XSAM/otelsql`. `db, _ := otelsql.Open("postgres", dsn, otelsql.WithAttributes(semconv.DBSystemPostgreSQL))`. Каждый query — span с `db.statement`, `db.operation`, `db.sql.table`.

**Упражнение 21.16.** Инструментируй **Redis/go-redis**: `github.com/redis/go-redis/extra/redisotel/v9`. `rdb.AddHook(redisotel.NewTracingHook())`. Каждая команда — span с `db.system = redis`, `db.statement = GET user:123`.

**Упражнение 21.17.** Инструментируй **Kafka producer/consumer**: `github.com/open-telemetry/opentelemetry-go-contrib/instrumentation/github.com/segmentio/kafka-go/otelkafka`. Producer: inject span context в message headers. Consumer: extract и создай child span.

**Упражнение 21.18.** Инструментируй **NATS**: вручную inject/extract через message headers. Producer: `msg.Header.Set("traceparent", carrier.Get("traceparent"))`. Consumer: extract, создай span с `trace.WithLinks()`.

**Упражнение 21.19.** Создай **custom instrumentation** для бизнес-логики: `func ProcessOrder(ctx context.Context, orderID string) error { ctx, span := tracer.Start(ctx, "ProcessOrder", trace.WithAttributes(attribute.String("order.id", orderID))); defer span.End(); ... }`. Добави sub-spans для каждого шага.

**Упражнение 21.20.** Создай **span metrics bridge**: `otelcol` (OpenTelemetry Collector) конфигурация `spanmetrics` processor. Генерируй RED metrics (Rate, Errors, Duration) из spans автоматически. Покажи, что trace → metrics без кода.

### 105. Prometheus — метрики

Покажи bucket'ы: `le=0.005`, `le=0.01`, ..., `le=+Inf`.

**Упражнение 21.24.** Создай **Summary** (редко используется, предпочитай Histogram): `requestLatency := prometheus.NewSummaryVec(prometheus.SummaryOpts{Name: "http_request_latency_seconds", Help: "...", Objectives: map[float64]float64{0.5: 0.05, 0.95: 0.005, 0.99: 0.001}}, []string{"method"})`. Покажи вычисление quantile'ей на клиенте vs сервере.

**Упражнение 21.25.** Создай **custom Collector**: `type DBStatsCollector struct { db *sql.DB }` с методами `Describe(ch chan<- *prometheus.Desc)` и `Collect(ch chan<- prometheus.Metric)`. Экспортируй `sql.DBStats` (OpenConnections, InUse, Idle, WaitCount) как метрики. Покажи advanced instrumentation.

**Упражнение 21.26.** Настрой **Prometheus HTTP endpoint**: `http.Handle("/metrics", promhttp.Handler())`. Проверь `curl localhost:9090/metrics`. Покажи формат: `# HELP`, `# TYPE`, значения.

**Упражнение 21.27.** Настрой **Prometheus scrape**: `prometheus.yml` с `job_name: 'go-services'`, `static_configs: [targets: ['localhost:8080', 'localhost:8081']]`. Проверь targets в Prometheus UI (`http://localhost:9090/targets`).

**Упражнение 21.28.** Создай **RED metrics** для HTTP API: Rate (`http_requests_total`), Errors (`http_requests_total{status=~"5.."}`), Duration (`http_request_duration_seconds_bucket`). Напиши PromQL queries:

### 110. Production monitoring и SRE

**Упражнение 21.60.** Определи **SLI (Service Level Indicator)**: `availability = successful requests / total requests`, `latency = request duration`, `error rate = failed requests / total requests`. Напиши PromQL для каждого.

**Упражнение 21.61.** Определи **SLO (Service Level Objective)**: `availability >= 99.9%`, `latency p95 < 200ms`, `error rate < 0.1%` за 30 дней. Создай Grafana dashboard с SLO panels. Настрой alerts при burn rate > 1% за 1 час.

**Упражнение 21.62.** Рассчитай **Error Budget**: `1 - SLO = 0.1%` = 43.2 минут downtime/month. Создай dashboard: `error_budget_remaining = 1 - (errors_this_month / (total_requests_this_month * (1 - SLO)))`. Alert при budget < 50%.

**Упражнение 21.63.** Настрой **Multi-window, multi-burn-rate alerts**: `fast burn` (1% budget in 1 hour) → page immediately. `slow burn` (100% budget in 3 days) → ticket tomorrow. Покажи `alert: ErrorBudgetBurn` with multiple conditions.

**Упражнение 21.64.** Создай **Runbook** для каждого alert: `HighErrorRate` → "1. Check /metrics for 5xx spikes. 2. Check logs for stack traces. 3. Check recent deployments. 4. Rollback if needed. 5. Escalate to on-call if unresolved in 15 min". Храни в Git (Markdown), link в Alertmanager.

**Упражнение 21.65.** Настрой **Synthetic Monitoring** (blackbox exporter): `probe_success`, `probe_duration_seconds` для critical endpoints (`/health`, `/ready`, key API paths). Проверяй из multiple locations. Alert на `probe_success == 0`.

**Упражнение 21.66.** Настрой **RUM (Real User Monitoring)**: OpenTelemetry Web SDK в браузере. `traceparent` header на все fetch/XHR. Backend correlates frontend trace with backend trace. Measure: page load time, API latency, JavaScript errors.

- In staging: load test, verify SLO, tune thresholds

- Culture: "if you can't observe it, you can't operate it"

### Ключевые моменты для освоения Observability:

1. **Three Pillars**: Metrics (aggregated, quantitative), Logs (discrete, qualitative), Traces (temporal, causal). Не выбирай один — используй все, коррелируй между ними.

2. **Correlation is king**: `trace_id` в логах, `span_id` в метриках, `timestamp` для join. Без correlation — три изолированных сигнала. С correlation — единая картина.

3. **Cardinality matters**: метрики с высокой cardinality (`user_id`, `request_id`) убивают Prometheus. Используй traces/logs для high-cardinality, метрики для aggregation.

4. **Sampling**: 100% traces на development, 1-10% на production (или tail-based: sample ошибочные/медленные 100%, остальное 1%). Head-based (decision at root) vs tail-based (decision after completion).

5. **Alert on symptoms, not causes**: "HTTP 5xx rate > 1%" лучше, чем "CPU > 80%". Symptom-based alerting → action-oriented. Cause-based → noise, false positives.

6. **SLO-driven development**: определи SLO первым делом. Всё остальное — инструменты для достижения. Error budget — разрешение innovate/ship fast. Если budget есть — deploy смело. Если нет — freeze features, focus on reliability.

7. **Observability is not monitoring**: monitoring — знаешь, что искать (known unknowns). observability — можешь понять, что происходит (unknown unknowns). Explore data, don't just check dashboards.

8. **Production profiling**: pprof — development. Continuous profiling (Pyroscope) — production. Сравни профили до/после деплоя. Найди regression за минуты, не часы.

9. **Runbooks are code**: версионируй, review'й, тестируй. Alert без runbook — бесполезен. Runbook без execution — теория. Автоматизируй где возможно.

10. **Culture > Tools**: observability — это подход, не набор инструментов. Инженеры пишут instrumentation как часть feature. SRE review'ит observability в PR. Post-mortem без blame — learning opportunity.
