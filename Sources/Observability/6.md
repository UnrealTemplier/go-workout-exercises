Этот раздел ориентирован на **контроль состояния систем в продакшене**: вы научитесь собирать и экспортировать метрики для Prometheus, настраивать распределенную трассировку с помощью OpenTelemetry, связывать логи с трейсами для сквозного поиска ошибок, ротировать лог-файлы, а также использовать низкоуровневые инструменты профайлинга рантайма Go (`pprof` и `runtime/trace`) для поиска утечек памяти и зависаний процессора.

### Раздел 37: Контроль состояния систем в продакшене (Observability) (Задачи 417–435)

#### Подраздел 37.1: Метрики с Prometheus и OpenTelemetry (Задачи 417–422)

*Метрики дают числовое представление о работе системы в реальном времени. Здесь вы научитесь собирать базовые типы метрик (Counters, Gauges, Histograms) и экспортировать их для систем мониторинга.*

417. **Базовый экспортер Prometheus**: Установите официальный клиент Prometheus для Go: `github.com/prometheus/client_golang/prometheus/promhttp` [417]. Напишите простой HTTP-сервер, который регистрирует обработчик по умолчанию для эндпоинта `/metrics` [417]. Запустите сервер, откройте страницу в браузере и изучите дефолтные метрики рантайма Go (выделение памяти, количество горутин, активность GC), которые клиент собирает автоматически.
418. **Метрика Counter (Счетчик)**: Создайте метрику типа Counter с поддержкой меток (labels) — `prometheus.NewCounterVec` [418]. Назовите её `http_requests_total` с метками `method` (метод запроса) и `status` (HTTP-статус ответа) [418]. Напишите HTTP-middleware, которое при каждом входящем запросе увеличивает счетчик на единицу с указанием конкретных меток (например, `method="POST"`, `status="201"`).
419. **Метрика Gauge (Измеритель)**: Метрика Gauge показывает текущее мгновенное значение, которое может как увеличиваться, так и уменьшаться. Создайте измеритель `active_websocket_connections` с помощью `prometheus.NewGauge` [419]. Напишите WebSocket-обработчик (из задач №387–394), который при подключении нового клиента вызывает `gauge.Inc()`, а при отключении — `gauge.Dec()` [419].
420. **Метрика Histogram (Гистограмма)**: Гистограммы незаменимы для замера распределения задержек (latencies). Создайте гистограмму `http_request_duration_seconds` с помощью `prometheus.NewHistogramVec` [420]. Настройте кастомные бакеты (buckets), например, `[]float64{0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5}`. Напишите middleware, замеряющее время обработки входящего запроса, и записывайте длительность в гистограмму с помощью метода `Observe()`.
421. **Переход на OpenTelemetry Metrics**: Стандарты индустрии смещаются в сторону OpenTelemetry. Используя пакеты `go.opentelemetry.io/otel/metric`, настройте инициализацию глобального `MeterProvider`. Напишите пример счетчика `api_calls_count` с помощью OpenTelemetry API и настройте экспорт метрик по протоколу OTLP (OpenTelemetry Line Protocol).
422. **Кастомный сборщик метрик (Collector)**: Иногда метрики нужно извлекать напрямую из сторонней системы (например, количество зарегистрированных пользователей из БД PostgreSQL). Напишите структуру, реализующую интерфейс `prometheus.Collector` (методы `Describe` и `Collect`). Внутри метода `Collect` делайте быстрый SQL-запрос `COUNT(*)` к таблице пользователей и регистрируйте результат как метрику Prometheus.

#### Подраздел 37.2: Структурированное логирование и корреляция (Задачи 423–426)

*Структурированные логи в формате JSON позволяют быстро фильтровать информацию, а корреляция связывает лог-файлы с распределенными трейсами.*

423. **Маскирование конфиденциальных данных в `slog`**: При логировании объектов в JSON-формат велик риск случайно записать в лог пароли, номера карт или персональные данные. Напишите кастомный обработчик (Handler) для встроенного пакета `slog`. Он должен перехватывать все записываемые атрибуты лога и заменять значения полей с именами `password`, `card_number` и `email` на маску `[REDACTED]`.
424. **Ротация лог-файлов на диске**: Писать логи в один бесконечный файл на сервере опасно — диск может переполниться. Настройте запись логов из `slog` в файл с автоматической ротацией с помощью популярной библиотеки `gopkg.in/natefinch/lumberjack.v2`. Настройте ротацию: максимальный размер файла 50 МБ, хранить не более 3 старых файлов, удалять файлы старше 10 дней.
425. **Корреляция Трейсов и Логов (Log Correlation)**: Напишите middleware для HTTP-сервера, интегрированного с OpenTelemetry. Middleware должно извлекать текущий `TraceID` и `SpanID` из активного контекста и автоматически добавлять их в качестве полей `trace_id` и `span_id` в каждую запись `slog` при логировании. Это позволит вам мгновенно находить все логи, относящиеся к одному конкретному запросу пользователя.
426. **Логирование ошибок со стеком вызовов**: Напишите хелпер для `slog`, который при передаче объекта `error` анализирует его структуру. Если ошибка содержит в себе обернутые ошибки (`errors.Unwrap`), хелпер должен разложить их на структурированный JSON-массив. Также добавьте автоматическое извлечение и запись стека вызовов (stack trace) для ошибок уровня `Error`.

#### Подраздел 37.3: Распределенная трассировка с OpenTelemetry (Задачи 427–431)

*Трассировка визуализирует путь прохождения запроса через цепочки микросервисов, помогая находить узкие места.*

427. **Инициализация OpenTelemetry Tracing SDK**: Напишите функцию инициализации трейсера `InitTracer()`. Настройте отправку трейсов на локальный коллектор (например, Jaeger или Tempo) по протоколу OTLP (gRPC или HTTP). Обеспечьте корректный сброс буферов трейсера при выходе из приложения через `tracerProvider.Shutdown()`.
428. **Создание ручных спанов (Spans)**: Напишите функцию `ProcessOrder()`, которая создает именованный спан с помощью `otel.Tracer("order-service").Start(ctx, "ProcessOrder")` [428]. Внутри функции установите кастомные атрибуты спана (например, `order.id = 42` [428]) и запишите ключевые события процесса в виде логов-эвентов с помощью `span.AddEvent("validation_started")` [428]. Не забудьте завершить спан через `defer span.End()`.
429. **Обработка паник и ошибок в трейсах**: Если внутри спана происходит ошибка или паника, трейс должен визуализировать это красным цветом. Напишите код: оберните выполнение тяжелой функции в блок с `recover()`. При возникновении ошибки запишите её в спан с помощью `span.RecordError(err)` [429] и явно установите статус спана в `codes.Error` с описанием причины падения [429].
430. **Сквозная трассировка по HTTP (Context Propagation)**:
    * Создайте HTTP-клиент, который с помощью `otelhttp` или ручного внедрения (Inject) упаковывает `TraceID` текущего спана в HTTP-заголовки запроса по стандарту W3C Trace Context [430].
    * Создайте HTTP-сервер, который с помощью экстрактора (Extract) извлекает этот `TraceID` из заголовков входящего запроса и создает дочерний спан [430].
    Проверьте, что в системе визуализации (Jaeger) оба действия склеились в один общий трейс.
431. **Автоматическая трассировка gRPC-запросов**: Интегрируйте готовые интерцепторы OpenTelemetry для gRPC на стороне клиента и сервера (пакет `go.opentelemetry.io/contrib/instrumentation/google.golang.org/grpc/otelgrpc`) [431]. Убедитесь, что все метаданные трассировки передаются между микросервисами автоматически без ручного написания кода внедрения заголовков.

#### Подраздел 37.4: Профайлинг и рантайм-диагностика (Задачи 432–435)

*Профайлинг позволяет исследовать внутреннее состояние рантайма Go, выявлять "прожорливые" функции и устранять утечки памяти.*

432. **Интеграция HTTP-профайлера `pprof`**: Подключите стандартный пакет профайлинга к вашему работающему веб-приложению, импортировав пустой пакет `_ "net/http/pprof"` [432]. Настройте запуск вспомогательного HTTP-сервера на отдельном порту (например, `localhost:6060`) только для нужд диагностики, чтобы закрыть доступ к диагностическим эндпоинтам из внешней сети.
433. **Диагностика утечки CPU**: Напишите функцию, которая содержит в себе алгоритмическую ошибку, приводящую к высокой утилизации процессора (например, пустой цикл `for {}` или неэффективный пересчет строк). Запустите нагрузку на сервис. С помощью утилиты `go tool pprof` соберите профиль процессора за 30 секунд: `go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30` [433]. С помощью команд `top` и `list` найдите ту самую функцию, которая забирает больше всего процессорного времени [433].
434. **Диагностика утечки памяти (Heap Profile)**: Напишите фоновый воркер, который раз в секунду создает структуру большого объема и складывает её в глобальный слайс, имитируя классическую утечку памяти (память аллоцируется, но GC не может её очистить). Запустите сервис. Соберите профиль кучи с помощью команды: `go tool pprof http://localhost:6060/debug/pprof/heap` [434]. Найдите строку кода, которая аллоцирует память, остающуюся в куче навсегда.
435. **Трассировка выполнения рантайма (`runtime/trace`)**: Трассировщик выполнения Go позволяет детально изучить работу планировщика горутин и задержки GC. Напишите код, записывающий трассировку выполнения программы в течение 5 секунд в файл `trace.out` с помощью пакета `runtime/trace`. Запустите веб-визуализатор командой `go tool trace trace.out` [435]. Проанализируйте график активности горутин, время блокировок на системных вызовах (Syscalls) и работу сборщика мусора.
