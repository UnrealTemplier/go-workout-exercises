Архитектура бэкендов — это вершина мастерства Go-разработчика. Здесь решается не "как написать код", а "как организовать систему", чтобы она была поддерживаемой, масштабируемой и отказоустойчивой. Хорошая архитектура — это набор осознанных компромиссов (trade-offs), а не следование догмам.

Ниже представлен **масштабный блок из 95 упражнений (с 951 по 1045)**, который проведет вас от простого CRUD-монолита до построения глобально распределённых энтерпрайз-систем.

### Тема 100: Простые архитектуры и монолиты
*Начинаем с основ. Большинство стартапов и внутренних инструментов не нуждаются в микросервисах.*
951. **Трёхслойная архитектура (3-Tier):** Создайте проект со слоями: Handler (HTTP) → Service (бизнес-логика) → Repository (БД). Изучите, почему это минимально жизнеспособная структура.
952. **Структура проекта:** Организуйте код по стандарту `golang-standards/project-layout`: `/cmd`, `/internal`, `/pkg`, `/api`, `/migrations`, `/scripts`.
953. **Dependency Injection:** Реализуйте ручную инъекцию зависимостей через конструкторы (`NewService(repo Repository)`) без использования DI-фреймворков. Поймите, почему в Go не любят рефлексию.
954. **Configuration Management:** Используйте `github.com/spf13/viper` или `caarlos0/env` для загрузки конфигурации из переменных окружения, `.env` файлов и флагов CLI с приоритетами.
955. **Graceful Shutdown:** Реализуйте паттерн, где при SIGINT сервер перестаёт принимать новые запросы, дожидается завершения текущих (с таймаутом), закрывает соединения с БД/Redis/Kafka и только потом завершается.
956. **Monolith First:** Создайте полноценный CRUD-монолит для e-commerce (Users, Products, Orders, Payments) с чёткими границами модулей внутри одного процесса.
957. **Modular Monolith:** Разделите монолит на независимые модули (`/internal/users`, `/internal/orders`), которые общаются только через публичные интерфейсы, а не импортируют внутренние структуры друг друга.
958. **API Versioning:** Реализуйте версионирование API через URL (`/v1/users`, `/v2/users`) или через заголовки (`Accept: application/vnd.myapi.v2+json`). Обсудите trade-offs.
959. **Feature Flags:** Интегрируйте систему feature flags (например, через Redis или LaunchDarkly) для постепенного rollout новых фич без redeploy.
960. **Background Jobs:** Реализуйте систему фоновых задач через Redis queue или PostgreSQL `SKIP LOCKED` (для простой job queue без внешних зависимостей).

### Тема 101: Clean Architecture и Domain-Driven Design (DDD)
*Для сложных бизнес-доменов, где логика важнее инфраструктуры.*
961. **Слои Clean Architecture:** Разделите код на 4 слоя: Entities (доменные объекты) → Use Cases (бизнес-логика) → Interfaces (adapters) → Frameworks (HTTP, DB). Зависимости направлены только внутрь.
962. **Hexagonal Architecture (Ports & Adapters):** Определите "порты" (интерфейсы) для внешних зависимостей (UserRepository, EmailSender) и реализуйте "адаптеры" (PostgresUserRepository, SendGridEmailSender).
963. **Domain Entities:** Создайте богатые доменные объекты с поведением (методами), а не просто структуры с данными. Например, `Order.CanBeCancelled() bool`, `Order.ApplyDiscount(percent float64)`.
964. **Value Objects:** Реализуйте неизменяемые объекты для концепций без идентичности: `Money{amount, currency}`, `Email{address}`, `Address{street, city, zip}`.
965. **Domain Events:** Создайте систему событий (`OrderCreated`, `PaymentProcessed`), которые генерируются при изменении состояния агрегатов и публикуются в event bus.
966. **Aggregates:** Определите границы агрегатов (например, `Order` как aggregate root, содержащий `OrderItems`). Транзакции не должны пересекать границы агрегатов.
967. **Repositories:** Реализуйте репозитории, которые скрывают детали хранения. Интерфейс `OrderRepository` не должен знать про SQL или PostgreSQL.
968. **Application Services:** Создайте use case'ы как тонкие orchestration слои: `CreateOrderUseCase.Execute(dto CreateOrderDTO) (OrderID, error)`.
969. **Anti-Corruption Layer (ACL):** При интеграции с legacy-системой создайте адаптер, который транслирует внешнюю модель в вашу доменную модель, защищая её от "загрязнения".
970. **Bounded Contexts:** Разделите большую систему на контексты (например, "Inventory", "Billing", "Shipping"), каждый со своей доменной моделью и БД.
971. **Ubiquitous Language:** Убедитесь, что имена классов, методов и переменных отражают бизнес-терминологию (не `data1`, `process()`, а `Invoice.CalculateTax()`).

### Тема 102: Микросервисная архитектура
*Когда монолит становится слишком большим и сложным.*
972. **Service Decomposition:** Разделите монолит на микросервисы по бизнес-возможностям: User Service, Product Service, Order Service, Payment Service.
973. **API Gateway:** Создайте единый entry point (через Kong, Envoy или собственный Go-сервис), который роутит запросы к нужным микросервисам, агрегирует ответы, занимается аутентификацией.
974. **BFF (Backend for Frontend):** Создайте отдельные API для мобильного и веб-клиентов с разными контрактами и оптимизациями под каждый клиент.
975. **Inter-Service Communication (Sync):** Используйте gRPC для синхронного общения между сервисами с retry, circuit breaker и timeout.
976. **Inter-Service Communication (Async):** Используйте Kafka/RabbitMQ для асинхронного общения (event-driven) для снижения coupling.
977. **Service Discovery:** В Kubernetes используйте DNS-based discovery. Для on-premise рассмотрите Consul или etcd.
978. **Distributed Transactions (Saga):** Реализуйте Saga pattern через orchestration (центральный координатор) или choreography (сервисы реагируют на события друг друга).
979. **Saga Compensation:** Для каждого действия в Saga реализуйте компенсирующее действие (например, `ReserveInventory` → `ReleaseInventory` при ошибке платежа).
980. **Idempotency Keys:** Добавьте `Idempotency-Key` заголовок для всех POST/PUT/PATCH запросов, чтобы повторные вызовы не создавали дубликаты.
981. **Strangler Fig Pattern:** Постепенно мигрируйте с монолита на микросервисы, перенаправляя трафик через API Gateway на новые сервисы по мере их готовности.
982. **Database per Service:** Каждый микросервис имеет свою БД. Используйте event sourcing или CDC для синхронизации данных между сервисами.

### Тема 103: Хайлоад паттерны и масштабирование
*Когда RPS измеряется десятками тысяч, а данные — петабайтами.*
983. **CQRS (Command Query Responsibility Segregation):** Разделите модели для записи (commands) и чтения (queries). Write model — нормализованная БД, Read model — денормализованные view в Redis/Elasticsearch.
984. **Event Sourcing:** Сохраняйте все изменения состояния как последовательность событий в Kafka/EventStoreDB. Восстанавливайте текущее состояние через replay событий.
985. **Materialized Views:** Создавайте read-оптимизированные проекции из event stream (например, `UserOrdersView` обновляется при каждом `OrderCreated` событии).
986. **Read Replicas:** Настройте master-slave репликацию в PostgreSQL. Write операции идут в master, read — в slaves (через separate DB connection pool).
987. **Database Sharding:** Горизонтальное шардирование по `user_id` (например, `user_id % 16` определяет шард). Реализуйте routing logic в приложении или через Vitess/Citus.
988. **Caching Strategies:** Реализуйте Cache-Aside (lazy loading), Write-Through, Write-Behind (async write). Используйте Redis для hot data, CDN для static assets.
989. **Cache Invalidation:** Реализуйте инвалидацию кэша через pub/sub (Redis Pub/Sub) при изменении данных в БД.
990. **Rate Limiting:** Реализуйте distributed rate limiter через Redis Lua scripts (token bucket или sliding window) для защиты от DoS и fair usage.
991. **Load Shedding:** При перегрузке отбрасывайте "дешёвые" запросы (health checks, неважные метрики) или возвращайте cached/stale data.
992. **Backpressure:** Если consumer не успевает обрабатывать сообщения из Kafka, уменьшайте fetch size или приостанавливайте producer.
993. **Bulkhead Pattern:** Изолируйте ресурсы для разных клиентов/тенантов (separate thread pools, connection pools), чтобы падение одного не уронило всю систему.
994. **Circuit Breaker:** Реализуйте автоматическое "размыкание цепи" при N подряд ошибках к downstream сервису, с последующими попытками восстановления.
995. **Retry with Exponential Backoff:** При transient errors делайте retry с увеличивающейся задержкой (1s, 2s, 4s, 8s) и jitter для предотвращения thundering herd.
996. **Horizontal Scaling:** Спроектируйте сервисы как stateless, чтобы можно было запускать N инстансов за load balancer'ом. State храните в Redis/PostgreSQL/Kafka.
997. **Vertical Partitioning (Functional Partitioning):** Разделите данные по функциональности: "горячие" данные (последние заказы) в быстрой БД, "холодные" (архив) в дешёвом хранилище (S3 + Athena).

### Тема 104: Энтерпрайз паттерны и Multi-tenancy
*Для B2B SaaS, fintech, healthcare с жёсткими требованиями к безопасности и compliance.*
998. **Multi-tenancy (Shared DB, Shared Schema):** Все тенанты в одной БД, каждая таблица имеет `tenant_id`. Используйте Row-Level Security (RLS) в PostgreSQL для изоляции.
999. **Multi-tenancy (Shared DB, Separate Schemas):** Каждый тенант имеет свою схему в одной БД. Более изолированно, но сложнее управлять миграциями.
1000. **Multi-tenancy (Separate DB):** Каждый тенант имеет свою БД. Максимальная изоляция, но дорого и сложно масштабировать.
1001. **Tenant-aware Routing:** В API Gateway извлекайте `tenant_id` из JWT/subdomain и роутите запрос к нужной БД или региону.
1002. **Data Residency:** Храните данные EU-тенантов в EU-регионе, US-тенантов — в US. Реализуйте через geo-routing и separate deployments.
1003. **Audit Logging:** Логируйте все изменения критичных данных (кто, когда, что изменил, старое/новое значение) в append-only таблицу или Kafka topic.
1004. **Soft Delete:** Не удаляйте данные физически, помечайте как `deleted_at`. Это нужно для audit и восстановления.
1005. **PII Encryption:** Шифруйте персональные данные (email, phone) at rest через application-level encryption (например, `pgcrypto` или HashiCorp Vault).
1006. **Secrets Management:** Используйте HashiCorp Vault или AWS Secrets Manager для хранения DB credentials, API keys. Никогда не храните секреты в коде или env vars в plain text.
1007. **RBAC (Role-Based Access Control):** Реализуйте систему ролей (`admin`, `manager`, `user`) с permissions на уровне ресурсов (`orders:read`, `orders:write`).
1008. **ABAC (Attribute-Based Access Control):** Более гибкая модель: "пользователь может редактировать заказ, если он его владелец И заказ в статусе draft".
1009. **OAuth2/OIDC Provider:** Реализуйте собственный Identity Provider или интегрируйтесь с Keycloak/Auth0 для SSO.
1010. **Compliance (GDPR, HIPAA, PCI DSS):** Реализуйте "right to be forgotten" (удаление всех данных пользователя), data retention policies, encryption in transit and at rest.

### Тема 105: Реальные кейсы и комплексные системы
*Применяем все паттерны вместе для построения production-grade систем.*
1011. **Case Study: Twitter-clone (High Read, Medium Write):**
    * Timeline generation: fan-out on write (для обычных пользователей) vs fan-out on read (для знаменитостей).
    * Timeline storage: Redis sorted sets для быстрого получения последних tweets.
    * Media storage: S3 + CDN для изображений/видео.
    * Search: Elasticsearch для full-text search по tweets.
    * Real-time notifications: WebSocket + Redis Pub/Sub.
1012. **Case Study: Uber-like (High Write, Geo-spatial):**
    * Location tracking: NATS/Redis для real-time updates местоположения водителей (100k updates/sec).
    * Matching algorithm: geo-spatial queries через PostGIS или Redis GEO.
    * Surge pricing: Kafka Streams для real-time подсчёта demand/supply ratio.
    * Trip lifecycle: Saga pattern через events (DriverAssigned → TripStarted → TripCompleted → PaymentProcessed).
1013. **Case Study: E-commerce (Complex Business Logic):**
    * Inventory management: distributed locks через Redis для предотвращения overselling.
    * Pricing engine: правила скидок, промокоды, dynamic pricing.
    * Order processing: Saga с компенсирующими действиями.
    * Payment gateway integration: idempotency, webhook handling, reconciliation.
1014. **Case Study: Fintech/Banking (ACID, Compliance):**
    * Double-entry bookkeeping: каждая транзакция — это debit и credit записи.
    * Fraud detection: real-time scoring через ML model ( TensorFlow Serving).
    * Audit trail: immutable log всех операций.
    * Regulatory reporting: batch jobs для генерации отчётов.
1015. **Case Study: Video Streaming (High Bandwidth, CDN):**
    * Video transcoding: background jobs через Kafka + FFmpeg workers.
    * Adaptive bitrate streaming: HLS/DASH manifest generation.
    * CDN integration: CloudFront/Cloudflare для delivery.
    * Recommendation engine: collaborative filtering через Elasticsearch.
1016. **Case Study: IoT Platform (Massive Scale, Time-series):**
    * Device connectivity: MQTT broker (например, EMQX) для миллионов устройств.
    * Time-series storage: TimescaleDB или InfluxDB для метрик.
    * Rule engine: CEP (Complex Event Processing) для триггеров на основе правил.
    * Device management: OTA updates, device twins.
1017. **Case Study: Collaborative Editing (CRDT, Real-time):**
    * Operational Transformation (OT) или CRDT для conflict resolution.
    * WebSocket для real-time sync между клиентами.
    * Presence awareness: кто сейчас редактирует документ.
    * Version history: snapshot'ы каждые N операций для быстрого восстановления.
1018. **Case Study: Booking System (High Contention):**
    * Seat reservation: optimistic locking через `version` column или distributed locks.
    * Time-limited holds: временное резервирование с TTL (Redis).
    * Waitlist: очередь на освобождённые места.
    * Overbooking strategy: статистическая модель для компенсации no-shows.

### Тема 106: Infrastructure as Code и Cloud Native
*Архитектура не существует без инфраструктуры.*
1019. **Docker Multi-stage Builds:** Оптимизируйте Dockerfile для минимального размера образа (builder stage → runtime stage с `scratch` или `distroless`).
1020. **Kubernetes Deployments:** Создайте Deployment, Service, ConfigMap, Secret манифесты для вашего Go-сервиса.
1021. **Helm Charts:** Упакуйте K8s манифесты в Helm chart с values для dev/staging/prod.
1022. **Kustomize:** Используйте Kustomize для управления различиями между окружениями без шаблонов.
1023. **GitOps (ArgoCD/Flux):** Настройте автоматический деплой при мердже в main branch через GitOps.
1024. **Service Mesh (Istio/Linkerd):** Внедрите service mesh для mTLS, traffic management, observability без изменения кода.
1025. **Horizontal Pod Autoscaler (HPA):** Настройте автомасштабирование на основе CPU/memory или custom metrics (например, queue length).
1026. **Pod Disruption Budgets (PDB):** Гарантируйте, что при maintenance всегда доступно минимум N реплик сервиса.
1027. **Resource Requests/Limits:** Правильно настройте CPU/memory requests и limits для предсказуемого scheduling и предотвращения OOM.
1028. **Readiness/Liveness Probes:** Настройте health checks для корректного traffic routing и auto-restart при hang.

### Тема 107: Resilience Engineering и Chaos Testing
*Система должна работать даже когда всё ломается.*
1029. **Failure Mode Analysis:** Для каждого компонента (БД, Redis, Kafka, external API) проанализируйте: что произойдёт при его падении? Как система деградирует?
1030. **Graceful Degradation:** Если recommendation service недоступен, возвращайте popular items вместо персональных рекомендаций.
1031. **Timeout Everywhere:** Установите таймауты на все network calls (HTTP, gRPC, DB, Redis). Нет таймаута = бесконечное ожидание = cascade failure.
1032. **Retry Budget:** Ограничьте общее количество retry в системе (например, не более 10% от общего трафика), чтобы retry storm не усугубил проблему.
1033. **Chaos Testing (Pod Kill):** Используйте `pumba` или `chaos-mesh` для случайного убийства подов и проверки, что система восстанавливается.
1034. **Chaos Testing (Network Latency):** Эмулируйте сетевые задержки через `tc` (traffic control) и проверяйте, что таймауты и retry работают корректно.
1035. **Chaos Testing (Database Failover):** Остановите primary БД и проверьте, что приложение корректно переключается на replica.
1036. **Disaster Recovery (DR):** Настройте cross-region replication для БД и object storage. Тестируйте failover в DR регион.
1037. **Backup and Restore:** Регулярные backups БД с тестированием restore procedure. RPO (Recovery Point Objective) и RTO (Recovery Time Objective).
1038. **Runbooks:** Документируйте процедуры для incident response: "что делать при high CPU", "что делать при DB connection pool exhaustion".

### Тема 108: Performance Optimization и Benchmarking
*Когда "достаточно быстро" — это не достаточно.*
1039. **Load Testing:** Используйте `k6`, `vegeta` или `wrk` для нагрузочного тестирования. Определите max RPS, P99 latency, breaking point.
1040. **Profiling in Production:** Используйте `pprof` для снятия CPU/memory profiles в production (на canary инстансах) для поиска bottlenecks.
1041. **Database Query Optimization:** Используйте `EXPLAIN ANALYZE` для медленных запросов. Добавляйте индексы, оптимизируйте JOIN'ы, используйте materialized views.
1042. **Connection Pooling:** Настройте optimal pool size для PostgreSQL (`max_conns = (core_count * 2) + disk_spindles`). Используйте PgBouncer для connection multiplexing.
1043. **Batch Processing:** Объединяйте множество мелких операций в batch (например, bulk INSERT вместо 1000 отдельных INSERT'ов).
1044. **Async Processing:** Выносите "тяжёлые" операции (email sending, image processing) в background jobs через Kafka/RabbitMQ.
1045. **Финальный босс (Global-scale SaaS Platform):**
    Спроектируйте multi-tenant SaaS платформу для project management (типа Jira/Asana):
    
    **Архитектура:**
    * Modular monolith для core functionality (projects, tasks, users).
    * Микросервисы для специфичных доменов: Notification Service, Analytics Service, Billing Service.
    * API Gateway (Kong) с rate limiting, authentication, request routing.
    * BFF для web и mobile клиентов.
    
    **Data Layer:**
    * PostgreSQL (с Citus для sharding) для transactional data.
    * Redis для caching, sessions, real-time presence.
    * Elasticsearch для full-text search по tasks.
    * Kafka для event streaming и async communication.
    * S3 для file attachments.
    
    **Multi-tenancy:**
    * Database-per-tenant для enterprise customers (изоляция, compliance).
    * Shared database с Row-Level Security для SMB customers.
    * Data residency: EU tenants в eu-west-1, US tenants в us-east-1.
    
    **Scalability:**
    * Horizontal scaling через Kubernetes HPA.
    * Read replicas для read-heavy operations.
    * CQRS для analytics dashboard (write model → Kafka → materialized views в ClickHouse).
    * CDN для static assets и media.
    
    **Resilience:**
    * Circuit breakers для external integrations.
    * Retry с exponential backoff и jitter.
    * Bulkhead isolation для tenant workloads.
    * Graceful degradation при partial failures.
    
    **Observability:**
    * OpenTelemetry для distributed tracing.
    * Prometheus + Grafana для metrics и SLO dashboards.
    * Loki для structured logs.
    * Jaeger для trace visualization.
    
    **Security & Compliance:**
    * OAuth2/OIDC для authentication.
    * RBAC + ABAC для authorization.
    * Encryption at rest (AES-256) и in transit (TLS 1.3).
    * Audit logging для compliance (SOC 2, GDPR).
    * Secrets management через HashiCorp Vault.
    
    **Deployment:**
    * GitOps через ArgoCD.
    * Blue-green deployments для zero-downtime releases.
    * Feature flags для gradual rollout.
    * Canary deployments с automated rollback при errors.

### 💡 Золотые правила архитектуры бэкендов:

1. **Start with a monolith.** Микросервисы — это решение проблем масштабирования организации, а не технологий. Начните с modular monolith, разделите на сервисы только когда монолит станет bottleneck.

2. **YAGNI (You Aren't Gonna Need It).** Не внедряйте Kafka/CQRS/Event Sourcing "на будущее". Эти паттерны добавляют огромную сложность. Используйте их только когда реально столкнётесь с проблемой, которую они решают.

3. **Trade-offs, not dogmas.** Нет "правильной" архитектуры. Есть trade-offs: consistency vs availability (CAP theorem), latency vs throughput, simplicity vs flexibility. Осознанно выбирайте based on requirements.

4. **Design for failure.** В distributed systems всё ломается: сеть, диски, БД, внешние API. Проектируйте систему предполагая, что любой компонент может упасть в любой момент.

5. **Simplicity wins.** Самая лучшая архитектура — та, которую команда понимает и может поддерживать. Избегайте over-engineering. Если можно решить проблему проще — решайте проще.

6. **Evolve, don't predict.** Требования меняются. Проектируйте систему так, чтобы её можно было эволюционировать (loose coupling, clear boundaries). Не пытайтесь предугадать всё на 5 лет вперёд.

7. **Observability from day one.** Вы не можете улучшить то, что не можете измерить. Метрики, логи, трейсы должны быть встроены с самого начала, а не добавлены "потом".

8. **Automate everything.** Infrastructure as Code, CI/CD, automated testing, automated rollback. Ручные процессы — это source of errors и bottleneck.

9. **Security by default.** Encryption, authentication, authorization, audit logging — это не "фичи", которые можно добавить позже. Это фундамент, который должен быть с первого дня.

10. **Document decisions.** Используйте ADR (Architecture Decision Records) для документирования важных архитектурных решений: контекст, варианты, выбранное решение, последствия. Это knowledge base для команды.
