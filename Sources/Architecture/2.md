### 14. Архитектура бэкендов (от простых до enterprise/хайлоад)

501. **Слоистая архитектура «handler → service → repository»**. Реализуйте CRUD для сущности User с in-memory хранилищем, строго разделяя транспортный, бизнес-логический и storage слои.
502. **Dependency Injection (ручная)**. Передавайте зависимости (репозитории, логгер, конфиг) через конструкторы. Запретите глобальные переменные, добейтесь тестируемости.
503. **Конфигурация приложения**. Загружайте настройки из YAML/JSON-файла и переменных окружения с приоритетом env. Используйте библиотеку `envconfig` или `viper`.
504. **Graceful Shutdown всей системы**. Реализуйте корректный порядок остановки: сначала прекращаем приём новых запросов, затем завершаем фоновые горутины, закрываем соединения с БД и брокерами.
505. **Структура проекта: `/cmd`, `/internal`, `/pkg`**. Создайте проект с пакетами `cmd/server`, `internal/app`, `internal/handler`, `internal/service`, `internal/repository`, `pkg/logger`. Опишите, что куда класть.
506. **Модульный монолит с доменными пакетами**. Разделите внутренние пакеты по доменам: `internal/users`, `internal/orders`. Каждый домен имеет свой handler, service, repository. Избегайте циклических зависимостей.
507. **Middleware pipeline**. Выстройте цепочку middleware (логирование, аутентификация, восстановление после паники, трассировка) с возможностью конфигурирования порядка без изменения кода.
508. **Версионирование API**. Реализуйте `v1` и `v2` эндпоинтов на одном сервере. `v2` меняет формат ответа. Клиенты могут плавно мигрировать.
509. **Паттерн Repository (интерфейс)**. Опишите интерфейс `UserRepository`. Реализуйте две имплементации: `PostgresUserRepo` и `InMemoryUserRepo`. Переключайтесь между ними флагом конфигурации.
510. **Unit of Work (транзакционность)**. Создайте `UnitOfWork`, который управляет транзакцией БД. Сервис создаёт нескольких пользователей в одной транзакции через UoW.
511. **Сервисный слой с доменными сервисами**. Выделите `UserService` и `OrderService`. При создании заказа сервис заказов вызывает сервис пользователей для проверки существования пользователя. Покажите инверсию зависимостей.
512. **Domain-Driven Design: Entities, Value Objects, Aggregate Root**. Спроектируйте заказ как агрегат: `Order` (root), `OrderItem` (entity), `Address` (value object). Вся логика изменения заказа только через методы агрегата.
513. **Domain Events (внутридоменные события)**. После создания заказа генерируйте событие `OrderCreated`. Внутри того же процесса (in-process) обработайте его для отправки уведомления.
514. **Event Sourcing**. Храните не текущее состояние заказа, а последовательность событий (`OrderCreated`, `ItemAdded`, `OrderConfirmed`). Восстанавливайте состояние проигрыванием событий. Реализуйте с JSON-колонкой в PostgreSQL.
515. **CQRS (разделение команд и запросов)**. Команды (create, update) идут через доменную модель. Запросы (получение списка) идут напрямую в БД через оптимизированные read-модели (денормализованные).
516. **Transactional Outbox для надёжной публикации событий**. Сервис сохраняет событие в таблицу `outbox` в той же транзакции, что и изменение агрегата. Отдельный процесс отправляет события в брокер с гарантией at-least-once.
517. **Saga (Choreography) для распределённой транзакции**. Сервис заказов создаёт заказ, публикует событие. Сервис резервирования товара слушает событие, резервирует, публикует своё событие. Если резервирование не удалось, сервис заказов компенсирует, отменяя заказ.
518. **API Gateway на Go**. Напишите обратный прокси, который маршрутизирует запросы к разным микросервисам по префиксам (`/users`, `/orders`). Добавьте агрегацию ответов: один endpoint собирает данные из двух сервисов и возвращает клиенту.
519. **Rate Limiter и Circuit Breaker на уровне Gateway**. Встройте в API Gateway ограничение по количеству запросов (токен-бакет) и автоматическое отключение проблемного сервиса (circuit breaker) с восстановлением.
520. **Идемпотентные API**. Реализуйте эндпоинт создания платежа, который принимает `idempotency-key`. Повторный запрос с тем же ключом возвращает сохранённый результат, не выполняя операцию повторно.
521. **Стратегии кэширования**. Реализуйте Cache-Aside для получения профиля пользователя (проверка кэша → БД → запись в кэш). Добавьте инвалидацию при обновлении. Используйте Redis.
522. **Шардирование на уровне приложения**. Реализуйте маршрутизацию запросов к разным инстансам PostgreSQL по ключу (например, `user_id % N`). Обеспечьте прозрачную работу репозитория.
523. **CQRS с разными хранилищами для чтения и записи**. Команды пишут в PostgreSQL (нормализованно), запросы читают из Elasticsearch или MongoDB. Реализуйте асинхронную синхронизацию через брокер.
524. **Backpressure (защита от перегрузки)**. Ограничьте количество одновременно обрабатываемых запросов с помощью буферизированного канала-семафора. При заполнении очереди возвращайте 503 с Retry-After.
525. **Проектирование отказоустойчивости**. Примените Bulkhead (отдельные пулы соединений для разных downstream), Retry с exponential backoff, Timeout для всех внешних вызовов.
526. **Горизонтальное масштабирование: stateless-сервисы**. Спроектируйте сервис так, чтобы любой экземпляр мог обработать любой запрос. Вынесите состояние в Redis (сессии) и БД. Покажите балансировку через Nginx или Kubernetes Service.
527. **Бизнес-мониторинг архитектурных компонентов**. Для каждого сервиса и доменного действия экспортируйте метрики успеха/ошибок. Настройте дашборд, показывающий здоровье всей системы (архитектурный обзор).
528. **Strangler Fig Pattern (миграция монолита)**. Возьмите монолитный эндпоинт и проксируйте его через новый микросервис, постепенно вытесняя старую реализацию. Покажите на примере `/users`.
529. **API-First разработка с кодогенерацией**. Опишите сервис в OpenAPI 3.0, сгенерируйте серверный код (`oapi-codegen`), реализуйте только бизнес-логику. Повторите с gRPC (`protoc`).
530. **Комплексный проект: highload-сервис коротких ссылок**. Спроектируйте и реализуйте сервис, выдерживающий 10 000 RPS: кэширование в Redis, шардирование PostgreSQL по хэшу короткого ключа, идемпотентное создание, сбор метрик и трейсинг.
