## Часть XXII. Архитектура бэкендов на Go

### 112. Монолит и модульная архитектура

**Упражнение 22.1.** Спроектируй **CRUD-сервис на одном пакете**: `main.go`, `handlers.go`, `models.go`, `db.go`. Все в `package main`. Покажи, почему это работает для 100 строк, но ломается при росте.

**Упражнение 22.2.** Раздели на **слои (layered architecture)**: `handlers/` (HTTP), `services/` (бизнес-логика), `repositories/` (данные), `models/` (сущности). Каждый слой зависит только от нижележащего. Покажи направление зависимостей (внутрь).

**Упражнение 22.3.** Инвертируй зависимости через **интерфейсы**: `repository.UserRepository` — интерфейс, `repository.PostgresUserRepository` — реализация. `service.UserService` принимает `UserRepository`, не знает о PostgreSQL. Покажи DIP (Dependency Inversion Principle).

**Упражнение 22.4.** Реализуй **Clean Architecture** (Uncle Bob): слои `entities` → `usecases` → `interface_adapters` → `frameworks_drivers`. В Go: `domain/` (entities, interfaces), `usecase/` (interactors), `delivery/http/` (handlers), `repository/postgres/` (DB). Покажи, что `domain` не зависит ни от чего.

**Упражнение 22.5.** Реализуй **Hexagonal Architecture (Ports & Adapters)**: `domain/` (business logic), `ports/` (interfaces: `ForStoringUsers`, `ForSendingEmails`), `adapters/` (реализации: `PostgresUserStore`, `SMTPEmailSender`, `MockEmailSender`). Покажи, что домен — центр, всё остальное — заменяемые адаптеры.

**Упражнение 22.6.** Реализуй **Vertical Slice Architecture**: не разделяй по слоям, а по **фичам**: `features/user/create/`, `features/user/get/`, `features/order/create/`. Каждый slice содержит handler, service, repository, model. Покажи, что добавление фичи = добавление папки, не изменение 10 файлов.

**Упражнение 22.7.** Реализуй **Feature Modules с shared kernel**: `modules/user/`, `modules/order/`, `modules/payment/`, `shared/` (logger, config, middleware, errors). Каждый модуль — mini-clean-architecture. Покажи, как модули коммуницируют через **events**, не прямые вызовы.

**Упражнение 22.8.** Реализуй **Modular Monolith**: монолит, но с чёткими границами модулей. Каждый модуль имеет свой `internal/` (скрыт от других модулей). Коммуникация только через `pkg/events/` (event bus). Покажи путь к микросервисам: вырезай модуль, добавляй gRPC/HTTP API.

### 113. Микросервисы — проектирование и границы

**Упражнение 22.9.** Спроектируй **декомпозицию по DDD Bounded Contexts**: `User Context` (профиль, аутентификация), `Order Context` (заказы, корзина), `Payment Context` (списание, возврат), `Inventory Context` (склад, резервирование), `Shipping Context` (доставка, трекинг). Покажи, что каждый контекст — потенциальный микросервис.

**Упражнение 22.10.** Определи **Aggregate Roots**: `User` (root: `User`, entities: `Address`, `PaymentMethod`), `Order` (root: `Order`, entities: `OrderItem`, `OrderStatus`), `Product` (root: `Product`, entities: `ProductVariant`, `Inventory`). Покажи invariants: `Order.total = sum(OrderItem.subtotal)`.

**Упражнение 22.11.** Реализуй **Domain Events**: `OrderCreated`, `PaymentProcessed`, `InventoryReserved`, `ShipmentShipped`. Events — immutable facts, не команды. Публикуй внутри aggregate, когда state меняется. Покажи eventual consistency между контекстами.

**Упражнение 22.12.** Реализуй **Anti-Corruption Layer (ACL)**: `Order Service` интегрируется с legacy `Payment Gateway`. Создай `PaymentGatewayAdapter` (переводит наш `PaymentRequest` в их XML), `PaymentGatewayTranslator` (их callback → наши `PaymentProcessed` event). Legacy не "загрязняет" наш домен.

**Упражнение 22.13.** Спроектируй **Saga Orchestration**: `OrderSaga` (orchestrator) координирует: `CreateOrder` → `ReserveInventory` → `ProcessPayment` → `ShipOrder`. Каждый шаг — gRPC/HTTP/event. Compensation: `PaymentFailed` → `ReleaseInventory`. Реализуй state machine в `OrderSaga`.

**Упражнение 22.14.** Спроектируй **Saga Choreography**: нет центрального orchestrator'а. `OrderService` публикует `OrderCreated`. `InventoryService` подписывается, резервирует, публикует `InventoryReserved`. `PaymentService` подписывается... Покажи децентрализацию, но сложность отслеживания.

**Упражнение 22.15.** Реализуй **CQRS в микросервисе**: `Order Command Service` (PostgreSQL, normalized schema, transactions) обрабатывает `CreateOrder`, `CancelOrder`. `Order Query Service` (Elasticsearch/ClickHouse, denormalized views) отвечает на `GetOrderHistory`, `SearchOrders`. Синхронизация через events.

**Упражнение 22.16.** Реализуй **Event Sourcing**: `OrderAggregate` хранит не текущее состояние, а последовательность `OrderCreated`, `OrderItemAdded`, `OrderPaymentApplied`, `OrderShipped`. `GetState()` = `fold(events, initialState)`. Покажи: replay, temporal queries, audit trail.

**Упражнение 22.17.** Реализуй **Materialized View из Event Stream**: `OrderProjection` читает `OrderEvents` Kafka topic, строит `OrderSummary` в Redis/PostgreSQL. Пересоздай projection с нуля (replay с начала stream). Покажи, что view — disposable, source of truth — events.

**Упражнение 22.18.** Спроектируй **Strangler Fig Pattern**: legacy монолит на Java. Новый сервис `UserService` на Go. API Gateway маршрутизирует: `/users/*` → новый сервис, остальное → legacy. Постепенно вырезаем функциональность. Покажи incremental migration.

### 114. API Gateway и BFF

**Упражнение 22.19.** Реализуй **API Gateway** (Kong/Envoy/самописный): маршрутизация `/users/*` → `user-service:8080`, `/orders/*` → `order-service:8080`, `/payments/*` → `payment-service:8080`. Добавь: auth (JWT validation), rate limiting, request/response transformation.

**Упражнение 22.20.** Реализуй **Backend-for-Frontend (BFF)**: `Mobile BFF` (агрегирует данные для iOS/Android: мало полей, оптимизированные запросы), `Web BFF` (больше данных, SSR-ready), `Admin BFF` (все поля, фильтры, экспорт). Покажи, что generic API плох для всех клиентов.

**Упражнение 22.21.** Реализуй **GraphQL Gateway (Apollo Federation)**: `User Service` предоставляет `type User @key(fields: "id")`. `Order Service` extends `User` полем `orders: [Order]`. Gateway агрегирует schema'ы, маршрутизирует queries. Покажи federated graph.

**Упражнение 22.22.** Реализуй **gRPC-Gateway**: `order.proto` с HTTP annotations (`option (google.api.http) = { get: "/v1/orders/{id}" }`). `protoc-gen-grpc-gateway` генерирует HTTP REST API поверх gRPC. Один сервис — два протокола.

**Упражнение 22.23.** Реализуй **Sidecar Gateway (Istio/Linkerd)**: сервис не знает о TLS, mTLS, retry, circuit breaker, rate limit. Sidecar proxy (Envoy) добавляет это transparently. Покажи service mesh vs API gateway.

### 115. Data management и persistence

**Упражнение 22.24.** Спроектируй **Database-per-Service**: `User Service` → PostgreSQL (users, auth), `Order Service` → PostgreSQL (orders, items), `Inventory Service` → PostgreSQL (products, stock), `Analytics Service` → ClickHouse (events, aggregations). Покажи, что shared database — антипаттерн.

**Упражнение 22.25.** Реализуй **Saga с Outbox Pattern**: `Order Service` транзакция: `INSERT INTO orders ...` + `INSERT INTO outbox (topic, payload) ...`. Отдельный worker читает outbox, публикует в Kafka, удаляет. Покажи atomicity: БД commit = event published (eventually).

**Упражнение 22.26.** Реализуй **Change Data Capture (CDC)**: Debezium читает PostgreSQL WAL (`pgoutput`), публикует `dbserver1.public.orders` в Kafka. `Search Service` (Elasticsearch) и `Cache Service` (Redis) — consumers. Покажи zero-code data pipeline.

**Упражнение 22.27.** Спроектируй **Polyglot Persistence**: `User Service` — PostgreSQL (relational data), `Session Service` — Redis (TTL, fast access), `Search Service` — Elasticsearch (full-text), `Analytics` — ClickHouse (OLAP), `Logs` — Loki/Elasticsearch (time-series). Покажи правильный инструмент для задачи.

**Упражнение 22.28.** Реализуй **Read Replica Pattern**: `Order Service` пишет в PostgreSQL primary, читает из read replicas (load balancing). Replication lag: `SELECT pg_last_xact_replay_timestamp()` — покажи eventual consistency. Стратегия: "read own writes" (писатель читает primary).

**Упражнение 22.29.** Реализуй **Sharding**: `User Service` шардирует по `user_id % 16`. Router layer (pgBouncer/самописный) направляет запрос. Rebalancing: добавь шард, мигрируй диапазон (consistent hashing). Покажи горизонтальное масштабирование.

**Упражнение 22.30.** Реализуй **CQRS с Event Sourcing**: `Command Side` — Event Store (Kafka/NATS JetStream, append-only). `Query Side` — multiple projections: `OrderSummaryView` (Redis), `OrderAnalyticsView` (ClickHouse), `OrderSearchView` (Elasticsearch). Покажи, что projections независимы, replayable.

### 116. Communication patterns

**Упражнение 22.31.** Реализуй **Synchronous Communication (gRPC)**: `Order Service` вызывает `Inventory Service.Reserve()` synchronously. Покажи coupling: latency stack, cascading failure, tight runtime dependency. Когда уместно: simple operations, strong consistency needed.

**Упражнение 22.32.** Реализуй **Asynchronous Messaging (Events)**: `Order Service` публикует `OrderCreated`. `Inventory Service` подписывается, обрабатывает. Покажи decoupling: services evolve independently, temporal decoupling (consumer offline OK). Когда уместно: eventual consistency acceptable.

**Упражнение 22.33.** Реализуй **Asynchronous Request-Response (Commands)**: `Order Service` отправляет `ReserveInventoryCommand` в queue, ждёт `InventoryReserved` или `InventoryReservationFailed` event. Timeout: если нет ответа за 5s → compensation. Покажи async saga.

**Упражнение 22.34.** Реализуй **Circuit Breaker + Fallback**: `Order Service` → `Payment Service`. CB: Closed (normal) → Open (5 errors, 30s timeout) → Half-Open (1 trial). Fallback: если Open, queue payment for later processing (async). Покажи graceful degradation.

**Упражнение 22.35.** Реализуй **Bulkhead Pattern**: `Order Service` имеет пулы: `Pool A` (10 goroutines) для `Inventory Service`, `Pool B` (10 goroutines) для `Payment Service`, `Pool C` (5 goroutines) для `Email Service`. Если `Payment Service` медленный — `Pool B` заполнен, но `Pool A` и `Pool C` работают.

**Упражнение 22.36.** Реализуй **Retry with Exponential Backoff + Jitter**: `Inventory Service` временно недоступен. Retry: 100ms, 200ms, 400ms, 800ms + random jitter (0-100ms). Jitter предотвращает thundering herd при восстановлении. Max retries: 3, then circuit breaker.

**Упражнение 22.37.** Реализуй **Idempotency Key**: клиент генерирует `Idempotency-Key: uuid` для `CreateOrder`. Сервер хранит обработанные ключи (Redis, TTL=24h). При повторе с тем же ключом — возвращает cached response, не создаёт дубликат. Покажи exactly-once обработка.

**Упражнение 22.38.** Реализуй **Transactional Outbox + Inbox**: `Outbox` (публикация events) + `Inbox` (идемпотентная обработка входящих events). `Inbox` таблица: `idempotent_key`, `processed_at`. При получении `OrderCreated` — `INSERT INTO inbox ... ON CONFLICT DO NOTHING`. Покажи exactly-once consumption.

### 117. High-load и масштабирование

**Упражнение 22.39.** Спроектируй **Caching Strategy**: `Cache-Aside` (проверь кеш → miss → БД → кеш), `Read-Through` (кеш сам ходит в БД), `Write-Through` (писать в кеш и БД синхронно), `Write-Behind` (писать в кеш, async в БД). Покажи trade-offs по consistency и latency.

**Упражнение 22.40.** Реализуй **Multi-Level Cache**: L1 (in-process, `sync.Map`, 1ms), L2 (Redis, 5ms), L3 (PostgreSQL, 50ms). `GetUser`: L1 → L2 → L3. `Invalidate`: publish event, все уровни обновляются. Покажи hit rate per level.

**Упражнение 22.41.** Реализуй **Cache Warming**: при деплое новой версии — preload hot data into cache. `CacheWarmer` читает `SELECT * FROM products WHERE active = true ORDER BY views DESC LIMIT 10000`, пишет в Redis. Покажи, что cold cache = DB overload.

**Упражнение 22.42.** Реализуй **Rate Limiting (Token Bucket)**: `user_id` — 100 requests/minute. Redis: `INCR user:123:rate` + `EXPIRE 60`. Или `redis-cell` модуль. Distributed: все instances share Redis state. Покажи fairness.

**Упражнение 22.43.** Реализуй **Rate Limiting (Sliding Window Counter)**: Redis `ZADD` timestamp'ов, `ZREMRANGEBYSCORE` старых, `ZCARD` для подсчёта. Точнее, но дороже. Покажи precision vs performance trade-off.

**Упражнение 22.44.** Реализуй **Load Balancing (Layer 4)**: HAProxy/Nginx TCP passthrough. Round-robin, least-connections, IP-hash (sticky sessions). Покажи, что L4 не видит HTTP, работает с любым TCP.

**Упражнение 22.45.** Реализуй **Load Balancing (Layer 7)**: Nginx/Envoy HTTP routing. Path-based: `/api/v1/users/*` → `user-service-v1`, `/api/v2/users/*` → `user-service-v2`. Header-based: `Canary: true` → `user-service-canary`. Cookie-based: `version=v2` → `user-service-v2`.

**Упражнение 22.46.** Реализуй **Auto-Scaling (HPA)**: Kubernetes `HorizontalPodAutoscaler` по CPU (target 70%), memory, custom metrics (Kafka lag, request latency). `KEDA` для event-driven scaling: 0 replicas when no messages, scale to 100 when 10000 messages in queue.

**Упражнение 22.47.** Реализуй **Database Connection Pooling**: `pgxpool` с `MaxConns=50`, `MinConns=10`, `MaxConnLifetime=1h`. Мониторинг: `pgxpool.Stat().TotalConns()`, `IdleConns()`, `WaitCount()`. Покажи, что pool exhaustion = cascading failure.

**Упражнение 22.48.** Реализуй **Async Processing (Worker Pool)**: HTTP API принимает `CreateReportRequest`, возвращает `job_id`. Job queue (Redis/RabbitMQ/Kafka). Workers (10 goroutines) обрабатывают. Client polls `GET /jobs/{id}/status`. Покажи decoupling от long-running tasks.

**Упражнение 22.49.** Реализуй **Backpressure**: `Order Service` получает 10000 RPS, `Payment Service` обрабатывает 1000 RPS. Queue (Kafka) буферизует. Если queue > 100000 messages — reject new requests (`503 Service Unavailable`), клиент retry. Покажи, что без backpressure — OOM, data loss.

**Упражнение 22.50.** Реализуй **Graceful Degradation**: `Recommendation Service` недоступен. `Product Service` возвращает products без recommendations (default: popular items). `Search Service` returns results without personalization. Покажи partial functionality vs total failure.

### 118. Security и compliance

**Упражнение 22.51.** Реализуй **Zero Trust Architecture**: нет "internal network" = trusted. Каждый сервис аутентифицирует caller (mTLS + JWT). Каждый request авторизуется. Network segmentation: `frontend` → `api-gateway` → `services`, но `services` не общаются напрямую без auth.

**Упражнение 22.52.** Реализуй **mTLS everywhere**: сервисы имеют certificates issued by internal CA. `Order Service` verifies `Payment Service` certificate, `Payment Service` verifies `Order Service`. No service-to-service trust without mutual verification.

**Упражнение 22.53.** Реализуй **OAuth2/OIDC**: `API Gateway` → `Authorization Server` (Keycloak/Auth0). Client получает `access_token` (JWT). Gateway validates token, extracts `sub` (user_id), `roles`, `scopes`. Передаёт `X-User-ID`, `X-Roles` downstream. Покажи token introspection vs local validation.

**Упражнение 22.54.** Реализуй **RBAC + ABAC**: `RBAC`: `role=admin` → all operations, `role=user` → own data only. `ABAC`: `order.owner_id == user.id` OR `user.hasPermission("orders:view:all")`. Policy engine (OPA/Rego) для сложных правил.

**Упражнение 22.55.** Реализуй **Data Encryption**: encryption at rest (PostgreSQL TDE, disk encryption), encryption in transit (TLS 1.3), field-level encryption (PII: `encrypt(credit_card)` в application layer, key in HSM/Vault). Покажи defense in depth.

**Упражнение 22.56.** Реализуй **Secret Management**: нет secrets in code/env. `HashiCorp Vault` / `AWS Secrets Manager` / `Kubernetes External Secrets`. Application requests secret at startup, caches in memory, rotates automatically. Audit: who accessed what secret when.

**Упражнение 22.57.** Реализуй **Audit Logging**: immutable log of all sensitive operations. `who` (user/service), `what` (operation), `when` (timestamp), `on_whom` (target), `result` (success/failure), `before`/`after` (for changes). Append-only, signed, replicated. Retention: 7 years.

**Упражнение 22.58.** Реализуй **GDPR/CCPA Compliance**: `right to access` — export all user data. `right to erasure` — delete/anonymize user data across all services. `data portability` — machine-readable export. `consent management` — track what user consented to, when, revoke.

**Упражнение 22.59.** Реализуй **Input Validation Defense**: `whitelist` approach (accept known-good), not `blacklist` (reject known-bad). Validate at edge (API Gateway), validate at service, validate at database (constraints). Sanitize: HTML escape, SQL parameterization, path traversal prevention.

**Упражнение 22.60.** Реализуй **Rate Limiting + DDoS Protection**: per-IP (1000 req/min), per-user (100 req/min), per-endpoint (`/login` — 5 req/min). CloudFlare/AWS Shield for L3/L4. Application-level for L7. Challenge (CAPTCHA) for suspicious patterns.

### 119. DevOps и deployment

**Упражнение 22.61.** Реализуй **CI/CD Pipeline**: GitHub Actions/GitLab CI. Stages: `lint` (`golangci-lint`), `test` (`go test -race -cover`), `build` (`go build`, Docker build), `scan` (Trivy/Snyk for vulnerabilities), `deploy-staging` (auto), `deploy-production` (manual approval). Gates: coverage > 80%, no critical CVEs.

**Упражнение 22.62.** Реализуй **GitOps (ArgoCD/Flux)**: Git repo = single source of truth for Kubernetes manifests. ArgoCD watches repo, syncs cluster. `Application` CRD defines sync policy (auto/manual), prune (delete resources not in git), self-heal. Rollback = `git revert` + sync.

**Упражнение 22.63.** Реализуй **Blue-Green Deployment**: two identical environments. Blue = current, Green = new. Test green, switch traffic (DNS/load balancer), blue stays for instant rollback. Zero downtime, but double resources.

**Упражнение 22.64.** Реализуй **Canary Deployment**: 1% traffic to new version. Monitor: error rate, latency, business metrics. Auto-promote: 1% → 10% → 50% → 100% if metrics healthy. Auto-rollback if error rate > baseline + 5%. Argo Rollouts/Flagger.

**Упражнение 22.65.** Реализуй **Feature Flags**: `LaunchDarkly`/`Unleash`/`custom`. `if feature.IsEnabled("new-checkout", userID) { newCheckout() } else { oldCheckout() }`. Gradual rollout: 1% users, 10%, 100%. Kill switch: disable feature in 1 second without deployment.

**Упражнение 22.66.** Реализуй **Infrastructure as Code (Terraform/Pulumi)**: PostgreSQL cluster, Redis cluster, Kubernetes cluster, load balancer, DNS, TLS certificates. Version controlled, code-reviewed, tested (terratest). Drift detection: `terraform plan` shows differences.

**Упражнение 22.67.** Реализуй **Observability-Driven Deployment**: deploy → monitor SLO for 30 min → auto-promote or rollback. Metrics: error rate, latency p95, business metrics (orders/min). If any metric degrades → automatic rollback to previous version.

**Упражнение 22.68.** Реализуй **Chaos Engineering**: `LitmusChaos`/`ChaosMesh`. Kill random pod: service should auto-heal (Kubernetes restart), traffic should reroute (no 500s). Network partition: split-brain detection, quorum requirements. Latency injection: circuit breaker should open.

**Упражнение 22.69.** Реализуй **Disaster Recovery**: RPO (Recovery Point Objective) = 5 min, RTO (Recovery Time Objective) = 15 min. Multi-AZ: synchronous replication (RPO=0). Multi-region: asynchronous replication (RPO=5min). Automated failover: Patroni/HAProxy for PostgreSQL. Regular DR drills.

**Упражнение 22.70.** Реализуй **Cost Optimization**: right-sizing (monitor CPU/memory usage, adjust requests/limits), spot instances for batch jobs, reserved instances for baseline, auto-scaling to zero (KEDA for dev environments). FinOps: team accountability for cloud spend.

### 120. Enterprise patterns и сложные системы

**Упражнение 22.71.** Спроектируй **Multi-Tenant SaaS**: `shared database, shared schema` (tenant_id column, row-level security), `shared database, separate schema` (schema per tenant), `separate database` (isolation, cost). Покажи trade-offs: isolation, cost, complexity, compliance.

**Упражнение 22.72.** Реализуй **Tenant Isolation**: `tenant_id` in every table, `WHERE tenant_id = current_tenant()` in every query (RLS policy in PostgreSQL). JWT contains `tenant_id`, service extracts and enforces. Cross-tenant queries forbidden. Resource quotas per tenant.

**Упражнение 22.73.** Реализуй **Plugin Architecture**: core system + plugins (shared library, gRPC service, WebAssembly module). `PluginManager` loads plugins dynamically. Sandboxing: WebAssembly (WASI) for untrusted plugins, gRPC for trusted. Version compatibility: plugin API versioning.

**Упражнение 22.74.** Реализуй **Workflow Engine**: DSL for business processes (BPMN-like). `OrderWorkflow`: `ReceiveOrder` → `ValidateInventory` → `CheckCredit` → `ProcessPayment` → `ShipOrder` → `SendInvoice`. Visual designer, execution engine, monitoring. Long-running: wait for human approval (days).

**Упражнение 22.75.** Реализуй **Rules Engine**: business rules as data, not code. `if order.total > 1000 and customer.tier == "gold" then discount = 10%`. Drools-like in Go: parse rules, build RETE network, evaluate facts. Hot reload: change rules without deployment.

**Упражнение 22.76.** Реализуй **Event-Driven Architecture (EDA)**: все state changes — events. `Event Store` (Kafka/NATS) = source of truth. `Projections` = read models. `Process Managers` = orchestrate sagas. `Event Replayers` = rebuild state, debug, audit. No direct DB writes from handlers.

**Упражнение 22.77.** Реализуй **Command Query Responsibility Segregation (CQRS) at scale**: `Write Model` — Event Store, strong consistency, simple queries by ID. `Read Models` — multiple, optimized per query: Elasticsearch (search), Redis (hot data), ClickHouse (analytics), Neo4j (graph). Eventual consistency: seconds, monitored lag.

**Упражнение 22.78.** Реализуй **Event Sourcing + Snapshotting**: 1M events per aggregate → replay takes 10s. Snapshot every 100 events: `Snapshot{Version, State}`. Replay: load latest snapshot + events after version. Compaction: archive old events, keep recent + snapshots.

**Упражнение 22.79.** Реализуй **Distributed Transaction (Saga) with Compensation**: `BookHotel` → `BookFlight` → `BookCar`. Если `BookFlight` fails → `CancelHotel`. Compensation idempotent, retryable, order-independent where possible. Timeout: if compensation fails, alert human intervention.

**Упражнение 22.80.** Реализуй **Data Mesh**: domain-oriented data ownership. `User Domain` owns `user data`, publishes `user events`. `Order Domain` owns `order data`. `Analytics Domain` consumes events, builds datasets. Self-serve data platform: discover, access, quality, governance.

### 121. High-load и performance engineering

**Упражнение 22.81.** Спроектируй **System for 1M RPS**: horizontal scaling (1000 instances), stateless services, shared-nothing architecture. Load balancer (L4) distributes. Caching at every layer: CDN (static), edge cache (API responses), application cache (hot data), database cache (query results).

**Упражнение 22.82.** Реализуй **Connection Pooling at Scale**: 1000 instances × 50 DB connections = 50000 connections. PostgreSQL limit: ~10000. Solution: PgBouncer (connection pooler), `transaction` pooling mode. Or: RDS Proxy, read replicas, connection multiplexing.

**Упражнение 22.83.** Реализуй **Request Coalescing**: 1000 requests for same `product:123` simultaneously. Only 1 goes to DB, 999 wait for result. `singleflight.Group` (Go) or `cache stampede` protection. Reduces DB load 1000x for hot keys.

**Упражнение 22.84.** Реализуй **Request Deduplication**: same `CreateOrder` request retried by client (network timeout). `Idempotency-Key` + `singleflight` = process once, return cached response. Even across instances: Redis distributed lock.

**Упражнение 22.85.** Реализуй **Prefetching + Predictive Caching**: ML model predicts "user likely to view product X next". Prefetch into cache before request. Warm CDN edge for geographic region. Reduce latency from 200ms to 20ms.

**Упражнение 22.86.** Реализуй **Load Shedding**: system overloaded (CPU > 90%, latency p99 > 2s). Drop low-priority requests (analytics, non-critical reads). Accept high-priority (payments, critical writes). `503` with `Retry-After` header. Client backs off exponentially.

**Упражнение 22.87.** Реализуй **Admission Control**: `token bucket` for incoming requests. If bucket empty — reject immediately. Protects backend from overload. Separate buckets per priority, per tenant, per endpoint. Dynamic: reduce rate if latency grows.

**Упражнение 22.88.** Реализуй **Parallel Processing**: `GetOrderDetails` needs data from 5 services. Sequential: 5 × 100ms = 500ms. Parallel: `errgroup.Group`, 5 concurrent requests, 100ms + overhead. Timeout: `context.WithTimeout(150ms)`, return partial if some fail.

**Упражнение 22.89.** Реализуй **Batching + Windowing**: 1000 `GetUser` requests/sec. Individual: 1000 DB queries. Batched: accumulate 50ms window, 1 query `SELECT * FROM users WHERE id IN (...)`. 1000 → 20 queries. Trade-off: latency + throughput.

**Упражнение 22.90.** Реализуй **Approximation Algorithms**: `HyperLogLog` for unique users (0.1% error, 1KB memory vs 1GB for exact). `Count-Min Sketch` for frequency (heavy hitters). `Bloom Filter` for "probably in set" (cache negative lookups). Acceptable for analytics, not billing.

### Ключевые моменты для освоения архитектуры:

1. **Start simple, evolve**: монолит → modular monolith → microservices. Не начинай с микросервисов. Extract service когда bounded context ясен, team растёт, deployment independence нужен.

2. **Domain-Driven Design**: бизнес-логика в центре. Термины бизнеса в коде. Aggregates, entities, value objects, domain events — защищают invariants.

3. **Event-driven > synchronous**: асинхронные события дают loose coupling, temporal decoupling, natural audit trail. Но добавляют complexity: eventual consistency, idempotency, ordering.

4. **Observability-first**: если нельзя наблюдать — нельзя управлять. Метрики, логи, трейсы — не после фичи, а вместе с ней.

5. **Security by design**: zero trust, defense in depth, least privilege. Не "добавим security потом" — это never happens.

6. **Performance is feature**: SLO — часть требований. Error budget — инструмент управления. Load testing, profiling, chaos engineering — регулярные практики.

7. **Culture > Tools**: Conway's Law — архитектура отражает коммуникации в организации. Inverse Conway Maneuver: организуй команды для желаемой архитектуры.

8. **Trade-offs everywhere**: нет "правильного" решения. Есть контекст, constraints, priorities. Документируй decisions (ADRs — Architecture Decision Records).

9. **Automate everything**: CI/CD, infrastructure, testing, security scanning, deployment, rollback. Если ручной шаг — он сломается в 3 часа ночи.

10. **Learn from failures**: post-mortem без blame, public incident reviews, chaos engineering. Resilience — не отсутствие failure, а ability to recover.
