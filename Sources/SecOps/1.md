Вот продолжение — **33 упражнения** (с 430 по 462) по безопасности инфраструктуры и SecOps: защита цепочки поставок ПО, ядерная безопасность сокетов и контейнерная изоляция. Структура сохранена: блоки по темам, внутри каждого — от простого к сложному.

## Блок 36. Supply Chain Security, `govulncheck` и SLSA

### Уровень 1. Базовый сканинг и аудит зависимостей
430. **Запуск `govulncheck`.** Установите `golang.org/x/vuln/cmd/govulncheck`, запустите на реальном Go-проекте. Проанализируйте вывод: различите `Vulnerability #1: GO-2024-...` с `Found in` (пакет импортирован) и `Not found in` (пакет есть в графе, но уязвимый символ не вызывается). Объясните, почему call graph analysis снижает false positives.
431. **Сравнение с ручным аудитом.** Выполните `go list -m all | grep <vulnerable_pkg>` и `go mod graph`. Покажите, как `govulncheck` использует OSV (Open Source Vulnerabilities) database и `vulncheck.Binary` для бинарников. Объясните, почему `govulncheck ./...` анализирует исходники, а `govulncheck -mode binary ./app` — скомпилированный бинарник.
432. **Генерация SBOM.** Используйте `syft` (или `cyclonedx-gomod`) для создания SBOM (CycloneDX/SPDX) из `go.mod`. Проверьте наличие `purl`, `license`, `hash`. Объясните NTIA minimum elements: supplier, component name, version, other unique identifiers, dependency relationship, author of SBOM data.
433. **Уязвимость в indirect dependency.** Создайте ситуацию: `go.mod` содержит `github.com/gin-gonic/gin v1.9.0`, которая тянет `github.com/chenzhuoyu/base64x` со старой косвенной зависимостью. Покажите `go mod why github.com/chenzhuoyu/base64x`. Исправьте через `go get -u` или `replace` директиву. Объясните, почему `go mod tidy` не всегда поднимает indirect до безопасной версии.

### Уровень 2. SLSA, Provenance и подпись артефактов
434. **SLSA Levels в теории и на практике.** Напишите эссе с примерами для Go-проекта: **Level 1** — SBOM + provenance (who, what, when); **Level 2** — signed provenance + hosted build (GitHub Actions); **Level 3** — hardened build (hermetic, reproducible, no external network, readonly source); **Level 4** — two-person review + reproducible builds. Спроектируйте CI/CD для достижения Level 3.
435. **Cosign: подпись бинарника.** Используйте `cosign sign-blob` для подписи Go-бинарника. Проверьте через `cosign verify-blob`. Объясните keyless signing: OIDC (GitHub Actions token) → Fulcio (CA) → ephemeral key pair → подпись → Rekor (transparency log). Покажите, что private key никогда не существует на диске.
436. **Rekor Transparency Log.** После подписи найдите запись в Rekor через `rekor-cli get --uuid <...>` или `cosign verify` с `--rekor-url`. Объясните, как transparency log защищает от отката подписей (software supply chain transparency): злоумышленник не может тайно подписать вредоносный бинарник, не оставив публичной записи.
437. **SLSA Provenance generation.** Настройте `slsa-github-generator` (`.github/workflows/slsa3.yml`) для сборки Go-приложения. Получите `provenance.intoto.jsonl`. Проверьте аттестацию через `cosign verify-attestation --type slsaprovenance`. Объясните, что provenance связывает artifact с конкретным git commit, builder и build parameters.

### Уровень 3. Защита реестров и зависимостей
438. **Dependency Confusion Attack.** Создайте приватный модуль `company.com/internal/api`. Покажите, что если `GOPRIVATE` не настроен, `go get` может обратиться к public proxy и скачать одноимённый публичный модуль (если злоумышленник его зарегистрирует). Исправьте: `GOPRIVATE=company.com`, `GONOSUMDB=company.com`, `GONOPROXY=company.com`. Объясните разницу между тремя переменными.
439. **Checksum Database (`sum.golang.org`).** Покажите, как `go.sum` защищает от MITM: при `go mod tidy` Go сверяет hash модулей с `GOSUMDB`. Объясните, почему отключение `GOSUMDB=off` — антипаттерн. Покажите, как `go env GOSUMDB` работает с `sum.golang.org` (публичная аудиторская база).
440. **Private Module Proxy (Athens/Artifactory).** Настройте `GOPROXY=https://athens.company.com,https://proxy.golang.org,direct`. Покажите, что приватные модули кэшируются и проверяются внутри perimeter. Объясните air-gapped сценарий: `GOPROXY=https://athens.company.com` (без fallback) + `GONOSUMDB=*` + `GONOPROXY=*`.
441. **Vendoring для immutable builds.** Выполните `go mod vendor`. Соберите с `-mod=vendor`. Покажите, что сборка не требует сети. Объясните, когда vendoring предпочтительнее proxy: air-gapped, compliance (все исходники в репозитории), reproducibility (фиксированный набор файлов).

### Уровень 4. CI/CD hardening и runtime
442. **Reproducible Builds.** Настройте `GOFLAGS="-trimpath"` и `-ldflags="-s -w -buildid="`. Соберите бинарник дважды на разных машинах с одинаковым Go version. Сравните `sha256sum`. Объясните, почему полная воспроизводимость в Go сложна (build IDs, CGO, timestamps в `-ldflags`, `math/rand` в генераторе).
443. **Binary Hardening.** Проверьте защиты через `checksec --file=./binary`. Объясните, что Go runtime уже включает: stack canaries (`-fstack-protector` equivalent), PIE (`-buildmode=pie` для ASLR), partial RELRO. Покажите, как включить `GOAMD64=v3` для CET/IBT (где поддерживается). Объясните, почему `CGO_ENABLED=0` уменьшает attack surface.
444. **GitHub Actions Hardening.** Настройте workflow: `actions/checkout` с `persist-credentials: false`, `pin` actions по SHA (не по floating tag), `dependabot` для GitHub Actions. Объясните supply chain атаки на CI/CD (compromised action, typosquatting в marketplace).
445. **Container Image Scanning.** Используйте `trivy image` или `grype` для сканирования образа Go-приложения. Сравните базовые образы: `alpine`, `debian:slim`, `distroless`, `scratch` + статический бинарник. Покажите, что `distroless` минимизирует CVE surface. Объясните, почему `scratch` + `CGO_ENABLED=0` — идеал для Go.

## Блок 37. Защита сетевых сокетов на уровне ядра

### Уровень 1. Slowloris и таймауты приложения
446. **Slowloris: демонстрация атаки.** Напишите (в образовательных целях) Go-«атакующий»: открывает 1000 TCP-соединений, шлёт HTTP-заголовки байт за байтом с `time.Sleep(10s)` между байтами. Запустите против дефолтного `http.ListenAndServe`. Покажите, что сервер исчерпывает лимит соединений и перестаёт отвечать legit клиентам.
447. **Read/Write/Idle Timeouts.** Настройте `http.Server` с `ReadHeaderTimeout: 5s`, `ReadTimeout: 10s`, `WriteTimeout: 10s`, `IdleTimeout: 120s`. Повторите Slowloris. Покажите, что атака умирает на `ReadHeaderTimeout`. Объясните разницу: `ReadTimeout` (весь запрос + body), `ReadHeaderTimeout` (только headers, защита от Slowloris), `IdleTimeout` (keep-alive).
448. **Connection Limits.** Реализуйте `netutil.LimitListener` (или свой atomic-счётчик) с `maxConns = 100`. При превышении — новые соединения немедленно закрываются (`TCP RST` или `503` + `Connection: close`). Покажите, что это защищает от ресурс-исчерпания, но не от DDoS на уровне ядра (SYN flood).
449. **Rate Limiting на accept.** Реализуйте middleware/обёртку над `net.Listener`: token bucket (`x/time/rate`) на новые соединения per IP (определяем через `conn.RemoteAddr()`). При превышении — `conn.Close()`. Объясните, как это защищает от application-level connection floods, но требует `sync.Map` для state per IP.

### Уровень 2. SYN flood и ядерные механизмы
450. **SYN Cookies.** Проверьте `sysctl net.ipv4.tcp_syncookies`. Объясните механизм: при переполнении `tcp_max_syn_backlog` ядро не выделяет `struct request_sock`, а кодирует state в ISN (Initial Sequence Number). При легитимном ACK — восстанавливает соединение. Покажите, что Go-приложение ничего не замечает (защита на уровне ядра).
451. **SYN Backlog Tuning.** Покажите `sysctl net.ipv4.tcp_max_syn_backlog`, `net.core.somaxconn`, `net.core.netdev_max_backlog`. Объясните связь с `syscall.Listen(fd, backlog)` в Go: `backlog` = `min(somaxconn, переданный аргумент)`. Настройте `somaxconn = 4096` для high-load сервера. Покажите через `ss -s` и `ss -lnt` текущий backlog.
452. **TCP_DEFER_ACCEPT и TCP_FASTOPEN.** Настройте `net.ListenConfig` с `Control` функцией: `syscall.SetsockoptInt(fd, syscall.IPPROTO_TCP, syscall.TCP_DEFER_ACCEPT, 1)` (или `TCP_FASTOPEN`). Объясните: `DEFER_ACCEPT` не передаёт соединение в userspace до первых данных (защита от empty SYN-ACK floods + меньше `accept()` вызовов). `FASTOPEN` — data in SYN, уменьшает RTT.
453. **Conntrack Table Exhaustion.** Покажите `sysctl net.netfilter.nf_conntrack_max`, `nf_conntrack_count`. Объясните, как iptables `state` module использует conntrack table. При DDoS (много уникальных src IP) таблица переполняется, и ядро начинает дропать пакеты (`dmesg | grep conntrack`). Покажите решение: `iptables -t raw -A PREROUTING -p tcp --dport 8080 -j NOTRACK` (для stateless фильтрации).

### Уровень 3. SecComp — фильтрация syscall
454. **SecComp Basics (libseccomp-golang).** Напишите Go-программу, которая через `github.com/seccomp/libseccomp-golang` разрешает только `read`, `write`, `exit`, `exit_group`, `rt_sigreturn`, `epoll_wait`, `accept4`, `close`. При попытке `os.Open` (syscall `openat`) — процесс получает `SIGSYS` и умирает. Объясните whitelist-подход.
455. **SecComp BPF вручную.** Создайте `[]unix.SockFilter` вручную: `BPF_STMT` для загрузки syscall number, `BPF_JUMP` для сравнения. Примените через `unix.Prctl(unix.PR_SET_SECCOMP, unix.SECCOMP_MODE_FILTER, ...)`. Объясните, что SecComp filter — это BPF-программа, выполняемая ядром на каждом syscall.
456. **Syscall Audit для Go-приложения.** Запустите Go HTTP-сервер под `strace -f -e trace=%network,%file -o trace.log`. Проанализируйте все syscall. Составьте whitelist для SecComp на основе реального trace. Объясните, почему Go runtime требует `mmap`, `futex`, `clone`, `sigaltstack`, `epoll_create1`, `getrandom` — и как их не забыть в фильтре.
457. **SecComp Notify (Linux 5.0+).** Используйте `seccomp_unotify` для перехвата `openat` в userspace. Напишите supervisor (отдельный процесс), который получает уведомление, проверяет путь (`/app/data/*` — разрешить, `/etc/shadow` — запретить), отправляет ответ ядру. Объясните, как это используется в rootless containers (containerd/runc).

### Уровень 4. Контейнеры, MAC и eBPF
458. **SecComp Profile для контейнера.** Напишите JSON SecComp profile для Docker: `defaultAction: SCMP_ACT_ERRNO`, разрешить `accept4`, `read`, `write`, `epoll_wait`, `futex`, `mmap`, `munmap`, `clone`, `exit`, `exit_group`, `rt_sigreturn`, `getrandom`. Запретить `execve`, `execveat`, `ptrace`, `mount`, `umount2`, `chroot`, `setns`, `unshare`. Объясните, почему `execve` — критично (RCE prevention).
459. **AppArmor Profile.** Напишите AppArmor profile для Go-бинарника: `network inet stream`, `capability net_bind_service`, `/app/config/** r`, `/app/data/** rwk`, deny `/etc/** w`. Загрузите через `apparmor_parser`. Объясните MAC (Mandatory Access Control) vs DAC: AppArmor ограничивает *программу*, независимо от user ID.
460. **Linux Capabilities.** Напишите Go-программу, которая через `golang.org/x/sys/unix` сбрасывает все capabilities через `capset` (или `prctl(PR_CAP_AMBIENT, PR_CAP_AMBIENT_CLEAR_ALL, 0, 0, 0)`). Оставьте только необходимые (`CAP_NET_BIND_SERVICE` если нужен порт <1024). Объясните, почему `CAP_NET_BIND_SERVICE` не нужен для портов >1024, и зачем `ALL` drop.
461. **Network Namespaces + cgroup v2.** Создайте network namespace (`ip netns add appns`), запустите Go-приложение внутри через `ip netns exec appns ./app`. Настройте cgroup v2: `echo 100000000 > /sys/fs/cgroup/app/memory.max`, `echo "100000 1000000" > cpu.max`, `echo 100 > pids.max`. Объясните, как изоляция ресурсов защищает от fork bombs и memory exhaustion.
462. **eBPF для Runtime Security.** Напишите простую eBPF-программу (C + `cilium/ebpf` или `libbpf-go`) для трассировки `tcp_connect` в Go-приложении. При соединении с неожиданным IP (не из whitelist) — отправляйте alert в userspace. Объясните, как eBPF позволяет обнаруживать аномалии без модификации приложения (runtime security, Falco-style).

## Как встроить в общий план обучения

**Рекомендуемый порядок прохождения:**

1. **Блок 36 (Supply Chain)** — начните после Блока 10 (криптография) и Блока 13 (AppSec), так как supply chain — это логическое продолжение безопасности: защита не только runtime, но и всего, что предшествует деплою.
2. **Блок 37 (Kernel Security)** — финальный блок инфраструктурной безопасности. Требует понимания `syscall` (Блок 6), `net/http` server internals (Блок 18/21), и `cgo` (Блок 5) для eBPF/libseccomp. Знание GMP (Блок 1) помогает понять, почему `LimitListener` с atomic-счётчиком масштабируется лучше mutex.

**Ключевые инструменты и команды для тренировки:**
```bash
# govulncheck
go install golang.org/x/vuln/cmd/govulncheck@latest
govulncheck ./...

# Cosign / SLSA
cosign sign-blob --yes --output-signature=sig app
cosign verify-blob --signature=sig --certificate=app.pem app

# SecComp
strace -f -e trace=%network,%file -o trace.log ./app
checksec --file=./app

# Kernel tuning
sysctl -w net.ipv4.tcp_syncookies=1
sysctl -w net.core.somaxconn=4096
iptables -t raw -A PREROUTING -p tcp --dport 8080 -j NOTRACK
```

**Что фиксировать в результатах:**
- Для Supply Chain: отчёт `govulncheck`, SBOM-файл, `provenance.intoto.jsonl`, `checksec` вывод до/после hardening.
- Для Kernel Security: `sysctl` конфигурация, `strace` логи, SecComp JSON profile, AppArmor `.aa` профиль, proof of Slowloris mitigation (`wrk`/`slowhttptest` + `ss -s`).

Если нужно — могу детально расписать **любое конкретное упражнение** с шаблоном кода, или выдать финальный блок на тему *«Каналы в рантайме, netpoller, sync.Pool, memory model и race detector»*.
