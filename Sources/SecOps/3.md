Инфраструктурная безопасность (SecOps) — это последний рубеж обороны. Даже если твой код идеален, уязвимая зависимость (`log4j` гоу... точнее, `go-jose`) или неправильно настроенный сокет могут положить весь продакшен. 

Завершаем наш марафон **22 упражнениями** (с 979 по 1000), которые доведут количество задач ровно до **1000**. Этот финальный блок научит тебя защищать цепочку поставок (Supply Chain) и настраивать ядро Linux для отражения DDoS-атак.

### Блок 111: Безопасность цепочки поставок (Supply Chain Security)
*Цель: Исключить использование уязвимых библиотек и предотвратить внедрение вредоносного кода через зависимости.*

979. **[Базовый `govulncheck`]** Установи утилиту `go install golang.org/x/vuln/cmd/govulncheck@latest`. Запусти её в своем проекте. Изучи отчет: утилита показывает не просто наличие уязвимой библиотеки, но и проверяет, *вызывает ли твой код* уязвимую функцию (анализ графа вызовов).
980. **[Симуляция уязвимости]** Подключи старую версию пакета с известной CVE (например, `github.com/golang-jwt/jwt/v4 v4.0.0`). Запусти `govulncheck`. Убедись, что утилита нашла уязвимость. Обнови пакет до последней версии и проверь, что отчет чист.
981. **[Каверзный кейс — Transitive Dependency]** Ты не используешь уязвимый пакет напрямую, но его использует одна из твоих зависимостей. Запусти `govulncheck`. Если уязвимая функция не вызывается в твоем графе вызовов, `govulncheck` выдаст предупреждение, но не ошибку. Объясни, почему это безопаснее, чем просто сканировать `go.sum`.
982. **[CI/CD Integration]** Добавь шаг `govulncheck ./...` в GitHub Actions. Настрой его так, чтобы пайплайн падал (non-zero exit code), если найдена уязвимость, которая реально используется в коде.
983. **[Private Go Proxy]** Если ты пишешь проприетарный код, по умолчанию Go может слать хеши твоих модулей на публичный `proxy.golang.org` для верификации. Настрой переменную окружения `GOPRIVATE=gitlab.mycompany.com/*`, чтобы Go не утекал информацию о внутренних пакетах.
984. **[go mod verify]** Запусти `go mod verify`. Объясни, что эта команда проверяет соответствие скачанных модулей в `$GOPATH/pkg/mod` хэшам из `go.sum` (защита от подмены файлов на диске).
985. **[Vendoring & Auditing]** Выполни `go mod vendor`. Передай папку `vendor/` на проверку в SCA-сканер (например, Snyk или Trivy). Оцени плюсы подхода (воспроизводимость сборки, аудит исходников) и минусы (огромный PR, если обновить зависимость).
986. **[SBOM (Software Bill of Materials)]** Сгенерируй SBOM для своего бинарника с помощью утилиты `syft`. Это JSON/XML файл со списком всех зависимостей и их версий. Изучи, зачем это нужно энтерпрайзу (для быстрого поиска уязвимостей по списку CVE, не разбирая исходники).
987. **[Каверзный кейс — Dependency Confusion]** Злоумышленник зарегистрировал в `proxy.golang.org` публичный пакет с тем же именем, что и твой внутренний приватный пакет (например, `github.com/company/utils`), но с версией `v99.0.0`. Если `GOPRIVATE` не настроен, Go может подтянуть вредоносный код. Настрой `GOPRIVATE` и проверь, что Go игнорирует публичную версию.
988. **[Reproducible Builds]** Собери бинарник дважды на разных машинах (с одинаковыми версиями Go). Сравни их хэши (`sha256sum`). Если они совпадают — сборка воспроизводима (защита от внедрения бэкдоров в процессе компиляции).

### Блок 112: Защита сетевых сокетов на уровне ОС (Hardening)
*Цель: Защитить Go-сервер от исчерпания файловых дескрипторов, медленных атак (Slowloris) и ограничить системные вызовы (Seccomp).*

989. **[Slowloris Simulation]** Напиши скрипт на Python/Bash (или Go-клиент), который открывает 1000 TCP-соединений к твоему Go `net/http` серверу и каждые 10 секунд шлет по 1 байту (например, `X-a: 1\r\n`). Убедись, что сервер быстро исчерпывает лимит файловых дескрипторов или потоков (OOM).
990. **[Mitigation: ReadTimeout]** Установи `http.Server{ReadTimeout: 5 * time.Second}`. Перезапусти атаку. Сервер должен закрывать соединения, которые не успели прислать заголовки за 5 секунд.
991. **[Mitigation: ReadHeaderTimeout]** В Go есть отдельный таймаут для заголовков. Установи `ReadHeaderTimeout: 5s`, но оставь `ReadTimeout: 60s`. Объясни, почему это лучше: мы сбрасываем медленные хедеры (Slowloris), но даем клиенту 60 секунд на загрузку большого файла (тела запроса).
992. **[Mitigation: MaxHeaderBytes]** Установи `MaxHeaderBytes: 1 << 20` (1MB). Отправь серверу 10MB заголовков. Сервер должен разорвать соединение, защищая память от переполнения.
993. **[File Descriptor Limits]** Напиши сервер, который принимает 10 000 соединений. По умолчанию лимит открытых файлов (ulimit) в Linux равен 1024. Поймай ошибку `socket: too many open files`. Увеличь лимит через `ulimit -n 65535` перед запуском Go-программы.
994. **[SO_REUSEPORT]** Напиши сервер, использующий `net.ListenConfig{Control: SO_REUSEPORT}`. Запусти 2 экземпляра этого сервера на одном порту (8080). Ядро Linux само будет балансировать входящие соединения между двумя процессами (Load Balancing на уровне ядра ОС).
995. **[TCP_DEFER_ACCEPT]** Настрой `TCP_DEFER_ACCEPT` в `ListenConfig`. Ядро Linux не будет будить Go-процесс при установке TCP-соединения, пока в сокете не появятся реальные данные. Это экономит CPU при атаках SYN-Flood (пустые коннекты обрабатывает только ядро).
996. **[Каверзный кейс — Seccomp Basics]** Изучи, что Go рантайм использует системные вызовы (например, `clone`, `mmap`, `futex`). Напиши профиль Seccomp (JSON для Docker), который разрешает только необходимые для Go сисколы. Запусти контейнер с профилем `default` и `unconfined`, посмотри на поведение.
997. **[Seccomp: Block ptrace]** Напиши кастомный Seccomp профиль, который запрещает сискол `ptrace`. В Go-коде вызови `syscall.PtraceAttach`. Убедись, что ядро убивает процесс (`SIGSYS`), предотвращая отладку и внедрение кода в продакшене.
998. **[Seccomp: Block Network Egress]** Напиши Seccomp профиль, который запрещает сискол `connect`. Запусти Go-приложение, которое пытается сделать HTTP-запрос. Убедись, что трафик блокируется на уровне ядра (защита от Reverse Shell или Data Exfiltration).
999. **[AppArmor]** Напиши профиль AppArmor для Go-бинарника, который разрешает чтение только из `/etc/myapp/config.yaml` и запись только в `/var/log/myapp/`. Попробуй прочитать `/etc/passwd` из Go-кода — ядро должно вернуть ошибку `Permission denied`.
1000. **[Финальное испытание — The Unbreakable Server]**
    Построй HTTP-сервер, устойчивый к любым атакам:
    - **Сетевые таймауты:** `ReadHeaderTimeout: 5s`, `WriteTimeout: 10s`, `IdleTimeout: 120s`, `MaxHeaderBytes: 1MB`.
    - **Сокеты ОС:** Настроен `SO_REUSEPORT` и `TCP_DEFER_ACCEPT` для балансировки и защиты от SYN-Flood.
    - **Seccomp:** Сервер запущен в Docker со строгим Seccomp-профилем (запрещены `ptrace`, `connect` к локальным сокетам базы данных разрешен, но запрещен любой внешний интернет).
    - **Supply Chain:** CI/CD пайплайн падает, если `govulncheck` находит активную уязвимость. Сгенерирован SBOM.
    - **Инфраструктура:** Лимит файловых дескрипторов (`ulimit -n`) настроен на 1 000 000 через systemd или K8s.
    - Сымитируй Slowloris и SYN-Flood атаки. Сервер должен продолжать отвечать на запросы легитимных клиентов с p99 latency < 50ms.
