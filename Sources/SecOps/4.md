### Тема 191: Supply Chain Security — Основы
*Supply chain attacks — это когда атакующий компрометирует зависимости вашего проекта (как в случае с event-stream npm package или SolarWinds).*

2181. **govulncheck установка:** Установите `govulncheck` через `go install golang.org/x/vuln/cmd/govulncheck@latest`. Это официальный инструмент от Go team.

2182. **Первое сканирование:** Запустите `govulncheck ./...` в вашем проекте. Изучите вывод: какие уязвимости найдены, их severity, affected packages.

2183. **govulncheck modes:** Изучите разные modes:
    * `govulncheck ./...` — сканирует imports
    * `govulncheck -mode=binary ./myapp` — сканирует compiled binary
    * `govulncheck -mode=extract ./...` — detailed vulnerability info

2184. **Understanding govulncheck output:** Разберите вывод:
    * OSV ID (Open Source Vulnerability ID)
    * Affected symbol (какая функция уязвима)
    * Call stack (использует ли ваш код уязвимую функцию)
    * Fixed version (в какой версии исправлено)

2185. **govulncheck в CI:** Добавьте `govulncheck` в GitHub Actions/GitLab CI. Fail build при обнаружении high/critical vulnerabilities.

2186. **govulncheck ignore:** Для false positives или accepted risks создайте `.govulncheck.ignore` файл с OSV IDs для игнорирования.

2187. **go.sum verification:** Изучите `go.sum` файл. Каждая строка — это cryptographic hash модуля. Go автоматически верифицирует checksums при `go mod download`.

2188. **Go Checksum Database:** Изучите `sum.golang.org` — это transparency log для Go modules. Все checksums публично логируются для предотвращения tampering.

2189. **GOSUMDB environment variable:** Настройте `GOSUMDB=sum.golang.org` (default) или отключите через `GOSUMDB=off` для private modules.

2190. **GOPRIVATE для private modules:** Настройте `GOPRIVATE=github.com/mycompany/*` для bypass sum database для private repos.

2191. **go mod verify:** Запустите `go mod verify` для проверки, что все модули в cache match их checksums в `go.sum`.

2192. **Module proxy:** Используйте `GOPROXY=https://proxy.golang.org,direct` (default) для кэширования modules. Это защищает от disappearing modules.

2193. **Direct vs proxy:** Поймите разницу:
    * `GOPROXY=direct` — качает напрямую из VCS (Git)
    * `GOPROXY=https://proxy.golang.org` — качает из Google's proxy
    * `GOPROXY=off` — только из local cache

2194. **Vendoring:** Используйте `go mod vendor` для создания `vendor/` directory со всеми dependencies. Это делает builds reproducible и independent от network.

2195. **Vendor vs modules trade-offs:**
    * Vendor: reproducible, но увеличивает repo size
    * Modules: smaller repo, но требует network для builds
    Используйте vendor для production-critical applications.

2196. **go mod tidy:** Регулярно запускайте `go mod tidy` для удаления unused dependencies и добавления missing ones.

2197. **Dependency pinning:** В `go.mod` используйте exact versions (`v1.2.3`) вместо ranges для critical dependencies.

2198. **Minimum version selection:** Поймите Go's MVS (Minimum Version Selection) algorithm. Go выбирает минимальную версию, которая удовлетворяет все requirements.

2199. **Replace directive:** Используйте `replace` для pinning specific versions или замены modules на forks:
    ```go
    replace github.com/vulnerable/pkg => github.com/mycompany/fork v1.2.4
    ```

2200. **Dependency audit script:** Напишите скрипт, который:
    * Запускает `govulncheck`
    * Проверяет `go mod verify`
    * Логирует результаты
    * Алертит при findings

### Тема 192: Подпись и верификация артефактов
*Cosign и Sigstore позволяют подписывать Docker images, binaries и другие артефакты для защиты от tampering.*

2201. **Cosign установка:** Установите `cosign` через `go install github.com/sigstore/cosign/v2/cmd/cosign@latest`.

2202. **Key generation:** Сгенерируйте key pair через `cosign generate-key-pair`. Это создаёт `cosign.key` (private) и `cosign.pub` (public).

2203. **Keyless signing (Fulcio):** Используйте keyless signing через Fulcio (Sigstore's CA):
    ```bash
    cosign sign --yes myregistry.io/myimage:tag
    ```
    Это использует OIDC identity (GitHub Actions, Google Cloud) вместо static keys.

2204. **Sign Docker image:** Подпишите Docker image:
    ```bash
    cosign sign --key cosign.key myregistry.io/myimage:v1.2.3
    ```

2205. **Verify Docker image:** Верифицируйте подпись:
    ```bash
    cosign verify --key cosign.pub myregistry.io/myimage:v1.2.3
    ```

2206. **Sign binary:** Подпишите Go binary:
    ```bash
    cosign sign-blob --key cosign.key --output-signature myapp.sig myapp
    ```

2207. **Verify binary:** Верифицируйте binary signature:
    ```bash
    cosign verify-blob --key cosign.pub --signature myapp.sig myapp
    ```

2208. **Attestations:** Создайте attestation (SLSA provenance):
    ```bash
    cosign attest --predicate slsa-provenance.json --type slsaprovenance myimage:tag
    ```

2209. **Verify attestation:** Верифицируйте attestation:
    ```bash
    cosign verify-attestation --type slsaprovenance myimage:tag
    ```

2210. **Rekor transparency log:** Изучите Rekor — это transparency log для signatures. Все signatures логируются публично для auditability.

2211. **Cosign в CI/CD:** Настройте GitHub Actions для автоматической подписи Docker images при push в main branch.

2212. **Cosign + Kubernetes:** Используйте cosign policy controller в Kubernetes для блокировки неподписанных images:
    ```yaml
    apiVersion: policy.sigstore.dev/v1beta1
    kind: ClusterImagePolicy
    spec:
      images:
      - glob: "myregistry.io/*"
      authorities:
      - key:
          data: |
            -----BEGIN PUBLIC KEY-----
            ...
            -----END PUBLIC KEY-----
    ```

2213. **SLSA framework:** Изучите SLSA (Supply-chain Levels for Software Artifacts):
    * Level 0: No guarantees
    * Level 1: Build script defined
    * Level 2: Hosted build platform
    * Level 3: Isolated, hermetic builds
    * Level 4: Two-party review

2214. **SLSA provenance generator:** Используйте `slsa-framework/slsa-github-generator` для автоматической генерации SLSA Level 3 provenance в GitHub Actions.

2215. **In-toto attestations:** Изучите in-toto framework для software supply chain security. Cosign использует in-toto format для attestations.

2216. **Multiple signatures:** Подпишите image несколькими keys (например, dev team + security team). Verifiers могут требовать все или subset signatures.

2217. **Signature expiration:** Настройте expiration для signatures через certificate validity period (для keyless signing).

2218. **Cosign annotations:** Добавляйте custom annotations к signatures:
    ```bash
    cosign sign --annotations "version=v1.2.3" --annotations "commit=abc123" myimage:tag
    ```

2219. **Verify annotations:** Верифицируйте annotations при signature verification.

2220. **Cosign + SBOM:** Подпишите SBOM вместе с image для complete supply chain transparency.

### Тема 193: SBOM (Software Bill of Materials)
*SBOM — это inventory всех компонентов в вашем software. Критично для vulnerability management и compliance.*

2221. **SBOM formats:** Изучите основные форматы:
    * SPDX (Software Package Data Exchange) — Linux Foundation standard
    * CycloneDX — OWASP standard
    * Syft format — Anchore's format

2222. **Syft installation:** Установите `syft` через `go install github.com/anchore/syft/cmd/syft@latest`.

2223. **Generate SBOM для binary:**
    ```bash
    syft packages myapp -o spdx-json > myapp.spdx.json
    ```

2224. **Generate SBOM для Docker image:**
    ```bash
    syft packages myimage:tag -o cyclonedx-json > myimage.cdx.json
    ```

2225. **Generate SBOM для directory:**
    ```bash
    syft packages dir:./myproject -o spdx-json > project.spdx.json
    ```

2226. **SBOM content:** Изучите SBOM content:
    * Package name и version
    * License information
    * Supplier/author
    * Checksums
    * Dependencies

2227. **Grype для vulnerability scanning:** Установите `grype` через `go install github.com/anchore/grype/cmd/grype@latest`.

2228. **Scan SBOM через Grype:**
    ```bash
    grype sbom:myapp.spdx.json
    ```

2229. **Scan Docker image через Grype:**
    ```bash
    grype myimage:tag
    ```

2230. **Grype + CI/CD:** Добавьте Grype в CI pipeline. Fail build при high/critical vulnerabilities.

2231. **SBOM attestation:** Подпишите SBOM через cosign:
    ```bash
    cosign attest --predicate myapp.spdx.json --type spdxjson myimage:tag
    ```

2232. **Verify SBOM attestation:**
    ```bash
    cosign verify-attestation --type spdxjson myimage:tag | jq '.payload | @base64d | fromjson'
    ```

2233. **SBOM в OCI registry:** Сохраните SBOM как OCI artifact в том же registry:
    ```bash
    oras push myregistry.io/myimage:sbom myapp.spdx.json
    ```

2234. **Dependency-Track:** Настройте Dependency-Track (open-source SBOM management) для centralized vulnerability management.

2235. **SBOM + govulncheck:** Комбинируйте SBOM generation с govulncheck для complete Go-specific vulnerability analysis.

2236. **NTIA minimum elements:** Изучите NTIA (National Telecommunications and Information Administration) minimum elements для SBOM:
    * Supplier name
    * Component name
    * Version
    * Unique identifier
    * Dependency relationship
    * Author
    * Timestamp

2237. **SBOM automation:** Настройте automatic SBOM generation в CI/CD pipeline для каждого build.

2238. **SBOM distribution:** Публикуйте SBOM вместе с releases на GitHub/GitLab для transparency.

2239. **SBOM + license compliance:** Используйте SBOM для license compliance checking (GPL, MIT, Apache compatibility).

2240. **SBOM monitoring:** Настройте continuous monitoring: при обнаружении новой vulnerability в component, alert через SBOM database.

### Тема 195: Slowloris и Socket Timeouts
*Slowloris — это DoS атака, где атакующий открывает множество соединений и отправляет данные очень медленно, исчерпывая server resources.*

2261. **Slowloris attack demo:** Напишите Slowloris client на Go, который открывает 1000 соединений и отправляет headers по 1 байту каждые 10 секунд.

2262. **Default Go HTTP server vulnerability:** Запустите стандартный `http.ListenAndServe()` и атакуйте его Slowloris. Убедитесь, что server исчерпывает connections.

2263. **ReadHeaderTimeout:** Настройте `ReadHeaderTimeout` в `http.Server`:
    ```go
    server := &http.Server{
        Addr:              ":8080",
        ReadHeaderTimeout: 10 * time.Second,
    }
    ```
    Это ограничивает время на чтение headers.

2264. **ReadTimeout:** Настройте `ReadTimeout` для ограничения времени на чтение всего request body:
    ```go
    server := &http.Server{
        Addr:        ":8080",
        ReadTimeout: 30 * time.Second,
    }
    ```

2265. **WriteTimeout:** Настройте `WriteTimeout` для ограничения времени на отправку response:
    ```go
    server := &http.Server{
        Addr:         ":8080",
        WriteTimeout: 30 * time.Second,
    }
    ```

2266. **IdleTimeout:** Настройте `IdleTimeout` для keep-alive connections:
    ```go
    server := &http.Server{
        Addr:        ":8080",
        IdleTimeout: 120 * time.Second,
    }
    ```

2267. **MaxHeaderBytes:** Ограничьте размер headers для защиты от header bombing:
    ```go
    server := &http.Server{
        Addr:           ":8080",
        MaxHeaderBytes: 1 << 20, // 1 MB
    }
    ```

2268. **http.MaxBytesReader:** Используйте `http.MaxBytesReader` для ограничения request body size:
    ```go
    r.Body = http.MaxBytesReader(w, r.Body, 10<<20) // 10 MB
    ```

2269. **Connection limits через ulimit:** Настройте `ulimit -n` для ограничения file descriptors per process.

2270. **SO_KEEPALIVE:** Включите TCP keepalive для early detection of dead connections:
    ```go
    listener, _ := net.Listen("tcp", ":8080")
    tcpListener := listener.(*net.TCPListener)
    conn, _ := tcpListener.AcceptTCP()
    conn.SetKeepAlive(true)
    conn.SetKeepAlivePeriod(30 * time.Second)
    ```

2271. **TCP_USER_TIMEOUT:** Настройте `TCP_USER_TIMEOUT` (Linux) для faster detection of broken connections:
    ```go
    file, _ := conn.File()
    fd := file.Fd()
    syscall.SetsockoptInt(int(fd), syscall.IPPROTO_TCP, 0x12, 30000) // 30s
    ```

2272. **Connection rate limiting:** Реализуйте rate limiting на уровне listener:
    ```go
    type RateLimitedListener struct {
        net.Listener
        rateLimiter *rate.Limiter
    }
    ```

2273. **HAProxy/Envoy перед Go:** Используйте reverse proxy (HAProxy, Envoy, Nginx) перед Go server для connection limiting и DDoS protection.

2274. **Cloudflare/CloudFront:** Используйте CDN с DDoS protection перед вашим server.

2275. **Slowloris testing tool:** Используйте `slowhttptest` для тестирования вашего server:
    ```bash
    slowhttptest -c 1000 -i 10 -r 200 -t GET -u http://localhost:8080
    ```

2276. **Monitor connection count:** Экспортируйте метрику `active_connections` в Prometheus. Алерт при превышении threshold.

2277. **Graceful degradation:** При high connection count возвращайте `503 Service Unavailable` для new connections.

2278. **Connection pooling на client side:** Настройте `http.Transport` с limits:
    ```go
    transport := &http.Transport{
        MaxIdleConns:        100,
        MaxIdleConnsPerHost: 10,
        IdleConnTimeout:     90 * time.Second,
    }
    ```

2279. **Context timeouts:** Всегда используйте context с timeout для outbound requests:
    ```go
    ctx, cancel := context.WithTimeout(context.Background(), 10*time.Second)
    defer cancel()
    req, _ := http.NewRequestWithContext(ctx, "GET", url, nil)
    ```

2280. **Финальный босс (Secure Go Microservice):**
    Создайте production-grade secure microservice:
    
    **Supply Chain Security:**
    * **govulncheck** в CI pipeline (fail на high/critical)

    * **Cosign signing** для Docker images и binaries
    * **SBOM generation** через Syft в SPDX format
    * **SLSA Level 3 provenance** через slsa-github-generator
    * **Private module registry** через Athens с S3 backend
    * **Vendoring** для reproducible builds
    
    **Network Security:**
    * **HTTP Server hardening:**
      - ReadHeaderTimeout: 10s
      - ReadTimeout: 30s
      - WriteTimeout: 30s
      - IdleTimeout: 120s
      - MaxHeaderBytes: 1MB
    * **Request body limiting** через http.MaxBytesReader
    * **TCP keepalive** с 30s period
    * **Connection rate limiting** через custom listener

    **Kernel-level Security:**
    * **seccomp profile** для ограничения syscall'ов:

### 💡 Золотые правила infrastructure security:

1. **govulncheck в CI — это must have.** Запускайте `govulncheck` на каждый PR. Fail build при high/critical vulnerabilities. Это защищает от known vulnerabilities в dependencies.

2. **Подписывайте все артефакты.** Docker images, binaries, SBOMs — всё должно быть подписано через cosign. Verifiers должны проверять signatures перед использованием.

3. **SBOM — это transparency.** Генерируйте SBOM для каждого build. Публикуйте его вместе с releases. Это позволяет vulnerability scanning и license compliance.

4. **SLSA Level 3 минимум.** Для production software стремитесь к SLSA Level 3 (isolated, hermetic builds). Это защищает от build system compromise.

5. **Private registry для enterprise.** Используйте Athens или Artifactory для private Go modules. Это даёт control over dependencies и protects от disappearing modules.

6. **Vendor для air-gapped.** Для air-gapped environments или maximum reproducibility используйте `go mod vendor`. Это делает builds independent от network.

7. **HTTP server timeouts обязательны.** Без timeouts ваш server уязвим к Slowloris и resource exhaustion:
    * ReadHeaderTimeout: 10s
    * ReadTimeout: 30s
    * WriteTimeout: 30s
    * IdleTimeout: 120s

8. **Request body limiting.** Всегда используйте `http.MaxBytesReader` для ограничения request body size. Иначе атакующий может отправить multi-GB payload и исчерпать memory.

9. **TCP keepalive для dead connections.** Включите keepalive с 30s period для early detection of dead connections. Это освобождает resources.

10. **seccomp для syscall filtering.** Ограничьте syscall'ы через seccomp profile. Запретите dangerous syscall'ы (ptrace, mount, reboot). Это снижает impact of container escape.

11. **Drop ALL capabilities.** В Docker/Kubernetes drop all Linux capabilities и add только необходимые. Principle of least privilege.

12. **Non-root user.** Никогда не запускайте containers как root. Используйте non-root user (UID 65534 или custom).

13. **Read-only root filesystem.** Mount root filesystem как read-only. Это предотвращает malware persistence.

14. **Context timeouts везде.** Все outbound requests (HTTP, gRPC, DB, Redis) должны иметь context с timeout. Иначе hung connections исчерпают resources.

15. **Connection pooling с limits.** Настройте connection pools с sensible limits:
    * MaxIdleConns: 100
    * MaxIdleConnsPerHost: 10
    * IdleConnTimeout: 90s

16. **Rate limiting на всех уровнях:**
    * Application level (per user/API key)
    * Network level (per IP через iptables)
    * Infrastructure level (через Envoy/HAProxy)

17. **Monitor connection count.** Экспортируйте `active_connections` в Prometheus. Алерт при превышении threshold (например, 80% от ulimit).

18. **Graceful degradation.** При overload возвращайте `503 Service Unavailable` вместо hanging. Это позволяет load balancer'у redirect traffic к healthy instances.

19. **Reverse proxy перед Go.** Используйте Nginx/Envoy/HAProxy перед Go server для:
    * DDoS protection
    * SSL termination
    * Connection limiting
    * Static file serving

20. **Test security регулярно:**
    * govulncheck для dependencies
    * Slowloris для DoS resilience
    * Penetration testing через OWASP ZAP
    * Chaos testing для failure scenarios
