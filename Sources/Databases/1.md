## Часть XVI. Работа с базами данных

### 55. database/sql — основы и PostgreSQL

**Упражнение 16.1.** Установи PostgreSQL (локально или через Docker). Создай базу `testdb`, таблицу `users (id SERIAL PRIMARY KEY, name TEXT, email TEXT, created_at TIMESTAMP)`. Подключись через `sql.Open("postgres", dsn)` (`github.com/lib/pq`) и проверь соединение `db.Ping()`.

**Упражнение 16.2.** Напиши функцию `CreateUser(name, email string) error`, использующую `db.Exec("INSERT INTO users(name, email) VALUES($1, $2)", name, email)`. Проверь `sql.Result` — `LastInsertId()` (не работает в PostgreSQL!) и `RowsAffected()`.

**Упражнение 16.3.** Напиши функцию `GetUserByID(id int) (*User, error)`, использующую `db.QueryRow("SELECT id, name, email, created_at FROM users WHERE id = $1", id).Scan(&user.ID, &user.Name, &user.Email, &user.CreatedAt)`. Обработай `sql.ErrNoRows`.

**Упражнение 16.4.** Напиши функцию `ListUsers() ([]User, error)`, использующую `db.Query("SELECT ...")`. Итерируй `rows.Next()`, сканируй в структуру. Не забудь `defer rows.Close()` и проверь `rows.Err()` после цикла.

**Упражнение 16.5.** Покажи **утечку соединений**, если забыть `rows.Close()`. Запусти 10000 запросов в цикле без `defer rows.Close()` — получи `"sorry, too many clients already"` от PostgreSQL. Исправь.

**Упражнение 16.6.** Напиши функцию `UpdateUserEmail(id int, email string) error`. Используй `db.Exec`. Проверь `RowsAffected()` — если 0, верни `sql.ErrNoRows` или кастомную ошибку `"user not found"`.

**Упражнение 16.7.** Напиши функцию `DeleteUser(id int) error`. Используй `db.Exec`. Обработай случай, когда пользователя нет — верни ошибку или `nil` в зависимости от требований.

**Упражнение 16.8.** Напиши функцию `CreateUsersBulk(users []User) error`, использующую **подготовленный запрос** (`db.Prepare`) и цикл `stmt.Exec(...)`. Покажи, что prepare один раз + exec много раз быстрее, чем `db.Exec` в цикле.

**Упражнение 16.9.** Перепиши bulk insert через **один запрос с множественными VALUES**: `INSERT INTO users(name, email) VALUES ($1, $2), ($3, $4), ...`. Сгенерируй SQL динамически. Сравни производительность с prepare + цикл.

**Упражнение 16.10.** Напиши функцию `SearchUsers(namePattern string) ([]User, error)` с `ILIKE` (case-insensitive like): `WHERE name ILIKE $1`. Передай `"%" + namePattern + "%"`. Обработай SQL-инъекцию — покажи, что placeholder'ы (`$1`) защищают.

**Упражнение 16.11.** Попробуй **SQL-инъекцию** намеренно: сконструируй запрос через `fmt.Sprintf("SELECT * FROM users WHERE name = '%s'", userInput)` с входом `"' OR '1'='1"`. Покажи, что это ломает безопасность. Исправь на placeholder'ы.

**Упражнение 16.12.** Напиши функцию `GetUsersPaginated(page, pageSize int) ([]User, int, error)`. Используй `LIMIT $1 OFFSET $2` для пагинации. Верни общее количество через `SELECT COUNT(*)`. Обработай `pageSize > 100` — ограничь максимум.

**Упражнение 16.13.** Напиши функцию `GetUsersSorted(sortBy, order string) ([]User, error)`. Валидируй `sortBy` против whitelist (`"name"`, `"email"`, `"created_at"`), иначе верни ошибку. Не подставляй `sortBy` напрямую в SQL без валидации!

**Упражнение 16.14.** Напиши функцию `GetUserStats() (map[string]int, error)`, использующую `COALESCE` и `GROUP BY`: `SELECT DATE(created_at), COUNT(*) FROM users GROUP BY DATE(created_at)`. Сканируй в `map[time.Time]int`.

### 56. Транзакции

**Упражнение 16.15.** Напиши функцию `TransferMoney(fromID, toID, amount int) error`. Используй `db.Begin()` для начала транзакции. Внутри: `UPDATE accounts SET balance = balance - $1 WHERE id = $2`, затем `UPDATE ... + $1`. `tx.Commit()` при успехе, `tx.Rollback()` при ошибке.

**Упражнение 16.16.** Покажи **"lost update"**: два параллельных `TransferMoney` без транзакции/блокировки. Баланс "теряется". Запусти 100 параллельных переводов — итоговый баланс ≠ начальному. Исправь через транзакцию + `SELECT FOR UPDATE`.

**Упражнение 16.17.** Модифицируй `TransferMoney`: добавь `SELECT balance FROM accounts WHERE id = $1 FOR UPDATE` в начале транзакции. Покажи, что "lost update" исчез. Объясни уровень изоляции `READ COMMITTED` + row-level locks.

**Упражнение 16.18.** Напиши функцию `CreateOrderWithItems(order Order, items []OrderItem) error`. Используй транзакцию: сначала `INSERT INTO orders`, получи `order_id` через `RETURNING id` + `Scan`, затем `INSERT INTO order_items` для каждого item. Всё или ничего.

**Упражнение 16.19.** Напиши **"savepoint"** в транзакции: `tx.Exec("SAVEPOINT sp1")`. Выполни рискованную операцию. При ошибке — `tx.Exec("ROLLBACK TO SAVEPOINT sp1")` вместо полного `Rollback()`. Продолжи транзакцию.

**Упражнение 16.20.** Напиши функцию `WithTransaction(ctx context.Context, db *sql.DB, fn func(*sql.Tx) error) error`. Оборачивай логику в транзакцию: `Begin`, `defer` с `Rollback` (если не committed), `Commit`. Покажи паттерн "unit of work".

**Упражнение 16.21.** Покажи **"transaction rollback on panic"**: внутри `WithTransaction` используй `recover()` в `defer` для `Rollback()` при панике. Логируй панику и перевыбрасывай.

**Упражнение 16.22.** Напиши **"optimistic locking"**: таблица `products (id, name, price, version INTEGER DEFAULT 1)`. При обновлении: `UPDATE products SET price = $1, version = version + 1 WHERE id = $2 AND version = $3`. Если `RowsAffected() == 0` — верни ошибку `"concurrent modification detected"`.

### 57. Пулы соединений и настройка

**Упражнение 16.23.** Настрой пул соединений: `db.SetMaxOpenConns(25)`, `db.SetMaxIdleConns(25)`, `db.SetConnMaxLifetime(5 * time.Minute)`. Объясни каждый параметр. Покажи, что без настройки пула — дефолт `MaxOpenConns = 0` (unlimited) может исчерпать ресурсы PostgreSQL.

**Упражнение 16.24.** Напиши программу, которая запускает 1000 горутин, каждая делает `db.QueryRow("SELECT pg_sleep(0.1)")`. С `MaxOpenConns = 10` — покажи, что запросы выполняются пачками по 10. С `MaxOpenConns = 0` — PostgreSQL может отказать.

**Упражнение 16.25.** Напиши **"connection health check"**: `db.PingContext(ctx)` с таймаутом. Используй в readiness probe HTTP endpoint'а. Покажи, что `Ping` проверяет не только TCP, но и способность выполнять запросы.

**Упражнение 16.26.** Напиши программу с **"connection leak simulation"**: открываешь `sql.Rows`, не закрываешь, итерируешь не до конца (`break` после первой строки). Покажи, что соединение остаётся занятым. Исправь: `defer rows.Close()` + дочитывай до конца или явно закрой.

### 58. pgx — продвинутый драйвер PostgreSQL

**Упражнение 16.27.** Перепиши подключение на `github.com/jackc/pgx/v5/pgxpool`. Создай `pgxpool.New(ctx, connString)`. Покажи, что pgxpool управляет пулом соединений автоматически.

**Упражнение 16.28.** Используй `pgx` для **batch запросов**: `batch := &pgx.Batch{}`, `batch.Queue("INSERT INTO users(name) VALUES($1)", "Alice")`, `batch.Queue(...)`. `br := pool.SendBatch(ctx, batch)`, затем `br.Exec()`. Покажи, что batch — один round-trip.

**Упражнение 16.29.** Используй `pgx` для **copy from**: `copyCount, err := pool.CopyFrom(ctx, pgx.Identifier{"users"}, []string{"name", "email"}, pgx.CopyFromSlice(len(users), func(i int) ([]any, error) { return []any{users[i].Name, users[i].Email}, nil }))`. Это самый быстрый способ bulk insert.

**Упражнение 16.30.** Используй `pgx` для **LISTEN/NOTIFY**: `conn.Exec(ctx, "LISTEN channel_name")`. В горутине читай `conn.WaitForNotification(ctx)` — получишь push-уведомления от PostgreSQL. Напиши простой pub/sub через БД.

**Упражнение 16.31.** Используй `pgx` с **кодеками для кастомных типов**: создай тип `Status` (enum в PostgreSQL: `'active', 'inactive', 'banned'`). Реализуй `EncodeText`/`DecodeText` для `pgx`. Сканируй напрямую в `Status`.

**Упражнение 16.32.** Используй `pgx` с **array типами**: PostgreSQL `TEXT[]`. Сканируй в `[]string` через `pgtype.Array[string]`. Или вставляй `[]string` напрямую — pgx конвертирует автоматически.

**Упражнение 16.33.** Используй `pgx` с **JSONB**: колонка `data JSONB`. Сканируй в `map[string]any` или структуру с `json` тегами. Вставляй структуру — pgx сериализует в JSON.

**Упражнение 16.34.** Напиши **"upsert"** через `ON CONFLICT`: `INSERT INTO users(email, name) VALUES($1, $2) ON CONFLICT(email) DO UPDATE SET name = EXCLUDED.name`. Верни `RowsAffected` и определи: insert или update произошёл.

**Упражнение 16.44.** Подключись к Redis через `github.com/redis/go-redis/v9`. Создай клиент: `rdb := redis.NewClient(&redis.Options{Addr: "localhost:6379"})`. Проверь `rdb.Ping(ctx).Result()`.

**Упражнение 16.49.** Напиши функцию `CacheIncr(key string) (int64, error)`, использующую `rdb.Incr(ctx, key)`. Покажи атомарность: запусти 1000 горутин, каждая `Incr` — результат будет ровно 1000.

**Упражнение 16.50.** Напиши функцию `CacheDecr(key string) (int64, error)`. Покажи, что `Decr` на 0 даст -1. Используй `IncrBy`/`DecrBy` для произвольных значений.

**Упражнение 16.51.** Напиши функцию `CacheSetNX(key string, value any, ttl time.Duration) (bool, error)`, использующую `rdb.SetNX(ctx, key, value, ttl)`. Это **distributed lock**: если ключ не существует — устанавливает и возвращает `true`. Иначе — `false`.

**Упражнение 16.52.** Реализуй **distributed lock** через `SetNX` + `Expire`: `SET key value NX EX 10`. Если lock получен — выполни работу, затем `Del(key)`. Обработай "владение" lock'ом: значение = UUID процесса, проверяй перед `Del`.

**Упражнение 16.53.** Реализуй **distributed lock с автопродлением**: goroutine раз в 5 секунд делает `Expire` на lock, пока основная работа не завершится. При завершении — `Del`. Используй `context` для отмены продления.

**Упражнение 16.54.** Напиши функцию `CacheMGet(keys ...string) ([]string, error)`, использующую `rdb.MGet(ctx, keys...)`. Покажи, что `MGet` возвращает `[]interface{}`, где отсутствующие ключи — `nil`.

**Упражнение 16.55.** Напиши функцию `CacheMSet(pairs map[string]string) error`, использующую `rdb.MSet(ctx, pairs)`. Покажи, что `MSet` атомарен (все ключи или ни одного).

### 63. Redis — продвинутые паттерны

**Упражнение 16.71.** Реализуй **Cache-Aside pattern**: `GetUserFromCacheOrDB(ctx, id int) (*User, error)`. Сначала `CacheGet("user:" + id)`. Если miss — `SELECT` из PostgreSQL, `CacheSet` результат, верни. Обработай **cache stampede**: если ключ протухает, 100 запросов одновременно ломятся в БД.

**Упражнение 16.72.** Реализуй **cache stampede protection** через `SetNX`: при cache miss — один запрос ставит lock `"lock:user:123"`, грузит из БД, кладёт в кеш, удаляет lock. Остальные ждут lock'а или берут stale-данные.

**Упражнение 16.73.** Реализуй **Write-Through cache**: `CreateUser` сначала пишет в БД, затем инвалидирует/обновляет кеш. `UpdateUser` — то же. Покажи консистентность.

**Упражнение 16.74.** Реализуй **Read-Through cache** с TTL: данные в кеше живут 5 минут. При обновлении в БД — `CacheDelete` (invalidate). Покажи **eventual consistency**: между `UPDATE` и `CacheDelete` читатели видят stale-данные.

**Упражнение 16.75.** Реализуй **Rate Limiter** через Redis: `SLIDE_WINDOW`. Ключ = `rate_limit:ip:minute:YYYY-MM-DD-HH-MM`. `INCR` + `EXPIRE 60`. Если счётчик > limit — `429 Too Many Requests`. Используй pipeline для атомарности `INCR` + `EXPIRE`.

**Упражнение 16.76.** Реализуй **Rate Limiter (sliding window log)**: `ZADD` timestamp'ов, `ZREMRANGEBYSCORE` старых (старше window), `ZCARD` для подсчёта. Более точный, но дороже по памяти.

**Упражнение 16.77.** Реализуй **Session Store** в Redis: `HSET session:abc123 user_id 123 expires 1234567890`. При каждом запросе — `HGETALL` + проверка TTL. `HDEL` при logout. Используй `EXPIRE` на весь ключ.

**Упражнение 16.78.** Реализуй **Pub/Sub** через Redis: `rdb.Subscribe(ctx, "channel1", "channel2")`. В горутине читай `sub.Channel()`. Другой клиент публикует через `rdb.Publish(ctx, "channel1", "message")`. Покажи real-time messaging.

**Упражнение 16.79.** Реализуй **Redlock** (упрощённый): несколько Redis-нод (3). Для получения lock'а — `SetNX` на большинство нод с одинаковым UUID и TTL. Для release — `Del` на тех же нодах, где получил. Обсуди ограничения Redlock.

**Упражнение 16.80.** Реализуй **CQRS (упрощённый)**: `WriteModel` — PostgreSQL, `ReadModel` — Redis. При создании заказа — пиши в PostgreSQL, публикуй событие в Redis Pub/Sub. Consumer обновляет Redis (denormalized view). Чтение — из Redis.

### Ключевые моменты для освоения работы с БД:

1. **Всегда используй placeholder'ы (`$1`, `?`)** — никогда не конкатенируй пользовательский ввод в SQL. SQL-инъекция — №1 угроза.
2. **`defer rows.Close()` сразу после проверки ошибки** — утечка соединений убивает production.
3. **Транзакции** — `Begin`, `defer Rollback`, `Commit`. Используй `SELECT FOR UPDATE` для конкурентных обновлений.
4. **Context везде** — `QueryContext`, `ExecContext`, `PingContext`. Позволяет отменить долгий запрос по таймауту или сигналу.
5. **pgx > lib/pq** для новых проектов — pgx быстрее, поддерживает batch, copy, LISTEN/NOTIFY, кастомные типы.
6. **Redis — не persistent storage** — используй для кеша, сессий, rate limiting, real-time. Критичные данные — в PostgreSQL.
7. **Cache patterns** — Cache-Aside (проверь кеш → miss → БД → кеш) наиболее гибкий. Помни о cache stampede и eventual consistency.
8. **Connection pooling** — настрой `MaxOpenConns`, `MaxIdleConns`, `ConnMaxLifetime`. PostgreSQL имеет лимит соединений (обычно 100).
