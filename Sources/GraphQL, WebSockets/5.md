REST и gRPC — это классика, но современные фронтенд-приложения часто требуют максимальной гибкости в запросах, а также интерактивности в реальном времени. Здесь на сцену выходят GraphQL и WebSockets.

Продолжаем нашу интенсивную тренировку. Впереди **15 отличных упражнений** (с 476 по 490), разделенных на два блока.

### Блок 39. GraphQL: Гибкие API с `gqlgen` (476–483)
В Go стандартом индустрии для GraphQL является подход "Schema-First" (сначала пишем схему, потом генерируем код). Лучший инструмент для этого — `github.com/99designs/gqlgen`.

476. **Инициализация gqlgen:** Создай пустой проект. Скачай пакет `github.com/99designs/gqlgen`. Выполни команду инициализации `go run github.com/99designs/gqlgen init`. Изучи сгенерированную структуру файлов (схема `.graphqls`, резолверы, модели и точка входа HTTP).
477. **Первый Query (Запрос):** Открой файл схемы `schema.graphqls`. Удали примеры и напиши свой тип `User` (id, name, age) и `Query` (метод `getUser(id: ID!): User!`). Запусти кодогенерацию `go run github.com/99designs/gqlgen generate`.
478. **Реализация Резолвера (Resolver):** Открой сгенерированный файл `schema.resolvers.go`. Найди метод `GetUser`. Напиши там логику возврата "захардкоженного" пользователя. Подними сервер, открой GraphQL Playground (по умолчанию на `http://localhost:8080`) и выполни запрос.
479. **Первая Mutation (Мутация):** Добавь в схему тип `Mutation` с методом `createUser(name: String!, age: Int!): User!`. Сгенерируй код, реализуй создание юзера (можешь сохранять в обычный `map` или срез) и протестируй через Playground.
480. **Вложенные резолверы:** Усложним задачу. Добавь тип `Post` (id, text). В тип `User` добавь поле `posts: [Post!]!`. Сгенерируй код. Обрати внимание, что gqlgen может попросить тебя написать отдельный резолвер для получения постов конкретного юзера. Реализуй его.
481. **Классическая проблема N+1:** В резолвере `posts` из упр. 480 добавь `fmt.Println("Запрос к БД за постами")`. В Playground запроси список из 5 юзеров, и у каждого запроси его посты. Посмотри в консоль сервера: ты увидишь 1 запрос на юзеров и **5 отдельных запросов** на посты. Осознай, как это "убьет" базу данных в продакшене.
482. **Dataloader (Решение N+1):** Установи пакет `github.com/graph-gophers/dataloader` или `github.com/vektah/dataloaden`. Напиши батч-функцию (которая принимает список ID юзеров и возвращает списки постов за ОДИН SQL-запрос). Внедрь даталоадер в резолвер `posts`. Запусти тот же GraphQL-запрос и убедись, что в консоли теперь только 2 "запроса к БД" (1 на юзеров, 1 на все посты).
483. **GraphQL Context (Авторизация):** Создай стандартную HTTP-middleware, которая проверяет токен в заголовке и кладет ID юзера в `context.WithValue`. В GraphQL-резолвере достань этот ID из контекста. Если ID нет — верни ошибку GraphQL.

### Блок 40. WebSockets: Двунаправленный Real-Time (484–490)
Учимся держать постоянное соединение с клиентом. Будем использовать библиотеку `github.com/gorilla/websocket` (самая популярная в Go).

484. **Upgrade до WebSockets:** Создай HTTP-хендлер. Используй `upgrader := websocket.Upgrader{}` и вызови `conn, err := upgrader.Upgrade(w, r, nil)`. Напиши цикл, который читает текстовое сообщение от клиента `conn.ReadMessage()` и отправляет его обратно `conn.WriteMessage()` (Эхо-сервер).
485. **WebSocket Клиент на Go:** Напиши отдельную Go-программу (клиент). Используй `websocket.DefaultDialer.Dial("ws://localhost:8080/ws", nil)`. В цикле отправляй серверу текущее время раз в секунду и читай ответ.
486. **Конкурентная запись (Паника!):** На сервере сохрани `conn` в глобальную переменную. Запусти 10 горутин, которые одновременно пытаются сделать `conn.WriteMessage(...)`. Поймай классическую панику WebSockets: *запись в одно WS-соединение из нескольких горутин не потокобезопасна!*
487. **Потокобезопасный WS-клиент:** Чтобы избежать паники из упр. 486, создай для каждого подключения структуру `Client` с каналом `send chan []byte`. Запусти для каждого клиента ОДНУ горутину-писатель (которая читает из `send` и делает `WriteMessage`) и ОДНУ горутину-читатель. Это классический паттерн работы с WS в Go.
488. **Паттерн Hub (Чат-комната):** Создай структуру `Hub`, которая хранит мапу активных клиентов `map[*Client]bool` и имеет канал `broadcast`. Любое сообщение, попадающее в `broadcast`, должно в цикле рассылаться всем клиентам из мапы. (Не забудь защитить мапу мьютексом или управлять ей через отдельную горутину, как в официальном туториале Gorilla).
489. **Ping / Pong (Keep-Alive):** Балансировщики нагрузки (например, Nginx) обрывают долгие WS-соединения, если в них нет активности. Настрой сервер на периодическую отправку `PingMessage` (раз в 10 секунд). Настрой клиентскую горутину на перехват `Pong` (`conn.SetPongHandler`) и продление дедлайна на чтение `conn.SetReadDeadline`.
490. **GraphQL Subscriptions (Скрещиваем темы):** В `gqlgen` (из прошлого блока) есть поддержка подписок (Subscriptions) поверх WebSockets. Добавь в схему `type Subscription { time: String! }`. Реализуй резолвер, который возвращает `<-chan string`. Внутри резолвера запусти горутину, которая пишет текущее время в этот канал каждую секунду. Подключись через Playground (он умеет работать с WS) и посмотри на бегущие данные в реальном времени.

---
**Совет к этому этапу:** При работе с WebSockets в Go всегда помни о **жизненном цикле горутин**. Каждое WS-соединение обычно порождает 2 горутины (для чтения и записи). Если клиент внезапно отключится (интернет пропал), ты должен гарантированно выйти из этих горутин, удалить клиента из Хаба и закрыть его каналы, иначе твой сервер быстро утечет по памяти!
