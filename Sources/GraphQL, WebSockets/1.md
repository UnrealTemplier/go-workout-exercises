## Часть XIX. GraphQL и WebSockets

### 88. GraphQL — основы

**Упражнение 19.1.** Установи `github.com/99designs/gqlgen`: `go run github.com/99designs/gqlgen init`. Изучи сгенерированную структуру: `graph/schema.graphqls`, `graph/model/models_gen.go`, `graph/resolver.go`.

**Упражнение 19.2.** Определи **GraphQL schema** для `User`: `type User { id: ID! name: String! email: String! createdAt: Time! }`. Сгенерируй код через `gqlgen generate`. Покажи, как gqlgen создаёт Go-структуры из schema.

**Упражнение 19.3.** Реализуй **Query resolver** `users: [User!]!`: `func (r *queryResolver) Users(ctx context.Context) ([]*model.User, error)`. Верни mock-данные из слайса. Запусти playground (`localhost:8080`) и выполни query.

**Упражнение 19.4.** Реализуй **Query resolver** с аргументом: `user(id: ID!): User`. Извлеки `id` из аргументов, найди пользователя. Верни `nil` + ошибку, если не найден.

**Упражнение 19.5.** Реализуй **Mutation resolver** `createUser(input: CreateUserInput!): User!`. Валидируй входные данные (email формат, name не пустой). Сохрани в in-memory map или PostgreSQL. Верни созданного пользователя.

**Упражнение 19.6.** Реализуй **Mutation resolver** `updateUser(id: ID!, input: UpdateUserInput!): User`. Обработай **partial update**: только переданные поля обновляются, остальные — без изменений. Используй `input.Name != nil` (pointer в Go).

**Упражнение 19.7.** Реализуй **Mutation resolver** `deleteUser(id: ID!): Boolean!`. Soft delete: установи `deleted_at`. Или hard delete — обсуди trade-offs. Верни `true` или ошибку.

**Упражнение 19.8.** Реализуй **Input type** с валидацией: `input CreateUserInput { name: String! @constraint(minLength: 2, maxLength: 100) email: String! @constraint(format: "email") }`. Используй directives или валидацию в resolver'е.

### 89. GraphQL — продвинутые темы

**Упражнение 19.9.** Реализуй **Nested resolver**: `type User { ... orders: [Order!]! }`. `orders` — отдельный resolver `func (r *userResolver) Orders(ctx context.Context, obj *model.User) ([]*model.Order, error)`. Покажи N+1 problem: запрос 100 пользователей → 100 запросов заказов.

**Упражнение 19.10.** Реши **N+1 problem** через **DataLoader**: `github.com/graph-gophers/dataloader`. Батчинг: вместо 100 отдельных запросов — 1 запрос `SELECT * FROM orders WHERE user_id IN (...)`. Реализуй `Loader` для `User.orders`.

**Упражнение 19.11.** Реализуй **Pagination** (offset-based): `users(limit: Int, offset: Int): [User!]!`. Верни `totalCount` через отдельный query или в payload. Обсуди проблемы offset-пагинации (performance при больших offset'ах).

**Упражнение 19.12.** Реализуй **Cursor-based pagination** (Relay spec): `type UserConnection { edges: [UserEdge!]! pageInfo: PageInfo! }`, `type UserEdge { node: User! cursor: String! }`. Курсор — base64-encoded `id:timestamp`. Поддерживай `first/after`, `last/before`.

**Упражнение 19.13.** Реализуй **Filtering**: `users(filter: UserFilter): [User!]!`, `input UserFilter { nameContains: String status: Status minCreatedAt: Time }`. Строй SQL динамически через `squirrel` или ручно. Обрабатывай nil-поля (фильтр не применяется).

**Упражнение 19.14.** Реализуй **Sorting**: `users(sort: UserSort!): [User!]!`, `enum UserSort { NAME_ASC NAME_DESC CREATED_AT_ASC CREATED_AT_DESC }`. Применяй `ORDER BY` в SQL. Валидируй sort-поле против whitelist.

**Упражнение 19.15.** Реализуй **Union type**: `union SearchResult = User | Order | Product`. Query: `search(query: String!): [SearchResult!]!`. В resolver'е верни разные типы. Клиент использует **inline fragments**: `... on User { name } ... on Order { total }`.

**Упражнение 19.16.** Реализуй **Interface**: `interface Node { id: ID! }`, `type User implements Node { ... }`, `type Order implements Node { ... }`. Query: `node(id: ID!): Node`. Верни любой тип, реализующий `Node`. Клиент использует inline fragments.

**Упражнение 19.17.** Реализуй **Custom scalar**: `scalar DateTime` (или используй встроенный `Time`). Реализуй `MarshalJSON`/`UnmarshalJSON` для кастомного формата (например, Unix timestamp или RFC3339). Зарегистрируй в gqlgen config.

**Упражнение 19.18.** Реализуй **Directives**: `directive @auth on FIELD_DEFINITION`. Примени: `type Query { me: User! @auth }`. В directive middleware проверяй JWT из `context`. Если невалиден — верни ошибку `UNAUTHENTICATED`.

**Упражнение 19.19.** Реализуй **Error handling**: кастомные ошибки через `gqlerror.Error`. Добавь `extensions` (код ошибки, поле): `&gqlerror.Error{Message: "validation failed", Extensions: map[string]interface{}{"code": "VALIDATION_ERROR", "field": "email"}}`.

**Упражнение 19.20.** Реализуй **Subscriptions** (через WebSocket, см. раздел ниже): `type Subscription { userCreated: User! }`. Клиент подписывается, получает события при создании пользователя.

### 90. WebSockets — основы

**Упражнение 19.21.** Напиши **WebSocket-эхо сервер** через `github.com/gorilla/websocket`: `upgrader := websocket.Upgrader{}`. В handler'е `conn, _ := upgrader.Upgrade(w, r, nil)`. Читай `conn.ReadMessage()`, пиши обратно `conn.WriteMessage(websocket.TextMessage, msg)`.

**Упражнение 19.22.** Напиши **WebSocket-клиент** в Go: `dialer := websocket.Dialer{}`, `conn, _, _ := dialer.Dial("ws://localhost:8080/ws", nil)`. Отправь сообщение, прочитай ответ. Покажи full-duplex: читай и пиши в разных горутинах.

**Упражнение 19.23.** Напиши **WebSocket чат-сервер**: храни `map[*websocket.Conn]bool` активных соединений с `sync.Mutex`. При получении сообщения — broadcast всем. Обработай подключение/отключение.

**Упражнение 19.24.** Напиши **WebSocket с heartbeat (ping/pong)**: сервер шлёт `ping` каждые 30 секунд (`conn.WriteControl(websocket.PingMessage, ...)`). Клиент отвечает `pong` автоматически (или вручную через `SetPongHandler`). Если pong не получен за 60 секунд — закрой соединение.

**Упражнение 19.25.** Напиши **WebSocket с reconnect**: клиент при разрыве ждёт 1s, 2s, 4s... (exponential backoff) до 30s. Переподключается, восстанавливает состояние (например, re-subscribe на каналы). Используй `context` для отмены.

### 91. WebSockets — продвинутые темы

**Упражнение 19.26.** Напиши **WebSocket с rooms/channels**: `map[string]map[*websocket.Conn]bool`. Клиент отправляет `{"action": "join", "room": "general"}`. Сообщения в room доставляются только подписчикам. Покажи изоляцию.

**Упражнение 19.27.** Напиши **WebSocket rate limiter**: per-connection limit — не более 10 сообщений/секунду. Используй token bucket или sliding window. При превышении — закрой соединение или отправь ошибку.

**Упражнение 19.28.** Напиши **WebSocket с authentication**: при подключении клиент передаёт JWT в query param (`?token=...`) или в `Sec-WebSocket-Protocol`. Валидируй в `Upgrader.CheckOrigin` или отдельном middleware. Закрой с `1008 Policy Violation`, если токен невалиден.

**Упражнение 19.29.** Напиши **WebSocket с graceful shutdown**: при `SIGINT` — закрой `upgrader`, отправь всем клиентам `CloseMessage` с кодом `1001 Going Away`, дождись `sync.WaitGroup`. Новые соединения не принимаются.

**Упражнение 19.30.** Напиши **WebSocket binary protocol**: отправляй protobuf-сообщения через `websocket.BinaryMessage`. Определи `message Type { JOIN = 1; LEAVE = 2; MESSAGE = 3; }`. Сериализуй через `proto.Marshal`, десериализуй через `proto.Unmarshal`.

### 92. GraphQL + WebSockets (Subscriptions)

**Упражнение 19.31.** Настрой **GraphQL subscriptions через WebSocket** в gqlgen: `transport.SSE` или `transport.Websocket`. Клиент отправляет `subscription { userCreated { id name } }`. Сервер пушит события при `createUser` mutation.

**Упражнение 19.32.** Реализуй **event-driven subscriptions**: `createUser` mutation пишет событие в Redis Pub/Sub или NATS. Subscription resolver подписывается на канал, транслирует в WebSocket. Покажи decoupling: mutation не знает о подписчиках.

**Упражнение 19.33.** Реализуй **subscription filtering**: клиент подписывается `subscription { userCreated(status: ACTIVE) { ... } }`. Только пользователи со статусом `ACTIVE` доставляются. Фильтр применяй на уровне event bus или resolver'а.

**Упражнение 19.34.** Реализуй **subscription authentication**: проверяй JWT при установке WebSocket-соединения. Закрой с `4401 Unauthorized`, если токен невалиден. Переподпиши при refresh токена.

**Упражнение 19.35.** Реализуй **subscription scalability** (Redis adapter): несколько инстансов GraphQL-сервера. Публикация в Redis → все инстансы получают → транслируют своим WebSocket-клиентам. Используй `go-redis` Pub/Sub.

### 93. Комплексные задачи

**Упражнение 19.36.** Реализуй **полный GraphQL API** для e-commerce:
- Types: `User`, `Product`, `Order`, `OrderItem`, `Review`
- Queries: `users`, `products(filter, sort, pagination)`, `order(id)`, `me`
- Mutations: `createOrder`, `addReview`, `updateProfile`
- Subscriptions: `orderStatusChanged(orderId)`, `newReview(productId)`
- DataLoader для N+1, cursor pagination, auth directive

**Упражнение 19.37.** Реализуй **GraphQL Gateway** (Apollo Federation-style, упрощённо):
- User Service: `type User @key(fields: "id") { id: ID! name: String! }`
- Order Service: `type Order { id: ID! userId: ID! user: User! }` — `User` резолвится через federation (запрос к User Service)
- Gateway агрегирует schema'ы, маршрутизирует queries

**Упражнение 19.38.** Реализуй **WebSocket real-time dashboard**:
- Сервер собирает метрики (CPU, memory, RPS) из микросервисов
- Публикует в WebSocket каждую секунду
- Клиент (браузер) отображает графики в реальном времени
- Поддержка multiple clients, room per service

**Упражнение 19.39.** Реализуй **WebSocket multiplayer game** (упрощённо, Tic-Tac-Toe):
- Комната на 2 игрока, matchmaking через Redis
- Состояние игры синхронизируется через WebSocket
- Ходы валидируются сервером (anti-cheat)
- Spectators: дополнительные WebSocket-подключения, readonly

**Упражнение 19.40.** Реализуй **GraphQL + WebSocket + gRPC hybrid**:
- Публичный API: GraphQL через HTTP/WebSocket (для фронтенда)
- Внутренние сервисы: gRPC (типобезопасность, производительность)
- GraphQL resolver'ы вызывают gRPC-сервисы
- Subscriptions через WebSocket, данные из gRPC streaming + Redis Pub/Sub

### Ключевые моменты для освоения GraphQL и WebSockets:

1. **GraphQL — client-driven API**: клиент запрашивает ровно нужные поля. Но это требует discipline: N+1 problem, сложность кэширования, раздувание запросов (query complexity analysis).
2. **DataLoader — must have**: без батчинга GraphQL убьёт БД. Каждый nested resolver — потенциальный запрос. DataLoader батчит за 1 tick event loop.
3. **Cursor pagination > offset**: для production с большими данными. Offset `O(n)` на больших таблицах, cursor — `O(log n)` с индексом.
4. **WebSockets — stateful**: хранение соединений в памяти, heartbeat, reconnect, backpressure. Не забывай про goroutine leak при забытых соединениях.
5. **Subscriptions через event bus**: не держи WebSocket-подключения в том же процессе, что и mutation'ы. Используй Redis/NATS для decoupling.
6. **Auth в WebSocket**: токен при подключении (query param или subprotocol), не в message payload. Закрывай с правильным close code.
7. **Hybrid architecture**: GraphQL для фронтенда (гибкость), gRPC для бэкенда (производительность, типобезопасность). Не пытайся натянуть GraphQL на всё.
