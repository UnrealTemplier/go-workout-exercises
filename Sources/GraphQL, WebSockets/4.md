Отличное дополнение! GraphQL и WebSockets — это две технологии, которые открывают дверь в мир **real-time приложений** и **гибких API**. GraphQL решает проблему over-fetching/under-fetching данных, а WebSockets обеспечивают двустороннюю связь с минимальной задержкой. В связке они позволяют строить современные интерактивные приложения (чаты, дашборды, коллаборативные редакторы, биржевые тикеры).

### Тема 86: WebSockets — Production-паттерны
751. Реализуйте **heartbeat mechanism**: сервер периодически отправляет ping-фреймы, клиент отвечает pong. Если pong нет N секунд — закрываем соединение.
752. Создайте **broadcast system**: функция, которая отправляет сообщение всем подключенным клиентам с обработкой ошибок (если один клиент "мертвый", это не должно блокировать остальных).
753. Реализуйте **message queue per client**: если клиент медленно читает, складывайте сообщения в буфер (канал) и отправляйте их асинхронно, чтобы не блокировать broadcast.
754. Добавьте **rate limiting** для WebSocket-сообщений: клиент не может отправлять больше N сообщений в секунду (защищает от спама и DoS).
755. Используйте **JWT-аутентификацию при handshake**: передавайте токен в query-параметре (`ws://host/ws?token=...`) или в первом сообщении после подключения.
756. Реализуйте **message acknowledgement (ACK)**: клиент подтверждает получение каждого сообщения, сервер ретраит неотправленные.
757. Создайте **presence system**: отслеживайте, кто из пользователей онлайн, и уведомляйте клиентов о появлении/исчезновении друзей.
758. Интегрируйте WebSocket с **Redis Pub/Sub** для масштабирования: сообщения, отправленные на одном инстансе сервера, доставляются клиентам на других инстансах.
759. Реализуйте **reconnection with state sync**: при реконнекте клиент отправляет ID последнего полученного сообщения, сервер досылает пропущенные.
760. Используйте **WebSocket subprotocols** (`Sec-WebSocket-Protocol`), если ваше приложение поддерживает несколько версий протокола.

    * **GraphQL API** (через gqlgen) для управления стримами, пользователями, чатами.

    * **JWT-аутентификация** для GraphQL и WebSocket.
    * **Rate limiting** через Redis Lua-скрипты.

### 💡 Золотые правила GraphQL и WebSockets:

#### GraphQL:
1. **gqlgen — ваш выбор.** Код-генерация из `.graphqls` файлов дает типобезопасность и производительность, избегая runtime-рефлексии. Не используйте библиотеки с "ручным" описанием схемы.

2. **DataLoader обязателен.** Без него вы получите N+1 проблему на любом мало-мальски сложном запросе. Это не оптимизация, это базовая гигиена.

3. **Ограничивайте сложность запросов.** GraphQL позволяет клиенту запросить хоть всю БД за один query. Всегда настраивайте query complexity analysis и depth limiting.

4. **Subscriptions — это WebSocket под капотом.** Понимайте, что GraphQL subscriptions используют WebSocket-транспорт, и все проблемы WebSocket (reconnection, heartbeat, scaling) актуальны и для них.

5. **Не используйте GraphQL для всего.** Для простых CRUD API REST может быть проще. GraphQL идеален для сложных графов данных с множеством связанных сущностей и для мобильных клиентов, где важен объем трафика.

#### WebSockets:
1. **Всегда реализуйте heartbeat.** TCP-соединение может "зависнуть" (half-open), и вы не узнаете об этом без ping-pong механизма. Это причина 90% "мертвых" подключений в продакшене.

2. **Используйте библиотеку `nhooyr.io/websocket`.** Она идиоматична для Go, корректно работает с context и имеет отличную документацию. `gorilla/websocket` больше не поддерживается.

3. **Не храните подключения в глобальной мапе без лимитов.** Это прямой путь к DoS. Всегда ограничивайте максимальное количество подключений на инстанс и используйте rate limiting.

4. **WebSockets не масштабируются "из коробки".** Если у вас 5 инстансов сервера, сообщение, отправленное на одном, не дойдет до клиентов на других. Используйте Redis Pub/Sub, NATS или Kafka как message broker.

5. **Graceful close — это must have.** Всегда отправляйте Close-фрейм с причиной перед закрытием соединения. Это позволяет клиенту понять, что произошло, и корректно реконнектиться.

6. **Для real-time данных подумайте о Server-Sent Events (SSE).** Если вам нужна только односторонняя связь сервер→клиент (например, уведомления), SSE проще, работает поверх HTTP/1.1 и не требует отдельного протокола.
