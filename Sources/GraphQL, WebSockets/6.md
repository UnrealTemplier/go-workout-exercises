### Раздел 34: Разработка API на GraphQL (Задачи 379–386)

*GraphQL предоставляет клиентам возможность запрашивать только те поля, которые им действительно необходимы. В этом блоке вы изучите генерацию кода по схеме (Schema-first), связывание данных, обработку ошибок и решение классической проблемы производительности N+1.*

379. **Проектирование схемы GraphQL**: Создайте файл схемы `schema.graphqls`. Опишите в нем тип `User` с полями `id: ID!`, `name: String!`, `email: String!`. Объявите корневой тип `Query` с методом `user(id: ID!): User` и `users: [User!]!`. Изучите разницу между подходами Schema-first (сначала схема) и Code-first (сначала код на Go) в экосистеме GraphQL.
380. **Настройка генератора `gqlgen`**: Установите самую популярную библиотеку для работы с GraphQL в Go — `github.com/99designs/gqlgen`. Сгенерируйте заготовку сервера с помощью команды `gqlgen generate` (предварительно настроив файл конфигурации `gqlgen.yml`). Запустите сгенерированный сервер и откройте в браузере интерактивную песочницу GraphQL Playground (обычно на порту `8080`).
381. **Реализация Query-резолверов**: В сгенерированном файле `schema.resolvers.go` найдите заглушки методов `User` и `Users`. Реализуйте их логику: извлеките данные из тестовой мапы в оперативной памяти и верните клиенту. Выполните тестовый запрос в Playground, запрашивая только поле `name`, а затем все поля сразу.
382. **Добавление мутаций (Mutations)**: Добавьте в схему `.graphqls` тип `Mutation` и метод `createUser(input: NewUserInput!): User!`. Опишите тип `NewUserInput` с необходимыми для регистрации полями. Перегенерируйте код через `gqlgen` и реализуйте резолвер для мутации, добавив логику сохранения нового пользователя и валидации входящих полей (например, проверка формата email).
383. **Связанные типы (Связи один-ко-многим)**: Добавьте в схему тип `Post` (поля `id`, `title`, `body`). Свяжите сущности: добавьте в тип `User` поле `posts: [Post!]!`. Перегенерируйте код. Обратите внимание, что `gqlgen` создаст для структуры `User` кастомный резолвер `Posts`. Напишите в нем логику получения постов конкретного пользователя по его ID.
384. **Решение проблемы N+1 (Data Loaders)**: 
    * Напишите запрос, который выбирает список всех пользователей, а для каждого пользователя запрашивает его посты.
    * Добавьте логирование SQL/БД-запросов. Обратите внимание, как для списка из $N$ пользователей ваша программа делает $1$ запрос на список пользователей и $N$ отдельных запросов на получение постов для каждого (проблема N+1).
    * Интегрируйте библиотеку DataLoader (например, `github.com/graph-gophers/dataloader` или встроенные средства `gqlgen`). Настройте батчинг (группировку) запросов: программа должна собрать все ID пользователей за один проход, сделать ровно один запрос вида `WHERE user_id IN (...)` к базе данных и распределить результаты по пользователям. Убедитесь, что количество запросов к БД сократилось до двух.
385. **Кастомные скаляры (Scalars)**: По умолчанию GraphQL поддерживает только базовые типы (String, Int, Float, Boolean, ID). Добавьте в схему кастомный скаляр `scalar Date`. Настройте `gqlgen` так, чтобы он связывал этот скаляр со стандартным Go-типом `time.Time`. Напишите методы маршалинга и демаршалинга для преобразования строки формата `YYYY-MM-DD` в `time.Time` и обратно.
386. **Обработка ошибок в GraphQL**: Напишите логику: если при поиске пользователя по ID он не найден, резолвер должен возвращать ошибку. Изучите спецификацию GraphQL: в отличие от REST, GraphQL-сервер всегда должен возвращать HTTP-статус `200 OK`, но при этом помещать описание ошибок в массив `errors` корневого JSON-ответа, сохраняя успешные части данных в объекте `data`. Реализуйте это поведение с помощью возврата ошибки из метода резолвера.

### Раздел 35: Real-time коммуникации с WebSockets (Задачи 387–394)

*Протокол WebSocket обеспечивает полнодуплексный обмен данными между клиентом и сервером по одному TCP-соединению. Вы научитесь апгрейдить соединение, управлять жизненным циклом сокетов и обеспечивать потокобезопасность.*

387. **Апгрейд HTTP-соединения**: Напишите стандартный HTTP-сервер. В обработчике `/ws` выполните процедуру обновления (upgrade) протокола HTTP до WebSocket с помощью библиотеки `github.com/gorilla/websocket` (используя структуру `websocket.Upgrader`). Настройте CORS, разрешив подключения со всех доменов во время рукопожатия (handshake).
388. **WebSocket Echo-сервер**: После успешного апгрейда соединения войдите в бесконечный цикл. Считывайте сообщения от клиента с помощью `conn.ReadMessage` и отправляйте их обратно в неизменном виде через `conn.WriteMessage`. Корректно обработайте выход из цикла и закрытие соединения, если клиент отключился (проверка на ошибки чтения).
389. **Архитектура широковещательной рассылки (Hub/Router)**: Напишите WebSocket чат-комнату.
    * Создайте структуру `Hub`, которая хранит список всех активных соединений клиентов `map[*websocket.Conn]bool`.
    * Напишите канал для регистрации новых клиентов, канал для отключения и канал для рассылки сообщений `broadcast chan []byte`.
    * Запустите горутину-диспетчер `run()`, которая слушает канал `broadcast` и в цикле отправляет полученное сообщение всем зарегистрированным клиентам.
390. **Потокобезопасность записи в сокет**: 
    * Объясните в комментариях к коду, почему метод `websocket.Conn.WriteMessage` не является потокобезопасным (одновременная запись из разных горутин в один сокет приведет к панике и разрыву соединения).
    * Напишите защищенный обертчик для отправки сообщений. Каждое клиентское соединение должно иметь свою фоновую горутину-писателя (write pump), которая слушает персональный канал сообщений горутины и последовательно пишет их в сокет, гарантируя строго один поток записи.
391. **Контроль мертвых соединений (Heartbeats/Ping-Pong)**: Если у клиента пропал интернет без явного закрытия вкладки браузера, сервер может держать сокет открытым бесконечно (утечка ресурсов). Настройте механизм пингов на сервере:
    * Сервер должен периодически (например, раз в 10 секунд) отправлять клиенту PING-кадр с помощью `conn.WriteControl(websocket.PingMessage, ...)`.
    * Настройте обработчик PONG-сообщений от клиента с помощью `conn.SetPongHandler`. Если от клиента не пришел PONG в течение заданного интервала ожидания (read deadline), сервер должен принудительно разорвать соединение.
392. **Передача структурированных данных (JSON по WebSockets)**: Измените ваш Echo-сервер так, чтобы он работал не с голым текстом, а со структурами. Объявите структуру `Event` с полями `Type string` и `Payload any`. Используйте методы `conn.ReadJSON` и `conn.WriteJSON` для автоматической сериализации/десериализации данных при передаче по сокету.
393. **Интеграция: Подписки в GraphQL (Subscriptions)**: Объедините знания из двух разделов. Добавьте в вашу схему GraphQL подписку: `subscription { messageAdded(room: String!): ChatMessage! }`. Реализуйте подписку в `gqlgen`, которая под капотом использует протокол WebSocket (обычно поверх подпротокола `graphql-ws` или `graphql-transport-ws`) для автоматической отправки событий клиенту при срабатывании мутации `createMessage`.
394. **Авторизация на фазе Handshake**: Напишите защиту вашего WebSocket-соединения. Клиент при подключении должен передавать JWT-токен в query-параметрах HTTP-запроса (например, `/ws?token=my_jwt`). Внутри HTTP-обработчика *до* вызова метода `Upgrader.Upgrade` извлеките токен, проверьте его валидность и, если токен неверный или просрочен, верните стандартный HTTP-ответ `401 Unauthorized`, прервав подключение на этапе рукопожатия.
