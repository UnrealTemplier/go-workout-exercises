### Раздел 43: Криптография и безопасность приложений (AppSec / Web Security) (Задачи 536–555)

#### Подраздел 43.1: Криптография (Симметричное и асимметричное шифрование) (Задачи 536–542)

*Использование надежных стандартов шифрования и правильная работа с источниками случайных чисел защищают конфиденциальные данные от компрометации.*

536. **Безопасная генерация случайных чисел**: Напишите генератор паролей и токенов сессий. Объясните разницу между псевдослучайными числами из стандартного пакета `math/rand` и криптографически стойкими случайными числами из пакета `crypto/rand` [536]. Напишите функцию генерации безопасной случайной последовательности байт заданной длины с использованием `rand.Read` [536].
537. **Симметричное шифрование AES-GCM**: Напишите функции для шифрования и дешифрования конфиденциальных файлов на диске с использованием симметричного алгоритма AES.
    * Используйте пакеты `crypto/aes` [536] и `crypto/cipher` [537].
    * Выберите режим шифрования GCM (Galois/Counter Mode), так как он обеспечивает аутентифицированное шифрование (AEAD) [537].
    * Обеспечьте генерацию уникального вектора инициализации (nonce) для каждой операции шифрования и упакуйте его в начало зашифрованного массива байт [537].
538. **Асимметричное шифрование RSA-OAEP**: Напишите утилиту для обмена зашифрованными сообщениями. Сгенерируйте пару ключей RSA длиной 4096 бит с помощью `crypto/rsa` [536] и `crypto/rand` [536]. Напишите код шифрования сообщения на публичном ключе и его расшифрования на приватном ключе с использованием криптографически стойкого алгоритма `rsa.EncryptOAEP` [538] и `rsa.DecryptOAEP` [538] с хэш-функцией SHA-256.
539. **Электронная цифровая подпись (RSA-PSS)**: Напишите систему подтверждения авторства документов. С помощью вашей сгенерированной ключевой пары RSA подпишите хэш текстового файла на приватном ключе, используя алгоритм PSS (`rsa.SignPSS`) [539]. Напишите функцию верификации этой подписи на публичном ключе (`rsa.VerifyPSS`) [539].
540. **Обмен ключами Диффи-Хеллмана (ECDH)**: Напишите симуляцию безопасного рукопожатия двух сервисов (Алисы и Боба). Используя пакет `crypto/ecdh` [540], сгенерируйте пары ключей на эллиптической кривой P-256 [540]. Напишите код вычисления общего секретного ключа (Shared Secret) для Алисы и Боба с помощью метода `dh.ECDH` [540].
541. **Экспорт и импорт PEM-ключей**: Напишите код сохранения ваших сгенерированных ключей на диск. Преобразуйте приватный ключ в формат PKCS#8, закодируйте его в PEM-блок с типом `PRIVATE KEY` с помощью пакета `encoding/pem` [541] и запишите в файл. Напишите код обратного считывания и парсинга PEM-файла с диска в объект ключа Go.
542. **HMAC-подпись для веб-хуков**: При получении событий от сторонней системы (например, Stripe или GitHub) нужно гарантировать, что запрос не подделан злоумышленником. Напишите генератор и валидатор подписи запроса. Используйте алгоритм HMAC-SHA256 (пакет `crypto/hmac` [542]). Для подписи используйте секретный ключ, известный только вашему серверу и внешней системе.

#### Подраздел 43.2: Хэширование паролей и современные токены (Задачи 543–548)

*Правильное хэширование паролей предотвращает их брутфорс в случае утечки БД, а современные стандарты токенов закрывают архитектурные уязвимости JWT.*

543. **Хэширование паролей с `bcrypt`**: Напишите функции регистрации и авторизации пользователей с хэшированием паролей. Используйте стандартный для индустрии пакет `golang.org/x/crypto/bcrypt` [543]. Объясните влияние параметра стоимости (cost factor) на время вычисления хэша [543]. Протестируйте скорость авторизации при стоимости 10, 12 и 14, написав бенчмарк.
544. **Современное хэширование с Argon2id**: Согласно рекомендациям OWASP, Argon2id является наиболее устойчивым алгоритмом к подбору паролей на GPU/ASIC. Реализуйте хэширование паролей с использованием пакета `golang.org/x/crypto/argon2` [544]. Задайте параметры: объем используемой памяти 64 МБ, количество итераций 3, уровень параллелизма 4, длина соли 16 байт [544]. Напишите функцию проверки соответствия введенного пароля сохраненному хэшу.
545. **PASETO-токены вместо JWT**: Стандарт JWT содержит ряд критических уязвимостей в дизайне (например, поддержка алгоритма `"none"`, уязвимости парсинга заголовков). Напишите генератор сессионных токенов авторизации на базе современного стандарта PASETO (Platform-Agnostic Security Tokens) версии 4 (локальные токены с симметричным шифрованием v4.local) [545] с использованием библиотеки `github.com/o1egl/paseto` или аналогичной [545]. Напишите комментарий, почему PASETO безопаснее JWT по умолчанию [545].
546. **Механизм ротации ключей подписи (Key Rotation)**: Реализуйте в вашей системе авторизации на базе PASETO/JWT механизм ротации ключей. Сервер должен хранить список активных ключей подписи. Новые токены должны подписываться самым свежим (актуальным) ключом, однако при проверке входящих токенов система должна успешно принимать токены, подписанные старыми ключами, если их время жизни (TTL) еще не истекло.
547. **Авторизация через OAuth2 (Authorization Code Flow)**: Напишите интеграцию вашего веб-сервера со сторонним провайдером авторизации (например, GitHub или Google), используя библиотеку `golang.org/x/oauth2` [547]. Реализуйте два HTTP-обработчика:
    * `/login` — генерирует случайную строку `state` (для защиты от CSRF), сохраняет её в сессию/cookie и перенаправляет пользователя на страницу авторизации провайдера [547].
    * `/callback` — проверяет совпадение `state`, запрашивает у провайдера обмен полученного `code` на `AccessToken` и сохраняет токен [547].
548. **Интеграция с OpenID Connect (OIDC)**: Расширьте OAuth2-авторизацию из предыдущей задачи до стандарта OIDC. Используйте пакет `github.com/coreos/go-oidc`. Напишите код, который запрашивает у провайдера `ID Token` (JWT), автоматически скачивает публичные ключи провайдера из эндпоинта JWKS (JSON Web Key Sets), валидирует подпись и извлекает из токена профиль пользователя (email, имя, ID).

#### Подраздел 43.3: Защита от специфических веб-уязвимостей (Задачи 549–555)

*Предотвращение атак на переполнение ресурсов, атак по времени выполнения и утечек конфиденциальной информации.*

549. **Защита от Doс на переполнение памяти (Payload Limit)**: При разборе входящего JSON-тела POST-запроса злоумышленник может отправить файл размером 5 ГБ, что мгновенно вызовет нехватку оперативной памяти (OOM) и падение вашего сервера. Напишите middleware, которое принудительно оборачивает чтение тела запроса `req.Body` в ограничитель размера `http.MaxBytesReader` [549] (например, лимит 1 МБ) перед вызовом `json.NewDecoder` [549]. Протестируйте поведение, отправив файл большего размера.
550. **Защита от SSRF (Server-Side Request Forgery)**: Ваше приложение принимает от пользователя URL картинки, скачивает её по HTTP и сохраняет на диск.
    * Объясните опасность атаки: если пользователь передаст адрес `http://127.0.0.1:8080/admin` или локальные IP-адреса вашей внутренней сети (RFC 1918), ваш сервер сам сделает опасный запрос во внутренний контур [550].
    * Напишите безопасный HTTP-клиент: перед отправкой запроса выполните резолвинг хоста в IP-адрес. Напишите проверку, блокирующую запрос, если IP-адрес относится к приватным диапазонам, loopback (`127.0.0.1`) или link-local (`169.254.169.254`) [550]. Используйте методы `net.IP.IsLoopback` и `net.IP.IsPrivate` [550].
551. **Автоматический аудит уязвимостей (gosec)**: Напишите два SQL-запроса к базе данных: один небезопасный (с конкатенацией пользовательской строки в тело запроса) и один безопасный (с использованием параметров). Установите инструмент статического анализа безопасности Go — `github.com/securego/gosec` [551]. Запустите проверку вашего кода через консоль и убедитесь, что `gosec` находит уязвимую конкатенацию и предупреждает о возможности SQL-инъекции [551].
552. **Безопасная настройка CORS**: Напишите middleware для настройки заголовков CORS (Cross-Origin Resource Sharing) [552]. Объясните в комментариях опасность использования небезопасной конфигурации `Access-Control-Allow-Origin: *` совместно с разрешением авторизации `Access-Control-Allow-Credentials: true` [552]. Реализуйте безопасную логику: middleware должно динамически проверять входящий заголовок `Origin` по белому списку разрешенных доменов вашей компании перед тем, как записать его в заголовок ответа.
553. **Защита от утечки технической информации (Information Disclosure)**: Напишите middleware обработки паник. Если в кодовой базе произошла паника, middleware должно записать подробный стек вызовов во внутреннюю систему логирования (для разработчиков), но пользователю вернуть строго стандартизированный JSON вида `{"error": "Internal Server Error"}` со статусом 500 [553]. Убедитесь, что наружу не просачиваются пути к файлам сервера, версии пакетов Go и технические детали ошибок.
554. **Затирание секретов в оперативной памяти**: Переменные типа `string` в Go неизменяемы, поэтому при обработке пароля или секретного ключа они могут надолго зависнуть в оперативной памяти (в куче) до запуска GC, что позволит злоумышленнику считать их из дампа памяти (heap dump) [554]. Напишите код: принимайте пароли в виде среза байт `[]byte`. После того как пароль проверен, принудительно затрите этот срез байт нулями во всей выделенной под него памяти с помощью функции `copy` или ручного обнуления элементов в цикле [554].
555. **Защита от атак по времени (Constant-Time Compare)**: Напишите функцию проверки API-токена пользователя. Объясните в комментариях опасность стандартного сравнения строк через оператор `==` (сравнение завершается на первом несовпадающем символе, что позволяет злоумышленнику угадать токен символ за символом по микросекундным изменениям времени ответа сервера) [555]. Исправьте уязвимость, применив функцию сравнения за константное время `crypto/subtle.ConstantTimeCompare` [555].
