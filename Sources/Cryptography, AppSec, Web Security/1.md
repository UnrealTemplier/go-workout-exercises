## Блок 10. Симметричное и асимметричное шифрование

### Уровень 1. Основы и генерация материала
133. **CSPRNG vs псевдослучайность.** Сгенерируйте 1 млн байт через `crypto/rand` и через `math/rand`. Покажите, что `math/rand` предсказуем (восстановите seed по первым значениям), а `crypto/rand` — нет. Объясните, почему `math/rand` нельзя использовать для ключей и nonce.
134. **AES-256-GCM: полный цикл.** Сгенерируйте ключ (32 байта из `crypto/rand`), nonce (12 байт, уникальный для каждого сообщения). Зашифруйте и расшифруйте сообщение через `crypto/aes` + `cipher.NewGCM`. Объясните, почему повтор nonce с одним ключом разрушает конфиденциальность (CTR-режим).
135. **AES-GCM с AAD (Associated Data).** Зашифруйте payload, передав в `Seal` AAD — например, `user_id:123`. Покажите, что изменение AAD при расшифровке (`user_id:999`) вызывает ошибку. Объясните, зачем нужен AAD в API-токенах и TLS-записях.
136. **Сравнение режимов: GCM vs CTR vs CBC.** Реализуйте шифрование одного и того же сообщения тремя способами. Объясните, почему CBC требует padding и уникальный IV, CTR — уникальный nonce, а GCM — аутентифицированное шифрование (AEAD) и предпочтителен.
137. **Envelope encryption (ключ в ключе).** Реализуйте схему: случайный Data Encryption Key (DEK) шифрует файл через AES-GCM, сам DEK шифруется Master Key (KEK) через RSA-OAEP или AES-GCM. Объясните, зачем нужна ротация KEK без перешифрования всех данных.

### Уровень 2. Асимметричная криптография
138. **RSA: генерация и OAEP.** Сгенерируйте пару RSA 2048/4096 бит. Зашифруйте сообщение через `rsa.EncryptOAEP`, расшифруйте. Объясните, почему PKCS#1 v1.5 устарел (Bleichenbacher attacks) и почему OAEP — стандарт.
139. **RSA-подписи: PSS vs PKCS#1 v1.5.** Подпишите хеш SHA-256 через `rsa.SignPSS` и `rsa.SignPKCS1v15`. Проверьте обе. Объясните, почему PSS (Probabilistic Signature Scheme) рекомендуется для новых систем.
140. **Гибридное шифрование (как в TLS).** Реализуйте полный протокол: клиент генерирует ephemeral AES-ключ, шифрует его RSA-OAEP (или ECDH) открытым ключом сервера, затем шифрует данные AES-GCM. Объясните, почему асимметричное шифрование не используется для bulk-данных.
141. **Ed25519: современные подписи.** Сгенерируйте ключевую пару `crypto/ed25519`, подпишите сообщение, проверьте. Сравните размер ключей (32 байт), подписей (64 байта) и скорость с RSA-PSS. Объясните, почему Ed25519 предпочтителен в современных протоколах (SSH, WireGuard, PASETO).

### Уровень 3. Инфраструктура открытых ключей
142. **PEM/DER и хранение ключей.** Реализуйте сохранение приватного RSA/Ed25519 ключа в PEM (PKCS#8), загрузку обратно. Добавьте шифрование приватного ключа паролем (AES-256-CBC или AES-256-GCM через `x509.EncryptPEMBlock`). Объясните, почему plaintext private key на диске — критическая уязвимость.
143. **x509: парсинг и валидация сертификатов.** Загрузите TLS-сертификат через `x509.ParseCertificate`. Проверьте: срок действия (`NotBefore`/`NotAfter`), Subject/SAN (`DNSNames`), KeyUsage. Напишите функцию `VerifyHostname` и `VerifyChain` с кастомным `x509.CertPool`.
144. **TLS hardening.** Настройте `http.Server` с `tls.Config`: минимум TLS 1.2 (или 1.3), строгий список cipher suites (только AEAD), отключение `InsecureSkipVerify` в клиенте. Объясните, почему `tls.Config` с `ClientAuth: tls.RequireAndVerifyClientCert` нужен для mTLS.

## Блок 11. Хеширование паролей и KDF

### Уровень 1. Базовые хеши
145. **bcrypt: полный цикл.** Реализуйте регистрацию и аутентификацию через `golang.org/x/crypto/bcrypt`. Сгенерируйте хеш с `cost=10` и `cost=14`. Замерьте время хеширования. Объясните, почему `bcrypt.CompareHashAndPassword` использует constant-time сравнение.
146. **argon2id: современный стандарт.** Реализуйте хеширование через `golang.org/x/crypto/argon2`. Используйте параметры: time=1, memory=64 MB, threads=4, salt=16 байт (из `crypto/rand`), key length=32. Объясните, как подбирать параметры под ваш CPU/память.
147. **Соль: уникальность и хранение.** Напишите функцию, которая генерирует случайную соль (16 байт) для каждого пользователя. Объясните, почему глобальная соль — уязвимость (rainbow tables), и как хранить соль вместе с хешем (например, `base64(salt+hash)`).

### Уровень 2. Продвинутые сценарии
148. **Password-Based KDF.** Используйте `argon2id` или `bcrypt` для получения ключа из пароля, затем используйте этот ключ в AES-GCM. Объясните разницу между *password hashing* (для проверки) и *key derivation* (для шифрования), и почему `bcrypt` не подходит как KDF для ключей AES.
149. **Transparent hash upgrade.** Реализуйте middleware: при успешном логине проверяете пароль против старого bcrypt-хеша, если совпало — перехешируете в argon2id и обновляете в БД. Объясните стратегию миграции без сброса паролей всех пользователей.
150. **Timing attacks и constant-time сравнение.** Напишите наивную проверку API-ключа (`if token == storedToken`) и измерьте время выполнения через `testing.B` с разными префиксами. Затем используйте `crypto/subtle.ConstantTimeCompare`. Объясните, почему `==` на строках уязвим для timing-атак.
151. **Pepper.** Добавьте application-wide secret (pepper — 32 байта из env) к паролю *перед* хешированием argon2id. Объясните, чем pepper отличается от salt (один на приложение, не хранится в БД, усложняет атаку при утечке БД).

### Уровень 3. HMAC и целостность
152. **HMAC-SHA256.** Реализуйте подпись webhook-запросов или API-ответов через `crypto/hmac` + `sha256`. Покажите, почему `HMAC(key, data)` безопаснее, чем `SHA256(key || data)` (length extension attacks). Реализуйте verify с `subtle.ConstantTimeCompare`.

## Блок 12. Токены, OAuth2/OIDC и аутентификация

### Уровень 1. JWT и его уязвимости
153. **JWT HS256: ручная сборка.** Сгенерируйте JWT вручную (header + payload + HMAC-SHA256) и через пакет (`github.com/golang-jwt/jwt/v5`). Проверьте подпись. Объясните структуру и почему base64url — не шифрование.
154. **Атака «alg: none».** Создайте JWT с `"alg":"none"`, удалите signature, покажите, что наивный парсер может принять его как валидный. Напишите защиту: жёсткий whitelist допустимых алгоритмов (`HS256`, `RS256`, `EdDSA`).
155. **Алгоритмическая путаница (RS256 vs HS256).** Покажите атаку: сервер проверяет RS256, но атакующий подписывает JWT симметричным HMAC с использованием публичного RSA-ключа как секрета. Напишите защиту: раздельные ключи для симметричных и асимметричных алгоритмов.
156. **JWKS endpoint.** Реализуйте endpoint `/.well-known/jwks.json`, который отдаёт публичные ключи в формате JWK. Напишите middleware, который загружает JWKS, кэширует и проверяет JWT подпись по `kid` (key ID) из header.

### Уровень 2. PASETO — безопасная альтернатива JWT
157. **PASETO v4.local (symmetric).** Используйте пакет `github.com/o1egl/paseto` (или аналог). Создайте токен с claims (`user_id`, `exp`), зашифруйте ключом из `crypto/rand` (32 байта). Объясните, почему в PASETO нет поля `alg` и почему payload зашифрован, а не просто base64.
158. **PASETO v4.public (asymmetric).** Создайте подписанный токен с Ed25519. Сравните с JWT RS256: размер токена, скорость проверки, отсутствие алгоритмической путаницы. Объясните, почему PASETO «secure by default».

### Уровень 3. OAuth2 и OIDC
159. **OAuth2 Authorization Code + PKCE.** Реализуйте клиентское веб-приложение: endpoint `/auth` (редирект на IdP), `/callback` (обмен code на token). Добавьте PKCE (`code_verifier`/`code_challenge`). Объясните, зачем PKCE при отсутствии client secret (SPA, мобильные приложения).
160. **OIDC: проверка id_token.** Реализуйте проверку JWT `id_token` от Google/Auth0: валидация `iss`, `aud`, `exp`, `nonce`. Извлеките claims (`sub`, `email`, `email_verified`). Объясните, чем `id_token` отличается от `access_token`.
161. **Refresh Token Rotation.** Реализуйте хранение refresh tokens в БД с полями `token_hash`, `family_id`, `issued_at`, `expires_at`, `revoked`. При обмене refresh → access выдавайте новую пару, инвалидируйте старую. Объясните, как это защищает от replay-атак и parallel refresh.
162. **Server-side sessions vs JWT.** Реализуйте сессии в Redis с `session_id` в `HttpOnly; Secure; SameSite=Strict` cookie. Сравните с stateless JWT: возможность мгновенной инвалидации (logout), размер cookie, проблема с масштабированием хранилища. Объясните, когда что использовать.

### Уровень 4. Продвинутые сценарии
163. **API Key с HMAC-подписью запроса.** Реализуйте AWS Signature v4-style подпись: canonical request → HMAC-SHA256 с секретом. Middleware проверяет подпись, timestamp (±5 минут), replay (nonce cache). Объясните, почему API keys в query string (`?api_key=...`) утечкают в логах.
164. **Scope-based access control.** Реализуйте middleware, который извлекает scopes из токена (OAuth2) и проверяет требуемые scopes для endpoint (`read:users`, `write:posts`). Объясните разницу между scopes (что разрешено делать) и claims (кто пользователь).
165. **DPoP (Demonstrating Proof-of-Possession).** Реализуйте упрощённый DPoP: JWT, подписанный ключом клиента (Ed25519), содержащий `htm` (HTTP method) и `htu` (URI). Сервер проверяет подпись и привязку к запросу. Объясните, как это защищает от theft bearer token (токен не работает без приватного ключа клиента).

## Блок 13. Защита API и типичные уязвимости (AppSec)

### Уровень 1. DoS и ограничения
166. **Ограничение размера тела.** Реализуйте middleware с `http.MaxBytesReader` (например, 1 MB). Покажите, что JSON на 100 MB вызывает `http: request body too large`. Объясните, почему `json.NewDecoder(r).Decode(&v)` без лимита — уязвимость.
167. **Безопасный JSON Decoder.** Напишите обёртку над `json.Decoder`, которая: (1) ограничивает глубину вложенности (защита от stack exhaustion через deeply nested JSON), (2) использует `UseNumber` для предотвращения float64 truncation, (3) проверяет количество ключей в объекте. Объясните, почему `encoding/json` по умолчанию не защищён от этих атак.
168. **Rate Limiting.** Реализуйте token bucket rate limiter (per IP и per user) с использованием `golang.org/x/time/rate`. Примените к endpoint `/login` для защиты от brute-force. Объясните, почему rate limit на уровне reverse proxy (nginx) недостаточен для логики приложения.

### Уровень 2. SSRF и инъекции
169. **SSRF: атака и защита.** Реализуйте сервис, который по URL делает HTTP-запрос (например, webhook fetch). Покажите атаку: `http://127.0.0.1:22/`, `http://169.254.169.254/latest/meta-data/` (AWS metadata), `http://internal-service/`. Напишите защиту: parse URL, resolve IP через `net.Resolver`, проверка against blocklist (loopback, link-local, private ranges), deny по умолчанию (whitelist), запрет redirects.
170. **Path Traversal.** Реализуйте endpoint `/files?name=report.pdf`. Покажите атаку `../../../etc/passwd`. Исправьте: `filepath.Clean`, `filepath.Join` с базовой директорией, проверка `strings.HasPrefix` после clean. Объясните, почему `filepath.Clean` alone недостаточно.
171. **SQL Injection.** Напишите уязвимый запрос через `fmt.Sprintf("SELECT * FROM users WHERE id = %s", userInput)`. Покажите инъекцию `' OR '1'='1`. Исправьте через `db.QueryRow("SELECT * FROM users WHERE id = ?", id)`. Объясните, почему prepared statements — единственный надёжный способ.
172. **Command Injection.** Реализуйте функцию, которая конвертирует изображение через `exec.Command("convert", input, output)`. Покажите уязвимость при `input = "input.jpg; rm -rf /"`. Исправьте: строгая валидация regex, передача аргументов слайсом (без shell), использование `filepath.Ext` whitelist.

### Уровень 3. Веб-специфичные уязвимости
173. **Open Redirect.** Реализуйте `/login?redirect=https://evil.com`. Покажите phishing-атаку. Защита: whitelist allowed hosts, использование relative paths only (`/dashboard`), или проверка `url.Parse` + `Hostname` against списка доверенных.
174. **CORS: безопасная настройка.** Напишите middleware, который обрабатывает `Access-Control-Allow-Origin` (строгий whitelist, не `*`), `Access-Control-Allow-Methods`, `Access-Control-Allow-Credentials`. Объясните, почему `*` + `Allow-Credentials: true` — уязвимость (CSRF с CORS bypass для публичных API).
175. **Security Headers.** Реализуйте middleware, добавляющий: `Strict-Transport-Security` (HSTS), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy`. Объясните назначение каждого заголовка и почему их отсутствие упрощает XSS/clickjacking.

### Уровень 4. Аудит и secure-by-default
176. **Secure Configuration Checker.** Напишите модуль, который при старте приложения проверяет: (1) `os.Getenv("SECRET_KEY")` не равен default/empty, (2) TLS включён в production, (3) `pprof` не exposed на public port, (4) `GIN_MODE` / `ENV` не `debug`, (5) пароли БД не захардкожены. При нарушении — `log.Fatal` с описанием. Объясните концепцию «secure by default» и «fail fast».

## Как встроить в общий план обучения

**Рекомендуемый порядок прохождения всех блоков:**

1. **Блок 10 (Шифрование)** — начните сразу после Блока 4 (`unsafe`), так как криптографические пакеты активно используют `unsafe` для zero-copy и constant-time операций.
2. **Блок 11 (Хеши)** — параллельно с Блоком 10, так как KDF тесно связан с симметричным шифрованием.
3. **Блок 12 (Токены)** — после освоения RSA/Ed25519 и HMAC, так как JWT/PASETO/OAuth2 — это прикладное использование этих примитивов.
4. **Блок 13 (AppSec)** — финальный блок, требует понимания HTTP-сервера (`net/http`), middleware и контекста.

**Ключевые инструменты и переменные для тренировки:**
```bash
# Для тестирования TLS
openssl req -x509 -newkey rsa:4096 -keyout key.pem -out cert.pem -days 365 -nodes

# Для анализа JWT/PASETO
jwt.io для ручной проверки структуры

# Для тестирования SSRF
python3 -m http.server 8080 &  # локальный target
curl "http://your-app/fetch?url=http://169.254.169.254/"  # AWS metadata

# Для проверки заголовков
curl -I https://your-app/ | grep -i "x-\|strict\|content-security"
```

**Что фиксировать в результатах:**
- Для криптографии: hex-дампы, размеры ключей/подписей, бенчмарки (ops/sec).
- Для безопасности: PoC-эксплойт + исправленный код + объяснение, почему защита работает.
- Для OAuth2: sequence-диаграмма (ASCII) flow с PKCE и без.

Если нужно — могу детально расписать **любое конкретное упражнение** с шаблоном кода, или выдать финальный блок на тему *«Каналы в рантайме, netpoller, sync.Pool, memory model и race detector»*.
