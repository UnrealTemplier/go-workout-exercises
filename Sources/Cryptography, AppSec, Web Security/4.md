### Тема 143: Основы криптографии и работа со случайностью
*Фундамент любой криптосистемы — это качественная случайность и базовые примитивы.*

1441. **crypto/rand vs math/rand:** Напишите код, который использует оба пакета для генерации чисел. Покажите, почему `math/rand` **никогда** нельзя использовать для security-задач (предсказуемость seed, state-based атаки).

1442. **Генерация криптографически стойкого токена:** Напишите функцию `GenerateToken(n int) (string, error)`, которая возвращает base64url-закодированные `n` случайных байт через `crypto/rand.Read`.

1443. **Session ID generation:** Создайте генератор session ID длиной минимум 128 бит энтропии. Объясните, почему этого достаточно для защиты от brute-force.

1444. **API key format:** Реализуйте генерацию API ключей в формате `prefix_random_checksum` (например, `sk_live_3xK9mN_abc`). Префикс помогает в логах, чексумма — детектирует опечатки.

1445. **Entropy analysis:** Напишите утилиту, которая оценивает энтропию сгенерированных данных через подсчёт Shannon entropy. Убедитесь, что ваш генератор даёт ~8 бит/байт.

1446. **Base64url vs Base64:** Покажите разницу между standard и URL-safe кодированием. Почему для токенов в URL/Cookie нужен именно base64url (без `+`, `/`, `=`)?

1447. **SHA-256 базовое использование:** Вычислите SHA-256 хэш строки через `crypto/sha256`. Покажите, как малейшее изменение входа радикально меняет хэш (avalanche effect).

1448. **SHA-256 streaming:** Вычислите хэш большого файла (10GB) без загрузки его целиком в память через `io.Copy(hash, file)`.

1449. **HMAC:** Реализуйте аутентифицированное сообщение через `crypto/hmac`. Покажите, как получатель проверяет подлинность сообщения и защиту от tampering.

1450. **HMAC timing attack protection:** Используйте `hmac.Equal()` вместо `bytes.Equal()` для сравнения HMAC. Объясните, почему обычное сравнение уязвимо к timing attacks.

1451. **SHA-3 и BLAKE2b:** Изучите `golang.org/x/crypto/sha3` и `golang.org/x/crypto/blake2b`. BLAKE2b быстрее SHA-256 и используется во многих современных системах.

1452. **SHA-1 и MD5 — никогда не использовать:** Напишите пример использования `crypto/md5` и объясните, почему они криптографически сломаны (collision attacks: 2^18 операций для MD5).

1453. **Constant-time comparison:** Реализуйте собственную функцию constant-time сравнения байтовых слайсов. Покажите, как branching в обычном сравнении раскрывает информацию.

1454. **Deterministic encryption (плохая практика):** Покажите, почему детерминированное шифрование (одинаковый plaintext → одинаковый ciphertext) раскрывает паттерны в данных.

### Тема 144: Симметричное шифрование (AES)
*AES — золотой стандарт симметричного шифрования. Но 90% проблем возникает в режиме использования, а не в самом алгоритме.*

1455. **AES ECB mode — НИКОГДА не использовать:** Зашифруйте известную картинку (Tux the penguin) через AES-ECB и покажите, что паттерн изображения остаётся видимым. Это наглядная демонстрация проблемы.

1456. **AES-CBC базовое использование:** Зашифруйте сообщение через AES-CBC. Покажите, как каждый блок XOR-ится с предыдущим ciphertext для создания зависимости.

1457. **Padding Oracle Attack (теория):** Реализуйте PKCS#7 padding. Покажите, как атакующий, зная только валидность padding'а, может расшифровать любой ciphertext за 128 × 256 запросов.

1458. **Защита от Padding Oracle:** Покажите, как аутентифицированное шифрование (AEAD) решает эту проблему. **Всегда проверяйте MAC/Tag перед decrypt.**

1459. **AES-CTR mode:** Реализуйте stream cipher через AES-CTR. Покажите, как counter должен быть уникальным для каждого сообщения.

1460. **Nonce reuse в CTR mode (катастрофа):** Зашифруйте два разных сообщения одним ключом и одним nonce. Покажите, что XOR ciphertext'ов даёт XOR plaintext'ов (можно восстановить оба сообщения!).

1461. **AES-GCM — современный стандарт:** Зашифруйте сообщение через AES-GCM (`crypto/cipher.NewGCM`). GCM даёт и конфиденциальность, и аутентичность.

1462. **GCM nonce size:** Используйте стандартные 96 бит nonce для GCM. Покажите, как 32-бит nonce в 32-бит счётчик даёт ~2^32 безопасных шифрований под одним ключом.

1463. **GCM additional data (AAD):** Зашифруйте сообщение с AAD (additional authenticated data) — например, заголовки сообщения, которые не шифруются, но аутентифицируются.

1464. **Key derivation из пароля:** Используйте `golang.org/x/crypto/pbkdf2` или HKDF для получения ключа из пароля/мастер-ключа.

1465. **HKDF для derivation множества ключей:** Из одного мастер-ключа получите разные ключи для шифрования и аутентификации через HKDF с разными info-параметрами.

1466. **Key rotation strategy:** Реализуйте схему с master key + data encryption keys (DEK). Данные шифруются DEK, DEK шифруется master key. При ротации меняется только master key.

1467. **Envelope encryption:** Создайте систему, где большие файлы шифруются случайным DEK, а DEK передаётся вместе с файлом в зашифрованном виде (паттерн AWS KMS).

1468. **Шифрование в покое (at rest):** Реализуйте прозрачное шифрование SQLite-файла через `github.com/xeodou/go-sqlcipher`.

1469. **Шифрование полей в БД:** Создайте transparent encryption слой: приложение пишет в plaintext, в БД попадает ciphertext. Используется для GDPR/PCI compliance.

1470. **Поиск по зашифрованным данным:** Реализуйте deterministic encryption для полей, по которым нужен поиск (с пониманием trade-off в безопасности).

1471. **AES-GCM 256-bit key benchmark:** Замерьте скорость AES-256-GCM на вашем железе. На современных CPU с AES-NI это ~3 GB/s.

1472. **ChaCha20-Poly1305:** Используйте `golang.org/x/crypto/chacha20poly1305` как альтернативу AES-GCM. На ARM-процессорах без AES-NI ChaCha20 в 3-4 раза быстрее.

### Тема 145: Асимметричное шифрование (RSA, ECDSA, ECDH)
*Асимметричная криптография решает проблему обмена ключами и цифровых подписей.*

1473. **RSA key generation:** Сгенерируйте пару RSA-ключей 2048 и 4096 бит через `crypto/rsa.GenerateKey`. Замерьте время генерации.

1474. **RSA-OAEP encryption:** Зашифруйте сообщение через RSA-OAEP (никогда не используйте textbook RSA / PKCS#1 v1.5 в 2026!). Покажите, как salt в OAEP даёт недетерминированное шифрование.

1475. **RSA размер ограничений:** Покажите, что RSA-OAEP 2048-бит может зашифровать максимум 190 байт. Поэтому RSA используется для шифрования симметричных ключей (hybrid encryption).

1476. **Hybrid encryption RSA + AES:** Реализуйте паттерн: генерируем AES ключ → шифруем данные через AES-GCM → шифруем AES ключ через RSA-OAEP → передаём оба ciphertext'а.

1477. **RSA-PSS signatures:** Подпишите сообщение через RSA-PSS. PSS доказуемо безопасна в отличие от PKCS#1 v1.5.

1478. **Bleichenbacher attack (теория):** Покажите, почему PKCS#1 v1.5 signatures уязвимы к forgery attacks. Используйте PSS всегда.

1479. **RSA timing attack на decrypt:** Покажите, что RSA decrypt в зависимости от данных занимает разное время (из-за китайской теоремы об остатках). Решение — constant-time RSA (уже есть в Go 1.20+).

1480. **ECDSA базовое использование:** Сгенерируйте пару ключей на кривой P-256 через `crypto/ecdsa`. P-256 в ~10 раз быстрее RSA-2048 для signatures.

1481. **ECDSA nonce disaster:** Покажите, что переиспользование nonce `k` в двух подписях позволяет вычислить приватный ключ. Sony PS3 hack 2011 был именно из-за этого.

1482. **Deterministic ECDSA (RFC 6979):** Используйте deterministic nonce derivation из приватного ключа и сообщения. Устраняет риск плохого RNG.

1483. **Ed25519 signatures:** Используйте `crypto/ed25519` — современные signatures, быстрее ECDSA, без проблем с nonce, constant-time. **Предпочитайте Ed25519 для signatures в новых проектах.**

1484. **Ed25519 vs ECDSA benchmark:** Сравните производительность Ed25519 и ECDSA P-256. Ed25519 должен быть быстрее и по signing, и по verification.

1485. **X25519 key exchange:** Используйте `crypto/ecdh` с кривой X25519 для ECDH key exchange. Получите shared secret между двумя сторонами.

1486. **Noise Protocol Framework:** Реализуйте базовый Noise_XX handshake поверх X25519 + ChaCha20-Poly1305. Это современный стандарт для E2E encryption.

1487. **Certificate-based authentication:** Загрузите X.509 сертификат, извлеките публичный ключ, верифицируйте им подпись.

1488. **Key size comparison:** Постройте таблицу: RSA-2048 ≈ ECDSA-256 ≈ Ed25519-256 по криптостойкости. Покажите, почему 256-bit elliptic curves заменяют 2048-bit RSA.

1489. **Post-quantum cryptography (эксперименты):** Изучите `github.com/cloudflare/circl` для NIST PQC algorithms (Kyber для KEM, Dilithium для signatures).

1490. **Hybrid classical+quantum:** Реализуйте hybrid key exchange: X25519 + Kyber-768. Это защитит от атак типа "harvest now, decrypt later".

### Тема 146: Хэширование паролей
*Пароли — самые уязвимые секреты. Правильное хэширование критично.*

1491. **Почему MD5/SHA для паролей — катастрофа:** Покажите, что на современном GPU можно перебирать ~10^10 MD5-хэшей в секунду. БД с MD5-хэшами 10M пользователей ломается за минуты.

1492. **bcrypt базовое использование:** Захешируйте пароль через `golang.org/x/crypto/bcrypt` с cost 12. Замерьте время (~250ms на пароль на современном CPU).

1493. **bcrypt cost tuning:** Определите оптимальный cost для вашего сервера: должен занимать ~250ms на хэш. Это даёт 4 пароля/сек на ядро — атакующему очень больно.

1494. **bcrypt salt встроен:** Покажите, что bcrypt автоматически генерирует salt и хранит его вместе с хэшем в формате `$2a$12$...`. Нет отдельного поля в БД.

1495. **bcrypt length limit:** Покажите, что bcrypt обрезает пароли до 72 байт. Длинный passphrase теряет энтропию! Используйте pre-hashing через SHA-256 для длинных паролей.

1496. **scrypt:** Используйте `golang.org/x/crypto/scrypt` с параметрами N=32768, r=8, p=1. scrypt memory-hard — атаки через ASIC становятся очень дорогими.

1497. **Argon2id — современный стандарт:** Захешируйте пароль через `golang.org/x/crypto/argon2`. Используйте Argon2id (winner Password Hashing Competition 2015).

1498. **Argon2 параметры tuning:**
    * memory: 64 MB minimum (для 1 потока)
    * iterations: 3-5
    * parallelism: число ядер
    * salt: 16 байт
    * key length: 32 байт

1499. **Argon2 benchmark под вашу нагрузку:** Определите параметры Argon2 так, чтобы хэширование занимало 300-500ms на ваш типичный сервер.

1500. **Argon2 в БД:** Храните хэш в формате `$argon2id$v=19$m=65536,t=3,p=4$salt$hash`. Это standard encoding.

1501. **Password pepper:** Добавьте server-wide secret (pepper) к паролю перед хэшированием. Pepper не в БД — утечка БД не даёт атакующему ничего без pepper.

1502. **Password migration strategy:** Реализуйте transparent rehashing: при успешном логине, если хэш в слабом формате (MD5/sha256/bcrypt cost<10), пересоздайте его в Argon2id.

1503. **Password validation policy:** Реализуйте валидатор: минимум 12 символов, проверка в HaveIBeenPwned database через k-anonymity API (без отправки пароля!).

1504. **Bcrypt timing attack protection:** Используйте постоянную стоимость сравнения. Покажите, как разница во времени успешного/неуспешного логина может раскрыть информацию.

### Тема 147: JWT, PASETO и современные токены
*JWT имеет серьёзные проблемы дизайна. PASETO их решает.*

1505. **JWT базовое использование:** Создайте и верифицируйте JWT через `github.com/golang-jwt/jwt/v5`. Разберите 3 части: header.payload.signature.

1506. **JWT алгоритмы и атаки:** Покажите 3 критических атаки:
    * `alg: none` bypass
    * Algorithm confusion (RS256 → HS256)
    * JKU/X5U header injection

1507. **JWT всегда verificate алгоритм:** Настройте `jwt.WithValidMethods([]string{"RS256"})`. Без этого ваш код уязвим к algorithm confusion.

1508. **JWT не для sessions:** Покажите, почему JWT плохи как сессионные токены (нельзя отозвать без state, большие по размеру, leak в логах).

1509. **JWT short-lived access + refresh:** Реализуйте пару: access token (15 мин) + refresh token (30 дней в БД с revocation). Это standard modern pattern.

1510. **Refresh token rotation:** При использовании refresh token выдавайте новый refresh и инвалидируйте старый. Детектируйте повторное использование (признак theft).

1511. **JWT в URL/Cookie — опасность:** Покажите, как JWT в URL попадает в логи nginx/прокси, в Referer header. Используйте HttpOnly Cookie для веб-приложений.

1512. **PASETO introduction:** Установите `aidanwoods.dev/go-paseto`. PASETO = Platform-Agnostic Security Tokens, создан чтобы решить все проблемы JWT.

1513. **PASETO v4.public:** Используйте Ed25519 для public tokens (аналог JWT с асимметричной подписью). Нет проблем с algorithm confusion.

1514. **PASETO v4.local:** Используйте XChaCha20-Poly1305 + BLAKE2b для encrypted tokens (конфиденциальность + аутентичность). У JWT нет standard encrypted mode.

1515. **PASETO implicit assertions:** Добавьте в токен данные, которые аутентифицируются, но не включаются в payload (например, IP-адрес, user agent).

1516. **PASETO footer:** Используйте footer для public данных (key ID), которые аутентифицируются, но не шифруются.

1517. **Macaroons (Bearer tokens с caveats):** Реализуйте macaroon через `gopkg.in/macaroon.v2`. Caveats позволяют создавать tokens с ограничениями (read-only, IP-bound, time-limited).

1518. **Third-party caveats:** Создайте macaroon с third-party caveat (должен быть discharge от другого сервиса). Это分布式 authorization без central database.

1519. **Biscuit tokens:** Изучите `github.com/biscuit-auth/biscuit-go`. Biscuit — современный формат с Datalog-based policies и оффлайн-верификацией.

1520. **Session tokens в Redis (simple и надёжно):** Для веб-приложений используйте 32-байтовый случайный token + Redis для state. Проще, безопаснее, revocable в любой момент.

### Тема 148: OAuth2 и OIDC
*Стандарт для third-party authorization и аутентификации.*

1521. **OAuth2 Authorization Code Flow:** Реализуйте полный flow: redirect на провайдера → получение code → обмен на access/refresh token → использование access token.

1522. **PKCE (Proof Key for Code Exchange):** Добавьте PKCE в ваш OAuth2 flow (обязателен для SPA и mobile приложений, рекомендуется для всех). Используйте S256 метод.

1523. **OAuth2 state parameter:** Всегда используйте криптографически случайный `state` параметр для защиты от CSRF. Без state ваш OAuth flow уязвим.

1524. **OAuth2 client credentials flow:** Реализуйте machine-to-machine аутентификацию для backend-сервисов.

1525. **OAuth2 Device Authorization Grant:** Реализуйте flow для CLI/SmartTV устройств, где пользователь вводит код на другом устройстве.

1526. **Refresh token rotation в OAuth2:** Автоматически обновляйте access tokens и обрабатывайте refresh token revocation.

1527. **OIDC discovery:** Используйте `.well-known/openid-configuration` для получения endpoints и public keys провайдера. Не хардкодьте endpoints.

1528. **OIDC ID Token validation:** Верифицируйте ID Token по всем правилам: issuer, audience, expiration, nonce, signature через JWKS.

1529. **JWKS (JSON Web Key Set):** Получайте public keys провайдера через JWKS endpoint. Кэшируйте их, обновляйте по расписанию и по kid miss.

1530. **Go OAuth2 client библиотека:** Используйте `golang.org/x/oauth2` для standard flow и `github.com/coreos/go-oidc/v3` для OIDC.

1531. **OAuth2 Authorization Server:** Реализуйте собственный OAuth2 сервер через `github.com/go-oauth2/oauth2/v4`. Поймите internals.

1532. **Scopes и audience:** Корректно используйте `scope` (права доступа) и `audience` (для какого сервиса токен). audience особенно важен в микросервисах.

1533. **Token introspection endpoint:** Реализуйте валидацию opaque access tokens через introspection endpoint (RFC 7662).

1534. **Token revocation endpoint:** Реализуйте revocation endpoint (RFC 7009) для immediate invalidation tokens.

1535. **Social login integration:** Интегрируйте Google, GitHub, Apple login в ваше приложение. Покажите особенности каждого провайдера.

### Тема 149: TLS/SSL и сертификаты
*Защита данных в transit.*

1536. **TLS версии и cipher suites:** Настройте `tls.Config` с минимумом TLS 1.2, предпочитаемо TLS 1.3. Уберите слабые cipher suites.

1537. **Certificate pinning:** Реализуйте certificate pinning в вашем HTTP-клиенте для защиты от MitM атак через поддельные CA.

1538. **Self-signed certificate generation:** Напишите код для генерации self-signed сертификатов с SAN (Subject Alternative Names) через `crypto/x509`.

1539. **CSR generation и подписание:** Сгенерируйте Certificate Signing Request и подпишите его через ваш собственный CA.

1540. **OCSP Stapling:** Настройте OCSP Stapling в вашем TLS сервере для быстрой валидации сертификатов.

1541. **Certificate transparency (CT):** Изучите CT логи. Все современные сертификаты должны быть в CT логах.

1542. **mTLS (Mutual TLS):** Настройте mTLS для service-to-service аутентификации. Оба конца предъявляют сертификаты. Используется в Zero Trust architecture.

1543. **ACME client:** Напишите простой ACME client (как cert-manager) для получения Let's Encrypt сертификатов автоматически.

1544. **TLS session tickets:** Настройте session resumption для снижения handshake latency.

1545. **SNI (Server Name Indication):** Настройте ваш TLS-сервер для хостинга нескольких HTTPS сайтов на одном IP через SNI.

1546. **HSTS (HTTP Strict Transport Security):** Установите `Strict-Transport-Security` header для форсированного HTTPS.

### Тема 150: Web Security и OWASP Top 10
*Практическая защита от основных веб-уязвимостей.*

1547. **SQL Injection через Go:** Покажите, что Go `database/sql` с placeholders защищён от SQLi по дизайну. Но конкатенация строк всё ещё опасна.

1548. **XSS (Cross-Site Scripting):** Напишите код с XSS-уязвимостью в template и исправьте её через `html/template` (автоматический escape) и CSP header.

1549. **CSRF (Cross-Site Request Forgery):** Реализуйте CSRF protection через double submit cookie + custom header. Покажите, почему SameSite=Strict/Lax в cookies тоже помогает.

1550. **CSRF tokens в forms:** Реализуйте stateful CSRF tokens в forms через hidden input и валидацию на сервере.

1551. **CSP (Content Security Policy):** Настройте strict CSP header: `default-src 'self'; script-src 'self'`. Защитите от XSS даже при успешной инъекции.

1552. **CORS (Cross-Origin Resource Sharing):** Настройте CORS корректно: конкретные origins (не `*`), credentials только когда нужно, без отражения Origin в Access-Control-Allow-Origin.

1553. **CORS preflight attacks:** Покажите, как атакующий может использовать CORS misconfiguration для data exfiltration.

1554. **SSRF (Server-Side Request Forgery) базовый кейс:** Напишите код, который принимает URL от пользователя и делает HTTP-запрос. Покажите, как атакующий обращается к `http://169.254.169.254/` (AWS metadata service) для получения credentials.

1555. **SSRF через IP decimal/hex:** Покажите, что `http://2852039166/` = `http://169.254.169.254/`. Наивный валидатор по IP-строке пропускает это.

1556. **SSRF через DNS rebinding:** Покажите, что валидация IP в момент получения URL не защищает: атакующий возвращает public IP первым DNS-запросом и 127.0.0.1 вторым.

1557. **SSRF mitigation в Go:** Реализуйте защиту:
    * Разрешённые schemes только `https://`
    * Whitelist доменов
    * Запрет private IP ranges (RFC 1918, 169.254.169.254)
    * Custom HTTP-клиент с DialContext, который валидирует IP **перед соединением**

1558. **Body size limiting:** Настройте `http.MaxBytesReader` для ограничения размера request body. Без этого ваш сервер уязвим к DoS через большие payload'ы.

1559. **Multipart form size limit:** Настройте `http.Request.ParseMultipartForm(maxMemory)` и ограничьте размер загружаемых файлов.

1560. **JSON decoder size limiting:** Используйте `json.Decoder.DisallowUnknownFields()` и ограничивайте глубину вложенности JSON (защита от zip bombs в JSON).

1561. **Path Traversal:** Покажите, как атакующий через `../../../etc/passwd` в параметре может читать произвольные файлы. Защититесь через `filepath.Clean` и валидацию пути в рамках базовой директории.

1562. **Open Redirect:** Покажите, как параметр `?redirect=evil.com` в login flow используется для phishing. Валидируйте redirect URLs по whitelist.

1563. **Clickjacking:** Установите `X-Frame-Options: DENY` и CSP `frame-ancestors` header.

1564. **MIME sniffing:** Установите `X-Content-Type-Options: nosniff` для защиты от MIME-based атак.

1565. **Security headers bundle:** Напишите middleware, которая добавляет все современные security headers в каждый response: HSTS, CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy.

### Тема 151: Secret Management
*Как безопасно хранить и использовать секреты.*

1566. **Никогда не хранить секреты в коде/ENV в plain:** Покажите, как секреты утекают в Git, логи, error messages. Используйте Secret Managers.

1567. **HashiCorp Vault integration:** Настройте Vault в Docker, получите секреты из Go-приложения через AppRole аутентификацию.

1568. **Dynamic secrets в Vault:** Настройте Vault для выдачи short-lived PostgreSQL credentials. Каждое приложение получает уникальный логин/пароль с TTL.

1569. **AWS Secrets Manager:** Интегрируйтесь с AWS Secrets Manager. Используйте IAM roles вместо access keys.

1570. **Финальный босс (Production Security Hardening):**
    Создайте микросервис аутентификации с full-stack security:
    
    **Password Storage:**
    * Argon2id хэширование с tuning под вашу нагрузку
    * Transparent password rehashing при успешном логине
    * Pre-hash длинных паролей через SHA-256
    * Pepper из Secret Manager
    * HaveIBeenPwned проверка через k-anonymity
    
    **Session Management:**
    * 32-byte случайные session tokens
    * Хранение в Redis с TTL 30 дней
    * Session rotation при privilege elevation
    * Concurrent sessions limiting
    
    **API Tokens:**
    * PASETO v4.local для user-bound tokens
    * API keys в формате `prefix_random_checksum`
    * Rate limiting per token через Redis
    * Scope-based permissions в токенах
    
    **OAuth2 Server:**
    * Authorization Code + PKCE flow
    * Short-lived access tokens (PASETO v4.public)
    * Refresh tokens в БД с rotation и revocation detection
    * JWKS endpoint с key rotation
    
    **Cryptographic Features:**
    * E2E encrypted user messages (X25519 + ChaCha20-Poly1305)
    * Hybrid RSA-OAEP + AES-GCM для file sharing
    * Ed25519 signatures для audit log integrity
    
    **Security Headers и Protections:**
    * Все OWASP security headers через middleware
    * CORS strict configuration
    * CSRF double-submit tokens
    * Body size limiting на всех endpoints
    * SSRF protection в URL preview feature
    
    **Secrets и Keys:**
    * Все секреты в Vault с automatic rotation
    * mTLS для service-to-service communication
    * Certificate pinning в clients
    
    **Monitoring:**
    * Failed login attempts alerting
    * Unusual location/device login alerts
    * Token usage anomalies detection
    * HSM-based master keys backup

### 💡 Золотые правила криптографии и AppSec:

1. **Никогда не изобретайте криптографию.** Используйте standard libraries и battle-tested algorithms: AES-GCM, ChaCha20-Poly1305, Ed25519, X25519, Argon2id.

2. **crypto/rand всегда, math/rand никогда.** Для любых security-задач (токены, ключи, salt, nonce) используйте только `crypto/rand`.

3. **AEAD (Authenticated Encryption) всегда.** Используйте AES-GCM или ChaCha20-Poly1305, никогда CBC в 2026 году. Без аутентификации ваш шифртекст уязвим к tampering.

4. **Nonces должны быть уникальными.** Повторное использование nonce в GCM/CTR/ECDSA полностью ломает криптосистему. Используйте counter-based nonce derivation.

5. **Пароли → Argon2id, никогда MD5/SHA/bcrypt в 2026.** Настройте параметры так, чтобы хэширование занимало ~500ms на ваш типичный сервер.

6. **JWT — это подписанные assertions, не sessions.** JWT нельзя отозвать. Для sessions используйте 32-byte tokens в БД/Redis. JWT хороши для short-lived access tokens между сервисами.

7. **PASETO > JWT для новых проектов.** Нет algorithm confusion, standard encryption mode, нет legacy проблем.

8. **SSRF — тихий убийца.** Любой код, который делает HTTP-запрос к user-supplied URL — это SSRF кандидат. Валидируйте IP в DialContext, запрещайте private ranges.

9. **Limit everything:** body size, upload size, JSON depth, request rate, concurrent connections. Без лимитов ваш API — подарок для DoS-атакующих.

10. **Security headers — 5 минут работы, годы защиты.** Настройте их в одном middleware: HSTS, CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, Permissions-Policy.

11. **Secrets не в коде, не в ENV в plain.** Используйте HashiCorp Vault, AWS Secrets Manager, Azure Key Vault. Автоматическая ротация — must have.

12. **mTLS для service-to-service.** В Zero Trust архитектуре каждый сервис аутентифицирует другие через сертификаты. Istio/Linkerd делают это автоматически.

13. **Timing attacks реальны.** Используйте constant-time comparison (`hmac.Equal`, `subtle.ConstantTimeCompare`). Разница во времени успешной/неуспешной аутентификации раскрывает информацию.

14. **Атакуйте свой код.** Перед деплоем подумайте как атакующий:
    * Могу ли я обойти аутентификацию?
    * Могу ли я получить данные другого пользователя?
    * Могу ли я выполнить код/запросы к внутренним ресурсам?
    * Могу ли я перегрузить систему?

15. **Bug bounties и security audit.** Для серьёзных приложений инвестируйте в внешний security audit. Свежий взгляд находит то, что разработчики пропускают.
