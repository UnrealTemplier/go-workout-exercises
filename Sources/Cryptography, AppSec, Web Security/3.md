Безопасность — это не просто "еще одна фича", это фундамент production-ready приложений. В Go стандартная библиотека `crypto` написана настолько хорошо, что позволяет реализовать криптографику уровня энтерпрайза без сторонних пакетов (за исключением хэширования паролей). 

Здесь **35 упражнений** (с 781 по 815), которые научат тебя шифровать данные, защищать токены, предотвращать SSRF и устранять уязвимости, за которые увольняют с работы.

### Блок 86: Хэширование паролей и защита от брутфорса
*Цель: Правильно хранить пароли пользователей, защищая API от тайминг-атак.*

781. **[MD5/SHA256 — Почему так нельзя]** Напиши функцию хэширования пароля через `sha256.Sum256`. Объясни, почему хранение паролей в виде обычного SHA-хэша смертельно опасно (уязвимость к радужным таблицам и быстрому перебору на GPU).
782. **[Salt]** Добавь к паролю случайную "соль" (сгенерируй через `crypto/rand`). Объясни, как соль защищает от радужных таблиц.
783. **[bcrypt]** Установи `golang.org/x/crypto/bcrypt`. Напиши функцию `HashPassword(password string) (string, error)` (используй `bcrypt.GenerateFromPassword` с cost=12).
784. Напиши функцию `CheckPassword(hashedPassword, password string) error` (`bcrypt.CompareHashAndPassword`). Убедись, что bcrypt автоматически извлекает соль из хэша.
785. **[Argon2id]** Установи `golang.org/x/crypto/argon2`. Напиши функцию хэширования через `argon2.IDKey`. Argon2 является победителем конкурса Password Hashing Competition и устойчив к атакам на GPU/ASIC за счет настройки потребления памяти.
786. **[Peppering]** Реализуй паттерн "Pepper" (перец): перед хэшированием в bcrypt конкатенируй пароль с секретной строкой из переменной окружения (`PEPPER_SECRET`). Объясни, чем pepper отличается от salt (соль уникальна для юзера и хранится в БД, перец один для всех и хранится в коде/KMS).
787. **[Каверзный кейс — Тайминг-атаки]** Напиши функцию, которая сравнивает два токена через `==`. Запусти бенчмарк, который показывает, что сравнение строк разной длины занимает разное время. Используй `crypto/subtle.ConstantTimeCompare` для безопасного сравнения секретов.

### Блок 87: Симметричное шифрование (AES)
*Цель: Шифровать конфиденциальные данные (например, API-ключи клиентов в БД).*

788. Сгенерируй 256-битный ключ для AES с помощью `crypto/rand.Read(make([]byte, 32))`.
789. **[AES-GCM]** Используй `crypto/aes` и `crypto/cipher`. Создай GCM (Galois/Counter Mode). Зашифруй строку. Объясни, почему GCM лучше CBC (аутентификация + шифрование, защита от padding oracle).
790. Расшифруй данные из предыдущего задания. Убедись, что при изменении одного байта в шифртексте `gcm.Open` возвращает ошибку (нарушена целостность MAC).
791. **[Nonce Management]** В AES-GCM nonce (IV) никогда не должен повторяться для одного ключа. Реализуй генерацию случайного nonce для каждого шифрования. Конкатенируй `nonce + ciphertext` перед сохранением в БД, а при расшифровке отрезай первые 12 байт.
792. **[Каверзный кейс — Reuse of Nonce]** Зашифруй два разных сообщения одним ключом и *одним nonce*. Реализуй XOR двух шифртекстов. Покажи, что результат равен XOR открытых текстов (катастрофическое нарушение конфиденциальности).
793. **[Шифрование больших файлов]** Используй потоковый шифр `crypto/cipher.NewGCM` или ChaCha20-Poly1305 для поблочного шифрования файла (читай по 64KB, обновляй nonce-счетчик, не загружая весь файл в память).

### Блок 88: Асимметричное шифрование и ЭЦП (RSA)
*Цель: Обеспечить безопасный обмен ключами и цифровую подпись.*

794. Сгенерируй пару RSA-ключей (2048 или 4096 бит) с помощью `rsa.GenerateKey(rand.Reader, 2048)`.
795. **[Шифрование]** Зашифруй короткое сообщение публичным ключом получателя (`rsa.EncryptOAEP` с SHA-256).
796. Расшифруй сообщение приватным ключом.
797. **[Digital Signature]** Подпиши хэш документа приватным ключом отправителя (`rsa.SignPSS`).
798. Проверь подпись публичным ключом (`rsa.VerifyPSS`).
799. **[Каверзный кейс — RSA Size Limit]** Попробуй зашифровать сообщение длиннее 190 байт напрямую через RSA. Поймай ошибку `message too long`. Изучи гибридную криптографию: как RSA используется только для шифрования сессионного ключа AES, а данные шифруются симметрично.
800. **[ECDSA]** Сгенерируй ключи для эллиптической кривой (`crypto/ecdsa`). Подпиши данные и проверь подпись. Объясни, почему ECDSA предпочтительнее RSA в современных системах (меньший размер ключа при той же криптостойкости).
801. **[X.509 Парсинг]** Считай `.pem` файл TLS-сертификата. Декодируй его из PEM в DER, затем распарси через `x509.ParseCertificate`. Выведи `Issuer`, `Subject` и срок действия (`NotAfter`).

### Блок 89: Токены аутентификации (PASETO, OAuth2, OIDC)
*Цель: Заменить уязвимый JWT на современные стандарты.*

802. **[JWT — База]** Используй `github.com/golang-jwt/jwt/v5`. Создай HS256 токен с claims (`user_id`, `exp`). Подпиши его секретом.
803. **[Каверзный кейс — alg=none]** Напиши мок-атаку на JWT: вручную создай токен с заголовком `{"alg":"none"}` и пустой подписью. Убедись, что строгий валидатор (`jwt.Parse` с проверкой метода) отклоняет его.
804. **[PASETO — Замена JWT]** Установи `github.com/o1egl/paseto`. Создай токен V4 (на базе Ed25519, публичная криптография). Подпиши приватным ключом.
805. Проверь PASETO токен публичным ключом. Извлеки claims. Объясни, почему PASETO безопаснее JWT (нет гибкости в выборе алгоритма, устраняет уязвимости с `alg`).
806. **[OAuth2 Client]** Используй `golang.org/x/oauth2`. Настрой конфиг для провайдера (например, GitHub или Google). Реализуй HTTP-обработчик `/login`, который редиректит пользователя на страницу авторизации.
807. Реализуй обработчик `/callback`, который принимает `code`, обменивает его на `AccessToken` (`Exchange`) и делает API-запрос к провайдеру для получения email пользователя.
808. **[OIDC (OpenID Connect)]** Используй `github.com/coreos/go-oidc`. Настрой провайдера. Скачай JWKS (JSON Web Key Set) по URL `/.well-known/openid-configuration`. Верифицируй ID Token, полученный от провайдера, используя удаленные публичные ключи.

### Блок 90: Web Security и защита API (AppSec)
*Цель: Закрыть бреши, через которые происходит 90% взломов веб-приложений.*

809. **[Ограничение размера тела]** Напиши middleware, которое ограничивает размер тела запроса до 1MB. Используй `http.MaxBytesReader(w, r.Body, 1<<20)`. Отправь 5MB JSON, убедись, что сервер обрывает соединение с ошибкой `413 Request Entity Too Large`.
810. **[SSRF Prevention]** Напиши HTTP-клиент, который принимает URL от пользователя. Распарси URL, резолви его в IP-адрес (`net.LookupIP`). Проверь, что IP не является приватным (`net.IP.IsPrivate()`, `IsLoopback()`, `IsLinkLocalUnicast()` — защита от доступа к 169.254.169.254 AWS Metadata и локальным сервисам).
811. **[Каверзный кейс — DNS Rebinding]** В предыдущем задании после проверки IP злоумышленник может сменить DNS-запись. Используй кастомный `net.Dialer` с `Control` функцией, которая проверяет IP-адрес прямо в момент установления TCP-соединения (на уровне сокета), блокируя приватные сети.
812. **[SQL Injection]** Напиши уязвимый запрос (`fmt.Sprintf("SELECT * FROM users WHERE name = '%s'", name)`). Покажи инъекцию (`' OR '1'='1`). Исправь с использованием `database/sql` плейсхолдеров (`$1`).
813. **[XSS (Cross-Site Scripting)]** Напиши обработчик, который выводит введенный пользователем текст в HTML. Используй `text/template` (уязвимо) и покажи внедрение `<script>alert(1)</script>`. Перепиши на `html/template`, который автоматически экранирует HTML-сущности.
814. **[CORS]** Настрой middleware для Cross-Origin Resource Sharing. Разреши запросы только с домена `https://myapp.com`. Убедись, что запросы с `https://evil.com` блокируются браузером.
815. **[Secure Cookies & HSTS]** Настрой выдачу cookie с флагами `HttpOnly`, `Secure`, `SameSite=Strict`. Добавьте middleware, которое устанавливает заголовок `Strict-Transport-Security: max-age=31536000; includeSubDomains` для принудительного использования HTTPS.
816. **[CSRF Protection]** Реализуй паттерн Double Submit Cookie: при GET запросе выдавай CSRF-токен в куки и в мета-тег. При POST запросе middleware должно сравнивать токен из куки и из заголовка `X-CSRF-Token`.
817. **[Финальное испытание — Secure File Vault API]**
    Создай HTTP API для хранения секретных заметок.
    - **Аутентификация:** PASETO V4 токены.
    - **Хэширование паролей:** Argon2id с солью.
    - **Шифрование данных:** Текст заметки шифруется симметричным AES-GCM. Ключ заметки генерируется случайно и шифруется публичным ключом пользователя (RSA-OAEP) перед сохранением в БД (гибридное шифрование).
    - **AppSec:** Защита от SSRF (если заметка содержит URL для парсинга), лимит размера тела (1MB), Strict CORS, HSTS.
    - **Тайминги:** Использование `subtle.ConstantTimeCompare` при проверке токенов доступа к конкретной заметке.
