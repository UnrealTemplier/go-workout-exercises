Безопасность (AppSec) — это область, где одна строчка неправильного кода может стоить компании миллионов долларов и репутации. Go имеет потрясающую стандартную библиотеку `crypto`, но криптография не прощает ошибок (например, повторного использования nonce или сравнения строк обычным `==`).

Продолжаем наш марафон. Впереди **35 критически важных упражнений** (с 706 по 740), которые сделают из тебя инженера, умеющего защищать данные, токены и API от современных векторов атак.

### Блок 67. Хэширование, Пароли и Криптографический Рандом (706–713)
Никогда не используй `math/rand` для секретов. Учимся работать с энтропией и безопасно хранить пароли (OWASP стандартам).

706. **Истинный рандом (`crypto/rand`):** Напиши функцию генерации безопасного токена (например, для сброса пароля). Создай срез `make([]byte, 32)` и заполни его через `rand.Read()`. Закодируй результат в строку через `base64.URLEncoding`.
707. **Хэширование (SHA-256):** Хэшируй строку "my_password" с помощью `crypto/sha256`. Выведи результат в hex-формате. *Осознай, почему это КАТЕГОРИЧЕСКИ нельзя использовать для хранения паролей* (современная видеокарта переберет миллиарды SHA-256 хэшей за секунду).
708. **Стандарт индустрии (`bcrypt`):** Установи `golang.org/x/crypto/bcrypt`. Хэшируй пароль с помощью `GenerateFromPassword`. Посмотри на полученную строку (она содержит соль и стоимость). Проверь пароль через `CompareHashAndPassword`.
709. **Cost (Стоимость bcrypt):** Запусти бенчмарк для `bcrypt` с `cost = 10` и `cost = 14`. Убедись, что увеличение стоимости делает хэширование экспоненциально медленнее (что защищает от брутфорса), но сильно грузит CPU сервера.
710. **Современный стандарт (Argon2):** На сегодня OWASP рекомендует алгоритм Argon2id (он защищен от атак на видеокартах/ASIC за счет требования памяти). Используй `golang.org/x/crypto/argon2`. Напиши функцию хэширования, задав параметры: время (time), память (memory) и потоки (threads).
711. **Тайминг-атаки (`crypto/subtle`):** Тебе прислали API-ключ. Если ты проверишь его как `if input == secretKey`, злоумышленник сможет попиксельно угадать ключ, замеряя наносекунды ответа сервера (сравнение `==` прерывается на первом несовпадающем символе). Замени `==` на `subtle.ConstantTimeCompare()`, которое всегда выполняется за одинаковое время.
712. **HMAC (Аутентификация сообщений):** Тебе нужно передать данные клиенту и убедиться, что он их не подделал. Используй `crypto/hmac` с SHA-256 и секретным ключом сервера, чтобы сгенерировать подпись для строки. Напиши функцию валидации этой подписи.
713. **Деривация ключей (HKDF):** У пользователя есть пароль, но для AES-шифрования тебе нужен ключ ровно в 32 байта. Используй `golang.org/x/crypto/hkdf`, чтобы безопасно "растянуть" пароль пользователя (с добавлением соли) до 32-байтного криптографического ключа.

### Блок 68. Симметричное и Асимметричное шифрование (714–722)
Шифруем данные для хранения на диске и передачи по сети.

714. **Уязвимость ECB (Теория в коде):** Используй `crypto/aes` для шифрования строки. Напиши (или найди) реализацию режима ECB. Зашифруй картинку (или блок повторяющихся данных). Изучи проблему "Пингвина ECB" — почему этот режим оставляет видимыми паттерны данных.
715. **AES-GCM (Золотой стандарт):** Никогда не используй просто AES. Используй AES-GCM (Galois/Counter Mode), который не только шифрует, но и гарантирует целостность (Authenticated Encryption). Зашифруй текст с помощью `cipher.NewGCM`.
716. **Смертный грех — Nonce Reuse:** Для работы GCM нужен `nonce` (уникальный вектор инициализации). Зашифруй два разных сообщения одним ключом и **одинаковым** `nonce`. Прочитай в документации, почему это полностью компрометирует ключ шифрования. Всегда генерируй `nonce` через `crypto/rand`!
717. **Асимметричная криптография (RSA):** Сгенерируй пару ключей (Private и Public) длиной 2048 бит через `rsa.GenerateKey`. Сохрани их на диск в формате PEM, используя пакет `encoding/pem` и `x509`.
718. **Шифрование RSA (OAEP):** Напиши код, который читает публичный ключ из файла и шифрует короткое сообщение (например, симметричный ключ) с помощью `rsa.EncryptOAEP`. Расшифруй его приватным ключом.
719. **Цифровые подписи (RSA-PSS):** Асимметричные ключи используются не только для шифрования, но и для подписей. Возьми хэш документа, подпиши его приватным ключом через `rsa.SignPSS`. Напиши функцию, которая проверяет подпись публичным ключом.
720. **Эллиптические кривые (ECDSA):** RSA — медленный и ключи у него огромные. Сгенерируй ключ с помощью `crypto/ecdsa` (кривая P-256). Подпиши сообщение. Обрати внимание, насколько подпись и ключ меньше по размеру по сравнению с RSA.
721. **Ed25519 (Современные подписи):** Используй пакет `crypto/ed25519`. Это современный, сверхбыстрый и безопасный стандарт цифровых подписей (используется в блокчейнах и современных TLS). Реализуй генерацию, подпись и верификацию. Убедись, что API этого пакета намного проще, чем у ECDSA.
722. **Гибридное шифрование (Конверт):** Тебе нужно зашифровать видеофайл (1 ГБ) для другого пользователя. RSA не умеет шифровать большие данные. Напиши алгоритм: 1) Генерируешь случайный ключ AES-256; 2) Шифруешь видео через AES-GCM; 3) Шифруешь сам ключ AES с помощью RSA публичного ключа пользователя.

### Блок 69. Токены, Авторизация и PASETO (723–731)
JWT устаревает из-за встроенных уязвимостей дизайна. Учимся работать с современными альтернативами и OAuth2.

723. **Анатомия JWT:** Без библиотек! Возьми строку `{"alg":"HS256"}` (заголовок) и `{"user_id":42}` (нагрузка). Закодируй обе части в Base64Url. Соедини через точку. Сгенерируй HMAC-SHA256 подпись от этой строки. Добавь подпись третьей частью. Ты только что руками создал валидный JWT.
724. **Уязвимость JWT "alg: none":** JWT позволяет клиенту самому указывать алгоритм подписи. Возьми библиотеку JWT. Создай токен, где в заголовке указано `"alg": "none"`, и удали подпись. Напиши "наивный" валидатор, который доверяет алгоритму из заголовка, и убедись, что он пропустит этот фейковый токен. (Всегда жестко задавай алгоритм при валидации JWT!).
725. **Знакомство с PASETO (Local):** Установи библиотеку (например, `aidarkhanov/nanoid` или `aead/paseto`). PASETO (Platform-Agnostic Security Tokens) лишен проблем JWT — версия протокола и алгоритм жестко зафиксированы. Сгенерируй `v4.local` токен (симметричное шифрование). Обрати внимание, что данные внутри зашифрованы (в отличие от JWT, который просто закодирован в Base64).
726. **PASETO (Public):** Сгенерируй `v4.public` токен, используя Ed25519 ключи (из упр. 721). Это асимметричный токен: сервер подписывает его приватным ключом, а любые микросервисы могут проверить его валидность, имея только публичный ключ.
727. **OAuth2 Flow (Клиент):** Используй пакет `golang.org/x/oauth2`. Зарегистрируй OAuth приложение в GitHub. Сгенерируй `AuthCodeURL`, перенаправь туда пользователя, получи `code` в callback-роуте и обменяй его на Access Token.
728. **Защита OAuth2 (State Parameter):** При генерации `AuthCodeURL` передай криптографически случайную строку в параметр `state`. Сохрани её в HttpOnly куку. В callback-роуте проверь, что `state` от провайдера (GitHub) совпадает с твоей кукой. Это защитит от CSRF-атак на логин.
729. **OpenID Connect (OIDC):** OAuth2 дает только токен для API. OIDC дает стандартизированный профиль юзера. Используй `github.com/coreos/go-oidc`. Настрой провайдера (например, Google), получи ID Token, валидируй его подписи (через публичные ключи Google) и распарси Email и Имя юзера.
730. **Безопасные Session Cookies:** Если ты не используешь токены (у тебя монолит и браузер). Напиши хендлер, который ставит сессионную куку. Установи флаги: `HttpOnly: true` (недоступно из JS/XSS), `Secure: true` (только HTTPS) и `SameSite: http.SameSiteStrictMode` (защита от CSRF).
731. **Refresh Токены (Лучшие практики):** Архитектурная задача. Access Token (PASETO) живет 15 минут. Refresh Token — это просто случайная строка на 64 символа (crypto/rand). Храни в БД не сам Refresh Token, а его *хэш* (например, SHA-256 или bcrypt). При получении Refresh Token от клиента, хэшируй его и ищи в БД. Если БД украдут — хакеры не смогут сгенерировать новые Access токены!

### Блок 70. Защита API от специфических уязвимостей (732–740)
Эти 9 упражнений защитят твой сервер от падений (DoS) и утечек данных, которые не ловит линтер.

732. **Защита от OOM (Billion Laughs / Large Body):** Ты принимаешь JSON от пользователя. Если хакер пришлет 10 ГБ файл, `io.ReadAll(r.Body)` вызовет Out Of Memory и сервер упадет. Оберни чтение в `http.MaxBytesReader(w, r.Body, 1024*1024)` (лимит 1 МБ). Убедись, что при превышении лимита запрос прерывается.
733. **Защита от Mass Assignment:** Ты парсишь JSON `{"name":"Ivan", "is_admin":true}` в структуру `User`. Если в структуре есть поле `IsAdmin` с тегами json, хакер получит права админа!
    *Решение:* Изолируй DTO (см. упр. 556). А также при парсинге используй `decoder := json.NewDecoder(r.Body); decoder.DisallowUnknownFields()`. Теперь, если хакер пришлет лишнее поле, парсер вернет ошибку.
734. **Уязвимость SSRF (Server-Side Request Forgery):** Напиши эндпоинт `/fetch?url=...`, который скачивает картинку по URL и отдает клиенту. Вызови его с `url=http://localhost:8080/admin_metrics` (или `http://169.254.169.254` для AWS). Убедись, что твой сервер услужливо скачал внутренние секретные данные и отдал их хакеру.
735. **Защита от SSRF (Custom Transport):** Реши проблему из 734. Напиши кастомную функцию `DialContext` для `http.Transport` твоего `http.Client`. Внутри функции резолвь IP-адрес домена и проверяй, не принадлежит ли он приватным/локальным подсетям (используй методы `net.IP.IsPrivate()` и `IsLoopback()`). Блокируй запрос, если IP внутренний!
736. **Защита от CSRF (Межсайтовая подделка запроса):** У тебя форма перевода денег. Если хакер разместит на своем сайте скрытую форму на твой `/transfer`, браузер жертвы автоматически прикрепит куки. Установи пакет `github.com/gorilla/csrf`. Настрой Middleware, сгенерируй токен в GET-запросе и проверяй его в POST-запросе.
737. **XSS и Content-Type Sniffing:** Ты отдаешь загруженный пользователем `.txt` файл. Если там внутри HTML-теги с `<script>`, старые браузеры могут "догадаться" что это HTML и выполнить скрипт. Добавь заголовок `w.Header().Set("X-Content-Type-Options", "nosniff")`. Убедись, что браузер строго парсит это как текст.
738. **SQL-инъекция в ORDER BY:** Ты знаешь про плейсхолдеры (`WHERE id = $1`). Но попробуй подставить пользовательский ввод в сортировку: `SELECT * FROM users ORDER BY $1`. Убедись, что это НЕ работает (БД экранирует это как строку). Из-за этого джуны склеивают строки `ORDER BY ` + userInput (уязвимость!). Напиши безопасный `switch / whitelist` в Go, который строго маппит пользовательские слова ("date_asc") в захардкоженные SQL-куски.
739. **Уязвимость Directory Traversal:** Напиши простой файловый сервер: `os.ReadFile(filepath.Join("/var/www/images", req.URL.Query().Get("file")))`. Сделай запрос с `file=../../../../etc/passwd`. Убедись, что сервер отдал пароли Linux. Защити это с помощью `filepath.Clean` и проверки префикса `strings.HasPrefix(path, "/var/www/images")`. (В реальной жизни просто используй `http.FileServer`!).
740. **Secure Headers Middleware:** В финале напиши глобальную Middleware `SecurityHeaders`, которая добавляет ко всем HTTP-ответам стандарты безопасности:
    *   `Strict-Transport-Security: max-age=63072000` (HSTS — заставляет браузер всегда использовать HTTPS).
    *   `X-Frame-Options: DENY` (защита от Clickjacking — запрет встраивать твой сайт в iframe).
    *   `Content-Security-Policy: default-src 'self'` (CSP — запрет на выполнение сторонних JS скриптов).

**Помни:** Криптография и безопасность — это не те места, где нужно "изобретать велосипед". 
Освоив эти 35 принципов, ты научишься строить заборы там, где большинство разработчиков даже не подозревают о существовании дыр. PASETO, Argon2id и защита от SSRF — это то, что сегодня требуют на позициях уровня Senior/Lead Backend. Используй эти знания с умом!
