### Тема 131: `reflect` — Основы и Законы рефлексии
*Пакет `reflect` позволяет интроспектировать типы и значения в runtime. Но у него есть строгие законы, которые нужно знать.*

1331. **Закон #1:** Изучите 3 закона рефлексии Роберта Пайка:
    * Из interface value можно получить reflect object
    * Из reflect object можно получить interface value
    * Для изменения reflect object он должен быть "settable"
    
    Продемонстрируйте каждый закон кодом.

1332. **reflect.TypeOf:** Получите `reflect.Type` для переменных разных типов (`int`, `string`, `struct`, `slice`, `map`, `chan`, `func`). Выведите `Kind()`, `Name()`, `String()`.

1333. **reflect.ValueOf:** Получите `reflect.Value` из переменных. Изучите разницу между `Type` и `Value`.

1334. **Kind vs Type:** Поймите разницу: `Kind()` возвращает базовую категорию (`reflect.Int`, `reflect.Struct`), `Type()` возвращает конкретный тип (`main.User`).

1335. **Zero values через reflect:** Создайте zero value для любого типа через `reflect.Zero(typ).Interface()`.

1336. **Проверка nil через reflect:** Используйте `reflect.Value.IsNil()` для проверки nil указателей, срезов, мап, каналов, функций. Поймите, почему нельзя вызвать `IsNil()` на value type (panic!).

1337. **Type assertion через reflect:** Реализуйте универсальную функцию, которая принимает `any` и проверяет, является ли значение определённого типа.

1338. **Interface unpacking:** Распакуйте `any` через `reflect.ValueOf(v).Elem()` (для указателей) и `Interface()`.

1339. **Iterating through struct fields:** Получите все поля структуры через `reflect.Type.NumField()` и `Field(i)`. Выведите имена и типы.

1340. **Iterating through slice:** Получите элементы среза через `reflect.Value.Len()` и `Index(i)`.

1341. **Iterating through map:** Получите ключи и значения мапы через `MapKeys()` и `MapIndex(key)`.

1342. **Comparing types:** Сравните два типа через `reflect.DeepEqual` и через прямое сравнение `Type` объектов.

### Тема 132: `reflect` — Продвинутая работа
1343. **Settability:** Создайте переменную `x := 10`, получите `reflect.ValueOf(x)` и попробуйте изменить через `SetInt(20)`. Получите panic "reflect: cannot set". Поймите почему (передано по значению!).

1344. **Settable value:** Используйте `reflect.ValueOf(&x).Elem()` для получения settable value. Измените значение через `SetInt(20)`.

1345. **CanSet проверка:** Всегда проверяйте `Value.CanSet()` перед вызовом `Set*` методов.

1346. **Модификация полей структуры:** Создайте структуру с приватными и публичными полями. Попробуйте изменить оба через reflect. Поймите, почему приватные поля не settable (CanSet возвращает false).

1347. **Модификация элементов слайса:** Измените элементы слайса через `Value.Index(i).SetInt(newVal)`.

1348. **Модификация мапы:** Добавьте новую пару в мапу через `Value.SetMapIndex(key, value)`.

1349. **Создание новых значений:** Используйте `reflect.New(typ)` для создания указателя на новый zero-value. Используйте `reflect.MakeSlice`, `reflect.MakeMap`, `reflect.MakeChan`.

1350. **Append к срезу через reflect:** Реализуйте функцию, которая добавляет элемент к срезу любого типа через `reflect.Append(slice, value)`.

1351. **Type conversions:** Используйте `reflect.Value.Convert()` для конвертации между совместимыми типами.

1352. **Type assertion через reflect:** Реализуйте `Value.Type().AssignableTo(targetType)` для проверки совместимости типов.

1353. **DeepEqual internals:** Изучите, как работает `reflect.DeepEqual`. Какие edge cases он обрабатывает (NaN, циклические ссылки, приватные поля)?

1354. **Custom DeepEqual:** Напишите собственную реализацию `DeepEqual` для образовательных целей.

1355. **Pointer indirection:** Используйте `reflect.Indirect(value)` для автоматического разыменования указателей.

1356. **Method invocation:** Получите все методы типа через `Type.NumMethod()` и `Method(i)`. Вызовите метод через `Value.MethodByName(name).Call(args)`.

1357. **Method on pointer receiver:** Изучите разницу: методы с pointer receiver доступны только через `reflect.ValueOf(&obj)`, а не `reflect.ValueOf(obj)`.

1358. **Unexported methods:** Поймите, что приватные методы не доступны через `MethodByName` из других пакетов.

1359. **FieldByName vs FieldByIndex:** Используйте `FieldByName("Name")` для доступа по имени и `FieldByIndex([]int{0, 2})` для вложенных структур.

1360. **PkgPath:** Изучите `Type.PkgPath()` для получения пакета, где определён тип (пустая строка для built-in типов).

### Тема 133: `reflect` — Производительность и оптимизация
*Рефлексия в Go имеет репутацию "медленной". Но при правильном использовании она может быть быстрой.*

1361. **Benchmark reflect vs direct access:** Сравните производительность доступа к полю структуры напрямую vs через `Value.FieldByName()`. Разница должна быть в 100-1000x.

1362. **Кэширование индексов полей:** Сохраните индексы полей (`Type.FieldByName()` возвращает `StructField` с `Index`) при первой обработке типа. Используйте `Value.FieldByIndex()` для последующих обращений. Это в 10x быстрее.

1363. **Кэширование reflect.Type:** Сохраните `reflect.TypeOf()` результаты в map по имени типа. Повторный вызов `TypeOf()` стоит времени.

1364. **Аллокации в reflect:** Профилируйте бенчмарк через `-benchmem`. Узнайте, какие операции создают heap allocations.

1365. **Zero-allocation reflection:** Напишите код, который не делает heap аллокаций при reflect операциях. Избегайте `.Interface()` вызовов в hot paths.

1366. **Type switches vs reflect:** Сравните `switch v := x.(type)` vs reflect. Type switch компилируется в быстрый jump table.

1367. **Interface indirection:** Поймите, что каждый вызов `reflect.ValueOf(v)` создаёт interface value wrapper, который может аллоцировать на heap.

1368. **Optimized struct iteration:** Используйте кэш полей (map of field names to indexes) для быстрой обработки структур без повторных reflect вызовов.

1369. **Bulk field access:** Используйте `reflect.VisibleFields` (Go 1.20+) для получения всех полей, включая embedded, за один вызов.

1370. **Avoid reflect.DeepEqual в hot paths:** Реализуйте кастомное сравнение для ваших структур без reflect.

1371. **Pre-computed field paths:** Для глубоко вложенных структур сохраните пути полей (`[]int` индексы) при startup для быстрого доступа в runtime.

1372. **Code generation vs reflection:** Для критичных по производительности участков рассмотрите кодогенерацию вместо runtime reflect (пример: `easyjson`, `ffjson`).

### Тема 134: Работа со Struct Tags
*Struct tags — это метаданные, прикреплённые к полям структур, которые читаются через reflect.*

1373. **Парсинг тегов:** Получите `reflect.StructField` для поля структуры и используйте `Tag.Get("json")` для получения тега.

1374. **StructTag.Lookup:** Используйте `Tag.Lookup("json")` вместо `Get` для различения отсутствующего тега и тега с пустым значением.

1375. **Множественные теги:** Парсите теги с несколькими значениями: `` `json:"name,omitempty" db:"user_name" validate:"required"` ``. Используйте библиотеку `github.com/fatih/structtag` для парсинга.

1376. **Напишите валидатор:** Создайте функцию `Validate(v any) error`, которая проверяет структуру по тегам `validate:"required"`, `validate:"min=5"`, `validate:"email"`.

1377. **Напишите JSON маппер:** Реализуйте собственную функцию, которая маршалит структуру в JSON, используя имена полей из тегов `json:"name"`.

1378. **Напишите SQL builder:** Создайте функцию, которая генерирует `INSERT` SQL statement на основе тегов `db:"column_name"`.

1379. **Напишите form parser:** Парсите `application/x-www-form-urlencoded` данные в структуру по тегам `form:"field_name"`.

1380. **Nested struct tags:** Рекурсивно обрабатывайте вложенные структуры, сохраняя путь полей (например, `user.address.city`).

1381. **Anonymous fields (embedding):** Корректно обрабатывайте embedded структуры при парсинге тегов.

1382. **Custom tag syntax:** Напишите парсер для собственных тегов со сложным синтаксисом (например, `mylib:"name,type=int,default=10"`).

1383. **Tag validation при компиляции:** Создайте линтер (используя go/ast), который проверяет корректность тегов в вашем проекте.

1384. **Tag inheritance:** Реализуйте наследование тегов: если у поля нет тега, используйте тег из embedded структуры.

### 💡 Золотые правила метапрограммирования в Go:

1. **Reflection — last resort.** Если задачу можно решить без reflect (дженерики, интерфейсы, кодогенерация) — решайте без него. Reflect:
   * В 100-1000x медленнее
   * Теряет type safety
   * Усложняет отладку
   * Скрывает ошибки до runtime

2. **Когда reflect оправдан:**
   * Библиотеки общего назначения (JSON encoder, ORM, DI frameworks)
   * Debug/inspection tools
   * Runtime plugin systems
   * Когда типы неизвестны в compile-time

3. **Кэшируйте результаты reflect.** Повторные вызовы `TypeOf()`, `FieldByName()` стоят дорого. Сохраняйте результаты в sync.Map.

4. **Кодогенерация > Reflection.** Для продакшен кода предпочитайте кодогенерацию:
   * Быстрее (нет runtime overhead)
   * Type-safe (компилятор проверяет)
   * Debuggable (видите сгенерированный код)
   * Инструментируется линтерами

5. **go:generate — это контракт.** Команда `go generate` должна быть идемпотентной (повторный запуск даёт тот же результат) и детерминированной.

6. **Форматируйте сгенерированный код.** Всегда пропускайте через `go/format.Source()` или вызывайте `gofmt -w`. Никогда не коммитьте неформатированный код.

7. **Добавляйте комментарии в сгенерированный код:**
   ```go
   // Code generated by my-tool; DO NOT EDIT.
   // Source: schema.sql
   // Version: 1.2.3
   ```
   Это стандарт индустрии и защищает от случайного редактирования.

8. **Не коммитьте generated code, если...** он легко перегенерируется и не имеет runtime зависимостей. Но в большинстве проектов generated code коммитится для reproducibility.

9. **AST анализ требует аккуратности:**
   * Обрабатывайте все node types (не только `*ast.Ident`)
   * Учитывайте scope и shadowing
   * Понимайте разницу между declaration и usage
   * Тестируйте на реальных кодовых базах

10. **Пишите линтеры через ast, а не regex.** Regex не понимает структуру кода. AST даёт корректный анализ.

11. **Тестируйте generated code:**
    * Snapshot tests (golden files)
    * Compile tests (сгенерированный код должен компилироваться)
    * Behavior tests (сгенерированный код работает корректно)
    * Round-trip tests (source → generated → source должно давать тот же результат)

12. **Минимизируйте runtime reflect в продакшене.** Если библиотека использует reflect для bootstrap (при старте), это нормально. Но в hot paths избегайте reflect любой ценой.

13. **Используйте generics (Go 1.18+) вместо reflect.** Многие паттерны, которые раньше требовали reflect (generic data structures, type assertions), теперь решаются через дженерики с нулевым overhead.

14. **Для сложных случаев комбинируйте:**
    * AST анализ при разработке (линтеры, анализаторы)
    * Кодогенерация при сборке (mock'и, boilerplate)
    * Generics в runtime (type-safe generic code)
    * Reflect только там, где без него не обойтись

15. **Read source of famous generators:**
    * `stringer` — enum string methods
    * `easyjson` — fast JSON marshaling
    * `mockery`/`gomock` — mock generation
    * `wire` — dependency injection
    * `sqlc` — SQL to Go code
    
    Изучение этих проектов даст вам master-class по кодогенерации.
