Метапрограммирование — это высший пилотаж. Это код, который анализирует, изменяет или создает другой код. В Go метапрограммирование представлено тремя китами: **Рефлексия** (динамический анализ в рантайме), **AST** (статический анализ исходников) и **Кодогенерация** (написание утилит для избавления от бойлерплейта).

Продолжаем нашу нумерацию. Впереди **30 архитектурных и хардкорных упражнений** (с 676 по 705), которые научат тебя писать собственные линтеры, ORM и генераторы моков.

### Блок 64. Рефлексия (`reflect`): Законы и Динамика (676–685)
Рефлексия позволяет программе исследовать собственные типы и переменные во время выполнения. Но за это приходится платить производительностью.

676. **Закон №1 (Interface -> Reflection Object):** Объяви переменную `x float64 = 3.4`. Используй `reflect.TypeOf(x)` и `reflect.ValueOf(x)`. Выведи их. Вызови метод `Kind()` у типа, чтобы убедиться, что базовый вид — это именно `float64`.
677. **Закон №2 (Reflection Object -> Interface):** Возьми `reflect.Value` из упр. 676. Верни его обратно в мир обычных интерфейсов с помощью метода `Interface()`. Сделай утверждение типа (type assertion) `.(float64)` и умножь на 2.
678. **Закон №3 (Settability - Изменяемость):** Попытайся изменить значение через `reflect.ValueOf(x).SetFloat(7.1)`. Получишь панику. Чтобы рефлексия могла изменять оригинал, ты должен передать **указатель**: `v := reflect.ValueOf(&x)`. Затем получи саму переменную через `v.Elem()` и вызови `SetFloat`. Проверь, что `x` изменился.
679. **Динамический парсер тегов (Struct Tags):** Создай структуру `User` с тегами `` `validate:"required,min=18"` ``. Напиши функцию `Validate(v any) error`, которая через рефлексию проходит по всем полям структуры (метод `NumField()` и `Field()`), читает теги (`Tag.Get("validate")`) и применяет правила валидации.
680. **Работа со вложенными и анонимными структурами:** Добавь в `User` анонимное поле `Address` (структуру). Напиши рекурсивную функцию на рефлексии, которая выводит плоский список всех полей, проваливаясь внутрь анонимных структур (проверяй `Kind() == reflect.Struct` и `Anonymous == true`).
681. **Динамический вызов функции (Call):** У тебя есть мапа `map[string]any`, где ключи — названия функций, а значения — сами функции с разными сигнатурами. Напиши код, который по строковому имени достает функцию, динамически собирает для нее срез аргументов `[]reflect.Value` и вызывает через метод `Call()`.
682. **Создание типов на лету:** У тебя есть типы ключа и значения в виде `reflect.Type`. Используй `reflect.MakeMap` и `reflect.MakeSlice`, чтобы динамически инициализировать мапу и срез этих типов, а затем добавь туда элементы через `MapIndex` и `Append`.
683. **DeepEqual своими руками:** Стандартный `reflect.DeepEqual` медленный. Напиши свою функцию `MyDeepEqual(a, b any) bool`, которая через рефлексию сравнивает две структуры по полям. Поддержи сравнение даже неэкспортируемых (приватных) полей.
684. **Цена рефлексии (Бенчмарк):** Напиши структуру из 5 полей. Напиши бенчмарк прямого присвоения полей и бенчмарк присвоения через `reflect.ValueOf(&s).Elem().Field(0).SetString(...)`. Запусти с `-benchmem`. Убедись, что рефлексия не только в десятки раз медленнее, но и вызывает лавину аллокаций памяти (попадание в кучу).
685. **Оптимизация (unsafe + reflect):** Пакет `reflect` предоставляет типы `StringHeader` и `SliceHeader` (или их современные аналоги в `unsafe`). Напиши код, который читает поле структуры через `reflect`, но затем использует `unsafe.Pointer` для получения прямого адреса памяти этого поля. Измени значение по сырому адресу в обход проверок `reflect.Value.Set()`. Сравни в бенчмарке — скорость будет близка к нативному коду!

### Блок 65. Анализ синтаксического дерева (AST) и кастомные Линтеры (686–695)
Код на Go — это просто текст. Мы превратим его в дерево (Abstract Syntax Tree) и будем анализировать программно.

686. **Токенизация (`go/scanner`):** Создай строку с Go-кодом `src := "package main; func main() { println(42) }"`. Используй `scanner.Scanner`, чтобы разбить текст на токены. В цикле выведи каждый токен (названия вроде `IDENT`, `LPAREN`, `INT`) и его позицию (строка/колонка).
687. **Парсинг файла (`go/parser`):** Используй `parser.ParseFile`, чтобы распарсить простой файл `main.go`. Полученный объект `*ast.File` выведи в консоль через функцию `ast.Print(fset, node)`. Изучи гигантское дерево, которое генерирует компилятор.
688. **Обход дерева (Visitor Pattern):** Напиши структуру, реализующую интерфейс `ast.Visitor` (метод `Visit(node ast.Node) ast.Visitor`). Передай её в `ast.Walk`. Заставь визитор находить и выводить названия всех функций (`*ast.FuncDecl`), объявленных в файле.
689. **Сборщик комментариев и Magic Tags:** Используй поле `Comments` в `*ast.File`. Напиши утилиту, которая сканирует Go-файл и находит все комментарии, начинающиеся с `// TODO:`. Выведи их текст и точный номер строки.
690. **Модификация AST:** С помощью `astutil.Apply` пройдись по дереву. Найди все вызовы функции `fmt.Println` (`*ast.CallExpr`) и программно замени имя пакета с `fmt` на `log`. Затем используй пакет `go/format`, чтобы сгенерировать из измененного дерева новый красивый исходный код и вывести его!
691. **Семантический анализ (`go/types`):** AST не знает типов (оно не знает, что `x` — это `int`). Используй связку `go/parser` + `go/types`. Распарси файл, прогони type checker и найди точный тип переменной `x` в выражении `y := x + 5`.
692. **Свой собственный Линтер (База):** Забудь про ручной парсинг для линтеров. Импортируй фреймворк `golang.org/x/tools/go/analysis`. Создай свой `Analyzer`. Напиши правило: линтер должен ругаться (вызывать `pass.Reportf`), если в коде используется функция `panic()`.
693. **Линтер "Magic Numbers":** Напиши Analyzer, который ищет "магические числа". Если в коде (вне объявления констант) встречается числовой литерал (`*ast.BasicLit`), отличный от `0` или `1`, линтер должен подсветить эту строку и попросить вынести число в константу.
694. **Поиск неиспользуемых полей структуры:** Напиши сложный линтер. Он должен найти объявление структуры (AST), запомнить все её поля. Затем пройтись по всему коду и посмотреть, к каким полям идет обращение (`*ast.SelectorExpr`). Поля, к которым не было обращений, пометить как мертвый код.
695. **Интеграция линтера (go vet):** Оберни свой `Analyzer` в функцию `singlechecker.Main(MyAnalyzer)`. Скомпилируй программу. Запусти её на своем проекте: `go vet -vettool=/path/to/your/linter ./...`. Поздравляю, ты расширил стандартный инструментарий Go!

### Блок 66. Кодогенерация (`go generate`, `text/template`) (696–705)
Кодогенерация — это "Go-way" замены дженериков (до версии 1.18) и ORM. Пишем код, который пишет код.

696. **Утилита `stringer`:** У тебя есть `type Status int` и блок констант (`Pending`, `Active`, `Banned`). Скачай официальную утилиту `golang.org/x/tools/cmd/stringer`. Поставь перед типом магический комментарий `//go:generate stringer -type=Status`. Выполни `go generate ./...` в терминале. Убедись, что появился файл `status_string.go` с быстрым методом `String()`.
697. **Внедрение файлов (`go:embed`):** Создай папку `sql` с файлами миграций (`.sql`). В Go-коде напиши `//go:embed sql/*.sql` над переменной `var migrations embed.FS`. Скомпилируй программу, удали папку `sql` с диска и запусти бинарник. Напиши код, который выводит содержимое файлов — убедись, что они "запеклись" внутрь исполняемого файла.
698. **Шаблонизатор (`text/template`):** Напиши простой `.tmpl` файл, который описывает структуру Go-кода (например, HTTP-хендлер). В Go-скрипте спарси этот шаблон `template.ParseFiles`, передай в него структуру с данными (имя хендлера, маршрут) и сгенерируй готовый `.go` файл на диск через `tmpl.Execute`.
699. **Форматирование сгенерированного кода:** Код из упр. 698 может получиться кривым (пробелы, переносы). Прогоняй сгенерированные байты через `format.Source(b)` (из пакета `go/format`) перед записью на диск. Если в коде есть неиспользуемые импорты, используй пакет `golang.org/x/tools/imports` (аналог `goimports`), чтобы утилита сама расставила и удалила импорты.
700. **Тег `ignore` для генераторов:** Генераторы не должны компилироваться в финальный бинарник. Вынеси логику генерации в файл `generator.go`. Добавь в самую первую строку файла `//go:build ignore`. В файле с бизнес-логикой напиши `//go:generate go run generator.go`. Запусти.
701. **Генератор Mock-ов своими руками:** Напиши утилиту `mockgen_lite`. Она принимает имя интерфейса. Используя `go/parser` (Блок 65), она находит этот интерфейс в текущем пакете, читает все его методы, их аргументы и возвращаемые типы. Затем через `text/template` она генерирует структуру `Mock...`, которая имеет те же методы, но возвращает дефолтные нули (или вызывает сохраненные функции).
702. **Генератор Getter / Setter:** Создай структуру с приватными полями и тегами `//gen:getter` и `//gen:setter`. Напиши утилиту, которая парсит этот файл (AST), находит эти комментарии над полями и генерирует рядом файл с публичными геттерами и сеттерами для этих полей (как в Java/Lombok).
703. **Генератор JSON Enum (Unmarshaler):** Стандартный `json.Unmarshal` парсит числа, а тебе нужно, чтобы клиент присылал строки `"PENDING"`, а в Go это превращалось в константу `1`. Напиши кодогенератор, который по AST констант-перечислений генерирует для них методы `MarshalJSON` и `UnmarshalJSON`.
704. **Свой DI-контейнер (Аналог Wire):** Напиши скрипт, который сканирует проект, находит все функции конструкторы, начинающиеся на `New...` (например `NewUserService(repo Repository)`). Скрипт строит граф зависимостей и генерирует одну большую функцию `InitApp()`, которая правильно, в нужном порядке вызывает все эти `New...` функции и возвращает готовую структуру приложения.
705. **Ультимативный CRUD Generator:** Совмести всё! Напиши CLI-утилиту. Она читает структуру, например `User{ID, Name}`. На основе этой структуры утилита генерирует: 1) SQL-миграцию `CREATE TABLE`, 2) Go-репозиторий с методами Insert/Get/Update/Delete (чистый SQL с плейсхолдерами), 3) HTTP-хендлеры для CRUD операций. Запуск одной команды `go generate` должен породить полностью рабочий микросервис для этой сущности.
