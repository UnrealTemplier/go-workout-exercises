Отличное дополнение! Message Queues — это "нервная система" распределенных систем. Kafka, RabbitMQ и NATS решают разные задачи: Kafka для high-throughput event streaming и log-based архитектуры, RabbitMQ для гибкого роутинга сообщений и work queues, NATS для ultra-low latency межсервисного общения.

Ниже представлен **масштабный блок из 105 упражнений (с 765 по 869)**, который проведет вас от первого `Publish` до построения production-ready event-driven архитектуры с exactly-once семантикой и observability.

### Тема 88: NATS — Легковесный и быстрый
*NATS — это "Redis для сообщений". Минималистичный, быстрый, с поддержкой JetStream для persistence.*
765. Поднимите локальный NATS сервер через Docker (`nats:latest`) и подключитесь к нему через `github.com/nats-io/nats.go`.
766. Реализуйте простейший **Pub/Sub**: один клиент публикует сообщение в тему `orders.new`, другой подписывается и получает его.
767. Используйте **wildcard-подписки**: подпишитесь на `orders.*` и `orders.>` (одноуровневый и многоуровневый wildcard).
768. Реализуйте **Request/Reply** паттерн: клиент отправляет запрос и синхронно ждет ответ (аналог RPC через NATS).
769. Создайте **Queue Group**: несколько воркеров подписываются на одну тему с `Queue: "workers"`, и каждое сообщение получает только один из них (load balancing).
770. Изучите **connection options**: настройте reconnect policy, max reconnect attempts, ping/pong interval для production-использования.
771. Реализуйте **graceful shutdown**: при получении SIGINT корректно отпишитесь от всех subjects и закройте соединение.
772. Используйте **context** для отмены операций: `nc.RequestWithContext(ctx, subject, data)`.
773. Добавьте **metadata в сообщения**: используйте NATS Headers (аналог HTTP-заголовков) для передачи trace ID, correlation ID.
774. Реализуйте **scatter-gather** паттерн: отправьте запрос множеству сервисов и соберите все ответы (fan-out/fan-in).
775. **JetStream basics:** Включите JetStream (`nats-server -js`) и создайте persistent stream `ORDERS` через `js.AddStream`.
776. Опубликуйте сообщение в JetStream stream с **acknowledgement**: `js.Publish` возвращает ack от сервера.
777. Создайте **consumer** с `js.PullSubscribe` и обрабатывайте сообщения батчами (pull-based consumption).
778. Используйте **push-based consumer** (`js.Subscribe`) для автоматической доставки сообщений.
779. Настройте **retention policy** для stream: `limits` (max messages/bytes/age), `interest` (хранить пока есть подписчики), `work queue` (каждое сообщение доставляется одному consumer).
780. Реализуйте **at-least-once delivery**: после обработки сообщения вызывайте `msg.Ack()`. Если воркер упал до ack — сообщение будет redelivered.
781. Используйте **Nak** для явного отказа от обработки (сообщение будет redelivered позже).
782. Настройте **dead letter queue**: сообщения, которые не удалось обработать после N попыток, отправляются в отдельный stream для ручного разбора.
783. Реализуйте **message deduplication** через `Nats-Msg-Id` header — NATS не будет дублировать сообщения с одинаковым ID в рамках окна дедупликации.
784. Создайте **Key-Value store** через JetStream: `js.CreateKeyValue(&nats.KeyValueConfig{Bucket: "config"})` — это как Redis, но с persistence и replication.
785. Используйте **NATS KV как service discovery**: сервисы регистрируют себя в KV с TTL, другие сервисы читают и обнаруживают доступные инстансы.
786. Настройте **NATS cluster** из 3 нод и проверьте, что клиенты автоматически подключаются к доступным нодам.
787. Реализуйте **monitoring**: подключитесь к NATS monitoring endpoint (`:8222/varz`, `/connz`, `/subsz`) и собирайте метрики для Prometheus.
788. **Финальный NATS босс:** Создайте систему уведомлений:
    * Микросервисы публикуют события (`user.registered`, `order.paid`) в JetStream streams.
    * Notification service подписывается на все события и отправляет email/SMS/push.
    * Используется Queue Group для горизонтального масштабирования notification service.
    * Dead letter queue для failed notifications с retry logic.
    * Exactly-once delivery через message deduplication.
    * Observability: OpenTelemetry трейсинг, Prometheus метрики (messages/sec, latency, error rate).

### Тема 89: Kafka — Event Streaming Platform
*Kafka — это distributed commit log. Идеален для event sourcing, CDC (Change Data Capture), high-throughput streaming.*
789. Поднимите локальный Kafka cluster через Docker Compose (Kafka + Zookeeper или KRaft mode). Используйте `confluentinc/cp-kafka` или `bitnami/kafka`.
790. Подключитесь к Kafka через `github.com/segmentio/kafka-go` (или `github.com/twmb/franz-go` — более современный и быстрый).
791. Создайте **topic** `orders` с 3 partitions и replication factor 1 через Admin API.
792. Реализуйте **producer**, который отправляет сообщения в topic `orders`. Используйте `Writer` с настройками `BatchTimeout`, `BatchBytes`.
793. Реализуйте **consumer** через `Reader`, который читает из topic `orders` с `StartOffset: FirstOffset` (с самого начала).
794. Изучите **partition key**: отправляйте сообщения с ключом `user_id`, чтобы все события одного пользователя попадали в одну partition (сохранение порядка).
795. Используйте **consumer groups**: запустите 3 consumer с одинаковым `GroupID`, и Kafka автоматически распределит partitions между ними.
796. Реализуйте **commit offset**: после обработки сообщения вызывайте `reader.CommitMessages(ctx, msg)`. Изучите разницу между auto-commit и manual commit.
797. Настройте **exactly-once semantics** через idempotent producer (`RequiredAcks: All`, `EnableIdempotence: true`).
798. Используйте **transactions** в producer для атомарной записи в несколько partitions (`BeginTransaction`, `SendOffsetsToTransaction`, `CommitTransaction`).
799. Реализуйте **dead letter queue**: при ошибке обработки отправляйте сообщение в topic `orders.dlq` с оригинальными headers и информацией об ошибке.
800. Создайте **compacted topic** (`cleanup.policy: compact`): Kafka будет хранить только последнее значение для каждого ключа (как Key-Value store).
801. Используйте **log compaction** для event sourcing: храните все события, но периодически "сжимайте" историю.
802. Реализуйте **consumer lag monitoring**: используйте `Reader.Stats()` или Kafka Admin API для отслеживания, насколько consumer отстает от producer.
803. Настройте **retention policy**: `retention.ms` (время хранения), `retention.bytes` (размер), `segment.bytes` (размер segment файла).
804. Используйте **Kafka Streams** (через `github.com/lovoo/goka`) для stream processing: фильтрация, агрегация, joins между topics.
805. Реализуйте **windowed aggregation**: подсчитывайте количество заказов за последние 5 минут с использованием tumbling window.
806. Создайте **Kafka Connect** source connector для CDC: читайте изменения из PostgreSQL через Debezium и публикуйте в Kafka topic.
807. Используйте **Schema Registry** с Avro/Protobuf schemas для обеспечения совместимости сообщений (backward/forward compatibility).
808. Реализуйте **schema evolution**: добавьте новое поле в Protobuf-схему и убедитесь, что старые consumers могут читать новые сообщения.
809. Настройте **Kafka cluster** из 3 брокеров и проверьте replication: остановите один брокер и убедитесь, что данные доступны.
810. Используйте **Kafka MirrorMaker 2** для репликации данных между дата-центрами.
811. Реализуйте **backpressure**: если consumer не успевает обрабатывать, уменьшайте `MaxBytes` или увеличивайте `MaxWait` в reader.
812. Создайте **Kafka Streams приложение** для real-time analytics: агрегируйте события из `orders` topic и записывайте результаты в `orders.daily_stats`.
813. Используйте **KSQL** или **ksqlDB** для SQL-подобных запросов к Kafka streams (declarative stream processing).
814. Настройте **monitoring** через JMX metrics и экспортируйте их в Prometheus через `jmx_exporter`.
815. Реализуйте **graceful shutdown** для consumer: при получении SIGINT дождитесь завершения текущей обработки и закоммитьте offset.
816. Используйте **Kafka Streams interactive queries** для доступа к state store (например, получить текущий баланс пользователя).
817. **Финальный Kafka босс:** Создайте event-driven e-commerce платформу:
    * **Order Service** публикует события `OrderCreated`, `OrderPaid`, `OrderShipped` в Kafka topic `orders`.
    * **Inventory Service** потребляет `OrderCreated` и резервирует товары (saga pattern через events).
    * **Payment Service** потребляет `OrderPaid` и обновляет статус платежа.
    * **Analytics Service** использует Kafka Streams для подсчета daily revenue, top products, conversion rate.
    * **Search Service** использует Debezium CDC для синхронизации данных из PostgreSQL в Elasticsearch через Kafka.
    * Все события используют Protobuf схемы через Schema Registry.
    * Exactly-once processing через idempotent producers и transactional consumers.
    * Dead letter queues для failed events с alerting.
    * Observability: distributed tracing через OpenTelemetry, Kafka lag monitoring, Prometheus metrics.
    * Horizontal scaling: каждый сервис имеет 3 инстанса в consumer group.

### Тема 90: RabbitMQ — Гибкий роутинг и Work Queues
*RabbitMQ — это классический AMQP broker с богатыми возможностями роутинга через exchanges и queues.*
818. Поднимите RabbitMQ через Docker (`rabbitmq:3-management`) и откройте Management UI на порту 15672.
819. Подключитесь к RabbitMQ через `github.com/rabbitmq/amqp091-go` (официальный клиент).
820. Создайте **queue** `orders` и отправьте в него сообщение через default exchange.
821. Реализуйте **consumer**, который читает из queue `orders` с auto-ack (`autoAck: true`). Изучите, почему это опасно (потеря сообщений при crash).
822. Используйте **manual acknowledgements**: `msg.Ack(false)` после успешной обработки, `msg.Nack(false, true)` для requeue при ошибке.
823. Создайте **Direct Exchange** `orders.exchange` и bind queue `orders.new` с routing key `order.created`.
824. Используйте **Topic Exchange** для гибкого роутинга: routing keys `order.created`, `order.paid`, `order.shipped`, подписки `order.*`, `order.#`.
825. Реализуйте **Fanout Exchange** для broadcast: одно сообщение доставляется во все binded queues (например, для уведомлений).
826. Создайте **Headers Exchange** для роутинга на основе заголовков сообщений (например, `x-priority: high`).
827. Реализуйте **work queue pattern**: один producer, несколько consumers, каждое сообщение обрабатывается одним consumer (round-robin).
828. Настройте **prefetch count** (`channel.Qos(10, 0, false)`): consumer получает не более 10 сообщений одновременно (backpressure).
829. Используйте **message TTL** (`x-message-ttl`): сообщения, которые не были потреблены за N миллисекунд, удаляются.
830. Настройте **queue TTL** (`x-expires`): queue автоматически удаляется, если к ней не было обращений N миллисекунд.
831. Реализуйте **dead letter exchange (DLX)**: сообщения, которые были rejected/nacked без requeue или истек TTL, отправляются в DLX для дальнейшего анализа.
832. Создайте **delayed message queue** через `rabbitmq-delayed-message-exchange` plugin или через TTL + DLX hack.
833. Используйте **priority queues** (`x-max-priority`): сообщения с высоким приоритетом обрабатываются раньше.
834. Реализуйте **RPC через RabbitMQ**: client отправляет запрос в queue с `replyTo` header, server обрабатывает и отправляет ответ в reply queue.
835. Используйте **publisher confirms**: `channel.Confirm(false)` и `channel.NotifyPublish` для гарантии, что сообщение принято брокером.
836. Настройте **transactions** (`channel.Tx()`) для атомарной публикации нескольких сообщений (но это медленно, используйте confirms).
837. Реализуйте **reliable delivery**: сохраняйте сообщения в локальной БД перед отправкой, помечайте как sent после confirm (transactional outbox pattern).
838. Создайте **sharded queue** через `x-consistent-hash` exchange для распределения нагрузки.
839. Используйте **consumer cancellation notification**: если queue удаляется, consumer получает уведомление и может переподключиться.
840. Настройте **high availability** через classic queues mirroring (в RabbitMQ 3.x) или quorum queues (в RabbitMQ 3.8+).
841. Реализуйте **clustering**: создайте cluster из 3 RabbitMQ нод и проверьте, что очереди реплицируются.
842. Используйте **federation** или **shovel** plugin для репликации сообщений между разными RabbitMQ clusters.
843. Настройте **monitoring** через Management HTTP API и экспортируйте метрики в Prometheus через `rabbitmq_prometheus` plugin.
844. Реализуйте **graceful shutdown** для consumer: при SIGINT дождитесь завершения текущих сообщений и закройте channel/connection.
845. **Финальный RabbitMQ босс:** Создайте систему обработки заказов:
    * **Order API** принимает заказы и публикует их в exchange `orders` с routing key `order.created`.
    * **Payment Service** потребляет из queue `payment.orders`, обрабатывает платеж и публикует `order.paid` или `order.failed`.
    * **Fulfillment Service** потребляет `order.paid` и запускает процесс доставки.
    * **Notification Service** использует Fanout exchange для отправки email/SMS/push уведомлений.
    * Dead letter exchange для failed orders с retry logic (exponential backoff через delayed messages).
    * Priority queues для VIP-клиентов.
    * Publisher confirms + transactional outbox для guaranteed delivery.
    * Consumer prefetch для backpressure.
    * Quorum queues для high availability.
    * Monitoring через Prometheus + Grafana дашборды (queue depth, consumer lag, message rates).

### Тема 91: Общие паттерны и Production-практики
846. **Transactional Outbox Pattern:** Реализуйте паттерн, где бизнес-операция и публикация сообщения происходят в одной транзакции БД. Отдельный процесс читает outbox table и публикует в queue.
847. **Idempotency:** Добавьте уникальный `message_id` в каждое сообщение. Consumer проверяет, обрабатывалось ли это сообщение раньше (через Redis или БД).
848. **Correlation ID:** Генерируйте уникальный ID для каждого бизнес-процесса и пробрасывайте его через все сообщения для distributed tracing.
849. **Saga Pattern через events:** Реализуйте распределенную транзакцию через цепочку событий с компенсирующими действиями (например, `OrderCreated` -> `PaymentFailed` -> `OrderCancelled`).
850. **Event Sourcing:** Сохраняйте все изменения состояния как последовательность событий в Kafka/NATS JetStream. Восстанавливайте состояние через replay событий.
851. **CQRS (Command Query Responsibility Segregation):** Используйте queue для команд (write operations) и отдельную read model (например, Elasticsearch) для запросов.
852. **Backpressure:** Если consumer не успевает, используйте prefetch limits, уменьшайте batch size или временно приостанавливайте producer.
853. **Circuit Breaker для queue:** Если queue недоступна, временно переключитесь на fallback (например, сохраняйте в локальную БД).
854. **Retry с exponential backoff:** При ошибке обработки отправляйте сообщение в delay queue с увеличивающейся задержкой (1s, 2s, 4s, 8s...).
855. **Poison pill handling:** Если сообщение вызывает crash consumer, отправляйте его в dead letter queue после N попыток, чтобы не блокировать всю queue.
856. **Message versioning:** Добавляйте версию схемы в заголовок сообщения (`schema-version: v2`). Consumer выбирает нужный парсер в зависимости от версии.
857. **Schema Registry:** Используйте Confluent Schema Registry (для Kafka) или собственный сервис для управления Protobuf/Avro/JSON схемами.
858. **Observability:** Инструментируйте producer и consumer OpenTelemetry spans. Каждый send/receive — это отдельный span с атрибутами (topic, partition, offset).
859. **Metrics:** Собирайте метрики: messages produced/consumed per second, consumer lag, processing latency, error rate, queue depth.
860. **Alerting:** Настройте алерты на: consumer lag > threshold, queue depth > threshold, error rate > threshold, dead letter queue не пустая.
861. **Graceful degradation:** Если queue недоступна, приложение должно продолжать работать (например, возвращать cached data или degraded response).
862. **Chaos testing:** Используйте `tc` (traffic control) или `pumba` для эмуляции сетевых задержек, потерь пакетов и падения брокеров.
863. **Security:** Настройте TLS для encryption, SASL для аутентификации, ACL для авторизации (кто может читать/писать в какие topics/queues).
864. **Multi-tenancy:** Изолируйте данные разных клиентов через отдельные topics/queues или через partition key + ACL.
865. **Testing с Testcontainers:** Используйте `testcontainers-go` для поднятия Kafka/RabbitMQ/NATS в интеграционных тестах.
866. **Local development:** Используйте Docker Compose с Kafka/RabbitMQ/NATS + их UI (Kafka UI, RabbitMQ Management, NATS Box) для локальной разработки.

### Тема 92: Сравнение и выбор технологии
867. **Когда использовать NATS:** Ultra-low latency (<1ms), простой pub/sub, request/reply, service discovery. Не подходит для persistence (без JetStream) и сложных роутингов.
868. **Когда использовать Kafka:** High-throughput (миллионы сообщений/сек), event sourcing, log-based архитектура, replay сообщений, stream processing. Overkill для простых задач.
869. **Когда использовать RabbitMQ:** Гибкий роутинг (exchanges), work queues, priority queues, delayed messages, RPC. Хороший баланс между возможностями и сложностью.
870. **Финальный босс (Event-driven микросервисная платформа):**
    Создайте систему типа "Uber/Lyft":
    * **Ride Request Service** публикует `RideRequested` в Kafka topic `rides`.
    * **Driver Matching Service** (NATS) потребляет события и ищет ближайших водителей через geo-spatial queries.
    * **Pricing Service** (RabbitMQ work queue) вычисляет surge pricing на основе спроса/предложения.
    * **Notification Service** использует RabbitMQ fanout для отправки push-уведомлений пассажиру и водителю.
    * **Payment Service** обрабатывает платежи через Kafka transactions (exactly-once).
    * **Analytics Service** использует Kafka Streams для real-time метрик (rides per minute, avg wait time, surge zones).
    * **Location Service** публикует обновления местоположения водителей в NATS (low latency) с JetStream persistence.
    * Все сервисы используют OpenTelemetry для distributed tracing.
    * Prometheus + Grafana для мониторинга (queue depths, consumer lag, message rates, latency percentiles).
    * Circuit breakers и retry logic для resilience.
    * Dead letter queues для failed messages с alerting.
    * Transactional outbox для guaranteed delivery.
    * Schema Registry для Protobuf schemas.
    * Horizontal scaling: каждый сервис имеет 3+ инстанса.
    * Chaos testing: убивайте брокеры и сервисы, проверяйте, что система восстанавливается.
    * Load testing: 10000 ride requests/минуту, P99 latency < 200ms.

### 💡 Золотые правила работы с Message Queues:

1. **Выбирайте инструмент под задачу:**
   - **NATS:** Simple pub/sub, request/reply, service discovery, ultra-low latency
   - **Kafka:** Event sourcing, high-throughput streaming, log-based, replay
   - **RabbitMQ:** Complex routing, work queues, priority, RPC, delayed messages

2. **Всегда используйте manual acknowledgements.** Auto-ack приведет к потере сообщений при crash consumer. Ack только после успешной обработки.

3. **Idempotency обязательна.** Сообщения могут быть доставлены несколько раз (at-least-once). Consumer должен корректно обрабатывать дубликаты через уникальный message_id.

4. **Dead letter queues — это must have.** Без DLQ вы не узнаете о сообщениях, которые не удалось обработать. Настраивайте retry с exponential backoff и алерты на непустые DLQ.

5. **Transactional Outbox для critical data.** Если сообщение должно быть отправлено вместе с бизнес-операцией, используйте outbox pattern. Это гарантирует, что либо обе операции succeed, либо обе fail.

6. **Schema evolution через versioning.** Всегда добавляйте версию схемы в сообщения. Используйте Schema Registry для управления совместимостью (backward/forward).

7. **Consumer lag monitoring.** Если consumer отстает от producer, queue будет расти бесконечно. Мониторьте lag и масштабируйте consumers.

8. **Backpressure через prefetch.** Не позволяйте broker завалить consumer сообщениями. Используйте prefetch count для контроля потока.

9. **Distributed tracing через correlation ID.** Пробрасывайте уникальный ID через все сообщения для end-to-end трассировки бизнес-процессов.

10. **Graceful shutdown обязателен.** При SIGINT consumer должен дождаться завершения текущих сообщений, закоммитить offset/ack и только потом завершиться.

11. **Тестируйте с Testcontainers.** Моки queue не найдут 30% реальных проблем (serialization, ordering, concurrency). Используйте Testcontainers для integration tests.

12. **Observability из коробки.** Каждый producer/consumer должен экспортировать метрики (Prometheus) и трейсы (OpenTelemetry). Без этого вы слепы в production.
