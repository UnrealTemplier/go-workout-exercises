## Блок 4. `unsafe.Pointer` и `uintptr`

### Уровень 1. Базовые концепции и правила игры
51. Напишите программу, которая через `unsafe.Pointer` преобразует `*int64` в `*float64` (без изменения битового паттерна). Выведите hex-дамп до и после. Объясните, почему GC не мешает при короткой жизни `unsafe.Pointer`, но почему хранение промежуточного `uintptr` в переменной — опасно.
52. Реализуйте функцию `ptrAdd(ptr unsafe.Pointer, offset uintptr) unsafe.Pointer`, эмулирующую C-арифметику указателей. Протестируйте на массиве `[5]int`. Объясните правило: *«`uintptr` — это целое число, а не указатель для GC»*.
53. Создайте структуру с полями `bool`, `int32`, `int64`, `byte`. Используя `unsafe.Sizeof`, `unsafe.Alignof` и `unsafe.Offsetof`, выведите layout в памяти (адрес каждого поля). Переставьте поля для минимизации padding и покажите разницу в размере.
54. Напишите generic-функцию (или для конкретных типов), которая через `unsafe` обнуляет любую структуру по указателю (`memset` аналог). Сравните с `reflect.ValueOf(...).Elem().SetZero()` через бенчмарк и объясните разницу в производительности.

### Уровень 2. Внутреннее устройство слайсов, строк и структур
55. Реализуйте `BytesToString(b []byte) string` **без копирования** через `unsafe`. Напишите юнит-тест, который показывает, что изменение исходного `[]byte` (если он mutable) ломает иммутабельность строки. Объясните, когда этот трюк допустим (read-only данные, например, из `mmap`).
56. Реализуйте обратное преобразование — `StringToBytes(s string) []byte` без копирования. Объясните, почему Go не позволяет модифицировать результат (runtime не паникует, но это UB), и как `unsafe` обходит контракт языка.
57. Напишите «визуализатор заголовка слайса»: создайте структуру, дублирующую `reflect.SliceHeader`, и через `unsafe.Pointer` приведите `[]int` к этой структуре. Выведите адрес underlying array, Len и Cap. Объясните, почему `Data` имеет тип `uintptr` в `reflect`, но вы должны работать с `unsafe.Pointer`.
58. Создайте «свой `sync.Map`» на `unsafe`: массив buckets из `unsafe.Pointer`, используйте `atomic.CompareAndSwapPointer` для lock-free вставки. Объясните, почему в `atomic` операциях нельзя использовать `uintptr` — только `unsafe.Pointer`.
59. Реализуйте type punning: прочитайте `uint64` как два `uint32` (младший и старший) через `unsafe`. Покажите результат на little-endian и объясните, почему код будет работать иначе на big-endian (если есть доступ к такой архитектуре).

### Уровень 3. Продвинутые техники и оптимизации
60. Напишите ring buffer на `unsafe`: аллоцируйте `[]byte`, затем используйте `unsafe` для прямого доступа к элементам по индексу без bounds checking. Сравните с обычным `[]byte` через `testing.B`. Объясните, когда компилятор сам убирает bounds check, а когда нет.
61. Создайте «object pool» без `sync.Pool`, используя `unsafe`: выделите большой `[]byte` (arena), разбейте на chunks фиксированного размера, ведите free list через `unsafe.Pointer`. Объясните, почему объекты без указателей не сканируются GC и как это ускоряет аллокацию при фиксированном размере.
62. Реализуйте **tagged pointer**: упакуйте 1-битный флаг в младший бит указателя через `uintptr`. Напишите функции `pack(ptr unsafe.Pointer, flag bool)` / `unpack(packed uintptr)`. Объясните, почему это работает только при alignment ≥ 2 и почему это невозможно сделать без `unsafe`.

### Уровень 4. Опасные паттерны и интеграция
63. Напишите программу, которая демонстрирует **dangling pointer** через `unsafe`: аллоцируйте объект в функции, сохраните `uintptr`, выйдите из функции (стек должен быть уничтожен), затем попытайтесь разыменовать. Объясните, почему это UB, и как moving GC (концептуально, не в текущем Go) делает `uintptr` ещё опаснее.
64. Реализуйте **zero-copy deserialization** для бинарного протокола: читайте файл в `[]byte`, через `unsafe` приводите к структуре (с учётом alignment). Объясните, почему packed structs в C (`#pragma pack`) ломают эту схему, и как `binary.Read` служит безопасным fallback.

## Блок 5. CGO

### Уровень 1. Базовые вызовы и накладные расходы
65. Напишите минимальную программу с `cgo`: вызовите `C.printf` из Go. Объясните магию комментария `// #cgo` и `// #include`. Покажите сгенерированный `_cgo_.go` через `go tool cgo` и найдите функцию-прокси.
66. Напишите C-функцию, которая принимает `int`, `double`, `char*` и возвращает `int`. Создайте Go-обёртки для каждого типа. Объясните правила конвертации: `C.int` vs `int`, `C.CString` и необходимость `C.free` для избежания утечек.
67. Реализуйте «калькулятор» на C с простыми операциями. Соберите как **static library** (`.a`) и слинкуйте через `#cgo LDFLAGS`. Объясните разницу между static и dynamic linking в контексте самодостаточного Go-бинарника.
68. Напишите микробенчмарк на накладные расходы `cgo`: вызов пустой C-функции в цикле 1 млн раз. Сравните с вызовом пустой Go-функции. Объясните, откуда берутся ~100–200 ns (переключение стеков, `runtime·entersyscall`, `pthread` locks, проверки `cgocheck`).

### Уровень 2. Типы, память и границы
69. Создайте C-структуру с вложенными массивами и указателями. Передайте её в Go через `cgo`. Объясните, как Go видит C-структуры (padding, alignment) и почему `unsafe` для доступа к полям не нужен, но `reflect` может понадобиться для сложных layout.
70. Напишите функцию на C, которая аллоцирует память (`malloc`) и возвращает указатель. Go-код должен использовать эту память, затем явно освободить через `C.free`. Объясните, почему Go GC не управляет C-памятью, и как `C.CBytes`/`C.CString` создают копии, чтобы избежать проблем.
71. Реализуйте передачу Go-слайса в C **без копирования**: используйте `&slice[0]` и C-функцию, принимающую `*C.int` и `len`. Объясните, почему нужно держать слайс **pinned** (не давать GC переместить underlying array) и как `runtime.KeepAlive` помогает.
72. Создайте Go-структуру с полем `*C.char`, указывающим на C-строку. Напишите функцию, которая корректно копирует данные в `string` через `C.GoString` и освобождает C-память. Объясните разницу между `C.GoString` (копирует) и прямым использованием C-указателя (zero-copy, но опасно).

### Уровень 3. Безопасность, потоки и обратные вызовы
73. Напишите программу с `cgo`, которая создаёт C-thread (`pthread_create`) из Go. Объясните, почему это опасно: C-thread не знает о Go-scheduler, а Go-signal handler может конфликтовать. Покажите использование `runtime.LockOSThread` для goroutine, работающей с C-thread.
74. Реализуйте **callback** (обратный вызов): C-функция принимает function pointer, Go передаёт `cgo`-экспортированную функцию (`//export`). Объясните механизм: Go создаёт C-функцию-обёртку (`crosscall2`), переключение стеков, и почему callback — самый дорогой путь в `cgo`.
75. Создайте программу, демонстрирующую `CgoCheck`: попытайтесь передать Go-указатель, содержащий внутри себя указатели, в C-функцию. Объясните, почему рантайм паникует (C не может следить за moving GC), и как обойти через `C.CBytes` (глубокое копирование в unmanaged память).

### Уровень 4. Интеграция и сложные сценарии
76. Напишите wrapper для небольшой C++ библиотеки (простой класс) через `extern "C"` интерфейс. Соберите с помощью `g++` и `#cgo LDFLAGS`. Объясните, почему `cgo` напрямую не поддерживает C++ (name mangling, exceptions, ABI).
77. Реализуйте `dlopen`/`dlsym` на чистом Go через `cgo`: загрузите `.so` во время выполнения, найдите символ и вызовите. Объясните разницу с `plugin.Open` и когда нужен ручной `dlopen` (например, опциональные зависимости).
78. Напишите **zero-allocation bridge** между Go и C: используйте разделяемую память (C-аллоцированный `mmap` или ring buffer), через `unsafe` Go читает/пишет без `cgo`-вызовов на каждую операцию. Объясните, как это используется в high-frequency trading для снижения latency.

## Блок 6. Системные вызовы, `mmap` и `epoll`

### Уровень 1. Базовые syscall
79. Напишите программу, которая использует `syscall.Syscall6` для вызова `getpid` (или `getuid`) на Linux. Сравните с `os.Getpid()`. Объясните, почему в Go предпочтительнее пакеты `syscall`/`golang.org/x/sys/unix` вместо прямого inline-asm.
80. Реализуйте «свой `sleep`» через `syscall.Nanosleep`. Объясните, почему raw syscall блокирует ОС-поток, и как Go-планировщик оборачивает это в `time.Sleep` (через `gopark` + timer thread).
81. Напишите программу, которая читает файл через `syscall.Read` (fd от `syscall.Open`). Объясните разницу между buffered I/O (`os.File`, `bufio`) и raw syscall, и почему `os.File` использует внутренний буфер + `syscall` пачками.

### Уровень 2. `mmap` и управление памятью
82. Реализуйте чтение файла через `mmap`: откройте файл, получите fd, вызовите `syscall.Mmap` (или `unix.Mmap`). Прочитайте содержимое как `[]byte` через `unsafe`. Объясните, почему это быстрее `read()` при многократном произвольном доступе.
83. Напишите программу с **anonymous mmap** (`MAP_ANONYMOUS`) для аллокации 1 GB. Объясните, как ОС лениво подкладывает физические страницы (demand paging). Покажите разницу `VSS` vs `RSS` через `/proc/self/status`.
84. Реализуйте «свой allocator» поверх `mmap`: выделите arena, разбейте на fixed-size blocks, ведите free list. Объясните, почему Go runtime не использует `mmap` напрямую для small objects (слишком дорого, нужен page-level granularity).
85. Напишите программу с `mmap` + `mprotect`: выделите страницу, сделайте её read-only (`PROT_READ`), попытайтесь записать — поймайте `SIGSEGV` через `signal.Notify`. Объясните, как это используется для защиты памяти (`W^X`, sandboxing).

### Уровень 3. `epoll` и event loop

87. Напишите программу, демонстрирующую **edge-triggered** (`EPOLLET`) vs **level-triggered** (`EPOLLIN`) `epoll`. Объясните, почему ET требует неблокирующих fd и цикл чтения до `EAGAIN`.

### Уровень 4. Продвинутое системное программирование

## Как интегрировать с предыдущим блоком

**Рекомендуемый порядок прохождения:**

1. **Сначала доведите Блок 1 (GMP) до уровня 3** — без понимания `runtime.LockOSThread`, `gopark` и `entersyscall` вы не поймёте, почему `cgo` и `syscall` такие дорогие.
2. **Затем Блок 4 (unsafe)** — он нужен для Блока 5 (zero-copy bridge) и Блока 6 (mmap → `[]byte` без копирования).
3. **Параллельно Блок 2 (аллокатор)** — чтобы понимать, зачем вам свой allocator на `mmap` (упр. 84), когда Go уже имеет `mcache`.
4. **Блок 5 (cgo)** — после `unsafe`, так как cgo часто требует `unsafe` для передачи слайсов.
5. **Блок 6 (syscall/epoll/mmap)** — в финале, так как это требует понимания всего вышеперечисленного.

**Ключевые инструменты для этих упражнений:**
```bash
go tool cgo -godebug          # посмотреть сгенерированные прокси
strace -e trace=mmap,mprotect,read,write,epoll_wait ./prog
perf stat -e context-switches,cache-misses ./prog
GODEBUG=cgocheck=2              # строгий режим проверки указателей в cgo
```

Если нужно — могу детально расписать **любое конкретное упражнение** с шаблоном кода, или выдать финальный блок на тему *«Каналы в рантайме, netpoller, sync.Pool и runtime timers»*.
