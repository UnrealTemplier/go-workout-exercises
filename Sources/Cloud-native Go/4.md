### Тема 186: Envelope Encryption с KMS
*Envelope Encryption — это паттерн, где данные шифруются DEK (Data Encryption Key), а DEK шифруется KEK (Key Encryption Key) из KMS. Используется в AWS, GCP, Azure для защиты данных at rest.*

2081. **Envelope Encryption концепция:** Изучите 4-шаговый процесс:
    * Generate DEK через KMS
    * Зашифруйте данные через DEK (AES-GCM)
    * Зашифруйте DEK через KMS (KEK)
    * Сохраните encrypted DEK + encrypted data вместе

2082. **AWS KMS setup:** Создайте KMS key в AWS Console или через Terraform. Изучите key policies и IAM permissions.

2083. **AWS KMS Go SDK:** Используйте `github.com/aws/aws-sdk-go-v2/service/kms` для вызова KMS API.

2084. **GenerateDataKey:** Вызовите `kms.GenerateDataKey()` для получения plaintext DEK и encrypted DEK. Plaintext используется для шифрования, encrypted сохраняется.

2085. **Encrypt data with DEK:** Используйте plaintext DEK для шифрования данных через AES-256-GCM:
    ```go
    block, _ := aes.NewCipher(dekPlaintext)
    gcm, _ := cipher.NewGCM(block)
    ciphertext := gcm.Seal(nil, nonce, plaintext, aad)
    ```

2086. **Store encrypted DEK + data:** Сохраните encrypted DEK и encrypted data вместе (например, в S3 object metadata или в БД).

2087. **Decrypt flow:** При чтении:
    * Извлеките encrypted DEK
    * Вызовите `kms.Decrypt()` для получения plaintext DEK
    * Используйте plaintext DEK для дешифрования данных
    * **Важно:** удаляйте plaintext DEK из памяти после использования

2088. **KMS key rotation:** Настройте automatic key rotation в KMS (раз в год). Старые encrypted DEKs остаются валидными, новые данные шифруются новым KEK.

2089. **KMS grants:** Используйте KMS grants для делегирования доступа к ключу другим AWS accounts или services.

2090. **KMS key policies:** Настройте fine-grained key policies: кто может использовать ключ, с каких IP, в какое время.

2091. **CloudTrail для KMS:** Включите CloudTrail для аудита всех KMS API вызовов. Это критично для compliance (PCI DSS, HIPAA).

2092. **GCP Cloud KMS:** Используйте `cloud.google.com/go/kms/apiv1` для GCP KMS. API отличается от AWS, но концепция та же.

2093. **Azure Key Vault:** Используйте `github.com/Azure/azure-sdk-for-go/sdk/keyvault/azkeys` для Azure Key Vault.

2094. **HashiCorp Vault как KMS:** Используйте Vault Transit secrets engine как альтернативу cloud KMS. Это даёт control over keys и on-premise deployment.

2095. **Envelope Encryption для БД:** Шифруйте sensitive columns в PostgreSQL через envelope encryption. DEK per row или per table.

2096. **Envelope Encryption для S3:** Шифруйте S3 objects client-side через envelope encryption перед upload. Это даёт full control over keys (vs S3-managed encryption).

2097. **DEK caching:** Для производительности кэшируйте plaintext DEK в памяти (с TTL). Но помните: при compromise приложения все cached DEKs скомпрометированы.

2098. **DEK per tenant:** Для multi-tenant SaaS используйте отдельный DEK per tenant. Это позволяет crypto-shredding (удаление данных через удаление DEK).

2099. **Crypto-shredding:** Для GDPR "right to be forgotten" удаляйте DEK пользователя. Данные становятся нечитаемыми без физического удаления.

2100. **KMS latency optimization:** KMS вызовы имеют latency 50-200ms. Кэшируйте DEKs, используйте batch operations, минимизируйте KMS calls.

2101. **KMS cost optimization:** KMS charges per API call. Для high-volume используйте DEK caching и batch encryption.

2102. **KMS + HSM:** Для maximum security используйте CloudHSM (AWS) или Cloud HSM (GCP) — dedicated hardware security modules.

2103. **KMS key aliases:** Используйте aliases для key rotation без изменения application code.

2104. **KMS cross-account:** Для multi-account AWS setup используйте cross-account KMS access через key policies.

2105. **Envelope Encryption testing:** Напишите интеграционные тесты, которые:
    * Шифруют данные через envelope encryption
    * Сохраняют в S3
    * Читают из S3
    * Дешифруют
    * Проверяют корректность

2106. **Envelope Encryption + S3 SSE:** Комбинируйте client-side envelope encryption с S3 server-side encryption (SSE-S3 или SSE-KMS) для defense in depth.

2107. **KMS key deletion:** Настройте pending deletion period (7-30 дней) для KMS keys. Это защита от accidental deletion.

2108. **KMS + Secrets Manager:** Используйте Secrets Manager для хранения database credentials, которые шифруются через KMS.

2109. **KMS monitoring:** Мониторьте:
    * KMS API call latency
    * KMS throttling (rate limits)
    * Failed KMS calls (permissions issues)
    * Key usage patterns

2110. **KMS disaster recovery:** Настройте multi-region KMS keys для DR. При failover в другой region используйте replica keys.

### Тема 187: Multipart Upload в S3/GCS
*Для больших файлов (>100MB) используйте multipart upload. Это позволяет параллельную загрузку частей, resume при failure, и обходит 5GB limit для single PUT.*

2111. **Multipart upload basics:** Изучите 3-шаговый процесс:
    * `CreateMultipartUpload` → получить upload ID
    * `UploadPart` для каждой части (min 5MB, max 5GB)
    * `CompleteMultipartUpload` для сборки

2112. **AWS S3 multipart upload:** Используйте `s3manager.Uploader` из AWS SDK для automatic multipart upload:
    ```go
    uploader := s3manager.NewUploader(s3Client)
    result, err := uploader.Upload(&s3manager.UploadInput{
        Bucket: aws.String(bucket),
        Key:    aws.String(key),
        Body:   file,
    })
    ```

2113. **Manual multipart upload:** Реализуйте manual multipart upload для fine-grained control:
    * CreateMultipartUpload
    * UploadPart для каждой части
    * CompleteMultipartUpload

2114. **Parallel part upload:** Используйте `errgroup` для параллельной загрузки частей. Это в 5-10x быстрее sequential upload.

2115. **Part size optimization:** Оптимальный part size: 16-64MB. Меньше — overhead от API calls. Больше — wasted bandwidth при retry.

2116. **Resume failed upload:** При failure сохраняйте upload ID и completed parts. Resume upload через `UploadPartCopy` или повторный `UploadPart` для failed parts.

2117. **Abort incomplete upload:** Используйте `AbortMultipartUpload` для cleanup incomplete uploads. Иначе они занимают место и incur storage costs.

2118. **Lifecycle policy для cleanup:** Настройте S3 lifecycle policy для automatic abort incomplete uploads старше 7 дней.

2119. **Multipart upload + envelope encryption:** Шифруйте каждую part через envelope encryption перед upload. Сохраняйте encrypted DEK per part.

2120. **Multipart upload progress tracking:** Отслеживайте progress: bytes uploaded / total bytes. Экспортируйте в Prometheus.

2121. **Multipart upload rate limiting:** Ограничьте bandwidth для multipart uploads, чтобы не saturate network.

2122. **Multipart upload + checksums:** Вычисляйте checksum (MD5, SHA256) для каждой part. S3 верифицирует checksums при CompleteMultipartUpload.

2123. **Multipart upload + metadata:** Добавляйте custom metadata к multipart upload (например, `x-amz-meta-encrypted-dek`).

2124. **Multipart upload + ACL:** Устанавливайте ACL для multipart upload (например, `private`, `public-read`).

2125. **Multipart upload + storage class:** Указывайте storage class (Standard, Infrequent Access, Glacier) для multipart upload.

2126. **Multipart upload + server-side encryption:** Используйте SSE-S3 или SSE-KMS для server-side encryption multipart uploads.

2127. **GCS multipart upload (composite objects):** GCS использует composite objects вместо multipart upload:
    * Upload parts как отдельные objects
    * `Compose` для объединения в один object
    Изучите отличия от S3.

2128. **GCS resumable upload:** Используйте resumable upload для больших файлов в GCS. Это позволяет resume при network failure.

2129. **Multipart upload benchmarking:** Сравните производительность:
    * Single PUT vs multipart upload
    * Sequential vs parallel parts
    * Разные part sizes
    * Разные concurrency levels

2130. **Multipart upload testing:** Напишите тесты, которые:
    * Загружают 1GB файл через multipart
    * Симулируют network failure mid-upload
    * Resume upload
    * Верифицируют integrity

### Тема 188: Service Mesh — Istio
*Service Mesh (Istio, Linkerd) добавляет observability, security и traffic management в микросервисную архитектуру без изменения application code.*

2131. **Istio setup:** Установите Istio в Kubernetes cluster через `istioctl install`. Изучите компоненты: istiod (control plane), Envoy sidecars (data plane).

2132. **Envoy sidecar injection:** Настройте automatic sidecar injection через `istio-injection=enabled` label на namespace. Каждый pod получает Envoy proxy.

2133. **Istio traffic flow:** Поймите, как трафик течёт:
    * Client → Istio Ingress Gateway → Service A sidecar → Service A
    * Service A → sidecar → Service B sidecar → Service B

2134. **mTLS через Istio:** Настройте automatic mTLS между сервисами через `PeerAuthentication`. Istio автоматически генерирует и ротирует сертификаты.

2135. **Istio VirtualService:** Создайте VirtualService для traffic routing:
    ```yaml
    apiVersion: networking.istio.io/v1beta1
    kind: VirtualService
    spec:
      hosts:
      - myservice
      http:
      - route:
        - destination:
            host: myservice
            subset: v1
          weight: 90
        - destination:
            host: myservice
            subset: v2
          weight: 10
    ```

2136. **Istio DestinationRule:** Создайте DestinationRule для traffic policies:
    * Load balancing (round robin, random, least conn)
    * Connection pool settings
    * Outlier detection (circuit breaker)

2137. **Istio canary deployment:** Реализуйте canary deployment через VirtualService с weight-based routing (90% v1, 10% v2).

2138. **Istio traffic mirroring:** Зеркальте production traffic на staging версию для testing без влияния на пользователей.

2139. **Istio fault injection:** Инжектируйте delays и errors для chaos testing:
    ```yaml
    fault:
      delay:
        percentage:
          value: 10
        fixedDelay: 5s
    ```

2140. **Istio rate limiting:** Настройте rate limiting через Envoy rate limit service.

2141. **Istio retries и timeouts:** Настройте automatic retries и timeouts в VirtualService:
    ```yaml
    retries:
      attempts: 3
      perTryTimeout: 2s
    timeout: 10s
    ```

2142. **Istio circuit breaker:** Настройте circuit breaker через DestinationRule:
    ```yaml
    outlierDetection:
      consecutiveErrors: 5
      interval: 30s
      baseEjectionTime: 30s
    ```

2143. **Istio authorization policies:** Создайте fine-grained authorization policies:
    ```yaml
    apiVersion: security.istio.io/v1beta1
    kind: AuthorizationPolicy
    spec:
      rules:
      - from:
        - source:
            principals: ["cluster.local/ns/default/sa/frontend"]
        to:
        - operation:
            methods: ["GET", "POST"]
    ```

2144. **Istio JWT authentication:** Настройте JWT validation в Istio RequestAuthentication.

2145. **Istio observability:** Используйте Kiali для визуализации service mesh topology, traffic flow, health.

2146. **Istio distributed tracing:** Istio автоматически инжектирует trace headers (x-b3-traceid, x-b3-spanid). Настройте Jaeger/Zipkin для сбора traces.

2147. **Istio metrics:** Istio экспортирует метрики в Prometheus: request count, latency, error rate per service.

2148. **Istio access logs:** Настройте Envoy access logs для detailed request logging.

2149. **Istio performance tuning:** Настройте Envoy concurrency, connection pool size, buffer sizes для optimal performance.

2150. **Istio vs Linkerd:**
    * Istio: более feature-rich, но сложнее
    * Linkerd: проще, быстрее, меньше overhead
    Используйте Linkerd для simpler setups, Istio для complex enterprise requirements.

### Тема 190: Distributed Tracing Context (W3C/B3)
*Для end-to-end tracing через множество сервисов нужно пробрасывать trace context через все boundaries.*

2166. **W3C Trace Context стандарт:** Изучите W3C Trace Context specification:
    * `traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01`
    * `tracestate: congo=t61rcWkgMzE`

2167. **traceparent формат:** Разберите формат:
    * Version (2 hex chars)
    * Trace ID (32 hex chars)
    * Parent ID (16 hex chars)
    * Trace flags (2 hex chars)

2168. **B3 headers (Zipkin):** Изучите B3 headers (используются в Istio):
    * `X-B3-TraceId`
    * `X-B3-SpanId`
    * `X-B3-ParentSpanId`
    * `X-B3-Sampled`

2169. **Context propagation в HTTP:** При исходящем HTTP request инжектируйте trace headers:
    ```go
    req, _ := http.NewRequest("GET", url, nil)
    otel.GetTextMapPropagator().Inject(ctx, propagation.HeaderCarrier(req.Header))
    ```

2170. **Context extraction в HTTP:** При входящем HTTP request извлекайте trace context:
    ```go
    ctx := otel.GetTextMapPropagator().Extract(r.Context(), propagation.HeaderCarrier(r.Header))
    ```

2171. **Context propagation в gRPC:** Используйте gRPC interceptors для автоматической propagation:
    ```go
    otelgrpc.UnaryClientInterceptor()
    otelgrpc.UnaryServerInterceptor()
    ```

2172. **Context propagation в Kafka:** Пробрасывайте trace context через Kafka headers:
    ```go
    msg.Headers = append(msg.Headers, kafka.Header{
        Key:   "traceparent",
        Value: []byte(traceparent),
    })
    ```

2173. **Context propagation в NATS:** Используйте NATS headers для trace context propagation.

2174. **Context propagation в RabbitMQ:** Используйте RabbitMQ message headers для trace context.

2175. **Multi-format propagation:** Поддерживайте оба формата (W3C и B3) для compatibility с разными systems:
    ```go
    propagator := propagation.NewCompositeTextMapPropagator(
        propagation.TraceContext{},  // W3C
        propagation.Baggage{},
        b3.New(b3.WithInjectEncoding(b3.B3MultipleHeader)),
    )
    ```

2176. **Trace context в logs:** Добавляйте trace_id и span_id в каждый log entry для correlation:
    ```go
    span := trace.SpanFromContext(ctx)
    logger.Info("processing request",
        "trace_id", span.SpanContext().TraceID(),
        "span_id", span.SpanContext().SpanID(),
    )
    ```

2177. **Trace context в metrics:** Добавляйте trace_id как label в Prometheus metrics для drill-down из metrics в traces.

2178. **Trace sampling:** Настройте sampling strategy:
    * Always sample errors
    * Sample 1% of successful requests
    * Tail-based sampling для interesting traces

2179. **Trace context validation:** Валидируйте trace headers при extraction. Reject invalid headers.

### 💡 Золотые правила cloud-native архитектуры:

1. **Envelope Encryption — это standard.** Никогда не храните plaintext keys в приложении. Используйте KMS для KEK, DEK для data encryption. Это даёт key rotation без re-encryption данных.

2. **Multipart Upload для файлов >100MB.** Single PUT имеет 5GB limit и не поддерживает resume. Multipart upload даёт parallel upload, resume при failure, и обходит size limits.

3. **Service Mesh для cross-cutting concerns.** mTLS, traffic management, observability — всё это должно быть в service mesh, а не в application code. Istio для enterprise, Linkerd для simplicity.

4. **Distributed Tracing Context обязателен.** Без trace context propagation вы не сможете отладить request, который проходит через 5+ сервисов. W3C Trace Context — это standard.

5. **Context propagation через все boundaries.** HTTP headers, gRPC metadata, Kafka headers, NATS headers — везде пробрасывайте trace context. Иначе trace обрывается.

6. **Trace ID в логах и метриках.** Каждый log entry и metric должен содержать trace_id. Это позволяет drill-down из Grafana в Jaeger в Kibana.

7. **mTLS между всеми сервисами.** В Zero Trust архитектуре нет trusted network. Каждый сервис аутентифицирует другие через сертификаты. Service mesh делает это автоматически.

8. **Graceful Shutdown — это закон.** При SIGTERM:
    * Stop accepting new requests
    * Wait for in-flight requests to complete (с timeout)
    * Close database connections
    * Flush buffers
    * Exit cleanly

9. **gRPC Keepalive для dead connection detection.** Без keepalive dead connections могут висеть часами, consuming resources. Настройте keepalive time (10-30s) и timeout (5-10s).

10. **Connection Draining при deployment.** При rolling update старые pods должны drain'ить connections перед termination. Иначе requests будут dropped.

11. **Canary Deployments через Service Mesh.** Никогда не деплойте сразу на 100% трафика. Используйте Istio VirtualService для weight-based routing (90% v1, 10% v2).

12. **Circuit Breakers в Service Mesh.** Istio DestinationRule с outlier detection автоматически circuit break'ит failing services. Это защищает от cascade failures.

13. **Retries с exponential backoff.** Настройте retries в Istio VirtualService. Но добавьте jitter для предотвращения retry storms.

14. **Rate Limiting per client.** Защищайте сервисы от abuse через rate limiting. Istio + Envoy rate limit service даёт distributed rate limiting.

15. **Fault Injection для chaos testing.** Istio позволяет инжектировать delays и errors для testing resilience. Делайте это регулярно в staging.

16. **Observability из коробки.** Service mesh автоматически даёт:
    * Distributed traces
    * Request metrics (count, latency, error rate)
    * Access logs
    * Service topology visualization
    
    Используйте это, не изобретайте своё.

17. **KMS key rotation.** Настройте automatic key rotation в KMS. Старые encrypted DEKs остаются валидными, новые данные шифруются новым KEK.

18. **Crypto-shredding для GDPR.** Для "right to be forgotten" удаляйте DEK пользователя. Данные становятся нечитаемыми без физического удаления из БД.

19. **S3 Lifecycle policies.** Настройте automatic abort incomplete multipart uploads, transition to Infrequent Access/Glacier, expiration старых objects.

20. **Test disaster recovery.** Регулярно тестируйте:
    * KMS key compromise response
    * S3 bucket recovery из backup
    * Service mesh failover при control plane failure
    * Multi-region failover
