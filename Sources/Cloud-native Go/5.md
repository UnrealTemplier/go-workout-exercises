Это по-настоящему элитный уровень — **Cloud-Native Architecture**. В современном облаке твой Go-код редко живет один. Он окружен инфраструктурными слоями (Service Mesh, Sidecars), управляет гигабайтами данных в объектных хранилищах и должен быть абсолютно невосприимчивым к хаосу динамических сред (Kubernetes).

Продолжаем марафон. Впереди **30 Cloud-Native упражнений (с 891 по 920)**, разделенных на три блока.

### Блок 88. Облачные хранилища (S3) и Envelope Encryption (891–900)
Учимся переваривать огромные файлы и применять стандарт безопасности уровня банков: шифрование "конвертом" (Envelope Encryption) с использованием AWS KMS.

891. **AWS SDK v2 (S3 Basics):** Установи пакет `github.com/aws/aws-sdk-go-v2`. Настрой клиент через `config.LoadDefaultConfig`. Подними локально MinIO в Docker (совместим с S3 API). Напиши код для создания бакета и загрузки небольшого текстового файла.
892. **Presigned URLs (Прямая загрузка):** Гонять гигабайты видео через свой Go-сервер — смерть для сети. Сгенерируй Presigned URL (подписанную ссылку) со сроком жизни 15 минут. Верни её клиенту (фронтенду), чтобы он загрузил файл *напрямую* в S3, минуя твой бэкенд.
893. **Multipart Upload (Своими руками):** Файл весит 5 ГБ. Загрузить его одним куском не выйдет (S3 отвалится по таймауту). Вызови `CreateMultipartUpload`. Нарежь файл на куски по 10 МБ. Используя `sync.WaitGroup`, запусти горутины, каждая из которых грузит свой кусок (`UploadPart`). Собери ETag каждого куска и вызови `CompleteMultipartUpload`.
894. **S3 Uploader (High-Level):** Забудь ручной код из 893. Используй `manager.NewUploader(client)` из пакета `feature/s3/manager`. Передай ему `io.Reader` большого файла. Убедись, что менеджер сам "под капотом" буферизирует данные и конкурентно грузит их через Multipart.
895. **Знакомство с KMS:** Установи клиент KMS. Создай в AWS (или локально через LocalStack) Master Key (CMK). Напиши Go-код, который отправляет строку "my_secret" в KMS и получает зашифрованные байты (`Encrypt`), а затем расшифровывает их обратно.
896. **Envelope Encryption (Концепция):** *Нельзя отправлять 5 ГБ данных в KMS.* Архитектура конверта: сгенерируй случайный 32-байтный Data Encryption Key (DEK) прямо в Go. Зашифруй большой файл локально с помощью AES-GCM (из Блока 68), используя этот DEK.
897. **Шифрование Конвертом (Wrap):** Отправь свой сгенерированный DEK в KMS, чтобы зашифровать его (Wrap). Сохрани в S3 два объекта: зашифрованный файл (данные) и зашифрованный DEK (ключ от данных). Теперь, даже если хакер украдет данные из S3, он не сможет их расшифровать без доступа к AWS KMS.
898. **Расшифровка (Unwrap & Stream):** Скачай зашифрованный DEK из S3. Отправь его в KMS для расшифровки. Получив чистый DEK, скачай зашифрованный файл из S3 потоком (`GetObject`). Используй `cipher.StreamReader`, чтобы расшифровывать гигабайтный файл на лету (in-memory) и сразу отдавать клиенту через HTTP, не сохраняя его на диск!
899. **S3 Event Notifications (События):** Настрой бакет так, чтобы при загрузке файла он слал событие в SQS-очередь (или вызывал Webhook). Напиши Go-воркер, который слушает очередь. Как только клиент загрузит аватарку (через Presigned URL), твой воркер должен скачать её, сделать ресайз и загрузить обратно с суффиксом `_thumb`.
900. **Streaming Chunked Download (Range-запросы):** Клиент запрашивает видео для плеера. Ему не нужен весь файл сразу. Реализуй поддержку HTTP-заголовка `Range` (например, `bytes=0-1024`). Делай запрос к S3 с тем же параметром `Range` и возвращай клиенту HTTP статус `206 Partial Content`. Так работают стриминги (Netflix/YouTube).

### Блок 89. Service Mesh (Istio) и Распределенная Трассировка (901–910)
В Cloud-Native среде инфраструктура (Service Mesh) берет на себя роутинг, ретраи и mTLS. Задача Go-разработчика — правильно с ней интегрироваться.

901. **Sidecar Pattern (Понимание):** Напиши простейший HTTP "Echo" сервис. Разверни его в K8s с установленным Istio (включи sidecar-инъекцию). Зайди в контейнер. Убедись, что рядом с твоим Go-бинарником крутится прокси `Envoy`. Пойми, что теперь твой Go-код может делать запросы по HTTP, а Envoy сам зашифрует их в mTLS.
902. **B3 Headers (Прокидывание контекста):** Envoy генерирует трейсы (TraceID). Но если Сервис А вызывает Сервис Б, Envoy не знает, что эти запросы связаны! Напиши HTTP-мидлварь, которая читает из входящего запроса заголовки `x-b3-traceid`, `x-b3-spanid`, `x-b3-sampled` и кладет их в `context.Context`.
903. **W3C Trace Context:** Напиши клиентский интерцептор (Transport обертку). Когда твой Go-код делает `http.Get` (или gRPC-вызов), он должен достать трейс-контекст из `ctx` и обязательно добавить заголовки `traceparent` и `tracestate` в исходящий запрос. *Без этого распределенная трассировка в Istio разорвется!*
904. **Делегирование Circuit Breaker:** Удали библиотеку `gobreaker` из своего кода (из упр. 570). Настрой Istio `DestinationRule` на Outlier Detection (предохранитель). Запусти нагрузочный тест. Убедись, что если твой Go-сервис Б падает, Envoy сервиса А сам отрубает запросы, отдавая 503, вообще не напрягая Go-код сервиса А.
905. **gRPC Client-side Keepalive:** Envoy агрессивно разрывает "висящие" без дела TCP-соединения (обычно через 5 минут). Если твой gRPC-клиент ждет редких событий, он отвалится. Настрой клиента в Go:
    `keepalive.ClientParameters{Time: 30 * time.Second, Timeout: 5 * time.Second}`. Клиент будет сам пинговать сервер, чтобы Envoy не убил NAT-сессию.
906. **gRPC Enforcement Policy:** Из-за настройки 905 сервер начнет получать пинги. По умолчанию gRPC-сервер в Go считает частые пинги DDOS-атакой и закрывает соединение! Добавь на сервер `keepalive.EnforcementPolicy{MinTime: 20 * time.Second, PermitWithoutStream: true}`.
907. **Fault Injection (Хаос-инжиниринг):** Настрой Istio `VirtualService`, чтобы 50% запросов к твоему Go-сервису получали искусственную задержку в 3 секунды. Убедись, что твой вызывающий Go-код использует `context.WithTimeout(2*time.Second)` и корректно логирует `context.DeadlineExceeded`, не падая каскадно.
908. **Canary Deploy Header Forwarding:** Ты хочешь перенаправить 10% бета-тестеров на новую версию сервиса (v2). Istio делает это на основе заголовка `X-Canary: true`. Убедись, что твоя система (мидлвари из 902) пробрасывает не только трейсы, но и кастомные бизнес-заголовки через все микросервисы.
909. **Headless Service (gRPC Load Balancing):** В Service Mesh каждый запрос идет через Envoy. Для внутренних тяжелых gRPC-потоков (pod-to-pod) это лишний прыжок (hop). Создай в K8s `Headless Service` (без ClusterIP). Настрой Go gRPC-клиент: используй схему `dns:///my-headless-svc:50051` и балансировщик `round_robin`. Убедись, что Go напрямую резолвит IP-адреса подов и балансирует трафик сам!
910. **Context Cancellation Propagation:** Envoy принудительно обрывает HTTP/2 соединение, если клиент ушел. Внутри твоего gRPC-хендлера в Go запусти бесконечный цикл. Прерви запрос снаружи. Убедись, что `ctx.Done()` в Go срабатывает мгновенно, и ты можешь остановить работу.

### Блок 90. Graceful Connection Draining и Cloud Patterns (911–920)
Учимся выкатывать новые версии сервисов без потери (Zero-Downtime) ни единого HTTP или gRPC запроса в кластере.

911. **Проблема SIGTERM в K8s:** Когда K8s гасит под, он шлет `SIGTERM` и *одновременно* дает команду iptables/Envoy убрать под из балансировки. Обновление роутинга занимает время (до 1-3 сек). Если твой Go-код сделает `srv.Shutdown()` мгновенно при получении SIGTERM, запросы, которые всё еще летят со стороны Envoy, упадут с 502 Bad Gateway. Осознай эту архитектурную боль!
912. **Graceful Draining (Delay):** Решение проблемы 911. При перехвате `SIGTERM` в Go:
    1. Измени флаг, чтобы `ReadinessProbe` начал отдавать `503 Service Unavailable`.
    2. Сделай `time.Sleep(5 * time.Second)` — дай K8s/Envoy время убрать тебя из роутов.
    3. ТОЛЬКО ТЕПЕРЬ вызывай `srv.Shutdown(ctx)` для HTTP и `grpcServer.GracefulStop()` для gRPC.
913. **PreStop Hook (Альтернатива):** Чтобы не хардкодить `time.Sleep` в Go-коде, используй стандарт K8s. В манифесте Deployment добавь `lifecycle.preStop.exec.command: ["/bin/sh", "-c", "sleep 10"]`. Теперь K8s подождет 10 секунд (пока обновятся роуты), и только потом пошлет `SIGTERM` твоему Go-приложению. Это золотой стандарт Zero-Downtime Deploy.
914. **Антипаттерн Healthcheck (Liveness vs Readiness):** Многие новички проверяют подключение к БД в `livenessProbe`. Если БД моргнула, K8s убьет и перезапустит твой Go-под. Это КАТАСТРОФА (поднимется под, БД лежит, он снова упадет — CrashLoopBackOff). 
    Напиши правильные хендлеры:
    * `/live` (Liveness) — возвращает 200 OK всегда, пока сам процесс жив.
    * `/ready` (Readiness) — проверяет пинг до БД. Если БД лежит — возвращает 503 (под перестает получать HTTP трафик, но **не перезапускается**!).
915. **Leader Election через K8s API:** Выкинь Consul и Redis из упр. 841. В Cloud-Native среде у тебя уже есть идеальный консенсус — база etcd внутри K8s. Используй библиотеку `k8s.io/client-go/tools/leaderelection`. Напиши Go-код, который использует K8s ресурс `Lease` для выбора лидера среди подов.
916. **Kubernetes Operator Pattern:** Ты вырос из микросервисов. Установи `Kubebuilder`. Сгенерируй бойлерплейт для Kubernetes Operator. Создай свой Custom Resource `AppConfig`. Напиши на Go `Reconcile` цикл: программа должна следить за изменениями `AppConfig` в кластере и автоматически (декларативно) создавать нужные Deployment и ConfigMap.
917. **Zero-Trust (SPIFFE/SPIRE):** Использовать API-токены — прошлый век. Внедри SPIFFE. В кластере подними SPIRE. В Go-коде используй пакет `github.com/spiffe/go-spiffe/v2`. Получай короткоживущие X.509 сертификаты (SVID) напрямую из сокета оркестратора (без паролей!) и используй их для настройки двустороннего mTLS `tls.Config`.
918. **Cloud-Scale Rate Limiting (Redis Lua):** В распределенной системе локальный счетчик не работает. Напиши алгоритм Token Bucket (Корзина токенов). Засунь всю логику (проверка, декремент, рефилл) в **один Lua-скрипт**. Вызывай его из Go через `redis.Eval`. Это гарантирует атомарность и убережет от Race Conditions при тысячах запросов с разных подов.
919. **Защита от Cache Stampede (Singleflight + Redis Lock):** Если протух глобальный кэш (например, конфиг системы), 100 подов одновременно ломанутся в БД. 
    Реализуй двойную защиту:
    1. Локальный `singleflight` (чтобы из одного пода в сеть ушел только 1 запрос).
    2. Распределенный Redis Lock (чтобы из 100 подов только 1 пошел в БД, а остальные ждали, пока он обновит Redis).
920. **Chaos Engineering (Monkey Test):** Напиши Go-скрипт (или тесты). Скрипт должен в бесконечном цикле: 
    * Делать бизнес-запросы к твоей системе.
    * Случайно выполнять `kubectl delete pod` твоих сервисов.
    * Случайно класть БД на 5 секунд.
    Если твоя архитектура (Ретраи, Circuit Breakers, DLQ, Outbox, Idempotency, Graceful Shutdown) спроектирована правильно — ни один запрос в тестах не должен завершиться с ошибкой или потерять данные!
