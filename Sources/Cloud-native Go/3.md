Облачные архитектуры и Service Mesh (Cloud-Native) — это реальность современного production-а. Когда ты деплоишь микросервисы в Kubernetes с Istio, твой код должен уметь правильно отдавать трассировки (чтобы они склеивались с Envoy-прокси), корректно закрывать долгоживущие gRPC соединения и шифровать гигабайты данных, не перегружая центральный процессор.

### Блок 108: Облачное хранилище и Envelope Encryption (KMS + S3)
*Цель: Безопасно хранить терабайты данных в облаке, не нагружая KMS, и загружать огромные файлы без Out-Of-Memory.*

955. **[S3 Baseline]** Используй AWS SDK v2 для Go (`github.com/aws/aws-sdk-go-v2`). Подними LocalStack или MinIO в Docker. Загрузи небольшой текстовый файл в бакет (`s3.PutObject`) и скачай его обратно.
956. **[Multipart Upload]** Напиши загрузчик больших файлов (> 100MB). Используй `s3.NewMultipartUploader`. Разбей файл на части по 5MB, загрузи их конкурентно (через горутины), затем вызови `CompleteMultipartUpload`.
957. **[Каверзный кейс — Abort Multipart Upload]** Если во время загрузки 5-й части пропало соединение, вызови `AbortMultipartUpload`. Если этого не сделать, "висящие" части останутся в S3 и будут тарифицироваться. Напиши cron-job, который вызывает `ListMultipartUploads` и удаляет загрузки старше 1 часа.
958. **[Envelope Encryption — Концепция]** Изучи паттерн: данные шифруются локальным симметричным ключом (AES-GCM), а сам локальный ключ шифруется облачным асимметричным ключом (KMS). В БД сохраняется только зашифрованный локальный ключ (Ciphertext Blob) и зашифрованные данные.
959. **[Интеграция KMS]** Сгенерируй KMS Key в AWS (или эмулируй в LocalStack). Используй `kms.GenerateDataKey` (вернет открытый ключ и зашифрованный ключ).
960. **[Шифрование и загрузка]** Зашифруй 50MB файл с помощью открытого Data Key (AES-GCM). Загрузи файл в S3. В метаданные объекта (`Metadata`) положи зашифрованный Data Key.
961. **[Расшифровка]** Скачай файл из S3. Достань зашифрованный Data Key из метаданных. Вызови `kms.Decrypt`, чтобы получить открытый ключ. Расшифруй файл локально.
962. **[Высокая сложность — Streaming Encryption]** Перепиши предыдущее задание так, чтобы не загружать весь файл в память. Читай файл чанками по 64KB, шифруйте их через `cipher.NewGCMEncryptor` (обновляя nonce-счетчик) и стримьте напрямую в `s3.NewMultipartUploader` через `io.Pipe`.

### Блок 109: Service Mesh (Istio/Linkerd) и Распределенный контекст
*Цель: Заставить Go-приложение "дружить" с sidecar-прокси (Envoy), корректно прокидывая трассировки и метрики.*

963. **[W3C Trace Context]** Напиши HTTP middleware, которое читает заголовок `traceparent` (формат: `version-trace-id-parent-id-trace-flags`). Извлеки `trace-id` и выведи в лог. Если заголовка нет — сгенерируй свой.
964. **[B3 Propagation]** Istio/Zipkin часто использует заголовки B3 (`X-B3-TraceID`, `X-B3-SpanID`). Напиши middleware, которое умеет читать и W3C, и B3, и конвертировать одно в другое при исходящем запросе.
965. **[Каверзный кейс — Header Stripping]** Envoy (Istio sidecar) сам генерирует метрики и трассировки. Если твое Go-приложение тоже шлет трассировку, может возникнуть дублирование или разрыв трейсов. Настрой OpenTelemetry так, чтобы он использовал контекст, переданный от Envoy (через `traceparent`), и не создавал новый корневой спан, если `traceparent` уже есть.
966. **[Istio DestinationRule (Circuit Breaker)]** Настрой Istio `DestinationRule` с лимитом: максимум 1 запрос на соединение, остальные ставить в очередь. Напиши Go-клиент, который делает 10 параллельных запросов. Используй `golang.org/x/time/rate` (Rate Limiter) на стороне клиента, чтобы не получать 503 от Envoy.
967. **[Istio Retry & Timeout]** Настрой VirtualService: если сервис вернул `5xx`, Envoy сделает 3 ретрая с таймаутом 2 секунды. В Go-коде НЕ реализуй ретраи (чтобы избежать двойных ретраев — "retry amplification"). Сымитируй 500 ошибку и посмотри в логах Envoy, как он сам повторяет запрос.
968. **[mTLS Verification]** Включи строгую mTLS политику (`PeerAuthentication: STRICT`) в Istio. Сделай запрос к твоему Go-сервису из другого пода. В Go-коде ничего менять не нужно (sidecar проксирует трафик). Попробуй обратиться к сервису в обход sidecar (например, через `kubectl port-forward` напрямую к порту пода) — поймай ошибку TLS.
969. **[Custom Metrics (Istio Telemetry)]** Настрой Istio на отправку кастомных метрик (например, количество заказов в корзине) из HTTP-заголовка `X-Order-Count`. Прочитай этот заголовок в Prometheus.

### Блок 110: Продвинутый gRPC (Keepalive, Connection Draining)
*Цель: Управлять жизненным циклом TCP-соединений в gRPC, чтобы избежать дедлоков и утечек ресурсов при деплое новых версий.*

970. **[Server-side Keepalive]** Настрой gRPC сервер с `keepalive.ServerParameters` (`MaxConnectionIdle: 5m`, `MaxConnectionAge: 10m`). Объясни, зачем это нужно (заставить клиентов переподключаться, чтобы балансировщик нагрузки (Envoy/L4 LB) пересчитал веса).
971. **[Client-side Keepalive]** Настрой gRPC клиент с `keepalive.ClientParameters` (`Time: 10s`, `Timeout: 5s`, `PermitWithoutStream: true`). Объясни, как PING/PONG кадры предотвращают закрытие соединения NAT-шлюзами или Cloud Load Balancer'ами (AWS NLB имеет idle timeout 350 сек).
972. **[Каверзный кейс — GOAWAY Frames]** Сервер решил закрыть соединение (сработал `MaxConnectionAge`). Он шлет клиенту кадр `GOAWAY` (HTTP/2). Напиши обработчик на стороне клиента `grpc.WithDefaultServiceConfig(...)`, который при получении `GOAWAY` должен прозрачно переподключиться к другому бэкенду, не уронив текущий стриминг или запрос.
973. **[Graceful Connection Draining]** В `main()` перехвати `SIGTERM`. Вызови `server.GracefulStop()`. Убедись, что сервер перестает принимать *новые* соединения, но дорабатывает *текущие* активные стримы.
974. **[Каверзный кейс — gRPC + Kubernetes]** K8s отправляет `SIGTERM` и *сразу* удаляет Pod из Endpoints (Service). Но Envoy sidecar может еще 5 секунд слать трафик на умирающий Pod, получая `connection refused`. Настрой в K8s `preStop` hook (`sleep 5`), чтобы дать Envoy время узнать об удалении Pod'а до того, как Go-процесс начнет shutdown.
975. **[Draining Long-lived Streams]** У тебя есть bidirectional stream, который держит соединение часами. `GracefulStop()` будет висеть вечно, дожидаясь его закрытия. Реализуй механизм: при получении `SIGTERM` отправляй всем активным стримам специальное сообщение `ServerShuttingDownError`, заставляя клиентов инициировать разрыв соединения.
976. **[Connection Pooling (Custom)]** Стандартный gRPC клиент держит 1 TCP-соединение на хост. Напиши кастомный `grpc.Resolver` и `grpc.Balancer`, который открывает N (например, 3) TCP-соединений к одному и тому же поду для увеличения пропускной способности (полезно для очень тяжелых streaming-сервисов).
977. **[Header Delayed Sending]** В gRPC ты можешь отправить заголовки ДО тела ответа. Используй `grpc.SetHeader(ctx, metadata.Pairs("x-cache", "HIT"))` в начале обработчика и `grpc.SendHeader` перед началом стриминга. Настрой Envoy/Linkerd на чтение этого заголовка для принятия решений о кэшировании.
978. **[Финальное испытание — Cloud-Native gRPC Service]**
    Разверни микросервис в локальном K8s (Minikube + Istio):
    - **Приложение:** gRPC сервер с методами Unary и Server Streaming.
    - **Трассировки:** OpenTelemetry SDK читает `traceparent` от Istio Ingress Gateway, создает дочерние спаны, прокидывает их в gRPC вызовы к зависимому сервису.
    - **Безопасность:** При чтении файлов из S3 используется Envelope Encryption (AWS KMS). Данные кэшируются в памяти, ключи в Redis.
    - **Сетевая стабильность:** Настроены gRPC Keepalive (клиент и сервер).
    - **Деплой:** При `kubectl delete pod` срабатывает `preStop: sleep 5`, затем Go-код ловит `SIGTERM`, рассылает `GOAWAY` стримам, вызывает `GracefulStop()`, закрывает пул Redis и завершается без единой 5xx ошибки в логах Istio.
