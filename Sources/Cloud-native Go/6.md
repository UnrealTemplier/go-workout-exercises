### Раздел 49: Облачные архитектуры и Service Mesh (Cloud-Native Go) (Задачи 641–655)

#### Подраздел 49.1: Облачные хранилища и шифрование конвертов (Задачи 641–645)

*Envelope Encryption (шифрование конвертов) сочетает скорость симметричного шифрования и безопасность централизованного управления ключами в облаке.*

641. **Шифрование конвертов (Envelope Encryption) с KMS**: 
    * Объясните в комментариях концепцию шифрования конвертов: почему мы не отправляем файлы размером в гигабайты напрямую в Key Management Service (KMS) облачного провайдера для шифрования (ограничения сетевого трафика и лимиты размера данных KMS).
    * Напишите код интеграции с AWS KMS (или GCP KMS) с использованием официального AWS SDK для Go.
    * Вызовите метод `GenerateDataKey` [641]. Получите локальный ключ шифрования данных (DEK) в открытом и зашифрованном (KMS) виде [641].
    * Зашифруйте тестовую строку с помощью DEK (симметричный алгоритм AES-GCM) [641].
    * Удалите открытый DEK из памяти, сохранив зашифрованный DEK рядом с зашифрованными данными.
642. **Потоковое шифрование (Streaming Envelope Encryption)**: При обработке терабайтных бэкапов мы не можем держать данные в оперативной памяти. Напишите Go-код, который принимает `io.Reader` исходного файла, читает его чанками, шифрует каждый чанк "на лету" с помощью DEK в режиме потокового шифра (например, AES-CFB или AES-GCM со смещением nonce) и записывает результат в выходной `io.Writer`.
643. **Многокомпонентная загрузка с шифрованием (Multipart Upload в S3)**: Используя AWS SDK v2 для Go, реализуйте загрузку большого файла в бакет S3 по частям (Multipart Upload) [643]. Каждый чанк (минимальный размер 5 МБ по требованиям S3) должен шифроваться локальным DEK (из задачи №641) непосредственно перед отправкой в S3 [643]. Обеспечьте вызов `CompleteMultipartUpload` при успешной отправке всех зашифрованных частей [643].
644. **Предотвращение утечек незавершенных загрузок (Abort Upload)**: Напишите код обработки ошибок для задачи №643. Если при загрузке одного из чанков в S3 произошел сбой, программа должна гарантированно вызвать метод `AbortMultipartUpload` [643]. Напишите подробный комментарий, объясняющий финансовые риски игнорирования этого шага (S3 продолжит бессрочно хранить недозагруженные части файла на дисках и тарифицировать их, так как они не видны в стандартном списке объектов бакета).
645. **Абстракция над Cloud Storage (S3 / GCS)**: Напишите интерфейс-абстракцию `BlobStorage` с методами `Upload(ctx context.Context, key string, r io.Reader) error` и `Download(ctx context.Context, key string) (io.ReadCloser, error)`. Реализуйте две конкретные структуры-адаптера: одна для AWS S3, вторая для Google Cloud Storage (GCS). Продемонстрируйте бесшовную замену облачного провайдера в вашей бизнес-логике.

#### Подраздел 49.2: Интеграция с Service Mesh и контекст трассировки (Задачи 646–650)

*Service Mesh (Istio, Linkerd) берет на себя маршрутизацию, mTLS и сбор метрик, но требует от Go-приложения корректной передачи контекста трассировок по сети.*

646. **Принципы работы Service Mesh (Sidecar pattern)**: Напишите подробный архитектурный комментарий, объясняющий роль Envoy Sidecar-прокси в Istio/Linkerd [646]. Опишите, как прокси перехватывает весь входящий и исходящий трафик пода, автоматически обеспечивая взаимный TLS (mTLS), балансировку и ретраи, и почему разработчику Go-бэкенда больше не нужно настраивать mTLS-сертификаты внутри кода приложения [646].
647. **Распространение контекста B3 (B3 Propagation)**: Некоторые устаревшие системы и Service Mesh используют формат заголовков B3 (разработанный Zipkin). Напишите HTTP-middleware в Go, которое парсит заголовки B3 (`X-B3-TraceId`, `X-B3-SpanId`, `X-B3-Sampled`) из входящего запроса, сохраняет их в контексте и автоматически добавляет их в качестве заголовков во все исходящие HTTP/gRPC запросы к другим микросервисам для поддержания сквозной трассировки в Istio.
648. **Распространение контекста W3C Trace Context**: Современный стандарт W3C (`traceparent`, `tracestate`) поддерживается OpenTelemetry по умолчанию. Напишите код интеграции W3C-распространителя (Propagator) в ваши HTTP и gRPC клиенты в Go. Настройте автоматическую передачу `traceparent` заголовков во все исходящие сетевые запросы.
649. **Канареечные релизы (Canary Deployments) и заголовки маршрутизации**: Istio использует HTTP-заголовки для интеллектуального разделения трафика. Напишите Go HTTP-клиент, который при выполнении межсервисных запросов автоматически пробрасывает заголовок `X-Beta-User` или версию API, если этот заголовок присутствовал во входящем запросе от внешнего пользователя. Объясните, как это помогает Istio направлять часть запросов на canary-версии ваших подов.
650. **Идентификация клиентов через SPIFFE ID**: В Service Mesh шифрование mTLS обеспечивается sidecar-прокси. Однако само приложение на Go может хотеть знать информацию о сертификате клиента для авторизации (например, SPIFFE ID). Напишите HTTP-обработчик в Go, который извлекает метаданные mTLS-сертификата (например, из заголовка `X-Forwarded-Client-Cert`, добавляемого Envoy) и проверяет права доступа на основе SPIFFE ID клиента.

#### Подраздел 49.3: gRPC Client-side Keepalive и Graceful Connection Draining (Задачи 651–655)

*gRPC работает поверх HTTP/2, удерживая постоянные TCP-соединения. Это создает проблемы с балансировкой нагрузки в Kubernetes, которые решаются тонкими сетевыми настройками.*

651. **Проблема зависших соединений за L4-балансировщиком**: Напишите архитектурный комментарий, объясняющий проблему балансировки gRPC в K8s [651]. Почему при масштабировании количества реплик gRPC-сервера вверх или вниз стандартный балансировщик L4 (K8s Service ClusterIP) не может перераспределить существующий трафик (так как gRPC удерживает долгоиграющие TCP-соединения, и все запросы от клиента продолжают идти на один и тот же под) [651].
652. **Настройка gRPC Client-side Keepalive**: Настройте параметры Keepalive на стороне вашего gRPC-клиента в Go с помощью `grpc.WithKeepaliveParams` [652]. Установите отправку фоновых пингов (`KeepaliveParameters` из пакета `google.golang.org/grpc/keepalive`) [652]:
    ```go
    keepalive.ClientParameters{
        Time:                10 * time.Second, // отправлять пинг каждые 10 секунд
        Timeout:             2 * time.Second,  // ждать ответ на пинг 2 секунды
        PermitWithoutStream: true,             // разрешить пинги даже без активных стримов
    }
    ```
    Объясните, как это помогает вовремя обнаруживать "мертвые" TCP-соединения, оборванные промежуточным роутером или файрволом без явного закрытия сокета.
653. **Защита сервера от частых пингов (Keepalive Enforcement)**: Чтобы клиенты не забивали сервер бесконечными пингами (DDoS-эффект), настройте на стороне gRPC-сервера политику `EnforcementPolicy` [653]:
    ```go
    keepalive.EnforcementPolicy{
        MinTime:             5 * time.Second, // минимальный интервал между пингами от клиента
        PermitWithoutStream: true,            // разрешить пинги без активных стримов
    }
    ```
    Объясните, почему при нарушении этого правила сервер принудительно разорвет соединение, отправив GOAWAY-фрейм с кодом ошибки `ENHANCE_YOUR_CALM` [653].
654. **Плавный сброс соединений (Graceful Connection Draining)**: Чтобы K8s мог равномерно перераспределять нагрузку между подами gRPC-сервера, заставьте клиентов периодически переподключаться. Настройте на сервере параметры `MaxConnectionAge` и `MaxConnectionAgeGrace` [654]:
    ```go
    keepalive.ServerParameters{
        MaxConnectionAge:      30 * time.Minute, // закрывать TCP-соединение через 30 минут
        MaxConnectionAgeGrace: 15 * time.Second, // дать 15 секунд на завершение активных RPC
    }
    ```
    Объясните, как это заставляет клиентов плавно переподключаться к другим подам без обрыва активных пользовательских запросов [654].
655. **Координация Shutdown с K8s preStop хуком в gRPC**: Объедините концепции Graceful Shutdown и K8s жизненного цикла. Напишите код gRPC-сервера, который при завершении работы сначала отправляет клиентам фрейм GOAWAY (сигнализируя о том, что новые запросы на этом соединении не принимаются, но старые дорабатывают), спит заданное время (например, 15 секунд preStop фазы K8s для обновления DNS и эндпоинтов), а затем вызывает `GracefulStop()`.
