## Блок 32. Envelope Encryption, KMS и Multipart Upload

### Уровень 1. Envelope Encryption и KMS
383. **Ручное Envelope Encryption.** Реализуйте на Go: сгенерируйте случайный AES-256-GCM ключ (DEK) через `crypto/rand`, зашифруйте им файл, затем зашифруйте DEK мастер-ключом (KEK) через AES-GCM или RSA-OAEP. Сохраните вместе: `encrypted_dek + nonce + ciphertext`. Объясните, зачем шифровать данные DEK, а не KEK напрямую (perf + ротация).
384. **AWS KMS: GenerateDataKey.** Используйте AWS SDK (`github.com/aws/aws-sdk-go-v2/service/kms`) для вызова `GenerateDataKey` (AES-256). Получите `Plaintext` (DEK) и `CiphertextBlob` (зашифрованный DEK). Зашифруйте файл, удалите `Plaintext` из памяти (`memzero`), сохраните `CiphertextBlob` рядом с данными. Объясните, почему DEK никогда не хранится в plaintext вне RAM.
385. **GCP Cloud KMS: аналог.** Реализуйте тот же сценарий через `cloud.google.com/go/kms/apiv1`. Сравните API: AWS возвращает DEK в ответе, GCP требует `Encrypt`/`Decrypt` вызовов для DEK (или `GenerateRandomBytes` + `Encrypt`). Объясните разницу в trust model.
386. **Key Rotation без перешифрования данных.** Реализуйте схему: старый KEK расшифровывает DEK, новый KEK зашифровывает тот же DEK, обновляет `encrypted_dek` в метаданных. Данные не трогаются. Объясните, почему envelope encryption позволяет ротировать KEK за O(1) на объект.

### Уровень 2. Multipart Upload с шифрованием
387. **S3 Multipart Upload вручную.** Используйте AWS SDK: `CreateMultipartUpload`, загрузите 5 частей по 100 MB через `UploadPart`, завершите `CompleteMultipartUpload`. Покажите, что ETag каждой части — MD5 (или контрольная сумма), и порядок parts важен. Объясните, зачем multipart: resume, parallel upload, большие файлы.
388. **Multipart + Envelope Encryption.** Реализуйте: перед каждым `UploadPart` генерируйте уникальный DEK (или derived key через HKDF от общего DEK + part number). Шифруйте часть AES-GCM, загружайте. Сохраните метаданные шифрования (`x-amz-meta-x-dek`, `x-amz-meta-x-nonce`) в `CompleteMultipartUpload`. Объясните, почему нельзя использовать один nonce для всех частей.
389. **Streaming Encryption без полного чтения в RAM.** Реализуйте `io.Reader`, который читает из `os.File`, шифрует chunk-by-chunk (AES-GCM с счётчиком), и передаёт в `UploadPart` через `io.Pipe`. Покажите, что пиковое потребление RAM — размер одного chunk (5 MB), а не всего файла. Объясните, почему AES-GCM streaming требует careful nonce management (counter-based).
390. **Проверка целостности после upload.** После `CompleteMultipartUpload` вызовите `HeadObject`, получите `x-amz-meta-x-dek`. Расшифруйте DEK через KMS, скачайте файл, расшифруйте, сравните SHA-256 с оригиналом. Объясните, почему S3 ETag не гарантирует целостность при клиентском шифровании (ETag считается от ciphertext).

### Уровень 3. SSE vs CSE и продвинутые сценарии
391. **SSE-KMS vs Client-Side Encryption.** Сравните: (1) SSE-KMS (S3 шифрует данные, ключ в KMS, вы не управляете DEK), (2) CSE (вы шифруете, KMS только оборачивает DEK). Покажите, что при SSE-KMS провайдер видет plaintext (внутри инфраструктуры), при CSE — нет. Объясните compliance (GDPR, HIPAA) требования к CSE.
392. **Object Lock + Legal Hold.** Настройте S3 Object Lock (WORM) на bucket. Загрузите зашифрованный объект с `Retention Mode: Compliance`, `RetainUntilDate: +7 years`. Покажите, что даже root-аккаунт не может удалить объект до даты. Объясните, как envelope encryption + WORM защищают от ransomware (зашифрованные данные не подменить).
393. **Пакетная ротация DEK.** У вас 10 000 объектов в S3. Реализуйте worker pool, который: читает `encrypted_dek` из S3 metadata, вызывает KMS Decrypt, затем KMS Encrypt с новым KEK, обновляет S3 metadata через `CopyObject` (metadata replace). Объясните, почему `CopyObject` — единственный способ обновить metadata без re-upload.

### Уровень 4. Production и производительность
394. **Производительность: KMS throttling.** Замерьте latency `GenerateDataKey` vs `Encrypt` локально. Покажите, что KMS API имеет quota (обычно 10 000 req/sec). Реализуйте DEK cache в памяти (LRU) для однотипных объектов, но с TTL < KEK rotation period. Объясните риск: кэшированный DEK в RAM — acceptable, но не на диске.
395. **Envelope Encryption для стриминга (HLS/DASH).** Реализуйте схему: каждый сегмент `.ts` шифруется отдельным DEK (или KEY rotation каждые N сегментов). DEK передаётся в `.m3u8` как `EXT-X-KEY` URI, защищённый OAuth. Объясните, почему это DRM-like схема, но с envelope encryption на уровне приложения.

## Блок 33. Service Mesh (Istio / Linkerd)

### Уровень 1. Базовая инфраструктура и mTLS
396. **Sidecar Injection.** Разверните приложение Go в Kubernetes с Istio/Linkerd. Покажите, что после injection в pod появляется `istio-proxy` (Envoy) или `linkerd-proxy`. Объясните, как iptables/`iptables-tables` (или eBPF в Linkerd) перехватывают весь egress/ingress трафик и направляют через sidecar.
397. **mTLS (Mutual TLS).** Настройте `PeerAuthentication` (Istio) или `ServerPolicy` (Linkerd) с `mtls.mode: STRICT`. Покажите, что pod без sidecar не может подключиться к сервису с STRICT. Объясните, как sidecar-ы обмениваются сертификатами (SPIFFE/SPIRE identity, автоматическая ротация через Citadel/Linkerd identity).
398. **L7 Traffic Management.** Настройте `VirtualService` + `DestinationRule` (Istio) или `TrafficSplit` (Linkerd): 90% трафика на `v1`, 10% на `v2`. Реализуйте Go-сервис с двумя deployment (`app=v1`, `app=v2`). Покажите распределение через `curl` в loop. Объясните, как mesh делает это без изменения клиентского кода.

### Уровень 2. Отказоустойчивость и безопасность
399. **Circuit Breaker в Mesh.** Настройте `DestinationRule` с `outlierDetection` (Istio): 5 consecutive errors → eject на 30 сек. Сымитируйте `500` в `v2` через Go-код (`if rand < 0.5 { return 500 }`). Покажите, что после 5 ошибок трафик на `v2` прекращается. Объясните, почему это L7 circuit breaker, а не TCP.
400. **Retries и Timeouts.** Настройте `VirtualService`: `retries.attempts: 3`, `perTryTimeout: 2s`, `timeout: 10s`. Сымитируйте в Go-сервисе `time.Sleep(5s)` (timeout) и `rand.Error()` (retry). Покажите, что mesh ретраит автоматически. Объясните, почему retries в mesh опасны без idempotency (см. Блок 24).
401. **Authorization Policy (L4/L7).** Настройте `AuthorizationPolicy` (Istio): только `service-a` может `GET /api/users` у `service-b`, `POST` запрещён. Покажите, что sidecar отклоняет запрос до достижения приложения. Объясните, зачем это нужно (zero-trust, defense in depth).

### Уровень 3. Observability и Canary
402. **Distributed Metrics.** Настройте `ServiceMonitor` (Prometheus) + Istio metrics (`istio_requests_total`, `istio_request_duration_seconds`). Покажите, что sidecar экспонирует метрики в формате Prometheus. Объясните, как это отличается от application-level metrics (нет необходимости инструментировать каждый сервис).
403. **Access Logs (Envoy ALS).** Включите Envoy access logs через `Telemetry` API (Istio) или `config.linkerd.io/access-log` (Linkerd). Покажите, что каждый HTTP/gRPC запрос логируется sidecar-ом с информацией: upstream, downstream, latency, response code. Объясните, почему это centralizes logging без изменения кода приложения.
404. **Canary Deployment с Flagger.** Настройте Flagger (или ручной `VirtualService` weight shift): 1% → 10% → 50% → 100% на `v2` с автоматическим rollback при росте 5xx. Реализуйте Go endpoint `/metrics` (latency, error rate). Покажите автоматический promotion/rollback. Объясните связь с SLO (Service Level Objectives).

### Уровень 4. Продвинутые сценарии
405. **Egress Gateway.** Настройте `EgressGateway` (Istio): весь outbound трафик к внешним API (Stripe, SendGrid) проходит через контролируемый gateway с TLS origination. Покажите, что pod не может напрямую достучаться до внешнего API (firewall + mesh policy). Объясните zero-trust egress.
406. **WASM Filter (Envoy).** Напишите простой WASM-фильтр на TinyGo (или Rust) для Envoy: добавляет custom header `X-Processed-By: wasm` к каждому запросу. Загрузите через `WasmPlugin` (Istio). Объясните, как WASM позволяет расширять L7 логику без перекомпиляции Envoy.
407. **Multi-Cluster Service Mesh.** Настройте `ServiceEntry` + `Gateway` для связи двух Kubernetes-кластеров (primary + remote). Покажите, что сервис из кластера A видит сервис из кластера B через DNS (`service-b.remote.svc.cluster.local`). Объясните роль `east-west gateway` и mTLS между кластерами.

## Блок 34. Распределённая трассировка (W3C / B3)

### Уровень 1. Контекст и propagation
408. **W3C Trace Context вручную.** Реализуйте middleware, которое парсит заголовки `traceparent` (`00-<trace-id>-<span-id>-01`) и `tracestate` (vendor-specific). Генерирует новый `span-id` для входящего запроса. Пропагирует дальше в исходящие HTTP-запросы. Объясните формат traceparent и флаги `01` (sampled).
409. **B3 Propagation (Zipkin).** Реализуйте аналог для B3: заголовки `X-B3-TraceId`, `X-B3-SpanId`, `X-B3-ParentSpanId`, `X-B3-Sampled`. Покажите, как B3 использует 64-bit IDs (vs 128-bit в W3C). Объясните, когда B3 нужен (legacy Zipkin), а когда W3C (OpenTelemetry, современный стандарт).
410. **Context propagation в gRPC.** Используйте `metadata.MD` для передачи traceparent в gRPC. Реализуйте `UnaryClientInterceptor` и `UnaryServerInterceptor`, которые извлекают/вставляют traceparent из `metadata`. Объясните, почему gRPC требует ручного propagation (нет стандартных заголовков как в HTTP).

### Уровень 2. OpenTelemetry SDK
411. **Ручной Span.** Используйте `go.opentelemetry.io/otel`: создайте `Tracer`, `Span`, добавьте `attributes` (`user_id`, `operation`), `events` («cache miss»), `status` (Error при 5xx). Завершите span через `defer span.End()`. Объясните, что span — это единица работы, а trace — дерево spans.
412. **Nested Spans и Parent-Child.** Реализуйте функцию `ProcessOrder`, которая создаёт span, внутри вызывает `ValidatePayment` (child span) и `ReserveInventory` (child span). Покажите в Jaeger/Zipkin UI иерархию: `ProcessOrder` → `ValidatePayment` + `ReserveInventory`. Объясните, как `context.Context` передаёт parent span.
413. **Sampling.** Настройте `TraceIDRatioBased(0.1)` (10% sampling) и `AlwaysOnSampler`. Покажите, что при высокой нагрузке только 10% трейсов попадает в collector. Объясните head-based vs tail-based sampling (tail требует буферизации, реализуется в collector, например, OpenTelemetry Collector).

### Уровень 3. Baggage и интеграция
414. **Baggage Propagation.** Добавьте в trace context `baggage`: `user-id=123`, `tenant=acme`. Покажите, что baggage передаётся через все сервисы (в HTTP headers `baggage-user-id=123`, в gRPC metadata). Объясните, почему baggage — это не тот же span attribute (baggage propagates, attributes — локальны).
415. **Trace Context + Service Mesh.** Покажите, что Istio/Linkerd автоматически добавляют `x-request-id` и пропагируют trace headers (если настроен `MeshConfig` с `enableTracing: true`). Объясните, как mesh дополняет application spans своими (Envoy span: ingress/egress, mTLS handshake latency).
416. **Correlation с Logs.** Реализуйте `zap`/`slog` hook, который добавляет `trace_id` и `span_id` в каждую log entry из `context`. Покажите в Kibana/Grafana Loki: по `trace_id` находятся все логи всех сервисов, участвовавших в запросе. Объясните, почему это критично для debugging production.

### Уровень 4. Производительность и production
417. **Span Batch Exporter.** Настройте `BatchSpanProcessor` с `BatchTimeout=1s`, `MaxQueueSize=2048`. Покажите, что при burst (>2048 pending spans) старые spans дропаются. Объясните, почему синхронный экспорт (`SimpleSpanProcessor`) недопустим в production (блокирует request).
418. **Trace Context Integrity.** Реализуйте middleware, которое отклоняет или очищает входящие `traceparent` с невалидным форматом (не hex, неправильная длина). Объясните, почему это важно: злоумышленник может заспамить collector фейковыми trace IDs, или сломать sampling.

## Блок 35. gRPC Client Keepalive и Graceful Draining

### Уровень 1. Keepalive и жизнь соединения
419. **Client Keepalive.** Настройте gRPC клиент с `keepalive.ClientParameters{Time: 10s, Timeout: 3s, PermitWithoutStream: true}`. Покажите через `tcpdump`/`ngrep` или gRPC logs, что клиент шлёт HTTP/2 PING кадры каждые 10 сек. Объясните, зачем это нужно: обнаружение «мёртвых» соединений (NAT timeout, LB silent drop).
420. **Server Keepalive Enforcement.** Настройте gRPC сервер с `keepalive.EnforcementPolicy{MinTime: 5s, PermitWithoutStream: false}`. Покажите, что клиент с `Time: 1s` получает `GOAWAY` (too_many_pings). Объясните, зачем сервер ограничивает частоту PING — защита от DoS.

### Уровень 2. Graceful Draining и Connection Management
421. **Graceful Shutdown (Server).** Реализуйте: при `SIGTERM` gRPC сервер вызывает `GracefulStop()` (ждёт завершения активных RPC), затем `Stop()` (hard stop после timeout). Покажите, что клиенты получают `Unavailable` и могут ретраить. Объясните, почему `GracefulStop` не закрывает существующие streams мгновенно.
422. **Connection Draining с LB.** Настройте Kubernetes `Service` + `preStop` hook (`sleep 15`), который даёт серверу время на `GracefulStop` до удаления pod из endpoints. Покажите через `kubectl get endpoints`, что pod удаляется из LB до фактического termination. Объясните, как это предотвращает 503 при rolling update.
423. **Client Load Balancing + Health Checking.** Настройте gRPC клиент с `round_robin` LB и `healthcheck` (gRPC health probe). Покажите, что при падении одного backend клиент автоматически переключается на другой. Объясните, почему DNS-based LB недостаточно (кеширование, stale endpoints).

### Уровень 3. Интеграция с Mesh и облаком
424. **gRPC через ALB/NLB.** Настройте AWS ALB (HTTP/2) или NLB (TCP) для gRPC. Покажите, что ALB терминирует TLS и делает L7 routing (`:authority` header), а NLB — прозрачен. Объясните, почему gRPC keepalive критичен при ALB (idle timeout 60 сек, без PING соединение дропается).
425. **Service Mesh + gRPC Keepalive.** Покажите, что Istio sidecar (Envoy) имеет свой `idle_timeout` (по умолчанию 1h для HTTP/2). gRPC keepalive PING сбрасывает Envoy idle timer. Объясните, как настроить `DestinationRule` с `tcpKeepalive` и `h2UpgradePolicy` для совместимости.
426. **Long-lived gRPC Streams (BiDi) и Draining.** Реализуйте BiDi stream. При `GracefulStop` сервер должен отправить `io.EOF` (закрыть stream) клиентам, а не обрывать. Клиент должен обработать `EOF` и реконнектиться. Объясните, почему BiDi streams сложнее drain, чем unary RPC.

### Уровень 4. Production и отладка
427. **gRPC Channelz.** Включите `grpc.Channelz` сервис. Напишите клиент, который запрашивает `GetChannel`/`GetSubchannel` и выводит: состояние соединений (`READY`, `IDLE`, `TRANSIENT_FAILURE`), количество streams, last call started. Объясните, как это помогает debug «залипших» соединений.
428. **Connection Pool Tuning.** Настройте gRPC клиент: `MaxRecvMsgSize`, `MaxSendMsgSize`, `InitialWindowSize`, `InitialConnWindowSize`. Покажите, как маленькое окно (64 KB) ограничивает throughput при высокой latency (RTT 100ms). Объясните BDP (Bandwidth-Delay Product) и зачем увеличивать window для WAN.
429. **Zero-downtime Deployment Pipeline.** Спроектируйте полный pipeline: (1) Kubernetes HPA + PDB (minAvailable: 1), (2) `preStop: sleep 20`, (3) gRPC `GracefulStop` + health check failure, (4) Istio `DestinationRule` connection pool settings, (5) client keepalive + retry policy. Покажите через `kubectl rollout restart`, что `hey` не видит 503. Объясните, как все компоненты (mesh, LB, client, server) работают вместе.

## Как встроить в общий план обучения

**Рекомендуемый порядок прохождения:**

1. **Блок 32 (Envelope Encryption)** — начните после Блока 10 (криптография), так как envelope encryption — прямое продолжение AES-GCM + RSA/Ed25519. Знание `crypto/rand` и `cipher` обязательно.
2. **Блок 35 (gRPC Keepalive/Draining)** — проходите после Блока 21 (gRPC-Web), так как это продолжение gRPC-инфраструктуры. Знание `context` и `sync` критично для graceful shutdown.
3. **Блок 34 (Tracing)** — параллельно с Service Mesh, так как tracing — это cross-cutting concern. Требует понимания `context.Context` propagation (Блок 1, GMP — goroutine-local storage не существует, только context).
4. **Блок 33 (Service Mesh)** — финальный блок cloud-native. Требует Kubernetes, но все паттерны (circuit breaker, retries, mTLS) опираются на предыдущие блоки: безопасность (Блок 13), idempotency (Блок 24), distributed tracing (Блок 34).

**Ключевые инструменты и команды для тренировки:**
```bash
# S3 Multipart Upload
aws s3api create-multipart-upload --bucket mybucket --key largefile.enc
aws s3api upload-part --bucket mybucket --key largefile.enc --part-number 1 ...

# Istio
istioctl install --set profile=demo
kubectl label namespace default istio-injection=enabled
istioctl dashboard jaeger  # или kiali

# gRPC keepalive debug
GRPC_GO_LOG_VERBOSITY_LEVEL=99 GRPC_GO_LOG_SEVERITY_LEVEL=info ./client

# Tracing
curl -H "traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01" http://api/
```

**Что фиксировать в результатах:**
- Для Envelope Encryption: схема DEK/KEK, latency `GenerateDataKey` vs local AES, proof of multipart integrity.
- Для Service Mesh: YAML-манифесты (`VirtualService`, `DestinationRule`, `PeerAuthentication`), скриншоты Kiali/Jaeger.
- Для Tracing: пример trace в Jaeger (иерархия spans), корреляция логов по `trace_id`.
- Для gRPC: `tcpdump` PING frames, proof of zero-downtime rollout (`hey` output).
