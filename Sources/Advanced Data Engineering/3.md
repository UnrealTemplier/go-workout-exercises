### Блок 91: MongoDB — Документоориентированная БД
*Цель: Освоить работу с BSON, агрегациями и распределенными транзакциями.*
*Пакет: `go.mongodb.org/mongo-driver/mongo`*

816. Подними MongoDB в Docker. Подключись к ней через Go. Создай коллекцию `users`. Вставь один документ (структура Go с тегами `bson:"_id"` и `bson:"name"`).
817. **[BSON Tags]** Создай структуру, где поле `Email` в Go мапится на поле `email_address` в MongoDB. Поле `Password` должно игнорироваться при сохранении (`bson:"-"`).
818. **[CRUD]** Реализуй поиск документов по условию: найди всех пользователей старше 25 лет (`bson.M{"age": bson.M{"$gt": 25}}`). Используй `options.Find()` для лимита и сортировки.
819. **[Aggregation Pipeline]** Напиши агрегацию, которая группирует пользователей по городу и считает их средний возраст. Этапы: `$match` (возраст > 18), `$group` (`_id: "$city"`, `avgAge: {$avg: "$age"}`).
820. **[Indexes]** Создай уникальный индекс по полю `email` (`mongo.IndexModel`). Попробуй вставить двух пользователей с одинаковым email и поймай дубликат ключа (`mongo.IsDuplicateKeyError`).
821. **[TTL Index]** Создай индекс с временем жизни (TTL) по полю `createdAt` (`ExpireAfterSeconds: 3600`). Вставь документ и убедись, что через час (или с перемоткой времени в БД) он удалится сам.
822. **[Сессии и Транзакции]** Создай сессию (`client.StartSession`). В рамках транзакции (`session.WithTransaction`) переведи деньги между двумя документами в коллекции `accounts`. Если баланс отправителя уходит в минус — вызови `session.AbortTransaction()`.
823. **[Каверзный кейс — Retryable Writes]** Сымитируй сетевое моргание (перезапусти контейнер Mongo во время транзакции). Настрой клиент с `RetryWrites: true` и убедись, что операция автоматически повторяется без ошибки на уровне приложения.
824. **[Высокая сложность — Schema Validation]** Настрой в MongoDB JSON Schema Validation на уровне коллекции (через `validator`). Попробуй вставить документ без обязательного поля `name` или с неверным типом `email`. Поймай ошибку валидации на уровне БД.

### Блок 92: ClickHouse — Аналитическая СУБД (OLAP)
*Цель: Научиться вставлять миллионы строк за секунды через бинарные протоколы.*
*Пакет: `github.com/ClickHouse/clickhouse-go/v2`*

825. Подними ClickHouse в Docker. Подключись через нативный TCP протокол (порт 9000, не HTTP 8123). Создай таблицу `events` движком `MergeTree`: `(id UUID, user_id UInt64, event_time DateTime, data String)`. Обязательно укажи `ORDER BY (event_time, user_id)`.
826. **[Batch Insert (Native Protocol)]** Напиши код, который вставляет 1 миллион строк за один сетевой запрос. Используй `Prepare` + контекстный `batch.Append()` в цикле, затем `batch.Send()`. Оцени скорость (должно быть < 1 секунды).
827. **[Каверзный кейс — Async Inserts]** Если ClickHouse не справляется с потоком мелких инсертов, он падает с `Too many parts`. Включи `AsyncInsert` в настройках подключения. Отправляй по 10 строк, ClickHouse сам соберет их в батч на сервере.
828. **[Streaming Read]** Напиши запрос `SELECT * FROM events WHERE user_id = 123`. Читай результат стримингом через `rows.Next()`, не загружая весь результат в память.
829. **[Агрегации]** Выполни запрос: посчитай количество событий и уникальных пользователей за последние 24 часа (`COUNT()`, `uniqExact(user_id)`, `GROUP BY toStartHour(event_time)`).
830. **[Materialized View]** Создай материализованное представление (MV), которое автоматически суммирует события по дням. Вставь сырые данные в `events` и сделай `SELECT` из MV, убедись, что данные там уже есть.
831. **[Columnar Reading]** Вместо строкового чтения используй колоночное чтение напрямую (`Query` с `Select("user_id", "event_time")`). Прочитай только нужные колонки в слайсы `[]uint64` и `[]time.Time`, минуя структуры (максимальная производительность).
832. **[Высокая сложность — Compression]** Настрой сжатие LZ4 или ZSTD на уровне соединения. Сравни сетевой трафик при передаче 1GB сырых данных со сжатием и без.

### Блок 93: Elasticsearch / OpenSearch — Поисковые движки

839. **[Aggregations]** Выполни поиск по всем статьям и запроси агрегацию `terms` по полю `tags`, чтобы получить топ-5 самых популярных тегов.

842. **[Высокая сложность — Custom Analyzer]** Создай индекс с кастомным анализатором: добавь фильтр `ngram` (разбивает слова на подстроки длиной 2-4 символа). Проиндексируй слово "GoLang" и убедись, что поиск по строке "Lan" находит этот документ ( автодополнение / search-as-you-type).

### Блок 94: CDC (Change Data Capture) и Логическая репликация
*Цель: Реагировать на изменения в PostgreSQL в реальном времени без поллинга.*
*Пакет: `github.com/jackc/pglogrepl`*

843. Настрой PostgreSQL в Docker: включи `wal_level=logical` и `max_replication_slots=10`.
844. Создай публикацию (`CREATE PUBLICATION my_pub FOR ALL TABLES;`) и слот логической репликации через Go-код (`pglogrepl.CreateReplicationSlot`).
845. Запусти репликацию (`pglogrepl.StartReplication`). Напиши бесконечный цикл, который читает WAL (Write-Ahead Log) сообщения.
846. Обрабатывай сообщения типа `*pglogrepl.RelationMessage` (сохраняй структуру таблиц в памяти) и `*pglogrepl.InsertMessage` (декодируй кортеж данных в Go-структуру).
847. **[Каверзный кейс — Schema Changes]** Что будет, если во время репликации в Postgres добавят новую колонку? Реализуй обновление локального кэша схем при получении нового `RelationMessage`.
848. **[Acknowledging LSN]** Реализуй отправку `StandbyStatusUpdate` обратно в Postgres каждые 5 секунд (подтверждение позиций WAL, чтобы Postgres не хранил логи вечно). Если не слать апдейты, слот будет разрастаться и переполнит диск.
849. **[High Availability]** Если твой CDC-воркер упал, поднялся заново — он должен продолжить чтение с того места, где остановился. Сохраняй последний подтвержденный LSN (Log Sequence Number) в Redis или локальный файл перед стартом репликации (`StartReplication` с `lsn`).
850. **[Маршрутизация событий]** Изменения таблицы `users` отправляй в Kafka topic `users_cdc`, а изменения `orders` — в `orders_cdc`.
851. **[Graceful Shutdown CDC]** Напиши обработчик `SIGINT`. При выключении воркер должен: доситать текущий WAL-сегмент, отправить финальный `StandbyStatusUpdate` в Postgres, закрыть соединение и сохранить LSN. Если этого не сделать, при следующем старте воркер может прочитать часть данных повторно (at-least-once).
852. **[Финальное испытание — Real-time Analytics Pipeline]**
    Построй сквозную систему аналитики в реальном времени:
    1. **Источник:** PostgreSQL (OLTP). Туда постоянно (через скрипт или HTTP API) идут INSERT'ы новых заказов.
    2. **CDC Worker:** Go-сервис с `pglogrepl` читает инсерты, декодирует их.
    3. **Буфер/Очередь:** Декодированные события пушатся в NATS JetStream (с гарантией доставки и персистентностью).
    4. **Аналитический приемник:** Второй Go-воркер читает батчами из NATS и пушит через Native Protocol прямо в ClickHouse.
    5. **Визуализация:** Сделай простенький HTTP-эндпоинт, который делает `SELECT count() FROM orders GROUP BY toStartMinute(time)` в ClickHouse и показывает количество заказов в минуту.
    - Система должна переживать падение любого компонента (Postgres, ClickHouse, NATS, самого воркера) без потери данных.
