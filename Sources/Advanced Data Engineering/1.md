## Блок 14. MongoDB

### Уровень 1. CRUD, индексы и атомарность
177. **Базовый CRUD и индексы.** Напишите сервис на Go (official `mongo-driver`), который создаёт коллекцию `events`, вставляет документы с полями `user_id`, `timestamp`, `payload`. Создайте single field index на `user_id` и compound index `{user_id: 1, timestamp: -1}`. Используйте `explain("executionStats")` и покажите, как index scan заменяет collection scan.
178. **Атомарные операции.** Реализуйте счётчик посещений через `$inc` и массив логов через `$push` с `$slice` (keep last N). Объясните, почему `FindOneAndUpdate` с `ReturnDocument: After` — идиоматичный способ атомарного read-modify-write в MongoDB.
179. **Schema Validation.** Определите JSON Schema на уровне коллекции (`validator` при создании). Покажите, что вставка невалидного документа падает с `WriteError`. Объясните компромисс: валидация в БД vs валидация в приложении (zero-trust).

### Уровень 2. Транзакции, агрегации и Change Streams
180. **Многодокументные транзакции.** Реализуйте перевод «кредитов» между двумя документами (кошельками) в одной коллекции через `session.StartTransaction()`. Покажите `CommitTransaction` и `AbortTransaction`. Объясните ограничения: транзакции не работают на sharded кластерах до 4.2, оверхед на snapshot isolation.
181. **Aggregation Pipeline.** Постройте pipeline для аналитики: `$match` (фильтр по дате) → `$group` (агрегация по `user_id` с `$sum`) → `$lookup` (join с коллекцией `users`) → `$unwind` + `$project`. Объясните порядок stages и почему `$match` должен быть как можно раньше (predicate pushdown).
182. **Change Streams.** Реализуйте watcher на коллекцию `events` через `collection.Watch()`. Фильтруйте по `operationType: "insert"`. Покажите механизм `ResumeAfter` с `resumeToken` для восстановления после реконнекта. Объясните, почему Change Stream требует replica set (oplog).

### Уровень 3. Производительность и отказоустойчивость
183. **Bulk Write.** Импортируйте 100 000 документов через `collection.BulkWrite()` с `ordered: false`. Сравните скорость с пошаговой `InsertOne`. Объясните разницу между `ordered` (стоп при ошибке) и `unordered` (продолжает, возвращает все ошибки).
184. **Read/Write Concern.** Настройте `writeconcern.New(writeconcern.WMajority())` и `readpref.SecondaryPreferred()`. Сымитируйте split-brain (отключение secondary) и покажите, как majority-write гарантирует durability. Объясните `linearizable` read и его цену (latency).
185. **Replica Set и Failover.** Подключитесь к replica set через `mongodb://host1,host2,host3/?replicaSet=rs0`. Сымитируйте `stepDown` primary. Покажите, как Go-driver автоматически переключается на новый primary. Объясните read preference: `primary`, `secondary`, `nearest`.

### Уровень 4. Шардирование и архитектура
186. **Шардирование.** Настройте sharded cluster (через `mongos`). Выберите shard key (hashed vs ranged) для коллекции `orders`. Покажите `sh.shardCollection()` и `sh.status()`. Объясните, почему неправильный shard key (монотонно возрастающий) создаёт «hot shard».
187. **Schema Design для MongoDB.** Реализуйте два подхода для хранения комментариев к постам: embedding (массив внутри документа поста) vs referencing (отдельная коллекция). Покажите, когда embedding лучше (read-heavy, bounded growth), а когда referencing (unbounded growth, нужна пагинация).

## Блок 15. ClickHouse

### Уровень 1. Создание таблиц и базовые запросы
188. **MergeTree и партиционирование.** Создайте таблицу `events` (`ENGINE = MergeTree`) с `PARTITION BY toYYYYMM(event_time)` и `ORDER BY (user_id, event_time)`. Объясните, почему `ORDER BY` — это primary key (sorting key), а не uniqueness constraint. Покажите `system.parts` и pruning партиций.
189. **Пакетная вставка.** Сравните три способа вставки 1 млн строк: (1) `INSERT INTO ... VALUES`, (2) `INSERT INTO ... FORMAT CSV`, (3) `INSERT INTO ... FORMAT JSONEachRow`. Замерьте throughput. Объясните, почему Values — самый медленный (парсинг SQL).

### Уровень 2. Бинарные протоколы и движки
190. **Нативный бинарный протокол.** Используйте `clickhouse-go/v2` с batch API: создайте `batch`, заполняйте колонки напрямую (`batch.Column(0).Append(...)`), отправьте. Сравните с HTTP-интерфейсом. Объясните, почему native protocol быстрее (columnar serialization, меньше оверхед).
191. **Специализированные движки.** Создайте таблицы: `ReplacingMergeTree` (deduplication по `order_id`), `SummingMergeTree` (суммирование `amount` при merge), `AggregatingMergeTree` (хранение `SimpleState`). Покажите, что `SELECT * FROM table FINAL` выполняет dedup/sum на лету, а `OPTIMIZE TABLE` — фоново.
192. **Материализованные представления.** Создайте MV, которая при вставке в `events` автоматически агрегирует `count(), sum(amount)` в `events_mv` с `ENGINE = SummingMergeTree`. Объясните, что MV — это trigger на insert, а не view на select.

### Уровень 3. Оптимизация схемы и индексы
193. **Индексы и pruning.** Создайте таблицу с `minmax` индексом на `event_time` и `bloom_filter` на `user_id`. Выполните запрос с `WHERE user_id = 'x'` и покажите в `EXPLAIN indexes = 1`, что bloom filter отсекает гранулы. Объясните разницу между primary key (sparse index) и secondary data skipping indexes.
194. **Денормализация и Nested.** Реализуйте схему «заказ + товары» двумя способами: (1) через `Array(Nested(product_id String, quantity Int32))` внутри заказа, (2) через JOIN с таблицей `order_items`. Покажите, что JOIN в ClickHouse дорог, а Nested/Array — идиоматичный путь.

### Уровень 4. Распределённые таблицы и кластер
195. **Distributed Engine.** Создайте локальные таблицы `events_local` на 2 шардах. Создайте `events_dist` (`ENGINE = Distributed`). Вставляйте в `events_dist`, читайте из неё. Объясните, как sharding key (`rand()` или `user_id`) определяет шард, и почему `Distributed` отправляет запрос на все шарды при `SELECT *`.
196. **Репликация и отказоустойчивость.** Создайте `ReplicatedMergeTree` с `ZooKeeper` (или `ClickHouse Keeper`). Покажите пути в ZK (`/clickhouse/tables/...`). Сымитируйте отказ ноды: вставка продолжается на реплику, чтение идёт через `load_balancing = in_order`. Объясните `insert_quorum`.

## Блок 16. Elasticsearch / OpenSearch

### Уровень 1. Индексация, mapping и базовый поиск
197. **Mapping и CRUD.** Создайте индекс с explicit mapping: `title` (text + keyword multi-field), `status` (keyword), `created_at` (date). Индексируйте документы через official Go client. Объясните, почему `dynamic: strict` предпочтительнее в production (mapping explosion).
198. **Bulk API и refresh.** Индексируйте 100 000 документов через `_bulk`. Сравните `refresh=wait_for`, `refresh=false`, `refresh=true`. Объясните translog, segments и почему `refresh=false` даёт максимальный throughput, но данные видны только после следующего refresh (1 сек по умолчанию).

### Уровень 2. Анализаторы и поисковые запросы
199. **Анализаторы и токенизация.** Создайте custom analyzer: `standard` tokenizer + `lowercase` + `russian_morphology` (или `stemmer`). Покажите `_analyze` API: как «бегущие» превращается в токен «бег». Объясните разницу `match` (analyzed) vs `term` (not analyzed) запросов.
200. **Bool-запросы и nested.** Постройте сложный `bool` query: `must` (title содержит «go»), `filter` (status = published, date range), `must_not` (deleted = true). Добавьте `nested` query для массива объектов `comments` с `inner_hits`. Объясните, почему `nested` нужен для массивов объектов (independent indexing).

### Уровень 3. Агрегации и архитектура индексов
201. **Агрегации.** Постройте dashboard-запрос: `date_histogram` (по дням) + `terms` (по статусу) + `avg` (rating) + `derivative` (рост от дня к дню). Объясните разницу между bucket aggregations (группировка) и metric aggregations (вычисления).
202. **Index Templates и ILM/ISM.** Создайте index template с pattern `logs-*`. Настройте ILM (Index Lifecycle Management): rollover при 50 GB или 1 день → warm (сжатие) → cold (только чтение) → delete (30 дней). Объясните hot-warm-cold архитектуру для логов.
203. **Шардирование и маршрутизация.** Создайте индекс с 3 primary shards и 1 replica. Покажите `_cat/shards`. Используйте custom routing (`_routing=user_id`) для co-location документов одного пользователя на одном шарде. Объясните, когда это ускоряет `term` query, а когда создаёт hot shard.

### Уровень 4. Продвинутые сценарии
204. **Snapshot / Restore.** Настройте S3 repository (`_snapshot/my_s3_repo`). Создайте snapshot, восстановите в другой индекс. Покажите инкрементальный snapshot (только новые segments). Объясните, почему snapshot — не backup в классическом смысле (pointer-based, не копия).
205. **Deep pagination и поисковая оптимизация.** Реализуйте экспорт 1 млн документов тремя способами: `from/size` (покажите OOM на больших offset), `scroll` (context-heavy), `search_after` (stateless, preferred). Объясните `query_then_fetch` vs `dfs_query_then_fetch`.

## Блок 17. CDC: PostgreSQL Logical Replication

### Уровень 1. Настройка и чтение слота
206. **Настройка PostgreSQL.** Включите `wal_level = logical`, `max_replication_slots = 4`, `max_wal_senders = 10`. Создайте публикацию `CREATE PUBLICATION mypub FOR TABLE users, orders`. Создайте слот репликации (`pg_create_logical_replication_slot`). Объясните разницу между `pgoutput` (native) и `wal2json` (текстовый).
207. **Чтение WAL через Go.** Используйте `jackc/pglogrepl` для подключения к слоту: `StartReplication`, цикл `WaitForReplicationMessage`. Обрабатывайте `PrimaryKeepaliveMessage` (отправляйте `StandbyStatusMessage` с `replyRequested`). Объясните, почему PostgreSQL может отключить клиента, если он не шлёт feedback.

### Уровень 2. Декодирование и обработка сообщений
208. **Декодирование pgoutput.** Распарсите поток WAL: `BeginMessage` (транзакция началась), `RelationMessage` (схема таблицы), `InsertMessage` (новая строка), `UpdateMessage` (старая + новая), `DeleteMessage`, `CommitMessage`. Выведите человекочитаемый лог изменений.
209. **Обработка TOAST.** Создайте таблицу с колонкой `TEXT` (>2 KB). При обновлении другой колонки покажите, что TOAST-поле передаётся как `ToastUnchanged` (не передаётся в WAL). Объясните, как обработать: либо хранить полную копию в consumer, либо делать `SELECT` из таблицы по ключу.
210. **Schema cache.** Постройте in-memory map: `relation_id → []column_name + []column_type`. Обновляйте при получении `RelationMessage`. Используйте для динамического маппинга `TupleData` в `map[string]any`. Объясните, почему `RelationMessage` может приходить не для каждой транзакции.

### Уровень 3. Построение CDC-пайплайнов
211. **PostgreSQL → Kafka.** Реализуйте producer: читаете WAL, сериализуете в Avro/JSON, публикуете в Kafka topic `db.users`, `db.orders` с key = `primary_key`. Обеспечьте ordering (same partition for same key). Объясните, как Kafka Connect Debezium делает то же самое.
212. **CDC → ClickHouse (Upsert).** Реализуйте consumer: CDC-события вставляются в `ReplacingMergeTree` с дополнительными колонками `_version` (LSN) и `_sign` (1 для insert/update, -1 для delete). Покажите, как `FINAL` и `OPTIMIZE` дают актуальное состояние. Объясните, почему ClickHouse не любит deletes и как `_sign` решает это.
213. **CDC → Elasticsearch.** Реализуйте consumer: `InsertMessage` → `index`, `UpdateMessage` → `update` с `doc`, `DeleteMessage` → `delete`. Обработайте partial update (только изменённые поля). Объясните, почему Elasticsearch не идеален для CDC (нет транзакций, возможны out-of-order updates).

### Уровень 4. Fault tolerance и schema evolution
214. **Fault tolerance и LSN tracking.** Реализуйте механизм: consumer обрабатывает батч, коммитит offset (LSN) в PostgreSQL через `SendStandbyStatus` только после успешной записи в downstream. При рестарте читайте с `restart_lsn`. Объясните at-least-once vs exactly-once semantics.
215. **Мониторинг и lag.** Напишите метрики: `pg_stat_replication` → `pg_current_wal_lsn() - confirmed_flush_lsn` (lag в байтах). Выведите в Prometheus. Настройте алерт при lag > 100 MB. Объясните, почему рост lag приводит к bloat WAL и потенциальному OOM.
216. **Schema evolution.** Выполните `ALTER TABLE users ADD COLUMN phone VARCHAR`. Покажите, что `RelationMessage` приходит с новой версией схемы. Реализуйте consumer, который динамически адаптируется (добавляет nullable колонку в downstream). Объясните backward compatibility: новые поля → nullable, удаление → soft delete.

## Как встроить в общий план обучения

**Рекомендуемый порядок прохождения:**

1. **Блок 14 (MongoDB)** — начните после Блока 10 (криптография), так как MongoDB часто используется для хранения токенов и сессий. Понимание транзакций требует знаний из Блока 1 (GMP — concurrency и атомарность).
2. **Блок 15 (ClickHouse)** — проходите после Блока 14, так как ClickHouse требует переосмысления подхода к схеме (денормализация вместо JOIN). Параллельно смотрите Блок 2 (аллокатор) — поймёте, почему columnar storage быстрее для аналитики.
3. **Блок 16 (Elasticsearch)** — после ClickHouse, чтобы сравнить аналитические и поисковые движки. Знание `mmap` из Блока 6 поможет понять, как Lucene использует memory-mapped files.
4. **Блок 17 (CDC)** — финальный блок, требует понимания всех предыдущих: PostgreSQL WAL → Kafka/Redis → ClickHouse/Elasticsearch. Concurrency из Блока 1 критичен для fault-tolerant consumer.

**Ключевые инструменты и команды для тренировки:**
```bash
# MongoDB
mongosh --eval "db.events.explain('executionStats').find({user_id: 'x'})"

# ClickHouse
clickhouse-client --query "EXPLAIN indexes = 1 SELECT * FROM events WHERE user_id = 'x'"
clickhouse-client --query "SELECT * FROM system.parts WHERE table = 'events'"

# Elasticsearch
curl -X GET "localhost:9200/events/_search?explain=true" -d '{...}'
curl -X GET "localhost:9200/_cat/shards/events?v"

# PostgreSQL CDC
psql -c "SELECT * FROM pg_replication_slots;"
psql -c "SELECT pg_current_wal_lsn(), confirmed_flush_lsn FROM pg_stat_replication;"
```

**Что фиксировать в результатах:**
- Для MongoDB: `explain()` выводы, сравнение embedded vs referenced, графики latency транзакций.
- Для ClickHouse: `INSERT` throughput (rows/sec), размер данных на диске до/после `OPTIMIZE`, query latency.
- Для Elasticsearch: `_profile` API, размер segments, heap usage при bulk indexing.
- Для CDC: sequence-диаграмма (WAL → RelationMessage → TupleData → Downstream), метрики lag в Grafana.
