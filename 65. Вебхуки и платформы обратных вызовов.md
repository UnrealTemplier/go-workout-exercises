# Вебхуки и платформы обратных вызовов

В этом файле собраны уникальные упражнения по теме **"Вебхуки и платформы обратных вызовов"**, отсортированные по возрастанию сложности.

---

1. **Проектирование схемы Webhook-события**: Создайте структуру события, отправляемого платформой (например, `Event` с полями `ID string`, `Type string`, `Timestamp int64`, `Payload any`). Напишите генератор секретных токенов для клиентов на базе безопасной случайности (`crypto/rand`), с помощью которых клиенты будут подтверждать подлинность ваших запросов.

2. **Базовая отправка и статусы.**: Реализуйте сервис, который отправляет HTTP POST с JSON-payload на URL подписчика. Обработайте статусы: 2xx — успех, 4xx — permanent failure (не ретраить), 5xx/timeout — temporary failure (ретрай). Объясните, почему 410 Gone означает «отпишите подписчика навсегда».

3. **Проектирование отправителя webhook с HMAC-подписью.**: Реализуйте HTTP-клиент, который отправляет webhook с JSON-телом. Подпишите тело с помощью HMAC-SHA256, используя общий секрет. Передайте подпись в заголовке `X-Webhook-Signature`.

4. **Базовый Webhook Dispatcher**: Напиши воркер (горутину), который читает события из канала (например, `OrderPaid`), сериализует их в JSON и делает `http.Post` на URL, сохраненный в настройках клиента.

5. **Регистрация webhook endpoint**: Создайте API для регистрации webhook: `POST /webhooks` с полями `url`, `events[]`, `secret`. Валидируйте URL (схема HTTPS, reachable host).

6. **[Базовый отправитель]**: Напиши функцию `SendWebhook(url string, payload []byte)`, которая делает POST-запрос с JSON-телом.

7. **Endpoint verification (Stripe-style)**: При регистрации отправляйте GET-запрос с `challenge` параметром. Клиент должен вернуть challenge в теле ответа — это подтверждает владение доменом.

8. **HMAC signature генерация**: При отправке webhook события подписывайте body через HMAC-SHA256 с общим secret. Добавляйте подпись в header `X-Webhook-Signature: sha256=...`.

9. **Timestamp в подписи**: Включайте `X-Webhook-Timestamp` header и подписывайте `timestamp.body` конкатенацию. Это защита от replay attacks.

10. **HMAC-SHA256 подпись.**: Реализуйте подпись на стороне отправителя: `HMAC-SHA256(secret, timestamp + "." + body)`, заголовок `X-Signature`. На приёмнике — проверка с `subtle.ConstantTimeCompare`. Объясните, зачем добавлять timestamp в подпись (replay protection) и как обрабатывать clock skew (±5 минут).

11. **Верификация на стороне клиента**: Реализуйте Go-клиент, который получает webhook, проверяет timestamp (не старше 5 минут), вычисляет HMAC и сравнивает через `hmac.Equal` (constant-time).

12. **Webhook dispatcher**: Создайте систему, которая при возникновении события (`order.paid`) находит все подписанные endpoints и ставит delivery задачи в очередь (Redis/Kafka).

13. **HMAC-подпись на стороне отправителя**: Чтобы злоумышленники не прислали ложные данные на сервер вашего клиента, все вебхуки должны подписываться. Напишите функцию на стороне вашей платформы, которая:
    * Вычисляет HMAC-SHA256 подпись от тела запроса (`Payload`) с использованием секретного ключа клиента.
    * Добавляет временную метку (timestamp) в заголовок `X-Webhook-Timestamp` (для защиты от Replay-атак — повторной отправки перехваченного валидного запроса).
    * Склеивает метку и тело запроса для вычисления подписи и упаковывает результат в заголовок `X-Webhook-Signature`.

14. **Асинхронная доставка**: Никогда не доставляйте webhooks синхронно в request handler. Всегда через background worker — иначе slow endpoints заблокируют ваш API.

15. **Приёмник webhook: проверка подписи и предотвращение replay-атак.**: Напишите HTTP-обработчик, который принимает webhook. Проверьте HMAC-подпись, сравните время запроса (`X-Request-Timestamp`) с текущим временем (отклонение не более 5 минут), и сохраните использованный `nonce` в Redis для предотвращения повторов.

16. **Безопасность (Подпись HMAC)**: Твой клиент должен знать, что вебхук пришел именно от тебя, а не от хакера. Перед отправкой вычисли HMAC-SHA256 подпись от тела (body) JSON, используя уникальный `secret_key` клиента. Добавь эту подпись в HTTP-заголовок `X-Signature`.

17. **[HMAC-Подпись]**: Перед отправкой вычисли HMAC-SHA256 от тела запроса с использованием секрета. Добавь заголовок `X-Signature-256: sha256=<hex>`.

18. **Idempotency-Key.**: Генерируйте `Idempotency-Key` (UUID v4) для каждого события. Приёмник хранит обработанные ключи в Redis с TTL 24 часа. При повторном получении — возвращает 200, но не обрабатывает. Объясните разницу между idempotency на уровне HTTP и на уровне бизнес-логики.

19. **Event payload структура**: Стандартизируйте payload: `{"id": "evt_...", "type": "order.paid", "created_at": "...", "data": {...}}`. ID события критичен для idempotency.

20. **Event ordering**: Обеспечьте доставку событий для одной сущности (`user_id`, `order_id`) в порядке возникновения. Используйте Kafka partition key или Redis stream с ordering.

21. **Multiple events per webhook**: Позвольте клиентам подписываться на `*` (все события) или на конкретные типы (`order.*`, `payment.failed`).

22. **Webhook filtering**: Добавьте filter rules: "доставлять только если `amount > 1000`" или "только для `region = EU`". Реализуйте через CEL (Common Expression Language) или JMESPath.

23. **Exponential Backoff.**: Реализуйте ретраи с интервалами: 1с, 2с, 4с, 8с, 16с (макс 5 попыток). Храните `attempt_count` и `next_retry_at` в БД. Напишите worker, который выбирает failed webhooks по `next_retry_at <= NOW()`. Объясните, почему max backoff ограничен (например, 1 час).

24. **Secret rotation**: Реализуйте dual-secret систему: при ротации оба секрета валидны в течение grace period (24 часа). Это позволяет клиентам мигрировать без downtime.

25. **Валидация подписи на стороне приемника**: Напишите HTTP-обработчик на стороне сервиса-приемника (клиента), который принимает вебхуки от вашей платформы.
    * Извлеките временную метку и подпись из заголовков.
    * Проверьте, что временная метка отличается от текущего времени не более чем на 5 минут (защита от устаревания запросов).
    * Самостоятельно вычислите ожидаемую сигнатуру и сравните её с присланной в заголовке за константное время с помощью `crypto/subtle.ConstantTimeCompare` [578], чтобы предотвратить атаки по времени (Timing Attacks) [578].

26. **Webhook logs и retries UI**: Создайте dashboard, где клиенты видят историю доставок: timestamp, status code, response body, retry count, next attempt.

27. **Защита от Replay Attacks (Атак повторного воспроизведения)**: Хакер перехватил подписанный вебхук и шлет его клиенту снова и снова. Добавь в генерируемый JSON (или заголовок `X-Timestamp`) текущее время (Unix timestamp). Подписывай конкатенацию `timestamp.body`. Клиент сможет отклонять вебхуки, которые старше 5 минут.

28. **Идемпотентность webhook-обработчика.**: Приёмник должен быть идемпотентным: используйте уникальный `idempotency-key` из тела или заголовка, чтобы повторная доставка одного и того же события не вызывала дублирования действий. Реализуйте проверку ключа в БД.

29. **Manual retry endpoint**: Дайте клиентам кнопку "Retry" для failed webhook delivery. Это критично для debugging.

30. **[Верификация (Приемник)]**: Напиши HTTP-сервер, который принимает вебхук. Прочитай тело запроса (`io.ReadAll`), вычисли HMAC и сравни с заголовком. Используй `hmac.Equal` для защиты от тайминг-атак. Если подпись неверна — верни `401 Unauthorized`.

31. **Jitter.**: Добавьте к backoff случайную составляющую: Full Jitter (`random(0, base)`) или Equal Jitter (`base/2 + random(0, base/2)`). Сымитируйте 1000 одновременных failed webhooks и покажите, что pure exponential создаёт thundering herd, а jitter — распределяет нагрузку.

32. **Test event endpoint**: Предоставьте `POST /webhooks/:id/test` для отправки тестового события. Stripe-style: `evt_test_...` с пометкой в payload.

33. **Exponential backoff**: Реализуйте retries по формуле `delay = base * 2^attempt`: 1min, 5min, 30min, 2h, 8h, 24h, 3 days, 7 days (типичный Stripe schedule).

34. **Jitter (обязательно!)**: Добавьте случайный jitter (±20%) к каждому delay. Без jitter при массовом сбое все retries "схлопываются" в один момент и DoS-ят failing endpoint.

35. **Full jitter pattern**: Используйте `delay = random(0, base * 2^attempt)` — более агрессивная версия jitter, рекомендованная AWS Architecture Blog.

36. **Circuit Breaker.**: Внедрите circuit breaker (ручная реализация или `github.com/sony/gobreaker`) перед отправкой: при 5 consecutive 5xx/timeout → состояние Open (30 сек), затем Half-Open (1 пробный запрос). Объясните, как это защищает и ваш сервис, и подписчика от DDoS.

37. **Очередь отправки вебхуков**: Прямая отправка вебхуков в основном потоке бизнес-логики заблокирует работу сервера при медленном ответе клиента. Напишите неблокирующую систему: при возникновении события в системе оно складывается в буферизованную очередь (или в топик брокера сообщений), а пул фоновых горутин-воркеров (Workers) последовательно вычитывает задачи и выполняет HTTP POST запросы к серверам клиентов.

38. **Max retries и dead letter**: После N неудачных попыток (обычно 15-20) помечайте webhook как disabled и отправляйте событие в dead letter queue для ручного разбора.

39. **Ретраи (повторная отправка) с Exponential Backoff и Jitter.**: Если получатель webhook возвращает ошибку 5xx или не отвечает, отправитель должен повторить попытку через 1с, 2с, 4с, 8с, 16с (с jitter ±15%). Реализуйте очередь повторов с ограничением максимального числа попыток.

40. **Receiver (Пишем надежного получателя)**: Напиши HTTP-хендлер для приема вебхуков. Внутри него:
    * Проверь `X-Timestamp`.
    * Вычисли ожидаемый HMAC и сравни его с `X-Signature` через безопасное сравнение `subtle.ConstantTimeCompare()`.

41. **Circuit breaker per endpoint**: Если endpoint failing подряд N раз, временно переставайте доставлять ему события (circuit open). Через M минут — half-open, пробуем один запрос.

42. **Slow endpoint detection**: Установите жесткий timeout на доставку (10-15 секунд). Slow endpoints не должны блокировать delivery других клиентов.

43. **[Exponential Backoff]**: Если сервер-приемник вернул `500` или таймаут, реализуй ретраи: 1 попытка сразу, 2-я через 2 сек, 3-я через 4 сек, 4-я через 8 сек.

44. **Delivery Log.**: Реализуйте таблицу `webhook_deliveries`: `id`, `subscription_id`, `endpoint`, `event_type`, `payload_hash`, `signature`, `attempts[]` (JSONB), `http_status`, `final_status` (delivered/failed). Напишите dashboard-запрос: failed за последние 24 часа с группировкой по endpoint.

45. **Concurrent delivery limiting**: Ограничьте количество одновременных deliveries на один endpoint (например, не более 10). Иначе burst событий положит клиентский сервер.

46. **Idempotency через event ID**: Клиент должен использовать `event.id` для deduplication. Один и тот же event может быть доставлен несколько раз (at-least-once semantics).

47. **Idempotency-Key header**: Отправляйте `Idempotency-Key: evt_...` header, чтобы клиенты могли использовать свои idempotency libraries.

48. **Ретраи с экспоненциальным бэк-оффом (Exponential Backoff)**: Если сервер клиента недоступен (возвращает статус `5xx` или запрос падает по таймауту), ваша платформа не должна сдаваться сразу. Реализуйте алгоритм повторных попыток. Напишите функцию вычисления задержки перед следующей попыткой по экспоненциальной формуле:
    $$\text{Задержка} = 2^{\text{попытка}} \times \text{базовый\_интервал}$$
    Ограничьте максимальную задержку (например, не более 1 часа) и количество попыток (например, до 5 раз).

49. **Batch delivery (опционально)**: Для high-volume клиентов группируйте события в batch webhook: `{"events": [...]}`. Снижает overhead в 100x.

50. **Subscription Management.**: Реализуйте CRUD подписок: `endpoint` (URL), `secret` (генерируется автоматически), `event_types[]` (whitelist), `active` (bool). Добавьте валидацию URL: запрет private ranges (SSRF-защита через resolve IP), обязательный HTTPS в production. Объясните, почему wildcard `event_types: ["*"]` — антипаттерн.

51. **Жесткие таймауты**: Клиентский сервер завис и не закрывает соединение. Если твой воркер будет висеть в ожидании, у тебя кончатся горутины. Оберни отправку вебхука в `context.WithTimeout(ctx, 3*time.Second)`. Никогда не жди клиента долго!

52. **Dead Letter Queue для не доставленных webhook.**: После исчерпания попыток поместите webhook-сообщение в отдельную таблицу БД или Kafka-топик «dead-letters» для ручного анализа и возможности повторной отправки администратором.

53. **Webhook signature versioning**: Поддерживайте несколько версий signature algorithm (`v1`, `v2`). При миграции на более безопасный алгоритм отправляйте обе подписи в переходный период.

54. **IP whitelisting**: Публикуйте статический IP-диапазон ваших webhook sender'ов. Крупные клиенты часто требуют whitelist по firewall rules.

55. **[Jitter (Дрожание)]**: Добавь случайную задержку (jitter) к экспоненциальному backoff (например, `delay + rand(0, 500ms)`). Объясни, почему это критически важно, если у тебя 1000 вебхуков упало одновременно (предотвращение "thundering herd").

56. **Egress through proxies**: Для enterprise-клиентов настройте delivery через их HTTPS proxy (forward proxy support).

57. **Batch Webhooks.**: Реализуйте batch-режим: накапливайте события 500 мс или до 100 штук, отправляйте одним POST с массивом payloads. Приёмник обрабатывает атомарно (все или ни одного) или поштучно с индивидуальными статусами в ответе. Объясните throughput/latency компромисс.

58. **mTLS для webhook delivery**: Предложите премиум-опцию: mTLS, где и ваш сервер, и клиент аутентифицируют друг друга сертификатами.

59. **Custom headers per webhook**: Позвольте клиентам задавать custom headers (например, `X-Api-Key` для их internal routing).

60. **Добавление случайного шума (Jitter)**: Если у клиента упал сервер, а затем восстановился, сотни запланированных повторных вебхуков со всех серверов вашей платформы могут одновременно ринуться к нему и обрушить его снова (проблема Thundering Herd). Добавьте в формулу вычисления задержки случайный шум (Jitter) [581], используя пакет `math/rand/v2` (доступен в Go 1.22+) [581]. Формула задержки со случайным разбросом:
    $$\text{Задержка} = \text{random}(0.5, 1.5) \times \left(2^{\text{попытка}} \times \text{базовый\_интервал}\right)$$

61. **Timeout configuration per endpoint**: Дайте клиентам настраивать timeout под их SLA (1s для real-time, 30s для batch processing).

62. **Экспоненциальный Backoff (Ретраи)**: Клиент ответил 503 или отвалился по таймауту. Напиши логику повторных попыток. Попытайся отправить вебхук 4 раза с паузами: 2 сек, 4 сек, 8 сек, 16 сек.

63. **Webhook с подписью тела (Signature v2: payload digest).**: Модифицируйте подпись, включив в неё HTTP-метод, путь и digest тела (SHA-256), чтобы избежать подделки на уровне прокси.

64. **Webhook Worker Queue.**: Реализуйте полный pipeline: `event` → Redis Stream/RabbitMQ → worker pool (N goroutine) → sender → retry scheduler (dead-letter queue при исчерпании попыток). Объясните at-least-once delivery: почему acknowledgment происходит только после HTTP 2xx, и как избежать дублирования при ребалансировке воркеров.

---

65. **Delivery attempts tracking**: Сохраняйте каждый attempt: timestamp, request body, response code, response body, latency. Это gold для debugging.

66. **Redacting sensitive data в logs**: При сохранении request/response body маскируйте PII и секреты перед записью в БД.

67. **Webhook delivery metrics:**
    * Delivery success rate
    * Mean/median/p99 latency
    * Retry rate
    * Dead letter queue size
    * Disabled endpoints count
    Экспортируйте всё в Prometheus.

68. **[Идемпотентность]**: Добавь в заголовок `X-Webhook-Id: <uuid>`. На стороне приемника сохраняй этот ID в Redis на 24 часа. Если пришел дубликат — отвечай `200 OK`, но не обрабатывай его повторно.

69. **Alerting на disabled endpoints**: Алерт клиенту (email/Slack), когда его webhook disabled из-за repeated failures. Это proactive support.

70. **SSRF protection в webhook registration**: При регистрации webhook не делайте verification request с вашего production server — атакующий может направить его на internal ресурсы (`http://169.254.169.254`, `http://metadata.google.internal`). Используйте isolated verification service.

71. **Автоматическое отключение подписок (Auto-disable)**: Напишите логику ведения лога доставок вебхуков. Если сервер конкретного клиента возвращает ошибку `410 Gone` или `404 Not Found` непрерывно в течение 48 часов, веб-платформа должна автоматически деактивировать эту подписку на вебхуки, сделать запись в лог и отправить уведомление на email администратора клиента.

---

72. **DNS rebinding protection**: При delivery разрешайте hostname и проверяйте, что IP не из private ranges (RFC 1918, 169.254.0.0/16). Иначе атакующий может redirect webhook на internal сеть.

73. **Full Jitter (Предотвращение шторма)**: Если упал крупный клиент, у тебя скопятся тысячи вебхуков. Когда клиент оживет, твои ретраи ударят по нему одновременно, снова положив сервер (Thundering Herd). Модифицируй паузу из упр. 781: добавляй к каждому интервалу случайный шум (Jitter). Например, вместо строго 4 секунд жди от 2 до 4 секунд (`random(0, delay/2) + delay/2`).

74. **Массовая рассылка webhook с контролем скорости.**: Реализуйте диспетчер, который отправляет webhooks нескольким подписчикам, ограничивая количество одновременных исходящих запросов (rate limiting на уровне горутин через семафор).

75. **Redirect following policy**: Не следуйте за redirect'ами при webhook delivery или следуйте максимум 1 redirect на тот же host. Open redirect может быть использован для SSRF.

76. **Large payload handling**: Установите max payload size (например, 256KB). Большие payloads DoS-ят клиентские endpoints и вашу сеть.

77. **Gzip compression**: Сжимайте webhook body через gzip для снижения трафика. Добавляйте `Content-Encoding: gzip` header.

78. **Rate limiting per endpoint**: Защищайте клиентов от burst'ов: не более N deliveries/сек на один endpoint, даже если у вас миллион событий в очереди.

79. **[Каверзный кейс — Replay Attack]**: Злоумышленник перехватил валидный вебхук и шлет его снова и снова. Добавь заголовок `X-Timestamp`. Включи timestamp в HMAC-подпись. На стороне приемника отклоняй запросы, timestamp которых старше 5 минут.

80. **Global rate limiting**: Защищайте свою инфраструктуру: общий outbound webhook RPS limit, чтобы не перегрузить own network.

81. **Backpressure при перегрузке**: Если delivery queue переполнена, временно переставайте принимать новые webhook registrations или переводите на degraded mode.

82. **Webhook payload versioning**: Добавляйте `api_version` в payload. При breaking changes в схеме увеличивайте версию, чтобы клиенты могли мигрировать постепенно.

83. **Пул воркеров для вебхуков**: Не создавай новую горутину на каждый вебхук, иначе всплеск событий выест всю память. Напиши Worker Pool на 100 воркеров. Они должны читать задачи из очереди (канала) и выполнять логику с ретраями.

84. **Webhook fan-out optimization**: Для события, на которое подписаны 1000 endpoints, не делайте 1000 serial deliveries. Используйте worker pool и batch fetching из очереди.

85. **Hot endpoint detection**: Детектируйте endpoints, которые генерируют disproportional трафик (один клиент потребляет 50% delivery capacity). Предлагайте им batch mode или отдельный tier.

86. **Webhook signature timing attack protection**: Всегда вычисляйте signature, даже если timestamp expired или невалидный. Иначе timing difference раскроет, какая проверка провалилась.

87. **Clock skew tolerance**: При timestamp verification допускайте ±5 минут clock skew между вашим и клиентским сервером.

88. **[Защита от Slow Loris]**: Если сервер-приемник отвечает медленно (читает по 1 байту в секунду), твой воркер заблокируется. Настрой `http.Client` с жесткими `Timeout` (например, 5 сек) и `ResponseHeaderTimeout`.

89. **Webhook delivery from multiple regions**: Для low-latency delivery клиентам в разных регионах используйте regional webhook sender'ы (US, EU, APAC).

90. **Webhook event retention**: Храните историю events 30-90 дней для manual retries и audit. Используйте ClickHouse для efficient storage.

91. **Dead Letter Queue (DLQ)**: Если вебхук не доставился после всех попыток, не выкидывай его. Сохрани его в таблицу БД `failed_webhooks` со статусом `exhausted`. Напиши админский эндпоинт, который позволяет нажать кнопку и переотправить протухший вебхук вручную.

92. **[Высокая сложность — Webhook Outbox]**: Напиши сервис, который сохраняет вебхук в таблицу `webhooks_outbox` в рамках основной бизнес-транзакции. Фоновый воркер читает таблицу, отправляет вебхуки и помечает строки как `delivered`. Если воркер упал, при рестарте он продолжит с места остановки.

93. **Идемпотентность Получателя (Receiver Idempotency)**: Твой Dispatcher может отправить один и тот же вебхук дважды (ошибка сети при получении 200 OK). На стороне Получателя (Receiver) добавь проверку по `Webhook-ID` в базу данных. Убедись, что бизнес-логика (например, зачисление бонусов) отрабатывает только один раз.

94. **Матрица выбора real-time технологий:**
    | Use Case | Технология |
    |----------|-----------|
    | Server→Client updates, auto-reconnect нужен | SSE |
    | Bidirectional чат, игры | WebSocket |
    | Streaming LLM tokens | SSE или Connect streaming |
    | Server→Client, corporate proxies | SSE |
    | Bidirectional, binary data | WebSocket |
    | Server→Client с multiplexing (HTTP/2) | SSE over HTTP/2 |

95. **Матрица выбора API стилей:**
    | Use Case | Стиль |
    |----------|-------|
    | CRUD ресурсы, public API | REST |
    | Flexible queries, mobile clients | GraphQL |
    | Межсервисное общение, streaming | gRPC/Connect |
    | Browser → backend, type-safe | Connect |
    | Много "действий", batch calls | JSON-RPC |
    | Event notification third parties | Webhooks |

96. **Webhooks vs Polling vs SSE:**
    * Webhooks: server-initiated, требует public endpoint у клиента
    * Polling: simple, но wasteful
    * SSE: client-initiated persistent connection
    Используйте webhooks для third-party integrations, SSE для own-client real-time.

97. **Cost comparison:**
    * Webhooks: outbound HTTP calls, cheap per delivery
    * SSE: persistent connection, требует connection tracking
    * WebSocket: persistent, bidirectional, более сложный state
    SSE/WebSocket требуют больше server resources per client.

98. **Event-driven webhook platform (Stripe-clone):**
    Создайте production webhook платформу:
    * **API:** регистрация/управление webhook endpoints
    * **Dispatcher:** Kafka-based delivery queue с ordering per endpoint
    * **Workers:** pool delivery workers с retries (exp backoff + full jitter)
    * **Security:** HMAC-SHA256 signatures с versioning, timestamp protection, SSRF/DNS rebinding protection
    * **Observability:** OpenTelemetry traces для каждой delivery, Prometheus metrics (success rate, latency percentiles, retry rate)
    * **UI:** customer dashboard с delivery logs, manual retry, endpoint health
    * **Circuit breaker:** per-endpoint circuit breaker
    * **Batch mode:** для high-volume клиентов
    * **mTLS:** премиум опция для enterprise
    * **Multi-region:** regional sender'ы для low-latency
    * **SLA:** 99.99% delivery success rate, <1s p99 latency от события до первой попытки

99. **Real-time collaborative editor (Linear/Notion-style):**
    Создайте collaborative приложение:
    * **SSE** для server→client streaming (presence, cursor positions, document updates)
    * **Connect** для request-response operations (save, load, permissions)
    * **CRDT** для conflict-free concurrent editing
    * **Presence system:** online users, typing indicators через SSE
    * **Optimistic updates** на клиенте + server reconciliation
    * **Offline support:** client буферизует changes, sync при reconnect (Last-Event-ID + delta)
    * **Permissions:** per-document access control
    * **Performance:** 100 concurrent editors per document, <50ms update latency

100. **Финальный босс (Universal API Gateway):**
    Создайте multi-protocol API gateway, который обслуживает все форматы:
    
    **Inbound protocols (clients → gateway):**
    * REST для public API
    * GraphQL для flexible queries
    * Connect для browser clients
    * gRPC для internal services
    * JSON-RPC для LSP-style tools
    * WebSockets для bidirectional chat
    * SSE для real-time feeds
    
    **Outbound protocols (gateway → third parties):**
    * Webhooks для event notifications
    * Connect clients для calling other services
    
    **Core features:**
    * **Unified auth:** JWT/OAuth2/PASETO tokens работают на всех protocols
    * **Rate limiting:** per-client, per-protocol, per-endpoint через Redis
    * **Request/response transformation:** Protobuf ↔ JSON ↔ REST mappings
    * **Caching layer:** Redis для responses, HTTP cache headers для REST
    * **Observability:** единый trace ID проходит через все protocols
    * **Circuit breaking:** per-upstream circuit breakers
    * **Load shedding:** при перегрузке отбрасываем "дешёвые" protocols (GraphQL introspection, REST OPTIONS)
    * **Protocol negotiation:** client указывает предпочтения через `Accept`/`Content-Type`
    * **SDK generation:** auto-generate clients для всех protocols из единой schema
    * **API versioning:** per-protocol versioning strategy
    * **Documentation:** auto-generated OpenAPI, GraphQL introspection, Connect/Protobuf reflection
    
    **Performance targets:**
    * 50k RPS sustained
    * <10ms p50, <50ms p99 gateway overhead
    * Protocol translation <1ms
    * Zero-downtime deployments через blue-green
    
    **Security:**
    * mTLS для internal services
    * WAF rules для public endpoints
    * DDoS protection per client
    * Request size limiting per protocol
    * SSRF protection для webhook delivery и internal calls

101. **Webhooks — это at-least-once delivery.**: Всегда документируйте это. Клиенты обязаны реализовать idempotency через `event.id`. Одна и та же доставка может прийти дважды.

102. **HMAC signatures обязательны.**: Без подписи любой может подделать webhook и выполнить действия от имени вашей платформы. Используйте HMAC-SHA256 + timestamp + constant-time comparison.

103. **Exponential backoff + jitter — не опция, а must.**: Без jitter массовый сбой у крупного клиента DoS-нет его сервера retries от всех ваших webhook'ов одновременно.

104. **Никогда не доставляйте webhooks синхронно.**: Всегда через background worker queue. Slow endpoint не должен блокировать весь delivery pipeline.

105. **Dead letter queue и manual retry.**: После N failures отключайте endpoint и алертите клиента. Дайте ему UI для просмотра failed deliveries и manual retry.

106. **Test all protocols в CI.**: Интеграционные тесты должны покрывать каждый protocol: REST endpoint, GraphQL query, Connect call, webhook delivery, SSE event, JSON-RPC batch.

107. **Блок 18 (Webhooks)**: — начните после Блока 13 (AppSec), так как Webhooks напрямую используют HMAC из Блока 10 и защиту от SSRF из Блока 13. Понимание retry/backoff требует знаний о concurrency из Блока 1 (GMP).

108. **Observability across protocols.**: Один request может пройти через REST → gRPC → webhook delivery. Сквозной `trace_id` через все protocols — это must have для debugging.

109. **Right tool for the job:**
   - Public API, ресурсы → REST
   - Mobile, flexible queries → GraphQL  
   - Межсервисное → gRPC/Connect
   - Real-time server→client → SSE
   - Third-party events → Webhooks
   - Bidirectional chat → WebSocket

110. **CORS и preflight — боль multi-protocol API.**: Connect требует specific allowed headers. SSE не требует preflight. WebSocket использует own handshake. Настраивайте per-protocol.

111. **Блок 19 (SSE)**: — проходите после Webhooks, так как SSE — это тот же HTTP, но с long-lived соединениями. Знание `http.Flusher` и `CloseNotifier` связывается с `netpoller` и `epoll` из Блока 6.

112. **Authentication единый, protocols разные.**: JWT/OAuth2 token должен работать на всех protocols. Middleware-слой, который извлекает identity независимо от protocol.

113. **Rate limiting per client, не per protocol.**: Клиент с 1000 RPS лимитом не должен иметь 1000 RPS на REST + 1000 на Connect + 1000 на SSE. Unified quota across protocols.

114. **Блок 20 (JSON-RPC 2.0)**: — после SSE, так как JSON-RPC часто используется как альтернатива REST для внутренних сервисов. Batch processing и reflection требуют знаний из Блока 7 (reflect).

115. **Backward compatibility — закон.**: Public API не должен ломать existing clients. Deprecation period минимум 6-12 месяцев. Versioning через URL (`/v2/`) или headers.

116. **Performance budgets per protocol.**: SSE connection overhead ~10KB memory, WebSocket ~20KB, REST request ~1KB. При 1M concurrent connections это разница в 10GB vs 20GB vs 1GB.
