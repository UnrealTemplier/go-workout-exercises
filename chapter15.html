Упражнение #1

Методы для кастомных типов на базе примитивов: type MyDuration int и правило локальности пакета

📌 Условие задачи

Создайте кастомный тип на базе встроенного: type MyDuration int. Напишите для него метод ToMinutes() float64 и ToSeconds() int. Проверьте вызов методов на переменной этого типа. Объясните, почему нельзя объявлять методы для базовых типов (например, напрямую для int) или для типов из чужих пакетов.

💡 Теоретический фундамент и концепция

Методы на пользовательских типах (Defined Types) и Receiver в Go:

  • В Go методы можно объявлять для любого именованного типа, объявленного в том же пакете, кроме базовых встроенных примитивов (int, string, float64) и указателей *T;
  • Синтаксис type MyDuration int создает совершенно новый определенный тип (Defined Type), сохраняющий базовое представление памяти int, но изолирующий набор методов (Method Set);
  • Правило локальности пакета (Package Locality Rule): Запрещено добавлять методы к типам, объявленным в других пакетах (например, time.Duration или http.Request). Это предотвращает коллизии методов (Orphan Rule) и обеспечивает модульность.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем тип type MyDuration int (время в миллисекундах).
2. Реализуем метод (d MyDuration) ToSeconds() int с получателем-значением (Value Receiver).
3. Реализуем метод (d MyDuration) ToMinutes() float64.
4. В main создаем переменную d := MyDuration(150000) и вызываем методы.
📄 main.go 
package main

import "fmt"

type MyDuration int

func (d MyDuration) ToSeconds() int {
	return int(d) / 1000
}

func (d MyDuration) ToMinutes() float64 {
	return float64(d) / 60000.0
}

func main() {
	d := MyDuration(150000)
	fmt.Printf("Длительность: %d мс\n", d)
	fmt.Printf("В секундах:   %d с\n", d.ToSeconds())
	fmt.Printf("В минутах:    %.2f мин\n", d.ToMinutes())
}
📄 Терминал 
go run main.go

# В секундах:   150 с
# В минутах:    2.50 мин
⚙️ Под капотом Go (Compiler, Linker & Runtime)

На уровне ассемблера метод func (d MyDuration) ToSeconds() int компилируется в обычную функцию main.MyDuration.ToSeconds(d MyDuration) int, где получатель (receiver) передается как первый скрытый параметр.

⚠️ Частые грабли и ошибки новичков

Вычисление расстояния Distance(other Point) и автоматическое разыменование получателя

📌 Условие задачи

Объяви тип Point с методом Distance(other Point) float64 (value receiver). Вычисли расстояние между двумя точками. Покажи, что метод можно вызвать и на значении, и на указателе (Go автоматически разыменовывает/берёт адрес).

💡 Теоретический фундамент и концепция

Value Receiver и автоматическое разыменование (Automatic Dereferencing):

  • Метод с Value Receiver (p Point) получает полную копию структуры в момент вызова;
  • Если метод вызывается на указателе ptr := &Point{}, компилятор Go автоматически преобразует вызов ptr.Distance(p2) в (*ptr).Distance(p2).

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем структуру Point с полями X, Y float64.
2. Реализуем метод (p Point) Distance(other Point) float64 с формулой Евклидова расстояния.
3. Создаем значение p1 и указатель pPtr := &p1.
4. Демонстрируем эквивалентность вызовов.
📄 main.go 
package main

import (
	"fmt"
	"math"
)

type Point struct {
	X, Y float64
}

func (p Point) Distance(other Point) float64 {
	dx := p.X - other.X
	dy := p.Y - other.Y
	return math.Sqrt(dx*dx + dy*dy)
}

func main() {
	p1 := Point{X: 0, Y: 0}
	p2 := Point{X: 3, Y: 4}

	d1 := p1.Distance(p2)
	fmt.Printf("Расстояние (вызов на значении):   %.2f\n", d1)

	pPtr := &p1
	d2 := pPtr.Distance(p2)
	fmt.Printf("Расстояние (вызов на указателе): %.2f\n", d2)
}

# Расстояние (вызов на указателе): 5.00

Компилятор анализирует AST и вставляет инструкцию загрузки значения из памяти перед вызовом.

⚠️ Частые грабли и ошибки новичков
  • Использование Value Receiver для структур большого размера (>128 байт), что приводит к лишним аллокациям и копированию памяти при каждом вызове.

Ответ: Value Receiver выбирают для маленьких иммутабельных типов (примитивы, маленькие структуры <= 16 байт). Pointer Receiver обязателен, если метод мутирует состояние или структура содержит мьютексы (sync.Mutex).

	"fmt"

)

type SafeCounter struct {
	*sync.Mutex // Указатель на мьютекс
	val         int
}

func NewSafeCounter() *SafeCounter {
	return &SafeCounter{Mutex: &sync.Mutex{}}
}

	c.Lock() // Promoted Lock
	defer c.Unlock()
	c.val++

		go func() {

			c.Inc()
		}()
	}
	wg.Wait()

}

package main

import (
	"crypto/sha256"
	"encoding/hex"
	"fmt"
)

type User struct {
	Email        string
	passwordHash string
}

func (u *User) SetPassword(raw string) {
	hash := sha256.Sum256([]byte(raw))
	u.passwordHash = hex.EncodeToString(hash[:])
}

func (u *User) CheckPassword(raw string) bool {
	hash := sha256.Sum256([]byte(raw))
	return u.passwordHash == hex.EncodeToString(hash[:])
}

func main() {
	u := &User{Email: "dev@yandex.ru"}
	u.SetPassword("super_secret_123")
	fmt.Println("Пароль верен?", u.CheckPassword("super_secret_123"))
	fmt.Println("Пароль неверен?", u.CheckPassword("wrong_pass"))
}

package main

	"fmt"
	"strings"
)

type Validator struct {
	errs []string
}

func (v *Validator) Required(val, field string) *Validator {
	if strings.TrimSpace(val) == "" {
		v.errs = append(v.errs, fmt.Sprintf("Поле %q обязательно", field))
	}
	return v
}

	if len(val) < min {
		v.errs = append(v.errs, fmt.Sprintf("Поле %q должно быть не короче %d символов", field, min))
	}
	return v
}

func (v *Validator) Errors() []string { return v.errs }

	v := &Validator{}
	v.Required("", "username").MinLen("123", 6, "password")
	fmt.Println("Форма валидна?", v.IsValid())
	for _, e := range v.Errors() {
		fmt.Println("❌", e)
	}
}

💡 Теоретический фундамент и концепция

Интерфейс в Go равен nil ТОЛЬКО если и type == nil, и data == nil. Типизированный nil (*MyError)(nil) имеет type != nil, поэтому if err != nil вернет TRUE!

2. Пишем ошибочную функцию GetErrorBad() error, возвращающую *MyError(nil).

4. Сравниваем результаты.
📄 main.go 
package main

type MyError struct{ Msg string }
func (m *MyError) Error() string { return m.Msg }

// ❌ ОШИБКА: типизированный nil попадает в интерфейс
func GetErrorBad() error {
	var err *MyError = nil
	return err // eface{type: *MyError, data: 0x0} != nil !
}

// ✅ ИСПРАВЛЕНИЕ: возврат явного nil
func GetErrorGood() error {
	var err *MyError = nil
	if err != nil {
		return err
	}
	return nil // eface{type: 0x0, data: 0x0} == nil
}

func main() {
	if err := GetErrorBad(); err != nil {
		fmt.Println("🚨 БАГ: err != nil сработал для nil указателя!")
	}

	if err := GetErrorGood(); err == nil {
		fmt.Println("✅ ИСПРАВЛЕНО: err == nil сработал корректно")
	}
}

	"errors"
	"fmt"
)

type OrderState string

const (
	Created   OrderState = "CREATED"
	Paid      OrderState = "PAID"
	Shipped   OrderState = "SHIPPED"
	Cancelled OrderState = "CANCELLED"
)

type Order struct {
	ID    int
	state OrderState
}

	if o.state != Created {

	return nil
}

📌 Условие задачи

Метод Clone(): структура Profile (Name string, Tags []string, Meta *Metadata). Метод Clone() *Profile создаёт глубокую копию (deep copy) — модификация срезов и указателей в клоне не влияет на оригинал.

💡 Теоретический фундамент и концепция

Поверхностное копирование (Shallow Copy) копирует указатели на те же срезы; Deep Copy выделяет независимую память.

🔍 Пошаговый ход решения и ход мысли инженера

2. Реализуем Clone() с созданием копий среза и указателя.

📄 main.go 
package main

import "fmt"

type Metadata struct{ Score int }

type Profile struct {
	Name string
	Tags []string
	Meta *Metadata
}

func (p *Profile) Clone() *Profile {
	if p == nil { return nil }
	
	// 1. Копируем срез тегов:
	tagsCopy := make([]string, len(p.Tags))
	copy(tagsCopy, p.Tags)

	// 2. Копируем структуру метаданных:
	var metaCopy *Metadata
	if p.Meta != nil {
		metaCopy = &Metadata{Score: p.Meta.Score}
	}

	return &Profile{Name: p.Name, Tags: tagsCopy, Meta: metaCopy}
}

func main() {
	p1 := &Profile{Name: "Илья", Tags: []string{"go", "k8s"}, Meta: &Metadata{Score: 100}}
	p2 := p1.Clone()

	p2.Tags[0] = "python"

package main

import (
	"fmt"
	"strings"
)

type HandlerFunc func(req string) string
type Middleware func(HandlerFunc) HandlerFunc

func LoggingMiddleware(next HandlerFunc) HandlerFunc {
	return func(req string) string {
		fmt.Printf("[LOG]: Получен запрос %q\n", req)
		return next(req)
	}
}

func AuthMiddleware(next HandlerFunc) HandlerFunc {
	return func(req string) string {
		if strings.Contains(req, "admin") {
			return next(req)
		}
		return "403 Forbidden"
	}
}

func main() {
	baseHandler := func(req string) string { return "200 OK: " + req }

	// Сборка цепочки:
	chain := LoggingMiddleware(AuthMiddleware(baseHandler))

	fmt.Println("Ответ 1:", chain("user_action"))
	fmt.Println("Ответ 2:", chain("admin_action"))
}

📌 Условие задачи

Потокобезопасная коллекция: структура ThreadSafeMap[K comparable, V any] с приватным sync.RWMutex и приватной map. Методы Set(k, v), Get(k) (v, bool), Delete(k), Len() int.

💡 Теоретический фундамент и концепция

RWMutex позволяет множественное параллельное чтение и эксклюзивную запись.

🔍 Пошаговый ход решения и ход мысли инженера

1. Объявляем дженерик-структуру ThreadSafeMap[K comparable, V any].
2. Реализуем Set, Get, Delete, Len с RLock/Lock.

📄 main.go 
package main

import (
	"fmt"
	"sync"
)

type ThreadSafeMap[K comparable, V any] struct {
	mu   sync.RWMutex
	data map[K]V
}

func NewThreadSafeMap[K comparable, V any]() *ThreadSafeMap[K, V] {
	return &ThreadSafeMap[K, V]{data: make(map[K]V)}
}

func (m *ThreadSafeMap[K, V]) Set(k K, v V) {
	m.mu.Lock()
	defer m.mu.Unlock()
	m.data[k] = v
}

func (m *ThreadSafeMap[K, V]) Get(k K) (V, bool) {
	m.mu.RLock()
	defer m.mu.RUnlock()
	val, ok := m.data[k]
	return val, ok
}

func main() {
	sm := NewThreadSafeMap[string, int]()
	sm.Set("users_online", 1420)
	val, _ := sm.Get("users_online")
	fmt.Println("Онлайн:", val)
}

	return nil

	Deleter

}

func NewInMemoryRepo[T any]() *InMemoryRepo[T] {

}

func (r *InMemoryRepo[T]) Get(id int) (T, bool) { v, ok := r.store[id]; return v, ok }
func (r *InMemoryRepo[T]) Save(id int, val T)   { r.store[id] = val }
func (r *InMemoryRepo[T]) Delete(id int)        { delete(r.store, id) }

	repo.Save(1, "Запись 1")

}

🔍 Пошаговый ход решения и ход мысли инженера

📄 main.go 
package main

import (
	"errors"
	"fmt"
)

type Server struct {
	Host    string
	Port    int
	MaxConn int
}

type Option func(*Server) error

func WithHost(h string) Option {
	return func(s *Server) error {
		if h == "" { return errors.New("host не может быть пустым") }
		s.Host = h
		return nil
	}
}

func WithPort(p int) Option {
	return func(s *Server) error {
		if p < 1 || p > 65535 { return fmt.Errorf("неверный порт: %d", p) }
		s.Port = p
		return nil
	}
}

func NewServer(opts ...Option) (*Server, error) {
	srv := &Server{Host: "127.0.0.1", Port: 8080, MaxConn: 100}
	for _, opt := range opts {
		if err := opt(srv); err != nil {
			return nil, err
		}
	}
	return srv, nil
}

func main() {
	s, err := NewServer(WithHost("0.0.0.0"), WithPort(9000))
	if err != nil { panic(err) }
	fmt.Printf("Сервер успешно сконфигурирован: %s:%d\n", s.Host, s.Port)
}

package main

import (
	"errors"
	"fmt"
	"sync"
)

type User struct {
	ID   int
	Name string
}

type UserRepository interface {
	Create(u *User) error
	FindByID(id int) (*User, error)
}

type InMemoryUserRepository struct {
	mu    sync.RWMutex
	users map[int]*User
}

func NewInMemoryUserRepository() *InMemoryUserRepository {
	return &InMemoryUserRepository{users: make(map[int]*User)}
}

func (r *InMemoryUserRepository) Create(u *User) error {
	m.mu.Lock()
	defer m.mu.Unlock()
	r.users[u.ID] = u
	return nil
}

func (r *InMemoryUserRepository) FindByID(id int) (*User, error) {
	m.mu.RLock()
	defer m.mu.RUnlock()
	u, ok := r.users[id]
	if !ok { return nil, errors.New("пользователь не найден") }
	return u, nil
}

func main() {
	var repo UserRepository = NewInMemoryUserRepository()
	_ = repo.Create(&User{ID: 1, Name: "Артем"})
	u, _ := repo.FindByID(1)
	fmt.Println("Найден пользователь:", u.Name)
}

package main

import (
	"errors"
	"fmt"
	"strings"
)

type QueryBuilder struct {
	fields []string
	table  string
	where  string
	limit  int
}

func NewQueryBuilder() *QueryBuilder { return &QueryBuilder{} }
func (q *QueryBuilder) Select(f ...string) *QueryBuilder { q.fields = f; return q }
func (q *QueryBuilder) From(t string) *QueryBuilder       { q.table = t; return q }
func (q *QueryBuilder) Where(w string) *QueryBuilder      { q.where = w; return q }
func (q *QueryBuilder) Limit(l int) *QueryBuilder         { q.limit = l; return q }

func (q *QueryBuilder) Build() (string, error) {
	if q.table == "" { return "", errors.New("секция FROM обязательна") }
	fields := "*"
	if len(q.fields) > 0 { fields = strings.Join(q.fields, ", ") }
	sql := fmt.Sprintf("SELECT %s FROM %s", fields, q.table)
	if q.where != "" { sql += " WHERE " + q.where }
	if q.limit > 0 { sql += fmt.Sprintf(" LIMIT %d", q.limit) }
	return sql + ";", nil
}

func main() {
	sql, _ := NewQueryBuilder().
		Select("id", "email", "status").
		From("users").
		Where("status = 'active'").
		Limit(10).
		Build()
	fmt.Println("Сгенерированный SQL:", sql)
}

💡 Теоретический фундамент и концепция

Асинхронная или синхронная шина событий для слабой связанности микросервисных компонентов.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем EventEmitter{ handlers map[string][]func(any) }.
2. Реализуем On, Emit, Off с sync.RWMutex.
3. Тестируем отправку события нескольким подписчикам.
📄 main.go 
package main

import (
	"fmt"
	"sync"
)

type EventEmitter struct {
	mu       sync.RWMutex
	handlers map[string][]func(data any)
}

func NewEventEmitter() *EventEmitter {
	return &EventEmitter{handlers: make(map[string][]func(any))}
}

func (e *EventEmitter) On(event string, fn func(any)) {
	e.mu.Lock()
	defer e.mu.Unlock()
	e.handlers[event] = append(e.handlers[event], fn)
}

func (e *EventEmitter) Emit(event string, data any) {
	e.mu.RLock()
	defer e.mu.RUnlock()
	for _, fn := range e.handlers[event] {
		fn(data)
	}
}

func main() {
	emitter := NewEventEmitter()

	emitter.On("order_created", func(d any) { fmt.Println("📧 Email сервис: заказ", d) })
	emitter.On("order_created", func(d any) { fmt.Println("📦 Склад: зарезервирован товар для заказа", d) })

	emitter.Emit("order_created", 1045)
}

	Endpoint string

Упражнение #124

Паттерн Пул Объектов (Object Pool): ConnectionPool с ограничением соединений через буферизированный канал

📌 Условие задачи

Паттерн Object Pool: структура ConnectionPool с методами Acquire() (*Connection, error), Release(*Connection). Инкапсуляция управления ресурсами с ограничением максимального количества соединений.

💡 Теоретический фундамент и концепция

Инкапсуляция пула соединений через буферизированный канал chan *Connection.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем Connection{ID int}.
2. Создаем ConnectionPool{ pool chan *Connection }.
3. Реализуем Acquire и Release.
📄 main.go 
package main

import (
	"errors"
	"fmt"
)

type Connection struct{ ID int }

type ConnectionPool struct {
	conns chan *Connection
}

func NewConnectionPool(size int) *ConnectionPool {
	cp := &ConnectionPool{conns: make(chan *Connection, size)}
	for i := 1; i <= size; i++ {
		cp.conns <- &Connection{ID: i}
	}
	return cp
}

func (cp *ConnectionPool) Acquire() (*Connection, error) {
	select {
	case conn := <-cp.conns:
		return conn, nil
	default:
		return nil, errors.New("пул исчерпан")
	}
}

func (cp *ConnectionPool) Release(conn *Connection) {
	cp.conns <- conn
}

func main() {
	pool := NewConnectionPool(2)
	c1, _ := pool.Acquire()
	fmt.Printf("Захвачено соединение #%d\n", c1.ID)
	pool.Release(c1)
	fmt.Println("Соединение успешно возвращено в пул!")
}

go run main.go

# Соединение успешно возвращено в пул!

Буферизированный канал реализует потокобезопасную очередь без дополнительных мьютексов.

⚠️ Частые грабли и ошибки новичков

Упражнение #125

Анализ производительности: бенчмарк Value Receiver vs Pointer Receiver для структур разного размера

📌 Условие задачи

Сравнение производительности Value vs Pointer Receiver: напиши бенчмарк для вызова метода с value receiver vs pointer receiver для структуры разного размера (16 байт, 128 байт, 1 КБ). Сделай выводы о накладных расходах на копирование.

💡 Теоретический фундамент и концепция

Копирование структур размером свыше 64–128 байт создает существенный оверхед по CPU и памяти.

🔍 Пошаговый ход решения и ход мысли инженера

1. Создаем структуру LargePayload (1024 байта).
2. Реализуем метод ProcessValue (Value Receiver) и ProcessPointer (Pointer Receiver).
3. Сравниваем время выполнения.
📄 main.go 
package main

import (
	"fmt"
	"time"
)

type LargePayload struct {
	data [1024]byte // 1 КБ памяти
}

func (p LargePayload) ProcessValue() byte   { return p.data[0] }
func (p *LargePayload) ProcessPointer() byte { return p.data[0] }

func main() {
	obj := LargePayload{}
	const N = 10_000_000

	// 1. Тест Value Receiver (копирует 1 КБ 10 млн раз):
	t0 := time.Now()
	for i := 0; i < N; i++ { _ = obj.ProcessValue() }
	durVal := time.Since(t0)

	// 2. Тест Pointer Receiver (передает 8 байт указателя):
	t1 := time.Now()
	for i := 0; i < N; i++ { _ = obj.ProcessPointer() }
	durPtr := time.Since(t1)

	fmt.Printf("Value Receiver:   %v\n", durVal)
	fmt.Printf("Pointer Receiver: %v\n", durPtr)
}

go run main.go
# Value Receiver:   8.2ms
# Pointer Receiver: 2.1ms
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Pointer Receiver передает адрес в регистре RDI (8 байт), избегая инструкции memmove.

⚠️ Частые грабли и ошибки новичков
  • Преждевременная оптимизация маленьких структур (Point, Time), где Value Receiver быстрее за счет отсутствия аллокаций в куче.
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «Когда Value Receiver быстрее Pointer Receiver?»

Ответ: Для структур размером $\le 16$ байт, так как они полностью помещаются в процессорные регистры и не вызывают escape analysis в кучу.

Упражнение #127

Финальный архитектурный проект: Чистая Архитектура (Clean Architecture) сервиса заказов

📌 Условие задачи

Финальный архитектурный проект: архитектура чистого сервиса (Clean Architecture). Слой Domain (сущности, интерфейсы репозиториев), слой UseCase (бизнес-логика через DI), слой Infrastructure (InMemory репозиторий), слой Delivery (HTTP хендлер / CLI). Все 4 слоя связаны через интерфейсы и композицию.

💡 Теоретический фундамент и концепция

Священный Грааль микросервисной разработки: инверсия зависимостей (DIP), слабая связанность и 100% тестируемость всех 4 слоев Clean Architecture.

🔍 Пошаговый ход решения и ход мысли инженера

1. Слой Domain: сущность Order и интерфейс OrderRepository.
2. Слой UseCase: сервис OrderUseCase с внедрением OrderRepository.
3. Слой Infrastructure: реализация InMemoryOrderRepository.
4. Слой Delivery: CLI/HTTP адаптер, вызывающий UseCase.
📄 main.go 
package main

import (
	"errors"
	"fmt"
	"sync"
)

// 1. DOMAIN LAYER
type Order struct {
	ID     int
	Amount float64
	Status string
}

type OrderRepository interface {
	Save(o *Order) error
	FindByID(id int) (*Order, error)
}

// 2. USECASE LAYER
type OrderUseCase struct {
	repo OrderRepository
}

func NewOrderUseCase(r OrderRepository) *OrderUseCase {
	return &OrderUseCase{repo: r}
}

func (uc *OrderUseCase) CreateOrder(id int, amt float64) error {
	if amt <= 0 { return errors.New("сумма заказа должна быть больше 0") }
	order := &Order{ID: id, Amount: amt, Status: "CREATED"}
	return uc.repo.Save(order)
}

// 3. INFRASTRUCTURE LAYER
type InMemoryOrderRepo struct {
	mu     sync.RWMutex
	orders map[int]*Order
}

func NewInMemoryOrderRepo() *InMemoryOrderRepo {
	return &InMemoryOrderRepo{orders: make(map[int]*Order)}
}

func (r *InMemoryOrderRepo) Save(o *Order) error {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.orders[o.ID] = o
	return nil
}

func (r *InMemoryOrderRepo) FindByID(id int) (*Order, error) {
	r.mu.RLock()
	defer r.mu.RUnlock()
	o, ok := r.orders[id]
	if !ok { return nil, errors.New("заказ не найден") }
	return o, nil
}

// 4. DELIVERY LAYER (Main)
func main() {
	// Сборка графа зависимостей (Dependency Injection):
	repo := NewInMemoryOrderRepo()
	useCase := NewOrderUseCase(repo)

	// Исполнение бизнес-сценария:
	if err := useCase.CreateOrder(7001, 15990.0); err != nil {
		panic(err)
	}

	order, _ := repo.FindByID(7001)
	fmt.Printf("🎯 [Clean Architecture] Заказ #%d успешно оформлен на сумму %.2f руб. (Статус: %s)\n", 
		order.ID, order.Amount, order.Status)
}
📄 Терминал 
go run main.go
# 🎯 [Clean Architecture] Заказ #7001 успешно оформлен на сумму 15990.00 руб. (Статус: CREATED)
⚙️ Под капотом Go (Compiler, Linker & Runtime)

Поток управления направлен от Delivery к Domain, а зависимости направлены внутрь к Domain (Dependency Inversion Principle).

⚠️ Частые грабли и ошибки новичков
  • Импорт слоев Delivery или Infrastructure внутрь Domain (Domain должен быть абсолютно чистым).
🏢 В продакшене BigTech и на собеседованиях

Вопрос с собеседования: «В чем ключевое отличие Clean Architecture от стандартной 3-уровневой архитектуры (Controller-Service-DAO)?»

Ответ: В Clean Architecture слой бизнес-логики (Domain/UseCase) не зависит от базы данных и фреймворков. База данных и HTTP-роутеры являются лишь внешними плагинами (деталями реализации), подключаемыми через интерфейсы.
