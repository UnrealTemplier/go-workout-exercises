В этом файле собраны уникальные упражнения по теме **"Документоориентированная база данных MongoDB"**, отсортированные по возрастанию сложности.

101. **Schema design first.**: В отличие от SQL, в MongoDB схема определяется паттернами доступа. Embed когда читаете вместе, reference когда читаете отдельно.

102. **Compound indexes — ваше всё.**: 90% slow queries в MongoDB решаются правильным compound index. Помните правило ESR (Equality, Sort, Range).

103. **Transactions только когда нужны.**: MongoDB transactions имеют overhead. Для большинства use cases достаточно single-document atomicity.

104. **Change Streams для real-time.**: Не делайте polling. Используйте Change Streams для event-driven architecture.

105. **Aggregation pipeline — мощный, но опасный.**: Сложные pipelines могут быть медленнее, чем application-side processing. Всегда проверяйте `explain()`.

106. **Блок 14 (MongoDB)**: — начните после Блока 10 (криптография), так как MongoDB часто используется для хранения токенов и сессий. Понимание транзакций требует знаний из Блока 1 (GMP — concurrency и атомарность).

107. **Right tool for the job.**: Не пытайтесь использовать одну БД для всего. PostgreSQL для OLTP, ClickHouse для OLAP, Elasticsearch для поиска, MongoDB для гибкой схемы, Redis для кэша.

108. **Блок 16 (Elasticsearch)**: — после ClickHouse, чтобы сравнить аналитические и поисковые движки. Знание `mmap` из Блока 6 поможет понять, как Lucene использует memory-mapped files.

109. **Мониторинг обязателен.**: Каждая БД должна экспортировать метрики в Prometheus: connection pool usage, query latency, replication lag, disk usage.

110. **Backups тестируйте.**: Backup без restore test — это не backup. Регулярно тестируйте восстановление.

111. **Schema migrations в CI.**: Используйте golang-migrate или goose для управления схемой. Миграции должны быть в том же PR, что и код.

112. **Connection pooling.**PgBouncer для PostgreSQL, connection pools в драйверах для MongoDB/ClickHouse. Без pooling вы исчерпаете connections.

113. **Блок 17 (CDC)**: — финальный блок, требует понимания всех предыдущих: PostgreSQL WAL → Kafka/Redis → ClickHouse/Elasticsearch. Concurrency из Блока 1 критичен для fault-tolerant consumer.
